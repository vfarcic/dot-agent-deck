## CPU, memory and disk per agent run

A new program, `dot-agent-deck-collector`, shows which agent run is loading a busy Linux machine. It sends each run's CPU time, memory and process count every 15 seconds, and the disk space of each worktree a run works in every 5 minutes, as OpenTelemetry metrics to the same backend as the deck's run traces. Each run's figures carry its `deck.run.id`, so you can see them next to its `agent.run` span and the agent's own telemetry.

A process that detaches from its agent still counts toward that agent's run. Memory is reported as each run's proportional share (`deck.run.memory.pss`, split into `anon`, `file` and `shmem`), so memory that several processes share is counted once instead of for each of them. Disk is reported once per worktree, however many runs share it, and use that belongs to no run is reported as unattributed. Paths are not sent unless you pass `--send-worktree-paths`, and `dot-agent-deck-collector worktree-id <path>` tells you which worktree an id is.

Run one collector per machine, as the user who runs your decks and with the same `OTEL_EXPORTER_OTLP_*` variables as the daemon. It collects only its own user's processes unless you pass `--all-users`. A systemd user service is the easiest way to keep it running. Try it with `dot-agent-deck-collector --once --stdout`. Releases now include `dot-agent-deck-collector-linux-amd64` and `dot-agent-deck-collector-linux-arm64`, the Nix package installs it next to the deck, and a source build produces it too. Homebrew does not install it. It runs outside the deck, so the TUI and the desktop app do not show these figures. The collector works on Linux only. At the default interval it used about 1.4% of one core on a heavily loaded machine. Detached work that finishes between two samples is undercounted.

See [CPU, memory and disk per run](https://agent-deck.devopstoolkit.ai/docs/telemetry.md#cpu-memory-and-disk-per-run).
