## Repo infrastructure: the notification MCP server is gone, and orphaned processes get reaped

No user-facing change and nothing under `src/` — this is how this repository's own orchestration notifies, plus a machine-level cleanup net.

An orphaned `telegram-mcp-bot` process was found burning **~104% of one core**, and had been for **1 day 12 hours** — about 78% of all user CPU on the dev box, while every agent in the deck was idle. It held 860 MB RSS against 63 MB for its healthy siblings, ignored `SIGTERM`, and needed `SIGKILL`. `telegram-mcp-bot@1.1.0` installs a global `uncaughtException` handler that logs instead of exiting, by design — *"Logging instead of dying keeps the stdio transport alive so the host stays connected"* — and with `startPolling()` holding the event loop open and no stdin-EOF handler, it cannot die when its parent does. Orphaned by an unclean session exit, both pipes break and the handler logs the resulting `EPIPE` through the pipe that just died, re-entering itself. Reproduced in isolation with the same pattern and no Telegram involved: with the polling loop it survives its parent and spins a core; without it, it exits on its own.

The polling existed to serve an inbound side this repo already forbade reading (`.dot-agent-deck.toml` has said *"Never read `telegram_get_updates`"* — an unauthenticated inbound channel and therefore a prompt-injection path — since PRD #126), so the whole cost bought nothing. It also scaled badly: Telegram permits exactly one `getUpdates` poller per bot token, and `.mcp.json` is tracked at the repo root, so every dispatch worktree inherited it — measured at 14 processes, 924 MB RSS, one shared token, 13 of them permanently losing a 409 fight and retrying every 30 seconds forever.

`scripts/notify.sh` replaces it with one `curl` call, restoring the shell-helper approach PRD #126 originally chose for the same reason (*"this repo runs four different agents; a shell CLI works for all of them with no per-agent wiring"*). Two rules that were instructions an agent had to follow are now properties of the tool: `chat_id` is always explicit and an unset `TELEGRAM_CHAT_ID` skips the send rather than retargeting it to whoever messaged the bot most recently, and there is no inbound path at all. The per-client tool-name trap that a live send once failed on goes away with the server.

`scripts/reap-orphans.sh` and its systemd **user** timer are the net for the next one, and it is deliberately a net rather than a fix — with the polling server gone it should never fire for this cause. It reaps only processes that are both owned by the invoking user and orphaned to `PPid 1`, under three rules: sustained CPU (two samples, not one), known orphaned MCP servers, and an **opt-in** catch-all by age. It dry-runs unless passed `--apply`, like `cargo xtask clean-e2e-tmp`. The never-kill list is matched against the executable name rather than the whole command line, because matching the full cmdline exempts any process whose *path* contains one of those words — found when a test spinner refused to be detected from a scratch directory under a checkout named `dot-agent-deck`. `dot-agent-deck daemon serve` is the entry that matters most there: it is orphaned by design, and its in-memory role maps exist nowhere else.
