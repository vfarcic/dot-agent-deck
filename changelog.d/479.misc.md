## The socket-timeout tests now document the behaviour that shipped, not the bug they were written against

`error/socket/003`–`006` were written test-first, while `request_from_socket`'s unbounded read was still live, and #419 landed the fix in the same PR without revisiting the wording. So the merged tree asserted, in its own test catalog, the opposite of what the code does: `error/socket/005`'s `tests/CATALOG.md` **title** read "`request_from_socket` **still hangs** against a peer that dribbles one non-newline byte…", when the whole point of that test is that it no longer does. Anyone scanning the catalog for "is the socket read bounded?" read a false negative on a fix that had shipped.

The title now names the asserted, green behaviour — the total-operation deadline fires even though every byte re-arms the per-read idle timeout — which is the shape its `003`/`004`/`006` siblings already had, so this was one entry left behind rather than a house style. The present-tense bug descriptions in the `#[spec]` Scenario comments in `src/hook.rs` ("has no read/write bound of its own, so against this daemon it hangs forever", "`request_from_socket` never returns") are past tense, and the future-tense references to a fix already in the same commit ("the production timeout the fix will add", "whatever operation-level deadline the fix chooses", "the 5s bound the fix adds", "passes both before and after the fix") now say what actually shipped. The historical explanation survives in every case: a reader still learns what the bug was and why each test is shaped the way it is, because that is what makes the stub daemons legible.

Three stale claims beyond the ones the issue listed came out of the same sweep. `error/socket/003`'s "does not assert" bullet said `SocketReply`'s three-way outcome "exists for a not-yet-submitted caller" — `main.rs` reads all three variants on `delegate`, `pane restart` and `pane spawn`, and on the `work-done`/`dispatch` acknowledgement since #1129, and has to, because on each of them "never reached the daemon" and "reached a daemon that did not answer" must be reported differently. The bullet now says what the family does assert instead: `004` and `007` assert `SocketReply::Line`, `006` asserts `SocketReply::NoReply`, and none of `001`–`008` asserts `SocketReply::Unreachable`. `error/socket/005`'s said "the shared, **vulnerable** `request_from_socket_inner` code path", present tense, of a path whose vulnerability is what #419 closed. And two in-body comments in `socket_005` still spoke of the deadline as unchosen ("the fix has not chosen yet", "whatever sane deadline the fix picks").

Prose only: no code, no assertion and no test behaviour changed, and the diff is comments plus catalog text. The issue's suggested follow-on — teaching `linkage-check` to flag RED-phase tells like "still hangs" or "the fix will add" in a Scenario comment or catalog title — is deliberately not done here; it is tooling work with its own design questions and belongs in its own issue.
