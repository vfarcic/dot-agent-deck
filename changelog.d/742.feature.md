## The desktop app can now observe several decks at once

The agent overview gains an **All Decks** option on the Deck selector: pick it and every configured deck's agents merge into one screen, each row attributable to its own deck, each deck carrying its own connection state. The header reports how many of the configured decks are actually up rather than just an agent count, so a disconnected deck shows as a degraded group instead of silently vanishing from the total. One unreachable deck no longer stalls the others — establishing a connection to a dead endpoint used to hold a lock across the whole map, so a single bad handshake queued every other deck behind its own connect timeout; that lock is now scoped per deck. The deck screen — tiles with live terminals — is unchanged and stays single-deck by design: attaching a terminal to a remote deck is out of scope here and is the subject of a follow-up.

A configured deck with no socket path yet is now **shown and counted** rather than silently omitted. It was not: the observed set was built by dropping every row the app could not connect to, and the same list was also what the header counted and what the screen drew — so three configured decks with one address still to be discovered read as `2/2`, with the third in neither the numerator nor the denominator and no group anywhere on screen. "Decks the user configured" and "endpoints the app can open a connection to" are now two lists. The first gets a group, a place in the total, and the settings panel's own words — *not configured yet, press Test connection*. The second is unchanged, and is still what gets a watcher, a tunnel and a handshake: a deck with no address gets none of the three, because there is nothing to point them at.

A deck that has not answered **yet** is now shown and counted too, which is the same gap reached from the other side. The app asks the deck it resolved to for a snapshot and learns about every other deck from that deck's reply, so a remote deck did not exist on screen until its own ssh tunnel, handshake and agent list had all come back — seconds later, and up to half a minute if the tunnel was slow. The header therefore read `DECKS 1/1` and then `DECKS 2/2`: two readings that both look like nothing is wrong, with the total itself moving under the reader. It now reads `1/2` and then `2/2` — the total is right from the first frame and only the count of decks that answered climbs — and the deck that is still coming gets a group of its own, named, saying it is being waited for rather than that anything failed. It never counts among the decks that answered and contributes nothing to the agent totals, exactly as an unreachable deck does not.

That state is now bounded rather than hopeful. The three requests that stand between a deck joining the fleet and its first report — the handshake, the event subscription and the agent-list fetch — each waited for a reply indefinitely, so a deck that accepted a connection and then went silent, a wedged daemon or a stalled tunnel, was not a failure any part of the app could observe: it was a request that never finished. A deck in that condition would have sat on the fleet view waiting forever, and would equally have frozen a refresh or a snapshot with nothing on screen to say why. Each now gives up after fifteen seconds and reports a deck that took the connection and did not answer, which is a different sentence from a deck that is not there. A deck whose watcher has died — a bug rather than a state — is separately recoverable now: Reconnect starts a replacement instead of being quietly refused for the life of the app.

This is observe-only. Cross-deck attach, workflow launch and per-deck lifecycle controls (start/stop a remote deck) are deliberately not part of this change — [#1073](https://github.com/vfarcic/dot-agent-deck/issues/1073) tracks that as a separate follow-up, and a wire verb to stop a remote deck does not exist yet regardless ([#1049](https://github.com/vfarcic/dot-agent-deck/issues/1049)).

No `PROTOCOL_VERSION` change and no compatibility break: the daemon is queried the same way for one deck or ten, over the same `Hello`, snapshot and event verbs it already served, and cannot tell a fleet client from a single-deck client. An older desktop build meeting a fleet-aware settings document degrades gracefully to its local deck and preserves the new selection token unchanged, so upgrading and downgrading the desktop app independently of the daemon stays safe.

Verified against two real `daemon serve` processes and a real loopback ssh tunnel end to end (the child process, the forwarded socket, teardown, and the trust gate asserted from both sides). What no automated tier can verify is what the connected window actually renders — that needs a WebDriver-level desktop test tier that does not exist yet ([#953](https://github.com/vfarcic/dot-agent-deck/issues/953)) — so a human confirming two real decks side by side in one window is part of this feature's own verification.
