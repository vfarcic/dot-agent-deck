## `daemon status` shows a real status again, and reconnect restores it instead of `Idle`

`dot-agent-deck daemon status` printed `STATUS=-  TOOL=-` for an agent whose dashboard card was visibly `● Thinking`, and `--json` simply omitted the `status` and `active_tool` keys for it. The same root cause broke the TUI's reconnect restore: detaching and reattaching rebuilt a busy agent's card as `● Idle` rather than restoring the status the daemon already knew.

The daemon keeps two views of the panes it owns — the PTY registry, which spawns and tracks them, and its own session state, which ingests their lifecycle reports — and the two had drifted apart. Only orchestration role panes were ever announced to the session-state side, so an ordinary pane existed in the registry and nowhere else. The daemon's admission check, which exists so that an arbitrary process cannot drive session state for a pane the daemon does not own, then correctly rejected every report that pane made: agents report `running`/`waiting`/`finished`, never a session start, and only a session start could register a pane after the fact. The status was therefore never recorded, and the query that joins live state onto each agent found nothing to join.

Every pane the daemon spawns is now announced to its session state at the moment it is spawned — for panes started by the dashboard and for panes started by the scheduler and by issue dispatch, whose single-agent cards had the identical gap. The admission check itself is unchanged and just as strict: it still admits only panes this daemon spawned and has not yet stopped, so a report naming a pane nobody spawned is still refused.

Both surfaces recover together: `daemon status` reports the live status and active tool for ordinary panes, and a TUI reattach restores a working agent's card as it was rather than resetting it to `Idle`.
