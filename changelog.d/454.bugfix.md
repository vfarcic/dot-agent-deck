## `daemon status` shows a real status again, and reconnect restores it instead of `Idle`

`dot-agent-deck daemon status` printed `STATUS=-  TOOL=-` for an agent whose dashboard card was visibly `● Thinking`, and `--json` simply omitted the `status` and `active_tool` keys for it. The same root cause broke the TUI's reconnect restore: detaching and reattaching rebuilt a busy agent's card as `● Idle` rather than restoring the status the daemon already knew.

The daemon keeps two views of the panes it owns — the PTY registry, which spawns and tracks them, and its own session state, which ingests their lifecycle reports — and the two had drifted apart. Only orchestration role panes were ever announced to the session-state side, so an ordinary pane existed in the registry and nowhere else. The daemon's admission check, which exists so that an arbitrary process cannot drive session state for an agent the daemon does not own, then correctly rejected every report that pane made: agents report `running`/`waiting`/`finished`, never a session start, and only a session start could register a pane after the fact. The status was therefore never recorded, and the query that joins live state onto each agent found nothing to join.

The daemon now resolves ownership from the PTY registry itself rather than from a second list it would have to keep in step by hand — for panes started by the dashboard and for panes started by the scheduler and by issue dispatch, whose single-agent cards had the identical gap. That closes the two ends a hand-maintained list could not: a pane is owned from before its process exists, so an agent that reports faster than its spawn call returns is no longer dropped, and it stops being owned the moment its process dies, so a short-lived pane leaves nothing behind. Long scheduled-task names are covered too — the generated pane id is now kept inside the length the daemon is willing to record, where before an over-long one was discarded and the same status join failed for exactly the reason above.

What the admission check guarantees, stated as it actually is: a lifecycle report is accepted only for an agent this daemon spawned and still owns, or for a pane this daemon explicitly registered. A *session start* is deliberately weaker — it may name a pane that is not yet known, which is what lets an agent's first hook arrive before its pane is registered — so a process running as the same user can still bring a card into existence for a pane nobody spawned. That is long-standing behaviour rather than anything new here, it is not a cross-user issue (the daemon's sockets are owner-only), and tightening it is tracked separately — but it is worth stating plainly, because it is narrower than "only panes this daemon spawned" sounds.

Both surfaces recover together: `daemon status` reports the live status and active tool for ordinary panes, and a TUI reattach restores a working agent's card as it was rather than resetting it to `Idle`.
