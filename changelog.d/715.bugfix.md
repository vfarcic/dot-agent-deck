## A half-written daemon prompt is no longer sent later, glued to whatever you had typed

When the deck writes into a pane on your behalf — a delegated worker's task pointer, or one of the daemon's own reports to an orchestrator — it types the text and then sends the Enter that submits it. Occasionally that sequence only half completes: the text lands and the Enter does not, or the text itself is cut off partway. The deck already knew about this case and deliberately did not retry, because retrying would risk a doubled prompt. What it also did, wrongly, was forget that anything had been left in that pane's input box.

That memory is the only thing standing between you and a merged turn. Those leftover bytes sit in the input box, unsubmitted, and nothing removes them — so the moment the deck writes the same text into the same pane again, both go in as one message, together with anything you have typed there in the meantime. The repeat is not an unlikely coincidence in either case: a worker's task pointer is deliberately the same one-line sentence on every hand-off, so it is identical by construction, and the daemon's idle-worker report is a role name plus a coarse elapsed time, so two of them about one worker read the same byte for byte.

Both paths now keep that record when a submit does not complete, which is what the delegated-worker silence report started doing in v0.38.0. A later identical write into a pane you have typed into since is refused rather than sent — for the task pointer, refused *and* reported on the worker's card, saying in as many words that submitting would have sent your unsent draft too, with the orchestrator's ledger cleared so it is not left waiting on work that never started.

What this does not fix, and is worth knowing: a half-completed submit still strands its bytes in the input box. Nothing in this release removes them — clearing a pane's input box on your behalf is a bigger decision than declining to write into it. What changes is only that they are never quietly folded into a later message. The refusal is also narrow rather than sticky: it applies only to a byte-identical repeat, only into a pane you typed into after the incomplete write, and it lapses after a minute, so a genuinely later delegation or report goes through normally.
