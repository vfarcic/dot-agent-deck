## `hooks install` now tells you when another install of the deck still has hook rules here

**Not a macOS issue.** It was found on a Mac, but it fires on any host that already has the deck installed by any means — apt, Nix, Homebrew, a manual copy — and then gets a second install. Nothing about it is platform-specific.

The shape: a machine already had the deck from Homebrew, `remote add` installed a second copy under `~/.local/bin`, and `hooks install` **appended** a rule rather than replacing one. Ten events, two rules each:

```
"command": "/opt/homebrew/bin/dot-agent-deck hook --agent claude-code"
"command": "/Users/you/.local/bin/dot-agent-deck hook --agent claude-code"
```

Every hook event was then delivered twice. Both commands run from the same agent process with the same environment, and the socket is resolved from the environment rather than from the invoked binary's path, so both reach the *same* daemon — the second delivery is pure duplication. The only hint anything was wrong came much later, when `hooks uninstall` reported `Removed 20 hook commands` and you had to notice that twenty was twice ten.

`hooks install` now names them:

```
Note: 1 other dot-agent-deck install still have hook rules here:
  /opt/homebrew/bin/dot-agent-deck
  Every hook event is delivered once per rule, and all of them reach the same daemon, so the
  extra deliveries are redundant. To collapse them, run `dot-agent-deck hooks uninstall` and
  then `hooks install` from whichever install you want to keep.
```

Because `remote add` prints the remote's `hooks install` output verbatim, this surfaces at the moment the duplicate is created rather than weeks later.

**The rules are reported, not pruned, and that was the harder half of the decision.** The obvious fix is to make the install replace any rule naming the same binary at a different path. But `hook_rule_identification_011` pins the opposite policy on purpose — two on-disk builds that share the basename `dot-agent-deck` are "distinct deployments", each keeping its own rule, and its doc comment notes it deliberately covers the branch where both paths really exist, which is exactly this case. Collapsing them would overturn a documented property and would silently drop a rule for someone running two builds side by side. What was actually broken here was never the coexistence; it was that it happened in total silence. So the silence is what got fixed, and whether the policy itself should change is a decision left where it belongs rather than made as a side effect of a bug fix.

The existing prune already handles the easy half: a same-named rule whose binary is *gone* is removed as stale. This is its live counterpart, which that prune cannot see because the other install is very much alive.
