## Whether a pane scrolls depends on the agent in it, and the deck now says so

Scrolling a pane with a two-finger swipe works on a `claude` pane and does nothing at all on a `codex` pane. Nothing was broken: the two agents use opposite scrolling models, and until now neither the docs nor the deck itself gave you any way to know that. A pane that silently ignores every swipe and every `PageUp` reads as locked, and the only honest thing to do about it was to explain it.

Agents fall into two camps. **App-managed** agents ask the terminal for mouse tracking precisely so they can receive the wheel and scroll their own transcript — claude requests all four mouse modes, and scrolling a claude pane has always worked. **Terminal-managed** agents expect the *terminal* to hold the history while contributing none of it: codex requests no mouse events at all, does not use the alternate screen, sizes its drawing region to the exact pane height and repaints its whole transcript in place, so no line ever scrolls off the top. Measured at the height codex rendered for, the retained buffer is zero lines. For an agent like that the deck has nothing to scroll, by wheel or by key, in any mode. That is now stated in [Keyboard Shortcuts](https://agent-deck.devopstoolkit.ai/docs/keyboard-shortcuts) under its own section, along with why scrolling up in a long codex session in a plain terminal *appears* to work — what you reach is the content that was on screen before codex started, never an earlier part of the conversation — and in [Workspace Modes](https://agent-deck.devopstoolkit.ai/docs/workspace-modes), which made the same uniform claim about reading a pane in command mode.

The deck no longer waits for you to go looking. Attempting a scroll on a pane that has nothing to scroll now overlays a brief centred line — `This agent redraws in place and keeps no scrollback — there is nothing to scroll` — in the same idiom as the command-mode banner, shortening on a narrow pane and clearing itself after a moment or on your next keystroke. It is reactive: it appears only when you actually tried to scroll, never on focus or spawn, so a pane nobody scrolls never shows it. It never consumes the key that dismisses it, so a character typed into a pane while it is up still reaches the agent. And it names no agent — the trigger is "this pane retains nothing *and* the agent has already produced eight screenfuls of output", which is what separates a repainting agent from a claude pane one second after it started, and which covers any future agent that renders the same way.

Underneath both, the deck now works out whether an agent wants mouse reporting by actually parsing the escape sequences instead of searching its output for four fixed byte patterns. That search had three holes, and every one of them produced the *same* locked-pane symptom for an agent that would otherwise have scrolled perfectly well. It missed the combined form `ESC[?1000;1002;1006h`, which contains none of the four patterns as a substring, so an app that sets all its modes in one sequence looked like it had set none. It let an enable anywhere in a chunk outrank a disable later in the same chunk, so an agent switching mouse reporting off stayed flagged on. And it could not see a sequence split across a read boundary, which is an ordinary thing for a PTY to do. Detection is now a real scan resolved in byte order, with each mode tracked independently — withdrawing one of four no longer reads as withdrawing all of them — and with the tail of an unfinished sequence carried into the next chunk under a fixed cap, so a malformed or hostile stream cannot grow it. Focus reporting (`ESC[?1004h`, the one private mode codex does set) is correctly not counted as mouse reporting.

Making codex's own transcript scrollable is not something the deck can do from the outside; it needs codex to use the alternate screen, enable mouse tracking, or bind a scroll key, and that has been raised upstream separately.
