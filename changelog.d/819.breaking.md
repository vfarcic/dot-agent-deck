## The desktop app asks the daemon which projects exist (`PROTOCOL_VERSION` 8 → 9)

The desktop app used to work out for itself which project a workflow launch would run in. It kept a list you typed into, saved in the app's own local storage and seeded from a directory it guessed — its own build directory, or wherever the app process happened to be running — and that list was the authority: whatever it said became the working directory the agents were started in. On the machine the app happened to be running on, that mostly worked. Pointed at a daemon on another machine it was silently wrong in both directions: the launch validated against a `.dot-agent-deck.toml` on your own machine that no agent would ever see, and it wrote the coordinator's context file there too, where no agent would ever read it. The directory the roles were then started in was one your machine had chosen and the daemon's machine had to live with.

**The daemon now answers that question, and it answers it about its own machine.** Open **Projects** and the app lists what the connected daemon can see: the directory that daemon was started in when that directory is a project, the working directory of every agent it is running, every orchestration's directory, and every scheduled task's. A project it has nothing running in is named by pasting an absolute path, which the daemon resolves on its own filesystem. The app never derives a path from its own environment — it sends back only a path the daemon gave it or one you typed. So against a remote daemon the projects offered are the remote machine's, the path a launch uses is that machine's own spelling of it, and the coordinator context is written where the agents will actually read it.

**Choosing a project comes before choosing a workflow, because the workflows come out of the project.** The workflow field is now a list of the orchestrations that project actually defines rather than a name you type and hope matches, and the project directory beside it is read-only. The roles the launch is checked against are that orchestration's own, so a missing or unexpected role is named on the sheet before you press the button rather than refused after it. The read-only directory is worth one sentence of explanation: a path spelled through a symlink resolves to a different basename, and an orchestration that leaves itself unnamed takes its name from that basename — so the daemon's own spelling is what keeps the picker and the launch talking about the same project.

**Nothing remembers a project any more, on either side.** The saved project list is gone and nothing is stored in its place; a chosen project lasts for the launch you are assembling and no longer. That is the same deal the terminal UI has always offered, where you pick a project by starting the deck in it. The offering refreshes itself through use: launching in a project puts an agent there, so the daemon knows it for as long as anything is running there. Two ordinary situations follow from that, and neither is an error. A daemon that is running nothing and was not started in a project has none to offer, says so, and gives you the path field instead — that is the whole of the first-run experience, with no remembered list behind it. And a project can stop being known between being listed and being launched, because the last thing running there exited; the app says the same thing in that case and re-lists, rather than reporting a failure.

**A new app and an older daemon now refuse each other at the handshake, by name.** These requests moved the wire protocol from version 8 to 9, and the desktop app requires an exact match before it attaches at all — so a new app meeting a still-running older daemon reports `protocol mismatch: desktop expects 9, daemon reports 8` instead of connecting and behaving oddly. Upgrading both is the remedy, and a packaged app is matched already because it bundles the daemon built alongside it. The **Connect anyway** escape hatch does not apply here: it relaxes a build-version difference, and the protocol check runs before it and is not overridable. There is deliberately no fallback to working the project out locally when the daemon happens to be on the same machine — that is the behaviour this change exists to remove, and putting it back on the least-tested path is exactly how it would return.

The plan, the bounds on what the resolve request will answer, and the enumeration of what the app is still allowed to read from its own filesystem are in [PRD #819](https://github.com/vfarcic/dot-agent-deck/issues/819).

Demo reel for PRD #819: https://youtu.be/xo7Kf6OtPYU. Watch before merging. It shows a real interactive Haiku coordinator, started through the daemon into the directory the daemon resolved, reading the context file the daemon composed and published there and visibly carrying out the task it found in it.
