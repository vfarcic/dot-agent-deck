## A prepared launch starts its roles in the project directory it verified

A launch from the desktop's New agent dialog or Runs screen checks that the project directory is still the one it prepared, and then starts each role there. If the directory was renamed away and a different one put under the same name in between, the role used to start in the replacement. On Linux the role now starts in the directory that was checked, and the launch is refused if the deck cannot enter that directory that way. On macOS the name is checked again just before the start, which narrows that window but does not close it. On both, a launch whose project directory is no longer a directory at start time is refused, instead of starting the role in your home directory.

## Two launches in one project no longer read each other's brief

Every orchestration launch — the desktop's New agent dialog and Runs screen, `dispatch --orchestration`, and the TUI's `Ctrl+n` — used to write its coordinator's brief to the one file `.dot-agent-deck/orchestrator-context.md`. A second launch in the same project, made before the first coordinator had read that file, replaced it, and the first coordinator then worked on the second launch's task. Each launch now writes its own `.dot-agent-deck/orchestrator-context-<id>.md` and points its coordinator at that file, and a later launch cannot change it. In a TUI tab opened with `Ctrl+n`, the brief re-sent to the coordinator after compaction or `/clear` is rebuilt from that tab's own file, so it keeps its own task; a tab the TUI rebuilt after a reattach still rebuilds it from `orchestrator-context.md`, as before. `orchestrator-context.md` is still written after every launch, for older decks and for role commands that name it. It holds the most recent launch's brief, except that two launches made from different places at nearly the same moment — say the desktop and a TUI's `Ctrl+n` — can leave it holding either one's. The per-launch files are removed with the other coordination files once they are 14 days old.

## Starting an orchestration no longer hangs on a deck that stops answering

The desktop's New agent dialog and Runs screen waited for as long as the deck took to prepare an orchestration launch, so a deck that took the request and never answered held **Starting…** open indefinitely. A deck now gives up on a preparation after 10 seconds, tells the desktop so, and withdraws it: nothing can be started from it and its brief is deleted (or, if that fails, cleaned up with the other coordination files once it is 14 days old), so trying again is safe. Against such a deck the desktop also stops waiting after 15 seconds. Against an older deck the desktop still waits the preparation out, as before.
