## `daemon status`'s 3-second round-trip deadline is now actually tested

`dot-agent-deck daemon status` bounds its whole connect+request round trip with `STATUS_REQUEST_TIMEOUT` (3s, `src/daemon_status.rs`) and reports `daemon status: unavailable (no response within 3s)` when it expires. Nothing exercised that branch. `daemon/status/003` looked like it did — it is the "no daemon reachable" test — but it points the CLI at a path with *nothing bound*, which fails at `connect(2)` in microseconds and takes the transport-error arm instead. The deadline arm had no coverage at all, so a regression that dropped the `tokio::time::timeout` wrapper, or raised the constant to a minute, would have shipped green and left the diagnostic hanging on exactly the wedged daemon it exists to diagnose.

`daemon/status/006` stages the one thing that reaches it: a stub Unix listener in a scratch directory that **accepts** every connection and then never writes a byte back, with the accepted streams deliberately held open — dropping one would close the connection, the client would read EOF, and the CLI would take the transport-error arm again. Both the human and `--json` forms of the real binary run against it concurrently, so the whole test costs roughly one deadline rather than two. It asserts the stub accepted one connection per invocation (proving this is not `/003`'s path), that each subprocess returns non-zero without a Rust panic, that each returns within the deadline it declares plus spawn slack, that each names that deadline on stderr, and that each prints nothing on stdout — the `--json` half of which matters on its own, since an empty-but-well-formed document would read to a consumer as a healthy daemon with zero agents.

The test carries its own absolute 8-second watchdog, written as a literal and never derived from `STATUS_REQUEST_TIMEOUT`, because a bound that follows the constant it guards would sail through a build that raised that constant. `kill_on_drop` is what makes it real rather than decorative: on expiry the dropped wait future takes the child process with it, so a build that lost the deadline *fails* instead of hanging, which is the only useful thing a test can do about an unbounded wait.

Verified with teeth, twice. With the `tokio::time::timeout` wrapper deleted from `run_daemon_status_cli`, the whole fast tier reports `4036 tests run: 4035 passed, 1 failed` — the one failure is `/006`, at 8.0s, naming the missing deadline, so nothing else in that tier was covering this. With the wrapper kept and `STATUS_REQUEST_TIMEOUT` raised from 3s to 60s, `/006` fails the same way and everything else stays green. On an unmodified build it passes in 3.0s, and the module it lives in runs in 3.1s end to end.

Test-only — no production source, no wire change, `PROTOCOL_VERSION` and `CONTRACT_BREAKS` untouched.
