## A symlink at the daemon's attach socket path is refused instead of trusted for what it points at

`verify_endpoint_trusted` — the out-of-band check the TUI and the desktop bridge run on the attach socket inode *before* they connect — used `std::fs::metadata`, which stats **through** a symlink. So the owner and mode it tested were the link target's, and the link's own were never consulted: a link owned by anybody at all was accepted as long as it resolved to some socket of ours at `0o600`. It now uses `symlink_metadata`, and a symlink at the endpoint path is refused on its own account with a reason that names the link rather than describing its target.

**What made it reachable is the `/tmp` fallback.** `attach_socket_path()` uses `$XDG_RUNTIME_DIR/dot-agent-deck-attach.sock` when that variable is set and `/tmp/dot-agent-deck-attach-<uid>.sock` when it is not — a plain ssh session or a container, which [PRD #741](https://github.com/vfarcic/dot-agent-deck/issues/741)'s remote decks make an ordinary case rather than an exotic one. `/tmp` is world-writable, so on such a host a *different* uid could pre-create that path. A regular file or a socket they owned was already correctly refused by the type and uid clauses; a symlink they owned was not.

**The impact, stated no wider than it is.** The attacker is not the listener, so this is **not** disclosure, privilege escalation or anything reachable over a network — the payoff is redirecting our own client to another of our *own* endpoints. Under `$XDG_RUNTIME_DIR` (mode `0o700`, ours) no foreign uid can create the entry at all, so a desktop session was never exposed this way. And under the *same-uid* premise the check states in its own docs, the new clause buys nothing: an actor who can plant a link can bind a real `0o600` socket of their own at that path instead.

**What else this now refuses, which is the part worth checking before upgrading.** Only one case changes from accepted to refused: a symlink at the endpoint path pointing at a socket that is genuinely ours at `0o600`. Three cases were already refused and only change their *reason* — a dangling link (was `stat failed: … os error 2`, i.e. filed as "the daemon never bound"; now named as a planted link), a link to a non-socket, and a link to a foreign-owned socket. Nothing else moves, and the deck has never created such a link itself, so this bites only an operator who made one deliberately — `ln -s /run/user/1000/dot-agent-deck-attach.sock /tmp/dot-agent-deck-attach-1000.sock` to let a non-XDG shell find a running daemon. The supported spelling for that is `DOT_AGENT_DECK_ATTACH_SOCKET`, pointed at the real path. Only the **final** path component is `lstat`ed, so a symlinked *ancestor* is resolved exactly as before — which matters on macOS, where `/tmp` is a symlink to `/private/tmp` and the per-user `$TMPDIR` sits under a symlinked `/var`.

**The availability half is improved but not closed, and the rest is [#1121](https://github.com/vfarcic/dot-agent-deck/issues/1121).** Because `/tmp` is sticky, the deck cannot unlink an entry another uid owns, and `bind(2)` refuses any path that already has one — so a squatter wedges that endpoint path until they or root remove it. What changes here is that every shape of planted entry now produces one clean, actionable refusal: lazy-spawn's presence test became an `lstat` too, so a *dangling* link no longer reads as absent, routes around the trust check, and gets answered with a daemon that then fails its own `bind` with `EADDRINUSE` and an error naming neither the squatter nor the real problem. The refusal also now names the escape hatch (set `DOT_AGENT_DECK_ATTACH_SOCKET` to a path only you can write). Restoring availability properly means moving the fallback endpoint into a `0o700` directory we own — the shape `remote_tunnel::tunnel_socket_dir_in` already uses for forwarded sockets — and that moves the endpoint path, which is a cross-version question of its own.

**No protocol contract change** (CLAUDE.md rule 12). `PROTOCOL_VERSION` stays at 9 and no `.breaking.md` fragment is warranted: nothing on the wire moves and no field shifts meaning. The check is client-side, local, and runs before the first byte; a daemon of any version binds a real socket, never a link, so an older daemon and a newer TUI verify the same inode by the same rules they always did. Verified by the cross-version manual run as well as by reasoning — see the PR.

Covered by six tests, two of them existing ones that had to move. In `platform::fsperm::unix`: the inverted characterization test [PRD #741](https://github.com/vfarcic/dot-agent-deck/issues/741) M1 left in place for exactly this change; a new one firing the same single refusal for a link to a socket, a regular file, a directory and nothing at all (so no attacker-chosen target can steer which clause answers); a new one pinning that a socket under a symlinked *ancestor* is still trusted; and `…refuses_a_path_with_nothing_at_it`, whose dangling-symlink half now asserts the opposite of what it did — that a planted link is **not** filed as an absent endpoint. In `daemon_attach`, both new: a planted link — live and dangling — must be refused *before* `spawn_fn` runs and must be left unlinked, while a live socket still short-circuits and an absent path still spawns.

Each one was checked against a mutant rather than only observed green: reverting `symlink_metadata` to `metadata` reddens all four symlink tests and leaves the three legitimate-case ones green; moving the symlink clause after the type clause reddens the three `fsperm` ones; and putting the presence test back to `Path::exists()` reddens only the dangling half of the `daemon_attach` one.
