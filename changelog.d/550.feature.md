## Every spawned pane is told where the main checkout is

A delegated agent working in a linked worktree often needs the **root checkout** — most commonly to leave a report or an artifact that has to outlive the worktree, which is temporary: closing a dispatched unit's tab removes its copy, and `dot-agent-deck worktree reclaim` removes one whose branch has merged. The deck gave it no way to find that, so the path had to be hand-written into the task by whoever delegated, and forgetting produced a *stall* rather than an error: the agent has nothing to resolve and correctly declines to guess.

Every pane the deck spawns now carries `DOT_AGENT_DECK_MAIN_WORKTREE`, alongside the existing `DOT_AGENT_DECK_PANE_ID` and `DOT_AGENT_DECK_AGENT_ID`. A role prompt can say *"write findings to `$DOT_AGENT_DECK_MAIN_WORKTREE/.dot-agent-deck/…`"* and no task has to carry the path. In an ordinary checkout the variable names that checkout — an ordinary checkout is a main worktree too — so a prompt written this way works whether or not the pane happens to be in a worktree. Purely additive: nothing in the deck reads the variable and no consumer is obliged to.

**Absent rather than guessed, which is the property worth relying on.** The variable is set only where the main worktree is genuinely resolvable, so an agent that finds it unset knows the deck could not work the answer out rather than being pointed somewhere wrong — a wrong path is worse than a missing one, because the agent writes into it and nobody notices. `spawn` also scrubs any inherited value first, which is what makes "unset" mean "unresolvable" instead of "whatever the daemon happened to inherit": a daemon launched from inside a deck pane in repository A that later spawns a pane in repository B would otherwise have told B's agent to write into A. Resolution runs from the **pane's own cwd**, not the daemon's — panes under one daemon routinely sit in different worktrees, so a value computed once per process would be right for at most one of them.

**Not `dirname` of the git common dir, which is how the issue proposed it and is wrong in two of six layouts.** `worktree_owner::main_worktree_of` asks git whether the directory is already in a main worktree (`--git-dir` equals `--git-common-dir`) and, when it is, takes git's own `--show-toplevel` — correct from a subdirectory, and correct for a repository whose store was relocated with `--separate-git-dir`, where the common dir's parent is not the checkout at all. When it is not, the main worktree is the directory *holding* the common dir, and that inference is proved rather than trusted: the candidate's own `--git-dir` has to be the common dir. Two real layouts fail that proof and yield nothing instead of a confident lie — a linked worktree of a `--separate-git-dir` repository (git keeps no back-pointer from the store to the checkout, so the answer is genuinely unrecoverable) and a linked worktree of a *bare* repository (which has no main worktree). A bare repository resolves to nothing for the same reason.

The variable is named for git's own term rather than `DOT_AGENT_DECK_ROOT`, which reads as the deck's own install or storage root: every other name in that namespace (`STATE_DIR`, `LOCK_DIR`, `REMOTES_DIR`) is something the deck owns, and `<TOOL>_ROOT` conventionally means where the tool lives.

**No TUI↔daemon contract change, checked rather than assumed** (CLAUDE.md rule 12). Nothing is added to or removed from `daemon_protocol.rs`, no field changes meaning, and `PROTOCOL_VERSION` is untouched. The injection happens entirely inside the daemon's own `agent_pty::spawn`, downstream of `StartAgent`, reading a `cwd` the wire already carried; an older TUI driving a newer daemon gets the variable without asking for it, and a newer TUI driving an older daemon simply does not, exactly as before. Nothing serializes the value, so no client parses it.
