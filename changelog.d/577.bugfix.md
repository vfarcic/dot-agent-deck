## The experimental flag is read from the project you name, not from wherever the deck was started

The `[features]` table that backs the `experimental` flag was the one config read in the deck resolved against the process's own working directory. Every other one — modes, orchestrations, roles — is resolved against a directory the caller hands it. The consequence was that a deck started anywhere other than its project read its feature flags from whatever directory the operator happened to be in, usually a `.dot-agent-deck.toml` that does not exist there at all. Every experimental surface then resolved off, silently and with nothing in the log to distinguish it from the gated feature having been deleted from the build.

The flag loader no longer reaches for the working directory. It takes the project directory as an argument, exactly like every other config read, and the deck resolves that directory once at its entry point — where it is a decision the code makes rather than an accident of where the process was launched. The behaviour that was always documented (the flag comes from the `.dot-agent-deck.toml` in the directory the deck was launched in) is now what the code actually does, and the daemon, which inherits its directory from the TUI that spawned it, still agrees with that TUI on the file by construction.

The startup log line now names the file the value came from — `experimental flag: ON (from /path/to/.dot-agent-deck.toml)` — so a flag that reads off because the wrong file was loaded is now distinguishable from one that is simply set to false. Both overrides are unchanged: `DOT_AGENT_DECK_EXPERIMENTAL` still decides the value outright, and `DOT_AGENT_DECK_FEATURES_CONFIG` still names one specific file to read and now wins over the project directory — which is the escape hatch if you deliberately run the deck from outside the project whose flags you want.
