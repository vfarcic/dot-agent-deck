## Only an installed deck is written into agents' hook configuration

Running `dot-agent-deck` from a copy of the binary parked somewhere scratch — a branch build under `/var/tmp` used to drive a sandbox, for instance — no longer registers that copy's path in the **global** hook configuration of every agent you have. It used to: the guard that kept `target/debug` and `target/release` paths out of those files recognised cargo build directories and nothing else, so any other path was treated as durable and written. Because each installer only normalises the rules naming the binary currently installing, the new path landed *beside* your installed deck's entries rather than replacing them, leaving every agent firing two deck hooks per event — in the reported case ten Claude entries beside ten, ten Codex, and eight Devin.

What counts as durable is now the same thing the resolver already searched for when it had to fall back: your installed deck at `~/.local/bin/dot-agent-deck`, or a `dot-agent-deck` in a directory on your `PATH`. A deck running from anywhere else resolves your install and writes that, which is the path already in the file — so there is nothing to add. With no install anywhere to resolve, `dot-agent-deck hooks install` fails with a message naming the location as the reason and writes nothing, and the silent startup install logs a warning and leaves your configuration untouched.

Entries a previous version already wrote are not swept up while the binary they name still exists, because a hook command that still works is deliberately left alone. Delete the stray copy and start the dashboard once — the existing self-heal then rewrites the rule whose binary is confirmed missing — or remove the entry by hand.

See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for how to check what is currently pinned.
