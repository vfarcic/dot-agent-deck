## An installed deck is preferred over a copy of itself in agents' hook configuration

Running `dot-agent-deck` from a copy of the binary parked somewhere scratch — a branch build under `/var/tmp` used to drive a sandbox, for instance — no longer registers that copy's path in the **global** hook configuration of every agent you have *alongside* the one you installed. It used to: the guard that kept `target/debug` and `target/release` paths out of those files recognised cargo build directories and nothing else, so any other path was treated as exactly as durable as a real install and written. Because each installer only normalises the rules naming the binary currently installing, the new path landed beside your installed deck's entries rather than replacing them, leaving every agent firing two deck hooks per event — in the reported case ten Claude entries beside ten, ten Codex, and eight Devin.

The deck now looks for an install first — `~/.local/bin/dot-agent-deck`, or a `dot-agent-deck` in a directory on your `PATH` — whatever it happens to be running from. A copy run from anywhere else therefore resolves your install and writes *that*, which is the path already in the file, so there is nothing to add.

With no install anywhere to find, the running binary is still used, as a last resort, and the deck now logs a warning saying it pinned a path it cannot vouch for. That keeps hooks working on a machine whose only deck is the one running — a desktop app starting its bundled daemon with no CLI installed beside it. A `target/` build remains the one case that is refused outright rather than pinned, because a build directory is known to disappear.

Entries a previous version already wrote are not swept up while the binary they name still exists, because a hook command that still works is deliberately left alone. Delete the stray copy and start the dashboard once — the existing self-heal then rewrites the rule whose binary is confirmed missing — or remove the entry by hand.

See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for how to check what is currently pinned.
