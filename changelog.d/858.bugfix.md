## `connect` no longer fails on the first attempt and works on the second

`dot-agent-deck connect <name>` often failed the first time it was run and succeeded when the same command was run again immediately, reporting `probe exceeded 10s wallclock deadline (laptop-side kill after ssh did not return)`. Two independent defects produced that, and both are fixed.

**The laptop-side kill was firing at half the budget its own ssh options permit.** The reachability probe configures ssh with `ConnectTimeout` and `ServerAliveInterval` set to the probe timeout and `ServerAliveCountMax=1`, which together allow ssh roughly twice that before it gives up on its own — but the deck's own timer, documented as a *backstop* for a remote that accepts the connection and never returns, was armed at the plain timeout. It pre-empted ssh instead of backing it up, so a connection ssh was still working on at 11–20 seconds was killed at 10 and reported as an unreachable host. The deadline is now derived from the same number the ssh options are built from, with headroom on top, so it stays outside them whatever the timeout is set to. The default probe timeout is unchanged at 10 seconds: raising it would have scaled the inconsistency rather than removed it.

**A probe failure on the first connect was fatal, though the retry machinery already existed.** `connect` retries up to five times with a backoff, but a reachability failure only entered that budget on an automatic *reconnect* — the initial attempt gave up immediately, which is why retrying by hand worked. The first attempt now gets a bounded retry of its own — the same size and the same `'<name>' not reachable yet — retrying…` line — so a link that needs a moment to wake connects on its own. The two budgets are separate: attempts spent getting connected are not taken out of the automatic reconnects, so a session that only came up on the last attempt still gets its full four if it later drops. What happens when the host really is unreachable is unchanged: the retries are spent and you get the same actionable `Could not reach remote…` message, not a "connection lost" line about a session that never existed. Conditions that retrying cannot fix — a missing or unrecognisable remote binary, a rejected handshake, a forward that could not bind — still fail on the first attempt.

**A connect in progress now says what it is waiting on.** Instead of up to ten silent seconds followed by a wall of red, the terminal shows `Connecting to '<name>'… checking the remote deck` and then `…waiting for the handshake` while each ssh round-trip is in flight, erased before the remote session takes over the screen. It is drawn only when you are at a terminal: piped or redirected, `connect` writes nothing extra.

See [Remote environments](https://agent-deck.devopstoolkit.ai/docs/remote-environments#surviving-sleepwake) for the retry budget and the failure modes.
