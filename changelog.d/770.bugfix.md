## A daemon restart no longer silently orphans a running orchestration

Recycling the local daemon while an orchestration was running could strand it permanently, and nothing said so. The daemon holds each orchestration's role registrations — which pane is which role, which one is the orchestrator, which orchestration they belong to — in memory only. There is no file and no snapshot, so stopping the daemon deletes them. An agent that has detached from the terminal it was born under survives that restart untouched: it keeps running, reconnects its hooks to the new daemon, and the new daemon keeps accepting them. Only delegation breaks. Every `dot-agent-deck delegate` from that pane is refused from then on with "the daemon holds no orchestration role for pane …", and there is no recovery short of re-dispatching the whole orchestration.

What made this expensive was the asymmetry rather than the loss itself. Status kept flowing, the agent kept working, the card kept updating — the pane looked completely healthy for as long as nobody delegated, which for an orchestrator is often hours into a run. The trigger was ordinary too: `daemon stop` is the documented way to recycle the daemon after a binary upgrade, and it said nothing about orchestrations.

`daemon stop` and `daemon restart` now refuse while the daemon holds live orchestration roles, listing each pane, its role and its orchestration, and saying plainly that the registrations are held in memory only and that a surviving agent will keep running but never delegate again. `--force` still overrides, so the choice is available — it is just no longer made blind. This sits alongside the existing managed-agent guard and is reported first when both apply, because it is the one carrying the consequence an operator recycling a daemon has not already accepted.

Panes that are already orphaned now say so on the dashboard. When the daemon receives a hook event from an orchestration role pane it holds no role for, it marks the event, and the card renders an `orphaned` marker in its title plus a row reading `Orphaned — delegation unavailable`. That turns a trap costing hours into a five-second diagnosis. The verdict is the daemon's alone: any such marker arriving on an inbound hook payload is stripped before the daemon decides, so nothing reaching the hook socket can badge a healthy card or suppress the badge on a broken one.

Deliberately not done: restoring the role maps from disk. A restart kills the terminals the daemon owned, so most panes in such a file would be genuinely dead, and a restored entry pointing at a dead pane would turn an honest refusal into a delegate that silently routes into a void — strictly worse than the failure it replaced.
