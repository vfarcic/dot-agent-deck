## A hook event can no longer speak for a pane it does not own

Until now, being able to reach the deck's hook socket was treated as authority to speak for *any* pane. `dot-agent-deck agent-event` reads `DOT_AGENT_DECK_PANE_ID` out of its own environment and forwards it, and the daemon took that claim at face value — so any process running as you could set that variable to somebody else's pane and drive that pane's card: mark a working agent Idle, mark an idle one Working, or attach a tool line to a conversation it has nothing to do with.

The daemon now mints an unguessable capability token for every agent it spawns, injects it into that agent's environment as `DOT_AGENT_DECK_AGENT_TOKEN`, and revokes it when the agent stops. On ingest it resolves the token back to *its own* record of which pane and which agent the token was minted for, and uses that — the pane and agent named in the payload are overwritten, not compared. A valid token for one pane therefore cannot drive another, which is the part a "check the claim matches" test would have missed.

**What changes for you.** An event that names a pane this daemon manages is refused unless the sender holds that pane's token. Agents the deck spawns inherit the token automatically and need no change. What breaks is an agent that was already running under an **older daemon** when you upgraded: its process has no token in its environment, so its hooks stop moving its card. Restart those panes after upgrading — a new spawn is all it takes. External agents that post about panes the deck does *not* manage are unaffected and still register their cards exactly as before.

The wire is compatible in both directions — the token is an additive optional field on the event, and an older daemon ignores it — so this is a change of meaning behind a stable shape, which is why it is recorded here rather than as an ordinary fix. The attach protocol did move: `PROTOCOL_VERSION` goes to 8 for a new `get-agent-token` request, so a mismatched TUI and daemon refuse each other at the handshake and the daemon is recycled, as it already is for any protocol bump.

**What this is and is not.** It binds an event to the process entitled to send it, and it raises the bar considerably. It is not authentication against an attacker who already runs code as you: the same user can read another process's environment, and therefore its token. Tying the check to the connecting process's identity instead is tracked separately.
