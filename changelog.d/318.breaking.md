## A hook event can no longer speak for a pane it does not own

Until now, being able to reach the deck's hook socket was treated as authority to speak for *any* pane. `dot-agent-deck agent-event` reads `DOT_AGENT_DECK_PANE_ID` out of its own environment and forwards it, and the daemon took that claim at face value — so any process running as you could set that variable to somebody else's pane and drive that pane's card: mark a working agent Idle, mark an idle one Working, or attach a tool line to a conversation it has nothing to do with.

The daemon now mints an unguessable capability token for every agent it spawns and injects it into that agent's environment as `DOT_AGENT_DECK_AGENT_TOKEN`. On ingest it resolves the token back to *its own* record of which pane and which agent the token was minted for, and uses that — the pane and agent named in the payload are overwritten, not compared. A valid token for one pane therefore cannot drive another, which is the part a "check the claim matches" test would have missed. A token stops resolving the moment a later agent takes over its pane, so it can never outlive its own generation and speak for a recycled pane id — while an agent's own last report, written as it shuts down, still arrives.

The token reaches exactly two places: the child's environment, and the reply to the attach-socket request that spawned it. There is deliberately **no** way to ask for an agent's token afterwards — an intermediate version of this change had one, and it defeated the mechanism rather than merely widening it, because the same socket lists every agent id without authentication.

A pane stays the deck's for as long as the deck still holds it, which includes the window after an agent has exited but before anything has taken its place. That window used to read as "not ours", so an event naming it was treated as an outside agent's and accepted on the strength of the payload alone.

**What changes for you.** An event that names a pane this daemon still holds is refused unless the sender holds that pane's token. Agents the deck spawns inherit the token automatically and need no change, and external agents that post about panes the deck does *not* hold are unaffected — they still register their cards exactly as before. Two narrower things do change:

- A hook that is executed by a **different `dot-agent-deck` binary than the one running the daemon** — a stale absolute path left in `~/.claude/settings.json` by an older install — carries no token and no longer moves a managed pane's card. Re-run `dot-agent-deck hooks install` so the settings point at the current binary.
- A launcher or wrapper that **scrubs the environment** (`env -i`, `sudo` without `-E`, a detached hook runner rebuilt from a login shell) drops the token the same way it already drops `DOT_AGENT_DECK_AGENT_ID`. That used to degrade matching; it now refuses the event. The daemon's log names the cause.

There is no "agent stranded by the upgrade" case to worry about: a daemon owns its children and kills them as it exits, so an agent cannot outlive the daemon that spawned it and find itself talking to a newer one. In the one exception — a daemon killed with `SIGKILL`, leaving an orphan behind — the replacement daemon does not manage that pane at all, so the orphan's hooks take the unchanged foreign-agent path and keep driving a card.

A second, narrower refusal comes with it: a daemon that runs panes now declines an event that names **no** pane, unless the payload claims the id of one of that daemon's own pane-less agents. That rule already existed but was evaluated against a list an ordinary spawn does not add to, so in practice a fleet-running daemon still accepted such events and they could drive a session by `session_id` alone. Note what the exception rests on: the agent id is a claim in the payload, not proof about the sender, and it is kept because dropping a pane-less agent's `SessionStart` would let input reach a target that declared itself view-only.

**The wire did not move.** The token is an additive optional field on the event and on the spawn reply, of exactly the shape `agent_version` and `schema_version` already use, so `PROTOCOL_VERSION` stays where it is and a mixed-version TUI and daemon still pair up. This is a change of *meaning* behind a stable shape, which is why it is recorded here rather than as an ordinary fix — and note the consequence of not bumping: the change is not announced by a handshake refusal, so the daemon log's refusal line is where it becomes visible.

**What this is and is not.** It binds an event to the process entitled to send it, and it raises the bar. It is not authentication against an attacker who already runs code as you: the same user can read another process's environment, and therefore its token. Tying the check to the connecting process's identity instead is tracked separately. It also guards hook **events** specifically — the other requests that share this socket still take the pane they name at face value, which is tracked as its own follow-up.
