## Status reports from a deck-spawned pane must now carry that pane's capability token

The status updates that drive a card — the hook events an agent's hooks send, `dot-agent-deck wrap`'s reports and `dot-agent-deck agent-event` — named the pane they came from, and the daemon believed that name. So any process running as you that knew a pane id, and `daemon status` prints them, could change what a deck-spawned agent's card said, mark it finished, or replace its card with one of its own. The daemon now holds these reports to the same capability token it already requires on `delegate`, `work-done` and the other agent commands: a report naming a pane the deck spawned is accepted only when it carries that pane's own token, and every `dot-agent-deck` command an agent runs inside its pane sends it automatically. A report from outside the pane, or carrying another pane's token, is refused and logged, and the card keeps showing what its own agent last said. So is a report that carries the pane's token but names a different agent than the one the deck started there (logged as `token_names_another_agent`), and a report that names no agent and carries the token of an agent the deck has since replaced in that pane — for example a leftover process of the previous agent still sending updates — which is logged as `token_generation_replaced`. A leftover process's reports that do name the previous agent cannot change the current agent's card either.

Agents the deck did not start keep working as before: their hooks need no token, and they still get a card. Reports that carry no token cannot change the card of an agent the running daemon started, even when they name the same session. One card is the exception: in a TUI that stayed open through a daemon restart, an agent that kept running keeps its existing card, which keeps updating (an orchestration agent's is shown as orphaned), and another process running as you that knows the agent's pane and agent id can change what that one card shows. Two things change for outside agents' cards. The deck now keeps at most 256 of them at a time; when a new one arrives beyond that, the one that has been quiet longest is removed. Cards of agents the running daemon started never count toward the limit. An agent that kept running across a daemon restart was started by the previous daemon, so in a TUI opened after the restart it counts as an outside agent and its card can be removed to make room; in a TUI that stayed open through the restart, its existing card does not count, is not removed to make room, and when the agent's session ends stays and shows Idle (still marked orphaned for an orchestration agent) instead of going away. And when an outside agent ends its session, or its card is removed to make room, the card goes away instead of being left behind as an empty card for that pane; a TUI older than the daemon still leaves the empty card.

**Why this is marked breaking.** The report format is unchanged: the token is an extra optional field that an older daemon ignores, and a command with no token sends exactly what it always did. What changed is what a newer daemon does with a report that names a pane it spawned and carries no token: it refuses it. So if the `dot-agent-deck` binary on a pane's `PATH` is **older than the daemon that spawned the pane**, which happens when the daemon was started from a different build than the one on `PATH`, that pane's card stops updating and the daemon logs each refusal with the reason `missing_token`. Put the matching binary on `PATH`, or set `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` on the daemon to accept token-less reports with a warning. That setting tolerates a *missing* token only; a token issued for a different pane is refused either way.

As with the existing token check, this is not isolation between agents running as the same user: another process running as you can still read an agent's environment. What changes is that a pane id is no longer enough to speak for that pane's card.
