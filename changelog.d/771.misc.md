## Both mandated gates run in a `devbox shell` on Linux again

`desktop/src-tauri` became a workspace member in `daf94f0`, and both gates CLAUDE.md tells every contributor to run before every commit carry `--workspace`. So `cargo clippy --workspace --all-targets --features e2e -- -D warnings` and `cargo test-fast` both build `dot-agent-deck-desktop`, which needs GTK 3, WebKitGTK and glib — and `devbox.json` provided none of them. On Linux the first failed at build time (`The system library 'glib-2.0' required by crate 'glib-sys' was not found`) and the second at run time (`libgdk-3.so.0: cannot open shared object file`). CI never noticed, because `ci.yml`'s `build` job installs the compile set with apt itself. The available workaround was `--exclude dot-agent-deck-desktop`, which silently leaves the desktop crate unlinted and untested — the two things the gates exist to prevent.

`devbox.json` now carries a `path:tauri-deps#tauri-deps` entry. `tauri-deps/flake.nix` builds the transitive pkg-config closure of the same libraries CI installs with apt, and an `env` block points `PKG_CONFIG_PATH` at it. Measured in a devbox shell with the GTK crates cleaned first: clippy finishes clean, and `cargo test-fast` runs 3472 tests including the desktop crate's 35, which had never executed in that shell before.

**Why a flake rather than more devbox packages, since the obvious fix is six lines in `packages`.** A devbox package lands in the profile as a bare store path, so `gtk3` contributes `gtk+-3.0.pc` and nothing its `Requires:` line names — a Nix profile does not follow propagated build inputs, so the closure would have to be spelled out by hand and would rot on the next nixpkgs bump. And `webkitgtk_4_1` and `libayatana-appindicator` are Linux-only, which needs devbox's object form for `packages`; converting the array to that form breaks `scripts/check-pin-lockstep.sh`, which reads the toolchain pins as `"rustc@1.97.1"` string entries. A flake gets the closure from Nix's own pkg-config setup hook, is Linux-only by itself, and leaves the array untouched.

**`apt-get install` inside a devbox shell looks like it should work and does not**, which is what made this expensive rather than merely annoying, and it is now written down in [the desktop GUI developer doc](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/desktop-gui.md). A devbox shell runs under Nix glibc, whose loader cache does not exist — `ldconfig -p` returns *zero* entries — so libraries under `/usr/lib` are invisible to the dynamic linker however they got there: `pkg-config` reports `glib-2.0` present, the build succeeds, and the test binary still dies on `libgdk-3.so.0`. The obvious second workaround trades one breakage for another: `LD_LIBRARY_PATH=/usr/lib/x86_64-linux-gnu` makes both Rust gates pass and then breaks Nix's own `node` with `undefined symbol: uv_tcp_keepalive_ex`, taking `pnpm install`, `pnpm build` and `pnpm test` with it.

So the fix sets **no** `LD_LIBRARY_PATH` at all. Each `.pc` file names absolute `/nix/store` paths, the linker is therefore invoked with `-L/nix/store/…-gtk+3-3.24.52/lib`, and Nix's `ld` wrapper turns every in-store `-L` into a matching `-rpath` — verified on the built test binary, whose RUNPATH lists gtk+3, glib, webkitgtk, cairo, pango and the rest by store path. That is per-binary and cannot leak into another program in the shell, which is exactly what `LD_LIBRARY_PATH` cannot promise.

`scripts/devbox-smoke.sh` now resolves each module through `pkg-config` and fails on any that is missing. It runs in CI's `devbox` job, which is the only job that can observe this regress: every other one installs the compile set with apt and would stay green with `devbox.json` empty of GTK.

Outside Devbox nothing changes — a Linux contributor on a distribution toolchain still installs `libwebkit2gtk-4.1-dev libgtk-3-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev` with apt, and that still works, because the Nix loader is the thing at fault rather than apt. Bundling a `.deb` locally additionally wants `patchelf`, `fakeroot`, `file` and `desktop-file-utils`; no gate in this repository runs `tauri build`, so those are deliberately not pinned here and are documented as a manual step instead.
