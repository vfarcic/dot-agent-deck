## A failed dispatch no longer deletes a worktree that agents are still working in

Dispatching an orchestration whose roles do not all start — one role's command misspelled, or a tool that is not on the daemon's `PATH` — reported the failure and then deleted the dispatched worktree, even though the roles that *had* started were live agents whose working directory that was. Their shell prompts still pointed at a path that no longer existed, and any file they went on to write landed nowhere recoverable.

The rollback assumed no agent could be running yet, which holds for a single-agent dispatch and never held for an orchestration: roles start one after another, so a failure at the third leaves the first two already running. The rollback now asks the same question the tab-close path has always asked — is any live agent still rooted in this tree? — before removing anything. When the answer is yes it leaves the worktree, its branch and its cleanup record alone, and the failure message says how many agents are still running in it and that closing them releases it. This is distinct from never force-removing a *dirty* tree on tab close: the risk here is not uncommitted content but a live process losing its working directory.

Partial orchestration spawns are now rolled back before the rollback is reached (see the entry for the orphaned agents), so in practice the dispatch reclaims its worktree exactly as it did for a spawn that never started anything. The check remains because deleting a working directory out from under a running agent is not a mistake worth risking on an assumption.
