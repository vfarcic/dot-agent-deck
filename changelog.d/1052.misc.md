## The release flow is a project-local skill again, and it says to resolve review threads

An agent would finish the review conversation on its PR — reply to every finding, fix each one — and stop there. Nothing told it to **resolve the threads**, and an unresolved thread blocks both halves of the merge: `required_review_thread_resolution` blocks the merge button, and the agent PR reviewer skips any pull request carrying one, so it blocks the approval that merge needs. [#1035](https://github.com/vfarcic/dot-agent-deck/pull/1035) sat a full day with fourteen green checks and all five of its findings already fixed; [#1019](https://github.com/vfarcic/dot-agent-deck/pull/1019) sat two days on a finding the reviewer itself retracted 34 seconds after the author rebutted it. A third effect is quieter: `pr-review-queue` reads unresolved threads as *"yours, needs feedback addressed"*, so a finished pull request keeps re-entering the work queue.

It could not be fixed where the instruction lived. The release procedure was `.claude/skills/dot-ai-prd-done`, a synced mirror of the `dot-ai` project, and CLAUDE.md rule 13 records what that costs: `04a3641` corrected its review-wait step and `e94388d` reverted it byte for byte five days later. By today that file told an agent to wait for **CodeRabbit** (not active here — the wait hangs to its timeout), mentioned the reviewer that *is* active zero times, said to **commit directly to `main`** (protected; returns `GH013`), told a worker to notify the team (the orchestrator is the only agent that notifies), and asked it to *"verify deployment"* and *"monitor for issues"* for a TUI binary that is not deployed anywhere.

So the flow is forked out as the project-local **`pr-create`**, owning one arc — committed work on a branch to a pull request that is green, reviewed, and ready for someone else to merge. It stops before merge by design, matching rule 8: these flows may arm auto-merge and hand off, never merge directly. `prd-full` is renamed alongside it because it calls it. Renaming rather than adding was the point: a new skill beside the old one would have left two conflicting release procedures with no way for an agent to tell which governs. `dot-ai-prd-start` stays mirrored — it has no project-specific content at all, so de-mirroring it would cost upstream updates and buy nothing.

The skill is **reviewer-neutral** (today Greptile, tomorrow something else) and its wait is **bounded**. The bound is load-bearing rather than cautious: an exhausted reviewer quota produces *no check-run at all* — measured 2026-08-23, indistinguishable from the app being uninstalled, with no message anywhere in the repository — so a wait keyed on "the check-run appears" never terminates. After its budget the skill proceeds and reports that no automated review was obtained, which is a result rather than a pass. 342 lines became 82.

**CLAUDE.md rule 8 shrank from 33 lines to 9**, keeping only what binds an agent that never invokes the skill — most pull requests here are opened without one. The mechanism it restated was already duplicated in [`docs/develop/governance.md`](docs/develop/governance.md), which gains the one section it lacked, on the automated reviewer and its quota; that doc also claimed Greptile "re-reviews on each push", which has been false since `triggerOnUpdates` was set to `false`.

**`.agents/skills/` collapses from 33 per-skill symlinks to one.** The links were created in a single commit on 2026-07-25 whose message says *"single source of truth"*, and nothing was added after, so the five project-local skills written in August — `verify-pr`, `reproduce-first`, `issue-queue`, `pr-review-queue`, `prd-queue` — were invisible to Codex, OpenCode and pi. One `.agents/skills -> ../.claude/skills` link produces the same layout, cannot go stale, and fails identically on Windows. `scripts/check-symlinks.sh` hardcodes no count and passes at three tracked links, self-test included; only its prose needed updating.
