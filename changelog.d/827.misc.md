## The desktop settings store cannot hold a credential, and that is now checked

The desktop app's settings document has one hard rule — a secret goes in neither `desktop.toml` nor `localStorage` — and the only thing watching it was a check that read key *names*, so a field called `endpoint` whose value was a token passed, a frontend-only `apiKey` on the TypeScript DTO was outside every check that existed, and no check had ever looked at a value at all. That is fine as a tripwire and was labelled as one; it is not a boundary, and the voice-control work needs a boundary before it stores an API key.

There is now one. Every field in the settings schema has to have a type from an allowlist of types that cannot carry arbitrary text, so a credential has no field to sit in whatever anyone calls it — and `String` is deliberately not on that list, which means the moment a credential *is* needed the gate goes red and the value has to go behind the keychain-backed secret seam instead. A uniquely-named sentinel is followed through every sink it could reach: the document on disk across a load–modify–save round trip, the settings IPC in both directions, the parse diagnostic, and both halves of the write-error split. The TypeScript DTO's shape is pinned field by field, the settings normaliser is pinned to construct its result rather than copy its input, and the app's `localStorage` key set is pinned constant by constant — so a new key is a deliberate edit and a review conversation rather than a line nobody sees.

What none of it claims is written down beside it, because a boundary described too widely is worse than one described honestly: a key the schema does not own keeps its value on disk, since the save merges rather than replaces, and a refused settings message can quote a value back to the webview that sent it. Both are measured rather than glossed. `docs/develop/desktop-gui.md` has the full table of what each check establishes and what it does not.
