## A remote deck's endpoint is now discovered by asking the deck over there, not by guessing at its filesystem

Connecting the desktop to a remote deck starts by finding out **where that host's daemon listens** — a path that cannot be derived locally, because `ssh -L` expands neither `~` nor an environment variable on the remote side and the far host's `XDG_RUNTIME_DIR` and uid are not knowable from here. That question used to be answered by a shell snippet running on the far host, restating the path rules in `sh` and picking a candidate with filesystem tests alone. It now runs the far host's own `dot-agent-deck daemon endpoint` first, and falls back to the snippet only when that host has no deck installed or is running a build that predates the subcommand.

**The fix is that an untrusted endpoint is no longer forwarded.** The old snippet could not check the socket's *mode* — there is no portable `test` predicate for one — so a listener at `0666` satisfied every clause it was able to carry, and the desktop forwarded it. The resolver applies the same `verify_endpoint_trusted` rules the local side applies: not a symlink, a socket, owned by this uid, mode exactly `0600`. That refusal **binds**: the snippet ends with no path rather than dropping to a rung that would print the same path unchecked, which is what makes the check a check rather than advice.

That closes the shapes a **different** user on the remote host could plant. It does **not** authenticate the listener, and nothing here should be read as saying it does: a completed handshake proves something is listening and speaks this protocol, not that it is the deck's daemon, and an attacker already running as the remote login user can satisfy every check. Making a forwarded endpoint self-describing is a separate question, tracked in [#1189](https://github.com/vfarcic/dot-agent-deck/issues/1189) with the design and the reason it was not taken here.

**What it does not yet fix is availability**, and the distinction is worth stating because a stale socket is the symptom users actually meet. A socket inode outlives the process that bound it and nothing in the old snippet connected, so a dead daemon's leftover entry was selected exactly as a live one was. The resolver now *detects* that — but it reports it as "nothing learned here" rather than as a refusal, deliberately, so the remaining candidates still get their turn. With one candidate to try there is nowhere else to go, so the outcome is the same "deck is not answering" as before. The detection pays off once there is a second candidate for discovery to move on to.

This is not a regression — the impersonation route predates the change, and exploiting it needs a foothold on the remote host under your own login. Local, non-forwarded endpoints were never affected: those are `lstat`ed before connect, so a symlink or a foreign-owned inode at the endpoint path is refused on its own account.

**Nothing on the TUI↔daemon wire moved.** The handshake the resolver performs is the existing `Hello`, so this adds no protocol version and no compatibility break, and a desktop updated ahead of the hosts it talks to keeps discovering them exactly as before.

The threat model, including what stays open, is in [`docs/develop/remote-endpoint-discovery.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/remote-endpoint-discovery.md).
