## A remote deck's endpoint is now discovered by asking the deck over there, not by guessing at its filesystem

Connecting the desktop to a remote deck starts by finding out **where that host's daemon listens** — a path that cannot be derived locally, because `ssh -L` expands neither `~` nor an environment variable on the remote side and the far host's `XDG_RUNTIME_DIR` and uid are not knowable from here. That question used to be answered by a shell snippet running on the far host, restating the path rules in `sh` and picking a candidate with filesystem tests alone. It now runs the far host's own `dot-agent-deck daemon endpoint` first, and falls back to the snippet only when that host has no deck installed or is running a build that predates the subcommand.

**The user-visible fix is availability.** A socket inode outlives the process that bound it, and nothing in the old snippet connected — so a stale entry left behind by a daemon that was killed was selected exactly as a live one was. The tunnel then came up against a socket nobody was listening on, and a remote deck that was genuinely running read as unavailable, repeatedly, until somebody cleaned the path up by hand. The resolver completes a bounded handshake before it answers, so on a host where it runs a stale entry is refused and discovery moves on to the live one.

**It also narrows a pre-existing security gap, and it is worth being exact about which one.** The old snippet could not check the socket's *mode* — there is no portable `test` predicate for one — so a listener at `0666` satisfied every clause it was able to carry. The resolver applies the same `verify_endpoint_trusted` rules the local side applies: not a symlink, a socket, owned by this uid, mode exactly `0600`. That closes the shapes a **different** user on the remote host could plant. It does **not** authenticate the listener, and nothing here should be read as saying it does: a completed handshake proves something is listening and speaks this protocol, not that it is the deck's daemon, and an attacker already running as the remote login user can satisfy every check. Making a forwarded endpoint self-describing is a separate question, tracked in [#1189](https://github.com/vfarcic/dot-agent-deck/issues/1189) with the design and the reason it was not taken here.

This is not a regression — the impersonation route predates the change, and exploiting it needs a foothold on the remote host under your own login. Local, non-forwarded endpoints were never affected: those are checked by `lstat` before connect and by peer uid after.

**Nothing on the TUI↔daemon wire moved.** The handshake the resolver performs is the existing `Hello`, so this adds no protocol version and no compatibility break, and a desktop updated ahead of the hosts it talks to keeps discovering them exactly as before.

The threat model, including what stays open, is in [`docs/develop/remote-endpoint-discovery.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/remote-endpoint-discovery.md).
