## The automated PR reviewer gates on the required checks, not on every check

Selection for the agent PR reviewer now waits on the status checks branch protection actually requires, and reads that list from the live `main-protected` ruleset at run time rather than from a copy kept by hand. A job protection deliberately leaves out of its required list no longer withholds a review.

It used to withhold one, and the cost was larger than "advisory" suggests. The selector refused a pull request when any check run on its head had failed, required or not; the reviewer's approval is what satisfies the required-review rule, so an advisory red blocked the only thing that could unblock the merge. PR #1076 lost its approval that way — all five required contexts green, and a `devbox` job that died fifteen seconds in on a 504 from a third-party CDN inside someone else's action, on a diff touching no devbox or workflow file.

Reading the required list from the ruleset is what makes the narrower gate safe rather than merely looser: the old blanket rule existed as a hedge against the ruleset requiring a context the script did not list, and a list re-read from that ruleset on every run is not one anybody has to remember to update. The hardcoded five remain only as a fallback for a run that cannot read the ruleset, which says so in its log and is pinned against `scripts/apply-branch-protection.sh` by a test.

Review of this change turned up a second, older defect in the same gate and it is fixed here too: a re-run check was being read at its *oldest* conclusion. The code picked whichever entry for a name came last in the API's response, under a comment asserting that re-runs append — they do not. `GET /commits/{sha}/check-runs` returns newest first, measured on `4afd7498`, so a check re-run from red to green went on reading as red. Selection now orders re-runs by `started_at` and `id` rather than by position, so it does not depend on how the endpoint sorts.

A ruleset that requires no status checks at all is now taken at its word rather than replaced by the fallback, and announced with a warning. Substituting the hardcoded five there would have reproduced this same issue one level up, with the reviewer holding out for checks GitHub no longer requires.

An ignored red is now named rather than swallowed: the selection log states which advisory checks were failing on a pull request it selected anyway, and the reason a pull request was skipped still names the required context that held it.
