## A spawn-time prompt now waits for the agent to say it is there, not for the deck to guess what it is

When the deck spawns a pane it draws the card for it immediately, and it works out what agent that card should say by reading the command it just chose to run — `claude …` means Claude Code. Three spawn-time delivery paths (a mode's seed prompt, an orchestration start role's remit, and a dispatched task) treated that resolved agent type as proof the pane could accept input, and wrote the first payload half a second later. A card is not a reader. Measured in the field: a pane spawned at 12:57:02 through a launcher (`devbox run agent` → init hooks → `claude`) had its seed typed in at roughly 12:57:02.5, about **3.7 seconds before the agent announced itself** — into a PTY whose program had not started reading.

Those three gates now additionally require that a producer has actually announced a conversation on the pane. The payload lands on the fast path when the agent is genuinely there, so that path no longer spends one of the two payload writes each delivery is allowed on a program that has not started reading — which matters because that spare write is the one bounded replacement a genuinely swallowed prompt has left, and because bytes sitting in a PTY before the agent's input is in submit-aware mode are the doubled-seed (`seedseed`) accumulation the cap exists to bound. A prompt was already recovered on retry rather than lost outright, so the visible change is that the first attempt is the one that works.

**An agent that announces nothing still gets its prompt, on the same schedule as before.** Each of the three paths keeps its unchanged 10-second fallback, which writes regardless of what the pane has said — opencode's cold boot, a Pi pane that reports no signal, a plain `cat` under the scheduler. Narrowing the fast path makes that fallback their only delivery rather than removing one, so the worst case this narrowing can introduce is a bounded wait, not a dropped prompt.

No compatibility contract moved and no action is needed: `PROTOCOL_VERSION` is unchanged at 9, no message or field changed shape or meaning, and the fact the gate now reads is derived from events the daemon already sends. A mixed-version pair keeps working in both directions — an older deck against a newer daemon behaves exactly as it does today, and a newer deck against an older daemon falls back to the 10-second path at worst.

Reported and fixed as [#1005](https://github.com/vfarcic/dot-agent-deck/issues/1005); [#1006](https://github.com/vfarcic/dot-agent-deck/issues/1006) covers the end-to-end test that could not reach this ordering, because the harness's directly-exec'd agent announced itself too fast to lose the race.
