## A failed worktree ownership marker no longer promises a confirmation prompt it cannot deliver

`dot-agent-deck worktree reclaim` removes a worktree unattended only when the deck can prove it created it, and that proof is a marker file written at creation time. When that write failed, the warning told the operator the worktree would read as **foreign** at reclaim time and need an **explicit confirmation**. In the case that most commonly emits that warning, it would not.

`std::fs::write` is `File::create` followed by `write_all`, and `File::create` truncates before the first byte is written — so a full disk, an I/O error or a killed process leaves a zero-length file where a moment earlier there may have been nothing at all. The ownership gate asked only whether a file was there, so that residue resolved to `Ours`, and a merged, clean worktree with `Ours` reaches the one verdict that deletes a directory **without** asking. The warning fired, and the prompt it promised never came.

Two changes, covering different halves of it. A failed write now removes what it left at the marker path, so the marker is genuinely absent and the confirmation genuinely happens; and the gate now requires the marker to be non-empty as well as present, which catches the killed-process case no error path can clean up after. Neither is atomicity and neither claims to be — a torn write that got *some* bytes onto disk still reads as a claim, and closing that would mean a temp-and-rename dance that could strand a second deck-owned file in git's administrative directory, which is worse than a truncated informational document.

Where the failure leaves a claim behind that cannot be removed — an unremovable leftover, or an earlier valid marker that a failed re-mark left intact — the warning now says *that* instead, and names the path to check before running `worktree reclaim`. Which of the two is reported comes from probing the marker path rather than from deducing it from which step failed; the two answers disagree in both directions.

Ordinary marker writes are unaffected, and a worktree whose marker was written successfully still reclaims exactly as before. The mechanism, and what it deliberately does not cover, are recorded in [`docs/develop/worktree-ownership.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/worktree-ownership.md).
