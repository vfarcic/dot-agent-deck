## The dispatch queue skills bring the base up to date before dispatching, instead of reporting it stale

`/issue-queue`, `/prd-queue` and `/pr-review-queue` each start a batch of isolated units, and `dispatch` cuts every one of them from whatever `HEAD` the caller is standing on — it takes no base or branch option, and `git worktree add` with no start-point resolves to `HEAD`. The first two skills fetched `origin` and verified every candidate against `origin/main`, which fixed what they *checked* and nothing about what the units were *built on*; `/pr-review-queue` did not look at the base at all. All three now fast-forward the checkout first, and only report when they cannot.

The old rule was to fetch and never pull, on the ground that the runner may have local work and a skill has no business moving their branch. That objection is right, and it is kept — it is exactly what the new preconditions test for. What was wrong was its scope: it declined every case because it distinguished none of them, and distinguishing them is three commands that cost nothing after a fetch the skill was already doing. When `HEAD` is `main`, no tracked file is modified, and there is no local commit that is not already on the remote, there is no local work to move: a `git merge --ff-only origin/main` under those conditions rewrites nothing, discards nothing, creates no merge commit, and is undone exactly by a `git reset --hard` back to the sha the skill printed. Untracked files are deliberately not a blocker, because a fast-forward that would clobber one already fails cleanly by itself.

Refusing was measured, and surfacing the staleness was not enough. On 2026-08-30 two orchestrations were dispatched for the desktop PRDs #740 and #745 from a local `main` six commits behind the remote — and one of those six commits was the one that introduces the `desktop/` directory both units had been dispatched to work on. Both were cut from a tree that did not contain the subject of their own PRD, and neither produced a single original commit before being stopped and re-dispatched. A unit cannot discover this about itself: it sees a valid checkout, finds the code its issue describes missing, and reasonably concludes the issue is stale rather than its base.

The three cases where local work really does exist — a modified tracked file, a `HEAD` that is not `main`, a `HEAD` carrying commits the remote has not seen — keep the old behaviour verbatim: nothing is touched, the precondition that stopped it is named, and dispatching anyway, clearing the blocker first, or deferring the batch stays the runner's choice. The refusal no longer stops the queue, though; selection never depended on the checkout, so it is carried forward and put in front of the runner at the moment they are already deciding how many units to start. Each skill now reports the base its units were cut from as a **distance from `origin/main`** rather than a branch name, because "cut from `main`" reads identically whether `main` is level with the remote or six commits behind it — which is precisely how the 2026-08-30 batch looked fine.
