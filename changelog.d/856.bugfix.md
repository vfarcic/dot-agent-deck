## The desktop's CLI column is the deck's answer, not the app's guess

The **CLI** column on the desktop's agent overview names the binary each agent runs — `claude`, `opencode`, `codex`. The app used to work that name out itself: the deck sent an agent *type*, and the app looked that type up in its own compiled-in copy of the agent registry. Which binary a running agent is, is a fact about the deck's world — the deck forked the process — so the app was answering a question it had no authority over.

**The deck now reports the binary name and the app copies it through.** Nothing about what you see changes while the app and the deck are the same build, which today they always are: the app refuses to connect to a deck on a different protocol version, and a build-stamp difference is either within one release or something you have to accept explicitly. That is a property of the connection check rather than of the design, and relaxing that check is exactly what is being worked on — at which point a column derived from the *app's* table could name a binary the deck does not run, plausibly and silently, which is the worst shape for a value read as fact.

**Where the deck names no binary the cell is now empty, and it used to read `agent`.** That happens for a pane the deck holds no agent type for — a plain shell, say — and for an agent type from a deck newer than the app. An empty cell says "the deck did not say"; the word `agent` said something about the pane that nothing had reported. It is the same thing the Spawned and Activity columns already do with a value the deck did not send, and, crucially, there is no longer any local table to fall back to — a fallback would put the divergence straight back.

Nothing in the protocol's shape moved: the binary name is a new optional field alongside the existing spawn and activity timestamps, so an older deck simply sends nothing and a newer one sends a key an older app ignores. `PROTOCOL_VERSION` is unchanged.
