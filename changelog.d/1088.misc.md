## CI can be put behind a merge queue, keeps every post-merge run, and says when `main` goes red

Three changes to `.github/workflows/ci.yml`, all of them consequences of one incident. On 2026-09-14 `main` was red for about 52 minutes and nobody was told. [#1066](https://github.com/vfarcic/dot-agent-deck/pull/1066) added a construction site for `dispatch::DispatchContext` and [#1081](https://github.com/vfarcic/dot-agent-deck/pull/1081) added a `caller` field to that struct, updating every constructor that existed on its own base. Each PR was green, neither had seen the other, git merged both cleanly because the conflict is semantic rather than textual, and the compiler reported `error[E0063]: missing field caller`. Three of the five required checks went red at `430dda26`; the post-merge run reported `completed/failure` and notified nobody; five further PRs merged on top before an unrelated desktop PR's conflict resolution supplied the missing field by accident. Nothing here touches `src/`, the TUI↔daemon protocol, orchestration or hooks, so `PROTOCOL_VERSION` is untouched and CLAUDE.md rule 12's cross-version check does not apply.

**`ci.yml` handles `merge_group`.** No workflow in this repository did before. A merge queue tests each PR on a temporary `refs/heads/gh-readonly-queue/main/…` branch carrying `main` plus every PR ahead of it — the projected `main` that a PR's own `pull_request` run never sees, because the `main-protected` ruleset has `strict_required_status_checks_policy: false` and nothing re-tests a stale branch before it merges. The trigger is the precondition for turning that setting on rather than the fix by itself: a queue enabled without one waits forever on five required contexts that never report against the queue's branches. Context names are what a ruleset matches and they do not move with the event — no job in this file carries a job-level `name:` or a `strategy:` matrix, so `build`, `build-macos`, `build-windows`, `security` and `e2e-deterministic` each report under their own job id here exactly as they do on a `pull_request`. The `changes` path filter is safe on this event for the reason its own comment already gives: `github.event.pull_request.user.login` is empty on a `merge_group` payload, so the author check fails and the job exits early with `devbox_only=false` / `flake_only=false`, the full matrix. A filter that read a base ref instead could have skipped everything and reported green having tested nothing, which is worse than hanging because it looks like success.

**Post-merge runs on `main` are no longer cancelled.** `ci-${{ github.ref }}` with an unconditional `cancel-in-progress: true` put every push to `main` into one group, so each merge killed the previous merge's verification — `2601bed8` and `51b7ee9e` never completed a run at all. A `pull_request` ref keeps the old behaviour under its own `refs/pull/N/merge` group, where a superseded run is genuinely waste; a push to `main`, a `merge_group` check and a `workflow_dispatch` each get a group of their own keyed on `github.run_id`. Setting `cancel-in-progress: false` alone would not have been enough: same-group runs then queue, GitHub holds at most one pending run per group, and a third arrival evicts the pending one, so the nine-merge batch would still have lost most of its runs to a different verb. For a queue check the stake is higher than a lost record — a cancelled `merge_group` check is a stuck merge.

**A failed post-merge run on `main` now says which commit and which job broke it.** The new `notify-main-red` job fires only when `github.event_name == 'push'`, `github.ref == 'refs/heads/main'` and `contains(needs.*.result, 'failure')`, so it is silent on pull requests and on queue checks, and a cancelled job does not page anyone. It `needs` every other job rather than only the five required contexts, because a red `nix`, `devbox`, `desktop-web`, `desktop-browser` or `windows-cross-check` also means `main` is broken. It cannot fail a build: `scripts/notify.sh` always exits 0, nothing parses its output or retries it, and the `::error::` annotation and the step summary are written first and unconditionally, so the run carries the commit, its subject and the failing job names whether or not a message goes out.

**The Telegram half of that job is dormant until two repository secrets exist.** `notify.sh` needs `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`; `gh secret list` reports neither on this repository as of 2026-09-15, so the send currently skips with `notify: TELEGRAM_BOT_TOKEN unset — skipping send` and returns 0. That is recorded here rather than left to be discovered, since a notification path that silently never fires is the defect the job exists to fix. Registering the two secrets is a repository-admin act, as is enabling the merge queue on the `main-protected` ruleset; both are follow-ups to this change rather than part of it.

**The merge-queue path is unverified and cannot be verified from a pull request.** A `merge_group` event is only delivered once the queue is enabled, so what has been checked is narrower than "it works": `actionlint` 1.7.7 with `shellcheck` 0.10.0 reports nothing on this file, and the notification step was extracted from the YAML and run against a synthetic `toJSON(needs)` payload, where it named exactly the two `failure` jobs and skipped the `cancelled` and `skipped` ones, wrote the summary, and exited 0 with both secrets unset. The `pull_request` group string is unchanged by construction — `ci-${{ github.event_name == 'pull_request' && github.ref || github.run_id }}` evaluates to `ci-${{ github.ref }}` on that event — so this PR's own checks behave exactly as before.

**Two claims in the file's own comments were narrowed rather than left standing** (CLAUDE.md rule 17). The `persist-credentials: false` note counted "nine checkouts" while there were already ten, and this change makes eleven; the count now carries the anchored `grep` that recounts it, anchored because an unanchored pattern matches the comment quoting it and reports twelve. The `e2e-deterministic` note claimed no other job in `ci.yml` reads `secrets.*`, which `notify-main-red` falsifies; the narrower fact that lane actually rests on is untouched, since neither Telegram secret is an agent or test credential, neither is registered, and that job is unreachable from a `pull_request` run.
