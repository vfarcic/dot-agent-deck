## Dispatched orchestration tabs keep their run-identifying label across a reattach

A dispatched or scheduled orchestration tab is labelled with its per-run identity — `mixed · issue-950`, the orchestration name plus the worktree it is working in — but that suffix was lost the moment you detached and reconnected, and the tab came back as the bare orchestration name. With several dispatches open at once every one of those tabs reattached under the same label, so the tab strip stopped saying which run was which, which is exactly the confusion the suffix exists to prevent. It was not remote-specific: `dot-agent-deck connect` runs the TUI on the remote host against that host's own daemon, so a local detach/reattach lost the label the same way — remote just makes detaching the normal way to work.

The label is now stamped on every role pane when the orchestration is spawned, so it survives the round trip through the daemon and the live tab and the reattached tab cannot disagree about it. An orchestration with no per-run identity to add — one whose working directory is already named after it — still shows its canonical name, unchanged. A worker pane that has to be re-created mid-run (a `clear = true` role whose predecessor is gone) now rejoins its tab carrying the same label instead of dropping it, which is the narrower version of the same loss.

No configuration or action is needed, and no compatibility contract moved: the field was already optional on the wire, so a mixed-version pair keeps working — an older daemon simply reports no label and the tab falls back to its name as before, and an older TUI against an updated daemon picks the label up.
