## The manual-review hold on the Rust toolchain pin is now actually a hold

`renovate.json` holds the workflow Rust toolchain pin for a human even on a patch, because it has to move in lockstep with `devbox.json`'s `rustc`/`cargo`/`clippy`/`rustfmt` by hand and because a Rust release is where new deny-by-default lints arrive. That hold has been advisory rather than enforced: the same `toolchain: 1.97.1` string was being detected a second time by Renovate's `github-actions` manager, which routed it into the automerging `GitHub Actions` group.

The customManager's own description is what hid it. It opened "The github-actions manager cannot see this: it reads the `uses:` ref" — true when written, false now. Renovate carries a registry of community actions whose version lives in an **input** rather than the ref (`lib/modules/manager/github-actions/community.ts`), and `dtolnay/rust-toolchain` is in it, mapped to `packageName: 'rust'` with `withSchema: valSchema('toolchain')` — it reads the identical string the custom manager was written for and emits it as depType `uses-with`. The `GitHub Actions` rule matched the manager with no depType filter at all, so it automerged all six depTypes that manager can emit rather than just action refs.

The two lanes were visible side by side and nobody had looked: [#624](https://github.com/vfarcic/dot-agent-deck/pull/624) (`rust-lang/rust`, branch `renovate/rust-lang-rust-1.x`, `manual-review`, "Automerge: Disabled by config") and [#623](https://github.com/vfarcic/dot-agent-deck/pull/623) (`rust`, `uses-with`, branch `renovate/github-actions`, no label, "Automerge: Enabled") proposed **byte-identical** 1.97.1 → 1.98.0 diffs — the same seven edits, the same blob hashes — on the same day. #623 did not merge itself only because CI was red from an unrelated `main` breakage, since fixed by [#609](https://github.com/vfarcic/dot-agent-deck/pull/609).

What that would have cost is concrete rather than theoretical, because nixpkgs has no Rust 1.98.0 yet — `devbox search rustc@1.98.0` returns `No results found`, and 1.97.1 is still the newest it offers. An automerged #623 would have moved CI to 1.98.0 while every `devbox shell` stayed on 1.97.1, breaking the property `ci.yml`'s own comment says the pinning exists to provide: that `cargo test-fast` locally and the same command in CI are the same claim. And because the rule carries a `groupName`, a toolchain change could have arrived bundled inside a PR titled "update GitHub Actions" alongside a handful of `@v7` bumps, merged without ever being read on its own.

The `GitHub Actions` automerge rule is now scoped to `matchDepTypes: ["action"]` — `uses: owner/repo@ref` and nothing else. That direction is deliberate: excluding the one dep name observed misbehaving would have been correct only until Renovate's registry grew its next entry, whereas a whitelist leaves anything the manager learns to detect tomorrow **outside** the automerging rule with no edit required. Being wrong this way costs a PR someone has to click; being wrong the other way costs an unreviewed toolchain change on `main`. A second rule states the hold on the non-action depTypes explicitly and labels it `manual-review`, following the convention the 0.x-minor rule set — a hold that exists only as an absence is invisible on the PR page and impossible to grep for. In this repo `uses-with` means two toolchains wearing a GitHub Actions costume: the Rust pin, and the docs site's Node version from `actions/setup-node`.

`taiki-e/install-action` is **not** in that registry today, so the `cargo-nextest` pin has the same exposure latently rather than actively. Its description now records that as an expiry date rather than a property, and the depType rules cover it the day the registry grows an entry, without anyone having to notice.

The duplicate PR is not suppressed, and that is the deliberate half. Disabling the `github-actions` lane for `rust` would have removed the noise and also removed the redundancy — leaving the custom manager's regex as the only detector of a pin whose named failure mode is *silent rot*, so that a reformatted `toolchain: "1.98.0"` (quoted, which the regex does not match) would take both lanes down at once. Two held PRs per Rust release is the cheaper mistake, and they self-resolve: the lanes edit the same lines, so merging either makes the other conflict and `rebaseWhen: conflicted` autocloses it, exactly as happened to [#252](https://github.com/vfarcic/dot-agent-deck/pull/252).

Renovate configuration only; no change to the shipped binary, and no version pin moved in this change.
