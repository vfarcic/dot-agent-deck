## Review a project's commands before the deck runs them

A project's `.dot-agent-deck.toml` decides which commands the deck runs and which prompts it gives your agents, so a repository you clone, or a change someone pushes to it, could make the deck run something you never looked at. The deck now runs an orchestration from a project's config only after you have approved what it would run.

When you start an orchestration in the TUI (the New Agent form, `Ctrl+n`) or in the desktop app (the New agent dialog, or Activate on the Runs screen), and you have not approved it before or its text changed since you did, the deck shows **Review project commands** before anything starts. It lists the project, the orchestration, and each role's name, command, description and prompt, marks the roles that are `changed` or `new` since your approval, and lists roles that were removed. Text that could disguise itself, such as control characters, is shown rather than obeyed. In the TUI press `a` to approve and start, or `Esc` to cancel; in the desktop app choose **Approve and start** or **Cancel**, or say "approve project commands" by voice. Enter never approves, and cancelling starts and stores nothing. An orchestration you approved, whose text has not changed, starts with no prompt, exactly as before. When the TUI restores a saved session, it asks the same way for each orchestration that needs it, and leaves one you decline unrestored.

Approvals are remembered per project and per orchestration, and cover the exact text you saw: changing a role's command, description or prompt by even one character asks again, while editing comments or another orchestration does not. A linked worktree of a git repository uses the approval of its main checkout, as long as the orchestration has a `name`; an unnamed one takes its name from the directory, so each worktree asks separately.

Work that runs while nobody is watching never asks: a schedule, **Run now**, a scheduled issue dispatch, `dot-agent-deck dispatch`, a delegate, `pane restart` and `pane spawn` refuse an orchestration that is not approved, start nothing, and report why where you will see it: the command's own output, the schedule's last run in `dot-agent-deck schedule list` and the TUI's schedule manager, and the deck's log. Each refusal names the orchestration, the project and the command that fixes it.

To manage approvals from a terminal outside the deck, use `dot-agent-deck trust list` to see what you approved and whether it still matches, `dot-agent-deck trust approve [<dir>] [--orchestration <name>]` to review and approve (add `--yes` for scripts), and `dot-agent-deck trust revoke` to withdraw an approval. The approve command refuses to run from inside a deck pane.

After upgrading, expect one prompt for each orchestration you open, including those restored when the TUI first starts, and approve once any project your schedules or dispatches use, since those are refused until you do. The desktop app cannot show the review through a deck whose daemon is older than this release, so it starts no orchestration on such a deck and tells you how to approve and start it there; upgrade that deck's daemon to start orchestrations on it from the app.
