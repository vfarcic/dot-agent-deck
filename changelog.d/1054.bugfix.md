## The agent reviewer had a credit cap it did not know about, and blew it on the largest PR

`pr-review.md` opened with *"Wall clock is the runaway guard. **There is deliberately NO credit cap.**"* That was false for as long as it had been written. gh-aw's firewall api-proxy applies `maxAiCredits` to every run from `vars.GH_AW_DEFAULT_MAX_AI_CREDITS || '1000'`, so declaring nothing does not mean uncapped — it means **1000**.

It surfaced the way the original comment predicted a cap would. On 2026-09-13 the sweep reviewed four pull requests successfully and the fifth — [#1035](https://github.com/vfarcic/dot-agent-deck/pull/1035), the largest open one at 70 files — died after eight minutes with `403 Maximum AI credits exceeded (1011.080265 / 1000)`, having produced **no verdict at all**. gh-aw filed the diagnosis itself: *"hit the configured `max-ai-credits` guardrail. Used 1K of 1K max (over by 11.1)."* The argument in that comment was right — a cap does not prevent spend, it wastes it, and because cost scales with diff size it fails selectively on the largest pull requests, the ones a review is most valuable on. What was wrong was the conclusion that the cap could be declined.

It cannot. The schema is `exclusiveMinimum: 0`, so there is no "unlimited" value, and AWF clamps anything above 10000 regardless. So the ceiling is now declared explicitly at **10000** — the highest reachable value — in the frontmatter rather than in a repository variable, so it is visible in the file it governs and shows up in a diff.

**Raising it is only half the fix, because a ceiling that is hit still yields nothing.** The verdict is a single comment posted at the end of the run, so an overrun leaves silence rather than a shallow answer — and silence is indistinguishable from the reviewer being switched off. The prompt now carries the other half: the agent is told its budget, told that overrunning produces no verdict at all, and given a **bounded amount of work** — rank the diff by risk, deep-read roughly the ten highest-risk files, make one pass, emit once — so it finishes inside the budget rather than discovering the edge. The first attempt at this was “post a provisional verdict, then refine it”, and review caught that it cannot work: `add-comment` is capped at 1, the agent has `edit: false` and read-only GitHub access, so a provisional verdict would simply **be** the verdict and the vote job would act on a pre-investigation read — trading a missing review for a wrong one, which is worse. It is also pointed at the largest single cost. The #1035 run fanned out four `general-purpose` subagents over a 70-file diff, each carrying its own context; delegation is now off by default, capped at two, gated on diff size, and never before the provisional verdict is posted. `INSUFFICIENT` is named as the honest outcome when a confident review does not fit in the budget.

Recompiling with `gh aw compile` also moves `GH_AW_ACTION_FAILURE_ISSUE_EXPIRES_HOURS` from `"168"` to `"0"` in the regenerated lock. That is a pre-existing drift between the committed locks and the current compiler default, not part of this change; it rides along because the lock is generated rather than edited. The two `issue-labeler` locks are left untouched and will pick up the same drift whenever they are next recompiled.
