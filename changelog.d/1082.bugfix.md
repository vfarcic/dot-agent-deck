## A producer-supplied id can no longer forge, overwrite or reorder a line in the daemon's log

Every id that arrives over the daemon's hook socket — the `pane_id`, `session_id` and `role` on each verb, the pane a message *claims* to come from, and the raw line itself — was written into a `tracing` field with `%` (Display), which escapes nothing. A raw LF in a `pane_id` therefore forged a whole additional log line, a CR overwrote the one being written, `ESC [ 2J` cleared the screen of whatever rendered the log, and a U+202E override reordered a line without changing a byte of it. The socket authenticates nobody and its provenance gate deliberately admits an *unattested* claim (a pane it has never heard of is `Unattested`, not refused), so reaching these fields needs nothing but the ability to connect to the socket as the same user.

Turning the subscriber's own ANSI styling off does **not** help and is the trap worth naming: it governs how the subscriber decorates its own output and escapes nothing inside a field value. The fix is `config_validation::escape_field_for_log`, which already existed and already guarded four name-carrying sites from PR #1081 — the same two halves, clamp then escape, so there is one definition of "safe in a diagnostic" rather than a second one for logs.

**22 sites**, enumerated from the code rather than taken from the issue's estimate: 17 in `src/daemon.rs`'s hook loop (the provenance refusal and its warn-only sibling, all seven `DaemonMessage` verbs, the `dispatch from unknown pane` refusal, the `Received event` line, the unrecognized-`event_type` warning and the foreign-`SessionStart` warning), 4 in `src/state.rs` (the two unknown-pane warnings, plus the two `delegate_targets` warnings that log an element of a producer-supplied `to` array), and the `Malformed event:` branch — which interpolated the whole rejected line into the log *message*, and so was the widest opening on the surface.

**No diagnostic lost evidence, and the one site where that was a real risk got its own bound.** The two raw-line sinks keep issue #903's 512-byte prefix and its `…<truncated>` marker rather than the 120-character value bound: an ordinary hook event is longer than 120 characters and its keys serialize in sorted order, so the value bound would have cut away the very `event_type` the `raw_line` warning exists to show — the fix would have cost the diagnostic. A test asserts both halves of that, including that the value bound really would have dropped it.

Three classifications were checked and deliberately left alone: `return_dispatch_completion`'s `unit_pane_id`, and the `work-done` sites above the role-map lookup, log bare because each is reached only when that producer string matched a daemon-minted key — at which point it *equals* one; `?`-Debug fields (`tool_name`, `tool_detail`, `signal.to`, `agent_type`) are already safe, because `str`'s `Debug` escapes control characters and Cf bidi formats alike; and `role`/`orchestration`/`mode` elsewhere are read back out of the role map or the project config. The one correction to that last group: `delegate_targets`' two warnings log an element of `signal.to`, which is producer-supplied and reached precisely when it matched no configured role, so those two are in the sweep.

Nothing on the wire moved: no message variant, no field shape, and no field's meaning. `src/daemon_protocol.rs` is untouched and `PROTOCOL_VERSION` does not change — this is what the daemon *logs*, not what it *sends*.
