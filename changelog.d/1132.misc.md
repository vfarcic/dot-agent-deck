## `pane-input/032` and `idle-worker/015` wait for the bytes instead of betting on 75 ms

`prompt/pane-input/032` wrote at a real `/bin/cat` PTY, slept a fixed **75 ms**, and then asserted the bytes had physically arrived — #851's shape, in a test `cargo test-fast` runs and therefore in the required `build` and `build-macos` jobs. Reproduced before touching anything, and it is not a theoretical risk: with its three sleeps at 0 ms the test **failed 3 of 3 runs**, every time at the same precondition (`the unsent user draft must physically reach the TUI PTY`). The result depended on the sleeps.

**Each sleep is now a wait on the condition it was standing in for.** Attempt 1's precondition waits for that delivery's payload and submit CR to finish round-tripping — both line terminators, the line discipline's echo and `cat`'s copy — rather than for a constant. The unsent draft is typed through the helper that drains the pane first, writes, and waits for the draft's own echo. The third sleep is gone outright: what it was buying is the drain the draft helper now does for itself.

**The draining half is the one easiest to mistake for tidiness, and it is the fix.** `/bin/cat` and the line discipline are two independent writers into one PTY output queue, so a `cat` copy still in flight can land **inside** the draft's echo and split it permanently — issue #850's interleave, measured and written up in `spawn.rs` when it was first fixed there. A wait for "the draft is visible" does not help once the draft can no longer be found in one piece.

**Establishing quiescence for the exact-equality baselines was the part that needed more than an arrival wait.** `before_replacement` and `before_probe` are compared to a later snapshot by `assert_eq!`, so it is not enough that the expected bytes have landed — nothing further may be coming, or a late `cat` copy lands inside the comparison window and reads as bytes the code under test sent. Three facts make each baseline quiescent by construction rather than by elapsed time: the drain settles everything the preceding deliveries owe; the draft carries no line terminator, so `cat` is given nothing to copy; and the echo wait proves the only bytes still outstanding have arrived. After the draft helper returns, the buffer cannot change again unless the code under test writes. In `scheduler/idle-worker/015` the notice is `payload + LF`, so it *does* complete the line the draft opened — there the baseline waits for the notice's own echo and then for both completed lines to have fully round-tripped.

**Two sleeps stay, deliberately, and they are a different kind.** Each of the three `after == before` assertions is a NEGATIVE: the contract is that the attempt writes nothing, so there is no byte whose arrival could end the wait and nothing to key it on. `spawn.rs`'s `UserFrameRetryExpectation::WritesNothing` keeps a 75 ms window for that reason and these keep theirs, at the value they have always had. What changed is the consequence of the window being too short: with the baseline now quiescent, the buffer is frozen unless the code under test writes, so a short window can only fail to catch a violation — it can no longer manufacture one. Before, a late `cat` copy of the *preceding* delivery's own line could land inside it and be read as the attempt's bytes.

**The helpers moved, because that is what the fix was blocked on.** #850/#851/#892 built these waits inside `src/spawn.rs`'s private `#[cfg(test)] mod tests`, where nothing else could call them, so the same defect sat unfixed in `src/ui.rs` and `src/state.rs`. They now live in a crate-level test-only module, `src/test_pty_wait.rs`, declared under `#[cfg(test)]` beside the `test_temp` and `test_isolation` precedent; `spawn.rs` keeps the vocabulary built on top of them (`wait_for_detached_delivery_attempt`, `attempt_slice`, `payload_echoes`, `type_user_frame`), where its only callers are. The move is verbatim — the alternatives were three divergent copies of a fix that took three issues to get right, or a re-derived short-sleep poll at each call site with none of the diagnostics. `scheduler/dispatch/018`–`021` and `/016` pass unchanged across it.

**Verified in both directions.** With **every** sleep in both tests at 0 ms — the three named ones and the negative windows too — they passed **40 of 40** runs: 20 on an idle box, then 20 more against 32 busy loops and a concurrent `--features e2e,e2e-live` clippy build, at load average 56 on 16 cores with `/proc/pressure/cpu` `some avg60` at 74.6. Idle alone is enough to falsify (that is how the original 3-of-3 failure was found) but not to confirm, which is why the loaded batch is there. And the assertions still have teeth: with the production guard disarmed at its source (`write_guarded`'s user-input refusal forced off), both tests fail on the byte-equality assertion — `pane_input_032` reporting the replacement payload appended twice, `idle_worker_015` the probe's bare `\r\n\r\n`.

**`scheduler/idle-worker/015` was fixed as prophylaxis, not in response to a reproduced failure, and the distinction is worth keeping.** Its two 75 ms sleeps **passed 3 of 3** at 0 ms on an idle box, so they were not load-bearing there. The residual risk is #850's interleave under contention, and that has not been reproduced for this test. It is the same shape against the same target and the fix is the same two calls, so it was taken — but nothing here demonstrates it was failing.

Test-only. No production code changed, so no TUI↔daemon contract question arises: `PROTOCOL_VERSION` is untouched and no `CONTRACT_BREAKS` entry is owed.
