## The fleet-view watcher-reclaim test stops racing a runtime it cannot drive

`a_watcher_whose_task_has_ended_does_not_hold_the_deck_hostage` (PRD #742 M14) failed intermittently on `build-windows` and passed on rerun. The cause is in the test, not the product: it releases a spawned task and then waits for the claim to become reclaimable with `for _ in 0..1_000 { tokio::task::yield_now().await }`.

That loop cannot make the thing it waits for happen. `tauri::async_runtime::spawn` does not use the runtime `#[tokio::test]` built — with no `async_runtime::set` in the binary it lands on tauri's global `default_runtime()`, a multi-threaded tokio runtime with its own OS threads — so the release has to cross a runtime boundary before `is_finished` flips. `yield_now` reschedules only the test's own task and hands that other runtime's worker nothing.

So the iteration count was a wall-clock budget in disguise, and a very small one. Measured on an idle 16-core Linux box, the loop resolved in **1–11 iterations and 17–41 µs**, putting its real budget at roughly **4 ms**. Under 4x CPU oversubscription it needed 46–174 iterations and **exhausted all 1000 once in ten runs** — the Windows failure, reproduced on Linux. Windows loses the race far more readily: its scheduling quantum alone is ~15.6 ms, four times the budget the loop actually had.

It now waits on a `tokio::time::timeout` of 5 s, polling every 5 ms with a sleep that genuinely parks the thread so the other runtime's worker can be scheduled. At **20x** oversubscription the reclaim takes 10.6–110.7 ms against that 5 s budget, a 45–470x margin — and the fastest of those is already larger than the whole budget the old loop had. No product code changed; the property under test is unchanged.
