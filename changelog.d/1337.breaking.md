## The "respawn failed" report is now a turn the orchestrator answers, and no longer names the role (`PROTOCOL_VERSION` unchanged)

When a `clear = true` delegate's respawn cannot start a replacement worker at all — typically because the role's command cannot be started — the daemon tells the orchestrator. Until now that report was `⚠ respawn failed for role '<role>' on pane <pane> (see daemon log for details)`, written into the orchestrator's pane and left there unsubmitted, so nothing happened until a human pressed Enter. In a dispatched unit there is no human, so the orchestrator went on waiting for a `work-done` that could never arrive. It now arrives as a submitted turn, `⚠ delegated worker respawn failed (dot-agent-deck daemon report)`, through the same guarded write-and-submit path the previous breaking release moved its two siblings (`⚠ delegated worker exited without work-done` and `⚠ delegated worker never came up`) onto. Its wording asks the orchestrator to decide: notify the user, reassign the task, or re-delegate it — and says that re-delegating retries the same respawn, which fails the same way while the cause is the role's own configuration.

The report also no longer carries the role name. Role names come from `.dot-agent-deck.toml`, which may belong to a repository you cloned, and text that becomes an agent's input should not carry values a repository controls; the two sibling reports already carried none. The only value in the report is the worker's pane id, which the deck has already restricted to letters, digits, `-` and `_`. The role and the underlying error are still in the daemon log (`~/.local/state/dot-agent-deck/deck.log`), on the `delegate: respawn for clear=true failed` line. If you have scripts or orchestrator instructions that look for `respawn failed for role`, update them to look for `delegated worker respawn failed`.

This is classified as a compatibility break even though nothing on the wire moved — no field added, removed or retyped, no new message, no handler signature change — because what changed is the *meaning* of an existing delivery: text that was inert daemon output is now model input that consumes a turn. Per this project's own rule (`docs/develop/versioning.md`) a semantic break behind a stable wire is versioned as breaking, which is why this drives a minor bump rather than a patch.

**What to expect if you upgrade.** An orchestrator that previously sat idle after a failed respawn will now visibly wake up and act on it. The behaviour changes when the **daemon** starts on the new build, not when the binary on disk is replaced, so if you upgrade while agents are running you keep the old daemon — and with it the old, unsubmitted report — until it next restarts. As with every automatic submission the deck makes, if the orchestrator's pane is holding an unsent draft you typed, the report is appended to that draft and both are submitted together.

See [Idle Workers & Notifications](https://agent-deck.devopstoolkit.ai/docs/idle-workers-and-notifications).
