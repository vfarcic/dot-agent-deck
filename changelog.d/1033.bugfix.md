## Codex hook trust is recorded again on hosts where one stray message used to end the attempt

Before recording trust for its own Codex hooks, the deck asks Codex itself which hooks it would load — a short `codex app-server` conversation in which the deck sends one request numbered `2` and waits for the reply numbered `2`. It matched that reply by its number alone. But Codex numbers *its own* requests from its own counter, so a message Codex sends of its own accord can carry the same number while being something else entirely — and such a message is a request, not a reply, so it carries no answer to read. The deck treated it as the answer anyway, gave up on the whole exchange, and logged `hooks/list reply carried no result` with the real answer still unread.

When that happened there was no trust to record, so Codex declined to run the deck's hooks and the pane fell back to the coarser stdout classification — the same degraded path the new `hooks install --agent codex` message describes. Nothing was damaged and no config was written; the events were simply less precise than they should have been, and on an affected host it happened on every Codex launch.

The deck now accepts only an actual reply — one carrying a result or an error — and skips anything else on the stream instead of giving up, so a message that arrives between the request and its answer costs nothing. The wait is still bounded by the same overall timeout, so a talkative server cannot hold a launch up.
