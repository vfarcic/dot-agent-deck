## Codex scoped hook trust answers the app-server's questions instead of ignoring them

On a machine where Codex is authenticated, `dot-agent-deck` has never once succeeded in recording scoped hook trust for the hooks it installs. Every wrapped Codex spawn warned `could not record scoped hook trust`, and every Codex agent's deck events fell back to the coarse stdout classifier — so a card's status was inferred from terminal output rather than reported by Codex's own hooks, and `user_prompt`, which only the native `UserPromptSubmit` hook ever sets, was always empty.

[#1033](https://github.com/vfarcic/dot-agent-deck/issues/1033) diagnosed the first half of that: the read loop accepted **any** JSON-RPC message whose `id == 2` as the `hooks/list` reply, and a server→client *request* carries an `id` from the server's own independent counter. That half shipped in [#1029](https://github.com/vfarcic/dot-agent-deck/pull/1029) — the matched message must now also *be* a response, and a non-matching one is stepped over instead of ending the attempt.

**It did not fix the symptom, and the operator's log says so precisely.** Counted on 2026-09-16 either side of `59073b60` (merged 2026-09-13T13:26:39Z): `hooks/list reply carried no result` ran at 145–448 a day for eighteen days and went to **zero** the afternoon that commit started running, while `hooks/list did not answer in time` went from ≤8 a day to 155, 269, 261, 200. Same population of spawns, same failure, one message later — 5,129 warnings in total, the last at 05:53 that morning. This is the answer to whether the timeout growth was a second problem or the first one wearing a different coat: it is the first one, and it is not load. Sixteen `codex app-server` processes driven against one home at once all answered in **under 1.2 s**, against a 5 s budget, so the deadline is not tight and has been left alone.

**The missing half is that ignoring a request is not the same as answering it.** JSON-RPC gives a server no way to learn that a reply is never coming, so a request the deck steps over stays *outstanding*, and a server that waits on it before doing further work never gets to `hooks/list` either. Stepping over the message therefore moved the failure from the stray message to the deadline — exactly the shift the log recorded — without removing it. The deck now replies to every server→client request with `-32601`, which is the literal truth (this client implements no server-initiated method; it sends two requests and reads their replies) and which releases a server waiting on one. Notifications carry no `id` and are still answered by nothing, per the spec. Measured against codex-cli 0.149.0 that an app-server takes such a line on stdin without complaint and still answers `initialize` and `hooks/list` normally, so the reply cannot cost the case that already works.

**The remaining cause is still not directly measured, and the second change here is what fixes that rather than another guess.** The stray message could not be reproduced in a fixture: an empty home, a ChatGPT-authenticated home, a home carrying the deck's ten hooks, an untrusted `cwd`, and sixteen concurrent app-servers on one home all answered `hooks/list` in 0.14–1.2 s having sent no request at all. What the log could never say is *which* message arrived, because `reply carried no result` named the shape and never the `method` or the `id` — which is why the issue had to be filed with its cause labelled a hypothesis, and why thousands of occurrences bought no more information than one. A failure now names what arrived instead of the reply (`skipped 3 message(s): request account/chatgptAuthTokens/refresh id=2; …`), counting every skip while naming at most the first eight so a flooding peer cannot grow the line.

Success is now `info!` rather than `debug!` for the same reason. The failure beside it is `warn!`, and that asymmetry cost a diagnosis: #1033 had to concede that "zero successes cannot be proven from the log alone" about a box carrying thousands of those warnings, because the one thing that would have refuted it was logged below the level anyone runs.

**What the real-agent test establishes, and what it does not.** `codex_hooks_001_real_interactive_turn_reaches_idle_without_exit` passes on this branch in 15.9 s under `DOT_AGENT_DECK_REQUIRE_REAL_E2E=1`, so it is a run and not the silent skip #1033 warns about, and its central assertion is a `Thinking` event whose `user_prompt` matches byte for byte — a field only Codex's native `UserPromptSubmit` hook ever sets. A real Codex's hooks do reach the deck here. It is a no-regression check rather than a confirmation of the production fix, and the issue's suggestion that "green confirms it" does not hold: the test's sandbox is a *fresh* credential-imported home, which is the condition that already answered `hooks/list` promptly in every fixture above, so the stray message it would need is one this test has no way to produce. Whether the same test also passed before this change is **unmeasured** — the control run was killed twice by the box, once for memory at a load average of 64 and once by a full disk — and the fixture evidence suggests it did, since `decline_server_request` fires only on a server→client request and no such request arrived in any of the five fixtures. The issue's own "still red on main" table does not settle it either: all three of its rows were measured on 2026-09-11, two days before the first half landed, and `is_hooks_list_response` exists at none of those commits. What will settle it is the diagnostic, on the operator's next day of logs.

Neither sibling issue falls out of this. [#1034](https://github.com/vfarcic/dot-agent-deck/issues/1034) (install shifts user rule indices) and [#1027](https://github.com/vfarcic/dot-agent-deck/issues/1027) (orphan records, unconditional re-enable, the `isManaged` default) both live in the install and trust-write paths; this change is confined to the JSON-RPC read loop that talks to `codex app-server`, and touches neither.

Nothing here crosses the TUI↔daemon protocol. The exchange is between the wrapper and a `codex app-server` child over a private pipe, and no daemon message, handler or field changes shape or meaning — `PROTOCOL_VERSION` stays at 9 and CLAUDE.md rule 12's cross-version check does not apply. What does change for a user is delivery: where trust now succeeds, Codex runs the deck's hooks and the deck's events come from Codex rather than from reading its terminal output.
