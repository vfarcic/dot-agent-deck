## A role you insert mid-config and then `pane spawn` lands where the config puts it, instead of at the end

Adding a role to an orchestration you already have open is a two-step move: edit `.dot-agent-deck.toml`, then run `dot-agent-deck pane spawn <role>` so it comes up without restarting the deck. Until now the second step only ever **appended**, wherever you had put the role in the first step. Edit `roles = [orchestrator, coder]` into `[orchestrator, reviewer, coder]`, spawn `reviewer`, and the live tab — and the session snapshot written from it — came out ordered `[orchestrator, coder, reviewer]`.

That is not only cosmetic. `resolve_orchestration_for_restore` compares the saved role sequence against the config element by element, so a snapshot in the wrong order is rejected exactly like one missing a role: the next restore reports drift, falls back to rebuilding the orchestration as a **plain pane**, and the orchestration tab is gone. The role indices the daemon stamps on `TabMembership` come from the *current* config, so they disagreed with the tab's own order at the same time.

The growth path now places the role instead of appending it. It takes the current config's role list and inserts before the first role that list puts **after** the new one, shifting `role_pane_ids`, `role_statuses` and the tab's `config.roles` together so they stay parallel; `start_role_index` moves with them, so `role_pane_ids[start_role_index]` still names the orchestrator's pane — the key the session snapshot hangs off and the pane the orchestrator prompt is delivered to. The snapshot is then **rebuilt** from the tab rather than pushed onto, which is what makes the persisted order match what you see.

**What it does not reconcile, deliberately.** Only a role being *added* is repaired. A role **removed** from the config, two roles **reordered**, or a role **renamed** are not: none is expressible as a `pane spawn` of one role, and each would mean deleting or moving slots whose panes are live agents — a bigger promise than this verb makes. Where such a drift leaves the tab unable to express the current config at all, placement degrades to the old append and restore falls back to a plain pane exactly as it does today. Two narrower degradations are the same by construction: a role the current config does not list at all appends, and existing slots are never moved.

`PROTOCOL_VERSION` is untouched, and CLAUDE.md rule 12's cross-version check does not apply. Nothing on the TUI↔daemon wire moved and no field changed meaning: `OrchestrationSurface` already carried the role's `role_index` resolved against the current config, and this is the TUI finally *honouring* it in its own tab bookkeeping rather than the daemon saying something new. The one persisted shape that changes — `[panes.orchestration]`'s `roles` order — is written and read by the same TUI, and an old TUI reading a new snapshot sees a role list in config order, which is the order its own drift guard wants.
