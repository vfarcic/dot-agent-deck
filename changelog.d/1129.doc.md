## The deck's trust boundary is written down: the OS user

Multiple agents in one deck run as one operating-system user, and nothing below that separates them — one process can read another's environment, and with it the per-spawn capability token that authorises hook-socket messages. That was known and measured; what was missing was a decision about it.

The decision is recorded, with its reasoning: **the deck's trust boundary is the OS user.** Every agent the deck runs is inside it and is trusted with respect to every other agent the deck runs. The operating rule that falls out of it: do not put an agent you would not trust with your whole working environment into a deck alongside agents you do.

The write-up covers what was rejected and why — a uid per agent (the only thing that would genuinely close it, and an entry price that turns a single-user developer tool into a multi-tenant agent runner: a privileged component, per-uid credentials, per-uid file ownership), and an LSM or sandbox profile (per-platform, owned by each agent rather than by the deck, and it closes one route to the token rather than separating the agents). It also states the trigger for revisiting: the deck running an agent on someone *else's* behalf, which is a product change rather than a security insight.

None of this makes the capability token pointless, and the page says why: it removes the *published* escalation — pane ids are advertised, tokens are not — and it binds every message to one spawn, which is what catches the accidental forgeries that actually happen.
