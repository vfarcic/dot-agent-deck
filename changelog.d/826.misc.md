## The desktop deck's global key handler no longer depends on the keydown target being an element

Nothing changes for anyone driving the app with a keyboard: a browser dispatches keyboard events at an element, so this was not reachable through the UI. It was reachable from a test, where it read as a broken app rather than as the optimistic cast it was.

`App.tsx`'s window-level `keydown` handler asserted `event.target as HTMLElement | null` and called `matches` on it **eagerly**, ahead of the ⌘K and Escape branches that never need the answer. `EventTarget` carries no `matches`, so the assertion left TypeScript with nothing to check, and a keydown dispatched at `window` threw `target?.matches is not a function` before Escape was reached — so no overlay closed. All four `fireEvent.keyDown` call sites that existed happened to target `document.body`, which is an element, which is why nothing caught it; `fireEvent.keyDown(window, …)` is the natural way to drive a document-level handler, and the next person to write one would have paid for it.

The question is now asked where it is used, below both early-returning branches, and the target is narrowed with `instanceof Element` rather than asserted — so the compiler checks this call and whatever is added beside it. A test dispatches Escape at `window` and asserts the settings overlay closes, pinning the guarantee rather than leaving it to be restored and forgotten. Two test files that had routed around the throw and described it in the present tense ([`useZoom.test.ts`](https://github.com/vfarcic/dot-agent-deck/blob/main/desktop/src/hooks/useZoom.test.ts), [`zoom.test.ts`](https://github.com/vfarcic/dot-agent-deck/blob/main/desktop/src/lib/zoom.test.ts)) say so in the past tense now; both kept their structure, which stands on its own reasons.
