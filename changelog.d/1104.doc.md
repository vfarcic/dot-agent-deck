## macOS as a remote host: the requirements page now says what actually ships

`docs/remote-requirements.md` told users that "Linux is the only supported host for a remote environment. macOS and Windows are not supported as remote hosts." The macOS half of that has been false since PRD #76: `remote add` runs `uname -s -m`, maps `Darwin x86_64` to the published `darwin-amd64` release asset and `Darwin arm64` to `darwin-arm64`, and applies no OS gate at all. The release workflow builds and uploads both, and the error text users see on an unsupported arch has been advertising them the whole time — `supported: linux-{amd64,arm64}, darwin-{amd64,arm64}`. So a Mac owner who read the requirements page and believed it was steered away from a path the installer would have accepted.

**The docs were corrected rather than the code, and macOS is now documented as what it is: installs, not validated end to end.** Promoting it to "Supported" would have been the same defect pointed the other way — an absolute about an implementation, asserted on the strength of reading the platform-detection function rather than running the thing. Nobody has installed onto a Mac over ssh, started a daemon there, spawned an agent under it and attached from a second machine, so the page does not claim anyone has.

A new **macOS as a remote host** section separates what is verifiable from what needs a Mac. Verified: there is no OS gate, the `darwin-*` assets exist, and the machinery the remote flow uses is written for Unix rather than Linux specifically — the daemon detaches with `setsid(2)`, `hooks install` has one Unix implementation, and the daemon's peer-credential check carries a macOS branch of its own. Since macOS is already a supported platform for the deck locally and `daemon serve` is a subcommand of that same binary, what is untested is the *arrangement* — install over ssh, run headless, attach from elsewhere — not whether the daemon runs on macOS at all.

Then the four places a Mac differs from the Ubuntu host the rest of the page was written against, each stated as a thing to check rather than a known failure: **no `systemd --user`**, so the daemon survives the ssh session via `setsid(2)` but nothing restarts it after a reboot and the deck ships no launchd unit; **no `XDG_RUNTIME_DIR` by default** — the variable is honoured on every Unix target, so a Mac that exports one behaves like a Linux host, but left unset the socket lands on the `/tmp/dot-agent-deck-{uid}.sock` fallback the same page flags as unsafe on multi-user hosts, making `$DOT_AGENT_DECK_SOCKET` more important there than on Linux; **the login Keychain**, where Claude Code 2.x keeps credentials instead of `~/.claude/.credentials.json`, and which an unattended Mac that rebooted without a console login leaves locked; and **sleep**, which suspends a Mac's agents where a Linux VM generally does not sleep at all.

The Windows half of the original sentence was accurate and stays, now with the reason attached rather than as a bare assertion: the platform detection has no Windows arm, so registration fails before it reaches an install, and the release publishes no Windows daemon binary for it to install anyway.

The operating-system table is restructured from a one-row distribution list into a three-row host-OS table carrying those three states, and the systemd and socket-path sections each gained a pointer to the macOS section so a reader who lands there mid-page is not left with Linux-only guidance. `docs/remote-environments.md` carried a quieter copy of the same claim in its opening definition ("a per-project Linux host") and is narrowed to match.

Validating the macOS path end to end is tracked in [#1158](https://github.com/vfarcic/dot-agent-deck/issues/1158); it carries the reproduction steps and the four differences as a checklist. If it passes, the hedging comes out and macOS becomes a validated host; if it fails, the result decides between fixing it and gating `add()` on Linux after all.
