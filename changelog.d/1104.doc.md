## macOS is a supported remote host on Apple Silicon, and the requirements page now says so

`docs/remote-requirements.md` told users that "Linux is the only supported host for a remote environment. macOS and Windows are not supported as remote hosts." The macOS half has been false since PRD #76 — `remote add` detects a Mac and installs a published macOS build onto it, with no OS gate anywhere in the path, and the error text you get on a genuinely unsupported machine has been advertising `darwin-{amd64,arm64}` the whole time. So a Mac owner who read that page and believed it was steered away from something the installer would have accepted.

**The docs were corrected rather than the code — and then the path was actually run, so the hedging is gone too.** The whole thing was validated end to end on 2026-09-19 (issue [#1158](https://github.com/vfarcic/dot-agent-deck/issues/1158)): `remote add` over ssh, `connect`, a Claude agent working in a pane, a disconnect, and a reconnect with the session intact, on a Mac Studio running macOS 26.6.2. So the status table now reads **validated end to end**. That was an Apple Silicon Mac, which the page says in a parenthetical; an Intel Mac gets a `darwin-amd64` build nobody has exercised.

A new **macOS as a remote host** section carries the result, and the two differences that turned out to need action rather than watching.

**Claude Code needs one `/login`, once, in the pane.** It keeps credentials in the login Keychain on macOS, and an ssh session genuinely cannot read them — ssh authenticates by key, so the login password is never presented to unlock the Keychain and there is no graphical context in which to prompt. The first run prints `Not logged in · Please run /login`, and that message is the fix: running it writes `~/.claude/.credentials.json`, which later sessions authenticate from. This is Claude Code's behaviour rather than a macOS-wide problem — `codex` and `opencode` keep credentials in files already and need no equivalent step. `ANTHROPIC_API_KEY` also works but bills as API usage instead of against a subscription, so it is documented as the fallback rather than the recommendation.

**A Mac has to be told not to sleep**, with `sudo pmset -a sleep 0` as the load-bearing setting — display sleep is harmless, system sleep suspends the agents. The page now notes that this is the *opposite* direction from "Surviving sleep/wake", which covers your own machine sleeping and is already handled by ssh keepalive and auto-reconnect; a sleeping host has no deck-side mechanism at all. `remote-environments.md` gained the matching sentence so a reader of that section is not left thinking it covers both.

Two further differences are recorded as measured rather than suspected. The socket does land on `/tmp/dot-agent-deck-{uid}.sock`, and the owner-only mode the page promises **holds** there (`srw-------`), so what remains is the directory concern rather than the socket file. And nothing restarts the deck after a reboot, since macOS has no `systemd --user` and the deck ships no launchd equivalent — agents do survive a disconnect, which the run confirmed, but reboot behaviour was not tested and is not claimed either way. Shipping a LaunchAgent is tracked in [#1172](https://github.com/vfarcic/dot-agent-deck/issues/1172).

The Windows half of the original sentence was accurate and stays, now with its reason attached rather than as a bare assertion. The operating-system table becomes a three-row host-OS table carrying those three states, and the persistence and socket-path sections each point at the macOS section so a reader landing mid-page is not left with Linux-only guidance. `docs/remote-environments.md` carried a quieter copy of the same claim in its opening definition ("a per-project Linux host") and is narrowed to match.

**Both pages also had their register corrected in the same pass.** Documentation should tell you how to *use* the deck, and reach for internals only where knowing one changes what you do. These two pages had drifted: `connect` was described as "an `ssh -t` wrapper" that "forwards keystrokes in and renders the bytes that come back"; quitting "exits without sending a detach frame" so "the daemon observes EOF on its socket"; the sleep/wake section explained that "the sleeping endpoint never sends a FIN/RST" and named two `ServerAlive*` ssh options that are not configurable anyway; the socket was documented down to `bind(2)` running "with a narrowed umask of `0o177`"; and an environment variable no user ever sets appeared in the quick start. Around thirty passages across the two pages now state the behaviour and its consequence instead — `connect` opens an ssh session, so your usual ssh config and keys apply; a connection killed by sleep is torn down within roughly 45 seconds of waking; the socket is always created owner-only and your umask cannot weaken it. What stays is what you can act on: paths, environment variables, commands, exit codes, and the timings you actually wait through.

**The provider a host happens to run on is no longer presented as if it mattered.** `remote-recipes.md` named UpCloud as "the reference host" and both pages recorded validation as having happened on "a fresh Ubuntu 24.04 LTS UpCloud VM" — provenance about one test rig, stated where a reader could do nothing with it, and implying a dependency that does not exist. The deck never learns what it is running on: `remote add` behaves identically on any host once SSH and a non-root user with the agent toolchain are in place, which the recipes page already said in passing ("the deck-side flow is identical") while its own headings said otherwise. Validation is now recorded against **Ubuntu 24.04 LTS**, with the Status note saying outright that the provider does not matter and that the recipes differ only in how you get a machine. The UpCloud recipe is gone — it was a vendor CLI invocation followed by "bootstrap the same way as the Hetzner recipe", and its one genuine note (cloud-init defaults to `root`) is already covered under *What to watch for*. Multipass, one worked cloud example, and bare metal remain.

Three things are named as still open rather than glossed: reboot behaviour, the `$DOT_AGENT_DECK_SOCKET` override on macOS, and hook delivery asserted directly rather than inferred from an agent reaching `Working`.
