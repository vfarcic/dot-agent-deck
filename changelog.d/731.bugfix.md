## A backup of a config the deck cannot parse is no longer written through a symlink

When the deck goes to install its hooks and finds an agent's config file already unparseable, it refuses to touch it and copies the bytes aside first — `~/.claude/settings.json.bak`, `~/.codex/hooks.json.bak`, `~/.config/devin/config.json.bak` — so a stray comma cannot cost you a config the deck then rewrites from scratch. That copy was a plain write to a fixed, entirely predictable name, and a plain write follows a symlink. On a machine where somebody else can add an entry to that config directory — a shared or group-writable home, not a private single-user one — the name could be claimed ahead of time and pointed at another file, and the deck would then truncate that file and fill it with the config's contents. Only the copy was affected; the config file itself was left alone, which is the whole point of that path.

The copy now goes out the same way every other config write already does: written to a fresh scratch file the deck creates exclusively, then moved into place. A rename does not follow a symlink either — it replaces the link — so a claimed name is overwritten rather than obeyed, and the bytes still land where the error message says they did. This is the last of the four writes named in the report; the other three were fixed in v0.39.0.

Two smaller things come with it. A fresh backup is now created owner-readable only, instead of taking whatever the umask allowed — it is a byte-for-byte copy of a config that may hold an org id or an auth reference, so it should not be readable by accounts the original was not. And the error the deck reports now names the backup only when there is one: it used to print the path unconditionally, including in the rare case where writing the copy had failed.
