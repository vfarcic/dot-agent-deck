## The deck checks Claude Code's input box before it types its doorbell, on Linux

When you had typed anything into a Claude Code agent's input box, the deck could no longer tell whether the box was empty, so it stopped typing its doorbell into that agent until it restarted. Now, for Claude Code running on Linux and started directly in its pane (its command starts with `claude`), the deck checks the box first and rings once a check finds it empty, so you can clear the box any way you like. While it checks, Claude Code's input box disappears for a moment and comes back with what it held. What you type meanwhile reaches Claude Code in order; `Enter`, `Backspace`, `Ctrl+C` and the other keys the terminal acts on, and anything typed after one of them, wait until Claude Code is back from the check, which takes a moment on a quiet machine and longer on a busy one.

To check the box, the deck sets that Claude Code's `VISUAL` and `EDITOR` to a small helper of its own, which still opens your own editor when you press `Ctrl+G`. Claude Code's Bash tool, including background commands and subagents, still sees your own `VISUAL` and `EDITOR`. Claude Code started through a launcher script gets neither, and neither does a Claude Code whose doorbell you turned off (`doorbell.claude = false`).

What to know:

- A single `Ctrl+C` during a check does what it always does once the check ends, unless the check opens your editor (next item): it clears a non-empty box, and on an empty one Claude Code asks you to press it again. Two presses during one check reach Claude Code back to back, as two quick presses would.
- Rarely, for example on a very busy machine, a check opens your own editor, as `Ctrl+G` would. A `Ctrl+C`, `Ctrl+Z` or `Ctrl+\` typed during that check or while the editor it opened is open isn't sent, nor is what you had typed after it by then, and both clients say `Input not delivered: your Ctrl+C, Ctrl+Z or Ctrl+\ and what you typed after it, while the deck's check had your editor open; type it again once the editor has closed`. An editor that runs in the pane, such as vim, also gets the keys you typed during the check before it opened.
- If Claude Code doesn't come back from a check, the keys that wait for it wait until you restart the agent, and the card says `input held: the agent hasn't come back from the deck's check; …`: close the pane or restart the agent, then type them again. Keys the deck still holds when the agent exits or restarts are dropped, not typed.
- Once you open your own editor with `Ctrl+G` in a Claude Code pane, the deck stops checking that pane's input box until the agent restarts; its waiting messages then reach it at your next prompt, and its card says `the deck can't check this agent's input box. Check its pane.`
- If your shell's start-up file (zsh's `~/.zshenv`, fish's `config.fish`) sets `VISUAL`, or unsets `VISUAL` and sets `EDITOR`, a Claude Code whose pane command has arguments gets that editor instead of the deck's helper. The same goes for a `VISUAL` or `EDITOR` in the `env` of Claude Code's settings files (`~/.claude/settings.json`, `~/.claude.json`, the project's `.claude/settings.json` and `.claude/settings.local.json`, the managed settings in `/etc/claude-code`, settings your organisation's server sends), which the deck reads; one of those files it can't read, and `--settings` on Claude Code's command line, count too. Once anything is typed into such an agent's box, the deck doesn't check it and types nothing more into it until the agent restarts; the card says `the deck can't check this agent's input box. Check its pane.` Set `VISUAL` and `EDITOR` where only an interactive shell reads them (zsh's `~/.zshrc`), not in Claude Code's settings files.
- A prompt recalled with the Up arrow can't be checked; the card says the same, and clearing the box lets the next check go ahead.
- If you change `~/.claude/keybindings.json` while the agent runs so that `Ctrl+G` does something else, a check sent in the next few seconds can run that action once in Claude Code. The deck then stops checking that agent's box until it restarts. Restart Claude Code from the deck after changing its key bindings.
- The deck reads the box in Claude Code's `dark`, `light`, `dark-ansi`, `light-ansi` and `dark-daltonized` themes; with another theme it may not recognise the box, and then checks and types nothing.
- If you set `TMPDIR` for Claude Code to a directory that other users could change (for example one created group-writable under a `umask 0002`), the deck reads the box as not empty and its card keeps saying `there may be an unsent draft. Send it or clear it.`; remove that write access with `chmod go-w`, or leave `TMPDIR` unset.
- The deck keeps that helper under its state directory (`~/.local/state/dot-agent-deck` by default) or, failing that, under `$XDG_RUNTIME_DIR`, and only where no other user can change the directories on the way. If `~/.local` is group-writable (common under a `umask 0002`) and `XDG_RUNTIME_DIR` isn't set, no Claude Code is checked: run `chmod go-w ~/.local ~/.local/state` and restart the deck's daemon.
- macOS isn't covered yet: there, once you type into the agent's pane, its messages wait until it restarts, as before. Codex gets the same check on Linux (see the Codex entry).

The TUI and the desktop app show the same card words. See [Orchestration → How the deck checks Claude Code's input box](https://agent-deck.devopstoolkit.ai/docs/orchestration.md#how-the-deck-checks-claude-codes-input-box).
