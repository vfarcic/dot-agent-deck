## The desktop app is now tested in a browser that actually lays it out

Until now every automated check of the desktop app ran under jsdom, which is a DOM implementation rather than a browser: it runs no layout engine, computes no geometry and paints nothing. That is a real ceiling, not a technicality — the ~296 existing tests can say what React put in the tree, and nothing about what you see. Two of the overview's contracts had been shipped as unverified because of it, and one test's comment had to be corrected after an audit found it claiming a height check jsdom cannot make.

There is now a browser tier. It builds the production bundle — the same `pnpm build` output that ships — serves it, and drives it in two engines: Chromium, and **WebKit**. The second one matters more than the count suggests. The app runs on WebKit in the wild (WebKitGTK under Tauri on Linux, WKWebView on macOS), and until now nothing automated had ever loaded it in a WebKit engine at all. Two behaviours that Chromium cannot answer for WebKit — `color-scheme: light dark` on `<meta>`, and `theme-color` with a `media` attribute — are now asserted on every pull request instead of being carried by a manual walkthrough alone.

The first assertions are the ones jsdom structurally could not reach. The agent overview's table really does overflow when you tick every column at a narrow window, and it scrolls **as one region**: every group card resolves the shared grid to identical track widths, each cell sits inside its own track, and scrolling moves every card and the column legend by the same amount — a card drifting out of step is exactly the failure that layout exists to prevent, and it only becomes possible once the table is wide enough to scroll. Rows stay the same height whether an agent's last prompt is long or absent, including when the longest string the app can ever render is put in one. And nothing on the deck or the overview pushes the page sideways at either of two stated window widths, which `overflow-x: hidden` would otherwise hide by clipping it.

The tier runs on every pull request as its own CI job, `desktop-browser`, and it is **advisory** — no browser suite has ever run on a GitHub runner for this repository, so its behaviour there is unmeasured, and blocking every merge on an unmeasured job is how a new gate gets disabled instead of fixed. Locally it is `pnpm test:browser` from `desktop/`, after a one-time browser install.

What it does not do: it does not drive the real Tauri window. There is no `tauri-driver` and no WebDriver session here, so real IPC, terminals over a real PTY, and the WebKit builds your own machine ships remain covered by the manual smoke check in `docs/develop/desktop-gui.md` and by nothing else. Playwright's WebKit is a WebKit, not *the* WebKit you will run. That document enumerates the rest of the gap rather than summarising it.
