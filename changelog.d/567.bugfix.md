## `linkage-check`'s worktree-drift remedy now names a command that can actually clear a locked entry

`cargo xtask linkage-check`'s repository-state preflight reports worktree-registry drift — an entry whose path is gone from disk but still registered — and used to end every such message with ``Run `git worktree prune` ``. For an entry that was `git worktree lock`-ed before its directory was removed, that command cannot clear the failure: git prunes no locked entry at any version, so it exits 0, prints nothing, leaves the registry exactly as it was, and the identical failure comes back on the next run. A contributor who followed the message verbatim had no path forward. Measured on git 2.34.1 and 2.55.0.

The drift itself was always a true positive — git emits no `prunable` attribute for a locked entry, so it falls through to the filesystem check and is correctly reported. Only the remedy was unactionable, which is the failure shape the preflight exists to prevent (a command that appears to succeed while the real state is untouched) reproduced inside the fix for it.

The remedy is now picked per entry. An unlocked entry's message is unchanged. A locked one names ``git worktree unlock <path> && git worktree prune``, with one `unlock` per locked path in front of the single prune that then clears them all, and a short clause saying why the obvious command is not the one named. git already reports the lock on the `locked` line of `git worktree list --porcelain`; the parser saw it and discarded it, and now keeps it.
