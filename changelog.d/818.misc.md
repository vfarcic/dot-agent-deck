## Two lane-1 e2e flakes that turned `e2e-deterministic` red on unrelated branches

`e2e-deterministic` was failing on branches that could not have caused it — including a `renovate/github-actions` run whose diff contains no Rust at all. Two tests were responsible, and they needed different fixes despite arriving together.

`orchestration/work-done/004` asserted four needles against the rendered orchestration surface, but only the FIRST of them waited; the other three were instantaneous `pane_contains` checks. The daemon composes its unsolicited-completion label as one message and the TUI renders whatever of it has arrived, so a grid sampled the moment the first needle appears can legitimately be mid-message. On a contended runner the test failed on the report-frame assertion having *passed* the two before it — a partial render, not a missing report. Each positive needle is now a bounded wait, which asserts the same thing without pinning *when* inside the message's own render. The negative assertion (the summary-file pointer must NOT appear) stays instantaneous deliberately, and is strictly more reliable there than before, because it now runs after every positive needle has settled.

`orchestration/remit/*` needed a scheduling fix, and the route to it is worth recording because the obvious answer was tried first and **measurably did nothing**. The file's two positive bounds were made `common::load_scaled` (issue #709) rather than a fixed 30s — and `orchestration_remit_001` failed anyway, with its own assertion message printing `within 30s`, i.e. a scale factor of exactly 1.0. `load_scaled` is `clamp(load1 / nproc, 1.0, 6.0)`, and a 4-vCPU GitHub runner running 4 test threads sits at `load1 / nproc` ≈ 1.0, so it cannot widen anything precisely where widening was needed. The scaling is kept, because it is correct on a contended *developer* box — which is what #709 measured, and what a dispatch agent actually runs on — but it is not what makes CI green, and the code comments now say so.

What makes CI green is `threads-required`, and `.config/nextest.toml`'s own measurement table had already said so. Row 3 of that table reads `30s serial (-j 1) → 7 PASS, each 2-5s` — and `-j 1` means *nothing else was running*. The existing `max-threads = 1` group reproduced that on a 16-core dev box, where it still leaves 15 threads for a tier that mostly is not competing for what these decks and daemons need; on a 4-vCPU runner it reproduces nothing, because it serialises the group against **itself only** while 2589 other tests keep contending. The condition the table proves sufficient had therefore never actually been established in CI. The group now reserves the whole pool, the same mechanism `scheduler/dispatch/015` already uses, with `priority` so it is scheduled early rather than draining a tail that holds 250-320s tests — so the reservation costs about its own 19-21s.

**None of this is a fix for [#818](https://github.com/vfarcic/dot-agent-deck/issues/818), and that issue stays open.** Why concurrent decks interfere at all — both failures landing on the same daemon `ListAgents`/live-status join, for `pane 1 (agent_id 1)`, identifiers every test in the file reuses — is untouched. This is containment made to hold in the place it was always meant to hold. Delete it when the isolation bug is found, not before.

Verified locally: both files in full, 31 tests passing, 19.0s before the scheduling change and 21.3s after; `cargo test-fast` 2401 passing; fmt and clippy green.
