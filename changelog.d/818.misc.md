## `e2e-deterministic` is green again after #789 turned it red on every branch

Lane 1 of the e2e tier (`e2e-deterministic`, added in #800) had been failing on **every** open PR and on **`main` itself** since 2026-09-01T23:27Z, so every contributor was reading a red CI job caused by somebody else's change. The bisect is unusually clean: the job was green five consecutive times, then failed on the `main` push run **five seconds** after `d47bc75` (#789) merged, and on every branch afterwards.

Worth stating because CLAUDE.md rule 8 invites the opposite reading — it records that lane 1 "has no honest runs" and that its stability on a GitHub runner was unknown, which makes any early failure look inherent. It was not: by the time #789 landed, lane 1 had five honest green runs behind it.

The fix has **two halves, and neither works without the other** — which is why this entry is longer than a timeout bump warrants. Both waits are correct, Decision 21-compliant `common::wait_until` / `wait_for_file_substr_count` polls; they were bounded at 10s, merely restating the harness-wide `WAIT_TIMEOUT` default. Both are now named 30s constants, `STATE_APPLIED_TIMEOUT` and `DELIVERY_TIMEOUT`, documented with why they differ from that default. On its own that changes nothing. The seven tests in the file are also not safe to run concurrently *with each other*, so `.config/nextest.toml` gains a `max-threads = 1` test group scoped to them by a regex on the Decision 17 function prefix.

Measured four ways, because each half looks like the wrong fix when tested without the other:

| bounds | concurrency | result |
| --- | --- | --- |
| 10s | default parallelism | 2 fail — `remit_001`, `remit_007` |
| 30s | default parallelism | 2 fail — same two |
| 30s | serial (`-j 1`) | 7 pass, each 2–5s |
| 10s | serial (the new group) | 1 fail — `remit_001` alone, needing >10s |
| 30s | + the new group | **7 pass, 18.7s** |

Rows 2 and 4 are the pair worth keeping. Row 2 says raising the bound does not help under parallelism, which reads as "the bound is irrelevant" — and row 4 refutes it: serialised, with nothing competing, `remit_001` still blew past 10s and took 13.5s. So the bound is necessary but not sufficient, and removing either half puts lane 1 straight back to red.

This is **containment, not a cure.** It does not explain why concurrent decks interfere; both failures land on the same wait — the daemon's `ListAgents`/live-status join never reporting the injected `Compacting` for `pane 1 (agent_id 1)`, identifiers every test in the file reuses. #818 stays open for the isolation bug, and the test group carries a comment saying to delete it once that is found rather than before. The group serialises against itself only, so the tier's wall clock is unchanged — it is set by one ~260s test, not by these seven.

Two other failures seen in the same window — `manager_016_wheel_over_dialog_does_not_scroll_side_pane` and `form_006_edit_repick_different_dir_wins_in_seed` — are **not** addressed here and are not #789's. Both are older tests that passed in all five green runs, and `manager_016` passed in the `main` run while failing on the Renovate PR, so they are genuinely intermittent under parallel load — the contention recorded in #415, #351, #322 and #701. They stay open on #818.
