## The `e2e-deterministic` CI lane is green again — and now for the right reason

Lane 1 (`cargo test-e2e`, added by #800 for PRD #502) had been failing on `main` and therefore on every open pull request since the merge of #789, so every PR carried a red job unrelated to its own change. Five consecutive honest green runs preceded that merge, and the four failures reported across #818 and #832 — `orchestration_remit_001`, `_003`, `_004` and `_007` — all landed in the file #789 added, `tests/e2e_orchestration_remit.rs`.

**A first round of CONTAINMENT shipped before this one** — 30s bounds on the positive waits plus an `orchestration-remit` `max-threads = 1` test group in `.config/nextest.toml` — and its own comment said to keep it until the isolation bug was found. That finding is below, so the bounds are kept and **the test group is now gone**: the seven tests run at full parallelism again, taking about seven seconds together rather than the nineteen they took serialised.

**The cause the containment suspected was not the cause, and that is worth stating because it was the standing lead.** Its comment blamed concurrent decks leaking into one another through the `pane 1` / `agent_id 1` identifiers every test in the file reuses. Those identifiers are per-deck — each deck's hook socket lives in its own per-test temporary directory and its daemon is addressed only through that directory — and the measurement says so directly: on the pre-fix file the exact panic that was attributed to identifier reuse reproduces with **one** deck in existence, running that single test alone under a sixty-four-way CPU load, five rounds red out of eight. There is no second deck in that run to interfere with. Serialising the group helped only because it changed the timing of the ordering bug described next, which is why it looked like an isolation fix.

**The cause is a genuine race in the new tests, not the parallel-run contention it was triaged as.** The approving review on #789 recorded four e2e failures as "all pass in isolation — parallel-run contention, not defects". They do not pass in isolation: on an idle sixteen-core box `orchestration_remit_001` failed **2 of 5** solo runs, with the exact panic CI reports. The fixture's orchestrator script appends each delivered pointer to `orchestrator-prompt.log` and only *then* forks a `python3` that reports the delivery back as a `thinking` event, so the log line every test waits on does not imply that confirmation has happened. Each test's next move is to inject a `Compacting` or a `/clear`-originated `SessionStart` for that same pane — and `AppState::apply_event`'s `EventType::Thinking` arm sets `session.status` unconditionally, so a confirmation still in flight lands second and destroys the status the test is about to poll for. An instrumented poll of the failing runs shows the pane sitting on `Thinking` for the entire ten seconds, the injected status never once sampled. Which side wins is decided by `python3` start-up latency against the test's own `ListAgents` round trip, which is why a runner executing eight thousand tests in parallel loses it far more often than a dev box does.

That also settles the fix. Raising the bounds — the remedy #818 proposed and the containment applied — cannot close it, because the status never comes back: with the bounds widened and the barrier removed, the module still went red on `_001` and `_003` under load. The tests now wait for the confirmation to be *applied* in the daemon's own state before injecting, which leaves the injection as the last word on that pane. `remit_003`'s history-only phase gets the same treatment for the same reason: its marker file proves only that the fixture *wrote* the event to the socket, and the daemon hands each hook connection to its own task, so "sent" carries no ordering guarantee at all.

**A second, separate failure class turned up while verifying the first, and it is fixed here too.** Every count assertion in the file hardcoded "the log must reach two pointer lines" (or must not), which silently assumed the spawn-time delivery had produced exactly one. It produces two whenever the fixture's confirmation misses the deck's 500 ms `unconfirmed_retry_delay(1)`: the deck then writes its one automatic replacement payload, the fixture logs it, and no re-assertion is behind it. So the negative checks redden on a designed retry rather than on the leak they exist to catch, and the positive checks green without a re-assertion having happened — the false-green hazard the file's own doc comment predicted, now measured at eight failures across six module runs under a sixty-four-way CPU load. Each assertion now counts from a settled baseline, so it measures one more line than the spawn-time delivery actually left behind, whatever that delivery cost.

**Two barriers that could pass without proving anything were tightened after review.** A settled baseline taken *after* a re-assertion absorbs everything written during its quiet window, so two rapid re-deliveries would have folded into one baseline and the "delivers exactly once" check would have accepted them — `orchestration_remit_004` now bounds that baseline by what a single delivery can legitimately write and, independently of the line count, stamps a sentinel into `.dot-agent-deck/orchestrator-context.md` that only a second *logical* re-assertion can destroy (a payload retry never rewrites that file). And waiting for a pane to read `Idle` after injecting a `/clear`-shaped `SessionStart` proves nothing when the pane is already idle, which is the resting state of the `cat` worker stub `orchestration_remit_005` injects into — each injection now first drives the pane to a uniquely-named active tool and waits for that, so the tool being cleared is a transition only the injected event can produce.

No production code changed — the defect is entirely in the test fixture's synchronisation, and the feature #789 shipped is unaffected. Verified as a streak rather than a single green run: eighteen consecutive green module runs under sixty-four- and ninety-six-way CPU load (load average up to 212 on sixteen cores), against 2/5 solo failures before the fix, plus two full green lane-1 tier runs of all 9309 tests.

Removing the test group was verified separately, because serialised runs could not answer the question it raises: twenty-two green module rounds at **full parallelism**, twenty of them under sixty-four- and ninety-six-way CPU load with the load average climbing to 229 on sixteen cores, against two of six rounds red on the pre-fix file under the same load. The seven tests were also green in five consecutive full lane-1 runs of all 2653 tests.

**One of those rotating families is fixed here too, because CI failed on it while this was in review.** `work_done_004_unsolicited_completion_is_visibly_labelled_in_the_attached_tui` asserts that the daemon's "unsolicited completion" label reaches the orchestrator's screen. The daemon writes it as one long line and the orchestration surface wraps it over several rows, so its parts become visible in paint order — and the test waited for the **first** of them and then read the grid **once** for three later ones. Instrumented from the instant that wait returned, the last-painted needle was still absent for a further 27.6ms and 37.4ms in two of five runs under a ninety-six-way CPU load, while the earlier ones were already there; a four-vCPU runner inside a full tier starves the render loop harder still, which is exactly what the captured grid showed — the framing painted and cut off immediately before the sentinel. Each positive check now polls, bounded at the same twenty seconds the first one already used, so a label that genuinely never arrives still fails. The negative check behind them is deliberately left as a single read: polling for an absence passes on the first frame that has not painted it yet, most easily on the starved runner this test keeps failing on, and it is sound as one read precisely because the three waits ahead of it have just proved the write finished painting. This was not reproduced as a local red — nought of eight solo runs under the same load — so it rests on that measured window and the CI grid rather than on a local red-to-green.

**What is still intermittent in that lane is not this, and removing the group did not change it.** Those five tier runs produced four different failure sets, none containing a remit test: `dispatch_005_respects_max_per_run` three times, `manager_016_wheel_over_dialog_does_not_scroll_side_pane` once and `idle_worker_008_closed_orchestrator_pane_id_reuse_receives_nothing` once. Two of those runs kept the group in place as a control and `dispatch_005` failed in one of them too, so the varying subset is the co-tenant load contention tracked in #701 and #818's own second problem class rather than anything the group was holding back. Each one passes when rerun alone — `dispatch_005` in 0.31s against the 0.72s it took while failing in the tier, the duration inflation #701 measures as the signal.

`pane_003_empty_dashboard_never_opens_close_confirmation`, also named in #818, is **not** this cause and is deliberately left alone: its single-shot `snapshot_grid()` caught a partially painted frame with the Help overlay up and the tab bar not yet repainted, which is issue #807's class rather than #789's. Two others seen in the same window — `manager_016_wheel_over_dialog_does_not_scroll_side_pane` and `form_006_edit_repick_different_dir_wins_in_seed` — are older tests that passed in all five green runs and stay open on #818 as ordinary parallel-load contention.

**One test outside this file was fixed too, because it is what reddened this branch's own lane.** `manager_010_blank_default_command_falls_back_to_claude` read the grid once for the `[Submit]` button immediately after the wait that proves the form title is painted — the wait and the lookup take two separate snapshots, and the form paints its button row in a second pass, so a single-shot read can land on a frame that is merely incomplete. That is issue #807's class, not #789's, and the same panic message is what #807 diagnosed at a sibling call site in the same file. It now polls through `TuiDeck::wait_for_in_grid`, the helper added for exactly this shape, which additionally dumps the grid if the button genuinely never arrives — `.expect()` dumps nothing, which is why the CI failure carried no evidence. The eleven remaining single-shot lookups in that file, and the rest of #807's sweep, are deliberately left to #807.
