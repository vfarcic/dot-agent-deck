## Two lane-1 e2e flakes that turned `e2e-deterministic` red on unrelated branches

`e2e-deterministic` was failing on branches that could not have caused it — including a `renovate/github-actions` run whose diff contains no Rust at all. Two tests were responsible, and they had different causes despite arriving together.

`orchestration/work-done/004` asserted four needles against the rendered orchestration surface, but only the FIRST of them waited; the other three were instantaneous `pane_contains` checks. The daemon composes its unsolicited-completion label as one message and the TUI renders whatever of it has arrived, so a grid sampled the moment the first needle appears can legitimately be mid-message. On a contended runner the test failed on the report-frame assertion having *passed* the two before it — a partial render, not a missing report. Each positive needle is now a bounded wait, which asserts the same thing without pinning *when* inside the message's own render. The negative assertion (the summary-file pointer must NOT appear) stays instantaneous deliberately, and is strictly more reliable there than it was, because it now runs after every positive needle has settled.

`orchestration/remit/007` failed on `STATE_APPLIED_TIMEOUT`, a fixed 30s ceiling on the daemon applying an injected `Compacting` event. It took 39.7s on the runner against ~2.3s for the same test locally — roughly 17x — which is the ratio no fixed ceiling absorbs however it is chosen. Both that bound and the sibling `DELIVERY_TIMEOUT` are now bases that `common::load_scaled` widens in proportion to measured machine load, the mechanism issue #709 already added for exactly this. Scaling costs a quiet box nothing: `wait_until` returns the instant its condition holds, so an idle machine still fails at 30s — measured, the two tests run in 0.88s and 2.29s after the change, unchanged from before it. The nextest kill window for the `orchestration-remit` group moves with it, because a 6x-scaled wait can reach 180s, which is precisely the default `3 x 60s` kill; without that the widened wait would be cut off by the runner instead of failing on its own assertion, losing the diagnostic the widening exists to preserve.

**This is not a fix for [#818](https://github.com/vfarcic/dot-agent-deck/issues/818), and that issue stays open.** The underlying question — why concurrent decks interfere at all, when both failures land on the same daemon `ListAgents`/live-status join for identifiers every test in the file reuses — is untouched. The existing `max-threads = 1` containment is still required and still not sufficient on its own; what changed is that its fixed companion bound was being reached, so the bound stopped being a constant somebody has to keep guessing upward. Delete the group when the isolation bug is found, not before.

Verified locally: the two tests alone, then both files in full (31 tests, all passing, 19.0s), then `cargo test-fast` (2401 passing).
