## The `e2e-deterministic` CI lane is green again

Lane 1 (`cargo test-e2e`, added by #800 for PRD #502) had been failing on `main` and therefore on every open pull request since the merge of #789, so every PR carried a red job unrelated to its own change. Five consecutive honest green runs preceded that merge, and the four failures reported across #818 and #832 — `orchestration_remit_001`, `_003`, `_004` and `_007` — all landed in the file #789 added, `tests/e2e_orchestration_remit.rs`.

**It was a genuine race in the new tests, not the parallel-run contention it was triaged as.** The approving review on #789 recorded four e2e failures as "all pass in isolation — parallel-run contention, not defects". They do not pass in isolation: on an idle sixteen-core box `orchestration_remit_001` failed **2 of 5** solo runs, with the exact panic CI reports. The fixture's orchestrator script appends each delivered pointer to `orchestrator-prompt.log` and only *then* forks a `python3` that reports the delivery back as a `thinking` event, so the log line every test waits on does not imply that confirmation has happened. Each test's next move is to inject a `Compacting` or a `/clear`-originated `SessionStart` for that same pane — and `AppState::apply_event`'s `EventType::Thinking` arm sets `session.status` unconditionally, so a confirmation still in flight lands second and destroys the status the test is about to poll for. An instrumented poll of the failing runs shows the pane sitting on `Thinking` for the entire ten seconds, the injected status never once sampled. Which side wins is decided by `python3` start-up latency against the test's own `ListAgents` round trip, which is why a runner executing eight thousand tests in parallel loses it far more often than a dev box does.

That also settles the fix. Raising the two ten-second bounds — the remedy #818 proposed — cannot work, because the status never comes back: with the bounds widened and the barrier removed, the module still went red on `_001` and `_003` under load. The tests now wait for the confirmation to be *applied* in the daemon's own state before injecting, which leaves the injection as the last word on that pane. `remit_003`'s history-only phase gets the same treatment for the same reason: its marker file proves only that the fixture *wrote* the event to the socket, and the daemon hands each hook connection to its own task, so "sent" carries no ordering guarantee at all.

**A second, separate failure class turned up while verifying the first, and it is fixed here too.** Every count assertion in the file hardcoded "the log must reach two pointer lines" (or must not), which silently assumed the spawn-time delivery had produced exactly one. It produces two whenever the fixture's confirmation misses the deck's 500 ms `unconfirmed_retry_delay(1)`: the deck then writes its one automatic replacement payload, the fixture logs it, and no re-assertion is behind it. So the negative checks redden on a designed retry rather than on the leak they exist to catch, and the positive checks green without a re-assertion having happened — the false-green hazard the file's own doc comment predicted, now measured at eight failures across six module runs under a sixty-four-way CPU load. Each assertion now counts from a settled baseline, so it measures one more line than the spawn-time delivery actually left behind, whatever that delivery cost.

No production code changed — the defect is entirely in the test fixture's synchronisation, and the feature #789 shipped is unaffected. Verified as a streak rather than a single green run: fourteen consecutive green module runs under sixty-four- and ninety-six-way CPU load (load average up to 212 on sixteen cores), against 2/5 solo failures before the fix, plus two full green lane-1 tier runs of all 9309 tests.

`pane_003_empty_dashboard_never_opens_close_confirmation`, also named in #818, is **not** this cause and is deliberately left alone: its single-shot `snapshot_grid()` caught a partially painted frame with the Help overlay up and the tab bar not yet repainted, which is issue #807's class rather than #789's.
