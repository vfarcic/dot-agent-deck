## The agent reviewer no longer re-casts the same approval every sweep

The daily PR-review sweep approved an unchanged pull request once per firing — twice a day, indefinitely — because only half of it was idempotent. The review pass skips any head that already has a verdict (`pr_review_select.py`), so no agent ran and no tokens were spent; the vote pass is selected on "has a current verdict" and never asked whether it had already voted on that head, so it cast the approval again. Measured on [#1029](https://github.com/vfarcic/dot-agent-deck/pull/1029): head `1263627a` was approved at 09:14Z and again at 18:59Z on 2026-09-12 with no commit in between, and the 17:00 sweep's own log reads `skip #1029: already has a verdict for 1263627a` immediately above `cast APPROVE for 1263627a`. Three of the four pull requests merged that day carried three approvals each by the same route.

The cost was signal rather than spend. `dismiss_stale_reviews_on_push` dismisses only the *latest* review per reviewer, so duplicates accumulated and the earlier ones stayed frozen reading `APPROVED` while the pull request's own `reviewDecision` was `REVIEW_REQUIRED` — and because the duplicates re-ran the issue [#998](https://github.com/vfarcic/dot-agent-deck/issues/998) attention path, they re-applied `needs-human-eye` and re-posted the full warning body on exactly the sensitive pull requests where a warning most needs to be read once rather than scrolled past.

The vote job now asks whether it has already acted on this exact head SHA, keyed on the review's `commit_id` and on the App's own login. That key is what preserves the two properties the asymmetry was built for and which the obvious fix — selecting on "already reviewed" — would have broken: a push moves the head, so the next head is votable; and a vote that failed transiently left no review at that SHA, so the next sweep still retries it. A review the App cast and a human then dismissed counts as cast, because re-casting it would fight the maintainer who dismissed it. The identity comes from `actions/create-github-app-token`'s `app-slug` output rather than being written out, so renaming the App cannot silently un-key the guard; an empty value fails **open** with a `::warning::` — a duplicate approval is noise, whereas a reviewer that cannot name itself and therefore approves nothing would block every merge it exists to unblock.

The two comment-only outcomes are bounded the same way and for the same reason: an `INSUFFICIENT` verdict is fixed for its SHA, so its notice is posted once. The deny-listed-and-auto-merge-armed notice is suppressed only while auto-merge is **still** armed, which keeps that notice's own instruction honest — it tells the reader to disarm auto-merge and re-run, and disarming drops out of that branch entirely and votes.

The guard is two pure predicates in `pr_review_common.py`, gated by eight new tests in `cargo test-fast` alongside the existing verdict-boundary ones — a runtime property in the same sense, since nothing compiles it and its failure mode is silent.

Review of this change found a second defect and it is fixed here too, because the guard made it load-bearing: every `gh api --paginate --jq` call in the reviewer parsed its output with a single `json.loads`, and `gh` applies the filter to each page and concatenates, so a response spanning pages is several JSON documents and raises `Extra data`. The boundary is **100** — `gh --paginate` appends `per_page=100` unless the caller sets one, measured with `GH_DEBUG=api`, not the 30 that GitHub defaults an unpaginated call to. All five call sites now parse the stream: the two added here, plus `checks_green`, `latest_verdict` and the selector's file list, which were already written that way. The selector's is the one nearest the boundary and the worst placed — [#1035](https://github.com/vfarcic/dot-agent-deck/pull/1035) carries 70 files of 100, and that call raises out of the selection loop, so crossing it would take down the entire sweep rather than one lookup.
