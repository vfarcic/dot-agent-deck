## `dispatch_020`'s user-input fixture no longer uses a fixed sleep as a synchronisation primitive

`dispatch_020_payload_guards_are_scoped_to_one_delivery` hard-red the **required** `build` job on PR #843 — a Renovate no-op whose diff was byte-identical to `main`, so no dependency change could explain it. The panic was at a *precondition*, not the property under test: "the production-shaped bracketed multiline paste must physically reach the PTY". `src/spawn.rs`'s `type_user_bytes` wrote a user draft to a real PTY, flushed, and then slept a fixed 75 ms; nothing waited for the bytes to become observable, so every caller's "must physically reach the PTY" assertion was a bet on a PTY round trip beating that constant. The fast tier sets `retries = 0` and neither `dispatch_020` nor `dispatch_018` is covered by a `.config/nextest.toml` override, so losing that bet once reddens a blocking check.

Reproduced before fixing, because the issue was filed from a code read and one CI log. Under 3x and 4x CPU oversubscription the unmodified test passed 45/45 runs — the race is real but rare, which is why luck was not the route. Shortening the sleep to 0 ms and re-running under 4x oversubscription failed **15/15**, with the dominant panic at `src/spawn.rs:4186` carrying the exact CI message. That pins the causal chain rather than inferring it.

The fix has **three parts.** The sleep is replaced by a content-keyed bounded poll: each maximal printable run of the written bytes — taken from the payload's *text*, with terminal escape sequences stripped — must appear in `registry.snapshot(agent_id)`. `type_user_bytes` now *asserts* rather than silently no-ops when handed a payload it cannot observe that way, and `type_user_frame` covers the bare newline control frames (`Ctrl+J` is `\n`, `Alt+Enter` is `ESC \r`, plain `Enter` is `\r`), which carry no text at all.

The second part is `wait_for_quiescent_lines`, which waits out the byte target's copy of any line the write finished. It is **observed rather than predicted**, and that is what makes it portable: `completed_lines` counts two terminators per completed line, so a pane with nothing in flight always holds an **even** count, and a caller that drained the pane first need only wait for the count to become even again. Unix honours the `\n` inside a bracketed paste and produces two more terminators; Windows' ConPTY consumes the paste markers and produces none; both are simply "even". It is sound only because of the drain below, and only for a write carrying at most one terminator — two would take the count from even straight to even — which both callers assert.

The third part is that the pane must be **drained before** the write, which surfaced only because the first part turned a silent 75 ms bet into a loud 8 s diagnostic. `/bin/cat` and the echo are two independent writers into one PTY output queue and the kernel commits echo in batches, so a pending `cat` copy can land *in the middle* of the write's echo:

```text
"automatic payload before plain Enter\r\n"   <- echo of the earlier line
"user"                                       <- this write's echo, cut off
"automatic payload before plain Enter\r\n"   <- cat's copy, interleaved
" turn completed with plain Enter"           <- the rest of this write
```

The scrollback is append-only, so that split is permanent — no amount of waiting reassembles the draft, and every `windows(draft.len())` search in the file, the tests' own preconditions included, then fails for good. Each `type_user_draft` call site now states how many input lines precede it, and `wait_for_drained_lines` (the existing `wait_for_detached_delivery_attempt` poll, renamed to the vocabulary of a caller counting writes) drains them first, leaving `cat` with nothing to copy until the write terminates a line.

Measured, all at 4x CPU oversubscription on 16 cores: 0 failures in 40 runs with everything in place; **2 failures in 30** with the drain alone disabled and **8 in 30** with the quiescence wait alone disabled, both at the final exact-equality assertion rather than the precondition. So no part is redundant, and the fix is a wait rather than a wider constant — CLAUDE.md rule 5 records for #818 why moving the threshold is not a fix.

**A first version of this fix passed `build` and failed `build-windows` on the same commit**, which is worth recording because it is the same class of error as the bug being fixed — a platform assumption written as if it were universal. That version cut its landmarks from the *raw* payload, so the bracketed paste's landmark was `[200~first line of an unsent draft`: Unix's line discipline knows nothing of the marker and echoes its printable tail literally, while ConPTY **parses** it and echoes nothing, so the landmark could never match on Windows. The callers' own preconditions had only ever looked for the draft text. Windows also honoured no line terminator inside the paste, so the "twice per completed line" arithmetic that version predicted was Unix-specific too — hence the observed even-count rule above. One assumption is left explicitly unverified rather than guessed twice: whether ConPTY echoes a *bare* control frame is not something this change has evidence for, so the frame's echo proof is `#[cfg(unix)]` and Windows keeps the 75 ms sleep it already had, with the quiescence wait additive on top. `scripts/windows-cross-check.sh` type-checks the result for `x86_64-pc-windows-msvc` from Linux with no errors.

Scope is deliberate. `src/spawn.rs` held 29 `sleep` calls, of which **25 were in the test module and 4 are production timers** outside it — so the issue's "29 in the test module" was the file total. This change removes the two on the observed path and leaves the other 23 alone: 12 are correct negative-observation windows that must stay, one is a fixture input rather than a wait, one must land inside a live 500 ms production window and so has no completion to poll for, three are poll intervals inside bounded waits, and **six are the same defect on paths this issue did not reach** — enumerated in the PR for follow-up. The test module now holds 27, the three new ones being poll intervals inside the new waits plus the Windows-only frame sleep. Narrowing `xtask/linkage-check`'s `src/` exemption for the sleep rule is left to the issue, as filed. No shipped behaviour changes — every hunk is inside `#[cfg(test)] mod tests`.
