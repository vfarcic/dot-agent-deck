## The `XDG_RUNTIME_DIR`-less endpoints move into a per-user directory another uid cannot write to

On a host with no `XDG_RUNTIME_DIR` — an ordinary ssh session, a container — the deck fell back to `/tmp/dot-agent-deck-{uid}.sock` and `/tmp/dot-agent-deck-attach-{uid}.sock`. `/tmp` is world-writable and sticky, so a **different** local user could create an entry at either of those exact paths, and once they had, the deck was stuck: `bind(2)` refuses any path that already has an entry, and a sticky directory only lets an entry's own owner unlink it, so neither the daemon nor `daemon_attach`'s stale-inode recovery could clear it. The deck on that host could not use its default endpoint again until the squatter or root removed it.

Both endpoints now live inside `$TMPDIR/dot-agent-deck-{uid}/`, as `hook.sock` and `attach.sock`. The deck creates that directory at mode `0700` through the same helper the ssh-forwarded tunnel sockets already used, which refuses a symlink and fails closed when another uid got there first — there is no entry inside it for an unprivileged stranger to create. It is `std::env::temp_dir()` rather than a hardcoded `/tmp`, so `$TMPDIR` is honoured, and the name does not collide with the tunnel module's own `dot-agent-deck-tunnels-{uid}`.

**What this buys, stated precisely, because it is a large reduction in exposure and not a closed door.** The old design left the socket *path* squattable every time the daemon was not running, because a graceful shutdown unlinks the socket and frees the name. The directory, by contrast, persists across daemon restarts — nothing removes it — so the window shrinks from "any moment no daemon is running" to "before this host's first successful launch, or after a `/tmp` cleaner reaps the directory". Inside that window the directory name is still predictable, and a local user who takes it first now causes a **refusal** rather than a bind failure: the deck will not start until that entry is removed. The refusal says which directory, which uid owns it, which uid you are, and which `DOT_AGENT_DECK_*` override routes around it, and since this release it reaches your terminal rather than only the daemon's log.

**The scope is narrower than the file name suggests.** This is an availability fix. Under `$XDG_RUNTIME_DIR` — mode `0700`, the user's own — no foreign uid could create the entry in the first place, so those paths are byte-identical to what they have always been, deliberately do not move, and a desktop session, where that variable is normally set, sees no change at all. The exposure was bounded by the directory, not by the fallback existing. [#1020](https://github.com/vfarcic/dot-agent-deck/issues/1020) had already closed the *trust* half of the same story by `lstat`ing the endpoint; this is the availability half.

**Every connection the deck opens to a local endpoint now checks who is listening.** Unix client connects read the peer's uid from the kernel (`SO_PEERCRED`, `getpeereid`) and refuse a listener belonging to another user — the same thing the Windows named-pipe transport has always done with the server's owner SID. The endpoint's own owner and mode are still checked first, before any connect is attempted; what the peer credential adds is the case a filename check cannot reach, where the entry is replaced between the check and the connect. Note what mode `0600` does and does not mean: it keeps *other* unprivileged users out, and it has never kept out root or another process running as you.

**The TUI still finds a running older daemon across the upgrade.** When the fallback applies and no daemon answers at the new endpoint, clients also look for one at the old spelling and use it if they find one. That matters because the silent version of this change is the bad one: an older daemon binds the old path, a newer TUI looks only at the new one, the two never meet, and the TUI lazy-spawns a second daemon with the first one's agents stranded under it — and the build-version handshake that exists to catch exactly that skew never fires, because it runs over a connection that is never made. The compatibility read restores the connection, so the handshake fires and you get the prompt you would get from any other version mismatch.

**One thing is not rescued, deliberately.** An agent that *outlives* the pre-#1121 daemon that spawned it carries the old endpoint in its own environment, because that is how an agent is pinned to the daemon that owns it. Once that daemon is gone its late hook events go to a dead address and are dropped silently, where before the replacement daemon re-bound the same address and they arrived as a foreign pane with a warning. Rescuing it would mean either letting a dead explicit endpoint fall through to a different daemon, or having the new daemon bind the old path as well — which is the squattable bind this whole change removes. It affects only an agent orphaned across this one upgrade on a host with no `XDG_RUNTIME_DIR`.

The old path is **read-only**: the deck never binds it and never creates it, and nothing that could unlink it is allowed to see it — resolution now records which rung produced an address, and the stale-inode recovery and lazy-spawn paths refuse anything but the address this build itself binds. A foreign entry planted at the old path fails the trust check and is stepped over. `daemon serve` binds the new spelling and only the new spelling, so a host converges on it as soon as its daemon is next restarted. The discovery probe that finds a *remote* host's daemon over ssh prefers the new spelling and falls back to the old one the same way, and now requires a candidate to be owned by you before preferring it — so a newer desktop still finds a remote deck running an older build, and a stranger's entry cannot shadow one. That probe still proves nothing about *who is listening* on the far host; remote endpoint authentication is tracked separately.

A directory the deck refuses now says why. Where a foreign-owned endpoint, state or lock directory used to surface as a bare `Operation not permitted` with no path attached, the refusal names the directory, which uid owns it, which uid you are, and the `DOT_AGENT_DECK_*` override that routes around it.

Windows is unaffected: its endpoints are named pipes (`\\.\pipe\dot-agent-deck-{user}-hook` / `-attach`) with no filesystem presence and no directory to own.
