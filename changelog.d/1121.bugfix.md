## The `XDG_RUNTIME_DIR`-less endpoints move into a per-user directory another uid cannot write to

On a host with no `XDG_RUNTIME_DIR` — an ordinary ssh session, a container — the deck fell back to `/tmp/dot-agent-deck-{uid}.sock` and `/tmp/dot-agent-deck-attach-{uid}.sock`. `/tmp` is world-writable and sticky, so a **different** local user could create an entry at either of those exact paths, and once they had, the deck was stuck: `bind(2)` refuses any path that already has an entry, and a sticky directory only lets an entry's own owner unlink it, so neither the daemon nor `daemon_attach`'s stale-inode recovery could clear it. The deck on that host could not use its default endpoint again until the squatter or root removed it.

Both endpoints now live inside `$TMPDIR/dot-agent-deck-{uid}/`, as `hook.sock` and `attach.sock`. The deck creates that directory at mode `0700` through the same helper the ssh-forwarded tunnel sockets already used, which refuses a symlink and fails closed when another uid got there first — there is no entry inside it for an unprivileged stranger to create. It is `std::env::temp_dir()` rather than a hardcoded `/tmp`, so `$TMPDIR` is honoured, and the name does not collide with the tunnel module's own `dot-agent-deck-tunnels-{uid}`.

**What this buys, stated precisely, because it is a reduction in exposure and not a closed door.** The old name was free for a squatter before this host's first launch, after a `/tmp` cleaner removed the socket, and for an instant at every daemon start, which removes its own stale socket before binding a fresh one. The directory, by contrast, is never removed by the deck, so only the first two of those windows remain: "before this host's first successful launch, or after a `/tmp` cleaner reaps the directory". Inside that window the directory name is still predictable, and a local user who takes it first now causes a **refusal** rather than a bind failure: the deck will not start until that entry is removed. The refusal says which directory, which uid owns it, which uid you are, and which `DOT_AGENT_DECK_*` override routes around it, and since this release it reaches your terminal rather than only the daemon's log.

**The scope is narrower than the file name suggests.** This is an availability fix. Under `$XDG_RUNTIME_DIR` — mode `0700`, the user's own — no foreign uid could create the entry in the first place, so those paths are byte-identical to what they have always been, deliberately do not move, and a desktop session, where that variable is normally set, sees no change at all. The exposure was bounded by the directory, not by the fallback existing. [#1020](https://github.com/vfarcic/dot-agent-deck/issues/1020) had already closed the *trust* half of the same story by `lstat`ing the endpoint; this is the availability half.

**Every connection the deck opens to a local endpoint now checks who is listening.** Unix client connects read the peer's uid from the kernel (`SO_PEERCRED`, `getpeereid`) and refuse a listener belonging to another user — the same thing the Windows named-pipe transport has always done with the server's owner SID. The endpoint's own owner and mode are still checked first, before any connect is attempted; what the peer credential adds is the case a filename check cannot reach, where the entry is replaced between the check and the connect. Note what mode `0600` does and does not mean: it keeps *other* unprivileged users out, and it has never kept out root or another process running as you.

**The TUI still finds a running older daemon across the upgrade.** When the fallback applies and no daemon answers at the new endpoint, clients also look for one at the old spelling and use it if they find one. That matters because the silent version of this change is the bad one: an older daemon binds the old path, a newer TUI looks only at the new one, the two never meet, and the TUI lazy-spawns a second daemon with the first one's agents stranded under it — and the build-version handshake that exists to catch exactly that skew never fires, because it runs over a connection that is never made. The compatibility read restores the connection, so the handshake fires and you get the prompt you would get from any other version mismatch. And if that older daemon goes away in the moment between being found and being talked to — you stopped it, it hit its idle window — the launcher treats it as the cold start it now is and starts a fresh daemon at the new endpoint, rather than reporting a failed handshake and exiting.

**An older client still finds a newer daemon, too.** The reverse pairing is a release that has already shipped: a deck binary from before this change looks only at the old spelling. Against a daemon that bound only the new directory it found nothing, concluded no deck was running, started a daemon of its own, and restored your saved session under it — a second orchestrator and a second copy of every worker, in the same project, while the originals kept running out of its sight, with nothing printed ([#1211](https://github.com/vfarcic/dot-agent-deck/issues/1211)). So a daemon on this fallback now **also** binds the old spellings, `/tmp/dot-agent-deck-{uid}.sock` and `/tmp/dot-agent-deck-attach-{uid}.sock`, beside its own endpoints, and removes them again when it stops. The older client connects, the build-version handshake runs, and you get the same mismatch prompt as before this change. It also means an agent that *outlives* the pre-#1121 daemon that spawned it — and so still carries the old endpoint in its environment — has its late hook events delivered to the new daemon again while the alias is bound, rather than to an address nothing listens on; what a daemon does with an event from a pane it does not own is unchanged.

**That second bind does not bring the squatting problem back, because it is allowed to fail.** The deck's own endpoint is still the per-user directory, bound first, and it is the address this build's clients look for first. The old spelling is only an alias: if an entry the deck does not trust sits at either path — one another user created, say — or another daemon is already listening there, the daemon logs a warning and carries on without that alias. It never removes an entry it cannot verify as your own stale socket, and at exit it removes only the socket it bound. Someone squatting the old spelling can therefore stop an *older* client from finding your deck, which they always could, but can no longer stop the deck from starting, which is what this change fixes.

**The alias is a deprecation shim, and it has an end date.** It will be removed no earlier than two minor releases after the release that first ships it, so a client up to two minor versions older than its daemon still finds it; [#1213](https://github.com/vfarcic/dot-agent-deck/issues/1213) tracks the removal.

The rest of the deck treats the old path as **read-only**: clients never create it, and nothing that could unlink it or lazy-spawn at it is allowed to see an address the compatibility read chose — resolution now records which rung produced an address, and the stale-inode recovery and lazy-spawn paths refuse anything but the address this build itself binds first. A foreign entry planted at the old path fails the trust check and is stepped over. The discovery probe that finds a *remote* host's daemon over ssh prefers the new spelling and falls back to the old one the same way, and now requires a candidate to be a socket you own **and not a symlink** before preferring it — so a newer desktop still finds a remote deck running an older build, and a stranger's entry cannot shadow one. Both halves are load-bearing: the socket and ownership tests each follow symlinks, so a link planted at the preferred path and aimed at any socket you happen to own would satisfy both. What that could cost you is discovery, not safety — the ownership test constrains the target to your own sockets either way, so it could never put a stranger's listener in front of you. That probe still proves nothing about *who is listening* on the far host; remote endpoint authentication is tracked separately.

A directory the deck refuses now says why. Where a foreign-owned endpoint, state or lock directory used to surface as a bare `Operation not permitted` with no path attached, the refusal names the directory, which uid owns it, which uid you are, and the `DOT_AGENT_DECK_*` override that routes around it.

Windows is unaffected: its endpoints are named pipes (`\\.\pipe\dot-agent-deck-{user}-hook` / `-attach`) with no filesystem presence and no directory to own.
