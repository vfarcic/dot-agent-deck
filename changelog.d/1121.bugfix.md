## The `XDG_RUNTIME_DIR`-less endpoints move into a per-user directory another uid cannot write to

On a host with no `XDG_RUNTIME_DIR` — an ordinary ssh session, a container — the deck fell back to `/tmp/dot-agent-deck-{uid}.sock` and `/tmp/dot-agent-deck-attach-{uid}.sock`. `/tmp` is world-writable and sticky, so a **different** local user could create an entry at either of those exact paths, and once they had, the deck was stuck: `bind(2)` refuses any path that already has an entry, and a sticky directory only lets an entry's own owner unlink it, so neither the daemon nor `daemon_attach`'s stale-inode recovery could clear it. The deck on that host could not use its default endpoint again until the squatter or root removed it.

Both endpoints now live inside `$TMPDIR/dot-agent-deck-{uid}/`, as `hook.sock` and `attach.sock`. The deck creates that directory at mode `0700` through the same helper the ssh-forwarded tunnel sockets already used, which refuses a symlink and fails closed when another uid got there first — there is no entry inside it for an unprivileged stranger to create. It is `std::env::temp_dir()` rather than a hardcoded `/tmp`, so `$TMPDIR` is honoured, and the name does not collide with the tunnel module's own `dot-agent-deck-tunnels-{uid}`.

**This is an availability fix, and the scope is narrower than the file name suggests.** The socket inode has always been mode `0600`, so nobody could read your traffic; and under `$XDG_RUNTIME_DIR` — mode `0700`, the user's own — no foreign uid could create the entry in the first place. Those paths are byte-identical to what they have always been and deliberately do not move, so a desktop session, where that variable is normally set, was never reachable this way and sees no change at all. The exposure was bounded by the directory, not by the fallback existing. [#1020](https://github.com/vfarcic/dot-agent-deck/issues/1020) had already closed the *trust* half of the same story by `lstat`ing the endpoint; this is the availability half.

**Nothing is stranded across the upgrade.** When the fallback applies and no daemon answers at the new endpoint, clients also look for one at the old spelling and use it if they find one. That matters because the silent version of this change is the bad one: an older daemon binds the old path, a newer TUI looks only at the new one, the two never meet, and the TUI lazy-spawns a second daemon with the first one's agents stranded under it — and the build-version handshake that exists to catch exactly that skew never fires, because it runs over a connection that is never made. The compatibility read restores the connection, so the handshake fires and you get the prompt you would get from any other version mismatch. The old path is **read-only**: the deck never binds it, creates it or removes it, which is what stops the squatting problem simply moving there — a foreign entry planted at the old path fails the trust check and is stepped over. `daemon serve` binds the new spelling and only the new spelling, so a host converges on it as soon as its daemon is next restarted. The discovery probe that finds a *remote* host's daemon over ssh prefers the new spelling and falls back to the old one the same way, so a newer desktop still finds a remote deck running an older build.

A directory the deck refuses now says why. Where a foreign-owned endpoint, state or lock directory used to surface as a bare `Operation not permitted` with no path attached, the refusal names the directory, which uid owns it, which uid you are, and the `DOT_AGENT_DECK_*` override that routes around it.

Windows is unaffected: its endpoints are named pipes (`\\.\pipe\dot-agent-deck-{user}-hook` / `-attach`) with no filesystem presence and no directory to own.
