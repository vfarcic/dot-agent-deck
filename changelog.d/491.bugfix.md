`dot-agent-deck connect <name>` no longer refuses a remote whose attach `PROTOCOL_VERSION` differs from the laptop binary's. The two constants never shared a wire: `connect` is an `ssh -t` wrapper that runs the *remote* binary's TUI against the *remote* daemon, so both ends of the attach conversation were always the same install and agreed by construction. The check could only reject remotes that were working perfectly, and its suggested recovery (`remote upgrade`) swapped the remote binary under the user's live agents. A remote that is simply older now connects and gets the existing soft upgrade nudge — newer-only, TTY-only, default-No, and it names the running-agent count — which was previously unreachable whenever the protocol digits happened to differ. `remote doctor`'s `ProtocolCompatible` check reports the same thing `connect` still enforces: whether the remote answers `daemon hello` at all, which stays fatal when it cannot.
