## Delegated Tasks Are Far Less Likely to Sit Unsubmitted in a Busy Worker's Input Box

On a loaded machine, a delegated task could be typed into the worker's input box and never submitted: the line sat there with an empty line under it, the worker looked healthy and idle, and the orchestrator waited for a `work-done` that never came. The worker had not finished taking the text in when Enter arrived, so it treated the two as one paste and the Enter as a newline.

The deck now waits for the task's line to appear on the worker's screen before pressing Enter, for up to 2 seconds, and presses it anyway after that. On a machine that keeps up nothing changes. Measured against Claude Code with three busy processes per CPU, the old fixed pause left 3 of 30 tasks unsubmitted; waiting for the line to appear left none of 50. The wait is a heuristic, not a guarantee: output that shows the task's delivery id early ends it early, and a very large pane skips it. In both cases Enter goes when it used to, and a task left unsubmitted is recovered by the re-sends.

If a task does end up sitting in the input box, each re-send now presses Enter a second time after a few seconds when the task is still in the input box, because an agent in that state ignores the first Enter. A task that shows only higher up, in the worker's transcript, most likely went in, and gets no second Enter. The re-send still never types the task again when it is visible.
