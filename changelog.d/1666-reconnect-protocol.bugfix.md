## The TUI and the desktop app no longer attach to a replacement daemon on another attach protocol

If the daemon was replaced while the TUI was open, the TUI reconnected to the new one without checking that the two speak the same attach protocol, so it could show a normal dashboard while it could not read what that daemon sent. It now checks the daemon's protocol on the connection it is about to use whenever it reconnects, reattaches or restores a pane, opens a new agent pane, lists the daemon's agents for one of those, or stops, renames or messages an agent. When the protocols differ it does none of them: a footer row says `⚠ Not attaching: daemon speaks attach protocol vN, but this binary speaks vM`, with the same two ways out as the startup refusal, until a daemon on its own protocol answers again, and a new agent pane is not started on that daemon. If the check cannot be made at all, the TUI keeps retrying rather than attaching. In the desktop app, opening an agent terminal, listing a daemon's agents on the dashboard, watching their activity, starting an agent, and stopping, renaming, messaging or answering one agent each check the daemon the same way. On a replacement daemon that the app would refuse when connecting, whether for another protocol or for a version that could make the app misread what it reports, the app does none of these, and an agent terminal opened against one is refused. **Stop daemon** and **Replace daemon** are deliberately left able to reach such a daemon, so that you can still recover from it. **Connect anyway** still applies to the second case, for every daemon the app would refuse for that reason until you quit the app.

After a deck restarts, it can run a new agent under the same name, or in the same pane, as an agent from before the restart. Acting on an agent you saw before the restart could reach that new agent instead: opening, focusing or typing into it, closing, renaming or messaging it, sending it the configuration request, retrying or cancelling its message, answering its question, reading its replies or giving it any other command by voice, or cleaning up after an orchestration that failed to start. Resizing its terminal could resize another view of it, and an agent pane already open in the desktop app could switch to the new agent by itself. A TUI pane that reconnected after the restart could also start showing the new agent and send it what you had typed while it reconnected, and a TUI card could go on showing the new agent's activity while refusing every action. In the desktop app, the agent the New agent dialog had just started could be opened as the restarted deck's agent, and a terminal could show the previous agent's output under the new agent's name. In both the TUI and the desktop app these actions are now not sent to the restarted deck, and say `that agent is gone (the deck restarted)`. A TUI pane is marked disconnected instead, discards what was typed for the old agent and says the same on the status line; a TUI card from before the restart is marked gone and stops updating, and the restarted deck's agent gets a card of its own; and an open desktop pane shows the same sentence in place of its terminal. A rename refused this way keeps the old name in both apps, also when it overlapped another rename. Voice reading of replies, which the first version of this fix stopped for every agent, reads them again. A pane that only lost its connection while the deck kept running still reconnects to its own agent. Closing the card or pane of such an agent still removes it.

See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting.md#daemon-speaks-attach-protocol-vn-but-this-binary-speaks-vm).
