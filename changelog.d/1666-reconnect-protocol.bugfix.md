## The TUI and the desktop app no longer attach to a replacement daemon on another attach protocol

If the daemon was replaced while the TUI was open, the TUI reconnected to the new one without checking that the two speak the same attach protocol, so it could show a normal dashboard while it could not read what that daemon sent. It now checks the daemon's protocol on the connection it is about to use whenever it reconnects, reattaches or restores a pane, opens a new agent pane, lists the daemon's agents for one of those, or stops, renames or messages an agent. When the protocols differ it does none of them: a footer row says `⚠ Not attaching: daemon speaks attach protocol vN, but this binary speaks vM`, with the same two ways out as the startup refusal, until a daemon on its own protocol answers again, and a new agent pane is not started on that daemon. If the check cannot be made at all, the TUI keeps retrying rather than attaching. In the desktop app, opening an agent terminal, listing a daemon's agents on the dashboard, watching their activity, starting an agent, and stopping, renaming, messaging or answering one agent each check the daemon the same way. On a replacement daemon that the app would refuse when connecting, whether for another protocol or for a version that could make the app misread what it reports, the app does none of these, and an agent terminal opened against one is refused. **Stop daemon** and **Replace daemon** are deliberately left able to reach such a daemon, so that you can still recover from it. **Connect anyway** still applies to the second case, for every daemon the app would refuse for that reason until you quit the app.

After a deck restarts, it can run a new agent under the same name, or in the same pane, as an agent from before the restart. Acting on an agent you saw before the restart could reach that new agent instead: opening, focusing or typing into it, closing, renaming or messaging it, sending it the configuration request, retrying or cancelling its message, answering its question, reading its replies or giving it any other command by voice, or cleaning up after an orchestration that failed to start. Resizing its terminal could resize another view of it, an agent pane already open in the desktop app could switch to the new agent by itself, a TUI pane that reconnected after the restart could show the new agent and send it what you had typed while it reconnected, and a terminal could show the previous agent's output under the new agent's name.

Now, when the TUI or the desktop app reconnects to a restarted deck, it removes the cards and panes of the agents the restart stopped, and in the TUI an orchestration tab left with none of its agents, and shows one notice naming each of them with its role and orchestration: `The deck restarted; these agents were stopped: coder (worker in team), api-fix.` The notice stays until you dismiss it, and agents a later restart stops join it. In the TUI it has a footer row of its own that a filter, a rename, Help or a confirmation dialog does not hide; on the dashboard or an orchestration tab `a` lists every agent it names, wrapping long names, and `c` dismisses it, while in a pane or a field those keys type as usual and the footer's `[Agents]` and `[Dismiss]` buttons work with the mouse. In the desktop app it lists every agent and closes with its `×`. The removed agents simply stop being shown: nothing is stopped or deleted to do this, so a dispatched unit's worktree and branch stay on disk. The restarted deck's agents get cards and terminals of their own, and none takes over a removed agent's name or output. Something that still holds an agent from before the restart behaves as follows:

- An action on it, such as a voice command, a confirmation that was already open, or a key pressed just before its card went, is not sent and says `that agent is gone (the deck restarted)`. A rename refused this way keeps the old name, also when it overlapped another rename.
- Text typed into a TUI pane while it was reconnecting to the restarted deck is discarded rather than sent to the new agent.
- Reading its replies aloud stops.
- A terminal opened for it reports that it is not attached.
- The New agent dialog, waiting for an agent it started just before the restart, times out rather than opening the restarted deck's agent.

A pane that only lost its connection while the deck kept running still reconnects to its own agent. Closing the card or pane of an agent that is still running still stops it.

See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting.md#daemon-speaks-attach-protocol-vn-but-this-binary-speaks-vm).
