A `desktop.toml` the desktop app cannot read no longer gets silently replaced with defaults. Until now the app answered *any* failure to load its settings document — a TOML syntax error, or a value this build's schema rejects — by starting on defaults with nothing on screen to say so, and the next settings save then merged those defaults over the file: appearance, zoom, endpoints and the deck selection all overwritten, the original gone. It did not present as an error at all. It presented as "my settings reset themselves", one click after opening the app.

Now the app still starts and still comes up on defaults — a preferences file is not worth failing a launch over — but it **says why**, and it **refuses to save** while the document is in that state, so the user's own bytes survive untouched. The settings sheet names what is wrong and where (`line 3, column 9`) the moment it is opened, before anything has been changed, and the footer beside it names the file; the message carries a locator and never a byte of the document, the same rule the load diagnostic already followed. Deleting or fixing the file restores saving.

This is reachable without anyone hand-editing anything — an interrupted write, a dotfile-sync conflict marker or disk damage all produce the same unloadable file — and it is reachable *by us*, because tightening a field validator converts previously-valid documents into unloadable ones: `port` became a newtype over `NonZeroU16` after a hand-edited `port = 0` reached OpenSSH as `-p 0`, and PRD #742 reserved `all` as an endpoint id. `desktop.toml` stays hand-editable, which the issue raised as an open question; dropping that would have removed neither the failure nor the need for this fix.

Nothing here crosses the TUI↔daemon protocol — `desktop.toml` is read and written entirely inside the desktop process and the daemon cannot observe it — so `PROTOCOL_VERSION` is untouched and CLAUDE.md rule 12's cross-version check does not apply.
