## Node.js and pnpm are no longer Devbox packages

`devbox.json` no longer ships `nodejs` and `pnpm`. Install them yourself — Node.js 24.x and pnpm 11.x, matching what CI pins — whether or not you use Devbox. Devbox's `init_hook` already prepends `$HOME/.local/bin` to `PATH`, so a user-level install there is visible inside `devbox shell` as well as outside it.

This removes a startup failure that cost a role on every multi-role orchestration started in a fresh worktree. Devbox's Node plugin installs a corepack `init_hook` and materialises `.devbox/virtenv/bin/setup-corepack.mjs`; when several agents entered the same cold environment at once, they raced on creating and removing that one path and one of them died with either `remove ...: no such file or directory` or `symlink ...: file exists`. The deck reported the orchestration as started, so the unit simply ran a role short — silently, unless you counted roles.

Nothing is lost by dropping the packages: the corepack hook was already a no-op here (`DEVBOX_COREPACK_ENABLED` is set nowhere, `desktop/package.json` pins no `packageManager`, and nothing outside `.devbox` referenced corepack), no Devbox script used `node` or `pnpm`, and CI has always taken them from `actions/setup-node` and `pnpm/action-setup` rather than from Devbox. The agent CLIs the Devbox scripts launch — `claude`, `opencode`, `pi`, `codex` — were already installed this way, so Node and pnpm now sit in the same category rather than in a category of their own.

The underlying limitation is unfixed and tracked in #791: Devbox's per-project materialisation is not safe against concurrent invocations, and a rarer race in its own state handling survives this change. Warming a fresh worktree once with `devbox run -- true` before starting several agents in it remains the general mitigation.
