## CI checkouts no longer persist the job's GitHub token

Every `actions/checkout` step in `.github/workflows/ci.yml` now sets `persist-credentials: false`. The action defaults that input to true, which writes the job's automatic `GITHUB_TOKEN` into the checkout's `.git/config` as an auth header for the life of the job, where anything the job runs can read it. The sharp case is the `e2e-deterministic` lane, which executes the PTY e2e tier — contributor-authored code — but the flag is on all nine checkouts because no job in that file needs the credential after the fetch: none of them pushes, the workflow's `permissions:` block grants only `contents: read` and `pull-requests: read`, and none of them reaches the remote from inside the checkout (no submodules, no git-sourced cargo or pnpm dependencies, and the git these jobs do run is local — the build script's version stamping, `cargo xtask linkage-check`, and the e2e harness's `git init` inside its own tempdirs).

This is hardening rather than the closing of an open hole: what bounded the token before was scope, not absence — the read-only `permissions:` block, plus a read-only token on any fork `pull_request` run whatever that block says. Both still hold; the flag is a layer under them. It deliberately does **not** extend to `release.yml` or `docs-publish.yml`, which push to `main` and must keep a usable credential in the checkout.

The comment block in `ci.yml` that argued the old position has been rewritten to describe what is true now, and the `security` job's `cargo audit` is unaffected: it clones the RustSec advisory database into `~/.cargo/advisory-db`, a separate repository that a config written into this checkout never reached.
