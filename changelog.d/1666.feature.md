Agent messages now wait in an inbox until received: tasks, worker reports, dispatch results and scheduled prompts have recorded delivery. Claude Code 2.1.296 and newer, OpenCode's TUI and Pi receive native messages; Pi also queues follow-ups while busy. Codex receives messages through an idle doorbell and at turn end. When native wake is unavailable, a short doorbell line tells the agent to fetch its waiting messages.

TUI cards and desktop tiles show `✉N queued`, `✉ delivered` or an error with `not delivered: …`, and `✉N waiting to wake: send it a prompt` when messages have waited a couple of minutes with nothing waking the agent for them. The desktop handoff rail follows delegation, delivery and work-done. Use `dot-agent-deck inbox list` inside an agent's pane to inspect its messages, `inbox fetch` to read and acknowledge them, and `daemon status` to see the **INBOX** and **WAKE** columns. A message too long to show whole names a file holding all of it, usually in the project's `.dot-agent-deck/` directory. The deck keeps the file while the message waits and, for a delegated task, until the worker finishes, exits or is given a newer task; after that it is kept for about a day, or removed sooner, though not within an hour, when many long messages pile up. Copy what you want to keep out of it.

OpenCode's plugins and Pi's extension now report where each deck message stands — handed over, started on, or not handed — and the deck keeps a receipt of each, so a message is no longer repeated because a reply went missing, a turn ran long, or the integration's watcher restarted. When the deck cannot tell whether a message reached the agent, it sends it again up to twice, marked as a possible repeat, then shows `✉ delivery uncertain` on the card with the reason; when for a few minutes it can neither check nor hand the message over again, for example because the agent's deck integration stopped, it shows it uncertain without repeating it. For Pi, when the agent stays idle for a few minutes after the deck handed it a message and has not started on it, for example because it has no credentials for its model provider, the card shows `✉ may not have reached the agent`; the deck does not send it again by itself, and choosing Retry may give the agent the message twice. Press `i` on the TUI card, or use the buttons on the desktop tile, to **Retry** (send it again, marked) or **Cancel** it; if two clients act at once, the second is told another client acted first. The TUI's **Deck messages** list shows the selected message's whole explanation, which says what Retry would do, and asks for a taller or wider window instead of retrying when it cannot fit. A message or offered job that OpenCode or Pi keeps queued behind a long turn waits for that agent with no time limit, and an offered job's claim time starts when the agent starts on it; one held for an hour without being started shows a one-time reminder with the same choices. Cancelling a task the deck had already handed over tells its orchestrator the task may already have reached the worker. Cards also say when an agent's deck integration is out of date — a Pi still running the deck's previous extension shows this until you restart it — when the deck could not update its OpenCode plugin or Pi extension as the agent started, when the `dot-agent-deck` command it runs is too old for this deck, when the integration has not connected yet, when hand-outs are paused, and when receipts cannot be recorded. Restarting an agent does not carry the messages waiting for it over to the restarted one: they show as not delivered, and an orchestrator is told about each of its tasks.

Agents can publish announcements to subscribed roles and orchestrators can offer jobs to a pool of workers with `dot-agent-deck inbox publish`, `offer`, `complete` and `release`, configured with `subscribe` and `take_offers`.

A Codex, Pi or OpenCode worker behind a launcher the deck cannot see through, such as `devbox run …` with no `agent = "…"`, no longer waits 30 seconds after each delegation that restarts it (`clear = true`), and `dot-agent-deck validate` no longer warns that it does. It still warns about such a role, because its card gets no agent from the config and a Codex agent behind it runs without the deck's wrapper; declare `agent` on the role to fix both.
