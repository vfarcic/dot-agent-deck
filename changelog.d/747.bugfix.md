## An agent pane on a very wide terminal no longer renders rewrapped, misaligned output

The deck refuses to make an agent's terminal larger than 4096 rows or columns. That cap is a deliberate defence: anything with access to the deck's socket can ask to resize a running agent, applications inside a terminal routinely trust the size they are told, and `65535x65535` is a cheap way to make one of them allocate or redraw itself into the ground. Nothing you can attach to a real display comes close to the limit.

The cap was applied in only one of the four places that have to agree about a pane's size, though. The daemon clamped the request just before handing it to the agent's terminal, quietly, and reported success. The deck itself applied no bound at all: it sized the pane, its own copy of the terminal's screen, and the request it sent, from the width the layout asked for. So past the cap the deck was reading the agent's output as if the lines were 4198 columns long while the agent had been told to wrap them at 4096 — a pane of text broken in the wrong places and running out of alignment with itself, with nothing logged and no error raised anywhere. Two widths reach it: a **zoomed** pane needs a terminal about 4099 columns wide, an ordinary one about 6200. Neither is a laptop, but a terminal spanning several large monitors, or a tmux window across them, gets there.

The bound is now decided once, at the point the per-frame layout works out how big each pane's terminal should be, and everything downstream — the pane's own screen, the resize sent to the daemon, and the agent's terminal — carries that same number. A pane wider than the cap runs its agent at the full 4096 columns and leaves the columns past that blank, which is the honest picture: the agent has no more columns to show. Panes narrower than the cap, which is every pane on every ordinary display, are untouched.

The clamp has also stopped being silent. The deck writes one line to its log the first time a pane is larger than an agent's terminal can be, saying why the pane stops short of the screen edge, and the daemon writes one the first time it has to narrow a request it was sent.
