## Automatic pane writes and seed pulls are now bound to the agent they were meant for, and refuse rather than land somewhere else

A pane id is a recycled handle: when an agent exits or is closed, its `DOT_AGENT_DECK_PANE_ID` is free for the next spawn to inherit. Several daemon-side paths used to act on that string alone, with a real gap between deciding where text should go and actually writing it — so if the intended agent went away inside that gap, the text was typed into whatever process had taken its place, and (for everything but the notices) Enter was pressed on it. A tool-capable agent could then act on work it was never given. Issue #608 closed this at the daemon's write-and-submit handler; this closes the paths enumerated below, on both directions of travel — the writes the daemon pushes, and the seed an agent pulls. It is a statement about those paths, not about the pane keyspace in general.

**This is a compatibility break in behaviour, not in wire shape.** No message, field or type in the attach protocol changed and `PROTOCOL_VERSION` is unchanged at 8, so an older and a newer build still interoperate. What changed is *who gets refused*: deliveries that previously landed now fail closed with zero bytes, and each refusal costs something visible. Those costs are listed below. The one new field is on the hook socket and is additive in both directions — see the `get-seed` section.

### The write paths, closed by type rather than by review

The guarded write APIs (`write_and_submit_guarded`, `write_and_submit_guarded_detailed`, `write_notice_guarded`) now take the expected agent identity as a `&str` instead of an `Option<&str>`. Passing no identity used to skip the identity comparison entirely and fall through to an unguarded write; that case no longer exists to be skipped, and every caller that had nothing to pass became a compile error. Two independent reviews of the #608 fix had each found sites the other missed, which is the argument for letting the compiler enumerate them.

The six paths, and the window each had:

- **Scheduled tab reuse.** A reuse fire waited out the deliver-on-idle debounce (5s by default, up to 60s under continuous typing) holding nothing but the pane id. The reuse decision also asked only whether *some* live process owned that pane, never whether it was one the task had spawned — although the reuse record has always stored those ids. It now resolves the pane's live agent, checks it against the record, and delivers bound to it. A tab whose agent was restarted in place is no longer recognised as reusable, so the next fire opens a fresh tab instead of re-delivering into it: an extra tab, rather than a scheduled prompt submitted into a process that never ran the task.
- **Dispatch results.** The daemon resolves the caller's directory, then does a git worktree creation and an agent spawn — unbounded, and deliberately outside any state lock — before writing the result back. It now captures the caller's agent id from the same registry record as the directory, and delivers to that.
- **The native-seed PTY fallback.** A pi pane's seed is stashed for the editor extension to pull; if no pull arrives within 15 seconds the daemon types the seed in as a safety net. That timer held only a pane id. It now takes the seed only from the record of the agent it was armed for, and leaves a stranger's seed where it is so that stranger's own pull can still find it.
- **Work-done feedback.** A worker's completion report is submitted into its orchestrator's pane, bound to the orchestrator the delegation was *commissioned* by. If the pane that commissioned the delegation is not the pane the completion routes to, the report is now dropped rather than delivered to the pane that happens to be there — it would otherwise arrive labelled as work that orchestrator asked for. Two cases are deliberately weaker and are not claims about who asked for anything: a completion nobody commissioned is bound instead to the pane's current agent, resolved immediately before the write; and because a completion carries no delegation generation, a completion credited to a *superseded* delegation is bound to the orchestrator of the newest delegation on that worker pane rather than to the one that issued the superseded task.
- **Two delegate notices** into the orchestrator pane — the one reporting that a `clear = true` replacement worker is not there, and the one reporting that its respawn failed outright. The first was already guarded but passed through an identity that could be absent, which put it back on the unguarded path in exactly the case where the orchestrator pane had just been freed. The second was unguarded on the reasoning that it reports a failure it learns about immediately; that is an argument about a window's size, not about the write being safe, and the two sibling arms of one `match` no longer disagree about it.

A refused write is **not** retried against whoever now holds the pane — that is the delivery this exists to prevent. A *partial* write is treated separately from a refusal at each of these sites: bytes of ours already reached the authorised target, so re-sending would duplicate a half-written message rather than repair it.

Binding to an identity means a delivery can now be *refused* where it previously landed somewhere, and both refusals cost something visible. Reuse costs an extra tab, as above. Work-done costs a **lost report**: an orchestrator agent replaced in place — a crash and a respawn on the same pane — keeps its pane but gets a new agent id, so every delegation still outstanding was commissioned against the old one, and each worker's completion is written to the daemon log with nothing surfaced in the pane. That is invisible unless you read `deck.log`. The same loss has a second, narrower cause once the generation check below is in place: a completion that arrives while its orchestrator is *between* conversations — the gap inside a `/clear`, where the agent id is unchanged but the pane's generation has momentarily gone — is refused rather than landing, and is dropped and logged the same way.

The two unguarded primitives those callers used to reach — `write_to_pane_and_submit` and `write_to_pane_notice` — are no longer available to production code. The first is deleted outright; the second is compiled only into the crate's own unit tests, where one fixture needs an identity-free write to retire the pane it is about to hand over. Until now the type change had removed the permissive *argument* but not the permissive *API*, so a future call site could still have reached an unguarded pane write with nothing to object.

### The two residual holes in #608's own fix

Both were documented in code comments rather than fixed, and both failed permissive.

**On a pane, a conversation that has ended no longer reads as an agent that never had one.** A caller may name no hook generation, because an agent that never reports one legitimately has none to name. But the end of a conversation *removes* the pane's generation while the agent and its pane stay alive, so an agent whose conversation had ended and whose successor had not yet announced itself — a `/clear`, a thread restart — read exactly like a sessionless agent, and an unnamed write could land there. The daemon now records the end against the agent id the ending event *names*, and only where its own registry confirms that that agent holds the pane the event names — so an end nobody can attribute records nothing, and cannot make this decision on a third party's behalf. The scope is deliberate: a **paneless** target has no pane-to-generation mapping at all and is re-validated by agent identity alone, exactly as streamed input is, so no generation check applies to it.

Two things about this are worth knowing rather than discovering. It is recorded per agent and never per pane: the daemon's existing per-pane record of the same event is never cleaned up when a pane closes or is recycled, so reading that one would have refused every future sessionless agent on that pane id for as long as the daemon ran — permanently, and precisely the agents the exemption exists to protect. And it **fails open where the evidence is absent**, in both of the ways evidence can be missing: hook events carry the agent id the daemon injects at spawn, but that field is optional and an external agent (or a wrapper that lost the variable on the way) sends none — and, as above, an end whose named agent the daemon cannot confirm holds the named pane is not attributed to anybody either. No end is recorded in either case, and such a producer's unnamed writes are accepted exactly as they were before. That is a deliberate degradation to the previous behaviour and the right default, but it is a limit rather than a guarantee.

**This one costs availability too, and the record is permanent.** That an agent has ended a conversation is remembered for as long as the daemon runs; nothing clears it, and nothing about a later moment makes an ended conversation un-ended. The refusal it drives is still conditional, because it is consulted only once the pane is found to have no current generation, so a successor announcing itself takes the decision away from it entirely. What that leaves is a live agent in a real conversation the daemon never learned about — its successor `SessionStart` lost or rejected — whose unnamed automatic deliveries are refused until that conversation ends. As above, a refusal writes zero bytes and is logged rather than retried into whoever else is there.

**Live attachment is no longer part of a delivery's authorization.** A delivery naming a generation the pane no longer has used to be refused on an *attached* pane and allowed on an unattached one. Attachment was the one input the delivery-time check could not read consistently with the rest — attaching never waits for the writer the check holds, so the value could be read stale in the permissive direction — and the refusal is now unconditional.

**This one costs availability, on headless decks specifically.** A `daemon serve` delivery with no client attached, bound to a generation that subsequently ends, is now refused on every retry and abandoned after 60 seconds with the prompt never delivered (bounded and logged, not silent, but lost). A delivery cannot un-bind itself from a generation, so it cannot fall back to the unnamed path. Under a running TUI this was already the outcome, because the TUI attaches to a pane as part of creating it, so what changed is that headless deliveries now behave like attached ones rather than more permissively.

### The `get-seed` pull

The other direction of travel on the same data: an agent's editor extension asking the daemon for the seed prepared for it. That request carried a caller-supplied pane id and nothing else, and the daemon answered it without checking who was asking and without skipping records of agents that had already exited — the filtering the registry's other operational lookups apply. An agent that exits on its own keeps its record until something reaps it, while a successor is allowed to claim the same pane id in the meantime, so two records could answer to one pane id and which one answered was unspecified. A successor could be handed its predecessor's opening task.

Exited records are now skipped, and the request carries the caller's own agent id so the daemon can require it to match the record holding the seed. **A caller that presents no agent id is still answered** rather than refused, from the pane's live occupant: refusing would cost a seed for every producer the daemon injected no id into, which is certain, and what requiring an id buys is less than it looks. It is not nothing — a caller presenting its *own true* id and a *foreign* pane is refused, because the record has to hold the pane the request names — so requiring one would raise the bar from "know the victim's pane id" to "know or guess the victim's agent id". But registry agent ids are sequential decimal strings from 1, so guessing one is cheap; that is a low bar to buy at the price of a lost opening task for every id-less producer.

The new field rides the hook socket, which carries no version handshake, and it is optional with a default. A newer client that has no id to present omits it entirely, so an older daemon receives the request it always received; an older client's request has no such field and reads as "could not say". Nothing here moves `PROTOCOL_VERSION`.
