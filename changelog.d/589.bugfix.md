## The new-pane form no longer offers a key it will refuse

When the name a new orchestration would take is already held by a live one, the form refuses to submit: `[Submit]` disappears from the action row and a warning says why. The footer directly beneath it went on reading `Tab: switch  ◀▶: mode  Enter: submit  Esc: cancel`. Pressing Enter there did nothing whatsoever — no error, no message, no movement — so the two lines of the same modal, one above the other, disagreed about whether submitting was available.

The wording was chosen from where the cursor was rather than from whether submit could succeed: Name is the field where Enter submits once an orchestration is selected, so the footer said `Enter: submit` whenever focus sat there. The collision was known one function away — it is what had already removed the button — but the footer never consulted it.

The footer now drops the `Enter:` clause entirely in that state, leaving `Tab: switch  ◀▶: mode  Esc: cancel`: the keys that still work, and no promise about the one that does not. That matches how the action row handles the same refusal, which removes `[Submit]` rather than dimming it. Both now read the single check the Enter key itself makes, so they cannot drift apart again, and typing a name that is free restores the button and the `Enter: submit` hint together. No other state's wording changes — in particular, a collision does not mute Enter on a field where Enter only advances focus, since nothing is refused there.
