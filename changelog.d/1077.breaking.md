## Hook-socket messages must now carry the capability token their pane was spawned with

Every message an agent sends the deck's daemon — `delegate`, `work-done`, `dispatch`, `pane restart`, `pane spawn`, `get-seed` and `dispatch --list-targets` — names the pane it comes from, and until now that name was the whole of the claim. The CLI copied `DOT_AGENT_DECK_PANE_ID` into the message and the daemon acted on it. So any process running as you that learned a pane id — and `daemon status` prints them — could make the daemon type a task into every worker of someone else's orchestration, write a fake completion report into an orchestrator's pane, or spend a dispatched unit's one-shot return route so that the real unit's report went nowhere.

The daemon now mints a random capability token for every agent it spawns, puts it in that agent's environment as `DOT_AGENT_DECK_PANE_CAPABILITY`, and requires every one of those messages to present it. It checks which pane the token was issued for and refuses the message if that is not the pane it names — so an agent cannot borrow its own valid token to speak for a neighbour. The daemon does not publish the token: it is not part of `daemon status`, `list-agents` or the agent records a client receives, and the daemon never writes it to its log. (An agent that prints its own environment into its pane does put it in that pane's scrollback, where an attached client can read it.) A respawned pane gets a new one, so an environment left over from a previous occupant no longer authorises anything.

**This is not isolation between agents, and it is not described as such.** The token has to be readable by the agent it belongs to, and on Linux another process running as the same user can read that agent's environment from `/proc/<pid>/environ`. What changes is that a pane id read off the daemon's own status output is no longer enough to impersonate a pane. Raw hook events and `agent-event` status reports are not covered by this change. `docs/develop/hook-provenance.md` has the full threat model, and [#1129](https://github.com/vfarcic/dot-agent-deck/issues/1129) tracks what remains open.

**Why this is marked breaking.** The message format is unchanged — `token` is an optional field, an older daemon ignores it, and a CLI with no token sends exactly what it always sent — so `PROTOCOL_VERSION` does not move and a newer `dot-agent-deck` still works against an older daemon. What changed is what a newer daemon *does* with a message that has no token: it refuses it. So a pane whose `dot-agent-deck` binary is **older than the daemon that spawned it** — which happens when the daemon is started from a different build than the one on `PATH` — has its delegations and completions refused. The daemon logs each refusal with the reason. If you are in that situation, put the matching binary on `PATH`, or set `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` on the daemon to accept token-less messages with a warning. That setting tolerates a *missing* token only; a token issued for a different pane is refused either way.

`work-done` and `dispatch` read no reply, so a refused one still exits 0 — the refusal is visible in the daemon log, not to the command that sent it.
