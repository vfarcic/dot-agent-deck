## Agents are told that `ci.yml` is already `workflow_dispatch`-able, and when reaching for it is worse than not

`.github/workflows/ci.yml` has carried a bare `workflow_dispatch:` for as long as anyone needed it, so any pushed branch can have the full matrix run on GitHub's runners with no local CPU at all — `git push -u origin <branch>`, then `gh workflow run ci.yml --ref <branch>`, then `gh run list --workflow ci.yml --branch <branch> --limit 1`. Nothing said so anywhere an agent reads. The trigger was no secret in itself: `release.yml`, `tag-release.yml` and `docs-publish.yml` are each described as dispatchable in `docs/develop/governance.md` and in their own skills. `ci.yml`'s was written about nowhere — not in `CLAUDE.md`, not in the `issue-queue` / `prd-queue` / `pr-review-queue` skills, and not in the task texts this repository's dispatcher composes for isolated units. So every dispatched unit compiled everything locally, on a box already running the other units, which is the condition issue #863 measured to `io full avg300=65.95` with the CPU idle and `ld` invoking the OOM killer. **No workflow changed. This is documentation and instruction only, and no gate's behaviour moved.**

**The framing is the change, not the capability.** A bare "you can run CI" would have been a net negative — it trades a slow local gate for a slower remote one — so what landed says *when* rather than *often*.

**The sharpest part of that framing is that a dispatch relieves no local gate, and cannot.** Rule 2's `cargo fmt --check` and clippy are a *pre-commit* gate, and there is nothing to dispatch until a commit exists, so they have already had to pass before the capability is even available; rule 5's `cargo test-fast` stays a per-task obligation and nothing here moves it. What a dispatch buys is the part **no local gate covers at all** — `build-macos`, `build-windows`, `e2e-deterministic`, `nix`, `devbox`, `security`, the two desktop jobs and `windows-cross-check` — at a moment of your choosing rather than only when the pull request opens, and the option of not adding a *second* broad local sweep to a box already busy running the mandatory ones. So: reach for it when the box is loaded, when the change needs a platform the developer does not have, or as a final pre-PR sweep; never as the per-edit gate, and never as a stand-in for a gate that runs before the commit. Measured on 2026-09-15 from the repository's own run history — the 37 completed `ci.yml` runs among the last 60 listed — a round trip has a **9.5-minute median** (7.3 fastest, 16.4 at p90, 26.7 worst) against a warm clippy of **9.3–10.4s** on a quiet box (CLAUDE.md rule 2's figure) or **14.3s** re-measured on this one under load — so as an inner loop it is 40 to 60 times worse.

**The expensive half is compiling, not testing, so "just run the tests in CI" relocates the small half.** Warm, `cargo test-fast`'s entire wall clock is the 25–30s rule 5 measures, because the build in front of the tests is then a no-op; and lane 1 of the e2e tier is already off this box since issue #502. What a freshly dispatched unit actually pays for is the build in front of both gates. Measured for this change in exactly that state — a dispatch worktree with no `target/` at all, `/proc/pressure/io` at `full avg60=49.23` — rule 2's clippy cold took **2m42s**, and `cargo test-fast` straight after it took **4m48s** wall of which only **37.1s** was executing its 3118 tests. Neither is a true cold worst case, since the second run inherited the first's unpacked registry; a unit's genuine first build is worse, which only widens the gap. The clippy figure is the *cheap* gate's cold cost: `clippy` type-checks and never links, while `cargo test-fast` compiles for real and links roughly 130 test binaries, which is the work `docs/develop/build-gate.md` bounds and the work an OOM kill lands on.

**Two of issue #896's own claims did not survive being checked, and the narrower versions are what shipped.** The issue says a unit that dispatches twice on one branch cancels its own first run, which was true of the pre-#1088 `ci-${{ github.ref }}` key with an unconditional `cancel-in-progress: true`; the current key is `ci-${{ github.event_name == 'pull_request' && github.ref || github.run_id }}` with `cancel-in-progress` scoped to `pull_request`, so a dispatch gets a group of its own, never cancels, and is never cancelled by a PR run on the same branch. The issue also says no local gate replaces `build-windows` or `build-macos`; that holds for macOS on a Linux host, but `scripts/windows-cross-check.sh` is a real partial counterpart for Windows — it type-checks the workspace for `x86_64-pc-windows-msvc` without linking, testing or linting it.

**Take the run id from the URL, not from a listing.** The obvious `gh run list --workflow ci.yml --branch <branch> --limit 1` is wrong twice over, and the page says so with the measurement: for the first seconds a dispatch is not listed at all, so the newest run is the *previous* one, and a branch with an open pull request also carries `pull_request` runs that are usually newer. Run on this issue's own branch on 2026-09-15, with the dispatch already complete, that command returned the PR's run `35025714262` on head `435e3358` rather than the dispatch `35025264144` on head `385e342d` — a different run, on a different commit, presented as the answer to the dispatch. Where a listing is genuinely needed, pin `--event workflow_dispatch` and check the head SHA.

`docs/develop/ci-on-demand.md` is the new reference: what a dispatch actually runs (eleven of the file's twelve jobs, and why the `changes` path filter resolves to the full matrix on an event that carries no `pull_request` payload), which five are the ruleset's required contexts, what it will not cancel, what it cannot cover (lane 2, the demo reel's `.cast` recordings, anything unpushed), and the measurement table behind the numbers above. `CLAUDE.md` rule 5 carries the short version next to the three tiers, because the question it answers is *where* a tier runs; the three queue skills carry one line each in the task text they compose, so a dispatched unit learns it the same way it learns the gates — keyed to authorship in `pr-review-queue`, which never dispatches a run against someone else's branch for the same reason it never pushes to one.
