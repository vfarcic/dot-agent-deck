## Delegated Tasks Lost to a Slow-Booting Worker Now Arrive

A delegated task typed into a worker that was still starting up could be swallowed without a trace, leaving a healthy-looking worker idle while the orchestrator waited for a `work-done` that never came. Agents that announce nothing before their first prompt, such as OpenCode, were the most exposed, because no fixed delay can prove they are ready.

The deck now waits for proof that the worker received its task — the agent starting a turn, a `work-done`, or an acknowledgement — and while none arrives it re-sends the task into the same worker process, never restarting it. Every delegation carries a short delivery id at the end of the line typed into the worker's pane (`… for your task. [delivery d-7f3a9c21]`), and the worker's task file now opens by asking it to run `dot-agent-deck ack d-7f3a9c21`, which stops the re-sending. Each re-send presses Enter first, and types the task again only when it is not visible in the worker's pane and the worker stays silent for a few seconds afterwards — never for a Codex worker, whose delivery the deck cannot always confirm, so a second copy could start the task twice; it skips the re-send if you have typed into the worker's pane since the deck last wrote to it. If every re-send goes unanswered, the orchestrator's went-quiet report says how many were made.

The schedule defaults to re-sends 20, 60 and 140 seconds after the first write; set `DOT_AGENT_DECK_DELEGATE_RETRY_SCHEDULE_MS` (comma-separated milliseconds) to change it, or `0` to turn it off. A worker whose tool allowlist names individual commands, such as `Bash(dot-agent-deck work-done:*)`, needs `Bash(dot-agent-deck ack:*)` as well. A role whose agent the deck cannot identify is not re-sent to; declare its agent to cover it.

See [A lost task is re-sent into the same worker](https://agent-deck.devopstoolkit.ai/docs/orchestration#a-lost-task-is-re-sent-into-the-same-worker).
