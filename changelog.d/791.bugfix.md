## A dispatch into a fresh worktree no longer silently starts one role short

Starting a multi-role orchestration in a **freshly created** worktree could kill one role at the moment it launched, and nothing said so. The deck reported the orchestration as started; the unit simply ran with five roles instead of six. Both observed occurrences took the orchestrator, which leaves the workers with nobody to delegate to — a team that looks healthy on the dashboard and can never make progress. The dropped role failed with one of two devbox errors: `remove …/.devbox/virtenv/bin/setup-corepack.mjs: no such file or directory`, or its complementary `symlink …: file exists`.

The cause is that devbox's per-project `.devbox` materialization is not safe against concurrent invocations of itself, and six roles starting together in a cold worktree are six concurrent first invocations. Only the *first* one is exposed, which is why the failure never appeared in a checkout anyone had used before, and why re-running a broken orchestration worked — the failed attempt materialized the directory on its way out. It only started biting once each dispatched unit got its own worktree.

Two changes, because the first does not subsume the second. The nodejs devbox plugin is now disabled (`disable_plugin: true` on the existing `nodejs` entry — the package and its version pin are untouched), so the file those two errors name is never created at all; verified by materializing a cold environment with and without the flag, where the whole `virtenv/nodejs` and `virtenv/bin` subtree is simply absent and `node` / `pnpm` still report the pinned 24.12.0 / 11.22.0. This costs nothing here because corepack was never used — no `packageManager` field in any package manifest, the enabling variable set nowhere, and CI taking Node and pnpm from its own actions. Separately, `dispatch` now materializes a newly created worktree's environment **once, serially, before spawning any role**, so no role is ever the one that has to create it. That covers both creation paths: a `dispatch` and an issue-dispatch fire.

The warm-up cannot become a new way for a dispatch to fail. A repository with no `devbox.json` starts no process at all, and a machine with no `devbox` — or a `devbox` that exits non-zero — is logged and stepped over. In each of those cases the roles start exactly as they did before, which is the previous behaviour rather than a new failure mode; devbox is optional here, and a project that does not use it should not be able to lose a dispatch to it.

One path is not merely neutral, and is worth knowing: if devbox has still not finished after ten minutes the dispatch stops waiting and starts the roles anyway, so they can race the unfinished materialization with the warm-up as one more contender. The alternatives are worse — waiting forever wedges the dispatch, and killing devbox mid-flight abandons a half-written `.devbox`, which is the other half of this same bug — so the bound is set where reaching it means something is genuinely stuck rather than merely slow, and the abandoned run is left to finish rather than killed.

**What is not fixed:** the underlying materialization is still not concurrency-safe. What is gone is the exposure — one manifestation, because the file it needs no longer exists, and the window itself for worktrees the deck creates. Create a worktree by hand and start several devbox-launched processes in it at once and you can still meet it; the mitigation is the same single `devbox run -- true` in the new directory first. `docs/develop/devbox-concurrency.md` records the mechanism, the measurements, and why a clean run proves nothing about a race this timing-dependent.
