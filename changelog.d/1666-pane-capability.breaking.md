## Deck messages reach an agent's processes that run outside its pane, such as Claude Code's background session

An agent's deck messages used to be handed only to processes the deck could trace back to the agent it started in the pane. Claude Code can run a conversation in a background session that it keeps outside that process, for example after `/resume`, and from there its hooks and its `dot-agent-deck inbox fetch` were refused with `inbox_not_agent_process`, so the agent's messages and work-done reports waited and never arrived. On Linux and macOS a process now takes the pane's messages, and posts as the pane, when it carries that pane's current deck environment and runs as the same user as the deck, wherever it runs. The agent's hooks and tool shell need no change on your side. A copy of the pane's environment in another terminal of yours now counts as the pane too, so keep it to the agent.

When the deck still refuses such a request, the refusal names its cause and what to do: `inbox_other_user` (run it as the user that runs the deck), `inbox_peer_unidentified` (run it again from the agent's pane and keep it running until the deck answers), `inbox_component_not_caller`, `inbox_receiver_above_agent` and `inbox_nested_agent` (run the inbox command from the agent's own integration rather than from another process, a shell outside the agent such as another tab of its terminal, or a nested agent). A request carrying another pane's capability, an earlier agent's capability or none is refused as before, with its own message.

This changes which requests the daemon accepts, so a desktop app from this release refuses an older daemon and says which versions they are. Upgrade the deck, the desktop app and the daemon together. See [Troubleshooting → An inbox request is refused](https://agent-deck.devopstoolkit.ai/docs/troubleshooting.md#an-inbox-request-is-refused).
