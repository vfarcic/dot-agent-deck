## The e2e CI lane no longer waits two and a half minutes before starting its slowest test

`lifecycle/version/001` is the one e2e test that has to `cargo build` the binary itself, so its wall clock is a compile rather than a run, and issue [#928](https://github.com/vfarcic/dot-agent-deck/issues/928) measured it at 351s of the deterministic tier's time against a 12.8s runner-up. Being a single test, no amount of runner width splits it — it set a ~6 minute floor on the `e2e-deterministic` job.

**The dominant cost was not the build. It was when nextest got round to starting it.** Read across 13 `e2e-deterministic` runs (2026-09-06 to 2026-09-09, GitHub `ubuntu-latest`), each from its own log: this test was the last of ~2,680 tests to *complete* in 13 of 13 runs, and it was also the last to *start*, at t = 148.6-156.9s every single time (mean 152.0s). nextest schedules in binary-name order and `dot-agent-deck::e2e_version_injection` sits about 70% of the way down that queue, so the job's whole test wall clock came out as that fixed offset plus this test's own duration — 220.6, 257.9, 270.8, 285.8, 318.8, 336.7, 439.6, 440.9, 441.2, 444.5, 448.3, 449.9 and 454.9 seconds across those runs, while every *other* test in the tier had finished by t = 198-292s. The offset stays that stable on runners whose speed varies 4x most likely because the queue ahead of it is largely PTY tests whose wall clock is set by their own waits rather than by the machine — that part is an explanation, not a measurement.

It now carries `priority = 25` in `.config/nextest.toml`, which puts it at the front. The tier's wall clock becomes `max(this test, everything else)` instead of `queue depth ahead of it + this test`. On the seven runs above 439s that is about 150s off a ~445s job. It is not free on every run, and the fastest one is where that shows: this test took 71.9s there while the rest of the tier finished at 198.1s, so the ceiling on the gain is 220.6s down to 198.1s — and the rest of the tier now shares the machine with the compile for its whole length rather than roughly half of it, so a tier that slowed by more than 11% under that would come out behind. The trade is deliberate; the seven 440s runs are the ones worth fixing. The value is 25 rather than 100 for a specific reason: `dispatch_015` holds `priority = 50` *and* reserves the whole thread pool, and an exclusive test reached mid-run makes nextest drain everything before it can take that pool — ordering this test above it would make that drain wait out a multi-minute compile.

**Stated plainly, because it is the cost of the change:** the nested compile now overlaps the whole tier instead of only its tail. On the run measured in most detail it overlapped for 113s of its 288s and then ran alone on an otherwise idle runner for 175s, which is why #928 called the test's `--jobs` cap "protecting nothing". That cap — half the machine's cores — is unchanged, and its premise (that this build runs beside the timed PTY tests) has gone from mostly false to true.

**One of the issue's two premises was wrong, and correcting it is why nothing changed in `ci.yml`.** #928 read the scratch `CARGO_TARGET_DIR` as defeating CI's cache — "cold on every run, forever". It does not. `Swatinem/rust-cache` caches the whole `target/` tree and its pre-save cleanup *recurses* into a nested target directory: it calls a directory a profile only if that directory holds `build`, `.fingerprint` or `deps`, and `target/version-injection-e2e` holds none of the three at its root, so it is walked rather than pruned, and the keep-list then spares every entry belonging to a dependency. Transcribed from the action at the SHA `ci.yml` pins and run against a real populated scratch directory: **995 entries kept, 24 removed** — the 24 being this package's own artifacts and fingerprints plus `incremental/`, `examples/` and the two cargo lock files. A cache-hit run therefore starts build 1 with the dependency graph already compiled, which is also why the sampled runs show no clean split between "No cache found" (351, 370, 305, 185s) and full cache hits (72 through 297s).

**The other correction is what dominates this test's cost, and it is neither of the issue's levers: the machine.** Measured on one 16-core dev box with identical work and identical flags, the three nested builds back to back took **65.0s cold on a quiet box (load 3-8) against 400.9s with three other agents building (load 13-18)** — a 6x spread, larger than every configuration lever put together. Warm: 24.0s against 142.3s. With `CARGO_INCREMENTAL=0` as CI sets it, 98.5s quiet against 455.6s busy. The full table is now in the test file, along with the CI spread, so nobody tunes this test against a single measurement again.

**A `debug = 0` build profile was tried and is deliberately not shipped**, and the numbers are recorded in the test file so the next person does not redo the work. Dropping debug info from a binary that is only ever run for `--version` and `daemon hello` looked obviously right, and on the busy box it looked like a halving. At matched low load it is worth 10-15% where it shows at all and slightly *negative* in the configuration CI uses (101.4s against 98.5s) — inside the noise the 6x table describes. The disk saving is real, about half (1.3 GB → 650 MB in CI's configuration), but taking it needs the profile declared in `Cargo.toml`, because rust-cache keys on that manifest and does not re-save on an exact key match — set as an environment variable inside the test it would rotate no key, leave the cache serving `debug` artifacts the build can no longer use, and make every run pay a cold build with nothing written back. Declaring it rotates the key once, and then the first cache written carries the old `debug` artifacts forward for good, since cargo never garbage collects a target directory and rust-cache re-saves whatever it restored. CI would store more, not less, for a time saving inside the noise. Halving what a worktree keeps on disk is still worth having and belongs with [#927](https://github.com/vfarcic/dot-agent-deck/issues/927), which owns per-worktree build cost.

`slow-timeout` was revisited as the issue asked and deliberately **kept** at 120s x 10. The cold case has not gone away — 4 of the 16 runs whose cache status was checked reported "No cache found", and a fresh worktree pays it too; the spread across the 13 runs is 71.9s to 305.4s with two no-cache runs at 351.1s and 369.9s; and scheduling the test first means it now runs contended for its whole duration rather than mostly alone, which can only widen that spread upward. Being killed there costs the test's own assertion message, the only thing that separates "the injection never reached the binary" from "the build did not finish".

What the test proves is untouched, and the only change to the test file is documentation. It still runs three real builds into an isolated target directory, still changes `DAD_VERSION` and `DAD_BUILD_ID` one at a time so that a single missing `cargo:rerun-if-env-changed` line fails it, and still runs each produced binary with both variables absent from its runtime environment. Two ways of going under the remaining floor were considered and rejected: collapsing the builds would stop pinning either rerun directive individually, and seeding the scratch directory from the main `target/debug` would mean reaching into cargo's artifact layout so that a test whose job is to prove a *build* behaves correctly starts from another build's output.

One smaller correction while in here: the issue's "613 crates" is the whole workspace's `cargo metadata --all-features` package count, which includes the Tauri desktop crate and every dev-dependency. The nested build's own graph is **224 packages** and 280 compilation units.
