## The desktop crate's applied selection is locked by every test that writes it, not just by nextest

No user-facing change, nothing under `src/`, and no test's assertions move — this is `desktop/src-tauri`'s unit tests only. `PROTOCOL_VERSION` is untouched and CLAUDE.md rule 12's cross-version check does not apply: the daemon, the TUI↔daemon protocol, orchestration and hooks are all unreached.

`apply_settings_selection` writes `APPLIED_SELECTION`, a process-global. `dto::tests` took a `SELECTION_LOCK` around its own writes and said so in a comment; **eight tests in `endpoint_test::tests` and `lib::tests` did not** — six of them by way of `lib::retarget_selection`, which writes the global on the caller's behalf and so does not look like a write at the call site. `cargo nextest run` gives each test its own process, so the global is never shared and the omission cost nothing. `cargo test` runs a crate's tests as threads in one process, where those writes land inside a guarded test's window. All eight now take the lock, which moves beside the global it guards and becomes `pub(crate)` so the writers outside `dto` can reach it.

It is `tokio::sync::Mutex` rather than `std::sync::Mutex`, matching `endpoint_test::tests`' existing `ATTACH_ENV_LOCK`. Six of the eight sites are `#[tokio::test]`s that hold the selection across an `.await`, and a `std::sync::MutexGuard` doing that is `clippy::await_holding_lock` — measured as eight errors under rule 2's `-D warnings` gate before the switch. It also has no poisoning, so a test that panics mid-selection releases the lock instead of converting its own failure into a failure in every sibling that writes the selection. The one site holding both locks takes `ATTACH_ENV_LOCK` first, so a consistent order is all the deadlock-freedom argument needs.

**`cargo test --lib` is still red, and issue #1078's diagnosis was one of three causes rather than the cause.** The issue reasoned from the selection alone and predicted the command would go green; it does not. Isolated by excluding the ten tests that move the other two globals, the selection race is **6 runs red before this change and 6 green after**, on the same 249 tests — so the lock does close what it is for. The other two are separate and neither is the selection: `endpoint_test::tests` sets the `DOT_AGENT_DECK_ATTACH_SOCKET` override process-wide under `ATTACH_ENV_LOCK`, but every one of the crate's 25 `Endpoint::local()` call sites reads it without taking that lock, so a sibling test sees a scratch socket as the local deck's identity; and `bind_attach_listener` flips the process umask to `0o177` inside `daemon_bridge::tests`' `RealDeck`, where a concurrent `create_dir_all` produces a directory with no execute bit and the next `bind` in it fails `EACCES`. Both are recorded in the tree as knowingly accepted nextest dependencies — `RealDeck`'s own doc comment says the flip "is accepted rather than avoided, because a socket this test created some other way would not be the thing the trust check is supposed to be running against". Fixing either means changing tests across the crate rather than adding a lock acquisition, so both are left to their own change and the trap they cause is unclosed.
