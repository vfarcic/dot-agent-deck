## Closing a dispatched unit that still holds uncommitted work now says so — and where (`PROTOCOL_VERSION` 7 → 8)

Closing a dispatched unit whose copy of the repo is clean deletes that copy. Closing one that still has uncommitted work keeps it, so the work is recoverable — but until now nothing said so. The keep existed only as a line in the daemon log, so the good outcome and the ordinary one looked identical from the deck: the card vanished either way, and a directory quietly stayed on disk holding work whose location you had no way to learn short of already knowing that `dot-agent-deck worktree list` exists.

The close confirmation now tells you before you answer it. Where the unit's copy is dirty, the dialog you are already looking at names the directory the work will be kept in, above the Cancel/Close options — so the path arrives while cancelling and committing is still an option, rather than after the pane is gone. Confirming repeats the same path on the status line, which outlives the dialog by fifteen seconds. A unit whose copy is clean says nothing at all, because that copy is about to be deleted and a warning on every close is a warning nobody reads.

The dirty check is a `git status --porcelain` run by the daemon, which is the only process that knows both the removal policy and, under a remote deck, the filesystem the worktree is on. It is time-boxed, because it now sits on a keystroke: when it does not answer in time the dialog still reports the path, under wording that does not claim more than was measured. That matches what the deck actually does — an unanswerable status check is already a reason to keep the directory rather than delete it.

**This is classified as a compatibility break because the wire shape moved.** The dialog asks the daemon a new question (`dispatch-worktree-close-preview`), which is a new request variant, so `PROTOCOL_VERSION` goes 7 → 8 and `dot-agent-deck connect` will refuse a laptop and a remote host running different sides of this change until both are upgraded. Locally the skew is self-healing and nothing else regresses: measured against a v0.38.0 daemon, a deck built from this change attaches to it, renders its orchestration, delegates, receives `work-done`, and takes hook events exactly as before — and the one request the older daemon cannot understand is refused cleanly, leaving the dialog to render as it always did rather than failing.
