## `~` paths expand with the host's own separator on Windows, and `~\proj` expands at all

`expand_path` — what turns the `~/proj` you type into a scheduled task's `working_dir` — glued the home directory to the rest of the path with a forward slash. On macOS and Linux that is the separator, so nothing moved there. On Windows the home directory is native, so `~/proj` came back as the mixed-separator `C:\Users\me/proj`.

That string resolves: Win32 accepts `/`, and the consumers all read it through a path type or canonicalise it. What it costs is text. The expanded value is persisted to `schedules.toml` by `schedule add` and `schedule update`, applied to every loaded task's `working_dir`, shown back to you in the scheduler UI, and carried to the daemon as a fire's `working_dir` or an orchestration cwd — so a stored and displayed path read `C:\Users\me/proj` rather than `C:\Users\me\proj`. It was inconsistent text, not a failed spawn.

The second half was a real non-expansion. `~\proj`, the form a Windows user actually types, matched neither the `~/` tilde test nor the absolute-path test, so it fell through to the relative branch and came back as `C:\Users\me\~\proj` — a literal `~` directory under the home directory. Both tilde separators are now accepted on Windows, and only `/` is on Unix, where `\` is a legal character in a file name and `~\proj` names a directory.

Only the tilde expansion changed. A path typed without a `~` is passed through exactly as typed on both platforms — including a Unix-style `/work/space` on Windows, which is rooted on whatever drive is current. Re-anchoring that is a change to text you wrote rather than to text the deck welded together, so it belongs with native Windows support ([#164](https://github.com/vfarcic/dot-agent-deck/issues/164)) and not here.

Native Windows is not a supported platform yet ([#164](https://github.com/vfarcic/dot-agent-deck/issues/164)), so nothing released reaches this today. Behaviour on macOS and Linux is unchanged.
