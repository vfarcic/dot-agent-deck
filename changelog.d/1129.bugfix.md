## A refused `work-done` or `dispatch` is no longer a silent success

`dot-agent-deck work-done` and `dot-agent-deck dispatch` used to write their line to the daemon's hook socket and exit 0 whatever the daemon then did with it. Since the per-spawn capability gate landed, the daemon can refuse such a message — and the only trace was a `warn!` in `deck.log`. An agent that reported "work done" and a caller that dispatched a unit both saw a clean success on something that went nowhere.

The daemon now acknowledges both verbs on the same connection, and the CLI reports a refusal: non-zero exit, with the daemon's own sentence and a greppable reason code on stderr.

```text
Error: the daemon did not accept this work-done report: refused: this pane was
issued a hook capability token and the message presented none. The usual cause
is that the `dot-agent-deck` binary invoked in this pane is older than the
daemon that spawned it; set DOT_AGENT_DECK_HOOK_PROVENANCE=warn on the daemon
to accept it anyway. [missing_token]
```

The sender this is for is the legitimate one, not the forger. A `dot-agent-deck` binary invoked inside a pane that is *older* than the daemon which spawned it forwards no token and is refused as `missing_token`; an agent that outlived the daemon that started it presents a token the new daemon never minted. Both are ordinary mixed-install conditions, and both used to report success. [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) has the two causes and their fixes.

The acknowledgement says the daemon **accepted** the message, not that the work behind it succeeded: it is written at the gate, before the handler runs, so a `dispatch` still returns as soon as the daemon has taken it rather than waiting out a worktree creation. A daemon that predates the acknowledgement writes nothing back, and the CLI keeps treating that as success — so an older daemon and a newer CLI (and the reverse) behave exactly as they did.
