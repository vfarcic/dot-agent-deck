## Every hand-written workflow references its actions by commit SHA instead of by movable tag

`uses: actions/checkout@v7` resolves a git **tag** when the workflow runs, and a tag is a mutable ref its owner can repoint at any commit — publishers routinely do, to ship patches under a major. So what a reviewer read and what the runner later executed were only guaranteed to be the same code until someone upstream moved the tag. That is not a hypothetical failure mode: the `tj-actions/changed-files` compromise of March 2025 worked exactly this way, retroactively repointing version tags at a malicious commit that every workflow referencing the tag then picked up silently.

`release.yml` is where this mattered most, because there the runner's output is the artifact rather than a verdict. Its `build` job compiles the four CLI binaries users download and run, and its `finalize` job both creates the public release and holds `HOMEBREW_TAP_TOKEN` and `SCOOP_BUCKET_TOKEN` — the one job where a compromised action reaches users and two external package registries at once. `docs-publish.yml` is on the same path for a less obvious reason: `release.yml` calls it with `secrets: inherit`, which forwards *every* repository secret, so its Docker actions run with the release credentials in scope even though nothing in the file names them.

All 66 `uses:` references across the eight hand-written workflows are now accounted for: 63 carry a full commit SHA with the tag in a trailing comment, and the remaining three are local `./.github/workflows/…` references, which GitHub resolves within the calling commit and does not accept a SHA for. 61 lines changed; the two DeterminateSystems pins added earlier for the same reason (#450) were already in this form and were re-verified rather than touched. The trailing `# vX.Y.Z` comment is the form Renovate's `github-actions` manager reads, so the pins stay under the same automated bump policy `renovate.json` already defines — `digest` and `pin` updates sit inside the automerging `GitHub Actions` group, and the `uses-with` hold on toolchain versions is unaffected because no `toolchain:` or `tool:` input changed.

Every SHA was resolved from the upstream repository by two independent API routes that had to agree — the tag ref with annotated tag objects dereferenced to their commit, and an independent server-side resolution of the same tag — then read back out of the written files and re-resolved a third time, with the SHA in the file additionally confirmed to be a real commit in that repository. Four of the sixteen tags turned out to be annotated tag objects rather than lightweight tags (`Swatinem/rust-cache`, `arduino/setup-task`, `softprops/action-gh-release`, `pnpm/action-setup`), which is worth checking rather than assuming: pinning an annotated tag's *own* object SHA produces a ref that looks pinned and is not the commit Actions checks out. The workflows were also parsed before and after and compared structurally, to establish that the ref after `@` is the only thing that moved.

**What this deliberately does not fix.** A commit pin fixes the fetcher, not the fetched, and several of these actions download an executable payload at run time: `arduino/setup-task` resolves `version: 3.x` to whatever the newest 3.x release is when `finalize` runs, `actions/setup-node` and `pnpm/action-setup` resolve `24` and `11` the same way, and `taiki-e/install-action` fetches a prebuilt cargo-nextest. Narrowing those is a behaviour change with its own verification to do, so it stays a separate decision rather than riding along here. The nested layer *is* closed, though, and was checked rather than assumed: thirteen of the sixteen actions are JavaScript actions with no internal `uses:` at all, two of the three composite ones (`dtolnay/rust-toolchain`, `taiki-e/install-action`) reference no other action, and the four internal references in `jetify-com/devbox-install-action` are themselves already SHA-pinned upstream.
