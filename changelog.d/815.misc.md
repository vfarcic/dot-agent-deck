## A devbox shell that resolves Tauri's GTK stack to the host now fails loudly instead of at load time

Issue #771's failure was **loud**: no GTK anywhere, so `cargo clippy --workspace --all-targets` stopped with `The system library 'glib-2.0' required by crate 'glib-sys' was not found`. Issue #780 fixed that by freezing the transitive pkg-config closure into `tauri-deps/flake.nix`. What replaced #771 was a **silent** failure of the same shape, and it was strictly worse: when `pkg-config` answers from the host's `/usr/lib/pkgconfig` instead of the Nix store, every step that reports anything reports success — `pkg-config --exists gtk+-3.0` passes, `--modversion` prints a real version, the compile links clean, clippy goes green — and the first thing to notice is `cargo test-fast` refusing to start, tens of minutes later, with `libgdk-3.so.0: cannot open shared object file: No such file or directory`, naming a library nobody configured.

`scripts/devbox-check-gtk.sh` now asserts, for each of the 13 modules, that the resolved **`libdir` is under `/nix/store`** rather than merely that the module exists. That is the exact value the wrong answer turns into: a `-sys` build script emits `cargo:rustc-link-search=native=<libdir>`, and Nix's `ld` wrapper mints a matching `-rpath` for every `-L` under `/nix/store` and for no other — so a `/usr/lib/x86_64-linux-gnu` answer is the precise moment the binary loses its RUNPATH, which makes it the right moment to fail. `scripts/devbox-smoke.sh` invokes the script and CI's `devbox` job runs that, the only job that can observe this regress since every other one installs the compile set with apt. `libdir` rather than `prefix` because all 13 define it and `libxdo` reports an empty `prefix`.

**The cause was not what #815 was filed against, and the difference is worth recording.** The empty `PKG_CONFIG_PATH` that the issue traced is real but inert. Nix's pkg-config **wrapper** — which is what the pinned `pkg-config@0.29.2` puts on PATH — discards the caller's `PKG_CONFIG_PATH` outright and re-execs the real binary with that variable replaced by a role-mangled one its own setup hook builds from the profile. Measured with a hand-written `.pc` file: reachable through `PKG_CONFIG_PATH_FOR_TARGET`, invisible through `PKG_CONFIG_PATH`. So `devbox.json`'s `env` block never affected resolution in either direction, and the load-bearing half of #780 was always the `path:tauri-deps#tauri-deps` package entry. Of the three candidate causes the issue listed, it was the third: **the outer environment**. `devbox run` reuses an already-computed devbox environment whenever one is inherited — `DEVBOX_PATH_STACK` is the trigger, isolated by stripping the `DEVBOX_*` variables one at a time — and then neither re-installs the profile nor re-applies the `env` block, so a shell entered before `devbox.json` last changed keeps a profile with no `tauri-deps` and no Nix `pkg-config`, and the host's `pkgconf` answers instead. The other two candidates are refuted: a clean `devbox run` applies the `env` block exactly as `devbox shell` does, and `$PWD` expands correctly, `devbox run` having already changed to the project root so even a subdirectory invocation is right.

That matters beyond this bug, because nested `devbox run` is this repository's normal case rather than an exotic one — every dispatched agent runs its commands inside a devbox shell. The failure message therefore names the stale environment as the most likely cause and gives the remedy: leave every nested devbox shell until `DEVBOX_PATH_STACK` is unset, then `devbox install` and re-enter.

`xtask/linkage-check/src/devbox_gtk_origin.rs` drives the script under a stubbed `pkg-config` in the fast tier — five tests, ~0.05s — because the property is a runtime assertion and nothing else, the same class CLAUDE.md rule 5 records for `clean_tmp.rs` and `junit_strip.rs`. It pins that a store `libdir` passes, that `/usr/lib/x86_64-linux-gnu` fails and says which module and what it answered, that an empty `libdir` fails, that `/nix/store` is matched as a prefix and not as a substring, and that `devbox-smoke.sh` still invokes the script at all. Verified by mutation: weakening the pattern back to a presence check turns three of the five red. The correction is also written into [the desktop GUI developer doc](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/desktop-gui.md) and `tauri-deps/flake.nix`, both of which previously described the `env` block as the mechanism.
