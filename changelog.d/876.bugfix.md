## A partial daemon write into a pane is now erased back out of the input box instead of being left there

When the deck's daemon writes a prompt into an agent's pane and the write stops part-way — some bytes accepted, then the PTY refuses the rest, or the whole prompt accepted and the Enter that submits it refused — those bytes were left sitting in that pane's input box, un-submitted, and nothing anywhere removed them. [#715](https://github.com/vfarcic/dot-agent-deck/issues/715) stopped them being silently merged into a later turn by remembering the payload and refusing a byte-identical repeat, but remembering is not clearing: that memory expires after 60 seconds and the bytes did not expire at all. At T+61 s the next identical write was admitted and submitted the leftovers together with whatever you had typed in the meantime, as one message you never sent. Most reachable on a delegation, where the worker's task pointer is deliberately the same one-line sentence on every hand-off and so is identical by construction.

The daemon now takes those bytes straight back out. Immediately after the failed write, still holding the same pane's writer, it sends exactly one Backspace for every byte that landed — so the fragment disappears and anything you had typed underneath it is left untouched, character for character. It is deliberately not a kill-line (`Ctrl+U`): a kill-line's meaning genuinely varies across the agent TUIs this project drives, and where it does work it takes the whole line, including your draft. An exact count of erases cannot take more than it put there. Holding the writer across both steps is what makes that a property of the lock rather than a guess — no keystroke of yours can reach the pane between the two, so the erases can only ever be undoing our own bytes.

Because the box is then genuinely clean, the write leaves no payload record, and the next delegation into that worker is admitted normally rather than refused for a minute and then admitted onto the wreckage anyway.

**It only erases what it can prove it can erase exactly, and says so when it cannot.** Every byte that landed must be printable ASCII — that is what makes "one byte written" provably "one erase" for any editor, char-stepping or grapheme-aware, and it guarantees the pane's escape parser and UTF-8 decoder are both in their ground state at the cut, so a partial `ESC[200~` paste marker or a half-written multi-byte character never gets erases fired at it. The burst is capped at 1024. And the erases have to land: the commonest cause of a partial write is a PTY whose agent has gone, where nothing can be written at all. In each of those cases the pre-existing behaviour is kept — the payload record stands and a byte-identical repeat is refused — and the pane's card now carries a notice saying the input box may hold a partial prompt above your own text, because clearing that mixture safely is something only you can do. The daemon's own silent-worker report is one such case by construction: it opens with a `⚠`, so it is never erased, and `scheduler/idle-worker/018` pins exactly that.

Status notices are deliberately untouched. Their bytes are *meant* to stay visible in the input box, and they never created the record that expires, so there was nothing here to fix for them.

Nothing about the TUI↔daemon protocol moved: no wire shape changed, no field changed meaning, and `PROTOCOL_VERSION` is untouched. A partial write is still reported as `ambiguous` to every caller and to the wire, because what stays genuinely unknown is what the agent's editor did with the bytes while they were briefly there — not whether they are still sitting in the box.
