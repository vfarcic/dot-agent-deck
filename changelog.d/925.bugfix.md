## A frame from one pane can no longer take over another pane's card

A hook frame carrying session key `K` while naming pane **B** used to be resolved through `K` at every seam in `apply_event` — the reuse guard, the same-key identity refresh, the `SessionEnd` restore, and finally the `entry()` that lands the frame's status on a card. Where `K` belonged to a card on pane **A**, all four reached pane A's card, and the unconditional `session.pane_id` refresh then dragged it onto pane B. Pane A was left with **no card at all**, and pane B's card carried pane A's identity, history and start time under pane B's status. In the terminal case it was worse: a `SessionEnd` naming pane B deleted pane A's live card and restored a placeholder in its place.

**The collision is reachable from a real producer, which the issue had left open as unverified.** On the hook path `session_id` and `pane_id` have independent origins — `crate::hook`'s builders take the session id from the **agent's own payload** and read `pane_id` / `agent_id` from the environment — so they can disagree. Claude Code's `--resume` and `--continue` reuse the original session id (that is exactly what its `--fork-session` flag opts out of, and it was measured rather than assumed: two print-mode calls, the second resuming the first, reported the same `session_id`). So resuming pane A's conversation in pane B makes pane B's hooks report under pane A's key while pane B is genuinely the pane they own — and `-c` picks the most recent conversation in the working directory, which two panes of one orchestration routinely share. Pi's `agent-event` cannot produce it: it derives both fields from `DOT_AGENT_DECK_PANE_ID`. What has **not** been reproduced end to end is the full two-pane deck run; the producer is demonstrated at the CLI and the ingest path is demonstrated by reading it.

**The fix re-keys rather than refuses.** Such a frame is not forged — admission has already confirmed the daemon owns pane B for that agent, and `owns_pane_event`'s own comment is explicit that owning a pane was never evidence about which generation a report belongs to, so dropping the frame would discard pane B's real status. Only the key is ambiguous, so the key is what gets disambiguated: before any other seam runs, a frame whose key resolves to a session on a different pane has that key qualified by the pane it actually named. Usually the derived key is transient — the reuse guard immediately adopts pane B's existing card whenever one carries that agent — and a distinct card is minted only where pane B genuinely has none. Qualifying **repeats** until the key stops resolving to another pane's session, because one pass is not a fixed point: a third pane holding a card under the derived spelling itself would otherwise catch the frame and reproduce the same bug one level down, and session ids arrive verbatim on producer payloads with no reserved format to rule that out. The repeat is bounded by the session map's own size, and cannot spin: each step prepends a strictly longer prefix, so it consumes a distinct member of a finite map that the loop never writes to.

**Freezing the pane pointer would have looked like a fix and been worse.** That refresh is one of nine fields written unconditionally on the surviving card (`display_name`, `last_activity`, `agent_type`, `last_user_prompt`, `first_prompts`, `status`, `active_tool`, `tool_count`, and the `recent_events` journal), so pinning the pointer alone yields a card *claiming* pane A while carrying pane B's status and tools — and `build_pane_status` keys by `pane_id`, so pane A would then report pane B's status.

This does not re-open issue #398, whose failure was two cards on **one** pane. Here the two cards sit on different panes, so one-card-per-pane is preserved — restored, in fact, since the relocation left pane A with none.

Neither a `PROTOCOL_VERSION` bump nor a compatibility break. The session key is a `HashMap` key in the daemon's in-memory `AppState`, and the protocol structs that carry a card's state were read for it rather than assumed: `SessionSnapshot` carries no session id and no pane id, `AgentRecord` carries no session id, and neither does `HydratedPane`. The one session id that crosses the attach wire is the client's `expected_session_id`, which is compared against `pane_hook_session` — populated from the **pre-remap** id captured at the top of `apply_event`, and untouched here. So no message changes shape, no field changes meaning, and an old and a new build exchange identical bytes.

Regression tests `status/supersede/012` (the status frame), `/013` (the terminal frame) and `/015` (a stacked collision on the derived key), each verified to fail against the source it fixes, plus `status/supersede/014` pinning the carve-out the guard must not swallow — a card created by a pane-less event still learns its pane from a later frame.
