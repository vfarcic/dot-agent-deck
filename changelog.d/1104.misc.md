## `agent_lifetime_bound`'s two tests stop reading a record that is not written yet

Both tests in `tests/agent_lifetime_bound.rs` install a shell stand-in that records one environment variable to a file and then blocks, and both wait for it with `wait_until(record.is_file())`. A plain `> "$RECORD"` makes that predicate true at the shell's `open(2)` — **before** `printf` has written a byte — so a poll landing in that window read `""`, trimmed it to `""`, and fired the assertion against an empty string. The message then blamed the product for losing a variable that had in fact never been read: `an unwrapped agent spawned through the in-process registry carries DOT_AGENT_DECK_TEST_LIFETIME_TAG="", so the reaper armed for its pane has no way to find a descendant that setsid's out of the pane's process group`.

`an_unwrapped_agent_spawn_carries_a_lifetime_tag` failed **2 of 14** `cargo test-fast` runs this way on a 16-core box, always in **~0.057 s** — which is the tell, because the test's own wait is 20 s and had plainly not elapsed. It is the unwrapped test that loses the race because nothing sits in front of its stand-in; the wrapped sibling has `wrap`'s startup between the spawn and the redirection, which usually carries the first poll clear of the window. The race is identical in both.

**The fix makes the observation honest rather than making the wait longer.** Both stand-ins now write to `<record>.part` and `mv` it into place through one shared `record_var_then_block` helper. `mv` within a directory is `rename(2)`, which is atomic, so the record is either absent or complete and `is_file()` means exactly what the wait reads it to mean — rather than being a signal that fires one syscall early. Polling for non-emptiness instead would have papered over a predicate that was simply not the condition the test cared about. Same correction `delegate/034` took in `364dc860`, for the same reason.

Verified in both directions rather than by re-running until green. Forcing the window on the **old** code (`: > "$RECORD"; sleep 0.3; printf … >> "$RECORD"`) reproduces the observed failure exactly — `…TAG=""` at the same assertion, same fast exit. Forcing the equivalent window on the **new** code (a 0.3 s sleep between writing `.part` and renaming it) leaves both tests passing, at 0.422 s against a 0.107 s baseline, which is them correctly waiting the window out. The tier then ran **9 consecutive green** `cargo test-fast` runs, against 2 failures in the 14 before.

Both tests' doc comments claimed the approach "cannot flake" — an absolute about an implementation that the measurement above falsifies (CLAUDE.md rule 17). They now say what is actually true: the assertion does not depend on how long anything takes, but it did depend on the record being complete when the wait first saw it.
