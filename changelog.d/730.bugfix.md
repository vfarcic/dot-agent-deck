## Your own hook handlers survive, and a second valid deck install is no longer repointed

Codex's `hooks.json` and Devin's `config.json` are shared files: your hooks live in them next to the deck's. Two things the deck did to them were wrong, and both fired on the silent install that runs at every startup rather than only when you asked for one.

**A handler of yours sharing a rule object with the deck's was deleted with it.** A rule's `hooks` array is a list of commands sharing one matcher, so putting your own audit command in the same rule as the deck's is a normal thing to do — and the deck removed the whole rule to refresh its own command, taking yours with it and saying nothing. Install and uninstall now remove only the deck's own command, leaving your handlers and the rule's `matcher` exactly as you wrote them. This is what Claude Code's installer has done since the same defect was fixed there; Codex and Devin now match it. A command of yours that merely *mentions* `dot-agent-deck` was already safe and still is.

**A deck hook pointing at a second, still-valid install is no longer repointed on every launch.** The rule is "repair only when the pin is one the deck could not have written, never merely because it differs from what I would write" — Claude Code and OpenCode already kept it, Codex and Devin did not. If you run the deck from two installs (two checkouts, or an installed deck plus a checkout), each resolves a *different* durable path, so the pin never settled: it flapped between them on every launch, each one undoing the last. Now a deck pin naming a usable binary is left alone, and only a pin the deck cannot use is repaired — one whose file is missing, one that is a bare name or a relative path (a bare name resolves through the agent's own `$PATH` and a relative one against whatever directory it happens to be in, so neither names a fixed binary), one that is not an executable file, or one inside a `target/debug` or `target/release` build directory. Two of those are worth knowing if you pin the deck by hand: a bare `dot-agent-deck`, or a `…/target/debug/dot-agent-deck`, is replaced even when that file is right there and runs — those are the two shapes that stop working later without warning. The same rule applies under an event the deck has stopped installing: the list of events the deck writes is not the list the agent runs, so a deck-signature command under one of those is not stale, and the install clears only what it may clear anywhere else — its own command, and a pin it cannot use. Note what "left alone" means, because it is not "adopted": the existing rule stays and the launching deck's rule is added **beside** it, so that agent fires two deck hooks per event — one per install — until you remove the one you no longer want.

**Codex hook trust is narrower.** Codex only runs hooks it trusts, and the deck records trust for its own. It used to identify those by the command's `hook --agent codex` ending alone — a convention anything able to write into your `hooks.json` can also end a command with, which is not a good enough reason to hand it Codex's permission to run. The deck now trusts only entries whose command is byte-exactly the one it just installed for the durable binary it validated, and trusts nothing at all when no durable path resolves. Uninstall deliberately stays wider so it still clears a trust record another deck install left behind — which means a hook the deck did not write, whose command nevertheless ends in `hook --agent codex` and which lives in the deck's own `hooks.json`, still has its command and its trust record removed by `hooks uninstall --agent codex`. That is unchanged from before and it is the safe direction for a revocation, but it is worth knowing rather than assuming otherwise.

`dot-agent-deck hooks install --agent codex` now also says what trust it recorded, instead of exiting successfully and silently: how many entries were trusted, or, when none were, which of the two reasons applies — Codex had no deck hook to trust at all, or it reported deck hooks whose command is not the one this install wrote (in which case events fall back to the coarser stdout classification and the deck says so rather than leaving you to notice). Setting `DOT_AGENT_DECK_LOG` now also gets you this command's own log lines, which it never produced before.

Nothing about the TUI-to-daemon protocol moved: these are edits to third-party agent config files, so `PROTOCOL_VERSION` is unchanged. See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for what the repair does and does not touch.
