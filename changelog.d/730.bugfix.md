## Your own hook handlers survive, and a second valid deck install is no longer repointed

Codex's `hooks.json` and Devin's `config.json` are shared files: your hooks live in them next to the deck's. Two things the deck did to them were wrong, and both fired on the silent install that runs at every startup rather than only when you asked for one.

**A handler of yours sharing a rule object with the deck's was deleted with it.** A rule's `hooks` array is a list of commands sharing one matcher, so putting your own audit command in the same rule as the deck's is a normal thing to do — and the deck removed the whole rule to refresh its own command, taking yours with it and saying nothing. Install and uninstall now remove only the deck's own command, leaving your handlers and the rule's `matcher` exactly as you wrote them. This is what Claude Code's installer has done since the same defect was fixed there; Codex and Devin now match it. A command of yours that merely *mentions* `dot-agent-deck` was already safe and still is.

**A deck hook pointing at a second, still-valid install is no longer repointed on every launch.** The rule is "repair only when the target is missing, never merely because it differs from what I would write" — Claude Code and OpenCode already kept it, Codex and Devin did not. If you run the deck from two installs (two checkouts, or an installed deck plus a checkout), each resolves a *different* durable path, so the pin never settled: it flapped between them on every launch, each one undoing the last. Now a deck pin whose binary still exists is left alone, and only a pin whose binary is positively gone is repaired. Note what "left alone" means, because it is not "adopted": the existing rule stays and the launching deck's rule is added **beside** it, so that agent fires two deck hooks per event — one per install — until you remove the one you no longer want.

**Codex hook trust is narrower.** Codex only runs hooks it trusts, and the deck records trust for its own. It used to identify those by the command's `hook --agent codex` ending alone — a convention anything able to write into your `hooks.json` can also end a command with, which is not a good enough reason to hand it Codex's permission to run. The deck now trusts only entries whose command is byte-exactly the one it just installed for the durable binary it validated, and trusts nothing at all when no durable path resolves. Uninstall deliberately stays wider so it still clears a trust record another deck install left behind. Hooks the deck did not author are unaffected, as before.

Nothing about the TUI-to-daemon protocol moved: these are edits to third-party agent config files, so `PROTOCOL_VERSION` is unchanged. See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for what the repair does and does not touch.
