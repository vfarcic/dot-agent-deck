## Send agent-run telemetry to an OpenTelemetry backend

The deck can now send a record of every agent run to an OpenTelemetry backend of your choice, such as Honeycomb's free plan: which agent ran in which pane, its role and orchestration, how long it spent in each status, when you typed into it, what kinds of shell commands it ran and how long they took (`cargo test` locally or in an RWX sandbox, for example), which pull request it opened and how long that pull request's CI took, and how the run ended. Over time that answers questions such as which agent finishes a kind of task with the least help from you, whether a change to your `CLAUDE.md` or skills helped, or how much time goes to tests and CI. Several machines can send to one backend and are told apart by their host name.

It is off unless you set an endpoint with the standard variables, for example `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS`, in the environment the daemon starts with; without one, nothing is sent and nothing changes. It works the same from the TUI and the desktop app. The deck sends metadata only: never prompts, file contents, agent output, tool-call arguments, your API key or other environment values, pane titles, branch names or paths. Of a shell command it sends only where it ran, the program's name and its first argument, each only when it looks like a plain command word, and never the first argument of programs whose arguments are usually text, files, hosts or credentials, such as `echo`, `cat`, `grep`, `curl`, `ssh` or `base64`. The only values it sends exactly as you wrote them are your own `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES`, so keep secrets out of those. It sends over HTTP to a backend whose certificate your system trusts, retries a busy or unreachable backend until the export timeout, and does not follow redirects; client certificates (mutual TLS) are not supported, and the page shows how to reach such a backend through a local OpenTelemetry Collector.

The agents the deck starts get the same configuration with the run's id added, so an agent's own telemetry can be joined to the deck's run in the backend. Every supported agent sends its own telemetry to the same backend with no setup from you when the deck can find the agent in its command (for Codex and Devin: run directly, through `env` or `devbox run`, or after a wrapper's `--`), and the deck never turns on an agent's recording of prompts, responses, tool arguments or tool output: Claude Code's metrics and events are switched on through its variables, OpenCode sends its logs and traces, Codex gets its traces and metrics switched on for the run (its logs stay off, because they carry tool arguments and output; keep credentials out of the endpoint URL, since it goes on Codex's command line), Devin is started with a per-run copy of its configuration that turns on its events and metrics with prompt and tool logging off (not yet confirmed against a signed-in Devin), and the deck's Pi extension sends Pi's model, token, cost and tool-name usage. A setting you made yourself is left alone, and the page says how to keep each agent's telemetry off. The model, exit code, issue and invoking skill of a run are not sent yet.

See [Telemetry](https://agent-deck.devopstoolkit.ai/docs/telemetry.md).
