## The two `shell_activity_monitor` tests that needed a 2-second window now wait for a child that is still there

`daemon::hook_ingestion_tests::shell_activity_monitor_reflects_a_real_detached_shell_command` and `..._stamps_the_owning_agent_across_a_session_rollover` failed **together** in 1 of 10 `cargo test-fast` runs on a 16-core box and never separately, passing in isolation and in the nine tier runs either side. Issue #1159 was filed with that measurement and with no diagnosis at all — no failure message captured, no instrumented re-run — so the first deliverable here was a captured failure rather than a fix.

**Captured deterministically, and the product was right.** Both tests are the only two in a family of seven that assert against a *real* spawned shell rather than an injected sampler; the other five are explicitly about the unusable-sample paths (`…discards_a_sample_that_answers_too_late_to_trust`, `…leaves_statuses_alone_when_the_sample_times_out`, `…backs_off_after_repeated_unusable_samples`). So a sample the monitor cannot use is a **modelled outcome with three tests of its own** — and these two typed a `sleep 2` into the pane and then asserted the resulting status inside 3 s (and the broadcast inside 5 s). That is a two-second window the signal had to be caught inside, and it is **shorter than the silence this monitor is designed to produce**: `SAMPLE_TIMEOUT` lets one tick wait 2 s for a sample, `MAX_TABLE_AGE` discards an answer older than 3 s, and `SamplingHealth` then holds the next sample off for up to `BACKOFF_MAX` = 8 s. A single slow sample consumes the whole stimulus.

Reproduced by injecting exactly that one modelled outcome into the real sampler — a first `process_table_async` answer delayed 3.5 s, nothing else changed — against byte-identical copies of both tests:

```
FAIL [   3.162s] proof_1159_one_overrunning_sample_kills_the_two_second_window
  PROOF-1159 after 3035ms status=Idle samples_started=1
  assertion `left == right` failed: the monitor must promote the session to Working
  while the detached child runs, with zero agent-emitted events involved
    left: Idle   right: Working

FAIL [   5.177s] proof_1159_same_wedge_kills_the_stamping_test_too
  PROOF2-1159 after 5133ms saw_busy=false samples_started=2
```

Against the reported `FAIL [ 3.076s]` and `FAIL [ 5.089s]`. `samples_started=1` is the whole story: across the 3 s window the monitor started exactly one sample, because the retained-not-abandoned future issue #429 introduced was still in flight, so the pane was never classified at all while the child lived.

**That also answers the clue the issue flagged — why they failed together and never singly.** It is not two independent deadlines. It is one cause whose duration exceeds *both* windows at once: one degraded sampling episode is longer than 2 s, so it takes out the 3 s test and the 5 s test in the same run, while the five siblings inject their own sampler and a wedged `ps` cannot reach them. #862 measured a real 19–20 s `ps` under a build storm, which is 10x either window.

**So the child now lives until the test kills it**, rather than the test racing a `sleep` to expire. The rising edge waits on a condition that stays true, and the falling edge is made true by construction — the test ends the child instead of hoping the `sleep` ended in time. Same shape as `shell_activity_004`'s ready-marker gate (PR #390), which fixed this class in the pane-primitive layer, and as #1148's `delegate_034`: make the state real, do not widen the wait. Catalog entry `status/shell-activity/008` had already written the principle down — a wall-clock threshold on this signal "would be a flake generator on a loaded machine (PRD #386's Test Plan says so about M5 explicitly)" — and these two tests were the place it had not been applied.

A shared `DetachedPaneChild` carries the stimulus for both tests and the new one below. The topology is PRD #386's and untouched: an interactive `/bin/sh` makes each foreground job its own process-group leader and `setsid(2)` is `EPERM` for a group leader, so `python3` detaches a *child* rather than itself, and the parent's `waitpid` keeps the pane occupied. What changed is the child's lifetime and that it reports its pid back — written with `os.write` on a raw descriptor and `os.rename`d into place, so a reader cannot observe the path at `open(2)` before the digits are in it, which is the unrelated TOCTOU the issue's own report separates itself from (`an_unwrapped_agent_spawn_carries_a_lifetime_tag`, #1104). The child is ended through the product's own `platform::proc::force_kill_pid`, which refuses pid 0 and anything resolving to a non-positive `pid_t`, so it cannot broadcast to a process group; `Drop` ends it too, so a panic mid-test strands nothing, and a 120 s backstop bounds the one path that skips both — a `SIGKILL`ed test process. Both pid-file paths are checked for the characters that would rewrite the generated command rather than name a file, so a `TMPDIR` containing a quote, `$` or a backtick fails in 0.087 s with a message naming the path instead of timing out on a signal that could never arrive.

**The wait bounds are derived from the monitor's own constants rather than raised until green.** `SHELL_ACTIVITY_SIGNAL_BUDGET` is 30 s: one degraded episode can legitimately swallow `MAX_TABLE_AGE` plus a `BACKOFF_MAX` hold-off, so ~11 s of silence is *correct behaviour* and any smaller bound asserts against the product's own contract; 30 s is ~2.7x that and half of nextest's 60 s slow-timeout period, so a genuinely dead signal still reports inside one slow window with its diagnostics intact. It bounds "the signal never arrived at all" and is paid only on the failure path — the child outlives it, so it is no longer a window anything has to be caught inside.

**Two failures that used to be one are now told apart.** Waiting for the pid file is a separate step from waiting for the status, so a shell that never ran the command fails on its own assertion naming the pane's own PTY output, instead of silently consuming the signal's budget and reading like a monitor defect. #1159 exists because nothing in the original failure said which of those had happened.

**The mechanism is now a test rather than a comment.** `shell_activity_monitor_reports_a_real_detached_child_after_an_unusable_sample` runs the real monitor with the real sampler and only its first answer delayed 3.5 s — overrunning `SAMPLE_TIMEOUT`, then landing past `MAX_TABLE_AGE` so the retained table is correctly discarded and a hold-off is armed — and asserts the session still reaches `Working`. A degraded episode may **delay** this signal; it must not lose it once the machine answers again. That is the property the two rewritten tests depend on, and it fails if the recovery path ever stops working.

**Verified under load, and the pass rate is the claim rather than a green run.** **80 consecutive passes of each of the three tests, zero failures**, on a 16-core box under a deliberate storm — 16 CPU spinners, 4 fork-storm loops, 2 continuous `ps -A` loops and 4 `dd conv=fsync` writers, on top of whatever else the shared box was doing — at load average 24–54, with the tier's own wall clock stretched from ~40 s idle to 51–92 s. Twenty of those are whole `cargo test-fast` runs (3300 tests each, 19 green; the one red is an unrelated `idle_worker_008_closed_orchestrator_pane_id_reuse_receives_nothing`, which passes in isolation and is reported separately rather than folded in here) and sixty are repetitions of the three tests alone. The pre-change baseline this replaces was 1 failure in 10 tier runs. CPU load alone never reproduced the original failure — 20 pair runs and 10 tier runs on a box at load 13–40 were all green, and the transition timings stayed at 717–1771 ms against the old 3000 ms bound — which is why the mechanism was established by injection instead of by repetition. The relevant contrast is the deterministic one: the injected wedge that failed both tests before this change is now a test that passes.

**No production code changed.** Every edit is inside `#[cfg(all(test, unix))] mod hook_ingestion_tests`; the daemon, the TUI↔daemon protocol, orchestration and hooks are untouched, so `PROTOCOL_VERSION` does not move, no `CONTRACT_BREAKS` entry is owed, and CLAUDE.md rule 12's cross-version manual test is not triggered.
