## A Flaky Test Precondition Stops Blaming the Wrong Thing

`orchestration/delegate/022` is the only coverage of issue #606 — a `clear = true` delegate landing while its worker's pane is mid-close, which used to kill the role for the rest of the session. It intermittently failed on its own *precondition* rather than on that subject, at a measured ~7% across two independent sightings, reporting that "the close never entered its grace window".

It was not the window. The precondition polled `pane_close_in_flight` every 5 ms and treated a finished `StopAgent` request as proof that no window had opened — which is exactly what a finished request cannot prove, because an attempt that never reached the daemon is silent about whether the pane would have closed. Both reported failures carried `stop_agent finished = true` together with `stand-in still live = true`, and those two are only consistent with the handler never reaching `close_agent`: its first act is removing the registry entry, so a close that had begun could not have left the stand-in live. The request's own error was discarded by a `let _ = closing.await`, so nothing anywhere named the cause. Injecting an unreachable daemon reproduces the reported failure text character for character.

The precondition also now waits for the pane's registry entry to be **gone**, not merely for the close to have begun. `begin_pane_close` — which is what resolves the signal — runs before `close_agent`, and `close_agent` is what removes that entry, so a delegate aimed at the gap between them finds a record and takes the ordinary respawn path rather than the `NotFound` recreation path #606 is about. That path removes the record itself and only then calls `spawn_agent`, which refuses a pane still held for cleanup — an error the recovery returns untouched, since only `NotFound` routes to it. The delegate fails, no replacement appears, and the test reports #606's own symptom for a scenario it never reached. Reproduced deterministically by taking the hold and the closing mark without the close: the delegate left the pane with no agent and destroyed its record on the way. The predecessor's gap was wider still — it returned on `pane_close_in_flight`, true a step earlier again.

The precondition is now **observed rather than sampled for**. It takes the registry's own `pane_close_signal` receiver *before* issuing the request, so the transition cannot happen unwitnessed however narrow it becomes — `begin_pane_close` resolves it by dropping the sender, and a resolved `oneshot` stays resolved. A request that returns before the close begins is treated as inconclusive and retried up to three times, each attempt first re-checking that the stand-in is still live and still owns its pane, so a genuine defect still fails rather than being retried at. When every attempt fails, the panic now carries each one's actual error.

The in-process daemon harness also waits for its **attach** socket before handing the address out. It gated readiness on the hook socket alone, while `run_daemon_with` binds the attach listener some way further down, so `spawn_inprocess_daemon` could return an address that was not yet connectable. Measured at microseconds on a loaded 16-core box, so this is not offered as the cause of the failures above — it is the same shape as the cause, and one of its two callers had hand-rolled the wait while the other had not.

No production code changed, and the test still fails when the property it guards is broken: with issue #606's recovery removed, it fails on its subject assertion with the pane dead for the session, as it should.

While confirming that, the same test surfaced a separate, pre-existing failure with the same text but a different cause: when a close outruns `PANE_CLOSE_SETTLE_TIMEOUT`, the `clear = true` recovery gives up and the role is lost for the session anyway. That is filed as [#1114](https://github.com/vfarcic/dot-agent-deck/issues/1114), together with the wider entry path above, and neither is addressed here; the assertion now reports `close still in flight` so the two verdicts can be told apart without repeating the investigation.
