## A missing documentation-site image now fails the build instead of 404ing in the browser

A reference to a file under `site/static/` that does not exist **builds clean**. Docusaurus does not resolve an image path at build time — it is a string that reaches the browser verbatim — so `onBrokenLinks: 'throw'` never sees it, the page ships, and the browser 404s. Nothing else looks at it either: the path is a string, so no compiler, no bundler and no link checker reads it.

That bit twice inside one pull request (#1155). One worker re-encoded the images to WebP and deleted `busy-deck.png` while another had just wired a landing-page row to that exact path — green build, broken image, caught only by loading the page. And `docs/orchestration.md` carried a raw `<img>` tag whose `src` MDX leaves alone, so the built page kept the literal relative path and the browser resolved it against the page URL as a directory the site never emits; it had been 404ing on the published site for months, found only because someone was reading that page for another reason.

A new `linkage-check` rule (16) resolves every `/img/...` and `./img/...` reference under `docs/` and `site/src/` against `site/static/img/` and fails the build on a miss. `docs/img` is a symlink to `../site/static/img`, so the two spellings end at the same bytes by two routes — Docusaurus serves the site-absolute one out of `site/static/`, and MDX resolves the relative one as a file reference next to the page — which is why one resolution target settles both. Nothing in the rule reads the symlink, which is also what keeps it working on a Windows checkout, where git may materialise a symlink as a text file holding its target.

**The scan is over text rather than over any one syntax**, deliberately: the three instances above arrived as a Markdown image, a JavaScript string in `site/src/data/landing-content.js`, and a raw HTML `<img>` — and the raw tag is precisely the form Markdown-aware tooling skips. A reference is matched wherever it appears, with a known image extension on the end, in every UTF-8 file under those two trees. What it deliberately does not resolve: absolute and protocol-relative URLs that happen to contain the same path segment (the delimiter the match requires on its left is what excludes them — in a URL that position holds the tail of the host), and the bare `img/...` and `../img/...` spellings, which nothing in either tree uses and which would widen what a repo-relative path written as *prose* can trip. The rule also refuses to pass vacuously: an absent `site/static/img/`, or a scan that matched no reference at all while that directory holds images, is itself a finding, because the failure mode of a text rule is that the text got reworded. An exception is declared on the line that takes it with `linkage-check:allow-missing-image` — in Markdown, as a trailing same-line HTML comment, which renders as nothing.

The raw-`<img>` instance the issue cites had already been converted to Markdown image syntax in `18041dc`, the same pull request the defect was found in; the rule covers that form regardless, since it is the one nothing else sees.

Fifteen tests plant every shape against synthetic trees — both spellings resolving and both missing, a raw tag, an uppercase extension, an absolute URL, a repo-relative path in prose, a non-image extension, a nested path, the line marker and its per-line scope, a missing image root, a symlinked directory the walk must not follow, and a whole-tree walk — and one asserts the checked-in `docs/` and `site/src/` resolve, so "no findings" means something.
