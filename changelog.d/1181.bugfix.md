## An ambient `GIT_DIR` no longer redirects worktree creation, worktree removal and branch deletion into a repository the deck never chose

`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` and their siblings outrank **both** `-C <dir>` and a command's `current_dir`. Every production `git` in the dispatch and reclaim paths passed one of those and cleared none of these, so a deck running with one of them set operated on whatever repository the variable named — and git reported success.

Measured on the exact command shapes, against two throwaway repositories: `GIT_DIR=<decoy> git -C <clone> worktree add <wt> -b <branch>` put the branch **and** the worktree in the decoy while the clone stayed untouched; `git worktree list --porcelain` with cwd `<clone>` enumerated the **decoy's** worktrees — that is the probe `worktree reclaim` makes its removal decision from; and `git worktree remove <path>` with cwd `<clone>` removed a decoy worktree from its metadata and **deleted it from disk**. The cleanliness gate that is supposed to protect an unexpectedly dirty tree was steered by the same variable, so it could be satisfied by one repository while the removal landed in another.

**How reachable this is, stated plainly.** It needs a deck that inherited one of those variables, which a daemon lazy-spawned from inside a `rebase --exec`, a pre-commit hook or a `bisect run` does — reachable rather than routine, and not observed in the wild. What *was* observed is the mechanism running at full strength inside this repository's own test suite: with a decoy repository named by `GIT_DIR`/`GIT_WORK_TREE`, a fast-tier run left **16 branches and 14 worktrees** in the decoy, every one of them created by production code.

`src/git_env.rs` is now the single place the ambient location environment is switched off, and every `git` the crate spawns is built by one of its constructors — `git_at` for the synchronous sites, `git_async` behind `run_git_status` / `run_git_capture` for the `tokio` ones. `src/worktree_owner.rs` already did this for its own module and its list was the one that moved; the fix is that list reaching the other four modules rather than a second copy of it, since a second copy drifts and a missing variable is silent data loss rather than a compile error. `GIT_CEILING_DIRECTORIES` is still deliberately left alone: it can only narrow git's upward walk, so an ambient one can at worst turn a call into git's own "not a git repository" error — never into a correct-looking action on the wrong repository — and honouring it leaves an operator's guard against walking a slow network mount in place.

Guarded in both directions. A re-exec'd regression test drives the real production entry points — `create_worktree`, the reclaim enumeration, the cleanliness gate, `branch -D`, and both removal paths — against a clone while every location variable names a decoy, with a control proving an un-neutralized `git` really does resolve the decoy from there, so the test cannot pass vacuously. Against the unfixed code it reports the decoy gaining `agent/ambient-probe`. And `cargo xtask linkage-check` gained rule 13, which fails the build on a `git` program literal anywhere in the crate's production sources outside `git_env` — the tripwire for the fourteenth call site, which no runtime test can be. It catches the multi-line `run_status(\n "git",\n …)` form that a grep for the call shape misses, and which an earlier hand enumeration of this class did miss.
