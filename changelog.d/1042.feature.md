## The desktop deck has one input per agent, and it says when that input cannot reach anything

Every agent tile in the desktop app used to carry a `MESSAGE <ROLE>` composer stacked directly on top of the agent's own terminal — two input fields, one above the other, with nothing on screen saying which to use. The composer was always the weaker of the two: an agent CLI's input is that CLI's whole interactive surface (`/` skills, `!` shell, `@` path completion, history, multi-line composition), and a parallel text box replicates none of it. The TUI has never had a second input field. The composer is now gone from the tile and from the Reader overlay, which leaves the Reader as the read-only viewer its construction always described.

**What the composer did that mattered has moved onto the terminal, where people actually type.** The composer was the only surface that reported *delivery*: its Send button went through an identity-bound guarded write that returns a named verdict, so it could tell a message that landed from one that was swallowed. The terminal now carries that honesty as a state on the pane rather than as a receipt for one message. A terminal whose agent has no live pane, or nothing live to write to, is disabled and carries a line saying exactly that — `Terminal input unavailable — the agent has no live pane — only its history remains.` — instead of accepting keystrokes into a void. The same happens after a guarded send comes back `wrong-session`, which is the case no snapshot can predict: a rolled-over pane reads as writable right up until a write is attempted, so it is knowable only by trying. Verdicts that mean delivery was merely *unconfirmed* (`stale`, `ambiguous`, `unknown`) warn without disabling, because the pane may be perfectly usable — the daemon reports a write refused *because the operator was typing into the pane* as `stale`, and disabling on that would shut the input precisely because somebody was using it.

This makes the report structured and persistent rather than ending a silence: the desktop's terminal bridge already wrote an in-band `[agent-deck] terminal input rejected: …` notice into the output stream when the daemon rejected a write. That notice scrolls away with everything else. What is new is a state the pane holds — the input disabled, the reason readable, and `data-input-state` on the terminal for anything that needs to see it.

**One capability is deliberately dropped: inserting a saved prompt into an already-running agent.** That picker lived inside the composer and goes with it. Choosing a saved prompt when *launching* a workflow is untouched and is the valuable half. It was not re-homed onto the terminal because the faithful version cannot work there: a PTY is a keystroke stream with no atomic buffer, so every newline in a saved prompt submits early — and multi-line is the main reason to save a prompt in the first place. Copying a prompt body and pasting it into the terminal is the workaround; making insert-without-submit work properly needs bracketed-paste framing verified per agent CLI, which is a feature of its own rather than a move.

The command palette's "Message coordinator…" entry is kept and now focuses the coordinator's terminal. The guarded send verb itself is unchanged and still registered: workflow launch delivers the coordinator's seed prompt through it, and it stays available as the programmatic delivery path. Nothing under `src/` changed, no daemon contract moved, and `PROTOCOL_VERSION` is untouched.
