## `cargo xver` runs CLAUDE.md rule 12's cross-version contract check as a command

Contributor tooling only — a new workspace member, `xtask/cross-version`, a `cargo xver` alias, and a maintainer doc. Nothing under `src/` is touched and no product behaviour moves.

**Why it exists.** Rule 12 requires a cross-version manual test for any change to the daemon, the TUI↔daemon protocol, orchestration or hooks, and it is written in keystrokes because a person was always going to run it. A dispatched agent reading it concludes it cannot type into two full-screen TUIs, declines the check, and leaves the review thread open. Eight green, mergeable pull requests (#1161, #1168, #1169, #1179, #1183, #1187, #1188, #1190) were each blocked on exactly that one unresolved thread. Rule 12's requirement is the scenario, not human fingers, so `cargo xver --branch <branch>` reproduces the scenario and writes an evidence file a reviewer can read afterwards.

**What a run does.** It builds the branch in a standalone disk-backed clone, starts a previous-release daemon with a three-role orchestration of stand-ins under it inside a private bubblewrap namespace with both endpoint roots masked, closes the old TUI with Detach, attaches the branch TUI over a PTY and declines its build-version mismatch prompt, then sends a delegate and both hook kinds. It asserts rule 12's four tells and prints each with the value it was decided on: exactly one `Attach protocol listening` line, the same daemon process at both ends, the delegate landing in its target pane, and the hooks arriving. A tell it could not measure, or one it expected and never recorded, makes the run `INCOMPLETE` rather than a pass.

**The reverse direction.** `--direction reverse` runs the pairing rule 12 does not prescribe: the branch daemon, with the previous release's TUI and CLI against it. That is the pairing that executes a daemon-side change, because the forward pairing's daemon is the previous release's. Reverse also carries a per-branch **probe** (`--probe auto` selects one from the branch's `dispatch-issue-<n>` component and refuses a branch it cannot tie to exactly one probe) and was written with negative controls run against `main`. On #1179 it found an older TUI that did not find the branch daemon lazy-spawning one of its own, which the PR disclosed, and then silently re-creating the live orchestration under that second daemon, which it did not. Rule 12 is not changed in substance: reverse is presented as an option, not as a new obligation.

**Trust boundary.** The runtime scenario is contained; the build is not. `cargo xver` is not an untrusted-code sandbox — the branch's `cargo build` and the `git`/`gh` input downloads run on the host, as you. What it adds is a build-time gate: a branch that changes build-time code relative to its merge-base with `main` (a `build.rs`, a `Cargo.toml`, `Cargo.lock`, anything under `.cargo/`, a toolchain file) is refused, naming the files, unless `--allow-build-changes` is passed after reviewing them. Run unreviewed or external code only in a disposable VM or as a user that holds no credentials. This branch's own diff adds a workspace member and would be refused by that gate, which is the gate working.

**What it does not cover.** No real agent (every role is a stand-in), so it says nothing about how a real agent behaves across the version boundary; Linux only; one previous release per run; and not the desktop's `classify_handshake`. `docs/develop/cross-version-harness.md` has the options, the five ways the manual procedure silently produces a false green and where each is handled, and the rest of what it does not cover.
