## A dispatched agent's prompt is confirmed again, instead of being reported as possibly never delivered

Every `dispatch --single` to a Claude Code pane spent the full 60-second delivery deadline retrying a prompt the agent had already received, then flagged the pane with the daemon's "a spawn-time prompt was written into this pane but the agent never reported submitting it — it may never have arrived — check whether this pane was given any task at all". The task had arrived, the agent had done the work, and in many cases had already reported back. What the operator got was a red pane and a warning about work that was finished.

**The cause is a producer rewriting our own payload before reporting it.** A delivery is provisional until the agent says it submitted the text we wrote, and the deck compares what comes back on `UserPromptSubmit` against what it wrote into the PTY. Any *multi-line* payload is written as a bracketed paste, and Claude Code does not report a paste verbatim — it reports the turn with the payload wrapped in its own `<pasted_content id="…">` … `</pasted_content id="…">` envelope, preceded by whatever blank lines earlier submit probes left in the input box. None of the three shapes the matcher accepted could match that, so the delivery could never be confirmed, only abandoned. This is the silent-failure mode the delivery module's own documentation warns about, reached from a direction nobody had measured: it fails by retrying until the deadline, which looks exactly like the bug the retry loop exists to fix.

**It became universal in v0.40.1.** The mechanism predates that release — it applies to any multi-line automatic prompt — but `dispatch --single` payloads were single-line until PRD #220 Phase 2 appended the `work-done` completion instruction to every one of them. From that commit on, no single-agent dispatch could be confirmed. The cost was not only cosmetic: an unconfirmed delivery writes one bounded *replacement* payload, so every dispatch also wrote a second copy of its task into a pane that may already have been holding the first — the accumulation hazard the delivery module documents, on prompts that deploy, delete and open issues.

**The fix teaches the matcher that fourth shape, and nothing wider.** A report whose paste envelope wraps our payload confirms the delivery. The envelope is a delimited region, which is what keeps this from degrading into "the report contains our prompt somewhere": the enveloped payload is compared as a whole against the same three shapes as before, only blank lines may precede the opening delimiter and only a bounded run of them, the id must be a short alphanumeric token, and the comparison budget shrinks by exactly what the envelope spent — because the hook truncates the whole reported turn at 200 bytes, so every byte in front of the payload is a byte taken off the end of it. The three existing shapes keep their exact accept set and evaluation order; the new one is asked only after they have all said no, so it can only add confirmations where the delivery was previously abandoned. The delivery log names it with its own `confirmation="paste-envelope"` slug and its own line, so an operator can see *why* a verbatim comparison could not answer.

**The two tests that should have caught it had a stale premise of their own.** `scheduler/dispatch/014` and `/015` drive their panes through shell stand-ins that read one *line* per submission — equivalent to what an agent TUI does only while every payload is single-line. Against a multi-line payload they shredded one paste into eight "submissions", none of which was the text the daemon wrote. They now assemble a whole bracketed-paste submission, as a real agent TUI does, and report it as one prompt. Both had also been failing earlier and louder, on a refusal that masked all of this: they run the real `dispatch` CLI from the test process while naming a pane, which the per-spawn hook capability check added in v0.41.0 correctly refuses, and they never got the opt-in that exists for exactly that harness pattern.

Verified against the real thing rather than the stand-ins: three interactive Haiku agents, each confirming its seed through the envelope on attempt 4 with no deadline abandonment, and both tests back to a ~8 second wall clock from the ~78 the retry budget was costing them.
