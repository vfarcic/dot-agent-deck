## Installing the deck's Codex hooks no longer silently untrusts your own hooks

`<CODEX_HOME>/hooks.json` is **your** user-scope hooks file. The deck shares it; it does not own it. Codex addresses a trust grant by a **file-positional** key — `<sourcePath>:<event_snake>:<group_idx>:<handler_idx>` — so moving a rule the deck did not write re-keys the grant attached to it. The deck's install removed its own rule from an event array and appended a fresh one at the end, which moved everything that had been sitting after it. Any hook of yours positioned after a deck rule therefore changed key on every deck install: the record you trusted stopped binding to it — left behind under the old key, or overwritten outright when the deck's own rule landed on that very key — and Codex refused to run your handler until you reviewed it again. The deck never touched your rule. It relocated it, and the relocation is what broke the binding.

**Measured against real codex-cli 0.149.0**, end to end through the shipped `hooks install --agent codex`, with the deck's rule at index 0 and a user's `/usr/bin/env USER_HOOK=1` at index 1 carrying the trust record Codex itself writes. Before a re-install the user's entry reports `pre_tool_use:1:0`, `trustStatus: trusted`. After one re-install it reports `pre_tool_use:0:0`, **`trustStatus: modified`** — it had been moved onto the deck's own stale record, whose hash does not match it. After the fix, the same fixture through the same command leaves it at `pre_tool_use:1:0`, `trustStatus: trusted`, and it stays there across a second install.

**The user's trust record was not merely orphaned — it was overwritten.** The deck's rule landed on `pre_tool_use:1:0`, the key the user's handler had been occupying, and the install's own trust write updates whatever row is already at a key. Measured on the same run: afterwards `[hooks.state]` holds the deck's hash at *both* `:0:0` and `:1:0`, and the user's hash is gone from the table entirely. Re-trusting in `/hooks` was the only way back, and nothing that read the file later could reconstruct what had been lost.

**The fix is to refresh in place rather than remove and re-append.** The install now overwrites the `command` string of the deck handler where it already sits, so nothing before or after it moves. Only the `command` is rewritten: `async`, `timeoutSec`, anything you hand-added, and the rule's own `matcher` are left exactly as they were — which also keeps Codex's `currentHash` stable across an unchanged re-install, since that hash is taken over command + `matcher` + `async`. A rule emptied by the sweep that removes a surplus copy of the deck's own rule is **kept** as an empty object rather than dropped: it contributes no trust key of its own but still consumes its `group_idx`, and dropping it would move everything after it, which is the defect this change removes.

Two limits, stated rather than left to be discovered. The legacy flat rule shape (`{"command": …}`) claims nothing and falls back to the previous strip-then-append path — the Codex adapter has never written one, so a flat deck rule there is a hand-edit, and how Codex indexes a handler inside one has not been measured. And the retired-event sweep — which takes the deck's rule out of an event the deck no longer installs — is still a removal, and a removal cannot help but move what follows it; it fires only when the deck's own event list shrinks, and there is nothing to overwrite its rule with.

**This also shrinks the orphan-record growth in `[hooks.state]`** that issue #1027 describes, at its source rather than by collecting anything: the deck's own record no longer changes key on each launch, so each install stops leaving one behind. No garbage collection was added — automatic GC remains cancelled on the evidence recorded in #1027, and this fix is part of why: the orphan a GC would have deleted is sometimes the user's own record for the user's own hook. Nothing here closes a security hole. The residue was already verified inert — Codex's `currentHash` is independent of position and of `sourcePath`, so an orphan can only ever re-authorise the same command it was written for, which is the deck's own.
