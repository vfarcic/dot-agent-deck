## `remote add` and `remote upgrade` use a Homebrew install on the remote instead of adding a second copy

On a remote where the deck was installed with `brew`, `remote upgrade` used to download the release into `~/.local/bin/dot-agent-deck` anyway. The Homebrew copy stayed on the old version, `connect` ran the new copy, and a daemon you started from your shell could be a different build from the one `connect` expected. A remote with only the Homebrew install could not be used with the `remote` commands or `connect` at all.

Both commands now check how the deck is installed on the remote. When a Homebrew formula owns it, `remote upgrade` runs `brew upgrade dot-agent-deck` there and nothing is written to `~/.local/bin`. Homebrew installs its tap's latest release, so the command records the version that landed and says so when it differs from the one you asked for. `remote add` registers the Homebrew install as it is. The registry now records the install method and the binary's path, and `connect`, `remote doctor` and the hook install use that path. Discovering a remote deck's socket over ssh also checks Homebrew's default locations.

If a remote has both a Homebrew install and a `~/.local/bin` copy, the command names both, uses the Homebrew one, and tells you to remove the other copy. Entries added before this change keep using `~/.local/bin` until the next `remote upgrade` detects the install. A client older than this release still runs `~/.local/bin/dot-agent-deck`, so it cannot connect to a remote whose only install is Homebrew's.
