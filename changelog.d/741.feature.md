## The desktop app can talk to a deck on another machine

Until now the desktop app could only ever talk to one deck: the one running on the machine the app was launched on. The socket path was resolved from this machine's platform paths and nothing could change it, so the app that shows you your agents was structurally unable to show you agents running anywhere else — on the build box, on the server where the long jobs actually live, on the machine you were sitting at yesterday.

**Settings now has a Decks section.** Add a deck by naming the host; leave the user blank if your `~/.ssh/config` already decides it, leave the key blank if it is in an agent, and name a `Host` block if you reach the machine through a bastion. A **Deck selector** sits in the top bar of both the deck and the agent overview, lists what you have configured with this machine first, and switching decks is a click: every terminal session detaches, the event stream is re-pointed, and a fresh snapshot for the chosen deck arrives immediately rather than on the next refresh.

**Test connection is the button that makes it diagnosable.** It exercises the whole path — the ssh hop, the tunnel, the handshake — without any screen having to work first, and it reports **one of twelve named states** rather than a single "failed". There is a difference between "ssh could not reach that host", "this machine has not verified its host key", "the login was refused", "the tunnel is up but nothing is listening over there" and "that deck speaks a different protocol version", and each of those tells you something different to go and do. The host-key state carries the exact command to run once in a terminal, built from the endpoint the tunnel actually uses, so the bastion and the port are in it. On a successful test it also **discovers the remote socket path for you** and writes it into the row, because that path cannot be guessed from this side and asking you to type it correctly before anything could test whether it was right is the wrong order to do things in.

**Nothing you configure is a secret.** A deck is stored as references only — a host, an optional user, a port, an optional key *path*, an optional jump-host *name* — in the app's own `desktop.toml`, and every field is length-bounded and charset-restricted before it is ever handed to `ssh`. Your own ssh config still decides everything it decided before; what the app forces on top of it is host-key checking and the things a GUI has to force because it has no terminal to prompt from, and Test connection discloses the forwards your config will add to the tunnel so they are visible rather than silent.

**What the app trusts is different for the two kinds of deck, deliberately.** A local deck keeps exactly the check it always had — the socket must be yours and mode `0600` — and for the first time every one of those refusals is pinned by a test. A remote deck rests on ssh host-key and user authentication instead, and the local check is *not* run against the forwarded socket, because a uid-and-mode test on an inode your own `ssh` client just created tells you nothing about who is on the far end. Neither is described as the other. Along the same line, **Stop daemon** and **Replace daemon** are unavailable against a remote deck and say why: stopping a process on a machine you do not own is not something a button should do quietly, and over a tunnel the obvious implementation would have killed your local `ssh` client and reported that a daemon had stopped gracefully.

**A remote deck at a different build connects rather than refusing.** A build-stamp difference against a *local* deck is still a refusal with a remedy you can take — replace it with the bundled build. Against a remote deck that remedy names a button that is disabled on the same screen, and a released daemon never matches a development build anyway, so the stamp becomes a badge: both builds stay named in the connection message for the whole session, the protocol version remains a hard floor that nothing can bypass, and what the project and workflow screens actually act on is the capability set the deck advertised — so an older deck says which verbs it is missing and keeps its running agents visible and usable.

The remote leg genuinely needs a second machine to prove, and a loopback `ssh` is not one. `docs/develop/desktop-gui.md` has the whole design, the manual walk-through, the twelve states, what your own ssh config still controls, and the transport alternatives that were measured and rejected.
