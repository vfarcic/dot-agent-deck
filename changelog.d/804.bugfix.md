## A reconnected card says how long its agent has really been quiet

Reconnecting a TUI to a running daemon (`dot-agent-deck connect`, or any restart of the TUI while its agents keep running) reset every card's `Last:` readout to `0s`, however long the agent had actually been idle. Hydration rebuilt each card from the daemon's snapshot — status, active tool, tool count, prompts, live target — but stamped its `last_activity` with the moment it was rebuilt, even though the daemon has sent the real instant as `SessionSnapshot.last_activity_ms` since PRD #745 M9. The card now carries that instant, so an agent that went quiet an hour ago reads `Last: 1h` straight after the reconnect.

**The desktop app had a larger version of the same defect, and the same change fixes it.** The snapshots its background watcher pushes (PRD #741 M4(b)) are rendered from a local copy of the daemon's state. That copy is re-seeded with the TUI's seeding function from each full `ListAgents` reply, which the watcher fetches at least every five seconds. Each paned agent's live state is then reported from the copy, so on those snapshots the **Last activity** column showed when the reply landed rather than the daemon's instant, and read `just now` however long the agent had been idle. Two cases were already correct. Refreshes a user action triggers fetch the list directly and report the daemon's value. Paneless agents keep the value the daemon sent, since the copy holds no session for them.

**The overlay is newer-only rather than unconditional, because `last_activity` also decides ordering.** It is the evidence `supersedes_generation` uses to decide whether a later frame retires a card, and the key `pane_writable`, `pane_session_id`, `agent_writable` and the `ListAgents` join use to pick the newest session. The snapshot's instant is taken only when it is strictly newer than every session this state already holds for the same pane or agent (including a card the seed replaces), and no later than the moment of seeding. Otherwise the previous behaviour stands. So no newest-wins pick changes, no new tie is created for hash order to settle, and a re-seed never moves a card's evidence backward: the high-water mark `apply_event` keeps (PRD #284). A future stamp is deliberately not imported. The value is producer-supplied, and the daemon can carry a future one only because its registry ground retires a disowned generation whatever the stamps say (issue #454). A client has no registry, so importing it would pin the reconnected card against every honest successor until the wall clock caught up. The `Last:` readout is `0s` either way. In the common case, where the state holds nothing else for that pane or agent and the stamp is not in the future, the card now carries the daemon's own instant. So when a frame from a different agent reaches both, `supersedes_generation` compares its stamp against the same value on the reconnected card as on the daemon's session, and both reach the same verdict. Before this change, a card seeded at "now" survived such a frame stamped between the agent's last activity and the reconnect, while the daemon retired its own session, and the TUI's `pane_writable` then disagreed with the daemon's.

**No `PROTOCOL_VERSION` bump and no compatibility break.** No message changes shape, and `last_activity_ms` keeps its meaning. What changed is how a client seeds its own local copy from it. The daemon's state never passes through the seeding function, so every decision the daemon makes is unchanged. A newer TUI against a daemon that predates the field reads it as absent and keeps the old behaviour. An older TUI against a newer daemon ignores it, as it always has.

Covered by `session/live/004` (hydration through a real in-process daemon carries the instant), `session/live/016` (the rendered `Last:` border), `status/supersede/016` (a different agent's frame retires the reconnected card exactly when it retires the daemon's session, and every pick agrees with the daemon's), `status/supersede/017` (existing evidence for the pane or agent leaves every pick on a freshly minted card unchanged; since PRD #1223 a same-agent card that reached the pane before hydration is kept rather than duplicated, and takes the snapshot only when the snapshot is the fresher evidence), `status/supersede/018` (a future-stamped snapshot cannot pin the card against a successor) and the desktop's `a_fetched_last_activity_survives_the_fold`. Each was checked to fail against the unfixed code, and each clause of the rule turns `status/supersede/017` or `/018` red when it is removed.
