## The demo reel refuses a cast that cannot prove which revision produced it

The demo-reel adapter decided a cast was publishable from **path existence** plus two static facts about the *test* — that its source changed on the branch, and that its `tests/CATALOG.md` line carries the ` [reel]` marker. None of those is a fact about the artifact, so a `full-stream.cast` that an older revision left on disk satisfied every one of them. A reel-eligible clip is by definition a real-agent recording, and its URL goes into the PR body **and** the changelog fragment, which flows into the public release notes — so the pipeline could publish a clip from an unknown revision, possibly one predating the redaction fixes in #502/#785, without anything noticing.

PR #805 fixed the cheap half by making the harness discard the previous run's artifacts at launch and on `skip_unless!`'s runtime-skip path, panicking rather than warning when a deletion fails for any reason other than `NotFound`. That closes every route which *reaches* one of those two call sites, and two do not: a **filtered** run — the normal way anyone works, and what CLAUDE.md rule 5 asks for — never selects the test at all, so nothing on the discard path executes; and `skip_unless!` evaluates its preflight expression *before* `_skip_if_err` is entered, so a kill or an abort inside a `check_*_available`, or inside an importer it calls, lands before the skip-path discard. Provenance covers both at once, which is why the answer was not a third discard.

The harness now writes a `provenance.json` sidecar beside each recording dump — schema, test name, outcome, the commit and `-dirty` flag parsed out of the binary's own compile-time `DAD_BUILD_ID`, the whole build id, nextest's run id, a redaction-implementation version and a wall-clock timestamp. `build.sh assemble` **refuses** a clip whose sidecar is absent, unreadable, of an unknown schema, missing a required field, records an `outcome` other than `passed`, or records a `commit` that is not the revision the reel is being built at — and it names the id and the reason for each one rather than silently including or excluding it. The gate is per-clip, so one stale sidecar drops one clip and the reel is still built from what survived, with the omission stated where the manifest is announced. The sidecar is written **last** of the dump's artifacts and discarded **first**, so a torn dump and a partial discard both leave something unpublishable rather than something publishable.

`run_id`, `build_id`, `recorded_at_unix`, `redaction_version` and `dirty` are **reported and gate nothing**, deliberately: a reel legitimately assembles clips from several filtered runs at one commit, so differing run ids only note the count, and recording from a dirty tree is the ordinary dogfood case. Neither can become a refusal without refusing something correct.

**What this establishes is narrower than "the cast is current", and the distinction is the point.** A selected clip was written by a harness *built from this commit* by a run that *was not unwinding a panic*. It does **not** prove the clip came from the latest run — a passing clip recorded at this commit by an earlier run is accepted, and correctly so, since the code that produced it is the code under test. Under `dirty` even the revision narrows, because one commit then covers more than one working state, which is why that flag is surfaced loudly rather than swallowed. `outcome: passed` means the harness was not unwinding a panic when the deck was dropped, not that nextest reported the test as passed. It says **nothing** about whether the cast's content is redacted — the harness redaction is a best-effort blocklist with two reproduced gaps ([#810](https://github.com/vfarcic/dot-agent-deck/issues/810)), and provenance and redaction do not cover for each other. And it is not a signature: the sidecar sits in the same gitignored directory as the cast, so whoever can write one can write the other.

Eleven new cases in `task reel-adapter-test` drive every refusal and every advisory, each by mutating one field of a copy of the fixture tree; three new guards in `tests/harness_isolation.rs` run in the fast tier and hold the two ends of the contract together — the harness's build-id parse, the write-last/discard-first ordering, and a check that every field the shell adapter reads is one the Rust harness writes and that both agree on the schema number. Without that last one the two halves live in different languages, neither compiles the other, and drift would refuse every clip silently until somebody next tried to publish. `REEL_ADAPTER_EXPECT_COMMIT` overrides the expected commit for the acceptance test and for a deliberate manual assertion; with it unset and `git rev-parse HEAD` unable to answer, the adapter **dies** rather than publishing unchecked. If a reel build starts refusing everything, the fix is to re-record at the current commit with `DOT_AGENT_DECK_RECORD=1 cargo test-e2e-live <filter>`, not to reach for the override.
