## The intermittent `build-macos` red in `live_014` is diagnosed and fixed in the test, not papered over with a timeout

`daemon_protocol::tests::live_014_spawn_time_is_observed_and_additive` was killed by nextest's default 3 × 60s window on `build-macos`, turning a required check red on a PR with no Rust in its diff ([#959](https://github.com/vfarcic/dot-agent-deck/issues/959)). No timeout was widened, no retry was added and the test did not move tier. What changed is one line in the test's own teardown, plus phase markers that are what made the diagnosis possible, plus a tombstone in `.config/nextest.toml` recording why there is no carve-out.

**It stalled; it was not merely slow, and that is measured rather than argued.** The run's own JUnit artifacts hold both halves: `nextest-macos-attempt-1` records `time="180.616"` and `nextest-macos-attempt-2` — a job-level re-run of the identical SHA with no code change — records **0.194s** for the same test on the same runner image. The Linux `build` job of that run took 0.115s. That is 931x. The failing attempt's machine was about 40% slower overall (median fail/pass duration ratio 1.40 across the 2440 tests both attempts recorded, 90th percentile 2.25), exactly one other test over a second was more than 2x slower, and 1535 other tests started *and finished* inside the 180.6s window — so the runner was scheduling work normally throughout. One test stalled, not the machine.

**The cause was found by reproducing it on a real runner, which is the only place it happens.** 4500 executions of this test, three at a time, on `macos-latest`: **18 stalled**, about 1 in 250, against roughly 1 in 450 observed in CI. The same 4500 on `ubuntu-latest` stalled **0** times. All 18 stopped at the same phase marker — `shutdown_all (adopted agent)` — with the stack in `AgentPtyRegistry::force_kill_and_reap_all`'s `try_wait` poll loop, which has no deadline, and the child in macOS `ps` state `?<Es` ("trying to exit") every single time.

**The mechanism is isolated, not guessed.** Varying one thing at a time on `macos-latest`, against the same `killpg(SIGKILL)` and `try_wait` loop, the stall needs four conditions at once — the child writes to the PTY, nobody drains it, both ends are still open, and the child is exiting of its own accord when the kill lands. A standalone reproduction of all four stalls 40 of 40 times; swapping the child for `/usr/bin/true`, dropping either end, adding a draining thread, or using a `sleep 300` that is still running when killed each gives 0 of 800. Every one of those is 0 of 800 on `ubuntu-latest` too, the unmodified shape included. That last condition is also why the real test stalled on only 0.4% of executions rather than all of them: its own phase markers put about 1.3ms between the spawn and the kill, so the SIGKILL usually wins the race and the child never reaches the exit path it gets stuck in.

**The defect was the test's own construction.** Its second half spawns a child the registry did not fork, to prove such a child reports no spawn time. It opened a PTY, spawned a bare `sleep` on it — which writes a usage line to that PTY and exits — and then held *both* ends alive while reading neither. The production spawn path never has that shape: `agent_pty::spawn` drops the slave as soon as `spawn_command` returns, and `spawn_agent` starts a `pump_reader` thread that drains the master for the agent's whole life. Dropping the pair as soon as the child owns its own copies is the fix, and it is one line. As a side effect the test's teardown went from 50.3ms to 0.1ms locally, because the child is now reapable on the first poll instead of needing a full 50ms cycle.

**The two alternatives #959 raised were both rejected on the evidence.** Widening `slow-timeout` could not have helped an unbounded wait — a carve-out only moves when the kill lands — and it would have hidden the defect behind a longer green. Moving the test out of the fast tier would not have touched the defect either: at least 76 of the 1838 `#[test]` / `#[tokio::test]` functions under `src/` fork a real PTY child (bodies containing `.spawn_agent(` or `spawn_command(`; helper-mediated spawns are not counted, so 76 is a floor), so moving one leaves 75 on the same three required jobs, and it would have deleted the only part of this test that proves its property — that the daemon records the instant it forked, which needs a real fork.

**The phase markers stay, and they cost nothing on the green path.** nextest stores a failed or timed-out test's stdout and stderr and drops a passing test's, `store-success-output` being at its default of false, so they appear only on a red run — including in the JUnit artifact each build job uploads per attempt, whose `<failure type="test timeout"/>` carries no message of its own. That is why the first occurrence told nobody anything, and it was verified against nextest 0.9.143 rather than assumed. `force_kill_and_reap_all` still has no deadline, so if this ever stalls again its captured stderr names the wait that hung.

The test still fails when the property it guards is broken: stamping `AgentRecord.spawned_at_ms` from `Utc::now()` on the read path makes it fail on "the spawn instant is recorded once and read back, never recomputed", checked against the final code. Nothing here touches `src/` outside one test function's body, the TUI↔daemon protocol, orchestration or hooks, so `PROTOCOL_VERSION` is untouched and CLAUDE.md rule 12's cross-version check does not apply.
