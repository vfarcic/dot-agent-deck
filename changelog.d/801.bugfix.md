## The desktop app no longer refuses a daemon it agrees with, when only the build stamps differ

The desktop app checks two things when it meets a daemon: that the wire protocol matches, and that the two were built from the same commit. Until now, failing the second check was as final as failing the first — the app reported the daemon incompatible and stopped there, with no way forward that a user could actually take.

That is an ordinary situation rather than an exotic one. The CLI and the app share a socket, so they share a daemon, and the two update on different cadences: run the TUI, then open the app, and the app refuses the daemon the TUI just started. The worst version is upgrading the app while yesterday's daemon is still running agents. **Replace daemon** is deliberately unavailable while agents are live — it never force-stops them, which is right — so the only path forward was killing nine running agents in order to open a window. A `DOT_AGENT_DECK_DESKTOP_ALLOW_BUILD_MISMATCH` environment variable existed, but an app launched from Finder inherits no shell environment, so it was never a remedy anyone could reach.

The TUI, meeting exactly this situation, has always prompted: it names the agents that are live and lets you decline and carry on. The desktop had the same information and offered no choice. That asymmetry is what is fixed.

**Connect anyway** now appears wherever the app reports a daemon incompatible — in the deck's connection banner and on the agent overview's incompatible note — whenever the mismatch is the build stamp alone. Replace daemon is not always beside it: that one is still offered only when the daemon reports zero live agents, and the overview offers no daemon lifecycle action at all. It asks for a confirmation first, which says what you are accepting: the two builds agree on the shape of everything they exchange, and a stamp difference can still mean divergent behaviour behind an identical wire — a field whose meaning changed while its shape did not. Unlike Replace daemon it is offered however many agents are live, because that is the case with no other way out.

Accepting is deliberately narrow. It lasts for the session and nothing is written to disk, so quitting the app restores the refusal and you decide again next time. It does not clear the warning: the connection banner stays up while connected, naming both builds, for as long as the app is open. And it relaxes the build-stamp comparison only — the protocol check runs first, is not overridable from anywhere, and a genuinely incompatible daemon is refused with no button offered, because pressing one could not have worked.

The environment variable still behaves exactly as before for development use.
