## The desktop app no longer refuses a daemon it agrees with

The desktop app checks two things when it meets a daemon: that the wire protocol matches, and that the two binaries are compatible. The first is exact and is not negotiable. The second used to compare the two builds' git commit stamps for exact equality — which answers "were these built from the same commit?", a question with very little to do with whether they can work together. Rebuild the app after lunch and it refused the daemon it had been talking to all morning, in the same words it would have used for a real incompatibility.

It now compares the **release version** each build reports, which is the number this project actually moves when compatibility breaks. While Agent Deck is on `0.x`, a change that breaks the app↔daemon contract bumps the minor digit and everything else bumps the patch — so `0.39.0` and `0.39.2` are compatible by construction, while `0.39` against `0.40` is a declared break. From `1.0` onward the ordinary SemVer rule applies and only the major digit counts. Two builds from different commits that name the same release now simply connect: no banner, no prompt, nothing to dismiss. The difference is still there to read — the agent overview's daemon card names both builds on hover — it is just no longer an alert.

Failing to read a version counts as a difference, never as a match. If either side reports a stamp the app cannot parse, or the daemon reports none at all, you get the prompt rather than a silent connection: the quiet path is taken only on positive evidence that both sides named the same release.

One thing this cannot see, and what covers it instead: a build from an unreleased branch describes itself by the last release it was cut from, so a compatibility break that has not been released yet looks like the release before it. That case is covered by the cross-version test this project requires before such a change merges — which is also what turns the break into the version bump this check can then see.

## Connect anyway, for the case where the versions really do differ

A declared break still refuses, and refusing on its own used to leave the user nowhere to go. The worst version is upgrading the app while yesterday's daemon is still running agents: **Replace daemon** is deliberately unavailable while agents are live — it never force-stops them, which is right — so the only path forward was killing nine running agents in order to open a window. A `DOT_AGENT_DECK_DESKTOP_ALLOW_BUILD_MISMATCH` environment variable existed, but an app launched from Finder inherits no shell environment, so it was never a remedy anyone could reach. The TUI, meeting the same situation, has always prompted: it names the agents that are live and lets you decline and carry on. The desktop had the same information and offered no choice. That asymmetry is what is fixed.

**Connect anyway** now appears wherever the app reports a daemon incompatible — in the deck's connection banner and on the agent overview's incompatible note — whenever the wire protocol agreed and it is the versions that differ. Replace daemon is not always beside it: that one is still offered only when the daemon reports zero live agents, and the overview offers no daemon lifecycle action at all. It asks for a confirmation first, which says what you are accepting: the two builds agree on the shape of everything they exchange, and a version difference can still mean divergent behaviour behind an identical wire — a field whose meaning changed while its shape did not. Unlike Replace daemon it is offered however many agents are live, because that is the case with no other way out.

Accepting is deliberately narrow. It lasts for the session and nothing is written to disk, so quitting the app restores the refusal and you decide again next time. It does not clear the warning: the connection banner stays up while connected, naming both builds, for as long as the app is open. And it relaxes the version comparison only — the protocol check runs first, is not overridable from anywhere, and a genuinely incompatible daemon is refused with no button offered, because pressing one could not have worked.

The environment variable still behaves exactly as before for development use.
