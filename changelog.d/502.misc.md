## The e2e tier runs in CI, as two lanes

The end-to-end tier now runs in CI. Until this change no workflow ran it at all: `tests/e2e_*.rs` was type-checked by the `build` job's clippy step and executed by nothing anywhere, which is how [#460](https://github.com/vfarcic/dot-agent-deck/issues/460) stayed broken on `main` across twelve commits. In its place a contributor was expected to run all 71 files locally before every pull request — an obligation that got worse the more the project leaned on parallel agents, because every dispatched unit ran the whole tier and N of them meant N copies competing for one machine ([#415](https://github.com/vfarcic/dot-agent-deck/issues/415) measured 6-7 of 40 files failing in parallel against 40 of 40 at `-j 1`).

A third cargo feature, `e2e-live`, splits the suite by whether a test needs a working agent credential. The 24 credential-requiring files open with `#![cfg(all(feature = "e2e", feature = "e2e-live"))]`; the other 47 keep the bare `#![cfg(feature = "e2e")]`. That gives three lanes. `cargo test-e2e` is lane 1 — the deterministic files, which need no secrets and now run on every pull request in a new `e2e-deterministic` job. `cargo test-e2e-live` is lane 2, a *superset* run of all 71 files, which runs from the new `e2e-live` workflow: per-merge on `main`, on `workflow_dispatch`, and on demand on a pull request labelled `run-live-e2e`. Lane 3 is what you run locally while debugging — the failing test, then its module. Both new jobs are deliberately advisory rather than required checks, and the required set is unchanged.

The pre-PR full-tier obligation is gone with it. `cargo test-fast` remains the per-task gate, and rule 6 is unchanged: rerun a failing test alone to confirm the fix, then its module. The clippy gate grows the new feature — `cargo clippy --workspace --all-targets --features e2e,e2e-live -- -D warnings` — because under `--features e2e` alone the 24 re-gated files compile to empty crates and are type-checked by nothing, the same hole class closed by [#407](https://github.com/vfarcic/dot-agent-deck/issues/407), [#436](https://github.com/vfarcic/dot-agent-deck/issues/436) and [#489](https://github.com/vfarcic/dot-agent-deck/issues/489).

The credential handling for lane 2 is [#785](https://github.com/vfarcic/dot-agent-deck/issues/785): an API key rather than the OAuth credential set, held as a secret on a `live-e2e` GitHub Environment whose required reviewer means a merge queues the credentialed run and waits for a human click. Two of that issue's steps are the repository owner's to perform by hand and remain open — setting the secret and adding the reviewer. Contributors: `CONTRIBUTING.md` has the three lanes, and `docs/develop/e2e-lanes.md` is the operational page, including the three reasons a green lane-2 run can still mean almost nothing — every credential preflight *skips* rather than fails and nextest counts that as a pass, an API key alone leaves most of the lane skipping because `check_claude_available` never consults `ANTHROPIC_API_KEY`, and the workflow's two npm agent-CLI pins are not tracked by Renovate.

Three properties of that credentialed job are worth naming, because each closes a way for it to look fine while being wrong. It **fails immediately before the run step** when `ANTHROPIC_API_KEY` is unset, empty or whitespace-only, since the preflights would otherwise treat such a key as an ordinary skip and the superset run would still go green with no real agent having run — the same fail-fast shape the release workflows use for `RELEASE_TOKEN`, except placed last rather than first, because a test job has no half-done state and a late failure still lets a keyless validation run exercise everything up to the credentialed command. Its honest limit is that emptiness is all it can check. It writes a **runtime-skip count to the run summary**, which needed `--success-output=final`, because a skip is a *successful* test and nextest suppresses a successful test's output by default; only the count crosses over, since a `SKIP:` line is ordinary output from a passing test rather than trustworthy metadata, and the reasons stay in the masked job log. And the JUnit report it uploads is **rebuilt from an attribute whitelist** by `scripts/junit-strip-output.py` before upload: nextest stores stdout and stderr for failed and retried tests, that file is written by the process holding the key, and GitHub's secret masking does not extend to artifacts a public repository serves to any logged-in reader. The job's event gating is an allowlist for the same reason — a trigger added later has to be named there too, so it fails closed rather than opting itself into a credentialed run.
