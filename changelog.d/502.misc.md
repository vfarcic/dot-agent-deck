## The e2e tier runs in CI, as two lanes

The end-to-end tier now runs in CI. Until this change no workflow ran it at all: `tests/e2e_*.rs` was type-checked by the `build` job's clippy step and executed by nothing anywhere, which is how [#460](https://github.com/vfarcic/dot-agent-deck/issues/460) stayed broken on `main` across twelve commits. In its place a contributor was expected to run all 71 files locally before every pull request — an obligation that got worse the more the project leaned on parallel agents, because every dispatched unit ran the whole tier and N of them meant N copies competing for one machine ([#415](https://github.com/vfarcic/dot-agent-deck/issues/415) measured 6-7 of 40 files failing in parallel against 40 of 40 at `-j 1`).

A third cargo feature, `e2e-live`, splits the suite by whether a test needs a working agent credential. The 24 credential-requiring files open with `#![cfg(all(feature = "e2e", feature = "e2e-live"))]`; the other 47 keep the bare `#![cfg(feature = "e2e")]`. That gives three lanes. `cargo test-e2e` is lane 1 — the deterministic files, which need no secrets and now run on every pull request in a new `e2e-deterministic` job. `cargo test-e2e-live` is lane 2, a *superset* run of all 71 files, which runs from the new `e2e-live` workflow: per-merge on `main`, on `workflow_dispatch`, and on demand on a pull request labelled `run-live-e2e`. Lane 3 is what you run locally while debugging — the failing test, then its module. Both new jobs are deliberately advisory rather than required checks, and the required set is unchanged.

The pre-PR full-tier obligation is gone with it. `cargo test-fast` remains the per-task gate, and rule 6 is unchanged: rerun a failing test alone to confirm the fix, then its module. The clippy gate grows the new feature — `cargo clippy --workspace --all-targets --features e2e,e2e-live -- -D warnings` — because under `--features e2e` alone the 24 re-gated files compile to empty crates and are type-checked by nothing, the same hole class closed by [#407](https://github.com/vfarcic/dot-agent-deck/issues/407), [#436](https://github.com/vfarcic/dot-agent-deck/issues/436) and [#489](https://github.com/vfarcic/dot-agent-deck/issues/489).

The credential handling for lane 2 is [#785](https://github.com/vfarcic/dot-agent-deck/issues/785): API keys rather than the OAuth credential set, held as secrets on a `live-e2e` GitHub Environment whose required reviewer means a merge queues the credentialed run and waits for a human click. Two of that issue's steps are the repository owner's to perform by hand and remain open — registering the two secrets (`ANTHROPIC_API_KEY` and `OPENAI_API_KEY`) and adding the reviewer. Contributors: `CONTRIBUTING.md` has the three lanes, and `docs/develop/e2e-lanes.md` is the operational page, including what a green lane-2 run does and does not prove and which four npm agent-CLI pins Renovate does not track.

**Lane 2 runs real agents from those keys, and a green run is proof rather than an absence of evidence.** The two halves arrived together. On the credential side, `check_claude_available` and `check_opencode_available` gained a *third* auth path — a non-empty `ANTHROPIC_API_KEY`, consulted after the credentials file and the macOS Keychain, so a developer with a real credential set is unaffected — and the workflow provisions codex's `~/.codex/auth.json` from `OPENAI_API_KEY` in one non-interactive command rather than widening that gate, which keeps its live model probe as the real proof of reachability. Three harness changes are coupled to the claude one, because the credential import and the `~/.claude.json` seeding sit inside a launch path that *panics* rather than skips: the import writes no credentials file when the key authorises the run, the seeding pre-answers Claude Code's API-key approval prompt (it defaults to **No**, so an unattended interactive agent would otherwise stall forever), and the harness now lets the key cross its environment scrub into the spawned deck. On the proof side, the run step sets `DOT_AGENT_DECK_REQUIRE_REAL_E2E=1`, which turns every runtime skip into a failure, with no off-switch; the two tests that genuinely cannot run there are excluded *by name* instead — `devin_live_001` permanently, since Devin offers no API-key path at all, and `dispatch_013`, which additionally wants a `GITHUB_TOKEN` and a live GitHub fixture repository. Gated tests that actually run went from **3 of 33** to **31 of 33**.

Three further properties of that credentialed job are worth naming, because each closes a way for it to look fine while being wrong. It **fails immediately before the credentialed steps** when either key is unset, empty or whitespace-only — not because a green run would otherwise be vacuous (the flag above closes that) but because a missing secret would instead surface as 26 separate preflight failures deep in a 90-minute run rather than a named error in seconds. It is placed last rather than first, unlike the release workflows' `RELEASE_TOKEN` check, because a test job has no half-done state and a late failure still lets a keyless validation run exercise everything up to the credentialed command; its honest limit is that emptiness is all it can check. It writes a **runtime-skip count to the run summary**, which needed `--success-output=final`, because a skip is a *successful* test and nextest suppresses a successful test's output by default; under the require-real flag that count is 0 by construction on a passing run, so it now reads as a consistency check on the flag rather than as the evidence itself, and only the count crosses over since a `SKIP:` line is ordinary output from a passing test rather than trustworthy metadata. And the JUnit report it uploads is **rebuilt from an attribute whitelist** by `scripts/junit-strip-output.py` before upload: nextest stores stdout and stderr for failed and retried tests, that file is written by the process holding the key, and GitHub's secret masking does not extend to artifacts a public repository serves to any logged-in reader. The job's event gating is an allowlist for the same reason — a trigger added later has to be named there too, so it fails closed rather than opting itself into a credentialed run.
