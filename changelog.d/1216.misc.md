## Adding a linkage-check rule is one registration, and the rule count is derived rather than typed

`cargo xtask linkage-check` is the repository's own static gate, and adding a rule to it used to mean editing **four separate places** in one 2,927-line shared file, `xtask/linkage-check/src/main.rs`: a hand-numbered `//! N.` doc list, a `// Check N` comment at the registration site, a `format!("[N] {v}")` failure tag, and a literal rule count in the success line. Every rule-adding pull request therefore edited the same lines with sequential numbers, so two of them conflicted *by construction* whatever they were about — measured three times in one day, between #1190/#1163, #1190/#1179 and #1163/#1179, none of which shared a subject. That file was the only one in the repository that collided between strangers.

**The count was the worse half, because it failed silently.** Two branches that each add a rule both raise the same literal by one, which produces *identical text* — so git merges it cleanly, with no conflict to draw anyone's attention, and `main` ends up reporting one fewer rule than it registers. That shipped twice on 2026-09-21, and was caught by neither the merge, nor `cargo fmt`, nor clippy, nor `cargo test-fast`: only by someone reading the number in the tool's own output. A clean merge that is quietly wrong is worse than a conflict.

Every rule is now one entry in a `RULES` table — a stable `number`, a stable kebab-case `name`, the `summary` that used to be the doc list, and the check itself — and the four derived things read that entry: the `[N]` tag (applied once, by the runner, from the table), the `--list-rules` output, the rule count (`RULES.len()`), and the order findings print in. Adding a rule is that entry and nothing else.

Four tests hold the table honest, and the first is what replaces the literal's silent failure with a red one: the numbers must be unique and run `1..=RULES.len()` in declaration order with no gap, so the one collision a table cannot prevent — two branches both claiming the next number, appended at different offsets and merged cleanly — is now a test failure rather than two rules sharing a number. The others pin unique kebab-case names, a usable summary on every entry (it is the only rule list there is), and that no entry's summary cites another rule's number.

**Rule numbers are unchanged and none will ever be renumbered.** They are cited by number in `CLAUDE.md`, under `docs/` and in comments throughout `tests/`, and a failure tag someone pasted into an issue has to keep meaning what it meant. `number` is written in each entry rather than taken from the entry's position for exactly that reason, and a rule is retired by making its check a no-op rather than by deleting its entry and shifting its successors.

Two visible consequences worth knowing. **Rules 5 and 6 now carry their `[5]` / `[6]` tag**, which they never did — their findings were emitted untagged for as long as the tag was a `format!` at the registration site, which is the drift the table removes. And findings now print in rule-number order (they were grouped by where in one long function each rule happened to run: 3, 4, 2, 1, 5, 6, 8, 15, 10, 11, 9, 12, 13, 14, 7).

`cargo xtask linkage-check --list-rules` prints what each `[N]` means, from the same table the tags come from, and a failure run now ends with a line pointing at it. [`docs/develop/linkage-check-rules.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/linkage-check-rules.md) is the contributor-facing version: how to add a rule, the two shapes one takes, the conventions a new rule follows, and what in that crate is deliberately not a rule.

One drive-by correction the table made findable: `check 13` named **three different rules** across this one crate — the git-literal rule (13, correctly), the bare-`git` rule (15) and the voice-registry rule (14) — because each was written while its rule was expected to land as 13, and nothing tied the prose to the registration. All of those citations, in the crate and in `docs/develop/desktop-gui.md`, now name the rule that is actually registered, and the crate's internal vocabulary is "rule N" throughout rather than a mix of "rule" and "check".
