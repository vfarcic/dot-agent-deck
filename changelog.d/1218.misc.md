## `idle_worker_008` waits for a stopped pane to be released before reusing its id

`idle_worker_008_closed_orchestrator_pane_id_reuse_receives_nothing` closes an orchestrator through the real `StopAgent` request and then spawns an unrelated agent on the freed pane id. It used to spawn the moment the reply arrived. But the `StopAgent` handler writes its reply first and drops the pane's cleanup hold afterwards, and `spawn_agent` refuses a held pane. Under contention the test sometimes lost that race and failed with `Duplicate pane id: idle-orchestrator-pane`. This was seen once in a full `cargo test-fast` run at load average 34–41 on 16 cores. Pinned to a single CPU, the unfixed test failed 10 of 100 runs; the fixed test failed 0 of 100.

The test now waits for `pane_close_in_flight` to go false before spawning. That is the same predicate `respawn_or_recreate_agent_for_pane` waits on. Waiting on `idle_worker_014`'s condition instead would have changed nothing. That test waits for `pane_current_agent_id` to become `None`, and after a `StopAgent` that is already true by the time the reply arrives. Pinned the same way, that variant failed 11 of 80 runs with the same error.

**The daemon's ordering is unchanged, deliberately.** Sending the reply before releasing the hold is incidental, not a promise. The hold only has to cover its cleanup, which is finished before the reply is sent. And no in-tree client reuses a pane id after a stop: the TUI and the desktop both mint fresh ones. Two comments that read as a stronger promise now say so. One is at the handler's release site. The other is `hold_pane_for_cleanup`'s cost note, which said the hold only covers the gap before `close_agent` drops the record. In fact it also covers `unregister_pane`, `finish_pane_close` and the reply. There is no wire or behaviour change.
