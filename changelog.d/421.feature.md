## Issue-dispatch schedules can skip issues that others have claimed

An issue-dispatch schedule can now skip issues that another machine, or another schedule dispatching the same repository, is already working on, so two decks pointed at one repository can avoid starting duplicate agents on the same issue. Set `claim_gating = true` in the schedule's `[scheduled_tasks.issue_dispatch]` table. A run then skips an issue that carries the `agent-deck/claimed` label while someone else's claim comment on it was posted or updated within `claim_ttl_hours` (default 168, a week), judged by GitHub's clock when GitHub reports it and otherwise by the machine's own clock with a warning in the daemon log, and the daemon log's skip line names the schedule, machine and GitHub account holding the claim and how long ago it was last active. Only claim comments by the repository's owner, members and collaborators make a run skip an issue, so on a public repository a comment from anyone else cannot hold an issue back. Every skip line now also says why the issue was skipped: its worktree exists, an open pull request targets its branch, or another schedule's claim.

A run that considers an issue whose worktree still exists updates its own claim comment once half of `claim_ttl_hours` has passed. An issue the run does not consider, because it is not among the first `max_per_run` issues listed, is not refreshed, and neither is one whose update fails, for example because the GitHub API rate limit is used up, so a claim can expire while its agent still works. A claim whose machine or schedule is gone expires after `claim_ttl_hours`, and a schedule whose own worktree and pull request are gone can dispatch the issue again despite its own old claim. Removing the `agent-deck/claimed` label releases a claim by hand. When an issue's claims cannot be read from GitHub, the issue is dispatched and the log says its claims were not checked. Both keys are set in the schedules file; `claim_ttl_hours` must be at least twice the longest gap between the schedule's runs plus one hour (145 for a weekday schedule), and a schedule that does not meet that keeps running and writing claims with gating off, which the daemon log reports as a warning on every start and reload.

Gating is off by default, so no schedule skips an issue for someone else's claim until you turn it on. Every issue-dispatch schedule, with gating on or off, now reads an issue's comments from GitHub when it skips the issue because its worktree exists, and updates its own claim comment from that skip once half of `claim_ttl_hours` has passed since its last update, so frequent schedules with many issues in flight spend more of the GitHub API rate limit; the documentation recommends running them every 15 minutes or less often. Decks of earlier versions keep writing claims but do not skip issues for them or update them while their agents work, so in a mixed fleet only the decks with gating on honour claims, and they honour an older deck's claim only until `claim_ttl_hours` after its last update.
