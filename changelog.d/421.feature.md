## Dispatched Issues Are Claimed on GitHub

An issue-dispatch schedule now tries to mark each issue it dispatches on GitHub, so anyone reading the repository's issue list can see that an agent is working on it, before a pull request exists.

Once an issue's agent has started, the deck adds the `agent-deck/claimed` label to the issue, creating the label in the repository first if it is missing, and posts one comment naming the schedule and a machine id computed from the dispatching machine's host name. Dispatching the same issue again from the same schedule, machine and `gh` account updates that comment instead of posting another one. An issue whose agent fails to start gets no claim. On a public repository the comment is public, so give issue-dispatch schedules names you are happy to publish.

Write access to the repository lets the account `gh` is signed in with do the whole claim, including creating the label. An account that can apply labels and comment on issues but not create labels can claim too, once the `agent-deck/claimed` label exists in the repository. When the claim cannot be written, for example with a read-only token or a GitHub call that times out, the daemon log gets one `claim failed for issue #<n>` line saying what happened to the label and to the comment and why, and the agent keeps working. The claims of one run share a two-minute limit on GitHub calls, so a slow GitHub cannot hold up dispatching; an issue whose claim is skipped once that limit is used up is still dispatched and gets the same line. The deck never removes the label or the comment, including when you close the issue's tab, so remove them by hand when you no longer want them. The claim does not yet stop another machine or schedule from dispatching the same issue.

See [Claims on GitHub](https://agent-deck.devopstoolkit.ai/docs/scheduled-tasks.md#claims-on-github).
