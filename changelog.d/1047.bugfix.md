## Workflow launch no longer fails on a stock Linux box

Launching a workflow refused any project whose `.dot-agent-deck/` directory was writable by group — which is what `mkdir` produces under the `umask 002` that Debian and Ubuntu ship, even when the group has exactly one member. On a default install that was every project on the machine, and the only way out was a `chmod` run outside the app.

The deck now clears group and other **write** from the directory itself — the `chmod go-w` the error message had been asking for, applied to the descriptor it already holds so it cannot be redirected — and confirms the result before writing anything. Read and execute are left exactly as they were, so a shared group still lists a directory it legitimately lists. A launch is refused only when those bits genuinely cannot be cleared: the directory belongs to another account, or the filesystem is read-only.

When it is refused, the message now says which directory, what mode it is in, and the exact command to run, on the machine running the deck. Previously neither the daemon's reply nor the desktop named the path at all, which took three failed launches and a filesystem-wide `find` to diagnose when the user had moved between projects between attempts.

See [Orchestration → The `.dot-agent-deck` directory](https://agent-deck.devopstoolkit.ai/docs/orchestration) for the full policy.
