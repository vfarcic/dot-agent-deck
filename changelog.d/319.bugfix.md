## The hook socket can no longer be used to exhaust the daemon

The daemon reads hook events as newline-delimited JSON, and it read them with no limit of any kind. A peer that connected and sent bytes without ever sending a newline had those bytes buffered indefinitely, so the daemon's memory grew until the process died and took every pane's agent with it. Separately, every accepted connection got its own task with no cap on how many could be outstanding, so a flood of connections reached the same end by a different route. Fixing either one alone left the other open.

Both are now bounded. A single hook line is capped at 64 KiB — comfortably above a real event, which measures 300–900 bytes even with a long shell command attached, and far below anything that threatens the daemon. A peer that exceeds it has its connection **closed**; the bytes are never truncated and re-parsed, because a padded prefix must not be able to smuggle a short valid event in behind it. Concurrent hook connections are capped at 128, and an excess connection is closed promptly rather than queued, so the accept loop stays responsive and the connections already inside the cap keep delivering. The worst case the daemon can now be made to hold is 8 MiB, less than a single frame it already accepts on its other socket.

Nothing changes for a legitimate agent: hook events are small and short-lived, and the caps are an order of magnitude past anything a real fleet produces.
