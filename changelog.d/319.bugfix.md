## The hook socket's reader is bounded, and a stalled peer can no longer wedge it

The daemon reads hook events as newline-delimited JSON, and it read them with no limit of any kind. A peer that connected and sent bytes without ever sending a newline had those bytes buffered indefinitely, so the daemon's memory grew until the process died and took every pane's agent with it. Separately, every accepted connection got its own task with no cap on how many could be outstanding, so a flood of connections reached the same end by a different route. Fixing either one alone left the other open.

Both are now bounded, and so is time. A single hook line is capped at 64 KiB — comfortably above a real event, which measures 300–900 bytes even with a long shell command attached, and far below anything that threatens the daemon. A peer that exceeds it has its connection **closed**; the bytes are never truncated and re-parsed, because a padded prefix must not be able to smuggle a short valid event in behind it. Concurrent hook connections are capped at 128, and an excess connection is closed promptly rather than queued, so the accept loop stays responsive and the connections already inside the cap keep delivering.

A cap alone would have traded one problem for another. Because a connection holds its slot for as long as it is open, 128 peers that connect and *say nothing* — or that trickle bytes forever without ever completing a line — could deny the socket to everything else, with no memory pressure and no recovery short of restarting the daemon. So the daemon now gives up on a connection that has not produced a complete line within 30 seconds, and on a reply it has not managed to write within 10. Every legitimate producer writes its line in one go immediately after connecting, so neither deadline is reachable by ordinary traffic; work the daemon does *for* a request (a dispatch that creates a worktree and spawns an agent, say) is not measured against them.

What that bounds is the **transport**: the reader's own buffers, across all connections, now total at most 8 MiB, less than a single frame the daemon already accepts on its other socket. It is not a claim about everything a peer can make the daemon hold — accepted events still create application state, and a peer sending valid events for an endless series of new session ids grows that without a bound of its own. That is pre-existing and tracked separately; it is named here so the number above is not read as more than it is.

Two smaller things came out of the same review. A hook line that the daemon logs — an unrecognized event type, or a payload it could not parse — now has any capability token taken out of it and is cut down to a 512-byte prefix, marked with how much was dropped, so a valid token can no longer be written verbatim into a log file that outlives the agent, and a peer looping malformed input can no longer grow the log 64 KiB at a time. A payload the daemon *could* read is rebuilt from the parsed record rather than scanned as text, so a token cannot be hidden from the redaction by spelling its field name differently. The warning for a refused excess connection is likewise rate-limited, with a count of what it suppressed.

Nothing changes for a legitimate agent: hook events are small and short-lived, and the caps are an order of magnitude past anything a real fleet produces.
