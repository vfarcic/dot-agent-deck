## Reattaching puts you back where you were — same tab, same agent

Detaching and reconnecting used to land you somewhere you did not choose. The active tab reset to the deck's own landing default, and every tab reset its focused pane to that tab's start role — so on a multi-role orchestration you were dropped into the orchestrator rather than the worker you had been reading, every single time. Focus was purely in-memory state: nothing wrote it down and nothing carried it across an attach, so a fresh TUI process had no way to know where the previous one had been. It was not remote-specific either, even though that is how it was reported — the same code runs for a local attach, and a local detach/reattach lost the position identically.

The deck now records your position in its saved session, so reattaching to a daemon that still holds your agents restores the tab that was active and the pane each tab had focused. Coming back onto a background orchestration tab shows the role you left it on, not its start role. If you were on the Dashboard when you detached, you come back to the Dashboard: that is a real choice and is now honoured, where before a reconnect with any orchestration open always jumped into it. Nothing is remembered when there is nothing to remember — a deck that never left the Dashboard writes no position, and the reconnect landing you already know stays exactly as it was.

Positions are re-checked against what is actually running when you reattach. A pane you closed in the meantime, or a role whose agent finished and exited while you were away, is simply not restored and that tab falls back to its start role as before — you are never dropped into a dead pane. The one case that deliberately restores less is a cold start against an *empty* daemon, where the deck rebuilds your panes from disk rather than adopting live ones: those panes are new, their identifiers are not the ones that were remembered, and honouring a remembered identifier there could put you in a different agent rather than merely the wrong one. A cold start therefore restores which kind of tab you were on and leaves the rest to today's behaviour.

The position lives in the deck's own saved session rather than in the daemon, so it survives a daemon restart and no client's focus move relocates another running client's view. The saved session is one file per machine account, though, and always has been: two decks running under the same one overwrite each other's snapshot wholesale — the pane list and the remembered command as much as the position — so the last one to exit decides where the next attach lands. No configuration or action is needed, and no compatibility contract moved: the field is optional in `session.toml`, so a session file written by an older build still loads and simply has no position to restore, and an older build reading a newer file ignores it.
