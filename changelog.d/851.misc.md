## `dispatch_018` and `dispatch_019` wait for the PTY instead of sleeping 75 ms

`build-windows` is one of the four **required** status checks, so unlike the advisory `e2e-deterministic` lane a flake there actually blocks a merge. On PR #830 it failed on two fast-tier unit tests at once — `spawn::tests::dispatch_018_user_input_disarms_detached_submit_probe` and `spawn::tests::dispatch_019_writer_release_does_not_expose_unstamped_user_input` — and re-running the same job on the same commit with no code change passed. Both panics were on a *precondition*, not on the property under test, and in both the pane snapshot held nothing but the mode-set escapes the pane emits at startup, i.e. the write had not propagated yet rather than gone wrong. `src/spawn.rs` was byte-identical across the PR head, `main` and the merge; `build` and `build-macos` passed on the same commit.

The mechanism was a fixed sleep where the module already had a poll. Each test wrote to a real PTY and then, after `tokio::time::sleep(Duration::from_millis(75))`, asserted the bytes had physically reached the pane — a bet on a PTY round trip beating that constant, with nothing waiting for the bytes to become observable. The fast tier sets `retries = 0` and no `.config/nextest.toml` override covers either test, so one lost bet reddens a blocking check. This is the same defect [#850](https://github.com/vfarcic/dot-agent-deck/issues/850) fixed for `dispatch_020`, on the two sites that fix did not reach, and it is fixed the same way: with the content-keyed bounded polls the module already has, which are keyed on the bytes being waited for and bounded only by a diagnostic deadline, so load makes them slower rather than wrong.

`dispatch_018` now waits for attempt 1's own echo through `wait_for_detached_payload_echo`. `dispatch_019` gets two halves, and neither is redundant: `wait_for_echo_bytes` replaces the sleep before the user draft's precondition, and `wait_for_drained_lines` drains the initial delivery **before** that draft is written. The drain is the half that looks like tidiness and is not — the byte target and the line discipline's echo are two independent writers into one PTY output queue, and the copy of an earlier line still in flight lands inside the exact-equality window at the end of that test, where it reads as bytes the refused retry sent.

Reproduced before fixing, since the issue was filed from one CI log. `dispatch_019` needed no production change at all: with its sleep at 0 ms under 4x CPU oversubscription it failed **14 of 15** runs, carrying the exact CI message. `dispatch_018` has an incidental 150 ms head start — production's `SUBMIT_DELAY`, which `write_and_submit_guarded` spends between the payload write and the submit CR — and survived 0 ms at 20x oversubscription and a fork storm; with that head start removed it failed **2 of 12** at 4x, again with the exact CI message. After the fix, at the same 4x load: `dispatch_019` **0 failures in 30**, `dispatch_018` **0 in 12** with the head start still removed. With the drain alone disabled `dispatch_019` fails **4 of 30**, at the final exact-equality assertion rather than the precondition — which is how the second half was shown to be load-bearing rather than assumed.

Windows verification is CI's: these are `#[cfg(test)]` unit tests in the fast tier, so `build-windows` runs them on every PR, and no local gate can replace it. Each of the three helpers this change calls is already exercised on Windows today by a test that passes that job — `wait_for_detached_payload_echo` by `scheduler/dispatch/016`, and both others by `scheduler/dispatch/020` since [#850](https://github.com/vfarcic/dot-agent-deck/issues/850). `scripts/windows-cross-check.sh` type-checks the workspace for `x86_64-pc-windows-msvc` with no errors.

Scope is deliberate. Five positive-arrival assertions in the same module are still bounded by a fixed sleep, including one inside `dispatch_018` itself with 800 ms of budget; they are enumerated for follow-up in [#892](https://github.com/vfarcic/dot-agent-deck/issues/892) rather than folded in here. Every hunk is inside `#[cfg(test)] mod tests`, so no shipped behaviour changes: no wire shape moved and no field's meaning shifted, so `PROTOCOL_VERSION` needs no bump and no `breaking` fragment applies. `tests/CATALOG.md` is unchanged — `scheduler/dispatch/018` and `/019` still assert exactly what they did, and only the fixture's synchronisation changed.
