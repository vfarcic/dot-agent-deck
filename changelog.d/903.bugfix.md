## The daemon's hook socket no longer reads or accepts without a limit

The daemon read each line on its hook socket with `next_line()`, which grows its buffer until a newline arrives or the peer goes away. Every managed agent has same-user access to that socket, so a compromised or simply buggy producer could send an arbitrarily large newline-free payload and make the daemon allocate a `String` of whatever size it chose — and then, if the payload did eventually parse, make `serde_json` allocate the fields on top of it. None of this was behind any admission control: the allocation happened before anything decided whether the event was even for a pane this daemon owns, so an event that was going to be discarded cost exactly as much as one that was going to be applied. Separately, every accepted connection got its own spawned task with nothing capping how many could be outstanding, so a producer that opened connections faster than they finished grew the task set and its per-connection buffers the same way. The practical failure was a daemon allocating until the OOM killer took it, and losing the pane role maps that live only in its memory with it.

Both are now bounded. A hook-socket line is capped at 8 MiB and **refused rather than truncated** past it: the connection is dropped with a warning naming the limit and how far over the line ran. Refusing matters more than the bytes saved — a prefix of a JSON object can parse, so truncating would risk applying a half-populated event rather than none. The cap is inclusive, so a line of exactly 8 MiB is still accepted, and it is deliberately generous: the largest message any producer this project ships puts on this socket is a `delegate` or `work-done` carrying task text, which is already capped at 1 MiB on the sending side, and everything else on the wire is small by construction — every bundled hook adapter, Claude Code's and Codex's and Devin's and OpenCode's alike, funnels through the same `dot-agent-deck hook` command, which truncates the prompt and shortens the tool detail before sending. The number is eight times that ceiling, which is the headroom JSON string escaping needs.

Concurrent hook connections are capped at 32, and the cap is **backpressure, not admission control**: at the limit the daemon stops accepting, and the next producer's connection waits in the kernel's listen backlog until a slot frees. A hook send is a connect, a small write and an exit, so the producer does not block — its line sits in the socket buffer and is read when the daemon gets to it. The daemon discards nothing; an event behind a burst is delayed. The one loss case left is a burst deep enough to fill the listen backlog too, where `connect` fails at the producer — which is a better place for it to surface than a write that appears to succeed into a daemon that will never read it. Rejecting the connection instead would have been simpler and would have thrown away a legitimate event every time a burst outran the cap.

Neither bound moves the wire. No message type, field, or field meaning changed, and the hook socket is not the versioned TUI↔daemon attach protocol — so `PROTOCOL_VERSION` is untouched. Nor is either bound reachable by a message an older build can construct through the shipped CLI: an older `delegate` or `work-done` is bound by the same 1 MiB task cap it always was, an older hook adapter truncates its fields before sending, and neither opens hook connections concurrently enough to queue behind the connection cap. In the other direction a newer CLI sending to an older daemon meets the old unbounded reader, unchanged.

A connection is also reclaimed if it goes a minute without completing a message, and that bound is part of the cap rather than an extra: capping the slots is what made a stalled connection expensive. Before it, a peer that connected and never wrote cost one parked task and ingest carried on around it; with 32 slots, 32 such peers would stop ingest altogether, so the cap on its own would have traded an unbounded-memory failure for an availability one that is cheaper to reach. Nothing legitimate comes near the minute: every producer shipped here is single-shot — it connects, writes one line and closes, and the reply-bearing verbs read their one reply under their own five-second bound before closing. Because the timer covers *one message* rather than the connection's life, it also reclaims a peer that dribbles bytes without ever finishing a line, and it restarts per message, so a producer that holds one connection open and streams events is unaffected as long as its gaps stay under a minute.

Two things this deliberately does not do. It does not name the offending producer in the refusal, because the pane id is inside the payload that was just declined and the only identity available at that point is the peer's OS credentials — binding hook-event provenance is a separate open issue. And it does not tell a peer that behaves *just* well enough — one message a minute, or a reconnect each time a slot frees — apart from a real producer, which needs to know which producer it is and so belongs with that same provenance work.
