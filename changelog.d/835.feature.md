## A scheduled task can now choose its spawn shape

`[[scheduled_tasks]]` entries take an optional `shape`, and `schedule add` / `schedule update` take a matching `--shape`. It settles what a fire opens, instead of leaving that entirely to the target directory:

```toml
[[scheduled_tasks]]
name = "pr-sweep"
cron = "0 9 * * *"
working_dir = "/home/you/code/your-repo"
command = "claude"
shape = "single"                    # ONE agent, even though this dir defines [[orchestrations]]
# shape = "orchestration"           # that dir's default orchestration
# shape = "orchestration:anthropic" # a named one
# (omitted)                         # unchanged: derived from the dir's config
```

**What this fixes is a silent one.** Before, the shape came from `working_dir` alone, so a schedule pointed at a repo defining `[[orchestrations]]` fired the **whole team** and ignored its own `command` — and nothing said so. Not the config, not `schedule list`, not the CLI; the only way to find out was to read the source. That hit the natural case for a scheduled sweep: you want the repo as `working_dir`, because that is where the repo's `.claude/skills/` load and where `git` has to run, and you want **one** agent to do the job. Those two were mutually exclusive. `shape = "single"` is that combination, and `command` finally takes effect.

`schedule list` now prints the shape of every task — `shape=config-derived` when unset — so the surprise above is visible without reading code.

A `shape` naming an orchestration the directory does not define **abandons the fire** and says so, listing what is available. It never falls back to another shape: quietly spawning something other than what you asked for is the behaviour this field removes, and a fallback would reproduce it with extra steps. A typo'd value is rejected when the file loads, naming the task, rather than surfacing on the next cron tick.

Existing schedules are untouched. With no `shape`, the fire takes the same config-derived path it always did.
