## The TUI-side pane maps now say, at each site, why they omit `pane_orchestration_map`

Five places in `src/ui.rs` register an orchestration's role panes into `pane_role_map`, `pane_cwd_map` and `orchestrator_pane_ids` and deliberately leave `pane_orchestration_map` empty: the two registrations in `surface_one_orchestration` (PRD #120's live orchestration surface), the `Action::SpawnPane` orchestration branch, the reconnect-hydration rebuild, and the daemon-empty snapshot restore. That omission is correct — the TUI process does not route, so it has nothing to scope — but it was written down nowhere, which made it look like an oversight waiting to be "fixed".

Each site now carries a comment, one of them the full reasoning and the other four citing it. The reason is recorded rather than just the instruction, because the failure mode is silent: `delegate_targets` scopes each candidate with `self.pane_orchestration_map.get(pane_id.as_str()) == orchestration`, so with every pane absent from the map both sides are `None` and the comparison degenerates to `None == None` — true for *every* pane. Anything that moved routing back TUI-side without populating the map first would fan one delegate out across every orchestration tab at once, and `orchestrator_for_worker` would resolve by `HashSet` iteration order: the cross-delivery class PRD #140 closed, reintroduced from the other direction, and passing any test that exercises a single orchestration.

One stale comment went with it. The `Action::SpawnPane` site read "Register pane-to-role and pane-to-cwd mappings for work-done resolution", a leftover from the pre-PRD-#93 model in which the TUI drained `work_done_events` and resolved them itself; it now names the daemon as the owner of that resolution. `AppState::pane_orchestration_map`'s own doc comment gained a line saying the field is daemon-only in practice.

Comments only — no behaviour, no tests, no wire change.
