## Registering a schedule now makes the desktop's project picker notice

The deck works out which projects it knows about from four things: its own startup directory, every live agent's working directory, every orchestration role's, and **every registered schedule's**. The desktop app re-lists projects automatically when the first three move — but no schedule information reached the app at all, so it could not react to the fourth. Add a schedule (from the TUI or `dot-agent-deck schedule add`) in a directory the deck has nothing else running in, and the new project was missing from the **Projects** picker until you pressed **Refresh**.

**The deck now reports one number and the app watches it.** It is a counter that goes up whenever the registered schedule set changes — nothing about the schedules themselves travels, because the app shows no schedules and should not be sent any. The picker re-lists when that number moves, and does not when it does not: a reload that changes nothing leaves it alone, so this does not turn into a refresh on every event.

**Refresh still works and is still the remedy where it has to be.** Against a deck too old to report the number, the app behaves exactly as it did before this change.

Nothing in the protocol's shape moved: the counter is a new optional field on the agent-list reply the app already polls, so an older deck sends nothing and a newer one sends a key an older client ignores. `PROTOCOL_VERSION` is unchanged.
