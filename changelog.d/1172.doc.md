## How to keep a macOS remote host's deck running across a reboot

`docs/remote-requirements.md` tells Linux users to set up `systemd --user` and `loginctl enable-linger` so the daemon survives logout and restarts after a crash. macOS has no counterpart, and the page said only that this was a gap. It now documents the launchd equivalent, the same way it documents the systemd one rather than shipping a unit file.

A `~/Library/LaunchAgents/` plist with `RunAtLoad` and `KeepAlive` supplies what the systemd unit supplies — start on login, restart on crash. The page gives the plist, the `launchctl bootstrap` line to load it, and the three things that are easy to get wrong:

- **A LaunchAgent, not a LaunchDaemon.** A LaunchDaemon runs in the system context with no user session, so it forfeits the user's environment and credentials — including the `~/.claude/.credentials.json` that Claude Code's one-time `/login` exists to create.
- **A LaunchAgent starts at GUI login, not at boot.** An always-on Mac with nobody sitting at it therefore needs auto-login to come back unattended, and auto-login interacts with FileVault, whose encrypted disk wants a password at startup before any automatic login can happen. A real tradeoff, stated rather than left to be discovered.
- **launchd does not source your shell profile.** The daemon repairs its own `PATH` at startup from an interactive login shell, so `~/.local/bin` resolves either way — but nothing else does, so anything the agents need from the environment belongs in the plist's `EnvironmentVariables` rather than in `~/.zshrc`.

**Written as "here is how to arrange it", not as "after a reboot X happens".** Reboot behaviour on macOS has not been tested, so the recipe is presented as a starting point and the section says so. Whether the deck should ship a plist of its own is still open, in [#1172](https://github.com/vfarcic/dot-agent-deck/issues/1172).
