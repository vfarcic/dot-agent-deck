## The doorbell checks for a dialog, a draft or an agent it can't read before it types

When an agent's own wake-up wasn't working, the deck typed its doorbell line into the agent's pane whenever the agent reported it was idle. The line could land in a dialog that had just opened, beside text you were typing, or in an agent whose screen the deck could not read, and an Enter could submit something other than the deck's line.

Now the deck types the doorbell only into a Claude Code version it has measured or into Codex 0.164.0, and only while the agent's input box is on screen, empty, and untouched since the deck last knew it was empty. Once anything has been typed into the box (text, spaces or empty lines that Claude Code draws nothing for, arrow keys, Escape), the deck can't tell from the screen that the box is empty again, so it checks the box before it types, and rings once a check finds it empty: clear the box any way you like. It can do that for Claude Code started directly in the pane on Linux; for Claude Code started through a launcher script, or running on macOS, where the deck has no input-box check yet, it can't, so it no longer types into that agent until the agent restarts, and every later message waits the same way: the TUI card and the desktop tile say `waiting: ask the agent to run dot-agent-deck inbox fetch; reinstall the deck integration to restore automatic delivery`. Ask the agent to run that command in its pane, or send it a prompt. The deck's own line, once the agent took it, doesn't count as typing, so an agent nobody types into keeps getting the doorbell. The line starts with six letters in brackets, drawn afresh each time, such as `(bmrtzx) dot-agent-deck: message m-… waiting, run: dot-agent-deck inbox fetch`. The deck checks that the line reached the input box intact before it presses Enter, and that the agent took it afterwards. If it sees anything change on the way, it presses no Enter, although a dialog that opens just after its last check can still receive the Enter; when it cannot be sure where its line went, it types nothing more into that agent until you submit or clear its input box and a check finds the box empty (where it can't check the box, until the agent restarts), and the TUI card and the desktop tile say so. Keys you type while the deck is typing are sent after it, exactly as you typed them. The deck also waits to start its line while a paste you are sending, or a key sequence it recognises as unfinished, is still arriving. When such a sequence is left unfinished, such as `Alt+]` in a terminal that sends it as the start of a sequence, the doorbell waits until you finish or cancel that key sequence; in a Claude Code version the deck has measured, `Ctrl+U` or Enter typed after an unfinished cursor key cancels it, and the deck then checks the box before it types. For an agent the deck can type into, when its pane is resized while a message waits, the deck first gives the agent the time it usually takes to redraw by itself, and only then asks it to redraw by narrowing its pane by one column and restoring it; an agent whose own redraw the deck sees in that time gets no such extra resize, and its message goes in once that redraw and the deck's other checks allow it.

The deck does not type the doorbell into OpenCode, Pi or Devin, or into a Claude Code or Codex version it has not measured: of Codex it types only into 0.164.0, and only while nothing has been typed into that Codex's pane since it started, so a delegated Codex worker on 0.164.0 takes its task without a prompt. In a small pane, such as 80 columns by 24 rows, a Codex that has just started is not rung before its first prompt: its card and tile say `not yet taken: the agent may be waiting at a prompt. Check its pane.`; send it a prompt. The `doorbell off` line in the deck log names the versions it types into. Their native wake-up, where there is one, still delivers. When nothing does, the agent's messages wait, and its card and tile say `waiting for the agent to fetch it. Send it a prompt.`: type a prompt in the agent's pane, in the TUI or the desktop app, and its hooks, plugin or extension hand it the messages at that turn; where that integration isn't connected, ask the agent to run `dot-agent-deck inbox fetch`. For an agent the deck won't type into, `dot-agent-deck daemon status` shows `none` under WAKE, and an orchestrator's notice that a task has not reached its worker says the same, except while the agent's own wake-up is armed (`native`) or it will take its messages when its current turn ends (`turn-end`). Other new card reasons say when the agent did not take the deck's Enter, when the deck's line may still be in the input box, and when a dialog may have taken the deck's keys. Codex's card says `waiting for the agent to fetch it. Send it a prompt.` once something was typed into its input box, too, and stays that way until the agent restarts: the deck can't check a Codex agent's input box, so every later message waits the same way.
