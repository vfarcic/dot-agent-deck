## The doorbell checks for a dialog, a draft or an agent it can't read before it types

When an agent's own wake-up wasn't working, the deck typed its doorbell line into the agent's pane whenever the agent reported it was idle. The line could land in a dialog that had just opened, beside text you were typing, or in an agent whose screen the deck could not read, and an Enter could submit something other than the deck's line.

Now the deck types the doorbell only into a Claude Code version it has measured, and only while the agent's input box is on screen and, as far as the deck can tell from the screen and from what was typed into it, empty, so it also waits for spaces or empty lines you typed that Claude Code draws nothing for. After you used Up, Tab, a long paste, an `@` file reference or text that is not plain ASCII in the input box, the deck waits until Claude Code reports the prompt your Enter sent; to let the doorbell go ahead, type any letter in the box and press `Ctrl+C` once, which clears it without sending anything, or type a prompt and send it. The line starts with six letters in brackets, drawn afresh each time, such as `(bmrtzx) dot-agent-deck: message m-… waiting, run: dot-agent-deck inbox fetch`. The deck checks that the line reached the input box intact before it presses Enter, and that the agent took it afterwards. If it sees anything change on the way, it presses no Enter, although a dialog that opens just after its last check can still receive the Enter; when it cannot be sure where its line went, it types nothing more into that agent until you submit or clear its input box, and the TUI card and the desktop tile say so. Keys you type while the deck is typing are sent after it, exactly as you typed them. The deck also waits to start its line while a paste you are sending, or a key sequence it recognises as unfinished, is still arriving; after an Escape on its own it types as it did before. In the rare case such a sequence is left unfinished, such as `Alt+]` in a terminal that sends it as the start of a sequence, the doorbell waits until keys you type end it.

The deck does not type the doorbell into Codex, OpenCode, Pi or Devin, or into a Claude Code version it has not measured. Their native wake-up, where there is one, still delivers. When nothing does, the agent's messages wait, and its card and tile say `waiting for the agent to fetch it. Send it a prompt.`: type a prompt in the agent's pane, in the TUI or the desktop app, and its hooks, plugin or extension hand it the messages at that turn; where that integration isn't connected, ask the agent to run `dot-agent-deck inbox fetch`. For an agent the deck won't type into, `dot-agent-deck daemon status` shows `none` under WAKE, and an orchestrator's notice that a task has not reached its worker says the same, except while the agent's own wake-up is armed (`native`) or it will take its messages when its current turn ends (`turn-end`). Other new card reasons say when the agent did not take the deck's Enter, when the deck's line may still be in the input box, and when a dialog may have taken the deck's keys.
