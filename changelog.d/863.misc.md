## Concurrent builds across worktrees no longer saturate a shared box

Nothing bounded how much building happened at once on a machine running several dispatch agents, each with its own worktree and its own `target/`. Measured on a 16-core / 27 GiB box: two concurrent `cargo test --no-run --workspace` runs plus a third starting later drove PSI `io full avg300=65.95` — for roughly two-thirds of a five-minute window **every** runnable task on the box was blocked on disk — with `dm-0` at 100% utilisation, `aqu-sz` 48, and 13 processes in `D` state almost all `ld`. `ld` then invoked the OOM killer, which took out `systemd-resolve`, `apparmor_parser`, `upowerd` and `wpa_supplicant` and left seven failed units behind. The CPU was idle throughout at `cpu some avg300=0.08`, which is why load average — 24-28, and counting every one of those `D`-state tasks — described the symptom and none of the cause.

`.cargo/config.toml` now points the Linux target's `linker` at `scripts/link-gate.sh`, which takes one slot from a machine-wide pool before exec'ing the real linker driver with rustc's argv untouched. Cargo resolves that path relative to the directory holding `.cargo`, so every worktree runs its own copy of the script while all of them contend for the **same** pool — the quantity being bounded is concurrency *across* worktrees, which is exactly what `-j` and `build.jobs` cannot express, since each bounds one invocation and nothing coordinates invocations.

**The bound is on links rather than on whole builds or on dispatch, and that placement is the substance of the change.** The deck never invokes cargo — `grep -rn '"cargo"' src/` finds nothing — so the dispatch scheduler cannot see a build to bound; what it can bound is agents, which `max_per_run` already does, and agent count is a poor proxy in both directions, since an agent spends most of its life editing while one agent running `cargo test-e2e` links about a hundred binaries by itself. Gating whole `cargo` invocations would have worked but would serialise builds that mostly are not linking, making a second agent wait out a ten-minute compile to reach a link it could have run immediately. Linking is where this workspace's I/O and memory actually go: measured here, one relink of every test binary in a **single** worktree peaked at 60 concurrent linker processes holding 8.3 GB resident.

Against that same relink, the gate at its computed default of 6 slots holds this worktree at 24 linker processes and 3.8-4.1 GB — measured over four runs alternating the gate off and on, where the ungated runs peaked at 60 processes and 8.3-8.6 GB both times. **What those runs do not establish is an effect on wall-clock time or on box-wide PSI**, and it is worth saying so plainly: two other agents were building unbounded throughout, their load varied about fivefold between the two pairs, and neither column separates the gate from them. A single build's wall time under the gate is a genuine open question — bounding links can only slow a build that is link-bound, and a relink of every test binary is the worst case for it. The measured claim is the footprint, not the speed.

The structural point is what the footprint buys, and it too is by construction rather than by measurement, since only this worktree carried the change while the others built against `main`: ungated, link memory scales with the number of concurrent builds, so three of them is more than a 27 GiB box has. Gated, three builds draw from the same six slots, because the pool is one fixed directory and `flock(2)` works across unrelated processes. Verified live during a three-way build storm: with three worktrees compiling at once, this one sat at exactly its six slots.

The slot count is derived from the machine rather than pinned to the box it was measured on — one slot per 4 GiB of RAM, never more than the core count, never fewer than one — so a 4-core CI runner lands at or above its own `-j` and the gate is inert there. It is Linux-only by construction: the `linker` key is set for `x86_64-unknown-linux-gnu` alone, so `build-windows` and `build-macos` select different triples and a POSIX shell script can never become the difference between a green and a red required check on a platform with no shell to run it.

**Every failure path runs the build ungated rather than failing it**: no `flock` on PATH, a pool directory that cannot be created or written, a missing or non-executable gate script, a slot count of `0`/`off` or one that is not a number, or a wait budget that expires — the last of which is what bounds the hang, so even a pool wedged by some future bug costs a delay and never a red build. There is no stale-lock path to recover, by construction: `flock(2)` locks are released by the kernel when the last descriptor closes, including on SIGKILL and OOM-kill, which matters here because the storm this exists for ends in an OOM kill. `DAD_LINK_JOBS=0` is the kill switch, `DAD_LINK_JOBS=N` sets the slot count, and `DAD_LINKER` restores a personally-configured linker driver that the repository's `linker` key would otherwise override.

Sixteen tests in `xtask/linkage-check/src/build_gate.rs` cover it in the fast tier — ~3.5s together — because the whole value is runtime behaviour and a compile-time gate proves nothing about it, the same class CLAUDE.md rule 5 records for `clean_tmp.rs`. They pin the bound itself, that `--jobs 1` genuinely serialises while three slots do not, exit-status transparency, verbatim argv forwarding to the real linker, a sane computed default for the host machine, that the pool's location does not follow `$TMPDIR` (which varies per process — this repository's own e2e harness relocates it — so deriving the pool from it would hand two agents two private pools that each look like they are working while bounding nothing), that `.cargo/config.toml` still routes links through the gate at all, and one test per rung of the degradation ladder including a SIGKILLed holder leaving no stale slot.

Adding the `linker` key changes every rustc command line, so the first build after this lands is a full rebuild — a one-time cost per target directory. Two of issue #863's four candidate mitigations are deliberately left as follow-ups in [#864](https://github.com/vfarcic/dot-agent-deck/issues/864), together with a third lever the issue did not list — the untouched `[profile.dev] debug` setting, which is what makes a target directory 63 G and each of ~100 test binaries link the whole graph's DWARF. `sccache` and a shared `CARGO_TARGET_DIR` are about not doing the work twice where this is about not doing it all at once, and the issue asks for them to be measured against each other rather than assumed. [`docs/develop/build-gate.md`](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/build-gate.md) has the full rationale, the measurements, and the escape hatches.
