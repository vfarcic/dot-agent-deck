## Cutting a release no longer needs a human to bypass the protected `main`

Releasing used to begin with a maintainer bumping the `flake.nix` version pin, committing it, and pushing straight at a ruleset-protected branch. That succeeded — the `main-protected` ruleset lists `RepositoryRole/always` as a bypass actor, so it printed `remote: Bypassed rule violations for refs/heads/main` and went through, which CLAUDE.md rule 8 names as worse than a rejection. Every pin from `v0.39.1` to `v0.40.1` landed that way. Nothing under `src/` is involved and no TUI↔daemon contract moves, so `PROTOCOL_VERSION` is untouched and rule 12's cross-version check does not apply.

**The pin and the tag now belong to a workflow.** `.github/workflows/tag-release.yml` is a `workflow_dispatch` that re-derives the version from the changelog fragments, bumps the pin, commits it to `main` and creates the tag — pushing under the `RELEASE_TOKEN` admin PAT that `release.yml` and `docs-publish.yml` have used for their own direct pushes since 2026-08-11. No new secret, no new bypass actor, no ruleset change. It has to own the tag as well as the pin, because a workflow triggered *by* a tag cannot create the commit that tag points at; the commit itself is unavoidable, since Nix exposes `rev` but never tag names, so a source build with no pin falls back to Cargo.toml's `0.1.0` placeholder.

**The pin commit deliberately carries no `[skip ci]`.** It is the commit that gets tagged, and GitHub skips workflow runs for a push whose head commit carries a skip marker — a tag push included — so a marked pin would mean no release at all. Leaving it off also means `ci.yml` now runs against the exact tree being released, which did not happen for `v0.40.1`. The old skill's empty-preparation-commit step survives inside the workflow for the one case where it is still needed: when the pin is already correct no commit is made, so the tag would land on whatever `main`'s tip is — and `docs-publish.yml` ends every release by committing `chore: update docs chart to <tag> [skip ci]`.

**The human checkpoint is kept as an explicit assertion rather than a confirmation prompt.** The dispatch takes the version as a required input and refuses when it disagrees with what the fragments compute, so the operator has to state the version they believe they are cutting instead of confirming one they have not seen. The version alone does not bind the checkpoint to a *tree*, though — a fragment of the same bump class merging between the review and the dispatch leaves the computed version identical — so the dispatch also takes the `main` SHA that was inspected and refuses when `main` has moved, and the run's summary lists the fragments it actually released. An `allow_mismatch` input covers a deliberate override. `release.yml`'s pin/tag consistency check is kept as a cheap backstop but now guards less than it did: it used to catch a forgotten manual bump, and on the automated path it compares one output of a workflow against another output of the same workflow.

**`dot-ai-tag-release` is forked to the project-local `tag-release`**, following issue #1052's precedent and renaming rather than adding, so no second release procedure is left beside the first. The urgency was not tidiness: the skill's Step 4 was added *locally* three weeks after the last sync and was carrying the instruction that stops a released binary reporting `0.1.0`, whose absence costs a deleted remote tag. Rule 13 records what the next sync does to a local edit in a `dot-ai-*` mirror. `analyze.sh` is kept whole — its pre-1.0 recalibration is what `docs/develop/versioning.md` cites as the implementation of its bump table — and now has two callers running the same code: the maintainer, to see the proposed version, and the workflow, to re-derive it.

**Two bugs in the cleanup step are fixed, one of them measured on this repository.** The skill told the operator to delete merged branches with `git branch -d` "as a safety net", but `-d` tests ancestry and a squash merge never lands a branch's commits on `main`, so it refuses every correctly squash-merged branch and hints straight at `-D` — on 2026-09-14 it would have refused all 13 correctly-merged dispatch branches, which is how a safety net becomes a reflex. `cleanup.sh` already had the check that works, from merged-PR state rather than ancestry; it now emits the tip SHA it vetted beside each branch so the delete can confirm the branch has not moved, and the skill uses `-D` gated on that comparison. Separately, `cleanup.sh` offered the **main checkout** for removal whenever it was run from a linked worktree: the worktree scan excluded only the current worktree, never the default branch, and `main` is by definition an ancestor of `origin/main`. `git worktree remove` refuses a main working tree, so the cost was a confusing failure rather than a deletion — but the list is what the operator confirms, and one that routinely contains the main checkout teaches them not to read it.

**`cleanup.sh` also runs on macOS now.** It was the one instance of the bash-4-only `declare -A` knowingly left behind by the #582 sweep, because a fix to a synced mirror would have been reverted rather than kept. Forking it retired that reason.
