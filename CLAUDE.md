# CLAUDE.md — dot-agent-deck

## PERMANENT INSTRUCTIONS

1. **Ask Before Creating Branches or Worktrees**: When starting feature work (including `/prd-start`), ask the user whether they want a worktree (`/worktree-prd`) or a regular branch. Never assume one or the other.
2. **Run `cargo fmt --check` and `cargo clippy --workspace --all-targets --features e2e -- -D warnings` Before Committing**: Always run both before creating any git commit. If fmt reports issues, run `cargo fmt` to fix them. If clippy reports warnings, fix the code. Stage any fixes before committing.

    **All three flags are load-bearing** — `--all-targets` and `--features e2e` per issue #407, `--workspace` per issue #436. The old rule said `cargo clippy -- -D warnings`, which type-checks *no test file at all*: without `--all-targets` cargo builds only lib and bin targets, and every one of the 62 `tests/e2e_*.rs` files opens with `#![cfg(feature = "e2e")]` (two with `#![cfg(all(feature = "e2e", unix))]`), so without `--features e2e` they compile to empty crates. An e2e-only change therefore passed the gate instantly and meaninglessly — measured by injecting a deliberate `E0308` into `tests/e2e_handshake.rs`: `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` both exited 0, and only the feature-enabled command caught it. `cargo fmt --check` is *not* affected — rustfmt is cfg-blind and walks the cargo target list, so it has always covered these files.

    The one command is a strict superset of the old one: no `not(feature = "e2e")` cfg exists anywhere, and `src/` never references the feature. It is also **cheap**: cargo caches the feature-on and feature-off fingerprints side by side, so alternating this with `cargo test-fast` costs ~0.2s warm; a from-scratch re-check of all 62 e2e targets is ~14s.

    This is a *type-check and lint*, not the e2e tier — it spawns no binaries and hits no LLM APIs, so it does not conflict with rule 5's "do not run `cargo test-e2e` per task". Before this change, e2e code was clippy-linted by no gate anywhere and type-checked only by `cargo test-e2e`, the most expensive gate in the repo. The Linux CI `build` job runs the same command; `build-windows` / `build-macos` deliberately stay on bare `cargo clippy -- -D warnings` (see the comments there — the L2 tier is Unix-only and reports dozens of E0425s under the Windows target).

    **`--workspace` covers the `xtask/*` members** (issue #436). Cargo's default target selection is the root package alone, so `xtask/docs`, `xtask/linkage-check` and `xtask/spec` were linted by no gate anywhere. `xtask/spec` and `xtask-docs` are path dev-dependencies so they were at least *built*, but building is not linting, and `xtask/linkage-check` was not even built — which is how an `unnecessary_sort_by` sat in its `clean_tmp.rs` on `main` long enough to be discovered by an unrelated PR. That lint was fixed in the same commit that added this flag, so the widened gate landed green. The widening is **free warm**: measured back to back, `--workspace` and root-only both return in 0.20s once cargo has the fingerprints, since the three `xtask` members are small and dependency-light. Note `--workspace` does **not** change which features reach the root package, so this stays a strict superset of the pre-#436 command.
3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (e.g. `tests/event_forwarding.rs`), not for the milestone or PRD that introduced them (e.g. `tests/m2_17_event_forwarding.rs`, `src/prd76_*.rs`). Milestone tags belong in commit messages and the PRD doc — long-lived filenames must outlive the branch. Existing `m*_` test files are scheduled for cleanup; do not create new ones in that pattern.
4. **Add or Update TUI Tests for Functional UI Changes**: When a change adds or modifies user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, embedded panes, hook delivery), add or update tests in the TUI harness. Use L1 (in-process `TestBackend` + `insta`) for pure widget/layout changes; use L2 (PTY + vt100, files named `e2e_*.rs`, gated by `#[cfg(feature = "e2e")]`) when the change touches the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change do not require new tests. **For a major user-facing feature, include at least one PTY-attached L2 test** (the vt100 harness that drives the real binary, e.g. mirroring `scheduler/live/*`) that exercises the user-visible surface — not only headless daemon-serve (`RunNow`) tests. Only PTY-attached tests record a `.cast`, but a cast alone is **not** enough to be demo-reel-eligible: a clip must genuinely spin up a **real agent** (spawn → agent → work) **and** be explicitly opted in with a trailing ` [reel]` marker on its `tests/CATALOG.md` entry (PRD #180/#20 — see `.claude/skills/demo-reel-adapter`). A synthetic/stand-in PTY test (cat, scripted echo, recorder stubs, terminal-probe, synthesized hook events) is left unmarked and never becomes a clip even though it has a cast; a feature whose entire e2e coverage is headless (or unmarked) ships with no reel clip. (PRD #120's `issue_dispatch` is the cautionary case: `scheduler/dispatch/001-010` are all headless, so the showcase clip required adding the PTY-attached `scheduler/dispatch/011`.) **A major user-facing feature should also have at least one REAL-scenario e2e test** that drives the genuine spawn→agent→work path with a *real* agent on a **cheap model** (Haiku for Claude, a mini model for OpenCode) through a cheap, deterministic-enough operation — e.g. "list the files and report a known sentinel filename" — rather than relying solely on a stand-in like `cat`. We have historically over-relied on stand-ins; a stand-in proves the plumbing but never that an agent genuinely runs against the cloned/worktree/target state. Real-agent tests live in the **pre-PR e2e tier** (flaky-tolerant, never in CI per rule 5); make them robust with a directive prompt plus a uniquely-named fixture **sentinel file** so the assertion survives LLM phrasing/tool variance. **The bar is: at least one test per major feature must validate it AS A USER ACTUALLY USES AND SEES IT** — the genuine, user-visible experience end to end, e.g. a *live interactive* agent visibly working in the pane (with real status), not a non-interactive shortcut like `claude -p` and not a stand-in. Print mode and stand-ins prove the wiring; they do not prove the user-facing reality. Interactive headless agents are achievable — seed claude's onboarding + per-folder trust into the test HOME (see `prepare_claude_home` / the `TuiDeck` claude-trust seeding hook) and pass `--allowedTools` so no permission prompt blocks; `scheduler/dispatch/013` is the reference (an interactive Haiku agent listing the freshly-cloned repo live in the pane). Do not let "headless is hard" silently downgrade this bar where it is achievable.
5. **Fast Tests Per Task, E2E Before PR**: `cargo test-fast` (alias for `cargo nextest run --workspace`) runs the fast tier — protocol/state tests plus L1 widget/render tests — and is the per-task gate. `cargo test-e2e` (alias for `cargo nextest run --workspace --features e2e`) additionally runs the L2 PTY/real-agent suite and is required to pass before the release flow. Do not run `cargo test-e2e` per task; it spawns binaries, hits LLM APIs, and is intentionally bounded to the pre-PR step.

    **`--workspace` is load-bearing on both aliases** (issue #489, duplicate #470) — the test-side sibling of rule 2's clippy flag, and it was missing for exactly as long. The workspace root is itself a package and there is no `default-members`, so cargo's default target selection is the **root package alone**: every test in `xtask/linkage-check` and `xtask/docs` executed in **no gate anywhere** — not `test-fast`, not `test-e2e`, not CI, which runs the same commands. Measured: `cargo nextest run` selects 1657 tests, `--workspace` selects 1705. (`xtask/spec` is a workspace member too but currently has no tests, so the 48 come from the other two.)

    What made this gap survive #436 is that its **compile-time half was already fixed**: `cargo clippy --workspace --all-targets` *builds* those tests, so a type error or a lint in them still fails rule 2's gate. Only the **runtime assertions were inert** — a test could be gutted to `assert!(true)` and every gate stayed green. That is not academic for `xtask/linkage-check/src/clean_tmp.rs`, the `clean-e2e-tmp` reaper: it is a **deletion** tool whose safety properties (owned-prefix matching, opt-in untagged reaping, symlinks never followed out of the temp root) are runtime assertions and nothing else.

    **Free warm**, the same way rule 2's widening is. The 48 added tests run in **~0.07s** and every one is under 40ms, so they disappear into the existing parallelism. Measured back to back on a warm cache, the full tier is **26.4–26.9s** root-only and **25.3–26.7s** with `--workspace` — the difference is below the run-to-run noise, because the tier's wall clock is set by its slowest single test (~20s), not by its count. Warm target-selection cost is likewise indistinguishable (~0.9–1.5s either way). Every xtask test is in-memory or `tempfile::tempdir()`-based — none reads a repo file, touches the network, or sleeps — so they genuinely belong in the fast tier rather than being tolerated there. (Amended 2026-08-14 by issue #521: `verify_pr_stream.rs` is the one exception to "reads no repo file" — it runs `.claude/skills/verify-pr/scan.sh` under a stubbed `gh` to prove a hostile PR title cannot forge a record in its output, so it reads those scripts and shells out to `bash` and `jq`. Still no git, no network, no sleep, and all seven tests together take ~0.06s. Where `bash` or `jq` is absent the runtime half prints `SKIP:` and returns; the static half needs neither. Amended again 2026-08-22 by issue #648: `pin_lockstep.rs` is the second such exception, and for the same shape of reason — it drives `scripts/check-pin-lockstep.sh`, which compares the toolchain and `cargo-nextest` versions pinned in `devbox.json` against the ones pinned in `.github/workflows/`, so reading repo files IS the rule rather than a shortcut around one. Fourteen of its fifteen tests run the script against synthetic `tempfile::tempdir()` trees; the fifteenth runs it against the real checkout and is the guard itself, which is what puts a drifted pin in front of `cargo test-fast` and the three required build jobs instead of leaving it for whoever next diffs the two files by hand. Same budget as the others: no git, no network, no sleep, slowest single test ~0.3s and all fifteen together ~0.7s wall. Unix-only by `#[cfg]` — the pins it guards feed a devbox that has no Windows support, and `build-windows` running them would only add a Git-Bash path-translation failure mode to a check that is already covered twice over.)

    **One exception, and what it costs** (added 2026-08-15, issue #568): this paragraph used to also claim "none shells out to git", and the 14 tests in `xtask/linkage-check/src/repo_state.rs`'s `mod real_git` now do — they build real repositories with real `git` because the code they cover, `repo_state::collect`, is a collector whose entire job is shelling out to git. They earn the fast tier on the property the claim was really protecting rather than on its letter: each builds two or three empty-commit repositories inside a `tempfile::tempdir()` with the ambient git configuration switched off (`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` pointed at a nonexistent path, `HOME` and `XDG_CONFIG_HOME` inside the sandbox), so none of them can read or write the checkout it is running in, and none touches the network or sleeps. Measured on the same warm cache as the numbers above, and quoted as a range because these are the first xtask tests that spawn processes and so are the first sensitive to what else the machine is doing: the slowest single one is **0.1–0.2s** and the 14 together add **under 0.2s** on an otherwise-idle box, degrading to ~0.5s and ~0.4s respectively with all 16 cores saturated by a concurrent `--features e2e` build. Either way it is lost in the tier, which is **26.7–29.0s** with `--workspace` against **29.8s** without — the difference stays below the run-to-run noise, because the wall clock is set by one ~20s test and not by the count. The two alternatives were worse: the `e2e` tier is the one rule 5 tells you not to run per task, so parking the collector's only coverage there arrives back at no coverage by a slower route; and hand-written fixtures are exactly what left `collect()` untested through PR #558. This is a reason, not a precedent — a new xtask test still should not shell out to git without one as specific.

    **All three CI jobs carry the flag** — `build`, `build-windows` and `build-macos`. This is *not* the place where Windows/macOS deliberately diverge: rule 2 notes those two jobs stay on bare `cargo clippy -- -D warnings`, but that divergence is caused by `--all-targets --features e2e` (the L2 tier is Unix-only and reports dozens of E0425s under the Windows target), and `--workspace` is no part of it. The aliases live in `.cargo/config.toml` and apply on **every** platform, so a macOS or Windows contributor typing `cargo test-fast` now runs the xtask tests; if their CI job did not, a platform-specific break in them would be invisible on PRs and surface only on that contributor's machine — precisely the failure mode `build-macos` was added to close.
6. **Iterate on a Failing Test by Rerunning Only That Test**: When a single test fails, after fixing the code rerun *only that test* first (`cargo test-fast lifecycle_001` or `cargo test-e2e lifecycle_001`) to verify the fix in isolation. Decision 17's function-name prefix (`<sub-area>_<NNN>_…`) makes the filter pick exactly one test. Only after that test passes, rerun the full tier (`cargo test-fast`, plus `cargo test-e2e` pre-PR) before committing.
7. **Every `#[spec]` Test Has a Scenario Comment**: When adding or modifying a `#[spec(...)]`-annotated test in `tests/`, the test function MUST carry a `/// Scenario:` doc comment of 1–3 sentences describing in plain English what the test does — start the app, what gets pressed/sent/written, what should happen visibly. The `cargo xtask docs --tests` command regenerates a local `.md` under `.dot-agent-deck/recordings/<test>/test.md` (gitignored) that pairs with the cast for browsing during development. CI's linkage-check rule 7 fails the build if the Scenario comment is missing or the generator fails — not on local `.md` drift, since it isn't committed.
8. **Wait for Greptile's PR Review After Opening/Pushing a PR — and READ It Before Merging**: Greptile reviews every PR **once, when it is opened**. Since 2026-08-23 `greptile.json` sets `triggerOnUpdates: **false**`, so it does **not** re-review after you push fixes — do not wait for a second review that will never come. It publishes on **four** surfaces, and you need more than one of them:
    - a **check-run** named `Greptile Review` (app `greptile-apps`), which appears **pending** while the review is in flight and then completes — so `gh pr checks <n>` is the simplest way to know whether it is done;
    - a **summary issue comment** by `greptile-apps` (`gh pr view <n> --json comments`) carrying an overview and a confidence score;
    - a **PR review object** (`gh pr view <n> --json reviews`), typically state `COMMENTED`;
    - **inline review comments** carrying the actual findings, tagged by priority (P1/P2/…), which appear ONLY via `gh api repos/{owner}/{repo}/pulls/<n>/comments`.

    **The findings live in the inline comments, so a green check is NOT the review.** A `COMMENTED` review with a passing check-run can still carry real P1/P2 defects; verified on #286, where a passing Greptile check accompanied two valid findings (one already-tracked, one a genuine gap that shipped and needed the follow-up #287). Always read the inline comments before merging, and respond to each finding — fix it, or say why not.

    **Greptile has a capped monthly review quota, and silence usually means the cap — not a broken integration.** Measured 2026-08-23: it reviewed every PR from 2026-08-12 through PR #597 at 2026-08-18T13:58Z, then stopped dead — **zero** comments *and* **zero** check-runs on every PR afterwards, while the dashboard read exactly **300 used**. Note the shape of that failure, because it is misleading: an exhausted quota creates **no check-run at all**, so it looks identical to the app being uninstalled, and there is no message anywhere in the repo saying what happened. The cause was `triggerOnUpdates: true`: 94 PRs opened 1–18 August at ~3.4 commits each is ~320 review triggers against a 300 cap, so the quota bought deep coverage of the first ~88 PRs and **nothing** for the rest, with the cutoff falling wherever that month's volume happened to land. Setting it `false` costs the re-review after you push fixes — a small loss, since `dismiss_stale_reviews_on_push: true` already forces a human to look again — and buys ~124 PRs/month against a 300 cap, i.e. every PR reviewed with headroom. **So when Greptile is silent, check the quota on the dashboard before concluding the integration broke**, and do not block a merge on it: an exhausted month is indistinguishable from an uninstalled app from inside the repo.

    (Corrected 2026-07-30: this rule previously claimed Greptile posts *no* pending placeholder and is "not a PR review object, not a status check / check-run". All three claims were wrong — measured directly on #286/#287. The old advice sent you polling issue comments for ~5 minutes when the check-run reports state directly, and implied a green check meant nothing needed reading.)

    Because the check-run has a real pending state, `Greptile Review` is *technically* safe to require — unlike a reviewer that only materialises on completion, it cannot leave a merge blocked on a check that never gets created. **It is nonetheless deliberately NOT required, while four CI jobs are.** Since 2026-08-11 the ruleset requires `build`, `build-macos`, `build-windows` and `security`: the four that establish *objective* correctness, two of which (the macOS and Windows builds) no local gate can replace at all, plus `cargo audit`. Greptile is excluded on principle rather than by oversight — **an approval is the judgment call, and deliberately waiving a Greptile finding is a legitimate approval**, so gating on the reviewer would convert advice into a veto. `strict_required_status_checks_policy` is `false`, so a PR is not forced up to date with `main` before merging; with a dozen PRs open, `true` would mean near-continuous rebasing for no correctness gain.

    Required checks were previously removed because CI pushes two commits directly to `main` — the changelog commit in `release.yml` and the docs chart bump in `docs-publish.yml` — and a direct push carries no check runs, so GitHub rejected `github-actions[bot]` with `GH006: … 7 of 7 required status checks are expected` and every tag died in `prepare` (v0.35.6 was the first casualty; v0.34.0–v0.35.5 predate the gate). Both pieces are now in place: `RELEASE_TOKEN` gives those pushes an admin identity the ruleset lets bypass, and the `|| github.token` fallback that could silently degrade them back to `github-actions[bot]` has been replaced by a fail-fast guard (below). **Re-adding the checks was gated on the fallback, not on the token** — with the fallback in place a missing secret reproduces the v0.35.6 failure while reporting a misleading cause, which is why the guard landed first. **In place is not exercised, though:** the bypass actors are verified to have survived the full `PUT` that added the checks (`gh api repos/vfarcic/dot-agent-deck/rulesets/20587589` still lists `RepositoryRole` id 5 `always` and `Integration` id 2740 `pull_request`, which `scripts/apply-branch-protection.sh status` now prints next to the required contexts), and the PAT has pushed to a `main` protected by the `pull_request` rule — but **no direct push to `main` has happened since `required_status_checks` returned** at 2026-08-11T15:00:51Z (v0.35.10 was cut the day before). Since v0.35.6 died specifically on a required-checks rejection of a check-run-less direct push, run `scripts/apply-branch-protection.sh status` before the next tag, and prefer the `docs-publish.yml` canary over a real release as the first thing to exercise it.

    **The write-vs-admin asymmetry is accepted deliberately.** `enforce_admins` is disabled, so the four checks genuinely gate [@prageethw](https://github.com/prageethw)'s merges (`write`, no ruleset bypass) while remaining advisory for the owner's (Admin role, `bypass_mode: always`). That is tolerable *because* the four are objective — a red `build-windows` is not a matter of taste — so the gate is the same bar the owner would hold himself to rather than a governance imposition on one maintainer. Judgment-bearing signals stay unrequired for both.

    **A required check that never reported makes a PR permanently unmergeable, and the fork case is the one that bites.** #416 (`codex/visual-control-deck`, an outside contributor's fork) has never had one of the four report, so the moment the checks went up it became `mergeable=UNKNOWN` with no path forward until its workflows actually run — measured within the hour. So when a fork PR stalls with nothing red, check whether its runs ever existed before hunting for a defect. **Do not confuse that with a check that reported `SKIPPED`, which counts as passing** — GitHub: *"A job that is skipped will report its status as 'Success'. It will not prevent a pull request from merging, even if it is a required check."* The difference is whether a check run exists at all. It matters because `ci.yml`'s `changes` gate skips all four required jobs on devbox-only and flake-only PRs, which looks like the #416 trap made reachable by anyone and is not — and independently, that gate is scoped by **author** to `renovate[bot]`, so a human PR touching only docs, only Markdown or only `prds/` gets the full matrix whatever its paths (measured on #504, #499, #469 and #464: all four ran, none skipped). Keep both facts in view before widening the `changes` gate beyond Renovate.

    **`scripts/apply-branch-protection.sh` is the only thing that reconstructs the ruleset, and `apply` is a full `PUT`** — every rule it does not emit is deleted, silently and with a success exit. It now emits `required_status_checks` too, so `apply` restores all four rules rather than a weaker three-rule ruleset; `REQUIRED_CHECKS` overrides the contexts, and omitting the rule takes `REQUIRED_CHECKS=` **plus** `ALLOW_NO_REQUIRED_CHECKS=true` — an empty or whitespace-only value on its own is refused, because on a full `PUT` it would strip all four checks off the live repository silently and exit 0, and an unset variable is a far more ordinary way to arrive there than a fork is. Run `status` after any `apply` and read the contexts back: a ruleset missing its checks looks identical from the PR page.

    **`main` is protected by both a PR requirement and status checks.** Since 2026-08-08 an active repository ruleset named `main-protected` targets `~DEFAULT_BRANCH`, carrying four rules as of 2026-08-11: `pull_request` (**1** required approval since 2026-08-09, plus stale-review dismissal and required review-thread resolution), `required_status_checks` (the four jobs above), `deletion`, and `non_fast_forward`. **Every change to `main` must therefore go through a PR *that another maintainer approves*** — nobody can approve their own, so your own PRs now wait on [@prageethw](https://github.com/prageethw) and his wait on you (issue #432; the count sat at 0 until a second maintainer existed, because a lone collaborator cannot satisfy it and every merge would have been a bypass). A plain `git push origin main` is rejected with `GH013: Repository rule violations found for refs/heads/main. - Changes must be made through a pull request.` Inspect it with `gh api repos/vfarcic/dot-agent-deck/rulesets`. Exactly two bypass actors exist: the **Admin** repository role (`bypass_mode: always` — which is why a `vfarcic` push prints `remote: Bypassed rule violations for refs/heads/main` and then succeeds) and the **Renovate** app (id 2740, `bypass_mode: pull_request`). **Renovate's bypass covers the required checks as well as the approval, so there is a zero-human-approval lane onto `main`** — confirmed on #510, authored *and* merged by `app/renovate` 81 minutes after the checks went up, with `reviewDecision: REVIEW_REQUIRED` and all four required checks `SKIPPED`. That is accepted by design (the net is `ci.yml`'s `push:` trigger re-verifying `main` after every merge), but treat it as a security property worth knowing rather than a footnote about automerge: on devbox-only and flake-only bumps, that post-merge run is the first time any Rust job sees the change. `RENOVATE_BYPASS=false` in the script closes the lane. **`github-actions[bot]` is deliberately NOT a bypass actor**, because `GITHUB_TOKEN` **cannot** be one on a user-owned repo (`422: Actor GitHub Actions integration must be part of the ruleset source or owner organization`).

    **How review is requested, and who merges.** Request review through the pull request's **reviewer field** — `gh pr create --reviewer prageethw`, or `gh pr edit <n> --add-reviewer prageethw` after the fact. An `@mention` in a comment notifies but does **not** put the PR in the reviewer's *Review requested* queue or their `gh pr status`, and is not what the approval rule counts; and do not *assign* the other maintainer, since an assignee is whoever drives the PR to done, normally the author. `.github/CODEOWNERS` carries one pathless rule (`* @vfarcic @prageethw`) and GitHub omits the author when auto-requesting from code owners, so the routing normally happens by itself — it is a **router, not a second gate** (`require_code_owner_review` stays `false`, so any maintainer's approval still satisfies the one required review). Three mechanics, every one of which fails *silently* rather than erroring — routing simply does not happen: `CODEOWNERS` is read from the **base** branch, so a PR that edits it does not benefit from its own change; a malformed entry disables routing altogether, so check `gh api repos/vfarcic/dot-agent-deck/codeowners/errors` after editing it; and a **draft** PR is not routed to code owners at all until it is marked ready, so do not open a PR with `--draft` unless you mean to, and run `gh pr ready <n>` the moment it is meant to be reviewed. **Request review LAST**, not first: `dismiss_stale_reviews_on_push: true` means any push after an approval voids it, so settle CI, read the inline comments, push the fixes and resolve the threads *before* asking, or you buy a guaranteed second round trip. **Merging is a separate act from approving, and there are now two legitimate routes.** Nothing in the ruleset constrains who presses the button (`require_last_push_approval` is `false`) and the approver is not obliged to, so the author normally merges after approval; reviewer-merges is a Prow convention where a *bot* does it. Since 2026-08-11 `allow_auto_merge` is `true`, so the alternative is to **arm auto-merge on the PR** and let GitHub land it once the ruleset's conditions are met — the one approval, the four required checks green, and every review thread resolved. **Arming it is not a bypass:** auto-merge waits for exactly the approval a manual merge needs, so nothing unapproved slips through it, which is why it is safe to arm *before* review lands. That holds **only while the ruleset is in force**, though — `allow_auto_merge` is a repository setting the ruleset does not own, so deleting the ruleset (the emergency override) makes every armed PR instantly mergeable with no approval. Disarm before lifting the gate; `docs/develop/governance.md`'s Emergency override gives the order. Note the interaction with `required_review_thread_resolution: true` — Greptile's findings arrive as review threads, so an armed PR will not merge while they are unresolved, and whoever resolves them is doing the reading this rule asks for. **Never merge your own unapproved PR:** for the owner the admin bypass makes that succeed silently rather than fail, which is exactly how the gate decays into ceremony. An automated flow whose last step is a merge (`/prd-done`, `/prd-full`) may now arm auto-merge and hand off, but must never merge directly. Full rationale in [`docs/develop/governance.md`](docs/develop/governance.md).

    CI consequently pushes to `main` under an admin identity instead: the `RELEASE_TOKEN` secret is an admin PAT, and both `release.yml` and `docs-publish.yml` check out with `token: ${{ secrets.RELEASE_TOKEN }}`. **Two things matter when you touch either workflow.** First, each job **verifies the secret is non-empty in its first step** and fails there with an actionable message. That guard replaced a `token: ${{ secrets.RELEASE_TOKEN || github.token }}` fallback which was correct when written — its comment said it kept the workflow unchanged "while the secret is unset, so this change is safe to merge before `main` is protected" — and became a trap once both halves of that condition flipped on 2026-08-08: all it could then do was silently degrade an **unset or empty** secret to `github-actions[bot]`, which cannot push to `main`, surfacing *late* at the push step with the release already half-done. Keep the failure at step 1; do not reintroduce a fallback. **Know what the guard does not cover:** it tests `-z`, so a token that is present but **expired, revoked or under-scoped passes it and still dies at `git push origin main`** in that same half-done state — the guard converts "nobody set the secret, or a caller did not forward it" from a late mystery into a named error, and claims nothing more. The old fallback did not cover the expired case either: a GitHub `||` yields the left operand whenever it is non-empty, so an expired PAT reached `actions/checkout` unchanged rather than being swapped out. Probing the token was rejected deliberately — an extra API call and a new failure mode on the release path, to cover a case that has never occurred. What actually validates a token is the `docs-publish.yml` canary (`gh workflow run docs-publish.yml`), so **re-run it after every PAT rotation**. Second — the one that actually bit — **a reusable workflow invoked via `uses:` receives no secrets unless the caller passes them.** `release.yml`'s `docs` job calls `docs-publish.yml` that way, so without `secrets: inherit` the callee's `secrets.RELEASE_TOKEN` is empty and its push dies on `GH013`; that is exactly how v0.35.9's `docs / publish` job failed at "Commit chart changes", leaving the docs image published to GHCR but `main`'s chart pointer stale, so the site never rolled forward (fixed in `428acef` by adding `secrets: inherit`). The standalone `/publish-docs` path was never affected, which is what pinned the cause down: `workflow_dispatch` runs `docs-publish.yml` directly, where the secret is in scope, so `f1204ec` landed on `main` at 15:06:34Z — 91 seconds *after* the ruleset was created at 15:05:03Z — and succeeded. Same workflow, same push target, same job steps; **only the invocation differed**, and with it whether the secret was in scope. Note that commit's *author/committer* is `github-actions[bot]`, because the "Commit chart changes" step sets `git config user.name` to that — but the identity that **pushed** it, and therefore the one the ruleset evaluated for a bypass, is the `RELEASE_TOKEN` PAT's admin account. Do not read the committer line as evidence that `github-actions[bot]` can push to a protected `main`; it cannot, which is the whole reason the PAT exists.

9. **Ask the Experimental-Flag Question When Starting a User-Facing PRD; Gate at the Seam**: When starting a PRD that introduces a new user-visible surface (pane, field, command, tab, footer, keybinding), ask the user whether that surface should ship behind the `experimental` feature flag (PRD #139). If **yes**:
   - Add **one** per-feature wrapper function in `src/features.rs` — e.g. `pub fn show_<feature>() -> bool { experimental_enabled() }` — and gate **only at the user-visible seam** (render and input-binding). Do **not** scatter `experimental_enabled()` checks through implementation code, and never branch business logic / daemon protocols / hook handling on the flag — it is a *presentation* switch (M3.2). Every call site reads `if features::show_<feature>() { … }` so `grep show_<feature>` finds them all for a mechanical removal at graduation.
   - Note the flag in the **PRD itself**, in the **changelog fragment** (`dot-ai-changelog-fragment`), and in the **docs** (`docs/develop/experimental-flag.md` lists the flag and how to enable it).
   - At ship time, file a **`graduate-<feature>`** follow-up issue. Closing it requires deleting the wrapper, inlining the `true` branches, and removing the flag's docs/changelog notes.

   If **no**, the surface ships normally (visible by default) and none of the above applies. The flag is off by default; enable it via `[features] experimental = true` in `.dot-agent-deck.toml` or `DOT_AGENT_DECK_EXPERIMENTAL=1` (env wins).
10. **Do Not Hard-Wrap Markdown Prose**: In Markdown files (docs under `docs/`, `*.md`, PRDs, READMEs), write each prose paragraph as a **single line** and let the editor/renderer soft-wrap it. Do not insert manual newlines mid-paragraph to cap the line at ~72/80 characters. Both CommonMark (GitHub) and Docusaurus/MDX reflow a paragraph to the viewport width — a single newline inside a paragraph is *not* a rendered line break — so hard-wrapping changes nothing in the output while making diffs noisier (one inserted word reflows the whole paragraph) and editing harder. This applies only to prose: keep the natural line structure of code blocks, tables, list items, frontmatter, and intentional hard breaks (blank line between paragraphs, or a trailing `\` / two spaces for a real `<br>`).

12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: In this project "breaking" means a change to the **TUI↔daemon protocol/handler contract** such that an older and a newer build can no longer safely interoperate — *including* a SEMANTIC break behind a stable wire (a field whose meaning changes, a role-map value type that shifts), **not** generic user-facing breakage. When a PRD or PR touches the **daemon, the TUI↔daemon protocol, orchestration, or hooks**, before opening the PR (and as part of `/prd-done`):
    - **Answer "did this change the TUI↔daemon contract?"** If the wire *shape* moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it is a same-wire / different-meaning (semantic) break, add a `changelog.d/<issue>.breaking.md` fragment so it is versioned as a compatibility break.
    - **Run the cross-version manual test.** Build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, and confirm the core flows still work end to end — a **delegate** still routes and **hooks** (work-done, status) still arrive. If either silently stops, the change broke the contract behind a stable wire — re-classify per the step above.
    - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with its sockets and `HOME`.** Pointing `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` / `HOME` / `DOT_AGENT_DECK_STATE_DIR` at a scratch dir is not enough: the log path is resolved separately, so a sandbox daemon otherwise correctly isolated still **appends into your real `~/.local/state/dot-agent-deck/deck.log`**. Two daemons interleaved in one log file is genuinely hard to read after the fact — one incident needed timestamp arithmetic against a socket path just to work out which of two daemons had logged an idle-shutdown line, and the wrong attribution changes the conclusion. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run. **Export `DOT_AGENT_DECK_EXPERIMENTAL` too**, for the same class of reason: project-config discovery walks up from **cwd**, not from `$HOME`, so a sandbox rooted at a sibling path still reads the operator's real `~/.dot-agent-deck.toml` and both daemons come up with whatever feature flags that file sets — measured on the #702/#687 run, where both sides came up `experimental: ON`. It does not bias a comparison (both sides read the same file), but a cross-version sandbox whose feature flags come from the real home is not actually isolated, so pin the flag explicitly rather than inheriting it.
    - **Bump policy** (while `0.x`): breaking → **minor**, feature/bugfix → **patch**; from `1.0` onward: breaking → major, feature → minor, bugfix → patch. So while in `0.x` the minor digit signals "compatibility broke", not "has new features". Full rationale, the `PROTOCOL_VERSION` floor, and the `.breaking.md` discipline are in [`docs/develop/versioning.md`](docs/develop/versioning.md).

14. **Never Put Build Artifacts or Worktrees on the Agent Scratchpad / a tmpfs**: A cargo `target/` built with `--features e2e` is several GB, and an agent session's scratchpad is often on a **tmpfs** (`/tmp` on the current dev box is a 14 GB RAM-backed mount). Two failure modes follow, both of which have already cost real debugging time. First, a build inside the scratchpad dies at link time with a misleading `error: linking with 'cc' failed` once the tmpfs fills — nothing points at the filesystem. Second, and less obviously, **whatever occupies a tmpfs occupies RAM**: a few GB of scratchpad shrinks what is left for `rustc` and lets the OOM killer reap a compile that would otherwise fit (a `signal: 9, SIGKILL` on a `rustc` invocation is the tell). Put every git worktree at a **disk-backed sibling** path — `../<repo>-<suffix>`, the scheme `/worktree-prd`'s `create.sh` and `/verify-pr`'s `setup.sh` already use — and never point `CARGO_TARGET_DIR` at the scratchpad. Use the scratchpad for what it is for: notes, diffs, logs, one-off scripts. `df -h /tmp` shows whether it is a tmpfs and how much room is left; `cargo xtask clean-e2e-tmp` (issue #322) reaps the e2e harness's per-process temp roots left behind by interrupted runs, and defaults to a dry run so you can see what it would remove first. It scans the **standard roots** — the harness's private `/var/tmp/dad-e2e-<uid>` parent, where current runs land, *and* the system temp dir, where every pre-#322 leftover still sits — vetting each one before reading it; a base you moved with `DAD_E2E_TMPDIR` is deliberately not scanned automatically and needs `--root`. Since issue #461 it decides by the owning PID embedded in each `dad-tests-<pid>-*` name rather than by age alone: a dead owner is reaped once the root is at least **30 minutes** old (`--older-than` does not hold it back — the floor is separate and much shorter), a live one is **never** reaped at any age and with no timestamp consulted at all, and the age threshold settles roots with no usable PID — `dad-unit-*` scratch dirs and the pre-fix lock dirs, which carry none; an untagged or malformed name; or a host with no `kill(2)`. The 30-minute floor is load-bearing, not caution: the PID names the *test* process, but the deck's lazily-spawned daemon `setsid`s out of that process group and can outlive it by up to `DOT_AGENT_DECK_TEST_MAX_LIFETIME_SECS` while still writing under the root, so reaping a dead owner instantly would hand `remove_dir_all` a live process's working directory. The old age-only rule was accidentally safe here because 6h is 72x that cap. **The floor is 2x the longest cap `tests/` pins, not 2x the 300s harness default** (issue #679): `orchestration_dispatch_002` pins **900**, and a `TuiDeck` builder's `with_env` is applied after the harness `env_clear` so that value reaches the child verbatim and `clamped()` — an *ambient*-value guarantee — never sees it. The floor sat at 600s reading as "2x 300" while that 900 was already on `main`, which left 300 seconds in which `--apply` could delete a root a still-entitled daemon was writing under. It is now derived in code (`DEAD_PID_MIN_AGE = MAX_PINNED_ORPHAN_CAP_SECS * 2`) and **linkage-check rule 11** fails the build on any pin under `tests/` above that constant, so raising a test's cap without raising the floor goes red instead of silently re-opening the window. Rule 11 deliberately has no per-line opt-out — unlike rules 8 and 10 it guards a pair of numbers that must move together, so the remedy is to raise the constant, not to exempt the line. In the other direction, a PID collision is only transient *within one boot*: across a reboot a leftover root's PID gets reissued to an early system unit, and the root is then pinned `live-pid` for the life of that boot — so pass `--ignore-liveness` to demote those roots to the age rule when you know the machine restarted. Survivors are listed individually with size and age, not just counted, so such a collision is visible. So if it reports nothing to reap, read the per-reason summary rather than assuming a threshold got in the way. There is deliberately **no** recycled-PID branch, which is a documented deviation from #461 as filed: proving recycling means ordering a process start against a directory timestamp, and that has to bridge the wall clock — `settimeofday` shifts the boot time behind `/proc/stat`'s `btime` while inode timestamps are never retroactively adjusted, so any forward clock step biases a *live* process toward looking recycled, which is the deletion-unsafe direction. Two implementations (the `/proc/<pid>` dentry mtime, then field 22 of `/proc/<pid>/stat`) both deleted live test roots. Losing the branch costs a deferral *within a boot*: a recycled PID pins its root until the colliding process exits, after which the next run reaps it as `dead-pid`. Across a reboot it costs more, which is what `--ignore-liveness` is for (above) — but that stays an operator assertion, never an inference. Do not reinstate it in any form, including a report-only annotation — the reasoning is in [`docs/develop/e2e-temp-dirs.md`](docs/develop/e2e-temp-dirs.md).
15. **Rebuild the Daemon After Every Commit While `tauri dev` Is Running**: The build version embeds `git describe`, so committing restamps the *desktop* binary on its next rebuild while the *daemon* binary on disk keeps the old hash. The deck then refuses the connection with "Desktop bridge error: build mismatch", and the GUI's **Replace daemon** button cannot recover it in dev — that path starts the bundled sidecar, which only exists in a packaged `.app`. Treat a commit in this repo as incomplete until you run `cargo build --locked --bin dot-agent-deck` (or `cd desktop && pnpm daemon:sync`), then `./target/debug/dot-agent-deck daemon stop` if one is running, then Reconnect in the app. The `pretauri` hook in `desktop/package.json` covers the *launch* case automatically but cannot cover mid-session commits. Note `cargo` may not be on PATH (rustup shims can be missing while the toolchain is present under `~/.rustup/toolchains/`); `pnpm daemon:sync` resolves it either way.
