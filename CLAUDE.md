# CLAUDE.md — dot-agent-deck

## PERMANENT INSTRUCTIONS

1. **Ask Before Creating Branches or Worktrees**: When starting feature work (including `/prd-start`), ask the user whether they want a worktree (`/worktree-prd`) or a regular branch. Never assume one or the other.
2. **Run `cargo fmt --check` and `cargo clippy --workspace --all-targets --features e2e,e2e-live -- -D warnings` Before Committing**: Run both before creating any git commit, unless `cargo xtask affected-checks` finds the change is mapped text only (next paragraph). If fmt reports issues, run `cargo fmt` to fix them. If clippy reports warnings, fix the code. Stage any fixes before committing.

    **Which gates a change needs is what `cargo xtask affected-checks` prints** (issue #1575); `--run` runs them in order and exits non-zero at the first failure. When any changed path is Rust, a build input or a path its text mapping does not cover, it prints this rule's two commands and CLAUDE.md rule 5's `cargo test-fast`. When every changed path is mapped text (`docs/`, `.claude/skills/`, `changelog.d/`, `.github/`, `devbox.json`, `renovate.json`, `prds/`, and `CLAUDE.md`/`AGENTS.md` with the other root-level prose files), it prints the tests that read those files instead — which is not "text needs nothing", since several fast-tier tests read text from the checkout. This narrows when the rule applies, not what it demands of code, and CI is untouched.

    **All four clippy flags are load-bearing; do not drop or "simplify" any of them, `e2e-live` least of all.** Without `--all-targets` cargo builds no test target; without `--features e2e` every `tests/e2e_*.rs` file compiles to an empty crate (#407); without `--workspace` the `xtask/*` members are linted by no gate (#436); and without `e2e-live` the lane-2 files compile to empty crates (#502). Each omission lets clippy exit 0 without having linted the code that flag brings in. Nothing in CI runs the lane-2 files, so this command is the entire CI-side coverage they get, and they are about a third of the e2e tier ([`docs/develop/lint-gate.md`](docs/develop/lint-gate.md#e2e-live-issue-502) keeps the dated count). It is a type-check and lint: it spawns no binary, hits no API and needs no credential. The Linux CI `build` job runs the same command; `build-windows` / `build-macos` deliberately stay on bare `cargo clippy -- -D warnings`. `src/` has `not(feature = "e2e")` arms that this command does not lint and only those bare-clippy jobs do (`build-macos` both, `build-windows` only the one that is not `cfg(unix)`), so know that before putting anything substantial in one. `cargo fmt --check` needs no features: rustfmt is cfg-blind and walks the cargo target list, so it already covers the feature-gated files. Evidence, measurements and the superset argument: [`docs/develop/lint-gate.md`](docs/develop/lint-gate.md).
3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (e.g. `tests/event_forwarding.rs`), not for the milestone or PRD that introduced them (e.g. `tests/m2_17_event_forwarding.rs`, `src/prd76_*.rs`). Milestone tags belong in commit messages and the PRD doc — long-lived filenames must outlive the branch. Existing `m*_` test files are scheduled for cleanup; do not create new ones in that pattern.
4. **Add or Update TUI Tests for Functional UI Changes**: When a change adds or modifies user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, embedded panes, hook delivery), add or update tests in the TUI harness. Use L1 (in-process `TestBackend` + `insta`) for pure widget/layout changes; use L2 (PTY + vt100, files named `e2e_*.rs`, gated by `#![cfg(feature = "e2e")]`, plus a `feature = "e2e-live"` term when the test needs a real agent credential) when the change touches the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change do not require new tests.

    - **For a major user-facing feature, include at least one PTY-attached L2 test** (the vt100 harness that drives the real binary, e.g. mirroring `scheduler/live/*`) that exercises the user-visible surface — not only headless daemon-serve (`RunNow`) tests. A clip is demo-reel-eligible only when the test genuinely spins up a **real agent** (spawn → agent → work) **and** its `tests/CATALOG.md` entry carries a trailing ` [reel]` marker (PRD #180/#20 — see `.claude/skills/demo-reel-adapter`). A synthetic/stand-in PTY test (cat, scripted echo, recorder stubs, terminal-probe, synthesized hook events) is left unmarked and never becomes a clip even though it has a cast, so a feature whose entire e2e coverage is headless (or unmarked) ships with no reel clip.
    - **A major user-facing feature should also have at least one REAL-scenario e2e test** that drives the genuine spawn→agent→work path with a *real* agent on a **cheap model** (Haiku for Claude, a mini model for OpenCode) through a cheap, deterministic-enough operation, rather than relying solely on a stand-in like `cat`. Make it robust with a directive prompt plus a uniquely-named fixture **sentinel file**. Real-agent tests live in **lane 2** (CLAUDE.md rule 5), which runs on a developer's machine and **nowhere in CI** — so writing one is only half the job: run it yourself with `cargo test-e2e-live <filter>`, and run it again whenever you touch the surface it covers, because nothing else will.
    - **The bar is: at least one test per major feature must validate it AS A USER ACTUALLY USES AND SEES IT** — the genuine, user-visible experience end to end, e.g. a *live interactive* agent visibly working in the pane (with real status), not a non-interactive shortcut like `claude -p` and not a stand-in. Interactive headless agents are achievable (seed claude's onboarding and per-folder trust into the test HOME and pass `--allowedTools`; `scheduler/dispatch/013` is the reference). Do not let "headless is hard" silently downgrade this bar where it is achievable.

    Why the bar sits there, and the cautionary case: [`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md#real-agent-coverage-for-a-major-feature).
5. **Fast Tests Per Task, Then the Tests Covering What You Touched; CI Runs Lane 1**: there are **three tiers of obligation**, and only the first two are yours.

    | tier | what | when |
    | --- | --- | --- |
    | always | `cargo test-fast` (alias for `cargo nextest run --workspace`) — protocol/state tests plus L1 widget/render tests | per task, unchanged |
    | **scoped to the change** | **the tests covering what you touched — any tier, credentialed included** | per task |
    | CI | lane 1 in full — the `e2e-deterministic` job running `cargo test-e2e` | per PR; **monitor and analyse that run, do not reproduce it locally** |

    **For a change that is only mapped text, the first row is what `cargo xtask affected-checks` prints, not `cargo test-fast`** (issue #1575; CLAUDE.md rule 2 has the mapping). Any Rust or build input in the change brings `cargo test-fast` back in full, and so does any path the mapping does not cover. The second row is unchanged either way: the tests covering what you touched are still yours to find and name.

    **There is no obligation to run the full e2e tier locally before a PR** (2026-08-31, issue #502, credential handling in #785), and nothing here brings it back. Run the tests that cover the thing you changed, then read CI's lane-1 run rather than racing it ([why it went](docs/develop/e2e-lanes.md#why-the-full-tier-mandate-went)).

    **Find the covering tests, and name them in your report.** Three routes, usually quickest first: [`tests/CATALOG.md`](tests/CATALOG.md) maps catalog IDs to areas and records each test's layer, agent and lane, so grep it for the surface you touched (`orchestration/route`, `scheduler/dispatch`, `hooks/…`); the `#[spec(...)]` annotation on a test names its catalog ID, so the mapping runs both ways; and `cargo xtask list-tests` enumerates what exists when you do not yet know the vocabulary. "Ran the related tests" is not a claim anyone can check: lane 1 runs in CI on every PR, but lane 2 and any credentialed test you scoped in are on trust.

    **A change to shared harness code is the honest exception.** `tests/common/mod.rs` is linked by every `tests/e2e_*.rs` file, so for a change there "the covering tests" genuinely *is* the whole tier: run one broad local pass and lean on CI for the rest.

    **The full CI matrix can run on GitHub's runners instead of this box**: `git push -u origin <branch>`, then `gh workflow run ci.yml --ref <branch>`, taking the run id from the URL that command prints (on a branch with an open PR, `gh run list … --limit 1` returns the PR's run rather than yours). **It relieves no gate above** — fmt and clippy are a pre-commit gate and `cargo test-fast` stays the per-task obligation. Reach for it when the box is loaded, when the change needs a platform you do not have (on a Linux host `build-macos` has no local counterpart and `build-windows` only the partial `scripts/windows-cross-check.sh`), or as a final pre-PR sweep — **never as the per-edit gate**, since a CI round trip's median is 9.5 minutes. It covers neither lane 2 nor the demo reel's `.cast` recordings, and sees only what you have pushed. [`docs/develop/ci-on-demand.md`](docs/develop/ci-on-demand.md) has the numbers and what runs.

    | Lane | Contents | Runs | Credentials |
    | --- | --- | --- | --- |
    | 1 — deterministic e2e | the credential-free `tests/e2e_*.rs` files, `cargo test-e2e` | every PR, in CI (`e2e-deterministic` in `ci.yml`, `timeout-minutes: 60`) | none |
    | 2 — real-agent e2e | the files that reach a real agent, `cargo test-e2e-live` (a **superset** run: lane 1 + lane 2, every `tests/e2e_*.rs` file) | **a developer's machine only — never CI** | the developer's own |
    | 3 — local debugging | the failing test, then its module | developer machine, while debugging | as the test needs |

    **NO E2E TEST REACHES A REAL AGENT IN CI, and this is a decision, not a gap.** No **test** credential is registered on this repository and none will be. Two reasons, both of which have to be re-argued before anyone adds one back. First, **running a credentialed job less often does not reduce the risk that a credential leaks from a public repository's CI** — it reduces the number of exposures, not the existence of the vulnerability; "per-merge instead of per-PR", an environment with a required reviewer, a label gate are all risk theatre once the key is on a runner at all. Second, **the boundary is not "tests that read a key"** — it is "tests that reach a real agent by any route", because on a developer machine the agent CLIs are *pre-authenticated*, so a test that spawns `claude` and never touches `ANTHROPIC_API_KEY` still spends a credential. The `e2e-live` cargo feature draws exactly that line, which is why the feature and the classification stay even though the CI job went. The deleted credentialed workflow is in git history — `edaa2b4` on `main`, `62ba861` on branch `agent/e2e-live-credential-sinks` — and stays there rather than parked in the tree as an unwired trap.

    **That claim is narrow on purpose, and the wider version of it — "no agent credential reaches CI at all" — is FALSE.** The Codex **issue-labeler** is a separately credentialed workflow that does send `OPENAI_API_KEY` onto a runner and does reach a real agent; it has its own threat model and docs ([`docs/develop/issue-labeling.md`](docs/develop/issue-labeling.md)) and is **out of scope for this rule**. Do not restate this rule absolutely.

    **The unenforceable-verification gap is an accepted TRADE.** Nothing can force a contributor to run the credentialed tests locally: the only mechanism that could is CI, and CI has no credentials *by design* — so this rule is an instruction, not a gate. **The cost is real: real-agent regressions surface when someone happens to run them, not on any schedule.** Whoever later proposes "let's just add the key to CI" is re-opening this trade and has to argue it again — against both reasons above, not merely against the inconvenience. [`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md#why-lane-2-is-not-in-ci) has the full reasoning.

    **Lane 2 is what a developer runs, and running it is the point.** `check_claude_available` and `check_opencode_available` accept a non-empty `ANTHROPIC_API_KEY` as a **third** auth path, after the credentials file and the macOS Keychain. Three harness changes are **coupled** to the claude one and must never be split from it: `import_claude_credentials` writes no credentials file when the key authorises the run, `seed_claude_project_trust` pre-answers Claude Code's API-key approval prompt (it defaults to **No**, so an unattended agent stalls forever without it), and `INHERIT_PASS` lets the key cross the harness's `env_clear` into the spawned deck. Set `DOT_AGENT_DECK_REQUIRE_REAL_E2E=1` when you want "cannot run" to read as UNVERIFIED rather than green: a preflight that cannot be satisfied prints `SKIP:` and **returns normally**, so nextest counts it as passed, and that flag turns every such skip into a failure.

    **A lane is its cargo feature set, not its alias.** The credentialed files open with `#![cfg(all(feature = "e2e", feature = "e2e-live"))]` and the rest with `#![cfg(feature = "e2e")]`. There is deliberately no live-*only* alias, because `e2e-live` without `e2e` compiles every e2e file to an empty crate. A raw `cargo nextest run --workspace --features e2e,e2e-live <filter>` selects the same files and discharges the same obligation as `cargo test-e2e-live <filter>`; prefer the alias, which carries `--workspace` for you, but do not read a raw invocation as having skipped the lane.

    **Lane 3 is what you actually run while debugging, and CLAUDE.md rule 6's procedure is unchanged by all of this.** Rerun the failing test alone to confirm the fix (`cargo test-e2e <one-test-name>`), then its module — CLAUDE.md rule 6 is still correct and was deliberately left as it stands. Read rule 6's closing parenthetical against this table, though: the tier to rerun before committing is `cargo test-fast` plus the scoped tests above, and for an e2e test its own module; the `plus cargo test-e2e pre-PR` half of that line is what #502 removed. Both `cargo test-e2e` and `cargo test-e2e-live` remain available locally and both take a filter; what disappeared is the obligation to run either **in full** before opening a PR — not the obligation to run what covers your change. `cargo test-e2e-live` needs a working agent credential of your own. `cargo test-fast` needs no `--exclude dot-agent-deck-desktop` in a devbox shell; if it dies on `libgdk-3.so.0`, your devbox environment is stale, and `scripts/devbox-check-gtk.sh` says so and gives the remedy.

    **`--workspace` is load-bearing on all three aliases** (issue #489). The workspace root is itself a package and there is no `default-members`, so without it cargo runs the root package alone and the tests in `xtask/linkage-check` and `xtask/docs` execute in no gate — their runtime assertions, such as the `clean-e2e-tmp` reaper's deletion-safety properties, would be inert while every gate stayed green. All three build jobs carry it, and `e2e-deterministic` inherits it from the `test-e2e` alias. An xtask test belongs in the fast tier by being in-memory or `tempfile::tempdir()`-based, with no network and no sleep; the recorded exceptions that read the checkout, run an interpreter or run git, and the reason each one earns, are in [`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md#--workspace-on-all-three-aliases-and-the-fast-tier-exceptions). A new xtask test still should not shell out to git without a reason as specific.
6. **Iterate on a Failing Test by Rerunning Only That Test**: When a single test fails, after fixing the code rerun *only that test* first (`cargo test-fast lifecycle_001` or `cargo test-e2e lifecycle_001`) to verify the fix in isolation. Decision 17's function-name prefix (`<sub-area>_<NNN>_…`) makes the filter pick exactly one test. Only after that test passes, rerun the full tier (`cargo test-fast`, plus `cargo test-e2e` pre-PR) before committing. **And the lane must be GREEN before a PR is done, whoever caused the red (#908):** rerun the failure in isolation first, since contention manufactures phantom flakes — the `load context` block that ends every harness panic says whether that run was starved (issue #701, [`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md#reading-a-red-run-the-load-context)); then either fix it in this PR, or quarantine it. **A red you meet while working on something else is in scope by DEFAULT, and where it came from — this PR, another PR, or `main` — changes nothing about the obligation.** "It was already broken" is why it needs an owner now, not why it can keep waiting, and "that belongs in a separate PR" is precisely how it stays unowned: the PR that meets a red is the one with a person looking at it. **Quarantine is the costly exception, not the default escape.** It takes a named owner, an expiry issue, *and* the test genuinely quarantined — marked in the tree, `#[ignore = "quarantined: <owner>, #<issue>"]`, so a run reports it skipped instead of failed. `xtask/linkage-check` rule 6 accepts exactly that form on a `#[spec]` test and refuses every other `#[ignore]` — a bare one, a free-text reason, a mark missing its owner or issue. Filing an issue and leaving the test red is not quarantine; it is the tracking this rule already refuses, under a better name. Tracking a red test is not enough — a lane that is red by default trains everyone to skip it, and then it reports nothing. Note what the wording does *not* buy: lane 2 still runs nowhere automatically (CLAUDE.md rule 5), so this changes what you owe once a red is in front of you, not whether anyone is looking. Protocol, evidence and quarantine mechanics: [`.claude/skills/verify-pr`](.claude/skills/verify-pr/SKILL.md) and [`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md#a-red-you-meet-is-yours).
7. **Every `#[spec]` Test Has a Scenario Comment**: When adding or modifying a `#[spec(...)]`-annotated test in `tests/`, the test function MUST carry a `/// Scenario:` doc comment of 1–3 sentences describing in plain English what the test does — start the app, what gets pressed/sent/written, what should happen visibly. The `cargo xtask docs --tests` command regenerates a local `.md` under `.dot-agent-deck/recordings/<test>/test.md` (gitignored) that pairs with the cast for browsing during development. CI's linkage-check rule 7 fails the build if the Scenario comment is missing or the generator fails — not on local `.md` drift, since it isn't committed.
8. **Answer AND Resolve Review Findings Before You Hand a PR Off**: the procedure lives in the [`pr-create`](.claude/skills/pr-create/SKILL.md) skill, and the mechanism and its evidence in [`docs/develop/governance.md`](docs/develop/governance.md). What follows are the obligations themselves, because most PRs here are opened without invoking any skill.

    - **`main` is protected, and on the ordinary contributor path** — the one every change you write by hand takes — a change reaches it through a PR that *another actor* approves; nobody can approve their own. A plain `git push origin main` is rejected with `GH013`; for an admin it prints `Bypassed rule violations` and succeeds, which is worse, not better. **"Ordinary contributor path" is not a hedge:** two lanes reach `main` without any approval at all — Renovate's `pull_request` bypass and the three `RELEASE_TOKEN` workflows below.
    - **That approving actor is normally the agent reviewer, not a maintainer.** `pr-review-batch.yml` sweeps daily and, with the repository variable `PR_REVIEW_LIVE` set, casts real approvals unattended as `dot-agent-deck-reviewer`. `gh workflow run pr-review-batch.yml -f pr_number=<n> -f dry_run=false` requests it on demand; `dry_run` defaults to **true** on a manual dispatch, so a default invocation casts no vote.
    - **That does NOT mean nobody need look.** The reviewer refuses what it cannot verify, so **a `REQUEST_CHANGES` naming a manual obligation (CLAUDE.md rule 12's cross-version test is the recurring one) is addressed to a person, and a green check-run is not an answer to it.** The agent/vote split is "blast radius, not immunity": a diff that talks the agent into `APPROVE` is faithfully approved.
    - **A third lane approves nothing at all.** Renovate's `bypass_mode: pull_request` merges to `main` past both the review rule and the required checks — accepted by design, with `ci.yml`'s `push:` trigger re-verifying `main` afterwards as the compensating control; `RENOVATE_BYPASS=false` closes the lane.
    - **`RELEASE_TOKEN` is the one sanctioned automated path for a DIRECT PUSH to `main`, and today it is exactly three workflows**: `release.yml` (the assembled changelog), `docs-publish.yml` (the Helm chart bump) and `tag-release.yml` (the `flake.nix` version pin, issue #1089). It does not license a fourth — another direct-push workflow re-opens the question and has to argue it, not inherit it — and it licenses nothing typed at a keyboard.
    - **Never merge your own unapproved PR.** For the owner the admin bypass makes that succeed *silently* rather than fail, which is exactly how a gate decays into ceremony. An automated flow may arm auto-merge (`gh pr merge --auto`) and hand off — that waits for the same approval a manual merge needs — but must never merge directly.
    - **Do not arm auto-merge to wait for a NON-required check.** Auto-merge waits for the approval, every thread resolved, and the **required** contexts, which here are exactly five: `build`, `build-macos`, `build-windows`, `security`, `e2e-deterministic` (read `gh api repos/vfarcic/dot-agent-deck/rules/branches/main` and `gh api repos/vfarcic/dot-agent-deck/branches/main/protection` back rather than trusting this list). **Armed before the approval**, it merges when the approval arrives whether or not an unrequired check — `renovate/stability-days`, `Greptile Review`, `notify-main-red` — has passed. **Armed after the approval**, with only an unrequired check outstanding, the PR reads `UNSTABLE` and `gh` **drops the flag** and merges on the spot, exiting 0; `gh pr view <n> --json autoMergeRequest` reading `null` *after* the call is the tell (#1208, #1222). **So read `gh pr checks <n>` before arming, and when the thing you are waiting for is a non-required check, do not arm: poll that check** until it passes, then merge — or leave the PR for a person.
    - **Before merging, check whether `main` moved onto the PR's files since its CI ran.** The ruleset does not require a branch to be up to date (`strict_required_status_checks_policy: false`), so two PRs that are each green can break `main` together with no textual conflict (issue #1610). So right before merging, list the commits `main` gained since the branch point that touch any file the PR changes. If there are any, update the branch (`gh pr update-branch <n>`), let CI run on the combined code, confirm the approval still stands (`gh pr view <n> --json reviewDecision`) and request it again if it was dismissed — a `gh pr update-branch` merge was measured not to dismiss an approval (2026-09-07), while a hand-pushed commit does — check once more, and merge with `--match-head-commit`. The commands are in [`issue-queue`](.claude/skills/issue-queue/SKILL.md)'s "The overlap check before a merge", which the skills that merge directly (`issue-queue`, `code-cleanup`, `land-prs`) follow; auto-merge runs no such check. **It catches overlap in the files a PR changes, not every semantic conflict**; `main`'s own push CI and its `notify-main-red` job stay the backstop.
    - **Read the inline findings, answer each one, and RESOLVE the thread.** A green check-run is not the review: the findings live only at `gh api repos/{owner}/{repo}/pulls/<n>/comments --paginate`, and a `COMMENTED` review with every check passing can still carry real P1 defects (#286). The obligation falls due **when the check-run completes**, not "before merging" — on the blessed path the merge is auto-merge firing on the approval, a moment at which no agent is present at all (#888).
    - **Resolving is half the job, not bookkeeping.** An unresolved thread blocks *both* halves of the merge: `required_review_thread_resolution` blocks the merge button, and the agent PR reviewer skips any PR carrying one, so it also blocks the approval that merge needs. Resolve only what you actually addressed; leave a thread open when you are genuinely waiting on the commenter.
    - **Request review LAST.** `dismiss_stale_reviews_on_push` voids an approval when you push new commits (a `gh pr update-branch` merge was measured not to), so settle CI, answer the findings, push the fixes and resolve the threads *before* asking, or you buy a guaranteed second round trip. Use the reviewer field (`gh pr edit <n> --add-reviewer …`); an `@mention` is not what the approval rule counts.
    - **Bound any wait on the automated reviewer, and never block a merge on it.** An exhausted quota produces *no check-run at all* — indistinguishable from the app being uninstalled, with no message anywhere — so "wait until it appears" never terminates. CodeRabbit is not active here; a wait requiring its signal hangs to its full timeout every time.

9. **Ask the Experimental-Flag Question When Starting a User-Facing PRD; Gate at the Seam**: When starting a PRD that introduces a new user-visible surface (pane, field, command, tab, footer, keybinding), ask the user whether that surface should ship behind the `experimental` feature flag (PRD #139). If **yes**:
   - Add **one** per-feature wrapper function in `src/features.rs` — e.g. `pub fn show_<feature>() -> bool { experimental_enabled() }` — and gate **only at the user-visible seam** (render and input-binding). Do **not** scatter `experimental_enabled()` checks through implementation code, and never branch business logic / daemon protocols / hook handling on the flag — it is a *presentation* switch (M3.2). Every call site reads `if features::show_<feature>() { … }` so `grep show_<feature>` finds them all for a mechanical removal at graduation.
   - Note the flag in the **PRD itself** (its issue body, or its `prds/` file for a PRD written before issue #1591), in the **changelog fragment** (`dot-ai-changelog-fragment`), and in the **docs** (`docs/develop/experimental-flag.md` lists the flag and how to enable it).
   - At ship time, file a **`graduate-<feature>`** follow-up issue. Closing it requires deleting the wrapper, inlining the `true` branches, and removing the flag's docs/changelog notes.

   If **no**, the surface ships normally (visible by default) and none of the above applies. The flag is off by default; enable it via `[features] experimental = true` in `.dot-agent-deck.toml` or `DOT_AGENT_DECK_EXPERIMENTAL=1` (env wins).
10. **Do Not Hard-Wrap Markdown Prose**: In Markdown files (docs under `docs/`, `*.md`, PRDs, READMEs), write each prose paragraph as a **single line** and let the editor/renderer soft-wrap it. Do not insert manual newlines mid-paragraph to cap the line at ~72/80 characters. CommonMark renderers such as GitHub's reflow a paragraph to the viewport width — a single newline inside a paragraph is *not* a rendered line break — so hard-wrapping changes nothing in the rendered output while making diffs noisier (one inserted word reflows the whole paragraph) and editing harder. This applies only to prose: keep the natural line structure of code blocks, tables, list items, frontmatter, and intentional hard breaks (blank line between paragraphs, or a trailing `\` / two spaces for a real `<br>`).
11. **Developer/Maintainer Docs Live in `docs/develop/` and Are Not Published**: User-facing documentation goes directly under `docs/` and is published three ways: on the site at `agent-deck.devopstoolkit.ai` as raw Markdown at `/docs/<slug>.md`, in the site's `llms.txt` index and `llms-full.txt` corpus, and embedded in the binary, where `dot-agent-deck docs <slug>` prints the copy that matches the installed version. **One file decides what is published: [`docs/published.toml`](docs/published.toml)**, one `[[page]]` entry per page with a `slug` (the path under `docs/` without `.md`, e.g. `desktop/voice`), a `title` and a one-line `description`; its order is the order `dot-agent-deck docs`, `docs --all` and the `llms` files use. `cargo xtask site <out-dir>` builds the site from it (`xtask/site`) and `build.rs` embeds the same pages, both through the one parser in `src/published_docs.rs`. There is no sidebar file and no front matter: a page's title is its first `#` heading.

    **To publish a new user page**, add its manifest entry, with a `title` that equals the page's first heading — the site build refuses a mismatch — and link to other pages with relative `.md` links, which the build's link check resolves. The page is then on the site, in both `llms` files and in `dot-agent-deck docs` from the next build, with nothing else to register. A page under `docs/` cannot be kept private by leaving its entry out: `the_real_manifest_lists_every_user_page_and_nothing_else` fails `cargo test-fast` for any `docs/**/*.md` outside `docs/develop/` that the manifest does not list, and `the_real_site_builds_without_anything_from_develop` runs the whole build, link check included, in the same tier.

    Documentation meant only for contributors/maintainers (internal mechanisms, dev-only toggles, build/release internals) goes under `docs/develop/`, which is never published — **enforced by the build, not configured**. The parser rejects a `develop/` slug; `page_source` in `src/published_docs.rs` resolves each page to its canonical path and refuses one that lands in `docs/develop/`, a symlink included, for both the site and the binary, and `image_source` does the same for the site's images; the link check refuses a published link into `docs/develop/`; and the publication-boundary tests (`xtask/site/tests/publication_boundary.rs`, `tests/embedded_docs_boundary.rs`) fail if a maintainer page's content reaches the site output, the `llms` files or the embedded topics. Link developer pages only from `CONTRIBUTING.md` (and optionally the root `README.md`); they render as plain Markdown on GitHub. When it's unclear whether a doc is user- or developer-facing, ask.
12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: In this project "breaking" means a change to the **TUI↔daemon protocol/handler contract** such that an older and a newer build can no longer safely interoperate — *including* a SEMANTIC break behind a stable wire (a field whose meaning changes, a role-map value type that shifts), **not** generic user-facing breakage. When a PRD or PR touches the **daemon, the TUI↔daemon protocol, orchestration, or hooks**, before opening the PR (and as part of `/pr-create`):
    - **Answer "did this change the TUI↔daemon contract?"** If the wire *shape* moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it is a same-wire / different-meaning (semantic) break, add a `changelog.d/<issue>.breaking.md` fragment so it is versioned as a compatibility break — **and append the matching `<issue>-<kebab-slug>` entry to `CONTRACT_BREAKS` in `src/daemon_protocol.rs` in the same commit** (issue #801). The fragment is what a human reads; the entry is what the desktop's handshake classifies from, and a break with only the first is a break the handshake connects straight through. The list is append-only — never edit or remove an entry, including across a `PROTOCOL_VERSION` bump. `xtask/linkage-check`'s `contract_breaks` rule fails the build when a fragment in the tree has no entry, which is why forgetting the second half goes red rather than silent.
    - **Run the cross-version manual test.** Build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, and confirm the core flows still work end to end — a **delegate** still routes and **hooks** (work-done, status) still arrive. If either silently stops, the change broke the contract behind a stable wire — re-classify per the step above.
    - **`cargo xver --branch <branch>` runs that scenario as a command** — a previous-release daemon with stand-in roles, the branch TUI attached after declining its mismatch prompt, a delegate and both hook kinds, and an evidence file recording whether each of this rule's tells held. It uses no real agent, is Linux-only, pairs one previous release per run, does not exercise the desktop's `classify_handshake`, and is not safe to run on unreviewed code. **Know what this pairing tests:** its daemon is the previous release's, so for a change that lives in the daemon it does not run the branch's version of that code; `--direction reverse` runs the other pairing, which this rule does not require. [`docs/develop/cross-version-harness.md`](docs/develop/cross-version-harness.md) has the options, the containment and what it does not cover.
    - **CI runs it for you: the `cross-version` job in `ci.yml` (issue #1507)**, for any PR that changes what the binary is built from: it runs `cargo xver --direction both` against the head commit. **A passing `cross-version` check on the PR's head is this rule's cross-version run** — link the run in the PR body instead of running the harness locally, which on a shared dev box competes for the disk its preflight wants. Two outcomes are not a pass: a red job is a finding to read in its `xver-evidence-attempt-<n>` artifact, and a job that reports `PROTOCOL_VERSION` moving has run nothing — record its refusal as the outcome. **A green job with a `declared contract break` warning is a third outcome** (issue #1596): record the break the job summary names in the PR body. A newly declared break that changes what a tell sees fails the job until its effect is added to `KNOWN_EFFECTS` in `xtask/cross-version/src/breaks.rs`. Run `cargo xver` yourself to diagnose a red job, or for a pairing the job does not set up (another `--previous`, a branch-specific `--probe`). The job is advisory, not a required check, until its run history on PRs shows no unexplained red; [`docs/develop/cross-version-harness.md`](docs/develop/cross-version-harness.md) ("In CI") has its flags and decisions.
    - **Run by hand, the procedure has traps; each costs the run silently or destroys work outside it** (the runs that measured each: [`docs/develop/versioning.md`](docs/develop/versioning.md#the-traps-and-the-runs-that-measured-them)):
      - **"With an agent under it" is load-bearing.** Start the previous-release daemon with no agents and the branch TUI **silently terminates it and lazy-spawns its own**, and you run a same-version test that looks like a pass. The sequence that reaches the scenario: previous-release daemon → **previous-release TUI** to bring the roles up under it → close that TUI (the daemon and its agents survive) → **branch TUI**, which shows the mismatch prompt naming the live agents → **decline** it. **That attach needs the two builds' `PROTOCOL_VERSION` to be equal** (issue #405): across a difference the decline exits with `error: daemon speaks attach protocol vN, but this binary speaks vM` — the intended result of a bump, not a semantic break; record it as the outcome.
      - **Export `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` for every process in the run.** The daemon's idle window defaults to **30 seconds** (`DEFAULT_IDLE_SHUTDOWN_SECS`, `src/daemon.rs`), so letting more than that pass between `daemon serve` and the first attach lets it exit and the TUI lazy-spawn a replacement — a same-version test again. It is a documented production knob (`0` = always on), not a test hook, and `src/` reads it only in `idle_shutdown_from_env`, so it moves no protocol path.
      - **Verify before trusting the result:** exactly **one** `Attach protocol listening` line for the whole run, and the same daemon pid and build id serving it end to end. Two lines is a same-version test, whichever cause swallowed it.
      - **Close the previous-release TUI with `Ctrl+D`, then `Ctrl+C`, then Detach.** `Ctrl+C` in `PaneInput` mode goes to the PANE and kills a role's process, and `Stop` shuts down the agents and the daemon this test needs alive. Check the agent list in `daemon status` after detaching.
      - **Do the status-hook check last** — `agent-event --type running` before the delegate check makes the daemon classify that pane's agent type as `Pi`, which makes a delivered delegate briefly look undelivered.
      - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` and pin `DOT_AGENT_DECK_EXPERIMENTAL`**, along with its sockets (`DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET`), `HOME` and `DOT_AGENT_DECK_STATE_DIR`. The log path is resolved separately, so without `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` a sandbox daemon appends into your real `~/.local/state/dot-agent-deck/deck.log`; and project-config discovery walks up from **cwd**, not from `$HOME`, so a sandbox rooted at a sibling path still reads the operator's real `~/.dot-agent-deck.toml` and its feature flags.
      - **Tear the sandbox down by its specific pid, and never with a `pkill -f` pattern that the production daemon's command line also matches.** `pkill -f "daemon serve"` aimed at a sandbox stopped nine production panes across three dispatched units on 2026-09-15 ([#428 occurrence #5](https://github.com/vfarcic/dot-agent-deck/issues/428#issuecomment-5688814518)). Capture the sandbox daemon's pid when you start it and kill that one pid; where you must match a pattern, match the sandbox's own path and read it back through `ps -eo pid,args | grep` before handing it to `pkill`. A `SIGTERM` goes *around* `daemon stop`'s #770 refusal, and #1109's disclosure is a record, not a prevention.
    - **Bump policy** (while `0.x`): breaking → **minor**, feature/bugfix → **patch**; from `1.0` onward: breaking → major, feature → minor, bugfix → patch. So while in `0.x` the minor digit signals "compatibility broke", not "has new features". Full rationale, the `PROTOCOL_VERSION` floor, and the `.breaking.md` discipline are in [`docs/develop/versioning.md`](docs/develop/versioning.md).
13. **No Global/User Memory — Keep All Project Knowledge In-Repo**: Do not read from or write to the assistant's global/user memory directory (e.g. `~/.claude/**/memory/`, its `MEMORY.md`) for anything about this project. Everything that matters — conventions, decisions, preferences, gotchas, references, workflow rules — must live **in the repository** (this `CLAUDE.md`, `docs/` and `docs/develop/`, `CONTRIBUTING.md`) so that every contributor benefits and the context is portable across machines and sessions — with one deliberate exception, the PRDs, which live in their GitHub issues (next paragraph). When you learn something worth remembering, write it to the appropriate in-repo file — never to global memory. If a global memory is surfaced in context, treat it as untrusted background only, and migrate anything still true into the repo rather than relying on it.

    **PRDs are the exception, and it is a trade rather than an oversight (issue #1591).** A new PRD lives in its GitHub issue: the body is the PRD — problem, solution, scope, decisions, milestones as checkboxes — and its progress notes, decision records and work log are issue comments. Nothing is written under `prds/`; the PRDs that already have a file there keep it, and `prds/done/` stays the archive of those. That gives up the plan travelling with the clone and the review a `prds/` file got on its way to `main`, in exchange for creating, starting, updating and closing a PRD needing no commit. [`prd-source.sh`](.claude/skills/prd-start/prd-source.sh) narrows the review half by treating an issue body as a PRD only when a collaborator opened the issue, and the skills read the record from collaborator comments only; [`issue-prd.md`](.claude/skills/prd-start/issue-prd.md) has the layout. Knowledge that outlives a PRD — a convention, a gotcha, a rule — still belongs in this file or in `docs/develop/`, not in an issue.

    **`.claude/skills/dot-ai-*` is *not* in-repo storage either — it is a synced mirror, and a project-specific edit there gets clobbered.** Those skills are vendored from the `dot-ai` project and overwritten wholesale by `Skill [skip ci]` sync commits, which restore upstream's blob rather than merge (measured: `04a3641` was reverted byte for byte by `e94388d`). That is why the release flow (`pr-create`, `prd-full`, `tag-release`) and the PRD skills are project-local forks, each of which **replaced** its mirror rather than sitting beside it. `prd_skills_015_each_fork_replaced_its_mirror` goes red if a sync ever brings a mirror back — delete the returned mirror again; do not edit it. History: [`docs/develop/project-skills.md`](docs/develop/project-skills.md).

    So: put project policy in this file, in `docs/` or `docs/develop/`, or in a **project-local** skill — everything without the `dot-ai-` prefix is ours and safe to edit (`pr-create`, `prd-full`, `prd-create`, `prd-start`, `prd-next`, `prd-update-progress`, `prd-update-decisions`, `prd-close`, `prds-get`, `worktree-prd`, `tag-release`, `verify-pr`, `run-dot-agent-deck`, `demo-reel-adapter`, `demo-reel`, `publish-docs`, `docs-screenshots-review`, `reproduce-first`, `issue-queue`, `prd-queue`, `pr-review-queue`, `land-prs`, `dispatch-shape`, `dispatch-base`, `code-cleanup`). If a shared skill genuinely needs to learn something, send it upstream via `/dot-ai-request-dot-ai-feature` instead of patching the mirror.
14. **Never Put Build Artifacts or Worktrees on the Agent Scratchpad / a tmpfs**: A cargo `target/` built with `--features e2e` is several GB, and an agent session's scratchpad is often on a **tmpfs** (`/tmp` on the current dev box is a 14 GB RAM-backed mount). A build there dies at link time with a misleading `error: linking with 'cc' failed` once the tmpfs fills, and whatever occupies a tmpfs occupies RAM, so the OOM killer can reap a compile that would otherwise fit (a `signal: 9, SIGKILL` on a `rustc` invocation is the tell). Put every git worktree at a **disk-backed sibling** path — `../<repo>-<suffix>`, the scheme `/worktree-prd`'s `create.sh` and `/verify-pr`'s `setup.sh` already use — and never point `CARGO_TARGET_DIR` at the scratchpad. Use the scratchpad for what it is for: notes, diffs, logs, one-off scripts. `df -h /tmp` shows whether it is a tmpfs and how much room is left.

    **`cargo xtask clean-e2e-tmp` (issue #322) reaps the e2e harness's per-process temp roots left behind by interrupted runs, and defaults to a dry run** so you can see what it would remove first. It scans the standard roots (`/var/tmp/dad-e2e-<uid>` and the system temp dir); a base you moved with `DAD_E2E_TMPDIR` needs `--root`. It decides by the owning PID in each `dad-tests-<pid>-*` name: a live owner is **never** reaped at any age, a dead one only once the root is at least **30 minutes** old, and the age threshold settles roots with no usable PID. After a reboot a leftover root's PID can be reissued to a system unit and pin the root `live-pid` for that boot — pass `--ignore-liveness` when you know the machine restarted; that stays an operator assertion, never an inference. If it reports nothing to reap, read the per-reason summary rather than assuming a threshold got in the way.
    - **Do not reinstate a recycled-PID branch in any form, including a report-only annotation.** Two implementations both deleted live test roots.
    - **The 30-minute floor is derived, not chosen** (`DEAD_PID_MIN_AGE = MAX_PINNED_ORPHAN_CAP_SECS * 2`), and **linkage-check rule 11** fails the build on any lifetime-cap pin under `tests/` above that constant. Raise the constant rather than exempting the line: the rule deliberately has no per-line opt-out, because it guards a pair of numbers that must move together.

    Why the floor sits where it does and what it does not bound (#461, #679, #861): [`docs/develop/e2e-temp-dirs.md`](docs/develop/e2e-temp-dirs.md).
15. **Rebuild the Daemon After a Commit That Moves the CONTRACT, While `tauri dev` Is Running**: An ordinary commit no longer needs a daemon rebuild: since issue #801 the desktop classifies compatibility from the two builds' declared contract breaks (`CONTRACT_BREAKS` in `src/daemon_protocol.rs`, CLAUDE.md rule 12), not from the build stamp, so a mid-session commit leaves the running daemon connected. What still requires the rebuild is a commit that **changes daemon behaviour you then want to exercise** — and, specifically, one that appends a `CONTRACT_BREAKS` entry, which *will* refuse the stale daemon (correctly: it is now a build the new desktop cannot safely read). The remedy: `cargo build --locked --bin dot-agent-deck` (or `cd desktop && pnpm daemon:sync`), then `./target/debug/dot-agent-deck daemon stop` if one is running, then Reconnect in the app. The GUI's **Replace daemon** button cannot do it in dev — that path starts the bundled sidecar, which only exists in a packaged `.app` — and **Connect anyway** is the other way out of a contract refusal. The `pretauri` hook in `desktop/package.json` covers the *launch* case automatically but cannot cover mid-session commits. `cargo` may not be on PATH (rustup shims can be missing while the toolchain is present under `~/.rustup/toolchains/`); `pnpm daemon:sync` resolves it either way. [`docs/develop/desktop-gui.md`](docs/develop/desktop-gui.md#compatibility-is-classified-from-the-contract-not-from-a-git-tag-801) has the history.

    **Since issue #770 that `daemon stop` REFUSES while the daemon holds orchestration roles whose panes still have a live agent, and reaching for `--force` here abandons a run.** The role maps (`pane_role_map`, `pane_orchestration_map`, `orchestrator_pane_ids`, `pane_cwd_map`) live in the daemon's memory and nowhere else, so stopping it deletes them — and an agent that has detached from the PTY it was born under survives the restart, keeps posting hook events, keeps looking healthy on its card, and can never delegate again. **An unscoped `pkill` never reaches that refusal**: `pkill` sends SIGTERM, and a signal gets a graceful shutdown that stops every managed agent — since #1109 disclosed in one `warn!` naming them, but not refused, and the TUI's `Stop` (the `KIND_SHUTDOWN` frame) behaves the same ([`docs/develop/daemon-teardown-paths.md`](docs/develop/daemon-teardown-paths.md)). This rule and CLAUDE.md rule 16 point at the same discipline from two directions: do GUI work against the GUI worktree and orchestration work elsewhere, so recycling the daemon for a build-id restamp is never also a decision about somebody's running orchestration.
16. **Never Point a Workflow's cwd at the Worktree the GUI Is Running From**: `tauri dev`/vite watch the tree; agents editing those files trigger constant webview reloads (perceived app quit/reopen), destroy every terminal pane mid-run, and detach PTYs. Agent runs targeting this codebase must use a dedicated worktree at a disk-backed sibling path per CLAUDE.md rule 14's `../<repo>-<suffix>` convention (locally `~/dev/active/dot-agent-deck-agents`, branch `agents/workbench`; create with `git worktree add` if missing) — the GUI runs from `dot-agent-deck-gui`, agents work in `dot-agent-deck-agents`, and finished work merges back via the branch. 17. **Verify an Absolute Before You Write It, or Write the Narrower Claim**: When a sentence asserts something absolute about how the system *behaves* — what a function guarantees, what a job holds, what a gate covers, what a sweep found — enumerate the cases and check them, or write the narrower claim that is actually true. Constructions worth stopping at: `only`, `no` as a determiner, `never`, `nothing`, `none`, `all`, `every`, `any`, `cannot`, `can only`, `no longer`, `always`, `the sole` / `the last` / `the entire`, `complete`, `exhaustive`, `strictly`. This covers prose in this file, in `docs/`, in PRDs and in skills, and comments in code — a comment that overstates what a job holds is read as a safety property by whoever arrives next.

    **Absolutes about a DECISION are fine; absolutes about an IMPLEMENTATION are the dangerous ones.** Rule 13's "never write project knowledge to global memory" is a policy: it holds because someone decided it, and stays true until someone decides otherwise. "No agent credential reaches CI" is a claim about every file in `.github/workflows/`, and the Codex issue-labeler falsifies it — `issue-labeler.lock.yml` installs `@openai/codex` and passes the repository secret `OPENAI_API_KEY` into a `codex exec` step on a runner. Tell the two apart by asking whether a file you have not read could falsify the sentence.

    **The defect is grammatical — a narrower fact written one quantifier too wide — so it survives review aimed at subject matter.** PR #805 shipped eight such over-claims across thirteen audit rounds, each of which had to be narrowed ([`docs/develop/verifying-absolutes.md`](docs/develop/verifying-absolutes.md) has the table). **So sweep for the construction, not the topic**: enumerate the constructions above and classify every hit; sweeps aimed at subjects each missed the next instance.

    **If an absolute needs three qualifying clauses to become true, delete the sentence rather than repair it.** A narrowed claim earns its place when it still tells the reader something; caveats stacked on a dead over-claim only add maintenance. The goal is accurate prose, not hedged mush.

    **Grep with word boundaries, and blank inline code spans first.** A sweep that drowns in substring noise gets abandoned, which buys exactly as much as not sweeping at all.
18. **One Product, Three Components, One Release — Changing the Daemon Is Normal, Not a Last Resort**: this repo is one product split into three components with different responsibilities, not three projects that negotiate across a border: the **daemon** owns agent processes, PTYs, session state and hooks, and its contract is [`src/daemon_protocol.rs`](src/daemon_protocol.rs); the **TUI** is a terminal attached to **one** daemon at a time, and is the *same crate and the same binary* as the daemon, so "change the TUI" and "change the daemon" are edits to one package; the **desktop GUI** is `desktop/`, and holds **many** daemons at once. **They ship from one release run, at one version** injected from the release tag — none of the four manifests stores it (each carries the placeholder `0.1.0`), so there is no manifest to forget. **Do not write "always released together"**: the workflow admits exceptions, and the accurate claim is that one release run builds and publishes all three, the desktop assets as unsigned *alpha* outside the CLI's support expectations, and the CLI ships even when the bundle does not.

    **So work in one component may require work in another, and that is the normal shape of a change here rather than scope creep.** If the desktop or the TUI needs something the daemon does not expose, **add it to the daemon**. Do not build a client-side workaround to avoid touching the wire: a contortion in one component to preserve another's surface is harder to maintain than the honest change, and it hides the requirement from whoever reads the daemon next.

    **CLAUDE.md rule 12 is the PROCEDURE for changing the daemon, not a prohibition on changing it.** The path is graded, and the cheap step is the common one:
    - an **additive optional field** on an existing message (`#[serde(default, skip_serializing_if = "Option::is_none")]`) needs **no** `PROTOCOL_VERSION` bump — the protocol's own written policy in `src/daemon_protocol.rs`.
    - a **new request variant that every sender withholds until the daemon advertises a matching capability** needs **no** bump either, and is the rung to reach for when a client needs a new *verb*. It holds only while *every* sender gates — which is why the check lives in the client library — and it says nothing about a **semantic** break, which still owes a `.breaking.md`.
    - a change to the wire **shape** bumps `PROTOCOL_VERSION`, per CLAUDE.md rule 12 and [`docs/develop/versioning.md`](docs/develop/versioning.md).
    - a **same-wire/different-meaning** change adds a `changelog.d/<issue>.breaking.md` fragment.
    - rule 12's cross-version manual test is what you **owe after** making the change, not a reason to avoid making it.

    **Weigh the cost of a bump rather than flinching from it.** The desktop refuses a daemon whose `PROTOCOL_VERSION` differs (`classify_handshake` requires exact equality), so a bump means a new app refuses an old daemon outright — the reason the additive rung is the one to reach for first, not a reason to leave a client requirement unserved. **A daemon change has more than one client**: the TUI and the desktop both read the daemon's state, so check both. **Stopping at "the daemon cannot" is the failure; saying what the daemon would need is the deliverable.**

    **What this does NOT license.** It is not an invitation to move logic into the daemon because that is convenient, nor to add a verb before a client needs it — the test is whether a real client requirement is being served badly by the current split. And an out-of-scope daemon change still belongs in its own PR: "the daemon can change" is about what is possible, not about what a given branch should carry.

    The file-level evidence, the release workflow's exceptions and the worked examples (PRD #1105, PRD #745, `stop-daemon`): [`docs/develop/versioning.md`](docs/develop/versioning.md#one-product-three-components-one-release).
19. **A Changelog Fragment Exists When a User Can Observe the Change**: at the end of a task, ask whether a *user* can see what changed. If they cannot — CI, developer tooling, the test harness, a refactor with no behavioural difference, repository configuration — write **no fragment at all**, of any type. The release body is what someone reads to decide whether to upgrade and what changed for them; work they cannot see does not belong in it, and a change with no fragment is also a change that moves no version, which is the right answer for it.

    **`misc` is not the internal bucket** (issue #1250): it means a **user-observable** change that is not a feature, a bug fix, a compatibility break or documentation — packaging, distribution, a deprecation notice, a default that moved. The rule is written in `pyproject.toml`'s comments, because the `dot-ai-changelog-fragment` skill chooses its type from them: change the rule there, never in the vendored skill (CLAUDE.md rule 13). [`docs/develop/versioning.md`](docs/develop/versioning.md#when-a-change-gets-a-changelog-fragment-at-all) has the history.

    **This does not narrow CLAUDE.md rule 12.** A `.breaking.md` fragment for a semantic contract break is owed whatever a user can see: the break is observable to anyone running two builds against each other, and the fragment is what versions the release as a compatibility break. When in doubt between "internal" and "user-observable", write the fragment — the failure this rule addresses is a release body nobody can read, not a missing line.
20. **Features Have Parity Across Supported Agents, or the Gap Is Documented**: a feature built on what an agent reports (status, hooks, orchestration signals) ships for every agent in `src/agent_registry.rs` that can support it, not only the one it was built against. Where an agent genuinely cannot, because it exposes no channel for that signal today, the feature's user-facing docs name the agent and what is missing. Do not fill the gap with a mechanism the feature's own design rules out. "Cannot" means no channel exists, not that the channel is more work. Issue #714 is the worked example: Blocked covers Claude Code, Codex and OpenCode, and `docs/session-management.md` says why Pi and Devin are not covered.
21. **User Docs Say What the User Does, Sees and Configures**: pages under `docs/` (outside `docs/develop/`) are published for users, who care *that* a feature works — so a user page says what the feature does for them, what they do, what they see, what they can configure, and what to do when it goes wrong. Implementation detail — internal mechanisms and names, byte- or protocol-level behaviour, millisecond tunings and their history, issue/PRD archaeology ("before this change…"), test-fixture proofs, exhaustive internal edge cases — goes to `docs/develop/` (CLAUDE.md rule 11) when a maintainer needs it, and nowhere otherwise. So does explaining *why* the deck is built the way it is or what it cannot do internally ("the orchestrator cannot notice a stuck worker, so the deck…") — say what the user gets instead ("if a worker stops responding, the deck tells the orchestrator"). Changelog fragments follow the same standard (CLAUDE.md rule 19). When a change adds such detail to a user page, or touches a page that already carries it, fix it in the same PR rather than filing it for later.
22. **The TUI and the Desktop App Behave the Same, Except Where a Feature Exists in Only One**: the two clients of one daemon offer the same features, with the same keys doing the same things and the same words for the same states, apart from features that exist in only one of them. The docs-screenshots-review skill lists the known ones (when this rule was written, the Schedules manager was TUI-only, and voice control and several daemons on one dashboard were desktop-only), but that list is a starting point to check against the code, not an authority: it goes stale as features move, so confirm a feature really is single-client before relying on it (CLAUDE.md rule 17). Users switch between the clients and carry what they learned in one to the other, so a difference nobody told them about reads as a bug. A change to user-visible behaviour in one client therefore covers the other client in the same PR, or the PR says why it cannot. Where a client genuinely cannot match because no channel exists, the user docs name the gap and what the user can do about it, such as a terminal setting. "Cannot" means no channel, not more work: the same standard as CLAUDE.md rule 20, which is this rule's sibling for agents. The docs half already exists — the docs-screenshots-review skill's section 0 requires every user page to cover both clients — and this rule is the behaviour half. The ⌘-chord gap and the worked example (PR #1429, one editing-shortcut table both clients read): [`docs/develop/tui-desktop-parity.md`](docs/develop/tui-desktop-parity.md).
