# Contributing to dot-agent-deck

## Prerequisites

Enter `devbox shell` for the pinned toolchain — it provides `cargo-nextest` (test runner), `asciinema` (cast replay), and the rest of the project's CLI deps. Outside devbox, install nextest manually with `cargo install cargo-nextest --locked`. The `cargo test-fast` / `cargo test-e2e` / `cargo test-e2e-live` aliases in `.cargo/config.toml` resolve through nextest; without it they error with `no such command: nextest`.

The agent CLIs (`claude`, `opencode`, `codex`, `pi`) installed locally and logged in are needed only for the **live** lane, `cargo test-e2e-live` — the chain-smoke and other real-agent tests skip with a specific reason if the CLI or its credentials are missing. `cargo test-e2e` needs none of them.

### Cloning on Windows: turn symlinks on first

This repository tracks 35 symlinks — `AGENTS.md` → `CLAUDE.md`, the 33 entries under `.agents/skills/`, and `docs/img`. Git creates them as real links only when `core.symlinks` is on, which on Windows means Developer Mode is enabled (Settings → System → For developers) or git ran elevated. Otherwise git writes each one as a plain text file containing the target path — no error, no warning. `AGENTS.md` becomes a 9-byte file reading `CLAUDE.md`, so Codex and OpenCode, which read it for this project's conventions, silently get **no instructions at all**, and the skills tree resolves to nothing.

So turn on Developer Mode (or `git config --global core.symlinks true`) **before** cloning, and confirm with:

```sh
scripts/check-symlinks.sh
```

It prints `all 35 tracked symlinks materialised …` on a healthy clone and names every broken one otherwise. [`docs/develop/windows-symlinks.md`](docs/develop/windows-symlinks.md) has the repair steps for a clone that already came out wrong, and why CI can guard the runner but not your working tree.

## Snapshot review workflow

L1 widget/layout regressions are pinned by `insta` file snapshots under `tests/snapshots/`. When a PR's diff includes a new or modified `.snap` file, read the snapshot diff like a rendered screen — each line corresponds to one row of the dashboard's parsed grid. Accept the change only if the new rendering matches the catalog entry's prose; otherwise loop the change back to the author. Locally, `cargo insta review` walks pending diffs interactively.

## Reported bugs start with a failing test

When someone reports that something is broken, the first deliverable is a test that fails *for their reason* — not a fix. Then fix it and watch that same test pass. Assert the outcome at the altitude the reporter is looking at it: a file on disk, a log line, or a registry entry can all be correct while the screen is wrong. Before trusting a new test, confirm you have seen it fail, and after fixing, revert the fix once to confirm it goes red again — an assertion never observed failing is not evidence that it covers anything.

Prefer the reporter's configuration over a convenient stand-in. A `cat` role or a print-mode agent proves the plumbing and hides everything else — several defects here shipped green because the only coverage used one. Where a stand-in is necessary for cost, say so in the test and name what it stands in for.

(Agents working in this repo: the `reproduce-first` skill carries the full procedure and the traps that have cost real time.)

## TDD loop

Fast tier (per-task gate):

```sh
cargo test-fast lifecycle_001     # filter to one test
cargo test-fast                   # run the full fast tier
```

E2e tier — two lanes since issue #502, split by whether a test reaches a **real agent** (CLAUDE.md rule 5):

| Lane | Command | Contents | Runs |
| --- | --- | --- | --- |
| 1 — deterministic | `cargo test-e2e` | the `tests/e2e_*.rs` files that reach no real agent | in CI, on every PR (the `e2e-deterministic` job) |
| 2 — real agent | `cargo test-e2e-live` | a **superset**: every `tests/e2e_*.rs` file, so lane 1 plus the credentialed ones | **your machine only — never CI** |
| 3 — local | either alias with a filter | the test you are debugging, then its module | your machine |

The `Command` column is the convenient spelling, not the definition. A lane is selected by the cargo **features** its files' `#![cfg(…)]` attributes read, so a raw `cargo nextest run --workspace --features e2e,e2e-live <filter>` runs lane 2 exactly as `cargo test-e2e-live <filter>` does. The aliases in [`.cargo/config.toml`](.cargo/config.toml) are worth using anyway — they are shorter and carry `--workspace` for you — but running the raw command counts.

**There is no obligation to run the full tier before opening a PR.** That mandate was removed with issue #502: CI runs lane 1 on every PR, and every dispatched agent running the whole tier concurrently was itself a source of failures (#415 measured 6-7 of 40 files failing in parallel against 40/40 at `-j 1`). What you *do* owe is **the tests covering what you changed** — any tier, credentialed included — found via [`tests/CATALOG.md`](tests/CATALOG.md), the `#[spec]` annotations, or `cargo xtask list-tests`, and named in your PR description:

```sh
cargo test-e2e lifecycle_001            # lane 1 needs no credentials
cargo test-e2e-live claude_001          # lane 2 needs your own agent credentials
```

**No e2e test reaches a real agent in CI, and no test credential is registered on this repository.** (That is about the test tier. The Codex issue-labeler is a separately credentialed workflow that does pass a repository secret to a real agent on a runner — its own feature, its own threat model, [`docs/develop/issue-labeling.md`](docs/develop/issue-labeling.md), out of scope here.) Running a credentialed job less often does not reduce the risk that a key leaks from a public repository's CI — it reduces the number of exposures, not the vulnerability — and the line that matters is "reaches a real agent", not "reads a key", because your agent CLIs are already logged in. So lane 2 runs only where you run it, and a real-agent regression surfaces when someone runs those tests rather than on a schedule. That is a deliberate trade, and running lane 2 for the surface you touched is your half of it.

For a watch loop, `bacon test-fast` (or `bacon test-e2e` / `bacon test-e2e-live`) reruns on every save; press `f` to filter to currently-failing tests, `esc` to clear. Function names follow Decision 17's `<sub-area>_<NNN>_<suffix>` pattern, so the filter is unique by construction.

[`docs/develop/e2e-lanes.md`](docs/develop/e2e-lanes.md) covers the operational side: how to drive lane 2, why a green run can still mean almost nothing, and what keeps a credential out of the `.cast` recordings the demo reel publishes.

## How to add a new test

1. Pick an existing catalog ID in `prds/77-tui-testing-harness.md` under `## Test Case Catalog`, or add a new one (format: `<area>/<sub-area>/<NNN>`).
2. Write the test under `tests/render_<area>.rs` (L1) or `tests/e2e_<area>.rs` (L2), naming the function `<sub>_<NNN>_<short_suffix>` (Decision 17). Annotate with `#[spec("<area>/<sub>/<NNN>")]` from the `spec` dev-dep so the linkage check picks it up. A `#[tokio::test] async fn` is fine — the checker binds annotations with a real Rust parser, so the older "sync wrapper that blocks on an `_inner()` async fn" shape is a choice, not a requirement (issue #406).
3. Add a `/// Scenario:` doc comment of 1–3 sentences to the test function describing what it does in plain English (Decision 30). Run `cargo xtask docs --tests` whenever you want to refresh the local rendered `.md` under `.dot-agent-deck/recordings/<test>/test.md` — it's a browsing aid (gitignored, regenerated like `cargo doc`), not a commit gate.
4. Run `cargo xtask linkage-check` locally — it verifies the annotation matches the catalog, the function name carries the required prefix, no raw `sleep` / fixed-count polling crept into `e2e_*.rs`, AND the Scenario doc comment exists + the docs generator succeeds against the current source + catalog (rule 7). Before any of those it runs a repository-state preflight, which checks the repository rather than the catalog: it fails on a shallow object store when the clone has more than one worktree or the current checkout is itself a linked worktree, or on a registered worktree whose directory no longer exists, and when it fails `linkage-check` exits without running anything else. So `linkage-check` can fail with no catalog problem at all, and while the preflight fails it reports none of the checks above: fixing a Scenario comment will not change the output until the repository is. Each preflight failure names its remedy; [the linkage-check rule registry](docs/develop/linkage-check-rules.md#what-is-not-a-rule) explains why it is a preflight rather than a rule. If the new ID was previously on `xtask/linkage-check/m2.allowlist`, delete that line.

- [The directory-listing verb](docs/develop/directory-listing-verb.md) — the threat model and bounds for `ListDirectories`, the daemon verb behind the desktop's new-agent directory step (PRD #1223): one level per request, directories only, hidden and symlinked entries left out, a 1000-entry cap and a 2 s time budget that set `truncated` instead of failing, and canonical absolute paths both ways. Covers why it adds no authority — the same attach endpoint already accepts `StartAgent` with an arbitrary command and working directory — why that answers PRD #819's "resolve-only, never list" bound rather than overturning it, why the verb is bounded anyway, and the condition under which it must be re-examined alongside `StartAgent`: PRD #741 admitting a peer with less than full account authority.
- [Voice-first design](docs/develop/voice-first-design.md) — the standing principle that every new desktop feature must be reachable by voice, asked as a design-time question rather than a post-hoc audit, with PRD #1223's New agent dialog as the worked example: why a multi-step wizard resists a resolver that sees one utterance at a time and what collapsing it into one dialog bought, the resolver kinds that exist and the touch points a new one costs (and why `requires` is a column rather than a `Screen`), why a directory can be named only against the children on screen (the declined search verb), how D5's confirmation gate works today and where it will live, why names from repositories, configs and remote decks are untrusted — what leaves the machine on each command, the voice panel's **Names** setting, the untrusted data turn and the transcript-grounding check — why rule 13 proves classification rather than completeness, and a checklist for a new surface.
- [Adaptive issue and pull request labeling](docs/develop/issue-labeling.md) — the repository label taxonomy, read-only preview and live learning workflows, activation gate, batch limits, local `gh-aw` compilation, memory model, correction behavior, and security boundaries. Also records which mechanism owns the triage taxonomy: this workflow, not PRD #421's scheduled `triage-issues` skill, and why running both would be read as maintainer feedback rather than as a duplicate — while PRD #421's `agent-deck/claimed` dispatch claim stays outside it and cannot collide.
- [The linkage-check rule registry](docs/develop/linkage-check-rules.md) — how to add a rule to `cargo xtask linkage-check`, which is now one entry in `RULES` and nothing else (issue #1216). Covers the four hand-maintained places that entry replaced and why they made two unrelated rule-adding pull requests conflict by construction — with the hardcoded rule count the worse half, since two branches raising the same literal produce identical text that git merges cleanly and silently; the two shapes a rule takes (its own `run(root)` module, or a bucket on the one shared line scan); the conventions a new rule is expected to follow (say what it cannot see at the finding, refuse to pass vacuously when an input goes missing, plant bad input in tests rather than trusting a clean checkout); why rule numbers are stable identifiers that never renumber and how to retire one instead; and what in that crate is deliberately *not* a rule.
