# RWX: the Linux CI backend switch and sandboxed test runs

This repository can use [RWX](https://www.rwx.com) in two places, each behind its own switch. Both are off unless someone turns them on, and turning either off restores the plain GitHub Actions and local setup without touching anything else.

| switch | where | on | off |
| --- | --- | --- | --- |
| Linux CI backend for pull requests | the file `.github/ci-backend` | `rwx` | `gha`, or delete the file |
| test commands of `cargo xtask affected-checks --run` in an RWX sandbox | the environment variable `DAD_REMOTE_EXEC` | `rwx` | unset |

## The CI backend switch

**Where each job runs.** `.github/ci-backend` decides which system runs a **pull request's** Linux jobs. Pushes to `main` run everything on GitHub Actions whatever the file says, so `main`'s post-merge verification and the cache saves from #1743 never depend on RWX.

| job | pull request, `ci-backend=rwx` | pull request, `ci-backend=gha` | push to `main` |
| --- | --- | --- | --- |
| every Linux job in `ci.yml` (`fmt`, `clippy`, `build-release`, `test`, `e2e-build`, the `e2e` shards, `desktop-web`, `desktop-browser`, `desktop-driver`, `windows-cross-check`, `security`, `nix`, `devbox`) and `aarch64-crossbuild-check.yml` | RWX | GitHub Actions | GitHub Actions |
| `release-lib` in `ci.yml` (advisory) | RWX, as `.rwx/release-lib.yml` (status `RWX: release-lib`) | GitHub Actions | GitHub Actions |
| `cross-version` | GitHub Actions | GitHub Actions | GitHub Actions |
| `build-macos` | not run | not run | GitHub Actions |
| `build-windows` | `if: false` until Windows ships | | |
| `changes`, `notify-main-red`, `docs.yml`, the reviewer, labeling, releases | GitHub Actions | GitHub Actions | GitHub Actions |

The exceptions, and why:

- **`cross-version` stays on GitHub Actions.** Its harness contains the builds in unprivileged bubblewrap namespaces, and inside an RWX task bwrap cannot set up the network namespace (measured 2026-10-22: `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`).
- **`release-lib` moves to a run definition of its own, `.rwx/release-lib.yml`.** RWX reports one status per run and any failing task fails it, so a task in `.rwx/ci.yml` would be part of the required `RWX: linux`; the job is advisory ([release-lib-tier.md](release-lib-tier.md)).
- **`docs.yml` stays.** `docs-preview.yml` deploys the preview from its uploaded artifact through `workflow_run`, which only a GitHub Actions run can feed.
- **`build-macos` runs on `main`, not on pull requests.** RWX has no macOS runners, and on a pull request it was the slowest required check (5 to 18 minutes) for a 3% rate of macOS-only failures (545 runs, 2026-10-06 to 10-21). A macOS-only defect now surfaces on `main`: whoever merged watches that run and owns a red (the `merge-pr` skill), `notify-main-red` opens an issue, and `tag-release.yml` refuses to release a `main` whose run is not green. **A `build-macos` red can also be GitHub not giving a job a runner**: on 2026-11-16 the hosted macOS arm64 pool ran short and four runs had `build-macos-*` jobs cancelled after 15 minutes in the queue with "The job was not acquired by Runner of type hosted even after multiple attempts". `rerun-unacquired.yml` reruns a `main` push or dispatched run whose only failures are such jobs (and the aggregates over them), once, and `notify-main-red` holds its alert for that first attempt only; `scripts/ci-unacquired-runners.sh` decides, and any other failure leaves the run red for a person.

**How the switch works.** Both systems trigger on every pull request and both read the file at the **PR's head commit**, so they always make the same choice (GitHub Actions tests the merge commit, but reading the switch there would let a PR cut before `main` switched leave both sides skipping):

- **GitHub Actions** (`.github/workflows/ci.yml`): the `changes` job reads the file through the API and exposes `linux_backend`. When it says `rwx`, each Linux job's `if:` is false, so the job is skipped, and a job skipped by its own `if:` satisfies a required check. `aarch64-crossbuild-check.yml` has its own copy of that read.
- **RWX** (`.rwx/ci.yml`): the `backend` task reads the file. Unless it says `rwx`, every check task is skipped and the run passes in seconds, so RWX's check, `RWX: linux`, can be required whichever side is active.
- **Both skip the same jobs for the same change**: `scripts/ci-changes.sh` holds the path classification (a Renovate PR touching only the devbox or flake files, whether the change feeds the binary, whether the manifests changed), and both call it. GitHub Actions takes the PR's files from the API (a renamed file by both its paths); RWX computes them against the merge-base with the PR's base with `git diff --no-renames`, which is the same list.

Flipping the switch is a one-line pull request, and it takes effect on that pull request itself.

### What to know before turning it on

- **The ruleset has to require `RWX: linux`.** With the switch on, `build` and `e2e-deterministic` pass as skipped, so nothing blocks a merge on the Linux verdict until RWX's check is required too. `scripts/apply-branch-protection.sh`'s default list carries it, and the agent reviewer reads commit statuses (which is how RWX reports) as well as check runs. Applying the ruleset needs an admin, and only after `.rwx/ci.yml` is on `main`: a pull request whose branch lacks it gets no RWX run, so `RWX: linux` never reports and it cannot merge until it merges `main`.
- **Switch back before the credits run out.** A pull request that flips the file back to `gha` still runs on RWX until it merges; if RWX can no longer run, that PR's required RWX check never passes, and merging it needs an admin bypass. The same holds for removing `RWX: linux` from the ruleset.
- **RWX tests the PR's head commit; GitHub Actions tests the PR merged into its base.** A PR that is green on its head and red once merged with a moved `main` is caught by the overlap check before a merge (CLAUDE.md rule 8) and by `main`'s push run.
- **A pull request from a fork needs someone to start its RWX run by hand** in the RWX UI.
- **Tool caches live in the vault `dot_agent_deck_rwx_eval`, which must be LOCKED with `main` as its only permitted branch** (RWX UI: Vaults, then the vault, then Access Control), and whose "Allow public repositories" setting must stay on for GitHub-triggered runs on this public repository. RWX lets a run write a tool cache only when the vault is unlocked for it, so with that setting a pull request's run reads the caches and cannot write them, and a PR's build code cannot plant files that a later PR restores (the counterpart of `ci.yml` saving Rust caches only from `main`, #1743). The caches are written by `.rwx/ci.yml`'s daily cron (`main-tool-caches`, 04:00 UTC), which RWX runs on `main` and which keeps them inside their 48-hour lifetime. Until that first cron run after a lock, PRs build without caches (slower, not broken). A tool cache holds what its task changed on top of the layers it ran on, so restoring one over different layers can leave it naming files that are not there: the `nix` and `devbox` caches therefore carry the Nix release in their names, which renovate.json's NixOS/nix manager bumps with `NIX_VERSION` and `xtask/linkage-check`'s `rwx_nix_cache_keys` holds together (issue #2529), and the Ubuntu packages `desktop-driver` and `aarch64-crossbuild` need come from content-cached tasks of their own (`desktop-driver-packages`, `aarch64-packages`), so a run downloads them only when that task's inputs change (issue #2519).
- **Versions stay in step with local.** `.rwx/ci.yml` and `.rwx/sandbox.yml` pin the toolchain a third time, after `devbox.json` and the workflows. renovate.json's RWX customManagers bump them in the same grouped PRs as the other copies (every RWX bump is held for a human), and `scripts/check-pin-lockstep.sh` fails `cargo test-fast` when the Rust toolchain, nextest, pnpm or go-task in `.rwx/` disagree with `devbox.json`. RWX's own package versions (`git/clone`, `nodejs/install`, `rust-lang/install`) have no Renovate datasource and are bumped by hand.
- **Reading a red:** RWX's failures are not in `gh run view`. `gh pr checks <n>` lists `RWX: linux` with a link to the run, and `rwx results <run-id>` (or `rwx logs <task-id>`) shows what failed. For every test's outcome and time, not only the failures, see [Per-test results](#per-test-results).

### Per-test results

`rwx results <run-id> --json` gives each task's `TestCount` and `FailedTestCount`, and its text output names the failed tests, but it does not return the tests themselves. Measured on 2026-11-16 with CLI v3.36.1 (issue #2101): `rwx results` in either format, `rwx artifacts list` on a task that declares a `test-results` output (it answers `Artifacts for task … not found`) and `rwx mcp serve`, whose one tool is `get_run_test_failures`, returned no passing test and no per-test time; the Captain API pages in RWX's docs describe endpoints for test suites and flaky tests, not for one run's results. Before this, per-test results came from parsing nextest's lines in `rwx logs`, and the TypeScript suites' could not be read at all.

Each task that runs tests (`test`, the five `e2e` shards, `desktop-web`, `desktop-browser` and `desktop-driver`) also copies its JUnit file into `$RWX_ARTIFACTS` as `junit.xml` from an `EXIT` trap, so a failing task keeps it too. Read a run's files with:

```bash
scripts/rwx-junit.sh <run-id> [<out-dir>]     # <out-dir>/<task-key>/junit.xml, one per task
rwx artifacts download <task-id> junit.xml --output junit.xml   # one task
```

The script prints `<task-key> downloaded`, `missing` or `failed` for each task that reported tests, and exits non-zero unless every one downloaded; a run from before #2101 merged reads `missing` throughout. It reads each task's latest attempt; a nextest retry inside that attempt is in the file as `<flakyFailure>`. The nextest files are the format `.config/nextest.toml` describes, the same ones `ci.yml` uploads as GitHub artifacts.

## Sandboxed runs for agents

The point is twofold: the checks finish sooner, and the machine the agents run on stays free for them. With `DAD_REMOTE_EXEC=rwx`, `cargo xtask affected-checks --run` runs **every `cargo` command except `cargo fmt`** (so clippy and the test tiers, every compile) through `rwx sandbox exec --`, in the sandbox `.rwx/sandbox.yml` defines. `cargo fmt` stays local because it compiles nothing.

Measured on 2026-10-21, the full gates for a one-line Rust change, from an M-series Mac:

| | wall | CPU used locally |
| --- | --- | --- |
| all local | 512 s | 1,168 s |
| sandbox, cold (new sandbox) | 270 s | 15 s |
| sandbox, warm (kept from the previous run) | 143 s | 15 s |

The local run also failed ten tests that pass serially and on Linux, which is the machine being contended rather than the code.

It runs locally instead, and prints a note saying why, when the `rwx` CLI is missing, `rwx whoami` fails, `.rwx/sandbox.yml` is absent, or the variable names anything other than `rwx`. An unset variable prints nothing and changes nothing.

**Setting it on a box.** Every agent a deck daemon starts inherits the daemon's environment, so the variable has to be in the environment the daemon starts from, not only in one shell. On a box set up with `scripts/box/bootstrap.sh`, `--remote-exec` exports `DAD_REMOTE_EXEC=rwx` in the same three places `--use-vals` exports `USE_VALS`: a marked block at the top of `~/.bashrc`, `~/.config/environment.d/999-dad-box.conf`, and the running systemd `--user` manager. Like `--use-vals`, it sticks across re-runs while its block is in `~/.bashrc`, and a daemon that is already running gets it only once it is stopped and started from a fresh login. To turn it off, delete the block and re-run. The flag is opt-in because the sandbox's compute is billed to the account the `rwx` CLI is logged in as. The script installs the CLI either way, and logging it in (`rwx login`) is the operator's step. Until then the helper runs locally with the note above, and the run's closing list of logins still to do names `rwx`. Before the flag existed, the variable reached the agents only when whoever started the daemon had set it. In #1980's window it had been set, but nothing in the repository made sure of that (#2097).

With the standard `OTEL_*` variables set, as they are in an agent's shell under a deck with telemetry on, each `--run` also sends a trace recording which runner each command used, why a requested runner fell back, and how long each command took, so time with and without the sandbox can be compared across many runs rather than from one table: [gate-telemetry.md](gate-telemetry.md).

### For agents

When `DAD_REMOTE_EXEC=rwx` is set, run the commit gates through `cargo xtask affected-checks --run` rather than command by command, and run every other `cargo` command that compiles as `rwx sandbox exec -- <command>`: a build, a filtered `cargo test-e2e`, and a `cargo test-fast` or `cargo nextest` run filtered to a single test, since a filter narrows what runs, not what compiles. An e2e run also goes through `scripts/rwx-export-root.sh` inside the exec ([The export chain](#the-export-chain)). Unlike the helper, `rwx sandbox exec` does not fall back to a local run, so when `rwx whoami` fails run the command locally and say so. That includes `cargo mutants`, which `.rwx/sandbox.yml` installs at the version `/code-cleanup`'s `find-targets.sh` pins (until 2026-10-31 it was not installed, so mutation runs stayed on the shared box, and on 2026-10-27 one with `-j 5` drove its load to 80, mostly disk wait); still run it without raising `--jobs`, since each job is a separate full rebuild and link. Split a command that could run past 30 minutes into several execs (`cargo mutants --shard k/n`, test filters), because RWX kills one exec at 30 minutes and stops the sandbox with it ([Stopping](#stopping)). Leave the sandbox running when the command is done: a team's agents share their worktree's sandbox, and a stop kills a command a teammate is running in it. These instructions are repeated where agents read them first: the coder and tester role templates in `.dot-agent-deck.toml` and the gates that `/issue-queue` and `/prd-queue` put into a dispatched unit's task, since units given them only through CLAUDE.md rule 5 ran heavy commands locally with the switch on. Those places said "heavy" until 2026-10-30, when two units given the instruction ran a single-test `cargo nextest run <filter>` locally, not counting it as heavy, and took the shared box from a load of 2 to 26 in minutes; they now name the filtered runs. In #1980's window (2026-10-30 to 11-03) every gate run had the switch on and sent its compiles to RWX, yet Codex testers, whose role template named only the test commands, ran `cargo clippy` locally 42 times, and a coder ran a nine-minute `cargo check` locally (#2097); the templates and the queue skills now name `cargo check` and `cargo clippy` as well, and the tester's template names `cargo clippy`, `cargo check`, `cargo build` and `cargo mutants` alongside the test commands. **Never run lane 2 (`cargo test-e2e-live`, or any command with the `e2e-live` feature) or anything else that reaches a real agent in the sandbox**: no agent credential is placed there, and CLAUDE.md rule 5's reasons for keeping credentials off remote runners apply to it as much as to CI.

`desktop/`'s commands can go there too: the sandbox installs pnpm at `devbox.json`'s pin and Playwright's Chromium and WebKit with the Ubuntu packages they need (the `pnpm` and `playwright-browsers` tasks, copies of `.rwx/ci.yml`'s), so run them as `rwx sandbox exec -- bash -c 'cd desktop && pnpm install --frozen-lockfile && pnpm test'`, and likewise `pnpm test:browser`. Until 2026-11-26 neither was installed, and these ran on the shared box. Every sandbox, a Rust-only one included, waits for the browser task, so its cache is keyed on the `@playwright/test` pin alone: `playwright-version` reads the pin from `desktop/package.json` into a value, and `playwright-browsers` takes it as an env var rather than using the checkout, so a dependency bump that moves another line of that file reuses the installed browsers. Measured on 2026-11-26: a cache miss took 14 minutes on a slow Ubuntu mirror and 71 s on a fast one; with a line added to `desktop/package.json` and the pin unchanged, `playwright-version` ran again and `playwright-browsers` was a cache hit; and in the sandbox vitest passed 3,116 tests in 28 s and the Playwright suite passed 602 in both browsers in 2.4 minutes.

### Stopping

A sandbox is billed per second while active, idle included, and it stops itself after 5 minutes without activity (`--inactivity-timeout` in `.rwx/sandbox.yml`); a running command counts as activity, so that 5-minute stop does not cut a running command off. Apart from the 30-minute limit on one command (next paragraph), nothing else stops it by default, `--run` included: one unit's coder and tester work in the same worktree and so share its sandbox (RWX keys it by branch and config path), and until 2026-10-31 `--run` stopped the sandbox when it finished and the templates told agents to stop it after each command, so one agent's stop killed the command the other was running in it ("container does not exist", "cannot exec in a stopped container"), and every run after a stop started cold (the table's cold row rather than the warm one). Leaving it running costs at most five idle minutes after the last command. `DAD_REMOTE_EXEC_KEEP=0` makes `--run` stop it when it finishes, for a run you know nobody shares; that stop checks `rwx sandbox list` and stops it a second time, because `rwx sandbox stop` can time out and leave the sandbox active.

**One `rwx sandbox exec` is killed 30 minutes after it starts, and the whole sandbox stops with it** (issue #2077). Measured three times, each ending with `Task finished with exit code 137` in the sandbox task's log (`rwx logs <run-id> --task sandbox`) exactly 30:00 after the exec started: two long `cargo mutants` runs on 2026-11-03, and a `sleep 1900` on 2026-11-14 with CLI v3.36.1. The sandbox's `target/` and `/tmp` go with it, along with anything a teammate was running in it, and the local CLI reports only `failed to pull changes from sandbox`. It is not the 5-minute idle stop, and it is not the sandbox's age: a 21-minute exec survived, and one of the killed sandboxes had been alive for 66 minutes. Where RWX enforces it was not established. The CLI (v3.36.1) runs the command over SSH with no deadline of its own, and RWX's sandbox docs name no limit on one command. `rwx-sandbox --help` lists only `--first-exec-timeout` and `--inactivity-timeout`, and both default to 30m, the same as the kill. `.rwx/sandbox.yml` passes only `--inactivity-timeout 5m`, so either default may be what fires. Setting either flag above 30m was not measured. The 2026-11-14 kill came 30:00 after that exec started, not 30:00 after the sandbox's first exec two minutes earlier, which does not fit `--first-exec-timeout`'s documented meaning, though the docs do not rule it out. Until a run with both set higher (for example `rwx-sandbox --first-exec-timeout 2h --inactivity-timeout 2h`) survives past 30 minutes, split any command that could run past 30 minutes into several execs: `cargo mutants --shard k/n`, one exec per shard, or a long e2e run as several test filters, one exec each.

The sandbox sees uncommitted changes in the worktree, so it stands in for a local run before a commit.

### The version the sandbox's builds report

The sandbox's checkout is a shallow clone with no tags, so `build.rs`'s `git describe` finds no version there, and a build with neither `DAD_VERSION` nor a tag reports `0.1.0+unknown` (issue #326), which `remote upgrade` without `--version` refuses. So `.rwx/sandbox.yml`'s `version` task reads the newest `vX.Y.Z` tag at origin with `scripts/latest-release-version.sh` when the sandbox starts and sets it as `DAD_VERSION` for every command the sandbox runs, the way `.rwx/ci.yml`'s `backend` task and `ci.yml`'s `changes` job give CI's builds theirs, with the same script. That is the version a developer's checkout of `main` reports, and without it 11 lane-1 tests in `tests/e2e_remote_upgrade.rs` (`remote_upgrade_001` to `007`, `remote_connect_001` to `004`) fail in the sandbox and pass everywhere else (issue #2052). The task fails sandbox setup when origin has no such tag, rather than letting every build fall back to the placeholder. A sandbox keeps the value it started with, so a release tagged while it is running reaches it only after `rwx sandbox stop` or `rwx sandbox exec --reset`. To test a build whose version is unknown in the sandbox, unset the variable for that command: `rwx sandbox exec -- env -u DAD_VERSION <command>`.

### The build id, and why a no-change build stays fresh

Every `rwx sandbox exec` syncs the local tree in with a `git reset` to the local HEAD commit, a commit named `rwx-sync` and a `git reset HEAD~1`, so each exec rewrites `.git/HEAD`, the branch's ref file, `logs/HEAD` and the index even when nothing changed. `build.rs` watches those files with `cargo:rerun-if-changed`, which compares modification times, so until issue #2072 every exec rebuilt the root crate, the test harness and the desktop crate and relinked every test binary: on 2026-11-19 a no-change `cargo build --workspace --all-targets --features e2e,e2e-live` took 201 s, with cargo naming `.git/HEAD` as the cause. The sandbox now puts `scripts/rwx-sandbox-bin` ahead of the real `cargo` on PATH (the `cargo-build-id` task in `.rwx/sandbox.yml`). Its `cargo` composes `DAD_BUILD_ID` from the checkout's git content, `<DAD_VERSION>-g<short sha>[-dirty]`, with the two git commands `build.rs` uses, and then runs the real cargo. With both values injected, `build.rs` runs no git and watches no git file, and the git side of a rebuild comes from `cargo:rerun-if-env-changed=DAD_BUILD_ID`, which fires when the id moves: on a commit and on a dirty/clean flip. The same no-change build then took 1.2 s across five consecutive execs. The id is the one `build.rs` would have composed from the same checkout (the sync leaves the sandbox at the local commit with the local changes on top), so a sandbox build reports the local sha, and recordings made there keep it. The shim leaves the id to `build.rs` when `DAD_BUILD_ID` is already set, when `DAD_VERSION` is not a plain X.Y.Z (narrower than what `build.rs` accepts, which costs a prerelease version only the speed-up), and when the checkout cargo builds, the one `--manifest-path` names or else the working directory's, is not the sandbox's. `tests/sandbox_cargo_shim.rs` holds its value to `resolve_build_id`. A command that commits inside the sandbox and then builds in the same cargo invocation keeps the id the invocation started with. Bypassing the shim (an absolute path to cargo, as `cargo xver` uses) brings the git watches and the rebuild back for that command, and the first build after the shim appears rebuilds once because the injected id is new.

### The export chain

The composer probe's export path rule (`verify_export` in `src/composer_probe/path_rule.rs`) walks the export's path from `/` and refuses unless every directory on it, `/` included, is on ext2/3/4, XFS, Btrfs or tmpfs. An RWX task's `/` is overlayfs (`f_type` `0x794c7630`), so in a task as RWX starts it every export is refused, the deck never claims an input box empty, and every e2e test that needs an empty check takes the unsupported branch (`probe_026` and `probe_046` print which branch ran). That is the rule working, and it is not to be relaxed for CI.

So `.rwx/ci.yml`'s `e2e` task runs its tier under `scripts/rwx-export-root.sh`, which builds a root the rule accepts for that one command. It makes a directory on the task's XFS mount (the parent of `$RWX_ARTIFACTS`, `/opt/rwx/task-data/<task id>`, which RWX backs with the same disk as the task's overlay), and in a private mount namespace builds a new root there: `/` and `/var` are plain directories (root's, 0755), `/tmp` and `/var/tmp` empty ones (root's, 1777), and every other entry of `/` and `/var` stays the task's own, bind-mounted or re-created as the same symlink. It then chroots into that root as the calling user, with that user's groups, working directory and environment variables (those bash can export by name; an exported function is not carried) and no capabilities. The environment never touches the disk: the script reads it as root from `/proc/<pid>/environ` of the `sudo` it execs into and hands the command an open descriptor to it. A variable that points into the task's own `/tmp` or `/var/tmp` (`TMPDIR`, `SSH_AUTH_SOCK`) now points into the new, empty directories, so whatever it named there is not visible. When the command exits, or the script gets `TERM`, `HUP` or `INT` (which it forwards to the command, then waits for the command to exit), it unmounts the binds and deletes only what it made: the contents of the new `/tmp` and `/var/tmp`, the entries it created, and the directory. It removes nothing at all unless the mount table shows nothing still mounted under the root; when a mount will not detach, or the table cannot be read, it leaves the directory and prints `rwx-export-root: left <dir> in place: ...`. The harness's default temp base, `/var/tmp/dad-e2e-<uid>`, and each fixture's `TMPDIR` under it, then sit on a chain the rule accepts. The script needs `sudo` with `CAP_SYS_ADMIN` and `CAP_SYS_CHROOT`, which an RWX task's has, and refuses to run unless `RWX=true`. `ci.yml` does not use it: a GitHub runner's root is ext4.

To run e2e tests the same way in the sandbox: `rwx sandbox exec -- scripts/rwx-export-root.sh cargo test-e2e <filter>`, or the script in front of any other command that runs `tests/e2e_*.rs` tests, such as `cargo nextest run --workspace --features e2e --test <file>`. Without it the sandbox fails them where CI passes them: on 2026-11-16 a bare `rwx sandbox exec -- cargo nextest run --workspace --features e2e --test e2e_probe_delivery` failed 21 of the file's 36 tests, on `main` as on a branch, each with the probe reading the input box as unreadable and the notice never typed. CLAUDE.md rule 5, the coder and tester role templates and the gates `/issue-queue` and `/prd-queue` give a unit say so too, because the dispatched unit that hit this had been told only `rwx sandbox exec -- <command>` and reported the failures as a gap in the sandbox.

A green run under the script does not show that the tests took the supported branch: lane 1 passes on the unsupported one too. The check is the lines `probe_026` and `probe_046` print, which read `export-chain branch: supported / Empty ...` on the supported branch.

What is different inside the chroot, and what can be left behind:

- `/proc/mounts` and `/proc/self/mountinfo` list the new root and every bind under it as mounts of their own, nested under the `dad-export-root.*` directory's path on the task-data mount. A test that reads the mount table sees those entries, not the task's original table.
- `target/` stays on the task's overlay while the harness's temp base is on the task-data mount, so a test process cannot hard-link the deck under test into its root. The harness copies the build once into `/var/tmp/dad-e2e-<uid>/dad-deck-under-test/` and links each process's deck from there ([`e2e-temp-dirs.md`](e2e-temp-dirs.md#the-shared-copy-of-the-deck-under-test)). Before issue #2343 every test process wrote its own 192 MB copy. The writeback that caused stalled the fixture daemons' `fsync` calls, and a whole-file run of `tests/e2e_probe_delivery.rs` in the 16-CPU sandbox lost 7 to 11 of its 36 tests to `start-agent` timeouts with a `STARVED` verdict from `io full`.
- A `SIGKILL` of the script, or the task or sandbox dying under it, skips the cleanup and leaves `/opt/rwx/task-data/<task id>/dad-export-root.*` behind, with whatever the run wrote to its `/tmp` and `/var/tmp` (several GB for a full shard). So does the `left <dir> in place` warning. `cargo xtask clean-e2e-tmp` does not look there, since it scans `/var/tmp/dad-e2e-<uid>` and the system temp dir. In a CI task the directory goes with the task; in the sandbox it stays until the sandbox stops. To remove one by hand, first confirm nothing is mounted under it (`findmnt -R <dir>` prints nothing, which holds once the script's processes are gone, since the binds lived in their own mount namespace), then `sudo rm -r --one-file-system -- <dir>`.

Routes that were measured and do not work (2026-11-03): pointing `TMPDIR` or `DAD_E2E_TMPDIR` anywhere, since `/` itself is refused; an unprivileged user namespace (`unshare --user` is denied); an ext4 image, since the task has no loop devices; and a tmpfs root, the script's first version (RWX run `01a1a2c522be782eb2580f0d1d1e6f3b`): one shard leaves about 37 test roots of about 150 MB each under `/var/tmp`, which filled an 8 GB tmpfs until the harness's free-space check refused the rest of the shard, and `cargo xver`'s scratch check refuses a RAM-backed `/` (CLAUDE.md rule 14).

What it relies on: the task-data mount is RWX's, undocumented, and also holds `RWX_ARTIFACTS` and RWX's other control directories, beside which the script adds its own. If RWX moves it or takes it off a disk-backed filesystem, the script stops with the filesystem it found rather than running the tier on the unsupported branch; `DAD_EXPORT_ROOT_BASE` names another directory.
