# The cross-version harness — running rule 12 as a command

CLAUDE.md rule 12 requires, for any change touching the daemon, the TUI↔daemon protocol, orchestration or hooks, a **cross-version manual test**: build the branch, start a daemon from the previous release with an agent under it, run the branch TUI against that older daemon, and confirm a delegate still routes and hooks still arrive. `cargo xver` does that, scripted.

**Trust boundary — read this before running it on code you have not reviewed.** `cargo xver` builds the branch in a bubblewrap **build namespace** — no network, your home, `/tmp`, `/var/tmp` and `/run` masked, the build clone read-only, an allowlisted environment, private PID and user namespaces ([The build namespace](#the-build-namespace)) — and runs its daemon/TUI/CLI scenario in a second private namespace. It is still **not** an untrusted-code sandbox. The binary the branch builds runs in the runtime namespace, which masks `/run/user/<uid>` but not the rest of `/run`, so a branch binary can connect to the host's pathname sockets there — on the box this was written on, the Docker socket (which a member of the `docker` group can use as root) and the system D-Bus, both measured connectable from a namespace of the runtime's shape — and to any other socket outside the runtime masks. Both namespaces can read the rest of `/` that your uid can. And the input acquisition runs on the host, as you: `git` and `gh` with your environment, and the crate download (`cargo fetch`) with an environment of its own ([What runs on the host](#what-runs-on-the-host)).

On top of that sits a **build-time gate**: before anything is built it compares the branch with its merge-base with `main` and refuses a branch that changes build-time code — a `build.rs`, a `Cargo.toml`, `Cargo.lock`, anything under `.cargo/`, a toolchain file, or a file those pull in at the merge-base, such as a module of `build.rs` or the linker script `.cargo/config.toml` names — naming the files, unless you pass `--allow-build-changes` after reviewing them ([The build-time gate](#the-build-time-gate)). An opted-in branch then builds into a target dir of its own, so nothing its build writes reaches a later build of another branch. The gate detects a branch *supplying* build-time code; the build namespace is what contains the build, and the merge-base's own build-time code runs in it on every build. **Run unreviewed or external code — a stranger's pull request, a fork's branch — only in a disposable VM or as a dedicated user that holds no credentials.** `cargo xver --help` prints the same warning.

```sh
cargo xver --branch agent/dispatch-issue-1121
```

`cargo xver -- --branch …` is accepted too. The alias already ends in `--`, so that spelling used to reach clap as a positional argument and fail; the binary now drops one leading `--`.

That is the **forward** direction, and it is the default. `--direction reverse` runs the opposite pairing — the branch daemon with the previous release's TUI and CLI — and `--direction both` runs one after the other, each in its own sandbox with its own evidence file. [The reverse direction](#the-reverse-direction) says why rule 12's pairing alone leaves a gap and what reverse does and does not close.

## Why this exists

Rule 12's procedure is written in keystrokes because a person was always going to run it, and four of its paragraphs are about ways a person silently gets it wrong. That had a consequence nobody intended: a dispatched agent reading rule 12 concludes it cannot type into two full-screen TUIs, declines the check, and leaves the review thread open. Eight green, mergeable pull requests were blocked on exactly that one thread at the time this was written.

**Rule 12's requirement is the scenario, not human fingers.** A driver that reproduces the same scenario and asserts the same tells discharges the same obligation — and unlike a person's recollection, it leaves a file a reviewer can read afterwards.

## What a run does

A run has two halves. The **outer** half is the command you type, and it and every process it starts directly run on the host: `git`, `gh`, `rustc --print sysroot`, `cargo fetch`, `sha256sum`, `tar`, `date` and `bwrap` itself ([What runs on the host](#what-runs-on-the-host) says what environment each gets). The two Cargo commands that read the branch's or the merge-base's tree — the gate's `cargo metadata --no-deps` and `cargo build` — the outer half starts through `bwrap`, each in a [build namespace](#the-build-namespace) of its own. The **inner** half is the same binary, started by the outer half inside one private [bubblewrap](https://github.com/containers/bubblewrap) namespace. The daemon, both TUIs and every deck CLI call are started by the inner half, inside that namespace. The outer half executes no deck binary: it compares the downloaded previous release with the release's published `checksums.txt`, and the old binary's first execution anywhere in the run is its `--version`, inside the namespace.

1. **Outer, preflight.** Refuses a tmpfs or short-of-space runs root, target dir or fetch-phase Cargo home (`--min-free-gib`, default 100), proves an unprivileged `bwrap --unshare-all --disable-userns` namespace starts on this host, snapshots the current resolver's standard current-uid endpoint candidates — the XDG pair under `/run/user/<uid>`, the flat `/tmp` pair and the per-uid `/tmp/dot-agent-deck-<uid>/` pair — (file identity, listening socket inodes, and the owning pid and start time of each listener; not a path an explicit `DOT_AGENT_DECK_SOCKET` override names, another uid's runtime directory, or a path a branch introduces), censuses the host's deck processes — by executable name, as far as this uid can read them — by pid, start time and exe, and marks how far the operator's real deck log reached. In `resolved` mode it also requires the host's flat endpoints and per-uid endpoint sockets absent.
2. **Outer, inputs.** Settles which release is the previous one — `--previous` as given, or else resolved from `gh release list` (see [Which release is "previous"](#which-release-is-previous)) — then downloads its `dot-agent-deck-linux-amd64` with `gh release download` into `../dot-agent-deck-xver-releases/<tag>/` (once; later runs reuse it), downloads that release's `checksums.txt` again on every run, and refuses unless the binary's SHA-256 is exactly the one `checksums.txt` publishes for that asset. Nothing executes the binary here. Fetches `main` and the branch into a **standalone build clone** at `../dot-agent-deck-xver-src`, refusing an existing clone this version of the harness did not create (see [The build clone](#the-build-clone)), and checks the branch out detached at its `FETCH_HEAD`. Resolves the Rust toolchain. Runs the [build-time gate](#the-build-time-gate) against their merge-base, its `cargo metadata` in a build namespace — refusing, before anything is compiled, a branch that changes build-time code without `--allow-build-changes`. Picks the trust domain from the gate's answer: the shared `CARGO_TARGET_DIR` at `../dot-agent-deck-xver-target` for a branch whose build-time code is the merge-base's, `../dot-agent-deck-xver-target-opted-in-<branch slug>-<digest>` for an opted-in one. Downloads the branch's crates on the host with `cargo fetch --locked` into the harness's own Cargo home at `../dot-agent-deck-xver-cargo`, and only then builds the branch offline in a build namespace (see [The build namespace](#the-build-namespace)).
3. **Outer, sandbox.** Creates a fresh, owner-only (`0700`) sandbox `$S` under `../dot-agent-deck-xver-runs/<branch slug>-<epoch>/`, refusing to reuse any existing entry. Writes the three-role fixture into `$S/project/.dot-agent-deck.toml` and makes `$S/project` a standalone `git init` repository. Hard-links (or copies, across filesystems) the old binary, the branch binary and the harness itself into `$S`, so every deck binary the namespace runs, and the harness itself, has a path under `$S`.
4. **Outer, namespace.** Starts `bwrap` with the harness inside it and answers the inner half over its stdio (see [The pre-connect assertion](#the-pre-connect-assertion)).
5. **Inner, proof.** Reports its mount, PID and network namespaces to the outer half, which refuses any it shares; proves each mask by `dev:ino` and the operator's home empty; requires its own environment to be exactly the plan's allowlisted entries and the fixture to be what stops the deck's project-config walk; and records every residual `rw` submount the read-only root did not remount, as exposure. Runs the old binary's `--version` and, for a downloaded release, requires it to print exactly `dot-agent-deck <version>` (for `--old-binary` it is recorded, not enforced). Runs both builds' `daemon hello` and refuses a same-build-id pairing before any daemon starts.
6. **Inner, scenario.** (Forward; [reverse](#the-reverse-direction) swaps which build plays each part and changes nothing else.) Starts the **old** daemon and records its full identity; waits, by reading the kernel's socket table rather than by starting a client, until it listens where the endpoint matrix says it must; attaches the **old** TUI over a PTY and opens the orchestration through the production `Ctrl+N` flow, sending each key only once the screen shows the state that key is meant for (the picker's footer, the form, the orchestration chip hiding the Command field, `Enter: submit`) rather than after a fixed pause; confirms through `daemon status --json` that all three roles are live; closes that TUI with `Ctrl+D`, `Ctrl+C`, **Detach** and re-checks; attaches the **branch** TUI, records the build-version mismatch prompt and **declines** it with `n`; delegates from inside the orchestrator pane, then issues `work-done` and — last — `agent-event --type running` from inside a worker pane. The pre-connect assertion runs before every one of those clients.
7. **Inner, teardown.** Stops the branch TUI and then the daemon, each by verified identity (see [Teardown](#teardown-is-by-verified-identity)), then censuses the PID namespace for survivors.
8. **Outer, postconditions.** After the namespace has exited: requires no process left in the run's PID namespace and none referring to `$S`, the host's standard endpoint candidates unchanged since baseline, no host listener under `$S`, and no line mentioning `$S` among the bytes appended to the operator's real deck log; reports which baseline deck processes are still the same process.
9. Writes a markdown evidence file to `.dot-agent-deck/xver-evidence/<branch slug>.md` — `<branch slug>-reverse.md` for a reverse run, so the two directions of one branch never overwrite each other — or exactly to the path `--evidence` names, in either direction (the pair `--evidence` and `--direction both` is refused, since one path cannot name two files), and removes `$S` only after a clean pass with all postconditions met.

## The four tells

A run asserts these and prints each one with the value it was decided on, because the evidence file is what resolves a review thread and a reader who did not watch the run has to be able to check it.

| tell | what it rules out |
| --- | --- |
| exactly one `Attach protocol listening` line in the sandbox log | two means the branch TUI lazy-spawned its own daemon — the tell for *both* the no-agents cause and the 30-second idle-window cause, whichever swallowed the run |
| the same daemon process — its pid, and `/proc/<pid>/exe` still the old binary — at the start and at the end; plus `ss -xlp` naming that pid as the endpoint's owner at both ends | the daemon was replaced partway |
| a delegate still routed | the payload really landed in the target pane |
| hooks (work-done, status) still arrived | the daemon's feedback really reached the orchestrator's pane, and the status change really reached its own state |

Tell 2's `ss -xlp` runs inside the namespace, so the pids it names are the run's private PID namespace's; the evidence also records the kernel table's own answer (listening inode and holders) at both ends. Tell 2 does **not** re-read a build id at the end, and its title says so: the build id rests on two earlier observations — the executable it checks is the staged binary whose `daemon hello` build id the preflight recorded, and the mismatch prompt reported the running daemon's build id over the wire. A tell the harness could not measure is reported as **not checked** and the run is **INCOMPLETE**, not a pass. The table is written for forward; in reverse the same four tells pin the **branch** daemon and binary, and [The reverse direction](#the-reverse-direction) says what a second `Attach protocol listening` line means there.

## Why no tell passes vacuously

**What has been demonstrated by a run is narrower than the heading.** Pointing `--old-binary` at the branch build makes both sides report one build id, and the run is refused before any daemon starts. That shows the preflight's same-build-id refusal (`compare_hellos`) is not vacuous: a same-version pairing cannot be dressed up as a cross-version run. Because that refusal fires upstream of all four tells, no tell runs in it, so it demonstrates nothing about the tells themselves. Their non-vacuity rests on the reasoning below, traced through the code by review rather than demonstrated by a run.

- **Tell 1.** It counts lines in the sandbox's `deck.log`. Every deck process of the runtime scenario is started with `DOT_AGENT_DECK_LOG` pinned to that file, and a daemon a client lazy-spawns inherits that client's environment, so a second daemon writes its own line there. A log that cannot be read counts as zero lines, and zero fails exactly as two does: only one passes. It is counted after every other step.
- **Tell 2.** The attach endpoint's listeners are captured before the second TUI exists and again at the end, and the tell passes only when the two sets are equal **and** contain the recorded daemon pid — two empty sets are equal but contain no pid, so they fail — with that pid still alive and `/proc/<pid>/exe` the daemon's binary (the old one forward, the branch's in reverse). The daemon is the harness's own child and has not been reaped while it is alive, so its pid names that process and no other. `ss` being unavailable makes the tell **not checked**, which makes the run INCOMPLETE.
- **Tell 3.** It is asserted on the target `coder` pane's screen after focusing that pane. The stacked layout draws only the focused pane, and `coder` is `cat`, which shows only what the daemon wrote into its PTY, so the sentinel echoed by the orchestrator's own shell cannot satisfy it. The task file the daemon writes is read for an informational note and does not decide the verdict.
- **Tell 4.** `work-done` is asserted by the daemon-authored feedback line appearing in the orchestrator's pane, a different pane from the one that issued the command, so the issuing shell's echo cannot satisfy it. The status half is asserted by `daemon status --json` reporting the worker pane non-empty and not `Idle`, which is the daemon's own state. Both halves must hold, and a status wait that times out is a FAIL.
- **`role-set`** (reverse `generic` runs). It is read after tells 1 and 2, behind a pre-connect assertion that re-proves every path-bound listening socket in the namespace is the daemon's. Its presence clauses need positive evidence: each role listed exactly once and on the pane recorded after the detach — so a role missing, doubled or moved fails it — and each listed pane backed by a live process under the daemon in a `/proc` census. Its two absence clauses (no pane process outside the daemon's tree, no other `daemon serve` process) are read from that same census, which must contain the daemon itself, so an empty or foreign census cannot satisfy them. The one `daemon serve` process the second clause exempts is a per-pane **lifetime-cap reaper** — `arm_child_group_backstop` in `src/wrap.rs` forks one per pane whenever the daemon's environment names a cap, which the harness sets from `--max-agent-lifetime-secs` (1800 by default) — and it is recognised by what it is, not by where it sits: the intermediate that forks it exits immediately afterwards, so the reaper is reparented to init and is outside the daemon's tree when the census runs (the #1179 control's first run reported its three reapers as three second daemons for exactly that reason). A process is exempted only when every one of these is read from `/proc` and holds: it holds **no socket** of any kind, listening or connected; **no process descends from it**, so none carrying a pane id does, and every process's parent was readable; and it has a reaper's **identity** — the daemon's exe, exact command line and whole initial environment (a fork keeps all three), a positive `DOT_AGENT_DECK_TEST_MAX_LIFETIME_SECS` in that environment, an **empty** descriptor table (the reaper closes every one it inherited, 0/1/2 included, which no exec'd deck process runs without), and process group equal to session but not to its own pid (both name the intermediate that `setsid`'d). Its parent pid is recorded but decides nothing, and `DOT_AGENT_DECK_TEST_LIFETIME_TAG` is not used, because the reaper carries that only in memory. A `daemon serve` process that fails any one of those is a problem, whatever its command line — so #1179's shape still fails the tell twice over: its duplicated roles' pane processes are outside the daemon's tree, and the second daemon holds sockets and is those processes' ancestor, either of which alone fails the exemption whatever its identity. Its timing rests on the old TUI's startup order rather than on a pause: v0.41.0 makes its restore decision before its first frame, and by then the TUI has drawn the orchestration and been driven through tells 3 and 4. A listing or census that cannot be read is **not checked**.
- **The aggregation.** An isolation failure makes the run INCOMPLETE whatever the tells say; otherwise any failing tell makes it FAIL, and no tells, an unmeasured one, or an expected one that was never recorded make it INCOMPLETE; only then is it a PASS. "Expected" is the complete set for the run's direction and probe, required by id rather than inferred from the tells present: the four tells; in reverse also `role-set` for `generic` and the probe's own tell for every probe with a stimulus; and, on the cannot-discover path, the three collateral tells instead of all of those. So a scenario that stops recording early cannot aggregate to a PASS on whatever it did record. The command exits zero only for a PASS whose outer half completed and whose postconditions all held, and a postcondition that could not run counts as one that failed. `report.rs` and `outer.rs` unit-test that chain.

## The five false greens, and where each one is handled

Rule 12 documents four ways this procedure silently measures nothing; PR #1179 added a fifth. A false green here is worse than not running the check at all, because it clears a gate with nothing behind it.

1. **No agents under the old daemon.** With zero agents the branch TUI takes `MismatchAction::SilentRestart` — it SIGTERMs the old daemon and lazy-spawns its own, with no prompt and no output. The scenario's orchestration step is what avoids it, and the missing mismatch prompt is what catches it: the harness treats "no prompt" as a hard failure of the run rather than as a pass, because the prompt appearing *is* the proof the scenario was reached.
2. **The 30-second idle window.** `DEFAULT_IDLE_SHUTDOWN_SECS` is 30, so more than 30 s between `daemon serve` and the first attach and the daemon exits and gets replaced. Every process of the runtime scenario — the inner half, the daemon, both TUIs, the panes and every deck client — carries `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0`, which is the documented "always on" production value rather than a test hook.
3. **`Ctrl+C` in `PaneInput` mode goes to the pane.** With a role pane focused it kills that role's process and the orchestration comes back one role short. The harness sends `Ctrl+D` first, presses Enter only once the quit dialog shows `> Detach` selected (never `Stop`), and then re-asserts the three-role list — this one fails loudly rather than silently, and the re-assert is what makes it loud here.
4. **Teardown by an unscoped `pkill`.** See [Teardown](#teardown-is-by-verified-identity) below.
5. **`XDG_RUNTIME_DIR` being set, for a change that moves the endpoint path in the fallback case only.** On a normal desktop session it is set, both builds resolve byte-identical endpoints, and the run exercises the arm such a change did not touch. `--unset-xdg-runtime-dir` is the lever, and it is an option rather than a hardcode because for every other kind of change the ordinary desktop configuration is the faithful one.

## The reverse direction

### The gap in rule 12's pairing

Rule 12 prescribes exactly one pairing: a **previous-release daemon** with the **branch TUI**. That proves the branch client can drive an old daemon, which is a real property and the one the rule asks for. But most of what rule 12's trigger list names — daemon, orchestration, hooks — is code that runs **in the daemon**, and in the forward pairing the daemon is the previous release. For a daemon-side change the forward run therefore executes **none of the changed lines**: it passes against the old daemon's code and says nothing about the new. This is a gap in the rule as written, not in any one run.

`--direction reverse` is the pairing that does execute them: the **branch daemon**, with the orchestration stood up under it by the branch's own TUI, then the **previous release's TUI** started against it. When that TUI finds the branch daemon, its mismatch prompt is declined and the **previous release's CLI** issues every pane command, and the changed daemon code runs against the old client's traffic. When it does not find the daemon, none of that happens: the run measures what the old TUI reached instead, and its verdict says only that (see [the cannot-discover outcome](#what-is-genuinely-different-in-reverse) below). It models a downgrade, or a stale binary left on disk beside a newer daemon. Everything else about a run is unchanged: the same namespace, environment allowlist, pre-connect assertion before every client, teardown by verified identity and postconditions, in both directions.

For the eight branches this was first run on, the direction that executes the changed code was established from their diffs:

| PR | issue | changed code runs in | direction that executes it |
| --- | --- | --- | --- |
| #1161 | #1109 | the daemon's teardown paths | reverse |
| #1168 | #1031 | the daemon's delegate delivery | reverse |
| #1169 | #1082 | the daemon's logging, after decode | reverse |
| #1179 | #1121 | the client's resolver, and the daemon's bind | both |
| #1183 | #1182 | the hook CLI's normaliser, and the daemon's matcher | both |
| #1187 | #925 | the daemon's `AppState::apply_event` | reverse |
| #1188 | #1129 | the CLI's acknowledgement wait, and the daemon's acknowledgement write | both |
| #1190 | #1181 | git children the daemon spawns | reverse |

Reverse does not replace forward. Rule 12 asks for the forward run for every one of them; reverse is the additional run that reaches the daemon half.

### What is genuinely different in reverse

- **The prompt and its decline key are the OLD build's.** Both are established from that build rather than assumed: `src/build_version_handshake.rs` is byte-identical between v0.41.0 and every branch this was written against, the published v0.41.0 binary carries the prompt's strings, and in both builds `s`/`S` without Ctrl is the only affirmative key and every other key declines. The run sends `n`, records the prompt exactly as the old TUI printed it, and tells 1 and 2 then prove the old TUI stayed on the same daemon rather than restarting it.
- **The old client may not find the branch daemon at all.** That is a measured outcome with its own verdict, `OLD CLIENT CANNOT DISCOVER THE BRANCH DAEMON`, distinct from `FAIL` (the two builds reached each other and did not interoperate) and from `INCOMPLETE` (the harness could not tell). It needs positive evidence: a listener the run did not start, held by a process whose full identity is the old build running `daemon serve` with the run's marker — the daemon the old client lazy-spawned. The run records that second daemon by identity, lets the pre-connect assertion account for its listeners at exactly the paths it bound, and then asserts three collateral tells: the branch daemon is untouched, it still runs every role, and the old client's own daemon runs **none** of those roles. A collateral failure makes the run `FAIL`, because it means the fallback damaged something beyond not finding the daemon; an unmeasured one makes it `INCOMPLETE`. The third tell needs positive evidence before an empty listing counts: the old TUI makes its session-restore decision at startup, before its event loop draws a frame (v0.41.0's `run_tui` restores before its first `terminal.draw`), so an empty listing counts only once that TUI has drawn its main UI — the stats bar every layout draws — and is `not checked` before. What the verdict establishes is that narrow: the old client, started with the run's environment, did not reach the branch daemon, started one of its own, and the three collateral tells held. None of the four tells and no probe stimulus runs on this path, so it says nothing about how the branch daemon handles an old client's traffic, and the evidence file says so under its intro. Inside the namespace an old client that lazy-spawns does so into the private `/tmp`, so this is measurable without binding the current resolver's standard host endpoint paths. That is a statement about where the resolver puts that daemon's sockets, not about host risk in general (see the trust boundary at the top of this page). The second daemon is stopped by verified identity before the branch daemon, through `proc::terminate_identity` — it is not the harness's child, so there is no un-reaped handle, and the start-time field and the private PID namespace stand in for one, except across the verify-then-`kill(2)` window [Teardown](#teardown-is-by-verified-identity) describes.
- **Tell 2 pins to the branch daemon.** Same pid, and `/proc/<pid>/exe` the staged **branch** binary, at both ends.
- **Tell 1 still means "one daemon".** Exactly one `Attach protocol listening` line is the branch daemon's. Two in reverse mean a daemon of another build started: the old client lazy-spawned its own (it did not find the branch daemon), or an idle window swallowed the branch daemon and a client replaced it. In the cannot-discover outcome the count is recorded as part of the discovery evidence, where two is the expected consequence rather than a tell.
- **The endpoint matrix is learned, not predicted, in one configuration.** With `--endpoint-mode resolved --unset-xdg-runtime-dir` the daemon is a branch build, and whether it binds the flat fallback (every build before #1121) or the per-uid directory (#1121) is that branch's own behaviour. Both are candidates; the run waits until the daemon holds one pair and from then on requires every other candidate absent before every client — the same strength as a predicted matrix. The evidence says which pair it was, and, when the old TUI printed its prompt and tells 1 and 2 passed, records that it reached the branch daemon through its own resolution of that fallback. Every other mode has one candidate. Two probes run in this configuration: `discovery-fallback`, which refuses a daemon that bound the flat pair, and `generic`, which runs against either — the second is how [the #1179 negative control](#negative-controls) is run.
- **Teardown identity matters more, not less.** The daemon is a branch build whose command line looks even more like a production deck's. Every identity check is kept: start time, exe, exact cmdline, cwd, whole environment and mount namespace, re-read before its one SIGTERM and again before any SIGKILL.
- **`PATH` models the downgrade.** In reverse `$S/bin/dot-agent-deck` — first on `PATH` — is the previous release, and the branch build is staged at `$S/branch/dot-agent-deck`. Pane commands in reverse are typed with the old build's absolute path, so the evidence names exactly which binary sent each stimulus.

### Branch-specific probes

The four tells are rule 12's and reverse asserts them. They are not enough on their own, because a delegate and two hooks never reach, say, the line that escapes a hostile id in a log record. A reverse run therefore also carries a **probe**: the minimal stimulus that reaches the branch's changed arm, with an assertion on what the branch daemon then did. It is named with `--probe`, or selected by `--probe auto`, the default, from the branch's issue number — read only from a path component that is exactly `dispatch-issue-<n>`, as in `agent/dispatch-issue-1181`. Auto never falls back: a branch with no such component (`agent/dispatch-issue-1181-v2`, `agent/dispatch-issue-1109-1121`, `main`), with more than one, or naming an issue no probe was written for is refused before anything is built, and the refusal names any issue with a probe that the branch name mentions. `--probe generic` is how to ask for no stimulus on purpose: it adds one tell, `role-set`. The run prints the probe and how it was chosen, and the evidence file's probe row says the same. Probes run only in reverse, and an explicit probe with `--direction forward` is refused rather than dropped. `generic` runs in every endpoint mode; `discovery-fallback` needs `resolved` with `--unset-xdg-runtime-dir`; every other probe needs `sandbox-sockets`, the mode it was written against.

Every stimulus is issued by the previous release's CLI from **inside** a pane the branch daemon spawned, so it carries that pane's genuine identity and capability rather than one the harness copied, and each is preceded by the pre-connect assertion. No probe needs an agent credential: where a real agent's producer behaviour matters, the exact payload is injected through `dot-agent-deck hook` on stdin, or produced by a synthetic stand-in.

| probe | branch | stimulus | pass requires |
| --- | --- | --- | --- |
| `generic` | any; the [#1179 negative control](#negative-controls) | none beyond the four tells | the four tells, plus `role-set`, read after tells 1 and 2: the daemon lists each role exactly once, on the pane it had after the detach; each listed pane has a live process under the daemon; no process carrying a pane id is outside the daemon's tree; and no `daemon serve` process runs besides the daemon and its lifetime-cap reapers, each recognised from `/proc` by what it is (see the `role-set` tell above). It exists because tell 1 catches a second daemon but not a role set the old TUI's session restore spawned into the existing one. On the cannot-discover path it is not measured; the collateral tells are |
| `teardown-inventory` | #1161 | old-TUI `Stop` (`Ctrl+D`, `Ctrl+C`, `Down`, `Enter`, `y`), sending `KIND_SHUTDOWN`; only after the pre-connect assertion re-proves the daemon, and after tells 1 and 2 because it ends the daemon | exactly one `shutdown-frame` inventory record naming the agent and role counts and every captured pane, role and agent, and no `signal` record, before the daemon's exit |

### Negative controls

A probe is evidence of a fix only if it would fail without it. `teardown-inventory`, `late-session-start` and `paste-envelope` assert on a log record only the fixed build writes, and `log-escaping` on the escaped form of one. `cross-pane-session-key` and `git-env` assert on state a pre-fix daemon also produces, so they were run once against `main`, which carries neither fix, with `--branch main --direction reverse --probe <name>`: both FAILED there, `main`'s daemon losing alpha's status and cutting the dispatch's worktree from the decoy. Re-run that control after changing either probe — `cross-pane-session-key`'s second half now waits for the `SessionEnd` to be applied, which changes what its control measures. `signal-ack` has no control that could discriminate, by design (see [What reverse covers](#what-reverse-covers-and-what-it-does-not)).

**The #1179 control is the other direction of that question: not "does the probe fail without the fix" but "does the failure disappear without the change".** #1179's reverse run took the cannot-discover path and FAILED collateral 3: the v0.41.0 TUI did not find the branch daemon in the per-uid directory, lazy-spawned its own, restored the saved session there and re-created the whole orchestration under a second daemon. Attributing that to #1121 needs the same run against `main`, which binds the flat pair, to show the old TUI finding the daemon and not duplicating anything. `discovery-fallback` cannot be that run — it refuses a daemon that bound the flat pair, correctly, since that is not the arm it was written for — and `generic` is:

```sh
cargo xver --branch main --direction reverse --probe generic --endpoint-mode resolved --unset-xdg-runtime-dir
```

Add a lane's `--source-clone` and `--target-dir` when other runs share the box. The run learns which pair `main`'s daemon bound — the evidence's Isolation section names it, "the pre-#1121 flat fallback" if the attribution holds — and holds every other candidate, the per-uid and XDG pairs, absent before every client: the mirror image of the #1179 run, which held the flat and XDG pairs absent. Its verdict reads:

- **PASS** — the old TUI printed its mismatch prompt, which it can do only against a daemon it found; the prompt was declined; the four tells passed with tell 2 pinned to `main`'s daemon; and `role-set` passed: one set of the three roles, on the panes the setup TUI brought up, under the one daemon. Beside #1179's FAIL, that is the measured attribution: the same old client in the same configuration finds a pre-#1121 daemon and duplicates nothing.
- **FAIL on `role-set`** with tell 1 passing — the old TUI found the daemon, but the role set did not survive it intact: duplicated into the one daemon, replaced on new panes, or running outside it, which the tell's detail says. The old TUI's session restore then damages an orchestration without #1121's layout, and #1179's finding cannot be attributed to #1121 alone.
- **OLD CLIENT CANNOT DISCOVER THE BRANCH DAEMON**, or a FAIL on a collateral tell — `main` reproduces the non-discovery, which falsifies the attribution.
- **INCOMPLETE** — nothing was measured either way; the evidence says what was not, and the run should be repeated.

With `--branch agent/dispatch-issue-1121` the same command runs the code `discovery-fallback` runs there — the same fixture, the same two candidate matrices and the same classification of a missing prompt; on that path the two runs differ only in the probe the evidence names — so the control and the finding differ in the branch alone.

Three probes change the run's inputs, each narrowly, and the evidence file names each change. `late-session-start` adds `RUST_LOG=dot_agent_deck=debug` and the three delegate timer knobs set to `0`; `git-env` adds the eight location variables. Those are admitted by `sandbox::check_env` by exact name **and** value, never as a base allowlist entry, never with a credential-shaped name, and never replacing a base entry. That check does not prove a path-valued extra stays under `$S`; `git-env`'s values do because the probe builds every one of them from the sandbox's decoy path, and a future path-valued extra has to be confined the same way where it is defined (`Probe::extra_env` says so). The dispatch probes (`paste-envelope`, `signal-ack`, `git-env`) create `$S/config/config.toml` holding one key, `default_command` — what `dispatch --single` runs — and commit the fixture so a worktree has a `HEAD` to branch from. `git-env` also creates the decoy, a second standalone repository under `$S`, with an empty environment before any hostile variable exists.

### What reverse covers, and what it does not

When the old client finds the branch daemon, a reverse run covers the branch daemon's handling of **the stimuli it sends**: the same rule-12 flows, and each probe's one stimulus, from a v0.41.0 client, with the assertions above. Stated narrowly:

- **A cannot-discover verdict covers no stimulus at all.** On that path nothing the old client sends reaches the branch daemon. The verdict establishes that the old client, started with the run's environment, did not reach the branch daemon; which daemon it started instead, by full identity, and where that daemon listens; and the three collateral tells. It does not establish how the branch daemon would handle that client's traffic, and it says nothing about a client started with a different environment — one with `XDG_RUNTIME_DIR` set, or a socket override, resolves another arm.

- **Each probe covers one stimulus, not the changed surface.** `log-escaping` sends one control character in one field; `cross-pane-session-key` one two-pane collision; `git-env` one dispatch under one coherent set of hostile variables; `late-session-start` one swallowed CR. The probe spec's per-branch residual-risk notes list what each leaves out.
- **Stand-ins model one producer behaviour each.** The synthetic `claude` reproduces #1031's swallowed CR and #1182's envelope exactly as those issues measured them. It says nothing about when a real Claude boots or which envelope id it picks; the branches' own lane-2 tests are where a real agent is measured.
- **One previous release.** A client older or newer than `--previous` is not exercised.
- **The desktop GUI's handshake** (`classify_handshake`) is not exercised in either direction.
- **The three dispatch probes use `dispatch --single`'s defaults** — a `default_command` from the global config, a worktree beside the project — and do not cover an orchestration dispatch.
- **`signal-ack` is a compatibility check, and does not discriminate the fix, by design.** An old fire-and-forget client never reads the acknowledgement, so a daemon that writes none passes it too; it asserts that the acknowledgement's write to a closed peer does not break the verbs or wedge the listener, which is the reverse half of #1129's compatibility argument, not proof the write happens (nothing logs it). Its tell is titled `compatibility: …` in the evidence file, and the probe row says the same, so the tell list carries the distinction without the detail having to be read.

## Runtime-scenario containment

**This section is about the runtime scenario** — the inner half and what it starts: the daemon, both TUIs, the panes and every deck client. It does not describe the branch build, which runs before this namespace exists, in a build namespace of its own ([The build namespace](#the-build-namespace)), or the input acquisition, which runs on the host ([What runs on the host](#what-runs-on-the-host)); the trust boundary at the top of this page is the summary. Every property below is a property of that scenario, and several are narrower still — a claim about clients that follow the current endpoint resolver with the run's admitted environment, rather than about any code the branch could contain.

The first version of this harness isolated a run with environment variables alone, and in `resolved` mode that bound **real host addresses**: a run's published-v0.41.0 daemon, with `TMPDIR` pointing inside its sandbox, owned the host's `/tmp/dot-agent-deck-1000.sock` and `/tmp/dot-agent-deck-attach-1000.sock`, so for the length of that run any production client resolving the flat fallback would have reached a sandbox daemon. `TMPDIR` moves only a post-#1121 build's new primary fallback; the branch's compatibility root and every published build before it spell a literal `/tmp`. An independent safety audit then found the environment incomplete in every mode, the pre-connect check unable to tell who owned a socket, and a cmdline substring standing in for teardown identity. What follows is what replaced each of those, stated as narrowly as it was measured.

### The namespace

The daemon, both TUIs and every deck CLI call of a run execute inside one `bwrap` namespace, started with `--unshare-all --unshare-user --disable-userns --die-with-parent --new-session`, in which:

- `/tmp` is `$S/fallback-tmp` and `/run/user/<uid>` is `$S/run-user`. **Both** endpoint roots are masked because masking `/tmp` alone is not enough: under a read-only view of `/`, the production XDG sockets stay connectable — a read-only mount does not stop `connect(2)` on a Unix socket.
- `/var/tmp` is `$S/var-tmp`. No rule of the current resolver names `/var/tmp` (a branch could add one); other sandboxes park sockets there, and this keeps them out of reach as defence in depth.
- The operator's home — the password database's home directory, when that is a directory other than `/` — is an empty tmpfs, with only the path down to `$S` bound back into it when the runs root is under it, as it is by default. So `~/.local/bin` (where the production deck lives on the box this was written on), `~/.config/dot-agent-deck`, `~/.dot-agent-deck.toml` and every neighbouring sandbox under the home are not visible inside. On a host whose password-database home is `/` or not a directory nothing is masked there, and the evidence file's Isolation section says **no home was masked**.
- The rest of `/` is bound read-only. **Not every submount honours that, and the ones that do not are exposure.** Measured on the box this was written on, the submounts bwrap cannot remount stay `rw` — Docker's per-container `nsfs` and overlay mounts under `/run/docker/netns` and `/var/lib/docker/rootfs`, and `/proc/sys/fs/binfmt_misc`. They are root-owned, but ownership of a mount point does not prove the run's uid cannot write beneath it — mode bits, ACLs, group membership and FUSE all decide that — so the harness does not claim they are unwritable. It does not mask them either: on every run the inner half lists each `rw` mount that is not one of the run's own (`$S`, the masks, the home tmpfs, `/proc`, `/dev`) in the evidence file's Isolation section, as exposure rather than as a failure.
- The PID, network, IPC, UTS and user namespaces are private, and creating a nested user namespace is disabled.

Inside it a run resolves endpoints the way a real host does: with `XDG_RUNTIME_DIR` unset and `TMPDIR=/tmp`, a v0.41.0 daemon binds `/tmp/dot-agent-deck[-attach]-<uid>.sock` and a post-#1121 build looks first in `/tmp/dot-agent-deck-<uid>/` and then at those legacy paths — the same spelling as on the host, landing in `$S/fallback-tmp`. With `XDG_RUNTIME_DIR` kept, it is pinned to the host's spelling `/run/user/<uid>`, which inside is `$S/run-user`.

### The environment

Every process of the runtime scenario gets an environment built from an allowlist — `env -i`, not an overlay on the caller's: the inner half itself (bwrap's `--clearenv`, then the plan's entries), the daemon, both TUIs and every deck client. Processes the daemon starts — the panes — inherit the daemon's, plus the deck's own pane variables. The processes the outer half starts on the host do not get it; [What runs on the host](#what-runs-on-the-host) lists what each of those gets, and [The build namespace](#the-build-namespace) gives the build its own allowlist. The allowlist is `sandbox::ALLOWED_ENV`; the inner half requires its own environment to be exactly the plan's entries (which proves `--clearenv` held), the daemon's `/proc/<pid>/environ` is checked against the same map and recorded in the evidence, and a credential-shaped name is refused even if someone adds it to the allowlist.

| variable | why |
| --- | --- |
| `PATH` = `$S/bin:/usr/local/bin:/usr/bin:/bin` | the staged **client-side** build first: in forward the branch build, so a pane that shells a bare `dot-agent-deck` reaches the branch binary while the daemon in memory is still the old one — the upgrade this test is about; in reverse the previous release — the downgrade. The operator's `~/.local/bin` is deliberately absent. (The daemon then applies a login shell's `PATH` to what it spawns, which is why a probe's stand-in is always named by absolute path) |
| `HOME`, `TMPDIR=/tmp`, `TERM`, `LC_ALL`, `COLORTERM`, `SHELL`, `USER`, `LOGNAME` | ordinary settings; `USER`/`LOGNAME` come from the password database, not from the caller |
| `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` | `HOME` alone does not cover them: `schedules_path()` consults an inherited `XDG_CONFIG_HOME` before `HOME`, so a sandbox daemon could otherwise read the operator's real schedules and fire them |
| `DOT_AGENT_DECK_CONFIG`, `_SESSION`, `_SCHEDULES` | pinned to files under `$S/config`. The harness creates none of them except `config.toml` for a dispatch probe (one key, `default_command`; see [Branch-specific probes](#branch-specific-probes)); an absent schedules file is "no schedules". A TUI writes `session.toml` itself as it runs |
| `DOT_AGENT_DECK_STATE_DIR`, `_LOCK_DIR` | per-user state and the per-endpoint lock |
| `DOT_AGENT_DECK_LOG` | **resolved separately from the state dir.** Without it an otherwise-isolated daemon appends into the operator's real `~/.local/state/dot-agent-deck/deck.log` |
| `DOT_AGENT_DECK_EXPERIMENTAL` | pinned explicitly (off by default, `--experimental` to turn it on) rather than inherited |
| `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` | false green 2 above |
| `DOT_AGENT_DECK_TEST_MAX_LIFETIME_SECS` | a second backstop for a stand-in that escapes its process group; the PID namespace is the first |
| `GIT_CONFIG_NOSYSTEM=1` | git inside the run reads no system config |
| `DAD_XVER_SANDBOX=$S` | the run's unique marker: part of every sandbox process's identity, and what the post-run census looks for |
| a probe's additions | `RUST_LOG` and three delegate timers (`late-session-start`), #1181's eight git location variables (`git-env`) — each admitted by exact name and value, never replacing a base entry and never credential-shaped; see [Branch-specific probes](#branch-specific-probes) |
| `XDG_RUNTIME_DIR` | `/run/user/<uid>` (private inside) or, with `--unset-xdg-runtime-dir`, **absent** |
| `DOT_AGENT_DECK_SOCKET`, `_ATTACH_SOCKET` | `$S/hook.sock` / `$S/attach.sock` in `sandbox-sockets` mode; **absent** in `resolved` mode |

The fixture `$S/project/.dot-agent-deck.toml` is created fresh, must be a regular file owned by the run's uid, and is re-verified before launch: the deck's project-config discovery walks up from **cwd** and stops at the first such file, so this is what keeps the walk from reaching the operator's own config. With the default runs root, which is under the masked home, that is doubly true: nothing between `$S` and the home is visible to walk into. A `--runs-root` outside the home leaves its ancestors visible, read-only, and the fixture is then the only thing that stops the walk.

### The pre-connect assertion

Immediately before every client process the harness drives — each TUI, each `daemon status` poll — and before every deck command it types into a pane, the inner half re-proves, and aborts before the client exists if any of it fails or cannot be evaluated. It covers the clients the harness drives; a process that branch code starts on its own is not preceded by it. The harness's own clients are spawned directly, with no shell between the last check and their `execve`. A command typed into a pane is started by that pane's stand-in shell instead, with the environment the daemon gave the pane — the daemon's own, verified against the plan as part of its identity, plus the deck's pane variables — so check 2 covers a pane command only through the daemon's environment.

1. its mount namespace is the one it recorded at startup and not the outer half's, and each mask's `dev:ino` still matches;
2. the client's environment is exactly the plan's and passes the allowlist policy;
3. the daemon still matches its recorded identity (below);
4. each endpoint the matrix says the daemon owns is listening **in the kernel's table**, every listening inode there is held in `/proc/<daemon pid>/fd`, and the path is an owner-only socket of the run's uid;
5. each candidate the matrix says must be absent has no file and no listener;
6. every path-bound listening Unix socket in the run's network namespace is held by the daemon (abstract sockets are not in the census) — which is what rules out a second daemon, because only a listening one is reachable. A command-line count could not: with a lifetime cap set, the daemon forks (not execs) a reaper per pane that keeps its exe, command line and environment and never listens;
7. the outer half confirms the host's standard endpoint candidates are exactly as at baseline — same file identity or still absent, same listening inodes, every baseline owner still the same process holding its socket — and that no host listener lies under `$S`.

The endpoint matrix for `resolved` with `XDG_RUNTIME_DIR` unset — the #1121 configuration — is: the old daemon owns the flat `/tmp/dot-agent-deck[-attach]-<uid>.sock`; the per-uid `/tmp/dot-agent-deck-<uid>/{hook,attach}.sock` and the XDG pair must be absent. That absent half is what proves a run reached the **fallback arm** rather than one #1121 did not touch: of the endpoint candidates a branch client resolves, the only one that answers is the legacy flat one, reached through the compatibility read. The evidence records that proof before the branch TUI starts, and confirms it afterwards from tells 1 and 2.

**What the assertion does not have to win is the race** — for a client that follows the current resolver. Between the last check and the client's `connect`, the expected socket could vanish. A client that then resolves onward through the current resolver, with the run's admitted environment, can only land on another path inside `/tmp` or `/run/user/<uid>` — both private — because that environment names no host path. There it would lazy-spawn a daemon inside the namespace, which tell 1's count and the next pre-connect's second-listener check both catch. So for such a client the TOCTOU window can turn a run into a FAIL, and it cannot reach one of the host's standard endpoints. That is the resolver contract, not a filesystem guarantee: a client that ignores the resolver — a branch binary that deliberately opens, say, `/run/custom/deck.sock` — can connect to a host pathname socket outside the masks through the read-only root, window or no window.

### Teardown is by verified identity

On 2026-09-15 an agent finishing with a cross-version sandbox ran `pkill -f "daemon serve"`. That pattern also matches the **production** daemon's own command line, which took the SIGTERM 1.42 s later and gracefully stopped nine panes across three dispatched units ([#428 occurrence #5](https://github.com/vfarcic/dot-agent-deck/issues/428#issuecomment-5688814518)). `pkill` sends SIGTERM, so it goes *around* issue #770's `daemon stop` refusal rather than having to defeat it.

Nothing in this harness signals by name, and a cmdline substring no longer counts as identity. Each process the inner half tears down in the normal path has, captured right after spawn and re-read immediately before each signal of that teardown: its start time (field 22 of `/proc/<pid>/stat`), `/proc/<pid>/exe`, its exact NUL-separated command line, its cwd, its **whole** environment (which carries `DAD_XVER_SANDBOX`), and its mount namespace. A single difference refuses the signal and is recorded. The daemon gets exactly **one** SIGTERM — a second one force-exits it past its graceful teardown — then 20 s, well past its 3 s agent grace, and SIGKILL only after a second full re-verification. Two structural properties sit underneath the checks rather than replacing them: the process is inside the run's private PID namespace, where no host process has a pid at all; and its `Child` handle stays un-reaped until after the last signal, so the kernel cannot give its pid to anyone else in between. The TUIs are stopped through their own un-reaped handles after the same re-verification. Two failure paths signal before a full identity exists, both through a child handle that has not been reaped and so cannot name another process: a PTY client whose identity capture failed is killed and waited on at once, and a stand-in's hook child that times out is killed through its handle.

**Teardown is not race-free, and the window is narrow.** For the daemon and the TUIs the un-reaped handle closes it. For a process the harness holds no handle for — the second daemon an old client lazy-spawned in reverse, and a marked survivor the census finds — the last verification and the `kill(2)` are two system calls: the process can exit between them, be reaped by the namespace's init, and have its pid reused by another process of the same run. The start-time field catches a reused pid at verification time but cannot make the two calls atomic; a pidfd would. It was left as it is deliberately, because the window is confined to the run's own PID namespace during a teardown that is stopping everything in it: what it can reach is another of this run's processes, never a host one.

After the daemon, the inner half censuses the PID namespace: each survivor that carries the run's marker is signalled individually after its identity is recorded; one that does not is left alone. When the inner half exits, bwrap's init exits with it and the kernel kills every process left in the PID namespace, `setsid`'d or not; the outer half's census then requires that namespace empty. The outer half itself signals nothing but its own `bwrap` child, and only when `--run-timeout-secs` (default 1200) expires — through that child's un-reaped handle, which takes the whole namespace down with it.

### What runs on the host

None of this is in either namespace, and none of it is contained by anything above. It runs on the host, as the operator, in the host's mount, PID and network namespaces.

- **`cargo fetch --locked --manifest-path <clone>/Cargo.toml`** — the fetch phase, which prepares the crates the offline build needs. It downloads each crate the branch's `Cargo.lock` names, checks it against the lockfile's checksum and unpacks it into the harness's own Cargo home (`--cargo-cache`), and runs no build script and no proc macro. Cargo configuration could still name an executable — a credential provider, `net.git-fetch-with-cli` — or redirect a source, so it runs where no configuration but the harness's is read: its working directory is `/`, since Cargo reads configuration from its working directory's hierarchy and not from the manifest's (measured on Cargo 1.98.1), and `/.cargo/config*` must be absent; `CARGO_HOME` is that Cargo home, which must hold no `config*` or `credentials*`; and its environment is exactly `PATH` (the toolchain's `bin`, `/usr/bin`, `/bin`), `CARGO_HOME`, `HOME` and `XDG_CONFIG_HOME` (all three that Cargo home, which must also hold no `.gitconfig` or `git/config`), `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` — so a git dependency, should a branch's lockfile name one, is fetched without your git configuration. Whether Cargo's built-in git implementation honours those two git switches was not measured; this repository's lockfile has no git dependency. No proxy variable is passed, so a host that reaches the registry only through a proxy cannot fetch. A branch opted in with a changed `Cargo.lock` can make this download any crate the registry serves; it cannot make it execute one.
- **`rustc --print sysroot`**, from `/`, with the caller's environment minus credential-shaped names and `DOT_AGENT_DECK_*` — the rustup proxy reads its toolchain selection from that environment. It executes the proxy and the compiler it selects, and nothing of the branch's.
- **`git`** — `clone`, `fetch`, `checkout`, `status`, `rev-parse`, `merge-base`, `diff`, `ls-tree` and `archive`: the caller's environment minus the eight location variables and `GIT_CEILING_DIRECTORIES`, plus `GIT_TERMINAL_PROMPT=0`. They run in the build clone, so that clone's own git configuration and hooks apply to them; the build namespace binds the clone read-only, so nothing a build executes can write either (see [The build clone](#the-build-clone)).
- **`/usr/bin/git` for the sandbox's own repositories** — `git init` of `$S/project`, its fixture commit for the dispatch probes, and `git-env`'s decoy: an empty environment apart from fixed system paths, `HOME` and `XDG_CONFIG_HOME` under `$S`, no system or global configuration, and a ceiling at `$S`.
- **`gh release list` and `gh release download`**: the full caller environment, because they may need its GitHub credential.
- **`sha256sum` and `tar`**: an empty environment with `PATH=/usr/bin:/bin`. **`bwrap`**: an empty environment. **`date`**: the caller's.
- **The harness itself**, which is also what bubblewrap starts, read-only, inside each build namespace as its probe.

### What the runtime containment does not cover

- **Reads are not confined to `$S`.** Inside the namespace the rest of `/` is readable (read-only), apart from the masked home, `/tmp`, `/run/user/<uid>` and `/var/tmp`. Pathname sockets elsewhere stay connectable — under `/run` the Docker socket and the system D-Bus socket, and the nix daemon's under `/nix`, all three measured connectable on the box this was written on from a namespace of this shape. The Docker socket is the serious one: a member of the `docker` group can use it as root. No rule of the current resolver names any of them, but a branch binary that opens one directly connects. The [build namespace](#the-build-namespace) masks all of `/run` and covers the remaining host sockets with `/dev/null`; the runtime namespace does neither.
- **The sandbox's own sockets are reachable from the host.** A pathname socket under `$S` is a file on the host's filesystem, and pathname sockets do not respect network namespaces. A host process that deliberately connects to `$S/…` reaches the sandbox daemon, and so does a host deck started with an explicit `DOT_AGENT_DECK_SOCKET` or `DOT_AGENT_DECK_ATTACH_SOCKET` naming a path under `$S`. A normally configured host deck, resolving the standard XDG or `/tmp` paths, does not resolve under `$S`.
- **The host checks cover the standard endpoint candidates and the host network namespace, at the instants they run.** They prove those candidate paths and their listeners unchanged and no host listener under `$S`. They do not see a connection that changed nothing persistent, an endpoint at a custom path, or a socket in another network namespace, and they do not diff the rest of the host's filesystem; the read-only root and masked home are what keep writes out of it, subject to the residual `rw` submounts the evidence lists.
- **The deck census is an observation.** A baseline deck process that exits during a run is reported, not attributed — other units share the box. The production endpoints' owners are the exception: an owner that changes fails the run (INCOMPLETE), because that is exactly what an escape would look like.
- **The real-log check reads one file**: `DOT_AGENT_DECK_LOG` if the caller has it set, otherwise `~/.local/state/dot-agent-deck/deck.log`.
- **It needs bubblewrap and unprivileged user namespaces.** On a host where the smoke test fails the run refuses before building anything; there is no un-isolated fallback.

## The two endpoint modes

`--endpoint-mode sandbox-sockets` (the default) pins `DOT_AGENT_DECK_SOCKET` and `DOT_AGENT_DECK_ATTACH_SOCKET` to `$S/hook.sock` and `$S/attach.sock`. This is the right choice for any change that does not touch endpoint resolution. The matrix then requires every resolved candidate — flat, per-uid and XDG, all private — absent.

`--endpoint-mode resolved` sets neither override, so both builds resolve their endpoint the way they would on a real host — into the namespace's private `/tmp` and `/run/user/<uid>`. **Use it only when the change under test *is* endpoint resolution**: those overrides short-circuit resolution before the logic under test runs. Its deck processes cannot bind the host's standard endpoint candidates — `/tmp` and `/run/user/<uid>` are masked — so a `resolved` run no longer takes those addresses from the host. That is as far as the masks go: `$S` itself is visible from the host, and a branch that bound some other writable path visible in the namespace is not stopped by them. The outer preflight still refuses to start one while the host's flat or per-uid endpoint sockets exist, which keeps the before/after comparison unambiguous.

For issue #1121 the invocation is both levers together:

```sh
cargo xver --branch agent/dispatch-issue-1121 --endpoint-mode resolved --unset-xdg-runtime-dir
```

In that mode a run also records whether the branch build created an endpoint directory of its own (`/tmp/dot-agent-deck-<uid>` inside, `$S/fallback-tmp/dot-agent-deck-<uid>` outside) while it was attached to the old daemon at the legacy address. That is an observation rather than a fifth tell: it checks one change's claim about itself — that its compatibility read is read-only — where the four tells are what rule 12 asks of every change.

## The build namespace

Since issue #1212 the branch's `cargo build`, and the build-time gate's `cargo metadata --no-deps`, run in a bubblewrap namespace of their own, which the outer half starts before the runtime namespace exists. Until then both ran on the host as the operator, where every build script, proc macro and cargo-configured linker had the operator's files, processes, sockets, credentials and network. `xtask/cross-version/src/buildns.rs` builds the namespace, and each run's evidence file lists what it measured under **Build**.

### Its shape

- Started with `--unshare-all --unshare-user --disable-userns --assert-userns-disabled --die-with-parent --new-session`, as the runtime namespace is: private PID, network, IPC, UTS and user namespaces, and no nested user namespace. The network namespace holds only a loopback interface, and Cargo runs `--offline`.
- `/` read-only. The operator's home is an empty tmpfs, and so are `/tmp`, `/var/tmp` and all of `/run` — the whole of `/run`, unlike the runtime namespace, because the build needs nothing there and it holds the host's system sockets. The operator's Cargo home is masked too when `CARGO_HOME` puts it outside the home. The tmpfs mounts are RAM-backed (CLAUDE.md rule 14), so each has a size cap: 1 GiB for `/tmp`, 64 MiB for the others.
- Bound back at their own absolute paths: the build clone **read-only** (so `build.rs`'s `git describe` and Cargo's fingerprints keep working, and no build can plant a hook, a git configuration or a `.cargo/config.toml` in it), the trust domain's target dir **read-write**, and the toolchain's sysroot read-only when it lives under the home. The harness refuses a clone, target dir and fetch-phase Cargo home any two of which nest: the Cargo home's `registry` is read-only only at its remapped path, so inside the target dir it would be writable through the target dir's bind.
- A Cargo home at `/tmp/xver-cargo-home`, inside the private `/tmp`, with the fetch phase's `registry` (and its `git`, if a fetch created one) bound read-only beneath it. It is new on every run, so a `config.toml` a build script leaves there is gone with the namespace. The operator's own Cargo home — its `config.toml`, `credentials.toml` and `bin/` — is never bound.
- Each pathname socket listening in the host's network namespace when the plan is made, and still visible through a bind, is covered by a read-only bind of `/dev/null`, so `connect(2)` on it is refused (a read-only mount does not stop `connect(2)` on a Unix socket). On the box this was written on that was one socket, the nix daemon's, which accepts build requests and can fetch over the network on a client's behalf.
- `--clearenv`, and then exactly `PATH` (the toolchain's `bin`, then `/usr/local/bin:/usr/bin:/bin`), `HOME` (the masked home), `CARGO_HOME`, `TMPDIR=/tmp`, `LC_ALL=C.UTF-8`, `GIT_CONFIG_NOSYSTEM=1`, and for the build `CARGO_TARGET_DIR`. No `RUSTC`, `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `RUSTFLAGS`, Cargo configuration variable, proxy or `DAD_*` build seam is admitted. The toolchain runs directly from its sysroot, not through a rustup proxy, so a `rust-toolchain.toml` in the branch selects nothing. A toolchain whose sysroot has no `bin/cargo` — a nix or devbox `rustc` package, whose cargo is a separate store path — is refused rather than widened into: run from a shell whose `rustc` resolves to a rustup toolchain.

The crates the offline build needs are fetched first, on the host, by `cargo fetch --locked` into the harness's own Cargo home (`--cargo-cache`, default `../dot-agent-deck-xver-cargo`), from a working directory and with an environment that read no configuration but the harness's — [What runs on the host](#what-runs-on-the-host) has the details. If the fetch did not prepare something the build needs, the offline build fails, which is the fail-closed direction.

### How each run is measured

bubblewrap does not start Cargo. It starts a read-only copy of the harness at `/run/xver/harness`, which measures the namespace it is in, writes the result as the first line of its stderr, and only then `exec`s Cargo in the same namespace with the same environment — minus the `PWD` bubblewrap adds after `--chdir`, which it accepts only with the chdir target as its value. A failed check exits before Cargo exists, and the run is refused. A build cannot forge the report: nothing Cargo prints can come before a line written before Cargo started, and the outer half reads the first report line only. The probe checks, and the evidence file records, each of these:

- its mount, PID and network namespaces differ from the outer half's;
- its environment is exactly the allowlist;
- no `.cargo/config` or `.cargo/config.toml` is visible in any ancestor of its working directory, so Cargo's hierarchical configuration is the working directory's own and the private Cargo home's;
- the only network interface is `lo`, and `connect` to an external IPv4 and an external IPv6 address fails;
- the masked home holds nothing but the bind destinations under it and the directories leading to them;
- the operator's Cargo `config.toml`, `config`, `credentials.toml` and `credentials`, and the private Cargo home's, are absent;
- the clone and its `.git` refuse a file creation — for `cargo metadata`, the extracted tree does;
- the host's standard deck endpoint candidates are absent, and `connect` fails on each of them and on every pathname socket that was listening on the host at plan time;
- `/proc` lists only the namespace's own processes;
- nothing is writable but the target dir (for the build) and the private tmpfs mounts: a residual `rw` submount the read-only root did not remount **fails** the check here, where the runtime namespace only reports it as exposure, and so does a `/proc/self/mountinfo` that cannot be read. None was found on the box this was written on, where the runtime namespace reports several under `/run`.

After bubblewrap exits, the outer half requires no process left in the namespace's PID namespace, and refuses the run otherwise. When bubblewrap's init exits the kernel kills every process left in that PID namespace, `setsid`'d or not, and `--die-with-parent` takes the namespace down if the harness dies.

What the probe measures is the namespace as a process bubblewrap started sees it. A build script sees that namespace plus the variables Cargo sets for it: `OUT_DIR`, `CARGO_*`, `RUSTC`, `HOST`, `TARGET`, `LD_LIBRARY_PATH` and, from Cargo's own TLS setup, `SSL_CERT_FILE` and `SSL_CERT_DIR`. The proof below is the measurement from inside one.

### The proof: a probing build script

For issue #1212 a scratch branch whose `build.rs` probes its surroundings before doing its normal work was built with `--allow-build-changes` (after the gate had refused it without the flag, naming `build.rs`), cold and then warm, and the second run passed all four tells. The probe only read and asked — `connect` and disconnect, `access(2)` via `test -w`, signal 0, read-only CLI calls — and wrote its findings to the one host path the build may write, its target dir. ### Read-only caches

Measured on Cargo 1.98.1: an offline build with the fetched `registry` bound read-only under a private writable Cargo home succeeds, and writes three entries to that home's root — `.package-cache`, `.package-cache-mutate` and `.global-cache`. With the whole fetched Cargo home bound read-only it succeeded too. The harness uses the first shape rather than rely on Cargo tolerating a read-only home for its locks and its last-use tracking.

### Trust domains

The build-time gate's answer picks the target dir the build may write:

- **mainline** — the branch's build-time code is identical to its merge-base: the shared `--target-dir`, reused across every such branch, so a warm rebuild stays warm;
- **opted-in** — the branch changes build-time code and `--allow-build-changes` was given: `<--target-dir>-opted-in-<branch slug>-<digest>`, the branch's own. The digest is of the repository and the branch together, so two branches whose slugs collide (`feature/x`, `feature-x`) and the same branch name from another `--repo` each get their own. Nothing an opted-in build writes is bound into another branch's build, and no other target dir is bound into it. Its first build is cold.

Each target dir carries a `.xver-trust-domain` file naming its domain and repository — `mainline <repo>`, or `opted-in <repo> <branch>` — so another `--repo`'s mainline is another domain too. An absent or empty directory is adopted and marked; one whose marker names another domain is refused; and one with content but no marker is refused, because it predates the build namespace, when an opted-in build ran on the host and could leave artifacts — build-script binaries among them — that a later build reuses. Remove such a directory and let the harness recreate it. A build can rewrite its own domain's marker, but that only makes the next run refuse: the path, not the marker, decides where a build writes.

### Cost

Measured on the box this was written on (16 cores, with other agents building throughout; `/proc/pressure/io` `some avg10` about 17): a cold build of `dot-agent-deck` took 100 s in the namespace and 83 s on the host into a separate target dir. Warm rebuilds after a checkout — `.git/index` touched, which reruns `build.rs` and recompiles and relinks the crate — took 9.3–11.9 s in the namespace and 9.6–20.9 s on the host, three of each, alternating: within the noise of a loaded box. The persistent same-path target dir is what keeps the fingerprints. The first `cargo fetch` into an empty Cargo home took 7.9–9.7 s.

### The linker pool

`scripts/link-gate.sh` takes a slot from a pool under `/tmp` by default ([`build-gate.md`](build-gate.md)). Inside the namespace `/tmp` is private and `DAD_BUILD_GATE_DIR` is not admitted, so the gate runs against a pool of its own: it bounds that build's concurrent links and nothing else. **A namespaced build is not gated against other builds on the host**, and the evidence file says so. The machine-wide pool is never bound into a build namespace, in either domain: build code that could write it could hold or delete every slot.

### What the build namespace does not contain

- **Reads, and where they can go.** The rest of `/` stays readable to your uid: `/etc`, `/nix/store`, other users' files as their permissions allow, and your own files outside the home and the masks. With no network and the host's sockets covered, the build has no direct route off the host for what it reads; what it can do is embed it in the binary — `include_str!` in ordinary source is enough, no build script needed — which the runtime scenario then executes and whose output lands in the evidence file, write it into its target dir, or print it: a failed build's last 40 lines of output are shown in your terminal, with control characters escaped so they cannot drive it.
- **The binary it produces.** The build namespace contains the build. The branch binary then runs in the runtime namespace, with the exposure [What the runtime containment does not cover](#what-the-runtime-containment-does-not-cover) lists — the Docker socket among it.
- **Resources.** There is no cgroup limit: a build can use all the CPU and memory the host has, and all the space on the target dir's filesystem. Only the tmpfs mounts are capped.
- **The kernel.** A kernel or bubblewrap vulnerability reachable from an unprivileged user namespace escapes this namespace, as it escapes the runtime one.
- **Mainline's own build-time code and the registry crates** run in every build — now inside the namespace; the gate trusts them as before.
- **A socket missing from the host's table when the plan is made** — bound later, reached through another hard-linked name, or in another network namespace — is not covered by `/dev/null` if a path to it is visible.
- **The fetch phase and the input acquisition** run on the host ([What runs on the host](#what-runs-on-the-host)).

## The build clone

The branch is built in a **standalone clone** — its own `.git`, cloned from `https://github.com/<--repo>.git` on first use — not in a linked worktree of the operator's repository. The first version used a linked worktree, and a linked worktree writes its registration, HEAD, index and reflogs into the source repository's common `.git`, outside anything the run owns, where another session's `git worktree prune` can reach it; its stash is shared with every other worktree too. The harness refuses a `--source-clone` whose `.git` is a file, requires `git rev-parse --absolute-git-dir` and `--git-common-dir` to both be the clone's own `.git`, refuses to build over tracked modifications, and runs every git command in the clone with the eight location variables removed (issue #834's shape).

**Only a clone the harness created.** When it creates a clone the harness writes `.git/xver-namespaced-build-clone` into it, and it refuses an existing clone without that file: such a clone predates the build namespace, when an opted-in branch's build ran on the host with write access to the clone — its hooks and git configuration among it, which the harness's own `git` commands honour — so the harness no longer builds in it. Remove it, or point `--source-clone` at a path that does not exist, and the harness re-creates it. From then on the build namespace binds the clone read-only, so no build can write the marker, a hook, a configuration or any other file there. The marker is what makes a clone acceptable, not what makes it dedicated: the harness fetches into it and checks the branch out detached there over whatever was checked out, so point `--source-clone` only at a clone used for nothing else.

It stays at a fixed path **outside** `$S`, which is a deliberate trade: a per-run clone under `$S` would give each run a fresh workspace path, and cargo would rebuild the whole workspace crate into the shared target dir every time — or, with a per-run target dir, compile everything from cold, fourteen times over on a box whose I/O has already saturated under concurrent builds (issue #863). At its default path the clone is under the masked home, so nothing inside the runtime namespace can see it (a `--source-clone` outside the home would be visible, read-only); the run executes the staged copy of the binary in `$S`. The runtime repository the run does touch, `$S/project`, is a standalone `git init` under `$S`.

The harness's own git commands in the build clone are these: a `git clone --no-checkout` once; then per run `git fetch <url> main` and `git fetch <url> <branch>` (each writes `FETCH_HEAD`, objects and the other metadata a fetch keeps in the clone's `.git`), `git checkout --detach FETCH_HEAD` (HEAD, the index and the working tree), and the read-only `status`, `rev-parse`, `merge-base`, `diff`, `ls-tree` and `archive`. None of those commits, amends, rebases, stashes or pushes, and none of them talks to GitHub except the two fetches and the first clone. They run in the build clone and nowhere else, which is a repository of yours only when `--source-clone` names one. Two things sit outside that list: the harness initialises `$S/project`, and commits its fixture there for the dispatch probes, with `/usr/bin/git` under `$S`; and the code `cargo build` executes can run `git` itself, inside the build namespace, against the read-only clone and with no network.

## The build-time gate

Before `cargo build` runs, the harness decides whether the branch supplies build-time code of its own — code that `cargo build --locked --offline --bin dot-agent-deck` would execute. Its answer decides whether the branch is built at all, and in which [trust domain](#trust-domains). It fetches `main` of `--repo` into the build clone, takes the merge-base of that and the branch HEAD (every merge-base, if the history has several), lists the paths `git diff --name-only --no-renames` says the branch changed since, and classifies each against the build-time surface:

- **by name, anywhere in the tree**: any `build.rs`, `Cargo.toml` or `Cargo.lock` (a new or changed registry crate brings its own build script and proc macros), `rust-toolchain` and `rust-toolchain.toml` (they select the compiler), and anything under a `.cargo/` directory (a wrapper, a linker, a source replacement);
- **derived at the merge-base**, from mainline's own tree: `git archive` extracts it into a fresh owner-only scratch directory beside the runs, `git ls-tree` proves the extraction is exactly that tree — no file dropped by an `export-ignore`, none added — and only then does `cargo metadata --no-deps` run there, in a [build namespace](#the-build-namespace) with the extraction bound read-only as its working directory. Walking the local dependency graph from the package that owns the `dot-agent-deck` bin — over normal and build edges, never dev ones, because `cargo build` builds no dev-dependency — finds each reached package's build script and every reached package that executes at build time (Cargo's "host" artifacts: a proc macro, a build-dependency, or anything those depend on), whose whole directory counts. Each build script's module closure counts — the files it pulls in with `mod`, `#[path]`, `include!`, `include_str!` or `include_bytes!` and a literal path. So does every repository path a string in `.cargo/config.toml` names, with each sibling script its text names, recursively, and every `[patch]` or `[replace]` path in the root `Cargo.toml`.

At the time of writing the derived set is `build.rs`, `build_version_resolve.rs` (which `build.rs` `mod`s), `scripts/link-gate.sh` (the `linker`) and `scripts/build-gate.sh` (which the linker script execs). The workspace's one proc macro, `xtask/spec`, is a dev-dependency, so a `cargo build` never compiles it; `desktop/src-tauri/build.rs` is outside this build's graph and counts by name only. The evidence file lists the set a run compared against.

The closure rests on one argument and has a stated edge. The argument: a changed file can make the build execute a *new* file only by naming it, and a file that names one in the ways the scan follows is itself counted, so the change shows up as a change to a counted file. The edge: the scan follows `mod`, `#[path]` and `include*!` with a literal path in a build script's module tree, and sibling file names in a script the cargo configuration names — nothing else. A file that a counted build script runs through `Command`, that a counted script runs by a non-sibling path, or that any of them reaches by a computed name, is not in the set, so an **existing** reference of that kind would leave a branch free to change the file it names. None exists at the time of writing — `build.rs` runs only `git`, and the linker script execs no repository file but its sibling `build-gate.sh` — and the evidence file lists the derived set every run compared against, which is where a new one would first show as missing.

The decision:

- **nothing counted changed**: the run proceeds, and the evidence file's **build-time code** row reads `build-time code identical to the merge-base with origin/main`, naming both commits;
- **something counted changed, no opt-in**: the run stops before `cargo build` — nothing compiled, no sandbox created, no evidence file written — and the error names every changed build-time file with the reason it counts. Review those changes; `--allow-build-changes` then builds them;
- **with `--allow-build-changes`**: the run proceeds, and the row records which build-time files changed and that the caller opted in. The build runs in the build namespace, into the opted-in trust domain's own target dir, and the evidence file's **Build** section names that dir;
- **with `--skip-build`**: nothing is built, so a change is not refused; the row still says whether the branch changed build-time code;
- **the comparison could not be made** — no merge-base, a failed fetch, an incomplete extraction, `cargo metadata` failing, no `dot-agent-deck` bin at the merge-base: the run refuses, as it does for a change. A gate that could not be evaluated has not been passed.

It was proven on a real branch without building it: `renovate/lock-file-maintenance`, which changes `Cargo.lock`, was refused with `Cargo.lock` named, and the target dir held no file newer than a marker written just before the run.

What it does **not** do, stated plainly: it detects changes; it contains nothing — the build namespace does the containing. The merge-base's own build-time code runs in every build and is trusted by construction; registry crates pinned by an unchanged `Cargo.lock` are unchanged, so they are trusted exactly as far as the merge-base's lockfile is; and a build the caller opts into executes the branch's code with what [the build namespace leaves it](#what-the-build-namespace-does-not-contain). The base is always `main` of `--repo` — deliberately not an option, since a caller-chosen base could be the branch itself — so with the default repository it is mainline, and with another `--repo` it is whatever that repository's `main` holds.

## Running several at once

Each run mints its own sandbox, namespace and endpoints, so neither mode and neither direction collides with another run at the endpoint level. What two concurrent runs do share by default is the **build clone and the target dir** — two runs would check out different commits into the same clone and build into the same target at once. Give each concurrent run its own `--source-clone` and `--target-dir`; a fixed set of lanes (`-xver-src-a`, `-xver-target-a`, …) reused across branches keeps the cache benefit. An opted-in branch's target dir is derived from `--target-dir`, so it stays in its lane. The fetch-phase Cargo home (`--cargo-cache`) is safe to share between concurrent runs: Cargo locks it while it writes, and every build namespace binds its `registry` read-only. The release cache (`--releases-dir`) is read-mostly once populated; pre-warm it with one run rather than racing the first download.

## Reading the evidence file

`.dot-agent-deck/xver-evidence/<branch slug>.md` (override with `--evidence`, which is written verbatim) carries: a **build-time code** row with [the build-time gate](#the-build-time-gate)'s answer — identical to the merge-base with `origin/main`, or which build-time files the branch changes and that the caller opted in; a **Build** section — the toolchain, which trust domain and target dir built the binary, the fetch phase's command and environment, each build namespace's shape and every check its probe measured, the build's duration, the survivor check, and whether the build was gated against other builds; the previous release's tag and where it came from — `given explicitly with --previous`, or `resolved, not given` with the repository and the UTC time of the listing it was read from — preflight lines saying the old binary matched its release's published `checksums.txt` (for `--old-binary`, that it is **not checksum-verified**) and that its `--version` ran inside the namespace, both builds' `daemon hello` output verbatim, the sandbox and staged binary paths, the daemon pid, each tell with the measured value it was decided on and a **Never recorded** line naming any expected tell the run did not record, an **Isolation** section listing every isolation check that was measured and held (namespace ids, mask identities, the daemon's recorded identity, the first pre-connect assertion per client kind with its kernel listener map, the fallback-arm proof in `resolved` mode, the residual `rw` submounts, the survivor census), a **Postconditions** section with the outer half's post-run checks, a numbered run log, and raw excerpts — the daemon's environment read back from `/proc`, the mismatch prompt as printed, the target pane's screen after the delegate, the orchestrator's screen after the hook, and the tail of the sandbox log. It is written on **every** path once the sandbox exists, including a run that broke down partway. A `--skip-build` run says so directly under the verdict, because the checked-out HEAD then says nothing about the binary under test: the line names the commit the binary's own build id names — flagged **STALE** when that is not the HEAD — or states that no commit is knowable from it. The build id is the binary's own stamp, from `git` when its `build.rs` last ran or from an injected `DAD_BUILD_ID`, and the line says that too.

The verdict is **PASS**, **FAIL** (a tell failed or the scenario broke down — the branch and the previous release did not interoperate, or the scenario could not be stood up, which the run log says), **INCOMPLETE** (a tell could not be measured or an expected one was never recorded, or an isolation check failed or could not be evaluated — so the run measured nothing either way), or, in reverse only, **OLD CLIENT CANNOT DISCOVER THE BRANCH DAEMON** (measured: the old client started a daemon of its own instead of finding the branch's, and the collateral tells proved nothing else happened). An isolation failure dominates: a tell measured inside a namespace that did not hold is not a measurement of the branch. A failed tell outranks a measured non-discovery, and an unmeasured one does too — "nothing else happened" is only a claim when it was measured. A reverse evidence file carries a **Discovery** section when that outcome occurred — with a line under the intro saying that none of the four tells and no probe stimulus ran — the probe it ran and how it was chosen, and each probe tell; a `generic` reverse run carries `role-set` too.

The sandbox is removed after a clean pass and kept after anything else; `--keep-sandbox` keeps it either way. Its `artifacts/` holds both PTY streams verbatim, the old daemon's stdio and the inner half's evidence JSON.

## What it covers, and what it does not

Forward covers the pairing rule 12 and [`versioning.md`](versioning.md) exist for: a **newer TUI against an older daemon**, over the real attach protocol, with real orchestration state in the old daemon's memory, asserting on payloads rather than on exit codes. Reverse covers the opposite pairing for the same flows plus one branch-specific stimulus each; [What reverse covers, and what it does not](#what-reverse-covers-and-what-it-does-not) states that narrowly.

It does not cover:

- **A real agent.** Every role is a stand-in (`sh`, `cat`), deliberately: this check is about the TUI↔daemon wire, so the runtime scenario is given no *agent* credential and invokes no agent. That is a statement about the scenario, not about every credential on the host: the build namespace masks your home, `/tmp` and `/run`, admits no credential-shaped variable and has no network, but a credential readable outside those masks stays readable to the build, and the runtime namespace can reach the host sockets [its containment does not cover](#what-the-runtime-containment-does-not-cover). (`gh release list` and `gh release download` use your GitHub credential; `--old-binary` with an explicit `--previous` calls neither.) It therefore says nothing about how a real agent behaves across the version boundary, and it is not a substitute for the lane-2 real-agent tests CLAUDE.md rule 4 asks for.
- **A daemon-side change, in the forward direction.** Forward runs the previous release's daemon, so a change that lives in the daemon executes nowhere in a forward run; `--direction reverse` is the pairing that runs it.
- **The desktop GUI.** `classify_handshake` compares `PROTOCOL_VERSION` and `CONTRACT_BREAKS` and is a different code path from the TUI's build-version handshake; nothing here exercises it.
- **More than one previous release per run.** `--previous` takes one tag.
- **Anything that is not Linux.** `/proc`, bubblewrap, `ss(8)` and `statvfs` are all assumed, and only the `linux-amd64` release asset is fetched. On any other target the crate still builds — it is a workspace member, and the Windows and macOS CI jobs build `--workspace` — but only to a stub that prints that `cargo xver` runs on Linux only and exits non-zero.
- **Flows other than the two rule 12 names, in forward.** A delegate and the two hook kinds are what a forward run drives; a contract break that touches neither would not be seen. A reverse run adds its probe's one stimulus and nothing more.

## Which release is "previous"

`--previous` names the old side. When it is omitted the harness resolves it rather than defaulting to a tag, because a hardcoded default is right on the day it is written and silently wrong from the next release on — a default run would then test against a release that is no longer the previous one, and nothing in its output would say so.

The rule matches how `release.yml` publishes: releases are created as non-drafts and flagged prerelease exactly when the version contains a `-`, and GitHub marks each newly published stable release Latest by default. So the resolved tag is the highest `vMAJOR.MINOR.PATCH` among the 100 most recently created releases that are neither drafts nor prereleases, **and** it must be the one GitHub marks Latest. The run stops, before anything is built, and asks for an explicit `--previous` when `gh` cannot be run or fails, when its output is not the expected listing, when no release qualifies, when none is marked Latest, or when the Latest one is not the highest — a release published out of version order, or Latest moved by hand, makes "the previous release" a judgement the harness does not make. There is no fallback to a hardcoded tag. `--old-binary` without `--previous` is refused too: that binary's version is not enforced, so a resolved tag would label a build it was never checked against.

The resolved tag is the latest release, and that is the release previous to the branch only when the branch already contains it — the usual case, a branch from current `main`. A branch cut **before** the current Latest is paired with a release newer than its own base: one forked from `main` between `v0.40.2` and `v0.41.0` and run after `v0.41.0` shipped would face a `v0.41.0` daemon carrying changes the branch has never seen. For such a branch, pass `--previous` with the release it was cut after, or rebase it onto current `main` first, after which the default is right. To tell which case you are in, compare `git describe --tags --abbrev=0 --exclude '*-*' <branch>` — the nearest stable release tag reachable from the branch, once `git fetch --tags` has brought the tags down — with the tag `gh release view --json tagName --jq .tagName` prints, which is the Latest release: the same tag means the default is right, and an older one is the tag to pass.

The tag is resolved once per invocation, so `--direction both` runs both halves against the same release. The terminal prints it before the run starts, and the evidence file's **previous release** row records it with its source. `previous.rs` unit-tests the choice and every refusal against canned listings; nothing there calls `gh`.

## When a run finds a real break

Report it and do not paper over it. A failing tell, or a missing mismatch prompt, is the harness saying the branch and the previous release did not interoperate — which is precisely the question rule 12 asks, and a `FAIL` here is the most valuable outcome a run can have.
