# The card actions editor

PRD #2374's decision of 2026-11-24, shipped with issue #2399 on PR #2491, lets the desktop app add, change, hide and remove card actions instead of the user editing `[catalog]` by hand. The user-facing description is in [`docs/desktop/agent-cards.md`](../desktop/agent-cards.md#the-card-actions-editor). This page is for whoever changes the request, the writer or the editor.

## The request

The daemon reads the user config of the machine it runs on, so for a remote daemon "the catalog" is that machine's file. The editor therefore goes through the daemon (CLAUDE.md rule 18), with one request:

- capability `agent-cards-catalog-edit` (`CAP_AGENT_CARDS_CATALOG_EDIT`), advertised on every platform;
- `AttachRequest::CardCatalogEdit { edit: Option<CatalogActionEdit> }`, wire op `card-catalog-edit`; no `edit` is a read that writes nothing;
- `AttachResponse.card_catalog_edit: Option<EditableCardCatalog>`, the catalog after the edit, or as read.

Both are additive and the request is withheld by `DaemonClient::card_catalog_edit` unless the `Hello` on the same connection named the capability and `hello-follow-on`, so there is no `PROTOCOL_VERSION` bump, no `.breaking.md` and no `CONTRACT_BREAKS` entry. An older daemon is sent nothing; the desktop shows its editor read-only.

`CatalogActionEdit` is tagged by `kind`: `add` and `update` carry a `CatalogActionInput`, `remove`, `hide` and `restore` carry a `name`. `update`, `remove`, `hide` and `restore` may also carry `base` (re-review N5): the `EditableCatalogAction` of that name as the editor last read it, or `null` when it read none. With a `base`, `apply_action_edit` compares it with the file's action of that name (as `editable_catalog` lists it, `hidden` and `overridden` included) and refuses the edit, writing nothing, when they differ, with a reason that names Refresh. A missing `base` (an app from before it) is not checked, and a daemon from before it ignores the key (the variants do not deny unknown fields), so the field is additive under `serde(default)` and moves no `PROTOCOL_VERSION`. `CatalogActionInput` has `deny_unknown_fields`, so a `path`, a `command` or any key a `[[catalog.actions]]` entry may not carry fails to parse, and the daemon answers its generic malformed-request refusal. An unknown `kind` fails the same way.

| edit | what it writes | refused when |
| --- | --- | --- |
| `add` | a new `[[catalog.actions]]` entry | the name is a deck default's or an existing user action's; the catalog already holds `MAX_CATALOG_ACTIONS` |
| `update` | replaces the user entry of that name in place (its keys keep their comments); for a deck default, writes a same-name override and takes the name out of `remove` | the name is neither a default nor a user action |
| `remove` | drops the user entry | the name is a default (hide it instead) or no user action |
| `hide` | puts a default's name in `catalog.remove` and drops any override | the name is not a default |
| `restore` | takes a default's name out of `remove` and drops any override | the name is not a default |

Every value is validated by the catalog's own `parse_action`, the code that reads the file: name syntax, reserved names (`open`, `reply`, `close`, `close-keep-worktree`, anything starting `question`), required description and prompt, length limits (`MAX_DESCRIPTION_CHARS`, `MAX_CATALOG_LABEL_CHARS`, `MAX_PROMPT_CHARS`), control characters (a prompt may hold line breaks and tabs, nothing else may), icon syntax. A refusal's reason names the field or the name at fault.

## The writer

`card_catalog::apply_action_edit` edits the raw TOML with `toml_edit`, as `config::merge_dashboard_config` does, touching only `[[catalog.actions]]` and `catalog.remove`: every other setting and table, the catalog's fields and the comments are kept. Within an entry it updates, a key the form sets keeps its place and comment, and a key the form leaves unset is kept too when keeping it changes nothing `parse_action` reads — `always = false # why`, `placement = "card"`, a `label` equal to the default — so a commented default survives an edit of the prompt (issue #2399 review 7); a key that would change the action is dropped. After the edit it resolves the result and refuses it when it would add a catalog problem the file did not already have, when the edited action would not be the one in effect, or when the file would be larger than the reader reads (`MAX_USER_CONFIG_BYTES`, 1 MiB). A file that is not valid TOML is refused; there is nothing to merge into.

`card_catalog::edit_user_catalog_at` reads the file, applies the edit and writes it through `config::write_config_strictly` (issue #2399 review 1, audit 2–5):

- **The read.** `read_user_config` resolves the path's link chain once (`config::resolve_symlink_chain`) and opens the file it leads to with `O_NONBLOCK | O_NOFOLLOW`, so a FIFO with no writer cannot hold the editor's mutex, and a link put at the end of the chain after it was resolved is refused (`ELOOP`). The open handle must be a regular file of at most `MAX_USER_CONFIG_BYTES`, read capped, UTF-8. A `NotFound` is an absent config only when `config::config_not_found_verdict` agrees: a dangling link at the path, or a folder above it that is one, is a reason, not a first run. The card reader (`resolve_from_user_config_at`) uses the same read.
- **The lock** (re-audit 2, final review F2, final audit A3 and section 2). An edit holds `config::lock_config_edit_by`, an advisory `flock` on `.dot-agent-deck-config.lock` beside the resolved config, from before its read until the rename; `DashboardConfig::save_to`, `config set`'s save, takes the same lock around its read, merge and save. The lock file is opened `O_NOFOLLOW | O_NONBLOCK`, created `0600` when missing, and never `chmod`ed, `chown`ed, replaced or deleted. An existing one is fstat'ed on the open handle and used only when it is a regular file owned by the daemon's effective user, with no group or other permission bits and a link count of 1 (`config::lock_file_unsafe`, Unix; outside Unix only the regular-file test applies). `lock_config_edit_by` sorts what it cannot use into three `ConfigLockProblem`s, and the two writers treat them differently:

  | category | when | catalog editor | `config set` |
  | --- | --- | --- | --- |
  | `Busy` | another writer held it until the deadline | refuses, "try again" | refuses, "try again", exit 1 |
  | `Unsafe` | an entry is there that fails the rule above, or that cannot be opened (a link, `ELOOP`; a file this user may not open) | refuses, naming the lock file and the reason | refuses, naming the lock file and the reason |
  | `Unavailable` | no entry is there and none can be created, or the fstat or the `flock` itself fails (a file system that cannot lock) | refuses | keeps its existing writer, `write_config_atomically`, and saves unlocked, as it did before the lock |

  The editor's bound is one deadline per request, `CONFIG_LOCK_WAIT` (3 s, well inside the desktop's 15 s round trip) from when `edit_user_catalog_at` starts: it waits for its turn on the in-process mutex (`edit_turn_by`, polling `try_lock`) and then for the file lock against that same deadline, so a request queued behind one that is waiting for a held lock is answered busy ("try again") instead of waiting out the first one's wait and then its own; a read that cannot have its turn in time is answered busy too. `config set`'s wait starts when it asks for the lock. Only those two waits are bounded: reading, writing, syncing and renaming the files have no deadline, and the polling can overshoot the deadline by a poll interval (20 ms) plus scheduling. The desktop's own timeout does not cancel the daemon's blocking task. A config whose folder does not exist yet is locked once the edit makes the folder; the last check then confirms there is still no file. Outside Unix `File::try_lock` is `LockFileEx`, and the rest of this list is Unix-only where it says so.
- **The save.** `write_config_strictly` is `write_config_atomically` without its fall-backs: where `config set` would write in place (a hard-linked file, an owner or group the swap would change, a folder that takes no temp file, a rename the file system refuses) it refuses and leaves the file as it was. Before anything is written it refuses a folder on the config's path that another user can change (`folder_others_can_change`, Unix; re-audit 5, final audit A2): any folder that is group- or world-writable without the sticky bit, or owned by someone other than this user and root. It resolves the configured path itself, one component at a time from the root (a relative path from the current folder), following each link where it meets it, in a folder component or in the final file's own chain, and applying `..` to the folder reached so far (final audit A2, round 4). A judged folder is judged with its parents, up to `$HOME` (as named or as resolved) for a folder inside it, and up to the root otherwise. Judged: the folder the final file is in, whether the file exists or not and wherever that folder is (final audit A2, round 5, C1); every folder holding a link it follows, at any depth; and every other folder it looks a name up in, except a folder strictly above `$HOME` that the walk passes through on its way to a target inside `$HOME`, which is judged only where it holds a followed link or holds the final file. So with `$HOME` at `team/alice` and `team` `0770`, `team/config.toml`, an absent `team/new.toml` and `../config.toml` from the home are each refused naming `team`, while `$HOME/config.toml` is not refused for `team`. So `$HOME/shared/alias/config.toml` with `shared` `0770` and `alias -> $HOME/private` is refused naming `shared`, and so are `$HOME/outer/config.toml` with `outer -> $HOME/shared/alias` (the link inside the expansion) and `$HOME/via-hop.toml -> $HOME/shared/hop.toml -> $HOME/private/config.toml` (a hop of the file's chain). It refuses a path whose walk follows more than 40 links (a loop among them), a link it cannot read, and an entry it cannot inspect; the final file may be absent, a folder before it may not. The error names the folder and the reason, and the user page tells the user to follow it rather than restating this rule. Then its write probe (`probe_for_write`; re-audit new 1) opens the target `O_WRONLY | O_NONBLOCK | O_NOFOLLOW`, so a FIFO put in its place with no reader fails at once (`ENXIO`) instead of holding the editor's mutex, requires a regular file on the handle, and requires the handle's `FileStamp` — device, inode, mode, uid, gid, link count — to be the one the read took (re-audit new 3). It creates the temp file beside the target resolved at read time with mode `0600` at the exclusive `O_CREAT | O_EXCL` open (final audit A1: a `chmod` after the open would leave a descriptor someone opened in between able to read the body), writes and syncs it, runs the caller's last check, gives it the mode the file had when read — for a config the editor creates, `0600`; the process umask is never changed, since the daemon is multithreaded — renames, then syncs the folder (best effort; the rename already happened, and a failed folder sync is not reported). Every `Err` means the file was not replaced. `config set` keeps `write_config_atomically` and its fall-backs.
- **The last check** (`still_as_read`), run after the temp file is written and before the rename: the path still resolves to the same target, the target's folder has the same device and inode, and the file has the same `FileStamp` and bytes as when read — or, when there was no file, there is still none. A change visible when it runs is refused rather than overwritten: a hand edit or another writer that takes no lock, a `chmod`, a new hard link.

**What is left open, on purpose.** The lock orders the deck's own writers; an editor that takes no lock (a hand edit, an older deck) is caught only by the last check, and one that saves between that check and the rename is not caught. The folder check judges the path by name when the save starts: a folder made writable by others, or swapped, after it is not caught, and the create, rename and cleanup still resolve the path by name rather than through a descriptor pinned to the vetted folder (descriptor-relative `openat`/`renameat` was considered and not taken: the check refuses a path on which another user can change, when the save starts, a folder the walk above judges, and an owner-controlled path is not a cross-user attack). Outside Unix there is no folder check and no write-probe flags, and every file has the same stamp, so the bytes are the comparison.

A file it cannot read is refused for an edit and left byte for byte; a read still answers, with the problem in `errors`. A missing file and its folder are created by an edit. One process-wide mutex serializes this function's cycles within one daemon, taken against the request's deadline (above). The daemon passes `config::user_config_path()`, never a path from the client, runs the call on a blocking task, and forgets its cached catalog after an edit, so the next card read resolves the new file whatever its modification time says. `CardStore::forget_catalog` bumps a generation, and a catalog read that began before the bump is not cached (`catalog_from` reads again, a few times at most), so a read of the old file finishing after the write cannot put it back (review 4). Nothing in the request runs a command.

`editable_catalog` lists the deck defaults in catalog order (a hidden one with the deck's own values), then the user's own actions in file order; `source` is `default` or `user`, and `default`, `overridden` and `hidden` say the rest.

## The desktop

- Tauri command `agent_card_catalog_edit { deckId, edit|null }`, one deadline (`DECK_REPLY_TIMEOUT`) for reaching the deck and the exchange. A refusal is the daemon's reason as given, and nothing was written; a daemon without the capability answers `CARD_CATALOG_EDIT_UNSUPPORTED`; the exchange runs in two steps against that deadline, `DaemonClient::card_catalog_edit_connection` (the connect and the `Hello` on the request's own connection, nothing of the edit written) and then `CardCatalogEditConnection::send`. A failure, or the deadline running out, in the first step says nothing was saved; an edit that failed or ran out of time in the second, once it was being written, carries `CARD_CATALOG_EDIT_MAY_HAVE_SAVED` (PR #2491 review, Qodo 10). The TS bridge marks that failure `outcome: "unknown"` (a vitest holds the two constants to one text), and the editor then says the change *may have been* made, keeps the form, and reads the list once — never repeating the edit (review 8). Transport tests sit beside the batch ones in `desktop/src-tauri/src/restart_binding_tests.rs`.
- The cards snapshot's `catalogEdit` carries the capability, as `batch` does. The editor (`useCardActionsEditor`, `AgentCardActionsEditor`) is bound to one daemon (PR #2491 decision 2026-11-25): each daemon section's ⋯ menu (`MoreMenu`, `daemon-more`) offers **Card actions** while `offeredFor(deckId)` says that daemon's cards are on the Dashboard, and it opens the editor on that daemon, titled "Card actions: <daemon>", with no Daemon picker; voice's `open_card_actions_editor` names the daemon with an optional `deck` (`preselectDeckId`). `openCardActionsEditor(undefined)` opens the only daemon showing cards and, with several, answers `CardActionsWhich` (the sentence and the daemons), which the registry entry hands to the voice panel's `askVoiceChoice`: the panel offers the daemons as the ordinary numbered `param_ambiguous` choice ("Which daemon?") of the row being dispatched, and the answer runs the row again with the chosen `deck_ref`; with no panel to ask (or a confirmation open), the sentence is the refusal. A spoken add, edit or removal with the editor closed opens it the same way, and with several daemons is refused with that sentence. While its daemon is off the Dashboard the editor is not drawn, and when that daemon comes back it loads its list (review 5); it never moves to another daemon by itself. A read or an edit answering after the editor moved to another daemon (closed and opened from another ⋯, or opened on another daemon by voice) is dropped (a read sequence number), and moving closes an open form, so nothing typed for one daemon is saved to another. Within one daemon (re-review N1) an applied write answer bumps `writeEpoch`, and a read that began before it is dropped; each reading-again bumps `rereadSeq`, and only the newest one's answer counts. Each form carries a generation; a Save's answer changes only the form it was sent from, and while a Save is under way the form's fields are locked and no other form opens (review 6). **Refresh** reads the list again keeping the form, and moves an open form's `original` (the `base` its Save sends) to the action as just read. The reading-again after Refresh or after an edit whose answer was lost has its own line (`agent-card-actions-editor-reread`, re-review N3): under way and read (said only after a lost answer, and "read again" only once a read answered) or failed with its reason, whatever error the form shows. The removal's confirmation is its own dialog on the overlay stack (`useInertBackground`), so the editor behind it is inert while it is open (review 13).
- The desktop names `dot_agent_deck::card_catalog`'s wire types; linkage-check rule 12 allows the module, with the argument in `desktop_project_boundary.rs`.
- The fixture bridge answers the editor for the `cards=tree` scene from `createFixtureCardCatalog`, the deck's two defaults, applying edits for the session (Playwright `desktop/agent-cards/061`, screenshot scene `agent-cards-actions-editor`).

## Icons

The app draws card action icons from a curated set of the lucide icons it already bundles, keyed by the catalog's `icon` name (`desktop/src/lib/cardIcons.tsx`, `CARD_ICON_NAMES`); the editor's picker offers exactly that set. The daemon validates only the icon's syntax, so a catalog may name an icon a newer app has; this app draws its generic icon for it. A card draws up to `CARD_ICON_LIMIT` (3) icons, then `+N`, in a row of their own at the card's bottom (`agent-card-foot`), right-aligned, sharing the line with the roll-up when the card has one (issue #2399 review 2). Two earlier placements failed the maximum-content case — three icons, `+N`, a long name, Needs you, the tree toggle and Close on a 224-pixel card: beside Close in the header they cut a root's name to two characters, and at the end of the status line they pushed the status out of its button. The bottom row is drawn, empty, on every card, so a card's height never depends on its actions; Playwright `desktop/agent-cards/076` measures that case at 375 and 1440 px. An action whose catalog `placement` is `detail` draws no icon (`cardIconActions`); `card` and `compact` draw one (review 11). The form offers the two choices as Show on the card and Only in the Card tab, and keeps an existing `compact` unless the other is picked.

The card's icons and the batch buttons are `ActionTipButton`s (`desktop/src/components/ActionTipButton.tsx`). Hover and keyboard focus both draw the text as a `role="tooltip"` portalled to `document.body`, positioned `fixed` from the button's box so no card's `overflow` clips it; the same text is always the button's accessible description, in a hidden element also portalled out of the card (so it is never part of the card's text), and the button carries it as `data-tip` for tests. There is no native `title`, which would draw a second tooltip. A disabled action is `aria-disabled`, not `disabled`: a native disabled button leaves the Tab order, and with it the only keyboard route to the reason. Its press does nothing.

The hover quotes at most 1,200 shown characters of the prompt (`hoverPromptText`), cutting only between segments or inside plain text, so a marker such as `⟦U+200B⟧` is quoted whole or not at all. An icon whose hover is cut does not send on a press, whatever its `confirm`: it opens the review step with the whole text (`hoverCutsPrompt`, audit 1).

The tooltip is sized from its text (re-review N2, re-audit new 2): `tipLayout` measures a hidden copy with the tooltip's class at the width it will have, then draws it below the button when it fits there, above when it fits there, or on the side with more room, with `max-height` capped to that room and `max-width` to the window's. When it fits on neither side, however few characters it has — eighty line breaks count as much as length — it ends with `TIP_CUT_NOTE` on its own line (drawn whole when the window leaves the tooltip room for that line), and the press tells its caller `{ whole: false }`; the card icon then opens the review as the character cut does (Playwright `desktop/agent-cards/080`). While the tooltip is shown it is measured again when its text changes, on a window `resize`, on any `scroll` (captured, so a scrolling container counts) and, where `ResizeObserver` exists, when the button's size changes, updating both its geometry and its cut state (final review F1, Playwright `082`). The press answers `whole: true` only when the press-time measurement fits **and** the tooltip was not drawn cut at any point since it was last shown (final audit A4, Playwright `083`): a cut tooltip followed by a larger window does not turn the press into a direct send, because nothing says the user read the text the redraw revealed. jsdom has no layout, so every tooltip fits there. Both cuts are safeguards for pressing the icon: a spoken `run_card_action` for a catalog action with `confirm = false` still sends directly (the catalog-direct-send policy in `commands.toml`), and moving the check onto voice would mean moving it into the shared action path.

On a deck whose daemon does batches every card carries its checkbox (PR #2491 review: there is no Select toggle), so **Needs you** is its bell alone on every card (`is-compact`; its `title` and a visually hidden "Needs you" stay) and a root's name keeps the 48 px `076` requires without the checkbox (re-review N6, Playwright `081`).

The batch confirmation groups the included agents by exact text alone; each agent's row keeps its own source badge (review 9).

## Voice

`open_card_actions_editor`, `add_card_action`, `edit_card_action` and `remove_card_action` are voice rows (the last two take a `card_action` param, the action's label as said; the first an optional `deck`, a `deck_ref` resolved as the New agent dialog's Daemon field is and passed as `preselectDeckId`, which replaced the retired picker's `choose_card_actions_daemon` row, PR #2491 decision 2026-11-25). Since issue #2399 review 12, so are the choices that write nothing: `refresh_card_actions`, `choose_card_action_icon` (a `filter_text`, the icon's name as said, matched by `cardIconByName`: the name, its words joined by dashes, or the one icon whose name holds every word) the two checkboxes, one row per state (`ask_before_sending_card_action` / `send_card_action_without_asking`, `offer_card_action_on_every_card` / `offer_card_action_when_agents_choose`) so a repeated phrase never toggles a box back, and, since re-review N4, the Placement choice the same way (`show_card_action_on_the_card` / `show_card_action_only_in_the_card_tab`; "on the card" keeps a file's `compact`). The checkboxes and the Placement select dispatch the entry for the state they are set to. Every write is `no_voice`: `saveCardAction`, `confirmRemoveCardAction`, `hideCardAction`, `restoreCardAction`, so a misheard word never becomes text an agent is sent. `desktop/agent-cards/060` fails when one of the editor's registry entries has neither a row nor a reason, and `075` drives the new rows. A spoken edit or removal said while the editor's list is not read yet (the editor closed, or still reading) waits for it: `editCardAction` and `removeCardAction` then answer a promise, which the voice entry reports through `reportPending`, settled with the form or confirmation opened, or with why not: the list names no such action, a save is under way, the read failed, or the editor was closed or moved to another daemon first. On a daemon that did not advertise the editor it is refused at once and nothing waits (PR #2491 review, Qodo 3; `desktop/agent-cards/084`). The text fields and the icon grid's search box are listed in linkage-check rule 14's control-site ratchet. Pressing a card's icon is the existing `run_card_action` row. Every editor row has a `card-actions-editor-*` phrase fixture, run against the real default backend in `voice_desktop_phrases_001` (lane 2, quarantined under #2138, so run with `--ignored`).

## The TUI

The TUI has no cards view, so it has no editor; its users edit `[catalog]` in the file, which `dot-agent-deck config set` keeps with its comments.
