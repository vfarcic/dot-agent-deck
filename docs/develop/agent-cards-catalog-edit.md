# The card actions editor

PRD #2374's decision of 2026-11-24, shipped with issue #2399 on PR #2491, lets the desktop app add, change, hide and remove card actions instead of the user editing `[catalog]` by hand. The user-facing description is in [`docs/desktop/agent-cards.md`](../desktop/agent-cards.md#the-card-actions-editor). This page is for whoever changes the request, the writer or the editor.

## The request

The daemon reads the user config of the machine it runs on, so for a remote daemon "the catalog" is that machine's file. The editor therefore goes through the daemon (CLAUDE.md rule 18), with one request:

- capability `agent-cards-catalog-edit` (`CAP_AGENT_CARDS_CATALOG_EDIT`), advertised on every platform;
- `AttachRequest::CardCatalogEdit { edit: Option<CatalogActionEdit> }`, wire op `card-catalog-edit`; no `edit` is a read that writes nothing;
- `AttachResponse.card_catalog_edit: Option<EditableCardCatalog>`, the catalog after the edit, or as read.

Both are additive and the request is withheld by `DaemonClient::card_catalog_edit` unless the `Hello` on the same connection named the capability and `hello-follow-on`, so there is no `PROTOCOL_VERSION` bump, no `.breaking.md` and no `CONTRACT_BREAKS` entry. An older daemon is sent nothing; the desktop shows its editor read-only.

`CatalogActionEdit` is tagged by `kind`: `add` and `update` carry a `CatalogActionInput`, `remove`, `hide` and `restore` carry a `name`. `CatalogActionInput` has `deny_unknown_fields`, so a `path`, a `command` or any key a `[[catalog.actions]]` entry may not carry fails to parse, and the daemon answers its generic malformed-request refusal. An unknown `kind` fails the same way.

| edit | what it writes | refused when |
| --- | --- | --- |
| `add` | a new `[[catalog.actions]]` entry | the name is a deck default's or an existing user action's; the catalog already holds `MAX_CATALOG_ACTIONS` |
| `update` | replaces the user entry of that name in place (its keys keep their comments); for a deck default, writes a same-name override and takes the name out of `remove` | the name is neither a default nor a user action |
| `remove` | drops the user entry | the name is a default (hide it instead) or no user action |
| `hide` | puts a default's name in `catalog.remove` and drops any override | the name is not a default |
| `restore` | takes a default's name out of `remove` and drops any override | the name is not a default |

Every value is validated by the catalog's own `parse_action`, the code that reads the file: name syntax, reserved names (`open`, `reply`, `close`, `close-keep-worktree`, anything starting `question`), required description and prompt, length limits (`MAX_DESCRIPTION_CHARS`, `MAX_CATALOG_LABEL_CHARS`, `MAX_PROMPT_CHARS`), control characters (a prompt may hold line breaks and tabs, nothing else may), icon syntax. A refusal's reason names the field or the name at fault.

## The writer

`card_catalog::apply_action_edit` edits the raw TOML with `toml_edit`, as `config::merge_dashboard_config` does, touching only `[[catalog.actions]]` and `catalog.remove`: every other setting and table, the catalog's fields and the comments are kept. Within an entry it updates, a key the form sets keeps its place and comment, and a key the form leaves unset is kept too when keeping it changes nothing `parse_action` reads — `always = false # why`, `placement = "card"`, a `label` equal to the default — so a commented default survives an edit of the prompt (issue #2399 review 7); a key that would change the action is dropped. After the edit it resolves the result and refuses it when it would add a catalog problem the file did not already have, when the edited action would not be the one in effect, or when the file would be larger than the reader reads (`MAX_USER_CONFIG_BYTES`, 1 MiB). A file that is not valid TOML is refused; there is nothing to merge into.

`card_catalog::edit_user_catalog_at` reads the file, applies the edit and writes it through `config::write_config_strictly` (issue #2399 review 1, audit 2–5):

- **The read.** `read_user_config` resolves the path's link chain once (`config::resolve_symlink_chain`) and opens the file it leads to with `O_NONBLOCK | O_NOFOLLOW`, so a FIFO with no writer cannot hold the editor's mutex, and a link put at the end of the chain after it was resolved is refused (`ELOOP`). The open handle must be a regular file of at most `MAX_USER_CONFIG_BYTES`, read capped, UTF-8. A `NotFound` is an absent config only when `config::config_not_found_verdict` agrees: a dangling link at the path, or a folder above it that is one, is a reason, not a first run. The card reader (`resolve_from_user_config_at`) uses the same read.
- **The save.** `write_config_strictly` is `write_config_atomically` without its fall-backs: where `config set` would write in place (a hard-linked file, an owner or group the swap would change, a folder that takes no temp file, a rename the file system refuses) it refuses and leaves the file as it was. It writes the temp file beside the target resolved at read time, syncs it, runs the caller's last check, renames, then syncs the folder (best effort; the rename already happened). Every `Err` means the file was not replaced. `config set` keeps `write_config_atomically` and its fall-backs.
- **The last check** (`still_as_read`), run after the temp file is written and before the rename: the path still resolves to the same target, the target's folder has the same device and inode, and the file has the same device, inode and bytes as when read — or, when there was no file, there is still none. A save by `config set`, another daemon reading the same file or a hand edit between the read and the save is therefore refused rather than overwritten. It narrows the window to the time between the check and the rename; it is not a lock, and a writer that saves inside that window is not caught. There is no cross-process lock: the compare-and-swap covers writers that do not cooperate, which a lock would not.

A file it cannot read is refused for an edit and left byte for byte; a read still answers, with the problem in `errors`. A missing file and its folder are created by an edit. One process-wide mutex serializes this function's cycles within one daemon. The daemon passes `config::user_config_path()`, never a path from the client, runs the call on a blocking task, and forgets its cached catalog after an edit, so the next card read resolves the new file whatever its modification time says. `CardStore::forget_catalog` bumps a generation, and a catalog read that began before the bump is not cached (`catalog_from` reads again, a few times at most), so a read of the old file finishing after the write cannot put it back (review 4). Nothing in the request runs a command.

`editable_catalog` lists the deck defaults in catalog order (a hidden one with the deck's own values), then the user's own actions in file order; `source` is `default` or `user`, and `default`, `overridden` and `hidden` say the rest.

## The desktop

- Tauri command `agent_card_catalog_edit { deckId, edit|null }`, one deadline (`DECK_REPLY_TIMEOUT`) for reaching the deck and the exchange. A refusal is the daemon's reason as given, and nothing was written; a daemon without the capability answers `CARD_CATALOG_EDIT_UNSUPPORTED`; an edit whose answer was lost after it was sent, or that failed in a way that cannot say whether the daemon got it, carries `CARD_CATALOG_EDIT_MAY_HAVE_SAVED`. The TS bridge marks that failure `outcome: "unknown"` (a vitest holds the two constants to one text), and the editor then says the change *may have been* made, keeps the form, and reads the list once — never repeating the edit (review 8). Transport tests sit beside the batch ones in `desktop/src-tauri/src/restart_binding_tests.rs`.
- The cards snapshot's `catalogEdit` carries the capability, as `batch` does. The editor (`useCardActionsEditor`, `AgentCardActionsEditor`) lists the daemons whose cards are on the Dashboard, in its order, and starts on the local one (`deckKind: "local"`), wherever it is listed, else the first. When every daemon leaves the Dashboard the editor is hidden, and when one comes back it loads that daemon's list (review 5). A read or an edit answering after the daemon shown changed is dropped (a read sequence number), and changing the daemon closes an open form, so nothing typed for one daemon is saved to another. Each form carries a generation; a Save's answer changes only the form it was sent from, and while a Save is under way the form's fields are locked and no other form opens (review 6). **Refresh** reads the list again keeping the form. The removal's confirmation is its own dialog on the overlay stack (`useInertBackground`), so the editor behind it is inert while it is open (review 13).
- The desktop names `dot_agent_deck::card_catalog`'s wire types; linkage-check rule 12 allows the module, with the argument in `desktop_project_boundary.rs`.
- The fixture bridge answers the editor for the `cards=tree` scene from `createFixtureCardCatalog`, the deck's two defaults, applying edits for the session (Playwright `desktop/agent-cards/061`, screenshot scene `agent-cards-actions-editor`).

## Icons

The app draws card action icons from a curated set of the lucide icons it already bundles, keyed by the catalog's `icon` name (`desktop/src/lib/cardIcons.tsx`, `CARD_ICON_NAMES`); the editor's picker offers exactly that set. The daemon validates only the icon's syntax, so a catalog may name an icon a newer app has; this app draws its generic icon for it. A card draws up to `CARD_ICON_LIMIT` (3) icons, then `+N`, in a row of their own at the card's bottom (`agent-card-foot`), right-aligned, sharing the line with the roll-up when the card has one (issue #2399 review 2). Two earlier placements failed the maximum-content case — three icons, `+N`, a long name, Needs you, the tree toggle and Close on a 224-pixel card: beside Close in the header they cut a root's name to two characters, and at the end of the status line they pushed the status out of its button. The bottom row is drawn, empty, on every card, so a card's height never depends on its actions; Playwright `desktop/agent-cards/076` measures that case at 375 and 1440 px. An action whose catalog `placement` is `detail` draws no icon (`cardIconActions`); `card` and `compact` draw one (review 11). The form offers the two choices as Show on the card and Only in the overlay, and keeps an existing `compact` unless the other is picked.

The card's icons and the batch buttons are `ActionTipButton`s (`desktop/src/components/ActionTipButton.tsx`). Hover and keyboard focus both draw the text as a `role="tooltip"` portalled to `document.body`, positioned `fixed` from the button's box so no card's `overflow` clips it; the same text is always the button's accessible description, in a hidden element also portalled out of the card (so it is never part of the card's text), and the button carries it as `data-tip` for tests. There is no native `title`, which would draw a second tooltip. A disabled action is `aria-disabled`, not `disabled`: a native disabled button leaves the Tab order, and with it the only keyboard route to the reason. Its press does nothing.

The hover quotes at most 1,200 shown characters of the prompt (`hoverPromptText`), cutting only between segments or inside plain text, so a marker such as `⟦U+200B⟧` is quoted whole or not at all. An icon whose hover is cut does not send on a press, whatever its `confirm`: it opens the review step with the whole text (`hoverCutsPrompt`, audit 1).

The batch confirmation groups the included agents by exact text alone; each agent's row keeps its own source badge (review 9).

## Voice

`open_card_actions_editor`, `add_card_action`, `edit_card_action` and `remove_card_action` are voice rows (the last two take a `card_action` param, the action's label as said). Since issue #2399 review 12, so are the choices that write nothing: `choose_card_actions_daemon` (a `deck_ref`, resolved as the New agent dialog's Daemon field is and passed as `preselectDeckId`), `refresh_card_actions`, `choose_card_action_icon` (a `filter_text`, the icon's name as said, matched by `cardIconByName`: the name, its words joined by dashes, or the one icon whose name holds every word) and the two checkboxes, one row per state (`ask_before_sending_card_action` / `send_card_action_without_asking`, `offer_card_action_on_every_card` / `offer_card_action_when_agents_choose`) so a repeated phrase never toggles a box back. The checkboxes dispatch the entry for the state they are set to. Every write is `no_voice`: `saveCardAction`, `confirmRemoveCardAction`, `hideCardAction`, `restoreCardAction`, so a misheard word never becomes text an agent is sent. `desktop/agent-cards/060` fails when one of the editor's registry entries has neither a row nor a reason, and `075` drives the new rows. The text fields and Placement are listed in linkage-check rule 14's control-site ratchet. Pressing a card's icon is the existing `run_card_action` row. The new rows have no phrase fixtures yet: those run against a voice model with a credential.

## The TUI

The TUI has no cards view, so it has no editor; its users edit `[catalog]` in the file, which `dot-agent-deck config set` keeps with its comments.
