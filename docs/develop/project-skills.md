# Project-local skills, the former dot-ai mirrors, and where PRDs live

CLAUDE.md rule 13 is the policy: project knowledge lives in the repository, never in an assistant's global memory; the `.claude/skills/dot-ai-*` skills are project-owned now that syncing from `dot-ai` has stopped; and a new PRD lives in its GitHub issue. This page is the history and the measurements behind the last two, moved out of the rule by issue #905. In the paragraphs below, "this rule" means CLAUDE.md rule 13, "this file" means CLAUDE.md, and "rule 8" means CLAUDE.md rule 8.

## Why the mirrors could not be edited, and why they can now

**`.claude/skills/dot-ai-*` was not in-repo storage while it was a synced mirror, because a project-specific edit there got clobbered.** Those skills were vendored from the `dot-ai` project and overwritten wholesale by manual `Skill(s) [skip ci]` sync commits, which did not merge — they restored upstream's blob. This was measured, not feared: `04a3641` (2026-06-14) narrowed the release skill's review-wait step so it would stop hanging on inactive CodeRabbit, and `e94388d` (2026-06-19) reverted it **byte for byte** five days later (`index e5f1b69..b95d270`, the exact inverse of the edit).

**The syncing has stopped.** The last sync commit was `be9002ee` (2026-07-14), no workflow in the repository runs one, and the maintainer decided during PRD #1666 not to run another. So the `dot-ai-*` skills that remain — `dot-ai-changelog-fragment` and `dot-ai-request-dot-ai-feature` — are project-owned: edit or delete them like any other skill here. They keep the prefix as a record of where they came from. The same PRD deleted `dot-ai-manageKnowledge` and `dot-ai-manageOrgData`, whose camelCase names Pi refuses to load.

## Why the release flow and the PRD skills are forks

**That is why the release flow no longer lives there — twice over.** Issue #1052 forked the PR half out as the project-local [`pr-create`](../../.claude/skills/pr-create/SKILL.md), with `prd-full` following because it calls it. That mirrored copy had drifted into instructing agents to do the wrong thing here — wait for a reviewer that is not active, commit straight to a protected `main`, notify the user from a worker role — and none of it could be fixed in place. Renaming rather than adding was the point: a new skill beside the old one would have left two conflicting release procedures with no way to tell which governs. Issue #1089 then forked the tagging half out as [`tag-release`](../../.claude/skills/tag-release/SKILL.md), for a sharper version of the same reason: its Step 4 had *already* been rewritten locally by `b0a1cb4e`, three weeks after the last sync, and was sitting there waiting for the next one to delete it — the instruction that stops a released binary reporting `0.1.0`, whose absence costs a deleted remote tag.

**And the PRD skills followed, for the same reason** (issue #1591): `prd-create`, `prd-start`, `prd-next`, `prd-update-progress`, `prd-update-decisions`, `prd-close`, `prds-get` and `worktree-prd` are project-local forks, because they assumed the PRD is a `prds/` file, and an edit to the mirrors would have been reverted by the next sync. Each fork **replaced** its mirror rather than sitting beside it, as `pr-create` did, and changes only what depended on the file, so a later comparison with upstream stays small. Deleting a mirror stuck where editing one did not, and `prd_skills_015_each_fork_replaced_its_mirror` (`xtask/linkage-check/src/prd_skills.rs`) goes red if one comes back. With the syncs stopped that would take someone re-importing it by hand, but the test still earns its place: a returned mirror would sit beside its fork as a second, conflicting procedure for the same job, so delete the returned copy.

## Why a new PRD lives in its issue

**PRDs are the exception, and it is a trade rather than an oversight (issue #1591).** A new PRD lives in its GitHub issue: the body is the PRD — problem, solution, scope, decisions, milestones as checkboxes — and its progress notes, decision records and work log are issue comments. Nothing is written under `prds/`. The PRDs that already have a file there keep it, and `prds/done/` stays the archive of those; nothing was migrated. That gives up two things this rule otherwise wants: the plan is not in the clone, so it does not travel with the repository, and an issue body never passes the review a `prds/` file did on its way to `main`. What it buys is that creating, starting, updating and closing a PRD needs no commit — on a protected `main` (CLAUDE.md rule 8) each of those cost a branch, a PR, CI and an approval, which the maintainer decided on 2026-10-05 was too tedious to keep paying for a planning document. The review half is narrowed rather than waved away: [`prd-source.sh`](../../.claude/skills/prd-start/prd-source.sh) treats an issue body as a PRD only when a collaborator opened the issue, and the skills read the record from collaborator comments only. [`issue-prd.md`](../../.claude/skills/prd-start/issue-prd.md) has the layout. Knowledge that outlives a PRD — a convention, a gotcha, a rule — still belongs in this file or in `docs/develop/`, not in an issue.
