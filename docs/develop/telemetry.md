# Telemetry internals

How the deck's OpenTelemetry export (PRD #1741) decides two things the user page, [`docs/telemetry.md`](../telemetry.md), describes only by their result: what an `agent.operation` span says about a shell command, and which `codex` or `devin` the `PATH` shim adds to.

The design and measurements of the separate resource collector (PRD #1859) are in [The per-run resource collector](#the-per-run-resource-collector-prd-1859).

What each agent can report beyond these spans (tokens, cost, quota, outcomes), and the record and outcome taxonomy PRD #633 proposes from real runs, are in [Execution accounting](execution-accounting.md).

## From a command line to `deck.operation.program` and `deck.operation.word`

The classifier is `src/telemetry/operation.rs`. It does not parse shell syntax: it reads words that an allow-list matches, and any other word it reads declines the command, so the span carries neither program nor word. It reads the first line of the command, split on `&&`, `||`, `;` and `|` (`segments`) and into words on spaces and tabs only. The first segment that does more than set up the next is the one described: a segment running `cd`, `export`, `source`, `.`, `set` or `true` (`SETUP_PROGRAMS`) is skipped, and in front of the program so are `NAME=value` assignments and an `env`, `sudo`, `command`, `time` or `nice`, with the options each knows (`Options`) and their values (`time -f %e cargo test` is `cargo test`).

Every word read, from the start of the line up to and including the program's first non-option argument, must match the allow-list, or the command declines and no later segment is read:

- A **simple word** (`is_simple_word`) matches `^[A-Za-z0-9/._+:,@%-]+$`. So none of `$`, a backtick, a quote, `#`, `(`, `)`, `{`, `}`, `[`, `]`, `\`, `<`, `>`, `*`, `?`, `!`, `~`, `=`, `&`, `;`, `|` or whitespace other than the space and tab that end a word. The program, every word of a skipped setup segment, each wrapper option and option value, and each option before the first argument must be one; so must the first argument, which must also not start with `-` or `+`. An attached `--option=value` is not one, so `time --format=%e cargo test` declines.
- A **simple assignment** (`is_simple_assignment`) is `NAME=` and zero or more simple-word characters, `NAME` matching `^[A-Za-z_][A-Za-z0-9_]*$`. It may stand in front of the program, after a wrapper's options, and as an argument of a setup segment (`export X=1`).
- A wrapper option the wrapper's table does not know, as `env -S`, declines.
- For `sh`, `bash`, `zsh` and `dash` with `-c`, the script is either a simple word or one quoted word, `'…'` or `"…"`, with no quote, `$`, backtick or `\` inside (`unquote`); its inside is read by these same rules. Anything else declines. Since the inside holds no quote, a script nested in it is a single simple word, so nesting ends there. This is the one quoted word the classifier reads.
- A shell reading its script from standard input, as `bash -s` or a shell with no operand, sends only its own name, and its operands are not read: they are the script's arguments, not its text, so `bash -s '$X'` still sends `bash`. Its options are not exempt: each must still be a simple word, and an `-o` value too, so `bash -s -o 'pipefail'` declines. Exempting the operands is the other exception to the allow-list above.
- A program that is shell grammar rather than a command — a reserved word, declaration builtin or precommand modifier of a shell the classifier unwraps (`SHELLS`: sh, bash, zsh, dash), `eval` or `exec` (`UNSUPPORTED_PROGRAMS`) — declines the command, whether it is reached directly, behind a wrapper or inside a `-c` script: its operand is a name (`local x`, `foreach x (…)`), data (`case x in`, `repeat 3`) or a command of its own (`eval x`, `noglob x`), so it has no word to send. The list is taken from each shell's own documentation, and each part of it carries its source in the code:
  - POSIX sh's reserved words (Shell Command Language, section 2.4), which are also dash's: `!`, `{`, `}`, `case`, `do`, `done`, `elif`, `else`, `esac`, `fi`, `for`, `if`, `in`, `then`, `until`, `while`;
  - bash's, from `compgen -k` and the bash manual's "Reserved Words": `[[`, `]]`, `coproc`, `function`, `select`;
  - zsh's, from the "Reserved Words" section of its [Shell Grammar](https://zsh.sourceforge.io/Doc/Release/Shell-Grammar.html) documentation: `end`, `foreach`, `repeat`, `nocorrect` and the declaration words `declare`, `float`, `integer`, `local`, `readonly`, `typeset`;
  - the precommand modifiers from the same page that are not read as prefixes: `-`, `noglob`, `builtin` (bash's too).

  Two reserved words are deliberately not on it: `time` (bash and zsh) is read as the wrapper it is, and `export` (zsh) is skipped as a setup word (`SETUP_PROGRAMS`) when its words are simple. The punctuation words decline without the list, as words that are not simple (`!`, `{`, `[[`) or not command words (`-`), and are listed to keep it whole. `shell_reserved_words_name_nothing` names these words itself rather than reading `UNSUPPORTED_PROGRAMS`, so a word dropped from the list fails it.

Once the program is found, its basename is taken and goes through the shape filter. The first non-option argument is the word only when it is the program's first argument (`named`): an option before it may take it as its value (`sshpass -p <password>`, `mysql -u <user>`), and which options take one is not known for an arbitrary program, so `git -C dir status` and `cargo +nightly fmt` send their program and no word. The rule applies to the program described, not to the wrappers in front of it, whose option tables say exactly which options take a value, nor to a shell's script file, which follows options the shell's own table reads (`bash -e ci.sh` sends `ci.sh`). The word then goes through the shape filter and the wordless-program deny-list; the user page lists both, because they decide what can leave the machine. Words after the first argument are not read, so `cargo test 2>&1 | tail` is `cargo test`. A program on the deny-list is read up to its first argument like any other, and declines the same way (`grep --include=*.rs x` sends nothing); only then is its word dropped. When the program itself is not sent, its word is not sent either.

Codex reports a shell call as its arguments joined with spaces (`JOINED_ARGV_TOOL`), which loses where each argument ends. So for Codex the classifier (`classify_joined_argv`) keeps the program only, never a word, from the first word of the line, or, for `<shell> -c<flags> <script>`, the first word of the script. That word must be a simple word before its basename is taken: for `/bin/sh -lc #/private/x` or `WORKDIR=/private/x cargo test`, taking the basename first would send `x`. Only that word is checked, since no word after it is sent: `cargo 'x'` and `node -e '…'` send their program here, where the raw-command path declines them. It declines a program that sets up, wraps or is another shell (`cd`, `env`, `sudo` and the rest), and one of `UNSUPPORTED_PROGRAMS`, since the program it runs may be inside a later argument, and it never reads the arguments after the script.

## Which `codex` and `devin` the shim adds to

The shim (`src/telemetry/shim.rs`) decides what to add from the environment it runs in, so a program between the shim and the agent that changes that environment would make it decide from the wrong configuration. It therefore adds only to a program it recognises as the agent itself, judged on the file with symlinks resolved (`launcher_is_certain`):

- an ELF or Mach-O executable;
- for Codex only, `bin/codex.js` inside a `node_modules/@openai/codex` package, which is the `bin` entry of the package npm installs. This is a recognition heuristic, not authentication: any readable file at that canonical path is accepted, a hard-linked or modified copy included;
- a script under `/nix/store/` whose text, read in full up to 64 KiB, contains neither `HOME` (and so neither `CODEX_HOME` nor `XDG_CONFIG_HOME`) nor `OTEL_`.

Everything else declines: a script in any language outside those paths, a file it cannot read, a Nix store script larger than the limit. A recognised launcher is trusted not to change `CODEX_HOME`, `XDG_CONFIG_HOME`, `HOME` or an `OTEL_` variable after the shim has decided; a substituted or modified launcher that does gets the additions decided from the environment the shim saw. The Nix check reads the script's text for those literal names (`names_no_decision_variable`); it does not prove what the script does, so it misses a name the script computes or splits (`CODEX_HO""ME`, or a name assembled from parts) and a chained wrapper, a store script that runs another script which changes those variables. The user page says which installs are supported and what to do with a customised launcher. An earlier version classified scripts by their `#!` interpreter and declined only shells; a shell under another name and a Python wrapper both got through, which is why the rule is now an allow-list.

The e2e tests stand in for the agents in these forms: `telemetry/otlp/016` links a Python recorder from a fake `node_modules/@openai/codex/bin/codex.js`, and `telemetry/otlp/017` builds a small native `devin` with `cc` that runs the recorder.

## Switches the deck sets only when the user has not

The deck adds `CLAUDE_CODE_ENABLE_TELEMETRY`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER` and `OTEL_EXPORTER_OTLP_PROTOCOL` for Claude Code, and `DOT_AGENT_DECK_PI_TELEMETRY=1` for Pi, only when the agent's environment leaves each unset, and reads `OTEL_SDK_DISABLED` and the exporter and protocol selectors as opt-outs. The daemon reads its environment once into a map of UTF-8 strings (`config::process_env`), so a value that is not UTF-8 cannot be stored as it is; dropping it would read as unset and have the deck set the variable over the user's value. The variables in `config::SET_WHEN_UNREADABLE` are therefore kept as `config::UNREADABLE` instead: set, with a value no reader takes for `true`, `otlp` or an HTTP protocol. So the deck adds none of those switches, an unreadable `OTEL_SDK_DISABLED` counts as disabled (`config::sdk_disabled`), an unreadable selector declines its signal, and an unreadable protocol declines the deck's own export. Other variables with a value that is not UTF-8 are still left out. The shim does not rely on this: it adds nothing at all when an `OTEL_` or configuration-home variable is not UTF-8 (`exact_env`).

## Leftover Devin configurations

Each Devin configuration file is named `devin-<run>-<pid>.json`, for the Devin's process id. A daemon removes its runs' files when each run ends and at its shutdown. At its start it also sweeps files left by a daemon that crashed or was killed (`remove_leftover_config_files`), but the directory is shared by every daemon on the same state directory, so on Unix the sweep removes a file only when `kill(pid, 0)` reports `ESRCH` for the pid in its name; `EPERM` and any other error count as alive. The system can reuse an exited Devin's pid, which keeps that file until a later start. On other platforms the sweep still removes every such file.

## Querying the telemetry from Claude Code

The repository's `.mcp.json` declares Honeycomb's hosted MCP server for the US region (`https://mcp.honeycomb.io/mcp`), so a Claude Code session in this repo can query the shared Honeycomb environment that receives the deck's telemetry. The server is remote, so it starts no local process. The file holds no credentials: run `/mcp` once in Claude Code to sign in through the browser with your own Honeycomb account, and the Honeycomb team needs Honeycomb Intelligence enabled for the server to answer. A team in the EU region uses `https://mcp.eu1.honeycomb.io/mcp` instead. Of the agents the deck supports, only Claude Code reads `.mcp.json`; the others need the server added in their own configuration.

## The per-run resource collector (PRD #1859)

`dot-agent-deck-collector` is the second binary of the root package (`src/bin/dot-agent-deck-collector.rs`), with its pure-data core in `src/telemetry/collector/`. It is a separate process that reads `/proc`: nothing in the daemon, the protocol, the spawn path or either client knows it exists. The user page's [CPU, memory and disk per run](../telemetry.md#cpu-memory-and-disk-per-run) says what it sends and how to run it; this section is the design and the measurements behind it.

### Design

- **Attribution** (`aggregate.rs`). A process belongs to the run named by the `deck.run.id` in the first `OTEL_RESOURCE_ATTRIBUTES` entry of its `/proc/<pid>/environ`, decoded with the deck's own decoder (`telemetry::resource::parse_resource_attributes`). Failing that, it takes its parent's run in the same sample; failing that, it is unattributed and is looked at again every sample. Both kinds of attribution are sticky per `(pid, starttime)`, so a process that double-forks keeps its run, and a process that loses its parent keeps the run it inherited. Sticky means an environment that later names *no* run does not take a process out of its run; one that names *another* run does: every visible process's `environ` is read at every sample, so a process that keeps its pid and execs with another run's environment moves to that run from that sample on, its earlier credit staying with the run it left (`a_process_that_execs_into_another_run_moves_to_it`). Reading every environment costs about what reading every `stat` does: 3 ms per sample for the 100 processes of the dev box's user, against 2.7 ms for `stat`, 2.9 ms for `status` and 112 ms for `smaps_rollup` (Python, 20 rounds, 2026-10-25). That was measured against detecting an exec from `stat`'s `comm` or the `exe` link, which are cheaper but miss an exec of the same binary, the case of a shell that execs a shell with a new environment. The five other identity keys (`deck.pane.id`, `deck.agent`, `deck.role`, `deck.orchestration.name`, `deck.orchestration.id`) are copied from the run's oldest own-environment process; no other key from any process's environment is sent (`identity.rs`).
- **Users.** A run is keyed by `(deck.run.id, uid)` (`RunKey`), where the uid is the process's effective uid, the second value of the `Uid:` line of `/proc/<pid>/status` (`procfs::parse_effective_uid`, read by `reader.rs`). It is not the owner of `/proc/<pid>`: a process that calls `prctl(PR_SET_DUMPABLE, 0)` gets root-owned `/proc` files whatever user it runs as (on the 7.0 kernel of the dev box, `/proc/<pid>`'s own inode kept the user's uid while `environ`, `status`, `stat` and `smaps_rollup` in it turned root's), which would admit another user's process to a root collector's default filter and merge users under `--all-users`. A process inherits a run only from a parent of its own uid, and a process whose uid changes loses its sticky attribution. A process of the collector's own uid whose `environ` it may not read (`EACCES`/`EPERM`: a non-dumpable one) is kept as `Environ::Unreadable`, which names no run of its own: it keeps a run it was already attributed to (both kinds of attribution are sticky), and otherwise can only inherit. To a collector that is not root its `smaps_rollup` is unreadable too, so it has CPU and no PSS (`a_non_dumpable_process_of_the_own_user_is_read_as_that_user`, whose child acknowledges a successful `prctl` over a pipe before the parent reads it; a reader of the same user without `CAP_SYS_PTRACE` is refused that child's environment, while root may be refused it or not (root without the capability read it in the RWX sandbox), so as root, or holding the capability, the test expects whatever a direct read gives). Another user's unreadable process is still left out. By default the reader keeps only processes of the collector's own effective uid; `--all-users` keeps every readable one and adds `deck.run.uid` to run resources, because two users' runs with one id are then two series. Attribution trusts labels the process controls: any process can name any run id of its own user, so the key stops cross-user merging, not same-user forgery.
- **Identity parsing is bounded.** A process's `OTEL_RESOURCE_ATTRIBUTES` is read from every visible process at every sample, so `run_identity` refuses a value over 16 KiB, decodes it in one pass keeping only the six keys (with the deck decoder's rules, last duplicate winning), and leaves out a value over 256 decoded bytes rather than truncating it, so two long run ids cannot collapse into one. The quadratic duplicate search of `parse_resource_attributes` is not on this path.
- **CPU** is credited per process, `utime + stime + cutime + cstime`: its whole total at first sight, its increase afterwards; and a process that vanished has its last-seen total taken back from its nearest surviving ancestor, capped by that ancestor's increase in children time, because the ancestor reaped it and its `cutime` now holds all of it. That is why in-tree short-lived work matched the cgroup to within 0.1 s at every cadence tested in the workloads below, apart from one +4% double count from a non-atomic sample.
- **Memory** is `smaps_rollup`'s `Pss_Anon`, `Pss_File` and `Pss_Shmem`, sent as three points of one gauge rather than one sum, because only `Pss_Anon` tracks a cgroup's own memory (below).
- **Read order** per sample (`reader.rs`): every `stat` first, then each process's `status` and environment, then `smaps_rollup`, then the `cwd` link of run-attributed processes, which names the directory without looking it up on its filesystem. The reader takes its pids as an argument, so an in-crate test reads one process it started (`a_cleared_reparented_process_is_counted_unattributed` double-forks a burner with a cleared environment and checks it lands unattributed with CPU and anonymous PSS, which the L2 test on a shared box cannot isolate from other unattributed work; its launcher holds the burner as an unreaped child until the test has the burner's pidfd, so the guard that kills the burner on the way out cannot kill a process that took over its pid). Reading every `stat` in one pass keeps short the window in which a child reaped mid-sample is counted twice.
- **Worktrees** (`disk.rs`). A process's worktree is the nearest ancestor of its `cwd` holding a `.git` that git would take for a checkout's (`is_git_entry`): a directory, or a regular file whose contents start with `gitdir: ` (a linked worktree or a submodule), opened with `O_NOFOLLOW | O_NONBLOCK` and checked as opened. A `.git` symlink, wherever it points, and any other entry make no checkout (`a_git_symlink_or_a_stray_git_file_makes_no_checkout`), and the walk's nested-repository check applies the same rule, so a directory holding a `.git` symlink is walked as part of its worktree; `deck.worktree.id` is the first 16 bytes of SHA-256 over its canonical path, a pseudonym rather than a secret (`worktree-id` computes it for a user). It is unsalted by decision: the promise is that paths are not sent, not that ids cannot be linked, so a guessed path's id can be recognised and one path has one id on every machine. A machine-local HMAC key was considered and not built. **A run's worktree is decided once** (`otlp::RunWorktrees`): at the first sample that sees the run, as its oldest member that has one, or as none when no member is in a worktree then. That decision, "none" included, holds when that process exits, another changes directory, or a member enters a worktree later, and through the run's terminal report, so a run's live and terminal points have identical resource attributes and stay one series. Deciding "none" for good trades the worktree id of a run that starts outside a repository for a series that never changes identity mid-run. The same holds when discovery fails transiently at that first sample (a `cwd` that cannot be read, or a toplevel that cannot be canonicalised then): the run keeps "none" for its life. It is forgotten once the terminal request is built.
- **Discovery is off the sampling path** (`discovery.rs`). Finding a working directory's toplevel touches its filesystem (`lstat` of each ancestor's `.git`, reading a `.git` file, `canonicalize`), so on a stalled NFS mount it can block, and on the sampling thread that stopped CPU and memory reports for every run, even with `--disk-interval 0`. Lookups now run on `discovery::WORKERS` = 2 threads with at most `discovery::MAX_OUTSTANDING` = 64 queued or running, bounded as the walks are: a directory has at most one lookup outstanding, which keeps its place until it returns, so a stalled one holds one worker and one place while the other worker answers the rest (`a_stalled_lookup_holds_up_only_its_own_answer`). Two stalled at once hold both workers, and until one returns no directory gets a new answer: runs already decided keep their worktrees, and a run first seen meanwhile is decided as none. CPU and memory are reported for every run throughout. Each directory in use is looked up again at every sample, those a new run waits for first, then never-answered ones, then the oldest, and its last answer stands until the new one arrives. **Pending lookups and the first-sight decision:** a sample that sees a run for the first time waits up to `FIRST_SIGHT_WAIT` = 1 s for the lookups of that run's members' directories, then decides the run's worktree from the answers it has; a lookup still outstanding then counts as no worktree, exactly as a failed one does, and the run keeps "none" for its life. That keeps the decision once-only, so a run's points never change identity, at the cost of a run that starts on a directory whose lookup stalls past a second losing its worktree id. Waiting longer would delay every run's report for that sample; deciding later would send the run's first points without the worktree id its later points carry. The wait is on the blocking thread the sample runs on, and only for runs not decided yet, so a stalled directory delays a sample by at most one second, once for each new run that needs it. A new run's directory that missed the bound is queued as places free during that second, as `look_up_all` does, so a first sample with more than 64 new directories still decides each one whose lookup answers in time (`a_first_sight_wait_refills_past_the_bound`, `every_new_run_gets_its_worktree_past_the_lookup_bound`); only one still outstanding at the deadline is decided as none. The second is counted from when the lookups start, after the sample's `/proc` reads and `cwd` links, which on a busy host can take that long themselves (`the_first_sight_wait_starts_after_a_slow_process_read`); the final sample's is also cut to its walk wait. `--once` has no later sample to look the rest up in, so `Discovery::look_up_all` queues each directory once as room frees under the bound, and waits for every one, within its 600 s deadline (`looking_up_all_refills_past_the_bound`).
- **The walk** sums `st_blocks × 512` per inode once and skips nested repositories. It traverses through open directory descriptors, not paths: the root is opened with `openat2(RESOLVE_NO_SYMLINKS)`, each subdirectory relative to its parent's descriptor with `openat2(RESOLVE_NO_SYMLINKS | RESOLVE_BENEATH | RESOLVE_NO_XDEV)`, falling back to `openat(O_NOFOLLOW | O_DIRECTORY)` once `openat2` reports `ENOSYS`, `EPERM`, `EINVAL` or `E2BIG`. On the fallback the root is opened one component at a time from `/`, each `openat(O_NOFOLLOW | O_DIRECTORY)` relative to the descriptor before it, every component but the last with `O_PATH` on Linux, so that an ancestor needs search permission and not read permission, as in an ordinary path lookup (`a_root_below_a_search_only_ancestor_is_walked`, both open paths, a directory root and a file root; elsewhere, where there is no `O_PATH`, the ancestors are opened for reading), because a single `open` with `O_NOFOLLOW` protects only the last component: an ancestor renamed and replaced with a symlink after discovery would otherwise move the walk, and its device baseline, outside the worktree (`a_root_whose_ancestor_is_swapped_for_a_symlink_is_not_walked`, both open paths). A file given as the root is measured by `fstatat(AT_SYMLINK_NOFOLLOW)` relative to its parent, opened the same way with `O_PATH` for every component, the parent included. The opened directory's own `fstat` is what is checked (directory, root's device, no `.git` inside), so a directory renamed and replaced with a symlink between the look and the open is not followed (`a_directory_swapped_for_a_symlink_is_not_followed` swaps it through a test hook, on both open paths). `RESOLVE_NO_XDEV` also refuses a same-device bind mount. The fallback compares mount ids instead: once it opens a directory, it reads that directory's and the root's mount id, from `statx(STATX_MNT_ID)` (Linux 5.8, called as a raw `syscall(SYS_statx, …)` because glibc's wrapper arrived in 2.28 and the aarch64 release build links against glibc 2.23, where a strong reference to it fails to link) or else from the `mnt_id:` line of `/proc/self/fdinfo/<fd>` (Linux 3.15), and leaves the directory out when they differ, as `openat2` would have (`boundary`, `mount_ids_tell_mounts_apart` for both sources, `fdinfo_names_the_mount_id`). Leaving a known crossing out keeps the fallback's figure equal to the primary path's, rather than marking the walk incomplete for something the primary path leaves out on purpose. A boundary the fallback cannot read, because neither source reports a mount id (a kernel before 3.15, or `statx` refused with `/proc` not mounted), is never taken for the root's own mount: the directory is left out and the walk is incomplete (`the_fallback_enters_only_directories_known_to_be_on_the_roots_mount`). So on the fallback a same-device bind mount under the worktree is entered only where a mount id shows it is not one. In practice the fallback is a kernel before 5.6, or a container runtime whose seccomp filter refuses `openat2`, as some did; fdinfo reports a mount id on both. Directories' devices are compared and files' are not, because on overlayfs a file reports the underlying filesystem's device rather than the overlay's its directory reports. So a file bind-mounted onto a path inside the worktree is counted, whichever filesystem it comes from.
- **What a walk counts when something fails.** `readdir` reports an error only through `errno`, so `next_name` clears it first and returns an error rather than the end of the directory; a directory that cannot be read to its end makes the walk incomplete (`a_readdir_error_makes_the_walk_incomplete`, through a test hook). An entry that vanished between the listing and the look (`ENOENT`) has nothing left to count and changes nothing. Any other entry the walk cannot look at, such as one in a directory it may read but not search, makes the walk incomplete (`an_entry_it_cannot_look_at_makes_the_walk_incomplete`), and so does a subdirectory that fails to open for a reason other than being denied, a symlink, a mount or gone, or whose opened descriptor cannot be `fstat`ed. A directory it may not enter (`EACCES`/`EPERM` on the root's device) is the one counted case: its own blocks are counted and the walk stays complete. Checking a hard link against the inodes already held comes before checking the budget, so a repeat link to a counted inode never stops a walk (`repeat_hard_links_never_stop_a_walk`), which a pnpm `node_modules` past a million inodes would otherwise do.
- **A failed walk withdraws the figure** (`walks.rs`). A walk that fails outright (the worktree vanished, or its root cannot be opened) clears the worktree's last figure, so the old byte count is not sent on as current: the worktree has no disk point until a walk succeeds again (`a_failed_walk_withdraws_the_last_figure`). Withholding was chosen over marking the old point stale, because a point with an old timestamp and no "stale" convention reads as current on every backend. The failure is logged at most once a minute, by worktree id and the error's kind (`entity not found`), never its path or the error's text.
- **Walk budgets and the pool** (`walks.rs`). Each walk runs under `DEFAULT_BUDGET`: 4,000,000 entries, 1,000,000 tracked inodes (directories and multiply-linked files, for deduplication: the walk's memory), 64 levels (each level holds one open directory, two descriptors, so the two workers hold at most about 260), and 600 s, plus a cancellation flag set when the pool is dropped. Every insertion into the tracked set is held to the inode budget, a directory the walk may not enter (`EACCES`/`EPERM`) included (`denied_directories_count_against_the_inode_budget`). The deadline and the flag are cooperative: they are checked once per directory entry, between system calls, so an `openat`, `readdir` or `fstatat` that blocks on a stalled filesystem holds its worker past 600 s, and two such workers stop further disk updates until they return. The pool bounds how many threads that can tie up; it cannot interrupt them. A walk that hits any of them returns what it counted with `complete: false`, sent as the point attribute `deck.worktree.disk.complete = "false"` and logged (by worktree id, at most once a minute). Walks run on `WORKERS` = 2 threads fed by at most `MAX_OUTSTANDING` = 16 queued-or-running jobs; past the bound, a due worktree waits for a later sample, never-walked and oldest first. A worktree has at most one outstanding job, which keeps its place after the worktree goes inactive, so leaving and re-entering does not start a second walk; completions carry a generation and only the awaited one is applied. `--once` uses the same pool (`measure_all`) with a 600 s deadline, cancels what is still running then, and waits a second for its partial result. A pool whose threads cannot be spawned turns disk metrics off with a log line instead of panicking.
- **Sampling is off the async runtime, and neither it nor an export holds up the stop** (the binary). The export loop runs on a current-thread Tokio runtime, and a sample (reading `/proc`, waiting for first-sight lookups, the walks' bookkeeping) is synchronous, so each runs on a blocking thread through `spawn_blocking`: the `Sampler` is moved in and comes back with the sample's request. The loop is a small state machine (`InProgress`: nothing, a sample, or the export of the request that sample returned) that waits on that work and on `SIGTERM` and `SIGINT` together, so a stop is received, and its instant taken, during a sample and during an export alike (`a_signal_during_an_export_ends_the_loop_within_the_budget` sends the test process a real `SIGTERM` while an export waits on a backend that never answers). The next sample starts at a tick after the export has ended; a tick missed meanwhile is skipped (`MissedTickBehavior::Skip`).
- **Shutdown has one budget.** `SHUTDOWN` covers everything left after `SIGTERM` or `SIGINT`, from the stop's arrival. A sample still running is awaited and its request exported, not replaced by the final one, because under delta temporality its interval's CPU is in no other request (`a_sample_in_progress_at_the_stop_is_exported_too`). That export, or a regular one in progress at the stop, runs alongside the final sample, which queues what is due and waits up to 5 s from the stop for the walks queued or running (`Walks::settle`, `settle_waits_for_outstanding_walks_within_its_bound`), so a worktree whose first walk finishes within that time is in the final request. A walk still running then is not waited for, and a cold walk of a large worktree (27 s for the largest measured) will not make it. The final request is exported last, by the end of the budget or its usual deadline, whichever comes first (`Attempts::until`, `the_final_export_ends_within_the_shutdown_budget`). What has not finished 10 s after the stop is abandoned, with a log line, rather than waiting on a `/proc` read or a backend that does not answer; the runtime is then shut down without waiting for a blocking thread. A `--stdout` line is written synchronously and is not cut short. Neither figure is configurable: systemd's default stop timeout, 90 s, is far above both.
- **Export** is OTLP over HTTP, protobuf or JSON, with the same `OTEL_*` resolution rules as the deck's exporter, the `METRICS` form of each variable replacing the general one, including the deck's rule that a non-positive timeout means the default. The protobuf encoder (`collector/otlp.rs`) reuses the deck's wire helpers in `telemetry/otlp.rs`, and a unit test decodes it back and compares it with the JSON encoding. No redirect is followed. Retries reuse the deck exporter's helpers (`is_retryable_status`, `retry_after`, `jittered`, `RETRY_*_BACKOFF`): 429/502/503/504, connection errors and timeouts are retried with jittered doubling backoff, a `Retry-After` in seconds lengthening the wait; any other status is final. One deadline, the export timeout or the sampling interval whichever is shorter, bounds the whole send: each attempt gets what is left of it as its request timeout, the answer's body is read under it, and a wait that would end at or past it is not started. Those decisions live in `Attempts`, which takes the instants it decides from, so its tests (`the_deadline_is_the_shorter_of_timeout_and_interval`, `a_wait_past_the_deadline_is_not_started`, `retry_after_only_lengthens_a_wait`) need no clock or network; one loopback smoke test (`an_unanswered_send_ends_at_its_deadline`) is the only one with a one-second deadline; it awaits the send's own result without requiring that the backend received the request first, and expects `timed out` whichever stage of the send that deadline ends, its backend giving up quietly on a request that never arrives whole. A 2xx answer's body is read by the collector's own `read_body`, which counts a body as whole only once its end arrives: a body that fills `MAX_RESPONSE_BODY` (64 KiB) exactly is read on for its end, and one that goes past it, inside a chunk or after it, is `Body::TooLarge`. The cap is on the body `read_body` accumulates: each chunk arrives as the `bytes::Bytes` reqwest handed over and is checked against what is left of the cap before any of it is copied in, so the accumulated body never holds more than 64 KiB. The chunk itself is the transport's, sized however hyper read it, and that cap does not bound it. Unlike the deck exporter's `bounded_body`, it reports a body that errors, does not end by the deadline or is too large instead of reading it as complete or empty, and `answered` makes such a send a failure (`--once` exits 1, held terminals stay held) that is not retried, since the backend may have kept the request. `read_body` takes its chunks through a small `Chunks` trait, so its tests script the chunks and need no network: the body tests (`a_body_is_read_whole_once_its_end_arrives`, `a_body_that_stalls_or_breaks_at_the_cap_is_not_read`, `a_body_past_the_cap_is_too_large`, `an_oversized_partial_rejection_is_not_delivered`) give a stall a short deadline that nothing has to happen within, and every other read a 30-second one; `a_send_fares_as_its_answer_reads` covers `answered`. Two loopback tests with a 30-second deadline check the whole path against real HTTP (`a_success_whose_body_is_cut_short_is_not_delivered`, which includes a close with exactly 64 KiB of a longer declared body, and `whole_answers_are_delivered_or_reported`). A whole body is decoded as an `ExportMetricsServiceResponse` (`decode_metrics_partial_success_json`, or the shared protobuf decoder, whose field numbers are the traces response's): rejected points are logged by count only, never the backend's `errorMessage`, not retried, and make `--once` exit 1; a warning with nothing rejected is logged and counts as delivered.
- **What a failed export loses.** A live run's cumulative CPU recovers on the next delivered request. A terminal resource (`ResourceMetrics::terminal`) of a failed request is held by `PendingTerminals` and attached to every later request until one is delivered or partially rejected, at most `MAX_PENDING_TERMINALS` = 1024, held oldest first (a failed request's own terminals go after those already held), and the oldest dropped past that with a log line (`held_terminals_overflow_drops_the_oldest`). Still lost: the delta CPU of a failed request under `delta`/`lowmemory`, the gauges (memory, process counts, disk) of a failed request, terminal resources beyond the bound, anything held when the collector exits, and the rejected points of a partial success.
- **A partial rejection releases the held terminal reports, by decision.** A 2xx answer whose `partial_success` reports rejected points is a request the backend accepted, apart from the points it names. The OTLP specification says a client must not retry such a request, and the collector cannot tell which points were rejected, since the answer gives a count and an error message, not the points. Sending the held terminal reports again would duplicate in the backend every point it already accepted, and would not recover the rejected ones, which it would most likely reject again for the same reason. So `emit_holding` treats a partial rejection as delivered for holding purposes and clears what it held; only `Delivery::Failed` (no 2xx, or a 2xx whose body did not arrive whole) keeps it. The rejection is logged with its count, and `--once` exits 1.

### Why environment grouping and not a cgroup per run

A cgroup per run would be the ground truth, and it is what the measurements below compare against. It is not built because it changes how the deck starts agents, and it needs a delegated cgroup subtree, which the daemon's session scope does not have (the live daemon ran in a non-delegated `session-<n>.scope`, as #1692 also found). Environment grouping needs neither, matched the cgroup to within 0.1 s in every in-tree workload measured below but one (a +4% double count on a cold build at 1 s), and keeps double-forked processes that keep their environment, which a parent-pid walk (#1692) lost. The ancestry fallback is required, not a refinement: on the live box, 25% of run processes carried no run id of their own (harnesses and tools that replace the environment). Moving to a cgroup per run is #1897.

- **The undercount is short-lived detached work**: a double-forked process is counted while it is alive at a sample; what it uses after its last sighting is reaped outside the run. Short double-forked commands were 4–5% seen at any cadence. The lost time lands in no bucket the collector can see (the user's systemd manager reaps it, and its environment is not readable), the unattributed one included.
- **The run's last interval** is reaped by the deck daemon when the agent exits, so a run loses up to one interval of CPU.
- **A double count** of +4% appeared once (48.82 s against 46.92 s), on the third of three cold builds at 1 s, when a child was reaped while the sample was being read; not at 2 s or slower. Reading every `stat` in one pass before anything else narrows that window; it does not close it, because a sample is not atomic.

### The collector's own cost

Measured on the release build, on the same box while it was very busy: 16 cores at load average 60–86, 509–667 pids, 148–310 of them visible to the user, 14 live runs.

| What | Figure |
| --- | --- |
| CPU per sample, steady state (`--interval 1`, 120 samples) | 187 ms; 18.7% of a core |
| CPU per sample at the default 15 s (`--disk-interval 0`, 12 samples over 181 s) | 211 ms, 94% of it system time; 1.40% of a core |
| One `--once` sample, wall clock, fresh process (30 runs) | p50 367 ms, p95 552 ms, max 649 ms |
| Resident memory while sampling | 5.4–5.6 MB (PSS 3.3 MB) |
| `--once` with disk: 9 worktrees in use, 0.07–98.9 GB, 185 GB in all | 25.9 s wall cold (0.9 s user, 3.3 s system), 2.3 s warm (0.7 s, 1.6 s); 15–16 MB peak resident |

System time dominates because `smaps_rollup` walks each target's mappings under its `mmap_lock`; the Python prototype found it three-quarters of a sample's cost on a quieter box (156 ms per sample, 404 pids). At the default interval that is about 1.4% of one core, so the default stays at 15 s; the systemd unit on the user page also sets `Nice=10`. The disk walk's cost is the size of the worktrees in use, which is why walks run on their own threads and on their own, slower interval.

### Why not macOS

The collector needs two things Linux gives for every process through `/proc`: the process's environment, which says which run it belongs to, and its proportional memory. macOS has no `/proc`, reports no proportional memory figure for a process, and restricts reading another process's environment, so the binary is a stub there that prints `only Linux is supported` and exits 3. A cgroup per run (#1897) would not help: macOS has no cgroups either.

### Packaging

- **GitHub release**: the `build` job's Linux legs upload `dot-agent-deck-collector-linux-amd64` and `-linux-arm64` as artifacts named `dot-agent-deck-collector-<suffix>`, which `finalize`'s `dot-agent-deck-*` pattern brings into `dist/`, `checksums.txt` and `attest`. The macOS legs build the collector too (it is a target of the package) but do not publish it, because there it is the stub that exits 3.
- **Nix**: crane's `installFromCargoBuildLog` installs every non-test executable the build log reports for a workspace member, so the package installs `bin/dot-agent-deck-collector` with no change to `flake.nix`.
- **Homebrew**: the formula installs one binary per platform and does not carry the collector; the user page points Homebrew users at the release binary.
- **`dot-agent-deck upgrade`** replaces the deck's binary only.
