# The agent pane's Card panel

PR #2491's decision of 2026-11-25 removed the card overlay (`AgentCardOverlay.tsx`). A card now opens its agent's pane, and the pane shows the card in a **Card panel** beside the terminal. This page says how that is wired; the user-facing behaviour is in [`docs/desktop/agent-cards.md`](../desktop/agent-cards.md#the-card-panel).

## Where the state lives

The cards are the overview's (`useAgentCardsView` in `AgentOverview`), and the agent pane is the overview's **sibling** in `DeckShell` (`App.tsx`, `OverviewAgentPane`), so the two meet through a small store:

- `desktop/src/lib/paneCards.ts` — `createPaneCardsChannel()`, created once per shell. The overview publishes a `PaneCardsView` (`shownFor`, `cardFor`, `resultsFor`, `treeFor`, `endedFor`, `notice`, `controls`) in a layout effect; the pane reads it with `usePaneCards` (`useSyncExternalStore`), so only the pane re-renders when a card changes.
- The panel's open state is the **shell's** (`cardPanel` in `DeckShell`), settled once per navigation (`settleCardPanel`), keyed by the `requestedView` object a navigation creates: open when the view carries `cardPanel: true` (it came from a card, `+N`, the table's Show card or `show_agent_card`), or when the card needs the user, else the user's last explicit choice: `cardPanelChoice`, set by `chooseCardPanel`, falling back to the stored one (`readCardPanelChoice`, `localStorage`, `try/catch`). A panel the last pane forced open is not a choice, so a move between agents does not carry it (PR #2491 review J5, `095`). A pane settled before the overview published anything (the app opening on a pane) is settled again in a layout effect, before paint; after that **only** `setCardPanel` (the header's Card button, voice's `open_card_panel` / `close_card_panel`) changes it. That rule is the point: the panel's size is the terminal's, and a terminal size change is a resize the agent sees, so card updates never toggle it (`095`, Playwright `097`).
- Once open for a navigation, the panel keeps its slot while the card is gone or its deck's cards are not shown (a disconnect drops them in `useDeckRuntime`): `OverviewAgentPane` renders `AgentCardPanel` with no card, which says "This card is not available right now." and draws no actions, and keeps the header's Card button so the user can still close it (`chooseCardPanel` refuses only an open while the deck shows no cards). Gating the panel on `shownFor` removed and restored the slot with no input (PR #2491 review J2; `105`, Playwright `105`). While the deck is not answering, the pane also withholds Generate config and Close agent, so at 375 px its header is a row shorter; no terminal is attached then, and after the reconnect the terminal's box is what it was.
- A card the deck keeps while its agent is gone (an exited orchestration role) opens `EndedCardPane`, a read-only pane backed by the card alone: no terminal attach, no Close agent, the Card panel open, and one sentence where the terminal would be (`data-terminal-state="ended"`). `DeckShell` reads whether the open view has a card from the channel as a boolean (`useSyncExternalStore`) to make a view card-backed, and remembers the view it last showed that way (`endedPaneView`). A view whose agent the user just closed (`stoppingAttempt`) still goes back to the dashboard (PR #2491 review J1; `104`, Playwright `025`).
- Once card-backed, a view keeps that until the card is really gone or the agent is really back (PR #2491 review L1, L2). While its deck is not answering it stays the ended pane, even when `useHeldAgentRecord` still holds a live record from before the agent ended (`108`). On a deck answering again, retirement is decided from the runtime's own cards listing in the same render, through `cardListing` in `lib/agentCards.ts`: `listed`, `omitted` (a listing from the connected daemon process leaves the card out, or the deck now names another process than the view's), or `awaiting` (no listing from that process yet). Only `omitted` retires the view. It never reads the channel for this: the overview republishes the channel in a layout effect a render after the reconnect, and a retirement decided from the previous render's value closed the pane before the cards were read (`104`'s second case, Playwright `104`). A live record of the agent clears `endedPaneView`, so the live pane is back and a later outage holds that record as before.
- `EndedCardPane` renders `AgentCardPanel` with `readOnly`: no action icons, no answer buttons, and a note saying so, and its `runCardAction` member is replaced by one that refuses before the send hook (PR #2491 audit M1, `107`). The agents' list and the cards are separate listings, so a card can still say its actions are enabled for a moment after its agent has gone; the daemon still refuses a press on a stopped agent, and the pane does not rely on that. The references and the header's moves keep the overview's members.
- Opened at the references (a card's `+N`), `AgentCardPanel` scrolls them into view and focuses the section once per navigation, with `preventScroll`; a card update never takes focus (PR #2491 review J6; Playwright `025`).
- Under 900 px the panel stacks above the terminal at a **fixed** height (`flex: 0 0 min(40vh, 260px)`), not a content height: an auto height moved the terminal whenever the card's text changed (found by `097` at 375 px).
- `AgentTile` always wraps the terminal and the panel in `.agent-pane-body` (`display: contents` on a tile), so the terminal is never re-parented when the panel comes and goes.

## The review

The single-action review and the Close confirmation, which were the overlay's confirm step, are `AgentCardReviewDialog` — a dialog of its own on `OVERLAY_LAYER.dialog`, over the dashboard or the pane. `useAgentCardsView` holds it as `review` (`{ key, name, actionId, token, sent, reviewed }`); `confirmCardAction` sends the reviewed token only, and after Send the dialog shows the result and closes with Close. From Send on, `reviewed` keeps the action as it was sent, its label and the press's own answer (numbered by `reviewRun`, so a late answer lands only on the review that sent it), apart from the card and from the results `pruneCardResults` drops: a Close removes the card and an agent can stop offering an action it got, and the dialog renders that sent, pending or uncertain outcome before its "no longer offered" branch, keeping "Nothing was sent" for a review never sent (PR #2491 review J4, `106`). `closeCardReview` is `no_voice`: voice's `close` reaches it through the fence it registers, as it reaches the batch confirmation. `runCardAction`'s `openPane` (the table menu's primary action) opens the agent's pane with its panel under the review.

## Navigation and keys

`stepAgentCard` moves from the pane's agent (`AgentOverview`'s `agentPane` prop) through the dashboard's placed order (`stepCard`) and opens the next agent's pane through the same `openAgent` path. `[`, `]` and `n` are handled in `DeckShell`'s pane `keydown` listener beside `Escape`, and only when the focused element is not inside `.agent-terminal-stack`, an `.xterm`, or a field; in the terminal they reach the agent (Playwright `098` asserts the bytes).

## Voice decisions

- `show_agent_card`, `next_needs_you_card` and `run_card_action` run on the dashboard and the agent pane; `next_agent_card` and `previous_agent_card` on the agent pane only.
- **"close the card" closes the panel** (`close_card_panel`), and `close_agent_card` was replaced rather than retired in favour of `close`: with the overlay gone, a user saying "close the card" while looking at the pane's panel means the panel, and "back to dashboard" / "close" keep leaving the pane. Retiring it would have sent "close the card" to `close`, which leaves the pane — more than was asked.
- `reply_to_agent_card` was retired with the reply box: its only target was that box. "open the coder" then "tell it …" (`dictate_to_agent`) types into the agent's terminal, unsent. The `reply_text` param kind (`ParamKind::ReplyText`) is now declared by no row; it is left in the crate for a follow-up to remove.
- The editor's placement row is `show_card_action_only_in_the_card_panel` (was `…_only_in_the_overlay`).

## The TUI

The TUI has no cards view, and its agent pane has no Card panel. Adding one would mean: subscribing the TUI to the card list (the daemon's `AttachRequest::ListAgentCards`, which the desktop already uses, and its change notifications), a ratatui panel widget beside the embedded terminal that renders an entry's two parts, key bindings for its actions that respect the TUI's command mode, the same "never resize by itself" rule for the PTY size, and a review step for agent-written text. That is a feature of its own, not a small change, so it is not part of PR #2491; the user docs name the gap ([In the TUI](../desktop/agent-cards.md#in-the-tui)).
