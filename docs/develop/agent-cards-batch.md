# Batch card actions (issue #2399)

Issue #2399 is step 2 of PRD #2374's agent cards: one card action sent to many agents in one press, from a card with agents under it or from a selection in the Cards view. The user page is [`docs/desktop/agent-cards.md`](../desktop/agent-cards.md) ("Send one action to many agents"); this page holds the wire, the checks and the decisions a maintainer needs. The tree the batch follows is [`agent-cards-tree.md`](agent-cards-tree.md).

Per CLAUDE.md rule 18 the **daemon** decides who is included, what text each card gets and whether each delivery may go; the desktop sends the entries the user picked and draws the daemon's answers. The TUI has no cards, so it has no batch (PRD #2374's documented gap); the CLI's `card act` stays one card at a time.

## The wire: one verb, one capability

`AttachRequest::InvokeCardActionBatch` (`op: "invoke-card-action-batch"`, `src/daemon_protocol.rs`):

| field | what it holds |
| --- | --- |
| `mode` | `"preview"` or `"execute"` (`CardBatchMode`) |
| `action_id` | the action, by the id the cards list it under |
| `request_id` | names the batch: 1 to 124 bytes of `[A-Za-z0-9._:-]` |
| `entries` | `CardBatchEntry`: `pane_id`, `agent_id`, and for `execute` the `action_token` and `instance_id` the preview answered |

The answer rides on `AttachResponse.card_action_batch` (`CardBatchResult`: `request_id`, `entries`), one `CardBatchOutcome` per distinct entry, in the request's order. `outcome` is `included` / `skipped` for a preview and `delivered` / `closed` / `failed` for an execution. A `delivered` entry also carries `state`, the delivery state its own card records for the same press: always `queued` when the batch answers, since the text is in the agent's inbox and the agent has not confirmed it (PR #2491 review). `delivered` names the outcome the press reached, not the agent's receipt; the field is additive and optional (`skip_serializing_if`), and the desktop words the row by it. A `delivered` entry without `state` (an earlier development build of this verb) is read as `queued`, the most a press can say when it answers, so a row reads **Delivered to the agent** only when a daemon says `state: "delivered"`, which this daemon does not send. An included entry carries `name`, `label`, `kind`, the exact `prompt` with its `prompt_source` (absent for a close), and the `action_token` and `instance_id` to execute with. A skip or failure carries a stable `code` and a `message`. An entry that fails leaves the response's `ok` true; `ok: false` is reserved for a request refused as a whole (`check_batch`: a malformed request id, an empty or oversized action id, no entries, more than `MAX_BATCH_RAW_ENTRIES` = 512 entries counting repeats, an oversized identifier, more than `MAX_BATCH_ENTRIES` = 256 distinct cards).

**The daemon advertises `agent-cards-batch`** (`CAP_AGENT_CARDS_BATCH`) on every platform. `DaemonClient::invoke_card_action_batch` is the one sender and sends only on a connection whose own Hello named it and `hello-follow-on`; it binds the connection to the `instance_id` the cards were listed by, as `invoke_card_action` does. `AgentCardsAnswer.batch` (set by `tree_gate`) tells the desktop whether to offer batches; the Tauri command is `agent_card_invoke_batch`, and the webview's runtime member is `invokeCardActionBatch(deckId, actionId, { mode, entries, requestId, instanceId })`.

**Rule 12 answer: no `PROTOCOL_VERSION` bump and no `.breaking.md`.** The request is a new verb every sender withholds until the daemon advertises it (rule 18's capability rung), the response field is additive and optional, and nothing about `invoke-card-action` or the card list changed meaning.

## Why preview, then execute

A batch is always confirmed, whatever each action's own `confirm` says (PRD #2374, #2399 scope), and the confirmation must show exactly the text each agent will get. Two calls make that hold:

- **preview** reads a fresh computation of the cards (`refresh`) and classifies each entry with `preview_entry` — the checks a single press makes in `invoke_once`, less the ones a preview cannot make. It sends nothing and remembers nothing. Skip codes are a single press's refusal codes: `unknown_entry` / `stale_entry` (no such card / the pane holds another agent), `unknown_action`, `client_side_action` (Open), `text_required` (a reply: the user's own words, one card at a time), `action_disabled`, and `agent_stopped` (`CODE_AGENT_STOPPED`, the `REASON_AGENT_STOPPED` word) for a prompt action whose agent is not running.
- **execute** takes only what the user confirmed, each entry with the `action_token` and `instance_id` its preview answered, and runs each through `invoke` — the single press's own path: the request-id claim and admission caps, the instance check (`daemon_replaced`), the token check (`stale_action`), delivery through `post_card_message`, and the record on that card's `recent_deliveries`. So an entry whose action changed after the preview fails on its own with `stale_action` and is sent neither text, and the entries after it still go (`execute_batch` does not stop on a refusal).

Each entry is invoked under its own request id, `<batch request_id>#<rank>` (`batch_entry_request_id`), where `rank` is the entry's place among the batch's distinct entries ordered by identity — pane, then agent generation (`batch_entry_ranks`) — never its place in the request (PR #2491 review). The same cards listed in another order therefore get the same ids. **The `#` keeps entry ids in a namespace of their own**: a client's request id may contain only letters, digits, `.`, `_`, `:` and `-` (`check_request` refuses anything else), so no single press can name an entry's id. An entry therefore never replays, is refused by, or forgets a single press's remembered answer, whatever request ids a client chooses: a single press under `b:0` before or after batch `b` is its own press, with its own answer and its own replay protection (`a_single_press_under_a_batch_s_old_entry_id_keeps_its_answer_across_the_batch`). Entries reach the single press's path past `check_request` (`invoke_checked`; `check_batch` has already bounded their fields), and go through everything after it. The suffix is at most `#255`, which is why the batch id is limited to 124 bytes.

**A batch is remembered whole, in a memory of its own** (PR #2491 review). `execute_batch_once` claims the batch id in `StoreInner.batches` (`CardStore::claim_batch`), not in the single presses' remembered requests, with a fingerprint over the action and every distinct entry's pane, agent, token and instance, taken in identity order (`batch_fingerprint`). The record (`RememberedBatch`) holds that fingerprint and, once the entries have run, the batch's answer: its per-entry outcomes, shortened when they are too large to keep whole (below).

- **A repeat of a remembered batch invokes no entry.** The same action and the same set of cards, in any order, is the same batch: a repeat gets the stored outcomes, listed in the repeat's order (`in_repeat_order`), and a repeat that arrives while the batch is running waits for that run and gets the same outcomes. So nothing a single press's memory forgets in between can make a repeat post again.
- **Any other request under a remembered batch id is refused whole** before an entry runs: a card added or removed, another token, another action, or an id a single press already used (and a single press is refused `request_reused` under a remembered batch's id). The response's `ok` is false, and the desktop reads it as `deck_refused`.
- **The binding and the outcomes leave memory together.** `CardStore::finish_batch` stores the answer and, under the same lock, forgets the batch's entries' own single-press answers (`<id>#<rank>`, ids only this batch's entries can have), so no entry answer outlives the record that binds the id to its set of cards. A batch's record lasts up to `REQUEST_ID_MEMORY` (10 minutes), sooner when newer batches need the room. The batch records have their own bounds, `MAX_REMEMBERED_BATCHES` (256) and `MAX_REMEMBERED_BATCH_BYTES` (4 MiB of accounted strings — the outcomes' text and running batches' reservations, not the heap the feature takes), and that memory drops the oldest answered batch first, never a running one, so a batch record never takes a single press's room. **The entries' presses are another matter**: while an entry runs, it is claimed in the single presses' memory like any press (`run_once`), so it counts toward that memory's caps, the per-card running caps included, and may push out an older single answer exactly as a single press would, until `finish_batch` removes it. A repeat after a batch is forgotten is a new batch and delivers again. A memory full of running batches refuses a new one whole (`busy`).
- **An answer too large to remember whole is remembered smaller, never as a refusal.** `finish_batch` tries the whole answer, then each entry's outcome, code, message id and state with its message cut to `COMPACT_MESSAGE_CHARS` (`compact_outcome`), and then each entry `unknown` with code `answer_not_kept` (`minimal_outcome`). A running batch reserves `BATCH_ENTRY_RESERVE_BYTES` (1 KiB) per entry besides its ids, which is what guarantees the last form fits. The supervisor answers the first caller and every repeat waiting on the run with what `finish_batch` kept, so they and a later repeat all get the same answer (`a_batch_answer_too_large_to_remember_is_kept_smaller_and_never_read_as_a_refusal`).
- **Only a batch that passes the cheap checks is remembered.** A new batch none of whose entries passes a single press's admission checks (`StoreInner::admission`: this daemon process, a card the store holds, the action's current token — the checks `admission_refusal` runs for a single press) is answered with each entry's refusal, invokes nothing and remembers nothing, so a stream of such batches cannot churn either memory. Passing them does not mean an entry can act: a disabled action, Open or a reply passes them, and the full single press then refuses it. A batch with at least one entry that passes is remembered, and its other entries fail on their own as before.
- **The run does not depend on its caller.** The entries run on a task of their own and a supervisor stores the answer, as `run_once` does for a single press, so a caller that is cancelled changes nothing: the batch finishes and is remembered. Each entry's outcome is recorded the moment its press answers, so a run that panics is remembered with the outcomes of the entries that answered before it, and every other entry `unknown` with code `interrupted` (`interrupted_batch`); its repeats get that answer rather than running again.
- **`ok: false` means nothing ran.** The daemon refuses a batch whole (`check_batch`, a reused id, no room) only before any entry runs. Once an execution starts, every answer, a repeat's included, is per entry: an entry the daemon cannot account for is `unknown` (`BATCH_UNKNOWN`) with `interrupted` or `answer_not_kept`, never a whole-request error the desktop would read as "nothing was delivered".

A preview claims nothing and remembers nothing.

`confirm` is `true` on every entry — the batch's confirmation is the user's confirmation of each — and `text` is always `None`, so no reply goes in a batch. Entries run one after another, not in parallel: each takes the card store's turn anyway, and a close waits for its process.

Duplicates are dropped before anything is acted on (`distinct_batch_entries`: the first naming of a pane and agent wins), so a card is never pressed twice by one batch. `check_batch` bounds a request in three steps, each before the next (audit S2): at most `MAX_BATCH_RAW_ENTRIES` (512, twice the distinct cap) entries counting repeats, then every identifier's size, and only then the distinct count, which hashes the identifiers and stops at the first card over `MAX_BATCH_ENTRIES`. The attach frame cap (`MAX_FRAME_LEN`, 16 MiB) is what bounds the request parsed before any of these run.

## The desktop

`useAgentCardsView` (`desktop/src/hooks/useAgentCardsView.ts`) holds the selection and the batch on screen:

- **The selection is always on** (PR #2491 review). There is no selecting mode: every card of a deck whose daemon advertises batches (`batchFor`) carries its checkbox, and `CardSelection` is only the selected keys and the `batchChoices` they offer. `AgentCardsSelectionBar` (`AgentCardsGrid.tsx`) is rendered last in the dashboard's scroll region (`.overview-body`) while the selection is not empty, `position: sticky; bottom: 0`, so it stays at the region's foot wherever it is scrolled and, scrolled to the end, sits in flow below the last card: that is the room the cards get for it, with no measured padding, and `margin-top: auto` keeps it at the foot when the cards do not fill the region. The region ends above the voice row (`.deck-main`'s `padding-bottom: var(--voice-row-height)`), so the bar cannot cover it. Its **Clear** is `clearCardSelection`. When the bar goes while it holds focus (Clear pressed from the keyboard, voice's `clear_card_selection`, or the selected cards leaving the list), its layout effect's cleanup, which runs before the bar's DOM is removed, moves focus with `preventScroll` to the checkbox of the card toggled last (`CardSelection.last`), or to the scroll region when that card is not drawn; left on the removed button, focus falls to the document and WebKit's next Tab starts from the page's header with the region scrolled to the top (PR #2491 review H1; Playwright `089`, vitest `090`). Its icons, a card's own and the Card tab's are each wrapped in `ActionIconGroup` (`ActionTipButton.tsx`, class `action-icon-group`: `--teal-soft` background, `--teal-rim` border, both themes), so the actions are in the same box in all three places. A card's own Close stays outside its group; the batch's Close, in the bar, is one of the batch's actions and sits inside it. Needs you is always the compact bell on a card, so the name keeps its room beside the checkbox (Playwright `081`; the bar and the group are `087` and `088`).
- **What a batch reaches.** By voice (`run_card_action_batch`): the card and its whole subtree (`cardSubtree`, from the same `cardTree` the view draws), whether or not the tree is open. From a selection: the selected cards. Selecting a closed card selects its subtree — the only way to reach a subtree by hand since the card overlay and its batch row went (PR #2491 decision 2026-11-25); an open card's checkbox is the card alone, because its children are on screen to pick (PRD #2374 decision of 2026-11-20, item 8).
- **Which actions are offered** (`batchChoices`): every action one of the cards offers, less Open, a reply and an answer to one agent's question (their ids and texts belong to one card). Whether each card gets it is the daemon's call in the preview.
- **Several daemons.** A selection can span decks; the hook asks each daemon process for its own preview and execution and shows the answers together. Each answer stays in a `CardBatchGroup` carrying its `deckId` and `instanceId`, and the dialog keeps that identity on every row: pane and agent ids are daemon-local, so a row's React key and the preview-name fallback for a nameless execution failure are deck + instance + pane + agent (#2399 review 1, audit S1). When a batch reaches more than one daemon, every row says which (`agent-cards-batch-daemon`, the dashboard's own `deckName`).
- **One daemon's preview failing does not block the others** (PR #2491 review). `startBatch` settles each daemon's preview on its own (`Promise.allSettled`). A daemon that answers and declines the preview — its handshake classified incompatible (`require_compatible`), a `Hello` on the request's own connection on another attach protocol or not admitted (`ClientError::ProtocolMismatch`, `ClientError::NotAdmitted`), the request refused as a whole (`check_batch`'s caps among them), a replaced daemon or one without batches — has its preview answered by the bridge: every entry `skipped` with the reason (`deck_refused`, `daemon_replaced` or `unsupported`), which the dialog lists like any skip. A daemon whose preview call rejected — it could not be resolved, trusted or reached, its establishment handshake failed, the connection broke or its answer could not be read, or it did not answer within the bound — becomes a `CardBatchGroup` whose agents are all `skipped` with `code` `daemon_unreachable` (`CODE_BATCH_DAEMON_UNREACHABLE`) and `BATCH_DAEMON_UNREACHABLE` followed by its error. Either way the other daemons' agents are reviewed as usual, and a skipped row without a name from its daemon keeps the name its card shows. `sendCardBatch` executes only the groups with an included entry, so such a daemon is sent nothing. When every daemon's preview call rejected there is nothing to review, and the dialog shows the errors (distinct ones joined by `; `) as "Nothing was sent", as one failure did before.
- **Late answers.** `batchRun` is bumped by every start, send and close, so a preview or execution that answers after the user closed or restarted the batch changes nothing.
- **A batch being sent cannot be dismissed or replaced** (#2399 review 2). `batchSending` is set in the same tick as Send and cleared when every daemon's call has settled: with an answer, an error or the bridge's timeout. While it is set, `closeCardBatch` returns `BATCH_STILL_SENDING`, which the dialog shows (`agent-cards-batch-refusal`) and voice's `close` speaks through the overlay stack's close callback; Cancel is disabled; and a new batch (by voice, the only route while the modal is up) is refused with `ANOTHER_BATCH_SENDING`. So none of the dialog's ways out, and no second batch, throws away the per-agent results while the daemons are still acting. Switching the base screen away from the dashboard (`App.tsx`'s `base` leaving `overview` for the deck screen) unmounts the hook and its state with it; that is not guarded. Opening an agent from the dashboard does not unmount it: the agent's pane opens with `from: "overview"` as a sibling of the still-mounted `AgentOverview`.
- **A daemon that takes the execution and never answers** (#2399 re-review). The Tauri command `agent_card_invoke_batch` takes one deadline when it starts, `card_batch_reply_timeout` from then (`desktop/src-tauri/src/lib.rs`, PR #2491 review), and runs both of its steps against it: acquiring the deck's trusted link (`state.daemon.trusted(...)`, which can wait on the deck's establishment gate and a handshake; a failure there, or the deadline running out there, is `failed` with `not_sent`, since the request is written only after the link is held), then the batch client exchange — the follow-on connect, `Hello`, request and reply. The deadline is `DECK_REPLY_TIMEOUT` (15 s) for a preview, and that plus `CARD_BATCH_ENTRY_ALLOWANCE` (10 s) per entry for an execution, since the daemon runs entries one after another and answers once, after the last, capped at `CARD_BATCH_EXECUTE_CEILING` (180 s, PR #2491 review). The cap is there because the dialog holds the whole app while it waits and refuses Cancel, `Escape` and voice's `close`: uncapped, a 256-entry batch would freeze the window for over 40 minutes. Three minutes is the longest freeze accepted. Prompt entries are in-memory posts of milliseconds each, so a batch of any allowed size answers in seconds. A close's wait for its agent to stop is bounded by `AGENT_TERMINATE_GRACE` (3 s), but the rest of a close (releasing the pane, a kept worktree) is not (`src/agent_pty.rs`, `PANE_CLOSE_RECREATE_TIMEOUT`'s comment), so a batch of many closes on a loaded host can run past the ceiling. A batch past the ceiling reads **No answer** on every row, like any unanswered batch, while the daemon carries on; each card's own delivery history shows what it did. When it runs out, a preview fails (it sends nothing anyway), and an execution answers every entry `unknown` with code `no_answer` (`CARD_BATCH_UNKNOWN`, `CODE_CARD_BATCH_NO_ANSWER`): whether the request was written is not known, since the bound covers the connect and `Hello` too, and if it was, the daemon may still be delivering, so neither `failed` ("nothing was sent") nor `delivered` is true. A daemon that did receive it does not notice the client leaving until it writes its answer, so it keeps going. **The same holds when no readable answer comes back after the request was written** (#2399). `connection_lost` covers two cases: the connection broke after the request was written (the daemon closing the socket mid-batch, or a cut-off reply), and a reply that arrived but could not be decoded. In both it is not known whether the agents got the action. `DaemonClient::invoke_card_action_batch` answers every failure from the request's first byte on as `ClientError::Unanswered`, and the bridge maps it to `unknown` with code `connection_lost` (`CODE_CARD_BATCH_CONNECTION_LOST`) and a message saying the deck's answer was lost or could not be read after the request was sent. A failure before the request was written (the deck cannot be resolved, trusted or reached, its `Hello` fails, or it is a successor of the daemon that listed the cards) answers every entry `failed` with `not_sent` or `daemon_replaced`, and a daemon's refusal of the `Hello` or of the whole request answers `failed` with `deck_refused` (a preview's entries `skipped`): the daemon refuses a batch whole only before it runs any entry. An execution the daemon started is answered per entry, and the bridge passes that answer on as it is, its `unknown` entries included. A follow-on connect or `Hello` that hangs until the bound runs out also reads `no_answer`, the cautious side, since the bound does not tell the two apart. The hook's `catch` in `useAgentCardsView.ts` is left for an error the bridge did not place (the call itself rejected), and it answers `unknown` too, with no code, the error and the sentence that it is not known whether the agent got it, never `failed`. Nothing is retried, under the same request id or a new one; the dialog shows the rows as **No answer**, `batchSending` clears because the call settled, and the user decides from the cards whether to send again.

`AgentCardBatchDialog` shows the preview (`agent-cards-batch-confirm`), then the results (`agent-cards-batch-results`). `Escape` dismisses it through `VOICE_ACTIONS.closeCardBatch`, under the same sending guard. The skipped agents are folded into one disclosure button counting them by code (`byReason`, worded by `skipWords`; a code it does not know reads "for another reason" and each row keeps the daemon's own message), and within one text group (`sameText`) of more than `INCLUDED_FOLD_AFTER` (10) agents the names after `INCLUDED_SHOWN` fold behind that group's own "+N more" (`foldNames`). Only names fold: every distinct text is quoted with its source mark (`GroupSource`, `agent says` or `catalog`), however long the list, and the heading counts the agents and the distinct texts (PR #2491 audit K1, `102`); both are local `useState` disclosures listed in `voice-control-sites.toml`, not registry entries (`092`, `093`). Its list scrolls and Cancel and Send stay in view at every width (Playwright `desktop/agent-cards/033`).

With more than one distinct text (`distinctTexts > 1`), Send also waits until each quotation has been in the body's view at least once (PR #2491 audit K1, `useSeenTexts`). Each quotation carries `data-batch-text`, its index among the quoted texts, and is watched by an `IntersectionObserver` rooted at the scrolling `.agent-cards-batch-body`, or, where the webview has none, measured two animation frames after the dialog opens, the body scrolls, the window resizes or Show next text scrolls, so the frame between has painted what is measured; a later change restarts that wait. A quotation counts as seen when nearly all of it (`SEEN_SHARE`, 0.9) or at least half the body's height of it was in view (`quotationInView`); a text taller than the body is never wholly in view, which is why the second bound exists. While any is unseen the footer says "Scroll to see all N texts" and offers Show next text, which only scrolls the first unseen quotation into view: it counts as seen when the observer, or the fallback's measurement, then finds it in view, never in the task that pressed the button, so several presses in one go enable nothing (PR #2491 final verification P1). A new preview starts unseen, and a report is credited only to the preview it was taken for (PR #2491 observer race): each watched quotation is bound, when the watcher is installed, to the key it quoted then (a `WeakMap`), because React reuses a row's node for the next preview's text and a browser may deliver an observer's queued sample after the replacement has rendered and before the old observer's passive cleanup has disconnected it. A watcher counts only while it is the installed one and its key signature is the committed preview's (set in a layout effect, so before any task can deliver a report about that commit's DOM), and a node's credit goes only to its bound key, and only when that key is in the shown preview. jsdom has no layout, so `AgentCardsBatch.test.tsx` lays the dialog out itself (`layOutBatch`: the body a 324 px view, a quotation inside it once scrolled into view) and its `pressSend` presses Show next text and lets the frames run for each text, as a user can; `109` drives a stubbed `IntersectionObserver` and then the measured fallback, and Playwright `desktop/agent-cards/109` drives the real observer and, with it removed, the real fallback, at 1440 × 500 in both engines; `109`'s third vitest case and its third Playwright case deliver an old preview's sample after a replacement, and assert it credits nothing. One text, however many agents share it, sends at once. Voice still never presses Send.

## Voice (CLAUDE.md rule 23)

Every way to start a batch is on voice, and every one of them only opens the confirmation: `sendCardBatch` is `no_voice` (PRD #802 D5, as `confirmCardAction`).

- `runCardActionBatch` (`run_card_action_batch`: `agent: agent_ref`, `action: card_action`) — a card and its whole subtree. Like `run_card_action` it resolves the action by its spoken label, here across the card and its subtree.
- `selectAgentCard` / `unselectAgentCard` (`select_agent_card` / `unselect_agent_card`: `agent: agent_ref`) — the same selection the checkboxes build, through `toggleCardSelected` with `want` set, so repeating "select the coder" does not undo it. A closed card takes its subtree along, as its checkbox does, and selecting from the table shows the Cards view. An `agent_ref` resolves against the agents voice reaches (the daemon the app shows, or every daemon under **All daemons**), so a selection across daemons is built under **All daemons** or by switching between utterances. A bare "select the coder" is `open_agent`'s (its description lists "select"); the two rows' descriptions send card / selection / batch wording here, the way `show_agent_card` takes "card".
- `runSelectionBatch` (`run_card_action_on_selection`: `action: card_action`) — the selection, with the spoken label matched against each selected card's buttons.

These were added in the #2399 review (suggestion 3): naming one card's subtree cannot reach an arbitrary set — unrelated roots, siblings without their parent, cards on several daemons — so a `no_voice` reason pointing at `run_card_action_batch` claimed an equivalence that does not hold. `clearCardSelection` (`clear_card_selection`, no parameters) empties the selection, as the bar's **Clear** does, and answers "No card is selected." when it is already empty; it replaced the Select button's `toggleCardSelecting`, which went with the selecting mode (PR #2491 review). What stays off voice: `toggleCardSelected` (the checkbox flips; voice says which it wants), and `closeCardBatch`, reached by voice through `close` on the overlay stack.

## Not in this step

`when` conditions on actions (#2398) are not applied: a preview offers what is available today (an action is enabled, and a prompt action's agent is running). #2398 extends the preview's classification.
