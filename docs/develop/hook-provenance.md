# Hook-socket provenance

Issues [#1077](https://github.com/vfarcic/dot-agent-deck/issues/1077) and [#1129](https://github.com/vfarcic/dot-agent-deck/issues/1129). This page is the threat model for the per-spawn hook capability token: what it ties together, what it defends against, and — stated before anything else so nobody cites it as more than it is — what it does **not** defend against. It is also where the deck's **trust boundary** is recorded, because #1129 settled it: see [The trust boundary](#the-trust-boundary-the-os-user). The mechanism lives in [`src/hook_provenance.rs`](../../src/hook_provenance.rs), whose module docs carry the same argument next to the code.

## What it is not

**It is not a boundary against a deliberate same-uid adversary.** The token has to be readable by the legitimate sender, and the legitimate sender is a process running as you. On Linux, one process's environment is readable by other processes of the same uid through `/proc/<pid>/environ`. That was measured on the development box this was written on rather than assumed: with YAMA `ptrace_scope = 1`, a same-uid process that was neither ancestor nor descendant of the target could still read the target's `environ` and find the `DOT_AGENT_DECK_*` keys in it. A sibling agent that reads a victim pane's environment gets the victim's token and can then forge everything the gate checks. `hidepid=` on `/proc` does not change this — it hides processes belonging to *other* users.

Nothing inside this deck's reach closes that. Any mechanism whose secret is delivered to the agent falls the same way, and the alternatives that deliver no secret are covered below and do not work either. Genuine separation needs the agents to run under different uids, which the deck does not do.

## The trust boundary: the OS user

**Decided (issue #1129): the deck's trust boundary is the operating-system user. Every agent it runs is inside that boundary and is trusted with respect to every other agent it runs.** This is a policy, not a measurement — it holds because it was chosen, and it stays true until someone chooses otherwise. What follows is the argument, because a decision recorded without its reasoning is worth much less than one that can be re-examined.

The operating rule that falls out of it, stated so it can be quoted: **do not put an agent you would not trust with your whole working environment into a deck alongside agents you do.** Not "into the same orchestration" — into the same *deck*, and in practice into the same login session, because nothing below the uid separates them.

### Why the boundary sits there rather than at the agent

**Because above that boundary the adversary model stops being coherent.** An agent that would read a sibling's `/proc/<pid>/environ` to steal its capability token is a process with your shell, your checkout, your `~/.ssh`, your `~/.claude` and `~/.codex` credentials, your `git` remotes and your ability to write any file you can write. Forging a `delegate` into a sibling's workers is not the cheapest thing available to it — it is one of the *most* expensive. The same process can rewrite the project's `.dot-agent-deck.toml`, edit the hook scripts in the other agent's own configuration, replace the `dot-agent-deck` binary on `PATH`, or simply `kill` the sibling. A boundary that stops the expensive attack and leaves the cheap ones open is not a boundary; calling it one is the thing this page exists to prevent.

That is the same conclusion [#401](https://github.com/vfarcic/dot-agent-deck/issues/401) reached from the other end — "any process able to write to that socket already has code execution as the user, so it can do considerably worse than redirect keystrokes" — and it is that issue's option 1, taken deliberately rather than by default.

**What the boundary does not excuse.** It is a statement about a *deliberate* adversary, and the non-adversarial half is still a correctness obligation. An accidental forgery — a stale `DOT_AGENT_DECK_PANE_ID` inherited by an unrelated process, a recycled pane id, an agent that outlived the daemon that spawned it — is a bug whether or not anyone is attacking, and it is the case that actually happens. That is the half the token closes and keeps closing (see [The mechanism](#the-mechanism)); "same-uid agents are trusted" is not a licence to stop checking that a message came from the spawn it claims.

### Why not a uid per agent

It is the one option that separates the agents at the kernel's own boundary rather than confining one route to a token they can all still read, and it is **not** proposed. Not because it is merely large, but because it changes what the product is: a single-user developer tool becomes a multi-tenant agent runner, and every one of the following is an entry-price item rather than a follow-up.

- **A privileged component appears.** The deck today runs wholly unprivileged as you. Allocating uids needs a setuid helper, a root daemon, or user namespaces with `newuidmap`/`newgidmap` and a `/etc/subuid` allocation — a component with more privilege than the thing it supervises, on every platform separately.
- **The socket's permission model goes.** `0600` on the hook and attach sockets is what keeps other users out. With agents under other uids it has to become a per-agent socket or `0660` plus a shared group — and at that point `SO_PEERCRED`'s uid genuinely *does* become a discriminator, which is worth knowing, since [the argument against it below](#why-not-so_peercred) rests on every agent sharing one uid.
- **Credentials do not divide.** Each agent CLI reads its own config and credentials out of `$HOME` — `~/.claude`, `~/.codex`, `~/.config/opencode`. A per-agent uid needs a per-uid `HOME`, so either the user's single credential is copied into N homes (which *lowers* the bar rather than raising it: N copies of one secret, each readable by a uid that did not have it before) or each uid needs its own subscription, which the user does not have.
- **The filesystem stops agreeing.** Dispatched units work in git worktrees the daemon creates as you, in a repository owned by you. Git refuses a repository owned by another uid unless `safe.directory` says otherwise, and shared write access across uids means ACLs or a shared group on every path the deck writes — worktrees, `.dot-agent-deck/`, the state dir, the log. [`worktree-ownership.md`](worktree-ownership.md) is the existing surface that assumes one owner.
- **The supporting tooling assumes one uid too.** The e2e temp-root reaper decides by `kill(2)` liveness against pids it does not own ([`e2e-temp-dirs.md`](e2e-temp-dirs.md)); `daemon stop` resolves its peer through `SO_PEERCRED` ([`src/platform/peercred/`](../../src/platform/peercred/)).
- **It is Linux-shaped.** The unprivileged route above — user namespaces plus a `/etc/subuid` allocation — is a Linux facility. On macOS creating a user account needs administrator rights and there is no user-namespace equivalent; Windows has no uid at all. Each would need its own design and its own argument.

**The trigger for revisiting is a product change, not a security insight.** If the deck ever runs an agent *on someone else's behalf* — a hosted deck, a shared runner, an agent supplied by a third party — the boundary above is no longer the right one and the uid split is the entry price. Nothing learned about `/proc` changes that; a change in who the agents belong to does.

### Why not an LSM or sandbox profile

Landlock, AppArmor, SELinux or an agent's own sandbox could deny one agent read access to another's `/proc/<pid>/environ`, and that is genuinely narrower and cheaper than a uid split. It is still not a boundary, for reasons that compound rather than alternate:

- **It is per-platform, and the deck ships for three.** Landlock and AppArmor are Linux facilities; macOS and Windows would each need a separate mechanism, and this page would then have to be read per-OS.
- **The deck does not own the sandbox.** The deck spawns the command the user configured, and the confinement that command runs under is the agent's own — Codex's sandbox policy, Claude's permission model. Making the deck wrap each agent in a profile means the deck deciding what that agent may read, including the repositories and credentials it exists to use.
- **It closes one route to the token, not the capability.** An agent that prints its own environment puts its token into its pane's scrollback, which any attach client can snapshot; an agent's own files, its worktree and its shell are all still reachable. Denying `environ` while leaving those means a smaller published hole, not a separated agent.
- **A partial denial invites the wrong reading.** The failure this page is written against is someone citing the mechanism as more than it is. "Confined on Linux, when the profile is installed, against one of several routes" is exactly the kind of claim that gets quoted without its qualifiers.

None of that makes a profile worthless — a user who wants one is not wrong, and it does raise the cost of the specific `/proc` read. It is not a thing this project can claim, which is a different statement.

### What the token is still for, given all that

Nothing above makes it pointless, and the reasoning that it might is the reason this section exists.

- **It removes the *published* escalation.** Pane ids are advertised by `list-agents`, by `daemon status` and in the TUI. The token is not: it is absent from the `AgentRecord` clients receive and the daemon never logs it. So the #1077 path — read a pane id off the daemon's own status output and forge a message — no longer reaches anything, and an adversary needs a *different* capability, reading another process's environment — a deliberate act rather than a by-product of ordinary work.
- **It binds a message to one spawn**, which is the half that catches the accidental forgeries described above. That is a correctness property, not a security one, and it is the half that earns its keep on an ordinary day.

## The problem it does address

Every message on the hook socket names a `pane_id`, and before this change that name was the whole of the claim. The CLI copies `DOT_AGENT_DECK_PANE_ID` into the field, and the daemon acted on it. Consequences, all pre-existing:

- `delegate` naming an orchestrator's pane makes the daemon write and submit a task prompt into **every worker pane of that orchestration**.
- `work-done` naming a worker's pane makes the daemon write feedback into **the orchestrator's pane** — a different pane from the one the message claims to come from.
- PRD #220's dispatch return route is one-shot, so a forged completion **spends** it and the real unit's later completion resolves to nothing.

The socket is owner-only, which keeps other OS users out. It does not separate the several agents the deck deliberately runs under one uid, and those agents can read every pane id off the daemon's own `list-agents` / `daemon status` output.

## The mechanism

1. **Mint.** Every `AgentPtyRegistry::spawn_agent` mints 256 bits from the operating system (`getrandom`), keeps it on the agent's `RunningAgent`, and injects it as `DOT_AGENT_DECK_PANE_CAPABILITY` beside the pane id and agent id. A caller-supplied value is stripped, not honoured, so no two records can carry one token. The variable's name deliberately avoids `KEY`, `SECRET` and `TOKEN`: Codex's `shell_environment_policy` strips names matching `*KEY*`/`*SECRET*`/`*TOKEN*` from its shell tool whenever `ignore_default_excludes = false`, and a capability that never reaches the agent's shell turns every legitimate `work-done` from that agent into a silent refusal. A respawn mints a fresh one. The inherited value is also scrubbed from the base environment, so a daemon started from inside another deck's pane does not pass that deck's token on.
2. **Present.** The CLI reads the variable and puts it in the `token` field of every `DaemonMessage` it sends — all eight verbs: `delegate`, `work_done`, `get_seed`, `dispatch`, `list_targets`, `restart_role`, `spawn_role`, and since issue #1383 `ack`. Since issue #318 it also adds a top-level `token` key to every raw `AgentEvent` line it writes: `dot-agent-deck hook` (which OpenCode's plugin and Codex's hooks invoke too), `dot-agent-deck agent-event` and `dot-agent-deck wrap`. The key is omitted when there is no token, so a producer outside the deck writes exactly the JSON it always did.
3. **Check.** `run_hook_loop` classifies every `DaemonMessage` before any handler runs. It resolves **token → record → pane** and compares that pane with the one the message names. Raw `AgentEvent` lines go through the same gate, with one difference described in [Raw `AgentEvent` traffic](#raw-agentevent-traffic).

The direction of step 3 is the point. The token is not an extra field checked against the claim; it *is* the claim. So an agent holding a perfectly valid token of its own still cannot name a sibling's pane.

| message presents | the daemon | verdict |
| --- | --- | --- |
| a token minted for the pane it names | admits it | `Attested` |
| a token minted for a **different** pane | refuses | `WrongPane` |
| a well-formed token this daemon never minted | refuses | `UnknownToken` |
| a value not shaped like a token | refuses | `Malformed` |
| no token, for a pane this daemon issued one | refuses (see the policy below) | `Missing` |
| no token, for a pane this daemon never issued one | admits it, as before | `Unattested` |

A refused `delegate`, `restart_role`, `spawn_role` or `list_targets` gets an `error` on the connection. A refused `get_seed` gets the same `{"seed":null}` as "nothing pending", so the pane's real occupant still receives its seed through the PTY-injection safety net. The log line names the verb, the claimed pane and the reason, and never the token.

**`work_done` and `dispatch` are told too, since issue #1129** (and `ack`, which joined that family in issue #1383 — though its CLI exits 0 either way, because a worker told to acknowledge first must never be derailed from its task by a failed acknowledgement). They have no response type of their own — their handlers produce nothing — so the daemon answers both with a `SignalAck` (`src/event.rs`) written at the gate, before the handler runs, and the CLI turns a refusal into a non-zero exit naming the reason. Until then they read no reply at all and exited 0 whatever the daemon did, which made a refused report indistinguishable from an acted-on one. The sender that matters here is not the adversary but the **legitimate** one: a `dot-agent-deck` binary in the pane older than the daemon forwards no token, is refused as `missing_token`, and used to report success on a completion that went nowhere. [#1182](https://github.com/vfarcic/dot-agent-deck/issues/1182) is that failure mode observed in the wild, where the silence also masked an unrelated bug underneath by sending readers to the daemon log's refusals instead of to the cause.

Three things the ack deliberately does **not** claim, because the whole point of writing it at the gate is that it costs the caller nothing to wait for:

- It is not a receipt for the work. `accepted: true` means the gate admitted the message, and the handler has not run yet. `dispatch`'s handler is awaited inline in the hook loop and spends a whole worktree-create-and-spawn; an ack written after it would park the calling agent for the duration.
- It does not make the *other* silent drops visible. A `dispatch` from a pane the registry holds no record for, and a `work_done` from a pane in no role map with no retained dispatch return, are both still logged and dropped with nothing said to the sender. Reporting those means answering after the handler, which is the trade above.
- It does not reach an **older** CLI, which does not read the line. That population is exactly the one the `missing_token` refusal is about, so the remedy stays what it was: update the binary the pane invokes, or set `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` on the daemon.

Telling the caller discloses nothing a caller on this socket could not already obtain. A refusal names why, and `missing_token`'s message says the claimed pane was issued a token — which tells a caller that guessed a pane id that the pane is real. Pane ids are already published by `list-agents`, by `daemon status` and in the TUI, and `delegate`, `restart_role`, `spawn_role` and `list_targets` have answered their refusals on this same socket since #1077, so any caller able to send one of those already had the same oracle. The refusal text is what keeps it no wider: it never echoes the presented token and never names the pane a token actually belongs to. The daemon does not publish the token anywhere else either — it is held on `RunningAgent`, not on the `AgentRecord` clients receive — but an agent that prints its own environment puts its token into its pane's scrollback, which any attach client can snapshot.

### Raw `AgentEvent` traffic

Issue #318 extended the gate to the status events that drive a card. `classify_event` (`src/hook_provenance.rs`) decides them, delegating to the same `classify` the verbs use, and the hook loop applies the verdict **before** anything else touches the event: a refused event reaches no registry side effect (the Codex rollout arm, the persisted agent type), no `AppState` and no broadcast. The broadcast is the one that matters most, because an attached TUI or desktop applies whatever the daemon sends it with no registry of its own, so a refusal placed after the fan-out would refuse nothing there. No reply is written for a raw event, refused or not: hooks are fire-and-forget, and an agent may read what its hook prints.

The token is read off the line with `PresentedToken` (`src/event.rs`) and is never a field of `AgentEvent`, so nothing the event reaches afterwards — the session journal, the broadcast, an older TUI's decode — can carry it.

| event names | event presents | the daemon | verdict |
| --- | --- | --- | --- |
| a pane this daemon issued a token for | that pane's token, and the token's own `agent_id` | admits it | `Attested` |
| a pane this daemon issued a token for | that pane's token and no `agent_id`, from a generation that still speaks for the pane | admits it | `Attested` |
| a pane this daemon issued a token for | that pane's token and no `agent_id`, from a generation a successor has replaced on the pane | refuses | `Superseded` |
| a pane this daemon issued a token for | that pane's token with a **different** `agent_id` | refuses | `WrongAgent` |
| a pane this daemon issued a token for | another pane's token, an unknown token, or a malformed value | refuses | `WrongPane`, `UnknownToken`, `Malformed` |
| a pane this daemon issued a token for | no token | refuses (see the policy below) | `Missing` |
| a pane this daemon **never** issued a token for | anything, or nothing | admits it as an outside agent's | `Unattested` |
| no pane, and an `agent_id` the daemon spawned without a pane | the same matrix, against that agent's token | as the rows above | as the rows above |
| no pane, and no `agent_id` the daemon spawned paneless | anything, or nothing | admits it as an outside agent's | `Unattested` |

**The never-issued row is deliberately different from the verbs'.** For a `DaemonMessage`, an unknown token is refused whatever pane it names, because the refusal protects authority. For a status event naming a pane this daemon never spawned, refusing an unknown or mismatched token protects nothing — the sender can drop the token and be `Unattested` anyway — and it would cost a real case: an agent that survived a daemon restart keeps posting with its old daemon's token, and its events are what paint the orphaned badge on its card (issue #770). So a never-issued pane is `Unattested` whatever it presents.

**`WrongAgent` binds the generation as well as the pane.** Every first-party producer — the hook CLI for Claude Code, Codex, OpenCode and Devin, `agent-event` (Pi's extension and shell roles), `wrap`, and subagents' hooks, which run in the same process environment — reads `DOT_AGENT_DECK_AGENT_ID` and the token from the same spawn's environment, and a respawn replaces both. So an attested event naming another agent is a holder of one generation's token speaking for a different generation of the same pane.

**`Superseded` closes the same door for an event that names no agent.** Such an event would otherwise be judged by its pane alone, and a pane is a reusable slot: a leftover process of a replaced generation, still holding that generation's token, could drop `agent_id` and have its report credited to whichever generation holds the pane now. So the token's own spawn is asked instead (`HookTokenDirectory::token_owner_speaks_for_pane`, which is `generation_ownership(pane, owner)`), by the same retirement rule a tagged event is judged by: a lone retiree with no successor still speaks for its pane, so its late token-bearing final `Idle`/`SessionEnd` lands, and a generation a successor has taken the pane from does not. The gate asks first; because a successor can claim the pane between the gate and the apply, the daemon asks again under its state lock immediately before the fan-out (`ingest_hook_event`) and once more at admission, where `AppState::apply_hook_event_watching_waiting` judges the event by the token's generation, passed as an argument, while leaving its absent `agent_id` in place for the untagged-status rules.

**Registry side effects follow the generation that sent the event, not the pane.** An attested event's generation is its token's owner, or the agent it names. The persisted agent type is written by `AgentPtyRegistry::set_agent_type_for_generation` onto that generation's record, and only while it still speaks for the pane, decided under the registry's lock in the same critical section as the write; the old pane scan could land on a successor's record, so a replaced generation's own tagged `SessionStart` typed its successor. A work event lifts the quota-block latch of that generation only (`quota_note_work_event(pane, generation)`), so a replaced generation's untagged report cannot clear its successor's block. A tagged report from a displaced generation is still attested — it keeps its path to the state's generation check, and to its own card on a client — so these keys, not a gate refusal, are what keep it off the successor's record.

**One type write has no generation to follow, and it is a `warn`-mode compatibility limitation.** The registry type write reaches `set_agent_type_for_generation` only for an event the gate did not classify as an outside agent's (an unproven event writes no registry type at all), and for a pane this daemon issued a token to, an admitted event that carries neither a token nor an `agent_id` exists only under `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` (under `enforce` it is refused as `Missing`). An outside agent's token-less, agent-less event is admitted under either policy, as `Unattested`, but never reaches the setter. For the `warn`-mode event, `set_agent_type_for_generation` falls back to the pane's single speaking generation, filling its type only if it is still unknown, and doing nothing when no generation or more than one speaks. With no identity evidence it cannot tell a legacy report from an exited generation A apart from one from the current generation B: if B's type is still unknown, A's late report types B, and because the setter only fills an unknown type, B's own later report does not correct it. So under `warn` not every type write follows the sending generation; under `enforce`, and for every token-bearing event under either policy, it does.

**What an outside agent's event can do.** An `Unattested` event is admitted, and the daemon stamps it with `daemon_unproven` (`UNPROVEN_METADATA_KEY`, stripped from producer input) before the broadcast. `AppState` files its card as UNPROVEN (issue #601): the card is drawn and updated, but its pane is never put into `managed_pane_ids`, and it counts against `MAX_UNPROVEN_SESSIONS` (issue #697, below). With an ownership oracle installed (the daemon) every `SessionStart` reaching the auto-registration branch is unproven, since anything that reached it is by definition not registry-proven; a process without one (the TUI, the desktop fold) reads the daemon's marker, and still treats an unmarked start as its own pane arriving before `register_pane`.

What an unproven event may NOT do, in every process that applies it:

- **Reach a proven card, beyond the one restart-survivor exception below.** It is refused when the card key it resolves to — after the #925 re-key, before anything is mutated — is a card the process holds as its own, whichever pane either side names: a paneless report naming a paned card's key and a paned report naming a paneless card's key are refused like a same-pane one. The pane-reuse adoption and the retire step consider only outside cards for it. So it cannot update, relocate, end or retire a proven card, and cannot enrol one in the evictable set.
- **Be promoted by a later lookup.** The marker is the gate's verdict and is authoritative: a marked event never takes the owned arm of `AppState::apply_event`, so a pane issued a token between the gate classifying the event and the apply does not turn it into its new owner's report. In a process that registered the pane itself it is refused.
- **Touch the registry.** It does not arm the Codex rollout tailer, persist an agent type onto a record, move the quota-block latch, or open, close or record a waiting-for-input episode.
- **Write an agent-keyed record.** An event carrying `daemon_unproven` records nothing in `agent_generation_closures`, in the daemon or a client, the restart-survivor exception included, so no stream of invented agent ids can grow that map.

**The restart-survivor exception is compatibility, not ownership.** A client with no registry that stayed attached across a daemon restart still registers the panes whose agents survived it, and the new daemon never issued those panes a token, so their reports arrive marked unproven and the client would refuse every one: the card would freeze, and for a role pane (issue #770) the client would never learn the role is orphaned. So the daemon stamps a second verdict on an unproven report naming a pane: `daemon_no_live_agent` (`DAEMON_NO_LIVE_AGENT_METADATA_KEY`, stripped from producer input) when it holds no live agent on that pane, and additionally `orchestration_orphaned` when the pane is also a role pane with no role-map entry. A marked event carrying either stamp, on a pane the client registered, goes to `AppState::apply_orphan_survivor_report` instead of the ordinary path, and only when `orphan_survivor_card` finds exactly one card of the client's own on that pane whose `agent_id` equals the event's (both absent counts). There it may update that card's bounded reporting state — its status, through the same `apply_status_transition` every card uses (which also moves the active tool, tool count, block and subagent-wait fields), its last activity and its capped event journal — and, only when the daemon stamped `orchestration_orphaned`, its orphan badge, with no structural or per-pane/per-agent writes: the session key the event names is ignored, it creates, re-keys, adopts, retires and removes no card, a `SessionEnd` only settles the card `Idle`, it keeps the event's unproven standing for every other guard, and it writes no per-pane or per-agent record. With no matching card it is refused like any other marked event. The daemon decides both stamps under its state lock, sampling the registry's live panes (and, for the orphan stamp, its role map) there rather than before waiting for the lock, so a pane the deck spawned an agent on while the report waited is stamped with neither.

### The unproven-card budget

Issue #697. `AppState` keeps at most `MAX_UNPROVEN_SESSIONS` (256, `src/state.rs`) unproven sessions. The unit is the session, not the pane, because one outside pane can carry any number of sessions. A pane is admitted as an outside agent's for exactly as long as at least one unproven session sits on it, so ending or evicting its last session also withdraws the pane: a later status for it without a fresh `SessionStart` is rejected.

Admitting a new unproven session at the cap evicts the least recently active one, ordered by when this process applied each session's last event — never by the producer-supplied timestamp, which a flood could stamp in the future to make itself un-evictable. An outside agent that keeps reporting therefore outranks a one-shot flood entry, and the set heals once the flood stops. Cards a process holds as proven — in the daemon, agents this daemon spawned — are never counted and never evicted. A daemon-restart survivor is not one of them on the daemon: a previous daemon spawned it, the current one never issued its pane a token, so its reports are `Unattested` and its daemon-side card is an unproven card, counted and evictable like any outside agent's. (A client that still registers the survivor's pane keeps its own card for it, which is proven there and not counted: the daemon's eviction of its own card for the survivor leaves it in place, and the survivor's `SessionEnd` settles it `Idle` rather than removing it.) Evicting or ending a session also clears what `AppState` keeps per pane for an outside pane left with no card (`pane_started_at`, `pane_hook_session`, `pane_generation_closures`, `pane_generation_announced`, `untagged_status_panes`, `waiting_superseded_sessions`), and an event carrying `daemon_unproven` records nothing in the agent-keyed `agent_generation_closures`. The bookkeeping follows the card's pane: a card admitted without a pane that later learns one has its entry moved to that pane, so the pane's maps are cleared when the card goes and the eviction announcement names the pane the card carries. When the deck registers a pane as its own, any outside card on it is removed with its bookkeeping rather than left as an uncounted second card.

`AppState::retained_map_sizes` (test-only) names every per-pane and per-agent map an unproven event can write; `hook_provenance_audit_outside_flood_bounds_every_retained_map` floods the real socket with three times the cap and asserts each stays within it, and `hook_provenance_audit_client_orphan_flood_retains_nothing_per_agent` does the same for a client's orphan exception.

Each unproven session keeps an 8-event journal rather than the managed 50, because a retained event can be as large as a hook line: 256 journals at the managed size could hold close to a gigabyte, at 8 about an eighth of that. `SubagentWait::subagent_ids` is capped at 64 for every session, keeping the newest.

The TUI and the desktop fold apply the same bound to the same ordered stream, so a client attached since the daemon started evicts the same session itself. For a client that attached later and holds a different set, the daemon also broadcasts each eviction as a `SessionEnd` marked `daemon_unproven_evicted` (`UNPROVEN_EVICTED_METADATA_KEY`, stripped from producer input), queued by `apply_event` and sent by `ingest_event` after the event that caused it, under the same lock. A client removes a card on that announcement only when it holds the card as an outside agent's itself: the daemon files a restart survivor's reports as an outside agent's, so without that check an outside sender could have the daemon announce the eviction of a card under the key and pane of a survivor card a client still holds as its own (`hook_provenance_audit_client_eviction_removes_only_an_outside_card`). And a client drops a card's outside-card accounting only together with the card (round-3 audit B1). The two sides can file one outside card under different keys — the #925 cross-pane re-key depends on the cards each side already holds, so a client that attached late can keep `s` on pane B where the daemon qualified it to `B::s` — and an announcement naming a key the client holds on a different pane once removed the accounting while keeping the card, leaving it counted nowhere: outside the budget, read as the client's own, and refusing its own sender's reports. The client now looks for its card on the announced pane, under the announced key or that key with the pane's qualification added or removed, and removes the card and its accounting together or neither. Spelling is not enough to identify the card (round-4 audit B1): a producer's literal key can equal another session's qualified one, so a client can hold two cards on the announced pane that both fit it. The candidate must therefore also carry the evicted card's `agent_id` (the announcement carries it, `None` included), and the client removes it only when exactly one candidate does; with none, or more than one, it declines and removes nothing rather than guess, since a wrong guess loses a live card and its journal and declining only leaves a card for the client's own budget to retire (`hook_provenance_audit_eviction_reconciliation_matches_the_evicted_agent`, `hook_provenance_audit_ambiguous_eviction_removes_nothing`). A divergence that does not fit that shape (an adoption that landed on a different card, say) matches nothing; the client's card stays counted against its own budget and goes when that budget evicts it (`hook_provenance_audit_mismatched_eviction_neither_promotes_nor_strands`, `hook_provenance_audit_mismatched_evictions_keep_the_client_bounded`). An older client reads it as an ordinary `SessionEnd`: it removes the same card, but because an older client registered the outside pane as its own when the card was drawn (it does not read `daemon_unproven`), it then restores an empty placeholder card for that pane, as it does when any session on one of its panes ends.

### Why "was this pane issued a token" is not derived from the live records

A pane can be momentarily without any record while still holding authority: `respawn_agent_for_pane` removes the old record before `spawn_agent` inserts the new one, the daemon's role maps survive that, and a `clear = true` role respawns on every delegation. An answer derived from the live records would read that window as "never issued" and admit a token-less forgery landing in it. So the registry records each pane in a separate set at the moment its token is minted, under the same lock that reserves the spawn, and never prunes it.

### Why `Unattested` is not the obvious hole

It is reached only for a pane id this daemon has never issued a token for. In the daemon, the role maps that carry delegate and work-done authority are written only by `AppState::register_orchestration_role`, and each of its callers invokes it only after its spawn returned `Ok` — which is after the pane was recorded as issued. So a message landing in `Unattested` names a pane that holds no role. That was established by enumerating the write sites; a new writer of those maps that does not go through a spawn would break it.

## Why not `SO_PEERCRED`

It is the obvious reach, and it does not answer the question.

- **The uid is the wrong discriminator.** Every agent the deck runs has the same uid — that is the threat. The socket is already `0600`, so a uid check separates nothing the filesystem does not already separate.
- **The pid cannot be resolved to a pane in time.** The peer pid is unforgeable, and a walk up the process tree could in principle find which pane's PTY the sender lives under. But `work-done` and `dispatch` are fire-and-forget: the CLI connects, writes one line and exits, so by the time the daemon has the line the sender is routinely gone. A check that answers "cannot tell" for a legitimate sender has to fail open, and one that fails open is not a check — an adversary exits first.
- **When it does answer, it is weaker.** It costs a `ps` sample per message, is defeated by `setsid` and by re-parenting to init, and a same-uid adversary controls its own process tree.

## The `DOT_AGENT_DECK_HOOK_PROVENANCE` knob

Set on the **daemon**. Anything other than exactly `warn` (case-insensitive) is `enforce`, including a typo — a switch that weakens a check must not flip by accident.

`warn` moves exactly one verdict: `Missing` is admitted, with a per-message `warn!` naming the pane. It exists for the one situation in which a legitimate sender produces `Missing`: the `dot-agent-deck` binary invoked inside a pane is **older** than the daemon that spawned it, so it does not know to forward the token the daemon put in its environment. That happens when a daemon is started from a build other than the one on `PATH`. The refusal message names this variable so whoever hits it can act.

It does **not** relax `WrongPane`, `UnknownToken` or `Malformed`. None of them can be produced by an older CLI — an older CLI sends no token at all — so tolerating them would buy compatibility with nothing and re-open the forgery the gate exists to stop.

## Compatibility

The wire change is additive and moves no `PROTOCOL_VERSION`, which versions the attach socket rather than the hook socket: `token` is `#[serde(default, skip_serializing_if = "Option::is_none")]` on every payload, an older daemon ignores the key, and a CLI with no token emits exactly the JSON it always did. What changed is what a newer daemon **does** with a missing token, which is a semantic break and is recorded as one in `changelog.d/1077.breaking.md`.

| CLI | daemon | result |
| --- | --- | --- |
| new | new | enforced |
| new | old | works — the old daemon ignores `token` |
| old | old | works, unchanged |
| old | new | `Missing` is refused; set `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` on the daemon, or put the matching binary on the pane's `PATH` |

An agent that survives a daemon restart holds a token the new daemon never minted, so its messages are refused as `UnknownToken`. That changes what the log says rather than what happens: the role maps died with the old daemon, so those messages already had nowhere to route. Its raw status events are not refused: the new daemon never issued its pane a token, so they are `Unattested` and still reach the TUI, which is what paints the orphaned badge.

Issue #318 is the same shape for raw events and is recorded as its own break (`changelog.d/318.breaking.md`, `CONTRACT_BREAKS` entry `318-hook-event-capability-token`): a `dot-agent-deck` in a deck-spawned pane that is older than the daemon sends token-less status events, which a newer daemon refuses as `missing_token`, so that pane's card stops updating. The remedy is the same. The four metadata markers (`daemon_unproven`, `daemon_unproven_evicted`, `daemon_no_live_agent`, `daemon_attested_owner`) are additive: an older client ignores the first, third and fourth and reads the second as an ordinary `SessionEnd`; a newer client against an older daemon receives none of them and keeps the older behaviour, an outside agent's pane included. An older client therefore keeps the check-to-broadcast window described under [What stays open](#what-stays-open) that `daemon_attested_owner` closes for a newer one.

**A newer client fails closed on one legitimate report, deliberately.** A client has no registry, so `daemon_attested_owner` is all it has to judge an untagged frame by, and it refuses one whose owner differs from the `agent_id` of the card the frame would land on — the direct key, or the one card on the pane an untagged adoption would pick. That is what keeps a replaced generation A's late untagged report off its successor B's card, and the comparison cannot tell it apart from the reverse: when B, the pane's current token owner, reports **without** `agent_id` while the client still holds A's card (B's tagged start has not reached it, or never will), the daemon admits and adopts the report and the client refuses it. Accepting a mismatching card would reopen the A-onto-B case, so the trade stays. It is reachable only when B's reports lose their agent id — every first-party producer reads `DOT_AGENT_DECK_AGENT_ID` from the same spawn environment as the token, so a wrapper or hook that drops that one variable and keeps the token is the realistic cause — and recovery is not automatic for such a producer, since it may never send the tagged frame that would draw B's card. Recovery is to restore `DOT_AGENT_DECK_AGENT_ID` in the agent's environment, or to resynchronize the client (detach and reattach), which replaces its cards with the daemon's. The same comparison also refuses an owner's untagged report whose selected card carries a third agent's identity; that is conservative, and grants the report nothing. `hook_provenance_audit_current_owner_untagged_report_is_refused_on_a_predecessors_client_card` pins the behaviour.

## What stays open

- **Same-uid `/proc/<pid>/environ` reading** is **not** open — it is decided, above: [The trust boundary](#the-trust-boundary-the-os-user). It is listed here so a reader arriving at this section does not go looking for a fix that is deliberately not coming. The half of [#1129](https://github.com/vfarcic/dot-agent-deck/issues/1129) that *was* code — a refused `work-done` or `dispatch` being invisible to the command that sent it — is closed by the `SignalAck` described above.
- **The silent drops the ack does not cover** — a `dispatch` from a pane with no registry record, and a `work_done` from a pane in no role map with no retained dispatch return. Both are logged and dropped with nothing said to the sender, for the reason given above (answering them means answering after the handler). Not tracked by its own issue; filed here so it is not mistaken for something #1129 closed.
- **Raw `AgentEvent` traffic is gated for deck-spawned panes since issue #318, and not for anything else.** What is closed: a status event naming a pane, or a paneless agent, this daemon spawned is accepted only with that spawn's token, so a same-user process that knows a deck pane's id can no longer change its card, retire it with a forged `SessionStart`, or end it. That includes issue #1383's delivery signal: the delegate re-send treats a worker's turn event (`Thinking`, a tool call and the like) as proof its task arrived, and for a deck-spawned worker that event is now attested, so a forger that knows the worker's pane and agent ids can no longer stop its re-sends. What is not: an outside agent's events — a pane or paneless agent this daemon never spawned — carry no proof and are admitted on the sender's word, so any same-user process can draw, update or end an outside agent's card and can occupy the unproven-card budget (its least-recently-active entries are evicted first, so a genuine outside agent that keeps reporting is evicted last). Under `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` a token-less event for a deck pane is admitted, exactly as for the verbs. On a client that still shows a card on a pane it registered and the daemon holds no live agent on — a daemon-restart survivor's, typically — a same-user process that knows the pane id and that card's agent id can change that one card's bounded reporting state, and on a role pane badge it orphaned (the restart-survivor exception above); it cannot reach any other card through it, draw or remove a card, or grow the client's state. On the daemon a survivor's card is an outside agent's like any other. Separately, the attested-generation check has a short check-to-use window, and it is closed on the client side rather than removed: `ingest_hook_event` asks whether an untagged report's token generation still speaks for its pane under the state lock, and its registry writes are keyed to that generation, but a respawn does not take the state lock, so a successor can claim the pane in the synchronous section between that check and the broadcast. The daemon's own apply re-judges such a report by the token's generation and refuses it. An attached client has no registry, so the daemon stamps every attested frame with `daemon_attested_owner`, the agent the token was minted for (removed from producer input first, like every daemon marker), and a client refuses a marked frame that names no agent when the card it would land on — the card under its session key, or the one card on the pane an untagged status report would adopt — carries a different `agent_id`. So on a client that reads the marker, a replaced generation's late status report or `SessionEnd` no longer reaches its successor's card, and in particular no longer removes it and restores a placeholder (`hook_provenance_audit_untagged_relay_cannot_reach_a_successors_client_card`). The frame's own absent `agent_id` is left as it is, so the untagged-status rules downstream are unchanged. What stays: a client older than the marker keeps the window, and a frame whose destination card carries no `agent_id` at all is not refused, as there is nothing to compare. A report the under-lock re-check drops is logged with `reason="token_generation_replaced"`. And the same-uid `/proc/<pid>/environ` read above defeats this as it defeats the verbs' gate. Issue #1243's echo gate is a heuristic of the kind #1383's signal was, on the output side, and the token does not reach it: it releases the Enter of every submit the deck makes once the payload's tail — for the delegate pointer, its delivery id — appears anywhere on the target's screen, so a same-user process writing to that terminal can print it early. At worst that makes that pane's submit as early as the fixed `SUBMIT_DELAY` it replaced, the in-place re-send recovers a pointer left unsubmitted that way, and no other pane is affected. [Delegate delivery](delegate-delivery.md#trust-bounds) has both signals in context.
