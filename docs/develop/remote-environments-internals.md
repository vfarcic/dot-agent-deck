# Remote environments: rationale, mechanisms and validation history

Maintainer notes moved out of the published pages `docs/remote-environments.md`, `docs/remote-requirements.md` and `docs/remote-recipes.md` when they were rewritten for the user's agent (PRD #1419). The published pages say what a user does and sees; this page keeps why the remote surface is built the way it is, how parts of it work underneath, and what has and has not been validated. Code references: `src/remote.rs`, `src/connect.rs`, `src/remote_doctor.rs`, `src/remote_tunnel.rs`, `src/deck_list.rs`, `src/platform/paths.rs`, `src/platform/ipc/unix.rs`.

## Validation record

- **Linux** was validated end to end on a fresh Ubuntu 24.04 LTS VM. Nothing in `remote add` checks the distribution; it reads `uname -s -m` only. The "Required" host list was confirmed empirically on that VM; the "Recommended" hardening was not re-validated end to end on a clean provision.
- **macOS** was validated end to end on 2026-09-19 ([#1158](https://github.com/vfarcic/dot-agent-deck/issues/1158)): `remote add` over ssh, `connect`, a Claude agent working in a pane, a disconnect and a reconnect with the session intact, on a Mac Studio running macOS 26.6.2 (`Darwin arm64`), deck 0.41.0 on both ends. `remote doctor` reported the same as for a working Linux remote. An Intel Mac (`darwin-amd64`) has not been exercised.
- **Still open on macOS** ([#1176](https://github.com/vfarcic/dot-agent-deck/issues/1176)): reboot behaviour, the `$DOT_AGENT_DECK_SOCKET` override, hook delivery asserted directly rather than inferred from an agent reaching `Working`, and an Intel Mac. Whether the deck should ship its own launchd plist is [#1172](https://github.com/vfarcic/dot-agent-deck/issues/1172). On the validation host the socket was observed at `/tmp/dot-agent-deck-501.sock` with mode `srw-------`; that run predates or coincides with the per-user fallback directory from #1121, so treat the path as historical.
- **Reverse tunnel**: verified end to end with a service reachable only from the laptop's loopback, fetched from a remote through the tunnel. Not validated against a real corporate VPN ([#97](https://github.com/vfarcic/dot-agent-deck/issues/97)). [`scripts/reverse-tunnel-validation.sh`](../../scripts/reverse-tunnel-validation.sh) is the manual, container-based validation path: it runs sshd in a container with a service reachable only from the laptop's loopback and reproduces every `remote doctor` failure mode deterministically, which is how the indistinguishable-error case was found. Two false-pass traps it guards against: an auth failure exits 255 exactly like a forward collision, and a wholesale forwarding refusal produces the same error text as a port collision, so a collision assertion has to verify that the first session actually bound before drawing a conclusion.
- **Kubernetes as a transport** is designed in [#81](https://github.com/vfarcic/dot-agent-deck/issues/81) and not shipped. `--type kubernetes` parses and is refused (`RemoteAddError::KubernetesNotYetImplemented`); a registry row of that type is listed by the picker but refused by `connect`.
- **systemd user unit and LaunchAgent**: the published pages give a unit and a plist as starting points. Neither is installed by the deck and neither has been validated across a reboot. The unit uses `Restart=on-failure` rather than `always` so that a daemon the TUI's build-version restart terminates is not immediately respawned by systemd beside the one the TUI lazy-spawns; that interplay has not been exercised. `Restart=on-failure` is also what an accepted upgrade restart relies on (below).

## Why the laptop's version never blocks `connect`

`connect` runs the remote binary's TUI over `ssh -t`, and that TUI attaches to the remote daemon; the laptop contributes ssh and a terminal. The laptop's compiled-in `PROTOCOL_VERSION` is never a party to any wire conversation in this flow, so since issue #491 `connect` does not compare it with the remote's (PRD #161 D3). What remains is a *floor*: the remote must answer `--version` with `dot-agent-deck <version>` and must answer `daemon hello`. The upgrade offer is the only version-aware step, and it is newer-only, default-no, skipped without a TTY, and falls back to the existing install on failure, so it can never strand a user from their session.

## Why `remote add` and the probes use `BatchMode=yes`, and the live session does not

`SystemSshExecutor` forces `BatchMode=yes` so the CLI fails fast on a missing key or an unknown host key instead of wedging on a prompt it cannot show. The interactive `ssh -t` session in `build_connect_command` deliberately omits it, so a prompt there would reach the user's terminal — but the version and handshake probes run first and do use it, so in practice a first-time host key has to be accepted with a plain `ssh` before `connect` too. The published pages tell users exactly that.

## Keepalive and reconnect design (PRD #148)

A sleeping laptop's TCP connection dies silently. Without `ServerAlive*`, an `ssh -t` session never notices and the TUI freezes on a dead socket. The live session uses `ServerAliveInterval=15` / `ServerAliveCountMax=3` (about 45 s to detect), higher than the probe path's `ServerAliveCountMax=1`, so a brief real blip (15–30 s) does not tear down a working session. ssh exit status 255 uniquely marks a transport failure (ssh passes a clean remote exit through verbatim), which is what auto-reconnect keys on. `MAX_CONNECT_ATTEMPTS = 5` bounds it so a genuinely gone remote surfaces an error instead of looping; `RECONNECT_BACKOFF = 2 s` gives Wi-Fi association, DHCP or a VPN a moment. Since issue #858 a reachability probe failure on any attempt, including the first connect, counts against the budget, and the first connect and later reconnects keep separate budgets. Exposing the timings as configuration was left as a possible future improvement.

`DOT_AGENT_DECK_SSH_PROBE_TIMEOUT_SECS` (default 10, clamped to 1–3600) becomes `ConnectTimeout` and `ServerAliveInterval` on the probe's ssh, which bounds ssh's own wallclock at roughly twice the value; the laptop-side kill is armed later, at `remote::wallclock_kill_secs` of it. Issue #858: armed at the raw value, the kill was the binding constraint and reported a connection ssh had not finished with as an unreachable host. Raising the default is therefore not the remedy for a slow link failing at the deadline; it scales both bounds together. The lower clamp exists because OpenSSH treats `ConnectTimeout=0` as no timeout and `ServerAliveInterval=0` as keepalives off; the upper clamp prevents `Instant + Duration` from panicking between spawn and poll, which would leak an unreaped ssh child.

Before issue #344 a forward that could not bind (`ExitOnForwardFailure yes` with the port taken) was classified as an unreachable host and burned the reconnect budget against a network path that was never broken. It now surfaces as `SSH forwarding failed` and is not retried.

## Detach versus quit, and Stop

Before PRD #93 Phase 2 / M4.2 the quit dialog offered Quit / Detach / Cancel, where Quit exited without telling the daemon and Detach sent an explicit signal so the daemon's logs could tell a voluntary detach from a network drop; both left agents running. Every pane is now daemon-backed, so the dialog is Detach / Stop / Cancel (PRD #92 F1 added Stop as the "take everything down" gesture, with a second confirmation; Detach stays the default so muscle memory is not destructive).

## `remote doctor`: what "read-only" means and why

`remote doctor` issues no mutation of its own. Every remote command it runs is a query: `sshd -T` for the resolved sshd policy, a `/dev/tcp` connect for the liveness of a forward. Every ssh session it opens passes `-o ClearAllForwardings=yes -o ControlMaster=no -o ControlPath=none -o PermitLocalCommand=no -o UpdateHostKeys=no`, so it creates none of the forwards the `Host` block asks for, leaves no master connection, runs no `LocalCommand` and does not rewrite `known_hosts` on key rotation. Consequences: its own probes are immune to the forwarding problems it diagnoses, and `ForwardBound` reports pre-existing state rather than a listener it created. The one command without those options is `ssh -G`, which never connects and whose purpose is to show the forwards the others suppress.

`ClearAllForwardings` does not touch agent or X11 forwarding, so each session also passes `-o ForwardAgent=no -o ForwardX11=no -o ForwardX11Trusted=no -o GSSAPIDelegateCredentials=no -o AddKeysToAgent=no`. A `Host` block with `ForwardAgent yes` would otherwise hand the laptop's ssh-agent to the endpoint on every probe, and `remote doctor` is exactly the command run against a host already suspected. The `ForwardAgent` check reads the *configured* value from `ssh -G`, so the report still warns about it while the diagnostic declines to do it.

Host-key verification is left exactly as configured, neither weakened nor strengthened. `UpdateHostKeys=no` stops rotation-driven rewrites but not first use: under `StrictHostKeyChecking accept-new` (or `no`) a first connection appends the host key, like any ssh. Forcing `yes` would make the command useless on a remote not yet connected to, which is when a diagnostic is most wanted.

**The SOCKS greeting.** For a reverse-dynamic forward (`RemoteForward <port>` with no destination), the liveness probe writes the three-byte SOCKS5 no-auth greeting `05 01 00` and looks for `05 00`. A plain connect only proves something listens, so a squatter would pass; the handshake tells the recipe's tunnel from an unrelated service. The greeting goes only to a port the user declared to be SOCKS by omitting the destination. A `RemoteForward` with a concrete destination carries whatever was tunnelled (a database, an internal API), so the doctor connects and says nothing, and reports `UNKNOWN`: `PASS` and `WARN` both exit 0 and would be a confident all-clear about a listener nobody verified, `FAIL` would call a usually-healthy setup broken, and doing better would mean writing a probe into the user's database port. The probe carries its own short read deadline because `bash`'s `/dev/tcp` never times a read out, so a silent listener would otherwise hold the probe for the whole probe-timeout window. The listen address is interpolated into a command the remote shell parses, so only an IPv4 literal, a non-link-local IPv6 literal (a link-local one needs a zone index the deck will not interpolate) or a hostname of `[A-Za-z0-9.-]` is probed.

**Three exit codes.** `UNKNOWN` never reads as `PASS`, and separating `2` from `1` makes the most common real-world outcome, a healthy tunnel on a host where `sshd -T` needs a root the user lacks, a stable scriptable `2` rather than something indistinguishable from a broken tunnel.

**Only the first reverse forward** that `ssh -G` resolves is probed for liveness; `RemoteForward` lists them all. That is enough for the single-tunnel recipe it was built for.

**A tunnel-less remote exits 1.** `classify` reports `RemoteForward` as `FAIL` when `ssh -G` resolves no reverse forward, because the command was built as the reverse-tunnel diagnostic (PRD #345). The published pages say so explicitly, since an agent running `remote doctor` as a general health check on a remote without a tunnel would otherwise read the `1` as a broken remote.

## The endpoint fallback directory and its compatibility alias (issue #1121)

The published requirements page gives users the resolution order and the one-sentence relocation note; the reasoning is here.

The `$TMPDIR/dot-agent-deck-{uid}/` fallback is for hosts without `XDG_RUNTIME_DIR` (an ordinary ssh session, a container, macOS). The endpoints live inside a directory the deck creates at mode `0700`. If it cannot make the directory owner-only for a reason other than a foreign owner, it refuses to start and names the directory and the override rather than reporting a bare `Operation not permitted`.

What that fixes is availability, not confidentiality. The old flat `/tmp/dot-agent-deck-{uid}.sock` sat directly in a world-writable sticky directory, so another local user could create an entry at that exact path; the daemon's `bind(2)` then failed with `EADDRINUSE` and the deck could not remove the entry, because a sticky directory only lets the entry's owner unlink it. Confidentiality was never the gap: the socket inode has always been `0600`, and under `$XDG_RUNTIME_DIR` (mode `0700`, the user's own) no foreign uid could create the entry.

**The directory name is predictable, so the deck does not depend on winning it.** If another uid owns `/tmp/dot-agent-deck-{your-uid}` (created before first launch, or after a `/tmp` cleaner removed it), the deck creates `dot-agent-deck-{your-uid}.` plus 16 random hex digits at `0700` with a single `mkdir` that fails if anything exists, and binds both endpoints there. Hooks, `daemon status`, `daemon stop` and the TUI find it by listing the temp directory for owner-only siblings with that prefix that belong to the user. The daemon logs a warning naming both directories. The choice is sticky: once relocated, later starts keep using the relocated directory while the usual one does not exist, so a squatter removing their entry cannot make two starts disagree. To return to the usual location, stop the deck and remove every `/tmp/dot-agent-deck-{uid}.*` directory with its contents.

**Compatibility alias.** So that a binary from before this change (a stale install earlier on `PATH`, or an environment pinned to an older release) finds a newer daemon and shows its version-mismatch prompt instead of starting a second daemon, a daemon on the fallback also binds `/tmp/dot-agent-deck-{uid}.sock` and `/tmp/dot-agent-deck-attach-{uid}.sock` and removes them when it stops. It is best-effort: an untrusted entry there, or another daemon listening, produces a warning and the daemon carries on at the per-user directory. A squatter on the old spelling can therefore stop an older client from finding the deck but cannot stop the deck from starting. An older binary that does not know about a relocated directory finds the daemon through this alias; failing that, a binary that already uses the per-user directory cannot start a second daemon while the directory is taken and fails with a message naming it. The alias is intended to be removed in a later release.

**Peer check.** Since #1121 round two, every Unix connect entry point (`src/platform/ipc/unix.rs`, `refuse_foreign_peer`) compares the listener's uid (`SO_PEERCRED` / `getpeereid`) with the caller's and refuses a mismatch, telling the user to set `DOT_AGENT_DECK_SOCKET` and `DOT_AGENT_DECK_ATTACH_SOCKET` under a directory only they can write. It says nothing about the far end of an ssh-forwarded socket, whose local peer is the user's own `ssh`; [remote-endpoint-discovery.md](remote-endpoint-discovery.md) covers that boundary. Root is outside every uid check.

## The shared deck list (issue #1350) and Homebrew installs (issue #1372)

The CLI's `remotes.toml` became the desktop app's deck list in #1350: `remote::default_remotes_path` is the one resolver both clients call, and every production writer edits one row through `crate::deck_list` under a cross-process lock rather than rewriting the file, so neither client drops the other's rows or unknown keys. `RemotesFile::save`, which rewrites the whole file, remains for test fixtures; a pre-#1350 CLI still uses a whole-file rewrite, which is why the published page asks users to keep both clients on one release. Desktop builds from before the move kept their decks elsewhere and migrate them on first start, de-duplicating against rows `remote add` already wrote and keeping the selected deck selected.

#1372 made the remote binary's location a registry field (`install`, `binary`), because a Homebrew-installed deck lives at `<prefix>/bin/dot-agent-deck`. `RemoteBinaryPath` admits only an absolute path of `[A-Za-z0-9/._+-]`, enforced both when parsing the remote's answer and when deserializing `remotes.toml`, so a hand-edited or hostile value is refused before it reaches a remote shell. The recorded install belongs to the host it was detected on, so changing a row's host, user or port drops it; changing the key file or jump host keeps it. Homebrew prefixes are probed by absolute path because a non-interactive ssh shell usually does not have `brew` on `PATH` (Homebrew adds itself in a login profile); a custom prefix is found only through `command -v brew`.

## Upgrade: install from the client, restart in the daemon (PRD #1487)

One procedure serves `remote upgrade`, `connect`'s upgrade offer, the desktop's **Upgrade** and the desktop's local **Replace daemon**: `daemon_upgrade::upgrade_daemon` in `src/daemon_upgrade.rs`. No client carries upgrade policy of its own (PRD D1); a client chooses only how to present a step and how to put the restart question. The function runs over three seams — `Installer` (put the build in place), `DaemonPort` (probe and restart the running daemon) and `RestartDecider` (answer "these would stop — restart now?") — and returns one serde type, `UpgradeOutcome`, which the CLI prints through `UpgradeOutcome::summary` and the desktop renders field by field. The sequence is: install; probe (nothing running is `NoDaemonRunning`); send the restart request, asking the decider whenever the daemon answers `NeedsConfirmation`, at most `MAX_CONFIRM_ROUNDS` requests; then wait up to `VERIFY_TIMEOUT` for the *successor* to answer, where an answer from the old daemon while it drains does not count (`wait_for_successor`). The successor is told from the old daemon by identity: the live daemon's `Hello` carries `instance_id`, 16 random bytes minted once per process (`daemon_protocol::daemon_instance_id`), the upgrade records it at the first probe (through the remote's `daemon probe --json`, which passes the `Hello` through, or over the local socket), and a matching answer counts only when it names a different process. That is what makes a reinstall of the same build safe: an old daemon that accepted the restart and kept answering with the same build is never reported as restarted, however long it answers (PRD #1487 review). When the first probe has no `instance_id` — an old daemon that predates the field, or a remote probed through an installed build that predates it and so drops the key — the upgrade falls back to the earlier rule — the endpoint seen empty in between, a different build, or, for the same build, a matching answer held for `VERIFY_SETTLE` (6 s, longer than the old daemon's 3 s drain) — which is an inference rather than a proof, and is kept only for daemons that cannot say who they are.

**A failed version check after the binary was replaced says so.** On the download path the `mv` has already put the new file in place, and after a successful `brew upgrade` Homebrew may have, when the `--version` check runs. If that check fails, `install_or_upgrade` returns `RemoteAddError::ReplacedButUnverified`, which names the binary, wraps the check's own error, and carries what is now on disk: the version the check read when it read a valid one, otherwise `remote::UNVERIFIED_BUILD` ("an unverified build"). `RemoteUpgradeError::installed_version` returns it, so the shared outcome is `Failed { stage: Installing, installed_version: Some(..) }` and the CLI and the desktop say the binary was replaced, did not verify, and that the daemon was not restarted onto it, rather than implying nothing changed. Under `--no-install`, and on `remote add`'s Homebrew path where nothing is upgraded, nothing was replaced, so the plain `VersionMismatch` stands.

**The split is by who can do each half.** The install is an ssh operation from the user's machine: it needs the user's `remotes.toml`, ssh keys and agent, and it installs the client's own version (or whatever the host's Homebrew tap has, #1372), so it stays `remote::upgrade_reporting_to` behind `SshInstaller` — in its `upgrade_entry_reporting_to` form, against the `RemoteEntry` the caller read once and also built its `SshDaemonPort` from, so the install and the restart reach the same machine even if the row is removed and re-added for another address meanwhile. The result is written to `remotes.toml` only while the row by that name still has the same route (`RemoteEntry::same_route`: host, login, port, key, jump host, socket), checked under the registry's edit lock (`deck_list::update_if`); a moved row fails the install with `RemoteUpgradeError::RouteChanged`, so nothing is restarted (Greptile 4208066970). The restart is the daemon's, because only the running daemon knows which agents and orchestration roles it holds: `AttachRequest::RestartDaemon` applies the policy daemon-side and is documented with the other teardown paths in [daemon-teardown-paths.md](daemon-teardown-paths.md#the-restart-request-prd-1487). The daemon resolves its successor from the path it recorded at `daemon serve` start; a client never sends a path.

**The remote restart travels the install's ssh route, not a tunnel.** `SshDaemonPort` (`src/remote_daemon.rs`) runs two hidden plumbing subcommands of the **freshly installed** remote binary over `SshExecutor::run_capped_within` and parses the last stdout line as JSON:

- `daemon probe --json` prints `{running, hello}` for the daemon running at that host's endpoint, through `DaemonClient::probe_running`, which never lazy-spawns. The existing `daemon hello` would not do: it prints the binary's own static hello, not the running daemon's.
- `daemon restart-installed --json [--expect-version V] [--confirm-hex H]` calls `DaemonClient::restart_daemon` against the local endpoint and prints `{running, reply, unsupported}`. `H` is the hex-encoded JSON of the confirmed `RestartStopSet`, because `run_capped` takes one command string and no stdin, and hex keeps that argument free of shell metacharacters.

Running the new binary is what makes the route sound: it is new by construction, because the install has just verified its version, so the plumbing it is asked to run exists. A clap usage error (exit 2) from either subcommand is classified `RemoteDaemonError::Unsupported` and every other non-zero exit `Failed`. **This deliberately supersedes the PRD's working design**, which said "a non-zero exit or an unparsable reply from `restart-installed` is treated as `Unsupported`": only exit 2 means "this binary does not know the subcommand". Any other non-zero exit is the subcommand running and failing — a transport error, a handshake timeout — and reporting that as "too old" would send the user to upgrade a build that is already new. An unparsable reply on exit 0 (`Malformed`) is still treated as too old on the restart path. Do not widen the `Unsupported` arm back to every non-zero exit. `SshDaemonPort` is deliberately general — "run this deck's CLI on the remote against that machine's daemon and parse a JSON line" — and owns nothing upgrade-specific.

**Both plumbing commands are bounded per command, whatever executor the port is given** (PRD #1487 audit A1). The install keeps `upgrade_ssh_executor()`'s keepalive-only session, with no wall-clock kill, because a release download may take minutes. The plumbing reuses that executor — same `SshTarget`, same jump host, same keepalives — but runs through `SshExecutor::run_capped_within`, which `SystemSshExecutor` implements with `run_local_bounded`: stdout and stderr are each capped at `REMOTE_DAEMON_REPLY_CAP` (256 KiB) **while they drain**, and the ssh process is killed at a per-command deadline. Before this, the keepalive executor's `run_capped` fell back to `Command::output()`, so a remote that streamed without end grew the client's memory, and one that never finished held the upgrade forever — keepalives prove the transport is alive, not that the remote command will finish. The deadlines live in `src/remote_daemon.rs`: `REMOTE_PROBE_DEADLINE` is ssh's connect allowance (`UPGRADE_SSH_CONNECT_TIMEOUT`, 30 s) plus 15 s for the remote binary to start and do its own bounded handshake, 45 s in all; `REMOTE_RESTART_DEADLINE` adds `RESTART_REQUEST_TIMEOUT`, 85 s in all. `RESTART_REQUEST_TIMEOUT` (40 s, `src/daemon_client.rs`) is derived from the daemon's worst case before it answers — the 10 s `RESTART_VERIFY_TIMEOUT` check of the installed build plus the 20 s `RESPAWN_SETTLE_TIMEOUT` wait for respawns to settle — plus a 10 s `RESTART_REPLY_MARGIN`, and const assertions in both files fail the build if either bound stops exceeding that sum. It used to be a flat 30 s, exactly the daemon's worst case, so an `Accepted` reply could arrive just as the client gave up (PRD #1487 review, Qodo 4200422524). The drain runs after the daemon has answered, so it costs the restart command nothing. A flood stops the drainer at the cap, which closes the pipe: the ssh process dies of it (one that ignores that and keeps blocking on the write is reaped at the deadline), and `run_json` refuses a capped reply as `Malformed` before it looks at the exit status, because a process killed by the closed pipe reports a meaningless one. A hang surfaces as "the remote command did not finish within Ns". `src/remote_daemon.rs`'s `production_executor_bounds` tests drive the real executor shape with a stand-in `ssh` that floods each stream or never exits. The default trait method — what test fakes use — ignores the deadline.

**The deadline bounds the streams, not only the ssh process** (PRD #1487 re-check R1). A descendant that inherits ssh's stdout or stderr — a `ProxyCommand`, a jump-route helper, a wrapper script — keeps the pipe's write end open after ssh exits or is killed, so a reader that waits for EOF waits on that descendant's lifetime, and `run_local_bounded` used to join its readers unconditionally. Now the readers fill a shared buffer and the call never joins them: once the direct child has exited, a stream still open after `POST_EXIT_STREAM_GRACE` (1 s) is cancelled, and at the deadline both are. On Unix the readers read non-blocking under `poll(2)`, so a cancel is noticed within a tick; a cancelled reader takes what the kernel already holds (at most 1 MiB) and closes its pipe. Where a pipe cannot be made non-blocking, a reader still blocked after `READER_STOP_GRACE` is abandoned rather than joined. The plumbing runs through `run_local_bounded_owning_group`, which starts ssh in a process group of its own and sends that group `SIGKILL` at the deadline and when a stream outlives the exited ssh, so a quiet helper left in the group is killed with it; a descendant that left the group (`setsid`, as a `ControlPersist` master does) is not signalled, but its streams are abandoned on time. **The group is signalled only while ssh is still unreaped** (final audit F1). The group id is ssh's pid, so it is reserved only while that pid is: and in the escaped-writer case nothing else holds it, so a reap before the grace's `killpg` would leave the number free for an unrelated group to take. The poll therefore observes ssh's exit with `waitid(…, WEXITED | WNOHANG | WNOWAIT)`, which leaves it a zombie; every signal is sent before the one reap, and `Leader::reap` consumes the handle so nothing can follow it. A group id of 0 or 1, a non-positive one, or the caller's own group is never signalled, and a poll that fails with `ECHILD` (something else reaped ssh) signals nothing. `remote.rs`'s `owning_group_*` tests record the order through a test seam and check, with the kernel, that ssh was still waitable at the moment of the signal. The owning variant is not the default, because a child in its own group no longer receives the terminal's `Ctrl+C`; the interruptible install pipeline and the other probes keep the plain `run_local_bounded`, which gets the stream bound but kills the child alone. The `production_executor_bounds` descendant tests cover a quiet stream-holding descendant after a finished command and under a stopped one, and (Linux) one that escaped the group.

**Jump hosts.** `SshTarget` gained `jump`, set by `RemoteEntry::ssh_target()` from the deck list's `jump_host` and emitted by `SystemSshExecutor::build_command` as `-J <alias>` after `HostAlias::parse` validates it, so the install and the restart reach a host the way the desktop's tunnel does (PRD Risk 4). `connect` clears it (`build_connect_command`): connect routing through a jump host is out of this PRD's scope.

**`connect` keeps the user's earlier answer across the ssh hop.** When the user chose **Keep current daemon** (or nobody could answer) during `connect`'s upgrade, `connect` adds `DOT_AGENT_DECK_KEEP_DAEMON=1` to the `env` prefix of the remote command, and the remote TUI's `ensure_compatible_daemon_or_die` takes the decline branch without prompting a second time: `ProceedOnExisting`, or #405's protocol refusal across a protocol skew. The variable is set only after a successful install, so the binary that reads it always understands it; it is honoured only when exactly `1`. For a daemon too old to be asked (`InstalledDaemonTooOld`), `connect` sets nothing, and the remote TUI's own attach handshake is the working fallback — it restarts an idle older daemon and prompts when agents are live, as it always has.

**Two limits found while documenting it (2026-10-03), both fixed in the same PRD:**

- **A supervised daemon starts no successor; it exits 75 and lets the service manager start the installed build.** Originally the successor was always spawned by the old daemon as a detached child. Under systemd that leaves it in the service's cgroup: when the old daemon (the unit's main process) exits, systemd stops the unit and kills the cgroup, successor included, and the documented unit's `Restart=on-failure` does not restart after a clean exit. Measured before the fix with `systemd-run --user -p Restart=on-failure … daemon serve`: `restart-installed` answered `accepted`, the log recorded `successor daemon spawned`, and eight seconds later the unit was `inactive` and nothing answered. Now `daemon serve` records a `Supervisor` at startup (`daemon_restart::detect_supervisor`), and after an accepted `Installed` restart `run_daemon_with` asks `RestartControl::take_successor_plan`: unsupervised, it spawns the successor exactly as before; supervised, it spawns nothing and `daemon serve` exits with `SUPERVISED_RESTART_EXIT` (75, `EX_TEMPFAIL`), which `Restart=on-failure` restarts from the unit's own `ExecStart` — the path the upgrade just installed into. No unit edit is needed. Detection requires evidence that *this* process is the one the manager started, because every child of a service inherits its environment and a false positive would exit for a restart nobody performs: systemd is `INVOCATION_ID` plus `SYSTEMD_EXEC_PID` equal to our pid (systemd 248+), or, without `SYSTEMD_EXEC_PID`, a parent whose `comm` is `systemd`; launchd is an `XPC_SERVICE_NAME` other than `0` plus a parent of pid 1. `ClientSpawns` (the local Replace) records no target, so a supervised daemon exits 0 there as before. Re-measured after the fix on systemd 259 with the same probe, plus an atomic `mv` of a fresh copy over the installed path before the restart: `accepted`, the deck log `restart accepted under a service manager; exiting for it to start the installed build supervisor=Systemd exit_status=75`, the journal `Main process exited, code=exited, status=75/TEMPFAIL` → `Scheduled restart job, restart counter is at 1` → `Started`, and four seconds later the unit `active (running)` with `NRestarts=1`, a new `MainPID` whose `/proc/<pid>/exe` is the new inode (the old one read `… (deleted)`), and `daemon probe` answering. **launchd is untested**: the plist's `KeepAlive` restarts on any exit, so the same exit should bring the job back, and without detection the setsid'd successor would escape launchd's process-group kill while `KeepAlive` started a second daemon beside it — but no run on a Mac has confirmed either. The pre-248 systemd fallback is unit-tested only.
- **An installed build too old to reach the daemon is `InstalledNotRestarted { InstalledBuildTooOld }`, not a failure.** `remote upgrade --version <a release before this one>` installs a binary with no `daemon probe`; the ssh port's probe sees clap's usage exit (2) and returns `PortError::InstalledBuildTooOld`, which `run_upgrade` maps to that outcome with no restart request sent. The restart request takes the same route since review S1: a build that answers `daemon probe` but not `daemon restart-installed` (exit 2) returns `PortError::InstalledBuildTooOld` from `DaemonPort::restart` and becomes the same outcome, naming the installed build — it used to reach `InstalledDaemonTooOld`, whose summary blamed the daemon, which was never asked. The CLI exits 0 and names `connect` as the way to switch; the desktop renders the `installed-build-too-old` kind. Before the fix this was `Failed { Restarting }` and a non-zero exit.

**A restart whose reply was lost is verified, not failed** (PRD #1487 review, Qodo 4200422524). Once the restart frame has gone out, the daemon may act on it whatever becomes of the reply, so a failure after that point that leaves the answer unread becomes `PortError::ReplyUnreadable`, and `run_upgrade` treats it as a request that may have been carried out: it emits `Verifying` and polls with `wait_for_successor`, which the old daemon's `instance_id` makes sound. A successor that answers gives `Restarted` (naming the set confirmed on that round); the old process still answering gives `Failed { Restarting }` saying the daemon did not restart; neither gives `Failed { Restarting }` saying it did not come back. For the local Replace (`ClientSpawns`) the check is `spawn_successor` itself: a daemon that did not accept keeps its endpoint, so nothing is spawned and the failure names both the lost reply and the still-running daemon. Failures from before the send stay plain failures. Where the line falls: `DaemonClient::restart_daemon` keeps the capability handshake and the connect the frame goes out on as ordinary errors (`TimedOut` for running out there), and reports anything after the first byte — a broken connection, a cut-off reply, the deadline — as `ClientError::Unanswered`; `WireDaemonPort` maps that and `Malformed` to `ReplyUnreadable`. Over ssh, `daemon restart-installed` exits `RESTART_NOT_SENT_EXIT` (1) when it failed before sending and `RESTART_UNANSWERED_EXIT` (3) when the request went out unanswered (`src/daemon_restart.rs`); `SshDaemonPort` treats only exit 1 and the ssh errors that mean no session was ever established (`ConnectionRefused`, `AuthFailed`, `HostKeyVerificationFailed`) as not sent, and everything else — exit 3, a crash's exit code, the session dropping, the deadline kill — as unread.

## Remote names

`remote add` has required names of `[A-Za-z0-9._-]`, starting alphanumeric, at most 64 bytes, since the rule was added; names registered before it keep working because validation is applied on write only (`deck_list.rs`, "Applied on write only, like validate_deck_name"). The desktop derives a name from the host because it deliberately takes no free-form label (`deck_list::derive_deck_name`).
