# Versioning and the "breaking" definition

> **Developer / maintainer reference.** This page documents release-process and contract discipline. It is intentionally excluded from the published documentation site and renders as plain Markdown here on GitHub.

`dot-agent-deck` ships the TUI and the daemon as the **same binary in two modes**, so the only cross-process contract that matters is the attach protocol between them and the handler semantics behind it. The daemon deliberately outlives the TUI (agents survive detach/sleep/network/machine-switch), which means a long-running daemon can keep serving an *older* contract after you upgrade the binary in place. That runtime skew — a newer TUI meeting an older still-running daemon — is the whole reason the word "breaking" needs a precise, project-specific meaning here.

## What "breaking" means in this project

**Breaking = a change to the TUI↔daemon protocol/handler contract such that an older and a newer build cannot safely interoperate.** This is *not* the same axis as "user-facing breaking change". It is specifically the cross-process contract between the two modes of the binary.

A change is breaking in this sense when it would make an older peer mis-behave against a newer one. That includes the obvious structural cases (a new request variant a client may send unprompted, a changed field shape) **and** the subtle ones: **semantic breaks behind a stable wire** — a field whose *meaning* changes, or a role-map value type that shifts — where the bytes still deserialize but one side now interprets them wrongly. The classic symptom is a delegate signal that the stale daemon silently no-ops because it doesn't understand the newer shape.

Read "unprompted" as load-bearing rather than as hedging: a new request variant that every sender withholds until the daemon has *advertised* a matching capability is **not** structurally breaking, because the gate keeps it out of the pairings in which an older peer would meet a frame it cannot parse, and the one residual route to such a frame fails closed. The gate, its reasoning, that residual and its two limits are in item 1 below.

Generic user-facing breakage (a renamed flag, a removed command, a changed default) is a normal product change and is **not** what the `breaking` changelog type is reserved for. Use it only for the cross-process compatibility break described above.

## How a break is detected and marked

Detection is layered — there is deliberately **no** mechanical CI schema/snapshot gate, because a type snapshot catches structural breaks (already covered below) but is blind to the residual risk, which is semantic.

1. **`PROTOCOL_VERSION` is the structural marker.** A wire-shape break must bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. That is mandatory, with one exception — the capability gate written out below this item. **Two call sites refuse on a `PROTOCOL_VERSION` difference, both on exact equality.** The desktop's `classify_handshake` in `desktop/src-tauri/src/daemon_bridge.rs` runs before the contract-break comparison in step 2 and is not reachable by that check's session-scoped bypass — so for the desktop the constant *is* a fatal floor, and a bump means a new app refuses an old daemon outright and vice versa. The TUI's startup handshake against a local daemon (`build_version_handshake`, [#405](https://github.com/vfarcic/dot-agent-deck/issues/405)) reads the daemon's `server_version` before its `DAD_BUILD_ID` comparison: a daemon on another protocol can still be *restarted* by that handshake — silently when no agents run under it, or on the user's `S` — but it is never *attached to*, so a matching build id does not wave the skew through, and declining the restart prompt exits with a refusal naming both numbers where it used to attach with no version check at all. So for the TUI a bump means a new binary and an old daemon with live agents cannot be paired; the user either restarts the daemon (stopping the agents) or attaches with the daemon's own build. Neither check covers the one-shot CLI subcommands, which send without that handshake, or a TUI whose daemon is replaced mid-session. `connect`'s surviving check is a presence floor rather than a version verdict: its laptop↔remote comparison was removed by [#491](https://github.com/vfarcic/dot-agent-deck/issues/491) because it compared two constants that never share a wire — `connect` ssh's in and runs the *remote* binary's TUI against the *remote* daemon, where that TUI's own handshake is the one that compares. See the enforcement note on `PROTOCOL_VERSION` in `src/daemon_protocol.rs`.

   **The exception: a new request variant that every sender withholds until the daemon advertises a matching capability does not bump.** What `PROTOCOL_VERSION` protects against is a pairing in which one peer is handed a frame it cannot parse. A variant whose every sender reads the daemon's advertised capability set first does not create that pairing in the ordinary cases: a newer client against an older daemon withholds the variant, an older client does not know it exists, and an older client against a newer daemon is unaffected because the daemon only ever *answers* the variant. One residual route survives, and it fails closed — a client handle whose cached capability set outlived a daemon that was then replaced by an older build does send the frame, and the older daemon answers `malformed request`, the client's call returns an error, and no state changes on either side. An **ungated** new variant still bumps, because there the older daemon's first sight of it is the frame itself, in every pairing rather than in one residual one.

   **The worked example is `focus-gained`** (PRD #1105, `AttachRequest::FocusGained`). It is gated on `CAP_FOCUS_GAINED`, which the daemon lists in `DAEMON_CAPABILITIES`; `DaemonClient::focus_gained_while` — which `focus_gained` delegates to, and which both production senders (the TUI's `focus_report` and the desktop's terminal bridge) go through — checks that capability before it opens the claim connection, and returns `FocusReport::Withheld` without writing anything when it is absent. It contributed no bump: `PROTOCOL_VERSION` was 9 when `focus-gained` landed and `focus-gained` left it there. The constant is now 10, and that is [#1049](https://github.com/vfarcic/dot-agent-deck/issues/1049)'s `stop-daemon`, which is this rule's other side rather than a counter-example: it has a capability string (`CAP_STOP_DAEMON`) and a helper to read it, but its one sender — `DaemonClient::stop_daemon`, through `run_daemon_stop_over_wire` — does **not** withhold on it. It sends the frame and reports the older daemon's `unknown variant` refusal as `WireRejected`. A capability nobody is required to check is advice to callers, not a gate, so the exception below does not reach it and the ordinary rule bumped. Do not read the 10 and `focus-gained` as connected: `focus-gained` ships under whatever number the wire is at, because the gate is what decides it.

   **Weigh what a bump costs before taking one anyway.** The desktop is the one call site that refuses on a difference, so a bump means a new app refuses every daemon still on the old number outright — including **remote decks on hosts the user does not own and cannot upgrade**, for whom the remedy a refusal implies does not exist (item 2's note below). What it would buy for a gated variant is small by comparison: the residual above is already refused at the request, and a bump would only move that refusal to the connection — while also refusing every correctly-paired older daemon. That comparison is what decided `focus-gained`, rather than the letter of the rule.

   **A gated optional FIELD on a verb every daemon knows is the same rung with a weaker residual** (PRD #1223's `StartAgent.authoring_kind`, gated on `CAP_AUTHORING_KIND`). The ordinary pairings behave as above — the one production sender, `DaemonClient::start_authoring_agent`, withholds against a daemon that does not advertise it — but the residual does not fail closed: an older daemon decodes `start-agent` happily, drops the unknown key and starts the agent with no seed, reporting success. So `start_authoring_agent` re-handshakes on every call and decides from that handshake's own reply rather than from the cached set — which every clone of a handle shares, so a clone's concurrent store could otherwise supply a set this call never received — and that shrinks the residual to a daemon replaced between two back-to-back round trips without closing it. A future gated field should make the same call, or give the daemon a way to acknowledge the field in its reply. PRD #1223 M6's `StartPreparedAgent.use_configured_command`, gated on `CAP_PREPARED_ROLE_COMMAND`, is the second such field and makes the same call: its one production sender, `DaemonClient::start_prepared_role`, decides from its own fresh `Hello` on every role start, because an older daemon would drop the key and start its default shell for the role. The same residual remains.

   **PRD #1223 added four capabilities on these two rungs and moved `PROTOCOL_VERSION` by nothing** — it was 10 before the PRD and is 10 after it. Two are gated variants: `ListDirectories` (`list-directories`, held by `DaemonClient::list_directories`) and `NewAgentOptions` (`new-agent-options`, held by `DaemonClient::new_agent_options`), whose residual fails closed as `focus-gained`'s does, and whose replies ride on new additive optional fields (`directories`, `new_agent_options`). Two are the gated fields in the paragraph above, `StartAgent.authoring_kind` (`authoring-kind`) and `StartPreparedAgent.use_configured_command` (`prepared-role-command`, advertised on Unix only), whose residual does not fail closed. No existing field changed meaning — every new daemon behaviour is reached only through one of the four, and an unset `authoring_kind` or `use_configured_command` leaves its verb byte-for-byte as it was — so the PRD owed no `.breaking.md` fragment and no `CONTRACT_BREAKS` entry.

   **PRD #1487's `restart-daemon` is a third worked example, and it contributed no bump** — `PROTOCOL_VERSION` was 10 before it and is 10 after it. `AttachRequest::RestartDaemon` is gated on `CAP_RESTART_DAEMON`, listed in both `DAEMON_CAPABILITIES` arrays because its dispatch arm is not `#[cfg]`-gated, and its one sender is `DaemonClient::restart_daemon`, which reads the capability from **that call's own** `Hello` (`fresh_capabilities()`) rather than from the handle's cache and returns `GatedQuery::Unsupported` without writing the frame when it is absent. Reading it fresh is the point of this verb rather than a nicety: the request replaces the daemon behind the endpoint, so a cached set is exactly the stale-handle residual the paragraph above describes. Both production routes reach that one sender — the desktop's local Replace through `WireDaemonPort`, and every remote upgrade through `SshDaemonPort`, which runs the freshly installed remote binary's hidden `daemon restart-installed` subcommand on the host — so `StopDaemon`'s counter-example cannot recur. The answer rides the additive optional `AttachResponse::restart`. No existing field or verb changed meaning: an older daemon never receives the frame, an older TUI never sends it, and a newer daemon's `Hello` differs only by one more capability string; `DOT_AGENT_DECK_KEEP_DAEMON`, which `connect` adds to the remote TUI's environment, is set only after an install the client just verified, so the remote binary that reads it is new by construction. So the PRD owed no `.breaking.md` and no `CONTRACT_BREAKS` entry — `remote upgrade` now restarting the daemon is a user-visible CLI change, which is a `feature` fragment (CLAUDE.md rule 19), not a contract break. Its review added `AttachResponse::instance_id` to the live `Hello` reply — a random per-process identity the upgrade compares to tell the old daemon from its successor — on the first rung, an additive optional field: an older client ignores the key, an older daemon omits it and the upgrade falls back to its earlier settle rule, and no existing field changed meaning, so it moved `PROTOCOL_VERSION` by nothing and owed no `.breaking.md` either. Its CLAUDE.md rule 12 run is recorded on the PR.

   **Two limits, so this is not read as a general licence.** It covers only a variant *every* sender gates — one raw call site that skips the check puts the change back on the bump list, and the check belongs in the client library rather than in each caller so that stays true. And it says nothing about **semantic** breaks: what a gated variant does to the meaning of an existing field is item 2's question, not this one. #1105 is its own illustration — the gate meant `focus-gained` moved `PROTOCOL_VERSION` not at all, and the focus-driven sizing behind the variant still needed a `changelog.d/1105.breaking.md` fragment.

   **The hook socket is not versioned by `PROTOCOL_VERSION` at all**, so a new verb there needs no bump either — `get_seed`, `list_targets`, `restart_role`, `spawn_role` and, since issue #1383, `ack` all shipped without one. Each degrades by the same route: an older daemon decodes the unknown `message_type` as neither a `DaemonMessage` nor an `AgentEvent`, logs it as malformed and answers nothing, and the CLI treats no answer as unverifiable rather than as a failure — for `ack`, it says on stderr that it could not confirm receipt and exits 0, and prints "Acknowledged" only on the daemon's accepted reply. For `ack` that property is load-bearing, because `AckSignal` deliberately carries none of `AgentEvent`'s required fields — if it did, an older daemon would ingest the acknowledgement as a status event (pinned by `an_ack_line_never_decodes_as_an_agent_event` in `src/event.rs`). The other pairing, an older `dot-agent-deck` in a worker pane against a newer daemon, rejects `ack` as an unknown subcommand; the task file tells the worker to carry on, and the daemon's re-send stops on the worker's own turn events instead. [Delegate delivery](delegate-delivery.md#the-ack-command) has the rest of the `ack` handshake.

2. **A human-marked `.breaking.md` changelog fragment for semantic breaks, PLUS the `CONTRACT_BREAKS` entry that goes with it.** A same-wire/different-meaning change cannot be detected mechanically, so the author marks it. That declaration is now written in two places, and **both are mandatory**:

   - `changelog.d/<issue>.breaking.md` — the `breaking` towncrier type defined in `pyproject.toml`. This is what a human reads, and what [`analyze.sh`](../../.claude/skills/tag-release/analyze.sh) turns into a minor bump.
   - an entry in `CONTRACT_BREAKS` in `src/daemon_protocol.rs`, spelled `<issue>-<kebab-slug>`, appended in the **same commit**. This is what the software reads: it rides every `Hello` reply, and the desktop's `classify_handshake` compares the two builds' lists as sets and refuses across a difference. The list is **append-only** — never edit or remove an entry, including when `PROTOCOL_VERSION` bumps past it, because a stale entry costs one string on both sides of a comparison that then agree about it while a removed one silently re-marries two builds a break separates.

   `xtask/linkage-check`'s `contract_breaks` rule fails the build when a fragment in the tree has no matching entry, so forgetting the second half goes red rather than silent. It is deliberately one-directional: `release.yml` consumes a fragment and deletes it while the entry stays for ever, so an entry with no fragment is the normal state of every past break.

   **This is what issue [#801](https://github.com/vfarcic/dot-agent-deck/issues/801) changed, and why the entry is not bookkeeping.** The desktop used to classify compatibility from the `git describe` build stamp, and then from the release digits it could read off that stamp. Both read a **tag**, and a tag is applied after the content it names lands — so a branch cut in between described as the *previous* release while being functionally the new one, and two byte-identical trees were reported incompatible. The digits could also only ever refuse across a break somebody had already declared, since only a declared break bumps the minor while `0.x` (table below) — so reading the declaration itself loses nothing and gains the case a digit cannot reach: a break declared on an **unreleased** branch, which has no minor to move yet. See [desktop-gui.md](desktop-gui.md#compatibility-is-classified-from-the-contract-not-from-a-git-tag-801).

   **The desktop's remote decks lean on this harder than anything else does.** For a deck reached over ssh the build stamp is not a refusal and never was under PRD #741 M8; since #801 it is not a refusal for a *local* deck either. `PROTOCOL_VERSION` still gates every connection exactly as it did, but for a *semantic* break this fragment, its `CONTRACT_BREAKS` entry, and the manual test below are the whole of what stands behind it.
3. **A cross-version manual test** (see below) for any PR that touches the daemon, the protocol, orchestration, or hooks.

## Which older clients are supported

**Clients older than v0.35.0 are not supported against a current daemon** (maintainer decision, 2026-10-08, recorded on [#463](https://github.com/vfarcic/dot-agent-deck/issues/463)). v0.35.0 is the first release carrying PRD #140's per-tab orchestration token (`TabMembership::Orchestration.orchestration_id`), which every client built from this repository stamps on every orchestration role it starts: the TUI (`src/tab.rs`), the daemon's own spawn paths (`src/spawn.rs`) and the desktop (`desktop/src-tauri/src/lib.rs`).

Until #463 the daemon kept a fallback for a client that sent no token: it routed that client's panes on the round-11 `(name, orchestration_cwd)` tuple, the `NameCwd` variant of the routing identity. That fallback is retired, and what replaced it is a refusal rather than a deletion. Deleting the variant alone would have left a token-less pane with no identity at all, which is one merged routing group rather than a clean failure; and the daemon does not act on `client_version`, so a check in the client would not stop an old TUI. So:

- **The daemon refuses** an orchestration `StartAgent` (and `StartPreparedAgent`, which shares its handler) whose membership carries no `orchestration_id`, with an error prefixed `START_ERR_ORCHESTRATION_ID_REQUIRED` (`orchestration-id-required`) that names the v0.35.0 cut-off. Nothing is started. Test: `orchestration/identity/011`.
- **The TUI places a token-less orchestration record on the dashboard** instead of rebuilding a tab for it, with one session warning naming the orchestration. Only a daemon from before #463 can hold such a record, since it accepted the start this daemon refuses.
- **The routing identity is the token** (`OrchestrationIdentity { id, name }`), with no second variant.

The wire is unchanged: `orchestration_id` stays an optional field, so this is a same-wire semantic break rather than a `PROTOCOL_VERSION` bump — `changelog.d/463.breaking.md` and the `CONTRACT_BREAKS` entry `463-orchestration-start-requires-instance-token`. A bump would have refused every current pairing at the connection to catch a request shape only a pre-v0.35.0 client sends, while the refusal catches exactly that request. Since v0.44.0 ([#405](https://github.com/vfarcic/dot-agent-deck/issues/405)) a current TUI already refuses a daemon on another attach protocol, so the old-daemon/new-client half of the pairing was closed before this.

**What "supported" means here**, so the next cut-off is argued the same way: a supported older client is one whose requests a current daemon serves with its documented meaning. The cross-version check in CLAUDE.md rule 12 pairs a branch with the **previous release**, which is always inside the supported window; a pairing older than the window is not a test this repository owes. Moving the cut-off is a maintainer decision and is recorded in this section.

## The 0.x bump policy

While the major version is `0`, the bump rules are deliberately shifted down one level from standard SemVer so the **minor digit tracks compatibility**, not features:

| Change | While `0.x` | From `1.0` onward |
|---|---|---|
| breaking (protocol/handler contract) | **minor** (`0.31.x → 0.32.0`) | major |
| feature (new user-facing functionality) | **patch** (`0.31.1 → 0.31.2`) | minor |
| bugfix | **patch** | patch |

The consequence worth internalizing: while in `0.x`, a feature-only release is a *patch* release, and **only a protocol-breaking change bumps the minor**. So the minor digit stops meaning "has new features" and starts meaning "compatibility broke" — if `0.31.x` becomes `0.32.0`, an older peer can no longer safely talk to a `0.32.x` one. This is already implemented on the release side in [`.claude/skills/tag-release/analyze.sh`](../../.claude/skills/tag-release/analyze.sh) (the `breaking → minor`, `feature/bugfix → patch` recalibration); the table above is the policy that script encodes. That script has two callers and they run the same code: a maintainer, from `/tag-release` Step 1, to see the proposed version; and `.github/workflows/tag-release.yml`, to re-derive it at release time and refuse when it disagrees with the version the maintainer supplied.

## When a change gets a changelog fragment at all

**A fragment exists when a user can observe the change.** An internal-only change — CI, developer tooling, the test harness, a refactor with no behavioural difference, repository configuration — gets **no fragment**, of any type. The bump policy above only ever sees fragments, so a change with none is a change that does not move the version, which is the right answer for work no user can see.

The types in `pyproject.toml` are the choice you make *after* that question is answered yes. `misc` is for a user-observable change that is not a feature, a bug fix, a compatibility break or documentation — packaging, distribution, a deprecation notice, a default that moved.

**This reverses what `misc` used to mean, and the reversal is the point** (issue #1250). It was defined as "internal improvements, CI/CD, tooling, refactoring (improves the project but users don't directly see it)", with `showcontent = true` — so exactly the work a release body should omit was given a category that guaranteed it appeared. Release 0.41.1's `Miscellaneous` section runs to roughly 90 lines of CI, harness and tooling detail. Five fragments queued for the following release were deleted with that change rather than left to ship one release later.

**The rule lives in `pyproject.toml`'s comments because that is what the tooling reads.** The `dot-ai-changelog-fragment` skill picks its type from the list there, using "a comment above it describing when to use that type" — so the comment *is* the instruction every agent follows. That matters because the skill itself is a vendored mirror that must not be patched (CLAUDE.md rule 13): a project-specific edit inside `.claude/skills/dot-ai-*` is restored to upstream's blob by the next sync commit. CLAUDE.md rule 19 carries the same rule for agents that never open `pyproject.toml`.

## The declared minimum Rust toolchain

`Cargo.toml`'s `[workspace.package] rust-version` is **1.97.1: the toolchain this project is built and tested on**, the same version `devbox.json` installs and every `.github/workflows/` job asks `dtolnay/rust-toolchain` for. `the_declared_msrv_matches_the_pinned_toolchain` in [`xtask/linkage-check/src/pin_lockstep.rs`](../../xtask/linkage-check/src/pin_lockstep.rs) fails the build when they disagree, so the three copies move together — it reads the workflow pins, which `repository_pins_are_in_lockstep` already ties to devbox. Renovate moves all three in one pull request (issue #1478): the workflow pins and `rust-version` are read from the same `devbox` datasource as devbox.json's `rustc`, `cargo`, `clippy` and `rustfmt`, and one `packageRules` group bundles them, so a Rust upgrade is proposed only once devbox can install it and is held for a human. `rust-version` needs a `customManagers` entry of its own because Renovate's cargo manager does not extract it; `renovate_reads_exactly_the_declared_msrv` fails the build if that entry stops matching it.

**Why not a lower, measured floor** (issue #451). One can be established — the graph's true minimum was measured at 1.93.1, set by `serial_test@4.0.1` — but nothing re-establishes it. No job builds on it, so a dependency bump or a new `std` call raises the real minimum and the declared one quietly stops being true; a floor measured on Linux in one profile says nothing about the Windows and macOS `cfg` arms. It also binds the wrong people: `serial_test` is a **dev**-dependency, and cargo enforces the package's `rust-version` even for `cargo build --bin`, so a test-only dependency would set the number a user building only the binary is refused by. The claim this repo can keep is "the toolchain we test", and CLAUDE.md rule 17 is about not writing the other kind.

**What it does to dependency resolution.** Declaring a floor switches cargo's resolver to preferring versions compatible with it (`incompatible-rust-versions = "fallback"`, the default under edition 2024). Renovate then uses two commands that disagree: per-dependency PRs run `cargo update --precise`, which keeps a version whose own `rust-version` is above the floor, while the Monday `lockFileMaintenance` job runs plain `cargo update`, which downgrades it again. With the floor set to the **pinned** toolchain that only happens for a dependency needing a newer rustc than CI has — and there the downgrade is correct, because such a version cannot build here anyway until the pin moves. Read a recurring downgrade as a signal that the pin is behind, not as noise to silence: `incompatible-rust-versions = "allow"` would silence it by making the declaration meaningless in the one place it has teeth, and no job would then catch the lockfile drifting past what we can compile.

## Cross-version manual-test discipline

`PROTOCOL_VERSION` catches structural breaks and the `.breaking.md` fragment records semantic ones the author already knows about — but the failure mode we most want to catch is a semantic break the author *didn't* realize they introduced. The backstop is a manual test, required before merging any PR that touches the daemon / protocol / orchestration / hooks:

1. Build the PR branch's binary.
2. Start a daemon from the **previous release** (the last tagged binary), and start an agent under it.
3. Run the PR-branch **TUI** against that older daemon and confirm the core flows still work end to end: a **delegate** still routes, and **hooks** (work-done, status updates) still arrive.

**Step 2's *"start an agent under it"* is load-bearing, and step 3 has a decline step.** Get either wrong and this gate silently measures nothing:

- **Keep that agent running when the PR-branch TUI starts.** On a `build_version` mismatch with **zero** agents, the newer binary takes `MismatchAction::SilentRestart` (`src/build_version_handshake.rs`, PRD #161): it SIGTERMs the older daemon and lazy-spawns its own, with no prompt and no output, regardless of TTY. Every check then passes against a *new* daemon and you report a clean cross-version gate having actually measured new-against-new — nothing on screen says the daemon was replaced.
- **Decline the mismatch prompt.** With agents present the handshake asks instead of restarting; press any key other than `S`. Declining returns `HandshakeOutcome::ProceedOnExisting`, which attaches to the older daemon unchanged (PRD #161 D4, the never-strand rule). Accepting restarts the daemon on the new binary and lands you in the same false pass, with the agents stopped as well.
- **When the two builds' `PROTOCOL_VERSION` differs, declining refuses instead of attaching** ([#405](https://github.com/vfarcic/dot-agent-deck/issues/405)): the prompt says the binary cannot attach, and the decline exits non-zero with `error: daemon speaks attach protocol vN, but this binary speaks vM`, leaving the old daemon and its agents running. That is the intended result, not a failed run: a bumped protocol already *is* the compatibility statement, and there is no attached session to test delegates and hooks in. Record the refusal as the outcome of step 3, and make sure the PR bumps the version for a reason the bump list names.
- **Confirm before trusting the result:** the daemon serving the new TUI should still have the previous release's binary as its `exe`.

If delegate or hooks silently stop flowing, the change broke the contract behind a stable wire — bump `PROTOCOL_VERSION` (if the wire shape moved) and/or add a `.breaking.md` fragment **with its `CONTRACT_BREAKS` entry** so the release is versioned as a compatibility break and the desktop's handshake can see it. This step is enforced in-repo by **CLAUDE.md permanent instruction 12**, which every agent in this project loads and follows, and by the project-local [`pr-create`](../../.claude/skills/pr-create/SKILL.md) skill, which asks the question as part of opening a PR.

### The traps, and the runs that measured them

CLAUDE.md rule 12 lists the traps of a hand-run cross-version test as short imperatives. Issue #905 moved the evidence for each here. Each item is the rule's bullet as it stood before that move; "this rule", "this procedure" and "the three above" refer to CLAUDE.md rule 12, and "rule 15" to CLAUDE.md rule 15.

- **"With an agent under it" is load-bearing, and skipping it produces a false green rather than an error.** Start the previous-release daemon with no agents, point the branch TUI at it, and the branch TUI **silently terminates that daemon and lazy-spawns its own in under a second** — PRD #103/#161's build-version handshake behaving exactly as designed: the build ids differ, nothing is running, so it restarts with no prompt. Nothing in the output says so. You then run a **same-version** test that looks like it passed, which is worse than not running one. Measured 2026-08-29 on the PRD #313 run, which lost a full attempt to it. The sequence that actually reaches the scenario is: previous-release daemon → **previous-release TUI** to bring the roles up under it → close that TUI (the daemon and its agents survive) → **branch TUI**, which now shows the mismatch prompt naming the live agents → **decline** it, and the new TUI attaches to the old daemon unchanged. **That attach needs the two builds' `PROTOCOL_VERSION` to be equal** (issue #405): across a difference the decline exits with `error: daemon speaks attach protocol vN, but this binary speaks vM`, leaving the old daemon and its agents running. That refusal is the intended result of a bump, not a semantic break, and there is no attached session left to test a delegate or hooks in — record it as the outcome. Verify you got it before trusting the result: exactly **one** `Attach protocol listening` line for the whole run, and the same daemon pid and build id serving it end to end (that run: `0.38.0-g5a56361`, both sides reporting `server_version: 7`, so it exercised semantics behind a stable wire rather than a handshake rejection — which is what this rule is for). A corollary worth knowing when weighing how much a contract break would actually cost: because the handshake prompts whenever agents are live, **no ordinary user reaches a new TUI against an old daemon without consciously declining that prompt**. **The trap has a second mouth, and a correctly sequenced run falls into it too.** The daemon's idle window defaults to **30 seconds** (`DEFAULT_IDLE_SHUTDOWN_SECS`, `src/daemon.rs`), so letting more than that pass between `daemon serve` and the first attach logs `Daemon idle window elapsed (no clients, no agents, no pending schedules)`, the daemon exits, the TUI lazy-spawns a replacement, and the run is silently a same-version test again — measured on the PRD #745 run, which lost its first attempt to it exactly as #313 lost one to the no-agents cause. Export `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` for every process in the run: it is a documented production knob (`0` = the "always on" / legacy remote behavior) and not a test hook, and `src/` reads it in exactly one place — `idle_shutdown_from_env`, whose only consumer is the idle-timer task — so it moves no protocol path. The `Attach protocol listening` count is therefore the tell for **both** causes: one line is the run you meant, two is a same-version test whichever cause swallowed it. **A third mouth, on the step that closes the previous-release TUI: `Ctrl+C` in `PaneInput` mode goes to the PANE, not to the deck.** With a role pane focused it kills that pane's process instead of opening the quit dialog, so the orchestration comes back one role short and the delegate half cannot run at all — measured 2026-09-05 on the PRD #882 run, which lost its first attempt to it by killing the orchestrator. Press `Ctrl+D` first (the footer says `Ctrl+d for dashboard`), then `Ctrl+C`, then take **Detach**, not `Stop`: `Stop` shuts down the agents and the daemon, which is the whole thing this test needs kept alive. This one at least fails loudly rather than silently — the role is simply absent from `daemon status` — so check the agent list after detaching as well as the `Attach protocol listening` count. And **do the status-hook check last** — sending `agent-event --type running` before the delegate check makes the daemon classify that pane's agent type as `Pi`, which routes prompt delivery differently and makes a delivered delegate briefly look undelivered.
- **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with its sockets and `HOME`.** Pointing `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` / `HOME` / `DOT_AGENT_DECK_STATE_DIR` at a scratch dir is not enough: the log path is resolved separately, so a sandbox daemon otherwise correctly isolated still **appends into your real `~/.local/state/dot-agent-deck/deck.log`**. Two daemons interleaved in one log file is genuinely hard to read after the fact — one incident needed timestamp arithmetic against a socket path just to work out which of two daemons had logged an idle-shutdown line, and the wrong attribution changes the conclusion. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run. **Export `DOT_AGENT_DECK_EXPERIMENTAL` too**, for the same class of reason: project-config discovery walks up from **cwd**, not from `$HOME`, so a sandbox rooted at a sibling path still reads the operator's real `~/.dot-agent-deck.toml` and both daemons come up with whatever feature flags that file sets — measured on the #702/#687 run, where both sides came up `experimental: ON`. It does not bias a comparison (both sides read the same file), but a cross-version sandbox whose feature flags come from the real home is not actually isolated, so pin the flag explicitly rather than inheriting it.
- **Tear the sandbox down by its specific pid, and never with a `pkill -f` pattern that the production daemon's command line also matches.** A **fourth** way this procedure goes wrong, and categorically different from the three above: those cost you the run — two of them silently — while this one destroys work outside the test. Measured 2026-09-15 — [#428 occurrence #5](https://github.com/vfarcic/dot-agent-deck/issues/428#issuecomment-5688814518) — where an agent finishing with a sandbox at `~/dev/xver-876` ran `pkill -f dot-agent-deck-linux-amd64` and then `pkill -f "daemon serve"`. The second pattern matches the **production** daemon's own command line (`…/dot-agent-deck daemon serve`), which took the SIGTERM **1.42 s** later and gracefully stopped every agent it managed — **nine panes across three dispatched units**. So capture the sandbox daemon's pid when you start it and kill that one pid; where you must match a pattern, match the sandbox's own path rather than a verb every deck on the box shares, and read it back through `ps -eo pid,args | grep` before handing it to `pkill`. Note **why nothing stopped it**: `pkill` sends **SIGTERM**, so this goes *around* #770's `daemon stop` refusal rather than having to defeat it (rule 15). Issue #1109 settled the structural half and settled it as "no refusal": a daemon that argues with a SIGTERM is escalated to `SIGKILL` by whatever sent it, which loses the graceful drain too, so the signal path and the TUI's `KIND_SHUTDOWN` frame now **disclose** rather than refuse — one `warn!` naming every agent and orchestration role they take down, before the drain empties both ([`daemon-teardown-paths.md`](daemon-teardown-paths.md)). That is a record, not a prevention: a stray `pkill` still takes the daemon and its panes down, and this step is still what stops it happening. This warns against the deliberate route and closes nothing else — #428's occurrence #4 had an agent whose kills **were** correctly scoped and the production daemon died anyway, which is why that issue's "Still open" item 1, the e2e harness's unisolated attach socket, is a separate live problem.

## Where the reported version comes from, and how to inject it

`Cargo.toml` carries `version = "0.1.0"` as a **placeholder** — it is not bumped per release, so it doubles as the last-resort fallback (step 3 below). For any build expected to be *newer* than `v0.1.0` — every build of `main`, and every release since the first — a reported version of `0.1.0` means the two resolution steps above it both failed. That is issue #250. Note that `0.1.0` is not a *unique* failure signature: `v0.1.0` is a real published tag and GitHub release, so a correct build of that tag legitimately reports `0.1.0`, as does an explicit `DAD_VERSION=0.1.0`. Read the number against the version the build was supposed to produce rather than treating it as failure on its own. The two values a build actually bakes in are emitted by `build.rs` as compile-time env vars: `DAD_VERSION` (the SemVer string behind `--version`, the upgrade nudge, `remote add` pre-flight and the PRD #161 negotiation) and `DAD_BUILD_ID` (`<version>-g<short-sha>[-dirty]`, the finer-grained identifier behind the PRD #103 daemon-restart handshake).

Each is resolved in this order (issue #250):

1. a **pre-set `DAD_VERSION` / `DAD_BUILD_ID` in the build environment**, if present and valid;
2. **git** — `git describe --tags --abbrev=0` and `git rev-parse --short HEAD`, the path a release build and a normal dev checkout take;
3. **`CARGO_PKG_VERSION`** / `<version>-unknown` — the last-resort placeholder.

Step 1 exists for builds where git metadata is absent and step 2 therefore degrades: a source tarball, a shallow or `.git`-less clone, `cargo install --git`, or a sandboxed distro/Nix build. Without an injection those builds silently claim to be `0.1.0`, which every version-aware code path then mis-handles. Packagers should build with the real version in the environment:

```sh
DAD_VERSION=1.2.3 DAD_BUILD_ID=1.2.3-nixpkgs cargo build --release
```

Four properties of that path are worth knowing:

- **An injected `DAD_VERSION` must be valid SemVer.** After a leading `v`/`V` is stripped (the strip a git tag gets) and surrounding whitespace trimmed, the remainder is parsed by `semver::Version::parse` — deliberately the *exact* parser `src/version.rs` uses, so the set of values the build script accepts is by construction the set the binary can parse. Accepted: an `X.Y.Z` core of `u64` fields without leading zeros, plus an optional `-<prerelease>` and an optional `+<build>` suffix (`1.2.3`, `v0.35.2`, `0.25.0-alpha.0`, `1.2.3-alpha+meta` are all fine). Rejected: anything that parser rejects (`1.2`, `1.2.3.4`, `release-7`, `01.2.3`) — because `src/version.rs` does `semver::Version::parse(env!("DAD_VERSION")).expect(…)` and would panic the binary at startup. A rejected injection is *ignored with a `cargo:warning`* and resolution falls through to the next step rather than emitting it.
- **An injected `DAD_BUILD_ID` must be a single line drawn from a bounded alphabet:** ASCII alphanumerics plus `.`, `-`, `+` and `_`. There is no *format* to conform to — the build id is only ever compared as an opaque string by the handshake, so `1.2.3-nixpkgs` or `1.2.3-1ubuntu1` are fine — but the value is emitted into a `cargo:rustc-env=` directive and later rendered into terminals and logs, and Cargo parses build-script output line by line. An interior newline would therefore let the value append a *second* build-script directive (`rustc-env`, `rustc-cfg`, `rustc-link-arg`) — so surrounding whitespace is trimmed and anything outside the alphabet is rejected with a `cargo:warning`, falling through to the git-composed id. The same line-protocol rule applies to every value `build.rs` emits, and a rejected value is escaped (never interpolated raw) into the warning that reports it.
- **Falling all the way through to the placeholder emits a `cargo:warning`**, so a mis-provisioned source build is diagnosable at build time instead of silently reporting the oldest possible release.
- **Changing an injected value invalidates the cached build** (`cargo:rerun-if-env-changed`), so a second build with a different `DAD_VERSION` does not quietly keep the first one.

The repo's own release pipeline uses this seam: `release.yml`'s build job passes the `prepare` job's version as `DAD_VERSION` (and names it in `CROSS_BUILD_ENV_PASSTHROUGH` so it reaches the `cross` container too). On a tag push that is the same string `git describe` resolves in the tagged checkout, so nothing changes; on a `workflow_dispatch` release from `main` the tag does not exist yet, and without the injection the artifact would bake the *previous* release's version and be published under the new tag.

The `prepare` job **validates that version as SemVer before it writes it to `GITHUB_OUTPUT`**, and fails the release if it does not match. The reason is the fall-through above: `build.rs` *ignores* an invalid injection rather than failing the build, so a malformed `workflow_dispatch` input or an oddly-named tag would be dropped silently and the artifact would resolve its version from git — or from the `0.1.0` placeholder — while still being published under the requested tag. That is issue #250 again, so the gate rejects the value at the one place it enters the pipeline instead of letting every consumer (the changelog script, the changelog commit message, the release tag, the `task` publish steps, the docs workflow) inherit it. Two details of the check matter if you ever edit it: it is deliberately at least as strict as `semver::Version::parse` — including a digit bound that keeps the three core fields inside `u64` — so nothing it accepts can be rejected downstream; and it pins `LC_ALL=C` and spells its character classes out as explicit ASCII enumerations, because a bracket *range* in a bash regex is resolved through the active locale's collation, which had let values like `1.2.3-é` and full-width digits through on a runner whose locale happened to be `en_US.UTF-8`.

The resolution logic itself lives in `build_version_resolve.rs` at the repo root as pure functions, compiled as an out-of-line module by both `build.rs` (`mod build_version_resolve;`) and `tests/build_version.rs` (`#[path = "../build_version_resolve.rs"] mod …`) — `cargo test` cannot reach code inside a build script, so this is what makes the order testable. A module rather than an `include!` on purpose: rustfmt does not follow `include!`, so the shared file would otherwise escape the mandatory `cargo fmt --check` gate. `lifecycle/version/001` (`tests/e2e_version_injection.rs`) covers the whole chain by rebuilding the binary with the vars injected, twice over changing one variable at a time to pin the rerun directives.

## One product, three components, one release

CLAUDE.md rule 18 says the daemon, the TUI and the desktop app are one product, that changing the daemon is normal, and that the protocol's change path is graded. Issue #905 moved the file-level evidence and the worked examples behind it here. Each paragraph is the rule's text as it stood before that move; "rule 12" and "rule 17" mean CLAUDE.md rules 12 and 17, and "this file" means CLAUDE.md.

### The three components

- the **daemon** owns agent processes, PTYs, session state and hooks; its contract is [`src/daemon_protocol.rs`](../../src/daemon_protocol.rs).
- the **TUI** (`src/ui.rs`, `src/main.rs` and friends) is a terminal attached to **one** daemon at a time — `Endpoint` (`src/daemon_client.rs:68`) is a single `Local`/`Remote` choice, not a map. It is also the *same crate and the same binary* as the daemon, which is a subcommand of it (`src/main.rs:210`): the root package declares no `[[bin]]` at all, so one `dot-agent-deck` binary is both. "Change the TUI" and "change the daemon" are edits to one package.
- the **desktop GUI** is `desktop/`: a TypeScript frontend under `desktop/src/` plus its own workspace-member crate under `desktop/src-tauri/`, which depends on the root package by path. It holds **many** daemons at once — `links: AsyncMutex<HashMap<EndpointIdentity, Arc<TrustedDaemon>>>` (`desktop/src-tauri/src/daemon_bridge.rs:284`), one entry per deck.

### One version, injected rather than stored

**They ship from one release run, at one version — and that version is not three numbers someone keeps in step, it is one number none of them stores.** All four manifests carry the literal `0.1.0` and always will: `Cargo.toml:12`, `desktop/src-tauri/Cargo.toml:3`, `desktop/package.json:4`, `desktop/src-tauri/tauri.conf.json:4`. Each is a deliberate placeholder. The real version is injected from the release tag — into the binaries through `build.rs`'s `DAD_VERSION` seam (`build.rs:22-61`, which prefers an injected value over `git describe`), and into the desktop bundle through the `jq` merge in `release.yml`'s desktop leg, which then *asserts* that the version reached the output filename rather than trusting the exit code. The one tracked file carrying a released number is `flake.nix:59`, pushed to `main` by `tag-release.yml` (rule 8). So the three cannot drift apart by someone forgetting a manifest: there is no manifest to forget.

**Do not write "always released together" — the workflow admits exceptions, and rule 17 applies to this file hardest of all.** `release.yml`'s `desktop-bundle` and `desktop-publish` jobs are both gated on `!inputs.skip_desktop` (lines 546 and 705). On the path this repo actually releases by — `/tag-release` dispatching `tag-release.yml`, which pushes the `v*` tag that triggers `release.yml` as a separate run — that gate is **unreachable**: `tag-release.yml` declares no such input, and `inputs` is empty on a tag push, so the desktop bundles on every tagged release. `skip_desktop` is reachable only by dispatching `release.yml` by hand, and its own comment calls it "an escape hatch for cutting a release while the bundler is known-broken, not an opt-in". The second exception is a failure rather than a choice: the bundle matrix is `fail-fast: false`, and when every leg fails `desktop-publish` errors with "the CLI release itself is unaffected and complete". So the accurate claim is **one release run builds and publishes all three, the desktop assets as unsigned *alpha* outside the CLI's support expectations, and the CLI ships even when the bundle does not** — not "always released together".

### The graded path, with its worked examples

**Rule 12 is the PROCEDURE for changing the daemon, not a prohibition on changing it** — and that misreading is the entire reason this rule exists. The path is graded, and the cheap step is the common one:
- an **additive optional field** on an existing message needs **no** `PROTOCOL_VERSION` bump. That is not a judgement call; it is the protocol's own written policy — "**Do NOT bump:** additive optional fields tagged `#[serde(default, skip_serializing_if = "Option::is_none")]`" (`src/daemon_protocol.rs:11-14`). PRD #745 landed two of them in one commit, `SessionSnapshot::last_activity_ms` (`src/state.rs:715`) and `AgentRecord::spawned_at_ms` (`src/agent_pty.rs:2425`); `79ade039` added 236 lines to `src/daemon_protocol.rs` and left the constant alone.
- a **new request variant that every sender withholds until the daemon advertises a matching capability** needs **no** bump either, and this is the rung to reach for when a client needs a new *verb* rather than a new field. Also the protocol's own written policy — "**Do NOT bump:** … a new [`AttachRequest`] variant that every client withholds until the daemon names it in [`DAEMON_CAPABILITIES`]" (`src/daemon_protocol.rs:8-16`). PRD #1105 is the worked example: `AttachRequest::FocusGained` ships gated on `CAP_FOCUS_GAINED`, with the check in the client library (`DaemonClient::focus_gained_while`) rather than in each caller, and it moved `PROTOCOL_VERSION` by nothing. **Read that as "contributed no bump", not as "the constant is 9"** — the constant is now 10, and that is #1049's ungated `stop-daemon` (#1113), landing on `main` while #1105 was in review. A gated variant ships under whatever number the wire is already at; do not read a bump beside it as having been spent on it, and do not read one as overturning the decision. **Two limits, both load-bearing.** It holds only while *every* sender gates — one raw call site that skips the check puts the change back on the bump list, which is why the check lives in the client library. `stop-daemon` is the worked counter-example and it is not a contradiction: it *has* a capability string, but `run_daemon_stop_over_wire` sends the frame without consulting it and reports the older daemon's `unknown variant` refusal instead, so the exception never reached it. And it says nothing about a **semantic** break: #1105 contributed no bump and still owed a `.breaking.md`. [How a break is detected and marked](#how-a-break-is-detected-and-marked) item 1 carries the reasoning, the cost of a bump, and the one residual pairing that survives — a client handle whose cached capability set outlived a daemon replaced by an older build — which **fails closed**.
- a change to the wire **shape** bumps `PROTOCOL_VERSION` (`src/daemon_protocol.rs:388`), per rule 12 and [How a break is detected and marked](#how-a-break-is-detected-and-marked).
- a **same-wire/different-meaning** change adds a `changelog.d/<issue>.breaking.md` fragment.
- rule 12's cross-version manual test is what you **owe after** making the change, not a reason to avoid making it.

### The flinch, and what it cost

**The flinch is real and it has cost work.** PRD #1105 spent rounds asking only what the desktop could do without touching the wire, and its own record of what finally shipped reads: "What made it tractable, which is the part that had been assumed impossible" (`prds/done/1105-desktop-agent-pane-overlay.md:450`). #1073's `PROTOCOL_VERSION` objection is about N decks × M concurrently visible *tiles*; it had been applied to a single overlay pane, which needed no wire change at all. PRD #745 is the model to copy instead: it scoped output previews out because the daemon "genuinely could not serve [them] today" — and then **named the daemon-side work** that revisiting the decision would imply (`prds/done/745-desktop-agent-overview-landing-screen.md:123`). Stopping at "the daemon cannot" is the failure; saying what the daemon would need is the deliverable.
