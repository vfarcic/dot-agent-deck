# Project config trust: maintainer notes (PRD #1885)

The user page is [`docs/project-trust.md`](../project-trust.md). This page records what a maintainer needs and a user does not: where the decision lives, the store, the wire, which execution points are gated and which are deliberately not, and why the contract break has no `KNOWN_EFFECTS` entry. The binding decisions are the two decision records on issue #1885 (comments 6755578007 and 6756637155); this page summarises them as built, on 2026-11-10.

## Where the decision lives

`src/project_trust.rs` owns it: what an approval records (`ApprovedRole`: `name`, `command`, `agent`, `start`, `clear`, `description`, `prompt_template` of every resolved role, after `extends`), the project identity (`project_identity`), the store, the verdict (`TrustVerdict::{Approved, NeverApproved, Changed}`), the refusal text (`refusal_text`, which always names `dot-agent-deck trust approve <dir> --orchestration <name>`) and the digest. Every daemon-side gate calls `check_blocking` / `check_named_blocking`, which re-reads the store each time, so an approval from the CLI takes effect without a daemon restart. The TUI and the desktop do not decide: they ask the daemon (`ProjectTrustState`) and approve through it (`ApproveProjectTrust`), so both clients share one decision and one store. The TUI widget and its gate are `src/trust_prompt.rs`; the CLI is `src/trust_cli.rs`; the desktop's bridge is `desktop/src-tauri/src/trust_review.rs` and its flow `desktop/src/lib/projectTrust.ts`.

**The digest is SHA-256 over the shown text**, never the config revision (`project_resolve`'s FNV hash), which is a staleness hint and not collision-resistant. Its only job is to make an approval cover exactly what a client showed: `ApproveProjectTrust` carries it, and a digest that no longer matches is refused with `trust-text-changed` and records nothing.

## The store

`<state_dir>/project-trust/approvals.json` (`STORE_DIR`, `STORE_FILE`), `state_dir` being `crate::config::state_dir()` (`DOT_AGENT_DECK_STATE_DIR`, else `$XDG_STATE_HOME/dot-agent-deck`, else `~/.local/state/dot-agent-deck`). The directory is created owner-only through `TrustedDir`; a write replaces the file whole (owner-only temp file, `fsync`, rename) under an exclusive lock on `approvals.lock`, so a CLI approval and a daemon approval cannot lose each other's write. The file is JSON, `{"version": 1, "approvals": [{project, orchestration, approved_at, roles: [...]}]}`; it keeps the approved text itself, not only a digest, so a prompt can mark which roles are `changed` or `new` and list removed ones. A file larger than 16 MiB is refused as not one this build wrote. An unreadable store is treated as holding no approvals and logged, which fails closed.

**The store's location is chosen by the daemon's environment, and that is a boundary, not a guarantee.** `TrustStore::default_location()` follows `DOT_AGENT_DECK_STATE_DIR` and `XDG_STATE_HOME` as `state_dir()` does, and nothing refuses a state directory inside a project. So a daemon started from a shell that loaded a project's environment (devbox's init hook sourcing the project's `.env`, a direnv `.envrc`) can be pointed at an approvals file the project wrote, as long as it passes the `TrustedDir` checks. A daemon already running is not moved by a later edit to a child agent's environment, since the location is read in the daemon's own process. This is the same class as the excluded project-environment and build-input execution (issue #1885's decision record) and the accepted same-UID limit (#1886): it is why the user page tells users to start the daemon from their own shell, and why neither page calls the store agent-proof or out of a project's reach.

`TrustStore::use_state_dir_for_this_process` moves where approvals are kept for a whole process (a test harness running daemon code in-process); a `cfg(test)` build uses a private directory. Neither changes whether a spawn is checked. The harness pre-approves fixture projects through the real store or the real CLI (`tests/common/lib.rs`: `approve_project_fixture`, `TuiDeck::trusting_project`, `DaemonProc::approve_project_trust`); a test that wants the prompt opts out with `without_trust_preapproval` / `spawn_daemon_serve_untrusted`.

**Project identity:** `project_identity` resolves a directory in a git repository to the repository's main working tree, joined with the config directory's position inside its own worktree (so two configs in two subdirectories of one repository stay two projects). Anything git cannot answer falls back to the canonical config directory, which can only split projects, never merge two.

**A linked worktree borrows the main checkout's identity only when its geometry is verified** (`verified_geometry_of` in `src/worktree_owner.rs`, the review round of 2026-11-10). git answers `--git-common-dir` from whatever a `.git` file names, so a directory holding a copied or hand-written `.git` file pointing into another repository's store would otherwise be keyed on that repository's main checkout and inherit its approvals. `verified_geometry_of` reads `--show-toplevel`, `--git-dir` and `--git-common-dir` once and accepts a linked worktree only when its administrative directory is `<common>/worktrees/<name>` (the registration `git worktree list` reads), that directory's `gitdir` back-pointer (absolute, or relative to it under `worktree.useRelativePaths`) canonicalises to this worktree's `.git`, which is a regular file, and `<common>`'s parent holds `<common>` as its `.git` directory. A directory failing any check is keyed on its own canonical path, so a copied `.git` file does not share an approval. `schedule_003_a_forged_gitfile_does_not_borrow_another_checkouts_approval` and the unit test `a_linked_worktree_is_keyed_on_its_main_checkout` pin it. **An unnamed orchestration is keyed on the project's basename** (`approval_name` in `src/project_trust.rs`, Qodo's finding on PR #2256). `load_project_config` names a block with no `name` after the directory it was read in, which differs in every linked worktree, so `TrustCheck::evaluate` keys such a block on the basename of the verified `project_identity` instead, and `TrustCheck::orchestration` (what refusals, `print_check` and `ProjectTrustView` show) carries that name. The loaded config no longer says whether a block was unnamed, so a name equal to the config directory's basename is read as one; only at a linked worktree's top level does that change anything, and there a block explicitly named after the worktree's directory is keyed on the project's basename too, still against its own exact text. `inspect_config` (behind `trust approve --orchestration`, `ProjectTrustState` and `ApproveProjectTrust`) matches the approval name first and the loaded name second, so the TUI (which sends back the view's name) and the desktop (which sends the name it listed) both resolve. The name comes from the verified identity, so a forged `.git` file keys the directory on itself and its unnamed block keeps its own basename. `schedule_005_an_unnamed_orchestration_is_shared_by_a_linked_worktree` and `config_trust_schedule_006_an_unnamed_orchestration_dispatches_once_the_clone_is_approved` pin it. This is approval keying only: delegate lookups by name in a linked worktree still use the loaded name.

## The wire

`CAP_PROJECT_TRUST` (`"project-trust"`) gates two attach requests, `ProjectTrustState { path, orchestration }` and `ApproveProjectTrust { path, orchestration, digest }`, with the reply on `AttachResponse::project_trust`. Every sender withholds them unless the daemon advertises the capability (CLAUDE.md rule 18, second rung), so there is no `PROTOCOL_VERSION` bump. `PrepareOrchestration` gained the typed error code `not-approved` (`PROJECT_ERR_NOT_APPROVED`); a client that does not know the code still shows the sentence after it, which names the CLI fix. The hook socket has no verb that approves: only a client acting on a user's answer and `dot-agent-deck trust approve` do, and the CLI refuses inside a deck pane (`PANE_IDENTITY_ENV`).

A client meeting a daemon without the capability: the TUI never prompts, reads the store itself read-only and refuses an unapproved orchestration with `OLDER_DAEMON_NOTE` and the approve command; the desktop cannot read the deck's store (it may be on another host, and a client-side read is what the desktop project boundary forbids), so it answers `Unsupported` with `older_deck_refusal` and starts nothing.

## The contract break, and why `KNOWN_EFFECTS` has no entry

The new refusals on existing requests (the desktop's prepare and prepared start, `delegate`, `pane restart`, `pane spawn`, `dispatch`) are declared as a contract break, after issue #1233's precedent: `changelog.d/1885.breaking.md` and `CONTRACT_BREAKS` entry `1885-unapproved-project-config-refused`. The wire did not move, so `PROTOCOL_VERSION` did not either. `cargo xver`'s setup TUI answers the trust prompt with `a`, so the sandbox project is approved in the serving daemon's store before any tell runs, and no tell meets the break; [`cross-version-harness.md`](cross-version-harness.md) has the detail.

## In-deck approval requests (issue #2330)

A refusal on an unattended path used to end at the printed `trust approve` command, which itself refuses inside a deck pane. `src/trust_requests.rs` is what lets the user answer inside the deck instead. Every daemon-side refusal of an unapproved check goes through `trust_requests::refusal_for` (`spawn::approval_refusal_asked_by` for dispatch, a scheduled fire, Run now and the issue-dispatch clone check; `ProjectConfigs::trust_refusal` / `delegate_trust_refusal` for `delegate`, `pane restart` and `pane spawn`). In the serving daemon it raises a `TrustRequest` keyed by project, approval name and digest (the key an approval covers), broadcasts the whole list as `BroadcastMsg::TrustRequests`, and words the refusal `requested_refusal_text`, or `declined_refusal_text` for a key the user denied. The desktop's `PrepareOrchestration` (its New Agent path, which shows its own review) and `branch_differs_refusal` (approving the branch's text would replace the default branch's approval) raise nothing.

**Only `daemon serve` raises.** The hub is process-wide and serves only once `trust_requests::install` gives it the daemon's broadcast sender, which `main.rs` does next to the hook-pin refresh, for the same reason: `run_daemon_with` also runs in-process test daemons. Everywhere else `refusal_for` is `TrustCheck::refusal`, so the TUI's read-only fallback and the CLI are unchanged.

**The rules as built.** A key already pending raises nothing new (a retry opens no second dialog); a new digest for the same project and orchestration replaces the pending one, which could no longer be approved as shown. `DenyTrustRequest { id, digest }` closes the request and remembers the key (at most `MAX_DENIALS`, oldest forgotten) until the daemon exits; it declines nothing when the request under `id` carries another digest, since a restarted daemon numbers anew and a review left open across the restart would otherwise decline text the user never saw. An approval of that same text, by a client (`ApproveProjectTrust` calls `note_approved`) or found by a later check, forgets the denial; an approval of another text of the orchestration (a linked worktree's, say) does not, so a declined text stays declined until the daemon restarts, as the issue's rule says. At most `MAX_PENDING_REQUESTS` are pending; past that a refusal is the PRD #1885 text and raises nothing. `run_sweep` re-checks pending requests every `SWEEP_INTERVAL` and drops one that is approved (the CLI writes the store without telling the daemon), whose config now reads another digest, or whose config or orchestration is gone, so the dialog closes in every client. A store that cannot be read settles nothing. The clients retry a review they could not read after a five-second back-off (`TRUST_REQUEST_RETRY_AFTER`, `TRUST_REQUEST_RETRY_MS`), and the TUI's key guard restarts on every key it ignores, so typing under way when the review appears cannot reach `a`. Nothing here is written to disk: a restart drops pending requests and denials, and the user page says so.

**The wire.** `CAP_TRUST_REQUESTS` (`"trust-requests"`): the `Hello` and `SubscribeEventsWithSnapshot` replies carry `AttachResponse::trust_requests` (additive, optional), changes arrive as `BroadcastMsg::TrustRequests` (a new `kind`; a client that predates it decodes `Unknown`, issue #1637's precedent, so no `PROTOCOL_VERSION` bump), and `DenyTrustRequest { id }` is withheld by `DaemonClient::deny_trust_request` unless the cap is advertised (CLAUDE.md rule 18, second rung). Approving is the existing `ApproveProjectTrust`; a client reads the text with the existing `ProjectTrustState` on the request's `config_dir`. `daemon_client::trust_requests_of` takes a list only from a reply that advertises the cap, bounded and escaped (`TrustRequestList::sanitized`). Every list carries a `revision`; the TUI keeps the newest (`AppState::apply_trust_requests`) and re-seeds from `Hello` on every resubscription, which also covers a restarted daemon counting from zero. The broadcast reaches every subscriber, so it is not gated per connection; what is gated is what a client does with it and what it sends back. No `.breaking.md`: an older client against this daemon sees the refusal text change (it still names the CLI command) and no dialog, and an older daemon advertises no cap, so a new client shows none.

**The clients.** TUI: `poll_trust_requests` (`src/ui.rs`) runs every frame. It sends queued denials, closes an open request's review when the daemon stops listing it (`request_answered_elsewhere_message`), and otherwise opens the oldest unseen request's review through `TrustPromptPurpose::Request` once the deck is in `Normal` or `PaneInput` with no prompt open and no held restore waiting, reading the view with `project_trust_state` (an approved answer opens nothing). The prompt is `PromptAction::Request` (`a approve · Esc deny`), led by `REQUEST_INTRO` and `Asked by:`; it takes no key for `REQUEST_KEYS_ARM` after it opens, on top of the existing undrawn-choice guard, and returns to the mode it opened over. Approving starts nothing. Desktop: the per-deck connection carries the requests from the handshake, re-read on the broadcast (`agent_view.rs` marks a handshake re-read, as for hook-binary notices), and the review flow opens the existing dialog in request mode; see `desktop/src/lib/projectTrust.ts`. Its approve stays voice-reachable through `approve_project_commands`, and Deny is the dialog's cancel control, reached by voice through `close`.

**Telling the refused agents (issue #2348).** Approval still starts nothing; instead each refused agent is told the answer and decides whether to retry, since the refused request may be stale by then. The four agent paths pass a `RefusedCaller` (pane, the agent holding it, the verb) to `refusal_for`: `dispatch.rs` from `ctx.caller`, `delegate_trust_refusal` and `dispatch_one_owned`'s re-check from the orchestrator's pane and agent, and `pane restart` / `pane spawn` from the signal's pane and `pane_current_agent_id`. Schedules, Run now and issue dispatches pass `None`. `TrustRequestHub::raise_for` records the caller against the pending request (`waiting`, once per agent and verb, at most `MAX_WAITING_CALLERS`); a declined key records nobody, since its refusal already says so; a replacing digest carries the old request's callers over, since their retry reads the config as it now reads. Every way a request closes queues one `CallerNotice` per agent in the hub's `outbox`, grouping its verbs: `deny` as `Answer::Declined`, `settle_approved` (client approval, or a check that found it approved) as `Approved`, and the sweep as `Approved` for an approval in the store (`trust approve` from a terminal) or `Withdrawn` for a changed or missing config (`stale_requests_blocking` answers which). A check that found the text approved does not tell its own caller, which is already starting it (`settle_approved_except`). The served functions take the outbox under the hub's lock and post it after releasing it, on the blocking pool (`deliver`), through the `NoticeSink` that `main.rs` installs: `inbox_sink`, which posts a deck notice with `post_notice_to_live`, so an agent no longer holding its pane is skipped. The refusal promises a notice (`REQUESTED_WILL_TELL`) only to a caller the hub recorded with a sink installed, and keeps `REQUESTED_RETRY` otherwise. No wire changed: the notice is an ordinary deck notice on the existing inbox, and the refusal is free text.

The tests: `trust_requests` unit tests (the hub, the sweep, the wire, the served refusal wording, the callers' notices), the `request_tui_*` tests in `src/ui.rs`, and `config-trust/request/001`–`005` (`tests/e2e_config_trust.rs`).

## Execution points

Gated in the daemon, refusing and reporting (never prompting): a scheduled fire and Run now (shape override included), a scheduled issue dispatch, `dispatch`, every `delegate` (the worker's `prompt_template` is project text reaching an agent, so not only `clear = true` roles; checked at reply and again at a respawn), `pane restart` and `pane spawn`, and the desktop's `PrepareOrchestration` and the prepared start's re-read. Issue dispatch and `dispatch` check **before** the worktree's `devbox` warm-up: issue dispatch creates the worktree unwarmed, checks the config the spawn will read (a reattached `agent/issue-<n>` branch's own), and on a refusal removes the worktree so the issue is retried once approved. Since the run checked the clone first, a refusal there means the reattached branch carries other text, and approving it would replace the default branch's approval (one per project and orchestration) and refuse every later fire; so `refuse_unapproved_worktree` (`src/issue_dispatch_run.rs`) records `branch_differs_refusal`, which names the branch and the clone and offers aligning the branch or `git -C <clone> branch -D agent/issue-<n>` instead of an approve command naming the removed worktree. When the clone itself is no longer approved (revoked or changed meanwhile), the clone's own refusal is recorded instead. `config-trust/schedule/004` pins it. A refused schedule fire is recorded by `src/schedule_outcome.rs` beside the store and shown by `schedule list` and the TUI's Schedules manager (`refused`); the next fire clears it before it runs.

Prompting, in a client: the TUI's New Agent form and session restore (restore holds back each unapproved orchestration for its own prompt, restores the rest, and leaves a cancelled one unrestored). A held snapshot, whether queued in `pending_trust_restores`, open in the prompt or cancelled (`declined_trust_restores`), is written back unchanged by every session save (`keep_held_trust_restores`, both the periodic flush and the save on quit), unless a live tab of the same project and config name already saves it, so the next start asks again; this reverses the earlier choice not to write a cancelled restore back (Greptile's finding on PR #2256). `dot-agent-deck snapshot clear` is how a user drops it. `config-trust/restore/002` and `/004` pin it, the desktop's New agent dialog and the Runs screen's Activate.

**Restore no longer falls back to a plain pane.** Before PRD #1885, a saved orchestration whose snapshot no longer resolved (`resolve_orchestration_for_restore` failing: config missing, orchestration renamed, role set changed, `project_path` diverging from the saved dir) or whose rebuild failed was restored as a plain dashboard pane running its saved command, the PRD #89 behaviour. That command is the start role's as captured, and a snapshot that does not resolve cannot be trust-checked, so it would have run unapproved project text. Both cases now push a `session_warnings` line (`Warning: <reason>; orchestration '<name>' was not restored`, or `Warning: failed to rebuild orchestration '<name>': <error>; it was not restored`, printed on exit) and `continue`; the rest of the session restores. `session/restore/009`, `/010` and `/012` were changed from asserting the fallback to asserting it is gone, and `config-trust/restore/003` covers the three drift shapes.

**The remit re-arm is gated too, and never prompts.** The TUI re-sends the orchestrator's remit when its conversation is compacted or `/clear`ed (`reassert_orchestrator_prompt`, `src/ui.rs`). After a warm reattach the tab's `OrchestrationConfig` was read from the config without a trust check, so those two call sites are the only paths that could publish unapproved text to a running orchestrator; `rearm_trust_gate` (`src/ui.rs`) runs before both. Its decision is `decide_rearm` / `decide_rearm_for_dir` in `src/trust_prompt.rs`: publish the tab's text only when the daemon answers `approved` and the approved roles are exactly that text; when they are not but a fresh read of the config is the approved text with the same role names, order and `start` flags, publish that and adopt it into the tab (`Rearm::PublishApproved`); with an older daemon (`GatedQuery::Unsupported`) check the tab's text against the store read-only; otherwise refuse (`Rearm::Refuse`), naming the approve command, with the text in the status line and a `warn!`. A refused `/clear` re-arm is marked seen so it is not retried every frame. While a daemon answers, the TUI does not substitute its own store read for the daemon's `changed`, so an orchestration running approved text whose file was then edited and not approved is refused. `config-trust/rearm/001` covers it; `orchestration/remit/001`–`011` cover the ordinary re-arm.

**The daemon's re-arm needs no gate of its own (PRD #82).** For an orchestration the daemon records a context file for (a dispatch, a schedule, a desktop start: anything that went through a preparation), the daemon re-arms the coordinator itself on the same two triggers (`AppState::orchestrator_rearm_due`, `daemon_protocol::rearm_orchestrator`), and a TUI that sees `CAP_REARM_ORCHESTRATOR` leaves those tabs alone. It reads no config: it republishes the recorded file's bytes as a new per-publish file (`republish_orchestrator_context`). Those bytes are the ones the preparation composed and the trust gate admitted when the orchestration started, so republishing them publishes nothing that was not approved, and an edit to the config since then does not reach the coordinator until the orchestration is started again. The TUI's gated path above stays for the tabs the daemon records no file for (a `Ctrl+n` start) and for a daemon too old to advertise the capability. The desktop has no re-arm path of its own; it gets the daemon's.

**Refusal text is escaped at its source.** `refusal_text` escapes its own output (`untrusted_text::escape_control_and_bidi`), so every sink (scheduler stderr, the schedule outcome, the daemon log, the delegate, restart, spawn and dispatch responses) gets it escaped; `log_refusal`'s fields, the spawn path's approval-check error and the CLI's delegate error are escaped too. Names and paths inside `TrustCheck` stay raw, for identity and argv. `config-trust/escape/001` pins it.

**What a desktop approval is bound to** (the review round of 2026-11-10). Each shown review has a number that is never reused, and its token is that number plus the digest it shows (`reviewToken` in `desktop/src/lib/projectTrust.ts`). The voice surface reads the token when an utterance is declared (`VoiceContext.trustReview`), refuses the answer when it moved (`REVIEW_MOVED_ON`), and hands it to the dispatch, where `approveShownReview(declared)` approves only that review; the dialog passes the token it rendered to `approve`. The start continuation runs only while the review it was asked for is still on screen and the host is mounted, so Cancel, `Esc`, voice's close and an unmount during an in-flight approval start nothing (the approval itself may already be recorded, which the dialog says). The Runs screen captures its deck when Activate is pressed and sends it with the query, the approval and `ActivateOrchestration.deck_id`; a selection change closes the review and says so with `reviewDeckChangedNotice`: `REVIEW_DECK_CHANGED` before Approve and start was pressed, and while an approval is in flight (`busy`) a sentence that nothing started but the original deck may still record the approval, with the `trust revoke` command as the toast's detail. Both clients launch with the `config_revision` the daemon returned with the approved view (`ProjectTrustView::config_revision`, an additive optional field filled by `trust_view_now`), so text re-shown after `trust-text-changed` starts at its own revision and a later edit is still refused as `stale-revision`.

Deliberately not gated, and stated on the user page:

- the raw attach-socket `StartAgent`, which takes an arbitrary command by design (control-plane scoping, #1886);
- `dispatch --command` / `--agent`, an agent-chosen command (T2, #1887);
- a schedule's own `command`, from the user's global config;
- the desktop Runs screen's role profiles, which are the user's own commands behind an existing disclosure dialog (the project prompt text that path hands an agent is gated);
- restore's replay of the orchestrator prompt saved in `session.toml`, which is gated by the current config's approval but not recomposed from it;
- `devbox.json` and the rest of a project's build inputs.

**Honest limit:** the store and the CLI are reachable by any process running as the user, agents included; refusing the CLI inside a deck pane stops an agent that keeps the deck's environment, not one that drops it or writes the file. Closing that is #1886's.
