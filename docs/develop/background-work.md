# Background work after an agent's turn

Issue #1678. When an agent that reports its own turn boundaries ends its turn, its card stays **Idle**, and work it left running — background commands and background subagents — is shown beside the status as `Background: 2 commands, 1 subagent · 3h 12m` instead of flipping the card back to **Working**. The user-facing description is [Session Management → Work left running after a turn](../session-management.md#work-left-running-after-a-turn); this page is the mechanism. The binding design notes for the unit live in the issue's comments.

Before this change the shell-activity monitor ([`shell-activity-signal.md`](shell-activity-signal.md)) promoted a pane whose agent had a qualifying command running in its own POSIX session to `Working`, which meant a command Claude Code backgrounded at its 120 s cap kept the card `Working` for as long as the command lived, and a subagent Claude Code 2.1.296 runs in the background left the card `Idle` with no sign anything was still going.

## The two latches

Both live in a private per-card `BackgroundTrack` in `AppState::background_tracks` (`src/state.rs`), keyed by card id and present only where the daemon's ownership oracle is installed. `SessionState` carries no field for them, because fixtures build it by exhaustive literal.

- **Reporting latch (`reports_turn_boundaries`).** Set by the first genuine status report from this spawn: any admitted event except what the daemon authors (`ShellBusy`, `ShellIdle`, the card-surfacing and wrapper-fork `SessionStart`s, delivery notices, quota lifts), the `Unknown` catch-all, and the Codex wrapper's output-classified frames, which read Codex's screen rather than a turn boundary (`is_genuine_turn_report`). Pi's extension reports count. It resets when a different agent id takes the card (process replacement). On a pane with the latch set, `ShellBusy`/`ShellIdle` never move the status; a pane without it keeps the PRD #386 behaviour, `shell_synthetic_working` and its takeover protections included.
- **Turn latch (`turn_ended`).** Set by a main-thread `Idle` (Claude's `Stop`, OpenCode's session idle, Pi's finished) or `QuotaBlocked`, and by a terminal main-thread `Error` without a tool name from Claude Code or OpenCode (Claude's `StopFailure`, OpenCode's `session.error`); a failed tool call does not end the turn. Cleared by `Thinking` or a main-thread `ToolStart`. Subagent events (anything carrying the subagent-id metadata key) and shell events never change it, so Needs Input, Blocked or Error after an ended turn leave it set.

Background counts are published only while both latches are set. During a live turn a process in its own session is the foreground tool call, not background work, so both counts are zero.

## The subagent tracker

`BackgroundTrack::subagents` maps a subagent id to the daemon's receipt time of its `SubagentStart`, in epoch milliseconds on the daemon's clock; payload timestamps are not used. The id is `AgentEvent.metadata[SUBAGENT_ID_METADATA_KEY]`, not `AgentEvent.agent_id`.

- A start inserts through `entry`, so a duplicate start keeps the original time.
- A stop removes the id. **A stop for an id the map does not hold is a no-op for the tracker**: it decrements nothing, clears nothing and raises nothing. Claude Code 2.1.296 sends three such unpaired internal stops per run. The tracker is updated beside `apply_event`'s existing logic, not by an early return in it, so the `SubagentWait` resolver still sees every stop (a stop can end a permission wait the tracker never saw start).
- **Bounds.** At most `MAX_SUBAGENT_IDS` (128) ids. An id must be non-empty and at most `MAX_TRACKED_SUBAGENT_ID_BYTES` (256) UTF-8 bytes; a longer one is not tracked at all rather than truncated, since two ids sharing a prefix would collapse into one. Its event keeps the subagent-id metadata key, so a `ToolStart` from it is still attributed to the subagent and does not read as a main-thread call.
- **The undercount is accepted.** A start that arrives while 128 ids are tracked is not recorded, and an oversized id is not recorded either, so the published `subagents` count understates in those cases. There is deliberately no anonymous overflow counter: `SubagentWait.overflow` is not reused, because an unknown stop decrements it, and a stop with nothing to pair against cannot be told apart from Claude's unpaired internal stops.
- The map is cleared on a genuine `SessionStart` that names a new hook generation for the pane (Claude Code's `/clear` sends one); the record's commands stay, with their first-seen ages, because they belong to the process and not to the conversation.
- **A conversation's end retires its record explicitly**, not by whether a card is still filed under its key, because the placeholder a managed pane gets back after a `SessionEnd` reuses the key `pane-<pane_id>`. The admitted `SessionEnd` clears the subagents and the turn latch, so nothing is counted until a turn of the next conversation ends, keeps the commands and their ages for that turn, and moves the record onto the restored placeholder when it is the same agent's, so the revision keeps advancing for that spawn. `remove_sessions_for_pane` and `apply_daemon_pane_closed` empty the record of every card they remove, commands included, in place: a card the same spawn gets back under that key continues the revision, and the record goes at the next event's sweep if the key stays empty. Its counts are also emptied when the monitor retires the spawn (below).

## The counted scan

`qualifying_command_sessions` (`src/platform/proc/scan.rs`) returns the distinct POSIX session ids below the agent that qualify as commands: the same structural session-boundary test the boolean path uses, with the per-agent argv cross-check applied to **every** candidate when the agent has a shape (no early return on the first match), deduplicated by session id, and keeping `walk_with_reference_session`'s re-rooting at a nested terminal session so a Codex wrapper's inner agent is not counted. The boolean `descendant_shell_activity` is derived from it. It reads the same `ps` columns as before (issue #862's cost measurement still holds) and keeps the deadline, the retained sample, table-age rejection and backoff. An unknown root, session id or sample is `None`, not zero; on `None` the last known set is kept, and a valid sample replaces it.

On Windows the process-table scan returns `None`, so no command is ever counted there; subagent counts are unaffected.

## Durations: first seen, not process start

`BackgroundTrack::commands` maps each qualifying session id to the time the daemon **first sampled** it, including while it was still the foreground tool call, so a command that becomes background when the turn ends keeps its age. `observe_commands` keeps the first-seen time of every session still present and drops sessions that left a valid sample; an unknown sample restarts nothing. `since_ms` is the minimum over the commands and subagents currently tracked, recomputed when items leave, so it follows the oldest item still running rather than a sticky minimum. The process table has no start-time column, and adding one would put back the per-poll cost issue #862 removed; reading the OS start time is a possible later refinement.

## The aggregate is the daemon's, with a revision

`BackgroundWork { commands, subagents, since_ms }` (`src/event.rs`) is computed after the status transition, under the ingest write lock, by `BackgroundTrack::republish`, which advances a per-spawn `revision` (checked `u64`, reset with the track on process replacement) whenever the aggregate changes. It reaches clients two ways, both additive optional fields:

- `SessionSnapshot.background` / `background_revision`: `background` is `None` when there is nothing to show; the revision is present once the card has had any change.
- `AgentEvent.background` / `background_revision` on the event that changed the aggregate, on every later event of a card whose aggregate has changed at least once (so a turn end that leaves the count where it was, such as the `Stop` after a same-agent `/clear` with a command still running, still carries it), and on every `ShellBusy`/`ShellIdle` of a reporting pane. `Some` with both counts zero is an explicit clear; an absent field means the event carries no aggregate, not that the work ended.

`daemon::ingest_event` applies **before** it broadcasts, still under the one write-lock hold, so the broadcast copy can carry the aggregate the apply computed while `SubscribeEventsWithSnapshot` ordering stays as it was.

**Producer copies are stripped.** `admit_producer_event` drops `background` and `background_revision` from every raw hook/producer frame, `ingest_event` clears them again before the apply, and `apply_event` clears them on the daemon's own path. A count a producer sends therefore never reaches a card through the hook path.

**Clients copy, never reconstruct.** The TUI's `AppState` and the desktop's `AgentView` run the same fold in client mode (no ownership oracle, so no `BackgroundTrack`). `fold_background_copy` keeps an event's aggregate when its revision is at least the one held (equal is idempotent) and otherwise forward-stamps the held one; `seed_hydrated_session` re-seeds from a snapshot unless the card already holds a newer revision. That merge (`merge_snapshot_background`) is decided by revision alone, never by the activity watermark the snapshot's other fields are weighed by, on a minted card and on a card the upsert keeps alike, because the aggregate can change with no producer activity at all. Re-seeding the same spawn's placeholder (`insert_placeholder_session` replacing a card under `pane-<pane_id>` that names the same agent) carries the held aggregate and revision onto the fresh card before the snapshot is merged; a card of another agent under that key starts from nothing. That is what closes the desktop's `AgentView::install` double-apply race: an event drained after a reply that already reflects a later revision cannot resurrect finished work. The client half of the reporting gate is the same signal: a `ShellBusy`/`ShellIdle` that carries an aggregate comes from a daemon that tracks turn boundaries and does not promote status; one without it comes from an older daemon and promotes as before.

## The monitor's emit rule

The shell-activity monitor (`src/daemon.rs`) keys its readings by spawn identity — pane, registry agent id, shell pid — revalidates under the state lock that the sampled spawn is still the pane's current one before it applies or broadcasts, and emits with the sampled spawn's agent id, never with the id of whatever card holds the pane now.

- **A reporting pane emits only when something it publishes changes**: the sampled session set (and with it the command count or ages), a busy edge, and once when its turn ends while busy. That last emit is the `ShellBusy` an older event-folding client has always received at that moment.
- **The PRD #386 M6b level re-emit (`status_regressed`) stays for non-reporting panes only.** Its predicate — busy and the card is `Idle` — is exactly the steady state of a reporting pane after `Stop`, so applying it there would emit every 500 ms for as long as the command runs.
- **A spawn that leaves the candidate set** (closed, respawned, exited) has its reading dropped.
- **Retirement is a lifecycle check, not a reading.** At the top of every poll, before a sample is started or awaited, the monitor checks each card whose record still counts commands or subagents against the registry (`AgentPtyRegistry::agent_is_live_on_pane`), and `AppState::retire_departed_background_spawns` empties the record of every spawn that is no longer live on its pane, without waiting for a `SessionEnd` it may never send. So a spawn that exits before its first valid sample, on a platform whose sampler always answers `None`, or while the sampler is failing or backing off for another pane, is still retired; a spawn that is still live is not touched, so an unknown sample keeps its commands.
- **A retirement that changes the published aggregate is broadcast**, under the same write lock, as the daemon's report (`AgentEvent::is_background_retirement`): a `ShellIdle` carrying `BACKGROUND_RETIRED_METADATA_KEY`, the departed agent's id, its card's session key and pane, the card's own last activity as its timestamp, and the explicit-zero aggregate with the advanced revision. The daemon journals the same aggregate on its card. A client applies the report through `apply_background_retirement`, ahead of all generation, adoption and status logic: it lands only on that agent's existing card on that pane, moves only the background copy (by revision), and is refused when no such card exists, so a successor's card in the same pane is out of its reach and a card already gone is not rebuilt. `ingest_event` strips the marker from every inbound frame, and the daemon refuses the report if one reaches its `apply_event`. An older client reads it as a plain `ShellIdle` for the departed card; an older client that has already dropped that card can mint one from it.

## Known limits

- **Retirement waits for the next poll.** A departed spawn's work is retired by the monitor's next lifecycle check, so an attached client can show it for up to one poll interval (500 ms) after the process exits, longer while the state lock is contended. An exited agent's record also drops out of `ListAgents`, so the desktop's agent list loses that agent, line and all, on its next reconcile.
- **A spawn the registry does not hold is retired as soon as it counts anything.** The lifecycle check asks the registry, so a card whose agent id the registry has no live record of on that pane has its counts emptied at the next poll.
- **An old client on a new daemon** folds the daemon's `ShellBusy` into `Working` as it always has (it ignores the aggregate fields), so its card can read `Working` while its snapshots say `Idle`, and it shows no indicator. This is a display limitation of the old client, not a contract break: no field changed meaning and `PROTOCOL_VERSION` did not move.
- **A new client on an old daemon** receives no aggregate fields, so it promotes `ShellBusy` as before and shows no indicator.
- **Per-agent coverage** (CLAUDE.md rule 20): Claude Code, Codex and OpenCode report commands and subagents; Pi's extension and Devin's hooks carry no subagent lifecycle, so they report commands only.

## OpenCode subagents are child sessions

OpenCode runs a subagent as a child session: `session.created` names it with a `parentID`, and it then reports its own `session.status` (busy / retry / idle), `session.idle`, `session.error` and `session.deleted`, and its own tool calls, all under the child's id. Measured against `opencode 1.18.35` on 2026-10-11 with one `task` call on Haiku: the child's `session.created` (carrying `parentID`) arrived after the root's `task` tool call and before the child's first `busy`, the child then sent `busy` six times, its `bash` call's `tool.execute.before` carried the child's `sessionID`, and it ended with `session.status` idle followed by `session.idle`, before the root went idle. The deck's plugin (`plugin_template` in `src/opencode_manage.rs`) normalizes that into the paired lifecycle the tracker already understands, so the daemon needs no OpenCode-specific subagent logic:

- A child going busy or retry sends `subagent.start` with `subagent_id` set to the child's raw id; going idle, failing or being deleted sends `subagent.stop` for it. Both are filed under the session the child descends from (a grandchild's under the root), and the hook CLI (`build_opencode_event`) maps them to `SubagentStart` / `SubagentStop` with `SUBAGENT_ID_METADATA_KEY`.
- **Only a transition is sent.** The plugin keeps the set of children it reported active: a second busy sends nothing, an idle for a child that is not active sends nothing (a child goes idle through both `session.status` and `session.idle`, and a failed run sends `session.error` then idle), and a child that goes busy again after finishing starts again. Creation alone starts nothing and deletion only ends a child already active, because a child session outlives the call that ran it. At most 128 children are reported active at once, the tracker's own cap; a child past it sends neither its start nor its stop.
- **A child's other reports stay off the card's status (#1354).** Before this, the plugin filed a child's session events, tool calls and prompt under the root through its directory alias, since a child shares the root's directory: the child's `session.created` reached the daemon as the root's `SessionStart`, which repaints a card Idle, its going idle as the root's turn end, its tool calls as main-thread `ToolStart`s and the prompt the subagent was given as the user's prompt. Now its `session.created`/`updated` and other session events are not sent, its user message is not reported, and its tool calls and permission events carry `subagent_id`, which the decoder keeps only on `subagent.*`, `tool.execute.*` and `permission.*`.
- **A child's permission prompt is its subagent's.** `permission.asked` from a known child is filed under the root with `subagent_id`, so it decodes to a subagent-attributed `PermissionRequest` and joins `SubagentWait` the way a Claude Code or Codex subagent's prompt does; the child's `SubagentStop` then ends a wait it alone raised (`status/subagent/006` semantics). Its `permission.replied` decodes to a `Thinking` that carries both `subagent_id` and `permission_state = replied` (`AgentEvent::is_subagent_permission_reply`). The reducer gives that event its own arm ahead of the ordinary `Thinking` one: it takes the subagent off the wait through `release_subagent_wait`, the helper the `SubagentStop` arm uses, and changes nothing else. So it resumes the card as `SubagentWait` says (Idle after an ended turn, Thinking during one), leaves a main-thread wait and the active tool alone, and, being subagent-attributed, does not clear `turn_ended`. Attribution alone would not have been enough, because the ordinary `Thinking` arm sets the main thread's status. An older daemon reads the same event as a plain `Thinking`, which is what it received before this change.
- **Ancestry must be known when the child reports.** It comes from `session.created` / `session.updated`, or from the background client lookup the reply path already makes. A session whose ancestry is not yet known is treated as the root's, as before; that is the case when the plugin loads after a child was created. A user message the plugin recorded before its session was known to be a child keeps the id of the session that sent it. Learning that the session is a child drops the message, and so does finding either that id or the text part's `sessionID` to be a child's when the text arrives, so the child's prompt is not reported as the user's whichever order the events come in.
- **Routing survives the ancestry cache.** `sessionParents` keeps the 256 most recently noted sessions, so a long-running child can lose its entry while other children are created. Where a child's reports go is therefore kept apart from it: `activeSubagents` maps each child reported active to the root it descends from and the session id and directory its `subagent.start` was sent with, until it stops, and `childRoutes` maps the 256 children seen most recently to their root. `isChildSession` consults both when `sessionParents` has no entry, and `rootKeyOf` falls back to them where the ancestry walk breaks, which also files a grandchild under the root when its parent's ancestry entry has gone but the parent's route has not. A stop is sent under the same session id as its start.
- **Disposal ends active children.** On `server.instance.disposed` (and the plugin's own exit flush) a `subagent.stop` is sent for every child still in `activeSubagents`, before the root's `session.deleted`, so the daemon's count does not depend on how the root's close is handled.
- **Bounds on what the plugin holds.** A session or message id the plugin keeps in its child-session, alias, pending-prompt and reply records is at most 256 UTF-8 bytes (`MAX_ID_BYTES`, the tracker's own bound). A longer child id is recognised by `sessionKey`, a fixed-size key built from its length and a digest of all of it, never by a cut-down copy, so two long ids sharing a prefix stay apart. Such a child is never reported active, so it sends no `subagent.start` or `subagent.stop` and is not counted; its tool calls and permission events still carry `subagent_id`, set to `oversized-subagent-id`, so none of them reads as the main thread's. Its prompt therefore cannot be ended by its stop, only by its answer or by the main thread moving. A pending user message or reply record with an oversized message or session id is not kept, so that prompt or reply is not reported. By count, `sessionAliases` keeps its 256 newest aliases (a forgotten one is worked out again from `directorySessions` when its session next reports) and `messageRoles` its 64 newest pending user messages (an older one's prompt is then not reported). `knownSessions` and `directorySessions` are not bounded by count or bytes. Both hold one entry per directory that root sessions report from, not one per session, and forgetting an entry would change what the daemon sees: the root's next report would be announced as a new `session.created`, or a new session in that directory would become its first root.
