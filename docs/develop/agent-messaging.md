# Agent messaging

Maintainer reference for the per-agent inbox and wake integrations. User behavior and setup belong in [Orchestration](../orchestration.md#delivery-in-the-tui-and-desktop-app). The core is `src/inbox.rs`; `src/inbox_hub.rs` owns connections, rendering and notifications; `src/inbox_cli.rs`, `src/inbox_prompt.rs` and `src/doorbell.rs` connect it to agents. Both clients consume the daemon's inbox summaries and broadcasts.

## Inbox model

The daemon owns an in-memory inbox. Restarting it loses inbox contents. Messages have ids of the form `m-<eight-character-deck-id>-<16-hex-random-bits>`, generated with OS randomness; an id is also the dedup key. A persistent deck id distinguishes decks, while the random suffix separates messages across restarts. The id lives at `<state_dir>/deck-id`; a first start publishes it under a lock on `.deck-id.lock` with a hard link, which never replaces an id another start published. A state directory on a filesystem that can neither lock nor hard-link fails the daemon's first start with an error saying so, rather than letting two daemons publish different ids. Direct addresses are `inbox.<deck>.<encoded-pane>`; the recipient binding also names the current agent generation. An exited generation's bound messages become undeliverable rather than moving to its replacement. Unbound messages can wait for a pane's next agent. A bound message goes in only while its agent still holds its pane, asked under the inbox lock right before insertion (PR #1735 fifth review, N4): `post_to_live`, attach `post-message` and the inbox's own notices check it there (`InboxHub::post_direct_where`, and `set_live_agent_check` for the hub's notices), as `post_delegate` and publish/offer already did. The exit sweep runs after the registry marks the agent exited, so a post that passes the check is swept, and one that fails it is refused with `recipient_gone`, removing any body it saved and giving back any reserved room.

| State | Meaning and next transition |
|---|---|
| `queued` | Eligible for one consumer to fetch. |
| `fetched` | Held by that consumer, awaiting acknowledgement. Ack settles it; nack, stream loss or ack-wait makes it available again. |
| `acknowledged` | Receipt recorded. This is not task completion. |
| `claimed` | An offer has a time-limited owner. Completion settles it; release, expiry or owner exit returns it to the pool. |
| `undeliverable` | Delivery limit reached, recipient exited, inbox closed or message superseded. The reason determines whether a card notice is owed. |

One budgeted hand-over carries at most 16 blocks (`inbox_prompt::MAX_IDS`), the most ids Claude's prompt hook reads from one prompt, so no block is in context unacknowledged (PR #1735 fifth review, N1). The default ack-wait is 60 seconds and `max_deliver` is 5. Retry preserves the id; consumers should act on an id once. Dedup remembers up to 4096 ids for ten minutes. The pending limits are 256 per recipient and 4096 daemon-wide, with a 1 MiB body limit; a bound refuses explicitly rather than evicting pending work. Terminal history retains at most 64 messages per pane, 1024 daemon-wide and 16 MiB of bodies, evicting the oldest terminal messages first. Terminal bodies expire after one hour while summaries remain within the count bounds; closing a pane drops its terminal history. Pending work is not trimmed to make history space. Stored subjects are one line of at most 200 characters.

Publish fans out copies with one id, with state per recipient. Subscription resolution excludes the sender and stays inside the sender's orchestration instance or dispatch tree. Offers go to one eligible subscriber at a time; acknowledging an offer claims it. The default claim is 30 minutes, with a 60-second minimum and 24-hour maximum. Release, expiry and owner exit exclude the former holder from subsequent assignment. Publish and offer share a per-agent budget of 60 per minute; deck-generated messages are exempt.

### Delegated-task retirement

A newer delegation or a pane restart retires the worker's earlier unacknowledged tasks as superseded, and superseded tasks are not reported. The newer task's room is reserved, and its long body saved, before anything else: `dispatch_one_owned` calls `InboxHub::reserve_delegate` ahead of the supersede and of a `clear = true` restart, so a task the inbox refuses, or whose body cannot be saved, supersedes nothing and restarts nothing (PR #1735 fifth review, N8 and B-01). The older tasks it retires count as room it replaces, so an inbox those tasks fill is no refusal. Answers the deck reserved room for are not held to the recipient's bound, so an inbox they pushed past it can still refuse the task, and does so before anything is retired (reviewer B-04). The task itself is checked against the recipient's bound only when it reserves, not again when it goes in (PR #1735 sixth review): ordinary messages posted to the worker while the task is being prepared (its body saved, a `clear = true` worker restarted) are admitted against the bound as it then stands, and the task goes in after them, so the worker's inbox can then hold more than `max_per_recipient`. Ordinary posts to it are refused with `inbox_full` until enough of its messages settle (`a_reserved_task_goes_in_over_an_inbox_filled_while_it_was_prepared`). Reserved answers add to the excess the same way, so it has no fixed size. When the task is not posted after all (its worker is no longer live, a `clear = true` restart fails, or the inbox refuses it while it is prepared or at the post), the notice telling the orchestrator so goes into the task's reservation instead (`post_orchestrator_notice_in`, PR #1735 sixth review RB2-01), so a deck that filled meanwhile cannot refuse it too. That room was granted counting the older tasks the new one would have retired, and those stay live because nothing was posted, so the notice can leave the deck one message over `max_messages` for that dispatch, and ordinary posts are refused with `deck_full` until room returns. Each such dispatch, and each reserved answer, can add one more, so the deck-wide excess has no fixed size either. A worker's `work-done` names no task, so the deck infers which one it answers. If the worker acknowledged a task since its previous `work-done`, the completion answers that task, and only tasks that have reached the worker since (fetched at least once, not acknowledged) are retired with it. A newer task it never fetched stays queued and watched, so the orchestrator is still told if it does not reach the worker. Otherwise the worker answered a task it took another way, such as its task file, and every unacknowledged task to its pane is retired. So one late `work-done` for an acknowledged task leaves a newer task the worker never fetched queued.

Which branch a `work-done` takes is decided by the worker's own sequence of acknowledgements and completions, so that protection depends on the worker acknowledging each task it takes and reporting each completion once. Two sequences defeat it (audit A2-3):

- **A repeated `work-done` cancels a newer task the worker never fetched.** The worker acknowledges task A and reports it done; that completion consumes the acknowledgement, and a newer task B stays queued. A second `work-done` then finds no acknowledgement since the previous one, takes the second branch, and retires B as superseded, unreported.
- **An acknowledged task that is never completed keeps a later file-taken task queued.** The worker acknowledges A without completing it, takes B from its task file without acknowledging it, and reports B done. The completion is read as answering A, retires only fetched tasks, and leaves B queued and watched, so the orchestrator may be told B did not reach the worker, and B may be handed to the worker again.

Both stay within the reporting worker's pane: the acknowledgement it consumes and the tasks a completion retires are that pane's. **Not done:** task-bound completion evidence — a `work-done` naming the task id it answers — would close both; until it exists this is an accepted limit.

### Publish and offer integration

`src/inbox_pubsub.rs` resolves live pane membership from the registry and the daemon's orchestration, role, working-directory and dispatch-return maps. It reads each member directory's project configuration. `subscribe` on an orchestration or role supplies topics; role `take_offers` supplies job pools; `[dispatch] subscribe` subscribes the caller to its dispatch tree. Omitted keys inherit through `extends`; an explicit list, including an empty one, replaces the inherited list. Names match `[a-z0-9][a-z0-9-]{0,63}`, with at most 64 entries per list.

The CLI exposes `inbox publish <topic> --text|--file`, `inbox offer <pool> --text|--file [--claim-ttl <duration>]`, `inbox complete <id>` and `inbox release <id>`. A body uses exactly one input option; `--file -` reads stdin, bounded at 1 MiB. `--claim-ttl` accepts unit-bearing durations such as `30m`, `1h30m`, `90s` or `500ms`; the daemon applies its claim-duration bounds.

| Hook-socket verb | Request fields beyond pane, agent and token | Successful reply |
| --- | --- | --- |
| `inbox_publish` | `topic`, `body` | `InboxPostReply`: `id`, `delivered_to`, and `refused_full` when some recipients are full. |
| `inbox_offer` | `pool`, `body`, optional `claim_ttl_ms` | `InboxPostReply`: `id`, and `offered_to` when assigned; the latter is absent while pooled. |
| `inbox_complete` | `id` | `InboxClaimReply`: `outcome: "completed"`. |
| `inbox_release` | `id` | `InboxClaimReply`: `outcome: "released"`. |

Refusals carry `refused` (stable code) and `error` (explanation), without a success id or outcome. Publish/offer codes include `invalid_topic`, `invalid_pool`, `not_live`, `no_scope`, `scope_changed`, `not_orchestrator`, `body_not_saved`, `rate_limited`, `inbox_full`, `deck_full`, `body_too_large`, `duplicate`, `too_many_offers` and `claim_ttl_out_of_range`. Publish and offer re-read the scope up to three times while agents change; if the scope still changes during admission, they refuse with `scope_changed`. Claim operations also use `not_claimant`, `unknown` and `claim_expired`; a complete or release that reaches the inbox after its claim expired, but before the ticker returned the offer, returns the offer to its pool and answers `claim_expired`. Provenance refusal codes apply, including `unattested` for a missing token on a legacy-admitted pane and `malformed_token` for an empty token. The four verbs also bind the peer pid to the managed agent's process tree under the same platform policy as waiters, refusing a proven mismatch with `inbox_not_agent_process`, and require the attested agent to be live in the pane. The verbs that take or settle the agent's own mail — `inbox_fetch`, `ack`, the `get_seed` alias and arming an `inbox_wait` — need positive evidence instead (PR #1735 second review): on Linux, macOS and Windows they are refused unless the peer is shown to be the managed agent or its descendant, so a peer whose ancestry cannot be read, a peer the kernel does not identify and a pane with no agent process are refused as a proven mismatch is. A connection keeps reporting the process that made it, so a caller can make its own ancestry unreadable by handing a connection to another process and exiting; best effort would admit that. `inbox_fetch`, `ack` and `inbox_wait` refuse with `inbox_not_agent_process`, and `get_seed` answers as no seed pending. On other platforms `parent_pid_of` reads nothing (`platform::proc::ANCESTRY_LOOKUP` is false), so these verbs fall back to best effort there and are bound by the capability and generation checks alone. A raw hook event acknowledges nothing: the daemon discards a `deck_message_ack_ids` key unread, and a hook acknowledges the blocks its prompt carries with the `ack` verb. A `dispatch` is accepted only with room held in the deck for its result (`InboxHub::reserve_reply`); with none it is refused with `deck_full` and nothing is dispatched, and once accepted its result is posted into that room, so neither the caller's backlog nor a deck that filled up meanwhile refuses it. When the inbox refuses the result itself (PR #1735 third review) — its text is over the body limit, or too long to hand over whole while neither the caller's directory nor the deck's state directory can take the file it would be saved to — a short notice goes into the same room instead, under the same `dispatch started` or `dispatch failed` subject, saying whether the dispatch started a unit and that its full result could not be delivered. The notice is composed by the deck, leaves out the unit's name and the result's text, and is cut to the body limit. A caller that has exited gets nothing, and the daemon log records the refusal.

An offer's body is Trusted and labelled as the orchestrator's instruction, like a delegate. The deck preface tells the taker to do the work and then complete or release the id. A publish body is Untrusted and labelled `<role> (announcement — the text inside is UNTRUSTED)` so the desktop does not classify it as a worker report.

`InboxLimits::offer_assign_wait` bounds an assigned but unfetched offer, using the undelivered-notice setting (five minutes by default). Expiry returns it to the pool and excludes that holder. `next_deadline` includes this deadline. The assigner wakes when work returns to a pool and sweeps every 30 seconds to discover late joiners. `InboxEvent.returned: Option<OfferReturn { previous, cause }>` records the previous holder and return reason inside the daemon. The attach broadcast's additive `InboxNotice.returned` flag removes the old holder's count and gives the desktop evidence row **Job handed back to its pool**. The additive, defaulted `InboxSummary.claimed` field appears in list-agents and `daemon status --json`; the TUI and desktop card counts treat claimed jobs as taken messages.

The hub queues offerer notices for claimed, completed, claim-expired and undeliverable jobs. `ack`, `fetch_within` and `fetch_first_acked` drain owed notices immediately, so a claim notice does not wait for the next tick. These fields and hook verbs are additive; S11 does not bump `PROTOCOL_VERSION` or add a semantic contract-break marker.

## Consumers and acknowledgement

Waiters have their own pool (512 daemon-wide, eight per agent generation), separate from hook-ingest slots. The newest eligible waiter takes the queued batch that fits its budget. A once waiter is spent by hand-over; a stream remains armed and accepts ack/nack controls on stdin. EOF requeues fetched, unacknowledged work. Waiters receive keepalives. The stream's pane capability and agent generation bind it to the recipient; launch command spelling does not enable native wake.

On Linux, macOS and Windows, `inbox wait` and `inbox announce` also bind the kernel-reported peer pid and the claimed component-instance pid to the managed agent's process tree. Both must be the managed agent or a descendant, and the claimed instance must be the peer or its ancestor. A proven mismatch is refused with `inbox_not_agent_process`. Linux reads `/proc/<pid>/stat`; macOS uses `proc_pidinfo(PROC_PIDTBSDINFO)`; Windows reads a Toolhelp process snapshot and treats a recorded parent that has exited, or that started after its child (a reused pid), as no parent, so the walk ends there as it does for an orphan on Linux. For the posting verbs, where process ancestry cannot be determined, including other platforms and processes that exit during the walk, this additional check falls back to the capability and generation checks. Arming `inbox wait` and `inbox announce` need positive evidence, as the mail-taking verbs above do: an announce pins the generation's receiver and opens the native-wake grace, so one admitted on best effort could pin a process that has exited and lock the real integration out with `another_component_armed` (PR #1735 third review). Every announcer holds its connection open until the daemon answers — the Claude and Codex `SessionStart` hooks, and `dot-agent-deck inbox announce` as the OpenCode server plugin and the Pi extension run it — so it is alive, and readable, while it is checked. On Windows the receiver's shell resolution and the same-kind nesting check still have no executable lookup, so those two steps are skipped there. The kernel-reported peer is bound to its process, not to its pid (PR #1735 third review): when the daemon accepts a hook connection it records the peer's start time — Linux `/proc/<pid>/stat` field 22, macOS `proc_pidinfo(PROC_PIDTBSDINFO)`'s `pbi_start_tvsec`/`pbi_start_tvusec`, Windows `GetProcessTimes`' creation time — and reads it again after each ancestry walk. A different start time means the pid now names another process, so a connection whose creator exited cannot borrow the ancestry of a later process that reuses the creator's pid; every bound verb refuses it with `inbox_not_agent_process`, and a start time that cannot be read refuses the verbs that need positive evidence. Linux counts start times in clock ticks (`CLK_TCK`, usually 100 a second), so a pid reused by a process started within the same tick as the creator would pass; macOS counts microseconds and Windows 100-nanosecond units. This binds the connecting process; the component-instance pid a request names is still checked by ancestry alone, as an ancestor of that bound peer. A stream from the same component instance supersedes its predecessor; a legacy stream's unacknowledged work is requeued, while a receipt stream's predecessor is asked to resume instead ([Receipts and possession](#receipts-and-possession-opencode)); a different live instance is refused. A generation's native receiver is pinned to the first instance that arms or announces, resolving through hook shells to the agent rather than pinning a transient hook shell. A different instance cannot replace it after a stream closes, and announce can be refused with `another_component_armed`. An unnamed instance does not create a pin and cannot replace an existing one.

The inbox verbs bind authority to the agent's process tree: a process the agent runs, such as a command in its tool shell or a nested agent of another kind naming the outer agent's process as its component instance, acts with the outer agent's authority and can act as its receiver. The pin keeps a second non-shell instance out once one has armed or announced; it does not distinguish the agent from processes it runs that use its instance identity. For Claude Code below the 2.1.296 waiter gate, the deck's generated settings omit the waiter and its SessionStart hook does not announce native wake, so the first arriving receiver instance pins the generation.

OpenCode targets the session on screen, creates and navigates to one from the home route, and returns a child view to its root. It supplies model and agent from the target's last user message, then process history, then argv; a UI-only model selection before any prompt is not exposed to this path. The server plugin intercepts a doorbell in `chat.message` only in the full TUI's worker thread or `--mini`, fetches with `--adapter-integration 2 --rx <its receiver>`, so the fetched attempts are bound to its own receipt stream (caps on that stream, bodies to the fetch), and replaces the text in place; an assistant turn commits pending deck attempts in the same session through its parent; human messages and prompts in another session commit nothing. Main-thread `run`, `serve` and `acp` do not intercept it. Reassigning `output.parts` or transforming historical messages is not equivalent. `attach`, `acp`, `web`, `pr` and `github` remain unmeasured; the user docs claim doorbell fallback there.

The mini repaint nudge shrinks the PTY by one column, waits 300 ms by default, then restores it. It bypasses recorded geometry and scrollback changes. A concurrent real resize wins. Only `opencode_mini` streams request this nudge.

Pi kills its watcher on `session_shutdown` and starts a new one on session start, including `/new`, fork, switch and reload. Late callbacks are guarded by extension generation and caught so a stale context cannot kill Pi. Stream exit 3 means outside a deck or missing capability: Pi stops retrying rather than looping forever. Other watcher failures use bounded backoff. Its doorbell `input` handler fetches without acknowledgement, marks the original line handled and submits the framed content; receipt still waits for the committed user message.

Pi tags each native hand-over attempt and removes the tag in its `input` handler, consuming superseded attempts and messages already committed. An idle recheck retries an attempt the handler has not seen; after `input`, a retry needs the refusal witness described in [Pi extension](pi-extension.md#native-inbox-delivery). Without that witness the message waits for inbox ack-wait redelivery, which replaces the attempt when Pi has nothing queued. Unanswerable status queries do not trigger a retry. This guard cannot recall an attempt already past `input`; receipt and retry retain the inbox's at-least-once semantics.

### Long turns: hold and the late ack

This section is the legacy policy, which Pi's extension and the hooks still use. OpenCode's plugins are on the receipt policy ([Receipts and possession](#receipts-and-possession-opencode)) and send none of `hold`, `nack` or a CLI acknowledgement; the daemon applies `hold`, `nack`, the ack-wait and `max_deliver` only to a `Legacy`-owned assignment.

A stream component may answer a redelivery with `{"hold":[id]}` when it still holds that message, queued in the agent behind the turn in progress, and did not hand it over again. For a direct message, the deck refunds that redelivery's hand-over, and the count never drops below one. The refund applies while the message is fetched by that stream and was first fetched less than one hour ago (`DEFAULT_HOLD_BOUND` in `src/inbox.rs`). Past that bound, `max_deliver` applies as it does to every consumer. A refunded hold also moves a delegated task's undelivered-notice deadline a full `DOT_AGENT_DECK_INBOX_UNDELIVERED_NOTICE_AFTER_MS` past the hold. A daemon that predates `hold` reads the line as an empty ack.

An offer fetched by a stream stays assigned to its holder when its ack-wait runs out, provided it remains within the hold bound and the previous hand-over was not left unanswered. It is handed to the same holder's stream again, and while the stream answers each such hand-over with `{"hold":[id]}`, the offer stays with that holder. Holding an offer refunds nothing: its delivery count measures assignments, and another hand-over to the same holder is not counted. The hold is bounded by the offer's claim TTL and `DEFAULT_HOLD_BOUND`, whichever is shorter, measured from the first fetch by the current holder.

The offer returns to its pool, excluding the holder, when the bound passes, a hand-over again goes unanswered for one ack-wait, or the stream does not fetch that hand-over within `DOT_AGENT_DECK_INBOX_UNDELIVERED_NOTICE_AFTER_MS`. An offer fetched by a consumer other than a stream returns at the first ack-wait. A nack or dropped stream also returns it to its pool. The hold bound resets for a new assignment. Pi answers `hold` for a held offer id as for a direct message, and its ack claims it.

Pi answers `hold` for a redelivered id that it is holding behind an admission, or that a hand-over still carries and that may still commit. A redelivery that replaces a hand-over lost after `input` is not a hold: the replaced hand-over did not reach the agent.

**Confirming acknowledgements (PR #1735 third review).** An agent-side component does not take its acknowledgement as recorded until the deck says so, because the deck may never hand the message over again (it allows `max_deliver` hand-overs, possibly one), and one it does hand over again would otherwise run twice.

- Pi keeps each id it acknowledges — over the watcher's stdin, which answers nothing, or with the CLI — until `dot-agent-deck ack --json <id>` reports `{"acknowledged":true}`. The first ask comes a second after a stdin acknowledgement, or at once when the CLI carries it; later asks back off doubling to 30 seconds, eight asks at most. Each id keeps its own schedule, on its own timer, and the asks go out one at a time: a new acknowledgement never moves another id's next ask (PR #1735 third review), so a steady stream of new commits cannot keep postponing an older confirmation. A refusal by id (`undeliverable`, `wrong_agent`, `unknown`, reported `"final":true`) ends it at once. That and running out of asks are shown as a warning naming the message in Pi's `ui.notify`.
- Pi also remembers the ids its agent answered, at most 256: the deck hands one of those over again only because it never recorded the acknowledgement, so it is acknowledged again, not prompted again. It keeps both sets process-wide across session replacements.
- The Claude Code and Codex hooks (`UserPromptSubmit`, Codex `Stop`) are one process per event, with no state between them. Each sends its `ack`s one connection per id and reads the deck's answer (`hook::ack_confirmation`); an unanswered one is asked again, three asks at most, 100 ms apart and doubling, all within the 5-second budget the single connection had. A refusal by id or running out of asks is written to the hook's stderr; whether the agent shows a hook's stderr in its main view is not measured. One never recorded is handed over again after the ack-wait, as before.

An ack from the bound agent for a direct message that became undeliverable after `max_deliver` hand-overs is recorded: the message becomes acknowledged and the ack answers `acknowledged`. A message undeliverable for any other reason still answers `undeliverable`. The daemon remembers up to 256 such messages for one hour (`LATE_ACK_MAX_RECORDS` and `LATE_ACK_MEMORY` in `src/inbox_hub.rs`).

A notice the hub owes (claimed, completed, undeliverable, late-delivery correction) that a full inbox or deck refuses stays owed and is tried again on the next acknowledgement or fetch, or after a second at the latest, until it is posted or its recipient is gone. A worker's `work-done` and a dispatched unit's completion hold room for their report before anything is taken on (`InboxHub::reserve_reply`), and the report goes into that room, or a short deck notice in its place when the inbox refuses the report itself; with no room the `work-done` is refused with `deck_full` and nothing it would consume is touched (PR #1735 fifth review, N3).

When a delegated task's orchestrator was told the task "has not reached the worker" and the worker then acknowledges it, that orchestrator generation gets one correction with the subject `task delivered after all`. This notice does not touch the card, so there is nothing to clear. A task that ran out of hand-overs before its late ack is corrected once through the late-ack record instead; its delegate watch has already been removed. The worker then counts as having received a task for work-done retirement.

For a task reported undeliverable after `max_deliver`, the recipient's card is lifted from its not-delivered Error to Thinking by a daemon-authored event carrying the `delivery_notice_cleared` metadata key. This happens once no other message the card was told about is still owed a correction, and only while the daemon's copy of the card still shows the deck's notice. Both the TUI and the desktop app consume this event.

Claude Code's once waiter has no channel to answer `hold`, so a direct message waiting behind a long Claude turn can still be redelivered and reported not delivered before it arrives. The orchestrator is then told it arrived. An offered job returns to its pool at the first ack-wait, so a Claude worker in a long turn can lose it to another worker; the former holder's late ack answers `wrong_agent`.

## Receipts and possession (OpenCode)

PRD #1666 §13 step 4 switched OpenCode, both contexts together, from the ack-wait to the receipt policy of design v3.2. The pure model is `src/inbox_attempts.rs`, the spool `src/inbox_receipt.rs`, the hub's engine `src/inbox_engine.rs` (a child of `src/inbox_hub.rs`), the watcher `src/inbox_watcher.rs`, and the plugins' generated JavaScript in `src/opencode_manage.rs`.

**One policy per assignment.** Each inbox copy carries an owner (`crate::inbox::AssignmentOwner`), fixed at its first issuance by the receiver that took it: `Legacy` when an `inbox fetch`, a hook or Pi took it, `Receipt` when an OpenCode receipt stream did. A direct message has one assignment for life; an offer one per holder, so the owner is cleared when it returns to its pool. The legacy ack-wait, requeue, `nack` and `hold` touch only `Legacy`-owned copies, and a receipt receiver never takes a `Legacy`-owned one, so the two policies never run for one assignment even while an unconverted consumer shares the pane. Pi and the hooks stay legacy until their slices.

**The stream.** `inbox wait --agent opencode|opencode-mini --stream --adapter-integration 2 [--doorbell-only] [--resumed]` registers a receiver in its slot (`opencode_tui` or `opencode_server`); the two contexts never fence each other. The first line is `{"registered":{"rx","slot","keepalive_ms"},"resume":[…]}`. Hand-outs are `messages` whose entries add `a`, `e`, `d`, `repeat` and, for the watcher only, `caps`; the watcher strips the caps before the plugin sees the line. Other daemon lines: `grant` (answer to `may`), `revoke`, `rebound` (a resumed attempt's new delivery number and, for the watcher only, its caps, so a replacement watcher can still publish its receipts), `issued` (caps of attempts a doorbell fetch bound to this receiver), `keepalive`. The plugin writes `possess {seq, seen, held}` (a snapshot on every change and in answer to each keepalive), `may` (the final hand-over check), `handed`, `committed`, `not_handed`, `revoked_ack`, `already_handed`, `resume_answers` and, for mini, `repaint`.

**Receipts before the daemon is told.** For `handed` and `committed` the watcher publishes `<msg>.<A>.<e>.<stage>` into `$DOT_AGENT_DECK_INBOX_SPOOL/<pane>/<agent>/rec` with that stage's cap, then forwards the control; a publish still in flight is added to every snapshot it forwards meanwhile, counted per attempt, so overlapping `handed` and `committed` publishes keep it held until the last finishes (inbox/opencode/043). A stage report for an attempt whose cap the watcher lacks publishes nothing and is reported `degraded`, never as a receipt. The daemon keeps the caps of issued attempts (beside the hashes that admit records) only to hand them to a replacement watcher in `rebound` (inbox/opencode/042). The hub's clock reads the spool off the executor while any attempt could still have an unseen commit: a bounded scan whose every admitted commit is applied, whichever issued attempt it is for (fenced, lapsed, an earlier assignment's, a late-correction verifier's), then an exact lookup of each lapse candidate's commit record. A found commit settles it; only a completed, error-free cycle and a lookup that finds nothing clears it. An automatic repeat needs every possibly handed attempt of the assignment cleared, revalidated under the lock against possession regained while the IO ran, so no snapshot, TTL expiry, resume answer or control can repeat anything before the clock has looked (inbox/boundary/019, inbox/boundary/020, inbox/attempts/005). A message that cannot go on for two `POSSESS_TTL`s — no check can tell, or no receiver takes its scheduled repeat — is `Uncertain` and waits for the user. A generation with no spool to read (none started, or its reader could not be built) follows the degraded policy: its candidates count as checked, and its card says receipts are degraded. The deck's own read errors degrade the generation too (inbox/boundary/023). That is fail-closed by design, and it has a cost: a file at an attempt's exact record name that is a well-formed record carrying the wrong cap is neither admitted nor removed by a scan, so that attempt is Unknown, never absent, for as long as the file stays, and it never lapses into its marked repeat. A same-user process can obstruct a lapse this way without holding any genuine cap, and this alone sets no `receipts_degraded` (a U2 obstruction, accepted). A spool that cannot be opened or written sets `receipts_degraded`, sticky for the generation, shown on both clients' cards. So does a daemon whose spool could not start at all (`Spool::start` failing, four lost pending-lock races among the ways): every receipt generation's card names that failure (`InboxHub::set_spool_error`, inbox/boundary/016), and delivery goes on without receipt protection rather than claiming it. The daemon reaps spool instances earlier runs left a step at a time: `Spool::start` takes the first step and a thread takes another every minute (`REAP_INTERVAL`); each step lists at most 8192 root names on from where the previous one stopped, so a dead instance listed after any number of names that stay is reached within one pass (inbox/receipt/018). On Windows the spool's directories are held open without delete sharing, so they cannot be renamed or deleted, and every spool operation, which Windows makes by path, rechecks through those held handles before and after that no directory of the chain has become a reparse point in place (`FSCTL_SET_REPARSE_POINT` on an empty directory needs neither a rename nor delete sharing); one that has fails the operation, which degrades the generation (inbox/receipt/017). A reparse point made and removed again inside a single operation is not seen. When the attempt model returns an attempt's evidence reservation, its records, caps and revoke marker are removed; at exit the generation's spool directory goes.

**Possession and the final check.** The plugin holds an attempt from hand-out until it commits or is positively not handed. A callback asks `may`, and once granted, re-checks synchronously — the context still active, the grant's epoch the receiver's current one, the attempt neither revoked nor dropped — with no await before `promptAsync`. Every watcher start bumps the epoch, so an approval outlived by a rebinding or a disposal never reaches OpenCode; the callback asks again under the new incarnation, or reports `not_handed`. A refused `may` is only a refusal: the daemon changes no stage for it, because an earlier approval of the same attempt may still be live in the context. `not_handed` is the plugin's own report, sent after it has revoked the attempt locally, so no outstanding approval of it can reach OpenCode afterwards, and never while another callback of the attempt is inside its `promptAsync`, which reports for itself (inbox/attempts/018, inbox/opencode/037). Until that report, or a resume answer, a fence or exit, a cancelled message stays held and keeps its evidence. A doorbell substitution is synchronous inside `chat.message`: the fetch that issues its attempts under the hub's lock is its final check. An aborted turn (the session idle with an attempt handed and not started) or a reverted prompt (`message.removed`) drops the attempt from the snapshots: a lapse, not a release, so the deck may repeat it, marked. The receiver remembers every attempt whose native call began, so such an attempt is never reported `not_handed` afterwards and a revoke of it is answered `already_handed` (inbox/opencode/039). After the call began, only OpenCode answering it with a 4xx (its prompt route refuses before it accepts with 204) is a not-handed witness; a thrown error or any other failure is lost, for a marked repeat, and an offer stays bound (inbox/opencode/038, inbox/opencode/044). The callback's last synchronous check also re-reads the caller's own guards after the awaited grant — the TUI's target session and dialog, `--mini`'s root session — and drops the callback, `not_handed`, when they no longer hold (inbox/opencode/040).

**Reconnects.** A stream that ends decides nothing at once: no requeue, and the incarnation stays its slot's. With no snapshot for `POSSESS_TTL` (three keepalives) its attempts lapse. The next registration of the slot retires it and is sent its open attempts to resume: the same context (a respawned watcher, `--resumed`) answers `retained` for what it still holds and the attempt is rebound, with its caps, and no repeat; a reloaded context answers `unknown`, which fences the attempt and, once the clock's spool check finds no commit, gives one marked repeat on the same generation. With no registration within three `POSSESS_TTL`s of the close, the model retires the incarnation itself and fences what it held, so a Cancel can end those attempts, an offer stays bound, and a message nobody takes is `Uncertain` after the wait bound (inbox/boundary/021); the doorbell's tick counts such a scheduled repeat as waiting mail. A watcher whose plugin sends no snapshot for three keepalives (a stalled or dead event loop) closes its stream. A plugin that closes its watcher's input (dispose) starts none again.

**The adapter floor.** A generated plugin declares `ADAPTER_INTEGRATION` (2) on its stream and its doorbell fetch; an OpenCode stream or doorbell fetch declaring less or nothing is refused `adapter_too_old`, registers nothing, leaves the mail queued and silences the doorbell. When an OpenCode agent spawns (its agent type is OpenCode, or its command's first word is `opencode`, bare or path-qualified: inbox/boundary/018), the daemon regenerates the plugin from its own binary before the child starts, so the agent never loads a copy the refresh had not reached yet (inbox/boundary/025). A plugin pinning another live install keeps that pin (PRD #1487) and is rewritten only when its template declares an integration below the floor, so two installs that both meet it never rewrite each other's; a refresh that cannot write a file sets `refresh_failed` on the card until a registration proves the integration current. It also starts the readiness deadline (`ARM_DEADLINE`, 120 s; past it with no registration the card says `not_armed`, cleared by a later registration, which then gets the queued mail), and runs the capability probe off the executor: `<pinned> inbox wait --adapter-integration 2 --help` with a literal argv and a 5 s deadline, reading 64 KiB of each output stream and draining the rest; a CLI still running at the deadline is killed and reaped, and output another process still holds open then proves nothing. The pinned binary is the pane's absolute `DOT_AGENT_DECK_BIN`, else the plugin's pin. Only clap's refusal, `error: unexpected argument '--adapter-integration' found` as the whole first line of stderr on exit 2 (a trailing carriage return and ANSI styling ignored, on every platform), sets `cli_too_old` (mail queued, doorbell silent); only a help line listing `--adapter-integration` on exit 0 is support; a timeout, an old help that exits 0 without the flag, or any other answer, a diagnostic in other words or another language included, sets nothing. A registration outranks the probe: a `cli_too_old` that arrives after one changes nothing, and a later registration clears one (inbox/boundary/017).

**What both clients show.** `InboxSummary` carries the card notices flattened beside the counts — `attention` items `{message_id, revision, kind, from_label, subject, task_id?}` with kind `uncertain`, `out_of_attempts` or `held_long`, `integration`, `receipts_degraded` and `evidence_paused` — and an `InboxNotice` with `attention_update` carries them whole whenever they change. The TUI keeps them per pane (`AppState::inbox_attention`) and opens its picker on `i`; the desktop refetches `ListAgents` on any inbox broadcast and lists the rows on the tile. Words are `src/inbox_display.rs`, mirrored by `desktop/src/lib/inboxWords.ts` and pinned by `tests/fixtures/inbox-display.json`.

**Retry and Cancel.** The attach verbs `inbox-retry` and `inbox-cancel` `{pane_id, agent_id, message_id, revision, request_id}` answer on `AttachResponse.inbox_action` with `applied`, `stale`, `not_applicable`, `already_settled`, `retry_limit` or `unknown`. Clients send them only to a daemon advertising `inbox-actions` (`DaemonClient::inbox_action`, rule 18's second rung). They apply the model's compare-and-transition under the hub's lock: a press at a revision the message has moved past is `stale`; of two presses of the same verb at the same revision, the first applies and the other is answered `stale`, while the same `request_id` sent again answers as before. For a delegated task, its orchestrator gets `task delivery uncertain` once, `task delivered after all` if it then commits, and `task cancelled` for a Cancel.

## Claude version gate and framing

`CLAUDE_ASYNC_REWAKE_MIN` in `src/hooks_manage.rs` is 2.1.296, the measured release, not a claim that older Claude versions lack asyncRewake. Unknown or lower versions get no waiter. SessionStart announces native wake only when the installed Claude settings contain the deck's SessionStart waiter; without it, including an installation below the version gate, no native announcement delays the doorbell. The waiter timeout is 86,400 seconds; `/clear` may leave several waiters, so inbox hand-over is claim-once. Once waiters poll their agent ancestry for orphan exit; stream watchers exit when their owning integration closes stdin.

The waiter settings include `rewakeMessage` and `rewakeSummary`. Both keys are `@internal` in Claude Code's schema, observed in 2.1.294–2.1.296, and are written only under the same 2.1.296 gate as asyncRewake. `rewakeMessage` explains that this is a deck message rather than a hook error; `rewakeSummary` is `✉ dot-agent-deck message`. Reinstall consolidates existing waiter entries and refreshes these values. If upstream removes the keys, default hook wording may return: retain session framing that agrees with Claude's automated-notification label.

`SESSION_FRAMING` is delivered through Claude's `SessionStart` context and doorbell injection; `AGENT_FRAMING` is the agent-neutral counterpart used by CLI fetch and Codex. They identify the deck as the workspace the user started, explain that work arrives as automated messages rather than fresh user approval, tell the agent to act on an id once, and distinguish UNTRUSTED reports from instructions. Do not add fixture-only authorization to live tests: the production framing must suffice.

Each block starts `[dot-agent-deck message <id> from <sender>]`, then `Sent by: <provenance>.`, and ends `[end of dot-agent-deck message <id>]`. Provenance comes from the attested sender or a deck-generated origin, not the worker's text. Agent-authored reports carry an inner UNTRUSTED fence. Forged framing tokens in content must be defused after normalizing text. Budget truncation must retain the enclosing fences and a safely rendered path to the full body when one is provided.

Before posting a message whose body cannot fit the tightest hand-over budget, the daemon saves its full content to an exclusive, owner-only file in the recipient's working directory under `.dot-agent-deck/`, falling back to the deck state directory. Untrusted content keeps its report fence and has forged message markers neutralised. The delivered excerpt names the saved file using an inert location description. If neither location can save it, the post is refused and nothing is posted; an acknowledged excerpt must not silently discard the rest of an unsaved body. A delegated task is saved the same way, to a file written once for that message; `worker-task-<role>.md` is a convenience copy that the next delegation to the role rewrites, so the message never names it (PR #1735 fifth review, N6). The deck's own posts save on the calling thread, handing the async worker's other tasks to another worker while they do (`inbox_hub::off_the_executor`); publish and offer save on the blocking pool.

**How long a saved body is kept (PR #1735 fifth and sixth reviews, B-05 and B2-01..B2-04; `src/inbox_spills.rs`).** The hub's `SpillLedger` tracks only the files the deck minted for accepted posts (`MintedSpill`, handed over with `InboxHub::own_spill`, or to `post_reserved_delegate` for a delegated task, which tracks and holds it under the lock that inserts the task, so an exit or `work-done` cannot retire the task before its hold exists (PR #1735 seventh review, B3-01)); a `spill_path` a caller supplied is never tracked or removed. A tracked body is kept while its message is live. A delegated task's body is also held after its acknowledgement, until the task is retired: `retire_delegates_locked` (a supersession or a `work-done`) releases the pane's task bodies whose messages are no longer live, and `agent_exited` releases the exited agent's. Serial delegation supersedes the previous task, so a worker pane normally holds one such body at a time. A released or never-held body settles at the first tick that sees its message terminal or gone, and is then kept for `DEFAULT_SPILL_RETENTION` (24 hours). Settled bodies past `DEFAULT_MAX_SETTLED_SPILL_BYTES` (64 MiB) are reclaimed oldest first, but only those settled at least `DEFAULT_SPILL_PROTECTED_GRACE` (1 hour) ago; when everything over the bound is within its grace the bound is exceeded rather than a body removed. Live and held bodies do not count against the bound. A removal that fails (other than the file already being gone, or the path no longer matching the deck's naming) goes back into the ledger and is tried again at the next tick, logged once. So does a path whose directory or file cannot be looked up, say for want of search permission: that is not taken for a mismatch, and a takeover keeps such an entry rather than filtering it out (PR #1735 seventh review, B3-02).

Each daemon run keeps an inventory under `<state_dir>/inbox-spills/`: a lock file `run-<unique>.lock`, created as `.pending-<unique>`, locked with `File::try_lock` and renamed into place, held for the whole run and never replaced; and a JSON inventory `run-<unique>.list` (`{"version":1,"spills":[{"path","bytes","settled_unix_ms"}]}`, where a path that is not UTF-8 is recorded as `path_raw` instead: the hex of its bytes on Unix, of its UTF-16 code units on Windows), replaced whole on every change of the ledger by writing `.pending-<unique>.list`, syncing it and renaming it over the old one. The hub writes it outside its own lock; a write that a newer one overtook is skipped. `settled_unix_ms` is the wall-clock settlement time, absent while the body is live or held. A starting daemon takes over every inventory whose lock file it can lock: an entry with a recorded settlement keeps its retention from then (removed at once if it ran out), and an entry without one gets a fresh retention from the takeover, which this run's inventory records so a later restart does not grant another. The taken-over lock file and inventory are removed (inventory first, lock last, under its lock) only once this run's inventory has been written with what they held (`TakenSources::release`); otherwise they stay for the next start. An inventory that is not a regular file (opened `O_NOFOLLOW | O_NONBLOCK` on Unix, so a FIFO cannot block the start), is larger than 16 MiB, does not parse or has another version is left in place, logged. A `.pending-` file is removed once a minute old and nobody is using it: a lock file still being created is checked by locking it, and an inventory still being written, `.pending-<unique>.list`, by its run's lock file, never by locking the inventory itself. On Windows a lock is mandatory, so a lock on a file another handle reads or writes fails that read or write; no path here locks a file that any handle reads or writes.

Removal is limited to a tracked path matching the deck's naming: a regular file named `inbox-message-<deck>-<unique>.md`, directly inside a `.dot-agent-deck` directory that is not a symlink, checked by path just before `remove_file`. That is a check of the path's shape at that moment, not of the object the deck created: a process that can rename entries in the project's context directory can still put another regular file at a tracked path and have it removed, or race the parent check. Pinning the minted file's identity and deleting relative to a validated directory handle is the U2 hardening listed for a follow-up issue.

The ledger is the one thing that deletes a saved body once its post was accepted and the body tracked; `MintedSpill`'s drop removes the body of a post that was refused, or whose body was never handed to the ledger. The coordination sweep that runs when an orchestrator context is published (`sweep_coordination_files`, `src/orchestrator_context.rs`) deletes `.md` files in `.dot-agent-deck` by age, and `is_sweepable_coordination_name` excludes every `inbox-message-*.md` name, any deck's, so it cannot delete the full body of a message that is still queued or a task that is still running (RB2-02). The other deletion paths over that directory remove only names they created or recognise as orchestrator contexts (`withdraw_published_context`, `remove_ended_orchestration_context`, `remove_created_file`, the mirror's temp file). Removing a whole worktree removes its `.dot-agent-deck` with it. The cost of one owner: a saved body whose inventory was lost, or whose deck's state directory is never started again, is not reclaimed by anything.

## Doorbell guards

The only automatic text typed into an agent's composer is the fixed doorbell: ` dot-agent-deck: message <id> waiting, run: dot-agent-deck inbox fetch`. It contains no task body. Eligibility requires queued work, no armed consumer, an elapsed native-arm grace, a hook-reported idle moment, and no unsent human draft. Unknown status, busy agents, permission prompts and unknown dialogs hold it. The guard applies to input from either client; no draft-deferral cap overrides it.

Codex additionally requires a recognised empty composer on screen, so an Enter interpreted as a newline does not cause the next ring to submit the user's draft. The one non-empty composer the doorbell writes to is one showing the exact line it last typed into that pane, message id included, left unsubmitted because Codex did not take that line's Enter. Two such states were seen live on Codex 0.160.0: the Enter was dropped, leaving Codex's cursor right after the line (`inbox/codex/013`), or, under CPU pressure, the Enter became a newline in the composer, leaving the cursor on the empty row directly below the line at the composer's indent (`inbox/codex/016`). In either, the next ring, or the cleanup once the message leaves `queued`, sends its bare CR alone, which submits the line, and types no second line on top. A ring that only flushed keeps the line recorded, so if Codex swallowed that CR as well, the next ring flushes again (`inbox/codex/017`). The record is dropped when the cleanup CR goes or a ring types a new line, and after that the line gets no byte (`inbox/codex/015`); a doorbell-shaped line naming another message gets none either (`inbox/codex/014`). That can be after the message the line names has left `queued`: while other work is queued, a ring due for it is sent in place of the owed cleanup, and if that ring only flushes, it keeps the record (`inbox/doorbell/018`). So while a frame matching the recorded line stays on screen and a message stays `queued`, each due ring the guards admit sends one lone CR, with no fixed total. That is deliberate: the flushed line runs `inbox fetch`, which serves whatever is queued, and dropping the record there would leave the remaining work behind a stranded line the deck sends no byte to. A flush that Codex also takes as a newline leaves the line above two blank composer rows with the cursor on the second, which the recogniser does not match, so the flushing stops there (`tests/codex_composer_guard.rs`); that holds for that rendered layout, not as a guarantee about how a renderer draws it. The match is on what the screen shows, not proof of where the text came from: a process that controls what the pane renders can draw the exact line and cursor, and a person can type the line, and either earns the flushing CR, again on each due ring for as long as the record and the queued work last, and each CR goes to whatever then owns the pane's input. The agent-identity, draft and admission checks still apply to it. Codex hides its `? for shortcuts` hint while the composer holds text, so that recogniser finds the composer from the bottom of the screen rather than from the hint. If Codex changes its UI and the recogniser stops matching, idle ringing waits; a user-started turn still enables the Stop hand-over. Native arm grace prevents startup ringing before a component has had time to connect. Doorbell retries have their own schedule and do not increment inbox hand-over attempts.

**Stalled wake (PR #1735 fifth review, R5).** The doorbell's tick also keeps a `StallClock` per agent generation. It runs while messages are queued, no native component is armed and the agent's status does not explain the wait (Thinking, Working, Compacting, WaitingForInput and Blocked do; Idle, Error and no status do not), and starts again when the oldest queued message changes. After `DOT_AGENT_DECK_INBOX_WAKE_STALL_AFTER_MS` (120 s by default) it calls `InboxHub::set_wake_stalled`, which records the oldest message, sets `InboxSummary.wake_stalled` and broadcasts an `InboxNotice` for that message with `wake_stalled: true` and `wake_update: true`. A notice with `wake_update` reports the stall and nothing else (PR #1735 fifth review, B-03 and B-04): the message it names did not change state, its `state` repeats the state that message is in, and a client must not count it as a message event. Every change of the stall is sent as one, its end included (`wake_stalled: false`), so a client seeds the stall from `InboxSummary.wake_stalled` when it hydrates and follows these notices from there. The TUI applies one by setting the card's stall alone, bypassing `PaneInbox::apply`; the desktop refetches the pane's inbox on any `BroadcastMsg::Inbox`, so it reads the stall from the summary without interpreting the flag. A client that predates `wake_update` treats such a notice as an ordinary state notice for that message; inside the unreleased protocol 11 break that is a refinement, not a separate compatibility break. Both clients then show `✉N waiting to wake: send it a prompt` (`inbox_display::WAKE_STALLED`, `WAKE_STALLED_HINT`, pinned with the desktop by `tests/fixtures/inbox-display.json`). It clears when that message leaves `queued`, when the agent starts working, or when the agent exits. It is a card line, not a status: an `Error` status would itself stop the doorbell, which rings only an idle agent. It covers every wake path, decided from what the inbox and agent report rather than why a ring was held, and does not loosen any doorbell guard.

Eligibility is revalidated under the PTY writer before each automatic write step. A per-pane admission epoch changes when the agent, doorbell-relevant status, writability or wrapper fork changes, invalidating a previously scheduled ring; an armed consumer also cancels a ring.
