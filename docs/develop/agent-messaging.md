# Agent messaging

Maintainer reference for the per-agent inbox and wake integrations. User behavior and setup belong in [Orchestration](../orchestration.md#delivery-in-the-tui-and-desktop-app). The core is `src/inbox.rs`; `src/inbox_hub.rs` owns connections, rendering and notifications; `src/inbox_cli.rs`, `src/inbox_prompt.rs` and `src/doorbell.rs` connect it to agents. Both clients consume the daemon's inbox summaries and broadcasts.

## Inbox model

The daemon owns an in-memory inbox. Restarting it loses inbox contents. Messages have ids of the form `m-<eight-character-deck-id>-<16-hex-random-bits>`, generated with OS randomness; an id is also the dedup key. A persistent deck id distinguishes decks, while the random suffix separates messages across restarts. The id lives at `<state_dir>/deck-id`; a first start publishes it under a lock on `.deck-id.lock` with a hard link, which never replaces an id another start published. A state directory on a filesystem that can neither lock nor hard-link fails the daemon's first start with an error saying so, rather than letting two daemons publish different ids. Direct addresses are `inbox.<deck>.<encoded-pane>`; the recipient binding also names the current agent generation. An exited generation's bound messages become undeliverable rather than moving to its replacement. Unbound messages can wait for a pane's next agent.

| State | Meaning and next transition |
|---|---|
| `queued` | Eligible for one consumer to fetch. |
| `fetched` | Held by that consumer, awaiting acknowledgement. Ack settles it; nack, stream loss or ack-wait makes it available again. |
| `acknowledged` | Receipt recorded. This is not task completion. |
| `claimed` | An offer has a time-limited owner. Completion settles it; release, expiry or owner exit returns it to the pool. |
| `undeliverable` | Delivery limit reached, recipient exited, inbox closed or message superseded. The reason determines whether a card notice is owed. |

The default ack-wait is 60 seconds and `max_deliver` is 5. Retry preserves the id; consumers should act on an id once. Dedup remembers up to 4096 ids for ten minutes. The pending limits are 256 per recipient and 4096 daemon-wide, with a 1 MiB body limit; a bound refuses explicitly rather than evicting pending work. Terminal history retains at most 64 messages per pane, 1024 daemon-wide and 16 MiB of bodies, evicting the oldest terminal messages first. Terminal bodies expire after one hour while summaries remain within the count bounds; closing a pane drops its terminal history. Pending work is not trimmed to make history space. Stored subjects are one line of at most 200 characters.

Publish fans out copies with one id, with state per recipient. Subscription resolution excludes the sender and stays inside the sender's orchestration instance or dispatch tree. Offers go to one eligible subscriber at a time; acknowledging an offer claims it. The default claim is 30 minutes, with a 60-second minimum and 24-hour maximum. Release, expiry and owner exit exclude the former holder from subsequent assignment. Publish and offer share a per-agent budget of 60 per minute; deck-generated messages are exempt.

### Delegated-task retirement

A newer delegation or a pane restart retires the worker's earlier unacknowledged tasks as superseded, and superseded tasks are not reported. A worker's `work-done` names no task, so the deck infers which one it answers. If the worker acknowledged a task since its previous `work-done`, the completion answers that task, and only tasks that have reached the worker since (fetched at least once, not acknowledged) are retired with it. A newer task it never fetched stays queued and watched, so the orchestrator is still told if it does not reach the worker. Otherwise the worker answered a task it took another way, such as its task file, and every unacknowledged task to its pane is retired. So one late `work-done` for an acknowledged task leaves a newer task the worker never fetched queued.

Which branch a `work-done` takes is decided by the worker's own sequence of acknowledgements and completions, so that protection depends on the worker acknowledging each task it takes and reporting each completion once. Two sequences defeat it (audit A2-3):

- **A repeated `work-done` cancels a newer task the worker never fetched.** The worker acknowledges task A and reports it done; that completion consumes the acknowledgement, and a newer task B stays queued. A second `work-done` then finds no acknowledgement since the previous one, takes the second branch, and retires B as superseded, unreported.
- **An acknowledged task that is never completed keeps a later file-taken task queued.** The worker acknowledges A without completing it, takes B from its task file without acknowledging it, and reports B done. The completion is read as answering A, retires only fetched tasks, and leaves B queued and watched, so the orchestrator may be told B did not reach the worker, and B may be handed to the worker again.

Both stay within the reporting worker's pane: the acknowledgement it consumes and the tasks a completion retires are that pane's. **Not done:** task-bound completion evidence — a `work-done` naming the task id it answers — would close both; until it exists this is an accepted limit.

### Publish and offer integration

`src/inbox_pubsub.rs` resolves live pane membership from the registry and the daemon's orchestration, role, working-directory and dispatch-return maps. It reads each member directory's project configuration. `subscribe` on an orchestration or role supplies topics; role `take_offers` supplies job pools; `[dispatch] subscribe` subscribes the caller to its dispatch tree. Omitted keys inherit through `extends`; an explicit list, including an empty one, replaces the inherited list. Names match `[a-z0-9][a-z0-9-]{0,63}`, with at most 64 entries per list.

The CLI exposes `inbox publish <topic> --text|--file`, `inbox offer <pool> --text|--file [--claim-ttl <duration>]`, `inbox complete <id>` and `inbox release <id>`. A body uses exactly one input option; `--file -` reads stdin, bounded at 1 MiB. `--claim-ttl` accepts unit-bearing durations such as `30m`, `1h30m`, `90s` or `500ms`; the daemon applies its claim-duration bounds.

| Hook-socket verb | Request fields beyond pane, agent and token | Successful reply |
| --- | --- | --- |
| `inbox_publish` | `topic`, `body` | `InboxPostReply`: `id`, `delivered_to`, and `refused_full` when some recipients are full. |
| `inbox_offer` | `pool`, `body`, optional `claim_ttl_ms` | `InboxPostReply`: `id`, and `offered_to` when assigned; the latter is absent while pooled. |
| `inbox_complete` | `id` | `InboxClaimReply`: `outcome: "completed"`. |
| `inbox_release` | `id` | `InboxClaimReply`: `outcome: "released"`. |

Refusals carry `refused` (stable code) and `error` (explanation), without a success id or outcome. Publish/offer codes include `invalid_topic`, `invalid_pool`, `not_live`, `no_scope`, `scope_changed`, `not_orchestrator`, `body_not_saved`, `rate_limited`, `inbox_full`, `deck_full`, `body_too_large`, `duplicate`, `too_many_offers` and `claim_ttl_out_of_range`. Publish and offer re-read the scope up to three times while agents change; if the scope still changes during admission, they refuse with `scope_changed`. Claim operations also use `not_claimant`, `unknown` and `claim_expired`; a complete or release that reaches the inbox after its claim expired, but before the ticker returned the offer, returns the offer to its pool and answers `claim_expired`. Provenance refusal codes apply, including `unattested` for a missing token on a legacy-admitted pane and `malformed_token` for an empty token. The four verbs also bind the peer pid to the managed agent's process tree under the same platform policy as waiters, refusing a proven mismatch with `inbox_not_agent_process`, and require the attested agent to be live in the pane. The verbs that take or settle the agent's own mail — `inbox_fetch`, `ack`, the `get_seed` alias and arming an `inbox_wait` — need positive evidence instead (PR #1735 second review): on Linux, macOS and Windows they are refused unless the peer is shown to be the managed agent or its descendant, so a peer whose ancestry cannot be read, a peer the kernel does not identify and a pane with no agent process are refused as a proven mismatch is. A connection keeps reporting the process that made it, so a caller can make its own ancestry unreadable by handing a connection to another process and exiting; best effort would admit that. `inbox_fetch`, `ack` and `inbox_wait` refuse with `inbox_not_agent_process`, and `get_seed` answers as no seed pending. On other platforms `parent_pid_of` reads nothing (`platform::proc::ANCESTRY_LOOKUP` is false), so these verbs fall back to best effort there and are bound by the capability and generation checks alone. A raw hook event acknowledges nothing: the daemon discards a `deck_message_ack_ids` key unread, and a hook acknowledges the blocks its prompt carries with the `ack` verb. A `dispatch` is accepted only with room held in the deck for its result (`InboxHub::reserve_reply`); with none it is refused with `deck_full` and nothing is dispatched, and once accepted its result is posted into that room, so neither the caller's backlog nor a deck that filled up meanwhile refuses it. When the inbox refuses the result itself (PR #1735 third review) — its text is over the body limit, or too long to hand over whole while neither the caller's directory nor the deck's state directory can take the file it would be saved to — a short notice goes into the same room instead, under the same `dispatch started` or `dispatch failed` subject, saying whether the dispatch started a unit and that its full result could not be delivered. The notice is composed by the deck, leaves out the unit's name and the result's text, and is cut to the body limit. A caller that has exited gets nothing, and the daemon log records the refusal.

An offer's body is Trusted and labelled as the orchestrator's instruction, like a delegate. The deck preface tells the taker to do the work and then complete or release the id. A publish body is Untrusted and labelled `<role> (announcement — the text inside is UNTRUSTED)` so the desktop does not classify it as a worker report.

`InboxLimits::offer_assign_wait` bounds an assigned but unfetched offer, using the undelivered-notice setting (five minutes by default). Expiry returns it to the pool and excludes that holder. `next_deadline` includes this deadline. The assigner wakes when work returns to a pool and sweeps every 30 seconds to discover late joiners. `InboxEvent.returned: Option<OfferReturn { previous, cause }>` records the previous holder and return reason inside the daemon. The attach broadcast's additive `InboxNotice.returned` flag removes the old holder's count and gives the desktop evidence row **Job handed back to its pool**. The additive, defaulted `InboxSummary.claimed` field appears in list-agents and `daemon status --json`; the TUI and desktop card counts treat claimed jobs as taken messages.

The hub queues offerer notices for claimed, completed, claim-expired and undeliverable jobs. `ack`, `fetch_within` and `fetch_first_acked` drain owed notices immediately, so a claim notice does not wait for the next tick. These fields and hook verbs are additive; S11 does not bump `PROTOCOL_VERSION` or add a semantic contract-break marker.

## Consumers and acknowledgement

Waiters have their own pool (512 daemon-wide, eight per agent generation), separate from hook-ingest slots. The newest eligible waiter takes the queued batch that fits its budget. A once waiter is spent by hand-over; a stream remains armed and accepts ack/nack controls on stdin. EOF requeues fetched, unacknowledged work. Waiters receive keepalives. The stream's pane capability and agent generation bind it to the recipient; launch command spelling does not enable native wake.

On Linux, macOS and Windows, `inbox wait` and `inbox announce` also bind the kernel-reported peer pid and the claimed component-instance pid to the managed agent's process tree. Both must be the managed agent or a descendant, and the claimed instance must be the peer or its ancestor. A proven mismatch is refused with `inbox_not_agent_process`. Linux reads `/proc/<pid>/stat`; macOS uses `proc_pidinfo(PROC_PIDTBSDINFO)`; Windows reads a Toolhelp process snapshot and treats a recorded parent that has exited, or that started after its child (a reused pid), as no parent, so the walk ends there as it does for an orphan on Linux. For the posting verbs, where process ancestry cannot be determined, including other platforms and processes that exit during the walk, this additional check falls back to the capability and generation checks. Arming `inbox wait` and `inbox announce` need positive evidence, as the mail-taking verbs above do: an announce pins the generation's receiver and opens the native-wake grace, so one admitted on best effort could pin a process that has exited and lock the real integration out with `another_component_armed` (PR #1735 third review). Every announcer holds its connection open until the daemon answers — the Claude and Codex `SessionStart` hooks, and `dot-agent-deck inbox announce` as the OpenCode server plugin and the Pi extension run it — so it is alive, and readable, while it is checked. On Windows the receiver's shell resolution and the same-kind nesting check still have no executable lookup, so those two steps are skipped there. The kernel-reported peer is bound to its process, not to its pid (PR #1735 third review): when the daemon accepts a hook connection it records the peer's start time — Linux `/proc/<pid>/stat` field 22, macOS `proc_pidinfo(PROC_PIDTBSDINFO)`'s `pbi_start_tvsec`/`pbi_start_tvusec`, Windows `GetProcessTimes`' creation time — and reads it again after each ancestry walk. A different start time means the pid now names another process, so a connection whose creator exited cannot borrow the ancestry of a later process that reuses the creator's pid; every bound verb refuses it with `inbox_not_agent_process`, and a start time that cannot be read refuses the verbs that need positive evidence. Linux counts start times in clock ticks (`CLK_TCK`, usually 100 a second), so a pid reused by a process started within the same tick as the creator would pass; macOS counts microseconds and Windows 100-nanosecond units. This binds the connecting process; the component-instance pid a request names is still checked by ancestry alone, as an ancestor of that bound peer. A stream from the same component instance supersedes its predecessor and requeues unacknowledged work; a different live instance is refused. A generation's native receiver is pinned to the first instance that arms or announces, resolving through hook shells to the agent rather than pinning a transient hook shell. A different instance cannot replace it after a stream closes, and announce can be refused with `another_component_armed`. An unnamed instance does not create a pin and cannot replace an existing one.

The inbox verbs bind authority to the agent's process tree: a process the agent runs, such as a command in its tool shell or a nested agent of another kind naming the outer agent's process as its component instance, acts with the outer agent's authority and can act as its receiver. The pin keeps a second non-shell instance out once one has armed or announced; it does not distinguish the agent from processes it runs that use its instance identity. For Claude Code below the 2.1.296 waiter gate, the deck's generated settings omit the waiter and its SessionStart hook does not announce native wake, so the first arriving receiver instance pins the generation.

| Agent | Component | Receipt signal |
|---|---|---|
| Claude Code | `SessionStart` and `Stop` asyncRewake once waiters (`inbox wait --agent claude`) | The waiter writes framed blocks to stderr and exits 2. The `UserPromptSubmit` hook for the prompt that carries those blocks acknowledges their ids with the `ack` verb. Doorbell `UserPromptSubmit` fetches and acknowledges when injecting context. The once waiter cannot answer `hold`, so a worker in a long turn can lose an offered job to the next worker. |
| Codex | `UserPromptSubmit` doorbell injection and `Stop` turn-end hand-over | The hook fetches and acknowledges with an inclusive 6000-byte budget. Stop returns `decision: block` with the framed content. Without trusted hooks, model-run `inbox fetch` acknowledges receipt. |
| OpenCode full TUI | Separate `dot-agent-deck-tui.js` TUI plugin; stream component `opencode_plugin` | `promptAsync`, then an assistant `message.updated` acknowledges pending deck messages in that session at or before its `parentID`. This covers coalesced turns; resolving `promptAsync` alone is insufficient. |
| OpenCode `--mini` | Server plugin stream component `opencode_mini` | An assistant turn acknowledges its parent or any earlier user message in the same session; ack and session-idle request a repaint nudge. |
| Pi | Extension stream component `pi_extension`, started per `session_start` | `sendUserMessage(text, { deliverAs: "followUp" })`, then a committed user `message_start` carrying the opener. Never acknowledge on the pre-commit `input` event; `message_end` tracks the turn reply, not receipt. OpenCode targets the session on screen, creates and navigates to one from the home route, and returns a child view to its root. It supplies model and agent from the target's last user message, then process history, then argv; a UI-only model selection before any prompt is not exposed to this path. The server plugin intercepts a doorbell in `chat.message` only in the full TUI's worker thread or `--mini`, fetches with `ack: false`, and replaces the text in place; an assistant turn acknowledges pending deck prompts in the same session through its parent; human messages and prompts in another session are not acknowledged. Main-thread `run`, `serve` and `acp` do not intercept it. Reassigning `output.parts` or transforming historical messages is not equivalent. `attach`, `acp`, `web`, `pr` and `github` remain unmeasured; the user docs claim doorbell fallback there.

The mini repaint nudge shrinks the PTY by one column, waits 300 ms by default, then restores it. It bypasses recorded geometry and scrollback changes. A concurrent real resize wins. Only `opencode_mini` streams request this nudge.

Pi kills its watcher on `session_shutdown` and starts a new one on session start, including `/new`, fork, switch and reload. Late callbacks are guarded by extension generation and caught so a stale context cannot kill Pi. Stream exit 3 means outside a deck or missing capability: Pi stops retrying rather than looping forever. Other watcher failures use bounded backoff. Its doorbell `input` handler fetches without acknowledgement, marks the original line handled and submits the framed content; receipt still waits for the committed user message.

Pi tags each native hand-over attempt and removes the tag in its `input` handler, consuming superseded attempts and messages already committed. An idle recheck retries an attempt the handler has not seen; after `input`, a retry needs the refusal witness described in [Pi extension](pi-extension.md#native-inbox-delivery). Without that witness the message waits for inbox ack-wait redelivery, which replaces the attempt when Pi has nothing queued. Unanswerable status queries do not trigger a retry. This guard cannot recall an attempt already past `input`; receipt and retry retain the inbox's at-least-once semantics.

### Long turns: hold and the late ack

A stream component may answer a redelivery with `{"hold":[id]}` when it still holds that message, queued in the agent behind the turn in progress, and did not hand it over again. For a direct message, the deck refunds that redelivery's hand-over, and the count never drops below one. The refund applies while the message is fetched by that stream and was first fetched less than one hour ago (`DEFAULT_HOLD_BOUND` in `src/inbox.rs`). Past that bound, `max_deliver` applies as it does to every consumer. A refunded hold also moves a delegated task's undelivered-notice deadline a full `DOT_AGENT_DECK_INBOX_UNDELIVERED_NOTICE_AFTER_MS` past the hold. A daemon that predates `hold` reads the line as an empty ack.

An offer fetched by a stream stays assigned to its holder when its ack-wait runs out, provided it remains within the hold bound and the previous hand-over was not left unanswered. It is handed to the same holder's stream again, and while the stream answers each such hand-over with `{"hold":[id]}`, the offer stays with that holder. Holding an offer refunds nothing: its delivery count measures assignments, and another hand-over to the same holder is not counted. The hold is bounded by the offer's claim TTL and `DEFAULT_HOLD_BOUND`, whichever is shorter, measured from the first fetch by the current holder.

The offer returns to its pool, excluding the holder, when the bound passes, a hand-over again goes unanswered for one ack-wait, or the stream does not fetch that hand-over within `DOT_AGENT_DECK_INBOX_UNDELIVERED_NOTICE_AFTER_MS`. An offer fetched by a consumer other than a stream returns at the first ack-wait. A nack or dropped stream also returns it to its pool. The hold bound resets for a new assignment. Pi and both OpenCode plugins answer `hold` for a held offer id as for a direct message, and their ack claims it.

Pi answers `hold` for a redelivered id that it is holding behind an admission, or that a hand-over still carries and that may still commit. A redelivery that replaces a hand-over lost after `input` is not a hold: the replaced hand-over did not reach the agent.

**Confirming acknowledgements (PR #1735 third review).** An agent-side component does not take its acknowledgement as recorded until the deck says so, because the deck may never hand the message over again (it allows `max_deliver` hand-overs, possibly one), and one it does hand over again would otherwise run twice.

- Pi and both OpenCode plugins keep each id they acknowledge — over the watcher's stdin, which answers nothing, or with the CLI — until `dot-agent-deck ack --json <id>` reports `{"acknowledged":true}`. The first ask comes a second after a stdin acknowledgement, or at once when the CLI carries it; later asks back off doubling to 30 seconds, eight asks at most. Each id keeps its own schedule, on its own timer, and the asks go out one at a time: a new acknowledgement never moves another id's next ask (PR #1735 third review), so a steady stream of new commits cannot keep postponing an older confirmation. A refusal by id (`undeliverable`, `wrong_agent`, `unknown`, reported `"final":true`) ends it at once. That and running out of asks are shown as a warning naming the message: Pi's `ui.notify`, the OpenCode TUI plugin's `api.ui.toast`, and the server plugin's `client.tui.showToast` (whether `--mini` draws a toast is not measured).
- Each of them also remembers the ids its agent answered, at most 256: the deck hands one of those over again only because it never recorded the acknowledgement, so it is acknowledged again, not prompted again. Pi keeps both sets process-wide across session replacements. The OpenCode server plugin (doorbell and `--mini`) and TUI plugin run in different JavaScript contexts in the full TUI, so each knows only its own: a doorbell-answered message the deck goes on refusing to record for a whole ack-wait, then hands to the TUI plugin's stream, is prompted again.
- The Claude Code and Codex hooks (`UserPromptSubmit`, Codex `Stop`) are one process per event, with no state between them. Each sends its `ack`s one connection per id and reads the deck's answer (`hook::ack_confirmation`); an unanswered one is asked again, three asks at most, 100 ms apart and doubling, all within the 5-second budget the single connection had. A refusal by id or running out of asks is written to the hook's stderr; whether the agent shows a hook's stderr in its main view is not measured. One never recorded is handed over again after the ack-wait, as before.

The OpenCode TUI and `--mini` plugins remember the session each deck prompt went to, and they follow `session.status` and `session.idle`. A redelivery of a prompt that is still pending, in a session that has stayed busy since, is answered with `hold` and is not prompted again. If the session goes idle with the prompt unanswered (an abort), or `message.removed` removes its user message (a revert), the next redelivery prompts it again. With no busy status seen for the session, a redelivery prompts again, as before.

An ack from the bound agent for a direct message that became undeliverable after `max_deliver` hand-overs is recorded: the message becomes acknowledged and the ack answers `acknowledged`. A message undeliverable for any other reason still answers `undeliverable`. The daemon remembers up to 256 such messages for one hour (`LATE_ACK_MAX_RECORDS` and `LATE_ACK_MEMORY` in `src/inbox_hub.rs`).

When a delegated task's orchestrator was told the task "has not reached the worker" and the worker then acknowledges it, that orchestrator generation gets one correction with the subject `task delivered after all`. This notice does not touch the card, so there is nothing to clear. A task that ran out of hand-overs before its late ack is corrected once through the late-ack record instead; its delegate watch has already been removed. The worker then counts as having received a task for work-done retirement.

For a task reported undeliverable after `max_deliver`, the recipient's card is lifted from its not-delivered Error to Thinking by a daemon-authored event carrying the `delivery_notice_cleared` metadata key. This happens once no other message the card was told about is still owed a correction, and only while the daemon's copy of the card still shows the deck's notice. Both the TUI and the desktop app consume this event.

Claude Code's once waiter has no channel to answer `hold`, so a direct message waiting behind a long Claude turn can still be redelivered and reported not delivered before it arrives. The orchestrator is then told it arrived. An offered job returns to its pool at the first ack-wait, so a Claude worker in a long turn can lose it to another worker; the former holder's late ack answers `wrong_agent`.

## Claude version gate and framing

`CLAUDE_ASYNC_REWAKE_MIN` in `src/hooks_manage.rs` is 2.1.296, the measured release, not a claim that older Claude versions lack asyncRewake. Unknown or lower versions get no waiter. SessionStart announces native wake only when the installed Claude settings contain the deck's SessionStart waiter; without it, including an installation below the version gate, no native announcement delays the doorbell. The waiter timeout is 86,400 seconds; `/clear` may leave several waiters, so inbox hand-over is claim-once. Once waiters poll their agent ancestry for orphan exit; stream watchers exit when their owning integration closes stdin.

The waiter settings include `rewakeMessage` and `rewakeSummary`. Both keys are `@internal` in Claude Code's schema, observed in 2.1.294–2.1.296, and are written only under the same 2.1.296 gate as asyncRewake. `rewakeMessage` explains that this is a deck message rather than a hook error; `rewakeSummary` is `✉ dot-agent-deck message`. Reinstall consolidates existing waiter entries and refreshes these values. If upstream removes the keys, default hook wording may return: retain session framing that agrees with Claude's automated-notification label.

`SESSION_FRAMING` is delivered through Claude's `SessionStart` context and doorbell injection; `AGENT_FRAMING` is the agent-neutral counterpart used by CLI fetch and Codex. They identify the deck as the workspace the user started, explain that work arrives as automated messages rather than fresh user approval, tell the agent to act on an id once, and distinguish UNTRUSTED reports from instructions. Do not add fixture-only authorization to live tests: the production framing must suffice.

Each block starts `[dot-agent-deck message <id> from <sender>]`, then `Sent by: <provenance>.`, and ends `[end of dot-agent-deck message <id>]`. Provenance comes from the attested sender or a deck-generated origin, not the worker's text. Agent-authored reports carry an inner UNTRUSTED fence. Forged framing tokens in content must be defused after normalizing text. Budget truncation must retain the enclosing fences and a safely rendered path to the full body when one is provided.

Before posting a message whose body cannot fit the tightest hand-over budget, the daemon saves its full content to an exclusive, owner-only file in the recipient's working directory under `.dot-agent-deck/`, falling back to the deck state directory. Untrusted content keeps its report fence and has forged message markers neutralised. The delivered excerpt names the saved file using an inert location description. If neither location can save it, the post is refused and nothing is posted; an acknowledged excerpt must not silently discard the rest of an unsaved body.


## Retired delivery interfaces

S12 removes `delegate_retry`, `submit_echo`, `prompt_delivery`, `WriteAndSubmit`, `SubmitText`, guarded task-body sends, provisional prompt confirmation, readiness buffers, the seed fallback and the draft cap. `get-seed` remains an inbox compatibility alias; `--reports-prompts` is a hidden no-op. `ack d-...` returns `unknown`: only inbox message ids can be acknowledged, and the former `stopped`/`not_pending` delivery outcomes are gone. Human input from both clients uses `WriteInput`.

The daemon warns at startup for each set entry in `REMOVED_DELIVERY_SETTINGS` without logging its value. The removed reuse debounce and desktop seed buffer have no effect either.

## Doorbell guards

The only automatic text typed into an agent's composer is the fixed doorbell: ` dot-agent-deck: message <id> waiting, run: dot-agent-deck inbox fetch`. It contains no task body. Eligibility requires queued work, no armed consumer, an elapsed native-arm grace, a hook-reported idle moment, and no unsent human draft. Unknown status, busy agents, permission prompts and unknown dialogs hold it. The guard applies to input from either client; no draft-deferral cap overrides it.

Codex additionally requires a recognised empty composer on screen, so an Enter interpreted as a newline does not cause the next ring to submit the user's draft. The one non-empty composer the doorbell writes to is one showing the exact line it last typed into that pane, message id included, left unsubmitted because Codex did not take that line's Enter. Two such states were seen live on Codex 0.160.0: the Enter was dropped, leaving Codex's cursor right after the line (`inbox/codex/013`), or, under CPU pressure, the Enter became a newline in the composer, leaving the cursor on the empty row directly below the line at the composer's indent (`inbox/codex/016`). In either, the next ring, or the cleanup once the message leaves `queued`, sends its bare CR alone, which submits the line, and types no second line on top. A ring that only flushed keeps the line recorded, so if Codex swallowed that CR as well, the next ring flushes again (`inbox/codex/017`). The record is dropped when the cleanup CR goes or a ring types a new line, and after that the line gets no byte (`inbox/codex/015`); a doorbell-shaped line naming another message gets none either (`inbox/codex/014`). That can be after the message the line names has left `queued`: while other work is queued, a ring due for it is sent in place of the owed cleanup, and if that ring only flushes, it keeps the record (`inbox/doorbell/018`). So while a frame matching the recorded line stays on screen and a message stays `queued`, each due ring the guards admit sends one lone CR, with no fixed total. That is deliberate: the flushed line runs `inbox fetch`, which serves whatever is queued, and dropping the record there would leave the remaining work behind a stranded line the deck sends no byte to. A flush that Codex also takes as a newline leaves the line above two blank composer rows with the cursor on the second, which the recogniser does not match, so the flushing stops there (`tests/codex_composer_guard.rs`); that holds for that rendered layout, not as a guarantee about how a renderer draws it. The match is on what the screen shows, not proof of where the text came from: a process that controls what the pane renders can draw the exact line and cursor, and a person can type the line, and either earns the flushing CR, again on each due ring for as long as the record and the queued work last, and each CR goes to whatever then owns the pane's input. The agent-identity, draft and admission checks still apply to it. Codex hides its `? for shortcuts` hint while the composer holds text, so that recogniser finds the composer from the bottom of the screen rather than from the hint. If Codex changes its UI and the recogniser stops matching, idle ringing waits; a user-started turn still enables the Stop hand-over. Native arm grace prevents startup ringing before a component has had time to connect. Doorbell retries have their own schedule and do not increment inbox hand-over attempts.

Eligibility is revalidated under the PTY writer before each automatic write step. A per-pane admission epoch changes when the agent, doorbell-relevant status, writability or wrapper fork changes, invalidating a previously scheduled ring; an armed consumer also cancels a ring.
