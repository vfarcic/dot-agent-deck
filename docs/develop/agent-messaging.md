# Agent messaging

Maintainer reference for the per-agent inbox and wake integrations. User behavior and setup belong in [Orchestration](../orchestration.md#delivery-in-the-tui-and-desktop-app). The core is `src/inbox.rs`; `src/inbox_hub.rs` owns connections, rendering and notifications; `src/inbox_cli.rs`, `src/inbox_prompt.rs` and `src/doorbell.rs` connect it to agents. Both clients consume the daemon's inbox summaries and broadcasts.

## Inbox model

The daemon owns an in-memory inbox. Restarting it loses inbox contents. Messages have ids of the form `m-<eight-character-deck-id>-<16-hex-random-bits>`, generated with OS randomness; an id is also the dedup key. A persistent deck id distinguishes decks, while the random suffix separates messages across restarts. The id lives at `<state_dir>/deck-id`; a first start publishes it under a lock on `.deck-id.lock` with a hard link, which never replaces an id another start published. A state directory on a filesystem that can neither lock nor hard-link fails the daemon's first start with an error saying so, rather than letting two daemons publish different ids. Direct addresses are `inbox.<deck>.<encoded-pane>`; the recipient binding also names the current agent generation. An exited generation's bound messages become undeliverable rather than moving to its replacement. Unbound messages can wait for a pane's next agent. A bound message goes in only while its agent still holds its pane, asked under the inbox lock right before insertion (PR #1735 fifth review, N4): `post_to_live`, attach `post-message` and the inbox's own notices check it there (`InboxHub::post_direct_where`, and `set_live_agent_check` for the hub's notices), as `post_delegate` and publish/offer already did. The exit sweep runs after the registry marks the agent exited, so a post that passes the check is swept, and one that fails it is refused with `recipient_gone`, removing any body it saved and giving back any reserved room.

| State | Meaning and next transition |
|---|---|
| `queued` | Eligible for one consumer to fetch. |
| `fetched` | Held by that receiver, awaiting acknowledgement. Ack settles it. Every attempt positively not handed makes it available again; otherwise its attempt model decides (a possession that lapses repeats it, marked as a possible repeat, or makes it uncertain). |
| `acknowledged` | Receipt recorded. This is not task completion. |
| `claimed` | An offer has a time-limited owner. Completion settles it; release, expiry or owner exit returns it to the pool. |
| `undeliverable` | Delivery limit reached, recipient exited, inbox closed or message superseded. The reason determines whether a card notice is owed. |

One budgeted hand-over carries at most 16 blocks (`inbox_prompt::MAX_IDS`), the most ids Claude's prompt hook reads from one prompt, so no block is in context unacknowledged (PR #1735 fifth review, N1). The default ack-wait is 60 seconds and `max_deliver` is 5. Retry preserves the id; consumers should act on an id once. Dedup remembers up to 4096 ids for ten minutes. The pending limits are 256 per recipient and 4096 daemon-wide, with a 1 MiB body limit; a bound refuses explicitly rather than evicting pending work. Terminal history retains at most 64 messages per pane, 1024 daemon-wide and 16 MiB of bodies, evicting the oldest terminal messages first. Terminal bodies expire after one hour while summaries remain within the count bounds; closing a pane drops its terminal history. Pending work is not trimmed to make history space. Stored subjects are one line of at most 200 characters.

Publish fans out copies with one id, with state per recipient. Subscription resolution excludes the sender and stays inside the sender's orchestration instance or dispatch tree. Offers go to one eligible subscriber at a time; acknowledging an offer claims it. The default claim is 30 minutes, with a 60-second minimum and 24-hour maximum. Release, expiry and owner exit exclude the former holder from subsequent assignment. Publish and offer share a per-agent budget of 60 per minute; deck-generated messages are exempt.

### Delegated-task retirement

A newer delegation or a pane restart retires the worker's earlier unacknowledged tasks as superseded, and superseded tasks are not reported. The newer task's room is reserved, and its long body saved, before anything else: `dispatch_one_owned` calls `InboxHub::reserve_delegate` ahead of the supersede and of a `clear = true` restart, so a task the inbox refuses, or whose body cannot be saved, supersedes nothing and restarts nothing (PR #1735 fifth review, N8 and B-01). The older tasks it retires count as room it replaces, so an inbox those tasks fill is no refusal. Answers the deck reserved room for are not held to the recipient's bound, so an inbox they pushed past it can still refuse the task, and does so before anything is retired (reviewer B-04). The task itself is checked against the recipient's bound only when it reserves, not again when it goes in (PR #1735 sixth review): ordinary messages posted to the worker while the task is being prepared (its body saved, a `clear = true` worker restarted) are admitted against the bound as it then stands, and the task goes in after them, so the worker's inbox can then hold more than `max_per_recipient`. Ordinary posts to it are refused with `inbox_full` until enough of its messages settle (`a_reserved_task_goes_in_over_an_inbox_filled_while_it_was_prepared`). Reserved answers add to the excess the same way, so it has no fixed size. When the task is not posted after all (its worker is no longer live, a `clear = true` restart fails, or the inbox refuses it while it is prepared or at the post), the notice telling the orchestrator so goes into the task's reservation instead (`post_orchestrator_notice_in`, PR #1735 sixth review RB2-01), so a deck that filled meanwhile cannot refuse it too. That room was granted counting the older tasks the new one would have retired, and those stay live because nothing was posted, so the notice can leave the deck one message over `max_messages` for that dispatch, and ordinary posts are refused with `deck_full` until room returns. Each such dispatch, and each reserved answer, can add one more, so the deck-wide excess has no fixed size either. A worker's `work-done` names no task, so the deck infers which one it answers. If the worker acknowledged a task since its previous `work-done`, the completion answers that task, and only tasks that have reached the worker since (fetched at least once, not acknowledged) are retired with it. A newer task it never fetched stays queued and watched, so the orchestrator is still told if it does not reach the worker. Otherwise the worker answered a task it took another way, such as its task file, and every unacknowledged task to its pane is retired. So one late `work-done` for an acknowledged task leaves a newer task the worker never fetched queued.

Which branch a `work-done` takes is decided by the worker's own sequence of acknowledgements and completions, so that protection depends on the worker acknowledging each task it takes and reporting each completion once. Two sequences defeat it (audit A2-3):

- **A repeated `work-done` cancels a newer task the worker never fetched.** The worker acknowledges task A and reports it done; that completion consumes the acknowledgement, and a newer task B stays queued. A second `work-done` then finds no acknowledgement since the previous one, takes the second branch, and retires B as superseded, unreported.
- **An acknowledged task that is never completed keeps a later file-taken task queued.** The worker acknowledges A without completing it, takes B from its task file without acknowledging it, and reports B done. The completion is read as answering A, retires only fetched tasks, and leaves B queued and watched, so the orchestrator may be told B did not reach the worker, and B may be handed to the worker again.

Both stay within the reporting worker's pane: the acknowledgement it consumes and the tasks a completion retires are that pane's. **Not done:** task-bound completion evidence — a `work-done` naming the task id it answers — would close both; until it exists this is an accepted limit.

### Publish and offer integration

`src/inbox_pubsub.rs` resolves live pane membership from the registry and the daemon's orchestration, role, working-directory and dispatch-return maps. It reads each member directory's project configuration. `subscribe` on an orchestration or role supplies topics; role `take_offers` supplies job pools; `[dispatch] subscribe` subscribes the caller to its dispatch tree. Omitted keys inherit through `extends`; an explicit list, including an empty one, replaces the inherited list. Names match `[a-z0-9][a-z0-9-]{0,63}`, with at most 64 entries per list.

The CLI exposes `inbox publish <topic> --text|--file`, `inbox offer <pool> --text|--file [--claim-ttl <duration>]`, `inbox complete <id>` and `inbox release <id>`. A body uses exactly one input option; `--file -` reads stdin, bounded at 1 MiB. `--claim-ttl` accepts unit-bearing durations such as `30m`, `1h30m`, `90s` or `500ms`; the daemon applies its claim-duration bounds.

| Hook-socket verb | Request fields beyond pane, agent and token | Successful reply |
| --- | --- | --- |
| `inbox_publish` | `topic`, `body` | `InboxPostReply`: `id`, `delivered_to`, and `refused_full` when some recipients are full. |
| `inbox_offer` | `pool`, `body`, optional `claim_ttl_ms` | `InboxPostReply`: `id`, and `offered_to` when assigned; the latter is absent while pooled. |
| `inbox_complete` | `id` | `InboxClaimReply`: `outcome: "completed"`. |
| `inbox_release` | `id` | `InboxClaimReply`: `outcome: "released"`. |

Refusals carry `refused` (stable code) and `error` (explanation), without a success id or outcome. Publish/offer codes include `invalid_topic`, `invalid_pool`, `not_live`, `no_scope`, `scope_changed`, `not_orchestrator`, `body_not_saved`, `rate_limited`, `inbox_full`, `deck_full`, `body_too_large`, `duplicate`, `too_many_offers` and `claim_ttl_out_of_range`. Publish and offer re-read the scope up to three times while agents change; if the scope still changes during admission, they refuse with `scope_changed`. Claim operations also use `not_claimant`, `unknown` and `claim_expired`; a complete or release that reaches the inbox after its claim expired, but before the ticker returned the offer, returns the offer to its pool and answers `claim_expired`. Provenance refusal codes apply, including `unattested` for a missing token on a legacy-admitted pane and `malformed_token` for an empty token. The four verbs also require the connecting process to be a member of the pane, as waiters do, and the attested agent to be live in the pane. Since PRD #1666 part 3 a member is a process the kernel recorded as the deck's own uid, or one in the managed agent's process tree ([hook-provenance.md, Inbox admission](hook-provenance.md#inbox-admission-the-panes-capability-and-the-decks-user-prd-1666-part-3)); a process outside that tree under another uid is refused `inbox_other_user`, and where the uid cannot be read (Windows today) a process proven outside the tree is refused `inbox_not_agent_process`. The verbs that take or settle the agent's own mail — `inbox_fetch`, `inbox_receipt_fetch`, `ack`, `inbox_committed` and arming an `inbox_wait` — need positive evidence instead (PR #1735 second review): a peer the kernel does not identify, or whose pid names another process by the time the deck has checked it, is refused `inbox_peer_unidentified`; where the uid cannot be read, a peer whose ancestry cannot be read is refused `inbox_peer_unidentified` too, and a pane with no agent process `inbox_not_agent_process`. A connection keeps reporting the process that made it, so a caller can hand a connection to another process and exit; best effort would admit that. `get_seed` takes nothing since part 3's H5, and answers every caller, refused or admitted, with the same withdrawal. On platforms where `parent_pid_of` reads nothing (`platform::proc::ANCESTRY_LOOKUP` is false), these verbs fall back to best effort and are bound by the capability, the uid and the generation checks. A raw hook event acknowledges nothing: the daemon discards a `deck_message_ack_ids` key unread, and a hook acknowledges the blocks its prompt carries with the `ack` verb. A `dispatch` is accepted only with room held in the deck for its result (`InboxHub::reserve_reply`); with none it is refused with `deck_full` and nothing is dispatched, and once accepted its result is posted into that room, so neither the caller's backlog nor a deck that filled up meanwhile refuses it. When the inbox refuses the result itself (PR #1735 third review) — its text is over the body limit, or too long to hand over whole while neither the caller's directory nor the deck's state directory can take the file it would be saved to — a short notice goes into the same room instead, under the same `dispatch started` or `dispatch failed` subject, saying whether the dispatch started a unit and that its full result could not be delivered. The notice is composed by the deck, leaves out the unit's name and the result's text, and is cut to the body limit. A caller that has exited gets nothing, and the daemon log records the refusal.

An offer's body is Trusted and labelled as the orchestrator's instruction, like a delegate. The deck preface tells the taker to do the work and then complete or release the id. A publish body is Untrusted and labelled `<role> (announcement — the text inside is UNTRUSTED)` so the desktop does not classify it as a worker report.

`InboxLimits::offer_assign_wait` bounds an assigned but unfetched offer, using the undelivered-notice setting (five minutes by default). Expiry returns it to the pool and excludes that holder. `next_deadline` includes this deadline. The assigner wakes when work returns to a pool and sweeps every 30 seconds to discover late joiners. `InboxEvent.returned: Option<OfferReturn { previous, cause }>` records the previous holder and return reason inside the daemon. The attach broadcast's additive `InboxNotice.returned` flag removes the old holder's count and gives the desktop evidence row **Job handed back to its pool**. The additive, defaulted `InboxSummary.claimed` field appears in list-agents and `daemon status --json`; the TUI and desktop card counts treat claimed jobs as taken messages.

The hub queues offerer notices for claimed, completed, claim-expired and undeliverable jobs. `ack` drains owed notices immediately, so a claim notice does not wait for the next tick. These fields and hook verbs are additive; S11 does not bump `PROTOCOL_VERSION` or add a semantic contract-break marker.

## Consumers and acknowledgement

Waiters have their own pool (512 daemon-wide, eight per agent generation), separate from hook-ingest slots. The newest eligible waiter takes the queued batch that fits its budget. A once waiter is spent by hand-over, and one that goes away before its hand-over completes requeues the batch it was given. A stream is a receipt stream ([Receipts and possession](#receipts-and-possession-opencode-and-pi)); a stream from a component with no receipt slot is refused before it arms (inbox/boundary/036). Waiters receive keepalives. The stream's pane capability and agent generation bind it to the recipient; launch command spelling does not enable native wake.

`inbox wait` and `inbox announce` also need the connecting process to be a member of the pane (above), and bind the claimed component-instance pid to it: the claimed instance must be the peer or its ancestor, or it is refused `inbox_component_not_caller`, and not a process above the managed agent (the daemon, a terminal, init), nor resolve through shells to one, or it is refused `inbox_receiver_above_agent`; a process between the peer and that instance running the instance's executable, an agent of the same kind nested in it, is refused `inbox_nested_agent`. Linux reads `/proc/<pid>/stat`; macOS uses `proc_pidinfo(PROC_PIDTBSDINFO)`; Windows reads a Toolhelp process snapshot and treats a recorded parent that has exited, or that started after its child (a reused pid), as no parent, so the walk ends there as it does for an orphan on Linux. For the posting verbs, where process ancestry cannot be determined, including other platforms and processes that exit during the walk, this additional check falls back to the capability and generation checks. Arming `inbox wait` and `inbox announce` need positive evidence, as the mail-taking verbs above do: an announce pins the generation's receiver and opens the native-wake grace, so one admitted on best effort could pin a process that has exited and lock the real integration out with `another_component_armed` (PR #1735 third review). Every announcer holds its connection open until the daemon answers — the Claude and Codex `SessionStart` hooks, and `dot-agent-deck inbox announce` as the OpenCode server plugin and the Pi extension run it — so it is alive, and readable, while it is checked. On Windows the receiver's shell resolution and the same-kind nesting check still have no executable lookup, so those two steps are skipped there. The kernel-reported peer is bound to its process, not to its pid (PR #1735 third review): when the daemon accepts a hook connection it records the peer's start time — Linux `/proc/<pid>/stat` field 22, macOS `proc_pidinfo(PROC_PIDTBSDINFO)`'s `pbi_start_tvsec`/`pbi_start_tvusec`, Windows `GetProcessTimes`' creation time — and reads it again after each ancestry walk. A different start time means the pid now names another process, so a connection whose creator exited cannot borrow the ancestry of a later process that reuses the creator's pid; every bound verb refuses it with `inbox_peer_unidentified`, and a start time that cannot be read refuses the verbs that need positive evidence. Linux counts start times in clock ticks (`CLK_TCK`, usually 100 a second), so a pid reused by a process started within the same tick as the creator would pass; macOS counts microseconds and Windows 100-nanosecond units. This binds the connecting process; the component-instance pid a request names is still checked by ancestry alone, as an ancestor of that bound peer. A receipt stream registering again in its slot retires its predecessor, and the new registration is asked to resume the predecessor's attempts ([Receipts and possession](#receipts-and-possession-opencode-and-pi)); a different live instance is refused. A generation's native receiver is pinned to the first instance that arms or announces, resolving through hook shells to the agent rather than pinning a transient hook shell. A different instance cannot replace it after a stream closes, and announce can be refused with `another_component_armed`. An unnamed instance does not create a pin and cannot replace an existing one.

The inbox verbs bind authority to the pane's members: a process the agent runs, such as a command in its tool shell or a nested agent of another kind naming the outer agent's process as its component instance, or a process outside its tree that holds the pane's capability and runs as the deck's uid (Claude Code's background session host), acts with the outer agent's authority and can act as its receiver. The pin keeps a second non-shell instance out once one has armed or announced; it does not distinguish the agent from processes it runs that use its instance identity. For Claude Code below the 2.1.296 waiter gate, the deck's generated settings omit the waiter and its SessionStart hook does not announce native wake, so the first arriving receiver instance pins the generation.

OpenCode targets the session on screen, creates and navigates to one from the home route, and returns a child view to its root. It supplies model and agent from the target's last user message, then process history, then argv; a UI-only model selection before any prompt is not exposed to this path. The server plugin intercepts a doorbell in `chat.message` only in the full TUI's worker thread or `--mini`, fetches with `--adapter-integration 2 --rx <its receiver>`, so the fetched attempts are bound to its own receipt stream (caps on that stream, bodies to the fetch), and replaces the text in place; an assistant turn commits pending deck attempts in the same session through its parent; human messages and prompts in another session commit nothing. Main-thread `run`, `serve` and `acp` do not intercept it. Reassigning `output.parts` or transforming historical messages is not equivalent. `attach`, `acp`, `web`, `pr` and `github` remain unmeasured; the user docs claim doorbell fallback there.

The mini repaint nudge shrinks the PTY by one column, waits 300 ms by default, then restores it. It bypasses recorded geometry and scrollback changes. A concurrent real resize wins. Only `opencode_mini` streams request this nudge.

Pi runs one generated receiver per Pi process, not per session: `/new`, resume, fork and a reload of the same extension version keep the same watcher. Its lifecycle, its doorbell substitution and the fence at its two hand-over points are in [Pi: one receiver per process](#pi-one-receiver-per-process). Stream exit 3 means outside a deck or missing capability: Pi stops respawning for the process rather than looping forever. Other watcher failures use the shared receiver's bounded backoff.

### Long turns and the late ack

There is one delivery policy, the receipt policy: since PRD #1666 part 3's H5 every receiver is on it, and the deck refuses every way an older `dot-agent-deck` took mail under the legacy policy that made a fetched message available again when its ack-wait ran out ([Withdrawn legacy delivery](#withdrawn-legacy-delivery-prd-1666-part-3-h5)). A long turn is the attempt model's to judge: possession, the turn clock, and a lapse into a marked repeat or uncertainty ([Receipts and possession](#receipts-and-possession-opencode-and-pi), [Claude Code on receipts](#claude-code-on-receipts-prd-1666-part-2)).

**Confirming acknowledgements (PR #1735 third review).** `dot-agent-deck ack --json` says whether the deck recorded an explicit acknowledgement (`hook::ack_confirmation`: recorded, refused by id, or unconfirmed when the deck gave no answer it stands behind). Hooks do not acknowledge by id: they commit the exact attempts they printed (part 2 §1.3, part 3's H4), and H5 removed the retrying id-ack (`acknowledge_at`) that hooks from before those parts used.

An ack from the bound agent for a direct message that became undeliverable after `max_deliver` hand-overs is recorded: the message becomes acknowledged and the ack answers `acknowledged`. A receipt receiver's commit of such a message, contradicting the not-handed reports it ran out of attempts on, settles it the same way: the attempt model settles it, the inbox copy becomes acknowledged, and the late-ack record, while it is retained, corrects the orchestrator and clears the card once (reviewer R9T-03). A message undeliverable for any other reason still answers `undeliverable`. The daemon remembers at most 256 such messages, oldest dropped first, and drops those older than one hour whenever it records another (`LATE_ACK_MAX_RECORDS` and `LATE_ACK_MEMORY` in `src/inbox_hub.rs`), so a record can outlive the hour until then.

A notice the hub owes (claimed, completed, undeliverable, late-delivery correction) that a full inbox or deck refuses stays owed and is tried again on the next acknowledgement or fetch, or after a second at the latest, until it is posted or its recipient is gone. A worker's `work-done` and a dispatched unit's completion hold room for their report before anything is taken on (`InboxHub::reserve_reply`), and the report goes into that room, or a short deck notice in its place when the inbox refuses the report itself; with no room the `work-done` is refused with `deck_full` and nothing it would consume is touched (PR #1735 fifth review, N3).

When a delegated task's orchestrator was told the task "has not reached the worker" and the worker then acknowledges it, that orchestrator generation can get one correction with the subject `task delivered after all`, while the task's delegate watch remains. This notice does not touch the card, so there is nothing to clear. A task that ran out of hand-overs before its late ack can be corrected once through its late-ack record instead, while that record is retained; its delegate watch has already been removed. The worker then counts as having received a task for work-done retirement.

**A correction is possible, never promised (PRD #1666 part 2).** The uncertain notice and the cancel notice for a task that may have been handed over say "A later receipt may produce a correction." after telling the orchestrator to check the worker's pane, and the user page says a correction may follow, because what the deck keeps to correct with is bounded and in memory. An uncertain task is corrected through its delegate watch; a cancelled one through that watch or its `cancelled_tasks` record, which holds at most 256 tasks (`MAX_CANCELLED_TASKS`), oldest dropped first; a task that ran out of hand-overs through its late-ack record, bounded as above. Each of these goes with a deck restart. A late receipt is also not seen once the attempt's verifier is reclaimed ([Possession](#claude-code-on-receipts-prd-1666-part-2)) or the worker's generation exits, and an uncertain task's correction goes when a delegation with `--supersede` to the same `clear = false` worker retires its watch (`retire_delegates_locked`), while the worker may still commit it.

For a task reported undeliverable after `max_deliver`, a late acknowledgement whose late-ack record is still retained can lift the recipient's card from its not-delivered Error to Thinking by a daemon-authored event carrying the `delivery_notice_cleared` metadata key; once the record is dropped, the late ack clears nothing. The event is sent only when no other message the card was told about is still owed a correction, and only while the daemon's copy of the card still shows the deck's notice. Both the TUI and the desktop app consume this event.

Before PRD #1666 part 2, Claude Code's once waiter could not say it held a message, so a direct message waiting behind a long Claude turn could be redelivered and reported not delivered before it arrived. On receipts the turn clock stands in for that (C-1, [Claude Code on receipts](#claude-code-on-receipts-prd-1666-part-2)); the legacy behaviour remains for a Claude Code hook the deck serves legacy. There, an offered job returns to its pool at the first ack-wait, so a Claude worker in a long turn can lose it to another worker, and the former holder's late ack answers `wrong_agent`.

## Receipts and possession (OpenCode and Pi)

PRD #1666 §13 step 4 switched OpenCode, both contexts together, and its Pi slice then switched Pi, from the ack-wait to the receipt policy of design v3.2. The pure model is `src/inbox_attempts.rs`, the spool `src/inbox_receipt.rs`, the hub's engine `src/inbox_engine.rs` (a child of `src/inbox_hub.rs`), the watcher `src/inbox_watcher.rs`, and the receiver's JavaScript in `src/inbox_receiver.js`, which `src/opencode_manage.rs` inlines into OpenCode's plugins and `inbox_receiver::pi_module()` wraps as Pi's `pi-extension/src/inbox-receiver.js`.

**One policy.** A message is handed to a receipt receiver only while its inbox copy is queued for the receiver's generation, and from then on that generation's attempt model decides what becomes of it; the engine mirrors the model's decisions only into a copy whose recipient still admits that generation, so an offer that moved to another holder is never settled by its earlier holder's model. Until part 3's H5 each copy carried an owner (`AssignmentOwner`) that kept the legacy ack-wait and the receipt model apart while unconverted consumers shared a pane; with the legacy policy withdrawn there is nothing to keep apart, and the field is gone.

**The stream.** `inbox wait --agent opencode|opencode-mini|pi --stream --adapter-integration 2 [--doorbell-only] [--resumed]` registers a receiver in its slot (`opencode_tui`, `opencode_server` or `pi`); the slots never fence each other. The first line is `{"registered":{"rx","slot","keepalive_ms"},"resume":[…]}`. Hand-outs are `messages` whose entries add `a`, `e`, `d`, `repeat` and, for the watcher only, `caps`; the watcher strips the caps before the plugin sees the line. Other daemon lines: `grant` (answer to `may`), `revoke`, `rebound` (a resumed attempt's new delivery number and, for the watcher only, its caps, so a replacement watcher can still publish its receipts), `issued` (caps of attempts a doorbell fetch bound to this receiver), `keepalive`. The plugin writes `possess {seq, seen, held}` (a snapshot on every change and in answer to each keepalive), `may` (the final hand-over check), `handed`, `committed`, `not_handed`, `revoked_ack`, `already_handed`, `resume_answers` and, for mini, `repaint`.

**Receipts before the daemon is told.** For `handed` and `committed` the watcher publishes `<msg>.<A>.<e>.<stage>` into `$DOT_AGENT_DECK_INBOX_SPOOL/<pane>/<agent>/rec` with that stage's cap, then forwards the control; a publish still in flight is added to every snapshot it forwards meanwhile, counted per attempt, so overlapping `handed` and `committed` publishes keep it held until the last finishes (inbox/opencode/043). A stage report for an attempt whose cap the watcher lacks publishes nothing and is reported `degraded`, never as a receipt. The daemon keeps the caps of issued attempts (beside the hashes that admit records) only to hand them to a replacement watcher in `rebound` (inbox/opencode/042). A replacement watcher learns from its registration which attempts it is asked to resume; a stage report for one of them that arrives before the daemon's `rebound` answer waits for those caps, up to five seconds, held in the snapshots meanwhile, and goes degraded only if none come (an answer the plugin did not give as `retained` ends the wait at once; inbox/opencode/048). A stage report that reaches a watcher before it has read its registration waits for that registration within the same five seconds, rather than failing for want of a spool: "not registered yet" is not "registered without a cap" (inbox/opencode/050). A report whose watcher's registration does not come within those five seconds is degraded too, as is one still waiting when the stream ends, which ends both waits at once (inbox/opencode/051). The plugin keeps a stage report it makes while no watcher runs (a restart's backoff) or before the new watcher has registered: that attempt answers the resume `retained`, and the report goes to the watcher after the resume answers (inbox/opencode/049). A report a watcher took and then died with is sent again to the next only when the new registration hands back authority to publish it: its attempt is asked back (`resume`, an attempt not yet final), or it is a `committed` report for an attempt the registration lists as `correctable` (r8k R8G-03). Any other is dropped. So a context that survives its watcher's restart keeps the commit it witnessed in the meantime (inbox/opencode/049). `correctable` lists the final attempts of the slot's retired incarnations that keep their late-commit verifier and are not reclaimed — a `HandedInert` attempt after a Cancel, a `Fenced` one still verifying — each with its commit cap only (`InboxCorrectable`), from the generation's own model and evidence store, after `admit_receiver` admitted the registering instance; another slot, another generation and a refused instance get nothing (inbox/opencode/053). The watcher takes the cap out of the line under the lock that opens its spool and forwards the bare refs, so a late commit its predecessor died with is published with the attempt's own cap, can correct the sender ("delivered after all, despite Cancel") and returns the evidence (inbox/opencode/052, inbox/opencode/054); a `handed` report for such an attempt still has no cap and is degraded. Registration hands back no stage, approval or callback, and an attempt it does not list (reclaimed, or never verifying) keeps the missing-cap degradation. A hand-back holds a `Fenced` attempt's verifier for as long as the incarnation it was handed to lives (r8k B02, `Attempt::correcting`): the registration makes a spool check already under way stale (the mark), and `verify_candidates` leaves the attempt out, so no absence returns the evidence of a commit the replacement may still be replaying. If that replacement dies before publishing, the next registration hands the attempt back again, and the commit still corrects the sender once, provided the task still has a correction route — its delegate watch or a retained cancelled-task record (inbox/attempts/019). Verification resumes once the holder is retired with no successor (`closed_retire_after` after its stream closed); a context that registers only after that, and after a check found nothing, has lost the hand-back. The hold costs one evidence reservation per such attempt for as long as its holder lives, whether or not the context saved a commit for it, since the daemon cannot tell which. Pi's successor watcher can reuse this: it needs a retained answer for the open attempts it was passed, so they come back through `resume` and `rebound`, and its tests have to cover repeated successor registrations, since every registration lists the slot's correctable attempts again until they are committed or reclaimed. Told to stop (its stdin ends), or once its stream ends, a watcher waits up to two seconds for its publications in flight before it exits, and the plugin's stop sends SIGTERM only if the watcher is still running three seconds after it ended the watcher's stdin, on a timer that keeps nothing alive. That allows bounded time for publication: a commit reported as the context is disposed can reach the spool and the daemon (inbox/opencode/051), and can still be lost or reported degraded. The plugin's stop does not flush stage reports queued while no watcher is registered (a restart's backoff, or before the new watcher registers): there is no authority to publish them with, and waiting for one would hold the context past the bounded drain. Their attempts may take the checked, marked-repeat path, if their message is still eligible for one; the generation's exit makes its live messages `Undeliverable(Exited)` and clears their scheduled delivery instead, and the repeat limits and a message already terminal also stop it. Like any context loss, that is not covered. The watcher's test knobs (`DOT_AGENT_DECK_INBOX_TEST_PUBLISH_DELAY_MS`, `…_DROP_COMMITTED`, `…_REBIND_DELAY_MS`, `…_REGISTER_DELAY_MS`) are read only by a build with the `e2e` feature, and the PTY spawn removes them from what an agent inherits, so only a spawn that sets one explicitly passes it on. The hub's clock reads the spool off the executor while any attempt could still have an unseen commit: a bounded scan whose every admitted commit is applied, whichever issued attempt it is for (fenced, lapsed, an earlier assignment's, a late-correction verifier's), then an exact lookup of each lapse candidate's commit record. A found commit settles it; only a completed, error-free cycle and a lookup that finds nothing clears it. An automatic repeat needs every possibly handed attempt of the assignment cleared, revalidated under the lock against possession regained while the IO ran, so no snapshot, TTL expiry, resume answer or control can repeat anything before the clock has looked (inbox/boundary/019, inbox/boundary/020, inbox/attempts/005). A clearance covers one repeat decision: every hand-out of the assignment withdraws its siblings' clearances and bumps their marks, so the next repeat waits for a check made after that hand-out, and a commit published, or a lookup turned Unknown, in between is seen (inbox/boundary/029). The hand-out re-checks the clearances itself, not only the clock's rule that scheduled the repeat: a clock pass that runs late can clear an attempt and schedule its repeat, and the next pass then retires the closed stream and fences the attempt, withdrawing its clearance while the repeat, younger than the wait bound, stays scheduled; a successor registering then finds the hand-out's own check the only thing refusing it (inbox/boundary/037). A fenced attempt keeps a late-commit verifier: once its message has ended (a Cancel, say), the clock looks its commit up, a commit found corrects the sender while the task still has a correction route (its delegate watch, or a cancelled-task record not yet evicted), and only a lookup that finds none returns its evidence, so, in a generation with a spool to read, a receipt published before the Cancel is not deleted unread (inbox/boundary/028); a generation without one follows the degraded policy below, under which the candidates count as checked. A message that cannot go on for two `POSSESS_TTL`s — no check can tell, or no receiver takes its scheduled repeat — is `Uncertain` and waits for the user. A generation with no spool to read (none started, or its reader could not be built) follows the degraded policy: its candidates count as checked, and its card says receipts are degraded. The deck's own read errors degrade the generation too (inbox/boundary/023). That is fail-closed by design, and it has a cost: a file at an attempt's exact record name that is a well-formed record carrying the wrong cap is neither admitted nor removed by a scan, so that attempt is Unknown, never absent, for as long as the file stays, and it never lapses into its marked repeat. A same-user process can obstruct a lapse this way without holding any genuine cap, and this alone sets no `receipts_degraded` (a U2 obstruction, accepted). A spool that cannot be opened or written sets `receipts_degraded`, sticky for the generation, shown on both clients' cards. So does a daemon whose spool could not start at all (`Spool::start` failing, four lost pending-lock races among the ways): every receipt generation's card names that failure (`InboxHub::set_spool_error`, inbox/boundary/016), and delivery goes on without receipt protection rather than claiming it. The daemon reaps spool instances earlier runs left a step at a time: `Spool::start` takes the first step and a thread takes another every minute (`REAP_INTERVAL`); each step lists at most 8192 root names on from where the previous one stopped, so a dead instance listed after any number of names that stay is reached within one pass (inbox/receipt/018). On Windows the spool's directories are held open without delete sharing, so they cannot be renamed or deleted, and every spool operation, which Windows makes by path, checks through those held handles, before and after, that no directory of the chain is a reparse point (`FSCTL_SET_REPARSE_POINT` on an empty directory needs neither a rename nor delete sharing); one that is there when a check looks fails the operation, which degrades the generation (inbox/receipt/017). That is detection, not confinement: a postcheck cannot undo a create, link, rename or remove that already went through a redirected path, and a junction installed and removed between the two checks is not seen. Write sharing stays allowed on the held handles; the reason, that dropping it would not stop an attribute-access handle from setting a reparse point, is unverified, and receipt/017 uses a generic writable handle, so it cannot tell. When the attempt model returns an attempt's evidence reservation, its records, caps and revoke marker are removed; at exit the generation's spool directory goes.

**Possession and the final check.** The plugin holds an attempt from hand-out until it commits or is positively not handed. A callback asks `may`, and once granted, re-checks synchronously — the context still active, the grant's epoch the receiver's current one, the attempt neither revoked nor dropped — with no await before `promptAsync`. Every watcher start bumps the epoch, so an approval outlived by a rebinding or a disposal never reaches OpenCode; the callback asks again under the new incarnation, or reports `not_handed`. A check still unanswered when its watcher ends is not a refusal either: the receiver's `may` waits up to five seconds for the successor to register (after its resume answers, so the attempt is answered `retained`) and asks once more under it. That is one wait and one re-ask: no registration in time resolves as refused, and so does a re-ask that is refused, times out, fails to write, is stopped or drained, or is voided by another restart (PR #1735 review 4305713311, inbox/opencode/055). Pi's pump shares the receiver and asks again on the registration as before. An approval also expires: it is usable for nine keepalives (capped at five seconds) from when it was asked for, measured on the monotonic clock. The daemon retires a closed stream no sooner than nine keepalives after the close, and the close follows any approval it sent, so a context whose event loop stalled with an approval buffered, past the watcher's exit and the retirement, cannot call once the deck fenced the attempt and a Cancel may have ended it (inbox/opencode/046). A refused `may` is only a refusal: the daemon changes no stage for it, because an earlier approval of the same attempt may still be live in the context. An attempt makes at most one `promptAsync`: the check also refuses an attempt whose native call already began, so that call's outcome is the attempt's. `not_handed` is the plugin's own report, from a refused check or from a 4xx answer to that one call, and either is sent after the plugin has revoked the attempt locally, so no outstanding approval of it can reach OpenCode afterwards, and never while a callback of the attempt is inside its `promptAsync`, which reports for itself (inbox/attempts/018, inbox/opencode/037). Nor is it sent once a revoke of the attempt was answered `already_handed`: a 4xx answer to a call that a revoke met in flight leaves the attempt possibly handed, also when the session went idle and dropped the attempt's held entry before or after the revoke, so the receiver does not contradict an answer it remembers (PR #1735 review 4306466350, reviewer R9U-02, inbox/opencode/056). It remembers 4096 such answers, oldest dropped first; once one was dropped, a 4xx answer to a call it made is treated as possibly handed, a lapse rather than a `not_handed`. Until that report, or a resume answer, a fence or exit, a cancelled message stays held and keeps its evidence. A doorbell substitution is synchronous inside `chat.message`: the fetch that issues its attempts under the hub's lock is its final check. An aborted turn (the session idle with an attempt handed and not started) or a reverted prompt (`message.removed`) drops the attempt from the snapshots: a lapse, not a release, so the deck may repeat it, marked. The receiver remembers the attempts whose native call began or that it reported committed, so such an attempt is never reported `not_handed` afterwards and a revoke of it is answered `already_handed`, including one that races the commit receipt's publication (inbox/opencode/039, inbox/opencode/045, inbox/opencode/047). That memory holds 4096 attempts, oldest dropped first; once one was dropped, the receiver answers a revoke of any attempt it does not hold `already_handed` and reports no `not_handed` for it, since absence no longer proves the attempt was never handed (inbox/opencode/045). The attempts revoked here are remembered the same way, 4096 at most, so a late doorbell fetch or an outstanding approval cannot bring one back; because nothing bounds how many revokes arrive while a fetch or an approval is outstanding, dropping one voids every approval given before the drop, so a forgotten attempt a late fetch returns is held but not ready under an approval given before the drop; a fresh `may` can still make it ready (reviewer R9T-04). A receiver that starts from another's state (Pi's version replacement) keeps at most 4096 of each of these memories, the newest, and counts dropped called attempts as possibly handed. That fail-safe has a visible cost. It lasts as long as the receiver, watcher restarts included. A Cancel answered this way ends the message as possibly handed, an offer stays with the worker, and the attempt keeps its late-commit verifier until a commit or the generation's exit, where for an attempt that was in fact never handed no commit ever comes. Enough of those exhaust the evidence budget and show `deck messages paused` on both clients, which only an agent restart clears; restarting the watcher alone clears neither the receiver's overflow nor those verifiers. After the call began, only OpenCode answering it with a 4xx (its prompt route refuses before it accepts with 204) is a not-handed witness; a thrown error or any other failure is lost, for a marked repeat, and an offer stays bound (inbox/opencode/038, inbox/opencode/044). The callback's last synchronous check also re-reads the caller's own guards after the awaited grant — the TUI's target session and dialog, `--mini`'s root session — and drops the callback, `not_handed`, when they no longer hold (inbox/opencode/040).

**Reconnects.** A stream that ends decides nothing at once: no requeue, and the incarnation stays its slot's. With no snapshot for `POSSESS_TTL` (three keepalives) its attempts lapse. The next registration of the slot retires it and is sent its open attempts to resume: the same context (a respawned watcher, `--resumed`) answers `retained` for what it still holds and the attempt is rebound, with its caps, and no repeat; a reloaded context answers `unknown`, which fences the attempt and, once the clock's spool check finds no commit, gives one marked repeat on the same generation. With no registration within three `POSSESS_TTL`s of the close, the model retires the incarnation itself and fences what it held, so a Cancel can end those attempts, an offer stays bound, and a message nobody takes is `Uncertain` after the wait bound (inbox/boundary/021); the fenced attempts keep their verifiers until the clock has read the spool (inbox/boundary/028); the doorbell's tick counts such a scheduled repeat as waiting mail. A watcher whose plugin sends no snapshot for three keepalives (a stalled or dead event loop) closes its stream. A plugin that closes its watcher's input (dispose) starts none again.

**Lost revokes are sent again (r8k R8G-04).** A revoke line can be lost on its way: the attempt's incarnation has no link (its stream closed and nothing has registered yet), or its queue of waiting lines is full (`RECEIPT_SIGNAL_CAPACITY`, 64), where the line is dropped and the stream stays open. A line takes its room in that queue under the hub lock, as it is built, and holds it until `flush` writes it; a hand-out, or a doorbell fetch's `issued` caps, is issued only once its line has its room, so a pass that finds the queue full issues nothing and the mail stays waiting, and another pass cannot crowd out a hand-out already issued (auditor R9T-A02). Nothing else would send it again: a terminal message is no lapse candidate, and a stream is retired only by a replacement registration (which retires its predecessor, healthy or not, and answers through the resume) or by the clock after it closed. So a retained rebind sends the owed revoke to the new incarnation at once (`inbox/boundary/038`), and the clock sends every revoke still owed an answer again one ack-wait after it was last sent (`AttemptModel::revokes_due`, `inbox/boundary/039`); `Receipts::next_deadline` counts an owed revoke, so the clock runs for it even when the message is terminal (`inbox/boundary/040`). A revoke is owed while its attempt is revoked, not final, not waiting for a resume answer and not reclaimed; it stops only at the receiver's answer, a commit, a resume answer or its silence, the stream's retirement or exit (`inbox/boundary/043`). Neither a send nor an absence makes the attempt final (`inbox/boundary/041`). The clock's periodic resends are rate-limited to one line per owed attempt per ack-wait (60 s by default, none sooner on that path: `inbox/boundary/042`). A retained rebind is not: it sends at once whenever it happens and restamps the attempt's send time, so repeated registrations can send more than one line within an ack-wait. The evidence budget bounds how many attempts can be owed at once. It does not bound the number of re-sends: a live receiver that keeps sending snapshots and never answers a revoke is sent one per ack-wait for as long as it lives, and each such attempt keeps its evidence reserved. Enough of them exhaust the budget and show `deck messages paused`, whose remedy is restarting the agent.

**The adapter floor.** A generated plugin declares `ADAPTER_INTEGRATION` (2) on its stream and its doorbell fetch; an OpenCode stream or doorbell fetch declaring less or nothing is refused `adapter_too_old`, registers nothing, leaves the mail queued and silences the doorbell. When an OpenCode agent spawns (its agent type is OpenCode, or its command's first word is `opencode`, bare or path-qualified: inbox/boundary/018), the daemon regenerates the plugin from its own binary before the child starts, so the agent never loads a copy the refresh had not reached yet (inbox/boundary/025). A plugin pinning another live install keeps that pin (PRD #1487) unless this install is an eligible newer copy, which takes the pin over (issue #1637); a pin that is kept has its plugin rewritten around it only when the template declares an integration below the floor. So two installs that both meet the floor rewrite each other's plugin only through that takeover; a refresh that cannot write a file sets `refresh_failed` on the card until a registration proves the integration current. It also starts the readiness deadline (`ARM_DEADLINE`, 120 s; past it with no registration the card says `not_armed`, cleared by a later registration, which then gets the queued mail), and runs the capability probe off the executor: `<pinned> inbox wait --adapter-integration 2 --help` with a literal argv and a 5 s deadline, reading 64 KiB of each output stream and draining the rest; a CLI still running at the deadline is killed and reaped, and output another process still holds open then proves nothing. The deadline bounds the probe's return and the bytes it keeps, not its reader threads: a reader of a stream a descendant holds open stays until that descendant closes it. The pinned binary is the pane's absolute `DOT_AGENT_DECK_BIN` — the spawn's env overlay, else the daemon's own inherited value, an empty or relative overlay entry masking an inherited one — else the plugin's pin. Only clap's refusal, `error: unexpected argument '--adapter-integration' found` as the whole first line of stderr on exit 2 (a trailing carriage return and ANSI styling ignored, on every platform), sets `cli_too_old` (mail queued, doorbell silent); only a help line listing `--adapter-integration` on exit 0 is support; a timeout, an old help that exits 0 without the flag, or any other answer, a diagnostic in other words or another language included, sets nothing. A registration outranks the probe: a `cli_too_old` that arrives after one changes nothing, and a later registration clears one (inbox/boundary/017).

**The adapter floor for Pi (G6, G7, G10).** Pi's extension declares integration 2 on its stream and on its doorbell fetch (`--adapter-integration 2 --rx <rx>`). A Pi stream declaring less or nothing and a Pi generation's doorbell fetch without `--rx` are refused `adapter_too_old`, and a Pi generation's `get-seed` (`get_seed_withdrawn`, which since part 3's H5 takes nothing for any caller) is answered with no seed; each sets the out-of-date notice: nothing registers, no seed is served, the mail stays queued, and both clients' cards say the integration is out of date (inbox/boundary/030). When the daemon spawns an agent it identifies as Pi (`pi_spawn` in `src/agent_pty.rs`: its declared agent type, else the basename of its command's first word), it rewrites the extension before the child starts, off the executor, into the directory the child resolves: `PI_CODING_AGENT_DIR`, else `HOME`, each from the child's env overlay, else the daemon's own environment, a relative one taken in the child's working directory (`orchestrator_ext::refresh_for_spawn`, inbox/boundary/032). A write that fails sets `refresh_failed_pi` (`IntegrationNotice::RefreshFailedPi`, words `REFRESH_FAILED_PI`), and the daemon's `warn!` lists the target directory with its error. Pi is not a `CliAgent`, so the remedy names `orchestrator setup` run with the agent's `HOME` and `PI_CODING_AGENT_DIR`, never `hooks install --agent pi`, which does not exist. The capability probe chooses its binary the way the extension does (`inbox_probe_binary`): `DOT_AGENT_DECK_BIN` when absolute in the child's environment (the overlay, else what the daemon passes on), else the daemon's own binary, which the extension receives as `DOT_AGENT_DECK_EXE`; an OpenCode pin is never Pi's probe. The extension hands its receiver only an absolute path (`isAbsoluteOverride`, defined in `orchestrator.ts`), and the generated module runs only an absolute path to an executable file (inbox/pi/031), so `resolveDeckBin`'s bare-name fallback never starts a watcher: the spawn fails, nothing registers, the receiver retries on its backoff and the card says `not_armed` past `ARM_DEADLINE`. Two caveats, both accepted: a Pi started through a launcher the deck does not identify gets no spawn refresh, only the copy the daemon writes into its own default directory when it starts serving; and two decks of different versions that share one Pi directory overwrite each other's copy.

**What both clients show.** `InboxSummary` carries the card notices flattened beside the counts — `attention` items `{message_id, revision, kind, from_label, subject, task_id?}` with kind `uncertain`, `out_of_attempts`, `not_started` or `held_long`, `integration` (including `refresh_failed_pi`), `receipts_degraded`, `evidence_paused` and, since PRD #1666 part 3, `admission_refused` (the refusal code of a request the pane's current generation made for its own mail, present while mail waits for it; [hook-provenance.md, Inbox admission](hook-provenance.md#inbox-admission-the-panes-capability-and-the-decks-user-prd-1666-part-3)) — and an `InboxNotice` with `attention_update` carries them whole whenever they change. The TUI keeps them per pane (`AppState::inbox_attention`, `AppState::inbox_admission_refused`) and opens its picker on `i`, also for a refusal alone, which it shows whole above the rows; what the daemon raised for a pane before the TUI had its card, such as a `refresh_failed_pi` raised while the agent spawns, reaches the card through the daemon's account of the pane rather than through notices the TUI keeps: the card-surfacing `SessionStart` the daemon sends for each pane it starts a card for carries the pane's `InboxSummary` (`surfaced_inbox` metadata, which the hook ingress strips from producer frames), read and broadcast under the inbox lock its notices are sent under, so it covers every notice before it and none after; the first subscription and every resync take each listed pane's summary from a snapshot ordered with the stream (`SubscribeEventsWithSnapshot`, whose receiver the daemon opens and whose summaries it reads under that same inbox lock), where the daemon offers it — a daemon that does not predates the inbox. The startup hydration's own `ListAgents` reply is not ordered with the stream and is not read for inboxes. A notice for a pane with neither an account nor management is dropped. An account taken from a daemon summary takes no notice naming another agent generation: the daemon's next account of the pane establishes a new one. Besides the start and the snapshot, the daemon gives one whenever a new generation takes a pane, whatever started it (a first start, a `clear = true` respawn, `pane restart`, a re-created pane): the registry publishes the generation and then sends an `inbox_handover` broadcast with its `InboxSummary`, under the same inbox lock, so a client's account follows the replacement at its place in the stream and the replaced generation's late notices change nothing (auditor R9S-A01). Under that lock the hub first asks the registry whether the generation still holds the pane, and sends nothing for one a successor has been published over since, so a hand-over delayed past its successor's cannot take the account back (auditor R9T-A01). A client applies it to a pane it manages or already has an account of; an older client reads the kind as `Unknown`. An account built from notices alone ignores a notice naming one of the last eight generations it replaced. A notice for a message going back to the queue from being taken carries `requeued`, so a client whose account counted the message as taken does not count it again; the desktop refetches `ListAgents` on any inbox broadcast and lists the rows on the tile, each with its whole reason. The TUI picker gives the cursor's row the rows its whole reason needs before it windows the others, and `r` sends Retry only while that reason is on screen at a width that holds its longest word (`inbox_attention_retry_readable`); otherwise it answers `make the window taller…` or `make the window wider…` (`inbox_attention_retry_needs`) and sends nothing (status/025). The desktop list scrolls and has no such state. Words are `src/inbox_display.rs`, mirrored by `desktop/src/lib/inboxWords.ts` and pinned by `tests/fixtures/inbox-display.json`.

**Retry and Cancel.** The attach verbs `inbox-retry` and `inbox-cancel` `{pane_id, agent_id, message_id, revision, request_id}` answer on `AttachResponse.inbox_action` with `applied`, `stale`, `not_applicable`, `already_settled`, `retry_limit` or `unknown`. Clients send them only to a daemon advertising `inbox-actions` (`DaemonClient::inbox_action`, rule 18's second rung). They apply the model's compare-and-transition under the hub's lock: a press at a revision the message has moved past is `stale`; of two presses of the same verb at the same revision, the first applies and the other is answered `stale`, while the same `request_id` sent again answers as before. For a delegated task, its orchestrator gets `task delivery uncertain` once, `task delivered after all` if it then commits while a correction route for it is still held (see "A correction is possible, never promised" above), and `task cancelled` for a Cancel. Retry also applies to a `not_started` row, at the revision it was shown with ([Pi's not-started attention](#pis-not-started-attention-g3)); `not_started` itself posts nothing to the orchestrator, whose quiet-worker alert is unchanged.

### Pi: one receiver per process

Pi's extension (`pi-extension/src/index.ts`) keeps one process state on `globalThis` under `Symbol.for("dot-agent-deck.pi-receiver")` (`InboxProcess`): the generated receiver, the gate's records (`sent`, `passed`, `byId`, `committed`, `tags`), the attempts waiting for a session (`pending`), the current session (`current`, with a monotonic `token`), one serial `reportQueue` for status reports across instances, and the flags `disposed` and `notInDeck`. Every session instance Pi builds, `/new`, resume, fork and reload included, shares it. The reason is the shared receiver's memory: its stage reports (`reports`), the `correctable` hand-back and its `correcting` hold all assume that the receiver which witnessed a commit is the one that publishes it, so a commit seen in a successor session must reach the receiver holding that attempt's caps. This is not an isolation boundary between Pi sessions, which already share one process and environment; what it has to keep right is context and witness attribution within one generation.

- **The receiver outlives sessions.** Its `active()` is `!disposed && !notInDeck`, never "a session is current", so a watcher that exits unexpectedly respawns on its backoff even between sessions. `session_start` calls `receiver.ensure()`, which starts a watcher only when there is no child and no respawn pending; a healthy watcher is not registered again. `session_shutdown` touches neither the watcher's stdin nor its process. When Pi exits, the watcher's stdin closes and it drains (`DRAIN_WAIT`) and exits; delivery to the generation ends there. Watcher exit 3 (outside a deck, or missing capability) latches `notInDeck` for the process (inbox/pi/014, /029).
- **Session tokens.** Each `session_start` takes the next token and becomes `current`. Attempts are handed over from `pending`, oldest first and one at a time, while a session is current and the watcher is registered (`pump`; a session start or a registration resumes it). A hand-over captures the token and the receiver's epoch before its asynchronous `may`, and after the grant re-checks, with no await before `sendUserMessage`, that the same token is current, the epoch unchanged, the process not disposed and `receiver.ready(ref, granted)` holds. On a token, epoch or disposal mismatch it has made no native call: the attempt stays at the head of `pending`, uncalled, and the successor session or the next registration asks `may` again. A delayed `session_shutdown` clears `current` only if it is still its own, and still releases its own attempts: a `/new`'s passed ones `lost` and its unseen sends to `pending`, a reload's passed ones to the current session (inbox/pi/026). Tokens keep counting up across a version replacement, compatible or not, so no successor reuses an outgoing session's number.
- **No current session.** Attempts the receiver is handed are still taken (possessed, so the snapshot lists them and the daemon does not lapse them into a repeat) and wait in `pending`; the next `session_start` hands them over in order, each through a fresh `may`. With no successor the hold lasts indefinitely: not-started attention or `held_long` surfaces it, and Retry or Cancel (answered `revoked_ack`) are the recovery (inbox/pi/025).
- **Session replacements, as Pi 0.84.4 runs them.** `/new`, resume and fork tear the session down (`abort()`, `session_shutdown`, `dispose()`) and start a new runtime with an empty follow-up queue. So the outgoing instance's `session_shutdown` releases every attempt it passed that is uncommitted as `lost`, possibly handed, never `not_handed`, and puts what it sent but the gate has not seen back at the front of `pending`, uncalled, for the successor. The successor therefore calls `sendUserMessage` again for such an attempt: one attempt can be submitted to Pi more than once, while the tag check consumes the earlier submission at any gate, so it passes a gate once (inbox/pi/007). A reload keeps the same `AgentSession` and its queue, so it releases nothing: the reloaded instance takes over the outgoing instance's passed attempts (`reloadedFrom`), and a later `message_start` commits them. A reload whose shutdown arrives after its successor started hands them to that successor directly. Restoring a session emits no `message_start` (read in Pi 0.84.4's source), so no restored opener commits.
- **Commit witnesses.** A user `message_start` commits every attempt of the deck ids it carries that passed a hand-over point, or that was sent and reached Pi around the gate. Only the current instance, before its own `session_shutdown`, is a witness, and, while a version replacement drains, the reload's successor whose `session_start` waits on it; a commit never comes from a change of session (inbox/pi/012, /009, /028). An attempt of a deck id the process already committed (the same attempt handed out again, or a marked repeat the deck issued before it read the commit) is not handed to Pi again, from the stream or a doorbell fetch: it is reported `committed`, so its watcher publishes the receipt and the deck settles the message (PR #1735 review 4306950747). The hand-over checks this before it asks `may` and again after the approval, with no await before `sendUserMessage`, so a repeat whose approval was outstanding when the original committed is reported `committed` too (reviewer R9U-01, inbox/pi/007). This is best-effort duplicate suppression, not exactly-once: it holds while the message is still represented among the process's 4096 remembered committed attempt keys, carried across a reload or a compatible version replacement. Once the message's last remembered key is evicted, or in a process that starts without the memory (a restart of Pi, an incompatible replacement), a marked repeat can still run.
- **Status reports.** Every instance reports through the process-wide `reportQueue`, which a version replacement carries over, so the daemon receives reports in the order the handlers queued them across instances. A report from an instance that is no longer current is dropped. Its own `session_shutdown` Idle is reported while no session is current, ahead of the successor's reports, and dropped once a successor is current, here or in a replacement's process, whatever that successor's token: a delayed shutdown's Idle would otherwise land after the successor's Thinking and end its turn (inbox/pi/026). The successor's `session_start` reports its own Idle.
- **A version-mismatch reload.** A reload that evaluates a module whose `INBOX_VERSION` differs from the process state's replaces the receiver (`replaceVersion`), single-flight. A reload of the same version keeps the old receiver and the old module's closures, so a change to the inbox code takes effect in a running Pi only with a bump. The old state is marked disposed at once: it hands nothing more to Pi, asks for no grant and refuses those outstanding. Its watcher is drained and awaited (`receiver.drain()`: stdin closed, `SIGTERM` at 3 s, `SIGKILL` 2 s later), and the old receiver reads that watcher until it exits or the deadline passes; at the deadline the kill is sent and reading stops without an exit observed, so no successor starts before that point, but the drain does not prove the old process quiet after it: a message it hands out is held and joins `pending`, a revoke is answered in the receiver's state, and a commit witnessed meanwhile is kept as an unsent report, since the watcher's closed stdin takes no more controls. Only then does a new receiver start, registering `--resumed`. When the old state's `INBOX_STATE_VERSION` matches and its `INBOX_VERSION` is a receipt-stream version (2 is the first; version 1 never shipped, so a version-1 state is replaced as incompatible), its attempts, `pending`, reports, gate records, the reload's ownership of what passed and the report queue move over: the new receiver answers the deck's resumes `retained`, hands `pending` to the successor once it registers and publishes the kept reports with the authority the deck hands back for them. Otherwise it starts from `{forgot: true}` and answers resumes `unknown` and revokes `already_handed`: possibly handed, never `not_handed`, so the daemon's checked, marked repeat applies, and a commit witnessed during that drain is lost to the deck (inbox/pi/028). Delivery pauses for the drain. This is the outgoing version's code at work, so it holds for a replacement away from a version that has it. `drain()` is used only here; OpenCode's `stop()` is unchanged.
- **The extension from before the receipt stream.** Its process state (`Symbol.for("dot-agent-deck.pi-inbox")`) is found on first use, its instances retired and its watcher stopped, since the new receiver registers in its place.

**The fence at both hand-over points.** `sendUserMessage` is not where content passes to the model. Pi awaits its `input` handlers before ours runs, and a doorbell's transform returns after an awaited registration wait and fetch, so both points re-check, synchronously and with no await before they return:

1. *The tagged `input` gate* (`gate`): the hand-over carries a tag (`HAND_OVER_TAG_PREFIX`, `tagHandOver`). It passes, `transform` with the tag stripped and `handed` reported, only when the tag is one this process sent, the handler's instance is current and not shut down, the attempt was sent by that same instance (`Sent.token`), the process is not disposed, and `receiver.ready(ref, granted)` still holds for the approval the call was made under (epoch, age, not revoked, not already called). An unknown or older tag is consumed silently (inbox/pi/027); a failed check consumes the input and reports `not_handed` if the receiver still holds the attempt (inbox/pi/008, /032 a–c). A check that throws consumes too: the gate never returns undefined for our tag, which Pi would pass on to the model (inbox/pi/009). The handler returns the transform with no await of its own after the check; a busy hand-over's status report is queued in order and not waited for (inbox/pi/032 g–j).
2. *A doorbell* (`doorbell`): an input that is only the deck's doorbell line waits up to `DOORBELL_REGISTER_WAIT_MS` (5 s) for the watcher's registration, captures the session token, the receiver's epoch and `receiver.approval()`, fetches with `--adapter-integration 2 --rx <rx>` (so the daemon issues the attempts to this receiver), and takes what it fetched. It transforms the input in place into that content only if the same token is current, nothing is disposed or shut down, the epoch is unchanged and every fetched ref passes `ready` under the captured approval; otherwise it consumes the line and reports each fetched ref `not_handed`. With no registration in time, or nothing fetched, the line is consumed and the mail stays queued for the watcher; it is never passed to the model; the extension's doorbell fetch without `--rx` is refused for a Pi generation (inbox/pi/016, /032 d–f).

**What counts as `not_handed`, and what is `lost`.** `not_handed` is positive evidence that nothing reached Pi: a refusal before the call, a synchronous throw from `sendUserMessage`, the gate consuming the content, or an attempt sent but never seen by the gate once Pi is idle with nothing queued (`INBOX_UNSEEN_RECHECK_MS`, 30 s, or a settle after a later run started). Nothing after the gate is ever `not_handed`. An attempt past the gate is released `lost` by its session's `/new`, resume or fork shutdown, or by settle evidence (`settled`), a settle with no run active and nothing queued when: a run started since it passed (the run dropped it); `watchQueue` saw it queued behind the run that settle ends (Escape or a dequeue took it out of Pi's queue); or a `before_agent_start` prompt carried it, after Pi's refusal pattern (a settle while another run was active, then one with none) or with nothing queued. One still in preflight, or a Pi that cannot be asked, stays held (inbox/pi/010, /011). `lost` leaves the attempt possibly handed, and the daemon's checked, marked repeat decides.

### Pi's not-started attention (G3)

A preflight failure inside Pi, such as a provider with no credentials, happens after our gate passed the content and before any start report, and emits no settle. Nothing releases the attempt `lost`, possession keeps the daemon from repeating it, and without more the message would sit `✉ queued` with no notice. So the daemon raises attention instead: `AttentionKind::NotStarted`, card `✉ may not have reached the agent`, reason `NOT_STARTED_REASON`, with Retry and Cancel.

- **The line against `lost`.** `lost` needs positive evidence that the attempt left Pi — its session's `/new`, resume or fork shutdown, which releases it directly, or the settle evidence above, the `watchQueue` and `before_agent_start` cases included — and leads to an automatic, spool-checked, marked repeat. Not-started attention needs only the daemon's own clock and **never** repeats, issues or changes state: it is attention, recomputed on each tick (`AttemptModel::note_turn`, called from `tick_turn`), and only a user's Retry sends the message again. The orchestrator gets no separate notice. Both exist because neither covers the other: a message Pi took and never started, in a session that neither shuts down nor settles, gives `lost` nothing to fire on, and attention alone cannot justify a repeat that might run a message twice.
- **Scope.** Only attempts whose receiver slot is `Slot::Pi`. OpenCode never raises it.
- **The turn clock.** The hub keeps `st.receipts.turns: HashMap<AgentKey, TurnClock { busy, idle_since, seq }>`, apart from `gens`, so an edge never creates a spool-less, permanently degraded `Gen`. `AgentPtyRegistry::note_turn` returns `TurnSeen { seq, edge }` when it applied the edge to the live owner or kept it on a reserved spawn (`pending_busy`), with `seq` from a registry-wide counter; the daemon calls `InboxHub::note_turn` after the registry's guards drop but inside the same `AppState` write-lock section of ingest, so edges reach the hub in ingest order, and the hub ignores a `seq` at or below the clock's. The edges are the daemon's turn edges ([Doorbell guards](#doorbell-guards)): Started from the generation's own Thinking, ToolStart, Compacting or PermissionRequest, Ended from its Idle, a ToolEnd and a wrapper-classified event moving nothing. Started sets `busy`; only Ended while busy clears it and sets `idle_since`. A duplicate Idle, a session-start Idle, a registration or rebind, a keepalive and a watcher respawn move nothing. `note_inbox_spawn` seeds the clock with the registry's busy bit read at publication, so a Started from a reserved spawn is kept; a registration reads the clock and never resets it. An exit, or a reservation given up after an edge (`turns_abandoned`), removes the clock and records the key among the last `EXITED_TURN_KEYS` (1024) exited generations, which refuses a delayed edge for it while the key is still there (`forget_turns`).
- **The anchor.** `Msg::not_started_anchor` is set at the first *reported* possession of an attempt of the current delivery cycle (a snapshot listing it, never the issue grace) or its `handed` stage, and is not cleared when possession lapses across a watcher gap, so a respawning watcher can neither postpone nor re-arm the window. Commit, a terminal or latched state, or a Retry clears it; Retry records the attempts it leaves behind (`not_started_after_e`), and only an attempt issued after it anchors the new cycle.
- **Due and eligibility.** Due at `max(anchor, idle_since or anchor) + not_started_after`, evaluated only while the clock is not busy (`NOT_STARTED_AFTER`, 3 min; `DOT_AGENT_DECK_INBOX_NOT_STARTED_MS`). Eligible while the message is `Attempting`, not latched (so a Cancel's `HandedInert` never raises it) and its current attempt is held by a `Slot::Pi` receiver and not final. A Started, a commit or ineligibility withdraws it; only a real busy→idle re-arms it. Its due instant feeds `Receipts::next_deadline`, so the ticker wakes for it.
- **Projection and clients.** `notices()` projects it after Uncertain and OutOfAttempts and before HeldLong; a message both not-started and held an hour shows HeldLong. `uncertain()` is false for it and `retry_offered()` true. The TUI card counts `not_started` separately (`CardInbox`, 8 fields) with precedence uncertain → not_started → stalled/queued → delivered for the badge, and integration → evidence_paused → uncertain → not_started → held_long → degraded for the notice line; the desktop mirrors it in `inboxWords.ts`. Retry's guard accepts `state == Attempting && not_started == Some(revision)`: a picker opened before a Started withdrew the row is answered at its stale revision and nothing is issued (inbox/attempts/021, inbox/status/024).
- **What it can and cannot see.** It does not fire for a turn under way, a follow-up queued behind an observed turn, or slow boot before possession (that is `not_armed` or plain queued). It can fire for a long healthy preflight before the start reports, which is why the words say "may", and for a follow-up that stays uncommitted after its turn ends. A turn whose start reports never reached the daemon reads as idle, so the notice can appear while Pi is in fact working: it is attention from generation-level edges, not a health check of one message. Pins: inbox/attempts/020–023, /027, inbox/boundary/044, /045, inbox/status/023–025, inbox/pi/023 (TUI, stand-in Pi), inbox/pi/022 (real Pi, absent provider auth).

## Claude Code on receipts (PRD #1666 part 2)

Part 2's H1–H3 move Claude Code from the ack-wait to the receipt policy; part 3's H4 moves Codex's hooks and model-run `inbox fetch` on the same library ([below](#codex-devin-and-inbox-fetch-on-receipts-prd-1666-part-3-h4)). The code is `src/inbox_oneshot.rs` (the receiver library), `src/inbox_prompt.rs` (the prompt hook's commit), the one-shot rows of `src/inbox_attempts.rs` and `src/inbox_engine.rs`, and the hook-socket routing in `src/daemon.rs`.

**One-shot receivers.** A stream receiver lives as long as its agent; a one-shot takes one batch on one connection, hands it over, reports, and exits. Two slots hold them: `once_waiter` (Claude's `SessionStart`/`Stop` asyncRewake waiter, component `claude_waiter`) and `hook` (the `UserPromptSubmit` hook, component `claude_hooks`; since H4 also `codex_hooks`, and a model-run `inbox fetch` as `codex_hooks`, `devin_hooks` or `other`; at most `MAX_LIVE_HOOKS` (8) live per generation). `OneShotBatch` runs the sequence: ask `may` for every attempt of the batch and record when it asked; with nothing awaited after the grant, run the fence immediately before each block's first byte and write the blocks through a counting writer (`hand_over`); publish each attempt's receipt into the generation's spool (`publish`); and only then report on the connection (`controls`). A block is `NotHanded` only when none of its bytes was accepted or the fence refused it before its first byte; anything short of a whole block followed by a successful flush is `Possible`, which no later report can turn into not-handed. The caps stay inside `OneShotBatch`: the library puts them in none of the blocks, control lines, errors of its own or the batch's `Debug` output.

**What a written block means differs by slot.** For the waiter, a whole flushed block is `Handed`: Claude queues it as a `<task-notification>` prompt, and the commit comes later, from the prompt that carries it. The deck writes each attempt's caps to a caps file in the generation's spool, off the lock, before it releases the waiter's batch (`dispatch` stages it, `release` sends it), so the caps never travel on the waiter's connection, and the waiter and the prompt hook read them from there; an attempt whose caps file was not written is recorded not handed by the deck itself (R2-R01). The block's opener names the attempt (`[dot-agent-deck message <id> … delivery A.e`). For the prompt hook answering a doorbell, a whole flushed block of `additionalContext` is its commit, the strongest witness it has.

**`inbox_committed` and its commit-authority precondition.** The prompt hook reads every whole block the submitted prompt carries (at most `MAX_IDS`, 16), and for each named attempt reads its caps file, publishes the `committed` receipt on the attempt's commit cap, and names the attempt in one `inbox_committed` on the connection that asked the receipts question (`commit_attempts`). Nothing is acknowledged by id. The daemon admits the verb as it admits `ack`: token-attested for the pane it names and from the agent's own process tree (`mail_taker_admitted`). That is an in-tree, same-user authority, not proof that Claude's hook sent it, so what it may commit is bounded by the attempt's own witness (R2-A01): the attempt must be released by the deck (not withheld), must not be positively `NotHanded` (`AttemptModel::commit_admissible`), and must have its commit receipt on its own cap in the spool (`commit_candidates`, verified off the lock, then `commit_admissible` re-checked under it in `one_shot_committed`). A generation whose receipts the deck cannot read (no spool, or no scanner) is degraded already, and there the first two conditions alone decide. A caps file that is missing commits nothing, since that is no evidence the delivery did not happen and the attempt's own lapse decides it; one that is malformed or unreadable commits nothing and reports the generation's receipts degraded. A prompt naming an attempt that was never sent, or a raw `inbox_committed` naming a released attempt with no commit receipt, commits nothing (`inbox/claude/016`, `/023`).

**Possession (C-1 to C-4).** A one-shot attempt is fenced as soon as its connection closes, its waiter is superseded or a hook's hold (`hook_hold`, one ack-wait) runs out (C-2, C-3), because no control can come for it any more. A fenced attempt still keeps its verifier: a once-waiter attempt is possessed while the generation's turn clock (fed by the agent's own hook reports) reads busy, and for one ack-wait after the later of its issue and the end of the last turn (C-1), since Claude can hold a queued notification for a whole busy turn; and an approval the one-shot was granted stays usable for `grant_ttl` (one ack-wait) after it asked (C-4). Once neither holds and the spool check finds no commit receipt, the attempt lapses and the message gets a marked repeat on the same generation; once the automatic repeats are spent, it is `Uncertain` and both clients offer Retry and Cancel (`inbox/claude/017`). A notification queued behind a long quiet tool commits once, with no repeat (`inbox/claude/018`). What is left: a process paused between its fence and its write for longer than `grant_ttl`, or a notification Claude submits more than one ack-wait after its turn went idle, can deliver after the verifier is gone. That loses the sender's late correction, not the message, which is already terminal or on the lapse path.

**The receiver floor and routing.** Every one-shot of this binary declares `HOOK_INTEGRATION` (1). A one-shot request without it, or below it, comes from an older `dot-agent-deck` named in the agent's hook settings, and is refused before anything is issued (`refuse_hooks`): nothing registers, the mail waits queued, the doorbell stays silent, and the card's integration notice is `hooks_too_old` with the deck's own `hooks install` command for that agent when it can compose one (`CARD_INBOX_COMMAND_METADATA_KEY`; the floor remembers whose hooks it refused, `Floor::hooks_too_old_agent`). Since part 3's H5 a hook fetch on the legacy verb meets the floor at once whatever the generation's type (`legacy_verb_hook_fetch`); the type only chooses which agent's `hooks install` the card names (`legacy_hook_component`: the spawn's type, else the one the hooks reported (R2-R03), else an announced Claude component; Claude Code's for a fetch declaring the integration; none when the deck cannot tell). It is a hint, not authentication of the agent or its hooks.

**No routing hold.** Until part 3's H5 a hook fetch with no declared integration from an untyped generation was held for up to 2 seconds (`IngestOrder`, `HOOK_ROUTE_WAIT`, R2F-R02) until its `SessionStart` could say whether it went to the refusal or to the legacy fetch. With the legacy fetch withdrawn both ways are a refusal, so it is refused at once, and a current hook is served without waiting either (inbox/claude/024).

**Explicit `ack` on a handed-out message** (`CONTRACT_BREAKS` entry `1666-explicit-ack-requires-handed-attempt`) settles the newest attempt that may have been handed, and is refused `unknown` when every current attempt is recorded `NotHanded` or was withheld. This applies to every receiver. A message with no attempt answers `unknown` while it is still queued, never handed out (`1666-legacy-inbox-delivery-withdrawal`, inbox/boundary/071); a settled, claimed or undeliverable one answers as the store does, so a repeated ack is already acknowledged and a late ack of a copy out of attempts still corrects its sender.

The receipts capability each one-shot asks for before it takes or commits anything, and the mixed installs it closes, are under [Contract and validation](#contract-and-validation).

## Claude version gate and framing

`CLAUDE_ASYNC_REWAKE_MIN` in `src/hooks_manage.rs` is 2.1.296, the measured release, not a claim that older Claude versions lack asyncRewake. Unknown or lower versions get no waiter. SessionStart announces native wake only when the installed Claude settings contain the deck's SessionStart waiter; without it, including an installation below the version gate, no native announcement delays the doorbell. The waiter timeout is 86,400 seconds; `/clear` may leave several waiters, so inbox hand-over is claim-once. Once waiters poll their agent ancestry for orphan exit; stream watchers exit when their owning integration closes stdin.

The waiter settings include `rewakeMessage` and `rewakeSummary`. Both keys are `@internal` in Claude Code's schema, observed in 2.1.294–2.1.296, and are written only under the same 2.1.296 gate as asyncRewake. `rewakeMessage` explains that this is a deck message rather than a hook error; `rewakeSummary` is `✉ dot-agent-deck message`. Reinstall consolidates existing waiter entries and refreshes these values. If upstream removes the keys, default hook wording may return: retain session framing that agrees with Claude's automated-notification label.

`SESSION_FRAMING` is delivered through Claude's `SessionStart` context and doorbell injection; `AGENT_FRAMING` is the agent-neutral counterpart used by CLI fetch and Codex. They identify the deck as the workspace the user started, explain that work arrives as automated messages rather than fresh user approval, tell the agent to act on an id once, and distinguish UNTRUSTED reports from instructions. Do not add fixture-only authorization to live tests: the production framing must suffice.

Each block starts `[dot-agent-deck message <id> from <sender>]`, then `Sent by: <provenance>.`, and ends `[end of dot-agent-deck message <id>]`. Provenance comes from the attested sender or a deck-generated origin, not the worker's text. Agent-authored reports carry an inner UNTRUSTED fence. Forged framing tokens in content must be defused after normalizing text. Budget truncation must retain the enclosing fences and a safely rendered path to the full body when one is provided.

Before posting a message whose body cannot fit the tightest hand-over budget, the daemon saves its full content to an exclusive, owner-only file in the recipient's working directory under `.dot-agent-deck/`, falling back to the deck state directory. Untrusted content keeps its report fence and has forged message markers neutralised. The delivered excerpt names the saved file using an inert location description. If neither location can save it, the post is refused and nothing is posted; an acknowledged excerpt must not silently discard the rest of an unsaved body. A delegated task is saved the same way, to a file written once for that message; `worker-task-<role>.md` is a convenience copy that the next delegation to the role rewrites, so the message never names it (PR #1735 fifth review, N6). The tightest budget is the room Codex's tighter hook envelope leaves in its 6000-byte JSON line around the framing, counted JSON-escaped (`tightest_hand_over`, from `inbox_prompt::json_room`, the same computation the hooks send as `max_json_bytes`), and the body is measured as the hooks can print it at worst: after its separator, as a marked repeat, with the longest attempt opener. So a body heavy in quotes, backslashes or control characters that fits in plain bytes but not escaped is saved, and every cut block names its file (inbox/boundary/069). The deck's own posts save on the calling thread, handing the async worker's other tasks to another worker while they do (`inbox_hub::off_the_executor`); publish and offer save on the blocking pool.

**How long a saved body is kept (PR #1735 fifth and sixth reviews, B-05 and B2-01..B2-04; `src/inbox_spills.rs`).** The hub's `SpillLedger` tracks only the files the deck minted for accepted posts (`MintedSpill`, handed over with `InboxHub::own_spill`, or to `post_reserved_delegate` for a delegated task, which tracks and holds it under the lock that inserts the task, so an exit or `work-done` cannot retire the task before its hold exists (PR #1735 seventh review, B3-01)); a `spill_path` a caller supplied is never tracked or removed. A tracked body is kept while its message is live. A delegated task's body is also held after its acknowledgement, until the task is retired: `retire_delegates_locked` (a supersession or a `work-done`) releases the pane's task bodies whose messages are no longer live, and `agent_exited` releases the exited agent's. Serial delegation supersedes the previous task, so a worker pane normally holds one such body at a time. A released or never-held body settles at the first tick that sees its message terminal or gone, and is then kept for `DEFAULT_SPILL_RETENTION` (24 hours). Settled bodies past `DEFAULT_MAX_SETTLED_SPILL_BYTES` (64 MiB) are reclaimed oldest first, but only those settled at least `DEFAULT_SPILL_PROTECTED_GRACE` (1 hour) ago; when everything over the bound is within its grace the bound is exceeded rather than a body removed. Live and held bodies do not count against the bound. A removal that fails (other than the file already being gone, or the path no longer matching the deck's naming) goes back into the ledger and is tried again at the next tick, logged once. So does a path whose directory or file cannot be looked up, say for want of search permission: that is not taken for a mismatch, and a takeover keeps such an entry rather than filtering it out (PR #1735 seventh review, B3-02).

Each daemon run keeps an inventory under `<state_dir>/inbox-spills/`: a lock file `run-<unique>.lock`, created as `.pending-<unique>`, locked with `File::try_lock` and renamed into place, held for the whole run and never replaced; and a JSON inventory `run-<unique>.list` (`{"version":1,"spills":[{"path","bytes","settled_unix_ms"}]}`, where a path that is not UTF-8 is recorded as `path_raw` instead: the hex of its bytes on Unix, of its UTF-16 code units on Windows), replaced whole on every change of the ledger by writing `.pending-<unique>.list`, syncing it and renaming it over the old one. The hub writes it outside its own lock; a write that a newer one overtook is skipped. `settled_unix_ms` is the wall-clock settlement time, absent while the body is live or held. A starting daemon takes over every inventory whose lock file it can lock: an entry with a recorded settlement keeps its retention from then (removed at once if it ran out), and an entry without one gets a fresh retention from the takeover, which this run's inventory records so a later restart does not grant another. The taken-over lock file and inventory are removed (inventory first, lock last, under its lock) only once this run's inventory has been written with what they held (`TakenSources::release`); otherwise they stay for the next start. An inventory that is not a regular file (opened `O_NOFOLLOW | O_NONBLOCK` on Unix, so a FIFO cannot block the start), is larger than 16 MiB, does not parse or has another version is left in place, logged. A `.pending-` file is removed once a minute old and nobody is using it: a lock file still being created is checked by locking it, and an inventory still being written, `.pending-<unique>.list`, by its run's lock file, never by locking the inventory itself. On Windows a lock is mandatory, so a lock on a file another handle reads or writes fails that read or write; no path here locks a file that any handle reads or writes.

Removal is limited to a tracked path matching the deck's naming: a regular file named `inbox-message-<deck>-<unique>.md`, directly inside a `.dot-agent-deck` directory that is not a symlink, checked by path just before `remove_file`. That is a check of the path's shape at that moment, not of the object the deck created: a process that can rename entries in the project's context directory can still put another regular file at a tracked path and have it removed, or race the parent check. Pinning the minted file's identity and deleting relative to a validated directory handle is the U2 hardening listed for a follow-up issue.

The ledger is the one thing that deletes a saved body once its post was accepted and the body tracked; `MintedSpill`'s drop removes the body of a post that was refused, or whose body was never handed to the ledger. The coordination sweep that runs when an orchestrator context is published (`sweep_coordination_files`, `src/orchestrator_context.rs`) deletes `.md` files in `.dot-agent-deck` by age, and `is_sweepable_coordination_name` excludes every `inbox-message-*.md` name, any deck's, so it cannot delete the full body of a message that is still queued or a task that is still running (RB2-02). The other deletion paths over that directory remove only names they created or recognise as orchestrator contexts (`withdraw_published_context`, `remove_ended_orchestration_context`, `remove_created_file`, the mirror's temp file). Removing a whole worktree removes its `.dot-agent-deck` with it. The cost of one owner: a saved body whose inventory was lost, or whose deck's state directory is never started again, is not reclaimed by anything.


## Retired delivery interfaces

S12 removes `delegate_retry`, `submit_echo`, `prompt_delivery`, `WriteAndSubmit`, `SubmitText`, guarded task-body sends, provisional prompt confirmation, readiness buffers, the seed fallback and the draft cap. `get-seed`, which outlived S12 as an inbox compatibility alias, was withdrawn by part 3's H5 ([below](#withdrawn-legacy-delivery-prd-1666-part-3-h5)); `--reports-prompts` is a hidden no-op. `ack d-...` returns `unknown`: only inbox message ids can be acknowledged, and the former `stopped`/`not_pending` delivery outcomes are gone. Human input from both clients uses `WriteInput`.

The daemon warns at startup for each set entry in `REMOVED_DELIVERY_SETTINGS` without logging its value. The removed reuse debounce and desktop seed buffer have no effect either.

### Withdrawn legacy delivery (PRD #1666 part 3, H5)

Every receiver is on the receipt policy, so H5 withdrew the legacy delivery policy and refuses each way an older `dot-agent-deck` took mail under it, taking nothing and acknowledging nothing (`CONTRACT_BREAKS` entry `1666-legacy-inbox-delivery-withdrawal`; inbox/boundary/073 through the real daemon):

- **A plain `inbox_fetch` with no stream bound** (`handle_inbox_fetch`), whatever its `ack`. A CLI fetch is refused `cli_too_old` (`CLI_FETCH_TOO_OLD`). An agent hook's fetch on that verb meets the one-shot floor at once (`legacy_verb_hook_fetch`): refused `hooks_too_old` below it, the card naming that agent's `hooks install` (`legacy_hook_component`), and served on receipts at or above it. An OpenCode or Pi generation's doorbell fetch without `--rx` stays `adapter_too_old` (`old_adapter_doorbell`, which also covers an announced OpenCode component now). The stream-bound doorbell substitution (`--rx`) is unchanged.
- **A once `inbox_wait` from Codex's, Devin's or an unknown component**: refused `unsupported` (`WAIT_UNSUPPORTED`) before anything arms (inbox/boundary/072). Claude Code's waiter is served on receipts at its floor; a stream from a non-receipt component stays refused (inbox/boundary/036).
- **`get_seed`**: answered `{"seed":null,"refused":"get_seed_removed","error":…}` for every caller, admitted or not, so the answer says nothing about the pane (`GetSeedResponse::withdrawn`); a Pi generation's card still says to restart the agent. The `get-seed` subcommand is gone; `GetSeedRequest` and `GetSeedResponse` stay as decode-only wire, the new fields additive.
- **An explicit `ack` of a message never handed out** (queued, or an offer assigned but not handed out): `unknown`, nothing changed (inbox/boundary/071).

What went with it: the store's ack-wait (`MessageState::Fetched` has no deadline; `Inbox::next_deadline` carries only claims and unfetched offers' assignments), `Inbox::fetch`, `fetch_acked`, `requeue_consumer` and `redeliver`; the hub's legacy waiter (`arm`, `disarm`, its dispatch loop and per-agent cap: a receipt once waiter supersedes the older at once, and live hook receivers are bounded by `MAX_LIVE_HOOKS`), its fetch wrappers and `fitting`; `AssignmentOwner`; the hooks' id-ack retry and the CLI's settle-by-id; and the routing hold. Kept: the waiter map, its slot pool and `armed`, receipt closure, offer claim expiry, explicit `ack`, and the late-ack memory (`LATE_ACK_*`), which a commit after a message ran out of attempts still corrects its sender and card through. `AckHow::{PromptObserved, HookHandover, FetchedByCli}` stay as decode-only spellings, so an older daemon's `ListInbox` history decodes (inbox/boundary/070); no settlement produces them. The e2e-only `DOT_AGENT_DECK_INBOX_TEST_HOOK_INTEGRATION=none` knob still makes this binary send the legacy verbs, to stand in for an older one.

## Doorbell guards

The only automatic text typed into an agent's composer is the fixed doorbell: ` dot-agent-deck: message <id> waiting, run: dot-agent-deck inbox fetch`. It contains no task body. Eligibility requires queued work, no armed consumer, an elapsed native-arm grace, a hook-reported idle moment, and no unsent human draft. Unknown status, busy agents, permission prompts and unknown dialogs hold it. The guard applies to input from either client; no draft-deferral cap overrides it.

**Escapes and turns (r8k R8G-02).** The draft guard's one exception is a run of the user's Escape keys and nothing else (`DraftTracker` in `src/draft_deferral.rs`): like a draft it holds until a submit or the user's clear, and it can also be released by the end of a turn the daemon observes after the keys reached the PTY; the ambiguous case below keeps holding. A turn starts with a work report from the pane's own generation — Thinking, ToolStart, Compacting or PermissionRequest that is not daemon-authored, not a subagent's and not one `dot-agent-deck wrap`'s output classifier produced — and ends with that generation's Idle, again not a classified one. A ToolEnd starts nothing, because one arriving after its turn's Idle would open a turn the next Idle ends, releasing a menu's Escapes (`inbox/doorbell/030`), and the daemon cannot tell it from the first report of a turn whose start it missed; so a turn whose start report is lost or switched off releases nothing when it ends, and its Escapes hold until a submit or the user's clear (the Enter recovery below). A classified Idle ends nothing, because a wrapped Codex's quiet output is not its hooks reporting the turn over (`inbox/doorbell/029`). `AgentPtyRegistry::note_turn` applies an edge only while its generation is the pane's live owner (r8g R8G-01, `inbox/doorbell/020`), and keeps the edge of a spawn reserved on the pane but not yet published until publication carries it onto the fresh stream (`inbox/doorbell/025`); a Started edge creates the pane's stream, so a first turn reported before any input counts (`inbox/doorbell/024`). An Idle with no turn under way releases nothing: OpenCode's duplicate Idle (`session.status: idle` and `session.idle`) cannot release Escapes that opened a menu on an Idle agent (`inbox/doorbell/021`), and an agent with no hook-reported busy edge (a wrapper-only agent, or Codex with untrusted hooks) has no turn end to release on, so its Escapes hold until a submit or the user's clear, which the user docs say. The end of a turn is ordered against each PTY write that carried the bytes, partial writes included: the writer thread reads the pane's turn count under the input-state lock right after `write` returns, holding no lock across the write itself (it can block for as long as the agent does not read, issue #525), and the record applies a turn end counted after that reading (`PaneInputState::settle_written_bytes`, `inbox/doorbell/022`). An Idle ingested between the write and that reading may have come before the bytes reached the agent, where Escapes open a menu, so it is not applied and the Escapes hold (`inbox/doorbell/023` for an Idle before the write, `inbox/doorbell/027` for one between the write returning and that reading): the ambiguous window is decided towards holding. That is a best-effort policy over bytes and hook reports, not an interrupt-liveness guarantee. A genuine interrupt whose Idle is ingested inside the window — the agent read the Escapes and ended its turn before the writer thread took the input-state lock — holds the doorbell with no time bound, until a later turn of the pane's own agent ends, the user submits or clears the box, or another agent takes the pane; the user docs give that recovery (close any menu, press Enter in the empty input box, once more if needed, since an Enter straight after an Escape reads as Alt+Enter). The trade is deliberate: releasing in the window would type the doorbell line into Claude Code's rewind menu or Codex's backtrack menu whenever the Idle really came first, where it can pick an option the user never chose, while a held doorbell is visible and recoverable. No lock is held across the PTY write to close the window. A publication retires every writer still on the pane before it resets the pane's stream, so a write a predecessor that exited on its own had taken but not yet recorded neither feeds its successor's stream nor settles it against the predecessor's turn count: the count is per stream, not an identity (r8k B01, `inbox/doorbell/028`). Split Escapes pair only within one turn (`inbox/doorbell/026`). The order is the one the daemon observes, the PTY write against the hook's arrival, not the agent's own read: an agent that finished a turn on its own and emitted Idle before reading Escapes the daemon had already written has those Escapes read as the turn's interrupt. That is the observation boundary of a tracker outside the agent, not menu safety: bytes the PTY accepted are no proof of when, or in which state, the agent read them.

Codex additionally requires a recognised empty composer on screen, so an Enter interpreted as a newline does not cause the next ring to submit the user's draft. The one non-empty composer the doorbell writes to is one showing the exact line it last typed into that pane, message id included, left unsubmitted because Codex did not take that line's Enter. Two such states were seen live on Codex 0.160.0: the Enter was dropped, leaving Codex's cursor right after the line (`inbox/codex/013`), or, under CPU pressure, the Enter became a newline in the composer, leaving the cursor on the empty row directly below the line at the composer's indent (`inbox/codex/016`). In either, the next ring, or the cleanup once the message leaves `queued`, sends its bare CR alone, which submits the line, and types no second line on top. A ring that only flushed keeps the line recorded, so if Codex swallowed that CR as well, the next ring flushes again (`inbox/codex/017`). The record is dropped when the cleanup CR goes or a ring types a new line, and after that the line gets no byte (`inbox/codex/015`); a doorbell-shaped line naming another message gets none either (`inbox/codex/014`). That can be after the message the line names has left `queued`: while other work is queued, a ring due for it is sent in place of the owed cleanup, and if that ring only flushes, it keeps the record (`inbox/doorbell/018`). So while a frame matching the recorded line stays on screen and a message stays `queued`, each due ring the guards admit sends one lone CR, with no fixed total. That is deliberate: the flushed line runs `inbox fetch`, which serves whatever is queued, and dropping the record there would leave the remaining work behind a stranded line the deck sends no byte to. A flush that Codex also takes as a newline leaves the line above two blank composer rows with the cursor on the second, which the recogniser does not match, so the flushing stops there (`tests/codex_composer_guard.rs`); that holds for that rendered layout, not as a guarantee about how a renderer draws it. The match is on what the screen shows, not proof of where the text came from: a process that controls what the pane renders can draw the exact line and cursor, and a person can type the line, and either earns the flushing CR, again on each due ring for as long as the record and the queued work last, and each CR goes to whatever then owns the pane's input. The agent-identity, draft and admission checks still apply to it. Codex hides its `? for shortcuts` hint while the composer holds text, so that recogniser finds the composer from the bottom of the screen rather than from the hint. If Codex changes its UI and the recogniser stops matching, idle ringing waits; a user-started turn still enables the Stop hand-over. Native arm grace prevents startup ringing before a component has had time to connect. Doorbell retries have their own schedule and do not increment inbox hand-over attempts.

**Stalled wake (PR #1735 fifth review, R5).** The doorbell's tick also keeps a `StallClock` per agent generation. It runs while messages are queued, no native component is armed and the agent's status does not explain the wait (Thinking, Working, Compacting, WaitingForInput and Blocked do; Idle, Error and no status do not), and starts again when the oldest queued message changes. After `DOT_AGENT_DECK_INBOX_WAKE_STALL_AFTER_MS` (120 s by default) it calls `InboxHub::set_wake_stalled`, which records the oldest message, sets `InboxSummary.wake_stalled` and broadcasts an `InboxNotice` for that message with `wake_stalled: true` and `wake_update: true`. A notice with `wake_update` reports the stall and nothing else (PR #1735 fifth review, B-03 and B-04): the message it names did not change state, its `state` repeats the state that message is in, and a client must not count it as a message event. Every change of the stall is sent as one, its end included (`wake_stalled: false`), so a client seeds the stall from `InboxSummary.wake_stalled` when it hydrates and follows these notices from there. The TUI applies one by setting the card's stall alone, bypassing `PaneInbox::apply`; the desktop refetches the pane's inbox on any `BroadcastMsg::Inbox`, so it reads the stall from the summary without interpreting the flag. A client that predates `wake_update` treats such a notice as an ordinary state notice for that message; inside the unreleased protocol 11 break that is a refinement, not a separate compatibility break. Both clients then show `✉N waiting to wake: send it a prompt` (`inbox_display::WAKE_STALLED`, `WAKE_STALLED_HINT`, pinned with the desktop by `tests/fixtures/inbox-display.json`). It clears when that message leaves `queued`, when the agent starts working, or when the agent exits. It is a card line, not a status: an `Error` status would itself stop the doorbell, which rings only an idle agent. It covers every wake path, decided from what the inbox and agent report rather than why a ring was held, and does not loosen any doorbell guard.

Eligibility is revalidated under the PTY writer before each automatic write step. A per-pane admission epoch changes when the agent, doorbell-relevant status, writability or wrapper fork changes, invalidating a previously scheduled ring; an armed consumer also cancels a ring.

**Generation readiness and the message fence (PRD #1666 part 2).** Found on the released 0.47.0: after a `clear = true` respawn the doorbell could type into the new Claude Code before its prompt was up, because the card's Idle came from a placeholder or the shell monitor rather than from the agent. The doorbell now reads the generation's own readiness (`AppState::doorbell_readiness`, `ReadinessLevel`), kept apart from the Idle its card presents: `Unproven` (nothing from the generation's own hooks) is rung only through an agent whose writer recognises its empty composer on screen (Codex, `has_doorbell_composer`); `StartedOnScreen` (its own `SessionStart`, from an agent that posts it before its prompt is up: Claude Code) is ready once the writer recognises that prompt (`AgentSpec::doorbell_ready_screen`); and `Ready` is its own Idle, or its own `SessionStart` from an agent with no ready screen to wait for. A Claude Code whose prompt the deck does not recognise therefore gets no first doorbell until it reports Idle, which the user docs say with the remedy (type the first prompt, or press Enter in the empty box). An admission still holds for a write only at the same event count and no lower readiness (`DoorbellAdmission::still_holds`). Before each write step — the line, then each Enter — the writer re-checks that the message the line names is still in its generation's ringable queue and that no human input arrived, and stops on either even while other messages wait (`inbox/doorbell/*`).

**Accepted residuals (PRD #1666 part 2 G-fix review).** Two windows stay open by decision, and the user docs are worded to them. First, the check-to-write window: each step's recheck of the selected message (still in its generation's ringable queue), of human input and of the admission epoch happens before that step is handed to the PTY writer, and nothing revokes a step already handed over, so a fetch, an acknowledgement or a keystroke that lands between the last check and the write lets that one step through; a payload is one slice, not a per-character check. Closing it would need an execution-time write permit, and no hub lock is held across a PTY write to buy it. The separate cleanup CR is its own policy and can follow a message's settlement by design. Second, generation readiness is in daemon memory only (`AppState::pane_doorbell_ready`): a daemon that starts holding a generation it did not see start — a new `AppState` across a handover — has it `Unproven`, which withholds the doorbell (fail-closed) until that generation reports again: its own `SessionStart` (for Claude Code, plus its recognised prompt box) or its own Idle. No age fallback is applied. The `RestartDaemon` path stops managed agents before its successor starts, so it does not create this state; the residual is for any path that keeps a generation alive across a fresh `AppState`.

## Contract and validation

This change moves `PROTOCOL_VERSION` from 10 to 11. The semantic compatibility marker and `changelog.d/1666.breaking.md` must remain paired under rule 12. `SessionSnapshot.delivery_notice` and inbox status summaries are additive; older daemon hook behavior can omit the concise deck-message prompt on the card because the newer hook clears raw message text. Both clients must retain the not-delivered notice through attachment and resync. The Pi slice adds the `not_started` attention kind, the eight-field card value and the `refresh_failed_pi` integration notice inside the same version 11, which `main` (at 10) has not shipped, so they need neither a further bump nor a `CONTRACT_BREAKS` entry. The `cross-version` CI job pairs the previous release (protocol 10) with this branch (protocol 11), so what it records is the intended protocol refusal: the attach is refused and no delegate or hook scenario runs. That refusal is the rule 12 outcome the PR records; it is not a cross-version run of these stream semantics, and there is none, since no released build speaks them.

**Part 2 (Claude Code on receipts) moves `PROTOCOL_VERSION` from 11 to 12.** Version 11 shipped in `v0.47.0`, so nothing in part 2 rides it. The bump is for one attach-wire shape change: the integration notice gained `hooks_too_old`, a new value of an enum a 0.47.0 reader cannot decode, carried by the `inbox` and `inbox_handover` broadcasts and the agent record's inbox summary. The meanings that moved behind the unversioned hook socket are two fresh `CONTRACT_BREAKS` entries with their part-2 prose in a new `changelog.d/1666.breaking.md`: `1666-claude-one-shot-receipts` (the once-waiter and prompt hook as one-shot receivers, the receiver floor, exact commits, marked repeats) and `1666-explicit-ack-requires-handed-attempt` (an `ack <id>` of a receipt-owned assignment settles the newest attempt that may have been handed, and is refused `unknown` when every current attempt is recorded NotHanded or was withheld, for OpenCode and Pi too; a receipt-owned assignment with no attempt, and an unowned or legacy-owned message, still take the legacy `ack`). Part 1's `1666-inbox-replaces-typed-delivery` stays; the list is append-only.

The hook socket's skew is closed on that socket, because a one-shot CLI runs no attach handshake. In each direction:

- **An older hook against this daemon.** Its legacy `inbox_wait` or `inbox_fetch` without `hook_integration` meets the `HOOK_INTEGRATION` floor (`hooks_too_old`, card names that agent's `hooks install` command when the deck knows the agent). Since part 3's H5 this holds for every generation, typed or not, and the hook takes nothing ([Withdrawn legacy delivery](#withdrawn-legacy-delivery-prd-1666-part-3-h5)).
- **A newer hook against an older daemon.** Every one-shot (the waiter, the prompt hook's doorbell fetch, `inbox_committed`) first sends `inbox_receipts` on its own connection and needs `one_shot_receipts >= ONE_SHOT_RECEIPTS` in that same connection's answer, never a cached one, before anything else. The wait and fetch then go on `inbox_receipt_wait` / `inbox_receipt_fetch`, verbs a 0.47.0 daemon cannot decode, so it cannot hand them mail on legacy terms. An older daemon answers the question with nothing. `RECEIPTS_ANSWER_WAIT` (5 s) is each question's socket-wait budget: the connect's wait for an accept (a full accept queue included), writing the question and waiting for the answer. The deadline is checked around each socket wait and again after each line is received, so neither keepalives nor a line taken just after the deadline can carry a late answer past it; the reader queues at most `MAX_QUEUED_LINES` lines and holds one more while it waits for room. When the budget runs out before an answer (`Opened::TimedOut`) the one-shot takes no mail, publishes no receipt, sends no commit, prints `RECEIPTS_TIMED_OUT` on stderr and exits 1, which Claude Code shows the user. That notice says the deck did not answer in time, that no message was taken and the messages stay queued, and that an older daemon does not answer at all, without calling either cause the likelier: a slow daemon that serves receipts and an older one look the same from the hook. The commit's own timeout prints `RECEIPTS_COMMIT_TIMED_OUT` instead: the waiter that wrote the block the prompt carries already took that message, and it may be held as an issued attempt rather than queued, so that notice says only that this hook confirmed nothing and took no further message. A deck that answers without the capability (`Opened::Unsupported`) gets `RECEIPTS_UNSUPPORTED`, which says the daemon is most likely older; it too takes nothing and exits 1. On the commit's connection (`Committed::Withheld`) it gets `RECEIPTS_COMMIT_UNSUPPORTED` instead, and a lost commit connection (`Committed::Lost`) `RECEIPTS_COMMIT_CONNECTION_LOST`: like the commit's timeout, neither says no message was taken, since the prompt carries one the waiter took. That diagnosis is kept for a real answer: a connection that ends before any answer, a line that cannot be read, or a question write that fails for another reason than running out of time (`Opened::Lost`; on the commit's connection `Committed::Lost`) is no evidence of the deck's version (a supporting daemon that stops or restarts mid-exchange lands there, while a 0.47.0 daemon keeps the connection open and times out), so it prints `RECEIPTS_CONNECTION_LOST` (the commit, `RECEIPTS_COMMIT_CONNECTION_LOST`), which says the connection was lost before the deck answered, that no message was taken (the commit's: that the message in the prompt was not confirmed) and no receipt confirmed, and to check the daemon with `daemon status`, and exits 1. When the wait or the fetch fails before anything is taken, the mail stays queued on that daemon for a matching receiver, or, for a message not owned by receipts, a legacy `inbox fetch`; a commit that fails leaves the prompt's message as the waiter's attempt left it, possibly an issued attempt rather than queued. A socket whose connect is refused with a permission error (a listener running as another user, which the IPC client's peer check refuses, or the socket's mode or a directory above it denying this user) is asked nothing, since the question carries the token: the one-shot prints `RECEIPTS_FOREIGN_SOCKET` and exits 1. It is fixed text that names neither the path nor the uids, asserts neither cause over the other, and gives the remedy for each: point `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` at the user's own deck, or fix the permissions of the socket and the directories above it, the default endpoint included. The waiter asks once within the budget. Claude's prompt hook shares one budget of the same length (`prompt_receipts_wait`, from one absolute deadline set when the prompt arrives) between its commit and its doorbell fetch: the commit's question and exchange and the fetch's question, request and reply. Each phase still asks on its own connection and goes on only on that connection's own answer; a fetch reached with the budget spent asks nothing, prints `RECEIPTS_TIMED_OUT` and leaves its mail queued; a commit reached with it spent prints `RECEIPTS_COMMIT_TIMED_OUT`. A fetch whose request was sent but whose reply misses the deadline prints nothing: the deck may have assigned the mail by then, and the attempt is left to the issued-attempt recovery. A prompt against a daemon that does not confirm asks once (the fetch reuses that negative answer, a timeout, a lost connection, or a foreign-socket refusal; a positive answer is never reused). These are cooperative socket-wait budgets, not ceilings on the hook. `Connection::send` checks the deadline before each write and gives the write the time that is left; after it has seen the deadline pass it starts no further write, but a write the OS schedules late can still start or finish after the instant. Outside the shared deadline: resolving the socket's path inside `connect(2)`, which it does not pre-empt (a stalled filesystem can hold it); the endpoint resolution each phase makes before it connects, whose liveness probes (`PROBE_TIMEOUT`, 250 ms each) have budgets of their own; the commit's caps reads and receipt publications, synchronous spool IO the deadline does not interrupt (a late publication is possible, and is valid evidence; the `inbox_committed` line is then not sent); and, once a fetch has brought a batch, that batch's `may` questions, waited for within the grant lifetime (`grant_ttl`, 60 s by default), and the control report `OneShotBatch::run` sends after the hand-over, whose write gets its own `RECEIPTS_ANSWER_WAIT`; and the hook's own output and spool work and its final status event (an unbounded connect and write).
- **Mixed hook installs.** An older prompt hook beside a newer waiter recognises the waiter's block by its id and sends a broad `ack <id>`, which this daemon still accepts: an accepted downgrade from exact-attempt commit to id assertion, not evidence of the exact attempt. A newer prompt hook beside an older waiter: the older waiter is refused `hooks_too_old`. `hooks install` writes the status hooks, the prompt hook and the waiter from one binary in one settings write, so running it refreshes them together; restarting the agent alone does not.

**Mixed installs at a glance.** The user-facing table is in `docs/installation.md` ("When the deck, the app and the hooks are on different releases"); what each row rests on:

| Pairing | Where it is closed | Outcome |
| --- | --- | --- |

The `cross-version` CI job compares `PROTOCOL_VERSION` at the previous release with the head first. Against `v0.47.x` (protocol 11) it moves to 12 here, so the job runs no harness and records the protocol refusal as the rule-12 outcome ([cross-version-harness.md](cross-version-harness.md#in-ci)). Issue [#1755](https://github.com/vfarcic/dot-agent-deck/issues/1755) is not fixed by part 2 and is a known state: since `v0.47.0`, a pairing whose two builds speak the same protocol and both carry `1666-inbox-replaces-typed-delivery` fails tells 3 and 4, which still look for typed delivery, and `KNOWN_EFFECTS` has no entry for that break. No such pairing runs for this branch, because no released build speaks protocol 12; the rewrite of those tells is part 3's.

## Codex, Devin and `inbox fetch` on receipts (PRD #1666 part 3, H4)

H4 moves the remaining mail takers onto the one-shot library Claude Code's hooks use (`src/inbox_oneshot.rs`). `engine::slot_for` maps `codex_hooks`, `devin_hooks` and `other` to `Slot::Hook`, which every hook receiver shares: it is registered by its own `inbox_receipt_fetch`, issued what that fetch asked for once (`hook_fetch`: queued mail no live receiver holds, and scheduled repeats), and never a `dispatch` target, never superseded and never superseding. It is not entered in the generation's `waiters`, so it is never counted as an armed native waiter and never holds off the doorbell. `MAX_LIVE_HOOKS` and the hook hold bound it as before. A non-Claude wait stays unsupported: a receipt wait from these components is refused `unsupported`, and their legacy `inbox_wait`, which only an older binary sends, keeps the legacy waiter until H5. The mapping grants none of them a native wake.

**Codex's hooks.** The prompt hook answers a doorbell with `{"hookSpecificOutput":{"additionalContext":…}}` (consumer `doorbell_hook`), and `Stop` hands over `{"decision":"block","reason":…}` with no doorbell to name (consumer `turn_end_hook`): both build one `OneShotInjection` from a `HookHandOver` (component, consumer, optional rung, `Envelope`), and the fetch names its component (`InboxFetchRequest.component`, additive; absent means Claude Code's). A block written whole and flushed is the commit, the same degraded witness as Claude's prompt hook: Codex's continued turn never echoes the reason back, so nothing proves the model read it. The envelope and framing are written only with the first block the fence lets through (`Piece::Open`/`Close`), and separators only between blocks written (`Piece::Joint`, which keeps `inbox fetch --json`'s array valid too). So `Stop` goes on with the turn (reports no Idle) when its output was written and flushed whole with a block in it, those it was refused staying queued for the next hand-over; a batch the fence refuses whole prints nothing, and a write or flush that fails reports the turn's end too, its blocks only possibly handed (inbox/receipt/032). That last is not proof Codex did not go on: a write that stopped at the decision's trailing newline, or a flush that failed after every byte was taken, can leave a whole decision on stdout, which Codex reads and goes on with while the card reads idle, and a block it did take may come again marked as a possible repeat (inbox/receipt/033). A prompt carrying whole blocks commits their exact attempts as Claude Code's does (`commit_delivered`); the id-only `ack` of opened ids is gone. **The budget is Codex's 6000 bytes of the whole output line**: the hook takes the envelope and the escaped framing off it and sends the rest as `max_json_bytes` (additive), and the deck counts each block and its separator escaped as JSON (`InboxBudget::JsonBytes`), `delivery A.e` opener included, before it issues. Every block, the first included, is rendered within the budget less the separator printed before it, so a first message that does not fit goes alone, cut by the renderer to keep the whole line within 6000 bytes (inbox/boundary/068), keeping its head and naming the file the deck saved its body to at post.

**`inbox fetch`.** Plain `inbox fetch`, and `--json` without `--doorbell`, is a hook receiver with consumer `cli` (`inbox_cli::fetch_one_shot`). The CLI does not know its agent, so the deck serves it as the hook of the generation's agent type (its spawn type, else the one its hooks reported; a routing hint for the budget and the log, not authority). It registers as `Registrant::Cli`, which leaves the floor's verdicts alone: a model-run fetch proves nothing about the agent's hooks, so it clears no `hooks_too_old`, pre-inbox notice, readiness or `refresh_failed`, and one below `HOOK_INTEGRATION` is refused without raising `hooks_too_old`. It prints the framing and each block, or with `--json` `{"messages":[{"id","subject","from","text"}…]}`: a public projection, never the attempt, its caps or `issued`. Stderr carries fixed text, the deck's refusal code and sentence, and a write error's kind, nothing of the batch. It opens the pinned spool after the deck answers, since the deck makes the generation's spool directory as it registers the fetch. Outcomes: zero bytes reports `not_handed` (the deck requeues at once); a prefix or a failed flush reports `handed`, possibly handed, so the lapse decides with a marked repeat at worst; a block the fence refuses (a revoke, a closed connection, an expired approval, an unreadable revoke marker, or a spool that cannot be opened) is not handed and nothing of it is printed. It exits 0 only when every block was written and flushed. A spool it can read but not write (Codex's sandbox) makes the publish fail: the control carries `degraded`, the commit applies through the authenticated connection and the card says messages may repeat (`inbox/codex/020`). `inbox fetch --json --doorbell <id> [--adapter-integration 2 --rx R]` is unchanged: OpenCode's stream-bound substitution on the legacy verb, whose attempts belong to that stream. The one-shots are Unix only. On native Windows, which the deck does not support yet, neither hands anything over: the one-shot library is Unix only, so Codex's prompt hook and `Stop` hand nothing over, as Claude Code's hooks do not there, and since part 3's H5 plain `inbox fetch` says it cannot run there and sends nothing, the legacy fetch it used being withdrawn. Nothing builds or tests the Windows target, so neither half is measured.

**The sender gate.** Part 2's `one_shot_receipts` 1 says Claude Code's one-shots are served: that daemon refuses the CLI on the receipt verb and serves any other hook fetch as Claude Code's. So the answer to `inbox_receipts` gains `one_shot_senders` (additive; `claude_waiter`, `claude_hooks`, `codex_hooks`, `cli`; an unknown name reads as `Unknown`), and `serves_receipts(reply, sender)` lets Claude Code's senders on with the level alone and Codex's hooks and the CLI only when that same connection's answer names them. Part 2's daemon is therefore `Unsupported` for them, and 0.47.x, which answers nothing, `TimedOut`: either way nothing that could take mail, grant or publish is sent, and there is no legacy fallback. Codex's hooks say the `RECEIPTS_*` notices with Codex's remedy (`notice_for`: `hooks install --agent codex`, which rewrites Codex's hooks and records their trust). The CLI has its own words, because the model reading its output is the only reader, and they tell before-send from after-send: `CLI_RECEIPTS_UNSUPPORTED`, `CLI_RECEIPTS_TIMED_OUT` and `CLI_RECEIPTS_CONNECTION_LOST` say no message was taken; `CLI_FETCH_TIMED_OUT` and `CLI_FETCH_CONNECTION_LOST`, once the fetch was sent, say the deck may have set messages aside for it and offers any again later, marked as a possible repeat.

**What a user sees when a newer hook or CLI meets an older daemon** (an upgrade refreshed the agent's hooks, R-3, while the daemon still runs the earlier release, which the upgrade leaves running): the deck still types its doorbell; Codex's prompt hook asks, takes nothing, prints its notice on stderr and exits 1 (whether Codex shows a failing hook's stderr is not measured); the prompt reaches the model with the doorbell line and no message, the line tells it to run `dot-agent-deck inbox fetch`, and that command asks too, takes nothing and prints the CLI notice, which the model reads: the remedy is to restart the deck daemon on the newer release, or run `inbox fetch` with the daemon's `dot-agent-deck`. Busy mail: `Stop` asks, takes nothing, and the turn ends with its Idle reported, so the doorbell takes over. The messages stay with the daemon throughout.

**Agent parity (CLAUDE.md rule 20).** On macOS and Linux (native Windows is above), Codex: trusted hooks (prompt hook and `Stop`), prompt hook off (doorbell, model-run fetch and `Stop`), and untrusted hooks (doorbell and model-run fetch) all run on receipts, measured with real Codex (`inbox/codex/009`, `/011`, `/022`). Devin: doorbell and model-run fetch, pinned by a lane-1 stand-in only (`inbox/boundary/054`). Any other agent: doorbell and model-run fetch. Both clients project the receipt attention (uncertain, Retry, Cancel, degraded) from the same summaries as before; nothing client-side changed.

**Contract.** No `PROTOCOL_VERSION` bump: the attach wire is unchanged, and the hook socket gains additive optional fields (`one_shot_senders`, `component`, `max_json_bytes`). The meaning that moved is declared as `CONTRACT_BREAKS` entry `1666-remaining-inbox-one-shot-receipts`, with `changelog.d/1666-remaining-inbox.breaking.md`. No `cross-version` tell exercises Codex's hooks or `inbox fetch` (the roles are stand-ins), so `KNOWN_EFFECTS` gains no entry; the pairings are pinned by lane-1 stand-ins (`inbox/codex/023`, `inbox/cli/006`).
