# Self-upgrade: design and trust boundary

How `dot-agent-deck upgrade` and the desktop app's upgrade dialog notice a newer release and upgrade the copies installed on this machine (issue #1635), what each step verifies, and what the verification does not cover. The user-facing behaviour is in the published docs; this page is for whoever changes `src/self_upgrade/` or `desktop/src-tauri/src/self_upgrade.rs`.

## The seams

Everything lives in one root-crate module, `src/self_upgrade/`, which both clients call, so the TUI, the CLI and the desktop app use the same words (CLAUDE.md rule 22). The desktop crate reaches it through its path dependency on the root package.

| file | job |
| --- | --- |
| `detect.rs` | how one copy was installed. `detect` is a pure function of `DetectInputs`; `inspect` gathers the real inputs through a `Host`. |
| `plan.rs` | what to offer for that install and a newer release, and every line a client shows, as `PlanLine::Text` / `PlanLine::Command`. Pure. |
| `discover.rs` | the other copy on the machine: the desktop app from the CLI, the CLI from the desktop app, each inspected through its own install method. |
| `verify.rs` | the checksum manifest, build provenance through `gh attestation verify`, the new binary's `--version`, and the re-hash before a staged file is installed. |
| `execute.rs` | the private staging directory, downloading, and carrying out a confirmed plan. |
| `cli.rs` | `dot-agent-deck upgrade [--check\|--yes]`. |

Every subprocess and filesystem question the detection and planning steps ask goes through the `Host` trait, so a unit test fakes the machine; `SystemHost` is the real one. The staged downloads are real files, so the execute tests use temporary directories.

Every subprocess has a time limit (`Host::run_within`). A probe — `--version`, `dpkg-query`, `brew --prefix`, `gh auth status`, `codesign -dv`, `hdiutil detach` — gets `PROBE_TIMEOUT` (15 s). A check that asks a service — `gh attestation verify`, and the new app's `codesign --verify --deep` and `spctl --assess`, which can consult Apple's notarization service — gets `VERIFY_TIMEOUT` (60 s). A command that carries the upgrade out — `brew upgrade`, the `pkexec` installs, which wait for the user at the password prompt, `hdiutil attach` and `ditto` — gets `INSTALL_TIMEOUT` (15 minutes): long enough for a slow `brew` download or a user who steps away from the prompt, and still an end, so a stuck command cannot leave a dialog on Upgrading for good.

`run_bounded` in `mod.rs` is how `SystemHost` runs one. On Unix the command starts in a session of its own (`setsid` in a `pre_exec`), so it has no controlling terminal and the session's id is its process group's. A command that opens `/dev/tty` therefore fails at once with `ENXIO` instead of being stopped by `SIGTTIN` as a background job of the user's terminal and looking hung until its limit; stdin is `/dev/null` either way. Every command the core runs is non-interactive here (`brew upgrade`, `install` and `apt-get` behind `pkexec`, `hdiutil`, `ditto`, `gh`), and `pkexec`, which only the desktop app uses, asks through the session's graphical polkit agent, never the terminal: polkit finds that agent through the logind session, which `setsid` does not change, and an app started from a launcher had no controlling terminal to begin with. A command past its limit is stopped by `SIGKILL` to its group alone, never by a kill that matches a name, so what it started dies with it; a descendant that moved itself to another group or session escapes. The error names the command and says whether it was stopped, which is decided by whether it exited within `STOP_GRACE` (2 s) of the signal, not by whether the signal was accepted. What `pkexec` started runs as root and cannot be signalled by the user, so for it the error says it may still be running, and the child is handed to a thread that waits for it, so it is reaped whenever it exits instead of staying a zombie. A session of its own also means a terminal's `^C` does not reach the command; the CLI forwards its own (below). Each output stream is read on its own thread, which keeps the first `MAX_CAPTURE_BYTES` (1 MiB) and reads and drops the rest. The readers wait for data with `poll` and look at a stop flag between waits, and they stop at the limit, or `EXIT_GRACE` (2 s) after the command exits, even when a descendant still holds the pipes; their read ends are then closed, so such a descendant gets `EPIPE` instead of an unbounded buffer. On Windows (unsupported, #164) there is no group, and a reader stops only at the end of its stream. The timeout error carries whether the command was stopped (`unfinished_stopped`), which the privileged installs read (below).

`dot-agent-deck upgrade` forwards its own Ctrl+C and `SIGTERM` to the command it is running. Since the command is in a session of its own, the terminal's `^C` reaches only the CLI, and without forwarding the CLI would die and leave, say, `brew upgrade` running with nothing left to bound it. `cli.rs`'s `CliHost` wraps `SystemHost` and, for each command, installs a `SIGINT`/`SIGTERM` handler that only sets a flag, runs the command through `SystemHost::run_within_cancellable`, and puts the previous dispositions back afterwards; between commands the signals keep their defaults, so `^C` at a confirmation question still ends the CLI. `run_bounded` looks at the flag while it waits, and once it is set stops the command's group as on a timeout, waits up to `STOP_GRACE` for it to exit, and returns a cancelled error (`ErrorKind::Interrupted`, `cancelled_error`). The CLI prints `` `<command>` failed: it was cancelled and stopped ``, then `Cancelled.`, attempts nothing further and exits non-zero. A command that cannot be stopped keeps the may-still-be-running wording. This is the CLI's alone: `SystemHost` installs no handler, and the TUI and the desktop app stay alive across a command, so the limit keeps working for them. `tests/e2e_self_upgrade.rs`'s `cli_upgrade_006` sends `SIGINT` to the real binary while a stand-in `brew` runs.

A signal to the command's pid or group is sent only before `run_bounded` has reaped the command itself, because until then the pid cannot be reissued to another process. That rests on one assumption, written on `run_bounded`: nothing else in the process reaps these children — no `waitpid(-1)` elsewhere, and no inherited `SIGCHLD=SIG_IGN`, under which the kernel reaps them itself. Where a wait fails anyway (`ECHILD` under that disposition), ownership is taken to be lost: no signal is sent, and the error says the command may still be running (`unfinished_stopped` reads `Some(false)`), which a privileged install treats as an install that may still be running.

The L2 tests (`tests/e2e_self_upgrade.rs`) isolate the binary from the machine they run on. Each runs with a `PATH` holding only a stand-in `dpkg-query`, and with `DOT_AGENT_DECK_TEST_SYSTEM_ROOT` (`e2e` feature only) re-rooting the system folders `discover.rs` looks in for the other copy (`/Applications`, the `.deb`'s `/usr/bin/dot-agent-deck`, the well-known CLI folders) into the test's own folder. A `gh`, a desktop app or a `.deb` installed on the host therefore cannot change what a test sees.

## Detection

`detect::detect` decides the install method from the canonical executable path and a few facts about it, in this order, first match wins:

1. under `/nix/store` → Nix (notify only);
2. inside `<prefix>/Cellar/<formula>/` for one of the tap's formulas, where `<prefix>` is a default Homebrew prefix or the one `brew --prefix` reports → Homebrew (`brew upgrade <formula>`);
3. owned by a Debian package: the desktop `.deb`'s package → the desktop `.deb` (its bundled CLI upgrades with it); any other package → a system package (notify only);
4. a source build (a cargo build directory, a `cargo install` location, a dirty checkout's build id) → notify only;
5. on macOS, inside a `.app` bundle → the desktop `.dmg` install (swapped in place when its folder is writable and the running app is signed; otherwise the user downloads the new image);
6. otherwise a downloaded binary, replaced in place when its directory is writable, and staged for a privileged install when it is not.

## The release channel

`release_channel` (`src/self_upgrade/mod.rs`) puts a copy on one of two channels, `ReleaseChannel` in `src/version.rs`. A copy installed from the `dot-agent-deck-beta` Homebrew formula, or whose own version is a SemVer prerelease (`0.47.0-beta.1`), is on the prerelease channel; every other copy is on the stable channel. The stable channel asks GitHub's `releases/latest`, which never names a prerelease, and refuses an answer that is a draft or a prerelease anyway. The prerelease channel asks the `releases` list endpoint and takes the highest SemVer among the releases that are not drafts, so a beta is offered the next beta, and a stable release once it is higher than every beta. Each copy on the machine is planned on its own channel: `ReleaseSource::releases_for` asks `releases/latest` whenever a copy is on the stable channel and the list whenever one is on the prerelease channel, so a CLI on the stable formula beside a prerelease app is offered the newest stable release, the only kind its formula receives, and a prerelease copy beside a stable app the highest release known. The TUI's startup notice uses the same lookup, choosing the channel from its own version. Under the `e2e` feature, `DOT_AGENT_DECK_TEST_RELEASES_API_URL` and `DOT_AGENT_DECK_TEST_RELEASES_LIST_API_URL` replace the two endpoints for an L2 test.

The beta formula only ever receives prereleases (`release.yml`'s "Detect channel" step), so `brew upgrade dot-agent-deck-beta` cannot reach a stable release, and a copy on it is planned differently (`plan` in `src/self_upgrade/plan.rs`). The lookup (`ReleaseSource::releases_for`) returns a `Releases`: the newest release on the running copy's channel (the dialog's title), the newest stable release (from `releases/latest`, or from the list when no copy is on the stable channel), and the newest prerelease (the highest non-draft version with a SemVer prerelease suffix). A copy on the beta formula is on the prerelease channel, so the list is fetched whenever one is on the machine, and a desktop app on stable still finds the beta its CLI can move to. A beta-formula copy is offered `brew upgrade dot-agent-deck-beta` only for the newest prerelease newer than it. A stable release newer than both the copy and that prerelease is still noticed: with no newer prerelease the plan is notify-only and says the formula does not carry stable releases, and with one the plan offers the prerelease upgrade and mentions the stable release after it. Both give the switch command, `brew uninstall dot-agent-deck-beta && brew install vfarcic/tap/dot-agent-deck` (`BETA_TO_STABLE_COMMAND`), uninstall first because `docs/installation.md` says the two formulas conflict. A stable release below the offered prerelease is not mentioned. Every other copy is planned on its own channel: a stable copy against the newest stable release, and a prerelease copy, a downloaded one included, against the highest release known. The TUI's startup badge is a version alone and still names the highest release on its channel; `dot-agent-deck upgrade` then shows the plan above.

## The verification chain

For every plan that downloads something, in order:

1. **Provenance availability, before confirmation.** `ProvenanceCheck::detect` looks for `gh` and runs `gh auth status`, and the client puts the answer in `PlanOptions::provenance`. The plan carries it and says it in words: either the manifest's provenance will be checked with `gh attestation verify`, or it will NOT be, and why. A known logged-out state (`not logged in`, an invalid token) and an unexpected failure (`gh` cannot be spawned; `gh auth status` failing for another reason, such as no network) each get their own reason.
2. **Staging.** `Staging::create` makes a fresh directory `v<version>-<random>` with mode `0700`, created exclusively, inside the staging root (`upgrade/` under the deck's state directory). The root itself is refused unless it is a real directory (not a symlink), owned by the current user and not writable by group or others. Every staged file is created new with `O_EXCL` and `O_NOFOLLOW`, so nothing already at a path, a planted symlink included, is written through.
3. **The manifest.** `checksums.txt` (or `checksums-desktop-alpha.txt`) is downloaded into memory and written once into the staging directory for `gh` to read.
4. **Provenance.** When the plan promised it, `gh auth status` is asked again; if `gh` has since disappeared or logged out, the upgrade aborts rather than silently downgrading. Then `gh attestation verify <manifest> --repo <slug> --signer-workflow <slug>/.github/workflows/release.yml --source-ref refs/tags/v<version> --format json`. The JSON must name the SHA-256 of the manifest bytes held in memory as an attestation subject: `gh` reads the file while the checksums are parsed from memory, and that digest is what ties the two together.
5. **Checksum.** The asset is downloaded into memory and its SHA-256 must match the manifest's single entry for it. A missing, ambiguous or mismatched entry aborts.
6. **`--version`.** A CLI binary must answer as dot-agent-deck at the release's version (for the `.dmg`, the CLI bundled in the new app; the app also passes `codesign`, the running app's Team ID and Gatekeeper).
7. **Re-hash at the hand-off.** Right before the staged file is given to whatever installs it (the rename over a writable binary, `pkexec install`, `pkexec apt-get install`, `hdiutil attach`), it is hashed again against the verified digest, and a mismatch aborts.
8. **After a privileged binary install**, the installed target, now root-owned, is hashed against the verified digest before it is run for its `--version`. A mismatch is reported as an installed file that is not the verified build and must be reinstalled, and the file is not executed.
9. **When a privileged install does not complete.** `run_privileged` in `execute.rs` tells two failures apart. `pkexec` exiting 126 or 127, its own codes for a dismissed or refused prompt, or not running at all, is `UpgradeError::PrivilegeFailed`: nothing was installed, and the result hands over the `sudo` command for the staged file. Anything else, a failure past the prompt or a timeout, is `UpgradeError::InstallUnfinished`, worded once in `plan::install_unfinished_lines`. While the install may still be running (a timeout whose command could not be stopped), nothing is checked and no install command is offered, since a second install would race the first: the user is told to wait and then check with `<target> --version`, or `dpkg -s agent-deck` for the `.deb`. Once it has stopped, the target may be partly written, so it is looked at: the binary is hashed against the verified digest and against its own digest taken just before `pkexec` ran, and the package's version and status are read with `dpkg-query`. The package's new version is the one the staged `.deb` itself declares, read with `dpkg-deb -f <staged.deb> Version` (fixed arguments, the probe limit) once the file has been hashed again against the verified digest, never the release's version string: dpkg spells a prerelease `0.47.0~beta.1` where the release says `0.47.0-beta.1`, so the string comparison read a finished prerelease install as not new. When the `.deb`'s version cannot be read, or the file no longer matches its digest, the state is reported as could-not-be-checked and no install command is offered; there is no fallback to the string comparison. The previous version is still compared as the copy reported it, so a prerelease previous version reads as neither. The result says which it found (the previous version, the new one, neither, missing, or could not be checked), and the install command is offered again only when the target is known not to be the new version. A binary that matches neither is never run. The staging directory is kept while an install may still be reading it, and whenever a command for it is shown.

A command the user runs themselves (`sudo install …`, `sudo apt install …`) is only built once the download is verified, because the staging directory's name is not known before that. It starts with a checksum check of the staged file, `echo '<sha256>  <path>' | sha256sum -c - && sudo …` (`shasum -a 256 -c -` on macOS), so `sudo` runs only on the verified bytes. No command is built for a path that is not UTF-8, is longer than `MAX_SHOWN_PATH_CHARS`, or contains a control character, a bidi or other invisible formatting character, or a backslash (which `sha256sum -c` reads as an escape); the client shows how to upgrade manually instead. The desktop app keeps a command's exact text apart from its display copy, and offers Copy only when its own display sanitizer would leave the command unchanged.

After a `brew upgrade` exits 0, the upgraded copy's `--version` must report the offered release. `brew upgrade` also succeeds when the formula is already at the tap's newest, and the tap lags a GitHub release for a while after it is published, so otherwise a copy still on the old version would be reported upgraded. When it does not, the outcome is `Outcome::BrewNotUpgraded`, `Outcome::upgraded()` is false, and every client reports a failure and keeps the copy on offer. The `.dmg` swap attaches the image through a drop guard (`Attached` in `execute.rs`) that is held from before `hdiutil attach` runs, so a detach is attempted on every path that returns or unwinds, an attach that mounted the image and then failed or timed out included. The guard detaches only when something is at the mount point, which the upgrade created empty in its private staging directory (a file system mounted on it, or anything in it), plain first and then forced. A process that is killed outright, or aborts instead of unwinding, never runs the guard, and leaves the image attached without a warning. When even a forced detach fails, the outcome or the error (`StillMounted`, which keeps the mount point as a path rather than a string) names the mount point and gives the `hdiutil detach -force` command. That command is built by `plan::detach_image_command` with the same path checks as the install commands; for a mount point that fails them, the user is told to list the attached images with `hdiutil info` instead.

`dot-agent-deck upgrade` prints plan lines as items (`say_items` in `cli.rs`), not as rendered strings: prose goes through the control-and-bidi filter, and a command prints exactly as the core built it. One the filter would change is not printed at all, rewritten or not, and a line says it was left out.

### Why `--source-ref` is safe to require

Checked on 2026-10-10 against the published attestations: `checksums.txt` and `checksums-desktop-alpha.txt` of v0.46.0, v0.45.1, v0.45.0, v0.44.0 and v0.43.0 all verify with `--source-ref refs/tags/v<version>`, and v0.46.0's manifest checked against `refs/tags/v0.45.1` fails with `expected SourceRepositoryRef to be refs/tags/v0.45.1, got refs/tags/v0.46.0`. Releases are cut by pushing a `v*` tag (`tag-release.yml`), so the attestation's source ref is the tag. `release.yml` also has a `workflow_dispatch` trigger; a release cut that way would be attested with the dispatching branch as its source ref, and an upgrade to it fails provenance and changes nothing, which is the intended failure direction. Among the last 100 `release.yml` runs (listed with `gh run list --workflow release.yml`), one dispatched run succeeded, on 2026-04-27, months before self-upgrade existed. An upgrade only ever targets the newest release on the copy's own channel (next section).

## What a client keeps between a check and an upgrade

What runs must be what the user read. The TUI's dialog holds the plans it opened with and runs those. The desktop bridge (`desktop/src-tauri/src/self_upgrade.rs`) hands every check an id when it starts, keeps the newest `KEPT_CHECKS` checks by id, and drops a result older than one it already keeps (answering that caller with the newer check), so a slow check never replaces a fresh one. The dialog keeps the check it opened with and sends its id with Upgrade, and the bridge runs that check's plan; a check no longer kept is refused (`PLAN_GONE`) rather than replaced by a newer plan. The TUI orders its checks the same way (`upgrade_dialog::publish`).

The bridge runs one upgrade at a time. `SelfUpgradeState::claim` takes the run slot first, through the `Running` guard that lets go of it on any refusal, and only then validates the plan (the app not already installed, the check still kept, the plan actionable). The run holds the guard until it has published what it installed, so a second Upgrade cannot validate while the first runs and then install over the app the first one just installed, from an older retained check or any other.

When a privileged install may still be running (`InstallUnfinished` with `may_still_be_running`), the bridge remembers that copy (`mark_unfinished`): until the app restarts, `claim` refuses it and the check answer sends its plan as not actionable, ending with why. That is a per-copy state rather than a held run slot, so the other copy can still be upgraded. The bridge cannot tell when that install ends: it runs as root, and the core only reaps it.

After the app's own copy is installed — the `.dmg` swap, or the `.deb` through `pkexec apt-get`, both of which replace the running app's files (`Outcome::app_relaunch_notice`) — the running process is still the old build, so the next check plans it as behind again. The bridge remembers the installed result (`Installed`): the app's plan is sent as not actionable, the run command refuses it, the dialog shows the result with Relaunch, and the notice is the relaunch line when nothing else is behind. Tauri's restart spawns the binary path captured at startup, so on Linux it runs the new `/usr/bin/dot-agent-deck-desktop`. The TUI does the same for its own copy with `upgrade_installed` and its restart line.

## The residual same-user race

Every check above defends against a file changing between the network and the install, and against another user on the machine. None of them defends against a process already running as the same user, and that is a deliberate boundary rather than an oversight.

Such a process can replace a staged file in the window between the re-hash and the moment `pkexec install`, `apt-get` or `hdiutil` opens it. The narrow mitigations were chosen over a root-side installer that snapshots and verifies the file itself, because a same-user process can already intercept any privileged operation the user starts: it can edit the shell's rc files or put its own `sudo` or `pkexec` earlier on `PATH`, and wait for the user to type their password. A root-side snapshot helper would move the check across the privilege boundary without moving the trust boundary, which is the user's own account. What the mitigations buy is that the window is short, that a swap made before it is caught, and that a mismatch which reaches a root-owned target is reported and never executed.

The same reasoning covers the `--version` run of a staged CLI: it executes a file in a directory only the user can write.

It also covers how the desktop app finds the CLI (`discover::find_cli`), which the security audit raised as A9 and which was accepted rather than hardened. The app searches the login shell's `PATH` and then `WELL_KNOWN_CLI_DIRS`, and runs whatever `dot-agent-deck` it finds there for its `--version`, so a same-user process that can put a file earlier on that `PATH` (or edit the rc files that build it) gets that file run, and has its install method planned. That is the binary the user's own terminal would run for `dot-agent-deck`, and the same process could already replace it outright, so restricting discovery to a fixed set of directories would cost the common installs (a `PATH` entry the deck does not know about) without moving the trust boundary. What the discovered copy cannot do is choose what gets installed: its plan is built from its detected install method, and anything downloaded for it passes the same verification chain as the running copy's.

Build provenance is only as strong as `gh` is: a plan run where `gh` is missing or logged out still checks the checksum against the manifest, and says before confirmation that provenance will not be checked.

## The privileged binary install is not atomic

An accepted residual risk. The writable binary is replaced atomically (`atomic_replace`: a temporary file beside the target, checked, then renamed over it). The binary installed behind `pkexec` is not: `pkexec /usr/bin/install -m 0755 <staged> <target>` writes the target in place, so an install stopped part way, by the timeout or by a failure, can leave it partly written. Making it atomic means copying beside the target and renaming as root, and `pkexec` runs one command: that needs either a root shell (`sh -c`, a shell parsing a string as root) or a second command and so a second password prompt. Neither was judged worth it. The mitigation is the check after an install that did not complete (item 9 of the verification chain): the target is hashed, the user is told whether it holds the previous version, the new one, or neither, a target that matches neither is never run, and the install command is offered again when the target is not the new version.
