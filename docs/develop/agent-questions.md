# Agent questions: knowing and answering what an agent is waiting on

PRD #1542 gives the daemon a model of the question each agent is waiting on — a permission prompt, a multiple-choice menu, a form of several questions — and a request to answer it through the agent's own channel. The desktop's voice panel is its first client (user docs: [`docs/desktop/voice.md`](../desktop/voice.md#answering-an-agents-question)); #1497, which will speak a prompt aloud, is meant to read the same model. This page is the mechanism and its risks. The PRD (`prds/1542-voice-answer-agent-questions.md`) has the measurements every table below rests on, tagged by how each fact was established.

## The model: `pending_question`

`src/question.rs` owns `PendingQuestion`: an `id`, a `kind` (`permission`, `choice`, `plan`, `confirm`), one or more `Question`s (prompt, header, options in on-screen order, `multi_select`), the `tool` it is about (name, the deck's `tool_detail`, and a `use_id` where the agent supplies one), the `channel` the daemon would answer through (`held`, `keys`, `unsupported`) and an optional `subagent_id`. Each `QuestionOption` has a 1-based `index` (the number the agent draws), a `label`, a `role` (`allow_once`, `allow_always`, `deny`, `choice`, `free_text`), `keyboard_only`, and for `allow_always` a `scope` sentence the desktop's confirmation shows. Unknown enum strings deserialize to `Unknown`, which no client treats as answerable.

**Every text field is untrusted agent output** ([`voice-first-design.md`](voice-first-design.md) §6, and §10 for how the voice path treats it). `PendingQuestion::sanitized` caps it (`MAX_PROMPT_BYTES`, `MAX_LABEL_BYTES`, `MAX_DESCRIPTION_BYTES`, `MAX_QUESTIONS`, `MAX_OPTIONS`), strips control characters, and drops a question whose `id` is not a valid routing key (`is_valid_question_id`) or that has nothing to choose. The daemon applies it on arrival in `admit_producer_event` (`src/daemon.rs`), rewriting the question sanitized or dropping it; producers are not trusted to have done it.

It reaches clients on `SessionSnapshot.pending_question` (`src/state.rs`), additive and optional, so it moved no `PROTOCOL_VERSION` ([`versioning.md`](versioning.md) item 1). On the producer side it rides `AgentEvent.metadata["pending_question"]` as JSON (`AgentEvent::question` / `set_question`) rather than a new `AgentEvent` field: that moved no wire and touched none of the `AgentEvent` literals across the workspace.

### Set and clear

`apply_event` sets it from an event carrying a question (a `ToolStart` carrying one still counts the tool) and turns the status `WaitingForInput`. It clears on the first of: a `ToolEnd` for the question's `tool.use_id`, or, without one, a main-thread `ToolEnd` for the same tool name; a new turn, `Idle` (a `Stop`, or Codex's `Interrupt`), `SessionStart`, `Error` or `QuotaBlocked` on the main thread; an event whose `question_resolved_id` (`QUESTION_RESOLVED_METADATA_KEY`) names it; the held producer's connection closing unanswered; the subagent that raised it stopping; and the daemon's own answer. A `Notification` does not clear it — Claude Code's `permission_prompt` notification arrives about 6 s after the `PermissionRequest` it describes [observed on 2.1.289].

The two clears the daemon originates are broadcast as events of its own, built by `deck_question_event`, so the TUI's fold and the desktop's agent view drop the question too: the answer is a `Thinking` event marked `question_answered_by_deck`, and a released hold is an `unknown` event marked `question_released_by_deck` that changes no status. Both markers are stripped from producer frames and counted by `is_daemon_synthetic`. An older client decodes `unknown` as the no-op it always was.

## Producers, per agent

| Agent | Detects from | Channel | Notes |
| --- | --- | --- | --- |
| Claude Code | `PermissionRequest` hook (`claude_permission_request`) | `held`, except plan approval (`keys`) | Installed only for Claude Code ≥ 2.1.136 (`PERMISSION_REQUEST_MIN_CLAUDE_VERSION`) |
| Codex | `PermissionRequest` (`codex_permission_request`) and `PreToolUse` for `request_user_input` (`codex_request_user_input`) | `keys` | `Interrupt` hook installed to clear a keyboard deny |
| OpenCode | the plugin's `permission.asked` / `question.asked` | `held` | answered through the plugin's SDK client |
| Pi | the deck's extension wrapping `ctx.ui.select` / `confirm` / `input` (`installQuestionWrappers`, `pi-extension/src/orchestrator.ts`) | `held` | rests on undocumented behaviour |
| Devin | `PermissionRequest` (`devin_permission_request`) | `keys` | built from docs, **untested** |

**Claude Code.** The hook builds the question in-process and holds its socket connection open (`hold_question`) until the daemon answers or `CLAUDE_HOLD_DEADLINE` passes: 3570 s, which ends 30 s *before* the 3600 s `timeout` the deck installs the hook with (`PERMISSION_REQUEST_HOOK_TIMEOUT_SECS`), so the hook exits on its own before Claude Code cancels it. Claude Code shows its dialog while the hook waits, so the keyboard stays usable [observed]. On the daemon's answer the hook prints the decision (`claude_decision`): `allow`; `allow` with `updatedPermissions` set to the ONE update the "always" option stands for (below); `deny`; or, for `AskUserQuestion`, `allow` with `updatedInput` = the payload's `questions` **verbatim** plus `answers` (a label, an array of labels for `multiSelect`, or free text). `updatedInput` replaces the tool input rather than merging, so leaving `questions` out fails Claude Code's schema check [observed]. On EOF, a release, an unreachable daemon or any reply for another id, the hook exits 0 printing nothing, and Claude Code behaves as if there were no hook. A keyboard No or Esc makes Claude Code `SIGTERM` the hook [observed], which closes the connection and is the daemon's clearing signal; a keyboard Yes does not, and the tool's `PostToolUse` clears it instead. Plan approval (`ExitPlanMode`) is the exception: a hook `allow` does not dismiss that dialog [observed], so the question is built with `channel: keys` and the hook does not hold.

**Claude Code's "always" grants exactly what was confirmed** (audit A2). The option's label is chosen by the payload's first `permission_suggestions` entry, and that entry alone is what the decision sends (`claude_always_update`) — a later suggestion, such as the `setMode acceptEdits` that follows `addDirectories` in the captured Bash payload, is never sent, because nothing on screen or in the confirmation describes it. The confirmation's scope is written from that update itself (`claude_update_scope`): its `type` (`addDirectories` with its directories, `setMode` with per-mode wording, `addRules` with its rules when `behavior` is `allow`) and its `destination` (`session` reads "for the rest of this session", whatever Claude's own label says; `localSettings`, `projectSettings` and `userSettings` each name where it lasts). An update it cannot describe — another type, mode or destination, a non-allow rule — makes the option `keyboard_only`, and `claude_decision` prints no decision for it even if a reply named it. So does one it cannot show **whole**: a sentence longer than the snapshot's 300-byte `MAX_DESCRIPTION_BYTES` (which sanitizing would cut, leaving later directories or rules — and the destination — granted but unseen), a target that sanitizing would alter (control or bidi characters, surrounding whitespace), or a target containing the `,` the targets are joined with, which would read as two. The check runs at both seams, the producer that builds the option and the decision that sends it, so the scope a user confirms after sanitizing is byte-for-byte the scope the decision was checked against (`question/hold/010`). The labels are Claude Code's on-screen text, shortened on purpose: the `setMode` one drops the parentheticals Claude draws ("(auto-approve file edits and common file commands)", "(shift+tab)"), which are hints rather than the option; and Claude draws "from this project" beside an `addDirectories` suggestion whose destination is `session`, which the label keeps and the confirmation corrects.

**The Claude Code version gate.** Issue #714 measured that an older Claude Code given one unknown hook key drops every hook in `settings.json`. `PermissionRequest` exists from 2.0.45, but 2.1.136 fixed `AskUserQuestion` multi-select answers supplied as an array, so the gate sits there, above `StopFailure`'s 2.1.78. It reuses the install-time `claude --version` probe; an unknown version is treated as older. Whether a release between 2.0.45 and 2.1.136 drops all hooks given the key was not run. The tables apply from the gate: producers pass no agent version (none is in any payload), so `QuestionTables::covers(None)` is true.

**Codex.** A held `PermissionRequest` hook hides Codex's approval prompt ("Running hook") until the hook exits [observed on 0.160.0], so the hook returns at once and the daemon answers with keys. `request_user_input`'s options are in the raw `PreToolUse` `tool_input`, with a `tool_use_id` that becomes the question's `id` and `tool.use_id`, so its `PostToolUse` clears exactly that form. Codex reports no multi-select field [observed], so every Codex question is single-select. After a keyboard deny no tool hook fires, but `Interrupt` does [observed], so the deck now installs `Interrupt` (`CODEX_HOOK_EVENTS`) and maps it to `Idle`. Adding it changes the installed hook set; the install trusts the deck's own hooks by hash (`trust_deck_hooks_in`), so it is trusted with the rest. Whether Codex shows its "Hooks need review" prompt to a session already running when the set changes was not measured.

**OpenCode.** The plugin template (`src/opencode_manage.rs`) spawns `dot-agent-deck await-answer --agent opencode` with `{session_id, event, properties, cwd}` on stdin; Rust builds the event and the question (`opencode_permission_asked`, `opencode_question_asked`) and holds the socket; one stdout line is the decision, which the plugin maps (`opencode_reply`) and posts to `/permission/{id}/reply` or `/question/{id}/reply`. `permission.replied`, `question.replied` and `question.rejected` stop the child and are forwarded with `request_id`, which becomes `question_resolved_id`. Two facts force this shape: the plugin input's `serverUrl` is not listening in TUI mode [observed], so the reply must come from inside the OpenCode process; and the plugin's v1 client has no question-reply method, so the plugin posts through `client._client`, **the SDK's underlying HTTP client — an internal, not an API**. It is wrapped in one function with that comment; an SDK release that renames or hides it breaks OpenCode answering while detection keeps working. A free-text answer posted through `/question/{id}/reply` is built from the documented types and has not been run against a live OpenCode.

**Pi.** Pi asks no questions of its own. On every `session_start` inside a deck pane, the deck's extension replaces `ctx.ui.select`, `confirm` and `input` on the shared `ctx.ui` object with wrappers that mint an id, call the original with an `AbortSignal`, and start `await-answer --agent pi --question <json>` through `pi.exec`; whichever settles first wins, and the other is aborted. The question lands on session `{pane_id}-session`, the one `agent-event` uses. **This is not a documented extension API.** It relies on `ctx.ui` being one object shared by every extension with writable methods, observed on Pi 0.87.1 only; Pi replaces that object when it rebinds its UI, which is why the wrappers are re-applied on every `session_start`. If a Pi release freezes or stops sharing the object, the guard leaves `ctx.ui` alone (no support, no crash), and `question/live/006` is what notices. A permission-gate extension calling `ctx.ui.confirm` from a `tool_call` handler reaches the same object [inferred]; `editor` and `custom` dialogs are not wrapped.

**Devin.** Built from its documentation, with no logged-in host to run it: `PermissionRequest` → `keys`, only Allow once (`\r`) and Deny (`\x1b`) answerable, every other documented option `keyboard_only`. Labels, order and both keys are unverified, and whether a running hook hides Devin's prompt is unknown, which is why the hook does not hold.

### Provenance: only an attested message raises or clears a question

A question, and an agent's own "answered" marker (`question_resolved_id`), reach the daemon only inside a `question` message (`DaemonMessage::Question`), which passes the hook socket's provenance gate (`docs/develop/hook-provenance.md`) like every other verb (audit A9). Held questions always did; the ones the deck answers by keys — Codex's, Devin's, Claude Code's plan approval — and OpenCode's `permission.replied` / `question.replied` / `question.rejected` markers now leave `hook` as an **unheld** `question` message (`send_question_unheld_at`, `hold: false`) carrying the pane's hook token, and the daemon answers it with one `released` / `not_held` line as soon as it has applied it. The daemon stamps the event with the pane and agent the gate attested and treats that agent as the question's owner; a message the gate let through without attesting one (a pane it never issued a token to, or a missing token under `DOT_AGENT_DECK_HOOK_PROVENANCE=warn`) has its question metadata removed (`strip_question_metadata`). A **bare** `AgentEvent` — the unattested route every status still uses — has `pending_question` and `question_resolved_id` stripped on arrival, so it can still set a status but can no longer put a question on a card, or take one off by naming it, through that metadata. That is the whole of what the stripping covers: a bare frame's lifecycle **status** still clears a pending question exactly as `question_cleared_by` (`src/state.rs`) says — a main-thread `Idle`, `Error` or `SessionStart`, for example — as it did before questions had a provenance gate, and statuses are not authenticated.

The fallback keeps a status the card used to get. When no reply comes within `UNHELD_QUESTION_WAIT` (2 s) — an older daemon logs the message malformed and answers nothing — or the gate refuses it, the hook re-sends the event as a plain one without the question, so the card still reads **Needs Input** exactly as before the deck knew questions. Against an older daemon that costs each such hook up to 2 s, which on Codex delays its approval prompt by as much, since Codex draws the prompt only after the hook exits.

### Trust boundary

The daemon's local sockets trust the OS user, and nothing on this page changes that. Two consequences are worth stating because they are easy to over-read:

- **An attach client is trusted to supply the user's authorisation.** `AnswerQuestion`'s `confirmed_always` proves only that the client asserted a confirmation; the daemon cannot know one was shown. Any process that can open the owner-only attach socket can answer a pending question, always-allow included, without voice, countdown or dialog. The desktop's confirmation, countdown, grounding and lease are what make *its* answers deliberate; they are not a property the daemon enforces.
- **An installed extension or plugin is trusted too.** The OpenCode plugin and the Pi extension run inside the agent; a hostile Pi extension can replace the shared `ctx.ui` wrappers or resolve a dialog itself, and nothing in the deck can tell. A hostile-agent boundary would mean revisiting the decided OS-user isolation policy, not adding another secret to the agent's own environment.

What the provenance gate does close is the cheaper route for the question metadata: a same-user process that is not a deck pane's own producer can no longer raise or replace a question with a bare event, nor clear one by naming it in `question_resolved_id`. It can still send a bare lifecycle status that clears one under `question_cleared_by`'s rules — the legacy status trust above, not a new route.

## Answering: `AttachRequest::AnswerQuestion`

`AnswerQuestion { agent_id, question_id, answers: [QuestionAnswer], confirmed_always, revision? }` is withheld by every client unless the daemon advertises `CAP_ANSWER_QUESTION` (`"answer-question"`), and the check lives in the client library (`DaemonClient::answer_question_while`), so the variant needed no `PROTOCOL_VERSION` bump ([`versioning.md`](versioning.md) item 1, CLAUDE.md rule 18). It returns `AnswerReport::{Withheld, Superseded, Answered, Refused(AnswerRefusal)}`. A refusal is carried as the additive `AttachResponse.answer_refusal`, so no client branches on error text: `AgentNotFound`, `NoPendingQuestion`, `Stale`, `InvalidAnswer`, `KeyboardOnly`, `AlwaysNotConfirmed`, `Unsupported`, `ChannelGone`, `WriteFailed`, `KeyboardStarted`. An unknown code decodes as `Unknown`.

**Every answer is bound to one revision of the question** (audit A4). A question id is the producer's, so the same id can be registered again — a second hold for the same Claude Code prompt, a Codex re-raise with other content. The daemon therefore stamps each question with a **revision** of its own when it ingests it (`stamp_question_revision`, under the state lock that applies the event, before the fan-out), overwriting anything a producer sent: a held question takes its hold's generation; a repeat of the pending question with the same id and content keeps the revision it has (and a keyboard-only channel the daemon set on it); anything else gets a fresh one from the same counter (`HeldQuestions::mint_revision`). The revision rides the snapshot (`PendingQuestion::revision`, additive optional), the desktop echoes it on `AnswerQuestion` (`DaemonClient::answer_question_at_while`), and the handler refuses `Stale` when the revision named is not the pending one. Whether or not the request names one, the handler binds its own delivery to the revision it validated against: a held reply goes only to the hold whose generation it is (`HeldQuestions::answer`), every key is written only while it is still the pending revision, and the deck's clearing event, the `ChannelGone` clear and the keyboard-only mark all name it — so a same-id replacement that registers between validation and delivery is refused as stale rather than answered with a choice made for the question it replaced (`question/answer/010`). **An older client omits `revision`** (it is `#[serde(default)]`): the daemon then has only the id to check the request against — a replacement under the same id between the client's snapshot and its request is not detected there — but the validation-to-delivery binding still holds. These transitions are serialised by where they check, not by one lock: registration replaces a hold atomically under the holds map's mutex and applies the question under the state write lock; delivery checks the generation under that mutex and the revision under the PTY writer; a clear names the revision under the state write lock.

**One answer per agent, once per question.** The handler takes the agent's slot (`QuestionAnswers::slot`) before it first reads the pending question and holds it to its last write, so two clients answering together are serialised and the second finds the question gone. The pane's answered ledger (`QuestionAnswers::mark_answered`) remembers the last question id the deck emitted an answer for, which is refused as `Stale` even if its clearing event never applied or the producer raised it again; it is kept per pane, not in the slot, so pruning idle slots never forgets it.

The handler checks, in order: the agent, that a question is pending, that its id (and the revision, when named) is the one answered, that the deck has not already answered it, the whole form (every question answered exactly once, indices in range, one option on a single-choice question, text only with a free-text option, `MAX_ANSWER_TEXT_CHARS`), `keyboard_only`, and that an `allow_always` comes with `confirmed_always`. The daemon cannot verify the confirmation was shown; refusing its absence means a client that skipped it must lie explicitly. Indices are resolved to the stored question by the daemon (`ResolvedAnswer` carries `option_indices`), and each producer maps them onto **its own** payload, never onto labels that crossed the socket, which are capped and may be truncated.

- **Held:** the reply goes down the held connection (`question_holds().answer`), only to the registration whose generation is the validated revision; if the producer is gone the question is cleared (that revision only) and the answer refused `ChannelGone`, and if another registration holds it now the answer is refused `Stale` and the replacement is left alone.
- **Keys:** `answer_keys` turns the answer into the table's keys — one digit per question for a Codex form — and `AgentPtyRegistry::write_answer_keys` writes each as the user's own keystrokes with no terminator, re-checking under the writer that the same question is still pending, with `ANSWER_KEY_GAP` (400 ms) between keys. Notice-mode writes were not usable: they append a newline. **The daemon owns the PTY's input but not the agent's dialog position**, so the keys channel refuses with `KeyboardStarted` whenever a human keystroke reached the pane after the daemon first saw the question's revision (`QuestionAnswers::note_pending`, recorded in `ingest_event`; `user_typed_since_question`): keys aimed at a form the keyboard half-answered, or a prompt it already dismissed, would land on the wrong question or in the composer. **The comparison is by sequence number, not by clock** (audit N1). `PaneInputState` keeps a human-input counter that only a human keystroke moves (the attach `STREAM_IN` path); the deck's answer keys are written as `ByteSource::Answer`, which stamps the user-input clock (they are the user's answer) but never moves the counter. The question records the counter when it arrives; each key's write returns the counter value it was committed at, read while the PTY writer is still held — and every human keystroke needs that writer too — so the next check (`human seq > committed`) cannot mistake a keystroke landing right after the deck's write for the deck's own (`question/answer/011`). The check runs before the first key and again under the writer before every one. When a write is refused or fails after some keys went in, the question stays pending but its channel becomes `Unsupported` (`mark_pending_question_keyboard_only`), so no client offers the half-typed form again, and the refusal says to finish by keyboard.

**The deck's own event after an answer** clears the question in the daemon and every attached client. It is `Thinking` when the answer lets the agent carry on, and a status-less `Unknown` when it includes a deny (review S3): a deny ends or interrupts the turn rather than starting work, so the card keeps **Needs Input** for the moment until the agent's own next event says where it went.

**Where the keys channel's baseline comes from, and why Codex forms stay answerable by keys.** The baseline is when the daemon ingested the question, not when the agent drew it, so a keystroke made between the two would not be counted. For Codex that interval does not reach the user: the question comes from a hook Codex runs **before** it shows the prompt — the approval's `PermissionRequest`, whose running hook hides the prompt until it exits [observed on 0.160.0], and the `PreToolUse` for `request_user_input`, which runs before the tool that draws the form [inferred from the hook's name and order; not separately measured] — and the hook now sends the question as an unheld `question` message and waits for the daemon's acknowledgement (`send_question_unheld_at`) before it exits. So the daemon has ingested the question, and recorded its baseline, before Codex shows anything the user could type into. That is why whole-form Codex answers stay on the keys channel rather than becoming keyboard-only. Two limits: if the acknowledgement does not come within `UNHELD_QUESTION_WAIT` the hook falls back to a plain event without the question, and that question is then not answerable by the deck at all (the same holds against an older daemon, which answers nothing — there is no answering by voice there); and an agent that moves its own dialog with no keystroke and no hook is invisible to the deck (Risks).

### Held connections

Holds are keyed by the pane that raised the question and its id, carry the agent the provenance gate attested, and are answered only for that pane and agent (audit A5): a question id is the producer's own, so two panes can share one. Each registration gets a generation — the question's revision — and a handler lets go of its hold (`forget`) only while its generation is the one in place, so a superseded handler whose connection closes late cannot drop the hold that replaced it. **The cleanup after a successful `forget` is revision-checked too** (`drop_held_question`): a same-id replacement can register while it awaits, so the release event is applied only if, under the state write lock that applies it, the pane's pending question is still that revision, and the fallback clear names the revision (`clear_pending_question_revision`) — a cleanup never clears by a reused id alone, and the replacement keeps its question, its hold and its own answer (`question/hold/011`).

A held connection gives its slot in the hook pool (`MAX_CONCURRENT_HOOK_CONNECTIONS`, 32) back as soon as the hold is registered and waits under a budget of its own, `MAX_HELD_QUESTIONS` (64), so waiting prompts never queue the `PostToolUse`, status and orchestration hooks behind them (audit A6). A question raised past that budget is applied without its question — Needs Input, answered by keyboard. That includes a same-id **replacement** raised while the budget is full: it is refused a hold before its predecessor's is released, which is a conservative refusal (the prompt is answered by keyboard), not a bypass. The daemon also enforces `QUESTION_HOLD_DEADLINE` (3720 s, past both producers' own deadlines): a hold still waiting then is released, the question cleared, and the release broadcast, exactly as when the producer's connection closes. While it waits, the daemon reads at most 1 KiB from the connection, since any byte from a holding producer means it is gone.

**A question connection carries one request and ends with its reply** (audit A6/N2) — answered, released, superseded, not held, or released at the deadline. A held connection has given its pool slot back and its hold budget goes with the handler, so a socket kept open past the reply would otherwise go on reading and dispatching lines outside both bounds. Every first-party producer already sends one request per connection and reads one line: the Claude Code hook (`hold_question_at`), the `await-answer` child the OpenCode plugin and the Pi extension run, and the unheld Codex/Devin/plan path (`send_question_unheld_at`), whose plain fallback opens a connection of its own (`question/hold/008`).

## Compatibility

Rule 12's answer for the PRD is no `PROTOCOL_VERSION` bump and no semantic break: the snapshot field and the refusal field are additive optional, the request is capability-gated, and the release broadcast is an ordinary `AgentEvent` with an `event_type` every build decodes. The audit fixes kept that answer: `AnswerRefusal::KeyboardStarted` is one more code in an enum whose unknown codes decode as `Unknown`; the deck's answered event for a deny is an `unknown` event, which an older client reads as a no-op; and none of `pending_question`, `question_resolved_id` or `answer-question` exists in any release, so stripping the first two from bare frames changes nothing a released build relied on. On the hook socket, a newer hook binary sends unheld `question` messages that an older daemon logs as malformed, and falls back to the plain event after 2 s (above); an older hook binary's bare question frames reach a newer daemon as plain statuses, so that pane's questions are answered by keyboard until the hook binary is updated. A held `question` frame sent to an older daemon is logged malformed there too; Claude Code's hook then waits until that daemon's idle bound closes the connection and decides nothing, and the dialog is usable throughout. One meaning did shift: Codex's `request_user_input` and OpenCode's `question.asked` now raise **Needs Input** where they used to read **Working**, which an older TUI attached to a newer daemon also shows — the correct reading, so it was not classed as a break. The second audit round kept the answer as well: `PendingQuestion::revision` and `AnswerQuestion`'s `revision` are additive optional fields on structures no release has, a client that omits the revision gets the id check it had (above), and closing a question connection after its reply matches the one-request contract every producer already follows. A synthetic driver that waits for the hook CLI to exit on a `PermissionRequest` now deadlocks against a daemon that holds it; `tests/subagent_tool_status.rs` and `tests/e2e_hook_delivery.rs` were changed for that.

## Risks

- **A misheard "yes" approves something.** Bounded on the desktop by [`voice-first-design.md`](voice-first-design.md) §10: the model picks only listed option numbers, the app validates them against the snapshot, the answer is shown with a cancellable countdown, and the daemon refuses a stale or changed question.
- **The model can pick the wrong option for real words — accepted** (audit A1). Grounding proves the words it cites were said, not that they mean the option: an Allow once quoting "what time is it", or the "run that" of "no, don't run that", is armed. Accepted rather than closed by a second confirmation on every approval; what bounds it is that the countdown shows exactly what will be sent, speech and Cancel stop it, and always-allow keeps its own confirmation word ([`voice-first-design.md`](voice-first-design.md) §10).
- **Agents change their prompts.** The tables above are per verified version, and only lane 2 checks them.
- **Pi's channel is undocumented**, and **OpenCode's reply goes through an SDK internal**; either can break on an agent release while detection keeps working.
- **A held hook can outlive its question.** On Claude Code a keyboard Yes does not end the waiting hook [observed]; the daemon releases it on the tool's `PostToolUse`, and one that is never released waits out `CLAUDE_HOLD_DEADLINE`, and in the daemon `QUESTION_HOLD_DEADLINE`.
- **The keys channel cannot see the agent's dialog.** It refuses once the user has typed into the pane since the question arrived, which also refuses an answer after the user typed something unrelated there; the residual it does not close is the agent itself moving its dialog on with no keystroke and no hook.
