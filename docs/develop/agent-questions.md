# Agent questions: knowing and answering what an agent is waiting on

PRD #1631 gives the daemon a model of the question each agent is waiting on — a permission prompt, a multiple-choice menu, a form of several questions — and a request to answer it through the agent's own channel. The desktop's voice panel is its client (user docs: [`docs/desktop/voice.md`](../desktop/voice.md#answering-an-agents-question)), and PRD #1497's reading mode announces the same prompts from the same detection (below). This page is the mechanism and its risks. The PRD is issue #1631's body, which carries the M1 inventory and follow-up measurements every table below rests on, tagged by how each fact was established; it ports closed PR #1561 (built for #1542, also closed) onto #1617's detection.

## The model: `pending_question`

`src/question.rs` owns `PendingQuestion`: an `id`, a `kind` (`permission`, `choice`, `plan`, `confirm`), one or more `Question`s (prompt, header, options in on-screen order, `multi_select`), the `tool` it is about (name, the deck's `tool_detail`, and a `use_id` where the agent supplies one), the `channel` the daemon would answer through (`held`, `keys`, `unsupported`) and an optional `subagent_id`. Each `QuestionOption` has a 1-based `index` (the number the agent draws), a `label`, a `role` (`allow_once`, `allow_always`, `deny`, `choice`, `free_text`), `keyboard_only`, for `allow_always` a `scope` sentence the desktop's confirmation shows, and `maybe_hidden` for an option the agent may or may not draw (below; `Question::screen_numbers` gives the numbers the screen may show beside each option). Unknown enum strings deserialize to `Unknown`, which no client treats as answerable.

**Every text field is untrusted agent output** ([`voice-first-design.md`](voice-first-design.md) §6, and §10 for how the voice path treats it). `PendingQuestion::sanitized` caps it (`MAX_PROMPT_BYTES`, `MAX_LABEL_BYTES`, `MAX_DESCRIPTION_BYTES`, `MAX_QUESTIONS`, `MAX_OPTIONS`), strips control characters, and drops a question whose `id` is not a valid routing key (`is_valid_question_id`) or that has nothing to choose. The daemon applies it on arrival in `admit_producer_event` (`src/daemon.rs`), rewriting the question sanitized or dropping it; producers are not trusted to have done it.

**A form the deck would show only part of is keyboard-only, whole** (PR #1698 review). A form of more than `MAX_QUESTIONS` (8) questions, or with a question of more than `MAX_OPTIONS` (16) options of its own, gets the `unsupported` channel: it is shown as far as the caps keep it, nothing is offered, and `validate` refuses every answer to it as `Unsupported` before a countdown. Answering the part shown would either send an answer to some questions as the whole form's, or let a user who heard a partial option list pick by label among the options shown while the rest stay hidden. "Of its own" means the options the agent's payload lists: the ones the deck appends from its tables (Claude Code's Type something. and Chat about this, OpenCode's Type your own answer, Codex's None of the above) are not counted, so a question of exactly sixteen stays answerable with them after it. The producers apply the option rule (`own_options_fit`: `claude_permission_request` for `AskUserQuestion`, `opencode_question_asked`, `pi_dialog`'s `select`, and Codex's own tighter nine through `CODEX_DIGIT_OPTIONS`), because only they can tell an agent's options from appended ones. `sanitized` applies the question rule, and keeps `MAX_OPTIONS + MAX_APPENDED_OPTIONS` (18) options per question — room for every agent's appended options, which `question/model/006` checks against the tables — making the form keyboard-only when it has to cut more, the backstop for a producer that did not apply the rule (`question/model/004`, `question/model/006`). The text caps cut a prompt, header, label or description short rather than dropping anything a user could choose, so they leave a form answerable; an option's index, not its label, is what an answer names.

**A form with an option the deck cannot read is keyboard-only, whole** (PR #1698 review). `payload_options` reads a payload option that is a string or carries a string `label`; any other entry is not read. The options after it keep their place in the payload's list as their index, rather than moving up a place, and the producer that met it (`claude_permission_request` for `AskUserQuestion`, `codex_request_user_input`, `opencode_question_asked`) gives the whole form the `unsupported` channel: the agent draws an option the deck does not know, so an answer could name the wrong one — for Codex, the digit the deck types. Nothing is offered and `validate` refuses every answer to it — `Unsupported`, or `InvalidAnswer` for the index of the option it could not read; `claude_decision` and `opencode_reply` map no answer onto such a payload. `sanitized` is the backstop: a question whose option indices are not `1, 2, 3, …` in order makes the form keyboard-only, whether or not its producer said so (`question/model/007`). No agent is known to send such an option; this guards a malformed payload, which is not something a user does, so the user page does not mention it.

It reaches clients on `SessionSnapshot.pending_question` (`src/state.rs`), additive and optional, so it moved no `PROTOCOL_VERSION` ([`versioning.md`](versioning.md) item 1). On the producer side it rides `AgentEvent.metadata["pending_question"]` as JSON (`AgentEvent::question` / `set_question`) rather than a new `AgentEvent` field: that moved no wire and touched none of the `AgentEvent` literals across the workspace.

### Set and clear

`apply_event` sets it from an event carrying a question (a `ToolStart` carrying one still counts the tool) and turns the status `WaitingForInput`. It clears on the first of: the end of the call the question is about — a `ToolEnd`, or the `Error` the hook promotes a failed call's `PostToolUse` to — matched by `tool.use_id` when both the question and the end name a call, and otherwise by tool name from the same thread; a new turn, `Idle` (a `Stop`, or Codex's `Interrupt`), `SessionStart`, an `Error` that is not a call's, or `QuotaBlocked` on the main thread; an event whose `question_resolved_id` (`QUESTION_RESOLVED_METADATA_KEY`) names it; the held producer's connection closing unanswered; the subagent that raised it stopping; and the daemon's own answer. A `Notification` does not clear it — Claude Code's `permission_prompt` notification arrives about 6 s after the `PermissionRequest` it describes [observed on 2.1.289].

**Which call a question is about** (PR #1698 review). Tools run in parallel, including two calls of one tool, so clearing by tool name alone let a parallel call's end clear a question still on screen — Needs Input and the voice offer disappeared while the agent waited. Claude Code's `PermissionRequest` payload carries no `tool_use_id` (2.1.296's bundle: its hook input is the base fields, `tool_name`, `tool_input`, `permission_suggestions` and an MCP server; the captured `claude-permission-bash.json` has none either), and neither does Codex's (`permission-request.command.input` in 0.160.0 has `additionalProperties: false` and no such field). Both run `PreToolUse` before they ask, and that payload carries the call's `tool_use_id` and its `tool_input`. So the Claude-shaped hook stamps a SHA-256 of `tool_input` (`TOOL_INPUT_DIGEST_METADATA_KEY`, `tool_input_digest`) on every `ToolStart` and `PermissionRequest`, and `apply_event` ties a question its producer could not name a call for to the one `ToolStart` in the current turn's journal with the same tool, thread and fingerprint that has not ended (`question_call`), writing that call's id into `tool.use_id`. Matching the input at `ToolEnd` instead would fail the other way: a hook decision's `updatedInput` replaces the input the call runs with (`Fxr` in 2.1.296's bundle), which is how the deck answers an `AskUserQuestion`, so that form's own end would never match and Needs Input would stick. OpenCode names the call itself: `permission.asked` carries `tool.callID` (a tool's `ctx.ask` adds it in 1.18.35's bundle, and the captured fixture has it), the plugin forwards `tool.execute.before`/`after`'s `callID` as `call_id`, and `opencode_permission_asked` puts it in `tool.use_id`. Pi's questions name no tool, so no tool end clears them. While a question stays pending, a frame that ends another call leaves the card on Needs Input rather than moving it to Thinking or Error. **Residuals:** two calls of one tool with the same input cannot be told apart, so the question is left untied and the first of them to end clears it; so is a question whose call's `ToolStart` the daemon has not seen (a hook from before this change, a journal that dropped it, a `PreToolUse` hook that rewrote the input, or the `ToolStart` applied after the `PermissionRequest`), and one whose tool end names no call (an OpenCode plugin from before this change). Each falls back to the tool-name match, which clears on that call's own end as before. Whether Codex's `PreToolUse` and `PermissionRequest` report the same `tool_input` for one call is not verified; when they do not, its questions fall back the same way. No wire shape changes: the fingerprint and the OpenCode call id ride the free-form `metadata` map, and `tool.use_id` was already an optional field.

The two clears the daemon originates are broadcast as events of its own, built by `deck_question_event`, so the TUI's fold and the desktop's agent view drop the question too: the answer is an event marked `question_answered_by_deck` — a `Thinking` when no option it chose is a deny, and an `unknown` that changes no status when one is — and a released hold is an `unknown` event marked `question_released_by_deck` that changes no status. Both markers are stripped from producer frames and counted by `is_daemon_synthetic`. An older client decodes `unknown` as the no-op it always was. The keyboard-only mark the daemon sets after typing part of a Codex answer is broadcast too (`deck_keyboard_only_event`, PR #1698 review): an `unknown` event carrying the question with its `unsupported` channel at a fresh revision, so a client's fold offers it to the keyboard at once rather than at its next full listing, and a voice answer another client is counting down for the old revision is called off (`question/answer/008`). It carries no marker: it changes no status, reading mode announces nothing from it, and the question it carries stays pending.

## One detection path, shared with reading mode

The question and the status event that reading mode announces come from **one parse of one hook payload**, so there is one install, one version gate and one parser for each hook both features read (PRD #1631's one change to #1561):

- **Claude Code, Codex and Devin.** `hook::hook_payload_event` is the only parser: `build_event_typed` maps the payload to its event (`PermissionRequest` → `EventType::PermissionRequest`, with the tool and its detail), and `hook_question` adds the question to that same event (`AgentEvent::set_question`). Claude Code's `PermissionRequest` hook is installed once, behind `PERMISSION_REQUEST_MIN_CLAUDE_VERSION` (`src/hooks_manage.rs`); reading mode had no install of its own, so that gate is the only one.
- **OpenCode.** `build_opencode_event_with_question` parses `permission.asked` / `question.asked` once into both the `PermissionRequest` status and its question. When the payload names no tool, the question's tool fills the event's `tool_name` / `tool_detail`, so what reading mode says the agent wants (`voice::reading::permission_wants`) is what the question asks.
- **Pi.** The extension's held dialog arrives as a `WaitingForInput` event carrying the question (`hook::pi_await_answer`); reading mode announces such an event as a permission prompt with nothing it wants ("Asking for permission.").

**A held question is registered and published before the daemon waits for its answer.** `register_and_publish_held` (`src/daemon.rs`) takes the pane's question lifecycle once and, under it, registers the hold first and then ingests the event that carries the question with that registration's generation — which broadcasts its status to every reading session. Only then does the daemon wait on the hold — for the deck's answer, the producer's connection closing, or the hold deadline. So reading mode announces a Claude Code prompt while its `PermissionRequest` hook is still waiting for the deck's answer, not only when the hook exits (`question/detect/012`).

**What the two features do not share.** Reading mode announces from the status *event* (`status_turn_event`), not from `pending_question` on the snapshot; the voice panel answers from the snapshot. The deck's own answer is broadcast on the status stream marked `question_answered_by_deck` (`QUESTION_ANSWERED_BY_DECK_METADATA_KEY`).

**A prompt Claude Code reports twice.** Claude Code reports one prompt twice: the `PermissionRequest` hook as the prompt appears, and its `permission_prompt` notification about 6 s later [observed on 2.1.289], which can arrive after the deck already answered the prompt. `status_turn_event` maps a `WaitingForInput` that carries no question to `TurnEvent::PermissionNotice` rather than `Permission`, and `voice::reading::coalesce` keeps a queue of owed notifications: each announced `Permission` adds an entry stamped with its hook event's timestamp, and a `PermissionNotice` pays the oldest entry it can and is not spoken: one whose hook event is stamped no later than the notification and at most `PERMISSION_NOTICE_WINDOW` (30 s) before it, compared by event timestamps rather than arrival time (`notice_pays`). An entry lapses once an event is stamped more than 30 s after its hook, and neither the deck's answer nor turn progress (`ToolStart`, `ToolEnd`, `Thinking`, `Idle`) pays one. So a prompt reported both ways is spoken once when its notification comes within 30 s of its hook, two prompts followed by their two notifications are each spoken once, and a notification with nothing owed for it is announced — a Claude Code below `PERMISSION_REQUEST_MIN_CLAUDE_VERSION`, which has only the notification, or a prompt whose hook's entry lapsed because its own notification never came (`question/desktop/015`). A notification stamped before every hook still owed — clock skew between the two events — pays nothing and is spoken, and the hook's entry stays owed for its own notification. What this does not do: it pairs by order and time, not by prompt identity, since the notification carries no prompt id, so a prompt is not guaranteed to be said exactly once. A notification arriving more than 30 s after its hook, or stamped before it, is spoken a second time; and a notification-only prompt stamped 0–30 s after a hook whose own notification never came pays that hook's entry and is silenced. That last one is an accepted residual (PRD #1631's re-audit, F2): telling it apart from the hook's own late notification would need a prompt id the notification does not carry. The user page says only that a prompt may now and then be said twice or not at all, and that the card's **Needs Input** and the pane are what to check. Pi's held dialog is a `WaitingForInput` that carries its question, so it stays a `Permission`.

**The deck's answer retracts the announcement.** An event carrying `question_answered_by_deck` — an allow ingests a `Thinking`, a deny an `Unknown`, so the marker is read on any event type — becomes `TurnEvent::PermissionAnswered` and reaches the webview as a silent `permission_answered` sentence with empty text. `DeckReader` queues each permission prompt under a key of its own (`<agent>\u0000permission\u0000<n>`, apart from errors' `…\u0000alert\u0000<n>`), and on `permission_answered` drops that agent's prompts from the speech queue — stopping one being said — and nothing else: its queued error and summary, and every other agent's speech, stay. The answered prompt's delayed notification is still owed and absorbed as above, and a new prompt afterwards is announced (`question/desktop/016`, Rust and vitest). A question released without the deck's answer (the keyboard, or the producer going away) does not retract anything. On the desktop, an utterance heard while the app was speaking — which may be the app reading the prompt aloud — is never offered to the question ([`voice-first-design.md`](voice-first-design.md) §10, `question/desktop/014`).

## Producers, per agent

| Agent | Detects from | Channel | Notes |
| --- | --- | --- | --- |
| Claude Code | `PermissionRequest` hook (`claude_permission_request`) | `held`, except plan approval (`keys`) | Installed only for Claude Code ≥ 2.1.136 (`PERMISSION_REQUEST_MIN_CLAUDE_VERSION`) |
| Codex | `PermissionRequest` (`codex_permission_request`) and `PreToolUse` for `request_user_input` (`codex_request_user_input`) | `keys` | `Interrupt` hook installed to clear a keyboard deny |
| OpenCode | the plugin's `permission.asked` / `question.asked` | `held` | answered through the plugin's SDK client |
| Pi | the deck's extension wrapping `ctx.ui.select` / `confirm` / `input` (`installQuestionWrappers`, `pi-extension/src/orchestrator.ts`) | `held` | rests on undocumented behaviour |
| Devin | `PermissionRequest` (`devin_permission_request`) | `keys` | built from docs, **untested** |

**Claude Code.** The hook builds the question in-process and holds its socket connection open (`hold_question`) until the daemon answers or `CLAUDE_HOLD_DEADLINE` passes: 3570 s, which ends 30 s *before* the 3600 s `timeout` the deck installs the hook with (`PERMISSION_REQUEST_HOOK_TIMEOUT_SECS`), so the hook exits on its own before Claude Code cancels it. Claude Code shows its dialog while the hook waits, so the keyboard stays usable [observed]. On the daemon's answer the hook prints the decision (`claude_decision`): `allow`; `allow` with `updatedPermissions` set to the ONE update the "always" option stands for (below); `deny`; or, for `AskUserQuestion`, `allow` with `updatedInput` = the payload's `questions` **verbatim** plus `answers` (a label, an array of labels for `multiSelect`, or free text). `updatedInput` replaces the tool input rather than merging, so leaving `questions` out fails Claude Code's schema check [observed]. On EOF, a release, an unreachable daemon or any reply for another id, the hook exits 0 printing nothing, and Claude Code behaves as if there were no hook. A keyboard No or Esc makes Claude Code `SIGTERM` the hook [observed], which closes the connection and is the daemon's clearing signal; a keyboard Yes does not, and the tool's `PostToolUse` clears it instead. Plan approval (`ExitPlanMode`) is the exception: a hook `allow` does not dismiss that dialog [observed], so the question is built with `channel: keys` and the hook does not hold.

**Claude Code's "always" grants exactly what was confirmed** (audit A2). The option's label is chosen by the payload's first `permission_suggestions` entry, and that entry alone is what the decision sends (`claude_always_update`) — a later suggestion, such as the `setMode acceptEdits` that follows `addDirectories` in the captured Bash payload, is never sent, because nothing on screen or in the confirmation describes it. The confirmation's scope is written from that update itself (`claude_update_scope`): its `type` (`addDirectories` with its directories, `setMode` with per-mode wording, `addRules` with its rules when `behavior` is `allow`) and its `destination` (`session` reads "for the rest of this session", whatever Claude's own label says; `localSettings`, `projectSettings` and `userSettings` each name where it lasts). An update it cannot describe — another type, mode or destination, a non-allow rule — makes the option `keyboard_only`, and `claude_decision` prints no decision for it even if a reply named it. So does one it cannot show **whole**: a sentence longer than the snapshot's 300-byte `MAX_DESCRIPTION_BYTES` (which sanitizing would cut, leaving later directories or rules — and the destination — granted but unseen), a target that sanitizing would alter (control or bidi characters, surrounding whitespace), or a target containing the `,` the targets are joined with, which would read as two. The check runs at both seams, the producer that builds the option and the decision that sends it, so the scope a user confirms after sanitizing is byte-for-byte the scope the decision was checked against (`question/hold/010`). The labels are Claude Code's on-screen text, shortened on purpose: the `setMode` one drops the parentheticals Claude draws ("(auto-approve file edits and common file commands)", "(shift+tab)"), which are hints rather than the option; and Claude draws "from this project" beside an `addDirectories` suggestion whose destination is `session`, which the label keeps and the confirmation corrects.

**The Claude Code version gate.** Issue #714 measured that an older Claude Code given one unknown hook key drops every hook in `settings.json`. `PermissionRequest` exists from 2.0.45, but 2.1.136 fixed `AskUserQuestion` multi-select answers supplied as an array, so the gate sits there, above `StopFailure`'s 2.1.78. It reuses the install-time `claude --version` probe; an unknown version is treated as older. Whether a release between 2.0.45 and 2.1.136 drops all hooks given the key was not run. The tables apply from the gate: producers pass no agent version (none is in any payload), so `QuestionTables::covers(None)` is true.

**Codex.** A held `PermissionRequest` hook hides Codex's approval prompt ("Running hook") until the hook exits [observed on 0.160.0], so the hook returns at once and the daemon answers with keys. `request_user_input`'s options are in the raw `PreToolUse` `tool_input`, with a `tool_use_id` that becomes the question's `id` and `tool.use_id`, so its `PostToolUse` clears exactly that form. Codex reports no multi-select field [observed], so every Codex question is single-select. After a keyboard deny no tool hook fires, but `Interrupt` does [observed], so the deck now installs `Interrupt` (`CODEX_HOOK_EVENTS`) and maps it to `Idle`. Adding it changes the installed hook set; the install trusts the deck's own hooks by hash (`trust_deck_hooks_in`), so it is trusted with the rest. Whether Codex shows its "Hooks need review" prompt to a session already running when the set changes was not measured.

**A Codex form with a question of more than nine options is keyboard-only, whole** (Qodo, PR #1698). Codex's form takes an option by digit only for `1`–`9`: `option_index_for_digit` maps one `char::to_digit` to an index, `0` and anything past the option count to nothing (`codex-rs/tui/src/bottom_pane/request_user_input/mod.rs` at `rust-v0.160.0`, read from source, not measured live). The tenth option on is reached only by moving the highlight (`Up`/`Down`/`j`/`k`, wrapping) and pressing `Enter`, which depends on where the highlight is; a digit does not. The deck cannot read the highlight, and no answer table or `answer_keys` path types a cursor key (they type digits and letters), so that path is not as deterministic as the digit and is not taken. `codex_request_user_input` therefore gives a form whose any question has more than `CODEX_DIGIT_OPTIONS` (9) options of its own the `unsupported` channel: the form is shown whole, nothing is offered, and `validate` refuses every answer to it as `Unsupported` before a countdown — options 1–9 included, so a user never hears a partial list and asks for an option that was never offered. Codex's appended None of the above is not counted: it is keyboard-only by table, so a nine-option question with it as a tenth stays answerable. `answer_keys` keeps refusing an index past nine as the backstop (`question/model/005`).

**OpenCode.** The plugin template (`src/opencode_manage.rs`) spawns `dot-agent-deck await-answer --agent opencode --ack` with `{session_id, event, properties, cwd}` as the first line of its stdin; Rust builds the event and the question (`opencode_permission_asked`, `opencode_question_asked`) and holds the socket; one stdout line is the decision, which the plugin maps (`opencode_reply`) and posts to `/permission/{id}/reply` or `/question/{id}/reply`. `permission.replied`, `question.replied` and `question.rejected` stop the child and are forwarded with `request_id`, which becomes `question_resolved_id`. A subagent's child session (issue #1678) takes the same path: its `permission.asked` and `question.asked` are filed under the root session with the child's `subagent_id`, held through `await-answer` like the root's, and become that subagent's `PermissionRequest` or `WaitingForInput` and question (`PendingQuestion::subagent_id`), so the card's Needs Input is the subagent's wait and the deck can answer it; its `permission.replied`, `question.replied` and `question.rejected` carry both `subagent_id` and `request_id`, and are marked replied (`PERMISSION_STATE_REPLIED`), so each ends that subagent's wait and clears its question (`question/hold/019`, `question/detect/017`). A `permission.asked` or `question.asked` the plugin cannot hold — one naming no request id, or whose child cannot be spawned — is sent plainly without `properties`, so the card still shows Needs Input and no question is raised. A reply whose `request_id` is absent or fails `is_valid_question_id` sets no `question_resolved_id` and so clears nothing, on purpose: a reply that does not name its question must never clear an arbitrary one, so that question waits for its deadline or for a frame that supersedes it (`build_opencode_event_with_question`). Two facts force this shape: the plugin input's `serverUrl` is not listening in TUI mode [observed], so the reply must come from inside the OpenCode process; and the plugin's v1 client has no question-reply method, so the plugin posts through `client._client`, **the SDK's underlying HTTP client — an internal, not an API**. It is wrapped in one function with that comment; an SDK release that renames or hides it breaks OpenCode answering while detection keeps working. A free-text answer posted through `/question/{id}/reply` is built from the documented types and has not been run against a live OpenCode.

**OpenCode's answer is reported only once OpenCode took it.** OpenCode's reply API can refuse the post (an error response, which the SDK reports as `error` rather than throwing), or there may be no client to post through, and the daemon has already cleared the question by then. So the plugin's child asks to acknowledge: its held message carries `ack` (`QuestionSignal::ack`), and after the decision line it reads one more stdin line — the plugin's `{"delivered": bool, "detail"?}` (`ReplyAck`) for what OpenCode made of the post — and writes it to the daemon on the held connection (`opencode_hold_acked_at`). The daemon's handler reads it within `HELD_REPLY_ACK_WAIT` (5 s; the child waits 4 s for the plugin, `AWAIT_ANSWER_ACK_WAIT`) and reports it to the `AnswerQuestion` handler (`ReplyDelivery`), which waits for it **after** its clearing event and **outside** the pane's lifecycle, so OpenCode's own `permission.replied`, forwarded while the plugin is still finishing, is never queued behind it. Taken → the answer succeeds. Refused → the answer is refused `write_failed` with the sanitized reason (`ReplyAck::detail_for_client`, 200 bytes), the pane's last-answered mark is lifted (`unmark_answered`), and the plugin raises the question again — unless OpenCode has meanwhile reported that request answered (`resolvedRequests`) — so it is pending in the deck once more and answerable (`question/hold/015`, `question/detect/007`). No report in time, an unreadable one, or a reply line the daemon could not write → `AnswerRefusal::Unconfirmed`: the agent may or may not have it, so the question is not offered again and the desktop says the answer may have been sent. Every other producer — Claude Code's hook, Pi's child — acts on the reply line itself, so the line being written is the answer delivered, as before, and a line whose write or flush failed is `Unconfirmed` for them too (`question/hold/020`). An answer the child cannot turn into OpenCode's reply is acknowledged as not taken and nothing is printed; the plugin then has nothing to re-raise, so that question is left to the keyboard.

**OpenCode's and Codex's "always" are shown whole too** (audit A2, PR #1561 review). OpenCode's `always` reply grants every pattern in `permission.asked`'s `always` list, so the confirmation lists them all, joined by `, ` (`opencode_always_scope`); an empty list, a pattern that is not exact (`scope_part_is_exact`: trimmed, no control or bidi character, no `,`) or a sentence the snapshot would cut (`scope_shown_whole`) makes **Allow always** keyboard-only, and `opencode_reply` sends no `always` for it. Codex's `p` grants a prefix Codex cuts from the command, so its confirmation names the **whole** command (`codex_prefix_scope`), taken from the hook's `tool_input`, not from `tool_detail`, which is its first line cut at 120 bytes; a command that is missing, spans lines, or cannot be shown whole makes `p` keyboard-only, and `answer_keys` refuses to type a keyboard-only option at all. Devin's "allow for …" options are keyboard-only by table (`question/hold/014`).

**Pi.** Pi asks no questions of its own. On every `session_start` inside a deck pane, the deck's extension replaces `ctx.ui.select`, `confirm` and `input` on the shared `ctx.ui` object with wrappers that mint an id, call the original with an `AbortSignal`, and start `await-answer --agent pi --question <json>` through `pi.exec`; whichever settles first wins, and the other is aborted. A caller's own `signal` aborts both and settles the call as Pi settles a dismissed dialog (`false` for `confirm`, `undefined` otherwise), even when the original dialog ignores the signal, so a later deck answer cannot win it; a signal already aborted settles it without starting either. The question lands on session `{pane_id}-session`, the one `agent-event` uses. **This is not a documented extension API.** It relies on `ctx.ui` being one object shared by every extension with writable methods, observed on Pi 0.87.1 only; Pi replaces that object when it rebinds its UI, which is why the wrappers are re-applied on every `session_start`. If a Pi release freezes or stops sharing the object, the guard leaves `ctx.ui` alone (no support, no crash), and `question/live/006` is what notices. A permission-gate extension calling `ctx.ui.confirm` from a `tool_call` handler reaches the same object [inferred]; `editor` and `custom` dialogs are not wrapped.

**Devin.** Built from its documentation, with no logged-in host to run it: `PermissionRequest` → `keys`, only Allow once (`\r`) and Deny (`\x1b`) answerable, every other documented option `keyboard_only`. Labels, order and both keys are unverified, and whether a running hook hides Devin's prompt is unknown, which is why the hook does not hold.

### Provenance: only an attested message carries question metadata

A question, and an agent's own "answered" marker (`question_resolved_id`), reach the daemon only inside a `question` message (`DaemonMessage::Question`), which passes the hook socket's provenance gate (`docs/develop/hook-provenance.md`) like every other verb (audit A9). Held questions always did; the ones the deck answers by keys — Codex's, Devin's, Claude Code's plan approval — and OpenCode's `permission.replied` / `question.replied` / `question.rejected` markers now leave `hook` as an **unheld** `question` message (`send_question_unheld_at`, `hold: false`) carrying the pane's hook token, and the daemon answers it with one `released` / `not_held` line as soon as it has applied it. The daemon stamps the event with the pane and agent the gate attested and treats that agent as the question's owner; a message the gate let through without attesting one (a pane it never issued a token to, or a missing token under `DOT_AGENT_DECK_HOOK_PROVENANCE=warn`) has its question metadata removed (`strip_question_metadata`). A **bare** `AgentEvent` — the route every status uses — has `pending_question` and `question_resolved_id` stripped on arrival whatever the raw-event gate decided, so it can still set a status but can no longer put a question on a card, or take one off by naming it, through that metadata. That is the whole of what the stripping covers: a bare frame's lifecycle **status** still clears a pending question exactly as `question_cleared_by` (`src/state.rs`) says — a main-thread `Idle`, `Error` or `SessionStart`, for example — and how far that status is trusted is the raw-event gate's verdict (issue #318, [`hook-provenance.md`](hook-provenance.md#raw-agentevent-traffic)), not anything on this page. A status for a pane this daemon issued a token to is admitted **attested** when it carries that pane's token from a generation that still speaks for the pane; one with no token is refused, except under `DOT_AGENT_DECK_HOOK_PROVENANCE=warn`, the compatibility escape hatch for an older `dot-agent-deck` in the pane, which admits it with weakened authentication: no token proves who sent it, and the daemon still applies it only when the agent it claims — or, naming none, some generation — still speaks for the pane. A status for a pane this daemon never issued a token to (an outside agent's) is admitted **unattested** on the sender's word and marked `daemon_unproven`, and is applied as an outside agent's report, with the limits that page lists.

The fallback keeps a status the card used to get. When no reply comes within `UNHELD_QUESTION_WAIT` (2 s) — an older daemon logs the message malformed and answers nothing — or the gate refuses it, the hook re-sends the event as a plain one without the question, so the agent still shows as waiting for input — **Needs Input** on a TUI card, **waiting** on the desktop dashboard — exactly as before the deck knew questions. Against an older daemon that costs each such hook up to 2 s, which on Codex delays its approval prompt by as much, since Codex draws the prompt only after the hook exits.

A **held** question has the same fallback, and needs one more signal to reach it, because a daemon that takes the hold also answers nothing until the hold ends. So every holding producer — Claude Code's `PermissionRequest` hook and the `await-answer` child the OpenCode plugin and the Pi extension run — sets `confirm_hold` on its `question` message (`start_hold_at`, `src/hook.rs`), and a daemon that registers the hold writes a `held` line at once (`QuestionReply::held`), before the reply that ends it. When no line comes within `HOLD_START_WAIT` (5 s), the connection closes first, or the first line is not a reply, the hold never started: the producer re-sends the event as a plain one without the question (`settle_hold`), exactly as for a provenance refusal. A hold that started and then ended without a reply sends nothing more, since the daemon already applied the event that raised it (`question/hold/021`, `question/hold/022`).

### Trust boundary

The daemon's local sockets trust the OS user, and nothing on this page changes that. Two consequences are worth stating because they are easy to over-read:

- **An attach client is trusted to supply the user's authorisation.** `AnswerQuestion`'s `confirmed_always` proves only that the client asserted a confirmation; the daemon cannot know one was shown. Any process that can open the owner-only attach socket can answer a pending question, always-allow included, without voice, countdown or dialog. The desktop's confirmation, countdown, grounding and lease are what make *its* answers deliberate; they are not a property the daemon enforces.
- **An installed extension or plugin is trusted too.** The OpenCode plugin and the Pi extension run inside the agent; a hostile Pi extension can replace the shared `ctx.ui` wrappers or resolve a dialog itself, and nothing in the deck can tell. A hostile-agent boundary would mean revisiting the decided OS-user isolation policy, not adding another secret to the agent's own environment.

What the provenance gate does close is the cheaper route for the question metadata: a same-user process that is not a deck pane's own producer can no longer raise or replace a question with a bare event, nor clear one by naming it in `question_resolved_id`. Clearing one through a lifecycle status under `question_cleared_by`'s rules takes what the raw-event gate demands of that status (above): the pane's token, or a missing token under `warn` that a speaking generation's claim still has to pass — not a new route.

## Matching an utterance to the options (desktop)

The desktop works out which options an utterance chooses (`desktop/src-tauri/src/voice/question.rs`), in this order, and every path ends in `validate` against the snapshot:

1. **The typing-mode switches** said on their own are not answers (`question/desktop/013`), and **a cancel phrase** calls off a started answer.
2. **A free-text option the form waits on** takes the utterance verbatim.
3. **`option_match::match_options`**, with no model call (PR #1698). The words are `spoken_words` (lowercase, punctuation gone) with `LEADING_FILLER` and `TRAILING_FILLER` phrases taken off the ends while something is left. The **current question** is the only one, or the first the form has not answered; once a multi-question form is fully answered there is none: a number then goes to the model, and labels and parts of labels are looked for on every question. In order:
   - **Whole label** — the label's words equal the utterance's, as said or without filler — on the current question, then on any other. A whole label wins over another label that merely starts with it ("Yes" over "Yes, and switch to auto mode").
   - **A number** on the current question, through `choice::ordinal` ("2", "two", "second", "option two", "number two", "the second one", "the last one"). It names the option whose `index` is that number — the number the agent draws, or its place in OpenCode's unnumbered row — **and** any option whose whole label is that number; two such options are ambiguous. A number naming none is refused with the options listed. A number the screen may draw beside more than one option, because an option before them is `maybe_hidden`, chooses nothing (`uncertain_number`, above).
   - **Part of a label** on the current question: the utterance's words, a leading article aside, appear in the label in its order, and at least one of them is not in `LITTLE_WORDS`.
   - **Several options** of a multi-select current question: the utterance split on commas and `JOINERS` ("and", "plus"), each part naming exactly one option by whole label, number or part. A part naming none leaves the whole utterance to the model rather than half-taking it.
   - **Part of a label on any other question.**
   Words are compared allowing a plural `s` (both words longer than three letters) or, in words of five letters or more, one letter changed, added or removed (`same_word`). At every step, more than one candidate is **refused** naming them with their numbers (`could_be`), never guessed — with one exception for parts of labels (`decide_part`): when the utterance is how every candidate's label begins (`leads`), the candidates are on one question, and exactly one of them is an answerable `allow_once` option, that one is chosen. So "yes" to Codex's approval, which begins "Yes, proceed" and "Yes, and don't ask again …", is "Yes, proceed", and OpenCode's "allow" is Allow once; the countdown names the option before it is sent. Allow-always, scoped and deny options never win this way: two candidates with no allow-once option, or two allow-once ones, or a word that starts one label and sits later in another, are still refused (`question/desktop/032`). A whole label still wins first, so Claude's "yes" is Yes by its whole label, as before. On a question the deck cannot answer (`answerable: false`), anything this step matches or refuses becomes the keyboard-only sentence instead, so such a question is never half-matched.
4. **The Commands model** for everything else, with its answer grounded in the transcript (audit A1).

Typing mode no longer keeps an utterance from the question (PR #1698): the webview offers every utterance to a waiting question (`answerQuestion`), typing mode or not, unless the pane shows another tab. In typing mode it asks for `localOnly` (`desktop_voice_question`'s `local_only`), which stops before step 4 — the user page promises that nothing said in typing mode reaches the Commands service — so there an option is answered only by its number or words. A `not_answer` then goes on as before, and in typing mode it reaches the dictation path, whose write is refused while the question waits with the options listed (`questionOptionsToSay`, `voiceQuestionNextStep`). The countdown names the option it will send by its label (`countdown_line`: "“Yes” (allow once) — …"), whichever channel then sends it; the progress line of a form names the next question's options with their numbers, since the agent draws only the question it is on; and reading mode ends a permission announcement with "Say 1 for Yes or 3 for No." — or "Say 1 for Yes, or say No." where No's number is not certain — from the event's question (`reading::options_sentence`), answerable options only. The TUI has no voice and matches nothing.

## Answering: `AttachRequest::AnswerQuestion`

`AnswerQuestion { agent_id, question_id, answers: [QuestionAnswer], confirmed_always, revision? }` is withheld by every client unless the daemon advertises `CAP_ANSWER_QUESTION` (`"answer-question"`), and the check lives in the client library (`DaemonClient::answer_question_while`), so the variant needed no `PROTOCOL_VERSION` bump ([`versioning.md`](versioning.md) item 1, CLAUDE.md rule 18). It returns `AnswerReport::{Withheld, Superseded, Answered, Refused(AnswerRefusal)}`. A refusal is answered `ok: false` — unlike `CloseAgents`, whose refusals are reports answered `ok: true`, here `ok: true` means the answer was delivered, and the client reads it first — and is carried as the additive `AttachResponse.answer_refusal`, so no client branches on error text: `AgentNotFound`, `NoPendingQuestion`, `Stale`, `InvalidAnswer`, `KeyboardOnly`, `AlwaysNotConfirmed`, `Unsupported`, `ChannelGone`, `WriteFailed`, `KeyboardStarted`, `Unconfirmed`, `AnswerInProgress`. An unknown code decodes as `Unknown`.

**Every answer is bound to one revision of the question** (audit A4). A question id is the producer's, so the same id can be registered again — a second hold for the same Claude Code prompt, a Codex re-raise with other content. The daemon therefore stamps each question with a **revision** of its own when it ingests it (`stamp_question_revision`, under the state lock that applies the event, before the fan-out), overwriting anything a producer sent: a held question takes the generation **its own registration captured**, carried into ingestion beside the event (`ingest_event_in_lifecycle`'s `registration`) rather than looked up in the hold map by id, and its event is not applied at all if that registration has since been superseded (audit R1, `question/hold/012`); a repeat of the pending question with the same id and content keeps the revision it has (and a keyboard-only channel the daemon set on it); anything else — including an unheld event that names a held id with other content — gets a fresh one from the same counter (`HeldQuestions::mint_revision`), and the hold it no longer describes is released. The revision rides the snapshot (`PendingQuestion::revision`, additive optional), the desktop sends the revision the answer was resolved against on `AnswerQuestion` (`DaemonClient::answer_question_while`), and the handler refuses `Stale` when the revision named is not the pending one — including a request that names none, since it cannot say which registration of a reused id it was worked out against (PR #1698 review). Whether or not the request names one, the handler binds its own delivery to the revision it validated against: a held reply goes only to the hold whose generation it is (`HeldQuestions::answer`), each key is queued on the PTY only while it is still the pending revision and written only if it still is when the PTY thread reaches it, and the deck's clearing event, the `ChannelGone` clear and the keyboard-only mark all name it — so a same-id replacement that registers between validation and delivery is refused as stale rather than answered with a choice made for the question it replaced (`question/answer/010`), for a held reply and for a key whose replacement is recorded before the PTY thread's check of it; one recorded after that check is the residual below. **A request that omits `revision`** (it is `#[serde(default)]` on the wire) is refused `Stale` whenever the pending question has one, and the daemon stamps one on every question it ingests for a pane. No released client sends `AnswerQuestion`, so no client relied on the id check alone. **One lock per pane serialises the question's lifecycle** (audit R1–R3): `QuestionAnswers::lock_lifecycle`. Each of these transitions holds it and re-checks the registration it acts on at the point it commits — a held question's registration and publication (`register_and_publish_held`, one acquisition, so no other transition ever sees a hold registered but not yet published); every event ingested for the pane (`ingest_event`, since any event can raise, replace or clear the question) and the hold reconciliation it ends with; the cleanup of a hold whose producer went or whose deadline passed (`drop_held_question`); a held answer from its revalidation to the deck's clearing event; and each answer key from its revalidation until the write is queued on the pane's PTY thread (`write_answer_keys`). **"Every event ingested for the pane" includes one that names no pane** (audit T2): such an event is applied to its session by id, and a session keeps its pane, so a bare `Idle` naming a pane-backed session can clear that pane's question. `ingest_event` therefore resolves a pane-less event to its session's pane, takes that pane's lifecycle, checks the resolution again under the `AppState` lock and retakes the lifecycle if a concurrent event moved the session, and reconciles that pane's holds and keys baseline after applying it (`question/answer/014`). A pane-less event whose session has no pane takes no lifecycle and is reported as before. **A key's lifecycle ends at the queueing, not the write** (audit T1): holding it across a PTY write would hold every event for the pane behind an agent that is not reading. Queue order orders the key only against other PTY jobs — not against an event ingested after it was queued — so the key carries the question id and revision it was checked against (`AnswerGate`), and the PTY thread, immediately before writing it, checks that this is still the pane's pending question in the record `QuestionAnswers::note_pending` keeps — updated, under the lifecycle and the `AppState` lock, wherever the daemon changes which question is pending on the pane: after every ingested event and after the two fallback clears that bypass ingestion (`drop_held_question`, and a held answer whose producer is gone). A replacement or clear applied while the key waited in the queue drops it unwritten, and the answer is refused `Stale` when nothing was typed yet (`question/answer/013`). **What remains** is a change landing after that check: once the thread has found the question unchanged it writes the key, so a replacement ingested in that instant receives it, as does one the agent draws with no hook at all (Risks). The next key's check detects an ingested change; a redraw with no hook changes neither the pending-question record nor the human-input counter, so it stays undetectable and can receive the later digits too. The **lock order** is the agent's answer slot → the pane's writer → the pane's question lifecycle → the `AppState` lock → the registry's own mutexes (the hold map, `QuestionAnswers`' maps, the registry's inner state); nothing holding the lifecycle waits on a writer or a slot, and the lifecycle is never awaited under the `AppState` lock. It is daemon-internal: nothing on the wire changed for it.

**One answer per agent at a time, and not the same question twice in a row.** The handler takes the agent's slot (`QuestionAnswers::slot`) before it first reads the pending question and holds it to its last write. It takes it with `try_lock` and never waits for it: a second answer to the same agent while one is being sent is refused at once with `AnswerInProgress` — nothing sent, the desktop says another answer is still being sent — rather than queued behind a delivery that may be slow (a held reply waits up to `HELD_REPLY_ACK_WAIT` for OpenCode's acknowledgement), after which its question would be gone or changed anyway (`question/answer/016`). The pane's last-answered mark (`QuestionAnswers::mark_answered`) records the **last** question the deck emitted an answer for there — its id and the revision answered. That revision is refused as `Stale` even if its clearing event never applied. When the answer is over, under the pane's lifecycle, the mark is **settled** (`settle_answered`) to cover the id at every revision, so the producer raising it again is refused too — unless the pane's pending question is then a same-id replacement at another revision, registered while the answer was being sent (between a key's write and the mark, say): that one was never answered, so the mark stays on the answered revision and the replacement is answerable (`question/answer/017`). A key answer that fails part way settles the same way. The mark is kept per pane, not in the slot, so pruning idle slots never forgets it. It is one mark per pane, not a history of every question answered: after the deck answers Q1 and then Q2 on a pane, Q1 raised again under its old id is no longer recognised as answered.

The handler checks, in order: the agent, that a question is pending, that its id (and the revision, when named) is the one answered, that the deck has not already answered it, the whole form (every question answered exactly once, indices in range, one option on a single-choice question, text only with a free-text option, `MAX_ANSWER_TEXT_CHARS`), `keyboard_only`, and that an `allow_always` comes with `confirmed_always`. The daemon cannot verify the confirmation was shown; refusing its absence means a client that skipped it must lie explicitly. Indices are resolved to the stored question by the daemon (`ResolvedAnswer` carries `option_indices`), and each producer maps them onto **its own** payload, never onto labels that crossed the socket, which are capped and may be truncated.

- **Held:** under the pane's lifecycle the handler re-checks that the validated revision is still the pending one and not already answered, then sends the reply down the held connection (`question_holds().answer`), only to the registration whose generation is that revision; if the producer is gone the question is cleared (that revision only) and the answer refused `ChannelGone`, and if another registration is pending now the answer is refused `Stale` and the replacement is left alone. The deck's clearing event is ingested before the lifecycle is let go, so a same-id question raised right after the answer is registered after that event and survives it (`question/hold/013`).
- **Keys:** `answer_keys` turns the answer into the table's keys — one digit per question for a Codex form — and `AgentPtyRegistry::write_answer_keys` writes each as the user's own keystrokes with no terminator, re-checking under the writer and the pane's lifecycle that the same revision is still pending and holding the lifecycle until the key is queued — so an event that replaces or clears the question is applied either before the check, and the key is refused, or after the key is queued (`question/answer/012`), in which case the PTY thread drops the key if the change is recorded before its check of the key (`question/answer/013`) and otherwise writes it, and the next key's check detects the change — with `ANSWER_KEY_GAP` (400 ms) between keys. Notice-mode writes were not usable: they append a newline. **The daemon owns the PTY's input but not the agent's dialog position**, so the keys channel refuses with `KeyboardStarted` whenever a human keystroke reached the pane after the daemon first saw the question's revision (`QuestionAnswers::note_pending`, recorded in `ingest_event`; `user_typed_since_question`): keys aimed at a form the keyboard half-answered, or a prompt it already dismissed, would land on the wrong question or in the composer. **The comparison is by sequence number, not by clock** (audit N1). `PaneInputState` keeps a human-input counter that only a human keystroke moves (the attach `STREAM_IN` path); the deck's answer keys are written as `ByteSource::Answer`, which stamps the user-input clock (they are the user's answer) but never moves the counter. The question records the counter when it arrives; each key's write returns the counter value it was committed at, read while the PTY writer is still held — and every human keystroke needs that writer too — so the next check (`human seq > committed`) cannot mistake a keystroke landing right after the deck's write for the deck's own (`question/answer/011`). The check runs before the first key and again under the writer before every one. When a write is refused or fails after some keys went in, the question stays pending but its channel becomes `Unsupported` (`mark_pending_question_keyboard_only`), so no client offers the half-typed form again, and the refusal says to finish by keyboard.

**The deck's own event after an answer** clears the question in the daemon and every attached client. It is `Thinking` when the answer lets the agent carry on, and a status-less `Unknown` when it includes a deny (review S3): a deny ends or interrupts the turn rather than starting work, so the agent keeps showing as waiting for input (**Needs Input** in the TUI, **waiting** in the desktop app) for the moment until the agent's own next event says where it went.

**Where the keys channel's baseline comes from, and why Codex forms stay answerable by keys.** The baseline is when the daemon ingested the question, not when the agent drew it, so a keystroke made between the two would not be counted. For Codex that interval does not reach the user: the question comes from a hook Codex runs **before** it shows the prompt — the approval's `PermissionRequest`, whose running hook hides the prompt until it exits [observed on 0.160.0], and the `PreToolUse` for `request_user_input`, which runs before the tool that draws the form [inferred from the hook's name and order; not separately measured] — and the hook now sends the question as an unheld `question` message and waits for the daemon's acknowledgement (`send_question_unheld_at`) before it exits. So the daemon has ingested the question, and recorded its baseline, before Codex shows anything the user could type into. That is why whole-form Codex answers stay on the keys channel rather than becoming keyboard-only. **What the acknowledgement does and does not prove.** A successful acknowledgement orders the daemon's ingestion of the question — and its baseline — before the hook exits, and so before Codex draws anything. A **timeout** proves nothing about ingestion: when no acknowledgement arrives within `UNHELD_QUESTION_WAIT` the hook sends a plain event without the question, but that plain event does not retract or invalidate the question envelope already sent, and a plain `PermissionRequest` or `ToolStart` is not a question clear. So a daemon that applied the envelope and whose reply was delayed or lost, or one that ingests the queued envelope only after the hook gave up, can still hold the question as answerable by keys. **That is an accepted residual of keeping Codex on the keys channel, not something the deck prevents:** in the late-ingestion case Codex may already have drawn the prompt and taken keystrokes before the daemon recorded its baseline, so those keystrokes are not counted. It needs an acknowledgement slower than `UNHELD_QUESTION_WAIT` from a daemon that does ingest the message; making the fallback a guarantee would take an explicit invalidation or expiry of the envelope and a delayed-daemon test, neither of which exists. Against an older daemon, which logs the message malformed and never ingests it, the question is genuinely not answerable by voice. And an agent that moves its own dialog with no keystroke and no hook is invisible to the deck (Risks).

### Held connections

Holds are keyed by the pane that raised the question and its id, carry the agent the provenance gate attested, and are answered only for that pane and agent (audit A5): a question id is the producer's own, so two panes can share one. Each registration gets a generation — the question's revision — and a handler lets go of its hold (`forget`) only while its generation is the one in place, so a superseded handler whose connection closes late cannot drop the hold that replaced it. **The cleanup runs under the pane's question lifecycle and is revision-checked too** (`drop_held_question`): its `forget`, its release event and its fallback clear hold the lifecycle together, so a same-id replacement registers either before the cleanup — whose `forget` then finds the generation replaced and stops — or after it, never with its hold registered but not yet published. The release event is still applied only if the pane's pending question is that revision under the state write lock that applies it, and the fallback clear names the revision (`clear_pending_question_revision`), so a cleanup never clears by a reused id alone and the replacement keeps its question, its hold and its own answer (`question/hold/011`). **Reconciliation is registration-aware** (audit R3): after every ingested event, `release_pane_except` keeps only the hold whose id **and** generation are the pending question's id and revision, so no clear keeps a hold on the strength of its id alone. **A question from a session the pane has moved past is not applied** (`AppState::strip_superseded_question`, called in `ingest_event` under the `AppState` lock before the revision stamp and the fan-out): a late question event from the conversation before a `/clear` — an OpenCode `question.asked`, say — carries a fresh timestamp, so applied it would become the newest pending question on the pane and reconciliation would release the live question's hold. The superseded sessions are the ones issue #447's waiting watch already records per pane (`waiting_superseded_sessions`); the rest of the event is applied as before, and no client is sent the question (`question/hold/017`). **The pane's pending question is its current session's or none** (`AppState::pending_question_on_pane`): the current session is the pane's newest card, ties broken on the session id as `live_session_for` breaks them, so a question left on an older card beside a newer one with no question — a session switch that did not retire the old card — is not the pane's, and the next reconciliation releases its hold (`question/hold/018`).

A held connection gives its slot in the hook pool (`MAX_CONCURRENT_HOOK_CONNECTIONS`, 32) back as soon as the hold is registered and waits under a budget of its own, `MAX_HELD_QUESTIONS` (64), so waiting prompts never queue the `PostToolUse`, status and orchestration hooks behind them (audit A6). A question raised past that budget is applied without its question — Needs Input, answered by keyboard. That includes a same-id **replacement** raised while the budget is full: it is refused a hold before its predecessor's is released, which is a conservative refusal (the prompt is answered by keyboard), not a bypass. The daemon also enforces `QUESTION_HOLD_DEADLINE` (3720 s, past both producers' own deadlines): a hold still waiting then is released, the question cleared, and the release broadcast, exactly as when the producer's connection closes. While it waits, the daemon reads at most 1 KiB from the connection, since any byte from a holding producer means it is gone.

**A question connection carries one request and ends with its reply** (audit A6/N2) — answered, released, superseded, not held, or released at the deadline. A held connection has given its pool slot back and its hold budget goes with the handler, so a socket kept open past the reply would otherwise go on reading and dispatching lines outside both bounds. Every first-party producer already sends one request per connection and reads one line: the Claude Code hook (`hold_question_at`), the `await-answer` child the OpenCode plugin and the Pi extension run, and the unheld Codex/Devin/plan path (`send_question_unheld_at`), whose plain fallback opens a connection of its own (`question/hold/008`).

## Compatibility

Rule 12's answer for the PRD is no `PROTOCOL_VERSION` bump and no semantic break: the snapshot field and the refusal field are additive optional, the request is capability-gated, and the release broadcast is an ordinary `AgentEvent` with an `event_type` every build decodes. The audit fixes kept that answer: `AnswerRefusal::KeyboardStarted` is one more code in an enum whose unknown codes decode as `Unknown`; the deck's answered event for a deny is an `unknown` event, which an older client reads as a no-op; and none of `pending_question`, `question_resolved_id` or `answer-question` exists in any release, so stripping the first two from bare frames changes nothing a released build relied on. On the hook socket, a newer hook binary sends unheld `question` messages that an older daemon logs as malformed, and falls back to the plain event after 2 s (above); an older hook binary's bare question frames reach a newer daemon as plain statuses, so that pane's questions are answered by keyboard until the hook binary is updated. A held `question` frame sent to an older daemon is logged malformed there too, and that daemon answers nothing and keeps the connection open until its 60 s idle bound (`v0.46.0:src/daemon.rs`, the `Malformed event` arm of the hook loop): with no `held` line within 5 s the producer gives up and sends the plain event (above), so the card reads Needs Input and Claude Code shows its own dialog after about 5 s. Before PR #1698's review it showed no Needs Input at all. `confirm_hold` is an additive, default-false field and `held` one more `ReplyOutcome`, on a message no release has, and a daemon writes `held` only to a producer that asked for it. One meaning did shift: Codex's `request_user_input` and OpenCode's `question.asked` now raise **Needs Input** where they used to read **Working**, which an older TUI attached to a newer daemon also shows — the correct reading, so it was not classed as a break. The second audit round kept the answer as well: `PendingQuestion::revision` and `AnswerQuestion`'s `revision` are additive optional fields on structures no release has, a request that omits the revision is refused as stale (above) — which no released client can meet, since none sends `AnswerQuestion` — and closing a question connection after its reply matches the one-request contract every producer already follows. The third round (audit R1–R3) changed nothing on the wire: the per-pane question lifecycle, the registration generation carried into ingestion and the registration-aware reconciliation are daemon-internal, and no message, field, capability or meaning a client reads moved. Its one observable effect is ordering — an event for a pane, or one naming no pane whose session is on that pane, can now wait behind a question transition on that pane for as long as it holds the lifecycle: a key's revalidation and enqueue, a held question's registration and publication, a held answer from its revalidation to its clearing event, or a cleanup. A synthetic driver that waits for the hook CLI to exit on a `PermissionRequest` now deadlocks against a daemon that holds it; `tests/subagent_tool_status.rs` and `tests/e2e_hook_delivery.rs` were changed for that. The PR #1561 review fixes kept the answer too: `QuestionSignal::ack` is an additive, default-false field on the held `question` message, which no release has; `AnswerRefusal::Unconfirmed` is one more code that an older client decodes as `Unknown`; and `await-answer --ack` is a flag only the plugin template written by the same binary passes, so a plugin installed before it runs the child without it and gets the old, unacknowledged behaviour. The second review round (Qodo, PR #1561) kept it again: `AnswerRefusal::AnswerInProgress` is one more code an older client decodes as `Unknown` ("refused", which is accurate — nothing was sent); the revision-scoped answered mark and the superseded-session question gate are daemon-internal; and refusing a concurrent answer at once instead of queuing it changes how a second answer to the same agent ends while the first is in progress — before, it waited for the first and was then checked against whatever question the first left pending — not any message or field. The third review round (Qodo, PR #1561) kept it once more: which session a pane's pending question is read from, the Pi wrapper's cancellation and the question tests' daemon cap are each internal to the daemon, the Pi extension or the test harness, and no message, field or meaning moved. PR #1698's follow-up added `QuestionOption::maybe_hidden`, an additive field skipped when false and read as false when absent: an older desktop ignores it and handles Claude's prompt as before (the auto-mode entry is keyboard-only either way), and a newer desktop attached to an older daemon sees no mark and numbers every option as before (`question/model/008`).

## Risks

- **A misheard "yes" approves something.** Bounded on the desktop by [`voice-first-design.md`](voice-first-design.md) §10: the model picks only listed option numbers, the app validates them against the snapshot, the answer is shown with a cancellable countdown, and the daemon refuses a stale or changed question.
- **The model can pick the wrong option for real words — accepted** (audit A1). Grounding proves the words it cites were said, not that they mean the option: an Allow once quoting "what time is it", or the "run that" of "no, don't run that", is armed. Accepted rather than closed by a second confirmation on every approval; what bounds it is that the countdown shows exactly what will be sent, speech and Cancel stop it, and always-allow keeps its own confirmation word ([`voice-first-design.md`](voice-first-design.md) §10).
- **Agents change their prompts.** The tables above are per verified version, and only lane 2 checks them.
- **Pi's channel is undocumented**, and **OpenCode's reply goes through an SDK internal**; either can break on an agent release while detection keeps working.
- **A held hook can outlive its question.** On Claude Code a keyboard Yes does not end the waiting hook [observed]; the daemon releases it on the tool's `PostToolUse`, and one that is never released waits out `CLAUDE_HOLD_DEADLINE`, and in the daemon `QUESTION_HOLD_DEADLINE`.
- **Voice writes nothing into a pane whose agent waits on a question, checked at the write's turn.** In a waiting dialog a key can pick an option, so `questionWaiting` (`desktop/src/components/VoiceControlPanel.tsx`) refuses a dictation's words, an Enter (a spoken send, a trailing one, the countdown), a prompt command's keys and an Undo's words while the open pane's agent has a pending question, and the refusal's advice comes from one helper (`questionReach`, `voiceQuestionNextStep`): voice only where `answerQuestion` would offer the utterance to the question, otherwise "say “type off”", "open its terminal" or the keyboard. The hidden-terminal wording is defensive: every writer's pane gate (`contextLost`'s `hidden`) refuses a hidden terminal before this check runs. A dictation's write and an Enter check when their turn on the pane's write line comes, not again when the bridge hands the bytes to the daemon, so a question the snapshot reports in between — the write waiting behind the user's own keystrokes still in flight — is not caught there; prompt commands and Undo check again at the bridge (`guardedSend`).
- **The keys channel cannot see the agent's dialog.** It refuses once the user has typed into the pane since the question arrived, which also refuses an answer after the user typed something unrelated there; the residual it does not close is the agent itself moving its dialog on with no keystroke and no hook.
