# The directory-listing verb

PRD [#1223](https://github.com/vfarcic/dot-agent-deck/issues/1223) M1. This page records `AttachRequest::ListDirectories` — the daemon verb behind the desktop's new-agent directory step — its bounds, and the threat-model argument for adding a listing verb after PRD #819 had deliberately stopped at resolving one path. The mechanism lives in [`src/directory_listing.rs`](../../src/directory_listing.rs), whose module docs carry the bounds next to the code; the wire variant and its dispatch arm are in [`src/daemon_protocol.rs`](../../src/daemon_protocol.rs), and the client method is `DaemonClient::list_directories` in [`src/daemon_client.rs`](../../src/daemon_client.rs).

## Why a daemon verb

The TUI's Ctrl+n opens a directory picker that reads the TUI process's own filesystem. The desktop cannot do that for a deck: against a remote deck the desktop's filesystem is not the one the agent will run in, and even for a local deck the path an agent starts in has to be one the daemon can use. So the directory step asks the daemon, one level at a time, and sends back only paths the daemon supplied or the user typed — PRD #819's rule. The desktop never joins a listed parent and a child name itself.

## What it answers

The request is `{"op": "list-directories"}` with an optional absolute `path`, and — since issue [#1240](https://github.com/vfarcic/dot-agent-deck/issues/1240) — three optional fields that widen or narrow the listing (see *The listing options* below). With no `path`, the daemon lists the daemon user's home directory, canonicalised — not its startup cwd, which for a lazily spawned daemon is wherever some TUI happened to be launched.

A successful reply carries `ok: true` and a top-level `directories` object:

| field | meaning |
| --- | --- |
| `path` | the canonical absolute path that was listed (a typed symlinked spelling lists — and names — its target) |
| `parent` | the canonical absolute path of its parent; absent at the filesystem root, and the only "up" there is — there is no `..` entry |
| `entries` | `{ name, path, is_project }` per immediate subdirectory, sorted by name; `path` is canonical and joined by the daemon — or, for a symlink listed on request, its target's canonical path, with `is_symlink: true` (the key is omitted otherwise) |
| `truncated` | `true` when the entry cap or the time budget cut the listing short |

`is_project` is `true` when the subdirectory holds a `.dot-agent-deck.toml` that is a regular file and not a symlink — the same two type refusals the project reader (`project_resolve::read_config_file`) applies to that file. It is a hint for the form, which then asks `ResolveProject` for orchestrations; it is one `lstat`, not a parse, so a marked directory whose config is oversized or malformed still fails that request.

## The bounds

The list is carried from issue #1048 and each item is enforced in `src/directory_listing.rs` rather than trusted to a caller:

- **One level per request.** One `read_dir`; nothing recurses or walks.
- **Directories only.** An entry carries a name, a canonical path and the project marker. No files, sizes, times, owners or modes reach the reply.
- **Hidden entries are skipped and symlinked entries are not listed unless the request asks for them** (issue #1240, below); by default this is what the TUI's picker does: a name starting with `.` is dropped, and an entry is kept only when `DirEntry::file_type()` — which does not follow a symlink — reports a directory, and is reported only when an `lstat` taken as the reply is built still does (audit A3; see *A point-in-time snapshot* below). A symlink the user *types* is different: the typed path is canonicalised, so it lists the target.
- **A result cap**, `MAX_DIRECTORY_ENTRIES` = **1000**. Past it the reply carries the 1000 smallest names and `truncated: true`. Scanning continues within the time budget so the survivors are a sorted prefix rather than whichever names `readdir` produced first — the smallest of the whole directory when the scan finishes inside the budget, and of the part it reached when the budget cuts it; memory stays at one name more than the cap.
- **A time budget**, `DIRECTORY_LISTING_BUDGET` = **2 s**, measured from the start of the request's filesystem work. When it runs out the reply is what was gathered, with `truncated: true`. It is checked between entries and between marker probes, so it does **not** interrupt one system call that blocks — a `readdir` or `stat` on an unresponsive network mount takes as long as it takes. What contains that case is the concurrency bound below, not this deadline.
- **A concurrency bound of its own**, `new_agent_options::MAX_CONCURRENT_NEW_AGENT_QUERIES` = **4**, shared by `ListDirectories` and `NewAgentOptions` and by nothing else (audit A4). The permit is taken with try-acquire: when all four are held the request is refused at once as `busy` (below) instead of waiting, so at most four blocking threads are ever occupied by these two verbs, and none of them is one of the project verbs' `MAX_CONCURRENT_PROJECT_READS` permits — a burst of listings against a slow directory cannot hold `ResolveProject` or `PrepareWorkflow` up. The listing first ran under the project verbs' permits and the options query under none; both of those are gone.
- **Canonical, absolute paths both ways.** A caller path must be absolute, non-empty, at most 4096 bytes and free of ASCII control characters — the same predicate `ResolveProject`'s boundary check applies — so `relative/path` and `./x` are refused before any filesystem access rather than resolved against the daemon's cwd. The accepted path is canonicalised by the same helper the project reader uses, which also refuses a non-directory and a canonical form that is not UTF-8. An entry whose own name is not UTF-8 is skipped, because this JSON wire cannot carry it and a lossy spelling would be a path the caller could not send back. So is a subdirectory whose joined path fails the stricter **authoring-path predicate**, `authoring_seeds::is_safe_authoring_path` (audits A2 and D1): that caller-path predicate, plus a refusal of every `char::is_control` character (C1 as well as C0, so U+0085 NEXT LINE), U+2028 LINE SEPARATOR, U+2029 PARAGRAPH SEPARATOR, and the bidi formatting characters `untrusted_text::is_bidi_format_char` names (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069). So a subdirectory named with LF, CR, ESC, NEL, a Unicode line separator or a bidi override, or joined past 4096 bytes, is not listed, and every child entry's `path` is one an authoring start would accept back. That filter covers the child entries only (audit F8): the reply's own `path` — the canonical form of what the caller typed, or the home directory — and its `parent` are returned without it, so either can name a directory an authoring start refuses, for instance when a typed symlink resolves to a target whose name carries one of those characters. The start is not relying on the listing for that: `authoring_seeds::seed_for_start` checks the `cwd` it is actually given against the same predicate and refuses it before spawning, whichever listing the path came from. The filter runs before the cap, so a dropped name never takes a slot. The stricter half is needed because the caller-path predicate inspects bytes, and each of those characters spells as non-ASCII UTF-8, so it walks past a test for ASCII controls. Non-ASCII outside those classes — `café`, `日本` — is an ordinary name and is listed. The predicate refuses and never rewrites, because an escaped spelling would name a different directory. That matters beyond this verb: an authoring `StartAgent` (`authoring_kind` present) writes its `cwd` verbatim into the agent's seed, and the daemon refuses one whose `cwd` fails the same predicate, before spawning; a plain `StartAgent`'s `cwd` rules are unchanged. The desktop's display sanitizer (`desktop/src/lib/displayText.ts`) also drops U+2028 and U+2029 from what it renders — the one place it is wider than the Rust `strip_control_and_bidi` policy, because a webview can break a line on them and a terminal does not — since a deck predating D1 can still list such a name.

## The listing options

Issue [#1240](https://github.com/vfarcic/dot-agent-deck/issues/1240) found three kinds of directory the browser could not reach once PR #1235 removed the typed-path field: hidden ones, symlinked ones, and any past the entry cap. The typed path was the way around all three, and it was removed on purpose — it had to be absolute, which was tedious, and its main justification was a deck too old to list — so rather than restore it, the listing gained three optional request fields, each off by default:

| field | effect |
| --- | --- |
| `include_hidden: true` | a child whose name starts with `.` is listed too |
| `include_symlinks: true` | a child that is a symlink to a directory is listed too — under its own name, with its target's **canonical** path and `is_symlink: true` |
| `filter: "<text>"` | only children whose name contains the text, compared case-insensitively (the TUI picker's `refilter` rule), are kept — and the filter is applied **before** the cap |

**The symlink policy follows the reader's.** A listed symlink is resolved with the same canonicaliser a caller-supplied path goes through (`project_resolve::canonicalize_project_dir`: it must lead to a directory, and its canonical form must be UTF-8), and that canonical target must pass the authoring-path predicate the children do. A dangling link, a link to a file and a link whose target fails either check are not listed, and the resolution happens during the scan, so none of them takes a slot under the cap. The reply names the **target**, not a path through the link, which keeps "every path in the reply is canonical" true: entering a listed link lists its target, and "up" from there is the target's parent — exactly what a typed symlinked path always did. The project marker reported for a link is its target's, read with the same `lstat` rule (a symlinked `.dot-agent-deck.toml` inside the target still marks nothing). PRD #1223's open question 2 had chosen to mirror the TUI here; a GUI whose only way to reach a directory is to list it is the reason to revisit that, and the TUI's own picker is unchanged ([`tui-desktop-parity.md`](tui-desktop-parity.md)).

**The filter narrows before the cap, so it reaches past it.** With a filter, `MAX_DIRECTORY_ENTRIES` bounds the *matches*, and `truncated` means more matches exist than were returned. It does not reach past the time budget: a directory so large that the 2 s budget cuts the scan is searched only as far as the scan got, and the reply says `truncated` either way. The filter is refused as `invalid-path: …` (the code this verb already uses for a malformed argument, with a sentence that names the filter and does not echo it) when it is over `MAX_DIRECTORY_FILTER_LEN` = **255** bytes, or carries a control character or a path separator — a separator is in no file name, and a name with a control character is never listed. An empty filter filters nothing.

**The desktop's use of them.** Against a deck that honours them, the New agent browser always asks for symlinks (they render as a `link` row), asks for hidden directories while its **Show hidden** control is on (the list's `.` key toggles it), and — only when a listing came back `truncated` — sends its filter to the deck once typing pauses, so the deck searches the whole directory; a listing that was not truncated is complete and is filtered in the webview with no round trip.

**They add no authority**, for the reason the verb adds none (*Threat model* below): a peer that can send them can already `StartAgent` `ls -la` in any directory, hidden or linked. They do add work per request — one `realpath` per symlink in the scanned directory — which the existing time budget and concurrency bound contain.

## A point-in-time snapshot

A reply describes the directory as the request saw it, not as it stays. The scan chooses names from one `readdir`, and each chosen name is looked at again with `lstat` when the reply is built, so a child that was swapped for a symlink, replaced by a file or removed between the two is dropped instead of being reported as a real directory. A listed symlink gets the same re-check in two halves — the name is still a symlink, and the target the scan resolved is still a real directory — so a link removed, or a target swapped for a file or a link, in between is dropped too; a link re-pointed elsewhere in between is inside the residual this section describes. That narrows the window to the moment of that re-check; it does not close it. A change after the re-check, or racing it, is not prevented — the daemon holds nothing open against mutation, and a path in the reply can name a symlink, or nothing, by the time a client sends it back. Descriptor-relative no-follow operations (`openat` with `O_NOFOLLOW` from a held directory handle) would narrow it further and were declined as disproportionate at today's trust boundary: every peer that can send this verb can also send `StartAgent`, which takes its `cwd` as a string rather than a handle, so the consumer of a listed path is in the same position whatever the listing does (see *Threat model*).

## Refusals

A refusal is the ordinary `ok: false` with an `error` string, and apart from `busy` (below) it reuses the project verbs' codes rather than adding new ones. A malformed path answers `invalid-path: …`. Anything that goes wrong once the filesystem is consulted — no such path, not a directory, not readable, a non-UTF-8 canonical form — answers `unresolved:` followed by one fixed sentence that names no path and carries no OS error, so the reply does not tell a missing path from a regular file. That is the shape `ResolveProject` gives an arbitrary caller-supplied path; the sentence differs only in its noun, because this verb resolves a directory rather than a project. As with that verb, no timing property is claimed: the cases do observably different amounts of work.

One refusal is about the daemon rather than the request: `busy: …` means the new-agent query pool was full, nothing was read, and the same request sent again once an earlier one finishes is answered normally. `NewAgentOptions` returns it too, under the same code and sentence.

## Threat model

**What a caller learns that it could not learn before: nothing, for any caller that can reach the attach endpoint today.** The same endpoint accepts `StartAgent` with an arbitrary command and working directory, executed as the daemon's user — see the trust-boundary note on `AttachRequest::StartAgent`. A caller that can send `ListDirectories` can already start `ls -la` anywhere that user can read and receive its output over `AttachStream`. The verb adds a **structured, bounded** route to information the endpoint already exposes. It adds no authority.

That is the honest answer to PRD #819's "resolve-only, never list" bound. That bound constrained the project verbs, whose purpose was naming projects, and it was never what stopped enumeration — `StartAgent` was always the larger capability on the same wire. `ResolveProject` itself is unchanged and stays resolve-only; its doc comment now points here.

**It is not a reason to leave the verb unbounded.** #819's audit recorded that bounding the project verbs is not a substitute for authentication if PRD #741 ever admits a peer with less than full account authority, and the same holds here. The bounds above exist for robustness — a huge or slow directory degrades to a partial listing rather than a stalled request — and so that the verb's surface is already small when that day comes. **If such a peer is ever admitted, this verb must be re-examined alongside `StartAgent`, not after it.**

## Cross-version

The verb is on CLAUDE.md rule 18's capability-gated rung, so it contributes no `PROTOCOL_VERSION` bump. The daemon advertises `list-directories` in `DAEMON_CAPABILITIES` on every platform (the dispatch arm is not `#[cfg]`-gated), and `DaemonClient::list_directories` checks the advertised set itself and returns `GatedQuery::Unsupported` **without sending the request** when it is absent — including against a daemon that advertises no capabilities at all. No call site needs its own check. A sender that skips the client library and sends the frame to an older daemon gets that daemon's generic `malformed request: …` refusal and no listing, which fails closed. No existing field changes meaning: the reply's `directories` field is additive and optional and appears on no other response.

**The listing options (issue #1240) are on the same rung, gated on their own capability, `list-directories-options`.** They are fields rather than a verb, like `authoring-kind`, and for the same reason: serde drops an unknown key on `list-directories`, so a daemon from before them would answer a filtered request with an unfiltered listing and report success. `DaemonClient::list_directories` takes the options and answers `GatedQuery::Unsupported` without sending anything when they are not the default and the daemon does not advertise the capability; the desktop crate turns that into a sentence ("This deck cannot show hidden or symlinked directories…") rather than the "cannot list" answer, and its connection DTO carries `listingOptions` so the dialog offers none of it on such a deck in the first place. The check uses the cached handshake: the residual — a cached set outliving a daemon replaced by an older build — gets the PRD #1223 listing that build always gave, a degradation rather than a wrong answer the webview could not catch, since it filters what it shows anyway. The reply's `is_symlink` is omitted when `false` and is only ever `true` in answer to a request that set `include_symlinks`, so an older client never sees it. No `PROTOCOL_VERSION` bump, and no `.breaking.md`: a request that sets none of the fields is answered exactly as before.

The sibling query `NewAgentOptions` (PRD #1223 M2, capability `new-agent-options`, `DaemonClient::new_agent_options`) is gated the same way. It reads no caller-selected path — it reports the daemon host's `DashboardConfig.default_command` and `default_dir`, the compiled agent registry and the daemon's experimental flag — so it has no threat model beyond this one. `default_dir` is the one path in it, and it is the operator's own setting rather than a caller's: it passes the same boundary predicate and canonicaliser a listing path does, and is omitted (never an error) when it fails either or does not open. It runs in the pool above, and it reads `config.toml` with `DashboardConfig::load_bounded` rather than the TUI's `load`: the open is non-blocking so a FIFO at the path cannot hold the thread, only a regular file is read (a symlink to one is followed, as `load` follows it), and at most `MAX_DASHBOARD_CONFIG_BYTES` (1 MiB, the project-config reader's cap) — anything else answers with the defaults, so `default_command` is absent, and logs why without echoing the file.

## Tests

- `src/directory_listing.rs` unit tests: sorted one-level listing with canonical paths, hidden and file entries skipped, symlinked entries not listed while a typed symlink resolves to its target, a kept child swapped for a symlink, replaced by a file or removed between the scan and the reply dropped (through a test seam on the internal function, not a production knob), children whose names carry LF, CR, ESC, DEL, NEL, U+2028, U+2029 or a bidi override not listed and never taking a slot under the cap while an ordinary non-ASCII sibling is, the project marker's type policy, relative-path refusal, one generic refusal for a missing path and a regular file, the cap keeping the smallest names with `truncated`, an exhausted budget returning a partial listing, the root having no parent, a non-UTF-8 name skipped (Linux), and the wire shape.
- `src/daemon_client.rs`: both queries withheld, and never sent, against a daemon advertising no capabilities and against one advertising everything up to `focus-gained`; both answered by the real dispatch at this build; and, with the new-agent pool saturated, both refused as `busy` at once while `ResolveProject` on the same daemon still resolves.
- `src/new_agent_options.rs`: a full pool refuses the next query without spawning it rather than queueing it, and the permits return when the holders finish; with the daemon-wide pool saturated, `project_resolve::run_bounded` still acquires.
- `src/config.rs`: the bounded config read parses an ordinary file and one behind a symlink, and answers the defaults for a missing, malformed or oversized file and — without blocking — for a FIFO, directly or behind a link.
- `src/daemon_protocol.rs`: both capability strings advertised and equal to their `op`; request and reply wire shapes.
- `src/authoring_seeds.rs`: the authoring-path predicate refuses each class above — every C1 control and bidi formatting character is enumerated, each shown to pass the byte-level predicate alone — and accepts ordinary non-ASCII names (`café`, `日本`, emoji, a zero-width joiner, a non-breaking space); an authoring start whose `cwd` carries LF, CR, ESC, DEL, NEL, U+2028, U+2029 or a bidi override, or is relative, is refused for every kind without echoing the path; `src/daemon_client.rs`: through the real dispatch, such a start is refused and starts nothing while a plain start with the same `cwd` still starts.
- `src/directory_listing.rs`, issue #1240: a hidden child listed only with `include_hidden`; a directory symlink listed by its canonical target and marked, a dangling link and a link to a file not, and entering the listed path lists the target; a link whose target's path fails the authoring predicate not listed; a listed link removed or whose target became a file between the scan and the reply dropped; the filter applied before the cap, case-insensitively, with `truncated` describing the matches; a malformed filter refused before the filesystem. `src/daemon_client.rs`: the options withheld from a daemon advertising `list-directories` but not `list-directories-options` while a default listing is still sent, and all three honoured by the real dispatch. `src/daemon_protocol.rs`: the fields omitted when unset, round-tripping when set, and the capability advertised.
- `tests/e2e_new_agent_queries.rs` (lane 1, headless `daemon serve`): `newagent/browse/001`, `newagent/browse/002`, `newagent/browse/003` (children named with ASCII controls, NEL, U+2028, U+2029 or a bidi override not listed), and issue #1240's `newagent/browse/004` (hidden), `newagent/browse/005` (symlinked, by target) and `newagent/browse/006` (a filter reaching a directory past the cap) in [`tests/CATALOG.md`](../../tests/CATALOG.md); `tests/e2e_authoring_seed_delivery.rs`: `newagent/authoring/003` (an LF, NEL, U+2028 or bidi-override `cwd` refuses the authoring start, and a plain start with a control-byte `cwd` still starts).

What none of them forces is a real time-budget truncation against a live daemon: the budget has no injectable clock at the wire, so the budget path is covered at the function level with an already-expired deadline.
