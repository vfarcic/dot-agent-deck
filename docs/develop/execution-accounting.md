# Execution accounting: signals, record and outcomes

This page is the evidence for PRD #633's discovery milestones: which signals each supported agent exposes about a run, a minimal provider-neutral record built from them, and an outcome taxonomy checked against runs that already happened in this repository. It builds on PRD #1741, which shipped the deck's OpenTelemetry run traces ([`telemetry.md`](telemetry.md), the user page [`docs/telemetry.md`](../telemetry.md), `src/telemetry/`), and on #1692's resource measurements, folded into #633. It is a discovery record written on 2026-10-23, not a description of shipped behaviour: beyond what #1741 shipped, the only code behind it is milestone 4's prototype ([below](#prototype-results-milestone-4)), which is compiled for tests only and which nothing in the product calls. Milestone 5's outcome, Revise, is recorded [below](#decision-milestone-5).

PRD #1858 builds on the prototype described here; its design, and what of it is built, are in [Usage and how a run ended](telemetry.md#usage-and-how-a-run-ended-prd-1858). Statements below about the prototype describe it as of 2026-10-23.

**Privacy.** The extraction scripts whose output this page reports read only the fields named above, plus the working directory and timestamps that place a session in the cohort; they did not read message content, tool inputs or outputs, prompts, file contents or OpenCode's error bodies, and they kept only aggregates. The re-derivation on 2026-10-23 parsed Claude Code's, Codex's and Pi's JSON records to reach those fields, so content passed through its memory as it does through the prototype's reader, and it kept and printed only counts; it extracted OpenCode's per-message fields inside SQLite (`json_extract` of the named keys), so no message body left that database. Session ids appear on this page as the first eight hex digits of a SHA-256 of the id or file path. Worktree names appear because they name this repository's issues and pull requests. The scripts were throwaway and are deliberately not committed: they walk four agents' private stores and would have no consumer, so the cohort and field selection above are what reproduces them. The prototype's overhead driver, which reads only Codex rollouts and prints aggregates, is committed ([overhead](#overhead)).

**What the deck itself observed for these runs is not in the sample.** #1741's export merged on 2026-10-22, so the deck's own spans (`agent.run`, `agent.status`, `agent.operation`, `agent.ci`) did not exist for most of the sampled runs, and the backend that receives the maintainer's spans was not queried. Where a table below says "deck-observed", it says what the deck records by construction for a run it starts, read from `src/telemetry/` and [`docs/telemetry.md`](../telemetry.md), not a measured value. #1741's dogfooding milestone is where measured deck-side values come from.

## 1. Signal inventory

### Channels

| Channel | What it is | Content exposure |
| --- | --- | --- |
| **Deck state** | what the daemon knows without asking the agent: pane, run start and end and how it ended, orchestration role, status changes, typed input from a client (interventions), shell-command spans, the branch's pull request and its CI rollup | none beyond #1741's program-and-first-word rule for shell commands |
| **Hooks** | the events each integration strategy already delivers to the daemon (`src/hook.rs`, the OpenCode plugin, the Pi extension, Codex's native hooks behind `dot-agent-deck wrap`) | the hook payloads carry tool details and, for Claude Code and Codex, `transcript_path`; the deck's hook handling reads no token counts today |
| **Agent's own OpenTelemetry** | what an agent exports itself, which the deck switches on and tags with `deck.run.id` (#1741) | none with the agents' content switches off, which is how the deck starts them |
| **Local transcript or session store** | the files and database each agent writes for resume and history | the same file holds prompts, code and tool output next to the usage fields; reading usage means opening a file that holds content |
| **Agent CLI** | commands that print usage (for example a `/cost`- or `/status`-style command inside the agent) | interactive; not used here |
| **Forge (GitHub)** | pull request state, checks, closing comments | public repository metadata |

These are the same for every agent, because the deck, not the agent, observes them; the per-agent differences are in usage, below.

**Which channel gives tokens without content.** The agents' own OpenTelemetry does, for Claude Code, Codex, Pi and (by its docs) Devin, with their content switches off. OpenCode's default export carries no token counts (its experimental model-call spans can carry prompt text, so the deck leaves them off); its tokens are in its local database, next to the prompts. For runs from before telemetry was on, a local file or database is the channel this page found for every agent, and reading it means parsing a store that also holds prompts and code, even when only the usage fields are kept: it is not interception of the model traffic, but the reader is trusted with content. No signal here required a proxy or gateway in front of the provider.

### Subscription agents

Every agent in the sample ran on a subscription or a plan, as far as the files say: Codex reports plan type `prolite` on all 10,032 `token_count` records; OpenCode's OpenAI provider reports a cost of 0 on all 2,232 of its replies; 36 of the 101 Pi sessions used the `openai-codex` provider, a ChatGPT subscription; and the Claude Code `quotaLimits` record the deck already parses (`src/quota_signals.rs`, whose test fixture is a record observed on this machine) names a five-hour rate-limit window and an organisation spend cap for overage. So Claude Code ran on a plan with included usage, where usage past the limit can be billed as overage; which of its sampled usage, if any, was billed was not checked. No sampled run has a monetary figure known to be the provider's charge for that run.

The record should therefore keep three things apart, and never fill one from another:

- **Tokens**, which every agent but Devin (no local data) reported: in 629 of the 629 Claude Code sessions with a request, 201 of the 204 Codex sessions, 259 of the 300 OpenCode sessions with a request and 101 of the 101 Pi sessions. [Field presence](#field-presence-and-disagreement) says what the others are.
- **Quota consumed**, the change in a plan's used percentage over the run, where the agent reports it (Codex). For a subscription this is the figure that changes what a user does: it says how much of the week's allowance a run took. In the sample, the 12 Codex runs of one orchestration (`dispatch-prd-421`) took the weekly window from 26% to 45%. Concurrent runs share one window, so a run's delta is an upper bound when others overlap it.
- **Cost**, with provenance `estimated` (list-price equivalent: what the tokens would cost on a pay-as-you-go key) or `provider-reported` (what was actually charged, which only the provider's billing can give), and `unavailable` otherwise. An agent's `0` on a subscription provider is **unavailable**, not zero: OpenCode's zeros would otherwise make its runs look free next to Claude Code's estimates.

## 2. A minimal provider-neutral execution record

### Two units, not one

The sample shows that a session is not the unit a user decides about. The 37 sessions in `dispatch-prd-421` (14 Claude Code, 12 Codex, 5 OpenCode, 6 Pi) produced one pull request, #1813; `dispatch-prd-1542` produced 59 sessions and one closed pull request. An orchestration restarts a role's agent for each delegated task, so one role is many runs. The record has two levels:

- a **run**: one agent process the deck started in a pane, which #1741's `deck.run.id` already identifies;
- a **work item**: the issue or pull request the runs serve, which today is known only by convention (the worktree and branch name) and needs #628's durable work identity to be reliable. 53 of the 244 sampled worktrees had no pull request of their own: most worked on someone else's (verify, rebase, conflict, review findings), so attributing them by their own branch puts their work on nothing.

### Fields

Every field carries a provenance, one of `measured` (the deck or a collector observed it), `provider-reported` (the provider's or agent's own count), `estimated` (computed from other fields, for example tokens times a price list), `agent-asserted` (the agent's claim, for example "work done"), or `unavailable` (the value is not known, and the field carries the reason: no channel for this agent, a subscription's zero, a price the agent marked unknown, a value the channel did not record, a total over replies of which only some had the value, a quota window that reset during the run, a plan that changed during it, a used share that went down during it, a run that has not ended, or no work item). Unavailable is a value of the field, not a missing field.

| Field | Level | Provenance today | Source |
| --- | --- | --- | --- |
| run id, pane, agent, role, orchestration id, host | run | measured | #1741's `agent.run` |
| start, end, end reason | run | measured | #1741 |
| time per status, interventions, shell-command time | run | measured | #1741 |
| run termination (see [taxonomy](#revised-taxonomy)) | run | measured (end reason) plus provider-reported (the agent's last error or interrupt); unavailable until the deck reports an end | deck plus the agent's own telemetry |
| last turn | run | provider-reported | the agent's own record: a completed turn is not a finished run |
| agent version | run | provider-reported | the agent's telemetry or local store |
| model(s) | run | provider-reported | the agent's telemetry or local store |
| tokens: input, output, cache read, cache write | run, per model | provider-reported | the agent's telemetry; for OpenCode only its local database |
| quota consumed | run | provider-reported, an upper bound when runs overlap, and short by the run's first request (Codex writes its first sample after that request); assumes one account, since a sample names a plan, not an account | Codex `rate_limits`; unavailable elsewhere |
| cost | run | estimated (list-price equivalent) or provider-reported (API-key billing), else unavailable | the agent's estimate, or tokens times a dated price list |
| parent run | run | measured, once a nested run gets its own run id (it does not today, below) | the deck's own run tree |
| work item | run | measured where the branch names it, else unavailable | #628 |
| disposition | work item | measured | forge |
| verification (required checks passed on the merged head) | work item | measured | forge: the required-check list and the head commit, which #1741's CI rollup does not carry ([taxonomy](#revised-taxonomy)) |
| changed lines | work item | measured | Git |
| CPU, memory | run | measured | per-machine collector |
| disk | worktree | measured | per-machine collector |

### Aggregation without double counting

- **A run's tokens and cost come from one source per agent, never a sum of two.** Claude Code's session total already includes its subagents: in all 14 sampled sessions with subagent transcripts, `cost-state` output tokens were at least the parent's transcript plus its subagents' (in one, a Haiku subagent's tokens are counted in the parent's Haiku total although the parent made no Haiku request). Adding the subagent transcripts to the parent's total would count them twice.
- **The agent's own total is the source, not a transcript sum.** Claude Code's transcript misses requests its `cost-state` counts: Haiku models appear in `cost-state` and not in the transcript in 539 of the 618 sessions with a `cost-state`, the transcript's output total is lower in 592 of them, and output tokens agree within 1% in 78% of sessions and within 5% in 93%. Tools that sum transcripts undercount by that margin.
- **An agent started inside another agent's pane** (a `codex exec` from Claude Code) is a child run. Its tokens belong to it and to the parent's subtree total, never to the parent's own total; the record stores own totals and derives subtree totals. **#1741 does not give it a run id of its own**: the `PATH` shim (`src/telemetry/shim.rs`) adds Codex's telemetry configuration but mints no new `deck.run.id`, so the nested run inherits its pane's and is indistinguishable from the parent by run id. A distinct identity for a nested run is a requirement on the follow-up, not something #1741 supplies.
- **Retries** are separate runs of the same work item. A work item's total is the sum of its runs' own totals, so a retried item costs what both attempts cost, which is what a user wants to see. The same holds for the orchestrations above and for a dispatch to another project: a run is counted once, under its own run id, and rolled up by work item and by orchestration id.
- **Quota percentages do not sum across agents or plans**, and overlapping runs of one plan share a window. Roll quota up per plan and window, not per work item.
- **Runs the deck did not start** are not in the record. On this machine the agents' stores also hold runs started by tests and tools inside a pane, such as what are probably lane-2 test probes (one request on a cheap model, in a worktree where an agent was running tests; their origin was not verified). A run whose environment was cleared loses its `deck.run.id` and should count as unattributed, as #1692 proposed for processes.

### Privacy and redaction

- The record holds counts, identifiers the deck mints, model and agent names, and timestamps. It holds no prompt, response, tool input or output, file content, command line beyond #1741's rule, path or remote URL.
- Reading usage from a local store is the fallback for an agent with no telemetry channel (OpenCode tokens) and for history. The deck already reads two such stores narrowly for usage-limit signals: a bounded tail of the Claude Code transcript its own hook names (`read_claude_transcript_tail` in `src/quota_signals.rs`) and the Codex rollout (`src/codex_rollout_tail.rs`), comparing JSON keys only. A usage reader that does the same must select fields by name and drop the rest of each record before it leaves the function that parsed it, as the scripts behind this page did. A store's error bodies can hold more than an error: OpenCode's stored HTTP errors carry the provider's response headers, cookies included, so an error is recorded as its kind and status code only.
- A work item's title and a closing reason are maintainer-written prose. The record links to them; it does not copy them.

### Retention and storage

The agents' own stores are not a retention policy: they are each agent's, they can be cleaned up by the agent, and their formats are not documented as an interface, so an agent upgrade can change them without notice. The deck's record is small (one row per run, about twenty numeric or short fields) and should live in the daemon's state directory with a bounded age, defaulting to private and local, with OpenTelemetry export as the optional copy #1741 already makes. The bound itself is a decision for the storage PRD; nothing here measured how long users want to look back.

### Missing data

A value that is not known is `unavailable` with a reason (no channel, a subscription's zero, not recorded, a run not yet ended, and the others under [Fields](#fields)), never zero and never guessed, matching #1741's rule that "a value the deck cannot determine is left out". An empty usage observation — no usage record for the run, or none the reader could use — stays `unavailable` with reason `not_recorded`: missing capture is not evidence that the run consumed nothing. A zero token count has two sources. One is a zero the agent itself reported, such as a Codex running total of zero in every count or a Claude Code session total of zero, which is recorded as `provider_reported`, because the agent measured it and the deck did not. The other is a run confirmed to have made no request, which needs a channel that sees every request the run makes, such as a proxy in front of the provider; the prototype reads the agents' own records and has no such channel, so it cannot confirm that a run made no request, and it never derives a zero from the absence of a record. A subscription reply has unavailable cost. The prototype applies that rule to every agent's own cost figure, not only OpenCode's, and reply by reply: a `0` for a reply that used tokens is unavailable, a `0` for a reply that used none adds nothing, and a model whose replies are partly priced and partly not has an `incomplete` cost, never the priced part presented as the whole.

### Revised taxonomy

The candidate list mixes three different questions, and the sample breaks it where they disagree: a failed run in a merged item (row 10), an interrupted run in a superseded item (row 9), a merged item whose run was interrupted (row 1), and runs whose work is someone else's pull request (rows 7 and 20). Splitting it into three fields gave each of the 21 runs, and each mechanically classified session, a run termination, and each of the 19 hand-classified runs that served a work item a disposition (rows 13 and 17 served none):

- **Run termination** (per run; deck-observed end reason plus the agent's last error or interrupt): `completed`, `failed`, `interrupted` (by a person, or by the deck when it stops or restarts a run: the deck's end reason says which), `timed_out`, `unknown`. No sampled run timed out; the deck sets no run time limit today, so `timed_out` is reserved for when one exists. "Ended mid-turn" in the table above becomes `interrupted` or `unknown` once the deck's end reason is joined to it.
- **Work disposition** (per work item; forge): `merged`, `superseded` (closed with a successor named; all four closed agent pull requests here), `rejected` (closed without a successor; observed 0 times in 453), `resolved_without_change` (new; #240 and #415), `deferred` (closed as not planned; replaces "abandoned" where a decision was made), `abandoned` (no activity and no decision; not observable without a time rule), `open`.
- **Verification** (per work item, a property rather than an outcome): `verified` when the required checks passed on the head that merged; `failing`, `unverified`. On this repository's ordinary contributor path a merge waits for the required checks, but not every merge takes that path: CLAUDE.md rule 8 records Renovate's bypass, the two `RELEASE_TOKEN` workflows that push to `main` directly and an admin's bypass, so a merge here is not verified by construction. #1741's `agent.ci` does **not** measure verification: it is the overall CI rollup of the branch's pull request (`src/pull_request.rs`), which counts optional checks, reads a rollup of only skipped checks as passing, and names no commit. The prototype therefore records `checks`, the observed rollup, and leaves verification proper (the required-check list and the merged head's identity) to the follow-up.

Two more things the sample needs that are not outcomes: a run's **contribution target** (the work item it served, which is not its own branch for verify, rebase and review runs) and its **retry link** (a later attempt at the same work item, rows 18 and 19), both of which depend on #628.

## Resource attribution (from #1692)

#1692's measurements are in [its decision record](https://github.com/vfarcic/dot-agent-deck/issues/1692#issuecomment-6332111458) and summarised on [#633](https://github.com/vfarcic/dot-agent-deck/issues/633#issuecomment-6340717563); nothing was re-measured here. They fit the record as follows:

- **CPU and memory per run**, provenance `measured`, from a per-machine collector outside the deck that groups processes by the run identity they inherit in their environment (`DOT_AGENT_DECK_PANE_ID`, or `deck.run.id` in `OTEL_RESOURCE_ATTRIBUTES`), sampled every 15–30 seconds and sent over OTLP to the same backend so it joins on `deck.run.id`. Memory as PSS, since summed RSS read about twice the real peak. CPU of short-lived processes stays a known undercount unless the collector reads cumulative counters that include reaped children, a cgroup per run, or exits via eBPF.
- **Disk per worktree**, not per run: 12 of 17 panes on the busiest measured deck shared a worktree. It joins the record at the work-item level.
- **Unattributed** resource use (a process whose environment was cleared) is reported as such, the same rule as for runs above.
- macOS was not measured.

**Can a stock scraper group by environment variable? No, for both checked, as of 2026-10-23.** The OpenTelemetry Collector's `hostmetrics` process scraper (beta for metrics) matches processes by name only (`include` / `exclude` take `names` with a match type, in its `config.go`), and its resource attributes are the pid, parent pid, executable name and path, command, command line, owner and cgroup, with no environment. Prometheus `process-exporter` matches on `comm`, `exe` and `cmdline` and names groups from `{{.Comm}}`, `{{.ExeBase}}`, `{{.ExeFull}}`, `{{.Username}}`, `{{.Matches}}`, `{{.PID}}`, `{{.StartTime}}` and `{{.Cgroups}}`, again no environment; its `-children` option adds a process to its nearest matching ancestor's group, which is the parent-walk #1692 showed loses double-forked processes. Both can read the cgroup, so if the deck ever starts each run in its own cgroup (#1692's "what would change it"), either could group by it with no custom code. Until then, grouping by environment needs a small custom receiver or exporter.

### Prototype recommendation (milestone 4)

- **Metric set:** per run, the agent's own token totals by model (input, output, cache read, cache write), cost with provenance (`estimated`, or `unavailable` for subscription zeros and agents with none), quota consumed where reported, and the run termination; per work item, the disposition and verification fields above. Elapsed time, status time and interventions are already in #1741's spans.
- **Agents:** Claude Code (with telemetry on, the deck switches on its OTel export, whose `claude_code.api_request` events carry the tokens, and tags it with `deck.run.id`; their arrival in the backend was not checked, since the backend was not queried), Codex (its traces carry `gen_ai.usage.*` according to its source on `main`, to be confirmed against the installed version; its quota is only in the rollout file today) and Pi (the deck's own extension already sends `pi.model_usage`). Together they are three integration strategies. OpenCode has no token channel but its database, so it is the one agent that would need a local reader; leave it out of the first prototype and record it as unavailable. Devin needs a signed-in session to verify its docs before it is in. The prototype kept OpenCode's cost rule anyway, from values a caller supplies, and built no OpenCode reader ([results](#prototype-results-milestone-4)).
- **Where:** a backend-side derivation first, with no deck code, **conditional on verifying receipt**: if the three agents' usage arrives in the same backend as `agent.run`, joined by `deck.run.id`, a query can produce the record and show what is missing before anything is built. That arrival is what #1741's configuration is meant to produce, not something this page observed: the backend was not queried, and Codex's export from the installed version is unverified. A nested `codex exec` inherits its pane's `deck.run.id` ([aggregation](#aggregation-without-double-counting)), so grouping by run id would merge it into its parent's run. The prototype measured one ([results](#prototype-results-milestone-4)).

### Prototype results (milestone 4)

The prototype is `src/telemetry/accounting.rs`, registered in `src/telemetry/mod.rs` as `#[cfg(test)] mod accounting`: it is compiled for tests only, so it is no product API and ships in no release build, while its tests run in the fast tier. The daemon, the TUI, the hooks and #1741's exporter do not call it, and it opens no file it is not handed. Wiring it to a live run, and dropping that `cfg(test)`, is the follow-up PRD's first step. It implements the recommendation's metric set: per run, tokens by model, cost with provenance, quota consumed, run termination and the agent's last turn; per work item, disposition and the observed CI checks.

- **Provenance.** `Field<T>` is an enum of the five provenances, so a value cannot be stored without one, and `unavailable` carries one of ten reasons: `no_channel`, `subscription_zero`, `unknown_price`, `not_recorded`, `incomplete`, `window_reset`, `plan_changed`, `quota_decreased`, `run_not_ended`, `no_work_item`.
- **Identifiers.** Every string the record holds or exports (run id, agent, model, plan, error kind, work item, orchestration) is an `Ident`, whose one constructor accepts ASCII letters, digits and `._-:/@+`, at most 128 bytes. A record built field by field by code outside the module, without a normaliser, can therefore carry no line break, quote, space or non-ASCII byte either, and the attribute type's fields are private, so an exported string is an enum's name or an `Ident`. That is a shape check, not a privacy allow-list ([leakage risk](#leakage-risk)).
- **Normalisers** for Claude Code, Codex, Pi and OpenCode, each taking a struct of counts, model names and stop kinds and nothing else. Claude Code's comes from its own session total (`cost-state.modelUsage`): cost `estimated`, `unknown_price` when Claude Code sets `hasUnknownModelCost`, and tokens and cost `not_recorded` for a session with no total (row 21 above). Codex's comes from the rollout reader below, with cost `no_channel` and quota from the primary rate-limit window. Pi's and OpenCode's sum replies per model, classifying each reply's cost before adding it: the agent's figure is `estimated`, a `0` for a reply that used tokens is `subscription_zero`, only a reply with zero tokens and an explicitly reported zero cost adds nothing (a reply whose cost was not recorded is `not_recorded`, not zero), and a model whose replies mix priced and unpriced ones has an `incomplete` cost rather than the priced part's sum. OpenCode's input says per message whether the provider returned usage at all: a message without it (OpenCode's initial zeros on a failed or never-completed request, as in the 41 sessions above) has its tokens and cost `not_recorded`, a completed message that reported zero tokens is a provider-reported zero, and a model whose messages mix the two has its tokens `incomplete`, and its cost too unless every reported message is an explicit zero cost for zero tokens, which adds nothing and leaves the cost `not_recorded`. The normaliser enforces that mapping; deciding which messages had no usage, from the message's own error and completion fields, is the extraction's job, which #1858 builds. Pi's last reply names the last turn: a stop or a length limit completed it, a tool call leaves it mid-turn, an error failed it, an abort interrupted it, and no stop reason leaves it unknown. All four normalisers and the reader track at most 32 named models per run and credit the rest to no model, so the state a run holds is bounded whatever its input names; the Codex normaliser re-applies the cap to the summary it is given, so a summary built by hand rather than by the reader is bounded too. OpenCode's was cheap to add, since the zero rule needs no reader.
- **One token convention.** `input` counts every input token, cache reads and writes included, which is what `gen_ai.usage.input_tokens` means; `cache_read` and `cache_write` are parts of it. Claude Code, Pi and OpenCode report input without the cache, so their normalisers add it; Codex's `input_tokens` already includes its cached tokens.
- **Run termination** is unavailable (`run_not_ended`) until the deck reports an end, whatever the agent's last turn says: an interactive agent that completed a turn is waiting, not finished. The last turn is kept beside it as its own field (`provider-reported`, or `not_recorded`). Once the run has ended, it joins the agent's last turn to the deck's end reason as the [revised taxonomy](#revised-taxonomy) says. The agent's own failure, interruption or completion is `provider-reported`. A store that ends mid-turn is `interrupted` when the deck closed the pane or shut down and `unknown` when the agent exited (`measured`). A last turn the record does not name, or no agent record, makes a run that ended `unknown`. An agent's error kind becomes `error.type` only when it is an `Ident`.
- **Work item.** Disposition comes from forge state (`measured`): a pull request decides when there is one (merged; superseded when closed with a successor; rejected when closed without one; open), otherwise the issue (resolved without change, deferred, open). Nothing maps to `abandoned`, which needs a time rule. The second field is `checks`, the observed CI rollup on the item's pull request (#1741's CI state, `measured`), otherwise the agent's own claim (`agent-asserted`), otherwise unavailable: `passing`, `failing` or `pending`. It is deliberately not called verification, which needs the required checks on the merged head ([taxonomy](#revised-taxonomy)).
- **Local capture: a Codex rollout reader** (`CodexUsageReader`), taking the rollout's path as an argument. The rollout was chosen over the Claude Code transcript because its running total is Codex's own total (a transcript sum undercounts Claude Code, above) and because it is the one place this page found Codex's quota. On Unix it opens the path with `O_NOFOLLOW`, which refuses a symlink in the final component only: a symlinked parent directory is followed (a test pins that), so this is not confinement to a trusted root, and which roots the wired reader may open is #1858's decision. It opens with `O_NONBLOCK`, so a FIFO with no writer cannot stall the open, and it refuses anything but a regular file, from the opened descriptor's metadata, before reading a byte, so a FIFO, a device or a final-component symlink is an error rather than a stall; elsewhere it is a plain open followed by the same regular-file check. Each poll reads only bytes appended since the last one, at most 4 MiB and never past the file's length when the poll began, so the bytes and parsing work of one call are bounded however large the backlog or however fast the file grows; that is not a wall-clock bound, since a read from a slow disk takes as long as the disk does. What is left is drained by the next polls, and the reader reports the bytes outstanding. An incomplete trailing line waits in a buffer for its newline, up to 256 KiB, across polls, and a longer line is skipped. A file that gets shorter, or whose path names another file (on Unix, by device and inode), is read again from the start. Which lines are deserialised and what is kept from them are two separate steps. A line is deserialised when it contains one of five quoted marker words (`"turn_context"`, `"token_count"`, `"task_started"`, `"task_complete"`, `"turn_aborted"`) anywhere, so a content line with a string that is exactly a marker word is deserialised too; it is deserialised into structs holding only the record and payload types, the model, four token counts, the primary rate-limit window and the error kind. Only a record whose parsed type is one of those five then updates the summary, so such a content line is parsed and ignored. Each `token_count`'s growth of the running total is credited to the model of the latest `turn_context`. A running total missing its input or output count, missing a cache count that was not zero before, or inconsistent (its cache counts add up to more than the input that includes them, a sum that overflows included) is skipped and counted without moving the baseline, so a valid total after it is not counted twice. While such a skipped total is the latest one, the counts credited so far may fall short of the rollout's own, so the run's tokens are `incomplete`; a later usable total at or above the baseline covers the gap and makes them `provider-reported` again. The first usable total is credited even when every count in it is zero, so a rollout whose totals are all zero has a provider-reported zero, while a rollout with no usable total has its tokens `not_recorded`. A usable total lower than the baseline in any count is ambiguous: the counters may have restarted or the total may be wrong. A restart would need evidence in the rollout that the counters started over, such as a record marking a new process writing to the same file; the reader accepts no record as such evidence, so it makes the run's tokens `incomplete` rather than adding either reading, and leaves the baseline where it was. The one start-over the reader does recognise is the file's own, above: a file that got shorter or was replaced is a new rollout, with the summary reset. No running total in this machine's 211 rollouts went down ([reproducing it](#overhead)), so the ambiguous case has not been seen in real data. Two consecutive quota samples in different windows, under different plans or with the used share going down make the run's quota `window_reset`, `plan_changed` or `quota_decreased`. The reader's `Debug` shows its offset, buffer length and counters, not the buffered bytes or the path.
- **Aggregation** (`rollup`, `rollup_work_item`, `rollup_orchestration`). A run id seen twice counts once, as its last record, since a later snapshot of a running total supersedes an earlier one; snapshots are collapsed over the whole input before work-item or orchestration membership is decided, so a run whose work item was corrected counts under the corrected one only. Distinct run ids are distinct attempts and all count, so a retried item costs both attempts. A run marked as included in another run of the set (a Claude Code subagent in its parent's total) counts as a run and a termination but adds no usage; a child run with its own run id (a nested `codex exec`, once it gets one) adds its own. Money is summed per provenance and never across provenances. Quota rolls up per agent, plan and window instance (its reset time) as the union of the runs' ranges, so two overlapping runs in one window do not count the overlap twice, and it is never converted to money. Quota is assumed to be one account's: a sample names a plan, not an account, so deltas from several accounts on one plan and window would be merged.
- **Export mapping** (`run_attributes`, `work_item_attributes`), a pure function not called by the exporter. Keys are a closed enum, as #1741's `AttrKey` is. `deck.run.id` and `deck.agent` reuse #1741's names. Tokens are `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens` and `gen_ai.usage.cache_write.input_tokens`, with the model as `gen_ai.response.model`, one attribute set per model (a span event each). The rest is `deck.*`: `deck.tokens.provenance`, `deck.cost.microusd` and `deck.cost.provenance`, `deck.quota.plan`, `deck.quota.window_minutes`, `deck.quota.resets_at` (the window instance, in seconds since the Unix epoch, so a backend can keep successive windows apart), `deck.quota.used_from_bp` and `deck.quota.used_to_bp` (basis points of the window), `deck.run.termination`, `deck.run.last_turn`, `deck.work.disposition`, `deck.work.checks`, each with a `.provenance` and, when unavailable, an `.unavailable_reason`; plus `error.type`. An unavailable value is exported as its provenance and reason, never as 0. Money is an integer number of micro-dollars, because #1741's attribute values have no float type.

Its 48 unit tests run in the fast tier on synthetic fixtures: every provenance, reason and enum name, the subscription zero and per-reply cost classification with mixed priced and unpriced replies for both normalisers, a missing cost beside a priced reply, OpenCode messages without usage apart from reported zeros, ended and open runs and a Pi run ending on a tool call, the observed-checks field, each normaliser, the model cap in the normalisers (a hand-built Codex summary included) and the reader, the reader's appended-only reads, partial trailing lines, truncation and replacement, malformed and overlong lines, incomplete, inconsistent and lower running totals, quota plan changes and drops, a backlog drained over bounded polls, a budget cut inside an overlong line, a FIFO and a final-component symlink refused and a symlinked parent directory followed, the reader's `Debug`, the leakage guards below, retries, corrected work-item membership, Claude Code subagents, duplicated run ids in an orchestration, mixed money provenance, overlapping quota, the quota window in the export, and the literal spelling of every borrowed key. A 49th test is the overhead driver below, which does nothing unless asked to.

#### Overhead

Measured on 2026-10-23 with a release build over this machine's 208 Codex rollouts: 421 MB in 71,521 lines. The load average was 13.8 / 25.8 / 30.4 (1, 5 and 15 minutes) when it started and 13.8 / 25.4 / 30.2 when it ended. A first run at a load average of 37–43 gave the same full-read times and showed the reader allocating a 64 KiB read buffer on every poll; the buffer now lives on the stack, and the figures below are from the run after that change.

| Measurement | Result |
| --- | --- |
| Full read of all 208 rollouts, one fresh reader each | 1.80–1.84 s warm (229–234 MB/s), 2.07 s on the first pass; 54,028 allocations, 77 MB allocated in total, peak live memory 394 KB above the harness's own |

So an incremental reader polled every two seconds (the interval `src/codex_rollout_tail.rs` uses) costs microseconds per poll, and the slowest polls are those after a large tool output was appended. Most of a full read is the pre-filter scanning every byte for the five markers: 10,678 of 71,521 lines were deserialised.

**Reproducing it.** The harness behind the table was throwaway; its timing and agreement half is committed as the test `overhead_over_a_directory_of_rollouts` in `src/telemetry/accounting.rs`. It is not a `#[spec]` test, and it returns at once unless `DAD_ACCOUNTING_BENCH_DIR` names a directory: then it reads every `.jsonl` under it three times with one fresh reader each (no poll budget), runs the `serde_json::Value` baseline, checks each rollout's per-model sums against its own running total, replays the 20 largest one line at a time into scratch files under the crate's disk-backed test temp root, and times 100 idle polls on each. It prints aggregates only (counts, bytes, times and the load average), never a path, a file name or a line. It reads the user's own rollouts, so run it on the machine that holds them, never in a remote sandbox, and in a release build:

```sh
DAD_ACCOUNTING_BENCH_DIR=~/.codex/sessions cargo test --release --lib telemetry::accounting::tests::overhead_over_a_directory_of_rollouts -- --exact --nocapture
```

It does not reproduce the allocation figures, which came from a counting global allocator in the throwaway harness: a lib test binary shares one allocator across all its tests, so the committed driver has none. It was last run on 2026-10-23 in a debug build over the 211 rollouts then on the machine, after the inconsistent and lower running-total rules above were added: per-model sums equalled the running total in 211 of 211, with 0 malformed lines, 0 skipped running totals and 0 totals lower than the one before, so those rules change no result on this machine's data. Its debug-build times are not comparable with the table's.

#### Leakage risk

- **What it touches.** Every byte appended to the rollout passes through the reader's memory. The pre-filter scans each line, and serde_json scans every string of a line that passes it, content included, to reach the named fields; the narrow structs mean the rest is skipped rather than copied, not that it is never read. An incomplete trailing line, which can be a prompt or tool output, waits in the reader's buffer (up to 256 KiB) until its newline arrives and is then dropped; the reader's `Debug` reports that buffer's length, never its bytes, and not the path it reads. The reader is trusted with content in memory, as the scripts behind this page were; it does not intercept model traffic.
- **What it retains.** Model names, four token counts per model, the first and last rate-limit samples (plan type, used percentage, window length, reset time), and the last turn's end with its error kind. Model, plan and error kind are kept only as an `Ident` (ASCII letters, digits and `._-:/@+`, at most 128 bytes, judged after JSON escapes are decoded), so free text, a line break or non-ASCII text in those fields is dropped.
- **The shape check is not a privacy allow-list.** An absolute path (`/home/x/.ssh/id`), an email address and many credentials have an identifier's shape and are kept and exported; a test asserts exactly that, so the residual risk is written down rather than assumed away. Before the record is wired, the follow-up has to decide per field which values it may carry: agent names from the registry (`src/agent_registry.rs`); run, orchestration and work-item ids the deck mints or the forge numbers; model names from a list the deck knows, with an explicit rule for an unknown or custom model (kept, hashed or dropped); and plan and error kinds as enumerations where the agents document them.
- **What reaches the attributes.** The run id and agent the deck already exports, model names, counts, provenance and reason names, the plan and the error kind. Not the working directory, git remote or branch, instructions, prompts, replies, tool input or output, or error messages; `session_meta`, which holds the working directory, the git remote and the base instructions, is not one of the five record types, so the pre-filter skips it unless one of its strings is exactly a marker word, and none of its fields is kept either way.
- **On real data**, every one of the 10,678 deserialised lines was one of the five usage record types. A JSON string cannot hold an unescaped quote, so a content line passes the pre-filter only when one of its strings is exactly a marker word such as `token_count`, wherever that string sits in the line; such a line is deserialised and then ignored by its type, and the leakage test builds such lines on purpose.
- **The leakage tests** put a sentinel string in a prompt, a reply, tool input and output, command output, developer and base instructions, the working directory, compacted history, an error message and a non-identifier error kind, every one of those lines carrying a marker word so it is deserialised, and check that the reader's summary, the record and every exported attribute are free of it. Another feeds strings through each string field the reader keeps and each normaliser's model name: through the reader, the turn's model, the plan and the error kind, each with a JSON-escaped character that is kept once decoded, an escaped line break, a space and 128- and 129-byte values; through the Claude Code, Pi and OpenCode normalisers, a model name with a space, a line break, a path shape and 128 and 129 bytes; and a run id or agent, which cannot be built without passing the `Ident` check. A third exports records built by the Claude Code, Pi and OpenCode normalisers from a hostile model name, and one built field by field, and checks that every exported string is an enum's name or an `Ident`. The shape check itself has its own test, which keeps path-, email- and credential-shaped values and drops Unicode, a line break, a space, a quote, a backslash, the empty string and 129 bytes.

#### What implementing it changed on this page

- `unavailable` needed ten reasons, not only "no channel"; [Fields](#fields) and [Missing data](#missing-data) now say so.
- A Codex quota delta is short by the run's first request, because the first rate-limit sample is written after it; [Fields](#fields) now says so.
- The zero rule applies to every agent's own cost figure, not only OpenCode's, and to each reply before it is summed.
- A completed turn is not a finished run, so the record keeps the last turn beside the termination.
- #1741's CI rollup is observed checks, not verification, so the record names it `checks` and verification waits for the follow-up.
- Codex's `cache_write_input_tokens` was 0 on all 10,047 per-turn samples on this machine, so whether its `input_tokens` includes them is not known; the prototype assumes it does, as it does for cached tokens.

#### Not done, and why

- **Wiring.** Pointing the reader at a live run needs the rollout's path, which reaches the daemon only through Codex's hooks (`transcript_path`, already used by `src/codex_rollout_tail.rs`); Claude Code's own total is in the transcript its hook names; and Pi's usage reaches the deck's backend through the Pi extension. Each route goes through hook handling, the daemon or the Pi extension, which another orchestration owns until PRD #1666 part 3 merges, so wiring is a finding for a follow-up implementation PRD, not part of this prototype. So are storage, retention and a user surface.
- **Nested run identity.** A nested `codex exec` shares its pane's `deck.run.id` today ([aggregation](#aggregation-without-double-counting)); giving it its own is the follow-up's, and needs the spawn and daemon paths this run does not touch.
- **Subtree totals.** The page says the record keeps own totals and derives subtree totals; the prototype rolls up by work item and by orchestration only, and does not sum a run with its descendants by `parent_run_id`.
- **Verification.** The required-check list and the merged head's identity are not in #1741's CI state, which the prototype reuses as is.
- **Other readers.** Only the Codex rollout has a reader; Claude Code's, Pi's and OpenCode's normalisers take values a caller extracts.
- **Reader limits.** A file truncated and regrown past the reader's offset between two polls, keeping its inode, is not noticed: the reader carries on from its offset into the new content. It refuses a symlink only in the path's final component and follows symlinked parent directories, so it confines nothing to a trusted root; #1858 decides that policy before it hands the reader paths from hooks. On platforms other than Unix it notices a truncated file but not a replaced one, and its open follows symlinks and is not guarded against blocking before the regular-file check runs.
- **Not measured**: the reader on macOS, the export mapping against a real backend, and Claude Code, Pi and OpenCode stores.

### Preliminary read: Revise, leaning Go

- **Tokens are trustworthy** for the three agents that report them through telemetry, and for OpenCode from its database: reported in every sampled Claude Code and Pi session with a request, in 201 of 204 Codex sessions, and in 259 of 300 OpenCode sessions with a request, whose other 41 got no usage because their requests failed or never completed; and internally consistent where the agent keeps two counts (197 of 201 Codex rollouts exact, 300 of 300 OpenCode sessions). The caveat is the source: transcript sums undercount Claude Code.
- **Monetary cost is not**: no sampled run had a provider-reported charge, the estimates disagree with each other by 12–37% for the most-used model, and one agent reports zeros for a paid plan. It is usable only as a labelled list-price equivalent.
- **Metrics that would change a decision in this sample** (an inference from the data, since nobody was shown these values while the runs happened):
  1. **Run termination by model and agent**: 49 OpenCode sessions on this machine (40 of them in this repository's worktrees) failed on their first request with HTTP 400, on 7 different days in 17 directories, on models the subscription evidently does not serve (`gpt-5.4-mini` in 38 of the 49). Seeing that as a failure rate would make someone fix a configuration or a test's model choice.
  2. **Quota consumed per work item**: one orchestration's Codex runs took 19 points of a weekly allowance. That decides which agent takes the next task and whether to stop.
  3. **Interventions and interruptions per run**: 29 interrupted Claude Code sessions, and the deck's own intervention count, separate a run that needed help from one that did not, which is the "which roles need you most" question #1741's spans already answer.
  4. **Work-item roll-up across agents**: `dispatch-prd-421` cost Claude Code's estimate of $30 plus 19 points of Codex quota plus Pi's estimate of $2 for one pull request, which is the figure for comparing workflows.
- **Supersession, not rejection, is how agent work fails here**: 0 of 453 agent pull requests were closed without a successor. A record that counts only merged versus rejected would report a 99% success rate and miss the retries and superseded attempts that cost the most (rows 8, 18 and 19).

That is enough to argue against Stop, and against the narrowest Revise (outcome and interventions only), because tokens and quota are reliable and the record works across four materially different integrations without a proxy. It is not yet enough for Go: the PRD's bar asks for metrics that changed a real decision, and this evidence only shows that they would have. The prototype above, run against #1741's dogfooding, is what can show it. The [decision](#decision-milestone-5) below records the outcome.

## Decision (milestone 5)

**Outcome: Revise**, recorded on 2026-10-23 in [the decision record](https://github.com/vfarcic/dot-agent-deck/issues/633#issuecomment-6370966969). The orchestrator of PRD #633's discovery run made the call from the evidence on this page, and that evidence does not contradict it. It is not the PRD's narrowest Revise ("elapsed time, interventions, verification and outcomes"): the PRD's Revise trigger is token *or* cost accounting staying unreliable, and here only cost did, so the revision drops cost as spend and keeps tokens and quota.

### What Revise keeps and drops

**Keeps**: a provider-neutral record, per run, of tokens by model, quota consumed where the agent reports it, run termination, and interventions; per work item, disposition and verification (from the required checks on the merged head, which the prototype's observed `checks` are not); every field with its provenance and, when unavailable, its reason. Elapsed and status time stay in #1741's spans. Resource figures follow #1692's direction: CPU and memory per run and disk per worktree, from a per-machine collector outside the deck.

**Drops**: monetary cost as spend. Cost stays only as a labelled `estimated` list-price equivalent, or `unavailable`, and no surface presents it as billing or as a total across provenances. Also dropped for now: a deck-side store with its own retention, and a user surface for the record. #1741 already exports to a backend the user chooses, which is where #1829 analyses runs, so neither has a demonstrated need until Go is re-evaluated, and how far back users want to look was not measured.

### When Go is re-evaluated

Go is re-evaluated once #1741's dogfooding has produced deck-observed values for real runs and #1829's analysis of them shows whether at least three of the kept metrics changed a real decision: a run stopped, retried or reassigned, a workflow or model switched, or a failure investigated. That needs #1858 shipped first, since without it the backend sees the runs but not their quota or run termination, and sees no tokens for OpenCode. If the analysis finds three, the decision becomes Go and storage, retention and a user surface get their own PRDs; if it finds the metrics read and ignored, the decision moves toward Stop.
