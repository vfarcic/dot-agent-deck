# Agent restore

How the deck resumes an interrupted agent into its conversation (PRD #1790 stage 3). The user page, [`docs/interrupted-work.md`](../interrupted-work.md), says what a person sees; the journal side (the verdicts, the checks a restore makes, the lines it writes) is in [`work-journal.md`](work-journal.md#restoring-an-agent-prd-1790-stage-3). This page is the launch half: how the resume arguments reach the agent without the deck touching the command the user wrote.

## The launch shim carries the resume

The deck never edits a recorded command: it was the user's own shell text, and a command can be a script, a `devbox run …`, or a wrapper that starts the agent somewhere inside it. The resume goes through the same `PATH` shim telemetry uses (`src/telemetry/shim.rs`), which sits in front of the agent's program however it is started.

- **Installed whatever telemetry says.** The daemon writes the shim scripts into `<state dir>/telemetry/bin` at start (`telemetry::start_from`), on Unix, for `claude`, `codex`, `devin`, `opencode` and `pi` (the last two only for a Start over's fresh-start check: the shim adds nothing to them otherwise), and records the directory a successful install answered (`shim::record_installed`); a restore resumes through that directory only, and is refused `unsupported` when no install succeeded. With telemetry off that directory goes on no ordinary spawn's `PATH`; a restore puts it on its own spawn's.
- **One spawn, one request.** A restore spawn's environment carries `DOT_AGENT_DECK_RESUME_AGENT` (the program the agent's `ResumeSpec` names: `claude`, `codex`), `DOT_AGENT_DECK_RESUME_SESSION` (the conversation id) and `DOT_AGENT_DECK_RESUME_TOKEN`, and `PATH` with the shim directory first (`agent_restore::restore_path`: any entry that already is the shim directory is dropped, and an absent or empty daemon `PATH` gives the shim directory alone, never `<shim>:`, whose empty entry would search the current directory). The token is `<expiry>-<32 hex>` (`shim::mint_token`): 16 bytes of OS randomness, and an expiry in Unix seconds at the confirmation bound plus a minute, capped at an hour. Telemetry's own `PATH` addition is skipped when the shim directory already leads (`exporter::prepare_run`). Every spawn removes the three variables from what it inherits before applying its own (`agent_pty::spawn`, the scrub-then-overlay rule), so only the restore spawn carries a request.
- **In the shim.** When the program it stands in for is the one the request names, the shim removes the three variables from the program's environment (so nothing the agent starts is resumed into the same conversation). A call that starts no conversation leaves the request alone for the launch script's later call (`ResumeSpec::inspects`): a version or help query (`--version`, `-v`, `--help`, `-h` for Claude Code; `--version`, `-V`, `--help`, `-h` for Codex) or a managing subcommand (`claude mcp`, `claude doctor`, `codex login`, …), Codex's services `app-server`, `exec-server` and `remote-control` among them. So does a token past its expiry, or naming one more than an hour away. Otherwise it claims the token: `<token>.claim`, created exclusively in `<state dir>/telemetry/resume-acks`, which it opens once as a held descriptor (owned by this account, created and verified owner-only, not a link) and does every later operation relative to (`shim::open_acks`, `platform::trusted_dir::TrustedDir`). The claim is the one reservation a resume and a refusal share: a token claimed once is never claimed again, whatever the outcome. Then it publishes one outcome, written to a staging file and linked into place complete: either the agent's resume arguments in front of the user's own, as separate argv entries (`--resume <id>` for Claude Code, `resume <id>` for Codex, ahead of the wrapper's embedded-mode pair), with `<token>` acknowledging them; or, for an id that is not of the agent's syntax or user arguments that choose another conversation or command, `<token>.refused` holding the reason, and the program unchanged. A claim with no outcome is a call that failed after claiming: no arguments, and the daemon reads it as pending.
- **The deck's own probe carries no request.** In a Codex pane the wrapper runs `codex app-server` before the agent, to record trust for the deck's hooks (`codex_hooks_manage::probe_command`). It runs in the pane's environment, so it removes the three variables from that child, as it removes `OTEL_*`. Before that, and before `app-server` counted as a managing subcommand, the probe reached the shim first and the shim refused the request there (`app-server` read as a prompt), which spent the token: every Codex restore answered `not-resumed`, found by lane-2 `journal/restore/017`. Either half alone prevents it.
- **Which arguments conflict.** Claude Code's arguments are read the way its parser (Commander) reads them (`agent_registry::classify_claude`): an option's value is never taken for an option (`--append-system-prompt --continue` chooses no conversation), and short forms count, attached values and clusters included (`-r<id>`, `-cp`). The conflicting options are `-c`/`--continue`, `-r`/`--resume`, `--session-id`, `--fork-session`, `-p`/`--print`, `--from-pr`, `--teleport`, `--cloud`, `--environment`, `--bg`/`--background`, `--desktop` and `--no-session-persistence`. An option the classifier does not know is read as a flag, so a value after it reads as an argument of its own, never the other way round. For Codex, any positional argument (a subcommand or a prompt) conflicts, except the managing subcommands above.
- **The directory is bounded.** The shim claims nothing while `resume-acks` holds `MAX_ACK_ENTRIES` (512) entries. Each restore first removes the files of every token whose expiry passed more than an hour ago (`shim::retire_expired`), whichever daemon minted it: a shim claims no expired token, so its files are no longer what stops a replay, and the hour is room for a clock stepped backwards. A restore that still finds the directory at its bound is refused `too-many-pending`, as is one past `MAX_PENDING_RESTORES` (16) running at once. A token without an expiry (only a hand-made one) is never retired; the entry bound is what limits those.
- **The daemon confirms; the acknowledgement only explains.** The restore succeeds when the new agent's first attested hook session is the requested id. The acknowledgements are read through the held directory, each name looked at without following a link (`shim::ack_state`), for two things only: a published `.refused` outcome ends the wait early, and at the deadline, whether the published `<token>` exists tells `timed_out` (the shim applied the resume and no confirmation came) from `shim_not_reached` (nothing reached the shim, or a call claimed the token and published nothing). Either way the agent is stopped before anything is posted to it.

## What the shim cannot reach

A launch that does not pass through the shim is never resumed; the confirmation catches it and the restore answers `not-resumed`, offering Start over:

- the agent called by an absolute path, or `PATH` replaced, or a directory holding the real agent put in front of the shim's, by the command or a script it runs;
- a wrapper that drops the arguments it was given, or changes `HOME` or `CLAUDE_CONFIG_DIR` so the id names no conversation it can find (`session_mismatch` or `timed_out`);
- Windows, where there is no shim, and the daemon does not advertise `restore-agents`.

There is no fallback that types a resume command into a started agent (the 2026-10-27 decision keeps it as a fallback only; it would leave a blank agent while the deck waits for readiness, and would have to drive each agent's picker).

## Which agents

The table is `AgentSpec.resume` in `src/agent_registry.rs`: Claude Code carries a `ResumeSpec`; Codex, OpenCode, Pi, Devin and Antigravity do not, so their verdict is `start_over` with `agent-cannot-resume`, and the user page names what each is missing (CLAUDE.md rule 20).

**Codex is a gap for Stage 3 (#2492).** Lane-2 `journal/restore/017` (Codex 0.169.0) showed every Codex restore time out: the shim applied `resume <id>` (`shim=resumed` in `restore_failed`), but a resumed Codex, like a fresh one (`FirstHook::WithFirstPrompt`, measured on 0.160 and 0.164), sends its first hook only with its first prompt, so `restore_session_seen` never fires before `CONFIRM_TIMEOUT` and the agent is stopped (`failure=timed_out`). A longer bound does not help; confirming on the restart note's own turn would post the note before the conversation is confirmed, which the "never a blank agent" rule refuses. So `CODEX.resume` is `None`; 017 is quarantined (`#[ignore = "quarantined: vfarcic, #2492"]`) with its body as the test that lifts it. What stays for #2492: `CODEX_RESUME` and its classifiers, as `AgentSpec.session_args`, which the launch shim reads (so `journal/restore/004`'s Codex half and the app-server probe test still run) and Start over reads to refuse `codex resume`/`codex fork` commands; and the `fa4bf9bc` probe scrub, which is correct regardless.

`AgentSpec.session_args` is how an agent's own arguments choose a conversation for a resume, read even where `resume` is `None`. What a Start over checks is separate (audit B3): `AgentSpec.fresh_start`, a `FreshSpec` per agent the shim stands in front of, whose `selects` classifier says whether the agent's own arguments select an existing conversation. Each was read off the installed CLI's `--help` (2026-11-23): Claude Code `-c`/`--continue`, `-r`/`--resume`, `--session-id`, `--fork-session`, `--from-pr`, `--teleport` (the Commander-aware `classify_claude`); Codex a first positional `resume`, `fork` or `agents`, or `resume`/`fork` after `exec`/`e`; OpenCode `-c`/`--continue`, `-s`/`--session`, `--fork` (top level and `run`); Pi `-c`/`--continue`, `-r`/`--resume`, `--session`, `--session-id`, `--fork`; Devin `-c`/`--continue`, `-r`/`--resume`. For OpenCode, Pi and Devin option values are not skipped, so a value that looks like one of those options refuses (the safe side). Antigravity (no CLI here to read) and the default shell have no `FreshSpec`. `FreshSpec::command_reopens` reads a recorded shell command with `event::tokenize_command`, splits each word again at `;`, `&`, `|`, `(` and `)`, and classifies the arguments after each place a program is named, up to a separator; Start over runs it for every agent's `FreshSpec`, whatever the recorded agent type.

## One writer, and the checks at act time

The review and audit of the full stage (F1–F5, R#1–R#6) moved these into `src/agent_restore.rs`:

- **Bounded request (F5).** `check_selection` refuses the whole request `bad-selection` for a repeated attempt, more than `MAX_ITEM_AGENTS`, an attempt id over `MAX_SELECTOR_BYTES` or an item id over `MAX_ITEM_ID_BYTES`, before any read. A semaphore of `MAX_PENDING_RESTORES` permits, taken without waiting before the first read and held to the answer, bounds the requests being prepared or run (`too-many-pending`).
- **Claims, then a fresh read (F1, F2).** `start` takes `InFlight` (this daemon) and `claim::take` (every daemon on the state directory: `flock`ed `attempt-<hex>.lock` and `session-<hex>.lock` in the owner-only `<state dir>/restore-claims`), then `revalidate` runs `prepare` again for that one attempt and acts on its answer, not on the request's first read. A claim is released by removing its name while still locked, then closing it; a claimer checks that the name still names the file it locked (`TrustedDir::identity`), so a descriptor opened before a release claims nothing. A started agent's claims are held until its successor link is written (below), or until it is stopped after a failure; a failure whose stop could not be proven and whose `restore_failed` could not be written either keeps them for the daemon's life (`keep_fenced`), the fence it could not write down, and beside them (round-4 B2) a claim on every conversation that agent may be in (the one asked for, and the one it reported or was confirmed in, a Start over's new one included) and, when it reported none and its kind can be restored, on that kind's fence file (`kind-<hex>.lock`), which `claim::take` looks at for every restore of that kind without taking it (`held_elsewhere`); the same is held in this daemon's memory (`Held::fenced_sessions`, `fenced_kinds`). A claim another daemon held at that moment is not taken, and is logged. Lane 1: `journal/restore/030` (the e2e-only `DOT_AGENT_DECK_TEST_RESTORE_REFUSE_FAILURE=1` fails the `restore_failed` write). Multi-agent items are not restorable in this stage, so the second target of a request, if there ever were one, would find the item closed by the first and be refused, never started from a stale read. Lane-1 `journal/restore/020` holds a start over between its read and its start with the e2e-only `DOT_AGENT_DECK_TEST_RESTORE_BARRIER`.
- **Durable ownership (audit B1).** A started agent's successor link, `attempt_restored`, now carries `session`: the conversation its restore confirmed (the resumed one, or the new one a Claude start over reported). It is written with `try_record` and waited for before the closes and before the claims are released, outside the session quota that may hold the agent's own `attempt_session` back for a later flush. `Sessions::in_use` counts a live successor named by such a link as in that conversation until it reports another one itself. A link that cannot be written (or a start the journal gives no attempt id) stops the agent with `stop_proven` and answers `not-recorded`; the item stays listed. Lane 1 reaches both halves with the e2e-only `DOT_AGENT_DECK_TEST_WITHHOLD_SESSIONS=1` (the journal admits no session event) and `DOT_AGENT_DECK_TEST_RESTORE_REFUSE_EDGE=1` (`journal/restore/026`). **Retention (round-4 F1).** That link, and a `restore_failed` with `sessions` or `unknown_session`, are written under the old work, which is finished once its attempts ended; journal compaction does not let such a work go while a successor it names is not proven gone (`Index::guards`, `Index::eligible`; `WorkJournal::compact` asks `agent_restore::successor_gone_check`, which runs `launch_gone` over a complete launch-record read and answers no otherwise), and keeps the successor's own work with it (`Index::needs`), so the launch record that check reads is not pruned first. Unit: `compaction_keeps_restore_evidence_while_its_successor_may_run`.
- **Proven stop (F4, F4a, F4b, round-4 F5).** `stop_proven` runs `sweep_session` first, then `close_started_agents`. The leader is named by the pid and start time the registry read as it spawned the agent, before anything could reap it (`AgentPtyRegistry::child_identity`); without that start time no stop can be proven. The sweep counts a listing of the session's members only when the leader, by pid and start time (`platform::proc::probe_process_held`: running, stopped, or exited and not yet reaped), was there both before and after it: a session id is not handed out again while its leader holds it, so every member listed then is the launch's. It stops the leader (`SIGSTOP`) so it neither starts more processes nor is reaped meanwhile, `SIGKILL`s the other members, and kills the leader once it is the only one left; it answers stopped once no member can run, and kills the stopped leader before it gives up at `STOP_PROOF_BOUND`. **Once the leader is seen gone, nothing more is signalled**: members still listed under its number cannot be told from a later session that reused it, so the sweep only waits to see the session empty and otherwise answers unproven (`not-stopped`); an agent that exited on its own and left children behind is therefore not proven stopped. On Linux, the leader's pid held by a process with another start time means the session emptied before, which answers stopped without a signal; elsewhere it answers unproven. A member is signalled only through a `platform::proc::ProcessHandle` opened on it whose process still has the start time it was listed with and is still in the session. On Linux the handle is a pidfd (`pidfd_open`, `pidfd_send_signal`); `ESRCH` means the member is gone, `ENOSYS` (a kernel before 5.3) falls back to the bare pid, and any other failure (`EMFILE`, `EPERM`, …) leaves the member unsignalled, so the session is not seen empty (`platform::proc::pidfd_open_failure`). A member older than the leader is never signalled. **Residual:** on a kernel without pidfds and on macOS the signal goes to the bare pid, so a pid reissued between the identity check and `kill` is the window that remains. The sweep reads its processes through a `ProcessView`, so unit tests stand in for the OS (`the_sweep_stops_the_leader_and_kills_it_last`, `the_sweep_signals_only_the_launchs_own_processes`, `a_member_with_no_pinned_handle_is_not_signalled`). "Can still run" has one definition for the sweep and every later check (`platform::proc::running_session_of`): a process that exists and is not a zombie; a state that cannot be read stays unknown. `probe_process` answers `Exited` for a zombie, which `process_gone` reads as gone.
- **Conversation fence (audit B2, round-4 B2).** A failed restore writes `restore_failed` with `to`, the attempt it started, and, when its stop was not proven, `sessions`: the conversations that agent may be writing to (the one asked for and one it reported instead; for a start over, the old one and any it reported), and `unknown_session` when it reported none and was confirmed in none, for an agent whose kind a restore exists for, or of a kind not known (`Fence::of`). Every later restore or start over of the same attempt checks each `to`'s launch record like the old process (`launch_gone`), strictly: still running or unknown refuses. A restore of **any** item, from any daemon, into one of `sessions`, or, under `unknown_session`, of any agent of the same kind (either kind not known counts as the same), is refused `session-in-use` until that launch is proven gone (`Sessions::fenced`); the successor's own `attempt_ended` does not lift it. Every start through the shim watches for the first conversation the agent reports, and `confirm_fresh` reads it before it answers a refused acknowledgement, so a failure keeps it as evidence. Lane 1 makes the stop unproven with the e2e-only `DOT_AGENT_DECK_TEST_RESTORE_SKIP_SWEEP=1` (`journal/restore/027`; `/031` for an unknown conversation).
- **Fresh start (F3, audit B3).** Start over first refuses `command-reopens` when a recorded command it can read selects a conversation (an early refusal only). For an agent with a `FreshSpec`, the spawn then carries a one-shot fresh-start request, through the same shim, token mint and acknowledgement directory as a resume: `DOT_AGENT_DECK_FRESH_AGENT`, `DOT_AGENT_DECK_FRESH_SESSION` (Claude Code only: a new random UUID) and `DOT_AGENT_DECK_FRESH_TOKEN`, with the shim directory first on `PATH`. At exec time the shim of the named program claims the token and checks the real argument list (`shim::fresh_args`): arguments that select a conversation publish `<token>.refused` (`fresh-args-select`) and run unchanged; otherwise it publishes `<token>` and, for Claude Code, starts it with `--session-id <new id>` in front. Another shimmed program started meanwhile with arguments that select a conversation claims and refuses the token too, so `true;codex resume --last` in a Claude pane is caught. The request is removed from the named program's environment. The daemon (`confirm_fresh`) refuses `command-reopens` on a refused acknowledgement, and `not-fresh` when the shim was not reached (a conversation reported before any acknowledgement, or none within the bound), the agent exited, or a Claude Code start over's first attested session is not the new id; each stops the agent with `stop_proven` before anything is posted. So a Claude Code start over is confirmed new whether or not its old conversation is known. Codex's arguments are read with each level's own option grammar (`CODEX_TOP_LEVEL`, `CODEX_EXEC_LEVEL`, from `codex --help` and `codex exec --help`), and an argument it does not settle (an option it does not list, `-`, a short cluster) counts as selecting (round-4 F4). **Residual (round-4 F3/B1):** the shim checks the arguments of the program of the agent's name it finds on `PATH`, which may be a script of the user's; what that script adds before it starts the agent by another path is not seen. For Claude Code the new id and the first attested conversation still decide (`journal/restore/032`: a same-name wrapper adding `--resume` ends `not-fresh`); for Codex, OpenCode, Pi and Devin, which attest nothing a Start over can be checked against, such a script, like a program started after the token was spent, is not checked. Antigravity and the default shell carry no request and are not checked. A launch that starts no program of the agent's name through `PATH` (absolute path, `PATH` replaced) never claims the token and is refused `not-fresh`.
- **Legacy records (R#2).** `interrupted_work::Index::agent` gives a record without `pid` or `pid_start` the verdict `start_over{old-process-unknown}`, so both clients offer Start over; `check_agent` still refuses a restore of it `old-process-unknown`.
- **Act-time Git and live work (R#3, audit S1, S5).** A restore or start over that acts reads `item_git_facts` in `start`, for the item as `revalidate`'s fresh read found it, with the claims held, after the barrier and close to the spawn (`git_refusal`): a gone worktree refuses either (`folder-missing`), an open pull request refuses a start over (`pr-open`) and is only the question's note for a restore. A dry run reads them before the claims, for the question, and carries them; an acting restore does not. GitHub's state can still change between that read and the spawn. `Sessions::folder_in_use` refuses either (`directory-in-use`) while a launch of a live run, not ended, started in the same directory, compared by `DirKey` (canonical path, or device and inode), so a symlink or a `..` spelling is the same folder; a live launch whose folder cannot be read counts as in it. Lane 1: `journal/restore/029` (a pull request opened while a start over waits at the barrier, behind a fake `gh`) and `/025` (a symlink and a `..` spelling).
- **Restart note (R#4).** The note is admitted (`spawn::admit_seed`) before the spawn (`note-refused`). A post that fails after confirmation stops the agent with `stop_proven`, records nothing when the stop is proven (the item keeps its `resume` verdict and can be restored again), and answers `note-not-delivered`; lane 1 reaches that path with the e2e-only `DOT_AGENT_DECK_TEST_RESTORE_REFUSE_NOTE=1`.
- **Second launch read.** `prepare` reads launch records with `read_all_with_stats` and refuses `incomplete-read` on a truncated or skipped read, as the snapshot does.
- **CLI binding.** `interrupted restore` and `start-over` asking on a terminal carry the dry run's resolved item id (`RestoreOutcome::item`, `StartOverOutcome::item`, additive), the daemon process that answered it and, for a restore with no `--agent`, the attempts it said it would restore, into the action through `DaemonClient::restore_interrupted_pinned` / `start_over_interrupted_pinned`; a replaced daemon answers `RESTORE_DAEMON_REPLACED` and nothing is sent to it. With `--yes` there is no dry run and nothing to bind.

## The TUI

- **Capability.** The TUI asks the attached daemon for its interrupted work with `DaemonClient::list_interrupted_work_restorable`, which answers whether the same `Hello` advertised `restore-agents`. `s` on a daemon known not to says `RESTORE_UNSUPPORTED` and sends nothing; before a list has answered, the client's own capability gate on the restore request is the check, and its `Unsupported` answer is remembered the same way. The L1 seam sets that knowledge with `InterruptedSeamStep::RestoreCapability`.
- **One request.** `s` opens the question and sends nothing. `c`, `o` and `w` count only once a flushed frame showed every row of the question (the stage 2 presentation barrier, `refuse_undrawn_choice`), and only for a choice the verdict offers; the request is the human one, with no caller claim, and a restore or start-over in flight keeps every action waiting until it answers. The open pull request note comes from the list's Git facts (`restore_git_note`), not from a dry run.
- **The restored pane.** `agent_restore::start` announces the new dashboard pane with `spawn::surface_attach_started_agent`, as an attach start does, so an attached TUI titles the card with the agent's name; a start that is not confirmed is closed through `close_started_agents`, which announces the removal.
- **Saved-workspace restore (brief §11-Q1, option b).** With `show_agent_restore()` on, the daemon-empty restore of the saved session leaves out a plain saved pane whose folder and exact command equal a launch record joined, by work id and attempt, to an agent the attached daemon lists with a `resume` verdict (`ui::should_defer_saved_agent_restore`, catalog `journal/restore/018`). The list is asked for with a 5-second bound; the launch records are read from the local state directory, and a record of another deck's does not match, since a work id carries its state directory's deck id and 64 random bits, and a match needs both. A daemon that does not answer in time leaves every saved pane to start as before.

## The desktop app

- **Commands.** `interrupted_work_restore` and `interrupted_work_start_over` (`desktop/src-tauri/src/interrupted_work.rs`) call `DaemonClient::restore_interrupted` and `start_over_interrupted` with no caller claim, pinned to the daemon process the webview named, bounded at 120 seconds like the TUI's. They are not gated on the flag: the client library withholds both unless the same `Hello` advertised `interrupted-work` and `restore-agents`, and answers `unsupported` otherwise. The webview reads them through `interruptedWorkRestore` / `interruptedWorkStartOver` in `desktop/src/lib/bridge.ts`, and a malformed answer reads as `unsupported`.
- **The flag.** `DesktopFeatures.show_agent_restore` (`showAgentRestore` in the webview) projects `features::show_agent_restore()`. `AgentOverview` passes it to the dialog as `restoreShown`, and the dialog gates the **Restore** button, `s`, the agents in an item's details and `askRestore` (which voice reaches) on it, nothing else.
- **Capability.** The desktop has no `Hello` of its own to read `restore-agents` from, so it learns it from the first `unsupported` restore or start-over answer (`InterruptedDeck.restoreUnsupported`, per daemon process); `s` then says `RESTORE_UNSUPPORTED` and sends nothing, as the TUI's does.
- **One request.** A restore or start-over is held by `useInterruptedWork` like a dismissal: `busy` until it answers, then the list again. The question's choices act only once it has been presented (`data-presented`, the stage 2 barrier) and only for a choice the verdict offers. A clean answer (no refusal, every agent given its first message and recorded) closes the dialog, as the TUI closes its overlay; anything else shows `render_restore` / `render_start_over`'s lines on the list.
- **Voice.** `askRestoreInterrupted` (`restore_interrupted`) opens the question; the three confirms are `no_voice` registry entries, so no spoken phrase starts an agent.
- **The preview.** `?fixture=1&interrupted=restore` (or `restore-long`, the same with a long agent name) lists a resumable unit and a Pi that can only start over, and its restore and start-over remove the item, for the Playwright tests (`desktop/e2e/interrupted-work.spec.ts`).

## Hazards worth knowing

- **Claude Code's `--resume <id>` doubles as a search term**: an id it cannot find may open a picker rather than exit. No matching `SessionStart` arrives, so the confirmation times out and the agent is stopped, but the pane shows the picker until then.
- **Claude Code's `bypassPermissions` falls back to the default mode on resume**, so a restored agent may stop at permission prompts it did not stop at before.
- **A prompt on the original command line** would be sent again as a new turn on resume. For Claude Code the shim does not know every flag's arity, so it is not detected, which is acceptable because deck-started agents take their task through the inbox.
- **The desktop question across scrolling (R#5, audit S4).** The restore question counts as presented once all of each of its parts (`partsOf`: the question's child elements) has been on screen, at any scroll positions, each slice for `QUESTION_PRESENTED_MS`, as the TUI counts each row it drew across frames: `usePresented` keeps, per part, the spans of it that were on screen at both ends of that interval, merged, and counts the part once they cover its whole height. A part taller than the dialog therefore counts only once it was scrolled through, not when its middle filled the box. The other y/n questions keep the whole-question rule. The preview's `interrupted=restore-long` lists the restorable agent under a long name for the Playwright test.
- **A same-uid client can send the request with the experimental flag off**: the daemon serves the verbs whatever the flag says. A request carrying a pane claim is refused, which keeps a cooperative agent from restoring agents; it is not an authentication boundary.
