# Work journal

The work journal (PRD #1889) is the daemon's append-only record of what the deck ran: one **work** per launch (a pane, an orchestration, a delegation, a dispatch, a scheduled fire, a scheduled issue dispatch), the **attempts** (agent generations) that served it, where their reports went, and how each attempt and work ended. It survives daemon restarts, so a later daemon can tell which of a previous run's attempts never finished. It is the narrower model PRD #628 chose ([work-identity.md](work-identity.md#decision-revise)); this page is how it is built and how to read it.

The code is in two modules: `src/work_journal.rs` is the file format and the store (ids, the line codec, the redaction guard, the per-run writer thread, the reader, recovery and compaction), and `src/work_tracking.rs` is the daemon's side (`WorkTracker`, owned by `AgentPtyRegistry` and reached through `registry.work()`), which decides which work each launch, attempt, report and end belongs to. PRD #1790 added two stores keyed by the journal's ids, `src/launch_records.rs` and `src/dispatch_task.rs` ([What a restore needs](#what-a-restore-needs-prd-1790)).

## Where it lives

Everything is in `<state_dir>/work-journal/`, an owner-only directory beside `deck-id` (`state_dir` is `crate::config::state_dir()`, in absolute form). Several daemons can share one state directory, so each file has one writer:

| File | What it is |
| --- | --- |
| `run-<run>.jsonl`, then `run-<run>.<n>.jsonl` | The segments of one daemon run, `<run>` being the daemon instance id the daemon sends in `Hello` (it never holds a `.`, so the first `.` starts the number). `run-<run>.jsonl` is created when the journal opens, even before the run has anything to write. When the next line would take the current segment past 8 MiB (`SEGMENT_MAX_BYTES`), the run starts `run-<run>.1.jsonl`, then `.2`, and so on, all under the same run lock. One rule governs rotation: **the run's highest-numbered segment on disk is always the one it is writing**, because every reader and every compaction, this run's or another daemon's, treats the segments below it as sealed. The new segment's directory entry is synced before the run writes to it. When that sync fails, the new file is removed and the current segment keeps taking lines; when the removal fails too, the file is already the run's highest segment to everyone else, so the run switches to it anyway and logs a `warn!` (its lines are synced, but its entry may not survive a crash). A failed rotation is tried again only once the segment has grown further: a sixteenth of 8 MiB more after the first failure, doubling per failure up to 8 MiB (`Writer::rotate`), so a lasting fault costs one attempt and one warning per stretch of lines, not one per line. The writer remembers the next segment number across rotations (`Writer::next_segment`) and it only grows: a name that is already taken (only the run's own writer creates its segments, so such a file came from outside it) moves the number past it for good, with a rate-limited `warn!`, so taken names cannot stall rotation however many there are. Only the highest-numbered segment is still written; the lower ones are **sealed**. Only that run writes them. |
| `run-<run>.lock` | Held by run `<run>` for its whole life, the way `retained_store` holds its run lock (`.pending-<run>.lock` is created, locked, then renamed), and released only after the writer thread has written everything it was handed. A run whose lock is absent or can be taken is **dead**, and so are all its segments. A lock that cannot be judged counts as live, so its files are left alone. |
| `compacted-<run>.jsonl`, then `compacted-<run>.<n>.jsonl` | **Chunks** run `<run>`'s compaction wrote: the lines it kept from the files it folded, cut at about 8 MiB each (`COMPACTED_CHUNK_BYTES`). Each chunk is written to a temp file, `sync_all`, renamed to the next chunk name no file has, and the directory synced, all under `maintenance.lock`; a chunk is never appended to, so any run's compaction may fold any chunk again, whether the run that wrote it is live or dead. |
| `maintenance.lock` | Recovery and compaction hold it **exclusively**, and a read of the directory (`read_journal`, `WorkJournal::read`) holds it **shared** (the platform's whole-file lock, `std::fs::File::lock_shared`). So a read sees the directory before or after a compaction, never between its publish and its unlinks, and two daemons sharing the directory never maintain it at once. Recovery and compaction take it without waiting; a reader waits for it. |

A daemon whose journal cannot open (a directory that fails the owner-only check, an I/O error) runs with it disabled: it records nothing, and that is never fatal. A disabled journal still mints work ids, so agents still get `DOT_AGENT_DECK_WORK_ID` and telemetry still gets `deck.work.id` (see [The work id outside the journal](#the-work-id-outside-the-journal)).

**Read the directory, not a file.** Compaction folds dead and sealed segments into `compacted-*.jsonl` chunks and deletes them, and a long-lived run writes several segments, so a reader (and a test) scans every `run-*.jsonl` (numbered or not) and `compacted-*.jsonl` in the directory and merges them, never one segment path.

## Writing

`WorkJournal::record` never blocks and never touches a file: it stamps the event's `ts_ms` and hands it to the run's **writer thread** (`work-journal`) through a bounded queue of 4096 events (`QUEUE_CAPACITY`). The writer assigns `seq` as it writes, appends the line and follows it with `File::sync_data`, so the file is in the order events were handed over and `seq` has no gaps. When the queue is full the event is **dropped**, counted (`WorkJournal::dropped_events`) and logged with a `warn!` at most once a minute; a slow or stalled disk therefore costs journal lines, never a spawn, a report's acknowledgement or its wake effects. Because `record` only queues, the tracker calls it under its bookkeeping mutex (which is what orders an attempt's end after its start), and no bookkeeping lock or state write guard is ever held across file I/O. The filesystem reads a `workspace` needs are made before that mutex is taken.

`WorkJournal::try_record` is the blocking form (it waits for the write and answers its `seq`), for recovery and tests only. A graceful daemon shutdown (`shutdown_all_graceful`) waits at most 2 seconds (`SHUTDOWN_DRAIN`) for the queue to drain, and dropping the last handle waits as long for the writer to finish and release the run lock.

## Line schema, version 1

Every line is one ASCII-escaped JSON object (non-ASCII written as `\u` escapes, as `retained_store` writes) ending in `\n`, at most 4096 bytes before the newline:

```text
{"v":1,"seq":<u64>,"ts_ms":<u64>,"run":"<run>","kind":"<kind>","work":"w-<deck id>-<16 hex>", …kind fields}
```

- `v` is the schema version, `1` in this release.
- `seq` counts from 1 within one run's writing; `ts_ms` is Unix milliseconds; `run` is the writing daemon's instance id.
- `work` is a **work id**, `w-<deck id>-<16 lowercase hex>`: the deck id from `<state_dir>/deck-id` (so ids are unique across machines) and 8 bytes of OS randomness.
- An **attempt id** is `<run>/<agent id>`: the registry's agent id of one generation, under the run that spawned it.

| `kind` | Fields (`?` = optional) |
| --- | --- |
| `opened` | `launch`: `pane`, `orchestration`, `delegation`, `dispatch`, `schedule_fire` or `issue_dispatch`; `parent`?: a work id; `refs`: an object with any of `issue` (number), `repo` (`owner/name`), `branch`, `pr` (number), `task_id`, `unit_id`, `orchestration_id`, `orchestration`, `role`, `schedule`, `pane`; `workspace`?: a path |
| `attempt_started` | `attempt`; `pane`; `agent` (the agent id, a number); `role`? |
| `attempt_session` | `attempt`; `session`: the agent's own session id, as its hooks reported it; `agent`: the agent type (`claude_code`, `open_code`, `pi`, `codex`, `devin`, or `none` for one this build does not know). Added by PRD #1790 under `v:1`: a reader that predates it skips the kind. See [What a restore needs](#what-a-restore-needs-prd-1790) |
| `attempt_ended` | `attempt`; `how`: `exited`, `closed`, `replaced`, `replacement_failed`, `interrupted` or `unknown`; `code`?: the exit code, with `exited`; `cause`?: `daemon_shutdown` or `daemon_gone`, with `interrupted` |
| `linked` | `refs`, the same shape as `opened.refs` (defined, not emitted yet: see below) |
| `reported` | `report_id`; `task_id`?; `unit_id`?; `destination`: `inbox` or `recovery`; `to`?: the recipient's work id, when the deck knows it |
| `closed` | `how`: `pane_closed`, `unit_ended`, `task_done`, `fire_done`, `orchestration_ended`, `dismissed`, `reclaimed`, `restored` or `started_over` (`dismissed` and `reclaimed` added by PRD #1790 stage 2 under `v:1`: see [Interrupted work](#interrupted-work-prd-1790-stage-2); `restored` and `started_over` by stage 3: see [Restoring an agent](#restoring-an-agent-prd-1790-stage-3)) |
| `attempt_restored` | `from`: the attempt brought back; `to`: the new attempt that brings it back; `how`: `resumed` or `started_over`. `work` is `from`'s work. Added by PRD #1790 stage 3 under `v:1`: the minimal successor link (decision 4 of 2026-10-27: an explicit link, never a reuse of the old ids) |
| `restore_failed` | `attempt`; `failure`: `session_mismatch`, `refused`, `exited`, `shim_not_reached` or `timed_out`. `work` is the attempt's work. Added by PRD #1790 stage 3 under `v:1`: a resume of that attempt was tried and did not take |

`work` on every kind is the work the event belongs to.

### Reader rules

These ship in the first release, so a later schema can add to the journal without breaking this build's reader:

- A line whose `v` is greater than the reader knows is skipped.
- A line whose `kind` the reader does not know is skipped.
- Unknown fields are ignored.
- A complete line that cannot be parsed is skipped, wherever it is in the file.
- A final line with no `\n` is a torn write and is dropped.
- A line over 4096 bytes is skipped without being buffered.
- Lines are merged across files in `(ts_ms, run, seq)` order, and a second line with the same `run` and `seq` is a duplicate and dropped (a compacted chunk and a file it was folded from whose unlink failed can both be present).

- A `closed` line whose `how` the reader does not know fails to decode and is skipped as unparsable (not as an unknown kind), so it does not stop launch-record pruning (`launch_read_incomplete`) and compaction carries it byte for byte. That is why PRD #1790's dismissal and reclaim are new `how` values rather than a new kind, and why stage 3's restore and start over close with `how=restored` and `how=started_over`. The cost is a downgrade: a daemon older than PRD #1790 stage 2 does not see `closed how=dismissed` or `how=reclaimed`, and one older than stage 3 does not see `how=restored` or `how=started_over`, so it lists that work as interrupted again. Stage 3's two new kinds, `attempt_restored` and `restore_failed`, are unknown kinds to an older daemon: it skips them, and while one is in its read it pauses launch-record pruning, as stage 1's `attempt_session` did.

`read_journal` and `WorkJournal::read` apply all of these and return what they skipped in `ReadStats`. Recovery rewrites no file. Compaction carries a line it cannot read into its output byte for byte, up to 10,000 such lines per round (`carried_unreadable`); past that, and for a line over 4096 bytes or a torn tail, the line is discarded and counted in `CompactReport::discarded` (see [Budgets](#budgets)).

## What each launch mints

| Launch | Work | Parent | Opened |
| --- | --- | --- | --- |
| Pane (`StartAgent`, `StartPreparedAgent`, saved-session restore) | one per pane, minted at spawn, with `refs.pane` and `workspace` = the pane's cwd | none | when its first attempt is published, so a refused spawn writes nothing |
| Orchestration | one per instance id, minted the first time the daemon sees the instance, with `refs.orchestration_id`, `refs.orchestration` and `workspace` | the dispatch's or the scheduled fire's work that started it, else none | at its first published role pane |
| Delegation | one per delegated task, with `refs.task_id` and `refs.role` (no `workspace`) | the orchestration's work | once the delegate is posted (see [Delegations](#delegations)) |
| Dispatch (`dot-agent-deck dispatch`, either shape) | one per unit, with `refs.branch`, `refs.unit_id` and `workspace` = the worktree | the dispatcher pane's work, resolved daemon-side from the attested caller | after the unit is registered and its id known, before its task is posted |
| Scheduled fire | one per fire, `launch=schedule_fire`, with `refs.schedule` and `workspace` = the schedule's working directory | none | when the fire runs |
| Scheduled issue dispatch | one per issue, `launch=issue_dispatch`, with `refs.issue`, `refs.repo`, `refs.branch` and `workspace` = its worktree | the fire's work | at its spawn's first published pane, so a spawn that starts nothing writes nothing |

**Which work an attempt serves.** A pane that belongs to an orchestration instance is an attempt of the orchestration's work, with `role` on `attempt_started`, and gets no pane work of its own. A single-agent dispatched unit's generations are attempts of the dispatch's work, and a plain fire's spawned pane is an attempt of the fire's work. A scheduled issue dispatch's panes are attempts of the issue's work when it is single-agent; when it is orchestration-shaped, they are attempts of an orchestration work that is a **child of the issue's work**, by the orchestration rule above, so the issue's refs are one `parent` link up from the attempts. A respawn of the same pane (a `clear = true` delegate, `pane restart`, a re-create) keeps the work its previous generation served and is a new attempt.

### Delegations

The task id is the message id `dispatch_one_owned` mints before the post, so the delegation's work is minted and registered under that task id before `post_reserved_delegate` runs, with no hub lock held (`WorkTracker::delegate_pending`). Its `opened` and the `attempt_started` naming the bound worker generation are held in memory, and:

- written as soon as the post goes in (`delegate_posted`), whether the task is still live or was retired between the inbox accepting the post and that callback (a later post that superseded it called back first, its worker generation ended, its orchestration ended): the inbox accepted it, so it ran. A retired task whose events are still held is not evicted from the 64-entry ring of retired tasks; the ring evicts its oldest settled entry instead, so held entries are bounded by the posts in flight;
- written first, under the tracker's lock, if the worker's `work-done --task-id` is committed before that (a report that races the post);
- dropped if the post is refused (`delegate_refused`), live or retired, so a refused delegate leaves nothing in the journal, as a refused spawn does.

The worker's report is then `reported` on the delegation's work with `task_id`, `report_id`, `destination` and `to` = the orchestration's work, followed by `closed how=task_done`.

### Reports

`reported` means a report the worker or unit itself sent with `work-done`, written after the report is committed (`task_completion.rs`, `journal_report`), from both the live path and the supervisor's recovery path:

- a task's report goes on the delegation's work, `to` = the orchestration's work;
- a unit's terminal report (`work-done --done`) goes on the dispatch's work, with `unit_id`, `to` = the dispatcher's work;
- a note goes on the producer's work, `to` = the recipient's work when known.

`destination` is `inbox` when the report was posted to the recipient's inbox and `recovery` when it was set aside as a recovery row. The deck's own "dispatch ended" notice for a unit that ended without reporting is **not** a `reported`; that unit's work gets only `closed how=unit_ended`.

## Attempts and how ends map

`attempt_started` is written as `spawn_agent_with_dir` publishes the generation, under the registry lock that publishes it, so a stop (which can only find the generation once it is published) closes the pane's work after its start is booked. `attempt_ended` is written in `pump_reader` after `capture_termination`, mapped from the generation's `Termination`:

| `Termination` | `how` |
| --- | --- |
| `PaneCommandExited` | `exited`, with `code` |
| `Closed` | `closed` |
| `Closed` while the registry is shutting down | `interrupted`, `cause=daemon_shutdown` (best effort: the reader threads are detached and may not run before the process exits) |
| `Replaced` | `replaced` |
| `ReplacementFailed` | `replacement_failed` |
| `ReplacementPending`, `ConnectionEnded`, `Unknown` | `unknown` (none of them says how the attempt ended) |

An end that arrives before its start is held (at most 64) and written right after the start.

Works close as follows: a pane's own work `pane_closed` when its pane is stopped or closed; a dispatch's work `unit_ended` when its last pane goes (a dispatch with no caller registers no unit, so its work closes as a scheduled issue dispatch's does, below: `WorkTracker::launched_without_unit`); an orchestration's work `orchestration_ended` when its instance has no records left; a delegation's work `task_done` after its report; an issue-dispatch fire's work `fire_done` after the run finishes; a scheduled issue dispatch's work `pane_closed` with its pane when it is single-agent, and `orchestration_ended` when the orchestration it started ends when it is orchestration-shaped (right away when that pane or orchestration is already gone by the time its spawn returns). A plain fire's work closes `fire_done` with the pane it spawned when that pane is still serving it once the fire has run (`WorkTracker::fire_settled`), and right away otherwise: a fire that re-posted into a pane an earlier fire opened (`new_tab_per_fire = false`, so it has no attempts), one that opened an orchestration (whose own work carries on as its child), one whose spawn failed, and one whose pane already closed.

## What a restore needs (PRD #1790)

Stage 1 of PRD #1790 records, for every agent the daemon starts, what a later stage needs to start it again after a daemon restart. The journal keeps refs, ids and paths only (see [Redaction](#redaction)), and that rule is not relaxed for it, so the record is split three ways, each keyed by the journal's own ids:

- **The session id goes in the journal, as `attempt_session`.** The daemon's hook ingest (`ingest_event_core` in `src/daemon.rs`) hands the registry (`AgentPtyRegistry::session_seen`, which passes it to `WorkTracker::session_seen`) the session id of each report whose hook capability token attested its agent (`attempt_session_report`), recorded against that attested agent, never against an agent the report merely names: a report that also names an agent must name the same one, and a tokenless report records nothing, including one `DOT_AGENT_DECK_HOOK_PROVENANCE=warn` admits for a pane that was issued a token. Of those, only a report the state made the pane's current hook session (`AppState::pane_hook_session_id`): a report the state refused, or one about a conversation the pane has moved past, records nothing, and neither does one the daemon or the `wrap` output classifier authored. The tracker writes it the first time the attempt's id is seen and again each time it changes (a `/clear`, a new conversation), and never for an unchanged id; the last id written is in its book per live attempt and is retired with the attempt. A report from a generation whose spawn is reserved but not yet published (the hook beat the publication) is held, decided under the registry lock, and written in order right after that attempt's `attempt_started`; the held ids are dropped when the reservation ends without an attempt instead (an abandoned spawn, or one published serving no work: `WorkTracker::spawn_abandoned`, called by the registry in the lock hold that ends the reservation, in `abandon_locked`, the reservation's `Drop` and the publication). The held set is therefore bounded by the registry's reservations, one entry per reserved generation and at most `MAX_SESSION_LINES` ids each, rather than by a count of its own, so a reserved generation's first id is not dropped for want of room; a reservation whose `Drop` finds the registry lock poisoned leaks its entry, as it leaks the reservation itself. Nothing is written for an attempt that already ended. **Writes are bounded:** an attempt writes up to `MAX_SESSION_LINES` (32) `attempt_session` lines as its id changes. Past that, and whenever the journal's session quota refuses one, the latest id is held, not written at once: the daemon's session flush (`spawn_session_flush`, every `SESSION_FLUSH_EVERY`, 30 seconds) runs `WorkTracker::flush_held_sessions`, which hands each live attempt's held id to the journal, one line per attempt per round however often the id changed in between, and keeps an id the quota refuses again for the next round. The attempt's end also hands its held id over just before `attempt_ended`, outside the quota and best effort: `WorkJournal::record` drops it when the queue is full. An orderly shutdown (`shutdown_all_graceful`, after it has stopped the agents) hands every live attempt's held id over as well, in `WorkTracker::drain`, before its final barrier: outside the quota, waiting for queue room rather than dropping (`WorkJournal::record_within`), so a graceful stop does not depend on the next round or on a PTY reader, detached at shutdown, reaching the attempt's end. That hand-over is best effort: the shutdown's drain bound (`SHUTDOWN_DRAIN`, 2 seconds) caps its waits for queue room and for the writer, not the lock and the walk over the book, and each wait polls every 5 ms, so it can overrun the bound slightly; an id still unqueued at the deadline stays held and is logged rather than written, and one the writer has not written by then, or that a failed writer drops, is lost. **What this guarantees:** a live attempt's latest admitted id reaches the writer's queue at the first flush round after it was reported that finds room in the quota, without waiting for the attempt to end or for another hook. A daemon that dies before that round, or before the writer took the line, loses that id, and its restore finds the one written before it; a graceful stop hands it over at its drain, and it reaches disk when the writer keeps up within that bound. So a producer that keeps flapping writes 32 lines, then at most one per round, then one at its end. The session quota (`WorkJournal::record_session`) applies to the session events handed over through it, the per-change writes and the flush rounds: together they take at most a quarter of the writer queue (`SESSION_QUEUE_SHARE`), so session churn cannot crowd lifecycle events out of it. The end-of-attempt line does not go through it. **The current session is `work_journal::latest_session_of`'s answer**: the attempt's `attempt_session` line with the highest `seq` from its own run. Do not take the last one in the reader's order, which merges by wall clock (`ts_ms`) first, so a clock stepped backwards between two changes reverses them. Two agents report an id that is not their own resumable session: **Pi**'s hooks report a synthetic `<pane>-session` rather than Pi's own id, so nothing is written for a Pi attempt (`is_resumable_session`), and **OpenCode**'s plugin reports every later session in a folder under the folder's first session id, which is written as reported; a later stage settles which id an OpenCode resume needs.
- **The launch command and display name go in a launch record**, a store of its own beside the journal: `<state_dir>/launch-records/`, an owner-only directory (`0700`) holding one owner-only JSON file (`0600`) per attempt, named `<run>-<agent id>.json` (`src/launch_records.rs`). A record carries `v` (1), `work`, `attempt`, the exact `command` the spawn's caller gave before the daemon wrapped it (`null` for the default shell), `shell` (the spawn's `SHELL` override, or `null`), `agent_type`, the absolute `cwd`, the display `name`, and for an orchestration role its `role`, `orchestration` and `orchestration_id`, plus `ts_ms`. The `cwd` is the folder the child started in. For a prepared start (one entered through a verified directory's descriptor, which on Linux the child enters as a `/proc/self/fd/N` alias that names nothing after a restart), it is a path that names that verified directory (`agent_pty::prepared_launch_folder`): the path the start asked for, made absolute, while it still names the directory (compared by device and inode, the final component not followed); when the directory was moved and something else put at that path, the directory's current path, read on Linux from its descriptor and taken only once that path's own device and inode are the directory's. When neither names it (the directory was removed, or its path cannot be read, as on other Unix), `cwd` is `null` and the record carries `cwd_moved_from`, the path the start asked for, which a restore must not start the agent in; the field is absent otherwise. Otherwise it is resolved as the PTY library resolves it (`agent_pty::effective_launch_dir`): the spawn's cwd when it is a directory, otherwise the `HOME` the child gets (an env overlay's first), else the account's home. The PTY library repeats that directory test itself inside its spawn and falls back to `HOME` when it fails, so that folder is checked again once the child exists (`agent_pty::confirm_launch_dir`): when the path still names the directory it named before the spawn (device and inode), it is recorded; when it does not (removed or replaced in between), on Linux the child's own cwd is recorded, read from `/proc/<pid>/cwd` and kept only when that path's device and inode are the ones the link resolves to; and otherwise `cwd` is `null` with `cwd_moved_from` set to the resolved path, as for a prepared start. Off Unix the pre-spawn folder is kept unchecked. The registry's own `cwd` metadata still keeps only what the caller gave. The spawn path writes it (`WorkTracker::launch_recorded`, from `spawn_agent_with_dir` once the generation is published and the registry lock released), never a client, and only with an enabled journal. It is written whole to a temporary name, `.pending-<16 hex>-<run>-<agent id>.json`, synced and renamed into place, so a crash leaves no half record. `launch_records::read_all` (or `read_all_with_stats`, which counts what it skipped) is the reader: it skips a temporary or unreadable file, one whose `v` is not 1, and one whose file name is not the one its own `attempt` names, without hiding the others. One listing looks at most `MAX_LISTED` (65,536) directory entries: when the store holds more, `read_all_with_stats` answers the records it reached with `truncated` set, and `read_all` answers an error rather than a partial set, so a consumer cannot read "not listed" as "no record".
- **A dispatched unit's task goes beside its worktree**, as `<worktree>/.dot-agent-deck/dispatch-task-<work id>.md` (`src/dispatch_task.rs`), written by the daemon for `dot-agent-deck dispatch` and for scheduled issue dispatch before the unit spawns. It holds the task exactly as the dispatcher gave it (for an issue, the prompt with its issue number substituted), without the report instructions the daemon adds to a single unit's prompt. **The trust boundary is the OS user.** Before the save creates or changes anything (`orchestrator_context::open_held_context_dir`), it refuses, on Unix, a worktree root that another account could write: one owned by another account, writable by other, or writable by a group that is not this account's private group (the group named after the account with no other member, which is the group a Debian/Ubuntu `umask 002` leaves writable on the directories it creates; `orchestrator_context::project_root_refusal`, mode bits only, an ACL is not seen). It then refuses a worktree path another account could redirect (`orchestrator_context::resolve_trusted_dir_path`, judging each entry with `path_entry_refusal`): it resolves the path as the kernel does, from `/`, following each symlink, and every directory and symlink on the way, `/` included, must be owned by this account or root; a directory another account can write (other write, or group write for any group but the private one) must have the sticky bit, and the entry below it on the path must be this account's own, since the sticky bit only stops an account renaming entries it does not own. That is OpenSSH's `StrictModes` model: a worktree under `/tmp` (`1777`) in a directory of this account's own passes, and one under a non-sticky `0777` directory, or reached through a symlink placed in one, is refused. The resolved path, which goes through no symlink, must name the worktree root the save holds open (compared by device and inode), and it is where git is run. It also refuses a worktree that is not a git checkout, before touching `.dot-agent-deck`, so a save refused for any of these reasons neither creates nor re-permissions it. The reason: git is asked about the file by pathname, so an account that can rename entries of the worktree root could swap `.dot-agent-deck` for another directory while git looks and put it back before the file is created, and one that can rename entries of a directory above the root could swap the whole worktree the same way. Such an account can already change the worktree's source, or move it, so the save does not try to bind git's lookup to the directory it holds; it refuses a worktree where another account has that access. Off Unix the root's owner and mode are not judged. The save then opens the worktree's `.dot-agent-deck` once, the way an orchestrator-context publish does: without following a symlink, refusing one owned by another account before any repair, and clearing group and other write on the held descriptor or refusing when it cannot (the publish path's repair policy for the same folder); the file is created `O_EXCL`, owner-only, relative to that descriptor. Before any task byte exists it makes git ignore the file without changing a tracked file: it adds `.dot-agent-deck/` to the clone's `.git/info/exclude` (issue #329's mechanism), and when `.dot-agent-deck/` has no `.gitignore` it creates one containing `*`, which a negation in a tracked `.gitignore` above it (`!.dot-agent-deck/`) cannot override; an existing regular `.gitignore` there is never changed, and an existing entry of another kind (a FIFO, which git would block opening; a symlink; a directory) is refused. On Unix an existing regular `.gitignore` is relied on only when, read without following a symlink relative to the held descriptor, it is owned by this account and writable by neither other nor a group that is not this account's private group (`dispatch_task::ignore_file_refusal`, the worktree root's policy); otherwise the save is refused with a warning and writes nothing, since an account that could edit it could re-include the task between git's verdict and the file's creation. It then asks git whether the file's path is ignored (`git check-ignore -q`: exit 0 ignored, 1 not) and untracked (`git ls-files --error-unmatch`: exit 1 for its "did not match", 0 tracked), and writes no file, with a warning, when either says no or answers any other way, which is a git error and is never read as "untracked". Each git call runs in a process group of its own for at most `dispatch_task::GIT_DEADLINE` (10 seconds); past it the group is killed and the child reaped, the save fails with a warning, and the dispatch goes on and spawns the unit without a saved task. That is git's verdict at the save; a `.gitignore` edited later can change it. The task is written whole to a temp name in the held directory, `.dispatch-task-<work id>.md.tmp` (`O_EXCL`, owner-only), synced, and only then given its final name by a rename that refuses an existing entry (`renameat2(RENAME_NOREPLACE)` on Linux; `linkat` then `unlinkat` of the temp where that rename is unsupported and on other Unix), after which the directory is synced; so the final name never holds a cut-off task, even after a crash mid-write. Each dispatch mints a new work id, so a later dispatch into the same worktree writes a new file; a file already there for the same work id is kept and the save fails with a warning. The age-based coordination sweep (`is_sweepable_coordination_name`) leaves the published file alone by name, and removes a temp a crashed save left once it is past the sweep's age (`dispatch_task::is_temp_file_name`), since a temp is never read as a task; and the inbox spill retention removes only the `inbox-message-*` files it minted, so it does not reach it either. It goes when the worktree goes. Its text is never copied into the journal.

**Launch-record retention follows the journal's.** After each compaction round the daemon reads the journal (`prune_launch_records`) and removes a record only when that read holds no line of the record's work, **and** the read is not one `launch_read_incomplete` flags, **and** the record is at least an hour old (`PRUNE_GRACE`). `launch_read_incomplete` checks exactly three things: the read was truncated, or it skipped a line of a newer schema, or a line of a kind this build does not know, since such a line may be the one naming the work. A line the reader skipped as unparsable, too long or torn does not stop a prune. So a record outlives its work's lines in the journal, which compaction drops under the limits in [Retention and compaction](#retention-and-compaction); the hour covers a record written while its work's `opened` was still queued for the writer, or after the read the prune compared against. An incomplete read removes no record. A record whose work the journal never held (its event dropped from a full queue) goes once the hour has passed, since no reader of the journal can find that work either. The same prune removes up to 256 temporary files a crash left behind, and only those whose name has exactly the temporary shape above and whose run is not live (`WorkJournal::run_is_live`: not this daemon's run, and its `run-<run>.lock` is missing or exists and is not held; a lock it cannot judge counts as live), so the temporary file of a writer whose run lock is held is not reached; this happens whether or not the read was complete. The prune looks at the store one listing window at a time (`MAX_LISTED` entries), each call starting where the previous one stopped (`launch_records::PruneWindow`), so on a store larger than one listing successive rounds move through the store instead of repeating its first window; it removes a record only on what it saw, never on an entry's absence from the listing.

None of this changes the daemon's wire: no `PROTOCOL_VERSION` change, and nothing reaches a client yet.

## Interrupted work (PRD #1790 stage 2)

`src/interrupted_work.rs` derives the interrupted work list from a journal read, a launch-record read (`launch_records::read_all_with_stats`), whether each run is live (`WorkJournal::run_is_live`) and the kept report files (`RetainedStore::kept_reports`). It opens no file and runs no Git or forge query (resolving a workspace canonicalizes paths, as the redaction does): Git and forge facts are added by the caller, per [the authority boundary](#the-authority-boundary).

- **Interrupted.** An attempt is interrupted when its `attempt_ended` (keyed by attempt id) says `interrupted`, or when it has no `attempt_ended` and its run is not live, since startup recovery may not have written the end yet. A work is interrupted when one of its attempts is and it has no `closed`.
- **Items.** Works roll up to one item per root: a delegation rolls into its orchestration, and an orchestration into the dispatch or scheduled issue dispatch that started it. Any other parent (the dispatcher's pane or orchestration, a scheduled fire) is the item's launcher. The item kind is `unit` (root `dispatch`), `issue_dispatch`, `orchestration`, or `agent` (a pane, a scheduled fire's pane, or a root whose `opened` was not read). An item is listed when a work under it is interrupted and no work under it has a live attempt, or when it carries a kept report (below); never when its root has `closed how=dismissed` or `how=reclaimed`.
- **Launch records** are joined by attempt and used only when the record is the one for its attempt and the journal holds that attempt under the record's work and otherwise only under delegations (whose `attempt_started` names their worker's generation). Anything else is ignored.
- **Worktree.** The root's `workspace` (or the first one under the item) is resolved to an absolute path: a joined launch record's `cwd` that redacts to the same workspace is preferred, else the `~` is expanded against `$HOME` (`Workspace::to_path_with_home`).
- **Reports left for a caller that is gone.** A `reported` line is joined to its retained file by report id. It is listed under its producer's item, closed or not, when the file was not acknowledged and either was adopted in state `p`, `r` or `u`, or is this run's own file in state recovered (the inbox accepted it and set it aside when its caller went away, so its line still says `destination=inbox`), or the line says `destination=recovery`. Its "kept until" is the file's deadline.
- **Progress.** Each item carries `progress`: the distinct attempts under it (a delegation's `attempt_started` names its worker's attempt, counted once), the roles they ran as in the order the journal first names each across all of the item's works (an `attempt_started`'s role, or the role a delegation's `opened` names; at most 16), and the delegations opened under it and how many of them have `closed how=task_done`.
- **Incomplete.** A truncated journal or launch-record read sets `incomplete` on the list: an end or close that would hide an item may not have been read. So does a kept-report listing that stopped at its budget, which `RetainedStore::kept_reports` charges for every entry of `files/` and of every run directory in it, together.
- **Dismiss and reclaim** write `closed how=dismissed` or `how=reclaimed` on every work `CloseSets::works_under` names: the root, closed or not, and each work under it with no `closed` yet, so nothing under it is listed on its own later. `CloseSets` indexes one read once, so a dismissal of many items does not re-index the journal per item. Retention is unchanged: the work and the line that hides it age out together.

### The daemon verbs (`src/interrupted_work_daemon.rs`)

- **Bounded replies.** A list or a show is fitted to `MAX_REPLY_BYTES` (8 MiB, half the attach frame) before it is sent: a list keeps at most 2,000 items and 16 report entries per item, a show at most 1 MiB of report entries, every display string at most 4 KiB, and each counts what it left out (`omitted`, `reports_omitted`, `bodies_omitted`, `cut`). A show reads the bodies of the item's first 16 reports, or with `report` any one of the item's reports, matched against the item's whole list, not against what a reply carried. With `reports_from` (an additive, optional field of `ShowInterrupted`) a show answers one page of the item's kept reports: the entries from that index on, at most 16, and their bodies, with `reports_from` and `next_reports_from` on the answer (`fit_show_page`). So every kept report can be found past the list's 16 entries, a page at a time: the CLI's `interrupted show <id> --reports-from <n>`, and `n`/`p` in the TUI's details, which shows only the page it last asked for. A dismissal's selector is refused whole past 256 ids, 512 bytes per id or 32 KiB in all (`close`'s limits), and its `dismissed` and `refused` lists stop at 256 entries each, counting the rest; each dismissed item's name is cut to 4 KiB and the whole answer is fitted to `MAX_REPLY_BYTES`, refusals kept before dismissed items, with what it leaves out counted (`DismissOutcome::fit`). The closes are written before the answer is fitted, so fitting changes only what the answer names. An id that parses as a full work id names that item or none: when that item is no longer listed it is refused as not listed, never matched against another item's name or branch, so an action confirmed on one item cannot land on another.
- **Bounded children.** Every `git` and `gh` child of a list's facts and of a reclaim's geometry, marker and branch checks runs through `src/interrupted_work_probe.rs`: a deadline, a 256 KiB stdout cap, the child's process group `SIGKILL`ed and the child reaped before the call returns, and at most 8 such children at once across the daemon, each holding its permit until it returns. One list's enrichment shares a 20 s budget; an item not started by then gets no facts. The reclaim's dirty and nested-worktree check and its `git worktree remove` run through `issue_dispatch_run`'s runner, which kills the process group at its own bound, as `close`'s cleanup does.
- **Who may act.** Reclaim and dismiss refuse a request that carries a pane claim. The claim is optional on the wire, so this keeps a cooperative agent from acting and is not a boundary against a same-uid process that drops its identity, the same residual `close` discloses ([hook provenance](hook-provenance.md)).
- **Reclaim's guards.** After the journal checks (an untruncated read, the item still interrupted, not a plain agent) and the Git checks (a linked worktree at the recorded path, the item's branch, and the deck's owner marker naming the item's root as the launch that created the tree), the reclaim holds the worktree against spawns by its recorded and its canonical path, then resolves every directory anything the daemon runs or is starting is rooted in to its canonical form, outside the registry lock: one inside the worktree refuses the reclaim (`still-in-use`), and one that cannot be resolved refuses it too (`in-use-unknown`). A spawn whose directory resolves records its canonical spelling as well as the one it was given, so a start through a symlink to a held worktree is refused by the hold. It then takes the per-repository worktree lock, waiting at most `RECLAIM_LOCK_WAIT` (15 s) for it; when it cannot be taken nothing is removed: `kept-busy` when it was not obtained before the wait ran out, `kept-could-not-lock` when it could not be taken for another reason (its path not resolved, its file not opened or locked). `kept-busy` does not mean one operation held the lock throughout: see the lock wait below. The wait tries the lock without blocking (`flock` with `LOCK_NB`) and sleeps between tries (`acquire_spawn_lock_within`), so on Unix a reclaim that gives up leaves no `flock` waiting in the daemon's blocking pool; dispatch's own worktree-lock wait (60 s) and the attach listener's rebind use the same helper. That is the lock the deck takes to create a dispatch's worktree (`create_worktree`, which goes on without it after waiting 60 s) and to remove a worktree a spawn abandoned; removing a dispatched worktree when its agent closes does not take it. Under that lock it runs the dirty and nested-worktree check and then, immediately before `git worktree remove`, re-validates: the device and inode of the canonical path captured at preparation, the git metadata directory and its owner marker, still naming the item's launch, the checked-out branch, the worktrees inside it (asked again, so one added after the first check keeps the tree, `kept-holds-worktrees`), and last the device and inode again, since the probes in between take time. Any other difference keeps the tree (`kept-changed`).
- **The lock wait (`acquire_spawn_lock_within`, `src/platform/lock/mod.rs`).** On Unix each try is a blocking-pool job, and the wait answers by its deadline even when a try cannot run in time (auditor N7): a try still queued when the deadline passes is cancelled, one that starts after it does not try, and one that takes the lock after it lets go at once instead of handing it back. A try already inside the `open` cannot be cancelled, because `O_NONBLOCK` does not bound a slow filesystem; it lets go of what it took when it returns, and only the caller stops waiting for it. **Polling trades fairness for that bound** (auditor N8): a waiter sleeping between tries is not queued in the kernel, so a newcomer can take the lock while it sleeps, and steady short holders can make it miss every release and run out although each of them finished. So a timeout means only that the lock was not obtained in time (`could not get the lock in time`, `kept-busy`), not that one operation held it throughout. The callers accept the trade: worktree creation goes on without the lock after 60 s, as it did before (the bounded `git worktree add` retry still covers a concurrent add), the attach rebind binds without it, and a reclaim or an abandoned-spawn removal keeps the worktree and can be retried. Off Unix the wait is a timeout over the named mutex's blocking acquire, whose owner thread stays waiting for the mutex after the caller gives up; that predates PRD #1790 and is disclosed here, not fixed, so the no-waiter-left property is Unix's alone. `holders_that_take_turns_can_outlast_a_wait_which_says_only_that_it_ran_out` pins the timeout under turnover.
- **What reclaim does not guard against.** The hold refuses spawns this daemon starts, and the lock excludes only the operations that take it (above). Neither stops another process (a terminal, a Git command, another tool) from moving, replacing or switching the worktree, or from adding a worktree inside it. The re-validation checks each fact once, at its own point, and each has its own window between that check and `git worktree remove` acting on the path, which nothing here closes. The directory's identity is checked last (the second device and inode check), so a process that swaps another clean tree in at that path after it can still have that tree removed: Git resolves the path itself. The owner marker, the branch and the set of worktrees inside it are checked earlier, and changing one of them in place changes neither the directory's device nor its inode, so the identity check after them does not notice: a marker removed or rewritten or a branch switched after its own check, or a worktree added inside the tree after the nested list was taken, is not seen, and that nested worktree is removed with it. Without `--force`, Git refuses to remove a worktree in which it reports modified tracked files or untracked files. That covers only what Git reports: ignored files are removed, and so are changes to a tracked file Git is told not to look at (`git update-index --assume-unchanged` or `--skip-worktree`).
- **Whose tree it is (PR #2431 round 2).** `dispatch` and scheduled issue dispatch mint their launch's work id (`WorkTracker::mint_launch`) before `create_worktree` runs, and the ownership marker it writes records that id as `creator.launch` (`Creator::for_launch`); the `opened` is then held under the same id (`dispatch_held`, `hold_launch_as`). A unit's and an issue dispatch's item is rooted at that launch's work, so reclaim compares the marker's launch with the item's root alone (`worktree_owner::marked_launch_in`): the same id goes on, another refuses `newer-run`, and a marker naming none refuses `owner-unconfirmed` — an older build's marker, one written while the journal was disabled and there was no id to record, or a document that cannot be read, parsed or is over 64 KiB. The marker is read with one open that follows no symlink and does not wait on a FIFO (`O_NOFOLLOW | O_NONBLOCK`), the file type is checked on the opened descriptor, and the bytes come from that descriptor (`read_regular_bounded`, which the `gitdir` back-pointer read shares; PR #2431 round 3): a symlink at the marker path refuses `owner-unconfirmed` even when it points at a marker naming the item, a FIFO or any other non-regular file refuses `not-owned` without blocking, and off Unix, where no open refuses a symlink, every marker refuses `owner-unconfirmed`. A worktree created again at the same path gets a new git metadata directory and so a marker naming the later launch. The ownership gate (`is_marked`, and `worktree reclaim`) still reads only that the marker exists and is not empty. This replaced a journal rule that refused when a later `opened` named the same workspace: that rule removed the tree when the later run's `opened` was missing (the writer drops events on a full queue, and the journal can be disabled), named no workspace, was recorded through an alias since removed, or sorted before the item's because the clock stepped back, and it was read once, before the removal.
- **Recording a reclaim.** The task that removes the worktree writes the `closed how=reclaimed` lines, while it still holds the worktree, so a removal that finishes after the 30 s reply bound (the reply then says it timed out) is still recorded.

## Restoring an agent (PRD #1790 stage 3)

`src/agent_restore.rs` serves the two verbs that bring an interrupted agent back: `RestoreInterrupted` (with its conversation) and `StartOverInterrupted` (without it, in the folder it ran in). Both are withheld by the client library unless the daemon advertises `restore-agents` (Unix only) beside `interrupted-work`, both refuse a request carrying a pane claim, and the clients' surfaces are behind `show_agent_restore()` (`docs/develop/experimental-flag.md`); the daemon serves the verbs whatever the flag says.

- **The list's verdicts** (`InterruptedItem.agents[].restore`) come from the journal and the launch records alone, as stage 3's slice 3 made them. Two journal facts feed them now: a `restore_failed` line for an attempt turns a `resume` verdict into `start_over` with reason `not-resumed`, and `closed how=restored` or `how=started_over` on the root hides the item, as a dismissal does.
- **The launch record's process identity.** A record written by this build carries `pid` and `pid_start` (additive, still `v:1`): the agent's child process id and its start time (Linux: `starttime` from `/proc/<pid>/stat`; macOS: the process's start time), read at spawn. `launch_records::process_gone` answers `still-running` while a process with that pid and start time exists and `old-process-unknown` for a record without both fields or on another platform.
- **Every check runs again at act time and in a dry run**, never trusting the list's answer: a fresh snapshot of the journal, the launch records and the kept reports (`interrupted_work_daemon::snapshot`), refused `incomplete-read` when the journal read was truncated or the list is incomplete; the item resolved (`not-listed`, `ambiguous`) and still interrupted (`still_interrupted`); the launch records re-read with `launch_records::read_all`, never the partial set, and the attempt's record required to be its only one (`ambiguous-record`, `no-launch-record`) with its `work` among the item's works; the verdict required to offer the action (`not-restorable`: a restore needs `resume`, a start over takes `resume` or `start_over`); the record's `cwd` present (`folder-moved`, `folder-unknown`). For a restore, the attempt's current session (`latest_session_of`) must pass the agent's `ResumeSpec::valid_session_id` (`no-session-id`, `session-id-invalid`). Then the old process: `process_gone` (`still-running`; `old-process-unknown` refuses a restore but not a start over, which writes to no old conversation) and, on Linux, while the old pid names no process, a scan of `/proc/*/stat` for any process still in the session that pid led (`still-running`): a child the agent left behind, which a shutdown that killed the agent's process group did not reach. Linux does not reissue a pid that is still some process's session id, so a live pid with another start time means the old session emptied before. macOS is not scanned.
- **The folder** is checked last before the spawn: absolute, on disk (`folder-missing`), its path one only this account and root can redirect (`orchestrator_context::resolve_trusted_dir_path`), opened without following a final symlink as a `VerifiedProjectDir` whose identity must match the resolved path, and owned by this account and writable by no other account by mode bits, the private group excepted (`orchestrator_context::project_root_refusal`) (`folder-unsafe`). The agent starts through that held descriptor (`AgentPtyRegistry::spawn_agent_in`).
- **A dispatched unit's saved task** (a start over of a `unit` or `issue_dispatch` item) is read with `dispatch_task::read_saved`: `.dot-agent-deck` opened `O_DIRECTORY|O_NOFOLLOW`, owned by this account and writable by no other, the task opened relative to it `O_NOFOLLOW|O_NONBLOCK`, a regular file owned by this account with no group or other permission bits, at most 1 MiB and UTF-8 (`task-unsafe`); missing is `no-saved-task`. A plain agent's start over runs its command with no task. A task the inbox would refuse as a first message refuses `task-unsafe` before anything starts.
- **One at a time.** A restore or start over of an attempt holds it in a daemon-wide set until it answers; a second request meanwhile is refused `already-restoring`.
- **The spawn.** A new pane work (`launch: pane`, `work_id: None`), so the agent comes back as a dashboard pane both clients see through the ordinary events; the recorded `command`, `SHELL` override, `agent_type` and display name; a fresh pane id, `restored-<name>-<6 random hex>` through `spawn::next_pane_id` (the pane counter starts again in every daemon, so without the random part a restore would reuse the dead pane's id). A restore adds the one-shot resume request and the shim directory to that spawn's environment only: [Agent restore](agent-restore.md) has the mechanics.
- **Confirmation (restore).** The restore succeeds only when the new agent's first attested hook session (`AgentPtyRegistry::watch_restore_session`, fed from `session_seen`, keyed by the pane id minted before the spawn so an early hook is not missed) equals the requested id within 30 s (`CONFIRM_TIMEOUT`; `DOT_AGENT_DECK_TEST_RESTORE_CONFIRM_SECS` in an e2e build). A different session (`session_mismatch`), a refused acknowledgement from the shim (`refused`), the agent exiting (`exited`), or no confirmation in time (`timed_out` when the shim acknowledged, `shim_not_reached` when it did not) stops the new agent as `StopAgent` would (`spawn::close_started_agents`: its card and its process group), posts nothing to it, writes `restore_failed` for the attempt and answers `not-resumed`. The request waits for that final answer; there is no pending state.
- **On success.** A restore posts the restart note (`RESTART_NOTE_CONTINUE` or `RESTART_NOTE_ONLY`) as the agent's first inbox message, from the deck, reason `restart note` (`spawn::post_seed`); a start over posts the saved task, reason `saved task`, and no restart note. Then `closed how=restored` (or `how=started_over`) on every work `CloseSets::works_under` names for the item, and `attempt_restored{from, to, how}`. The answer says whether the first message was posted and whether the lines were written; neither failure stops the agent.
- **Answers.** `interrupted_restore` (`restored`, `refused`, and with `dry_run` `would_restore`) and `interrupted_start_over` (`started` or `refused`, and with `dry_run` `would_start`), each refusal a kebab code with the shared sentence (`interrupted_work::restore_refusal_sentence`), on an `ok` response. Additive optional fields and capability-gated requests: no `PROTOCOL_VERSION` change and no contract break.

## The daemon's bookkeeping is bounded

`WorkTracker`'s in-memory book holds entries only for what is live, and every entry is retired on a terminal path of what it tracks, so a long-lived daemon does not accumulate it:

- **A spawn** gets a `SpawnWork` guard from `resolve_spawn` and holds it to the end of `spawn_agent_with_dir`. Dropped before the spawn's first attempt is published (a refused duplicate pane, an error after the fork, an unwind), it forgets the pane work or orchestration work the spawn minted. Spawns of one orchestration share its unpublished work through a count, so a failed role spawn never removes a work another role is still starting or has already published.
- **A delegated task** is retired on its report, on its refusal, when a newer task's post supersedes it, when the worker generation it was bound to ends, and when its orchestration ends. Supersession is by id: the post retires exactly the tasks the inbox's task ledger settled as superseded by it (`PostedDelegate::superseded_tasks`), so a newer task to the same pane that is still on its way to being posted is never retired by an older one's post, whichever post completes first. Tasks retired without a report sit in a ring of the 64 most recent (`MAX_RETIRED_TASKS`), so a report already on its way still finds its work; a settled task evicted from that ring is remembered as task id → its work and its orchestration's work only, up to 4096 of them (`MAX_SETTLED_TASKS`, oldest first out), so a late report of a task superseded long before is still written on its work.
- **A pane** is forgotten when it is closed: by a stop (`stop_agent_steps`), and by a spawn's rollback (`close_started_agents`, when a later orchestration role fails or a pane's first prompt is refused), each once its close is confirmed. So a plain fire whose pane was rolled back is closed `fire_done` at once rather than waiting on a pane that is gone.
- **A dispatch's or a scheduled issue dispatch's work** is held (`WorkTracker::hold_launch`) until its spawn settles. A spawn that fails having written nothing of it forgets it. One that fails after something of it was written (an attempt of its own, or the orchestration it started, whose `opened` names it as parent, before a later role failed) writes its `opened`, so that child's parent can be found, and closes it: `unit_ended` for a dispatch, and as what it started ended for an issue dispatch. A unit's entry goes when the unit ends.
- **An end that arrives before its start** is held, at most 64.
- **A live attempt's session book** (PRD #1790: the last id written, how many lines it wrote, the id it holds back) is retired when the attempt ends. **The session ids held for a reserved generation** are removed in the registry lock hold that ends its reservation (publication, abandonment, or the reservation's `Drop`), so there is one entry per reservation the registry holds, each at most 32 ids; a `Drop` that finds the registry lock poisoned leaves its entry, as it leaves the reservation.

## Restart recovery

At startup, in `run_daemon_with`'s state-dir block after the retained store opens and before the inbox is installed and the scheduler starts, the daemon:

1. opens the journal for its run;
2. starts recovery (`WorkJournal::start_recovery_in_background`) on its own thread, so the async startup path does not wait for it (only when that thread cannot be started does the first attempt run in place): it reads every file, streaming each one line by line, and for every `attempt_started` of a dead run with no `attempt_ended` anywhere in the journal, appends `attempt_ended {how: interrupted, cause: daemon_gone}` to **its own** segment, with `work` = that attempt's work;
3. starts compaction off the startup path.

Recovery never rewrites a dead segment, and **never runs without `maintenance.lock`**, held exclusively. It runs on a background thread (`work-journal-recovery`): at once, and when another daemon's recovery or compaction (or a reader) holds the lock, again every 500 ms (`RECOVERY_RETRY`) until it gets it. This run's compaction is skipped (`CompactReport::skipped_recovery_pending`) until that first attempt has run. The skipped round is not left to the next hourly tick: the compaction task (`spawn_compaction`) waits for that first attempt on the blocking pool, in one-second slices (`WorkJournal::wait_recovery_attempted`), and runs the round as soon as the attempt has run. Recovery may therefore run while this run's own agents are live, which is safe: it only ends attempts of dead runs, whose segments this run never writes.

An attempt that gets the lock ends one of three ways (`RecoveryReport`): **completed** (`completed()`), **incomplete** (over its budget: it wrote nothing), or **failed** (an I/O error, kept in `error`, or an interruption line the writer could not write). Only a completed recovery ends the phase. An incomplete or failed one (`RecoveryStart::Retrying`) is tried again on the same background thread, after a wait that doubles from 500 ms up to 5 minutes (`RECOVERY_BACKOFF_MAX`), and right after every compaction round that folded files, since folding is what brings an over-budget journal back within recovery's budget. Compaction does not wait for an incomplete recovery (it would otherwise never get the chance to shrink the journal). The interruptions are therefore written later in the same run, not only at the next start. A deferred recovery runs while this run's own agents are live, which is safe: it only ends attempts of dead runs. After a SIGTERM an attempt's end may read `daemon_shutdown` (written by the dying daemon) or `daemon_gone` (written by the next one's recovery); both are correct.

No report is recorded against a task posted before the restart. The new daemon's tracker has no record of the old run's task ids, so `WorkTracker::reported` writes nothing for one; and a report from an agent of the old daemon, one that detached from its PTY and survived the restart, carries a hook capability token the new daemon has no record of, which it refuses (`Refusal::UnknownToken`, under every `DOT_AGENT_DECK_HOOK_PROVENANCE` policy). Such a task's attempts still open at the restart end `interrupted` instead, written by the dying daemon (`daemon_shutdown`) or by the new one's recovery (`daemon_gone`).

## Retention and compaction

Compaction runs once right after startup, in a spawned task on the blocking pool, and then hourly. Each round takes `maintenance.lock` exclusively without waiting (it skips the round when anyone holds it, a reader included). It may fold every dead run's files, every **sealed** segment (a live run's segment below its highest-numbered one, this run's own included) and every compacted chunk, into new chunks of its own run, and deletes what it folded. A live run's highest-numbered (writable) segment is read, so a work with a line there is kept, but never touched. So a daemon that stays up has its own finished history compacted and aged out without a restart. Lines are carried byte for byte; a torn tail may be dropped.

A work is **finished** when none of its lines is in a live run's writable segment and every attempt it started has an `attempt_ended`, whether or not it was `closed`: a pane work whose daemon went away is never closed, but recovery ends its attempts, and it must not be kept forever. There is one exception: a work that a **live** run started an attempt of and has not closed is not finished, unless it is a delegation (which gets no new attempt). That run may still serve it: a pane whose agent exited keeps its work until it is closed, and restarting it writes a new attempt of the same work, which must still find its `opened`, workspace and parent. It becomes finished once the run closes it or is gone. Compaction drops a finished work whose last event is older than 30 days (`RETENTION_AGE`) and keeps at most the 10,000 most recent finished works (`RETENTION_FINISHED_WORKS`). In both cases a work a kept work needs is kept too: its ancestors, and a work whose line ends an attempt the kept work started (a delegation's attempt is its worker generation, whose end is written on the orchestration's work). A work that is not finished is kept.

A round makes two streaming passes:

1. **Index.** It reads every file and keeps only a per-work index: when the work was last seen, its parent, the attempts it started and which work's line ended each, whether a line of it is in a writable segment, and which files hold its lines. The index is bounded by the compaction budget's entries and is not byte-budgeted: it reads every file, full chunks included, until it is full. When the index is over that budget, or the directory listing was truncated, the round **drops no work and removes no lock** (`CompactReport::retention_skipped`): a line it did not read could belong to, be a child of, or pin a work it would drop. It still folds files, which brings the journal's file count and bytes back within the rewrite's budget over rounds.
2. **Rewrite.** It picks files within the round's file and byte budget: first the files of the oldest works retention drops, each together with the files of every work that needs it, then segments and chunks under half the chunk size. A work is dropped only in a round that rewrites every file holding a line of it, so it is never half removed. Each picked file is streamed into new chunks; what a round does not pick waits for a later one (`CompactReport::over_budget`). A full chunk with nothing to drop is not rewritten, so no round copies the same full chunk again (the index pass still reads it every round). While the index fits its budget, a round with something to drop rewrites the files of the oldest works it drops first, so the journal comes down to the retention limits over rounds, in files and bytes, however far it is over one round's rewrite budget. A work whose files alone exceed the budget is folded on its own, over budget, when nothing else could be dropped.

**Index saturation is an accepted limitation.** The index needs an entry for every distinct work, attempt and file reference in the journal. When there are more than the budget's entries, which at the defaults (500,000) is roughly 125,000 finished works with one attempt each (a work, its attempt, the reference to that attempt and one file reference: four entries apiece), the index is full every round: retention is skipped (fail closed, as above), no dead run's lock is removed, and `CompactReport::index_saturated` is set, with a `warn!` at most once a day naming the condition. Folding alone does not cure it, because packing the lines into fewer files leaves the same number of distinct works and attempts; finished works stop aging out until the budget (`Budgets::compaction.entries`) is raised. Curing it in place would need a different indexing strategy (for example partitioned passes over the works), which this PRD does not build.

## Budgets

Every file is streamed and a line over 4096 bytes is never buffered. A read keeps the events it returns; recovery keeps an index of attempts; compaction keeps its per-work index (bounded by entries, not bytes) and, while it rewrites, a de-duplication set of at most the budget's entries `(run, seq)` keys and the unreadable lines it carries (`CompactReport::held_peak`). A listing keeps at most 65,536 names. Reading, recovery and compaction each work within a `Budget` of files, bytes and entries (`Budgets`, in `JournalOptions`). The budgets limit the input and memory a call takes on, so a huge or hostile directory, many short junk lines, many files or one enormous line cannot exhaust the daemon's memory; they do not bound wall-clock time, and the startup recovery still reads and writes the disk (each interruption it writes waits for its `sync_data`), on its own thread.

| Who | Default budget | Over budget |
| --- | --- | --- |
| A read (`read_journal`, `WorkJournal::read`) | 4096 files, 256 MiB, 500,000 lines | answers what it read, with `ReadStats::truncated` set and a `warn!` |
| Recovery | 4096 files, 512 MiB, 500,000 attempts | writes **nothing** that attempt (`RecoveryReport::incomplete`), since an end it did not read could make an interruption it wrote false, and is retried (see [Restart recovery](#restart-recovery)) |
| Compaction | 1024 files and 128 MiB rewritten per round; 500,000 index entries; 500,000 de-duplication keys per round | rewrites what fits and leaves the rest for a later round (`over_budget`); over its index budget it drops no work and removes no lock (`retention_skipped`, `index_saturated`), which lasts until the budget is raised (see above) |

Compaction also carries at most 10,000 unreadable lines (`carried_unreadable`) per round; the rest are discarded as they are read, never collected, and counted in `CompactReport::discarded`, so a directory full of junk shrinks instead of being carried forever.

## Redaction

- Refs, ids and paths only. No prompt, report or terminal text is written: `reported` carries a report id, and a dispatch's free-text name is not recorded (its slug is, in the branch).
- Only `workspace` may hold a filesystem path. A path under the home directory is written with the home prefix as `~` (`~/code/x`), and the home directory itself as `~`; any other path is written in its lexical form (below).
- The path is judged **as resolved**, not as spelled: `.` and `..` are resolved lexically in both the path and the home, and the path's canonical (symlink-resolved) form is compared against the home's lexical and canonical forms where they resolve. So `/home/../home/u/x`, `/home/u/./x` and a symlinked home reached by its target's spelling are all written `~/x`. The home's canonical form is computed once, when the journal opens. When the path's canonical form cannot be read for a reason other than its absence (a permission error, say), no privacy-safe spelling can be established and `workspace` is left out of the event.
- Every other string field is refused when it looks like a path (absolute, `~`-relative, a Windows drive path, or one containing either spelling of the home directory). Role, schedule and orchestration names get no stricter grammar: they are not paths into the home directory.
- Every string field is refused when it contains a control character (including `\n`, `\r`, `\t`) or is longer than 1024 bytes.
- A refused event, or a line over 4096 bytes, is dropped with a `warn!`, never truncated. A ref the rule refuses is left out of the event the tracker builds rather than dropping the whole event.

## The work id outside the journal

- **`DOT_AGENT_DECK_WORK_ID`.** With the journal enabled, every agent the deck spawns gets the id of the work its attempt serves, set beside `DOT_AGENT_DECK_AGENT_ID` after stripping any inherited or replayed value, whether or not telemetry is configured. An orchestration role's generation, including one respawned by a `clear = true` delegate, gets the orchestration's work id, never the delegation's: the delegation's link to that generation is its own `attempt_started`. The id is pinned on the generation's `AttestFacts.work`, which is how a respawn keeps it and how `dispatch` resolves the caller's work.
- **`deck.work.id`.** With telemetry configured, the same id is on the run's `agent.run` span and in the agent's `OTEL_RESOURCE_ATTRIBUTES` (`telemetry::propagation::agent_env`), so the agent's own telemetry carries it. It is not a resource attribute of the deck's own exporter, and `agent.handoff` does not carry it.
- **When there is no id.** A disabled journal (its directory unusable) still mints work ids, so both the variable and the attribute are set as usual; the work is just not recorded. The daemon always installs a journal, disabled or not, so the id is absent only when minting fails, which needs the operating system's random source to fail, or on a registry the daemon did not set up (a unit test's).

## The authority boundary

Git and the forge stay authoritative: Git for code, branches and whether a worktree exists; GitHub for what was asked (issue text), what happened to a change (PR state) and claims between people and machines. The journal is authoritative only for what the deck itself ran: which attempts ran, where, under which parent, how they ended and where their reports went. It is observational about whether the work is done. Anything that acts on it is to re-check Git and the forge first, as the scheduler's skip checks do today ([work-identity.md](work-identity.md#decision-revise)).

## Orderings a reader must not assume

- **`opened` before a work's attempts.** A single-agent dispatched unit's `attempt_started` is written before the dispatch's `opened`, because the unit id `opened` carries is minted after the unit's panes spawn.
- **A predecessor's end before its successor's start.** On a respawn the successor's `attempt_started` can precede the predecessor's `attempt_ended`, because the old reader thread ends after the successor is published.
- **A delegation's start before its worker's end.** When the worker generation ends between the inbox accepting a delegate and the tracker's callback for that post, the delegation's `attempt_started` is written after that generation's `attempt_ended` (which is on the orchestration's work). Key ends by attempt id, not by line order.
- **One work per attempt id.** A delegation's `attempt_started` names the worker generation, which is also an attempt of its role's (the orchestration's) work. That attempt's single `attempt_ended` names one of the two works. Recovery and compaction key ends by attempt id across the whole journal, and a reader should too.
- **File order.** Files are merged by `(ts_ms, run, seq)`; the order of files in the directory means nothing.

## What is deliberately not recorded

- **`linked` is defined but not emitted.** Linking a work to a pull request after the fact is left to a later PRD; until then a work's `pr` ref is absent and the branch is the join key.
- **No issue on interactive dispatch.** No issue number is parsed out of a branch or a dispatch name; only a scheduled issue dispatch, which knows its issue, records `refs.issue`.
- **No text.** No prompt, report body, terminal output or dispatch name, and nothing per tool call: the journal holds lifecycle events only. The hook-ingest path writes one kind, `attempt_session`, and only when an attempt's session id changes (or, past the per-attempt cap, at a flush round). A dispatched task's text and an agent's launch command and display name are kept outside the journal ([What a restore needs](#what-a-restore-needs-prd-1790)).
- **A fire that reuses an existing pane** (`new_tab_per_fire = false`) has a fire work with no attempts; it is `closed how=fire_done` right after the re-post.

## For the PRDs that build on it

Every consumer reads through the shared reader, and **checks `ReadStats::truncated` before inferring that something is absent or finished**: a truncated read stopped at its budget, so a missing `attempt_ended`, `closed` or work there means "not read", not "not written".

- **#1890, interrupted work after a restart.** Read the whole directory; a work is interrupted when an attempt of it ended `interrupted` (either cause) and the work has no `closed`. To find the issue to resume, start from the interrupted attempt's work and **walk up its `parent` chain to the nearest work whose `opened` carries `refs.issue`**: for a single-agent scheduled issue dispatch that is the work itself, and for an orchestration-shaped one it is the orchestration work's parent. That work's `refs.issue`, `refs.repo` and `refs.branch` say which issue to resume, and the authority boundary above says to re-check the branch and issue before acting.
- **#1860, per-work totals.** Join telemetry on `deck.work.id` (on `agent.run`, and on the agents' own data through `OTEL_RESOURCE_ATTRIBUTES`) and walk `parent` links for roll-ups: a delegation's parent is its orchestration, an orchestration's is the dispatch or fire that started it, a dispatch's is the dispatcher's work.
- **#1790.** Use the same reader (`read_journal` or `WorkJournal::read`, which take the shared maintenance lock and the read budget) rather than a second parser, so the skip rules above stay in one place, and key on work ids and attempt ids rather than on panes, which are reused. A truncated read cannot show that a work is done. This holds for what stage 1 added too: an attempt's sessions are its `attempt_session` lines from that reader in `seq` order, and its current one is `latest_session_of`'s; its launch record is joined on `attempt` (and `work`) through `launch_records::read_all`, never by pane; and a dispatched unit's task is found by its work id, as `dispatch-task-<work id>.md` in the worktree its `opened.workspace` names.

  **What a stage that acts on these records must check.** The reader makes a record well-formed, not safe to execute. A consumer that will start a command, resume a session or hand back a task from them must: join each launch record's `work` and `attempt` against a complete journal read, and refuse a record whose attempt the journal does not hold under that work; refuse an ambiguous attempt (two records for one attempt, or an attempt the journal holds under two works) rather than pick one; check the session id against the agent's own id syntax before using it (the journal's redaction keeps paths, control characters and over-long strings out of it, which is not a syntax check); pass a resume id to the agent as one literal argument, never interpolated into shell text; open the recorded `cwd` and the saved task without following symlinks and check they are owned by the user and not writable by group or other; and keep the explicit user confirmation and the check that the old agent process is gone before starting anything. `src/launch_records.rs`'s module docs repeat this list beside the reader.
