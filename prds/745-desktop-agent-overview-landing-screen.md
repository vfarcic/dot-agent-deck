# PRD #745: An agent overview as the desktop app's landing screen

**Status**: In progress — iterations 1 and 2 complete (M1–M12). **The M9/M11 cross-version manual test has been RUN and it passed** (2026-09-02, branch `630b0ab` paired against v0.39.0 `1ea0fe7`), so it is no longer a blocker on this PR leaving draft — see [Cross-version safety](#cross-version-safety) for the result and the two limits it carries: the roles were stand-in `bash` shells rather than real agents, and the desktop half is not covered. Iteration 3 (destinations, and promotion to landing screen) is deferred by design.
**Priority**: Medium
**Created**: 2026-08-30
**Issue**: [#745](https://github.com/vfarcic/dot-agent-deck/issues/745)

## Problem Statement

The desktop app opens straight into the control deck. `App` is two lines — `return <ControlDeck runtime={useDeckRuntime()} />` (`desktop/src/App.tsx:63-65`) — and `ControlDeck` renders one flat `.agent-grid` of every agent the daemon owns (`desktop/src/App.tsx:383-404`), each tile defaulting to a mounted terminal (`tabs[agent.id] ?? "terminal"`, `desktop/src/App.tsx:390`). There is no index, no "what is running right now" summary, and nothing that degrades gracefully once there are more agents than fit on screen. A daemon commonly runs nine or more.

Three things make that worse than a layout complaint.

**The deck renders everything, always.** Nothing virtualises or paginates. Each visible tile allocates an xterm with 8000 lines of scrollback and attempts a WebGL context (`desktop/src/components/TerminalViewport.tsx:61,93-104`); browsers cap concurrent WebGL contexts, and past the cap the addon's `catch` silently degrades that pane to the DOM renderer (`:101-104`). PRD #176's M1.3 throughput qualification — the milestone that was supposed to measure exactly this — is still outstanding (`prds/176-desktop-gui.md:123`), and no benchmark exists anywhere in the repo.

**Attaching a PTY is not tied to rendering one.** This is the finding that most shapes this PRD. `TerminalViewport` never attaches anything; the attach trigger is `TauriDeckBridge.attachAgents`, which attaches every agent in the snapshot that is not already attached (`desktop/src/lib/bridge.ts:367-373`), fired from `connect()` (`:488`) and again on **every** `desktop://snapshot` event (`:506`). Each attach opens a real daemon `AttachStream` socket (`desktop/src-tauri/src/terminal.rs:119-137`), and an `AttachStream` sends a full scrollback snapshot before it starts streaming (`src/daemon_protocol.rs:60-65`). So a list-only overview that mounts no terminal at all would still open nine sockets and replay nine scrollbacks today, for content nobody is reading.

**The grouping the screen wants is already delivered and thrown away.** The daemon sends each agent's tab membership — dashboard, mode name, or orchestration with role name, role index, start-role flag, orchestration id and display title — and it survives all the way into the webview (`desktop/src/lib/bridge.ts:45-48`). `agentFromDto` then reduces it to a role string and two booleans and drops the rest (`:143-152,179-180`); `AgentSession` has no `tab` field at all (`desktop/src/types.ts:58-88`). Nine agents belonging to two orchestrations currently read as nine unrelated tiles.

## Solution Overview

A fleet overview: every agent the daemon runs, grouped the way the daemon already groups them, described only by things that are actually true, with no terminal attached. Eventually it is what the app opens on, and you drill from it into an agent or an orchestration — but that promotion depends on those destinations existing, so it is staged deliberately rather than taken in one step (see [Staging](#staging)).

Three commitments define the screen.

**Honesty over completeness.** The overview shows what the daemon genuinely knows and nothing else. It is explicitly better to ship a narrow screen than a wide one padded with `Unavailable` — see [Columns: the central decision](#columns-the-central-decision), which settles this field by field. This extends to values the app currently *fabricates*: live mode renders `ATT 01` on every tile from a hardcoded `attempt: 1` (`desktop/src/lib/bridge.ts:163`, `desktop/src/components/AgentTile.tsx:135-138`), which is worse than showing nothing because it looks like data.

**No terminal on this screen, ever.** Whatever is showing output is what attaches. That requires making attach demand-driven, which is real work rather than a consequence of rendering no terminals — see [Demand-driven attach](#demand-driven-attach).

**Single-daemon today, daemon-shaped from day one.** The screen is written against one daemon, but the model carries a daemon identity and the layout's top-level unit is a daemon group — see [Preserving the multi-daemon extension](#preserving-the-multi-daemon-extension).

### Staging

The work is deliberately split so the *design* can be reviewed before any of the plumbing is built.

**Iteration 1 — fixture only.** The overview is built against the existing fixture transport, with no daemon involved, and ships **alongside** the current deck rather than replacing it: one rail button, deck still the default. It is knowingly a **dead-end dashboard** — informative, with nothing to click through to. The point is to settle layout, grouping, density and what a card carries while all of that is still cheap to change. This iteration touches no Rust and opens no socket.

**Iteration 2 — connected.** The same screen against a live daemon. This is where demand-driven attach becomes necessary (M7) and where the daemon-side `last_activity` field lands. Note the trap: because fixture mode opens no sockets at all, iteration 1 genuinely does not need the attach change — which makes it easy to carry the omission into iteration 2 unnoticed and ship a screen that is visually clean and costs exactly what today costs.

**Iteration 3 — destinations, and promotion to landing screen.** Deferred, explicitly. The overview only becomes the *landing* screen once there is somewhere to go from it: a group view (the current deck, filtered to one tab bucket) and a single-agent view. Until then, making it the default would land users somewhere they cannot leave. This is recorded here as the design's endpoint; whether it ships as a later iteration of this PRD or as its own is decided when we get there.

So this PRD as scoped **does not fully satisfy the title of issue #745**. It builds the overview and defers making it the landing screen. That is intentional and was the explicit decision — an overview with no exits is worse than no overview.

## Scope

### In Scope

- **The overview screen itself**: grouped agent cards, honest columns, live status, no terminals.
- **Grouping by the daemon's own tab buckets**: dashboard agents form a standalone bucket, which leads the screen the way the TUI's dashboard tab leads the deck; an orchestration reads as one unit with its roles in role order and its coordinator marked; mode tabs group by mode name.
- **View state above `ControlDeck`**, as a discriminated union from the start even while it carries only two values, so later destinations arrive as added variants rather than as a refactor.
- **One "Overview" rail button** to reach it. Converting the rail into real navigation is not attempted here.
- **A daemon identity on the agent model** and composite `(daemonId, agentId)` keying, while there is still exactly one daemon and it costs nothing.
- **Fixture work**, which is where iteration 1's whole value sits: cutting the fixture's agent shape down to the columns that genuinely exist; a **crowded scenario** (`?fixture=1&state=crowded` — several orchestrations, a mode bucket, standalone agents), because a four-agent fixture cannot answer a question about many agents; and a genuine **connected-with-zero-agents** state, which has no fixture at all today.
- **Empty, unreachable and incompatible states.**
- **Demand-driven terminal attach** (iteration 2): attach where a terminal is actually shown, rather than for every agent in every snapshot.
- **Surfacing three fields already on the wire but dropped by the desktop's own Rust DTO** (iteration 2): write lease, last user prompt, orchestration cwd. No protocol change; see [Cross-version safety](#cross-version-safety).
- **Removing the two fabricated live-mode values** (`attempt`, `branch`) from what the app presents as fact.
- **`last_activity` as an additive optional field on `SessionSnapshot`** (iteration 2) — the one daemon-side change in this PRD.
- **The Linux build-prerequisite docs gap.** `docs/develop/desktop-gui.md:8` names no command and never says that `cargo test-fast` and rule 2's clippy gate *require* the Tauri system packages because both run `--workspace`. A Linux contributor hits `gobject-2.0 was not found` on their first commit attempt with no pointer to that page.

### Out of Scope

- **Model, token, cost and context-window columns.** They do not exist in daemon state at all — not on the wire, not in `RunningAgent` (`src/agent_pty.rs:1726-1884`), not in `SessionState` (`src/state.rs:710-747`). Creating them is [PRD #633](https://github.com/vfarcic/dot-agent-deck/issues/633)'s discovery work, not this screen's.
- **Git branch per agent.** Nothing tracks it daemon-side; the only `git branch` calls in `src/` are deletions in the dispatch flows. Reconstructing it means either a subprocess per agent cwd on the daemon, or a desktop-side git call that breaks the "local daemons only" boundary (`docs/develop/desktop-gui.md:207`).
- **Attempt/retry count.** No such counter exists anywhere. Removing the fabricated one is in scope; inventing a real one is not.
- **A duration built from `SessionState.started_at`.** ~~Session duration~~ — superseded by M11, which ships an uptime column from a different source; the Work Log entry for 2026-09-02 records why the original rejection was overstated. `started_at` is still the wrong source, and for a *deeper* reason than the one stated here first: it is EVENT-derived, so an agent that has never emitted a hook event has no start instant at all, and the hydration path invents it as `now` when `pane_started_at` has no entry (`src/state.rs:5728-5738`). What ships instead is `AgentRecord.spawned_at_ms` — the instant the daemon forked the child, an observation rather than an inference, absent (and rendered as nothing) whenever the daemon did not do the spawning.
- **Terminal thumbnails, previews or output snippets on the overview.** Any of them re-creates the attach cost this PRD exists to remove. Worth noting for the future: this is the *only* thing discussed here that the daemon's API genuinely could not serve today — see [Why no new daemon API](#why-no-new-daemon-api).
- **Any change to the existing control deck's layout or contents.** It keeps working exactly as it does now and stays the default screen. Its eventual future is to become the group view (iteration 3), reached already filtered to one tab bucket; nothing here anticipates that beyond leaving it alone.
- **A group view and a single-agent view**, and therefore any drill-in navigation. Deferred to iteration 3 — see [Staging](#staging). This is what makes iteration 1 a dead-end dashboard, deliberately.
- **An unfiltered "show all agents" view.** Once the deck becomes the group view, a global all-agents variant is one more value in the view union. It is not built until someone misses it.
- **Connecting to more than one daemon.** That is [#742](https://github.com/vfarcic/dot-agent-deck/issues/742). This PRD only owes it a layout and a key that do not have to be rewritten.
- **Virtualisation or pagination of the overview.** Cards without terminals are cheap; revisit if a real deployment exceeds what one screen holds.
- **The `experimental` feature flag.** Deliberately not applied — see [Feature flag](#feature-flag).
- **Any end-to-end harness for the real Tauri window.** None exists (see [Testing](#testing-what-rule-4-means-here)); building one is its own PRD.

## Technical Approach

### Columns: the central decision

The issue is emphatic that this be decided deliberately, so it is decided here rather than deferred. **The overview shows only what the daemon genuinely exposes. No column is added to this PRD that would require inventing a new source of truth.**

Available today with **no daemon change and no protocol change** — all of it already reaches the webview:

| Column | Source | Note |
|---|---|---|
| Status | `SessionSnapshot.status` (`src/state.rs:642`) → `DAEMON_STATUS` (`desktop/src/lib/bridge.ts:128-140`) | The primary signal. Already exhaustively mapped, with an unknown status falling through to a neutral state rather than a terminal one. |
| Display name | `AgentRecord.display_name` (`src/agent_pty.rs:2006`) | Falls back to role. |
| Agent type / CLI | `AgentRecord.agent_type` (`src/agent_pty.rs:2030`), live value preferred (`desktop/src-tauri/src/dto.rs:270-275`) | |
| Working directory | `AgentRecord.cwd` (`src/agent_pty.rs:2011`) | Labelled as the working directory, **not** as "worktree" — the daemon has no per-agent worktree field. |
| Active tool | `SessionSnapshot.active_tool` (`src/state.rs:650`) | Name plus detail. The live answer to "what is it doing". |
| Tool count | `SessionSnapshot.tool_count` (`src/state.rs:652`) | |
| Orchestration membership | `AgentRecord.tab_membership` (`src/agent_pty.rs:2020`) → `DesktopTab` (`desktop/src-tauri/src/dto.rs:86-107`) | Orchestration name, role name, role index, start-role flag, orchestration id. Present in the webview today and discarded at `desktop/src/lib/bridge.ts:143-152`. Drives grouping. |

Available **on the wire but dropped by the desktop's own Rust DTO** — recovered by editing `map_agent` (`desktop/src-tauri/src/dto.rs:268-302`), with no daemon change and no protocol impact:

| Column | Source | Note |
|---|---|---|
| Last user prompt | `SessionSnapshot.last_user_prompt` (`src/state.rs:654-658`) | The honest replacement for the current hardcoded `"Task metadata unavailable from daemon"` (`desktop/src/lib/bridge.ts:161`). The TUI already renders it as the card's `Prmt:` line (`src/ui.rs:19344-19353`). |
| Write lease | `SessionSnapshot.live_target` (`src/state.rs:666-667`) | Replaces the hardcoded `writeLease: "unknown"` (`desktop/src/lib/bridge.ts:169`). |
| Orchestration cwd | `TabMembership::Orchestration` (`src/agent_pty.rs:369`) | Currently swallowed by the `..` rest-pattern in `map_tab` (`desktop/src-tauri/src/dto.rs:256`). Useful as the orchestration group's header. |

Requiring **daemon work**, and taken only in the last, severable milestone:

| Column | Source | Note |
|---|---|---|
| Last activity | `SessionState.last_activity` (`src/state.rs:718`) → `SessionSnapshot.last_activity_ms` | The daemon maintains it and already uses it as the `ListAgents` join tie-breaker (`src/daemon_protocol.rs:1482-1486`), but it was not on `SessionSnapshot`. Added by M9 as an additive optional field carrying **epoch milliseconds** — a documented **do-not-bump** case (`src/daemon_protocol.rs:11-14`). The desktop-side alternative, accumulating per-agent timestamps from the `desktop://daemon-event` stream, costs nothing but reads blank for every idle agent until it next does something — which on an overview is precisely the agent you most want a timestamp for. **Unlike a `started_at`-derived duration, it survives a restart honestly**: it is a high-water mark of observed event timestamps rather than a value re-minted on hydration, and when the daemon cannot vouch for it the field is absent and the column renders nothing. That difference is what let this ship where a duration built on `started_at` could not — see the M9 work-log entry for the check. (M11 then shipped a duration anyway, from `AgentRecord.spawned_at_ms`, which is an observation rather than an inference; the rejection below was always about the source and not about durations.) |

Explicitly **rejected** as columns, with the reason recorded so this does not get relitigated: model, tokens, cost, context-window percentage, git branch, attempt count, and a **session duration built from `SessionState.started_at`**. The first four do not exist in daemon state in any form; branch would need a subprocess per agent or a boundary violation; attempt has no counter; and `started_at` is event-derived, so it has nothing to say about an agent that has never emitted a hook event — the agent whose duration a reader most wants. That last rejection is the narrow one the Out of Scope bullet now states: M11 ships an **Uptime** column from `AgentRecord.spawned_at_ms`, the instant the daemon forked the process, which is an observation the daemon definitionally holds and renders as nothing when it did not do the spawning. The TUI's own session card shows none of them either (`src/ui.rs:19139-19364`), which is independent confirmation that the daemon does not have them rather than that the desktop forgot to ask.

### Why no new daemon API

The natural reading of "the overview is cheap, the deck is expensive" is that the daemon over-serves and needs a leaner endpoint. It does not, and building one would solve a problem we do not have.

The daemon's API is already factored into exactly the two things needed, kept apart:

- **`ListAgents`** returns structured metadata per agent — `AgentRecord` (`src/agent_pty.rs:1996-2066`) with id, pane id, display name, cwd, tab membership, agent type, rows/cols, and a nested `live: Option<SessionSnapshot>` (`src/state.rs:639-708`) carrying status, active tool, tool count, first prompts, last user prompt and write lease. **That single response covers every column in the table above.** `get_snapshot` already builds the desktop's whole snapshot from that one call (`desktop/src-tauri/src/daemon_bridge.rs:196-221`).
- **`AttachStream`** is the PTY byte stream, expensive by nature: a full scrollback replay on connect, then live output.

Two other things ride alongside, both already in place and both **O(1) in agent count**: one global event subscription (`desktop/src-tauri/src/lib.rs:654`), which is what makes the screen live rather than frozen at connect, and the `Hello` handshake that produces the connected / disconnected / incompatible states.

So the overview costs **one RPC plus one already-open event stream, whatever the agent count**. Today's deck costs that *plus one `AttachStream` socket and one full scrollback replay per agent*. Nine agents: one connection instead of ten. The entire difference is client-side.

The one thing the daemon genuinely could not serve today is an *output preview* — last N lines per agent without a live subscription — because the only way to get output at all is to subscribe to all of it. Previews are out of scope precisely so that gap never has to be filled; if that decision is ever revisited, this is the daemon-side work it implies.

### Demand-driven attach

What makes the deck expensive is not that it renders terminals — it is that attach is not tied to rendering at all. `attachAgents` lives inside `TauriDeckBridge`, takes the snapshot payload, and attaches every agent it has not already attached (`desktop/src/lib/bridge.ts:367-373`), filtered on `this.attached` rather than on anything mounted. It is called from `connect()` (`:488`) and from the `desktop://snapshot` listener (`:505`), neither of which knows what is on screen. `TerminalViewport` triggers nothing.

The consequence is the thing most likely to be lost: **a screen that displays no output still opens a socket per agent.** Launch the app on an overview today and the bridge opens nine `AttachStream` sockets with nine scrollback replays, streaming bytes into in-memory buffers that nothing displays. "Shows no terminals" and "opens no PTYs" are separate properties, and only the first comes free.

So attach moves out of the snapshot listener and to wherever a terminal is actually shown. Detach on leaving is a judgement call — re-attaching replays scrollback so nothing is lost, but bouncing between two agents pays that replay each time; a small most-recently-used set is the likely answer, and measuring beats guessing.

Note this change is **only meaningful alongside a screen that shows agents without their output**. Shipped against today's deck alone it would be a no-op, since every agent is displayed with a terminal and "attach what is shown" and "attach everything" name the same set. That is why it belongs in this PRD rather than in one of its own.

All of it is desktop-side, and directly testable at the bridge level today: `bridge.test.ts:118-142` already asserts on attach behaviour against a mocked `invoke`, so "the overview attaches nothing" is a real assertion rather than an aspiration.

### Grouping

The daemon's `TabMembership` is the grouping key, exactly as the issue suggests:

- **Orchestration** — one card per orchestration, identified by `orchestration_id`, titled by display title or orchestration name, listing its roles in `role_index` order with the start role marked. This is the unit; its members are rows inside it, never peers of it.
- **Mode** — grouped by mode name.
- **Dashboard** — a standalone bucket for agents belonging to neither.

**Order: standalone first, then orchestrations, then modes.** The reason is TUI parity rather than aesthetics — the TUI's dashboard tab is always the first tab, so the overview leads with the same bucket and a user moving between the two surfaces reads them in one order. Orchestrations and modes follow in first-appearance order, and roles inside an orchestration stay in `role_index` order.

`AgentSession` grows a structured `tab` field so the frontend stops reconstructing membership from a role string. Everything needed is already in `DesktopAgentDto.tab`.

### Screen and view state

**The rail looks like navigation and is not.** Of its six buttons (`desktop/src/App.tsx:299-306`), five open overlay sheets over the always-mounted deck — `projectsOpen`, `promptsOpen`, `workflowOpen`, `profilesOpen`, and Settings, which only sets a notice — and the sixth, "Runs", is a no-op whose `onClick` closes all four panels and whose `active` is computed as "none of them are open" (`:301`). Nothing in the app is a view; every "which surface" decision is a boolean in `ControlDeck`'s own `useState` block (`:69-87`). So adding real view state fills in an intent the code already gestures at rather than fighting an existing model.

The overview renders *instead of* the deck, so the new state belongs in `App` (`:63-65`), above `ControlDeck`. It goes in as a **discriminated union from the start**, even while it carries only `deck` and `overview`, so that iteration 3's group and agent views arrive as added variants rather than as a refactor of a boolean. No router library is warranted.

The rail gains one **Overview** button. "Runs" keeps its current behaviour for now, even though it will eventually have no referent once the deck becomes the group view — converting the rail into real navigation is iteration 3's problem, and pre-empting it here would be guessing.

### Preserving the multi-daemon extension

Two decisions, both free today, are what stop #742 from being a rewrite.

**The layout's outermost unit is a daemon group, not an agent group.** With one daemon that group renders with minimal chrome — a connection lamp and a socket/identity line, roughly what the rail shows now — and the orchestration/mode groups nest inside it. Adding a second daemon adds a sibling at that level and changes no inner component.

**Agents are keyed by `(daemonId, agentId)` from day one.** Agent ids are per-daemon monotonic integers starting at 1 (`src/agent_pty.rs:3286,4984-4985`), so two daemons both mint `"1"`. Nine separate maps currently key on the bare id, and two of them are sharp: `insert_unique_session` evicts by `agent_id` (`desktop/src-tauri/src/terminal.rs:63`), and `sendTerminalInput` resolves its session by bare `agentId` (`desktop/src/lib/bridge.ts:566`) — which in a multi-daemon world means keystrokes reaching the wrong daemon's agent. This PRD does not fix all nine; it introduces the daemon identity on the model and keys the overview and its drill-in by the composite, so #742 inherits a correct key instead of retrofitting one.

Partial failure — one daemon down while others are healthy — stays out of scope, but nothing here forces the single `ConnectionView` (`desktop/src/types.ts:9-17`) to remain global; it moves inside the daemon group.

### Empty, unreachable and incompatible states

Four states, all of which the daemon already distinguishes and the app already partly renders:

- **Connected, zero agents** — the first-run experience. Today this shows `<EmptyDeck>`'s "No active agent surfaces" with no banner (`desktop/src/App.tsx:405,484-486`). The overview owns this state properly and it must say what to do next. **There is no fixture for it**: `createFixtureSnapshot`'s ternary sends `state=empty` down the *disconnected* branch (`desktop/src/data/fixture.ts:264-268`), so `?fixture=1&state=empty` shows a disconnected banner over an empty deck. Adding a real one is in scope, because otherwise the first-run screen is the one screen with no way to look at it.
- **Disconnected** — banner plus the existing Start daemon / Reconnect actions (`desktop/src/App.tsx:354-360`).
- **Incompatible** — build or protocol mismatch, classified by `classify_handshake` (`desktop/src-tauri/src/daemon_bridge.rs:73-142`). Replace daemon stays gated on a zero-agent daemon (`desktop/src/App.tsx:358`); the overview must not imply a fleet it cannot see.
- **Loading** — the initial seed (`desktop/src/hooks/useDeckRuntime.ts:11-43`).

### Cross-version safety

Per CLAUDE.md rule 12, answered explicitly rather than as a formality.

**Iteration 1 (M1–M6) is the simplest possible rule 12 answer: no daemon contract change, and no Rust at all.** Every file it touches is TypeScript under `desktop/src/`. It does not reach the daemon wire, the desktop crate's Rust, or the webview IPC DTO — so there is nothing to bump, nothing to declare `.breaking.md`, and no cross-version manual test to run. The PR's rule 12 answer for iteration 1 is an unqualified **no**.

**M7 and M8 stay off the daemon wire too.** M7 (demand-driven attach) changes *when* `desktop_terminal_attach` is invoked, not what any protocol carries. M8 edits `map_agent`/`map_tab` in `desktop/src-tauri/src/dto.rs`, which is desktop-crate ↔ webview IPC and not the daemon wire; the fields it recovers are already being sent by the daemon and already parsed by the desktop, and are simply not copied into the DTO. No `PROTOCOL_VERSION` bump, no semantic change to any existing field.

**M9 and M11 are the milestones that touch the daemon.** M9 adds `last_activity_ms` to `SessionSnapshot`; M11 adds `spawned_at_ms` to `AgentRecord`. The rule 12 answer is the same for both, and the paragraph below is written for M9 because it came first — everything in it holds for M11 unchanged, with `session/live/014` standing where `session/live/013` does and `AgentRecord.spawned_at_ms` where `SessionSnapshot.last_activity_ms` does.

M9, in full: `PROTOCOL_VERSION` is 8 (`src/daemon_protocol.rs:227`) and **stays 8**: the module's own policy names additive optional fields tagged `#[serde(default, skip_serializing_if = "Option::is_none")]` as an explicit **do-not-bump** case (`src/daemon_protocol.rs:11-14`) — the same basis on which `AgentRecord.live` was added (`src/agent_pty.rs:2056-2065`). Nothing renames, retypes or re-means an existing field, so there is no semantic break behind a stable wire either and no `.breaking.md` fragment. `session/live/013` proves the forward-compatibility claim in both directions rather than asserting it: an older peer's snapshot payload with no key decodes to `None` with every other field intact, and a newer peer's payload carrying the key decodes without disturbing anything an older reader understands. Bump policy: **patch**.

#### The M9/M11 cross-version manual test — RUN on 2026-09-02, and it passed

**Result.** Branch head `630b0ab` was paired against tag **v0.39.0** (`1ea0fe7`) — two real builds of two different commits, with no `DOT_AGENT_DECK_BUILD_ID_OVERRIDE` anywhere. All three of the procedure's tells hold: exactly **one** `Attach protocol listening` line for the whole run; one daemon pid (**3622595**) and one daemon build id (`0.39.0-g1ea0fe7`) serving it end to end; and **`server_version: 8`** read off the **live** daemon's wire, via a read-only raw `Hello` frame, rather than inferred from the two binaries. Both trees carry `PROTOCOL_VERSION = 8`, so this exercised **semantics behind a stable wire** — which is what rule 12 exists for — and not a handshake rejection.

**What it exercised.** The branch TUI showed the build-mismatch prompt and **named the live agents** (`orchestrator`, `coder`); declining it attached the branch TUI to the v0.39.0 daemon with the full live state restored — both cards, both roles, the status the coder pane had been given under the *old* TUI, and the orchestrator pane's scrollback. Under that pairing a **delegate still routed** to its worker, **`work-done`** round-tripped back into the orchestrator pane, and a **status hook** repainted the card live. Two checks beyond the three the rule requires also passed: a **pane spawn** driven from the branch TUI (a wire *write* path) landed on the old daemon, and **read-path parity** held — `daemon status` run from the branch binary and from the v0.39.0 binary against the same live daemon returned byte-identical tables. Same-version controls were run at **both** ends: the v0.39.0 TUI before, and the v0.39.0 TUI again on the same never-restarted daemon after the branch TUI had detached. **Nothing behaved differently from same-version.**

**Two limits, stated rather than glossed.** First, the roles were **stand-ins, not real agents** — every one ran `bash --norc --noprofile -i`, and the `delegate` / `work-done` / `agent-event` calls were typed into the panes by hand. That genuinely proves delegate routing, hook delivery and card repaint survive the pairing; it does **not** prove a real agent does, and CLAUDE.md rule 4 records that this project has historically over-relied on stand-ins. Second, **the desktop half is not covered**: the Connect anyway → Overview → confirm `Uptime` and `Last activity` are blank observation described below was not performed, because no harness drives a real Tauri window (issue [#836](https://github.com/vfarcic/dot-agent-deck/issues/836)) and it remains a manual observation for the user.

So the claim this run supports, written at the width its evidence carries: **the TUI↔daemon contract is intact for these two additive fields, verified with stand-in agents; the desktop leg and the real-agent leg are not covered.**

**The procedure that was run**, kept here because a re-run should follow it. **Its documented trap makes a skipped step look like a pass rather than an error** (CLAUDE.md rule 12, measured on the PRD #313 run): with no agents live, the build-version handshake silently terminates the old daemon and lazy-spawns a matching one in under a second, and you then run a *same-version* test that looks like it passed. The order below is what actually reaches the scenario.

Sandbox first. Every process in the run — both daemons, both TUIs, the desktop app — gets these exported, and `DOT_AGENT_DECK_LOG` and `DOT_AGENT_DECK_EXPERIMENTAL` are the two most often forgotten: the log path is resolved separately from the sockets, so an otherwise-isolated daemon still appends into the real `~/.local/state/dot-agent-deck/deck.log`, and project-config discovery walks up from **cwd** rather than `$HOME`, so a sandbox at a sibling path still reads the operator's real `~/.dot-agent-deck.toml` and both sides come up with whatever feature flags it sets.

```sh
export SANDBOX=/tmp/dad-xver-745            # disk-backed, NOT the agent scratchpad (rule 14)
mkdir -p "$SANDBOX/home" "$SANDBOX/state"
export HOME="$SANDBOX/home"
export DOT_AGENT_DECK_STATE_DIR="$SANDBOX/state"
export DOT_AGENT_DECK_SOCKET="$SANDBOX/hook.sock"
export DOT_AGENT_DECK_ATTACH_SOCKET="$SANDBOX/attach.sock"
export DOT_AGENT_DECK_LOG="$SANDBOX/deck.log"
export DOT_AGENT_DECK_EXPERIMENTAL=0
export DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0   # the trap's second mouth (below)
```

1. Start a daemon from the **previous release** and leave it running.
2. Bring agents up under it with the **previous-release TUI** — this is the load-bearing step. At least one orchestration, so there is a delegate path to exercise.
3. **Close that TUI.** The daemon and its agents survive it.
4. Start **this branch's TUI** against the same sockets. Because agents are live, it must show the build-mismatch prompt and name them.
5. **Decline** the prompt. The new TUI now attaches to the old daemon unchanged.
6. Confirm the two flows that would break behind a stable wire: a `dot-agent-deck delegate` still **routes** to its worker, and **hooks** still arrive — a status change and a work-done both reach the card.
7. Verify you actually got the scenario before trusting the result: exactly **one** `Attach protocol listening` line in `$DOT_AGENT_DECK_LOG` for the whole run, and the same daemon pid and build id serving it end to end. Two such lines mean the run is a same-version test, from **either** of the two causes — step 3 or 5 did not take, or the daemon's default 30-second idle window elapsed before the first attach and the TUI lazy-spawned a replacement (`Daemon idle window elapsed …` in the log). This run lost its first attempt to the second cause, which is why `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` is in the sandbox block above; CLAUDE.md rule 12 now carries both. One further ordering note from the run: do the status-hook check **after** the delegate check, since an `agent-event --type running` makes the daemon classify that pane's agent type as `Pi`, which routes prompt delivery differently and makes a delivered delegate briefly look undelivered.

**The desktop half is separate, it has its own path onto an older daemon, and it was NOT run.** No harness drives a real Tauri window (issue [#836](https://github.com/vfarcic/dot-agent-deck/issues/836)), so this stays a manual observation for the user and the paragraph below is the instruction rather than a record. Issue #801 (commit `fa02054`) added **Connect anyway** for a build-stamp-only mismatch, so the desktop reaches this scenario without a TUI: previous-release daemon with agents live → this branch's desktop app → **Connect anyway** → open **Overview** and confirm the fleet renders and the **Last activity** column reads sensibly. The specific thing to look at is an agent that has been idle a while: it must show its real age (`34m ago`, `2h ago`), not `just now` and not blank. Blank for *every* agent means `AgentRecord.live` is absent, which is the older daemon behaving exactly as the no-bump decision predicts — expected only if the daemon you started genuinely predates `SessionSnapshot` itself, and otherwise a finding.

**M11 rode along with the M9 run rather than needing its own, and its TUI half is discharged while its desktop observation is not.** The procedure above is unchanged and its scope did not widen: same sandbox, same seven steps, same two flows to confirm. The Uptime observation in the next sentence belongs to the desktop half, so it remains outstanding with the rest of it. M11 adds no new failure mode to it — the field is additive and optional on the same wire, and it changes nothing about routing or hook delivery — so what it needs is one extra *observation* during the run already scheduled, not a second run. In step 6, look at the **Uptime** column alongside Last activity. Against a previous-release daemon it must be blank for every agent, because that daemon has no `spawned_at_ms` to send; a value appearing there would mean the field is being invented client-side, which is the one thing this milestone forbids. The forward direction — this branch's daemon serving an older client — needs no observation at all: an older client does not know the key and drops it.

The **positive** case, an agent whose uptime actually renders, is a same-version observation and belongs to the ordinary manual smoke check rather than to the cross-version run: start this branch's daemon, bring up an orchestration, open **Overview**, and confirm each row's Uptime is a plausible age that grows, that a `clear = true` delegate (which respawns the worker) resets **that worker's** uptime while leaving the orchestrator's alone, and that the hover shows the spawn instant.

**Bump policy**: patch. Nothing here breaks compatibility in either direction.

### Feature flag

CLAUDE.md rule 9 asks whether a new user-visible surface ships behind `experimental`. The answer here is **no**, and this is not a fresh judgement: PRD #176 decision 6 (`prds/176-desktop-gui.md:101`) already recorded it for this entire binary — *"the `experimental` flag (PRD #139) does not apply. That flag is a presentation switch that gates render/input seams inside the TUI binary… A separate GUI binary has no such seam — the act of building/running it is the opt-in. So maturity is handled by packaging."*

The mechanics confirm it. The desktop crate does link the root library (`desktop/src-tauri/Cargo.toml:15`), so `features::experimental_enabled()` is callable — but nothing calls it, and `run()` never calls `init_and_watch` (`desktop/src-tauri/src/lib.rs:995-1018`), so it would read the OFF default forever. Wiring it up honestly would mean resolving the flag against *some* project directory, and the desktop's only notion of one is `desktop_project_cwd()` — derived from `option_env!("CARGO_MANIFEST_DIR")` with a `current_dir()` fallback (`desktop/src-tauri/src/dto.rs:321-336`), a development convenience rather than a user's project. There is no good answer for a packaged app, which is itself an argument for not gating.

### Testing: what rule 4 means here

Rule 4 mandates coverage for user-visible behaviour and is written in the TUI's vocabulary — L1 (`insta` + `TestBackend`) and L2 (PTY + vt100, `e2e_*.rs`). This feature lands in the Tauri app, so the mapping is stated rather than assumed:

- **The desktop's L1 equivalent exists and is good**: vitest + jsdom + Testing Library (`desktop/package.json:14`, `desktop/vite.config.ts:17-21`), rendering the real `ControlDeck` against a hand-built runtime (`desktop/src/App.test.tsx:13-24,43-51`). `TerminalViewport` is already mocked out in that suite (`App.test.tsx:7-9`), so a screen with no terminals is *easier* to cover than the current deck. It stood at 7 files and 46 tests when this PRD was written; iteration 1 took it to **9 files and 100 tests**.
- **The Rust DTO half runs in the per-task gate.** `desktop/src-tauri` is a workspace member (`Cargo.toml:2-8`), so its 35 tests run under `cargo test-fast` and are linted by rule 2's clippy command. `agent_mapping_is_frontend_stable` (`desktop/src-tauri/src/dto.rs:639-647`) is the existing pattern for pinning a DTO's exact frontend-facing shape.
- **The desktop's L2 equivalent does not exist.** No Playwright, no WebdriverIO, no `tauri-driver`, nothing under `tests/` that mentions the desktop. Nothing drives the real window, real IPC, real xterm or real WebKitGTK. This PRD does not build that harness, and says so rather than implying rule-4 parity. The compensating control is the manual smoke check in `docs/develop/desktop-gui.md:250`, extended to cover landing on the overview and drilling in against a real daemon.
- **CI**: the `desktop-web` job runs `pnpm test` and `pnpm build` on every non-Renovate PR (`.github/workflows/ci.yml:132-153`), and `pnpm build` is `tsc && vite build` so it is the type gate too. Note `desktop-web` is **not** one of the four required checks — `build`, `build-macos`, `build-windows`, `security` are — so the Rust half of the coverage is the part that actually blocks a merge.

**What iteration 1 actually proves, stated precisely, because the two claims are easy to conflate.** Its tests assert that the overview mounts **no `TerminalViewport`** — spying on the mocked component so a mount-then-unmount still trips it — against a **fixture** runtime. That is a component-level property, and it is not the same as "attaches zero PTYs": attach is snapshot-driven, so in live mode `attachAgents` still fires for every agent from `connect()` and from every `desktop://snapshot`, whatever is on screen. This is precisely the risk recorded below, and a second review pass found it had already been walked into — the overview was reachable in live mode, where it attached everything while saying it attached nothing. Iteration 1 therefore gated the screen to fixture mode (`showOverview()` in `desktop/src/App.tsx`, both seams tested). **That gate is gone as of M7**, which made attach demand-driven and then removed it; the two seam tests were inverted rather than deleted, so the live-mode path through both is now the covered one.

**The bridge-level assertion was M7's obligation, not iteration 1's, and it is now discharged.** The single most valuable test in this PRD is the one asserting that a snapshot with N agents attaches **zero** terminals while the overview is up, because that is the property the whole design rests on and the one that will silently regress. It could not be written honestly until M7 made attach demand-driven. It now exists in `desktop/src/lib/bridge.test.ts`, driving `TauriDeckBridge` — the live bridge, the only one that owns PTYs at all — and the fixture-mode gate is gone.

## Success Criteria

- An overview of every agent the daemon runs is one click from launch, and reading it does not require opening a terminal.
- Rendering the overview attaches **zero** PTYs, proven by an automated bridge-level test rather than by inspection. **Met by M7.** Iteration 1 proved only that the screen mounts no `TerminalViewport` against a fixture runtime, and gated the screen to fixture mode for exactly that reason; M7 made attach demand-driven, proved zero attaches against `TauriDeckBridge` — the live bridge — for a nine-agent snapshot with nothing shown, and removed the gate.
- Nine agents across two orchestrations read as two units, with roles in role order and each coordinator identifiable — not as nine unrelated tiles.
- Every value on the screen is one the daemon actually reported. Nothing is fabricated, and nothing reads `Unavailable`.
- A daemon that is down, incompatible, or owns zero agents each produce a screen that says what happened and what to do next — and each is reachable in the fixture without a real daemon.
- The crowded fixture scenario is legible: the design answers "what is running right now" at fifteen agents, not only at four.
- The existing control deck is unchanged in behaviour and remains the default screen.
- Adding a second daemon later means adding a sibling group and no inner component changes; nothing in the overview is keyed by a bare agent id.

## Risks

- **"The overview shows no output" is not "the overview opens no PTYs".** These come apart because attach is snapshot-driven, not render-driven, and conflating them is how M7 gets dropped as unnecessary and the whole thing ships as a cosmetic change. Iteration 1 genuinely does not need it — fixture mode opens no sockets — which makes the omission easy to carry into iteration 2 unnoticed.
- **Demand-driven attach is a behaviour change to code that currently works.** Get it wrong and a terminal is blank, or duplicates output on re-attach. The existing generation/replay machinery (`desktop/src/lib/terminalBuffer.ts`, tested at `terminalBuffer.test.ts`) is the protection, and re-attach replays scrollback from the daemon — but this is the change most likely to break something people rely on.
- **Designing against a fixture that lies.** The fixture carries `model`, `cost`, `tokens`, `contextPercent`, `branch`, `spend: 2.57` and `run_7f24a`, none of which exist in live mode. Approve a layout built on those and it goes half-empty on first contact with a daemon. M1 exists solely to remove this risk, and it has to land before the design is reviewed, not after.
- **A four-agent fixture cannot answer a many-agent question.** The premise of the whole PRD is that the current screen fails at scale; reviewing the replacement at four agents reviews the wrong thing. Hence M2.
- **An honest screen may read as an empty screen.** Removing model, cost, tokens and context leaves status, tool, prompt and membership. (A duration is on that list no longer: M11 ships one from `AgentRecord.spawned_at_ms`, and M12 makes the whole set the operator's choice, so a screen that reads thin is now one column-picker click from being fuller.) That is genuinely useful, but it is a smaller card than the fixture's, and the fixture is what everyone has seen. The design has to make the remaining columns carry their weight rather than looking like a stripped-down version of something better.
- **A dead-end dashboard is only acceptable while it is additive.** Iteration 1 ships a screen you cannot navigate out of, which is fine only because the deck stays the default and nobody's workflow depends on the overview. Promote it to landing screen before iteration 3 exists and the app gets strictly worse than it is today.
- **Silent WebGL degradation, in the deck this PRD does not touch.** Every visible tile allocates an xterm with 8000-line scrollback and attempts a WebGL context (`desktop/src/components/TerminalViewport.tsx:61,93-104`); browsers cap concurrent contexts and past the cap the addon's `catch` drops that pane to DOM rendering with no indication. Nothing measures where that cap is. The overview sidesteps it; the deck and any future group view do not.
- **Scope creep toward #742.** Introducing a daemon identity is cheap; per-endpoint connection state, partial-failure handling and a keyed bridge map are #742's whole job. The line is: this PRD adds the *key* and the *outer group*, nothing else.
- **Scope creep toward #633.** Every rejected column has an obvious "but we could just…" answer. Each of them means new daemon state, and that is a different PRD.
- **No end-to-end coverage of the real window.** The screen can be proven correct against a hand-built snapshot and proven not to attach at the bridge, but nothing automated proves it works in the actual Tauri app against a real daemon. The manual smoke check is the only backstop, and manual checks decay.
- **PRD #176 M1.3 remains unmeasured.** This PRD reduces load without measuring anything, so the ceiling stays unknown — better, but still unquantified.

## Open Questions

1. **Does the group view mount a terminal per member, or only the focused one?** Deferred with iteration 3, but recorded now because it decides whether the group view answers the original complaint or relocates it: a single orchestration is commonly six roles, and the dashboard bucket is unbounded. Leaning: focused-only, with the rest as status cards — which makes the group view structurally the same component as the overview, just scoped.
2. **Two paths to the agent view.** Once destinations exist, overview → agent and overview → group → agent reach the same screen with different back behaviour. Worth deciding rather than discovering.

### 2026-08-30 — Iteration 1, round 2: the security audit and the code review

An audit and a review ran over the iteration-1 diff. Every finding below was taken; the constraints were unchanged, so nothing here touches `attachAgents`, `desktop/src-tauri/`, Rust, the daemon, or navigation.

**The security work is all at one seam, and that is the point.** Daemon-supplied strings — display names, working directories, orchestration and role names, tool names and details — originate in agent processes, so they are attacker-influenced by prompt injection from any file an agent reads. The daemon-side scrub does not cover it: `src/daemon_client.rs:258-267` calls `strip_control_chars`, whose `char::is_control` test is general category `Cc`, while the bidi formatting codepoints are `Cf` — so a `U+202E` in a display name reaches the webview intact and visually reverses that name, swallowing the inline siblings printed after it, COORDINATOR badge included, on a screen whose entire purpose is telling one agent from another. (That daemon-side gap affects the TUI too and is filed separately.)

So `desktop/src/lib/displayText.ts` is a **display-only** sanitiser applied in `AgentOverview.tsx`, mirroring `src/untrusted_text.rs::strip_control_and_bidi` codepoint for codepoint: C0/C1 controls plus `U+202A`–`U+202E`, `U+2066`–`U+2069`, `U+200E`, `U+200F`, `U+061C`, enumerated rather than approximated. It is in TypeScript at the render seam rather than in the Rust DTO **because grouping, sorting and the composite `(daemonId, agentId)` key keep the raw values** — sanitising upstream would corrupt the keys and could merge two agents that differ only in a stripped character. Rendered text and `title` attributes go through it alike.

**Zero-width joiners are deliberately NOT stripped**, and the decision is recorded rather than defaulted. They cannot reorder or reverse text, so they do not produce the spoof the filter exists to stop; they are load-bearing in legitimate names (ZWJ builds emoji sequences, ZWNJ changes the word in Persian, Arabic and several Indic scripts); and widening past the Rust policy would make the TUI and the desktop disagree about the same daemon string, which is the divergence `untrusted_text.rs` was written to end. The residual — a name of entirely invisible characters rendering as a blank cell — is bounded by the length clamps and by the row still carrying status, CLI and tool columns. A test pins the decision so a later "tighten this" does not quietly break emoji.

**Every rendered string is bounded before React sees it**, because `DesktopAgentDto` is a TypeScript *assertion* about a shape the daemon supplies and not a validated one. Budgets, in characters: name 128 (the daemon's own `DISPLAY_NAME_MAX_LEN`, so any name it would accept passes through untouched), path 120, tool name 32, **tool detail 60**, `title` 512, connection message 240. The tool detail is short on purpose: for Bash/shell events it is the tool's first *command line* (`src/hook.rs:182-232`), which is both a disclosure risk in screenshots and unreadable at fifteen rows. It is **bounded, not redacted** — the audit's secret-scrubbing suggestion was declined, because a pattern heuristic buys false assurance where a length bound is honest. No virtualisation or row cap was added; that stays out of scope.

**Paths render home-relative and daemons get a short label.** A leading home directory becomes `~`, and the daemon group header shows the socket path's last segment instead of the whole path — both keep a username or uid out of a screenshot, and both keep the full value in the `title` and the raw value as the identity key. The webview has no `$HOME` (reading one would mean a `src-tauri` change), so the abbreviation matches the *shape* of a home directory — `/home/<user>`, `/Users/<user>`, `/root`, `C:\Users\<user>` — rather than the actual one. The crowded fixture's two hardcoded paths are now neutral (`/home/dev/...`): they stay home-*shaped* on purpose, so a fixture capture exercises the abbreviation in exactly the recordings where an absolute home path would be the thing worth hiding.

**The cwd column is now the differences column the Work Log already claimed it was.** See the correction in the entry above: the first implementation hoisted a value only when the *whole* group shared it, so the standalone bucket printed all three rows, two of them identical. It now hoists the **most common** value, and only when at least two members share it — so a group whose members all differ prints every row, and a group of one prints its own without the header repeating it. **This changes what the crowded fixture looks like**: the standalone card gains `~/code/dot-agent-deck` in its header, ids 13 and 14 go blank, and `pi-extension` becomes the only printed directory on the card.

**The screen is now a real table.** The column legend was `aria-hidden` and the rows were a CSS-grid `<ul>`/`<li>`, so no cell had a column header. Each group card is a `<table>` with `<th scope="col">` per column, the visible fleet-level legend stays decoration, and each table's own `<thead>` is present for a screen reader and hidden by `clip-path`. The layout is untouched because `display: grid` stays on the rows — which is precisely why the ARIA roles are **also** restated explicitly (`role="table"`/`"rowgroup"`/`"row"`/`"columnheader"`/`"cell"`): applying `display: grid` to table elements strips their implicit table semantics in browsers, so the honest markup alone would not have delivered the association it was chosen for.

Four smaller review findings: `writeLease` is now marked `FIXTURE-ONLY (until M8 surfaces live_target)` — it is a real data field hardcoded to `"unknown"`, and unmarked it read as honest, which is the failure the annotation scheme exists to prevent; the five deck-internal collections are annotated as a group and the "every field" claim above is scoped to data fields to match. `role` left `OverviewAgent`'s `Pick<>` — the row renders `displayName` and `tab.roleName`, so the honest projection is now exactly what the screen consumes. `groupAgents` no longer falls back to the orchestration *name* when `orchestrationId` is absent, which could merge two distinct orchestrations into one card with colliding role indexes; an id-less agent now gets a key unique to itself. And the `loading` connection state — a fifth real branch — has a test.

### 2026-08-31 — Three audit findings closed, all of them M7 blockers

An audit of the branch found three defects on the overview's render seam. None is reachable today, and that is the whole point: every one of them is live the moment M7 removes the fixture gate, so they are recorded here as **blockers for that milestone** rather than as tidy-ups. All three are fixed with tests, and each test was verified to fail with only its own fix reverted.

**Synthetic id-less orchestration keys shared a key space with explicit ids.** `orchestrationId` is optional on the wire, so an id-less orchestration agent was keyed `agent:<agentKey>` — a string built from a socket path and a daemon-minted agent id, both knowable — and a comment claimed that key was "unique to itself". It was not. A different orchestration reporting that exact string as its **explicit** `orchestrationId` landed in the same `Map` entry: one card, one title taken from whichever record arrived first, colliding role indexes, and fleet and group counts that misled. Kind-namespacing did not close it, because the collision happened in the map *before* `groupKey` was applied. The two cases now live in provably disjoint key spaces — an explicit key always begins `orchestration:` because `encodeURIComponent` cannot produce that separator, and an anonymous one always begins `orchestration-anonymous:`. **No name-only fallback was reintroduced**, deliberately: the daemon's pre-id orchestration identity is `(name, cwd)`, so keying on the name alone would merge two unrelated orchestrations — trading a rare collision for a routine one. `OverviewGroup.id` is now optional and **absent** for such a group rather than carrying an invented value, on the same reasoning that made `cwd` optional: a `data-group-id` a drill-in could navigate by must name something the daemon has heard of.

**Raw identity strings bypassed the sanitise-and-clamp seam.** `data-daemon-id` took the socket path verbatim, `data-group-id` took a mode or orchestration id verbatim, and `data-testid`, DOM `id` and `aria-labelledby` values were built from raw group, daemon and agent ids — which falsified two claims the PRD makes, that every daemon-supplied string on this screen goes through `displayText` and that every rendered string is bounded before React sees it. The concrete risk is availability rather than injection, since React's escaping holds: `DesktopAgentDto.id` carries no frontend validation and no clamp, is bounded only by the 16 MiB protocol frame, and `encodeURIComponent` expands it roughly threefold, so a malformed daemon could make React allocate and reconcile enormous keys and attributes on every snapshot and freeze the webview. The new `domIdentity` seam sanitises and bounds every identity copy that reaches React, keeping a digest of the original so two over-long ids sharing a prefix stay two DOM ids. The **raw** values still do the grouping and still form the `(daemonId, agentId)` identity — bounding happens only on the copy, so no clamp can merge two agents or two groups. The existing hostile-string and length tests could not catch any of this because they inspect only text and `title`; the new tests sweep `data-*`, `id`, `aria-labelledby` and generated test ids.

**A display name made entirely of invisible characters was still an identity-spoofing primitive.** A name or group title composed only of retained default-ignorable characters (`U+200B`, `U+200C`, `U+200D`, `U+FEFF`) rendered as a blank identity cell, and two names differing only by such a character rendered identically. The fix is a visible fallback instead: `displayIdentity` substitutes `unnamed agent <id>` or `unnamed <kind> <id>`, honest because it invents no name and identifying because the daemon's own agent id is what every other surface calls that agent by. Blankness is judged *before* the clamp, so a long invisible name is not rescued into "visible" by the elision marker the clamp appends, and the detection set is deliberately wider than the stripped set — safe precisely because nothing is removed from what renders. The test proving ZWJ emoji sequences survive is unchanged and still passes.

The changelog fragment and the In Scope bullet both still listed the buckets ending on standalone. ### 2026-08-31 — M7 demand-driven attach implemented, behind the still-standing gate

**Attach is now driven by what is on screen, not by what the daemon owns.** `TauriDeckBridge` gains `setShownTerminals(agentIds)` on the shared `DeckBridge` interface — real on the live bridge, a genuine no-op on `FixtureDeckBridge`, which owns no PTYs — and all three eager `attachAgents` call sites are gone: `connect()`, the `desktop://snapshot` listener, and `runAction`'s `start_daemon` branch. That third one was reachable without a snapshot event at all, so leaving it would have meant clicking *Start daemon* still attached the whole fleet by a route no test covered.

**The semantics, which were the real decision.** Shown terminals are always attached and are **never capped**; leaving one does not detach it but moves it into a bounded **warm** set, so bouncing between agents costs no scrollback replay; the warm set alone is bounded by the exported `MAX_WARM_TERMINALS` (**3**), least-recently-left evicted first; and when nothing is shown the warm set flushes to **zero** rather than down to the bound. The user decision that forced the shape is the deck: it mounts a terminal on every tile, so a bound applied over everything attached would have killed six of nine visible panes the moment a nine-agent fleet was displayed — the PRD forbids altering the deck, and a three-deep cap over `attached` would have altered it beyond recognition. Flushing to zero rather than to the bound is what makes the overview's "no terminals attached" true when you arrive from a nine-tile deck, instead of true only on a cold start.

**Eviction is a full client-side teardown, and it cancels attaches still in flight.** Every map keyed by agent id is cleared — `sessions`, `attached`, `terminalChannels`, `pendingAttachments`, `pendingResizes`, a cancelled `resizeFrames` entry, `resizeInFlight` — before the daemon `desktop_terminal_detach` is invoked. Dropping `pendingAttachments` and `terminalChannels` *is* the cancellation of a pending attach: the post-await guard inside `attachAgents` then fails and takes the orphan-detach branch that was already written, so a late-arriving session is detached rather than installed behind a screen that no longer shows it. Cancellation is marking, never awaiting — a flush must not serialise behind one slow attach, or a single hung socket would freeze every later terminal switch. Warm membership is by agent id and does not require the attach to have landed, because a pending agent that is not a warm member is never selected by the LRU pass and installs itself afterwards past the bound. Eviction is deliberately **per agent** and never a `lifecycle` bump: `lifecycle` is a whole-bridge generation, and bumping it for a warm flush would also void every *shown* attach still in flight and permanently leak `resizeInFlight` for any agent mid-resize, since `flushResize`'s cleanup runs only while the lifecycle is unchanged.

**Both surfaces are wired, and the wiring is tested, because deleting the eager attach without it is a total regression that no bridge test can see.** `ControlDeck` derives the shown set from the tiles actually rendering a terminal (`tabs[agent.id] ?? "terminal"`, the same fallback `AgentTile` uses) and declares it in **one** call per render commit through an effect keyed on the joined id list — not once per tile, which would have left eight of nine warm and evicted five. `AgentOverview` declares `[]`, which is the screen's whole claim stated to the bridge rather than only printed in its header. Four new component tests pin exactly that: all four terminal-tab ids in a single call, an empty deck declaring `[]`, switching one tile to its Diff tab removing exactly that id, and the overview declaring `[]`. Each was verified to fail with only its own effect removed.

**The fixture gate is deliberately still in place.** `showOverview()` is untouched, so the overview remains fixture-only and **M7 is not ticked**. Lifting it is M7's final step and belongs in a separate commit after this change has been reviewed and audited: the gate is the safety net for precisely the defect this commit changes, and removing it in the same commit would mean no independent verification ever happened while the net was up.

**One consequence worth recording rather than discovering later.** With the snapshot listener no longer attaching, nothing re-attaches a *shown* terminal whose session the daemon ends (`handleTerminalState` drops it on an `end`/`error` state event) until the shown set is declared again. `setShownTerminals` re-declares the whole set and `attachAgents` filters on `attached`, so any repeat call repairs it — but the deck's effect only fires when the derived set changes, so today the repair needs a tab toggle or a navigation. The eager snapshot path used to heal this by accident. A narrowed re-attach of the shown set on each snapshot event would close it without reintroducing eager attach; it was left out of this commit on purpose, since the milestone's own instruction is that all three call sites go.

Coverage: 25 tests in `desktop/src/lib/bridge.test.ts` (13 new for this seam) and 4 new component tests, taking the desktop suite from 129 to 133. Four pre-existing bridge tests were updated, not weakened — each used `connect()` as a convenient way to get a session and now asks for one; the sanitized attach-failure notice and the generation-guard coverage they carry are unchanged. No Rust was touched, no protocol shape moved, and rule 12 has nothing to answer here: this is TypeScript inside the desktop client only.

### 2026-08-31 — The review and audit findings on demand-driven attach, closed

**A snapshot now re-declares the shown set, which is what heals a shown terminal whose session the daemon ended.** The previous entry recorded that gap as a known consequence; it is closed here by one line in the `desktop://snapshot` listener, `void this.attachAgents(Array.from(this.shown))`. The invariant re-asserted is deliberately narrow: **everything shown is attached**, never "everything attached is alive". A *warm* terminal — left behind, still attached — whose session dies stays dead until it is shown again, because nobody is looking at it and healing it off screen would spend a daemon socket and a full scrollback replay on a pane no one can see. `Array.from(this.shown)`, never the snapshot's own agents, is what keeps that true, and the comment that used to say "attach is driven by `setShownTerminals` alone" was reworded rather than left standing as the argument a future reader would cite for deleting the line again.

**The tester's direction guard did not actually guard the direction, and now does.** The handoff said `re-declares only the shown set on a snapshot event, never the fleet` would fail if the fix were written as `attachAgents(dto.agents.map(a => a.id))`. Measured: it does not — `attachAgents` filters on `shown.has || warm.has`, so passing the whole fleet is filtered back down to the shown set and the test stays green either way. The one case the two variants genuinely differ on is a **warm agent whose session ended**: it is still in `warm`, so the fleet variant re-attaches it and the shown-set variant does not. A new test pins exactly that, and it is the one that fails under the fleet variant — the guard is real now rather than assumed.

**A newline in a daemon-supplied agent id fanned out into several attaches, and bypassed `validate_agent_id` doing it.** `ControlDeck` joined the shown ids with `"\n"` for its effect dependency and then rebuilt the array with `.split("\n")`. Agent ids are raw daemon identities, not display strings, so one agent whose id contained a newline produced `setShownTerminals(["agent-a", "agent-b"])` — two attach paths from one tile. The security half is worse than the identity half: handed the id whole, `desktop_terminal_attach` reaches `validate_agent_id`, which rejects every control character; splitting first converts one *invalid* identity into several *valid* ones, and a malformed daemon can pack as many as a 16 MiB protocol frame holds, each allocating a channel, pending state, a promise and a Tauri invocation before the backend can reject it. The joined string is now a dependency **key only** — the array that reaches `setShownTerminals` is the one derived from `snapshot.agents`, held in a ref because the effect must key on the string while carrying the ids themselves. A component test pins that an id containing a newline arrives as one element.

**One outstanding attach invocation per agent, with the suppressed declaration coalesced rather than dropped.** Eviction deletes `attached` and `pendingAttachments` — that marking *is* how an in-flight attach is cancelled — so re-showing an agent used to start a fresh Tauri command while the previous one was still alive. The Rust side serialises every agent through one unbounded attach gate with no timeout and no cancellation, so against a stalled daemon each hide/reshow cycle added another channel, closure, promise and queued command, to be executed as an attach/detach storm if the daemon ever recovered. A new `attachInvocations` set, added before the invoke and removed in a `finally`, is the guard; it is deliberately not `pendingAttachments`, since a guard eviction clears re-arms every cycle and guards nothing, and it is the one agent-keyed set `evictTerminal` deliberately leaves alone.

**The guard needed a second small set, and that is a deviation from the audit's suggested shape worth stating.** Suppressing alone would have introduced the very defect the first fix above removes: hide and re-show faster than one attach round trip, and the cancelled command detaches its late session while the suppressed re-show never happens, leaving a dead pane with nothing to heal it until the next snapshot — and snapshots are event-driven, not periodic, so on an idle fleet that is not soon. So a suppressed declaration is recorded in `attachRequested` (a set, so at most one per agent however many cycles occur) and replayed **once** when the outstanding invocation settles, while the agent is still wanted and still unattached. A failed attach queues no request of its own, so this cannot become a retry loop. It stays a guard beside the state machine — a skip in the existing filter and a replay in the existing `try`'s `finally` — and touches none of the installed-session, channel-identity or generation machinery.

**`evictTerminal` now clears `pendingTerminal`, so its own doc comment is true.** The class has ten agent-keyed collections and eviction cleared nine; both the review and the audit found the same omission independently. Chunks buffered while no terminal listener is installed belonged to the session being torn down, so a surviving entry replayed a dead pane's scrollback ahead of the live one at the next `subscribe` drain. `agentIndex` is snapshot metadata rather than terminal ownership and is left alone, and `attachInvocations` is exempt for the reason above — both are now stated in the comment rather than implied.

**Known residual, recorded rather than fixed: client-side cancellation is marking only.** If `desktop_terminal_attach` has not returned when a flush evicts it, the frontend tokens are deleted but the backend command and its daemon `AttachStream` socket are not cancelled, so a daemon that accepts the stream and never completes holds the socket and the backend attach gate while the overview claims to hold nothing. Detach has a matching version: the Rust command waits for the per-session writer lock, which a blocked write can hold, and `.catch(() => undefined)` handles a rejection but not a promise that never settles. Fixing it is Rust work in `desktop/src-tauri/` and M7 is deliberately TypeScript-only, so it is left for a follow-up.

**The overview's copy was adjusted to claim exactly what is true under that residual.** The success criterion "rendering the overview attaches **zero** PTYs" is precise about what the screen *initiates* — zero, and that is what the bridge tests prove — but it cannot promise that a socket a previous screen began is already torn down at the moment the copy renders. The footnote said *"This screen reads one snapshot and attaches nothing"* and the header said *"no terminals attached"*; they now say the screen opens no terminal of its own and asks the bridge to release what the deck left attached, with the tear-down landing as that release completes. This branch's whole discipline is not overclaiming, and the UI copy is not the place to let it slip.

### 2026-09-01 — M9 complete: the daemon reports when it last saw each agent, and the honesty check that decided the shape

**The check came first, and it is the reason this milestone happened at all.** The PRD rejected session duration because `SessionState.started_at` is invented as `now` on hydration, so a duration resets under a restarted daemon and silently lies about long-running work. The obvious worry was that `last_activity` shares that defect — in which case rendering it would contradict the honesty principle in the same paragraph that cites it. It does not, and the reasons are worth recording, because two of the three are structural rather than incidental.

**`last_activity` is a high-water mark of observed event timestamps, never re-minted.** `apply_event` creates a session with `last_activity: event.timestamp` (`src/state.rs:7178`) and thereafter advances it only when a newer frame arrives (`src/state.rs:7221-7222`), guarded that way deliberately since PRD #284 sub-problem (b) so a delayed frame cannot move it backward. An agent quiet for an hour therefore snapshots as quiet for an hour. Compare `started_at` in the same struct: `insert_placeholder_session` falls back to `Utc::now()` when `pane_started_at` has no entry for the pane (`src/state.rs:5728-5729`), which is exactly the reset the PRD refused.

**The daemon-restart case resolves to ABSENCE rather than to a lie, and it does so for free.** The daemon persists no `AppState` — every construction site is `AppState::default()` — and its agents are its own children, so a restarted daemon has no sessions at all. `AgentRecord.live` is then `None`, `last_activity_ms` never reaches the wire, and every consumer renders nothing. That is the disposition the PRD asks for, reached by construction rather than by a guard someone has to remember. It is also the difference that made a column shippable here where duration was not: duration had no absent state to fall back to, because `started_at` is always populated with *something*.

**The one `now`-based path daemon-side is truthful where it is reached.** `insert_placeholder_session` does set `last_activity: now`, and `apply_event`'s `SessionEnd` restoration calls it (`src/state.rs:7043`) — but that call happens at the moment the session ended, so "last activity was now" is true. Its other callers are all in `src/ui.rs`, i.e. the TUI's own `AppState`, not the daemon's.

**One consequence deliberately left alone.** The TUI's reconnect hydration does not overlay `last_activity` from the snapshot, so a reconnected TUI card's `Last:` readout (`src/ui.rs:19282`) resets — a pre-existing inaccuracy that M9 has now made *fixable*, since the value finally crosses the wire, but has not fixed. Overlaying it is a one-line change in `seed_hydrated_session` and a bad one to make here: `last_activity` is the ordering evidence `supersedes_generation` weighs and the key `pane_writable` and the `ListAgents` newest-wins join select on, so seeding it to an older value could change which session wins a tie or whether a later event supersedes. That is daemon-adjacent behaviour, not a rendering change, and it belongs in its own change with its own tests.

**Wire representation: epoch milliseconds (`Option<i64>`), and the field carries its unit in its name.** Four reasons, in the order they mattered. A single integer has no format for two peers to disagree about — no offset suffix, no fractional precision to negotiate, no locale, and no `Date.parse` in the client's path, whose behaviour for non-ISO input is implementation-defined. Chrono's own `Serialize` for `DateTime<Utc>` emits RFC 3339 at *nanosecond* precision, which every JavaScript consumer silently truncates, so the wire would carry precision no consumer can represent. It is the same unit `Date.now()` produces, so the skew comparison is unit-for-unit. And a pre-formatted `"3m ago"` would bake the client's rounding, vocabulary and notion of "now" into the daemon's contract — the whole point of keeping the relative wording in the webview. The name is `last_activity_ms` rather than `last_activity` for the ordinary reason: a bare integer invites a seconds-versus-milliseconds mistake, and that particular mistake divides by a thousand and turns every relative time on the overview into fifty-seven years.

**`PROTOCOL_VERSION` stays 8, and the claim behind that is proven rather than asserted.** The field is tagged `#[serde(default, skip_serializing_if = "Option::is_none")]`, which the module's own policy names as an explicit do-not-bump case (`src/daemon_protocol.rs:11-14`), on the same basis `AgentRecord.live` was added. Nothing renames, retypes or re-means an existing field, so there is no semantic break behind a stable wire and no `.breaking.md`. `session/live/013` decodes an older peer's snapshot payload with no key (arrives as `None`, every other field intact) *and* a newer peer's payload carrying one (decodes without disturbing what an older reader understands). Worth noting for anyone reverting this to check the attributes are load-bearing: `#[serde(default)]` is belt-and-braces for an `Option<T>`, which serde already defaults to `None` when the field is missing — removing it alone changes nothing, while removing `skip_serializing_if` does, and fails the test.

**Clock skew: ordinary skew reads `just now`, and anything beyond it renders nothing.** The two clocks are genuinely two clocks — the instant is stamped by whichever hook process emitted the event (`src/hook.rs`), not by the daemon and certainly not by the webview — so a small positive skew is the ordinary case rather than a fault, and `displayActivity` absorbs one minute of it. Beyond that the value is not rewritten into `just now`, and that is the deliberate half: `last_activity` is producer-supplied and unclamped daemon-side on purpose, and the daemon has a test for a report stamped ten years out (`a_disowned_generations_far_future_session_cannot_pin_its_pane`), so calling such a value "just now" would be the same class of fabrication as the duration this PRD rejected — a negative `-60m ago` is merely the more obvious bug of the two. The same seam also declines a non-finite number and an instant outside `Date`'s ±100,000,000-day range, where an `i64` reaches nine orders of magnitude further than a `Date` does and `toISOString()` throws. Every refusal renders as blank, with no hover, exactly like absence. Note the desktop is *stricter* than the TUI here, which clamps unconditionally to `0s` (`format_elapsed`, `src/ui.rs:19449-19452`); the divergence is intentional and one-directional — the TUI never renders a negative either.

**The overview is now a nine-column grid, and Last activity is the fourth.** It sits beside State rather than at the end because "waiting" and "waiting, and quiet for two hours" are different situations and a reader should not have to scan across the row to tell them apart. ### 2026-09-01 — #801's root cause: compatibility is classified from the release version, not the git stamp

**The earlier #801 entry fixed the response to a refusal; this fixes the refusal.** That entry added a confirmation-gated **Connect anyway** because a user with live agents had no path forward. It was right and it stays. But it treated the symptom: `classify_handshake` compared two `git describe` stamps with `!=`, so it could not tell *"a compatibility break was declared between these builds"* from *"you rebuilt since lunch"*, and it prompted identically for both. The everyday case — a branch desktop at `0.39.0-ga0165f8` against a `v0.39.0` daemon at `0.39.0-g1ea0fe7`, protocol 8 on both sides, no `.breaking.md` anywhere between them — was a prompt this project's own policy says should never have appeared.

**The policy the classifier now encodes** is `docs/develop/versioning.md`'s bump table. While the major version is `0` the rules are shifted down one level from standard SemVer so the **minor** digit tracks compatibility: a protocol/handler break bumps the minor, a feature or a bugfix bumps the patch. From `1.0` onward the rules are standard and only the **major** moves on a break. So the compatibility key is `0.MINOR` while the major is `0`, and the major alone afterwards — and `compatibility_key` encodes both arms rather than hardcoding `major.minor`, which would silently start refusing compatible peers the day this repo ships `1.0`. `the_compatibility_key_tracks_the_minor_while_zerover_and_the_major_after` pins both arms at the key; `from_one_zero_onward_only_a_differing_major_refuses` pins the `1.x` arm end to end at the handshake.

**Three outcomes, in strict order.** Protocol differs → `Incompatible`, hard refusal, no override advertised, entirely unchanged. Protocol matches and the compatibility keys match → **Connected, silently**: no banner, no prompt, no Connect anyway. Protocol matches and the keys differ → the previous behaviour, `Incompatible` with the stamp message and a confirmation-gated Connect anyway, because a real break was declared between those releases.

**Parsing, and which way it fails.** `release_core` takes the leading `MAJOR.MINOR.PATCH` off a stamp and discards everything from the first `-` or `+`, which covers every form `build.rs` emits: the release `0.39.0-g1ea0fe7`, the dev `0.39.0-49-ga0165f8`, a `-dirty` suffix, and a version carrying its own SemVer prerelease (`0.25.0-alpha.0-g1ea0fe7`). **An unparseable or absent stamp on either side falls back to the prompt, never to the silent connect.** Silent connection is the permissive answer, so it is reached only on positive evidence that both keys parsed and matched; `release_versions_are_compatible` returns `false` for every other input, including a daemon that reported no stamp at all. `an_unreadable_stamp_on_either_side_falls_back_to_the_prompt` pins that direction over six inputs, and inverting the fallback to `true` reddens it plus six pre-existing tests.

**The residual, stated rather than hidden.** A development branch's `git describe` names the LAST release, so a branch carrying an *unreleased* semantic break describes as the release it was cut from and reads as compatible with it. Nothing in a build stamp can see that — the whole premise of the `.breaking.md` discipline is that a same-wire, different-meaning change is not mechanically detectable. It is backstopped by rule 12's cross-version manual test, run against the previous release before such a change merges, and by the fragment that test's outcome demands, which is what turns the break into a minor bump this classifier can then see. The doc comment on `release_versions_are_compatible` says exactly this in the code. Issue #801's proposed direction — per-capability `Hello` fields on the `guarded_send` precedent, and continuing the `#[serde(other)]` retrofit so daemon→client pushes degrade instead of killing the frame — is what would actually close it, and is untouched here.

**The protocol refusal is untouched, and the tests spend their weight proving it.** `protocol_mismatch_never_advertises_an_override` and `bypass_never_rescues_a_protocol_mismatch` pass unedited. Because both use an unparseable stamp, though, neither reaches the new code path at all — so `protocol_mismatch_still_refuses_a_release_compatible_pair` was added to pin the property at the new boundary: a pair the release check *would* wave through is still refused, with no override advertised, for all three allowance values.

**The trace for the silent case is a hover, not an alert.** A banner would recreate exactly the noise this removes, so the overview's daemon-card state line gains a `title` naming both builds when they differ, and nothing else changes; `clientBuildVersion` and `daemonBuildVersion` now ride the `ConnectionView` to carry it. The deck banner and Connect anyway needed no change — both already key on `status` and `buildStampMismatchOnly`, so a silent connect renders neither. The two new TypeScript tests for that pin existing production logic against regression rather than describing new behaviour, which is the honest way to read them.

**Rule 12: nothing to answer.** This is client-side classification inside the desktop crate. No wire shape moved and no field changed meaning; `src/` is untouched, no daemon or protocol code was edited, and `PROTOCOL_VERSION` is read rather than changed. No bump and no `.breaking.md`. The change makes the desktop *more* tolerant of a peer, and the tolerance is bounded by the release version that peer itself reports.

**The restart semantics were verified before anything was built, because the feature is worthless if they do not come out as the user asked.** The ask was: a restarted orchestration worker shows its latest iteration; an orchestrator that was never restarted shows its overall lifetime. **A restarted worker gets a NEW record, so it gets a new spawn instant.** `respawn_agent_for_pane_declared` (`src/agent_pty.rs:6038`) lifts the existing entry out of the registry with `inner.agents.remove(&agent_id)`, destructures it, terminates the child, and calls `spawn_agent` for a fresh one — the identity-preserving fields (`pane_id_env`, `display_name`, `cwd`, `tab_membership`, the two agent-type fields, the env and the PTY dims) are carried across by hand, and `spawned_at` is deliberately not among them. `respawn_or_recreate_agent_for_pane`'s issue-#606 recovery leg reaches `spawn_agent` too. So the `clear = true` delegate path — the one that restarts a worker — mints a new instant by construction, and a role nobody restarts keeps its original record for as long as it lives. **No "which duration is this?" flag is needed, because the two answers come from two different records.** The feature delivers exactly what was asked.

**No record outlives the process it describes on this path.** `agent_records()` — the source for `ListAgents`, and therefore for the desktop — filters entries whose `exited` flag is set (`src/agent_pty.rs:6976`), so a dead-but-unreaped child never reaches the wire and a spawn instant cannot tick up as a phantom uptime. `agent_record_any()` deliberately does *not* filter, but it is the cleanup path (`StopAgent` reading a stopping agent's `pane_id_env`) and nothing renders from it.

**Nothing is ever adopted.** `inner.agents` has exactly two insert sites: `spawn_agent`, and the `#[cfg(test)]` `insert_test_agent` seam. The daemon persists no registry, and its agents are its own children, so there is no path by which it comes to hold an agent it did not fork. The one production path that produces an `AgentRecord` with no spawn behind it is `daemon_client::list_agents`'s legacy branch, which synthesises records from an older daemon's id-only reply — and that reports `None`, which renders as nothing.

**Why spawn time beats `SessionState.started_at`, and why this PRD's original rejection of a duration column was overstated.** The Out of Scope bullet said `started_at` "is invented as `now` on hydration, so any duration resets when the daemon restarts under a live agent". Both halves are weaker than they read. `pane_started_at` (`src/state.rs:7025`, recovered at `:7178`) already preserves a pane's start across session churn, so a restarted *worker* does not reset through that path; and on a daemon restart there are no sessions at all, so the value resolves to **absence** rather than to a lie — the same disposition M9 relied on. The bullet is corrected in place rather than deleted, because the conclusion it reached was right for a reason it did not state: `started_at` is **event-derived**. A session exists only once a hook event has arrived, so an agent that has never emitted one has no start instant at all — and that is precisely the agent whose uptime a reader most wants. A spawn is something the daemon **did**: signal-independent, an observation rather than an inference, and definitionally known. That is the difference that made this shippable, not the reset.

**Where it is recorded, and every path where it is absent.** `AgentPtyRegistry::spawn_agent` stamps `chrono::Utc::now()` immediately after `spawn(opts)?` returns — the first moment the child exists, and before the lock acquisition that follows, which can block behind any other registry operation — and stores it on `RunningAgent.spawned_at`. That is the **only** site that writes a `Some`. It is `Option<DateTime<Utc>>` in memory rather than a bare `DateTime` precisely so absence is representable at the source instead of being manufactured at the edge: `insert_test_agent` registers a child the *caller* forked and honestly reports `None`. On the wire it is absent from a legacy id-only `ListAgents` reply, from any peer predating the field, and from the hand-built `AgentRecord` fixtures in the test suites. Every consumer renders nothing for absence — no dash, no placeholder — and there is **no `Utc::now()` fallback anywhere on the path**, which is the exact failure the original rejection was about.

**`DateTime<Utc>` in memory, epoch milliseconds on the wire, and the unit in the name.** `Instant` is monotonic and meaningless in another process, so it cannot cross a wire at all. The four reasons M9 recorded for milliseconds hold here unchanged: an integer has no format for two peers to disagree about, it is the unit `Date.now()` speaks so the client's whole computation is one subtraction, chrono's own `Serialize` for `DateTime<Utc>` emits RFC 3339 at nanosecond precision that every JavaScript consumer silently truncates, and a pre-formatted `"3h"` would bake the client's rounding and vocabulary into the daemon's contract. The field is `spawned_at_ms` rather than `spawned_at` for M9's reason: a bare integer invites a seconds-versus-milliseconds mistake, and that mistake divides by a thousand.

**`PROTOCOL_VERSION` stays 8, proven rather than asserted.** The field is tagged `#[serde(default, skip_serializing_if = "Option::is_none")]` on `AgentRecord`, which the module's own policy names as an explicit do-not-bump case (`src/daemon_protocol.rs:11-14`) — the same basis `AgentRecord.live` and `SessionSnapshot.last_activity_ms` were added on. Nothing renames, retypes or re-means an existing field, so there is no semantic break behind a stable wire and no `.breaking.md`. `session/live/014` decodes an older peer's `AgentRecord` with no key (arrives as `None`, `id`/`pane_id_env`/`display_name` intact) *and* a newer peer's payload carrying one (decodes without disturbing what an older reader understands). It also pins the honesty property twice over: the instant lies inside the spawn call, bracketed by `Utc::now()` either side, **and** it does not move when the same record is read again five milliseconds later — which is what settles it on a machine fast enough for the bracket to hold to the millisecond anyway.

**Clock skew: `displayActivity`'s policy is SHARED, and only the vocabulary is forked.** The three refusals were factored into one `relativeTo` guard that both functions call — the daemon reported nothing; the value is not a finite number; the instant is more than `CLOCK_SKEW_TOLERANCE_MS` ahead of the webview — plus the out-of-`Date`-range check, since an `i64` reaches nine orders of magnitude further than a `Date` does and `toISOString()` throws for one that does. Every refusal renders blank with no hover, indistinguishable from absence. Sharing it was the right call rather than a convenience: the three refusals **are** the policy, and a second copy is a second thing to keep true. What is deliberately *not* shared is the wording. `displayActivity` says `3m ago` because it names a moment in the past; `displayUptime` says `3m` because it names a span still running, and `3m ago` would be a different and wrong claim about the same number. Sub-minute reads `<1m` rather than `just now` for the same reason — "just now" answers *when*, not *how long* — and a tolerated negative elapsed lands in that bucket, so ordinary skew never shows as a negative count. One tolerance covers both instants deliberately: a spawn stamp is set by the daemon itself rather than by a hook process, so it is skewed by one clock rather than two — a strictly narrower gap inside the same band, not a reason for a second policy. Both boundary cases are pinned on `displayUptime` as well as on `displayActivity`, so a future edit that forks the guard fails rather than quietly leaving the two columns disagreeing about the same skew.

**The overview is now a TEN-column grid, and Uptime is the fifth.** It sits immediately after Last activity because the two answer one question between them — how long this agent has been alive, and how much of that it has spent doing nothing — and reading them apart is the point of putting them together. ### 2026-09-02 — M12 complete: the time columns were frozen, and the columns become the operator's choice

Two commits, deliberately separate — the first is a bug fix that should stay revertable without losing the feature.

**The time columns were FROZEN, and the bug failed exactly backwards.** `AgentOverview` read `Date.now()` once per render; snapshots are event-driven off the daemon watch stream and nothing polls anywhere. So an agent emitting nothing produced no re-render at all: `Last activity` said `3m ago` indefinitely while the truth became `30m ago`, and `Uptime` — a duration, and so inherently continuous — stopped counting. Any OTHER agent's event repaints the whole screen, so a busy fleet masked it entirely and the idle case, where "quiet for two hours" is the most valuable thing on the screen, is precisely where it stopped updating. M9 and M11 both shipped without it because every test injects its own `now` and every manual look at the screen was at a busy fleet.

**`useOverviewClock`, at ten seconds, and the number follows from what the columns print.** Both `displayActivity` and `displayUptime` render one unit, largest that fits, floored — so above a minute the smallest change either cell can make is a whole minute, and below it the label is a fixed `just now` / `<1m`. The only crossing a faster tick could sharpen is the one INTO the first minute bucket, and 10s bounds the lag on it to a tenth of the unit being crossed for six repaints a minute of a screen that mounts no terminal; a one-second tick would be sixty repaints a minute to change a label on one of them. It is a re-render and **nothing else** — no snapshot request, no reconnect, no daemon call — because the screen's design property is one RPC plus one already-open event stream (M7), and a polling loop here would quietly reinstate the per-agent cost that milestone removed. The instant is hoisted to the screen and passed down, so every cell on a repaint is relative to the same moment rather than to fifteen slightly different ones, which is what the row's comment had claimed while each row read its own clock.

**Paused while the document is hidden, and it catches up on the way back.** A backgrounded window repainting six times a minute forever is waste the browser throttles anyway; the cost of pausing is that the cells are stale by however long the window was away, so `visibilitychange` re-reads the clock IMMEDIATELY and only then restarts the interval. Waiting out an interval before correcting would show a knowably wrong time at the one moment the user is looking straight at it.

**The defaults, and the status/State reconciliation the user's wording forced.** Defaults are **name, status, working directory, uptime** — who it is, whether it is healthy, where it is working, how long it has been at it. The screen carried *both* a coloured status mark in the first track and a textual **State** column in the third, both rendered from `agent.status` and neither saying anything the other did not; the user asked for one "status". They are now **one column** whose cell holds both: the colour is still what you scan, the word is still what you read, and removing the column removes both. Two picker entries for one field would have been a question with no right answer, and keeping the mark permanent while the word was optional would have made "only the name is permanent" false. Nothing is lost — `data-status` on the `<tr>` is what tints a failed row, and it is not a column.

**The picker cannot offer a column the daemon cannot fill, and that is a compile error rather than a review note.** `COLUMN_FIELDS` is declared `as const satisfies readonly (keyof OverviewAgent)[]`, so its ids ARE field names of the `Pick<>` projection this screen has rendered from since M4 — `model`, `cost`, `tokens`, `contextPercent`, `worktree`, `attempt` and `duration` do not typecheck as entries. The picker derives its options from that list, so it inherits the honesty guarantee instead of restating it. The name column is permanent twice over: its checkbox is checked and disabled, and `orderedColumns` puts it back whatever a stored value says — a disabled checkbox governs the UI, not a `localStorage` key an older build wrote.

**Persistence, and the three ways a stored value goes wrong.** `dot-agent-deck.desktop.overview-columns.v1.<mode>` via `modeScopedKey`, for the reason every persisted key here is scoped that way (PR #416 review M1): a fixture visit must not hand live mode a layout. `readStoredColumns` takes the defaults for anything absent, unparseable or the wrong shape — a `SyntaxError` on mount would take the whole screen down; **drops** a stored id that is no longer a column, rather than carrying it through as a `<th>` with no cell under it and one dead grid track down every card; and takes the defaults again when nothing recognisable is left, since an empty result is indistinguishable from garbage and a user cannot reach it by unticking. Whatever survives is written straight back, so the next visit reads a value this build understands. Every one of these is about a value an OLDER BUILD wrote — the class of fault that breaks silently a release later rather than loudly today.

**The grid rework, and the one constraint that would have looked like a rendering bug.** `grid-template-columns` is generated from the selection and published ONCE as `--overview-grid` on a single `.overview-table-region` that wraps the legend and every group card. All the cards share that template — that is what makes the fleet read as one table across card boundaries — so the horizontal scroll has to be on the whole region and never per card: two cards at different scroll offsets desynchronise visibly, and only once the chosen set is wide enough to overflow, which is exactly when a reader is depending on the alignment. `min-width: min-content` on the track is what produces a scrollbar at all, and it works only because every flexible track carries a fixed px minimum (`minmax(150px, 1.3fr)`, never `minmax(0, …)`): the grid's min-content width is then the sum of those minimums — a fixed, content-independent number — rather than zero (tracks crushed to nothing, no overflow) or the width of the longest prompt on screen (which one 64 KiB prompt would blow past anything usable).

Once the operator picks the columns, hiding one by window width fights them silently, with nothing on screen saying so. The 1180px query held nothing else and is deleted; the 680px one keeps its padding and the decorative status pips. ### 2026-09-02 — The cross-version manual test is RUN, it passed, and it found a hole in rule 12's own procedure

**The pairing was real on both sides.** Branch head `630b0ab` against tag **v0.39.0** (`1ea0fe7`) — two builds of two different commits, v0.39.0 built in a throwaway worktree at the disk-backed sibling `../dot-agent-deck-xver` per rule 14, and **no `DOT_AGENT_DECK_BUILD_ID_OVERRIDE` anywhere**, so the mismatch the handshake saw was a genuine one rather than a simulated one. The sandbox carried all five rule-12 variables plus a superset (`DOT_AGENT_DECK_LOCK_DIR`, `DOT_AGENT_DECK_SESSION`, the four `XDG_*`, a pinned `PATH`), every process launched under `env -i`. Isolation was confirmed rather than assumed: the daemon's own first log line read `experimental flag: OFF (from <sandbox>/.dot-agent-deck.toml)` — the sandbox's config, not the operator's real `~/.dot-agent-deck.toml`, which does exist on that box — and the operator's real `~/.local/state/dot-agent-deck/deck.log` was never appended to.

**All three tells hold.** Exactly **one** `Attach protocol listening` line for the whole run. One daemon pid (**3622595**) and one daemon build id end to end — three `Hello`s in the log whose *client* side reads `0.39.0-g1ea0fe7` → `0.39.0-g630b0ab` → `0.39.0-g1ea0fe7`, while the *daemon* side never moves off `0.39.0-g1ea0fe7`. And **`server_version: 8`** read off the **live** daemon's wire, via a read-only raw `Hello` frame written straight to the attach socket, rather than inferred from the two binaries' compiled-in values. Both trees carry `PROTOCOL_VERSION = 8`, so this exercised **semantics behind a stable wire** — the case rule 12 exists for — and not a handshake rejection.

**What passed.** The branch TUI showed the build-mismatch prompt and **named the live agents** (`orchestrator`, `coder`); declining it attached to the v0.39.0 daemon with the full live state restored, including the status the coder pane had been given under the *old* TUI and the orchestrator pane's whole scrollback. Then the three flows rule 12 asks for: a **delegate routed** (daemon log `Received delegate signal`, the task file rewritten, and the pointer line rendered **in the worker pane's PTY**), **`work-done` round-tripped** back into the orchestrator pane, and a **status hook** repainted card 1 from `● No agent` to `● Needs Input`. Two checks beyond the required three also passed: a **pane spawn** driven from the branch TUI landed on the old daemon — a wire *write* path — and **read-path parity** held, with `daemon status` run from the branch binary and from the v0.39.0 binary against the same live daemon returning byte-identical tables. Both the TUI and the CLI on the client side were the branch build, so this was new-client → old-daemon on the attach socket **and** the hook socket. Same-version controls ran at **both** ends, the second of them on the same never-restarted daemon after the branch TUI had detached. **Nothing behaved differently from same-version.**

**Two limits, and they are named rather than glossed.** First, the roles were **stand-ins, not real agents**: every one ran `bash --norc --noprofile -i`, with the `delegate` / `work-done` / `agent-event` calls typed into the panes by hand. That genuinely proves delegate routing, hook delivery and card repaint survive the pairing; it does **not** prove a real agent does, and rule 4 records that this project has historically over-relied on stand-ins. Second, **the desktop half was not run** — Connect anyway → Overview → confirm `Uptime` and `Last activity` are **blank** against a previous-release daemon, where a value appearing would prove the client-side invention M9 and M11 exist to forbid. No harness drives a real Tauri window (issue [#836](https://github.com/vfarcic/dot-agent-deck/issues/836)), so that observation stays with the user. The claim this run supports, at exactly its evidenced width: **the TUI↔daemon contract is intact for these two additive fields, verified with stand-in agents; the desktop leg and the real-agent leg are not covered.**

**The run found a second cause of rule 12's own false pass, and CLAUDE.md now carries it.** The first attempt was invalid and was discarded rather than reported: roughly 30 seconds passed between `daemon serve` and the first attach, the daemon hit its default idle window (`Daemon idle window elapsed (no clients, no agents, no pending schedules)`), exited, and the TUI lazy-spawned a replacement — **two** `Attach protocol listening` lines and, silently, a same-version test. That is the *same* false pass rule 12 already warned about arriving by a **different cause**: the rule's warning is about starting with no agents, and this one fires even on a correctly sequenced run whenever setup takes longer than 30 seconds. Rule 12's trap paragraph now names both causes, gives `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` as the remedy — a documented production knob (`0` = the "always on" / legacy remote behavior, `src/daemon.rs`), not a test hook, read in exactly one place under `src/` and feeding only the idle timer, so it moves no protocol path — and states that the `Attach protocol listening` count is the tell for **both**. It also carries one ordering note from the run: **do the status-hook check last**, because an `agent-event --type running` sent before the delegate check makes the daemon classify that pane's agent type as `Pi`, which routes prompt delivery differently and makes a delivered delegate briefly look undelivered.
