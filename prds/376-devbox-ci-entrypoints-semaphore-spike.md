# PRD #376: Devbox-native CI entrypoints and a Semaphore pipeline spike

**Status**: In progress
**Priority**: Medium
**Created**: 2026-08-04

## Problem Statement

Two problems, one of which is a live bug.

**The toolchain is pinned locally and floating in CI.** `devbox.json` pins `rustc@1.97.1`, `cargo@1.97.1`, `clippy@1.97.1`, `rustfmt@1.97.1` and `cargo-nextest@0.9.140`. `.github/workflows/ci.yml:109` uses `dtolnay/rust-toolchain@stable` and `:113` installs nextest via `taiki-e/install-action@nextest` — both resolve to whatever is current on the day the job runs. So the local gate (`cargo test-fast`, aliased in `.cargo/config.toml`) and CI compile with different toolchains, and the divergence widens silently until a new release introduces a lint or a behaviour change. The first symptom will be a clippy failure that cannot be reproduced locally.

That is the same class of problem the `ci.yml:117-134` comment documents from 2026-07-30, where `cargo test` and `cargo nextest run` produced different flake behaviour and the fix was to align the runners so that *"green locally means the same thing as green in CI."* The runner was aligned; the toolchain version was not.

**There is no pipeline abstraction to reuse.** `Taskfile.yml` covers docs, demo reels, checksums, homebrew and scoop — release and packaging automation. It has no `build`, `test`, `lint` or `ci` task. The CI steps exist only as raw `cargo` invocations inside `ci.yml`, so nothing outside GitHub Actions can run them, including an agent working locally.

Separately, we want to evaluate Semaphore as a second CI provider (including its agentic `sem-ai` tooling) for a comparison. That evaluation needs the build steps to be invokable outside GHA anyway, because Semaphore has no equivalent of the marketplace actions `ci.yml` depends on. The toolchain has to be provisioned by hand there regardless — and `devbox.json` already pins exactly the right set, already under Renovate management (`renovate.json`, `matchManagers: ["devbox"]`, automerged for patch/minor).

So the second provider is the forcing function, but the pinning fix is worth landing on its own.

## Solution Overview

Introduce `task`-level CI entrypoints that wrap the existing cargo invocations, and provision the toolchain from `devbox.json` rather than from marketplace actions. Stand the result up as a new Semaphore pipeline covering the three jobs Semaphore Cloud can host, measure it against the GHA baseline, and use those numbers to decide whether to retrofit GHA.

Deliberately **do not** touch `ci.yml` or `release.yml` in this PRD. They are the working gate that Renovate automerges against, and they are the experimental control for the measurement. Editing them in the same change makes the comparison meaningless and puts a green pipeline at risk for no benefit.

## Scope

### In Scope

- New `task` entrypoints wrapping the commands `ci.yml` runs: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo build --release`, `cargo nextest run`, `cargo xtask linkage-check` (`ci.yml:114-144`) and `cargo audit` (`ci.yml:273`). Seven, not six as originally written: `ci.yml` also runs a plain debug `cargo build` on its macOS and Windows jobs (`ci.yml:256`, `:223`), which is a distinct command and got its own `ci-build-debug` entrypoint so the Semaphore macOS block can reproduce what the GHA macOS job does rather than doing strictly more work.
- `cargo-audit` added to `devbox.json`. `ci.yml:272` currently runs `cargo install cargo-audit --locked`, which compiles from source on every run and is almost certainly the slowest single step in CI. This is an unambiguous win independent of everything else in this PRD.
- `.semaphore/semaphore.yml` covering the three jobs Semaphore Cloud can host: `build` (Linux), `build-macos`, `security`.
- Measurement against the GHA baseline: cold nix bootstrap, `target/` cache hit rate, per-job and total wall clock. *Warm bootstrap dropped from this list: nix-store caching was removed (see the Work Log), so every job bootstraps cold from `cache.nixos.org` and there is no warm number to measure until store caching returns as a follow-up.*
- A recorded decision on whether to retrofit `ci.yml`, backed by those numbers.

### Out of Scope

- **Any edit to `ci.yml` or `release.yml`.** `git diff` against both must be empty when this PRD closes. Retrofitting GHA is a follow-up, gated on M5's numbers.
- **Windows.** Nix does not run natively on Windows — `ci.yml:193-195` already records this (*"the devbox/nix toolchain used locally is Linux-only"*) — and Semaphore Cloud has no hosted Windows runner, only self-hosted agents. `build-windows` stays on GHA with rustup. Two toolchain-provisioning paths is the accepted end state, not a gap to close later.
- **Publishing of any kind.** Publishing is confined to `release.yml` (triggered by `push: tags: ['v*']`) and `docs-publish.yml` (`workflow_call` only). `ci.yml` has no side effects, so a `ci.yml`-shaped Semaphore pipeline has nothing to double-publish. No publish flags, kill switches or conditionals are introduced anywhere — adding one to `release.yml` would create a silent-non-publish failure mode strictly worse than the double-publish it prevents.
- **Making Semaphore a required status check.** Renovate automerges cargo patch and ≥1.0 minor bumps on green CI (`renovate.json`). An unproven pipeline does not go in that path.
- Semaphore promotions and deployment targets. Interesting for a later comparison, but they imply release-shaped behaviour, which is out of scope here.

## Technical Approach

### Task entrypoints

Thin wrappers, one per existing CI step, so the mapping to `ci.yml` stays auditable and a diverging step is visible as a diff rather than as a behaviour change. No consolidation into a single `task ci` that hides which step failed — the four-job split in `ci.yml` exists so a platform-specific break is visible independently (`ci.yml:191-210`, `:233-244`), and the entrypoints should preserve that granularity.

### Reading `cargo --version` when comparing providers

Under the `cargo@1.97.1` devbox pin, `rustc --version` reports `1.97.1` while `cargo --version` reports `cargo 1.97.0 (c980f4866 2026-06-30)`. That is nixpkgs' 1.97.1 derivation reporting a 1.97.0 internal version — not a pin that failed to resolve, and not devbox picking the wrong package. It is written down here because any Semaphore-vs-GHA diff analysis that reads `cargo --version` will see `1.97.0` on the Semaphore side and must not conclude the pin did not take. `.semaphore/ci.sh` echoes both versions during the bootstrap and repeats this warning next to them.

### Caching is the part that does not abstract

This is the main technical risk and the reason this is a spike rather than a refactor.

`Swatinem/rust-cache@v2` (`ci.yml:112`) is not a thin wrapper. It derives keys from `Cargo.lock` plus the rustc version, selectively saves `~/.cargo` registry and git db plus `target/`, and prunes stale and incremental artifacts to keep the archive small. Replacing it means owning that logic.

Worse, the cache *backend* is irreducibly provider-specific: GHA uses the `actions/cache` REST API, Semaphore uses its `cache store` / `cache restore` CLI, and locally there is no cache because `target/` is already warm. No script abstracts that away — the pipeline will be provider-agnostic where it costs nothing (invoking cargo) and provider-coupled exactly where CI time is won or lost.

And the nix store looks like a second cache problem that does not exist today — except that on inspection it is better left uncached for now. See "Why there is no nix-store cache" below.

There is a third thing the cache is, which the first pass got wrong: an **untrusted input**. Cache keys derived from repository content authenticate the *content*, not the *producer*, so a branch that leaves the lockfiles untouched derives the default branch's keys while running its own `.semaphore/ci.sh`. Semaphore's cache CLI is project-wide (`store`, `delete`, `clear`), so a restore in a trusted job is a restore of somebody else's bytes. The pipeline now writes the cache only from the default branch, never restores over the checkout, and carries no prefix-fallback restores — and says in the file that the ref check is defence in depth rather than an authorization boundary, because the untrusted ref controls the script that performs the check. The real boundary is provider-side, which is why `docs/develop/ci-entrypoints.md` now opens with a checklist for project creation.

### Nix bootstrap cost

Devbox in CI needs nix installed and packages fetched. Cold, that is minutes. The conventional fix is `jetify-com/devbox-install-action`, which is a marketplace action and therefore unavailable on Semaphore and self-defeating on GHA, so the bootstrap has to be hand-rolled per provider. The honest expectation is that the first version is **slower** than the current `rust-cache`-based jobs; M5 exists to find out by how much.

Both installers are pinned and digest-verified rather than piped from a floating URL into a shell. HTTPS is transport security, not artifact integrity, and one of the two performs a privileged multi-user nix install — a mutated response there is root code execution on the agent. devbox's digests are the vendor's own, from the `checksums.txt` asset in its GitHub release. Determinate publishes **no** checksum and no build attestation for the nix-installer binaries, so those digests are self-recorded against the pinned release assets; that defends against a pinned artifact being mutated later, not against it having been wrong when recorded. Both pins are now Renovate-managed **for the version only** — a `customManagers` regex entry in `renovate.json` — with automerge explicitly off and `scripts/refresh-installer-digests.sh` as the second half of the bump, because Renovate cannot recompute the six paired digests. See the Work Log entry for why version-only management of a digest-verified pin is a real trade rather than a free win.

### Why there is no nix-store cache

The first version of `.semaphore/ci.sh` cached `/nix/store` as a `sudo tar -C / -cf` archive plus a `nix-store --dump-db` dump, restored with `sudo tar -C / -xpf -` and `sudo nix-store --load-db`. It is gone, for two independent reasons found in review.

**It was unsafe.** The archive arrived from the project cache with no digest, signature, producer identity or member allowlist, and was extracted at `/` as root with `-p`. An ordinary *relative* member such as `etc/ld.so.preload` therefore lands at `/etc/ld.so.preload` — tar's refusal of absolute and `..` members buys nothing when the extraction root is `/` — and `-p` as root preserves modes and ownership. `--load-db` then registers paths as valid from the dump's own claimed hashes, with no content re-hash and no signature check. Whoever could write that key had root code execution in a later trusted job.

**It had never worked**, which is why nobody noticed the first problem. It stored an absolute `$HOME/.cache/...` path; Semaphore's `cache store` strips the leading `/` and `cache restore` extracts relative to the working directory, so the restore produced a checkout-relative `home/...` tree while the code tested for the absolute path. Every job cold-provisioned, and any "warm bootstrap" number it produced would have been fiction.

The safe replacement shape is real and is written down in `.semaphore/ci.sh` so nobody reinvents the tar: `nix copy --to "file://<checkout-relative-dir>"` on the way out, `nix copy --from … --all` on the way back, signature verification left on and never disabled (nix has a flag for that and it must not appear in the file — an unsigned path refusing to import is the mechanism working), no `sudo` anywhere. It was not built now because for this workload it plausibly costs more than it saves and nothing has measured it: the paths worth caching are exactly the ones `cache.nixos.org` already serves signed from a CDN, so routing them through the project cache adds a full closure export plus an upload on the save side and a download plus a NAR re-import on the restore side; and the 4.4 GiB Linux closure would spend most of Semaphore's ~9.6 GB LRU project quota on paths a CDN already serves, evicting the `target/` archives that have no upstream alternative. So cold substitution is the measured baseline, and store caching is a follow-up that can be argued from M5's numbers instead of assumed.

### Machine mapping

| GHA job | Semaphore equivalent |
|---|---|
| `build` (`ubuntu-latest`) | `e1-standard-4` — 4 vCPU / 8 GB / 35 GB disk, Ubuntu 24.04 |
| `build-macos` (`macos-latest`) | `a2-standard-4` — Apple Silicon M2, 4 vCPU / 8 GB, Xcode16 or Xcode26 |
| `security` (`ubuntu-latest`) | `e1-standard-4` |
| `build-windows` | none — out of scope |

**Why `e1-standard-4` and not the `f1-standard-4` this table used to name.** `f1-standard-4` is **not available on this organization's plan**, which is what killed the first two runs: both Linux blocks reported `start_time: 0` — no agent ever assigned, not one command executed — and the API error is explicit, *"Selected machine type is not available in this organization."* The catalogue this org can actually provide is `a2-standard-4`, `e1-standard-1`, `e1-standard-4`, `e1-standard-8`, `e2-standard-2` and `f1-standard-2`; note `f1-standard-2` **is** offered, so it is specifically the `-4` size of F1 that is gated, not the F1 generation. Out of what is available, `e1-standard-4` is chosen for **vCPU parity with the GHA control**: `ubuntu-latest` is 4 vCPU / 16 GB, and vCPU count dominates compile wall clock, which is exactly what M5 measures. `e1-standard-8` (8 vCPU / 16 GB) would match the RAM but *double* the CPU, making Semaphore look artificially fast and the comparison invalid; `f1-standard-2` and `e2-standard-2` are 2 vCPU and understate. The 8 GB-against-16 GB gap is no longer speculative — `a2-standard-4` is also 4 vCPU / 8 GB and it passed the full compile + clippy + `nextest` tier on this branch, so 8 GB is proven adequate for this workload — and 35 GB of disk against a 4.4 GiB devbox closure plus `target/` is ample (`f1-standard-4` would have had 65 GB). `os_image: ubuntu2404` does not move with the machine type: E1, E2 and F1 all offer `ubuntu2204` and `ubuntu2404`.

**A known limitation on the measurement, recorded rather than closed.** Semaphore's docs state *"The E1 and E2 generations are legacy machine types … F1 and R1 are the recommended machine types for Linux workloads."* So M5's Linux numbers will come from a generation the provider is steering away from, and any conclusion drawn from them carries that caveat. The clean fix is a plan upgrade unlocking `f1-standard-4` — the exact `ubuntu-latest` analogue *and* the recommended generation — which is the repository owner's commercial decision, not a TODO this PRD can close.

A second, non-obvious lesson from those two failures: **the available machine types are an organization/plan property, not a schema property.** A pipeline that is valid YAML, naming a documented and correctly-spelled machine type, can still fail with every job at `start_time: 0` and no logs whatsoever. `sem get job <id>` reporting `start_time: 0` means *"no agent was ever assigned"*, and that is the signature of a machine type the org cannot provide. It cost two runs to learn, so it is also written into `docs/develop/ci-entrypoints.md`.

Note `a2-standard-4` has 8 GB against `ubuntu-latest`'s 16 GB, and it runs a debug `cargo build` (`ci-build-debug`, matching what `ci.yml`'s macOS job does — deliberately not the release build) plus clippy and the full `nextest` tier. That was written down as a live memory-pressure risk; **it is now measured and it is fine** — `build-macos` passed the whole tier inside 8 GB, twice.

### Cost

`vfarcic/dot-agent-deck` is public, so GHA is free for it, and Semaphore is added cost rather than saved cost either way. **The per-minute figure is currently unknown and must not be guessed.** This section originally said `$0.0075/min`; that was corrected to `$0.015/min` for `f1-standard-4`, and that figure no longer applies either, because the Linux blocks now run on `e1-standard-4` and the macOS block on `a2-standard-4`. **E1 per-minute pricing has not been verified** and has to be checked against this organization's plan before any cost claim appears here. Whatever it turns out to be, the evaluation must be argued on wall clock, cache behaviour and agent experience, not price.

### Renovate

No regression *for the toolchain*. `renovate.json` already has a `matchManagers: ["devbox"]` rule grouped as "Devbox packages" with automerge for digest/pin/patch/minor, so moving toolchain versions from GHA action refs into `devbox.json` keeps them bot-managed. The `github-actions` manager rule simply has less to do.

That was not the whole story, though, because this PRD also introduced two dependencies that live in **neither** file: the nix-installer and devbox pins in `.semaphore/ci.sh`, which no built-in manager can see. They are now covered by a `customManagers` regex entry grouped as "Semaphore CI installers", with **automerge explicitly off** — Renovate bumps the version and cannot recompute the six sha256 digests paired with it, so an automerged bump would land a pipeline that fails closed on every run. `scripts/refresh-installer-digests.sh` (`task refresh-installer-digests`) is the mechanical second half, and the PR body says so. See the Work Log for the argument, including the case against doing this at all.

## Success Criteria

- Each `ci.yml` step has a `task` entrypoint that runs identically on a local devbox shell and on Semaphore.
- `cargo-audit` comes from `devbox.json`; nothing compiles a CI tool from source.
- The Semaphore pipeline is green for `build`, `build-macos` and `security` on a PR and on a push to `main`.
- Measured and recorded: cold bootstrap, `target/` cache hit rate, per-job and total wall clock, each against the current GHA baseline.
- `git diff` against `ci.yml` and `release.yml` is empty.
- A written decision on retrofitting GHA, citing the numbers — including "no" as an acceptable outcome.

## Risks

- **The abstraction misses the part that matters.** Caching is where CI time lives and it is exactly what cannot be made provider-agnostic. The pipeline will still carry `if GITHUB_ACTIONS / elif SEMAPHORE` branches in its cache steps. If that is unacceptable, the premise of the PRD is weaker than it looks.
- **CI gets slower.** `rust-cache` is well tuned; a hand-rolled equivalent plus a nix bootstrap plausibly loses to it initially. M5 is the check, and a slower result is a legitimate reason to close this PRD without retrofitting GHA.
- ~~**macOS binary cache miss.**~~ **RETIRED (2026-08-04) — and darwin turned out to be the proven leg, not the at-risk one.** The worry was that worse nixpkgs darwin cache hit rates would leave `a2-standard-4` building the Rust toolchain from source, making the macOS job unusable; M2 gated it deliberately. `build-macos` has now passed twice on `a2-standard-4` in 5m45s with a cold bootstrap, which is not a from-source toolchain build. Two things about how this resolved are worth keeping, because both cut against how this PRD was written: the risk register put macOS at the top and Linux nowhere, and it is **Linux** that has failed twice and never run a command; and this risk was retired without any macOS-specific fix ever being written, because the block was correct the first time. The residual is honest rather than zero — two runs is not a track record, and the darwin closure is only as available as `cache.nixos.org` keeps it.
- **Scope creep into `ci.yml`.** The single largest risk for a session that does not have the originating discussion. `ci.yml` and `release.yml` are off limits: they are the control for the measurement, `release.yml` touches real users' `brew upgrade` path through `vfarcic/homebrew-tap` and `vfarcic/scoop-bucket`, and Renovate automerges against `ci.yml` being green.
- **Confounded comparison.** Changing GHA and standing up Semaphore at the same time means a slow Semaphore job cannot be attributed — machine, nix bootstrap or hand-rolled cache. This is the concrete reason for the out-of-scope rule above, not tidiness.
- **Two toolchain paths forever.** Windows keeps rustup and marketplace actions, so the pinning fix does not reach it. Given `portable-pty` is held at `=0.8.1` for a Windows ConPTY reason (`renovate.json`, `Cargo.toml`), Windows is where the load-bearing bugs live — and it is the platform this change cannot help.

Reimplemented: keys from `Cargo.lock` plus a toolchain fingerprint (taken from `devbox.json` + `devbox.lock` + the whole `gcloud/` flake source rather than `rustc -vV`, so a key exists before a toolchain does), the three cached locations, `CARGO_INCREMENTAL=0` plus deletion of any incremental dir, dropping `registry/src` and `registry/index/*/.cache`, and write-once-per-key-on-pass. Not reimplemented: pruning `target/` down to artifacts the current dependency graph references, build-script output pruning, and invalidation on toolchain-env changes beyond the lockfiles. **And one behaviour was implemented and then deliberately removed: the prefix-fallback restore.** It widens cache poisoning from "guess the one exact key" to "store under anything sharing the right prefix", which is not worth a near-miss archive from an unrelated lockfile state; the price is that a `Cargo.lock` bump is now a cold build rather than a rebuild-what-moved, and M5 should report the hit rate so that trade can be argued from numbers rather than from taste. Consequence of the missing pruning, stated rather than hidden: `target/` grows monotonically per key lineage, so the script caps the archive at `CARGO_TARGET_CACHE_MAX_MB` (4000) and logs loudly when it declines to store — a measured local `target/` is 8.5 GiB (1.4 GiB of it incremental), and Semaphore documents a per-project cache quota in the same order of magnitude. Whether the cap trips on a CI-shaped `target/` is one of the first things M5 will find out.

   One thing that is *not* a rust-cache behaviour but turned out to be load-bearing: **Semaphore's `cache store` strips a leading `/` and `cache restore` extracts relative to the working directory**, so only checkout-relative paths round-trip. `CARGO_HOME` is therefore moved inside the checkout (`.semaphore/ci.sh cargo-home`, exported once from the pipeline prologue so the path is never written down twice and cannot drift into a silently-cold cache), and every restore lands in a scratch directory from which only a validated allowlisted member is moved into place — never straight over the checkout, because an archive whose members are `Taskfile.yml` or `devbox.json` is code execution in the restoring job. That mechanism bounds what an archive can get **adopted into place**; it does not confine the provider's extractor, which has already run by then — see the Work Log for the precise claim and what would have to be verified to strengthen it.
3. **Do the task entrypoints eventually become GHA's interface too, or stay Semaphore-only?** This is the M6 decision. Staying Semaphore-only leaves the version-skew bug unfixed on the platform that actually gates merges, which would be an odd place to stop.

### 2026-08-04 — the `.semaphore/ci.sh` installer pins are now bot-managed, for the VERSION ONLY

The two pins the round below introduced (`DeterminateSystems/nix-installer` `v3.21.9`, `jetify-com/devbox` `0.17.5`) are now under Renovate, closing the "pinning without automation rots" follow-up that round deliberately left open. **What is managed is the version string and nothing else** — and that asymmetry is the whole entry, because it is a real trade rather than a free win.

**The mechanism.** A `customManagers` regex entry in `renovate.json` matches a `# renovate: datasource=github-releases depName=…` annotation immediately followed by the annotated assignment, so it matches exactly those two lines: not a digest, not the version where it appears in a download URL, not a version inside a comment, and not some future unrelated `*_VERSION` variable (verified against the real file — 2 matches, both intended, no digest line inside a match). A `packageRules` entry scoped to those two `depName`s under `matchManagers: ["custom.regex"]` groups them as "Semaphore CI installers" and sets **`automerge: false` explicitly**, not merely by omission.

**Why automerge off is load-bearing.** Each pin is paired with three per-platform sha256 digests that `ci.sh` verifies and **fails closed** on. Renovate cannot compute the sha256 of a GitHub release asset, so its PR moves the version and leaves six digests describing the *previous* release. Automerged, that puts a pipeline on `main` that hard-fails its first step on a provider nobody is watching yet — the worst version of this, because it is silent. The precedence was checked rather than assumed: none of the four `cargo` rules, the two `devbox` rules, `github-actions`, the `site/**` npm rule or the package-name rules can match a `custom.regex` dep, the trailing `major` rule also sets `automerge: false`, and nothing in the `extends` presets enables automerge. The new rule is nonetheless placed late in the array so a future broad automerge rule inserted above it loses.

**Making the PR actionable.** A bot PR a human cannot finish in one step rots exactly like the unpinned URL did, so `scripts/refresh-installer-digests.sh` (`task refresh-installer-digests`) is the second half: it reads the versions currently pinned in `ci.sh`, takes devbox's three digests from the vendor's own `checksums.txt` and self-hashes the three nix-installer binaries (preserving the distinction the digest table documents — Determinate publishes no checksum), and rewrites the table in place. It refuses to write anything if any download or lookup fails, refuses to touch the file if `ci.sh` carries a different number of digests than it knows how to refresh (its platform list mirrors ci.sh's `case` statements and nothing links the two copies), and `--check` verifies without writing. Renovate's `prBodyNotes` carries the command, so the instruction arrives with the PR rather than only in `docs/develop/ci-entrypoints.md`.

**Validated.** `renovate-config-validator --strict` passes with no migration warnings, so `managerFilePatterns` (Renovate 43 has removed `fileMatch`) and `prBodyNotes`-inside-`packageRules` are both accepted as written. A read-only `renovate --platform=local --dry-run=lookup` extracted **both** deps with the right `depName`s and resolved them against the live `github-releases` datasource with zero warnings; re-run against deliberately downgraded pins (`v3.21.7`, `0.17.3`) it proposed `v3.21.9` / `0.17.5` — the `v` prefix preserved on one and absent on the other — and grouped both into `renovate/patch-semaphore-ci-installers`, i.e. the branch slug derived from the new rule's `groupName`, which is the same rule object that carries `automerge: false`. The refresh script reproduced **all six currently-pinned digests byte-for-byte**, and additionally re-hashed the three devbox tarballs against `checksums.txt` under `--verify-assets`; against copies with a corrupted nix digest and a corrupted devbox digest it reported the drift, repaired both, and produced a file byte-identical to the real one; against a nonexistent release it aborted with a 404 and left the file untouched.

**The argument against doing this, recorded because it is not obviously wrong.** Version-only management of a digest-verified pin converts a *silent staleness* problem into a *loud recurring chore*: a bot PR arrives, fails its own verification by construction, and waits for a human to run a script. That is strictly more work than the unmanaged pin created, and the failure mode it prevents — an old-but-correct installer — is mild compared to what a mishandled bump does. Three things make it still worth it: the digest table's *only* purpose is to be current, staleness here is invisible where a red PR is not, the second half is one command that cannot half-apply, and `automerge: false` means the bot can never complete the dangerous half on its own. The one genuinely regrettable property is that a wrong edit to the annotation comment makes the manager silently stop matching — Renovate does not warn about a custom manager that matches nothing.

### 2026-08-04 — re-audit: the restore was a symlink escape, and "containment" was an overclaim

The re-audit of the round below closed the privileged-path, installer-pinning and tag-guard findings and left one Medium open: `restore_member` followed archive-controlled symlinks and adopted failed partial restores. Both halves are fixed, and the claim the mechanism was described with is corrected.

**A failed restore is a miss, not a hit.** The `|| true` on `cache restore` is gone. A nonzero exit now deletes the scratch tree and cold-builds, so a restore that writes half a member and then fails can no longer be adopted as though it were warm. Which of "key absent" and "transfer failed" a nonzero status actually means on Semaphore is unverified; treating both as a miss makes it unnecessary to know.

**Validate before adopting.** `-e` and `-d` follow symlinks, so the old check proved nothing about *where* the member was: an archive whose `.semaphore-cache-restore/.cargo-home` is a link to any directory on the agent made `…/.cargo-home/registry` test true and got that external directory moved into the checkout — reproduced against the old code in the harness below. Adoption now requires that every path component on **both** sides of the rename is a real directory (`-L` per component), that the member root is a real directory, that the tree contains nothing but real files and real directories, and that no file in it is hardlinked from outside it. Any failure deletes the scratch tree and returns a miss; nothing is ever repaired.

**Two rules worth recording, because both could have gone the other way.** *Symlinks: reject all of them inside the adopted tree*, not only the ones resolving outside it — "resolves outside" has to be computed, and a chain of links defeats a lexical computation while a real resolution is a second filesystem round trip to get wrong. It costs nothing measurable: a full local `target/` (33,896 files) and a populated `~/.cargo/{registry,git}` contain zero symlinks. If a dependency ever legitimately adds one, this fails closed to a loudly-logged cold build and the deliberate fix is to relax the rule, not delete it. *Hardlinks: count links per inode*, because the blunt `-links +1` test is unusable — cargo hardlinks its uplifted binaries (`target/debug/foo` ↔ `target/debug/deps/foo-<hash>`), 9,011 of those 33,896 files — so the check compares each inode's link count against the number of links to it found inside the member, and only an excess means an alias to something on the agent. `find -links` and `ls -ldi` are POSIX, so this works on the macOS agent too.

**The containment claim is downgraded in `ci.sh`, `docs/develop/ci-entrypoints.md` and this PRD.** The scratch-plus-allowlist mechanism bounds what an archive can get **adopted into place**. It does **not** confine the provider's extractor: `cache restore` writes before any of this code sees the scratch directory, so if Semaphore honours absolute or `..` members those files have already landed elsewhere and a scratch-only cleanup can neither detect nor undo them. That behaviour is unverified. One unverified provider behaviour is what stands between this and a real containment claim — which is why "verify `cache restore`'s handling of absolute and `..` members on a real agent, or sandbox the restore so only the scratch directory is writable" is now item 4 of the activation checklist, and a prerequisite before any project shares a cache across trust levels.

**Validated locally** with the stand-in `cache` CLI harness extended to hostile archives, where a fixture is a shell snippet standing in for "what the extractor wrote, and what it exited with". Seven cases, 38 assertions, all passing: `.cargo-home` a symlink to an external directory → rejected; the member itself a symlink → rejected; a symlink nested in the tree → rejected; a FIFO in the tree → rejected; a hardlink to an external file → rejected; a partially-written member plus a nonzero exit → miss, nothing adopted; the clean three-member restore → all adopted, cargo-style internal hardlink preserved, no stray entries. The poisoned-members case (`Taskfile.yml`/`devbox.json` in the archive) was re-run and both files are still byte-identical. The same harness run against the pre-fix script fails 14 of those assertions, including the external directory being moved into the checkout — the escape was real, not theoretical. Still unvalidated: everything involving the real Semaphore cache CLI, an agent, or macOS.

### 2026-08-04 — review round: the cache was unsafe AND dead; M2's blind spot closed

A reviewer and an auditor went over the pipeline file. Nine findings, all real. The headline is that the two most serious ones were the same code: **the nix-store cache was simultaneously a root-write primitive and dead code**, and the second fact is why nobody noticed the first.

**The nix-store cache is deleted, not repaired.** It took an archive from the project cache with no digest, signature, producer identity or member allowlist and ran `sudo tar -C / -xpf -` on it, then `sudo nix-store --load-db`. Because the extraction root is `/`, an ordinary relative member like `etc/ld.so.preload` lands at `/etc/ld.so.preload`; `-p` as root preserves modes and ownership; and `--load-db` registers paths as valid from the dump's claimed hashes without re-hashing content or checking signatures. And it had never worked: it stored an absolute `$HOME/...` path, `cache store` strips a leading `/`, so the restore could never match the absolute path it tested for. Fixing the path is precisely what would have armed the primitive. Full argument, including the signed `nix copy` shape to use if store caching returns and why it plausibly loses to the CDN here, is under "Why there is no nix-store cache" above and in `.semaphore/ci.sh`. **Consequence for M5: cold bootstrap is the baseline; there is no warm-bootstrap number to collect.**

**The cache is now treated as an untrusted input.** Content-derived keys authenticate content, not producers. A same-repository branch that leaves the lockfiles alone derives `main`'s keys while running its own `ci.sh`, and Semaphore's cache CLI is project-wide. So: one namespace, written only on a push to the default branch; branch and PR runs restore read-only and store nothing (stricter than a per-ref namespace, and it keeps per-branch multi-GB archives from LRU-evicting the shared ones); restores unpack into a scratch directory and only a validated allowlisted member is moved into place (see the entry above for how far that goes, and how far it does not); no prefix-fallback restores. The file says plainly that the ref check is defence in depth and not an authorization boundary, since the untrusted ref controls the script performing the check. `SEMAPHORE_GIT_REF_TYPE` is checked, not just `SEMAPHORE_GIT_BRANCH` — the latter is the *target* branch on a PR run, so branch-only logic would classify every PR against `main` as trusted.

**Both installers are pinned and digest-verified**, no more `curl | sh`: Determinate nix-installer `v3.21.9` and devbox `0.17.5`, downloaded to a file, checked against digests recorded in `ci.sh`, then executed. devbox's digests are the vendor's own (its release ships `checksums.txt`); Determinate publishes neither a checksum nor a GitHub build attestation for its installer binaries, so those are self-recorded and the comment says so. devbox now also installs from the release tarball into `$HOME/.local/bin`, which removed the last `sudo` outside the nix install itself.

**Smaller fixes.** The cache fingerprint now hashes every file in `gcloud/`, not just `flake.lock` — editing `flake.nix` alone previously produced the old key while `has_key` blocked replacing the stale archive, which would have corrupted warm-bootstrap numbers indefinitely (verified locally: the fingerprint moves). One writer per shared key: `build` owns the registry/git-db keys and its own `target/`, `build-macos` owns only its platform `target/` (`save-cargo-target-cache`), `security` writes nothing — `has_key` is not atomic, so shared writers duplicate GiB of work and confound M5. Every block is tag-guarded with `run: when: "tag !~ '.*'"`, which is defence in depth only: disabling tag triggers in Semaphore's project settings is the real fix and is now item 1 of an activation checklist in `docs/develop/ci-entrypoints.md`. Prose overclaims corrected in three places (the macOS job builds *debug*; M1 is seven steps; the wrappers cover seven cargo invocations, not "every step CI runs").

**What was actually validated this round**, since the honesty of that distinction is the point of this PRD: `bash -n` clean; both YAML files parse; the key derivation, trust gating, prune, store and restore paths were exercised end to end against a stand-in `cache` CLI locally — including a test that an archive carrying `Taskfile.yml` and `devbox.json` leaves both files untouched and gets reported and discarded. *(That last result was originally written up as "poisoned-archive containment". It is not containment — see the entry above; it is evidence that those two members are not adopted.)* Not validated: anything involving the real Semaphore cache CLI, the Conditions DSL expression, the installers on a real agent, or macOS. `git diff main -- .github/` is empty.

### 2026-08-04 — Created

Came out of a Semaphore evaluation discussion. Three decisions worth preserving, because they are the parts a fresh session is most likely to undo:

1. **The order is inverted on purpose.** The obvious plan is "make GHA provider-agnostic, then porting is trivial." Rejected: marketplace actions do not exist on Semaphore, so the toolchain has to be hand-provisioned there regardless. Writing the devbox layer on the Semaphore side first means no extra work, keeps GHA as an unmodified control, and produces the numbers that justify (or kill) the retrofit before touching a working gate.
2. **The version-skew fix is the real motivation**, not portability. Portability of the invocation layer is cheap and mostly cosmetic; caching stays provider-specific either way. `devbox.json` pinning vs `rust-toolchain@stable` floating is an actual latent bug.
3. **No publish conditionals anywhere.** `ci.yml` has no side effects and `release.yml` is out of scope, so the double-publish problem does not arise at this scope. If a full release pipeline is ever demoed on Semaphore, do it by pointing at **separate destinations** — the existing `NAME=dot-agent-deck-beta` channel in `Taskfile.yml`, a throwaway tap, a `:semaphore-test` image tag — rather than by flagging the real one. A flag can be misconfigured; a different destination structurally cannot collide. Note also that `release.yml`'s `concurrency: group: release` gives zero protection against a second CI provider, since concurrency domains do not span systems.
