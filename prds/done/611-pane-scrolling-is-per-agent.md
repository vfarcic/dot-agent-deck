# PRD #611: Pane scrolling is per-agent, and the deck should say so

**Status**: Implementation complete (M1-M3); PR pending
**Issue**: [#611](https://github.com/vfarcic/dot-agent-deck/issues/611)
**Builds on**: [#341](https://github.com/vfarcic/dot-agent-deck/issues/341) (the focused-pane scroll routing and the command-mode banner this PRD's notice is modelled on)
**Interacts with**: [#362](https://github.com/vfarcic/dot-agent-deck/issues/362) (wheel events routed by focus rather than by pointer), [#385](https://github.com/vfarcic/dot-agent-deck/issues/385) (which also extends the `mode/scroll` family)
**Priority**: Medium

## Problem Statement

Scrolling a pane with a two-finger trackpad swipe works on a `claude` pane and does nothing at all on a `codex` pane — "as if it's locked". Reported on macOS/Ghostty; the mechanism is agent-side and not OS-specific. `fn`+Up/Down (PageUp/PageDown) behaves the same way: works on claude, nothing on codex.

**No line of deck code is misbehaving.** Both branches of `scroll_focused_agent_pane` (`src/ui.rs`) do exactly what they were designed to do — `PaneInput` plus child mouse reporting forwards the wheel into the child's mouse protocol, and everything else moves the deck's own vt100 scrollback. The two agents use *opposite* scrolling models, and the deck supports one of them well and the other not at all.

| | claude | codex |
|---|---|---|
| Mouse tracking enabled | all four: `1000h`, `1002h`, `1003h`, `1006h` | **none** — only `1004h` (focus reporting, not mouse) |
| Alternate screen (`1049h`) | — | **no** |
| Who owns the transcript | **the app** | **the terminal** |
| Responds to PageUp / `ESC[5~` | yes | **no** |

**claude is app-managed.** It requests mouse tracking precisely so it can scroll its own transcript. The deck forwards the wheel while in `PaneInput`, claude scrolls itself, and the user sees exactly what they expect. **codex is terminal-managed.** It requests no mouse events, so no terminal ever sends it any; it expects the *terminal* to hold scrollback — while contributing none. For such an agent there is nothing in the deck's buffer to move, by wheel or by key, in any mode, and both branches of the routing decision therefore no-op silently.

Three separate things are wrong with that state of affairs, and they are what the three milestones address: the docs describe pane scrolling as though it worked uniformly, the deck gives no feedback when a scroll cannot land so working-as-designed reads as broken, and the very state the feedback would key off — `mouse_mode_enabled` — is derived by a function with zero tests and three verified defects.

## Solution Overview

Nothing here tries to give codex scrollback the deck cannot manufacture (see **Rejected routes** below, and Out of Scope). The work is to make the deck honest about a per-agent reality, and to make the state it reasons about correct.

1. **Say it in the docs** (M1). `docs/keyboard-shortcuts.md` states the per-agent reality: app-managed agents own and scroll their own transcript, terminal-managed agents contribute no scrollback, and for the latter the deck has nothing to scroll.
2. **Say it on screen** (M2). When a scroll is *attempted* and cannot land, a brief dismissable notice appears in the pane, modelled on the existing `COMMAND MODE — Ctrl+D to type` banner (`BANNER_LINE`, `src/ui.rs`). Silence is what turns correct behaviour into a bug report.
3. **Derive the state correctly** (M3). `scan_mouse_mode` (`src/embedded_pane.rs`) misses the combined SET form, lets an enable in a chunk beat a disable in the same chunk regardless of byte order, and cannot see a sequence split across a PTY read boundary. It is the input to the branch M2 reacts to, so its defects are the fastest way to make M2 lie.

## What was measured

A real 139 KB interactive codex session (v0.147.0) was captured with `script -qfc codex` and replayed through the repo's own `vt100` 0.16 at several parser heights, asking for 3 lines the way `FOCUSED_PANE_SCROLL_LINES` (`src/ui.rs`) does. `vt100` clamps `set_scrollback` to the real buffer, so the readback is authoritative:

| parser height | codex buffer depth |
|---|---|
| **51 rows (what codex rendered for)** | **0 lines** |
| 44 rows | 182 lines |
| 24 rows | 187 lines |
| 12 rows | 225 lines |
| *control: 2000 plain streamed lines @ 51 rows* | *1950 lines* |

Codex sizes its scroll regions to the exact terminal height (164 DECSTBM calls: `ESC[1;50r`, `ESC[40;51r`, …) and repaints its whole transcript in place — 4971 cursor-position sequences against 95 newlines. **It never lets a line scroll off the top**, so there is nothing for any terminal to retain. The 182–225 lines at smaller heights are an artifact of the parser being shorter than codex believed the terminal to be; they do not occur in reality. The control row proves the parser and the measurement are sound — the same rig retains 1950 of 2000 plainly streamed lines at the same height that yields zero for codex.

**Codex's transcript is unscrollable in Ghostty too.** Scrolling up during a long codex session in a plain terminal reaches the content that was on screen *before* codex started — never an earlier part of the conversation. Codex does not use the alternate screen, so the pre-codex screen stays in the host terminal's scrollback above its UI. That is what appears to be "scrolling working outside the deck". A deck pane spawned for the agent has no pre-existing content, so nothing moves at all. This matters beyond the diagnosis: it is the objection every user will raise, so M1's prose has to pre-empt it.

### Rejected routes

Two ways of manufacturing scrollback for a terminal-managed agent were considered and rejected.

- **Retaining overwritten frames.** Codex repaints its whole transcript region rather than emitting new lines, so successive frames are near-duplicates. Paging back through them would page through redundant screenshots, not scrollback — the user would see the same conversation tail again and again with cosmetic differences, which is worse than the honest nothing they get today.
- **Handing the agent a taller virtual terminal than the pane.** Codex lays out against the height it is told, and sizes its DECSTBM regions to it. Give it more rows than the pane has and its composer renders off-screen, breaking the live view to buy history for a view nobody is looking at.

**A real fix can only happen upstream in codex** — filed separately, and out of scope here.

## Hypotheses falsified along the way

Recorded so nobody re-treads them.

1. **Codex enables mouse tracking and ignores the forwarded wheel.** No — it enables none of the four mouse modes, so the forwarding branch of `scroll_focused_agent_pane` is never taken for it in the first place. The only private mode it sets is `1004h`, focus reporting, which is not mouse reporting.
2. **Codex's pane is scrollback-starved at startup while claude's is not.** No — the startup measurement showed the *opposite* (codex 9 lines, claude 0). Both startup captures were unrepresentative of a working session, which is why the measurement above uses a real 139 KB interactive capture instead.
3. **Mouse-mode is seeded per agent type.** No — only the test seams take a bool (`EmbeddedPaneController::for_scroll_seam_with_focused_pane` and friends); the real spawn path always seeds `false` and lets `scan_mouse_mode` derive it from the child's own bytes.
4. **`ESC[5~` reaches codex and scrolls it.** No — codex ignores PageUp entirely, which is why the keyboard path fails for exactly the same reason the wheel path does and why the M2 message must not offer one as a workaround for the other.

**`~/.local/state/dot-agent-deck/deck.log` has no scroll or mouse instrumentation at all**, which is why none of this was diagnosable from artifacts and why all of it had to be measured by replaying a captured session through the parser.

## Scope

### In Scope

- **Docs that state the per-agent reality.** `docs/keyboard-shortcuts.md` — its mouse/scrolling preamble and its `### Scrolling back through a pane` section, both of which read as though scrolling worked uniformly — plus any other published page making the same claim. `docs/workspace-modes.md`'s "Reading a Pane in Command Mode" turned out to be the only other one.
- **A reactive on-screen notice** when a scroll is attempted on a pane that has nothing to scroll, on dashboard panes and the orchestrator pane, modelled on the command-mode banner's tiering and self-clearing behaviour.
- **Correct derivation of `mouse_mode_enabled`**: the combined SET form, disable-wins-within-a-chunk by byte position, and carry-over across PTY read boundaries — with the unit tests the function has never had.
- **Harness coverage per CLAUDE.md rule 4** for M2, extending the existing `mode/scroll/00X` family in `tests/mode_indication.rs` rather than adding a near-duplicate, with the `tests/CATALOG.md` entries revised alongside.
- **A synthetic regression fixture** for M3 — a byte stream reproducing the DECSTBM-plus-repaint pattern — rather than the real captured session, which contains actual conversation content.

### Out of Scope

- **Making codex's transcript scrollable.** That requires codex to use the alternate screen, to enable mouse tracking, or to bind a scroll key, and belongs upstream. Nothing the deck can do from the outside substitutes for it; see **Rejected routes** above for the two attempts that were considered and why each fails.
- **Any registry entry naming codex.** Excluded by a Decision below rather than merely unplanned — the condition is detected, the agent is not.
- **Scroll or mouse instrumentation in `deck.log`.** Its absence is recorded as a Risk because it is why this took a replay rig to diagnose, but adding it is a separate piece of work with its own noise/volume trade-offs.
- **Pointer-based routing of wheel events (#362) and the wider copy/selection work (#385).** They touch the same call site and the same test family; they are not folded in here.
- **Worker panes in an orchestration.** See the scope Decision below — the reactive design covers them for free if anyone ever scrolls one, and they are not a target.

## Decisions

- **The notice is reactive, not proactive.** It fires when a scroll is *attempted* and cannot land — never on pane focus or on spawn. A proactive variant nags every codex pane at startup, including the many times nobody meant to scroll, and a notice that appears when you were not asking anything is noise that teaches users to ignore it. This matches the banner philosophy already documented for command mode: *"a key that isn't bound to anything keeps it up, because that is the moment you most likely thought you were talking to the agent"* (`docs/keyboard-shortcuts.md`).
- **The notice must not swallow the keystroke.** It is visual only, cleared by a timer or by the next key *without consuming it*. The alternative — a dismissal that eats the keypress — would introduce a dropped-character bug in `PaneInput` as the price of explaining a no-op, which is a straight downgrade.
- **Detect the condition, not the agent name.** The trigger is "this pane's scrollback is empty AND this pane has been handed substantial output". The constraint it exists to satisfy is the one #611 states and is unchanged: codex is not special, its *rendering model* is, a future repainting agent must be covered automatically, and a registry entry naming codex would go stale the moment either that agent or another one changed while silently under-reporting rather than failing loudly. **What each half of the conjunction buys is worth being exact about, because the corrected message below needs less of the second than the original framing claimed.** The notice now describes the *pane*, so its honesty rests on the first half alone — the live vt100 retained-line depth, which establishes directly and without inference that there is nothing here to scroll. The second half is no longer asked to be right about anything, least of all a rendering model, since nothing in the message asserts one; its remaining job is narrower and still worth having, which is not nagging a pane that is merely young — the claude pane one second after spawn, which has nothing to scroll *yet* and will have plenty in a minute. The threshold does not change on that account: a heuristic that only has to separate "new" from "not new" is one that eight screenfuls serves well, and it stays one named constant for the same reason it always was.
- **The message says what is true and offers no false alternative.** In particular it does **not** suggest PageUp — hypothesis 4 above establishes that PageUp fails for exactly the same reason the wheel does, so offering it would send the user to a second dead end and cost the message its credibility.
- **The message claims only what was observed about the pane, never the agent's rendering model.** Corrected in review; M2 shipped `This agent redraws in place and keeps no scrollback — there is nothing to scroll`, and the evidence behind the trigger cannot support that sentence. Bytes are counted as they are handed to the parser, before anything parses them, so a pane fed `8 * rows * cols` NUL bytes (15,360 at 24×80 — vt100 ignores every one of them), a pane fed cursor-control noise, or a pane whose chunk panicked the parser all arrive at "screenfuls fed, nothing retained" with no rendering model implied. **And the bytes need not be the agent's own**: an agent that `cat`s an untrusted file or prints a web response is relaying content it did not author, so a third party could make the deck state a falsehood in the deck's own trusted voice. The wording is now `Nothing to scroll — this pane has no scrollback to move through`, with `Nothing to scroll — no scrollback` as the narrow tier — both stating the observation and stopping there. The *why* stays in `docs/keyboard-shortcuts.md`, which M1 rewrote for exactly this and which can explain a per-agent distinction the deck cannot establish from one pane's output. The tier-boundary tests now derive their widths from the constants' own lengths rather than transcribing them, so a future reword cannot silently un-pin the boundary the way this one would have.
- **A live cannot-scroll notice suppresses the command banner on that pane, rather than being drawn over it.** Corrected in review. The notice is one line; the banner is not — from 5 inner rows up `draw_command_banner` selects a block-letter tier (`BannerTier::BlockCommand` at 40×5, `BlockCommandModeWithSubtitle` at 60×7), so drawing one line over it replaces the middle row and leaves block-letter rows above and below, plus a stray `Ctrl+D to type` at the richest tier. Only the single-line tiers were ever replaced cleanly, which is why the first precedence test — written at a two-row inner pane, which forces the single-line tier — reported "the notice wins" for a case that was really two messages interleaved. Command-mode **dimming is deliberately untouched**: it is gated on mode and focus alone and tells the user that typing does not reach the agent, which stays true while the notice is up.
- **Scope is dashboard panes and the orchestrator pane.** Worker panes in an orchestration are mostly autonomous and are not a scroll target in normal use. With the reactive design this needs no exclusion logic: a pane nobody scrolls never shows the notice, so the scope statement describes where it will be *seen* rather than a branch that has to be written.
- **Experimental flag → no.** CLAUDE.md rule 9 question asked and answered by the user before work started: M2 ships **visible by default**. It is a small explanatory message that makes existing behaviour legible, not a new mode or a new surface with its own semantics, and shipping it flagged-off would hide the explanation from exactly the confused user it exists for — the one who has already concluded the pane is "locked" and who will never have set `experimental = true`. Consequences to hold to: **no** `features::show_*` wrapper is added in `src/features.rs`, no `experimental_enabled()` call appears on this path, and **no `graduate-*` follow-up issue** is filed at ship time.
- **"Substantial output" is a byte count since spawn, measured in live pane screenfuls — and it measures the CURRENT parser epoch.** Resolved in M2 (was an Open Question); the epoch clause added by review. The trigger arms when **both** halves hold: the pane's **live vt100 retained-line depth is 0**, and the pane's parser has been handed at least `SCROLL_NOTICE_MIN_SCREENFULS` (**8**) × `rows` × `cols` bytes since the pane was created. A byte count beat the alternatives because it is the most direct expression of the sentence the notice makes: this agent has produced enough output to have filled the pane eight times over, and the buffer is still empty. Elapsed time says nothing about a quiet agent, and a count of parser feeds measures the daemon's chunking rather than the agent's output. The threshold is measured against the **live parser geometry**, deliberately never against `PANE_SCROLLBACK_LINES` (10,000) — every pane is constructed with that same capacity, so comparing against it would say the identical thing about every pane. Eight screenfuls is a heuristic and is named as one constant so it is one place to tune; both edges are pinned in `mode/scroll/001` (a 5-byte fresh pane stays silent, an 8-screenful zero-depth pane speaks) so a later change to the number cannot quietly lose either. **The counter is zeroed whenever `process_agent_output_chunk` rebuilds the parser**, which supersedes an earlier decision to keep counting a chunk the parser panicked on. That decision's rationale — the agent really did produce those bytes — is true and answers the wrong question: the pane's retained-line depth is a property of *this* parser, and `guarded_parser_feed`'s rebuild has just thrown away every line it held for reasons that are Agent Deck's own (`vt100` 0.16.2 panicking on a wide character in a short pane). Counting across the rebuild lets the deck satisfy "screenfuls fed, nothing retained" out of its own history loss and then attribute it to the agent. Both halves of the conjunction must describe the same parser epoch or neither means anything. Pinned by extending the existing panic regression `wide_char_in_one_row_pane_does_not_crash_the_tui`: the panicking chunk alone exceeds the threshold, and the counter after the rebuild does not.
- **The notice clears on a timer *or* on the next key, and — unlike the command banner — an unbound key clears it too.** Resolved in M2 (was an Open Question). The banner's rule that an unbound key keeps it up earns its keep there because an unbound key is the moment you most likely thought you were talking to the agent, which is exactly the state the banner exists to correct. That reasoning does not transfer: this notice answers a question the user asked a moment ago by scrolling, and once they have moved on to typing, holding the answer on screen is clutter. Dismissal therefore happens with no branch on what the key turned out to mean — which is also what makes the "must not swallow the keystroke" Decision above structural rather than a property to be maintained. `mode/scroll/005` pins both halves: an unbound `x` still reaches the child, and a bound `Ctrl+D` still performs its PaneInput → Normal transition. **It happens at the event seam, not only at the top of `handle_key_event`** (corrected in review): that funnel covers every key that reaches it, but it is not the only path — the non-live-pane intercept in the drain loop returns *before* it, changes mode and drains the rest of the burst, so a key aimed at a pane that had just become non-writable left the notice up. Clearing on the raw input event makes "the next input clears it" hold on every path, including any added later; the call inside `handle_key_event` stays because it is idempotent and is what the L1 dismissal seam drives. The clear is also **O(1) unless something is armed** — it runs on every character typed into a pane, and taking the pane-registry mutex to write `None` over `None` on every pane per keystroke is a cost paid for a state that is almost never live, so a controller-level atomic answers first.
- **The TTL is `COMMAND_BANNER_TTL`, not a second timeout.** Resolved in M2 (was implied by the Open Question above). The two are the same kind of thing — a brief explanation that fades on its own — and a user who has learned how long one lingers has learned both. A separate knob would be two numbers to keep in agreement for no gain.
- **A repeated failed scroll re-arms the notice, idempotently, refreshing its expiry.** Resolved in M2 (was an Open Question). The flicker the question worried about is avoided by construction rather than by staying quiet: re-arming overwrites one instant on one pane and nothing else, so there is no hide-then-reshow edge, no second notice stacked behind the first, and no frame rendered between the clear and the re-arm on the keyboard path. Staying quiet after the first attempt was rejected because the user swiping repeatedly at an unresponsive pane is precisely the user the notice exists for, and the second swipe usually means they did not read the first. `mode/scroll/005` distinguishes `visible_at_original_expiry` from `visible_at_refreshed_expiry` so "refreshes" cannot decay into "ignores".
- **M3's carry-over is threaded through `process_agent_output_chunk`, not parked on the pane.** Resolved in M2 (was an Open Question), and implemented in M3 rather than here. The widened signature is the acknowledged cost, and M2 already paid the same one for the same reason: the since-spawn byte counter that feeds the trigger above is incremented in that function, not at its caller. **The argument was originally stated wrongly and is corrected here** (review): it cited the function's own doc comment, *"both backends produce identical render state from identical bytes"*, but there are no longer two backends — the daemon-backed architecture removed the local-PTY reader thread, and `run_pane_io_task` is the sole production caller today (the other three call sites are unit tests). The placement is still right; the reason is that this is the one chokepoint where raw agent bytes become pane render state, so every derivation over that stream — mouse mode, the OSC 8 link map, the byte counter — has exactly one implementation, and a second reader path added later inherits all of them by construction instead of by somebody remembering to. Parked on the pane, each is state a new backend has to be told about separately, and the one that forgot would silently reintroduce the split-sequence defect.
- **A standalone scanner derives the mouse state, rather than reading it off the pane's own `vt100::Parser` — because the parser is rebuilt on a contained panic and this state has to survive that.** Recorded because the PRD as first written implied `vt100` could not do this, which is false, and a reader who checks will rightly ask why `scan_mouse_mode` exists at all. It could: the deck already feeds every agent byte into a `vt100::Parser`, `Screen` exposes `mouse_protocol_mode()` and `mouse_protocol_encoding()` publicly, and vt100's `decset`/`decrst` handlers iterate the parameter list — so **all three of M3's original defects (the combined form, byte order, the split sequence) were already handled by a parser this pane owns**, and the case for a second implementation cannot be built on capability. It rests on **lifetime**. `guarded_parser_feed` **rebuilds the parser** on a contained panic (`vt100` 0.16.2 on a wide character in a short pane), and a rebuilt parser has forgotten every DECSET the child ever sent. A flag read off it would go false at that moment and stay false until the agent happened to re-emit its mouse modes — which an app that sets them once at startup may never do — so a contained panic the user never sees would silently stop the wheel reaching a live claude pane for the rest of the session. `MouseModeScanner` lives beside the parser rather than inside it and is untouched by the rebuild, so the child's request outlives an incident that is the deck's own. **The symmetry with the since-spawn byte counter is deliberate, and resolves the opposite way for the same mechanism**: the counter is *zeroed* on a rebuild because it describes what *this parser* was handed, while the mouse state *survives* one because it describes what the *child* asked for. Same rebuild, opposite treatment, both correct — written down here so that a later reader who notices the asymmetry finds it explained rather than concluding one of the two is a bug.
- **The mouse modes are one mutually exclusive protocol plus a separate encoding, and the published flag requires SGR.** Corrected in review; the first M3 draft modelled 1000/1002/1003/1006 as four independent latches and published `any()` over them, which is not what a terminal does. The authority is the repo's own `vt100` 0.16.2, the crate that parses these very panes: `Screen::set_mouse_mode` **assigns** `mouse_protocol_mode` (so a later `1003h` supersedes an earlier `1000h`), `clear_mouse_mode` clears reporting **only when the DECRST names the mode currently in force**, and 1006/1005 go to a *separate* `set_mouse_encoding` field that enables no reporting whatsoever. The latch model was not merely imprecise, it was a regression this PRD would have introduced: on `ESC[?1000h` `ESC[?1002h` `ESC[?1002l` a real terminal ends with reporting **off**, while four latches leave the 1000 latch set and hold the flag true forever — where even the substring scanner it replaced would have cleared it. The model is now `protocol: None | Press(9) | PressRelease(1000) | ButtonMotion(1002) | AnyMotion(1003)` and `encoding: Default | Utf8(1005) | Sgr(1006)`; 9 and 1005 are included because they are the same match arms and cost nothing, and **1004 remains entirely unhandled** because it is focus reporting and treating it as mouse would break the exact case this PRD exists for. The published flag is `protocol != None && encoding == Sgr`. Requiring SGR is deliberate: `forward_mouse_scroll` emits SGR bytes and only SGR bytes, so forwarding to a child that selected the default or UTF-8 encoding injects input it will mis-parse, while declining costs at most one scroll of the deck's own buffer. The safety asymmetry decides it — being too generous puts unrequested bytes into somebody else's process, being too stingy costs a scroll — and it also settles the reviewer's separate note that the deck forwarded SGR regardless of what the child had selected. Sanity check, both pinned as tests: claude (1000+1002+1003+1006) is forwarded to, codex (1004 alone) is not.
- **vt100 and xterm disagree about one DECRST shape; vt100 shipped, and this is recorded as an OPEN QUESTION with a default rather than as a settled call.** The divergence is exactly one rule. `vt100` 0.16.2's `clear_mouse_mode` clears reporting **only when the DECRST names the protocol currently in force**; **xterm** sets `send_mouse_pos = MOUSE_OFF` on a DECRST of *any* of 9/1000/1002/1003, unconditionally. They therefore differ on precisely one shape — `ESC[?1000h` `ESC[?1002h` `ESC[?1000l` — which vt100 leaves reporting **on** (1002 is in force; the reset named 1000) and xterm turns **off**. **vt100 is what was implemented**, for two reasons: it is the emulator the deck's own rendering derives from, so the pane's screen and the pane's mouse flag can never disagree about the same bytes; and it is checkable **mechanically** rather than by assertion — `scan_mouse_mode_agrees_with_the_vt100_parser_it_shares_a_stream_with` feeds fifteen streams to both derivations and requires an identical answer, and the disputed shape is one of the fifteen. **The counter-argument is real and is not being waved away**: the child forms its expectations from the *real* terminal it believes it is talking to, not from the deck's rendering parser, so for a *forwarding* decision xterm is arguably the better model — and xterm's rule errs conservative, which is the direction this PRD's own safety asymmetry favours, since being too generous injects unrequested input into somebody else's process while being too stingy costs one scroll of the deck's own buffer. **It is not resolved here** because no agent measured for this PRD emits that shape at all (claude sets all four and withdraws none; codex sets no mouse protocol), because both models are defensible on their own terms, and because the SGR requirement above bounds the consequence either way. Switching is a one-line change — the `else if state.protocol == protocol` guard in `scan_mouse_mode`'s reset arm becomes an unconditional `else` — plus the differential test, which would then need an xterm oracle instead of the vt100 one. Left open deliberately for a reviewer to weigh in on; deliberately **not** filed as a follow-up issue, so the question is answered by the person reading the PR rather than pre-empted by a ticket.
- **CLAUDE.md rule 12 → the TUI↔daemon contract is unchanged; `PROTOCOL_VERSION` does not move and no `.breaking.md` fragment is needed.** All three milestones are strictly client-side. M1 is prose. M2 is render-seam and input-seam state living in the TUI's own `EmbeddedPaneController` and `UiMode` handling. M3 is a scanner over PTY bytes: `scan_mouse_mode` is called from `process_agent_output_chunk`, the one chokepoint where raw agent bytes become pane render state (see the corrected Decision above) — meaning the derivation happens on the client side of the wire, from bytes the daemon already streams unchanged as `KIND_STREAM_OUT`. Neither `mouse` nor any scroll offset appears anywhere in `src/daemon_protocol.rs`; the daemon has never known whether a child requested mouse reporting and does not learn it here. So `PROTOCOL_VERSION` stays at `7`, there is no same-wire/different-meaning break to version, and this is a **patch** bump. The rule 12 cross-version test remains worth running pre-PR as confirmation, not as a decision.

## Success Criteria

- `docs/keyboard-shortcuts.md` states the per-agent reality, and a user reading it can predict which of their agents will scroll and which will not, before trying.
- No published doc claims that pane scrolling works uniformly across agents.
- Attempting a scroll on a pane with nothing to scroll produces a visible, self-clearing explanation instead of silence — on the dashboard and on the orchestrator pane, by wheel and by key.
- The notice never consumes the keystroke that dismisses it: a character typed into a `PaneInput` pane while the notice is up reaches the agent.
- The notice does not appear on a freshly spawned pane that simply has not produced output yet, and does not appear on a pane whose scroll landed.
- No agent name appears in the trigger condition.
- `scan_mouse_mode` detects `ESC[?1000;1002;1006h`, honours a disable that follows an enable in the same chunk, and sees a sequence split across two PTY reads — each pinned by a unit test, where today the function has none.
- A claude pane, which emits all four mouse modes, still forwards the wheel to the agent in `PaneInput` after M3, and still scrolls the deck's own scrollback in command mode.
- `cargo test-fast` green per task; `cargo test-e2e` green pre-PR.

## Milestones

- [x] **M1 — Docs tell the truth about per-agent scrolling.** The mouse/scrolling preamble in `docs/keyboard-shortcuts.md` and its `### Scrolling back through a pane` section now state the app-managed versus terminal-managed distinction, that a terminal-managed agent leaves the deck nothing to scroll by wheel or by key in any mode, and why scrolling up in a plain terminal appears to work — the last of those under a new `#### How far back you can scroll depends on the agent` subsection that the other two link to. `docs/workspace-modes.md` carried the same uniform claim in "Reading a Pane in Command Mode" and is corrected alongside it. Keybinding tables, action names, remappability and the `Ctrl+PageUp`/`Ctrl+PageDown` note are all retained — this adds honesty, it does not delete reference material.
- [x] **M2 — The deck says so on screen instead of no-opping silently.** A failed scroll now overlays the pane with `SCROLL_NOTICE_TEXT` — one centred reversed line in the command banner's own idiom, through the same `draw_centred_banner_line`, degrading to a short form on a pane too narrow for the sentence and omitted below that. ## Risks and Mitigations

- **M3 and M2 are coupled, and getting M3 wrong reproduces the exact symptom this PRD exists to explain.** `scan_mouse_mode` derives `mouse_mode_enabled`, which is the precise input to the branch M2 reacts to. An agent that enabled tracking via the combined `ESC[?1000;1002;1006h` form is mis-derived as *not* mouse-enabled, the deck wrongly takes the scrollback branch, and it produces **this same "locked" symptom for an agent that would otherwise have worked** — and, worse after M2 ships, an on-screen notice explaining it. The corrected wording softens that second half without removing it: the notice no longer asserts a rendering model the agent does not have, but "this pane has no scrollback to move through" is still a true sentence that makes the deck's own mis-derivation read as a property of the pane, which is exactly the misdirection that makes such a bug expensive to find. claude emits all four modes and is therefore the agent most exposed. *Mitigation*: land M3's unit tests before or with M2's trigger, and pin the claude-shaped case (all four modes, combined and separate forms) explicitly rather than only the codex-shaped one.
- **`deck.log` has no scroll or mouse instrumentation at all.** None of this was diagnosable from artifacts; it needed a captured session replayed through the parser at four heights plus a control. The same absence will make the *next* report of this shape equally expensive, and it makes an M3 mis-derivation in the field invisible. *Mitigation*: recorded here as a known gap rather than fixed in this PRD (see Out of Scope); if M3 turns out to need field evidence, a single debug line at the point `mouse_mode` flips is the cheapest possible addition and is where to start.
- **A notice that fires when it should not is worse than silence.** The "substantial output" half of the trigger is what separates a mature zero-depth pane from a pane one second after spawn, and it is a heuristic. Too eager and every fresh pane tells its user there is nothing to scroll a moment before there is; too lazy and the codex pane the user is actually swiping at stays silent. *Mitigation*: pin both edges in the `mode/scroll` family — the fresh-pane negative case as well as the empty-buffer positive one — so a later tuning of the threshold cannot quietly lose either.
- **A pane's mouse flag outlives the attach session that derived it, so a replacement child can inherit it.** Each attach-stream session gets a fresh `MouseModeScanner`, but the pane's `mouse_mode` `AtomicBool` lives on the pane — so an agent that dies and is respawned under the same pane (PRD #92 F9's `clear=true` respawn) starts life with its predecessor's answer, and could be sent wheel reports it never requested. *Mitigation*: `run_pane_io_task` clears the flag on a **replacement** reattach only, decided by `reattach_replaces_the_child` comparing the daemon-side agent id it held against the one the lookup returned. A blanket clear-on-reattach was rejected: an ordinary same-PTY reconnect whose snapshot replay does not re-emit DECSET would stop the wheel working on a live claude pane, which trades a rare injection for a common regression. The residual exposure is deliberate and narrow — if a replacement ever reused its predecessor's agent id, the stale flag would survive, and the rule preserves rather than clears whenever it cannot tell (an empty previous id), because preserving is the direction that cannot inject.
- **M1's forward reference to M2 can go stale.** M1 ships first and tells users the deck says so on screen; M2's wording is not written yet. *Mitigation*: M1 keeps that reference light and promises no specific banner text, and M2 revisits `docs/keyboard-shortcuts.md` if its wording needs it.
- **Users may read M1 as the deck getting worse.** Nothing about behaviour changes in M1; only the documentation stops overpromising. Someone who had not yet noticed that their codex pane does not scroll will learn it from the docs. *Mitigation*: the docs say plainly why, and point at the upstream requirement, rather than leaving it as an unexplained limitation.

## Open Questions

- **Is `1004h`-only worth naming as its own signal?** Focus reporting without any mouse mode is, on the evidence here, a strong hint of a terminal-managed agent. It is deliberately *not* the M2 trigger — the Decision above detects the condition, not a mode fingerprint — but it may be a useful corroborating signal if the output heuristic proves hard to tune.
- **Should the DECRST rule follow xterm rather than vt100?** Genuinely open, with vt100 shipped as the default and both sides argued in the Decision above — the one shape they disagree on, the reason vt100 was implemented, and the reason xterm is arguably the better model for a forwarding decision. Deliberately carried in the PR description rather than in a follow-up issue, so the reviewer decides it rather than inheriting it.
