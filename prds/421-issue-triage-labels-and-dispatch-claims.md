## Problem Statement

Two separate gaps, both stemming from the same fact: **the deck reads GitHub and never writes to it.** Its entire `gh` surface today is **four** read-only invocations. Three are on the dispatch path — `repo clone` (`src/issue_dispatch_run.rs:531`), `issue list` (`:647`), `pr list` (`:655`) — and the fourth is in the `worktree list|reclaim` CLI verb: `pr list --head <branch> --state all --repo <slug> --json state,headRefName` (`src/worktree_reclaim.rs:417-431`), which is how that verb establishes a PR's merged state, deliberately *"via `gh`, never git ancestry"* (`src/worktree_reclaim.rs:4`). There is no write of any kind, anywhere in `src/`. (An earlier revision of this line counted three and omitted the reclaim verb. The **conclusion** is unchanged — none of the four writes — but the inventory is the premise the whole document rests on, so it is worth being exact: a provably incomplete inventory invites doubt about a conclusion that is in fact correct.)

**Gap 1 — nothing is triaged.** Issues carry no priority and no size. Of ~110 open issues, the large majority carry no labels at all; #421 itself was unlabelled when this PRD was written. The existing label vocabulary (`bug`, `enhancement`, `documentation`, `PRD`, …) describes *kind*, never *urgency* or *cost*, so there is no way to answer "what should be picked up next" without reading every issue. **`manual-review` is *not* a leftover** — an earlier revision of this line called it "referenced nowhere in the repo", and that is false: `renovate.json` applies it in **four** package rules (`:63`, `:96`, `:110`, `:116`) — 0.x minor cargo bumps, the workflow toolchain pins, the deliberate exact pins (`crossterm`, `futures-util`, `insta`), and every major bump. It is live vocabulary on exactly the PRs nobody watches closely, so **nothing in Phase 1 may delete it**; the earlier wording read as a premise for cleanup and acting on it would have broken Renovate's labelling silently.

**Gap 2 — dispatched work is invisible on GitHub until a PR exists.** When an `issue_dispatch` task puts an agent on an issue, it leaves no mark on the issue. `dispatch_decision` (`src/issue_dispatch.rs:277`) gates on two signals, both inferred side-effects:

1. the per-issue worktree exists on disk, or
2. an open PR's head branch is `agent/issue-<n>`.

Neither is visible to a human scanning the issue list, and neither is checkable by a *second* deck before it starts work. PRD #120 deliberately chose the head-branch check over parsing `Closes #n` (`src/issue_dispatch.rs:159-162`), so the deck never writes an issue↔PR link either. The result is a blind window between dispatch and the first PR — which, for a long-running or abandoned agent, is the entire lifetime of the work. Two decks pointed at the same repo will both dispatch the same issue; today that only surfaces later, when the second push collides on the shared `agent/issue-<n>` branch.

### Why the triage classifier runs locally

CI cannot do it: the repo's Actions secrets are exactly `HOMEBREW_TAP_TOKEN`, `RELEASE_TOKEN`, `SCOOP_BUCKET_TOKEN`, and workflow `secrets.*` references add only `GITHUB_TOKEN`. There is no LLM credential in CI and no intent to add one. The deck already spawns agents on a cron with `gh` on `PATH`, so the classifier belongs there.

## Solution Overview

Three phases, deliberately ordered so the zero-code win lands first and the riskiest change lands last behind a kill switch.

**Phase 1 — triage labels, no app code.** A repo skill carries the vocabulary and the uncertainty rule; an ordinary `[[scheduled_tasks]]` entry invokes it on a cron. This needs nothing from the application: a plain scheduled task already delivers a prompt to an agent that inherits the daemon's `PATH` and `gh` auth, and `docs/scheduled-tasks.md` already documents the prompt-invokes-a-skill pattern (`prompt = "/prd-full {{issue_number}}"`).

**Phase 2 — a visible claim, display-only.** On successful dispatch, mark the issue as claimed with the deck-owned label **`agent-deck/claimed`**. **M2.0 is decided** (2026-08-17; see Open Question 4) and the two candidates it weighed are recorded below for the reasoning trail, not as a live choice:

- **Assignment** (`gh issue edit <n> --add-assignee @me`) is GitHub's first-class "someone is on this" — it renders in the issue list, is filterable, needs no new vocabulary in any repo, and closes the loop on the project's own `query = "is:open no:assignee"` advanced-filter example. **Rejected.** Its cost is that it is a *shared identity*: it cannot be attributed to the deck, cannot be re-stamped without a destructive step, and cannot be released without risking a human's own self-assignment. Three P1s traced to that one cause.
- **A deck-owned label**, freely re-stampable and destroying no human signal — **but only where the name is genuinely the deck's own**. **Chosen, with the amendment that resolves the gap that had blocked it**: the bare name `in-progress` is *not* the deck's own, so nothing could tell a deck claim from a repo's own workflow label at release time. A **namespaced** name is deck-created by construction, which makes the question unaskable rather than unanswered. The remaining cost — per-repo vocabulary, since `--add-label` fails where the label is absent — is real and is paid on the dispatch path (see "Provisioning the gating label"), but creating `agent-deck/claimed` in someone's repo cannot clobber vocabulary they were using, which creating `in-progress` might.

**The claim is not released on close (M2.2). Expiry clears it**: the worktree signal vacates on tab close and a label signal never does, and #422's rule — derive the verdict, never trust a flag to have been cleared — points the same way. So the TTL is the clearing mechanism, not a backstop for one. **Best-effort throughout: a failure never fails a dispatch, but per M3.6 it is never invisible either.**

**Phase 3 — the claim becomes a third `dispatch_decision` signal**, so a *second* deck will not start work a *first* deck already began — and, symmetrically, so the first deck is never blocked by its own abandoned claim (Success Criterion 7, and "The claim must not poison the deck's own next dispatch"). The two halves are the same milestone: a gate that cannot tell an own claim from a foreign one delivers neither.

### Architecture: why Phase 3 derives rather than maintains

A claim the deck *maintains* rots. The only production site that reclaims a dispatched worktree is the `StopAgent` handler (`src/daemon_protocol.rs:1501-1510`), gated on `take_worktree` against a registry that is **wiped on daemon restart** (`src/issue_dispatch_run.rs:75`). So a maintained claim is orphaned whenever the daemon restarts before the tab closes, whenever `remove_worktree` fails (it is best-effort and only warns, `:225-229`), whenever the daemon is killed by a stray signal (a known recurring event here — #428, #272), and whenever the user follows the documented manual path: *"Run `git worktree remove` (or reopen and close the tab) to release a slot manually"* (`docs/scheduled-tasks.md`). An orphaned claim that also *gates* dispatch silently suppresses that issue on every machine, forever.

**"Only" is exact, and worth defending, because `take_worktree` has two call sites.** The second is on the spawn-failure path (`src/issue_dispatch_run.rs:453`) and it is **not** a reclamation site: it drops the registry entry alone and expressly leaves the directory on disk — *"the next fire's worktree-exists idempotency signal reclaims the issue"* — so it erases the deck's *memory* of a worktree while deliberately preserving the on-disk fact that gates re-dispatch. A reader grepping `take_worktree` finds two hits and has to work out why only one counts, which is reason enough to say so here.

Phase 3 therefore follows #422's rule — **derive the verdict from live GitHub state at decision time; never trust a flag to have been cleared.** Concretely, a claim marker alone is not a claim. A claim is *a fresh marker plus no evidence the work is dead* — and, where the marker is the deciding deck's **own**, the absence of its worktree **is** that evidence, which is the whole of Success Criterion 7 and is set out under "The claim must not poison the deck's own next dispatch":

- **Claim age comes from GitHub, not from deck-local state.** `GET /repos/{owner}/{repo}/issues/{n}/events` returns each event's `created_at` (verified against this repo; assignment events additionally carry `assignee`). The age of the most recent `assigned` event — or, under the label candidate, the most recent `labeled` event — is therefore computable with no local bookkeeping, which is exactly what makes it survive a daemon restart, a machine swap, or a `~/.config` wipe.
- **A claim older than a configurable TTL is stale and does not gate.** The issue is dispatched anyway and the claim's clock must move forward — **by re-writing the claim record, not by re-stamping the label; the next bullet records how that answer was reached and why the re-stamp was abandoned.** The intent is self-healing by construction: the worst case is one duplicate dispatch after the TTL, never a permanently wedged issue. **This is the design's answer to [#482](https://github.com/vfarcic/dot-agent-deck/issues/482)**, which records that nothing in PR #471 ever removes an `in-progress` label, so a discarded dispatch strands its issue permanently. Of #482's three options — un-claim on tab close, expiry, or leave it manual — **this PRD chooses expiry**, and Success Criterion 4 states it as a requirement.
- **How the claim gets re-stamped was the open design problem of this phase, and M2.0 settled it (2026-08-17).** The chain that got it there is kept in full, because the decision is only defensible against it — three Greptile P1s on PR #464 landed on it in succession, each one exposed by the fix for the previous:
  1. A bare `--add-assignee @me` refreshes nothing. GitHub's assignee API is idempotent: adding an already-present assignee is a no-op emitting **no new `assigned` event**. The derived age stays pinned, the claim reads stale forever, and gating silently collapses from the first TTL expiry — failing *open*, with no signal.
  2. Releasing the claim is destructive. `--remove-assignee @me` cannot tell the deck's claim from the user's own, because they are the same GitHub identity — so an unconditional release on tab close deletes a human's self-assignment. Recorded in full under Phase 2 below, since that is where the release call lives.
  3. So re-stamp with an explicit **unassign-then-reassign** pair, which does emit a fresh event. But every write on the claim path is best-effort by design, so a successful unassign followed by a failed reassign leaves the issue **fully unassigned** — reintroducing finding 2's destructive case through a different door. The pair is also non-atomic even when both calls succeed: between them the issue reads unclaimed, and a concurrent deck can dispatch into that window.

  **All three trace to one root cause, already named in Risks: assignment is a shared GitHub identity, not deck-owned vocabulary.** It cannot be re-stamped without a destructive step, and it cannot be attributed to the deck. That is structural, not a bug to patch — which is why this bullet records the problem rather than pretending a third patch settles it. **It is also the substance of M2.0's decision**: two of the three findings simply do not arise under the label candidate.

  **RESOLVED at M2.0 (2026-08-17): the first candidate wins, with a namespaced label name.** The three candidates are kept below because the reasoning is what makes the choice defensible, but the decision is made — see Open Question 4.

  **And then the re-stamp itself was dropped, which is the fourth finding on this mechanism and the one that ends it.** M2.0 initially kept remove-then-add, accepting its non-atomicity on the grounds that a namespaced label makes an interruption lose the deck's *own* claim rather than a human's signal. Greptile then landed two more P1s in immediate succession: M3.3(b) could not be stated satisfiably, because under remove-then-add an interruption *does* lose the claim; and the re-stamp's `--remove-label` flatly contradicts M2.2's prohibition on every removal path. **Four findings on one mechanism is the same evidence bb46b32 acted on earlier in this document's history** — it is evidence about the mechanism, not about the patches — so this is not a fourth patch.

  **The clock moves to the claim record.** Success Criterion 7 already requires a per-issue record naming task and host, written once and **edited** rather than appended. An edit moves its `updated_at`. So freshness derives from the record, the label is written once and never touched again, and every finding in this family dissolves at once: there is no re-stamp, so nothing to interrupt; no removal, so M2.2's prohibition becomes absolute and grep-checkable; and the idempotent-add behaviour that produced the *first* P1 stops mattering, because the label event is only a floor. It costs nothing new — the record was already mandatory — and it is truer to "derive, don't maintain" than the mechanism it replaces. **This refinement was made while closing out review on PR #464 and is the one part of M2.0 the maintainers did not explicitly choose**; it changes the freshness *carrier* only, leaving the label, the TTL, the kill switch and the no-release policy exactly as decided. Overrule it by naming a different carrier, not by restoring the remove-then-add pair.

  Candidate resolutions, **decided at M2.0, before Phase 2 is built** (not, as an earlier revision of this document had it, before Phase 3):
  - ✅ **CHOSEN — a deck-owned label instead of assignment** for the *gating* claim, named **`agent-deck/claimed`**. `labeled` events carry timestamps just as `assigned` events do, so the TTL still derives from GitHub. The re-stamp this bullet originally implied — remove-then-add — was **subsequently dropped altogether** (see the note above): the clock lives on the claim record, so the label is written once and never removed. The gap that had held this candidate back, that it destroys nothing a human owns *only where the name is the deck's own*, is what the namespace closes: ownership becomes true by construction instead of something the design has to establish at release time. Its one cost — the label must exist in every dispatched repo, since `--add-label` fails where it is absent — is **real, and is paid on the dispatch path**, not dissolved by Phase 1 as an earlier revision of this bullet claimed. See "Provisioning the gating label" below.
  - ❌ **Not chosen — never refresh.** Anchor freshness to something that moves on its own — recent commits on `agent/issue-<n>`, or PR activity — so no re-stamp is ever needed. Truest to "derive, don't maintain", and it removes every destructive call. **Known gap: the dispatch → first-commit window.** A freshly dispatched issue has no branch activity yet, so the claim reads stale immediately and the mechanism provides nothing exactly when it is most needed. That window needs an explicit bound in the design (a grace period anchored to branch creation, say) rather than an assumption that agents commit quickly.
  - ❌ **Not chosen — split the jobs.** Keep assignment as a write-only human-visible marker that is never removed (Phase 2, no destructive call at all) and gate on the two signals that already exist — worktree presence and an open PR on `agent/issue-<n>`. This is not a deferral: it is the minimal answer, and it is what the original analysis of #421 recommended before cross-machine gating was brought into scope. It de-risks Phase 2 immediately and costs Phase 3's cross-machine coordination, which has never been observed to be needed here.

  Note that **M3.3 must pin the destructive-write property whichever candidate wins**, so that a later change cannot quietly reintroduce one. With the clock on the claim record there is no re-stamp to interrupt, so the property is stated as a total absence — no code path removes any label from any issue — which is both stronger and cheaper to check than the interrupted-re-stamp test earlier revisions required. M3.3(b) states it that way. An earlier revision of this note required the interrupted-re-stamp form unconditionally, which under "Never refresh" and "Split the jobs" could only have been satisfied by building the destructive path the milestone exists to forbid.

  **M3.1 must also confirm the idempotent-assign behaviour empirically** whichever resolution wins — it was asserted rather than measured when this PRD was first written, which is how finding 1 got in.
- **The open-PR signal still wins.** An open PR on `agent/issue-<n>` means real work exists regardless of claim age.

This is what makes the phase safe, and it is why **M3.3 is the load-bearing milestone**: if a stale claim can wedge an issue, the phase is a regression however well the rest works.

#### Provisioning the gating label

**A fourth Greptile P1 on PR #464 landed on the label candidate itself: nothing in this PRD ever creates `in-progress` in a dispatch target.** The finding is valid, and it is the same failure shape as finding 1 — a gate that silently stops gating — arriving through the candidate that was supposed to fix it. Recorded here rather than patched into the bullet above, because the answer changes *where* the cost lands.

**Phase 1 cannot provision it, and the earlier claim that it "dissolves the cost" was wrong on two counts.** First, `in-progress` is not in Phase 1's vocabulary: In Scope and M1.1 list `priority-*`, `size-*` and `needs-triage`, and nothing else. Second — the part that survives even if the label is added to that list — **Phase 1 offers no ordering guarantee over Phase 3.** The triage schedule is a hand-written `[[scheduled_tasks]]` entry naming one repo in its prompt, configured independently of every `issue_dispatch` task's `repo`. A repo can therefore enter the dispatch queue having never been triaged, and nothing detects it. Both halves are measurable today: `vfarcic/dot-agent-deck` carries no `in-progress` label, and `vfarcic/dot-ai` — the target `docs/scheduled-tasks.md` uses for its own `issue_dispatch` example — carries neither `in-progress` nor any of the seven triage labels.

**So provisioning belongs on the dispatch path**: once per run, before any issue's claim is attempted, and **unconditional** — never gated on whether triage is enabled, because the claim never is.

**M2.0's namespace simplifies this materially, and that is one of the arguments that won it.** An earlier revision required `gh label create` **without** `--force`, so that a repo already carrying its own `in-progress` kept its colour and description instead of having them rewritten on every fire (up to 96×/day on a `*/15` cron) — and, because a no-`--force` create *fails* once the label exists, which is the steady state from the second run onward, the implementation then had to recognise `gh`'s already-exists rejection and treat it as success by matching CLI prose (`label with name "<name>" already exists`), with no status code or JSON to branch on and a textual match that can drift on a `gh` upgrade. **`agent-deck/claimed` removes the whole apparatus**: no repo owns that name, so there is nothing to protect, `--force` is safe, and converging colour and description onto the deck's own values is correct for it exactly as it is for the triage vocabulary. The fragile textual match disappears with it — which is worth more than the keystrokes, since it was the one piece of this design that could fail silently on a dependency upgrade.

**The triage vocabulary and the gating label are now provisioned the same way, and the asymmetry that used to separate them is gone.** Both are the deck's own vocabulary, so `--force` is right for both. The earlier rule split them because the claim label was `in-progress`, a name a repo may already use for its own workflow; the namespace removes that case. **One caution survives the change and belongs to the triage set alone**: `priority-high` and `size-high` are *not* namespaced and are common enough names that a repo may already own them, so force-writing them can still rewrite a repo's colours. That is a live question for M1.1, which in this design does not have the deck create the triage vocabulary at all — so it only bites if M1.1 decides otherwise. **PR #471 force-writes all seven and exempts only the claim label**, which is the inverse of where the caution actually applies.

**When the claim write fails anyway, it must be reported, not logged.** Best-effort is right — a claim failure must never fail a dispatch, which genuinely succeeded — but "best-effort" was never meant to mean invisible. A `tracing::warn!` reaches a sink nobody watching the deck is looking at, so the exact case this PRD exists to prevent (a read-only token; a repo the user cannot label) presents as a run of clean successful dispatches while every claim silently no-ops and a second deck duplicates all of the work. **A failed claim needs its own notification, distinguishable from both a successful dispatch and a failed one.** That obligation holds for the assignee candidate too — it is the general rule that finding 1 should have produced and did not. Note [#486](https://github.com/vfarcic/dot-agent-deck/issues/486): in #471 the label write and the claim comment each raise their own `IssueClaimFailed`, so a read-only token yields two notifications per issue reporting one cause. Whichever mechanism wins, the notification should be **once per issue naming both outcomes**, not once per write.

**Also relevant to where provisioning is called from:** [#483](https://github.com/vfarcic/dot-agent-deck/issues/483) records that #471's `ensure_claim_label` runs on *every* fire including fires that dispatch nothing — 96 `gh label create` calls a day against a repo that may have had nothing to dispatch. "Once per run, before any claim write" should therefore be read as **just-in-time**: once per run in which a claim is actually about to be written, not once per fire unconditionally. That keeps the ordering guarantee while dropping the call entirely on "nothing new" fires.

**PR #471 has already implemented most of this**, and reached it the same way, through its own review rather than by design: `ensure_claim_label` (unconditional, once per run, create-without-`--force`, already-exists treated as success), `NotifyEvent::IssueClaimFailed` for the write failure, and `scheduler/dispatch/020`, an e2e test that dispatches against a repo seeded with *no* labels and asserts the claim genuinely succeeded rather than merely being attempted. Its `gh` stub was tightened to hard-error on an unknown label name, mirroring real `gh`'s client-side name-to-ID resolution — which is also the empirical confirmation that `--add-label` fails where the label is absent, a claim this PRD had until now only asserted.

#### The claim must not poison the deck's own next dispatch

**A claim that gates is a claim that can gate the claimant.** This is not a hypothetical: it is the shape PR #471 shipped, it has already fired against the live fixture, and it is the reason `scheduler/dispatch/013` — the test CLAUDE.md rule 4 names as the reference every future major feature is told to mirror — cannot pass twice. Neither reviewer of this document raised it, and this document did not specify against it, so it is recorded here as the *specification* defect it is rather than as one PR's bug.

**Verified against the code rather than taken on report** (PR #471 at `fd24678e`, `tests/e2e_issue_dispatch_real.rs` and the fixture on `main`, 2026-08-17):

1. `claim_issue` writes the claim after a successful spawn (`src/issue_dispatch_run.rs:562`, `:584-593`).
2. Nothing in `src/` ever removes it — `git grep 'remove-label\|remove_label' -- src/` at that head returns **nothing**.
3. `dispatch_decision(worktree_exists, open_pr_with_matching_head, label_in_progress)` skips on **any** of the three (`src/issue_dispatch.rs:282-292`), so the claim alone is sufficient to gate.
4. `dispatch_013`'s schedule filters on `label = "agent-dispatch-test"` with `max_per_run = 1` (`tests/e2e_issue_dispatch_real.rs:107-121`), so **issue #1 is the only issue the test ever enumerates** — there is no second issue for a fire to fall through to.
5. Therefore the first successful run claims the only issue the test has, and every run after it enumerates that issue, reads its own claim, and skips — no agents register, and the test dies on its 120s roles precondition with `Records: []`, long before reaching the assertion it exists to make.
6. The fixture confirms it: `vfarcic/dot-agent-deck-tests#1` carries `in-progress` **right now**, alongside two claim comments, with nothing in any codebase that will ever remove them.

**A TTL does not rescue this, and it is important to see why, because the TTL is this document's headline answer to [#482](https://github.com/vfarcic/dot-agent-deck/issues/482).** Open Question 1 proposes 24h, chosen so *"a legitimately slow agent is not preempted"*. Two consecutive runs of the real-fixture test are minutes apart. Any TTL long enough to protect a slow agent is, by construction, orders of magnitude longer than the interval it would have to bridge — so expiry answers #482's *permanent* wedge and answers nothing at all about the deck re-dispatching after its own work ended. The two requirements are genuinely different and a single number cannot serve both.

**A test teardown does not rescue it either, and must never be allowed to look as though it does.** #471's mitigation is test-side: `clear_stale_claim` reads the label and `gh issue edit --remove-label`s it as a precondition, degrading to `skip_unless!` when the token cannot write. That fixes the symptom on one machine and hides it on every other. Measured, not assumed: `gh api repos/vfarcic/dot-agent-deck-tests/collaborators/prageethw/permission` returns **`read`**, so the second maintainer cannot clear the label at all — and a `skip_unless!` skip is counted as a pass by nextest, so on his machine the reference test would report green while never running. That is precisely the hazard Success Criterion 5 already names, arriving through the fix for a different one.

**So the specification must state the property the mechanism has to have, not just the mechanism.** Success Criterion 7 states it, and it gates M2.0: *a claim must never gate a dispatch that the deciding deck would otherwise perform against work of its own that no longer exists, and restoring that must happen on the production path with no write by any other actor.*

**What satisfying it costs, and the decision this document makes.** Freshness alone cannot distinguish "my own dead run, five minutes ago" from "another deck's live run, five minutes ago" — they are the same age and the same marker. Corroboration alone cannot either: a freshly dispatched agent has pushed no branch and opened no PR, which is the dispatch → first-commit window already recorded against the "Never refresh" candidate. **The distinction the deciding deck can actually make is between a claim that is its own and a claim that is not**, because for its own it holds the one signal nobody else has: whether the worktree it would have created still exists. That signal is already `dispatch_decision`'s first argument, already local, already free, and already checked first. The rule that follows is one line of truth table: **a claim whose claimant is this deck, with no worktree and no open PR behind it, is dead and does not gate** — dispatch, and re-claim. A claim by anyone else keeps gating, TTL-bounded exactly as Success Criterion 4 requires, so Gap 2's cross-machine protection is untouched.

**That forces a claimant record, so this document moves one In Scope** (see In Scope, and the corresponding reversal under Out of Scope). "Own" has to be derivable from GitHub, because after a workspace wipe — the test's situation, and a new machine's — the deck remembers nothing, and M3.1 forbids it remembering anything. Neither carrier already on the table supplies it: the `labeled`/`assigned` **actor** is the maintainer's own GitHub account, which separates two decks on one account not at all, and the **label name** identifies the deck-as-software, never the instance. A per-issue record naming **task name plus host** does, and it survives every restart, which `mint_orchestration_id()` (see "The identity question") does not. This is *not* a reversal of that section: what it rejects is a per-process nonce as an *orchestration instance* identity; task-plus-host is neither per-process nor per-orchestration. It does close that section's third objection, which was that the default `ScheduledTask.name` seed `Issues <owner>/<repo>` is byte-identical across machines — the host discriminates it. Where two daemons on one host share one task name the rule mistakes another claim for its own; the cost is one duplicate dispatch, which is failing *open* in the one direction this design already tolerates everywhere else.

**The three objections that put the claim comment Out of Scope are answered by writing it once per issue rather than once per fire.** It notified every watcher and reset the `actions/stale` clock because #471 *appends* a new comment on every claim; GitHub does not notify on an **edit**, and a comment that already exists cannot reset the stale clock a second time. The third objection — that editing needs comment-id bookkeeping — dissolves under M3.1's own rule: the deck **lists** the issue's comments and finds its own by a marker string in the body, which is derivation, not storage. Cost is one extra read per claim and a bounded one comment per issue, against the two-and-counting the fixture carries today.

**This is a design decision made on the author's behalf and is straightforward to overrule** — but overruling it means supplying a different answer to Success Criterion 7, not deleting the criterion. Any candidate that leaves the reference test dependent on a maintainer-only fixture write is not admissible, whatever else it gets right.

## Scope

### In Scope

- A `triage-issues` repo skill carrying the label vocabulary and the uncertainty rule, invocable as `/triage-issues <owner/name>`.
- Creating the label vocabulary: `priority-high|medium|low`, `size-high|medium|low`, `needs-triage`. **The separator is provisionally hyphenated** — see the header note and Open Question 4.
- A documented `[[scheduled_tasks]]` recipe that invokes the skill on a cron.
- **A dispatch claim written after a successful spawn**, best-effort at every step, carried by the deck-owned label **`agent-deck/claimed`** (M2.0, decided 2026-08-17 — see Open Question 4). **It is never cleared by the deck** (M2.2): expiry is the only clearing mechanism. Combined with the claim record carrying the freshness clock (M3.1), **the design contains no `--remove-label` call at all** — neither to release nor to refresh.
- Claim-aware `dispatch_decision`: a third signal, TTL-bounded, derived from live GitHub state — **and never sufficient on its own to gate the deciding deck's own dead work** (Success Criterion 7, and "The claim must not poison the deck's own next dispatch").
- **A per-issue claimant record on GitHub, naming the task and the host**, written once per claim and **edited rather than appended** on a re-claim, discoverable by **any** deck via a fixed marker string in its body (task and host are fields inside it, not part of the marker — a foreign deck must be able to find the record in order to age it, per M3.1). It carries two jobs: the freshness clock (its `updated_at`) and the own-vs-foreign distinction (its fields). This is what lets a deck recognise its own claim after a workspace wipe, which is what Success Criterion 7 requires and what nothing else on the table supplies. It reverses the Out-of-Scope exclusion below rather than sitting beside it.
- **If the claim is a label**, provisioning it in the dispatch target: just-in-time, on the dispatch path, before any claim write, unconditional and never gated on triage. Phase 1 cannot carry this — see "Provisioning the gating label".
- **A notification for a failed claim write**, distinct from a successful dispatch and from a failed one, and raised **once per issue naming both outcomes** rather than once per failed write (#486). Best-effort must not mean invisible; a claim that silently no-ops is a gate that silently stops gating.
- **Distinguishable skip reasons.** When dispatch skips an issue, the reason is reported and the causes are distinguishable from one another — worktree exists, open PR, claimed (with the claimant where one can be found), concurrent-creator race. This is what makes a stray third-party claim *diagnosable* rather than looking identical to nothing happening, and it is the natural mitigation for the silent-no-op risk this document already names. PR #471 implements it as a `SkipReason` enum with four variants, a renderer, and a changed `NotifyEvent::IssueDispatchSkipped`; it had no home in either scope list until this revision.
- A kill switch so claim-gating can be turned off in config without a rebuild.
- Test coverage across both tiers, including the `gh` stub arms that make the writes observable.
- Docs: `docs/scheduled-tasks.md` (the claim, the TTL, the recipe), `CONTRIBUTING.md` (the label vocabulary).
- A `changelog.d/421.<type>.md` fragment covering the cross-build behaviour skew Phase 3 introduces. (The repo's fragment convention is `<issue>.<type>.md` — `feature`, `bugfix`, `breaking`, `misc`; see `changelog.d/`.)

- ~~**Sticky claim comments.** Assignment was chosen over a comment; a comment notifies every watcher, resets the `actions/stale` clock (`.github/workflows/stale.yml`), and needs comment-id bookkeeping to edit rather than append. Revisit only if assignment proves insufficient.~~ **Reversed, and now In Scope as the claimant record.** The stated trigger — *"revisit only if assignment proves insufficient"* — has been met twice over: assignment is insufficient on the write side (three P1s, Architecture) and a claimant record turns out to be the only thing that satisfies Success Criterion 7. All three original costs were costs of *appending once per fire*, not of the comment itself: an **edited** comment does not re-notify watchers, cannot reset the stale clock a second time, and needs no id bookkeeping because the deck lists the issue's comments and matches its own marker — derivation, which M3.1 permits. PR #471 already posts such a comment, but appends a new one per claim; the correction is the write discipline, not the mechanism. See "The claim must not poison the deck's own next dispatch".
- ~~**An `in-progress` label.** Superseded by assignment.~~ **Reopened, then decided against this document's original position.** The exclusion rested on the label needing to exist in every dispatched repo (`--add-label` fails where it is absent), a cost this document originally believed Phase 1 dissolved and now records as real and paid on the dispatch path. Three P1 findings against the assignee mechanism reversed it. **M2.0 chose a deck-owned label — but not this one**: the gating claim is `agent-deck/claimed`, and the bare name `in-progress` stays excluded, because a name a repo may already own is exactly what made the label candidate unsafe on the release path. Whether the deck should nonetheless *read* a repo's own `in-progress` as a third-party claim is a separate question, still open at Open Question 2.

Recognising "this deck's own claim" is a strictly weaker requirement than identifying an orchestration instance, and it is the only one Success Criterion 7 needs.
- **A CLI verb for claiming or releasing an issue by hand.** Deliberately excluded for now, but the gap is real and is recorded as Open Question 5 rather than left silent — the claim is defined as a *cross-actor* signal on the read side, and no actor other than the scheduler can currently write or release one.
- **Non-GitHub forges.** Dispatch stays `gh`-only.
- **Retro-triage of the existing backlog by hand.** The first scheduled run handles it.

## Technical Approach

### Phase 1 — triage skill and schedule

The skill lives at `.claude/skills/triage-issues/SKILL.md` with `user-invocable: true`. It states the vocabulary, and the rule that decides the whole phase's usefulness: **when not confident, apply `needs-triage` and leave priority unset.** A wrong priority is worse than an absent one, because it is indistinguishable from a considered one.

The schedule is a plain task, not an `issue_dispatch` one — `issue_dispatch` would clone the repo and build a worktree per issue, which is heavy machinery for a job that only reads issue text:

```toml
[[scheduled_tasks]]
name = "triage-issues"
cron = "0 8 * * MON-FRI"
working_dir = "~/code/dot-agent-deck"   # must be a checkout of THIS repo
command = "claude"                       # required for a plain task
prompt = "/triage-issues vfarcic/dot-agent-deck"
enabled = true
```

Two constraints that are easy to get wrong, and belong in the docs: `working_dir` must be a checkout of this repo because `.claude/skills/` is project-scoped — that is how the agent discovers the skill; it is *not* the repo being triaged, which is an argument in the prompt. And `--command` is mandatory for a plain task (`src/schedule_cli.rs:70`: *"a scheduled task needs an agent command … to act on its prompt"*); only `issue_dispatch` tasks may omit it.

**Durability gap worth stating.** The three artifacts live in three places and only one is versioned: the skill is in git; the schedule is in `~/.config/dot-agent-deck/schedules.toml` on whichever machine runs the daemon; the labels are GitHub repo settings. The schedule vanishes with the machine. Documenting the recipe in `docs/scheduled-tasks.md` is the mitigation — the recipe is reproducible even though the instance is not. **This is also why Success Criterion 1 is scoped to repos a triage schedule actually covers**: nothing in this design enumerates repos or detects one that has never been triaged.

### Phase 2 — the visible claim

**M2.0 decided the mechanism before anything here is built, and that sequencing was the point.** An earlier revision of this document asserted the assignee mechanism flatly in In Scope while simultaneously calling the label the leading candidate and sequencing the decision into Phase 3; an implementer following that order would have built M2.1, M2.2, M2.4 and M2.5 against assignment, reached M3.3, been told to settle the mechanism first, followed this document's own recommendation to the label, and discarded all of it. That inversion is the defect M2.0 existed to remove, and it did: the milestones below are now written against a settled mechanism rather than a neutral placeholder.

A pure argv builder in `src/issue_dispatch.rs` (unit-testable, alongside `issue_list_argv` / `pr_list_for_issue_argv`, carrying the same `--` end-of-options guard), plus `claim_issue` in `src/issue_dispatch_run.rs` modelled on `ensure_worktrees_excluded`'s never-fatal discipline. **There is no `release_issue`, and no label-removal helper of any kind.** M2.2 chose expiry over release-on-close and M3.1 puts the freshness clock on the claim record rather than on a re-stamped label, so neither decision leaves a `--remove-label` call to write. Adding one for symmetry would put a destructive operation back in the tree with nothing calling it — the shape both decisions were chosen to prevent. The same holds for the Key Files table.

Write ordering is the one thing that must not be got wrong: **claim only after `spawn` returns `Ok`** (`src/issue_dispatch_run.rs:448`), so a failed dispatch never leaves a claim. Nothing goes into the close path (`src/daemon_protocol.rs:1501-1510`) beside `remove_worktree` — the claim is not cleared there or anywhere else.

**Release must not be unconditional** (Greptile P1, PR #464). Under the **assignee** mechanism, `--add-assignee @me` is idempotent and harmless, but `--remove-assignee @me` is destructive and **cannot tell the deck's own claim from the user's**, because they are the same GitHub identity. So a human who assigns themselves to an issue, which the deck then dispatches and later closes, has their own signal silently deleted. The same applies to two decks sharing one GitHub account: the first tab to close unassigns while the second is still working, and the issue reads as free.

This is the sharp edge of choosing assignment over a deck-owned label, and it lands in Phase 2 — the phase otherwise characterised as safe because it is display-only. Two candidate mitigations, to be decided in M2.2:

- **Release only a claim the deck can prove it created.** Local provenance is exactly what [#425](https://github.com/vfarcic/dot-agent-deck/issues/425)'s worktree ownership marker provides, so this converges with work already proposed rather than inventing a second mechanism. Preferred if #425 lands first.
- **Do not release at all**; let the TTL expire the claim. Consistent with "derive, don't maintain", and it removes the destructive call entirely. Cost: the claim lingers for up to one TTL after the tab closes, so the issue looks busier than it is.

**Under the label mechanism the release analysis changes — but less than two earlier revisions of this document claimed, and what remained was unresolved until M2.0 renamed the label (see the resolution below).** The first said a deck-owned label is *attributable*, so "release only a claim the deck can prove it created" stops needing #425's ownership marker at all, the label's own `labeled` event plus the claim record identifying the claimant. The second added the precondition — safe *provided* the label is genuinely deck-owned vocabulary — without asking whether anything can check it. **Nothing can** (Greptile P1 on PR #464, raised against the milestone that relied on it), for three reasons that compound:

- **Provisioning deliberately discards the distinction.** `gh label create` runs **without** `--force` and its already-exists rejection is *treated as success* (see "Provisioning the gating label"). That is what protects a repo's own label — and it is the same stroke that throws away the one signal which would have recorded whether the deck created the vocabulary or merely found it.
- **M3.1 forbids persisting it.** "No deck-local claim bookkeeping anywhere" is the rule that lets the TTL survive a restart, so there is no store in which a per-repo ownership fact could live.
- **The `labeled` event does not carry it.** The actor is whichever account ran `gh` — the maintainer's own. On the instance question it therefore separates the deck from a human no better than `assigned` does, which was the root defect of the assignee candidate.

**So the close path cannot establish the precondition it would have to satisfy, and release-on-close under a *bare* `in-progress` is not established as safe.** The failure is the same shape as the one it was supposed to escape: removing a marker the deck cannot prove it created destroys repository state exactly as an unconditional `--remove-assignee @me` destroys a human's assignment.

**RESOLVED at M2.0 (2026-08-17) by the second resolution below — the namespace.** The three compounding reasons above are all reasons the deck cannot *derive* ownership of a shared name. `agent-deck/claimed` makes ownership true by construction, so none of them has anything left to bite on: provisioning may discard the created-vs-found distinction because there is no repo-owned instance to confuse it with, M3.1's ban on persistence costs nothing because nothing needs persisting, and the `labeled` actor being the maintainer's own account stops mattering because the *name* carries the attribution the actor never could. **This does not by itself make the deck release on close** — M2.2 chooses expiry over release-on-close on separate grounds (see below) — but it converts release from *unsafe* to merely *unnecessary*, which is the difference between a hazard and an option. Candidate resolutions, **decided at M2.0 alongside the mechanism itself**:

- ✅ **ALSO CHOSEN, for M2.2 — do not release**; let the TTL expire the claim. Needs no ownership signal, and was the only option safe as designed *before* the namespace. It stays the choice afterwards on its own merits rather than for want of an alternative: the worktree signal vacates on tab close and a label signal never does, so making the label depend on a close handler firing is exactly the "trust a flag to have been cleared" that #422 forbids and that this whole section exists to avoid. Cost is the one already recorded above — the claim lingers for up to one TTL after the tab closes, so an issue reads busier than it is.
- ✅ **CHOSEN, for M2.0 — give the claim its own deck-owned name: `agent-deck/claimed`.** The entire difficulty is that `in-progress` is vocabulary a repo may already own; a name unmistakably the deck's is deck-created *by construction*, so release destroys nothing and no signal has to be derived or stored. It also separates the two sides cleanly, which the single-name design conflates: the deck **writes and releases** only its own marker, and whether it should *additionally* **gate** on a repo's own `in-progress` is a separate read-side question left open at Open Question 2. This is the same move as the "Split the jobs" candidate above, applied to vocabulary rather than to signals, and it is the one resolution that follows directly from this document's own diagnosis — that the assignee mechanism failed because it was *shared identity, not deck-owned vocabulary*. Cost: a name that must be provisioned in every dispatch target, and a divergence from #471, which claims with `in-progress` itself.
- ❌ **Not chosen — derive ownership from GitHub's own timeline** — compare the most recent `labeled` event for `in-progress` against the deck's claim record, and release only where the deck's own write is the one that put it there. The claim record here is the **comment on the issue** naming task, host and timestamp, which lives on GitHub, so reading it back is derivation and not the local bookkeeping M3.1 forbids. Truest to "derive, don't maintain" at the cost of a timeline read per close. **Weakest of the four, and it must not be chosen on the strength of the phrase "derive from the timeline" alone**: the actor field cannot carry the distinction, so ordering is doing all the work, and ordering has at least one hole — a human who removes and re-adds `in-progress` after the deck claimed produces a `labeled` event later than the claim comment, and the deck then releases a label it does not own. Requires the same empirical confirmation M3.1 demands, and a decision on whether that hole is acceptable, before anything is built on it.
- ❌ **Not chosen — record ownership explicitly** — #425's marker, or a provisioning-time probe that lists labels before creating. Both are bookkeeping, which M3.1 rules out; choosing either means amending M3.1 deliberately rather than bending it quietly. The namespace makes the question moot rather than answering it, which is strictly better.

The TTL remains required under every option, because release-on-close cannot fire when the daemon dies with the tab open — and under the chosen "do not release" it is not a backstop but the *only* clearing mechanism, which is why Success Criterion 4 states it as a requirement. **It is still not sufficient**: Success Criterion 7 is a separate obligation the TTL cannot discharge at any value, and it survives this decision untouched.

Best-effort means a missing permission, a read-only repo, or a `gh` failure never fails the dispatch, which genuinely succeeded. It does **not** mean the failure is invisible: per M3.6 it raises its own notification rather than only a WARN. Phase 2's claim is decorative, so a swallowed failure costs little there — but the same code path carries Phase 3's gate, where a silent no-op is a gate that has stopped gating, and this is exactly why Phase 3 cannot simply trust the claim to exist.

### Phase 3 — claim-aware dispatch

`dispatch_decision` gains a third parameter. The pure function stays pure — the caller resolves claim state and passes a verdict in, so the truth table remains exhaustively unit-testable. Evaluation order matters for the same reason the existing short-circuit does (`src/issue_dispatch_run.rs:361-371`): the worktree signal is local and free, so it is checked first and a `gh` failure on a locally-claimed issue can never turn a clean skip into a spurious failure.

The kill switch is a config knob on `IssueDispatchConfig` (`src/config.rs:586`) — claim-gating off by default until the TTL behaviour has been observed in the wild, so the feature cannot wedge a backlog while it is being trusted.

**Cross-version behaviour (CLAUDE.md rule 12).** This touches the daemon, so the check is triggered. The TUI↔daemon wire is **unchanged** — no `PROTOCOL_VERSION` bump. Verified: `NotifyEvent` does not appear in `src/daemon_protocol.rs`, and PR #471 — which adds a `NotifyEvent` variant and changes another — does not touch that file at all, so the notification surface required by M3.6 is genuinely off-wire. But an old daemon dispatches without claiming while a new daemon reads claims and skips, so a mixed fleet disagrees about what is in flight. That skew is a compatibility note, not a wire break: it needs a `changelog.d/421.<type>.md` fragment and the rule 12 cross-version manual run (isolating `DOT_AGENT_DECK_LOG` along with the sockets and `HOME`, per rule 12's third bullet).

### The identity question (issue §2), and why it is out of scope

Issue #421 proposes recording *which* orchestrator claimed an issue, via `mint_orchestration_id()`. Verified against the code, that mechanism cannot do the job:

1. **It is not durable.** `src/agent_pty.rs:381-382`: *"The token deliberately does NOT need to be reproducible across restarts"* — a per-process nonce plus a counter. So the test it is meant to enable ("is this my own earlier claim, or someone else's?") fails after any daemon restart, which is the same restart that already wipes `WorktreeRegistry`.
2. **It is not always minted.** `mint_orchestration_id()` is called only in the `SpawnTarget::Orchestration` branch (`src/spawn.rs:499`). A repo with no `[[orchestrations]]` block dispatches as a single-agent card and has no instance identity at all.
3. **The stated fallback is not unique where it matters.** `ScheduledTask.name` is "unique per daemon" (`src/config.rs:609`), but the default seed is `Issues <owner>/<repo>` (`src/issue_dispatch.rs:45-47`) — so two machines on default config produce byte-identical claimants, which is precisely the collision the proposal exists to solve.

The TTL design sidesteps **the orchestration-instance** question entirely: it never needs to know *which orchestration* claimed an issue, only how long ago. **It does not sidestep the claimant question**, and an earlier revision of this paragraph overstated that by saying the design never needs to know *who* claimed an issue at all. Success Criterion 7 needs exactly one bit — *is this claim mine?* — and the three objections above do not reach it: **task name plus host** is not minted per process, is minted on every dispatch path rather than only the orchestration branch, and is not byte-identical across machines the way the bare default seed `Issues <owner>/<repo>` is. That is a strictly weaker identity than issue #421 proposed and is the only part of it this design adopts. If genuine per-instance identity is wanted later, #425's worktree ownership marker remains the right home — local, durable, and free of GitHub-write risk.

Issue #421's closing observation is correct and worth acting on separately: **#156**'s premise ("there is no unique per-instance ID") was superseded by PRD #140. That issue's problem statement should be updated regardless of this PRD.

## Success Criteria

1. **Every open issue in a repo covered by a triage schedule** carries either a `priority-*` + `size-*` pair or `needs-triage`, within one cron period of being opened, maintained without anyone remembering to do it. *Scoped deliberately:* nothing in this design enumerates repos or detects a repo that has never been triaged (see "Provisioning the gating label"), the schedule names one repo in its prompt, and nothing runs between cron fires — so "every open issue everywhere" is not a criterion this design can meet, and an earlier revision that claimed it was over-scoped.
2. An issue being worked on by a dispatched agent is identifiable from the GitHub issue list alone, before any PR exists.
3. A dispatch failure never leaves a claim behind.
4. **A stale claim never permanently wedges an issue** — after the TTL, the issue is dispatchable again with no manual intervention, on a machine that has never seen the original claim. **This is the criterion that answers [#482](https://github.com/vfarcic/dot-agent-deck/issues/482)**; a design in which nothing ever clears a claim fails it by construction.
5. `tests/e2e_issue_dispatch_real.rs` — which is `scheduler/dispatch/013`, the reference harness CLAUDE.md rule 4 points every future major feature at — **runs and stays green across consecutive runs against the live fixture, for a maintainer whose token has only read access to the fixture repo** (measured: `prageethw` holds `read` on `vfarcic/dot-agent-deck-tests`). A test that skips rather than runs is counted as passing by nextest and proves nothing, so "green" here means *ran*. **Restoring the fixture to its original state is a separate, best-effort obligation** and must never be load-bearing for the criterion above — see Criterion 7 and M2.4. An earlier revision conflated the two and required a teardown that "works, or fails loudly" for a maintainer who cannot write to the fixture, which is unsatisfiable by construction: it can only fail loudly, so it specified the reference test to be permanently red on the second maintainer's machine.
6. Claim-gating can be disabled in config without a rebuild.
7. **The claim is self-restoring on the production path.** After a dispatch whose work no longer exists — the daemon was killed, the worktree was removed by hand, the tab was closed, the workspace was wiped — a later fire against the same issue **dispatches again with no write to the repository by any actor except the deck itself**, and with no manual `gh` incantation, no maintainer-only fixture cleanup, and no test teardown in the path. *The TTL does not satisfy this and was never able to*: Criterion 4's expiry is chosen long enough not to preempt a slow agent (Open Question 1 proposes 24h) while this criterion has to hold at the cadence a test re-runs, minutes apart — the two are different requirements and one number cannot meet both. A design in which the deck's own abandoned claim gates its own next fire fails this criterion by construction, whatever it does about #482. See "The claim must not poison the deck's own next dispatch" for why this is stated as a criterion rather than left to the implementation, and for the verified evidence that PR #471 fails it today.

### Phase 3: Claim-aware dispatch

**Phase 3's freshness mechanism is this document's highest-risk design, and the review record says so quantitatively.** **Eight** P1 findings have now landed on it, across two different carriers: the idempotent add that refreshed nothing; the destructive release; the interrupted re-stamp; the re-stamp's contradiction with the no-removal rule; a foreign claim with no readable clock; a live claim that expires because its owner skips before refreshing it; a live claim that expires because the *schedule* is sparser than the TTL (M3.1); and a dead foreign record that blocks the deck's own recovery for as long as it is retained, which is forever (M3.2). Each was exposed by the fix for the one before. (The count is worth stating correctly: an earlier revision of this sentence read "Five" while listing six, which understated the very evidence the paragraph exists to present.) The through-line is not any particular carrier — it is that **maintaining a liveness lease across machines, over an API with no compare-and-swap, is genuinely hard**, and a document cannot fully validate one. So treat the specification below as the *current best answer* rather than a settled protocol: **M3.1 must validate it empirically — against two real decks, not one — before Phase 3 is built**, and a finding at that point is expected rather than a surprise. The failure direction to prefer is stated once and holds throughout: a claim that wrongly reads stale costs one duplicate dispatch and self-heals; a claim that wrongly reads live wedges an issue. When in doubt, fail toward the duplicate.

**These milestones are written against a GitHub-derived clock, and the carrier is the claim record — not the `labeled` event.** Freshness is the **`updated_at` of the deck's claim record on the issue**, floored by the `created_at` of the most recent `labeled` event for `agent-deck/claimed` (which bounds when the claim can first have existed, and covers the case where a best-effort record write failed). Both are read from GitHub at decision time, so nothing local has to survive a restart, a machine swap or a `~/.config` wipe. An earlier revision had to hedge every "age" and "event" below, because two of M2.0's candidates ("Never refresh", "Split the jobs") produce no event at all; that hedge is discharged, and the wording below means what it says. The invariant it serves is still worth stating mechanism-independently, because it is what any future change has to preserve: **a claim no longer backed by live work must stop gating, and whatever establishes that must be observable to a second machine.**

- [ ] **M3.1** — Claim state derived from live GitHub at decision time: the `agent-deck/claimed` label, plus the claim's age taken from the **claim record's `updated_at`**, floored by the most recent `labeled` event's `created_at`. **The owning deck refreshes its own record while the work is alive.** A deck that is already working an issue *skips* it on later fires — the worktree signal short-circuits first, by design — so nothing on the normal path would ever advance its record, and a genuinely live claim would expire at the TTL and be dispatched over by a second deck. So the worktree-exists skip path also **refreshes the claim record**, and that is exactly the right trigger: the worktree still existing *is* the liveness fact, and refreshing on it publishes a local fact to every other machine. To keep this off the 96-fires-a-day path (#483), refresh only when the record is already older than **half the TTL** — bounding it to roughly two writes per TTL per in-flight issue. That bound is what makes the refresh cheap; it is *not* on its own what keeps a live claim from expiring, which is the requirement stated next. **The TTL must exceed the longest gap between refresh opportunities, and nothing in this design yet makes that true** (Greptile P1, PR #464, 2026-08-18). The refresh only fires when the *task* fires, so the cadence at which a live claim republishes its liveness is bounded below by that task's own `cron` — a value nothing here inspects. The two are configured independently: the TTL lands on `IssueDispatchConfig` (`src/config.rs:586`) while the cron lives on the `[[scheduled_tasks]]` entry. **The repo's own documented example collides with the proposed TTL**, so this is a default-config failure rather than a pathological one: `docs/scheduled-tasks.md` seeds `issue_dispatch` with `cron = "0 9 * * MON-FRI"`, which puts consecutive fires 24h apart on weekdays and **72h apart across a weekend**, against Open Question 1's proposed **24h** TTL. A claim written Friday 09:00 is not refreshable again until Monday 09:00 and expires Saturday 09:00 — so for two days a live claim reads stale to every other deck, which is exactly the duplicate dispatch the gate exists to prevent. **This is not discharged by "fail toward the duplicate", and the difference matters.** That preference resolves *ambiguity* — where the deck cannot tell a live claim from a dead one, prefer the recoverable duplicate over the wedge. Here there is no ambiguity: the work is alive, the deck holding it knows so, and the liveness fact (its worktree) is present locally the entire time. The mechanism simply never gets the chance to publish it. Reading the tie-break as cover for that would turn a tolerance for irreducible uncertainty into a licence for a mechanism that discards information it already holds — and it would concede Gap 2's cross-machine protection precisely on the sparse schedules that are the documented default. **So make the relationship a checked constraint rather than an assumption.** Both values are known to the daemon at config-load time, so require **TTL ≥ 2× the longest gap between consecutive fires** of the task, computed from the cron rather than assumed, and surface a violation alongside M3.4's kill-switch validation. The factor of two is what the half-TTL refresh threshold above needs in order to land one refresh inside every TTL: a refresh becomes eligible at age TTL/2, so a fire must occur within that TTL/2-wide window, which a gap wider than TTL/2 cannot guarantee. Where the gap cannot be computed, or the constraint cannot be met, claim-gating should stay **off** for that task rather than gate on a clock its schedule cannot keep current — which is also the honest default given M3.4 ships gating off anyway. **The residual is daemon downtime, and that part is genuinely irreducible**: a machine asleep or a daemon killed for longer than the TTL cannot refresh whatever the cron says. *There* the tie-break applies on its own terms — the claim lapses, a second deck may duplicate, and the duplicate self-heals. The distinction worth keeping is that downtime is unbounded and unknowable while a cron interval is neither, so only the second is a design hole and only the second gets a constraint. **A claim record is discoverable by any deck, not only by the one that wrote it** — it carries a fixed marker string identifying it as a dot-agent-deck claim record, with task and host as *fields inside* it. That is what makes a foreign claim ageable: the deciding deck reads every claim record on the issue and ages **each record on its own `updated_at`**, never an aggregate across them. Aggregating was this milestone's first answer and it is wrong in a way that took a further P1 to surface (Greptile, PR #464, 2026-08-18): a single `max(updated_at)` lets *any* fresh record hold *every* other record open, so one deck's recent claim makes another deck's long-dead one read live — including the deciding deck's own. M3.2 states the rule that consumes this, and the failure it removes. A marker only the writing deck could match would leave a foreign claim aged from the one-time `labeled` event, which never refreshes, so a live foreign claim would expire at the TTL while its owner was still working — duplicate dispatch, the exact failure the gate exists to prevent. **No deck-local claim bookkeeping anywhere** — the record lives on the issue, so reading it back is derivation, not storage. Refreshing the clock is an **edit of that record**: idempotent, atomic, non-destructive, and it needs no label write at all. **Empirically confirm two things before building on this**: that editing the record does move `updated_at`, and that a redundant `--add-label` of a label already present emits no new `labeled` event (the assumption the first P1 was made of — it was asserted rather than measured when this document was written). The second only matters for the floor; the design no longer depends on it.
- [ ] **M3.2** — Third signal wired into `dispatch_decision` with an exhaustive truth table; short-circuit order preserved so a `gh` failure cannot turn a local skip into a failure — noting that the worktree short-circuit now also carries M3.1's refresh, which must be best-effort and must never turn a clean local skip into a failure either. Skip causes are distinguishable and reported, per In Scope. **The claim must not be sufficient on its own to gate** (Success Criterion 7). Precisely: **the claim gates if and only if at least one claim record on the issue is *individually* live**, where a record is live when either it is **foreign** (it names another task or another host) and its own `updated_at` is within the TTL, or it is the deciding deck's **own** and a worktree or an open PR on `agent/issue-<n>` still backs it. Own records are judged on that direct evidence rather than on the clock, because for its own claim the deck holds the authoritative liveness fact and does not need to infer one; foreign records are judged on the clock, because it is the only evidence available. Note the own-live branch is behaviourally vacuous on the deciding deck — a worktree or open PR short-circuits to Skip before the claim is ever consulted — so in practice **an own record never gates**, which is exactly what Success Criterion 7 asks for. **This replaces an earlier "every, not any" formulation that was wrong, and the fix is the quantifier plus per-record ageing together** (Greptile P1, PR #464, 2026-08-18; independently reached by @prageethw on the same PR, whose (b) option this adopts). That rule dispatched only when *every* record on the issue was the deck's own and dead, on the reasoning that a second deck's record may be live. The reasoning was right and the rule did not implement it: because nothing in this design ever *removes* a claim record (M2.2 does not release, and M3.1 edits rather than deletes), a foreign record outlives the work it described **indefinitely**. So a stranger's long-dead record permanently fails the "every" test and the deciding deck can never recover its own abandoned work — it skips until the *aggregate* clock ages out, which is up to a full TTL and, under the aggregate-max reading M3.1 previously specified, potentially never, since any one fresh record held every other record open. That contradicts Success Criterion 7 as literally stated ("a later fire dispatches again with no write to the repository in between" — no TTL wait appears in it) and M3.3(c) would not have caught it, because it exercises the single-deck case only. **Ageing each record on its own clock is what makes the quantifier safe**: "any record individually live" now gates on a *live* foreign claim while a dead foreign record — its own `updated_at` past the TTL — stops gating anything, so the deck recovers its own work without ever dispatching over another deck's live work. Gap 2's cross-machine protection is untouched, since a genuinely live foreign claim is precisely the case that still gates. **One trade-off survives deliberately, and it is the conservative direction.** Between the moment a foreign deck's work dies and the moment its record ages past the TTL, that record still gates — so the deciding deck waits out the remainder of the foreign TTL before recovering its own work in that specific overlap. Identity ambiguity is treated more conservatively than time ambiguity on purpose: the deck can prove its *own* work is dead but can only ever infer that a stranger's is, and dispatching over another deck's live agent is the one failure this gate exists to prevent. The bound is one TTL and it clears itself with no write, so it is a delay rather than a wedge — which is what separates it from the defect above. The truth table is not exhaustive without the own-vs-foreign axis, so this milestone adds a dimension rather than a row, and it must be enumerated per record rather than per issue: the states that used to be one are `own+dead → Dispatch`, `foreign+stale → Dispatch`, and `foreign+fresh → Skip`.
- [ ] **M3.3** — **Stale claims self-heal.** Three tests, all required.

  **(a) The TTL releases the gate, and the clock then moves.** A claim older than the TTL does not gate and the issue dispatches — proven by a test that dispatches against a pre-aged claim written by no local daemon, **and asserts the derived age advanced afterwards**. The second assertion is the load-bearing one: without it the test passes against the broken design in which the age stays pinned forever and gating silently collapses at the first expiry. Under the chosen carrier the advance comes from editing the claim record, so the test reads the record's `updated_at`, not the `labeled` event. Do not satisfy it by weakening what "advanced" means.

  **(b) No label removal exists anywhere.** With the clock on the claim record, the design contains **no `--remove-label` call at all** — not to release (M2.2 chose expiry), and not to re-stamp (an edit refreshes the record without touching the label). So this test is an absence assertion, and a total one: **no code path removes any label from any issue, ever.** That is stronger than the interrupted-re-stamp test earlier revisions specified, and much easier to hold — a grep-level invariant rather than a behaviour under partial failure. It is also what makes the earlier hazard un-reintroducible rather than merely mitigated: there is no half-completed pair to interrupt, no window in which the issue reads unclaimed, and no possibility of removing a label the deck does not own.

  **(c) Success Criterion 7 — the deck re-dispatches its own dead work.** Dispatch an issue, let the claim be written, destroy the local work exactly as the real failures do (drop the workspace — no `StopAgent`, no release path, nothing a close handler could tidy up), fire again against the same issue with **no write to the repository in between**, and assert the issue **dispatches**. This test fails against PR #471's design *and* against M2.0's decision as written, which is precisely why it exists: the namespace fixed release and the TTL fixed the permanent wedge, and neither touched this. It is the unit-tier and stub-tier guard that stops `scheduler/dispatch/013` from being the place the defect is rediscovered, at real-agent cost. **It must cover the multi-record case, not only the single-deck one** — the gap the eighth P1 came in through (Greptile, PR #464, 2026-08-18): with a dead *foreign* claim record also present on the issue, the deck must still re-dispatch its own dead work, and with a **live** foreign record present it must still skip. A single-deck fixture passes against the aggregate-ageing design M3.2 has now replaced, so the two-record arms are the ones that actually pin the rule. Both are cheap at the stub tier, where claim records are fixtures rather than real decks.

  *M3.3 is the milestone the phase is only safe with — treat it as a hard gate, not a nice-to-have.*
- [ ] **M3.4** — Kill switch on `IssueDispatchConfig`, defaulting to off, with validation and a test. **It disables *gating*, not the *write*** (decided with M2.0, @prageethw's refinement): a claim that is written and visible but not yet trusted is the safe intermediate state to ship in, and it is the only configuration in which TTL behaviour can be watched against real data before anything starts suppressing dispatches. A switch that disabled the write too would make the observation period prove nothing.
- [ ] **M3.5** — Cross-version manual run per rule 12 (old daemon + new TUI, isolated `DOT_AGENT_DECK_LOG`/sockets/`HOME`), plus the `changelog.d/421.<type>.md` fragment recording the mixed-fleet skew.
- [ ] **M3.6** — **The claim can never silently no-op.** Two halves, both required, and both landing with the phase that first *writes* the claim — which M2.0 makes Phase 2, so this milestone is tracked there as M2.6. (a) The label is provisioned on the dispatch path — just-in-time, before any claim write, unconditional and never gated on triage (#483). **`--force` is fine and the already-exists textual match is no longer needed**: `agent-deck/claimed` is nobody else's vocabulary, so there is nothing to protect from being converged onto the deck's own colour and description (see "Provisioning the gating label" — an earlier revision required create-without-`--force` because the name was `in-progress`). (b) A failed claim write raises its own notification, distinguishable from a successful dispatch and from a failed one, **once per issue naming both outcomes** rather than once per failed write (#486); `tracing::warn!` alone does not satisfy this. **Required test properties:** dispatch against a repo carrying **no** labels at all; assert the claim genuinely *succeeded*, not merely that it was attempted — which is what a test written against the broken design also passes; and the `gh` stub must hard-error on an unknown label name, mirroring real `gh`'s client-side name-to-ID resolution. PR #471's `scheduler/dispatch/020` already satisfies all three and should be reused if #471 lands; the properties are stated here so that a replacement can be written from this document if it does not.

## Open Questions

1. **What TTL?** Long enough that a legitimately slow agent is not preempted, short enough that a dead claim clears within a working day. A starting proposal is 24h, revisited after M1.4-style observation. **This knob answers #482 and nothing else.** It is explicitly *not* what makes the deck's own re-dispatch work — that is M3.2's own-claim rule, per Success Criterion 7 — and expecting one number to serve both is what produced the self-poisoning design. The two pull in opposite directions: protecting a slow agent wants hours, un-blocking a re-run wants minutes, and there is no value that does both. **A third constraint now binds the number from below, and it is the one most likely to be missed** (M3.1): the TTL must also be at least twice the longest gap between consecutive fires of the task, or a live claim expires before its owner can republish it. The 24h proposal fails this against the documented `cron = "0 9 * * MON-FRI"` example, whose weekend gap is 72h — so 24h is not merely a guess to be revisited, it is **already known to be wrong for the schedule the docs recommend**. Whatever value is chosen must be justified against the cron it will run under, which is why M3.1 asks for the relationship to be validated rather than for a better constant.
2. **Should the deck reconcile claims it did not write?** **Narrowed by M2.0, and now a genuine either-way choice rather than a hazard.** The deck writes and gates on `agent-deck/claimed`, which nobody else uses — so the question is no longer "can we avoid honouring a foreign claim" but "should we *additionally* read a repo's own `in-progress` (or an assignee) as a third-party claim?" In favour: a human working an issue by hand is a real claim, and dispatching over it is the collision Gap 2 exists to prevent. Against: it re-imports the starvation the namespace just removed — any automation using that common name would exclude issues indefinitely — and it is unbounded, since the deck cannot enumerate what a repo means by its own vocabulary. **Recommendation: do not read foreign markers by default; if it is wanted, make it an explicit per-task config listing which labels to honour, so the vocabulary is stated rather than guessed.** Not decided here. The **write** side is not a question but a defect, tracked in Risks and settled by M2.2: the deck removes no marker at all.
3. **Does triage want a `sort` interaction with dispatch?** Once priorities exist, `query = "is:open label:priority-high sort:created-asc"` becomes the natural dispatch filter. PRD #222 already proposes a first-class `sort` field; these two should be aligned rather than solved twice. *Note the separator matters here beyond cosmetics:* under the colon form the qualifier needs quoting (`label:"priority:high"`) to parse unambiguously, so the hyphenated form is the safer input to #222's design.
4. **How does this PRD reconcile with [PR #471](https://github.com/vfarcic/dot-agent-deck/pull/471)?** — **ANSWERED 2026-08-17.** #471 ("claim dispatched issues and triage them on dispatch", by @prageethw, open, ~2.5k lines) implemented Phases 1–2 of this issue independently, and its design differed from this PRD on almost every axis. It was never a merge conflict — the two touch disjoint files — but a design disagreement, and it was settled the way this question asked for: **by the two maintainers, not by whichever PR merged second.**

   **The decision.** The gating claim is a **deck-owned, namespaced label — `agent-deck/claimed`** — with a **TTL** and a **kill switch that disables gating while leaving the write**. The deck **never releases** it; expiry is the only clearing mechanism (M2.2). This is the answer the comparison below pointed at all along — *"a deck-owned label with a TTL and a kill switch is neither PR's current design and is very likely the right answer"* — plus the one amendment that made it work: @prageethw's observation that this document's objection to the label candidate was an objection to the **name** `in-progress`, not to the **mechanism**. Namespacing makes release non-destructive, makes just-in-time provisioning safe, restores attribution, and moots the separator question for this label. Recorded in full at M2.0.

   **What it means for #471.** It **does not merge**. Its shape — a bare `in-progress` label, no TTL, no kill switch — is the one the first Risks row names as this document's central hazard, and `scheduler/dispatch/013` is that hazard already realised. The rework lands as a **fresh PR** citing this document's milestone numbering, rather than as a rewrite of #471: #471 predates this document, its 51 `PRD #421 M<x>.<y>` citations are numbered against an inverted scheme, and repointing them inside a 2537-line rewrite is exactly the error-prone step the citation hazard below describes. A fresh PR never creates the problem (see M4.4). What #471 got right travels with it — `ensure_claim_label`, `NotifyEvent::IssueClaimFailed`, `SkipReason`, and `scheduler/dispatch/020` are all required here and should be carried over rather than rebuilt.

   **What the decision does *not* settle.** **Success Criterion 7 survives it intact.** The namespace fixes *release*; the TTL fixes #482's *permanent* wedge; neither stops the deck's own dead claim gating its own next fire, because an own claim and a foreign one are the same label. That is M3.2's own-vs-foreign axis and M3.3(c)'s test, and it is the one thing that keeps `scheduler/dispatch/013` red until it is built. Open Question 2 (whether to *additionally* read foreign markers) is also still open, and is now a free choice rather than a hazard.

   The comparison that produced the decision is kept below, unchanged, because the decision is only defensible against it.

   | Axis | This PRD | PR #471 |
   | --- | --- | --- |
   | Claim mechanism | **`agent-deck/claimed`** (M2.0, decided) | bare `in-progress` label |

   Four of these deserve explicit attention:

   - **#471 ships the shape this PRD names as its central hazard.** The first Risks row says a stale claim wedging an issue permanently is "the reason issue #421's original 'write a label and gate on it' shape was not adopted". #471 is that shape with no TTL and no kill switch, and documents the wedge as intended behaviour: *"subsequent fires keep skipping the issue until someone removes the label."* That is the single substantive disagreement — everything else is vocabulary or packaging. It cuts both ways: #471's label avoids the two P1s that sank the assignee design on the *write* side, while this PRD's TTL is what stops a claim from wedging a backlog. Note that #471 never removes the label, so the release gap recorded above does not arise there — it is created by *this* document's release-on-close option, not by #471. **The two are complementary, not mutually exclusive: a deck-owned label with a TTL and a kill switch is neither PR's current design and is very likely the right answer.**
   - **The third-party-claim row compounds the expiry row, and the composite is the real exposure.** Honoured-regardless-of-applier is defensible on its own; no-expiry is a bounded gap on its own. Together they mean any `in-progress` label from any source starves an issue on every deck until a human intervenes. Read row by row this looks like two mild gaps; it is one sharp one.
   - **#471 adopts two things this PRD had put out of scope, and this PRD has since reopened both — but landed elsewhere on each.** The `in-progress` label: reopened on this document's own evidence, and M2.0 then chose a *namespaced* label rather than that name, so the two designs agree on the mechanism and differ on the name. The sticky claim comment: reopened as the **claimant record** Success Criterion 7 requires, but written **once per issue and edited**, where #471 appends one per claim — which is what makes its version notify every watcher and reset the `actions/stale` clock, the objection that had excluded it.
   - **Triage coverage is a real difference of job, not of quality.** A scheduled skill sweeps the whole backlog of the repos it is pointed at; #471's triage labels only issues a fire dispatches, so it never reaches the backlog no matter how long it runs. Success Criterion 1 belongs to the scheduled-skill design — but note the criterion is scoped to repos a schedule covers, so it is a claim about *coverage within configured repos*, not a claim this design triages the world. The two triage designs could coexist.
   - **The one axis where neither design is right, and this document was the cause.** #471's claim gates its own claimant, which is what has kept `scheduler/dispatch/013` red; but nothing in *this* document ever required otherwise, and its TTL — the thing it holds up as the answer to #482 — cannot supply it at the cadence a test re-runs. So the two designs were not disagreeing on this axis, they were both silent on it. Corrected here as Success Criterion 7 with M3.2/M2.2/M3.3/M2.4 behind it, so the reconciliation has a property to be reconciled *against* rather than one PR's fix to be ported. @prageethw has confirmed the diagnosis independently on this PR and has held the fixture's stale label deliberately, on the grounds that clearing it buys exactly one green run while the code still re-poisons — which is the same conclusion Criterion 7 reaches from the specification side.
   - **On two axes #471 is simply ahead, and this PRD has been corrected to match it: provisioning the gating label, and reporting a failed claim.** #471's `ensure_claim_label` runs once per dispatch run, and `NotifyEvent::IssueClaimFailed` makes a failed claim visible instead of burying it in a log — both reached through #471's own review, and both now required here as M3.6. This is worth noticing beyond the one fix: the axes above read as a design disagreement, but on the question of what happens when a best-effort write *fails*, the implementation had been more careful than the PRD. That is an argument for reconciling the two rather than picking a winner.

   **The milestone-citation hazard, and why it is a milestone (M4.4) rather than a note.** #471's code comments carry **51** `PRD #421 M<x>.<y>` citations, because #471 was developed against a different PRD on the author's fork. They fail in two different ways, and the second is worse:

   - **26 dangle**: `M1.0` (×12), `M2.0` (×10), `M3.0` (×4) do not exist in this document, which runs M1.1–M4.4.
   - **25 resolve to a real milestone that means a different phase**: `M1.2` (×12), `M1.3` (×6), `M1.4` (×3), `M2.1` (×2), `M1.1` (×1), `M2.2` (×1). The two numbering schemes are **inverted** — #471's `M1.x` is the *claim* work (`src/issue_dispatch.rs:295`: "PRD #421 M1.0/M1.1/M1.2 — claim label/comment argv + comment body") while this document's `M1.x` is *Phase 1 triage*; #471's `M2.x` is the *triage vocabulary* (`:444`) while this document's `M2.x` is the claim. So a reader following `// PRD #421 M1.2` on `src/issue_dispatch.rs:123` — the label riding along on the already-made issue-list call — lands on this document's M1.2, "`triage-issues` skill written". Twelve times.

   A dangling citation wastes a reader's time; one that resolves to the wrong thing misinforms them silently. **Merging this PRD converts 25 citations from the first kind into the second**, which is why M4.4 exists and why this document landing does **not** close [#481](https://github.com/vfarcic/dot-agent-deck/issues/481). #481 asks for `prds/421-automatic-issue-labelling.md` — still the path cited at `src/issue_dispatch.rs:392` — and this document is a differently-named file with different content and inverted numbering. The ~47 remaining fork-only citations in #471 (`review C3`, `reviewer F1`, `auditor F8`) are untouched by either option and are #481's own scope.

5. **Can any actor other than the scheduler participate in the claim protocol?** Today, no — and the claim is defined as a **cross-actor** signal on the read side, which makes the asymmetry worth naming. This document's own Gap 2 argues the claim exists so a *second deck* can check it; Success Criterion 4 requires it to work "on a machine that has never seen the original claim"; Open Question 2 asks whether a *human's* claim should be honoured. But nothing offers a human, a skill, or a test harness a way to **write or release** one. In #471 the helpers (`issue_edit_add_label_argv`, `claim_comment_body`, `Claimant`) are `pub` but reachable only from the scheduler path — `ensure_claim_label` is private — and there is no CLI verb; the only new command-line surface is `schedule add --triage`. The cost is already visible: #471's real-agent test had to hand-roll `remove_in_progress_label` and `clear_stale_claim` in `tests/e2e_issue_dispatch_real.rs`, matching a permission error textually to decide whether to skip, which is what produces the self-disabling teardown in the Risks table. Either scope in a `dot-agent-deck issue claim|release <repo> <n>` verb — which also gives #482 a documented manual recovery path better than a raw `gh` incantation — or state deliberately that the protocol is write-only for the scheduler and that every other actor uses `gh` directly. What is not defensible is defining a cross-actor protocol and leaving participation in it undesigned.
