# PRD #421: Issue triage labels, and a dispatch claim the deck writes back to GitHub

**Status**: Not started — **Phases 1–2 overlap an open implementation, [PR #471](https://github.com/vfarcic/dot-agent-deck/pull/471), whose design differs on most axes. Reconcile before building either. See Open Question 4.**
**Priority**: Medium
**Created**: 2026-08-09
**GitHub Issue**: [#421](https://github.com/vfarcic/dot-agent-deck/issues/421)
**Label separator**: **provisionally hyphenated** (`priority-high`, `size-low`) throughout this document, matching the repo's only compound label (`ci-cd`) and PR #471's implementation. The decision is still recorded as open in Open Question 4 — but the form is now written consistently in one style so that flipping it is a single mechanical pass over this document rather than four passages that had silently disagreed.
**Feature flag**: None. Rule 9's trigger is a new *user-visible surface* (pane, field, command, tab, footer, keybinding) and this PRD introduces none — the only new UI-adjacent artifact is a repo skill. The `experimental` flag is also the wrong tool here by rule 9's own terms: it is a **presentation** switch (PRD #139 M3.2, "never branch business logic / daemon protocols / hook handling on the flag"), and every behaviour below is dispatch logic. Phases 2 and 3 are de-risked by being best-effort and by the Phase 3 kill switch, not by a flag. *One qualification added after review:* M3.6(b) requires a **new notification type** for a failed claim write, and a notification is user-visible output. It is still not a pane/field/command/tab/footer/keybinding, and gating it would mean branching dispatch logic on a presentation switch — so the answer does not change, but "introduces no user-visible surface" is a slightly stronger claim than the document can make.

## Problem Statement

Two separate gaps, both stemming from the same fact: **the deck reads GitHub and never writes to it.** Its entire `gh` surface today is three read-only invocations — `repo clone` (`src/issue_dispatch_run.rs:531`), `issue list` (`:647`), `pr list` (`:655`). There is no write of any kind, anywhere in `src/`.

**Gap 1 — nothing is triaged.** Issues carry no priority and no size. Of ~110 open issues, the large majority carry no labels at all; #421 itself was unlabelled when this PRD was written. The existing label vocabulary (`bug`, `enhancement`, `documentation`, `PRD`, …) describes *kind*, never *urgency* or *cost*, so there is no way to answer "what should be picked up next" without reading every issue. `manual-review` exists as a label but is referenced nowhere in the repo — a leftover.

**Gap 2 — dispatched work is invisible on GitHub until a PR exists.** When an `issue_dispatch` task puts an agent on an issue, it leaves no mark on the issue. `dispatch_decision` (`src/issue_dispatch.rs:277`) gates on two signals, both inferred side-effects:

1. the per-issue worktree exists on disk, or
2. an open PR's head branch is `agent/issue-<n>`.

Neither is visible to a human scanning the issue list, and neither is checkable by a *second* deck before it starts work. PRD #120 deliberately chose the head-branch check over parsing `Closes #n` (`src/issue_dispatch.rs:159-162`), so the deck never writes an issue↔PR link either. The result is a blind window between dispatch and the first PR — which, for a long-running or abandoned agent, is the entire lifetime of the work. Two decks pointed at the same repo will both dispatch the same issue; today that only surfaces later, when the second push collides on the shared `agent/issue-<n>` branch.

### Why the triage classifier runs locally

CI cannot do it: the repo's Actions secrets are exactly `HOMEBREW_TAP_TOKEN`, `RELEASE_TOKEN`, `SCOOP_BUCKET_TOKEN`, and workflow `secrets.*` references add only `GITHUB_TOKEN`. There is no LLM credential in CI and no intent to add one. The deck already spawns agents on a cron with `gh` on `PATH`, so the classifier belongs there.

## Solution Overview

Three phases, deliberately ordered so the zero-code win lands first and the riskiest change lands last behind a kill switch.

**Phase 1 — triage labels, no app code.** A repo skill carries the vocabulary and the uncertainty rule; an ordinary `[[scheduled_tasks]]` entry invokes it on a cron. This needs nothing from the application: a plain scheduled task already delivers a prompt to an agent that inherits the daemon's `PATH` and `gh` auth, and `docs/scheduled-tasks.md` already documents the prompt-invokes-a-skill pattern (`prompt = "/prd-full {{issue_number}}"`).

**Phase 2 — a visible claim, display-only.** On successful dispatch, mark the issue as claimed. **Which mechanism carries the claim — GitHub assignment or a deck-owned `in-progress` label — is M2.0's decision, and M2.0 gates the whole of Phase 2** (see "Architecture" and Open Question 4). The two candidates differ in ways that reach every milestone below, which is why the choice is sequenced first rather than deferred into Phase 3:

- **Assignment** (`gh issue edit <n> --add-assignee @me`) is GitHub's first-class "someone is on this" — it renders in the issue list, is filterable, needs no new vocabulary in any repo, and closes the loop on the project's own `query = "is:open no:assignee"` advanced-filter example. Its cost is that it is a *shared identity*: it cannot be attributed to the deck, cannot be re-stamped without a destructive step, and cannot be released without risking a human's own self-assignment.
- **A deck-owned `in-progress` label** is freely re-stampable and destroys no human signal — **but only where the name is genuinely the deck's own, which `in-progress` is not**; a repo may already use it, and nothing in the design can tell at release time. That gap is UNRESOLVED and confined to the *release* path (see "Phase 2 — the visible claim"). Its cost is per-repo vocabulary — `--add-label` fails where the label is absent — which is paid on the dispatch path (see "Provisioning the gating label").

**Whether the claim is ever cleared is a further open decision (M2.2)** — an unconditional release on tab close deletes a human's own self-assignment and is ruled out. **Best-effort throughout: a failure never fails a dispatch, but per M3.6 it is never invisible either.**

**Phase 3 — the claim becomes a third `dispatch_decision` signal**, so a second deck will not start work a first deck already began.

### Architecture: why Phase 3 derives rather than maintains

A claim the deck *maintains* rots. The only production site that reclaims a dispatched worktree is the `StopAgent` handler (`src/daemon_protocol.rs:1501-1510`), gated on `take_worktree` against a registry that is **wiped on daemon restart** (`src/issue_dispatch_run.rs:75`). So a maintained claim is orphaned whenever the daemon restarts before the tab closes, whenever `remove_worktree` fails (it is best-effort and only warns, `:225-229`), whenever the daemon is killed by a stray signal (a known recurring event here — #428, #272), and whenever the user follows the documented manual path: *"Run `git worktree remove` (or reopen and close the tab) to release a slot manually"* (`docs/scheduled-tasks.md`). An orphaned claim that also *gates* dispatch silently suppresses that issue on every machine, forever.

Phase 3 therefore follows #422's rule — **derive the verdict from live GitHub state at decision time; never trust a flag to have been cleared.** Concretely, a claim marker alone is not a claim. A claim is *a fresh marker plus no evidence the work is dead*:

- **Claim age comes from GitHub, not from deck-local state.** `GET /repos/{owner}/{repo}/issues/{n}/events` returns each event's `created_at` (verified against this repo; assignment events additionally carry `assignee`). The age of the most recent `assigned` event — or, under the label candidate, the most recent `labeled` event — is therefore computable with no local bookkeeping, which is exactly what makes it survive a daemon restart, a machine swap, or a `~/.config` wipe.
- **A claim older than a configurable TTL is stale and does not gate.** The issue is dispatched anyway and the claim's clock must move forward — **by a mechanism the next bullet records as unresolved.** The intent is self-healing by construction: the worst case is one duplicate dispatch after the TTL, never a permanently wedged issue. **This is the design's answer to [#482](https://github.com/vfarcic/dot-agent-deck/issues/482)**, which records that nothing in PR #471 ever removes an `in-progress` label, so a discarded dispatch strands its issue permanently. Of #482's three options — un-claim on tab close, expiry, or leave it manual — **this PRD chooses expiry**, and Success Criterion 4 states it as a requirement.
- **How the claim gets re-stamped is UNRESOLVED, and is the open design problem of this phase.** Three Greptile P1s on PR #464 landed on it in succession, each one exposed by the fix for the previous:
  1. A bare `--add-assignee @me` refreshes nothing. GitHub's assignee API is idempotent: adding an already-present assignee is a no-op emitting **no new `assigned` event**. The derived age stays pinned, the claim reads stale forever, and gating silently collapses from the first TTL expiry — failing *open*, with no signal.
  2. Releasing the claim is destructive. `--remove-assignee @me` cannot tell the deck's claim from the user's own, because they are the same GitHub identity — so an unconditional release on tab close deletes a human's self-assignment. Recorded in full under Phase 2 below, since that is where the release call lives.
  3. So re-stamp with an explicit **unassign-then-reassign** pair, which does emit a fresh event. But every write on the claim path is best-effort by design, so a successful unassign followed by a failed reassign leaves the issue **fully unassigned** — reintroducing finding 2's destructive case through a different door. The pair is also non-atomic even when both calls succeed: between them the issue reads unclaimed, and a concurrent deck can dispatch into that window.

  **All three trace to one root cause, already named in Risks: assignment is a shared GitHub identity, not deck-owned vocabulary.** It cannot be re-stamped without a destructive step, and it cannot be attributed to the deck. That is structural, not a bug to patch — which is why this bullet records the problem rather than pretending a third patch settles it. **It is also the substance of M2.0's decision**: two of the three findings simply do not arise under the label candidate.

  Candidate resolutions, **to be decided at M2.0, before Phase 2 is built** (not, as an earlier revision of this document had it, before Phase 3):
  - **A deck-owned `in-progress` label instead of assignment** for the *gating* claim. `labeled` events carry timestamps just as `assigned` events do, so the TTL still derives from GitHub. Remove-then-add is still non-atomic, and it destroys nothing a human owns **only where the label name is the deck's own** — an unresolved gap for `in-progress` specifically, developed under "Phase 2 — the visible claim" and bearing on release, not on gating. This reverses the choice made when the PRD was written; the accumulated evidence favours it, and it remains the leading candidate. Its one cost — the label must exist in every dispatched repo, since `--add-label` fails where it is absent — is **real, and is paid on the dispatch path**, not dissolved by Phase 1 as an earlier revision of this bullet claimed. See "Provisioning the gating label" below.
  - **Never refresh.** Anchor freshness to something that moves on its own — recent commits on `agent/issue-<n>`, or PR activity — so no re-stamp is ever needed. Truest to "derive, don't maintain", and it removes every destructive call. **Known gap: the dispatch → first-commit window.** A freshly dispatched issue has no branch activity yet, so the claim reads stale immediately and the mechanism provides nothing exactly when it is most needed. That window needs an explicit bound in the design (a grace period anchored to branch creation, say) rather than an assumption that agents commit quickly.
  - **Split the jobs.** Keep assignment as a write-only human-visible marker that is never removed (Phase 2, no destructive call at all) and gate on the two signals that already exist — worktree presence and an open PR on `agent/issue-<n>`. This is not a deferral: it is the minimal answer, and it is what the original analysis of #421 recommended before cross-machine gating was brought into scope. It de-risks Phase 2 immediately and costs Phase 3's cross-machine coordination, which has never been observed to be needed here.

  Note that **M3.3 must pin the destructive-write property whichever candidate wins**, so that a later change cannot quietly reintroduce one — as an interrupted-re-stamp test under the candidates that re-stamp, and as an assertion that no re-stamp or release path exists under the ones that do not. M3.3 states both forms. An earlier revision of this note required the interrupted-re-stamp form unconditionally, which under "Never refresh" and "Split the jobs" could only have been satisfied by building the destructive path the milestone exists to forbid.

  **M3.1 must also confirm the idempotent-assign behaviour empirically** whichever resolution wins — it was asserted rather than measured when this PRD was first written, which is how finding 1 got in.
- **The open-PR signal still wins.** An open PR on `agent/issue-<n>` means real work exists regardless of claim age.

This is what makes the phase safe, and it is why **M3.3 is the load-bearing milestone**: if a stale claim can wedge an issue, the phase is a regression however well the rest works.

#### Provisioning the gating label

**A fourth Greptile P1 on PR #464 landed on the label candidate itself: nothing in this PRD ever creates `in-progress` in a dispatch target.** The finding is valid, and it is the same failure shape as finding 1 — a gate that silently stops gating — arriving through the candidate that was supposed to fix it. Recorded here rather than patched into the bullet above, because the answer changes *where* the cost lands.

**Phase 1 cannot provision it, and the earlier claim that it "dissolves the cost" was wrong on two counts.** First, `in-progress` is not in Phase 1's vocabulary: In Scope and M1.1 list `priority-*`, `size-*` and `needs-triage`, and nothing else. Second — the part that survives even if the label is added to that list — **Phase 1 offers no ordering guarantee over Phase 3.** The triage schedule is a hand-written `[[scheduled_tasks]]` entry naming one repo in its prompt, configured independently of every `issue_dispatch` task's `repo`. A repo can therefore enter the dispatch queue having never been triaged, and nothing detects it. Both halves are measurable today: `vfarcic/dot-agent-deck` carries no `in-progress` label, and `vfarcic/dot-ai` — the target `docs/scheduled-tasks.md` uses for its own `issue_dispatch` example — carries neither `in-progress` nor any of the seven triage labels.

**So provisioning belongs on the dispatch path**: once per run, before any issue's claim is attempted, and **unconditional** — never gated on whether triage is enabled, because the claim never is. `gh label create` **without** `--force`, so a repo that already carries its own `in-progress` keeps its colour and description instead of having them rewritten on every fire (up to 96×/day on a `*/15` cron). Without `--force` that call *fails* once the label exists, which is the steady state from the second run onward, so the implementation must recognise `gh`'s already-exists rejection and treat it as success — noting that `gh` reports it as CLI prose (`label with name "<name>" already exists`) with no status code or JSON to branch on, so the match is textual and can drift on a `gh` upgrade. It should drift toward a spurious warning, never toward swallowing a genuine failure.

**The triage vocabulary is provisioned differently from the gating label, and the difference is deliberate.** The seven triage labels are the deck's *own* vocabulary, so repeatedly converging their colour and description onto known values is correct, and `--force` is the right tool for them. The `in-progress` claim label is **not** the deck's own vocabulary — a repo may already use that exact name for its own workflow, and `priority-high` is a common enough name that the same caution is worth weighing there too. **This is a genuine divergence from PR #471** and it is now an axis in Open Question 4's table: #471 creates all seven triage labels *with* `--force` on the dispatch path, and only `claim_label_create_argv` omits it. This PRD's Phase 1 does not have the deck create the triage vocabulary at all — M1.1 is a human or skill job — so the two designs differ both on *who* provisions the triage labels and on *whether* they are force-written. Whichever design wins must state one rule for each of the two label sets rather than leaving L69's reasoning to be read as general.

**When the claim write fails anyway, it must be reported, not logged.** Best-effort is right — a claim failure must never fail a dispatch, which genuinely succeeded — but "best-effort" was never meant to mean invisible. A `tracing::warn!` reaches a sink nobody watching the deck is looking at, so the exact case this PRD exists to prevent (a read-only token; a repo the user cannot label) presents as a run of clean successful dispatches while every claim silently no-ops and a second deck duplicates all of the work. **A failed claim needs its own notification, distinguishable from both a successful dispatch and a failed one.** That obligation holds for the assignee candidate too — it is the general rule that finding 1 should have produced and did not. Note [#486](https://github.com/vfarcic/dot-agent-deck/issues/486): in #471 the label write and the claim comment each raise their own `IssueClaimFailed`, so a read-only token yields two notifications per issue reporting one cause. Whichever mechanism wins, the notification should be **once per issue naming both outcomes**, not once per write.

**Also relevant to where provisioning is called from:** [#483](https://github.com/vfarcic/dot-agent-deck/issues/483) records that #471's `ensure_claim_label` runs on *every* fire including fires that dispatch nothing — 96 `gh label create` calls a day against a repo that may have had nothing to dispatch. "Once per run, before any claim write" should therefore be read as **just-in-time**: once per run in which a claim is actually about to be written, not once per fire unconditionally. That keeps the ordering guarantee while dropping the call entirely on "nothing new" fires.

**PR #471 has already implemented most of this**, and reached it the same way, through its own review rather than by design: `ensure_claim_label` (unconditional, once per run, create-without-`--force`, already-exists treated as success), `NotifyEvent::IssueClaimFailed` for the write failure, and `scheduler/dispatch/020`, an e2e test that dispatches against a repo seeded with *no* labels and asserts the claim genuinely succeeded rather than merely being attempted. Its `gh` stub was tightened to hard-error on an unknown label name, mirroring real `gh`'s client-side name-to-ID resolution — which is also the empirical confirmation that `--add-label` fails where the label is absent, a claim this PRD had until now only asserted.

## Scope

### In Scope

- A `triage-issues` repo skill carrying the label vocabulary and the uncertainty rule, invocable as `/triage-issues <owner/name>`.
- Creating the label vocabulary: `priority-high|medium|low`, `size-high|medium|low`, `needs-triage`. **The separator is provisionally hyphenated** — see the header note and Open Question 4.
- A documented `[[scheduled_tasks]]` recipe that invokes the skill on a cron.
- **A dispatch claim written after a successful spawn**, best-effort at every step. **Which mechanism carries it — assignment or a deck-owned `in-progress` label — is M2.0's decision and gates Phase 2**; the two are compared under "Architecture" and in Open Question 4. **Whether it is ever cleared is M2.2's decision** — an unconditional release on tab close is ruled out (see Phase 2).
- Claim-aware `dispatch_decision`: a third signal, TTL-bounded, derived from live GitHub state.
- **If the claim is a label**, provisioning it in the dispatch target: just-in-time, on the dispatch path, before any claim write, unconditional and never gated on triage. Phase 1 cannot carry this — see "Provisioning the gating label".
- **A notification for a failed claim write**, distinct from a successful dispatch and from a failed one, and raised **once per issue naming both outcomes** rather than once per failed write (#486). Best-effort must not mean invisible; a claim that silently no-ops is a gate that silently stops gating.
- **Distinguishable skip reasons.** When dispatch skips an issue, the reason is reported and the causes are distinguishable from one another — worktree exists, open PR, claimed (with the claimant where one can be found), concurrent-creator race. This is what makes a stray third-party claim *diagnosable* rather than looking identical to nothing happening, and it is the natural mitigation for the silent-no-op risk this document already names. PR #471 implements it as a `SkipReason` enum with four variants, a renderer, and a changed `NotifyEvent::IssueDispatchSkipped`; it had no home in either scope list until this revision.
- A kill switch so claim-gating can be turned off in config without a rebuild.
- Test coverage across both tiers, including the `gh` stub arms that make the writes observable.
- Docs: `docs/scheduled-tasks.md` (the claim, the TTL, the recipe), `CONTRIBUTING.md` (the label vocabulary).
- A `changelog.d/421.<type>.md` fragment covering the cross-build behaviour skew Phase 3 introduces. (The repo's fragment convention is `<issue>.<type>.md` — `feature`, `bugfix`, `breaking`, `misc`; see `changelog.d/`.)

### Out of Scope

- **Sticky claim comments.** Assignment was chosen over a comment; a comment notifies every watcher, resets the `actions/stale` clock (`.github/workflows/stale.yml`), and needs comment-id bookkeeping to edit rather than append. Revisit only if assignment proves insufficient. Note that PR #471 posts exactly such a comment, to record the claimant — see Open Question 4.
- ~~**An `in-progress` label.** Superseded by assignment.~~ **Reopened** — this exclusion no longer holds. It rested on the label needing to exist in every dispatched repo (`--add-label` fails where it is absent), a cost this document originally believed Phase 1 dissolved and now records as real and paid on the dispatch path. Three P1 findings against the assignee mechanism make the label the **leading candidate** for the gating claim (see Architecture), and PR #471 has already implemented it. **The assignee-vs-label decision is M2.0's, and it is live, not settled.**
- **Recording *which orchestration* claimed an issue.** Assignment identifies a GitHub user, not an instance. See "The identity question" below for why the obvious mechanism does not work; #425's local ownership marker is the right home if this is wanted later.
- **A CLI verb for claiming or releasing an issue by hand.** Deliberately excluded for now, but the gap is real and is recorded as Open Question 5 rather than left silent — the claim is defined as a *cross-actor* signal on the read side, and no actor other than the scheduler can currently write or release one.
- **Non-GitHub forges.** Dispatch stays `gh`-only.
- **Retro-triage of the existing backlog by hand.** The first scheduled run handles it.
- **Any restriction on what the triage agent may run.** Decided: the skill scopes behaviour by prompt only. See Risks.

## Technical Approach

### Phase 1 — triage skill and schedule

The skill lives at `.claude/skills/triage-issues/SKILL.md` with `user-invocable: true`. It states the vocabulary, and the rule that decides the whole phase's usefulness: **when not confident, apply `needs-triage` and leave priority unset.** A wrong priority is worse than an absent one, because it is indistinguishable from a considered one.

The schedule is a plain task, not an `issue_dispatch` one — `issue_dispatch` would clone the repo and build a worktree per issue, which is heavy machinery for a job that only reads issue text:

```toml
[[scheduled_tasks]]
name = "triage-issues"
cron = "0 8 * * MON-FRI"
working_dir = "~/code/dot-agent-deck"   # must be a checkout of THIS repo
command = "claude"                       # required for a plain task
prompt = "/triage-issues vfarcic/dot-agent-deck"
enabled = true
```

Two constraints that are easy to get wrong, and belong in the docs: `working_dir` must be a checkout of this repo because `.claude/skills/` is project-scoped — that is how the agent discovers the skill; it is *not* the repo being triaged, which is an argument in the prompt. And `--command` is mandatory for a plain task (`src/schedule_cli.rs:70`: *"a scheduled task needs an agent command … to act on its prompt"*); only `issue_dispatch` tasks may omit it.

**Durability gap worth stating.** The three artifacts live in three places and only one is versioned: the skill is in git; the schedule is in `~/.config/dot-agent-deck/schedules.toml` on whichever machine runs the daemon; the labels are GitHub repo settings. The schedule vanishes with the machine. Documenting the recipe in `docs/scheduled-tasks.md` is the mitigation — the recipe is reproducible even though the instance is not. **This is also why Success Criterion 1 is scoped to repos a triage schedule actually covers**: nothing in this design enumerates repos or detects one that has never been triaged.

### Phase 2 — the visible claim

**M2.0 decides the mechanism before anything here is built.** The milestones below are written in mechanism-neutral terms — *claim* and *release* rather than *assign* and *unassign* — because the argv builders, the stub arms, the release policy and the fixture teardown all differ between the two candidates. An earlier revision of this document asserted the assignee mechanism flatly in In Scope while simultaneously calling the label the leading candidate and sequencing the decision into Phase 3; an implementer following that order would have built M2.1, M2.2, M2.4 and M2.5 against assignment, reached M3.3, been told to settle the mechanism first, followed this document's own recommendation to the label, and discarded all of it. That inversion is the defect M2.0 exists to remove.

A pure argv builder in `src/issue_dispatch.rs` (unit-testable, alongside `issue_list_argv` / `pr_list_for_issue_argv`, carrying the same `--` end-of-options guard), plus a `claim_issue` / `release_issue` pair in `src/issue_dispatch_run.rs` modelled on `ensure_worktrees_excluded`'s never-fatal discipline.

Write ordering is the one thing that must not be got wrong: **claim only after `spawn` returns `Ok`** (`src/issue_dispatch_run.rs:448`), so a failed dispatch never leaves a claim. Release, if M2.2 chooses to release at all, goes in the existing close path (`src/daemon_protocol.rs:1501-1510`), beside `remove_worktree`.

**Release must not be unconditional** (Greptile P1, PR #464). Under the **assignee** mechanism, `--add-assignee @me` is idempotent and harmless, but `--remove-assignee @me` is destructive and **cannot tell the deck's own claim from the user's**, because they are the same GitHub identity. So a human who assigns themselves to an issue, which the deck then dispatches and later closes, has their own signal silently deleted. The same applies to two decks sharing one GitHub account: the first tab to close unassigns while the second is still working, and the issue reads as free.

This is the sharp edge of choosing assignment over a deck-owned label, and it lands in Phase 2 — the phase otherwise characterised as safe because it is display-only. Two candidate mitigations, to be decided in M2.2:

- **Release only a claim the deck can prove it created.** Local provenance is exactly what [#425](https://github.com/vfarcic/dot-agent-deck/issues/425)'s worktree ownership marker provides, so this converges with work already proposed rather than inventing a second mechanism. Preferred if #425 lands first.
- **Do not release at all**; let the TTL expire the claim. Consistent with "derive, don't maintain", and it removes the destructive call entirely. Cost: the claim lingers for up to one TTL after the tab closes, so the issue looks busier than it is.

**Under the label mechanism the release analysis changes — but less than two earlier revisions of this document claimed, and what remains is UNRESOLVED.** The first said a deck-owned label is *attributable*, so "release only a claim the deck can prove it created" stops needing #425's ownership marker at all, the label's own `labeled` event plus the claim record identifying the claimant. The second added the precondition — safe *provided* the label is genuinely deck-owned vocabulary — without asking whether anything can check it. **Nothing can** (Greptile P1 on PR #464, raised against the milestone that relied on it), for three reasons that compound:

- **Provisioning deliberately discards the distinction.** `gh label create` runs **without** `--force` and its already-exists rejection is *treated as success* (see "Provisioning the gating label"). That is what protects a repo's own label — and it is the same stroke that throws away the one signal which would have recorded whether the deck created the vocabulary or merely found it.
- **M3.1 forbids persisting it.** "No deck-local claim bookkeeping anywhere" is the rule that lets the TTL survive a restart, so there is no store in which a per-repo ownership fact could live.
- **The `labeled` event does not carry it.** The actor is whichever account ran `gh` — the maintainer's own. On the instance question it therefore separates the deck from a human no better than `assigned` does, which was the root defect of the assignee candidate.

**So the close path cannot establish the precondition it would have to satisfy, and release-on-close under the label is not established as safe.** The failure is the same shape as the one it was supposed to escape: removing a marker the deck cannot prove it created destroys repository state exactly as an unconditional `--remove-assignee @me` destroys a human's assignment. Candidate resolutions, **to be decided at M2.0 alongside the mechanism itself**:

- **Do not release**; let the TTL expire the claim. Needs no ownership signal, and is the only option safe as designed today. Cost is the one already recorded above — the claim lingers for up to one TTL after the tab closes.
- **Give the claim its own deck-owned name.** The entire difficulty is that `in-progress` is vocabulary a repo may already own; a name unmistakably the deck's — `dot-agent-deck-claim`, say — is deck-created *by construction*, so release destroys nothing and no signal has to be derived or stored. It also separates the two sides cleanly, which the single-name design conflates: the deck can still **gate** on anyone's `in-progress` (Open Question 2 argues a human working an issue is a real claim) while **writing and releasing** only its own marker. This is the same move as the "Split the jobs" candidate above, applied to vocabulary rather than to signals, and it is the one resolution that follows directly from this document's own diagnosis — that the assignee mechanism failed because it was *shared identity, not deck-owned vocabulary*. Cost: a second label to provision, and a visible divergence from #471, which claims with `in-progress` itself.
- **Derive ownership from GitHub's own timeline** — compare the most recent `labeled` event for `in-progress` against the deck's claim record, and release only where the deck's own write is the one that put it there. The claim record here is the **comment on the issue** naming task, host and timestamp, which lives on GitHub, so reading it back is derivation and not the local bookkeeping M3.1 forbids. Truest to "derive, don't maintain" at the cost of a timeline read per close. **Weakest of the four, and it must not be chosen on the strength of the phrase "derive from the timeline" alone**: the actor field cannot carry the distinction, so ordering is doing all the work, and ordering has at least one hole — a human who removes and re-adds `in-progress` after the deck claimed produces a `labeled` event later than the claim comment, and the deck then releases a label it does not own. Requires the same empirical confirmation M3.1 demands, and a decision on whether that hole is acceptable, before anything is built on it.
- **Record ownership explicitly** — #425's marker, or a provisioning-time probe that lists labels before creating. Both are bookkeeping, which M3.1 rules out; choosing either means amending M3.1 deliberately rather than bending it quietly.

The TTL remains required under every option, because release-on-close cannot fire when the daemon dies with the tab open. Note that this does **not** restore assignment as the better candidate: the label still avoids two of assignment's three findings outright, and this gap is a *release* question that the "do not release" option answers without any new mechanism.

Best-effort means a missing permission, a read-only repo, or a `gh` failure never fails the dispatch, which genuinely succeeded. It does **not** mean the failure is invisible: per M3.6 it raises its own notification rather than only a WARN. Phase 2's claim is decorative, so a swallowed failure costs little there — but the same code path carries Phase 3's gate, where a silent no-op is a gate that has stopped gating, and this is exactly why Phase 3 cannot simply trust the claim to exist.

### Phase 3 — claim-aware dispatch

`dispatch_decision` gains a third parameter. The pure function stays pure — the caller resolves claim state and passes a verdict in, so the truth table remains exhaustively unit-testable. Evaluation order matters for the same reason the existing short-circuit does (`src/issue_dispatch_run.rs:361-371`): the worktree signal is local and free, so it is checked first and a `gh` failure on a locally-claimed issue can never turn a clean skip into a spurious failure.

The kill switch is a config knob on `IssueDispatchConfig` (`src/config.rs:586`) — claim-gating off by default until the TTL behaviour has been observed in the wild, so the feature cannot wedge a backlog while it is being trusted.

**Cross-version behaviour (CLAUDE.md rule 12).** This touches the daemon, so the check is triggered. The TUI↔daemon wire is **unchanged** — no `PROTOCOL_VERSION` bump. Verified: `NotifyEvent` does not appear in `src/daemon_protocol.rs`, and PR #471 — which adds a `NotifyEvent` variant and changes another — does not touch that file at all, so the notification surface required by M3.6 is genuinely off-wire. But an old daemon dispatches without claiming while a new daemon reads claims and skips, so a mixed fleet disagrees about what is in flight. That skew is a compatibility note, not a wire break: it needs a `changelog.d/421.<type>.md` fragment and the rule 12 cross-version manual run (isolating `DOT_AGENT_DECK_LOG` along with the sockets and `HOME`, per rule 12's third bullet).

### The identity question (issue §2), and why it is out of scope

Issue #421 proposes recording *which* orchestrator claimed an issue, via `mint_orchestration_id()`. Verified against the code, that mechanism cannot do the job:

1. **It is not durable.** `src/agent_pty.rs:381-382`: *"The token deliberately does NOT need to be reproducible across restarts"* — a per-process nonce plus a counter. So the test it is meant to enable ("is this my own earlier claim, or someone else's?") fails after any daemon restart, which is the same restart that already wipes `WorktreeRegistry`.
2. **It is not always minted.** `mint_orchestration_id()` is called only in the `SpawnTarget::Orchestration` branch (`src/spawn.rs:499`). A repo with no `[[orchestrations]]` block dispatches as a single-agent card and has no instance identity at all.
3. **The stated fallback is not unique where it matters.** `ScheduledTask.name` is "unique per daemon" (`src/config.rs:609`), but the default seed is `Issues <owner>/<repo>` (`src/issue_dispatch.rs:45-47`) — so two machines on default config produce byte-identical claimants, which is precisely the collision the proposal exists to solve.

The TTL design sidesteps this entirely: it never needs to know *who* claimed an issue, only *how long ago*. If per-instance identity is wanted later, #425's worktree ownership marker is the right home — local, durable, and free of GitHub-write risk.

Issue #421's closing observation is correct and worth acting on separately: **#156**'s premise ("there is no unique per-instance ID") was superseded by PRD #140. That issue's problem statement should be updated regardless of this PRD.

## Success Criteria

1. **Every open issue in a repo covered by a triage schedule** carries either a `priority-*` + `size-*` pair or `needs-triage`, within one cron period of being opened, maintained without anyone remembering to do it. *Scoped deliberately:* nothing in this design enumerates repos or detects a repo that has never been triaged (see "Provisioning the gating label"), the schedule names one repo in its prompt, and nothing runs between cron fires — so "every open issue everywhere" is not a criterion this design can meet, and an earlier revision that claimed it was over-scoped.
2. An issue being worked on by a dispatched agent is identifiable from the GitHub issue list alone, before any PR exists.
3. A dispatch failure never leaves a claim behind.
4. **A stale claim never permanently wedges an issue** — after the TTL, the issue is dispatchable again with no manual intervention, on a machine that has never seen the original claim. **This is the criterion that answers [#482](https://github.com/vfarcic/dot-agent-deck/issues/482)**; a design in which nothing ever clears a claim fails it by construction.
5. `tests/e2e_issue_dispatch_real.rs` stays green across consecutive runs against the live fixture, and leaves it in its original state — **including for a maintainer whose token cannot write to the fixture repo**, since a test that skips rather than runs is counted as passing by nextest and proves nothing.
6. Claim-gating can be disabled in config without a rebuild.

### Phase 2: Visible claim (display-only)

**M2.0 and M2.2 gate this list, and they can remove a box's subject entirely.** The milestones below are written in mechanism-neutral vocabulary — *claim* and *release* rather than *assign* and *unassign* — but neutral wording is not independence of content: M2.1's builders, M2.3's stub arms and M2.4's teardown all differ by mechanism, and M2.2's release decision determines whether a release path exists to build, stub or assert at all. **Where a milestone names an artifact the chosen policy does not produce, it is satisfied by asserting that artifact's absence — never by building it to tick the box.** That is the same rule M3.3 states for the re-stamp test, and it exists for the same reason: under "do not release", constructing a release builder in order to complete M2.1 would create precisely the destructive operation the policy was chosen to exclude. Read the list against M2.0's and M2.2's answers rather than top-down as an unconditional build order.

- [ ] **M2.0** — **Decide the claim mechanism: assignment or a deck-owned `in-progress` label.** *This gates every milestone below it.* The evidence is already assembled — three P1 findings against assignment (Architecture), the per-repo provisioning cost of the label ("Provisioning the gating label"), and PR #471's working implementation of the label form (Open Question 4). Record the decision and its reasoning in this document. Two of the three assignee findings do not arise under the label, so this decision is not merely a naming choice — **but the third does arise, on the release path**, and M2.0 must settle the label's ownership gap along with the mechanism (see "Phase 2 — the visible claim"), since two of its four resolutions change what M2.1 builds. Note that the strongest of them — giving the claim its own deck-owned name — makes this **not** a two-way choice: it is a third mechanism, and picking it makes the assignee-vs-`in-progress` framing itself the wrong question.
- [ ] **M2.1** — Pure argv builders + unit tests for the **claim** in whichever mechanism M2.0 chose, and for the **release only if M2.2 chose to release at all**. Under "do not release" there is no release argv, and writing one to complete this box would build the destructive operation that policy exists to exclude — so under that policy this milestone is the claim builder alone, and the release side is discharged by M3.3's assertion that no release path exists rather than by a builder nothing calls.
- [ ] **M2.2** — Claim written after a successful spawn; best-effort at every step, never fatal. **Decide and implement the release policy.** Under assignment: release only deck-created claims (via #425's ownership marker), or do not release and let the TTL expire it — an unconditional `--remove-assignee @me` is not acceptable, since it deletes a human's own assignment. Under the label: **release on close is not established as safe and cannot be chosen as written** — the deck cannot prove it created the marker it would remove, and Architecture records why (provisioning treats already-exists as success, M3.1 forbids persisting ownership, and the `labeled` actor is the maintainer's own account) together with the two resolutions that would make it choosable. So this milestone decides between **do not release**, which needs no ownership signal and is safe as designed today, and **release on close conditional on first supplying one** — never release-on-close asserted flat. The TTL is required either way — release-on-close cannot fire when the daemon dies with the tab open.
- [ ] **M2.3** — `gh` stub learns the claim verb, with tests asserting the claim is written on dispatch, **and asserting whatever M2.2 decided about close**: that a deck-created claim is cleared, or — under the no-release policy — that closing a tab performs *no* release call at all. Both are testable; what is not acceptable is leaving the close path unasserted. **The stub currently `exit 1`s on unrecognised argv (`tests/e2e_issue_dispatch.rs:101-102`), so a best-effort write would otherwise be silently swallowed and every existing test would stay green while proving nothing** — the stub arms are what make this milestone real.
- [ ] **M2.4** — `tests/e2e_issue_dispatch_real.rs` verified against the live fixture (`vfarcic/dot-agent-deck-tests` issue #1) across two consecutive runs, **leaving it in its original state**. **Under the no-release policy the deck itself never clears the claim**, so the test must do it explicitly in teardown — restoring the fixture is the test's own responsibility, not evidence that release works. The teardown must also work, or fail loudly, for a maintainer whose token cannot write to the fixture repo (Success Criterion 5); a teardown that silently degrades to a skip disables the test rather than protecting it.
- [ ] **M2.5** — Docs updated.
- [ ] **M2.6** — **If M2.0 chose the label, M3.6 lands here, in this phase, not in Phase 3.** M3.6 attaches to whichever phase first *writes* the claim; under the label candidate that is Phase 2. Tracked as its own box because a milestone that conditionally belongs to another phase is otherwise tracked in neither, and Phase 2 would complete with every box ticked while shipping a claim write whose failure is invisible.

### Phase 3: Claim-aware dispatch

**These milestones are written against an event-derived clock, and M2.0 can invalidate that.** M3.1 and M3.3 take the claim's freshness from the most recent `assigned`/`labeled` event, which is right for the two candidates that re-stamp — but **"Never refresh" anchors freshness to branch commits or PR activity and "Split the jobs" gates on worktree presence and an open PR, and neither produces an `assigned` or `labeled` event at all.** Under those candidates the wording below cannot be met as written, and both ways of appearing to meet it are wrong: reinterpret the acceptance criteria silently, or restore the destructive remove-then-add purely to make a clock advance. So read every "age" and "event" below as **whatever freshness signal M2.0's candidate actually provides**. The invariant this phase asserts is mechanism-independent, and it is the thing to hold onto when re-deriving: **a claim no longer backed by live work must stop gating, and whatever establishes that must be observable to a second machine.** M2.0 chooses which signal carries it. These milestones must be re-derived against that choice *before* they are worked — not reinterpreted while they are.

- [ ] **M3.1** — Claim state derived from live GitHub at decision time — the claim marker, plus the freshness signal M2.0's candidate provides: the age of the most recent `assigned`/`labeled` event under the re-stamping candidates, branch commits or PR activity under "Never refresh", worktree and open-PR state under "Split the jobs". **No deck-local claim bookkeeping anywhere** under any of them. **Empirically confirm the chosen signal behaves as assumed before building on it** — for the event-based candidates specifically, that a redundant claim write emits no new event, since the TTL design is void if that assumption is wrong in either direction.
- [ ] **M3.2** — Third signal wired into `dispatch_decision` with an exhaustive truth table; short-circuit order preserved so a `gh` failure cannot turn a local skip into a failure. Skip causes are distinguishable and reported, per In Scope.
- [ ] **M3.3** — **Stale claims self-heal.** The mechanism follows from M2.0 and the re-stamp candidate chosen with it (see Architecture). A claim older than the TTL does not gate and the issue dispatches — and **the freshness signal must then actually move**, which is where M2.0's choice changes the test rather than the intent. Under the re-stamping candidates that means the derived age advances: proven by a test that dispatches against a pre-aged claim written by no local daemon, **and asserts the age advanced afterwards** — without that second assertion the test passes against the broken idempotent-assign design. Under "Never refresh" and "Split the jobs" nothing re-stamps and no age is expected to move; there the equivalent assertion is that the signal those candidates *do* read — branch or PR activity, worktree state — reflects the new dispatch, and that the issue does not immediately re-dispatch on the next fire. Do not satisfy this box by reintroducing a re-stamp to make a clock tick. A second test must pin the destructive-write property, and **its form follows from M2.0**. Under a candidate that re-stamps, it is the **interrupted re-stamp** — first call succeeds, second fails — asserting no claim is destroyed. Under "Never refresh" or "Split the jobs" there is no two-call re-stamp anywhere to interrupt, and building one solely to satisfy this milestone would reintroduce the exact destructive path those candidates were chosen to remove; the milestone is met instead by asserting that **no re-stamp or release call path exists at all** — the same guarantee stated as an absence rather than as an interruption. Both forms are testable, and both stop a later change from quietly reintroducing a destructive write; what is not acceptable is leaving the property unasserted. *This is the milestone the phase is only safe with — treat it as a hard gate, not a nice-to-have.*
- [ ] **M3.4** — Kill switch on `IssueDispatchConfig`, defaulting to off, with validation and a test.
- [ ] **M3.5** — Cross-version manual run per rule 12 (old daemon + new TUI, isolated `DOT_AGENT_DECK_LOG`/sockets/`HOME`), plus the `changelog.d/421.<type>.md` fragment recording the mixed-fleet skew.
- [ ] **M3.6** — **The claim can never silently no-op.** Two halves, both required, and both landing with whichever phase first *writes* the claim — so if M2.0 chose the label, this milestone moves into Phase 2 as M2.6. (a) If the claim is a label, it is provisioned on the dispatch path — just-in-time, before any claim write, unconditional and never gated on triage (#483); created without `--force` so a repo's own pre-existing label survives, with `gh`'s already-exists rejection treated as success. (b) A failed claim write raises its own notification, distinguishable from a successful dispatch and from a failed one, **once per issue naming both outcomes** rather than once per failed write (#486); `tracing::warn!` alone does not satisfy this. **Required test properties:** dispatch against a repo carrying **no** labels at all; assert the claim genuinely *succeeded*, not merely that it was attempted — which is what a test written against the broken design also passes; and the `gh` stub must hard-error on an unknown label name, mirroring real `gh`'s client-side name-to-ID resolution. PR #471's `scheduler/dispatch/020` already satisfies all three and should be reused if #471 lands; the properties are stated here so that a replacement can be written from this document if it does not.

## Open Questions

1. **What TTL?** Long enough that a legitimately slow agent is not preempted, short enough that a dead claim clears within a working day. A starting proposal is 24h, revisited after M1.4-style observation.
2. **Should the deck reconcile claims it did not write?** An issue claimed by a *human* reads as claimed. That is arguably correct on the **read** side — a human working an issue is a real claim — but it means claiming an issue yourself quietly opts it out of dispatch, and under a label mechanism it means any automation that happens to use the name `in-progress` does too (see the third-party-starvation risk row). The **write** side is not a question but a defect, now tracked in Risks and M2.2: release must never delete a claim the deck cannot prove it made.
3. **Does triage want a `sort` interaction with dispatch?** Once priorities exist, `query = "is:open label:priority-high sort:created-asc"` becomes the natural dispatch filter. PRD #222 already proposes a first-class `sort` field; these two should be aligned rather than solved twice. *Note the separator matters here beyond cosmetics:* under the colon form the qualifier needs quoting (`label:"priority:high"`) to parse unambiguously, so the hyphenated form is the safer input to #222's design.
4. **How does this PRD reconcile with [PR #471](https://github.com/vfarcic/dot-agent-deck/pull/471)?** — **the blocking question.** #471 ("claim dispatched issues and triage them on dispatch", by @prageethw, open, ~2.5k lines) implements Phases 1–2 of this issue independently, and its design differs from this PRD on almost every axis. It is not a merge conflict — the two touch disjoint files — but a design disagreement that must be settled by the two maintainers rather than by whichever PR merges second.

   | Axis | This PRD | PR #471 |
   | --- | --- | --- |
   | Claim mechanism | M2.0's decision; label is the leading candidate | `in-progress` label |
   | Claim expiry | TTL derived from the age of the most recent claim event; a stale claim stops gating | **none** — the label gates until a human removes it or the issue closes (#482) |
   | Third-party claims | Open Question 2, unresolved on the read side | honoured **regardless of who applied it** — deck, human, or unrelated tool |
   | Kill switch | required (M3.4), gating off by default | none; the label always gates |

   Four of these deserve explicit attention:

   - **#471 ships the shape this PRD names as its central hazard.** The first Risks row says a stale claim wedging an issue permanently is "the reason issue #421's original 'write a label and gate on it' shape was not adopted". #471 is that shape with no TTL and no kill switch, and documents the wedge as intended behaviour: *"subsequent fires keep skipping the issue until someone removes the label."* That is the single substantive disagreement — everything else is vocabulary or packaging. It cuts both ways: #471's label avoids the two P1s that sank the assignee design on the *write* side, while this PRD's TTL is what stops a claim from wedging a backlog. Note that #471 never removes the label, so the release gap recorded above does not arise there — it is created by *this* document's release-on-close option, not by #471. **The two are complementary, not mutually exclusive: a deck-owned label with a TTL and a kill switch is neither PR's current design and is very likely the right answer.**
   - **The third-party-claim row compounds the expiry row, and the composite is the real exposure.** Honoured-regardless-of-applier is defensible on its own; no-expiry is a bounded gap on its own. Together they mean any `in-progress` label from any source starves an issue on every deck until a human intervenes. Read row by row this looks like two mild gaps; it is one sharp one.
   - **#471 adopts two things this PRD puts out of scope** — the `in-progress` label (an exclusion this PRD has since reopened on its own evidence, so the two now agree) and a sticky claim comment (still excluded here, on the grounds that it notifies every watcher and resets the `actions/stale` clock — a concern #471 does not address).
   - **Triage coverage is a real difference of job, not of quality.** A scheduled skill sweeps the whole backlog of the repos it is pointed at; #471's triage labels only issues a fire dispatches, so it never reaches the backlog no matter how long it runs. Success Criterion 1 belongs to the scheduled-skill design — but note the criterion is scoped to repos a schedule covers, so it is a claim about *coverage within configured repos*, not a claim this design triages the world. The two triage designs could coexist.
   - **On two axes #471 is simply ahead, and this PRD has been corrected to match it: provisioning the gating label, and reporting a failed claim.** #471's `ensure_claim_label` runs once per dispatch run, and `NotifyEvent::IssueClaimFailed` makes a failed claim visible instead of burying it in a log — both reached through #471's own review, and both now required here as M3.6. This is worth noticing beyond the one fix: the axes above read as a design disagreement, but on the question of what happens when a best-effort write *fails*, the implementation had been more careful than the PRD. That is an argument for reconciling the two rather than picking a winner.

   **The milestone-citation hazard, and why it is a milestone (M4.4) rather than a note.** #471's code comments carry **51** `PRD #421 M<x>.<y>` citations, because #471 was developed against a different PRD on the author's fork. They fail in two different ways, and the second is worse:

   - **26 dangle**: `M1.0` (×12), `M2.0` (×10), `M3.0` (×4) do not exist in this document, which runs M1.1–M4.4.
   - **25 resolve to a real milestone that means a different phase**: `M1.2` (×12), `M1.3` (×6), `M1.4` (×3), `M2.1` (×2), `M1.1` (×1), `M2.2` (×1). The two numbering schemes are **inverted** — #471's `M1.x` is the *claim* work (`src/issue_dispatch.rs:295`: "PRD #421 M1.0/M1.1/M1.2 — claim label/comment argv + comment body") while this document's `M1.x` is *Phase 1 triage*; #471's `M2.x` is the *triage vocabulary* (`:444`) while this document's `M2.x` is the claim. So a reader following `// PRD #421 M1.2` on `src/issue_dispatch.rs:123` — the label riding along on the already-made issue-list call — lands on this document's M1.2, "`triage-issues` skill written". Twelve times.

   A dangling citation wastes a reader's time; one that resolves to the wrong thing misinforms them silently. **Merging this PRD converts 25 citations from the first kind into the second**, which is why M4.4 exists and why this document landing does **not** close [#481](https://github.com/vfarcic/dot-agent-deck/issues/481). #481 asks for `prds/421-automatic-issue-labelling.md` — still the path cited at `src/issue_dispatch.rs:392` — and this document is a differently-named file with different content and inverted numbering. The ~47 remaining fork-only citations in #471 (`review C3`, `reviewer F1`, `auditor F8`) are untouched by either option and are #481's own scope.

5. **Can any actor other than the scheduler participate in the claim protocol?** Today, no — and the claim is defined as a **cross-actor** signal on the read side, which makes the asymmetry worth naming. This document's own Gap 2 argues the claim exists so a *second deck* can check it; Success Criterion 4 requires it to work "on a machine that has never seen the original claim"; Open Question 2 asks whether a *human's* claim should be honoured. But nothing offers a human, a skill, or a test harness a way to **write or release** one. In #471 the helpers (`issue_edit_add_label_argv`, `claim_comment_body`, `Claimant`) are `pub` but reachable only from the scheduler path — `ensure_claim_label` is private — and there is no CLI verb; the only new command-line surface is `schedule add --triage`. The cost is already visible: #471's real-agent test had to hand-roll `remove_in_progress_label` and `clear_stale_claim` in `tests/e2e_issue_dispatch_real.rs`, matching a permission error textually to decide whether to skip, which is what produces the self-disabling teardown in the Risks table. Either scope in a `dot-agent-deck issue claim|release <repo> <n>` verb — which also gives #482 a documented manual recovery path better than a raw `gh` incantation — or state deliberately that the protocol is write-only for the scheduler and that every other actor uses `gh` directly. What is not defensible is defining a cross-actor protocol and leaving participation in it undesigned.
