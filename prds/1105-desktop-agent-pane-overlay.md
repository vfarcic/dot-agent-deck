# PRD #1105: An agent pane overlay for the desktop

**Status**: Not started — this document is the plan, written before any implementation.
**Priority**: Medium
**Created**: 2026-09-15
**Issue**: [#1105](https://github.com/vfarcic/dot-agent-deck/issues/1105)

## Problem Statement

The desktop app can show you nine agents at tile size, and it cannot show you one agent's terminal large. `DeckSurface` renders one flat `.agent-grid` over every agent the selected deck owns, each tile mounting a terminal by default (`tabs[agent.id] ?? "terminal"`, `desktop/src/App.tsx:311`), and every tile is the same size as every other. Reading the one agent that matters right now means reading a ninth of the window.

Two partial escapes exist, and the shape of what is missing is exactly the gap between them.

**The Reader overlay is large and is not a terminal.** `OutputReader` renders an agent's output at reading width, re-snapshotting the resolved xterm buffer every 700ms (`desktop/src/components/OutputReader.tsx:7,42-50`). It is genuinely useful for reading, and it is a *text* projection: `terminalSnapshotText` resolves the buffer to plain text, so there is no cursor, no colour, no alternate screen, and no keyboard into the agent. It answers "what did this agent say" and cannot answer "work with this agent".

**The overview is an index with nowhere to go.** PRD [#745](https://github.com/vfarcic/dot-agent-deck/issues/745) built a fleet overview that deliberately mounts no terminal and attaches no PTY, and it named this gap in its own **Staging** section rather than leaving it to be discovered: *"the overview only becomes the landing screen once there is somewhere to go from it: a group view … and a single-agent view. Until then, making it the default would land users somewhere they cannot leave."* That is its deferred **Iteration 3 — destinations**. #745 shipped iterations 1 and 2 and left iteration 3 open. The overview today tells you which agent you want and then hands you nothing.

**And the third rendering is already halfway written.** An agent pane in this app is not a small widget. `AgentTile` carries five panel tabs — terminal, diff, checks, handoffs, artifacts (`desktop/src/components/AgentTile.tsx:23-29`) — plus evidence, rename, status, an embedded `TerminalViewport` and the Reader launcher, behind a fifteen-field prop interface (`:31-54`). Building an overlay as a second component beside it, with `OutputReader` already being a third rendering of the same agent's output, is how one agent ends up with three surfaces that drift apart one bug fix at a time. That outcome — not the layout — is what makes this a PRD.

## Solution Overview

Clicking an agent opens **that agent's pane, enlarged, inside the app**, from either of two screens: an agent card on the overview, and a tile on the deck grid. Same overlay, same component, two entry points. `Esc` or a close control returns the user exactly where they were.

Four commitments define it.

**One component at two sizes.** The grid tile and the overlay are the *same* component, rendered at two sizes, and every difference between the sizes is a **prop**. If the implementation finds itself wanting a second component, the props are wrong and that is the signal to stop. This is the central commitment of the whole PRD: the outcome being avoided is three copies of an agent pane, and the test of success is that a fix to a status chip, a tab, or a keyboard handler lands once.

**Closing costs nothing.** Returning from the overlay must put the user back with no terminal flicker, no re-attach and no scrollback replay. That is not free by default — it is a property of the bridge's warm set, and it is only preserved by keeping the deck grid mounted underneath. See [What closing must cost, and why the grid stays mounted](#what-closing-must-cost-and-why-the-grid-stays-mounted).

**Enlarging really enlarges.** The overlay asks the daemon for a bigger PTY rather than scaling a small one up. That is a product decision with a consequence for other people watching the same agent, and it is taken deliberately — see [Resizing the PTY, and what a TUI user sees](#resizing-the-pty-and-what-a-tui-user-sees).

**In-app navigation, not a router.** `DeckView` (`desktop/src/types.ts:276-278`) is already a discriminated union built for exactly this, and its own doc comment says so — *"so PRD #745 iteration 3's group and single-agent views arrive as added variants rather than as a refactor of a boolean. No router library is warranted for this."* This adds a variant. It adds no dependency.

### What this takes from #745's iteration 3, and what it leaves

Stated explicitly, because the risk here is quietly redefining someone else's deferred milestone to be whatever happened to get built.

#745's iteration 3 is written as four things: **a group view** (the existing deck, filtered to one tab bucket), **a single-agent view**, **drill-in navigation between them**, and **promoting the overview to the actual landing screen** (`prds/745-desktop-agent-overview-landing-screen.md:282`).

This PRD takes the **single-agent view** and the **navigation to it from both screens**. It leaves the **group view** and the **promotion to landing screen** untaken, and neither is reduced in scope by being left — the group view is still the whole deck-filtered-to-a-bucket screen #745 describes, with its own unanswered question about how many terminals it mounts (#745 open question 1). **#745's iteration 3 is therefore still open after this ships**, and should not be closed by it.

## Scope

### In Scope

- **One agent-pane overlay component**, opened from both the overview's agent cards and the deck's tiles, rendering the same component the grid tile renders, at a second size, differing only by props.
- **A third `DeckView` variant** carrying the agent's composite identity and the screen it was opened from, so the back behaviour is a property of the view value rather than of a history stack.
- **The deck grid staying mounted and attached underneath the overlay**, which is what makes closing free.
- **A genuine PTY resize on open and on close**, with the daemon's existing smallest-viewport policy left exactly as it is. **Superseded by M11 (2026-09-17):** under that policy the enlarged pane gained nothing whenever a TUI also showed the agent in a narrower tile, so the product owner chose focus-driven sizing — the last-focused client's viewer size wins, with the smallest-viewport policy kept as the fallback. See the [Work Log entry](#2026-09-17--focus-driven-sizing-the-decision-and-the-contract-m11-step-1).
- ~~**Cross-deck opening by switching the selected deck first and reverting on close**, reusing the existing single-deck attach with no wire change.~~ The **switch** is **DESCOPED** after two security audits. What replaced it is stronger rather than smaller: every agent the overview lists opens with a **live terminal on its own deck**, with no selection change and no wire change — see [Cross-deck terminals](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships).
- **A click target on the overview's agent cards**, and nothing else on those cards.
- **Keyboard**: `Esc` closes, matching `OutputReader`'s existing binding (`desktop/src/components/OutputReader.tsx:58-64`).
- **Test coverage** at the two tiers the desktop actually has — vitest/jsdom and Playwright over the built bundle — plus the shown-set assertions at bridge level.
- **A docs update** to `docs/develop/desktop-gui.md`, including the manual smoke check, since that check is the only thing that exercises the real window.

### Out of Scope

- **The group view**, and therefore deck → group → agent as a second path. Still #745 iteration 3's.
- **Promoting the overview to the landing screen.** The deck stays the default; `DeckShell`'s `initialView = { kind: "deck" }` (`desktop/src/App.tsx:120`) is unchanged.
- **Any change to what the overview's cards display.** #745's commitment — *"No terminal on this screen, ever"* — is untouched. The cards gain a click target and nothing else.
- **Cross-deck MULTIPLEXING.** The *pane* attaches across decks and needs no wire change — one pane is one stream to a deck this app already holds a tunnel to. What stays out is N decks × M concurrently visible **tiles**, which is [#1073](https://github.com/vfarcic/dot-agent-deck/issues/1073) and is not a refactor: the attach frame header carries no stream id, so muxing several streams over one connection is a wire change and a `PROTOCOL_VERSION` bump (`src/daemon_protocol.rs:649-666`).
- **The cross-deck SWITCH, which was in scope and was withdrawn.** It is out of scope now for reasons found rather than predicted; [its section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) records what was built, what the audits found, and what closed them. Cross-deck **opening with a live terminal** is in scope and ships — what is out is moving the user's selection, on their behalf or by a control offering to.
- **Retiring `OutputReader`.** The Reader is a *reading* projection with reflowed soft-wrapped lines and a copy control; the overlay is a *working* surface. Whether the overlay eventually subsumes it is [an open question](#open-questions), not a scope item — but the overlay must not become a fourth thing while that is undecided.
- **The per-tile composer**, whose removal is [#1042](https://github.com/vfarcic/dot-agent-deck/issues/1042) and lands first on this same branch as its own PR. The overlay inherits whatever that settles; it does not re-open it.
- **Measuring the WebGL context ceiling.** #745 records it as unmeasured and this PRD does not measure it either — see [Attach cost and the WebGL question](#attach-cost-and-the-webgl-question) for what this work does and does not do about it.
- **The `experimental` feature flag.** Not applied — see [Feature flag](#feature-flag).
- **Any harness that drives the real Tauri window.** None exists ([#953](https://github.com/vfarcic/dot-agent-deck/issues/953)); building one is its own PRD.

## Technical Approach

### The component, and the thing being avoided

`AgentTile` is the component. It grows a size prop — one prop naming which of two presentations to render, not a pile of booleans — and the overlay renders `AgentTile` with that prop set. Everything the two sizes differ in (which panel tabs are visible, whether the header is compact, how the terminal's box is computed, whether the Reader launcher shows) is derived from that one prop inside the component.

The rule that makes this enforceable rather than aspirational: **if a difference cannot be expressed as a prop, the answer is not a second component — it is that the difference is wrong.** The counter-example to keep in view is `OutputReader`, which *is* a genuinely separate component and earns it by being a different projection of the data (resolved text, not a terminal). "Bigger" is not a different projection.

### Screen and view state

`DeckView` today is `{ kind: "deck" } | { kind: "overview" }` (`desktop/src/types.ts:276-278`), and `DeckShell` switches on it with an early return: `if (view.kind === "overview") return <AgentOverview …/>; return <DeckSurface …/>` (`desktop/src/App.tsx:137-138`). So the union as used today **replaces** the mounted screen, and `DeckShell`'s own doc comment states the consequence — *"The deck is unmounted while the overview is up"* (`:125-127`), written up as the reason the zoom keys once died on the overview.

That is the constraint the new variant has to be designed around, because an overlay that unmounts the screen beneath it forfeits the no-flicker property before any of the rest of this matters. So the variant carries its origin:

```ts
| { kind: "agent"; deckId: string; agentId: string; from: "deck" | "overview" }
```

and `DeckShell` renders the base screen named by `from` **with the overlay on top of it**, rather than instead of it. The deck stays mounted when you arrived from the deck; the overview stays mounted when you arrived from the overview.

**This answers #745's open question 2** — *"Two paths to the agent view. Once destinations exist, overview → agent and overview → group → agent reach the same screen with different back behaviour. Worth deciding rather than discovering."* The decision is that **back behaviour is carried in the view value**, not inferred from a history stack. Closing sets `view` to `{ kind: from }`. When the group view arrives, it adds a third `from` and nothing else changes. Note the narrower claim: this answers the question for the two paths that exist after this PRD, and defines the mechanism the third path will use; it does not build the third path.

`deckId` rather than a bare agent id because agent ids are per-daemon monotonic integers and are *"unique only within a daemon"* (`desktop/src/types.ts:314`). `AgentSession` already carries `daemonId` (`:473`) and the overview already keys by the composite (`:470-473`), so the identity this variant needs exists. **What does not exist is composite keying everywhere**: #745 recorded nine maps keyed by a bare id and fixed only some, and this PRD does not fix the rest — but three of them turned out to be load-bearing here and are dealt with under [the composite keying](#the-composite-keying-and-what-it-alone-did-not-close).

### What closing must cost, and why the grid stays mounted

The bridge's warm set is what makes returning free, and its bounds are what make "just unmount the deck" wrong.

`setShownTerminals` is declarative and does four things in one pass — attach the newly shown, move the newly hidden into the warm set, evict warm overflow, and flush the warm set entirely when nothing is shown (`desktop/src/lib/bridge.ts:1647-1691`). Leaving a terminal does **not** detach it: it moves to the warm set, and *"It stays in `attached`, so coming back costs no attach and produces no replay — the whole point of warm"* (`:1667-1669`). But the warm set is bounded at three — `MAX_WARM_TERMINALS = 3` (`:1385`) — and the flush-to-zero case is unconditional: when the shown set is empty the overflow is `this.warm.size`, *"Flushed to ZERO rather than down to the bound"* (`:1675-1679`).

**There was one warm set for the whole app, keyed by bare agent id, and this PRD is what changed that.** `TauriDeckBridge` held a single bridge-wide `Set` for each of `attached`, `shown` and `warm` and a single bare-id `Map` for `sessions`; there was no deck-keyed terminal state anywhere. Worth recording because #1073's phrasing invited the opposite reading: its *"`setShownTerminals([])` clears only the selected deck's warm set"* was shorthand for the **behavioural scope** of the time, not a statement about storage — read literally, `[]` flushed the sole global set. Every one of those structures is now keyed by `agentKey(deckId, agentId)`, so *"clear this deck's warm set and preserve another's"* is expressible; what #1073 still owns is multiplexing several streams over one connection, which is a wire question rather than a storage one.

**How a dead terminal is noticed, narrowly.** The Rust `detach` emits no frontend event itself; the desktop stream task emits `TerminalState::End` on a stream-end frame or EOF, and `handleTerminalState` drops that agent's `sessions`, `attached` and `terminalChannels` entries (`desktop/src/lib/bridge.ts:1928-1948`). It deliberately does **not** drop `warm`, so a dead warm marker survives until a later shown-set operation handles it — pinned by `leaves a warm terminal whose session ended dead until it is shown again`. Reconciliation here is event-driven and asynchronous, which is what [the descoped cross-deck switch](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) turned on.

So the arithmetic for a nine-tile deck is not close — and it is the replacement **declaration** that produces it, not the React unmount. Unmounting `DeckSurface` invokes no cleanup declaration of its own, so unmount alone leaves the bridge holding its previous shown set, stale; what costs something is whatever declares next. Declare `[agentId]` directly from the nine shown ids and the other eight move to warm, `8 - MAX_WARM_TERMINALS` = **five** are evicted immediately, and one shown plus three warm survive. Closing the overlay then re-attaches those five, and an attach is not cheap — the daemon *"immediately follows the OK response with a single `KIND_STREAM_OUT` carrying the consistent scrollback snapshot"* before streaming (`src/daemon_protocol.rs:67-69`), over a socket opened per session (`desktop/src-tauri/src/terminal.rs`). Five scrollback replays is precisely the flicker this design exists to avoid.

**The empty declaration is worse, which makes the decision below stronger rather than weaker.** Declaring `[]` — what a base screen that declares nothing for itself produces, and exactly what the overview declares today (`desktop/src/components/AgentOverview.tsx:610-612`) — moves all nine to warm and then evicts `warm.size`, so it detaches **nine**, not five (`desktop/src/lib/bridge.ts:1675-1679`). A one-id overlay after that costs one replay to open and eight more to restore the deck. Both ways of getting this wrong are expensive: five replays down one path, nine detaches and nine replays down the other. There is no cheap way to unmount the grid.

**Decision: the deck grid stays mounted and attached underneath the overlay.** The shown set does not change when the overlay opens over the deck, so `setShownTerminals` is not called at all — the effect that calls it keys on the joined id list (`desktop/src/App.tsx:324,340-342`), which is unchanged. Zero attaches, zero detaches, zero replays, on open and on close. The steady-state cost of the overlay over the deck is therefore **exactly today's deck cost**, and the feature adds no sockets.

**The `setShownTerminals` contract is a hard constraint on how this is wired.** Its doc comment: *"It must be called ONCE per render commit with every shown id, never once per tile: nine single-id calls would leave eight of the nine warm and evict five of them, which is the same broken deck the bound exists to avoid"* (`desktop/src/lib/bridge.ts:1652-1656`). Exactly two non-test call sites declare a set today — `grep -rn setShownTerminals desktop/src --include='*.ts' --include='*.tsx'` returns the deck's (`desktop/src/App.tsx:340-342`, whose own comment restates the rule and notes that deleting the effect *"does not fail a bridge test"*), the overview's, which declares the empty set (`desktop/src/components/AgentOverview.tsx:610-612`), the type (`desktop/src/types.ts:805`), the hook passthrough (`desktop/src/hooks/useDeckRuntime.ts:269,307`) and the test files.

That second one is the trap in the `from: "overview"` path, and it is a trap by construction rather than by carelessness: the overview declares `[]` on mount while the overlay above it needs `[agentId]`, which is two declarations in one render commit and the exact pattern the contract forbids. **So the shown-set declaration must have a single owner that can see both the base screen and the overlay** — one call, one set, per commit. Getting this wrong does not fail loudly: depending on effect order it produces either an overlay with a dead terminal or an overview that has quietly attached one PTY while its own doc comment says it attaches none. M4 owns it and M8 pins it with a test.

**One xterm per agent, always.** The tile beneath the overlay must not also be rendering a live `TerminalViewport` for the same agent, because two viewports means two WebGL contexts and two `ResizeObserver`s both calling `resizeTerminal(agentId, …)` into a single per-agent coalesced entry (`desktop/src/lib/bridge.ts:2456-2461`) — so the one viewer geometry the daemon holds would ping-pong between tile size and overlay size every frame. The required property is **exactly one live xterm instance per agent at any moment**. Two mechanisms can deliver it and the choice is M3's:

1. **Promote the tile's own element in place** (fixed positioning over the grid, same React subtree). Keeps the xterm instance, adds no WebGL context, costs one `fit()`. Preferred.
2. **Re-parent into an overlay container.** Re-parenting remounts the DOM node xterm is bound to, so the instance is recreated and the transcript re-written client-side (`desktop/src/components/TerminalViewport.tsx:137,167`). No socket churn and no daemon replay, but a visible repaint on both open and close.

A third `TerminalViewport` mounted for an agent that already has one is rejected outright, for the reason above.

### Resizing the PTY, and what a TUI user sees

This is a product decision, recorded as one rather than left to fall out of the implementation.

**Superseded in part by M11 (2026-09-17).** This section describes sizing under PRD #882's smallest-each-axis rule, which is now only the fallback: the daemon gives an agent the last-focused client's viewer size, so a TUI user watching the same agent while the desktop holds focus is handed the desktop's grid and clips where their pane is smaller, rather than being "not asked to render a grid larger than itself". The decision to let the overlay resize stands. What changed and why is in the Work Log entries for [the contract](#2026-09-17--focus-driven-sizing-the-decision-and-the-contract-m11-step-1) and [the sizing rule](#2026-09-17--focus-driven-sizing-the-daemon-rule-m11-step-2).

A PTY has exactly one window size. The daemon negotiates it as **the smallest each axis over every registered viewer**, with the two axes minimised independently, matching tmux's `window-size smallest` (`src/agent_pty.rs:7187-7209`). Viewers are keyed per attach token rather than per client process, precisely because *"One process can hold two views of the same agent (two desktop tiles, or a tile plus the Reader overlay)"* (`src/agent_pty.rs:2084-2095`). The desktop's side of that contract is already written down in `TerminalViewport`: *"`fit()` PROPOSES a size; the daemon disposes"* — the tile measures its box, reports it as a request, then puts the grid back to whatever the daemon last applied (`desktop/src/components/TerminalViewport.tsx:172-211`).

**Decision: let it resize.** Opening the overlay raises this client's requested geometry; closing it lowers it back.

**What a TUI user watching the same agent observes.** Their pane reflows when the overlay opens, and reflows back when it closes. The direction is the safe one and it is bounded — **on the stated precondition that their client has reported an accurate geometry**, which the next paragraph shows is a precondition rather than a given. Under it: because the policy takes the minimum, raising the desktop's request can only raise the PTY *up to* the smallest of the other **reporting** viewers and never past it, so their pane is not asked to render a grid larger than itself and nothing is truncated for them. What they see is output reflowing to a different width, twice per overlay open/close cycle, when the desktop was the constraining viewer. When they are the constraining viewer, they see nothing at all and the overlay renders at their grid with the remainder of its box unused — which is `applyAppliedGrid` working as designed (`desktop/src/components/TerminalViewport.tsx:187-198`), not a bug to file.

**The precondition has two failure classes, and the second one is this app.** `effective_dims` minimises over viewers that have *actually reported a geometry* — *"Only viewers that have actually told us a geometry constrain anything"* (`src/agent_pty.rs:7202-7205`) — and returns `None`, meaning leave the size alone, when none has (`src/agent_pty.rs:7190-7208`). A viewer that is registered but not yet measured is `flatten()`ed away and constrains nothing, so "registers a viewport" is not the line; "has reported a geometry" is.

1. **A legacy or non-participating attach, unconstrained indefinitely.** The doc comment names it — *"an agent whose only client is a legacy one that never registers a viewport"* (`src/agent_pty.rs:7190-7193`). This is the only class the first draft of this section described, and it is not the only one there is.
2. **A current desktop attach, unconstrained until its first measured resize.** A tile very often attaches before `FitAddon` has measured it. When the bridge has no pending or applied geometry it sends no rows and no columns (`desktop/src/lib/bridge.ts:1815-1824`); Tauri then calls `attach_pending_viewport`, which registers a viewer token that *"contributes no constraint until its first resize"* (`desktop/src-tauri/src/terminal.rs:459-474`, `src/daemon_client.rs:1991-2001`). Until `TerminalViewport`'s animation-frame / `ResizeObserver` fit reports dimensions (`desktop/src/components/TerminalViewport.tsx:199-211`) that viewer is ignored by the minimum and can be handed a grid larger than its pane. Transient, and narrower than "every attach": the bridge sends geometry whenever it has a `pendingResizes` or `appliedGeometry` entry for the agent (`desktop/src/lib/bridge.ts:1818`), and `evictTerminal` clears the former but not the latter (`:1716-1741`), so the window is open on an attach for an agent this bridge has **not yet measured** and closed on a re-attach of one it has.

A current TUI is in neither class on its ordinary current-daemon paths: a new pane declares its layout dimensions at attach (`src/embedded_pane.rs:1212-1220`), current-daemon hydration declares the daemon's own recorded geometry (`src/embedded_pane.rs:1532-1556`), and auto-reattach declares the parser's current dimensions (`src/embedded_pane.rs:3053-3062,3097`). Its `None` hydration branch is backward compatibility for a daemon record predating PRD #104's dimensions, not the path a current TUI takes. **So the surviving claim is the narrow one: a viewer is never handed a grid larger than the geometry it last REPORTED — which is the same as "larger than itself" exactly while that report is current, and not while a pane has shrunk between fits — and a viewer that has reported nothing is not protected at all, "has not" including this app's own tiles for the frame or two before their first fit.**

Neither class is created by this feature. Existing tile attach already goes through `attach_pending_viewport`, so the transient window is pre-existing and PRD #882 owns the mechanism. What the overlay does is **exercise** it on a path where it is newly interesting: the overview attaches nothing, so opening an agent from the overview is a **first** attach, which is precisely when the window is open — and the overlay is also the largest single jump in requested geometry the app has. Not fixed here, and not claimed to be.

**The options, and why this one.** Three were available. *Let it resize* gives the user more content, which is the entire point of the feature, at the cost of reflow for other viewers. *Suppress the resize while the overlay is open* — keep reporting the tile's geometry — costs nothing to others and makes the feature a magnifying glass: the same eighty columns at a larger font, in a window that could hold two hundred. That is not worth building. *Scale the overlay to the applied grid and pad* is what the code already does whenever another client constrains it, so it is not a third option so much as the graceful degradation of the first, and it needs no new mechanism.

The trade is stated plainly rather than hidden: **this feature can reflow someone else's terminal.** PRD #882's policy is what makes that merely a reflow instead of a corruption, and the reason it is acceptable is that the smallest-wins rule was built for exactly this — multiple viewers of one PTY, each guaranteed to be on the padding side of a mismatch rather than the truncating side.

### Attach cost and the WebGL question

**What one attach costs**, concretely: one socket per session; an `attach-stream` request, to which the daemon replies OK and *"immediately follows … with a single `KIND_STREAM_OUT` carrying the consistent scrollback snapshot, then enters streaming mode"* (`src/daemon_protocol.rs:67-69`); and a daemon-side task feeding it. Client-side it costs an entry in each of the bridge's per-agent maps and a viewer registration that constrains the PTY's size.

**Steady state with the grid mounted underneath is unchanged from today.** The overlay adds no attach, because it shows an agent that is already shown; that is the whole argument for keeping the grid mounted, and it is why the overlay is cheap in the deck path. In the `from: "overview"` path the cost is one attach **for an agent on the selected deck** — the overview's shown set is empty, so opening one goes from zero attached to one, which is exactly #745's commitment that *"whatever is showing output is what attaches"* and is the minimum the feature can possibly cost. For an agent on another deck it is also **one**, declared against that agent's own deck ([the cross-deck section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships)); it is **zero** only where that deck has no live link to attach over.

**WebGL.** Every mounted `TerminalViewport` allocates an xterm with 8000 lines of scrollback (`desktop/src/components/TerminalViewport.tsx:105`) and attempts a WebGL context in a `try`, falling back to the DOM renderer on throw or on context loss (`:138-153`). #745 records that browsers cap concurrent contexts, that the cap is **unmeasured**, and that PRD #176's M1.3 throughput qualification is still outstanding. That remains true and **this PRD does not measure it**. What it does is avoid making it worse: the one-xterm-per-agent rule above means the overlay allocates **no additional context** over the deck path, and in the overview path it allocates one where the screen previously had none — none at all for an agent on a deck with no live link, whose pane mounts no viewport. So the ceiling is unchanged in the deck path and approached from zero in the overview path. Anyone who wants the number still has to go and get it; this document does not pretend it has been got.

### Cross-deck terminals: the switch is descoped, the ATTACH ships

The overview merges every observed deck's agents into one screen (PRD [#742](https://github.com/vfarcic/dot-agent-deck/issues/742)). Two different things were once true of that: the overview could offer an agent this app could not attach to, and the only idea for attaching it was to move the user's selection. **The second is descoped and the first is no longer true.**

#### What ships

**Every agent the overview lists opens as a working pane with a live terminal, whichever deck it is on.** The pane carries the composite `(deckId, agentId)` through attach, output, input, resize and refit; `desktop_terminal_attach` takes a deck id and `terminal::attach` resolves that deck's link through `DaemonLinks` instead of the process-global `trusted_daemon()`. **The selected deck does not move**, nothing writes `desktop.toml`, and there is no multiplexing: one pane is one stream to a deck this app already holds a tunnel to, over the existing verbs at the existing `PROTOCOL_VERSION`.

This was the product owner's decision, taken after the intermediate "open it, but no terminal" state had already shipped on the branch:

> The point of the overview page is to be able to see all agents of the selected deck or from all decks. It's like a control room… **It's a control plane from which you can access any agent and interact with it.** That makes the desktop app "special" when compared to the TUI. […] Now, if that results in us not being able to open a full agent from the overview page when all decks are selected, I consider it a big failure to meet the idea.

**The no-terminal state was narrowed, not deleted.** It fired for every non-selected deck, which is now false about the ordinary case; what it always also covered is a deck with **no live link** — disconnected, not yet reporting, configured with no address, not observed. There a `TerminalViewport` really would sit black forever, so the pane renders `data-terminal-state="unreachable-deck"` and a `role="status"` sentence naming the deck (`deckName`, matching the overview header and the Deck selector) and repeating that deck's own account of why it is not answering. Everything else in the pane works either way.

**`detach_all` on a selection change went with it.** That rule existed because attach was process-global, so a selection move meant every session was about to be talking to the wrong daemon. A session now names its own deck; what ends one is its deck **leaving the observed set** (`detach_decks_outside`, run unconditionally from `retarget_selection` — a deck can leave without the selection moving), that deck's daemon being stopped or replaced (`detach_deck`), or app exit (`detach_all`, now its only caller).

#### What stays withdrawn, and why the history matters

**Decision 5 was: opening such an agent switches the selected deck to that agent's deck first, reuses the existing single-deck attach, and reverts the selection on close.** It was taken, implemented, audited twice, and withdrawn on the evidence. It is recorded here as taken-and-withdrawn rather than deleted, because the reasoning that made it attractive is still correct and the next person to have the idea should meet what happened to it.

It is not coming back. Attaching on the pane's own deck is what made it **unnecessary** rather than merely unwise: there is nothing left for a selection switch to buy. There is deliberately no "click to switch decks" control in the row or in the pane.

**An earlier attempt gated the open CONTROL instead, and that was wrong too.** It rendered no open control on a non-selected deck's row and a two-word `other deck` marker in its place. A listed agent with no way to open it is a dead row, and it is worse than it sounds because nothing on a row tells a reader which deck they are pointing at — the refusal was legible only to someone who already knew the answer.

#### The two audit rounds, and how each finding is closed

Two independent read-only security audits found **the same defect shape twice**: *state created under deck A is later attributed to deck B, because identity is read from the current selection at use time rather than captured at creation.* Cross-deck attach could not be built over any of it, so all of it is closed here rather than deferred to [#1073](https://github.com/vfarcic/dot-agent-deck/issues/1073).

- **Round 1** found bare-id storage keys — `terminalFeed`, `terminalInputResults` and `appliedGeometry` — plus a pane that could be retargeted to another deck's namesake through the still-focusable base screen. Both were fixed then and are kept.
- **Round 2**, against the commit that fixed round 1, found four paths the storage-key fix does not reach, carried forward as [#1116](https://github.com/vfarcic/dot-agent-deck/issues/1116). Each is now closed:

| round-2 finding | what closed it |
|---|---|
| the terminal stamp identified the deck selected when `deliverTerminal` **ran**, not the deck that created the channel | `deliverTerminal` takes the origin target as a parameter; every producer holds it in scope from before the attach was invoked |
| a pending attach from the previous deck installed into the bridge's bare-id `sessions` map and took `sendTerminalInput` | it installs under its **own** deck's composite key — the pane that asked for the stream is still showing it — and `sendTerminalInput` resolves by composite **value** |
| `TerminalViewport` reused one xterm and its rendered scrollback across a deck change | `deckId` is a dependency of the build effect, and `terminalRegistry`/`registerRefit` are keyed `(deckId, agentId)` |
| a late geometry event repopulated the cache `adoptGeometryDeck` cleared, under the new deck's identity | the geometry listener resolves its session by **session id** and notifies with that session's creating deck; `adoptGeometryDeck` is deleted, because clearing was never an identity boundary |

Three more fell out of the same work: `insert_unique_session` evicted by bare agent id and closed another deck's live pane; `terminal::resize` resolved its daemon from the applied selection and could send this pane's grid to another machine's PTY; and a deck id arriving from the webview is now matched against `observed_decks()` rather than trusted as an address.

**Every one of those is mutation-checked** — the fix broken alone, a named test confirmed red, the fix restored — because a test written alongside a fix that passes either way is what this branch had already been caught by three times.

#### What the descope still removes, which was a user-visible cost

The withdrawn implementation wrote the selected deck through `desktop_set_settings` on open and wrote it back on close. That command **persists the document to disk** and then applies it, and the apply path tore down every terminal session. So the path cost a full teardown in each direction plus two persistent writes, and because the crate re-reads the file into a `toml::Table` and re-emits it with `toml::to_string_pretty`, a hand-formatted or commented `desktop.toml` was **reformatted by the first cross-deck open and not restored by the close**. Nothing about opening or closing a pane writes the settings document now, pinned by `writes no settings document when a pane opens or closes` (`desktop/src/AgentPaneDeckIdentity.test.tsx`). The residue after an *unclean* exit goes with it: there is no longer any selection for a kill to leave moved.

#### The composite keying, and what it alone did not close

Round 1's keying fix is **kept**, and this is the part that must not be over-claimed (CLAUDE.md rule 17; this branch has been corrected for exactly this three times).

**It fixes a pre-existing defect the overlay did not cause.** The reproduction needs no overlay at all: with two decks running a `planner` each, stream a sentinel into deck A's, switch decks with the ordinary `DeckSelector`, and deck B's same-id `planner` came up carrying A's retained scrollback under B's correctly resolved heading.

**What it does on its own:** a fresh mount reads the buffer, the verdict and the applied geometry belonging to the deck it names. **What it does not do on its own:** any of round 2's four items, which needed the origin stamping above. `docs/develop/desktop-gui.md` was titled *"The composite identity goes part of the way down"* for exactly that reason; it is now *"all the way down"*, and the sentence that renames it is the table above rather than the title.

Two other round-1 fixes are kept for reasons that survive all of this, and both are recorded here so they are not reverted as cross-deck machinery:

- **`useInertBackground` and focus containment.** `AgentPaneFrame` claims `role="dialog"` with `aria-modal="true"` over a base screen that is deliberately still mounted, and that claim has to be honoured whatever the deck story.
- **The composite render match in `DeckSurface` and the `DeckShell` close-on-mismatch effect.** A **deck-origin** pane means "this agent, on the deck you are looking at", and the deck surface renders the selected deck and nothing else — so when the selection moves under it that claim stops being true of anything on screen and the pane closes. An **overview-origin** pane makes no such claim and keeps its deck; the two rules are deliberately different and the difference is the screen underneath.

### Cross-version safety

Per CLAUDE.md rule 12, answered explicitly rather than as a formality, and verified against what the work actually touches rather than assumed from its shape.

**Scope of this section: M1–M10 and the cross-deck attach. M11 (focus-driven sizing) changes the daemon and the protocol, so every "no" below is about the earlier work only.** M11's rule-12 answers are in its [Work Log entry](#2026-09-17--focus-driven-sizing-the-decision-and-the-contract-m11-step-1).

**The answer is still no, and it stopped being the free answer.** Every milestone up to M10 was TypeScript under `desktop/src/`, which made the question trivial; the cross-deck attach is the first change on this PRD to touch `desktop/src-tauri/`. Re-asked from the rule's own definition rather than inherited:

- **Did the TUI↔daemon contract move?** No. Not one byte of `src/daemon_protocol.rs` changed, and no frame, field or verb is new. `terminal::attach` calls `attach_as_viewer` / `attach_pending_viewport` and `terminal::resize` calls `resize_agent_as_viewer`, exactly as before. **No `PROTOCOL_VERSION` bump**, and no semantic break behind a stable wire either — the meaning of every field the daemon sees is unchanged.
- **Is there a new daemon-facing BEHAVIOUR?** Yes, and it is worth naming rather than hiding: this app can now hold attach streams to **more than one daemon at once**. Each is an ordinary single attach on its own connection, which is what `DaemonLinks` and `EndpointTunnels` have done for snapshots since PRD #742; no daemon can tell the difference between this and two desktop apps. That is why it is not multiplexing and needs no stream id.
- **Does the webview IPC DTO boundary count as a contract under rule 12?** No, and the reasoning is the rule's own: rule 12 defines a break as *"an older and a newer build can no longer safely interoperate"*, and the webview bundle and the Rust binary are built, versioned and shipped as one artifact. There is no configuration in which an old bundle meets a new binary. `desktop_terminal_attach` gaining an **optional** `deckId` would be a compatible widening even if there were. **No `.breaking.md` fragment.**
- **Is the cross-version manual test owed?** The rule requires it for a change to *"the daemon, the TUI↔daemon protocol, orchestration, or hooks"*. This change is to a daemon **client** and touches none of the four. It was **not run**, and that is stated rather than implied. What it would exercise — a branch TUI against a previous-release daemon — has no path through this code: the desktop app is not the TUI, and the daemon side is untouched.

**What did move into the Rust gates**, which the earlier answer named as a consequence and which has now happened: the change is under `cargo test-fast`, rule 2's clippy gate and `cargo xtask linkage-check`, and it arrives with nine Rust tests in `desktop/src-tauri/src/terminal.rs` (per-deck endpoint resolution and its refusal, the composite session registry, the three deck-scoped detach verbs and the two `retarget_selection` call-site rules, and the per-deck resize).

### Feature flag

CLAUDE.md rule 9 asks whether a new user-visible surface ships behind `experimental`. The answer is **no**, and it is a recorded answer rather than a fresh judgement. PRD #176 decision 6 settled it for the entire desktop binary (`prds/176-desktop-gui.md:101`): the flag is a presentation switch gating render and input seams inside the *TUI* binary, a separate GUI binary has no such seam because building and running it is itself the opt-in, and maturity is handled by packaging. #745's **Feature flag** section restates the mechanics and adds the confirming detail — the desktop crate links the root library so `features::experimental_enabled()` is callable, but `run()` never calls `init_and_watch`, so it would read the OFF default forever, and the desktop's only notion of a project directory is a development convenience with no good answer for a packaged app.

Nothing about this PRD reopens that. No wrapper function, no `graduate-` follow-up issue.

### Testing: what rule 4 means here

Rule 4 is written in the TUI's vocabulary — L1 (`insta` + `TestBackend`) and L2 (PTY + vt100, `e2e_*.rs`). This feature lands in the Tauri app, so the mapping is stated rather than assumed, following #745's section of the same name.

- **L1 equivalent: vitest + jsdom + Testing Library** (`pnpm test`, `desktop/package.json:14`), rendering the real components against a hand-built runtime. This is where the substance of this feature is provable: that both entry points produce the same component, that the shown set is declared once per commit with the right ids, that closing restores the originating view, and that the overlay mounts no second `TerminalViewport` for an agent that already has one.
- **Browser tier: Playwright over the built bundle** (`pnpm test:browser`, `desktop/e2e/*.spec.ts`, types via `pnpm test:browser:types`), driven through the fixture query strings in Chromium and WebKit with no daemon involved. This is where geometry and layout claims belong — that the overlay actually occupies the window, that the grid beneath is not unmounted, that `Esc` closes it.
- **The Rust half runs under `cargo test-fast`** if any is touched. Per [Cross-version safety](#cross-version-safety) the plan is that none is; if a DTO field turns out to be needed, that half arrives with a `dto.rs` shape test.
- **Nothing drives the real Tauri window.** There is no `tauri-driver` and no WebDriver session in this repository ([#953](https://github.com/vfarcic/dot-agent-deck/issues/953)), so real IPC, a real xterm over a real PTY, and the distribution's own WebKitGTK or WKWebView are exercised by nothing automated — `docs/develop/desktop-gui.md:943` says so in those terms. **This is not rule-4 parity and is not claimed as such.** The compensating control is the manual smoke check (`docs/develop/desktop-gui.md:1042`), which M10 extends to cover opening an agent from each screen, resizing, and closing back — and which, like every manual check, decays.

**The two things no automated tier here can prove**, stated so nobody reads green checks as covering them: that a real PTY genuinely resizes when the overlay opens, and what a TUI user attached to the same agent sees while it does. Both are manual, both are in M10's smoke check, and the second one needs two clients on one agent.

## Success Criteria

- An agent can be opened enlarged from the deck and from the overview, and both produce the same component — provable by the component's own identity in the test, not by inspection.
- Opening and closing the overlay over the deck causes **zero** attaches, **zero** detaches and **zero** scrollback replays, asserted at bridge level rather than observed.
- `setShownTerminals` is called exactly **once** per render commit in every overlay path, including the one where the base screen is the overview, with the whole shown set.
- The overlay renders more of the agent's output than the tile does — a genuinely larger grid — whenever no other attached client constrains it.
- Closing returns to the screen the user opened from, with the deck's scroll position, selection and panel state intact.
- The overview's cards still mount no terminal and the overview still attaches nothing until an agent is opened.
- **Every agent the overview lists opens with a LIVE terminal, whichever deck it is on** — output, keystrokes, resize and refit all addressed to that agent's own deck, with two decks' same-id agents attachable at once ([why](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships)). The selected deck does not move. Opening or closing a pane writes the settings document **never**, from any screen, and nothing in the pane offers to move the selection. A pane says it has no terminal only where its deck has no live link, and then names the deck and repeats that deck's own failure.
- No new component renders an agent pane. The diff adds props to `AgentTile`; it does not add an `AgentTileLarge`.

## Risks

- **The fork happens anyway.** The single most likely failure is that someone finds one difference that is awkward as a prop and writes `AgentTileOverlay` "for now". Everything else in this PRD survives being done imperfectly; this does not. M1 exists to make the differences explicit before either size is written, and the success criterion is stated as a property of the diff for the same reason.
- **The grid is unmounted under the overlay "to save resources".** It is the intuitive optimisation and it is backwards. Unmounting by itself declares nothing, so what costs is the replacement declaration: a direct nine-to-one declaration evicts **five** past `MAX_WARM_TERMINALS` and buys five scrollback replays on close, and an empty declaration evicts **all nine** and buys nine. The saving is real and the cost is the exact thing the feature is for.
- **Two `setShownTerminals` calls in one commit, silently.** The overview declares `[]` on mount and an overlay above it needs one id. Nothing fails loudly: depending on effect ordering the result is a dead overlay terminal or an overview that has attached a PTY while claiming it attaches none. M4 and M8 are the whole defence.
- **A second `TerminalViewport` for an agent that already has one.** Two WebGL contexts and two `ResizeObserver`s writing one coalesced per-agent resize entry, so the daemon's viewer geometry oscillates. It would look like an intermittent reflow rather than like a wiring mistake, which is what makes it expensive to find later.
- ~~**The cross-deck path is a different feature wearing the same button.**~~ ~~**A crash while a cross-deck overlay is open leaves the selection moved.**~~ Both **retired**: nothing moves the selection and nothing writes the settings document. Two smaller ones replace them, named rather than hidden. **This app now holds attach streams to several daemons at once**, so a hung or slow remote deck is reachable from a screen the user thinks of as local; each stream is an ordinary attach on its own connection, but the failure modes of a remote deck are now in front of a user who did not select it. And **a deck that stops answering under an open pane replaces its terminal with a sentence** rather than closing the pane — better than a black rectangle, and still a pane that cannot do the thing the user pressed a maximise control for.
- **Reflowing someone else's terminal.** A TUI user watching the same agent sees their pane reflow when a desktop user opens an overlay, with nothing on their screen explaining why. Bounded by the smallest-wins policy so nothing is truncated for a viewer that has **reported** a geometry — and not bounded at all for one that has not, which covers a legacy client indefinitely and **any** current client, this app's own tiles included, until its first measured fit. That is PRD #882's pre-existing exposure rather than something this feature introduces; the overlay's contribution is to exercise the first-attach window again on the overview path and to make the largest single jump in requested geometry the app has. A genuine cross-client side effect, chosen knowingly. **Widened by M11:** under focus-driven sizing the unfocused client is handed the focused client's grid and clips where its pane is smaller — including a TUI from before M11, which cannot claim focus back (`changelog.d/1105.breaking.md`).
- **The WebGL ceiling stays unmeasured.** This work does not raise the context count in the deck path and adds one in the overview path, and it measures nothing. #745 and PRD #176 M1.3 both still want the number.
- **The real window is still driven by nothing.** Every automated tier here runs in jsdom or a browser. The overlay's interaction with real WebKitGTK, a real PTY and real IPC is covered by a manual check, and manual checks decay.
- **Scope creep into the group view.** "While we are here, the deck filtered to one orchestration is nearly free" is how #745's iteration 3 gets half-built by a PRD that said it would not build it. The line is: this adds one view variant for one agent.

## Open Questions

1. **Does the overlay eventually replace `OutputReader`?** The Reader is a resolved-text projection with reflowed lines and a copy control (`desktop/src/components/OutputReader.tsx:16-28,78`); the overlay is a live terminal. They answer different questions today. Once the overlay exists, whether the Reader is a *mode* of it, a control inside it, or a fourth surface that should have been retired is worth deciding deliberately rather than by accumulation. Not decided here; deliberately not pre-empted either.
2. **~~Should cross-deck opening be explicit?~~ ANSWERED: the click always works and the pane just works.** The question offered three options — implicit with honest feedback, confirm before switching, or *"disable the click for non-selected decks until #1073 lands"*. The third was shipped first and reversed; the first was then shipped as a pane that explained why it had no terminal; and what finally shipped is neither, because the premise under all three — that a non-selected deck's terminal cannot attach — stopped being true. The pane attaches on its own deck, so there is no feedback to be honest about and nothing to confirm. What survives of the question is the deck with **no live link**, where the pane says so; [the section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) has the sequence.
3. **~~What does the overlay do when its agent disappears?~~ ANSWERED: the view closes, and the two conditions that decide it are `paneAgentRetired` and `paneDeckAttachable`.** The daemon can end an agent while it is overlaid; "closing back to a deck that no longer has that tile is probably right" is now the decision, taken on the argument that *everything* the pane renders is a property of the agent record — heading, role, status, prompt, tool, the five tabs — so an ended state would have to be built from a view carrying two ids and a `from`. It is also the answer already given one condition away, where `deckPaneRetargeted` closes rather than suspends. The **visual** alternative is not foreclosed: an explicit ended state can replace the close later without moving either condition.

    **The reason this paragraph gave for downgrading the declaration half to an edge case was wrong, and that is the part worth keeping.** It claimed *"the stray attach is reconciled by a later `End`"*. The `End` is what **starts** the repetition: `handleTerminalState` removes the agent from `attached`, `useShownTerminals` keys its effect on the joined `(deckId, agentId)` string so a vanished agent never changes it and nothing re-fires to withdraw the declaration, and `subscribe`'s `desktop://snapshot` listener re-runs `attachAgents` over the whole standing shown set on **every** snapshot (`desktop/src/lib/bridge.ts`). So the agent cleared `attachAgents`' filter afresh on each snapshot, and each pass took the process-wide `attach_gate` and opened a socket for an agent that no longer exists — serialising against the attaches of panes that do, and over `ssh` behind a handshake that can hold that gate for tens of seconds. A repeat per snapshot for as long as the stale view is open is a defect, not an edge case.

    Two things the fix deliberately does not do. It does not close when the pane's deck is merely **not answering**: both empty agent lists in the crate are on that path (`disconnected_snapshot`, and `snapshot_with`'s non-connected early return) and `mapDesktopSnapshot` carries none over, so "the agent does not resolve" is also what a blink looks like — and closing on it would contradict this PRD's own decision that such a deck replaces its terminal with a sentence rather than closing the pane. And it does not make that sentence **reachable**, which is a second, smaller gap the work uncovered and left open: the state needs an agent record, a deck with no live link supplies none, so the pane is not rendered at all while the deck is away. What the fix guarantees there is that the *view* survives, so the pane returns intact when the deck does. Holding the last known record for an open pane would make the state renderable and is its own product call; filed as issue #1143.
4. **Does the overlay get its own keyboard surface beyond `Esc`?** Next/previous agent without closing is the obvious ask, and it interacts with the shown set — stepping through nine agents one at a time is exactly the pattern the warm-set bound was sized for. Worth deciding before it is discovered.
5. **Carried forward from #745, and now answered — recorded here so it is not re-asked.** #745's open question 2 (two paths to the agent view, and the back behaviour each implies) is answered by the `from` field on the view variant: back behaviour is carried in the view value. #745's open question 3 (detach policy on leaving a terminal) was already settled in its own implementation — the warm set with `MAX_WARM_TERMINALS = 3` is the MRU-with-a-small-fixed-bound it was leaning toward — and this PRD depends on that answer rather than revisiting it. #745's open question 1 (does the group view mount a terminal per member) stays open, with the group view.

So the variant carries `from` and `DeckShell` renders the base screen *with* the overlay rather than instead of it. This is the single structural constraint the rest of the design hangs off. (Corrected below: this paragraph originally said "evict six", and attributed the eviction to the unmount rather than to the declaration that replaces it.)

*The two hard parts are coupled, and the coupling runs the opposite way to intuition.* Keeping the grid mounted is what makes closing free; a mounted tile rendering its own `TerminalViewport` for the overlaid agent is what would make the resize incoherent, since the bridge holds one session and therefore one viewer token per agent (`desktop/src/lib/bridge.ts:2456-2489`) and the daemon minimises across viewers (`src/agent_pty.rs:7201-7209`). The resolution is "grid mounted, one xterm per agent" — both properties, at the cost of one rule that has to be enforced by a test rather than by structure.

*The cross-deck path is not the cheap reuse it reads as.* Decision 5 says "switch the selected deck first, reusing the existing single-deck attach", which sounds like a state flip. It is a settings-document write persisted to disk (`desktop/src-tauri/src/lib.rs:1422`) whose apply path calls `terminal::detach_all` when the deck moves (`:1513-1516`), and `apply_selection`'s own doc comment says the switch half *"detaches every terminal session"* (`:1440-1442`). The decision stands — it genuinely needs no wire change and no bump, which is what it was taken for — but the PRD scopes the no-flicker commitment to the same-deck path and states the cross-deck cost outright.

**One observation about identity, originally written up as a defect.** The revert does not re-declare the shown set on its own. This entry originally continued "and the restored deck keeps tiles whose sessions the switch tore down", and **that consequence is false**; the correction and what replaced it are in the reconciliation entry below.

**Not claimed, deliberately.** The WebGL context cap is still unmeasured and this PRD does not measure it. The real Tauri window is still driven by nothing automated. And this PRD takes one of #745's iteration 3's four parts, so #745's iteration 3 is still open after this ships.

### 2026-09-15 — M4 and M6: one owner, and what the ordering test found

**M4 — the shown set has one owner per mounted screen tree, and the two trees are mutually exclusive.** The mechanism is [`useShownTerminals`](../desktop/src/hooks/useShownTerminals.ts), which holds the ref-and-key effect that was inline in `DeckSurface`; `DeckSurface` calls it for the deck's set and `DeckShell` calls it for the overview's. `AgentOverview` no longer declares anything for itself, and its former effect is replaced by a comment saying it must not start again. The `from: "deck"` path keeps the property worth keeping: opening the pane changes neither `snapshot.agents` nor `tabs`, so the key is unchanged and **no call is made at all** on open or on close — now asserted rather than merely arranged (`does not redeclare the unchanged deck shown set while the pane opens or closes`).

The one thing worth reading twice is the third state. `undefined` means *"not the owner right now"* and makes no call; `[]` is a real and very expensive declaration, since it flushes the warm set to zero. Collapsing the two — the obvious `agentIds ?? []` — would make the commit that hands ownership from `DeckShell` to `DeckSurface` detach every terminal the deck is about to declare. So the dependency key is `agentIds?.join(…)`: `undefined` for no declaration, `""` for "nothing is shown".

**M4 also gained a condition that is not tidiness: an agent is declared shown only once its deck IS the selected one.** `terminal::attach` attaches against `trusted_daemon` — whichever deck is linked at the instant it runs — and agent ids are per-daemon monotonic integers. So declaring `[agentId]` for a cross-deck pane while the previous deck is still in force does not attach early; it attaches *that* deck's agent of the same id, on another machine, under the right name. The two-deck fixture in `CrossDeckAgentPane.test.tsx` (since renamed `AgentPaneDeckIdentity.test.tsx`) has a `planner` on both decks, which is the ordinary case rather than a contrived one. On the same-deck path the condition is already true when the pane opens, so it costs nothing there.

**M6 unconditional half — switch, revert, and the document restored.** (**All of this was withdrawn on 2026-09-16** — see that entry. `useCrossDeckSelection.ts` and `selectionForDeck` are no longer in the tree; the paragraph is kept as the record of what was built and measured.) `useCrossDeckSelection` writes the selection through `settings.save` (`desktop_set_settings`) when the pane's deck is not the selected one, captures the token that was in force, and writes it back on close. Both writes route through `endpointSectionToSave`, so a selection move asserts nothing about the stored rows, and a round trip that changes nothing else leaves the document equal — asserted as a `JSON.stringify` comparison rather than a field-by-field one. (This entry claimed "byte-identical" and the test was named for it; both were narrowed by the security audit, because what round-trips is the **DTO** and not the file. See the entry below.) The costs the [cross-deck section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) states are unchanged and are not claimed away: two persistent writes, and a full `detach_all` in each direction.

**Mapping a deck back to a stored row is by LABEL, and it refuses rather than guesses.** Nothing on this side can invert `EndpointIdentity::wire_id()`, so `selectionForDeck` matches `Endpoint::describe()` — which `describeEndpoint` derives from a row byte for byte, and which is what the Deck selector's own menu is built from. The connectable set is the local deck plus every row with a socket path, so a label matching **exactly one** row identifies that deck with certainty. Two rows differing only in socket path, identity file or jump host describe identically; there it returns `undefined` and **nothing is switched**, because selecting the wrong row would attach a different machine's agent of the same id under the right name. The visible cost of refusing is a pane whose terminal never attaches, which is a nuisance a user can see; the cost of guessing is not visible at all. Note it is exactly as precise as the control it automates — two colliding rows are already two identical entries in that menu.

**M6 conditional half — the ordering test was written, and NOTHING was built off it.** The milestone asked whether a user-visible stale interval exists across the overview round trip before any repair was written. The test is `declares no terminal on the pane's deck until that deck is the one in force`, and it was checked against its own absence: reverting the deck-match condition above turns it red (two declarations where one is expected), so it discriminates rather than describing an arrangement nothing would have broken.

**What it found: no user-visible stale interval on this path, so no bridge repair exists in this change.** No explicit selection generation, no deck-change invalidation, no composite React dependency. Three facts carry it. The overview's shown set is empty, so the switch's `detach_all` has nothing of this app's to tear down and produces no `End` for the pane's agent — the adverse "snapshot before `End`" ordering the [cross-deck section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) names has no stale `attached` marker to filter. `evictTerminal` is synchronous up to its `desktop_terminal_detach`, so even arriving at the overview from a nine-tile deck leaves `attached` empty *before* the later one-agent declaration is made, rather than leaving a marker for the declaration to trip over. And the declaration for the pane is made only after the switch has landed, so it attaches against the deck it names. The bridge side of that sequence was already pinned by M7's `attaches exactly one terminal for an overview-origin overlay`, which is the same `[] → [one] → []` shape, so it is not re-pinned here.

The honest reading of this is not "the risk was imaginary". It is that the risk lived one layer up from where the milestone expected it: not in the bridge's reconciliation, but in *when* the declaration is made. The condition in M4 is what closes it, and it is there for a correctness reason that stands on its own — a wrong-deck attach is not a promptness problem.

**The composite identity reaches the pane's own lookup, not only its shown set.** `OverviewAgentPane` resolved its agent by bare id out of the *selected* deck's snapshot, which on the cross-deck path finds the namesake on the deck being switched away from. It now resolves the fleet entry named by `view.deckId` and takes the agent and the evidence from it, which is what the variant carries a `deckId` for. The rest of the bare-id maps the PRD declines to fix — `terminalFeed`, `terminalInputResults`, `appliedGeometry` — are untouched and still bare. **That decline was reopened and reversed by the security audit; see the entry below.**

**Capability asymmetry between the two entry points, recorded as accepted rather than fixed.** The overview-origin pane is not given `onRename` or `onEvidenceSelect`, so it renders no rename control and selecting a handoff's evidence does nothing. Both are capabilities the screen genuinely lacks rather than presentation differences, which is why neither is expressed through the `presentation` prop: the evidence drawer is the deck's and no screen is mounted underneath that could open it, and a rename reports its outcome through the deck's **toast**, so wiring it here would fail silently. Closing the rename half needs `DeckShell` to grow a notice surface of its own, which is a new user-visible surface and therefore CLAUDE.md rule 9's question — beyond this PRD. ### 2026-09-16 — The security audit: two cross-deck identity blockers, and a reopened decision

An independent security audit of M1–M9 found **two blocker-class defects**, both of one shape: a pane showing or writing **another deck's agent** under the identity the user believes they opened. Neither needs a contrived fixture — agent ids are per-daemon monotonic, and the two-deck fixture this PRD already built has a `planner` on both decks.

**The decision this reverses, and why reversing it was right.** PRD #745 left nine maps keyed by bare agent id. #1105 fixed the ones the pane's own lookup needed and **explicitly declined** `terminalFeed`, `terminalInputResults` and `appliedGeometry`, on the reasoning recorded in the M4/M6 entry above: a tile's terminal is always the selected deck's and the overview mounts none, so nothing could put a second deck's agent in front of them. That reasoning was sound and this feature is exactly what falsified it. A cross-deck pane **is** a second deck's agent in front of them, and the decline stopped being defensible the moment the pane shipped. All three are now keyed by the composite `(deckId, agentId)` end to end, through [`agentKey`](../desktop/src/lib/agentKey.ts).

**Blocker 1 — a deck-origin pane could be retargeted to another deck's namesake, keystrokes included.** `AgentPaneFrame` declared `role="dialog"` and `aria-modal="true"` over a base screen that is deliberately still **mounted**, so every control behind it kept its place in the tab order — including the `DeckSelector`, which retargets the whole app. Selecting another deck there left `DeckShell` holding the old view value while passing only a bare `openAgentId` into `DeckSurface`, so the arriving deck's same-id agent was promoted into the open pane, snapshot reconciliation attached its session, and `sendTerminalInput(agentId, data)` resolved the bare-id session now belonging to it. Same role, same display text, no deck identity anywhere in the dialog.

Two protections, as the audit required, because they close different things:

1. **The base screen is genuinely inert.** [`useInertBackground`](../desktop/src/hooks/useInertBackground.ts) walks from the pane's element up to `document.body`, marks every element that is not an ancestor of it `inert`, and moves focus inside. Marking one subtree was not available — `inert` is inherited and no descendant escapes it, and on the deck path the pane *is* a tile inside the base screen, promoted in place so its xterm survives. Walking siblings is also what keeps it from rotting: a region added to the deck later is covered with no edit to the hook. The effect has no dependency array on purpose, so background content that arrives while the pane is open is marked on the commit that adds it.
2. **A deck-origin pane is fenced on identity and CLOSES.** A deck-origin pane means "this agent, on the deck you are looking at", and the selection can still move for reasons that are nobody's gesture — a `selectionFallback`, another window writing the settings document. Closing was chosen over suspending because it leaves nothing to be wrong about: a suspended pane still has to say whose agent it is showing, and the honest answer is nobody's. **The render does not wait for the effect**: `DeckSurface` takes an `openAgent` composite and promotes a tile only on the full `(deckId, agentId)` match, so the mismatched commit shows no pane at all rather than showing the wrong one for the frame before `useEffect` runs.

**Blocker 2 — the overview path replayed the previous deck's terminal buffer under the new agent.** `OverviewAgentPane` resolved heading and session by composite identity but passed the process-wide `terminalFeed`, whose buffers were keyed only by `agentId`. Leaving deck A detaches A's sessions and clears **no buffer**, so opening deck B's same-id agent mounted a `TerminalViewport` whose initial `terminalFeed.get(agentId)` read A's retained bytes and whose `!previous` branch wrote them into the new xterm — up to the feed's 1 MiB retention of another machine's output, under B's correctly resolved heading, with B's transcript empty. On a successful switch B's own `replace` frame eventually resets it; on a refused switch, a failed save or a failed attach, nothing ever does.

**M4's deck-match condition is correct, is kept, and does not cover this** — the audit is explicit and it is right. The viewport's backlog read happens at **mount**, before anything is attached at all, so delaying the declaration protects an attach that was never the problem. The fix is in the state: `TerminalFeed` takes `(deckId, agentId)`, `AgentTile` supplies `agent.daemonId` (the agent's **own** deck, never the selected one), and `TerminalChunk` carries a `deckId` stamped by the bridge at `deliverTerminal` — the single funnel every chunk passes through, and the only place that can name the deck the bytes came from, since `selectedDeckId` there is read off `fleet[0]` on every snapshot while React's copy is a commit behind.

**The two should-fixes on the same root cause.** A verdict recorded for deck A's `planner` could disable deck B's pane and print A's rejection notice under B's heading; `appliedGeometry` is removed by no per-agent eviction, so B's pane applied A's grid and an attach that beat the pane's first fit submitted A's cached dimensions to B — which the daemon's smallest-viewer policy turns into a real, transient reflow of B's PTY and of every other client attached to it, from a viewport on another machine. Both maps are keyed the same way now, and the bridge's own bare-id `appliedGeometry` cache is emptied on a selection change by `adoptGeometryDeck`, beside `adoptEvidenceDeck`.

**The byte-identity claim was narrowed rather than defended, and the consequence is now stated where a user meets it.** (Moot after the 2026-09-16 descope: there is no automatic switch and no write. Kept as the record of the correction.) `CrossDeckAgentPane.test.tsx`'s `onDisk` is an in-memory object and its assertion compares two **mocked** saves, so what it establishes is that the settings **DTO** round-trips unchanged, remote rows included. Production `desktop_set_settings` re-reads the TOML into a `toml::Table` and writes `toml::to_string_pretty`, which represents neither comments nor the original layout — so a hand-formatted or commented `desktop.toml` is reformatted by the first automatic cross-deck switch and the write on the way back restores nothing. The test is renamed (`…restores the settings DTO unchanged on close`), and the real consequence is written into the changelog fragment, the overlay section of `docs/develop/desktop-gui.md` and step 7 of the manual smoke check, which no longer implies an empty `diff`. Making the crate preserve formatting was deliberately **not** attempted; it is a much larger piece of work than this feature.

**The Escape absolute was made true rather than documented as false.** The PR review found that `presentation="overlay"` gates the Reader on the tile being *promoted* and says nothing about the other tiles the pane is drawn over, which stay at `"tile"` and keep any Reader they already had — mounted behind the scrim with its own `window` listener. Reader on tile A, pane on tile B, one `Escape`, both closed. `panePresent` is the screen-wide gate that closes it; the two stay separate props because one is a fact about this box and the other about the screen. It **dismisses** rather than hides, since a Reader restored on close would answer the next `Escape` instead of the deck. The comments in `App.tsx` and `AgentTile.tsx` now say which gate covers which route.

**Every fix has a test that fails without it, and the two blockers were mutation-checked from the audit's own scenario.**

| fix | guard | mutation result |
| --- | --- | --- |
| inert base screen | `makes the whole base screen inert while a pane is open…` (vitest) and `contains Tab inside the pane…` (Playwright, both engines) | hook removed → both red; the browser one proves what the attribute *does*, which jsdom cannot |

The blocker-2 test drives the **real** `useDeckRuntime` and the **real** `TerminalViewport` against a recording xterm, so it reproduces the disclosure rather than the fix's shape, and it carries its own positive control: the same buffer still reaches the deck it belongs to.

**Where the audit is challenged.** Nowhere on the defects — both reproduce exactly as described, and the mutation runs above are the evidence. One claim in it is narrower than written: `terminalInputResults` having "no bounded clear" on a refused switch holds only for as long as no snapshot arrives, since `adoptFleet` drops **every** recorded verdict on each fleet emit, and a live deck emits often. That changes the severity of that one should-fix and not the fix, which is the same composite keying the blocker needed.

**Rule 12: no.** Every file in this change is TypeScript, TSX or Markdown. Nothing touches the daemon, the TUI↔daemon protocol, orchestration or hooks; no Rust file is modified at all, `desktop_set_settings` is unchanged, and the `deckId` added to `TerminalChunk` and to `TerminalFeed` is an in-process frontend shape rather than a wire one. No `PROTOCOL_VERSION` move, no `.breaking.md`, no cross-version manual test.
### 2026-09-16 — Decision 5 withdrawn: cross-deck opening is descoped

**The user's decision, taken after a second independent audit found that the first round's fix had not closed the blockers.** Cross-deck opening is removed from this PRD. It is recorded as *taken, attempted and withdrawn on evidence* rather than deleted, because the reasoning behind it is still correct and the next person to have the idea should meet what happened to it. [The section](#cross-deck-terminals-the-switch-is-descoped-the-attach-ships) carries it; this entry is the account of how it got there.

**The pattern across both rounds is one shape, and that is what made a third round of repairs the wrong answer.** *State created under deck A is later attributed to deck B, because identity is read from the current selection at use time rather than captured at creation.* Round 1 found bare-id storage keys — `terminalFeed`, `terminalInputResults`, `appliedGeometry` — and they were fixed. Round 2, against the commit that fixed them, found the **stamping** and **lifetime** layers doing the same thing one level up, where a storage key cannot reach:

- the terminal stamp identifies the deck selected when `deliverTerminal` runs, not the deck that created the channel, so a late frame from A is stamped B and filed under B's correct composite key;
- a pending attach from the previous deck can still install into the bridge's bare-id `sessions` map and take `sendTerminalInput`;
- `TerminalViewport`'s xterm build effect depends only on `agentId`, so an in-place deck change reuses the instance and its rendered scrollback;
- a late geometry event from the previous deck can repopulate the cleared cache under the new deck's identity.

Each needs an origin deck or a selection generation captured with the channel, attempt or session and checked through installation, delivery and write authority — which is the identity boundary **cross-deck attach** has to draw anyway ([#1073](https://github.com/vfarcic/dot-agent-deck/issues/1073), a `PROTOCOL_VERSION` bump by construction). Doing it inside a PRD about a pane would have been building #1073's hardest part under another issue's number. [#1116](https://github.com/vfarcic/dot-agent-deck/issues/1116) carries all four forward with their `file:line` evidence and the sentinel reproduction.

**What was removed.** `desktop/src/hooks/useCrossDeckSelection.ts`; `selectionForDeck` in `desktop/src/lib/endpoints.ts` (its only caller was that hook — `DeckSelection` and `LOCAL_DECK_SELECTION` stay, since `DeckSelector` and `parseSelection` use them); the `desktop_set_settings` write on open and on close, and with it **the `desktop.toml` rewrite entirely** — a user-visible side effect this PRD was about to document rather than fix. Three tests went with the behaviour: the round trip and its DTO-identity assertion, the ambiguous-label refusal, and the M6 ordering test. `CrossDeckAgentPane.test.tsx` is renamed `AgentPaneDeckIdentity.test.tsx`, which is what its surviving seven tests are about.

**What ships instead, and why not a disabled control.** *(Superseded the same day — see [the next entry](#2026-09-16--the-descope-went-too-far-every-listed-agent-is-openable-again). The row behaviour below is what was built and then reverted; the test it names no longer exists.)* An overview row whose agent's deck is not the selected deck renders **no open control at all**; a short `other deck` marker carrying the reason in its `title` stands where it would be. A `<button disabled>` is still an affordance, and one that refuses every press reads as a broken feature rather than as a state with a remedy — the remedy being to select that deck, at which point the control is there. No "click to switch decks" was invented: that is new design and is #1073's. The guard is `offers no open control for an agent on a deck that is not selected, and says why` (`desktop/src/components/AgentOverview.test.tsx`), mutation-checked by making every row openable, which turns it red.

**What was kept, and why each survives the descope.** These are not cross-deck machinery and reverting them with the rest would have cost something real:

1. **`useInertBackground` and focus containment.** `aria-modal="true"` over a base screen that is deliberately still mounted is a claim that has to be honoured whatever the deck story.
2. **The composite render match in `DeckSurface` and the `DeckShell` close-on-mismatch effect.** The selected deck can still move under an open pane with no gesture in this window — a `selectionFallback`, another window writing the settings document, a reconnect — and these make the pane refuse to retarget rather than silently wear another deck's agent.
3. **The composite keying of `terminalFeed`, `terminalInputResults` and `appliedGeometry`, plus `adoptGeometryDeck`.** This fixes a **pre-existing** defect the overlay did not cause: the sentinel scenario — stream bytes into deck A's `planner`, switch decks with the ordinary `DeckSelector`, see A's scrollback under deck B's same-id `planner` — is reachable with no overlay at all, because ids are per-daemon monotonic and the state layer was bare-id. Reverting it would have reintroduced a known defect for nothing.
4. **The Reader suppression** (`panePresent`, `readerSuppressed`), which is about two `Escape` listeners on one screen and has no deck in it.

**The composite keying is a PARTIAL fix and is not described as anything else.** What it does: a *fresh mount* reads the buffer, the verdict and the applied geometry belonging to the deck it names. What it does not do: any of round 2's four items above — in particular the in-place case, which the fresh-mount test cannot observe by construction. `docs/develop/desktop-gui.md`'s section is retitled *"The composite identity goes part of the way down"* and enumerates the gap, and the sentence in `desktop-gui.md` saying the bridge's other maps "die with the selection" now names `sessions` as the one round 2 found an exception to. ### 2026-09-17 — Focus-driven sizing: the decision, and the contract (M11, step 1)

**What was found.** In the owner's `task run-all` configuration — a TUI and the desktop attached to the same agent — enlarging the desktop pane gained rows and no columns. The tester reproduced it below the browser, at the child PTY (`.dot-agent-deck/tester-repro-layer2.md`): the TUI's tile alone gave the shell `(42, 58)`, the desktop overlay's resize to `(22, 153)` gave `(22, 58)`, detaching the TUI gave `(22, 153)`, and the TUI's own zoom is capped the same way by any narrower second viewer. The resize path is not the defect — with the TUI detached, the same resize gives the shell all 153 columns. It is PRD #882's rule working as written: `effective_dims` takes the smallest rows and the smallest columns independently over every viewer that has reported a geometry (`src/agent_pty.rs:7597`). This PRD's own success criterion said the overlay is larger "whenever no other attached client constrains it", and the owner's everyday configuration is exactly the one where another client does.

**The decision, the product owner's, approved with its defaults.**

> Can it be that whichever gets the focus enlarges? … if I enlarge it in desktop, it gets bigger and then if I switch to the TUI (without changing the size), it gets whatever it should be in TUI.

1. **The last-focused client wins.** For every agent that client is viewing, the agent takes that client's viewer size. *Last*, not *currently*: leaving both clients for a browser reflows nothing.
2. **Fallback to PRD #882's per-axis minimum** when no client has claimed focus (cold start, a daemon restart, older clients only), or when the last-focused client has no viewer of that agent with a reported geometry.
3. **In the TUI, keyboard or mouse input counts as gaining focus**, as well as terminal focus-in events. Not every terminal reports focus changes — tmux only does with `focus-events on`.
4. **Older clients**, which never claim focus, take part only through the fallback, and a focus-capable client's claim overrides them.
5. **Two accepted costs**, listed below.

**Client identity — the design question the feature depends on, answered from the code.** Focus belongs to a *client*; the daemon sizes agents from *viewer tokens*, minted one per attach. How clients attach today:

- **The TUI opens one connection per embedded pane.** `EmbeddedPaneController` holds one `DaemonClient` (`src/embedded_pane.rs:556`), and every pane attach — a new pane, hydration, the fallback path and auto-reattach — calls `attach_as_viewer` (`src/embedded_pane.rs:1220,1554,1812,3099`), which opens a connection of its own in `attach_inner` (`src/daemon_client.rs:2131`). A resize opens another short-lived connection carrying only the token (`src/embedded_pane.rs:3177-3180`).
- **The desktop opens one connection per terminal session, per deck.** `establish` attaches through the deck's shared `TrustedDaemon.client` (`desktop/src-tauri/src/daemon_bridge.rs:64`) with `attach_as_viewer` or `attach_pending_viewport` (`desktop/src-tauri/src/terminal.rs:612-618`), keeps the token on the session, and `resize` sends it back (`desktop/src-tauri/src/terminal.rs:914`).
- **Before this change, the daemon grouped no client's connections.** `handle_connection` decodes exactly one request per connection; the viewer map was keyed per attach, "deliberately not per client process"; `Hello` logged `client_build_version` and stored nothing; and the attach handler reads no peer credential. A cross-platform peer-PID seam does exist (`crate::platform::peercred::peer_pid`, Unix and Windows), but its callers are clients learning a *daemon's* PID (`src/daemon_stop.rs:191`, `src/build_version_handshake.rs:369`).

**Design: an opaque id the client generates once per process and sends on every attach and on the focus claim; the daemon records it on the viewer entry that attach creates.** One process is one client for every deck it talks to — each daemon only ever sees its own attaches, and focus belongs to what a person is looking at, which is a process. Alternatives, and why each lost:

- *The peer PID of each connection*, through the existing `peer_pid` seam. The strongest alternative, because it needs no wire field on the attach at all. It loses on three counts. **A PID is reused**, and a 128-bit random id in practice is not: a daemon that recorded a focused PID can hand focus to an unrelated later process that was issued the same number and never claimed anything, unless the daemon also tracks every PID's connection lifecycle. **A remote deck sees the tunnel, not the client**: the desktop reaches it through `ssh -N -L`, so the daemon's peer is the `sshd` session on that host — which does group one desktop's connections per deck, since the tunnels refuse `ControlMaster` (`src/remote_tunnel.rs:1973-1974`), but changes whenever the tunnel is re-established, so a desktop that reconnects after a network blip would no longer match its own claim. And **two logical clients in one process cannot be expressed**, which is what an in-process test stand-in is.
- *A daemon-minted id handed back on `Hello`.* `Hello` is a one-shot connection like every request except the two streaming ones, so the id would still have to be presented on each attach. Minting adds a round trip and daemon state for ids that may never be used, and buys nothing: the daemon cannot authenticate the presenter either way.
- *A focus claim that lists the client's viewer tokens.* No new concept, but tokens exist only after attaching, so every attach made after a claim — a new tile, a respawn's auto-reattach — would sit outside the claimed set until the client claimed again, and the message would grow with the pane count.

**The id is not authentication.** Any peer on the attach socket can present any id and claim focus on another client's behalf. What that buys it is a different PTY size, and such a peer already holds the daemon user's local-exec authority through `start-agent`.

**The contract, as built in step 1.**

- **Capability:** `CAP_FOCUS_GAINED = "focus-gained"` (`src/daemon_protocol.rs:423`), in `DAEMON_CAPABILITIES` on every platform and therefore on the live `Hello` reply's `capabilities`. A client sends `focus-gained` only when that list names it — an absent `capabilities` field and a list without the string both mean withhold.
- **Focus claim:** `AttachRequest::FocusGained { client_id: String }`, on the wire `{"op":"focus-gained","client_id":"<id>"}` (`src/daemon_protocol.rs:1209`). `client_id` is required; a request without it does not decode. Its own short-lived connection, one request and one response. A valid id is recorded and answered `ok: true` with no other field set; an invalid one is answered `ok: false` with an error beginning `invalid client_id` and changes no state.
- **Identity on attach:** `AttachRequest::AttachStream` gains `client_id: Option<String>`, `#[serde(default, skip_serializing_if = "Option::is_none")]` — absent, not `null`, when unset (`src/daemon_protocol.rs:919`). Recorded on the viewer the attach registers. An attach that registers no viewer (no `rows`/`cols` and no `geometry_updates`) records it nowhere. An invalid id refuses the attach with `ok: false`, an error beginning `invalid client_id`, and no viewer registered.
- **Id grammar:** `is_valid_client_id` — 1 to `MAX_CLIENT_ID_LEN` (64) bytes of ASCII letters, digits, `-` and `_` (`src/daemon_protocol.rs:433,444`). Generated form: `daemon_client::generate_client_id()` returns `c-` followed by 32 lowercase hex digits (`src/daemon_client.rs:1119`).
- **Client library:** `DaemonClient::with_client_id(id)` (`src/daemon_client.rs:1243`) makes every attach from that handle and its clones send the id. `DaemonClient::focus_gained()` (`src/daemon_client.rs:1933`) returns `Err(ClientError::Malformed)` and sends nothing when the handle has no id; `Ok(FocusReport::Withheld)` and sends nothing when the daemon does not advertise the capability (one cached `Hello` per endpoint); `Ok(FocusReport::Recorded)` on `ok: true`; `Err(ClientError::Server)` on `ok: false`.
- **Daemon state:** `RegistryInner.focused_client: Option<String>` (`src/agent_pty.rs:3755`), written by `AgentPtyRegistry::record_focus` and read by `focused_client()` (`:7643`, `:7652`). It lives under the registry lock that every caller of `effective_dims` already holds. Each `RunningAgent.viewers` entry is now a `Viewer { geometry: Option<(u16, u16)>, client_id: Option<String> }` (`:2154`, `:2306`), readable as a copy through `viewers_of(agent_id)` (`:7659`). A resize through a viewer token moves that entry's `geometry` and never its `client_id`.
- **No focus-lost message.** Under "last-focused wins" losing focus changes nothing by itself: leaving for a browser must reflow nothing, and losing focus to another deck client is already said by that client's own claim. A lost message would have no state to change, and it would add an ordering hazard, because one client's "lost" and another's "gained" travel on separate connections and can arrive in either order. A client that goes away needs no message either — its attaches end, its viewers are released, and the fallback applies.

**"Last focused", precisely.** The `client_id` of the most recent valid `focus-gained` request **this daemon process** accepted, in the order the daemon handles them — two near-simultaneous claims resolve in that order, not in the order the users acted. (*Amended by the fix round*: the order is the coalescing gate's, which is where a claim is accepted; and a claim superseded by a newer one inside a single re-apply interval is accepted but never recorded, so it decides nothing.) A claim by the client already recorded changes nothing. It is not cleared when that client detaches, disconnects or its agents exit: a client with no viewer of an agent simply falls through to the fallback for it, and if the same process attaches again it is still the last client that was focused. It is lost when the daemon restarts, which is the no-claim fallback. A claim may name a client that has no viewers yet.

**The sizing rule — step 2 builds this; step 1 does not.** For each agent, with `F` the recorded last-focused client:

1. **Focused.** If `F` is set and the agent has at least one viewer whose `client_id` is `F` **and** whose geometry has been reported, the agent takes the smallest rows and the smallest columns **over those viewers only**. With one such viewer — the desktop bridge holds one session per agent per deck, which is this PRD's one-xterm-per-agent rule, and a TUI one attach per pane — that is exactly that viewer's geometry. Minimising over the focused client's own viewers keeps PRD #882's guarantee for the client being looked at: every pane it has on the agent can draw the agent whole.
2. **Fallback.** Otherwise — `F` unset, no viewer of the agent belongs to `F`, or all of `F`'s viewers of it are still unmeasured — PRD #882's rule unchanged: the smallest rows and the smallest columns over every viewer with a reported geometry.
3. **No reported geometry at all** leaves the size alone, as today.

It is re-applied on every existing trigger (attach, a resize through a token, a viewer's release) and **on every accepted claim, across every agent**, because a claim changes the answer for agents none of whose viewers changed. A claim that does not change `F` moves nothing, by `apply_dims_locked`'s existing no-change guard. Unchanged: the unattributed path (a resize with no token), clamping, and the geometry push to every participating viewer. A viewer with `client_id: None` can never equal `F`, which is what makes default 4 fall out of the rule rather than needing a branch.

**The two accepted costs.**

1. **Switching focus reflows.** Moving focus between two clients that both view an agent resizes that agent — SIGWINCH to the child, the scrollback ring cleared (PRD #104 M3), a geometry push to every viewer — once per switch, for every agent both show.
2. **The client not focused is handed a grid bigger than its pane and clips.** On any axis where its geometry is smaller than the focused client's, it adopts the applied geometry and draws past its edge. `effective_dims`'s doc comment names avoiding that truncating direction as the point of the current rule; it is acceptable here because it happens to the client nobody is looking at. An **older** client pays this for as long as a focus-capable client holds focus on an agent they share, because it can never claim focus back.

**What step 1 does not do.** It does not change sizing: `effective_dims` reads geometry through the new `Viewer` struct and nothing else, and reads neither `focused_client` nor `client_id`. It does not re-apply anything on a claim. No production code calls `with_client_id` or `focus_gained`, so neither the TUI nor the desktop sends an id or a claim. **Verified unchanged** three ways: the existing viewer-policy unit tests in `src/agent_pty.rs` pass unmodified; `cargo test-fast` passes; and a temporary in-process probe, deleted before committing, reproduced the owner's configuration against a real daemon — TUI viewer `(42, 58)`, desktop viewer resized to `(22, 153)`, applied `(22, 58)` — then claimed focus for the desktop, re-sent its resize, and claimed focus for the TUI: `(22, 58)` at every step.

**Unit tests added**, each mutation-checked by breaking the production code it covers and watching it go red: the claim's wire shape and its required `client_id`; `Hello` advertising `focus-gained`; `client_id` as an optional key on `attach-stream`; the id grammar and the generated form; the last claim winning against a real daemon; an attach recording its client on its viewer, a client with no id recording none, a resize keeping the client, and a non-viewer attach recording nothing; a malformed id refused on both verbs with no state change; a handle with no identity sending nothing; and the withhold against a daemon advertising nothing and one advertising only PRD #819's verbs.

**Rule 12, answered from `src/daemon_protocol.rs`'s own versioning note.**

- **`PROTOCOL_VERSION` bump: no — and it is argued against the note's letter, so it wants the owner's confirmation before merge.** The note lists "new `AttachRequest` variants" under *Bump*, and its PRD #819 paragraph says variants added after 9 ships are "another break for every user". 9 has shipped: `v0.40.0`, `v0.40.1` and `v0.40.2` all carry it. Read literally, that is a bump to 10. What the rule argues from is its first sentence — bump when a change "would cause an older or newer peer to mis-parse a frame" — and with the claim withheld unless advertised, no pairing produces such a frame: a newer client against an older daemon withholds; an older client never sends it; `client_id` on `attach-stream` is an additive optional key an older daemon ignores. The capability field was added by PRD #819 precisely to tell "speaks 9" from "answers this verb". Against that, a bump makes the desktop refuse every daemon at 9 outright (`classify_handshake`, `desktop/src-tauri/src/daemon_bridge.rs:806`, requires exact equality), remote decks the user cannot upgrade included. The note is narrowed in this commit — capability-gated variants do not bump, ungated ones still do — with the argument and its limits on `PROTOCOL_VERSION`. `docs/develop/versioning.md:11` still names "a new request variant" among the structural breaks without that qualification; if the decision stands it needs the same narrowing. Reversing it while 10 is unreleased is the constant, a paragraph, and this bullet.
- **An older daemon sent the claim anyway** fails the frame decode and answers `ok: false` with `malformed request: unknown variant …` (`src/daemon_protocol.rs:2378`), then closes the connection; no state changes. `focus_gained()` withholds first, so it reaches this only if the daemon behind the socket was replaced by an older build after the handle cached its capability set — and then the claim is refused and nothing changes. Nothing may branch on that text.
- **An older client against a newer daemon** never sends `client_id` or a claim, so its viewers carry `client_id: None`. With no focus-capable client holding focus, sizing is exactly PRD #882's. With one, after step 2 the older client is overridden on every agent both view and clips, and cannot claim focus back.
- **`.breaking.md`: yes, due in step 2, not in step 1.** Once step 2 lands, the applied geometry a registered #882-era viewer (`v0.40.x`) is handed can exceed the geometry it reported — a meaning change behind a stable wire, which rule 12 names as breaking. Step 1 changes no applied geometry, so a fragment now would describe behaviour the tree does not have. Step 2 adds `changelog.d/1105.breaking.md`, which makes the release carrying it a minor one.
- **The cross-version manual test is owed once M11 is complete** — after steps 2, 3 and 4 — and not in this step, which changes no observable flow. It must cover both directions: the branch TUI against a `v0.40.2` daemon with an agent under it, where the TUI must withhold the claim and sizing must be exactly PRD #882's; and a `v0.40.2` TUI against the branch daemon while the branch desktop holds focus, where the older TUI is expected to clip.

**Left open for steps 3 and 4.** *TUI cadence:* input counts as focus, so a naive TUI would open a connection per keystroke to repeat a claim that is almost always a no-op, and it cannot tell cheaply whether another client claimed focus in between. It needs a throttle, and the throttle window is exactly how long a switch back to the TUI goes unclaimed. *Desktop trigger:* window focus-in is the obvious event; whether input into a terminal also claims is the same cadence question. *A daemon-to-client "focus moved" push* would let a client skip redundant claims; the rule does not need one, and it is not designed here.

### 2026-09-17 — Focus-driven sizing: the TUI and the desktop claim focus (M11, steps 3 and 4)

**Both clients identify themselves and claim focus, against a daemon that at this point records the claim and sizes nothing by it.** Landed together in `7538567f`, before step 2. Sizing was untouched: neither `effective_dims` nor `src/agent_pty.rs` changed.

**Identity.** The TUI builds one `EmbeddedPaneController` per process, and its client is `DaemonClient::new(path).with_client_id(generate_client_id())`. Every attach path uses clones of that one handle — a new pane, startup hydration, `hydrate_pane`, and the I/O task's re-attach after a respawn — and the resize worker now shares it too rather than building a client per resize. The Ctrl+W stop path is not an attach and is unchanged. The desktop keeps one id per process in `daemon_bridge::desktop_client_id()`, a `OnceLock`, and `establish()` builds every deck link's client with it, so every terminal attach and every claim on every deck carries the one id, across the link rebuild too.

**`client_id` on attach is not capability-gated, and does not need to be.** `v0.40.2`'s `AttachRequest` has no `deny_unknown_fields`, it decodes with `serde_json::from_slice`, and its own test `unknown_fields_are_ignored_so_a_newer_client_degrades_against_an_older_daemon` decodes an `attach-stream` carrying an unknown key. The claim itself stays gated: `DaemonClient::focus_gained` withholds unless the daemon advertises `focus-gained`.

**The TUI's triggers.** `EnableFocusChange` (`?1004h`) is sent beside mouse capture and bracketed paste, and disabled on the clean teardown and in the panic hook. The event loop hands every event to the reporter (`src/focus_report.rs`) straight after `event::read()`; the claim is spawned, so nothing blocks. A terminal **focus-in** claims at once, never throttled. **Input** claims too, because not every terminal reports focus: a key press or repeat, a paste, and every mouse event except bare motion. A key release does not count — it is the tail of a press that already did, and can be the release of the shortcut that switched away — and neither does motion, because `EnableMouseCapture` turns on any-event tracking, so the terminal reports a pointer merely passing over the window. Input is throttled to one claim per `INPUT_CLAIM_INTERVAL` (1 s), suppressed input is dropped rather than deferred, and there is no trailing claim at the end of the window, because it would fire after a switch to the desktop and take focus back from the window the person moved to. The cost is confined to terminals that do not report focus: leaving, another client claiming, and coming back to type all within one second of the TUI's last claim goes unclaimed until the next input.

**The desktop's triggers.** Tauri's `WindowEvent::Focused`, handled in Rust: `tao` emits it from GTK's `focus-in-event` on Linux and `windowDidBecomeKey` on macOS, and `tauri-runtime-wry` synthesizes it from WebView2's `GotFocus`/`LostFocus` on Windows. On focus-in the app claims once per deck on which it holds at least one viewer — the decks where a claim can change a size — concurrently, so a slow remote deck does not delay a local one. Focus-out claims nothing. It **also** claims on a pane's deck when the pane is attached while the window is focused, after the attach so a refused attach claims nothing: without that, the owner's own order — focus the app, then open a pane — never claims the new pane's deck. Typing into a desktop terminal does not claim: keystrokes reach a terminal only after the window gained focus and claimed, and the `write` path carries xterm.js's automatic replies to an agent's terminal queries, which would claim focus for a window nobody is looking at. **Accepted gap:** another client claiming while this window keeps OS focus — a scroll over an unfocused TUI, or a client on another machine sharing a remote deck — leaves the desktop's pane at that client's size until the window loses and regains focus.

**Tests: eleven, and seventeen production mutations each turned at least one red.** TUI: the event classification and the throttle with synthetic instants (unit); a focus-in claim recorded by a real daemon, and a second one 10 ms after another client's claim taking focus back; 32 input events inside one window reaching a scripted daemon as exactly one claim, motion claiming nothing; nothing but `hello` sent to daemons advertising no capabilities or only PRD #819's verbs; every attach path carrying the controller's id, and a second controller carrying a different one. Desktop: every attach on every deck, across a re-established link, naming the one id; focus-in claiming once per deck with a viewer and not on a deck without one, and focus-out claiming nothing; an older deck sent only the link's `hello`; a pane opened in a focused window claiming on its deck and one opened unfocused not; and the window-event mapping. The event-loop line in `src/ui.rs` and the `?1004h` enable were left without an automated test here; step 2's `resize/policy/001` zoom case later covered the event-loop line end to end.

**Rule 12.** No wire shape changed: these steps only start sending the field and the verb step 1 defined. The branch TUI and desktop against `v0.40.2` still attach (the key is ignored) and never send `focus-gained` (withheld from the advertised set); the only extra traffic is one `Hello` per handle, cached once it succeeds. `.breaking.md` stayed due with step 2, which changes applied geometry.

### 2026-09-17 — Focus-driven sizing: the daemon rule (M11, step 2)

**The rule the contract specified is now what the daemon does, and with it M11's four steps have all landed.** Steps 3 and 4 (`7538567f`) had the TUI and the desktop claiming focus against a daemon that recorded the claim and sized nothing by it. This step makes the claim decide the size.

**Where it lives.** `AgentPtyRegistry::effective_dims` in `src/agent_pty.rs` now takes the registry's `focused_client` beside the agent. If that client has at least one viewer of the agent with a reported geometry, the agent takes the smallest rows and the smallest columns over that client's measured viewers only. Otherwise it is PRD #882's rule, unchanged: the smallest rows and the smallest columns over every viewer with a reported geometry, or `None` — leave the size alone — when there are none. Two small helpers carry it: `client_geometries` (one client's measured viewers of an agent) and `smallest_per_axis`, which both branches share, so the fallback is the old computation rather than a second copy of it.

**One re-apply path, extended rather than duplicated.** Every trigger calls the existing `apply_effective_locked`, which now takes the focused client read under the same registry lock, and which calls the existing `apply_dims_locked`: the no-change guard, the ioctl, the scrollback-ring clear and the geometry push to every participating viewer, all as before. The triggers:

- **An attach that registers a viewer** (`subscribe_with_viewport_for_client`). A returning focused client takes its agents back on attach.
- **A resize through a known viewer token** (`resize_for_viewer`). One arm serves all three resize cases the task named: the focused client's viewer resizing moves the agent to its new size; any other viewer resizing where the focused client has a measured viewer recomputes to the focused size, which the no-change guard makes free; and a resize on an agent the focused client does not view is the fallback, as before.
- **A viewer's release** (`release_viewer`, called when an attach ends). When the focused client's last measured viewer of an agent goes, the agent falls back. Focus itself stays recorded, as the contract says.
- **An accepted claim** (`record_focus`) — the new trigger. It re-applies exactly the agents on which the **new** or the **previous** focused client has a measured viewer: the new client's agents move to its size, and the previous client's agents that the new one does not view fall back. Every other agent's answer is the fallback before and after, so it is not touched; re-applying it anyway would change nothing but to undo a direct, unattributed resize the claim has no business with. A claim by the client already recorded returns before looking at any agent. The re-apply runs before the handler answers `ok`, so a client that reads the answer knows the resize has happened.

**A client with several viewers of one agent takes their per-axis minimum** — the contract's default, and kept after weighing the alternatives rather than inherited. The case is one client showing an agent twice, and both views are in front of the person who just focused it. The minimum is the largest size at which every one of those views can draw the agent whole. *Most recently resized* would hand the other view a grid larger than itself, needs an ordering the daemon does not keep, and would flip the size whenever either view re-sent an unchanged geometry. *Largest* clips a view the person is looking at by construction. The cost of the minimum is that a small second view on the focused client holds the agent small, which is PRD #882's trade restricted to the one client being looked at.

**`effective_dims`' doc comment was rewritten, not amended.** It used to say the per-axis minimum exists because anything else "would hand some other viewer a dimension larger than its pane, which is the truncating direction this policy exists to avoid". That is still why the fallback minimises, and the focused branch now does exactly that on purpose to every viewer outside the focused client. The comment states the rule, the multi-viewer choice with its argument, and that accepted cost, including that a client predating focus can never claim it back. Comments that restated the old policy as an absolute were narrowed with it: `RunningAgent::viewers` ("the PTY is never larger than anyone's pane"), `TerminalWidget`'s render note, `resize_agent_as_viewer` and `attach_as_viewer`, `AttachStream`'s viewport field, the TUI resize worker, the desktop's `TerminalAttachResult`, `TerminalViewport` and three "smallest-viewer policy" mentions in the desktop. The `FocusGained` handler and `record_focus` no longer say they size nothing.

### 2026-09-17 — Focus-driven sizing: bounded claim work, stale claims dropped, terminal modes guarded (M11, review and audit fixes)

**The review found no blockers; the security audit found two low-severity should-fix items, and both are fixed here with the review's two comment nits.** Neither audit finding crossed a trust boundary: a peer that can reach the attach socket already holds `StartAgent`, `Resize` and `StopAgent`.

**Finding 1 — claim work was unbounded, and a stale claim could win.** Every valid `focus-gained` from a client other than the recorded one re-applied every agent that client or the previous one viewed, under the registry lock, and each real size change is an ioctl (a SIGWINCH), a scrollback-ring clear and a geometry push. Two ids alternating turned each short request into registry-wide work and cleared replay history on every flip. On the clients, nothing cancelled a claim once started: the TUI's terminal focus-in bypasses the throttle and spawns a task per event, the desktop spawned a handler per native focus event, and a desktop claim held up on a slow remote link could land after the person had moved to the TUI and the TUI had claimed — resizing everything back to the window they had left.

- **The daemon coalesces.** Every claim passes a gate (`AgentPtyRegistry::accept_focus_claim`, with its own lock) before anything is recorded. A **focus pass** records whichever accepted claim is newest when it runs and re-applies the agents it moves; passes start at least `FOCUS_REAPPLY_INTERVAL` (250 ms) apart. A claim arriving an interval or more after the last pass runs one at once; a claim arriving sooner schedules one for the end of the interval or joins the one already scheduled. So each agent is resized by focus at most once per interval however many claims arrive, and **the last accepted claim is the one in force** afterwards. Skipping the claims in between is exact: a claim never recorded never decided a size, so nothing of it needs undoing. A claim naming the client that is already newest spends no pass, so a TUI's steady input claims cannot use up the interval and delay a real switch. The deferred pass runs on a spawned task, not on the connection, so a client disconnecting while it waits still has its claim applied; passes are serialised so the ids they take are recorded in the order taken.
- **`ok` still means applied.** The handler answers once a pass has recorded its claim or a newer one — at most one interval late, and only for a claim landing inside one. That is what keeps `resize/policy/001`, `/002` and `/004`–`/011` deterministic without editing them: each test's claim is awaited, and its `stty size` probe runs after the `ok`. `/005`, whose second claim lands inside the first's interval, now takes about 250 ms longer than its neighbours; it passed unchanged.
- **The registry lock is held one agent at a time.** `record_focus` picks the agents to move under one acquisition — an in-memory scan with no system call — and re-applies each under its own, reading the focused client afresh, so the longest single hold for a claim is one agent's ioctl rather than the registry's.
- **The clients drop a claim that went out of date before it was written.** `DaemonClient::focus_gained_while(still_wanted)` asks its condition after the claim's connection is open and immediately before the request is written, and returns the new `FocusReport::Superseded` with nothing written if it fails. The **TUI** keeps a generation that a newer admitted claim or a terminal `FocusLost` advances; input the throttle suppresses advances nothing. The **desktop** records each window focus report synchronously in the `on_window_event` callback — no longer in a task spawned per event, which could run two reports out of order — advancing a generation that every claim, including `establish`'s, carries and checks. **What remains:** a claim already written when the newer event arrives cannot be recalled. It reaches the daemon after its transit time — a local socket write, plus the ssh tunnel for a remote deck — and the daemon applies whichever claim it accepts last.
- **Observability.** `RunningAgent::geometry_changes` counts real PTY resizes, one ioctl, one scrollback clear and one geometry push each, read through `AgentPtyRegistry::geometry_changes_of`.

**Finding 2 — terminal modes were left on after an error exit.** Focus reporting (`?1004h`), and since before M11 mouse capture and bracketed paste, were turned off only by the clean teardown and the panic hook, so a failed `terminal.draw`, `event::poll` or `event::read` returning through `?` left the user's shell receiving mouse reports and `ESC [ I` / `ESC [ O`. `run_tui` now holds a `TerminalModesGuard`, modelled on `KeyboardEnhancementGuard`, whose `Drop` writes the disable sequences. The explicit ordered teardown stays — keyboard pop, then modes, then `ratatui::restore()` — and the guard is declared before the keyboard guard so an error return drops them in that same order. The on/off flag is shared by the guard, the teardown and the panic hook and is test-and-clear, so whichever paths run, the disables are written once, and a panic before the modes were turned on writes none. The enable sets the flag before writing, so a partly failed enable is still turned off.

**The review's nits.** `resize/policy/001`'s owner-configuration row assertion now carries a comment that it holds only while that TUI claims no focus. `RegistryInner::focused_client`'s doc states the invariant that makes never clearing it safe: the focused client decides sizing only through a viewer that has reported a geometry.

**Tests, each seen failing under a production mutation** (applied one at a time, files restored byte for byte):

- `agent_pty::…::alternating_focus_claims_resize_at_most_once_per_interval_and_the_last_wins` — two ids with measured viewers of one agent: 200 alternating claims back to back, two more inside the interval that opened, then 200 claims 5 ms apart; resizes stay within one per started interval, and each run's final claim is recorded and in force when its handle resolves.
- `agent_pty::…::a_repeated_claim_does_not_delay_the_next_switch`.
- `daemon_client::…::alternating_focus_claims_are_coalesced_by_the_daemon` — the same churn through the production handler: 200 concurrent alternating claims then two closing ones, bounded resizes, and the final claim's size in force when its `ok` arrives.
- `embedded_pane::…::focus_claims::a_claim_still_unsent_when_a_newer_event_arrives_is_never_sent` — a scripted daemon holds the claim's handshake; a focus-out drops it, and a second focus-in leaves exactly one claim on the wire.
- `terminal::tests::a_claim_still_unsent_when_the_window_focus_changes_is_never_sent` (desktop) — a scripted deck holds the link handshake; a focus-out makes the claim `Superseded` and the deck never receives `focus-gained`, and a second focus-in leaves exactly one.
- `ui::tests::terminal_modes_are_turned_off_when_the_event_loop_returns_an_error` and `…_once_whichever_teardown_paths_run` (Unix: on a Windows console crossterm sets mouse capture through the console API rather than writing a sequence).

`input_reaches_the_daemon_as_one_claim_per_window` now finishes its key claim before sending the focus-in that follows it, since the focus-in would otherwise drop that claim if still unsent; what it asserts about the throttle is unchanged.

**Rule 12 — no contract change.** No wire shape moved: the request, its reply and the capability are as they were. The rule is unchanged — the last claim the daemon accepts wins, and the fallback is untouched. What moved is timing inside the daemon: a claim landing within one interval of the previous pass is recorded up to 250 ms later, its `ok` comes as late, and a claim superseded within that interval is never recorded. No shipped client waits on the answer (the TUI's claim timeout is 2 s, the desktop's 5 s) and `v0.40.x` clients never send the claim, so the cross-version predictions in the step 2 entry stand as written. `PROTOCOL_VERSION`, its note and `docs/develop/versioning.md` were left alone, and the scrollback clear in `apply_dims_locked` is unchanged; coalescing only makes it fire less often.

### 2026-09-17 — Three owner decisions: no `PROTOCOL_VERSION` bump, the scrollback cost accepted, 250 ms kept (M11)

**The review and the audit left three questions that were the product owner's rather than the implementer's. All three are now answered, and none of them changes behaviour** — what changed is two documents that disagreed, one doc comment that read as an implementation detail, and one user-facing disclosure. The fourth item, the terminal-mode leak, turned out not to be a #1105 question at all and is now its own bug.

**1. `PROTOCOL_VERSION`: no bump for `focus-gained`, and the two documents now agree.** The decision was already argued in the note on the constant (`c0043ae8`): a request variant every sender withholds until the daemon advertises `CAP_FOCUS_GAINED` is kept out of the pairings in which an older daemon would meet a frame it cannot parse, and the one residual route to such a frame fails closed, so the thing the constant protects against does not arise from it. What was left inconsistent is that `docs/develop/versioning.md` still stated the unqualified rule in two places — "a new request variant" among the obvious structural cases, and "Any wire-shape break must bump `PROTOCOL_VERSION` … mandatory and non-negotiable". Both now carry the capability gate, with `focus-gained` as the worked example, the residual named (a client handle whose cached capability set outlived a daemon replaced by an older build — which fails closed: `malformed request`, an `Err` at the caller, no state change either side), and the cost of a bump stated, because the cost is what decided it: the desktop is the one call site that refuses on a version difference, so a bump makes a new app refuse every daemon still on 9 outright, **including remote decks on hosts the user does not own and cannot upgrade**, for whom the remedy a refusal implies does not exist. Two limits are written down so this is not read as a general licence — it covers only a variant *every* sender gates (the check lives in `DaemonClient::focus_gained_while`, which `focus_gained` delegates to and which both production senders go through, rather than in each caller), and it says nothing about semantic breaks, of which #1105's own `changelog.d/1105.breaking.md` is the illustration. The note on the constant now points at the doc and vice versa, and `src/daemon_protocol.rs`'s closing "keep bumping this on every wire-shape break regardless" says which sense of "break" it means.

**2. The scrollback drop on a size change: accepted, with the frequency premise re-affirmed rather than inherited.** `apply_dims_locked` clears the agent's 1 MiB replay ring on a *real* size change (after the no-change guard), and focus-driven sizing makes real size changes a routine interactive event rather than the rare one PRD #882 judged. **The clear stays, untouched.** What the review established is that the loss is narrower than the frequency suggests: the ring is used only to replay history to a *new* subscriber, so **only a client that attaches or re-attaches after the switch is affected**, and a client that stays attached keeps streaming into its own parser and its own scrollback (the TUI's 10 000 lines, xterm.js's 8 000) — so nothing disappears from the history of a client that stays attached, the desktop's hidden-but-attached warm tiles included. The reachable cases are a desktop tile brought back on screen, a pane respawn's re-attach, and a reconnect. Against that, the only option that would genuinely preserve history across a width change is re-wrapping up to 1 MiB of arbitrary ANSI to the new width on the daemon on every flip — real CPU per flip and genuinely hard to get right — and the cheap partial (clear only when the *column* count changes) helps only the subset of flips that are row-only, while a per-epoch ring still cannot replay across widths. Keeping the ring across a width change is also not obviously better for the user: old-width bytes replay garbled, which is why the clear exists. Two things reduce the exposure on their own: the coalescing added in this round means switches closer together than `FOCUS_REAPPLY_INTERVAL` apply as one size change rather than one each, so rapid flipping costs one clear rather than many; and the agent's own output refills the ring as it works. `docs/troubleshooting.md` already disclosed this and now says plainly who is affected — attach and re-attach, not an attached client — names the respawn and reconnect cases, and records that quick flips collapse into a single change.

**3. `FOCUS_REAPPLY_INTERVAL` stays at 250 ms.** Kept as shipped. Its doc comment now says in the first line of its own paragraph that this is a **product-visible number rather than an implementation detail**, and states it in what a person sees: it is the longest a switch between two apps can take to reflow the agent's pane, for a switch that lands inside another claim's window — they move to the other app and the terminal redraws up to a quarter of a second later. That delay is the entire price of the bound, so the next reader weighing a change knows they are weighing a product decision.

**The terminal-mode leak is not a #1105 question, and is filed as [#1141](https://github.com/vfarcic/dot-agent-deck/issues/1141).** The audit's second finding named focus reporting (`?1004h`), which has only ever been enabled on this branch — but mouse capture and bracketed paste were enabled in the same call and have leaked on an ordinary error exit since `acd37df3` (PRD #39), first shipped in `v0.14.0`. So every release from `v0.14.0` through `v0.40.2` leaves the user's shell receiving mouse reports and bracketed-paste markers when the TUI exits through a failed `terminal.draw`, `event::poll` or `event::read` rather than cleanly; panics were always covered by the hook. `3a2c2cc9`'s guard fixes that independently of this PRD, so it gets a bugfix fragment of its own (`changelog.d/1141.bugfix.md`) rather than being folded into #1105's, which describe the feature.
