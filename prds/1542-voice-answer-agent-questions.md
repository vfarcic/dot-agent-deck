# PRD #1542: Answer the open agent's questions by voice

**Status**: In progress (M1 done; decisions recorded 2026-10-03)
**Priority**: Medium
**Created**: 2026-10-03
**Issue**: [#1542](https://github.com/vfarcic/dot-agent-deck/issues/1542)
**Related**: [#1497](https://github.com/vfarcic/dot-agent-deck/issues/1497) (hearing the agent's turns, including its permission prompts), [#1541](https://github.com/vfarcic/dot-agent-deck/issues/1541) (interrupt, clear, scratch that)

## Problem Statement

An agent stops and asks — a permission prompt ("Allow this command?"), or a menu of options. Its card shows **Needs Input** (`WaitingForInput`). With voice on, the desktop app has no command that answers it: there is no "yes", "no" or "option 2". "Type 1" may work for some agents, but only by accident, and it goes through the Commands model and the five-second send countdown like any dictation. So hands-free use ends exactly when the agent needs the user.

#1497 plans to *speak* permission prompts aloud. Without this PRD, the user hears the question and still has to reach for the keyboard to answer it.

The TUI has a partial precedent: in command mode, `y` / `n` on a card in `WaitingForInput` writes a literal `y` or `n` to the pane (`Action::SendPermissionResponse`, `src/ui.rs`). It sends the same character whatever the agent is; M1 measured it correct on Codex and ignored on Claude Code and OpenCode. This PRD leaves it unchanged (decision 9).

## Solution Overview

While the agent on the desktop app's screen is asking a question the deck knows about, voice answers it. The user says what they would say to a person — "yes", "go ahead", "no", "the second one", "red", "red for colour and large for size", "always allow" — and the desktop's Commands model maps that to the options of **the question pending right now**. The model can only pick from that list (or nothing), and the app checks its pick against the list itself. The answer is shown, sent after the usual five-second countdown the user can cancel, and refused if the question changed in the meantime.

**The deck, not the client, knows the question.** The daemon builds a `pending_question` for each agent from what the agent's own hooks, plugin or extension report — every question of a form, each one's options, single or multiple choice, and which options are free text — and puts it on the agent's snapshot. Where an option is drawn on screen but never reported (Claude's and Codex's permission menus), the deck fills it from a per-agent, per-version table in the agent's registry entry, verified by real-agent tests; the screen is never read. That one model is also what #1497 reads to speak a prompt.

**The deck answers through the agent's own channel.** Where the agent takes an answer directly — Claude Code's `PermissionRequest` hook decision, OpenCode's reply API, Pi's dialog promise — the deck answers a whole form in one step. Where it does not (Codex), the deck sends the keys the per-version table names, including moving through a multi-question form; the user never says "next" or "submit".

**Coverage (rule 20):** Claude Code, Codex and OpenCode, permission prompts and multiple-choice forms; Pi, the dialogs other Pi extensions raise; Devin, built from its documentation and documented as untested. What each agent does not support is named in the docs.

## What the user sees

- An agent asks for permission. With #1497 on, the app reads it out; either way the card and pane show **Needs Input**.
- The user says "yes" (or "go ahead", "allow it"). The voice row shows *Allow once — <what was asked>* with the countdown; when it runs out, the deck answers, the row says *Allowed: <what was asked>*, and the agent continues.
- For a menu, the user says "option 2", "the second one" or the option's words; the row names the option chosen.
- For a form of several questions, the row shows the form and fills it in as the user answers, in any order and in one or several utterances ("red for colour and large for size"; "small and large" on a multiple-choice question). When every question has an answer, the countdown starts and the deck submits the whole form.
- An option that asks for the user's own words ("Type something", "None of the above") is filled by dictation.
- "Always allow" first opens a confirmation that says what it will always allow ("This will always allow edits in this session. Confirm?"); the user clicks or says "confirm", then the countdown runs.
- If the question changed or was answered by keyboard while the app was working out what was said, nothing is sent and the app says why.
- On an agent or a question the deck cannot answer, nothing is sent and the app says that this one must be answered by keyboard.

## Scope

### In scope

- An inventory of the questions each agent in `src/agent_registry.rs` asks (permission prompts, multiple-choice questions, other confirmations), how the deck can know each is pending and what its options are, and which keys answer it — verified against current agent releases (M1, done).
- The daemon's `pending_question` on each agent's snapshot: every question of a form, its options, single or multiple choice, free-text options; built from hook, plugin and extension payloads plus per-agent, per-version option tables. It is the one model voice and #1497 both read.
- A capability-gated request to answer it, and the per-agent channel that carries the answer: a held hook or plugin/extension decision where the agent takes one, keys where it does not.
- Every agent in `src/agent_registry.rs`: Claude Code, Codex and OpenCode, including their multiple-choice and multi-question forms; Pi, for dialogs raised by other Pi extensions; Devin, built from its docs and documented as untested.
- Voice answers on the desktop app's agent screen: the Commands model maps an utterance onto the pending options, the app validates the result locally, shows it, runs the countdown and checks staleness; multi-question forms fill in across utterances; free-text options by dictation; "always allow" behind an on-screen confirmation.
- Tests (including a lane-2 real-agent test), user docs and developer docs.

### Out of scope

- The TUI. Its `y` / `n` (`Action::SendPermissionResponse`) is left unchanged (decision 9); M4 is dropped.
- Interrupting, clearing and scratching — [#1541](https://github.com/vfarcic/dot-agent-deck/issues/1541).
- Speaking questions aloud — [#1497](https://github.com/vfarcic/dot-agent-deck/issues/1497), which reads this PRD's `pending_question`.
- Answering a question in an agent other than the one on screen (for example from the dashboard) — the user must be able to see what they are approving.
- Reading the terminal screen to find a question or its options.
- A permission gate of the deck's own for Pi.
- Free-text questions that are not part of a pending question (ordinary dictation already covers them), Claude Code's MCP elicitation forms, and Claude Code's folder-trust and Codex's startup trust prompts (no hook fires for them).

## Design decisions and constraints

- **Approving is consequential.** "Yes" to a permission prompt lets an agent run a command or edit files. So the Commands model may only choose among the options of the question pending now (or none), the app validates that choice against the list locally, the answer is shown and sent only after the cancellable countdown, it is refused when no question is pending, and it is refused when the question changed after the user spoke. "Always allow" needs an on-screen confirmation that names its scope.
- **Know the question from a reliable source.** Hook, plugin and extension payloads that carry the question and its options, plus per-version tables for options that are only drawn on screen. The screen is never read. Where an agent offers no channel, it is unsupported and documented — not approximated (rule 20: "cannot" means no channel exists).
- **The deck owns it.** Hooks, plugins and PTYs belong to the daemon, so detection and answering live there and reach clients through the protocol's graded path (CLAUDE.md rule 18: an additive optional field and a capability-gated request), with rule 12's cross-version check run.
- **One model, shared with #1497.** `pending_question` on the snapshot is the model; #1497 reads it to speak a prompt. Nobody keeps a second copy.
- **Staleness rules unchanged.** As for every voice command: nothing is sent if the pane changed, a confirmation is open, or the agent was replaced — and, here, if the pending question's id changed.

### What the deck receives today

- **Claude Code.** The deck installs `Notification` with matcher `permission_prompt` and **not** `PermissionRequest` (`HOOK_TYPES` and `make_rule`, `src/hooks_manage.rs`) [code]. - **Codex.** `PermissionRequest` is installed (`CODEX_HOOK_EVENTS`) [code]; the deck's event is `permission_request` with `tool_name: "Bash"`, `tool_detail: "touch codex_m1.txt"` and empty metadata [observed]. - **OpenCode.** The plugin forwards `permission.asked` / `permission.replied` (`src/opencode_manage.rs`) [code], but its `permissionPayload` looks for `prompt`/`title`/`message`/`text`/`question`, none of which `permission.asked` carries in 1.18 [docs: types], so the deck's event arrives with `user_prompt: ""` and no tool [observed]. The `question` tool arrives as `tool_start` with `tool_name: "question"` and no detail; `question.asked` is not forwarded at all, so the card reads **Working** while that menu is on screen [observed].
- **Pi.** The deck's extension never reports `waiting` (`piEventToAgentState`, `pi-extension/src/orchestrator.ts`) [code].
- **Devin.** `PermissionRequest` is installed (`DEVIN_HOOK_EVENTS`) and maps to Needs Input [code]; payload contents not observed [unverified].
- **None of the options reach the deck on any agent.** `AgentEvent` (`src/event.rs`) has no field for a question or its options, `tool_input` is reduced to a truncated `tool_detail`, and `SessionSnapshot` (`src/state.rs`) carries only `status` [code].

### Follow-up measurements (2026-10-04)

Same versions as above (Claude Code 2.1.289, Codex 0.160.0, OpenCode 1.18.34, Pi 0.87.1; Devin still not logged in), same tagging. Run on Haiku 4.5 (Claude), `gpt-5.6-luna` (Codex, OpenCode), and with no model at all for Pi, each in a private tmux server and a scratch project, with the deck's own hooks and plugins kept away from the real daemon. Claude ran with `--setting-sources project,local` and a `--settings` file of logging hooks plus a `PermissionRequest` hook that waited for an answer file. Codex ran with a scratch `CODEX_HOME` holding a copy of the auth file and logging hooks, trusted through Codex's own "Hooks need review → Trust all" prompt; `--dangerously-bypass-hook-trust` was not used. OpenCode ran with a scratch `XDG_CONFIG_HOME` holding a logging plugin that could reply through the plugin's SDK client.

**a. Pi — another extension's dialogs.**

- Pi 0.87.1 emits `ui_prompt_start` / `ui_prompt_end` to every extension, carrying `kind` (`select`, `confirm`, `input`, `editor`, `custom`) and `title` only — no options [docs: shipped types `UIPromptStartEvent`; observed].
- `ctx.ui` is one object shared by every extension (`ExtensionRunner.uiContext`, read through a getter at call time), and its `select` / `confirm` / `input` are writable properties [code: `dist/core/extensions/runner.js`; observed `writable=true`]. An extension that replaced `ctx.ui.select` and `ctx.ui.confirm` at `session_start` received a second extension's later `select("Pick a colour", ["Red","Green","Blue"])` and `confirm("Allow rm?", "Run rm -rf build?")` with their titles and options [observed].
- **Answering works.** The replacement called the original with an `AbortSignal` (`ExtensionUIDialogOptions.signal`, documented as the way "to programmatically dismiss the dialog") and resolved the caller with its own value: the dialog closed and the asking extension received `"Blue"` [observed]. When the keyboard answered first, the original resolved with the keyboard's answer (`false` for No) and the replacement cancelled its own wait [observed]. `ui_prompt_end` fired either way [observed].
- Limits. Replacing `ctx.ui` methods is not a documented extension API; it depends on that object staying mutable [observed on 0.87.1 only]. Pi replaces the object when it rebinds its UI (`setUIContext`, called from `_applyExtensionBindings`) [code], so the replacement has to be re-applied on every `session_start` [inferred]. Only the slash-command path was observed; a permission-gate extension calling `ctx.ui.confirm` from a `tool_call` handler reaches the same object [inferred]. `editor` and `custom` dialogs were not tried and have no option list to offer.

**b. Claude Code — version gate, forms, held hook.**

- Changelog: `PermissionRequest` added in **2.0.45**; "process 'always allow' suggestions and apply permission updates" in 2.0.54; "Fixed AskUserQuestion discarding multi-select answers when supplied as an array" in **2.1.136**; "PreToolUse and PermissionRequest hooks being skipped when matching them failed…" fixed in 2.1.288 [docs: `CHANGELOG.md`]. Whether a release between 2.0.45 and 2.1.136 drops all hooks given a `PermissionRequest` key was not run [unverified]; a gate at 2.1.136 makes it moot, and is above the existing 2.1.78 `StopFailure` gate.

**Where detection lives: the daemon.** The hooks, the plugin bus and the PTYs are all the daemon's, and the TUI and the desktop must answer identically (rule 18). Proposed shape, following the graded path:

- `AgentEvent` (`src/event.rs`) gains an additive optional `question` field (or a JSON string under one `metadata` key, which moves no wire at all), filled by `src/hook.rs` from `PermissionRequest` / `PreToolUse` (`AskUserQuestion`) for Claude, Codex and Devin, and from the plugin's forwarded `permission.asked` / `question.asked` for OpenCode (`src/opencode_manage.rs`).
- `SessionSnapshot` (`src/state.rs`) gains `pending_question: Option<PendingQuestion>`, `#[serde(default, skip_serializing_if = "Option::is_none")]` — no `PROTOCOL_VERSION` bump (`src/daemon_protocol.rs:11-14`). Set in `apply_event` on the question event; cleared on any event that proves the agent moved on (`ToolEnd`, `UserPromptSubmit`/`Thinking`, `Idle`, OpenCode's `permission.replied` / `question.replied`, and the deck's own answer). The keyboard-deny gap on Claude and Codex means "still pending" can be wrong after a keyboard answer; the staleness check below and, on Codex, the documented `Interrupt` hook are how that is contained.
- `PendingQuestion` = `{ id, kind: permission | choice | plan, summary, options: [{ index, label, description?, role: allow_once | allow_always | deny | choice | free_text }], multi: bool, raised_at_ms }`, where `id` is the agent's own (`tool_use_id` from Claude's `PreToolUse`, OpenCode's request id) or a deck-minted one. **Every text field is untrusted model output** (`docs/develop/voice-first-design.md` §6) and #1497 will speak it.

The daemon refuses unless `question_id` is the one pending now, then answers through the agent's own channel. The per-agent mapping belongs on `AgentSpec` (`src/agent_registry.rs`, "the single place per-agent data lives"), e.g. an `answer` handler beside `hook_install`.
- Answer channel per agent: **Claude — the `PermissionRequest` hook decision** (observed working, observed safe against a keyboard answer that wins the race, needs no option-to-key mapping, carries `AskUserQuestion` answers by label and makes a stale "yes" a no-op instead of a typed `1`). Its cost: the deck's hook process must hold a connection to the daemon until an answer or a timeout, one per open prompt, and the hook key needs the version gate above. **Codex — keys (`y` / `n`)** until it is measured whether a pending hook hides the prompt. **OpenCode — Enter / Esc** for permissions and digits for questions, moving to the plugin's reply API once a reply through it is measured to dismiss the TUI dialog.
- Files that would change: `src/event.rs`, `src/hook.rs`, `src/hooks_manage.rs`, `src/opencode_manage.rs`, `src/state.rs`, `src/daemon_protocol.rs`, `src/daemon.rs` / `src/daemon_attach.rs`, `src/agent_registry.rs`, `src/ui.rs` (`Action::SendPermissionResponse`), `desktop/src-tauri/src/daemon_bridge.rs`, `desktop/src-tauri/src/voice/outcome.rs` (`local_intercept`), `desktop/src-tauri/src/voice/choice.rs` (ordinal and label matching), `desktop/src/components/VoiceControlPanel.tsx` (`VoicePane`, the one `VoiceContext` gate), `desktop/src/types.ts`. **The shared model with #1497.** `PendingQuestion` on the snapshot *is* the model: #1497 reads `summary` and `options` to speak a prompt, this PRD answers by `id`. Neither keeps its own copy, and #1497 should not speak a prompt this snapshot does not carry, so the two cannot disagree about what is being asked.

**Phrase set, matched locally and whole-utterance** (the `voice/dictation.rs` reserved-set rule, live only while the pane on screen has a `pending_question`):

- allow: "yes", "allow", "approve", "yes allow", "allow it"
- deny: "no", "deny", "reject", "don't allow"
- always allow: "always allow" (see below)
- choice: "option N" / "number N" for N in 1..9, ordinals ("the first one", "the second one"), and an option's label as the whole utterance, through `voice::choice::answer`'s rules. A bare number is not offered, to keep dictated numbers dictatable.
- Options with `role: free_text` ("Type something.", "Chat about this", "None of the above", "Tell Claude what to change") are refused by voice with "answer that one by keyboard".

**"Always allow" by voice** — pros: it is the answer a hands-free user most wants on a repetitive prompt, and every supported agent offers one. Cons: it removes future prompts, its scope differs per agent and per prompt (Claude: a directory or rule for this project; Codex: a command prefix; OpenCode: the request's `always` patterns; Devin: five scopes), a mishearing is not undone by the next utterance, and on Codex the hook decision cannot express it at all (`updatedPermissions` fails closed). **Recommendation: offer it only through an on-screen confirmation that names its scope** (the D5 `ConfirmDialog` pattern), and not on Codex until its key `p` is measured. Not offering it at all is the safer fallback if the confirmation is judged too heavy for the first ship.

**Experimental flag (rule 9).** Recommendation: **yes**, behind a `show_voice_answers()` wrapper gated at the voice row and at the TUI's new behaviour. Reasons: the first ship covers three of five agents, Devin is unverified, Claude's path adds a hook key that needs a version gate, and an approval is consequential — this is a surface that should earn its default. Counter-argument worth weighing: the TUI half fixes a present bug (a false "Permission approved." on Claude and OpenCode), and a fix should not hide behind a flag; if that weighs more, gate only the voice phrases and ship the TUI change unflagged.

**Q3 — dashboard answering.** Recommendation: **the agent's own screen only** for this PRD, as scoped. The dashboard shows a status, not the question, and `pending_question.summary` is untrusted text that would have to be rendered in full, with the options, before "yes" could be safe there. The snapshot field makes a later dashboard design possible without new plumbing.

3. **Options drawn only on screen** — Claude's tool-permission and plan-approval menus, Codex's command-approval menu, the extra free-text options Claude Code, Codex and OpenCode append to a multiple-choice list, and any other menu whose labels are not in a payload — come from a **per-agent, per-version table** in the agent's registry entry, verified by lane-2 real-agent tests. The deck does not read the screen.
4. **Matching what the user says is the desktop's Commands model, not a phrase list.** It maps the utterance onto the options of the question pending now — by number, ordinal, the option's words, or a synonym such as "yes" / "go ahead" for an allow option. It may only return options from that list, or none, and the app validates its answer against the list locally. The answer is shown, sent after the existing five-second voice countdown (cancellable), and checked against the still-pending question (staleness) before it is sent.
5. **Multi-question forms.** The pending question carries the whole form: every question, its options, single or multiple choice, and its free-text options. The user answers in any order, in one utterance or several ("red for colour and large for size"; "red and blue" on a multiple-choice question), and the app shows the form filling in. When every question has an answer, the app sends the whole set after the countdown and the deck performs Next / Submit itself; the user never says "next" or "submit". Where the agent takes answers directly (Claude's `PermissionRequest` `updatedInput.answers`, OpenCode's reply API) the deck answers in one step instead of keys. Free-text options are filled by dictation.
6. **"Always allow" is offered**, but only after an on-screen confirmation in the desktop app that names its scope ("This will always allow … Confirm?" — click it or say "confirm"), and then the countdown.
7. **Detection lives in the daemon**, with no model and no user configuration: the daemon builds the pending question deterministically from hook, plugin and extension payloads plus decision 3's tables. The wire follows rule 18's graded path: an additive optional `pending_question` on the agent's snapshot (no `PROTOCOL_VERSION` bump) and a capability-gated `AttachRequest` variant to answer it (no bump; the capability check lives in the client library, as `focus_gained_while`'s does). Rule 12's cross-version check is run.
8. **One model, shared with #1497.** `pending_question` is the model; #1497 (voice "reading on", which will speak permission prompts — no PRD file, branch or PR exists for it yet) reads it. Nobody keeps a second copy.
9. **Desktop only, from the agent's own screen** — not the dashboard. **M4 is dropped**: the TUI's `y` / `n` (`Action::SendPermissionResponse`, `src/ui.rs`) is left unchanged.

## Risks

- **A misheard "yes" approves something.** Mitigated by the model being able to choose only among the pending options, local validation of its choice, the visible cancellable countdown, the pending-question and staleness checks, and a confirmation in front of "always allow".
- **The model selects an option while quoting real words that do not mean it — an accepted residual** (audit A1). Grounding checks that the words the model cites were said, not that they mean the option: "what time is it" cited whole for Allow once, or the "run that" of "no, don't run that", passes and arms the countdown. Decided (2026-10-04) to accept it rather than add a second confirmation to every approval, which would end hands-free answering: the countdown shows exactly what will be sent, speech stops it once detected and Cancel stops it, and "always allow" keeps its own confirmation word. Pinned as current behaviour by `question_desktop_007` and vitest `question/desktop/012`.
- **Agents change their prompts.** Options drawn only on screen come from per-version tables, which go stale on an agent upgrade. Mitigated by keying the tables on verified versions and by the lane-2 tests that pin them, which catch a change only when someone runs them (rule 5).
- **Pi's channel is undocumented.** It rests on `ctx.ui` staying a shared, mutable object. A Pi release that changes that loses Pi support; the lane-2 Pi test is what notices.
- **A held hook outlives its question.** On Claude, a keyboard "yes" does not end the waiting hook process [observed], so the daemon must release it on the next event; one that is not released waits until its hook timeout.
